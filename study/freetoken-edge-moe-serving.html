FreeToken: Efficient Edge-Native MoE Serving with Bandwidth-Adaptive Execution — paper note FreeToken: Efficient Edge-Native MoE Serving with Bandwidth-Adaptive Execution — 논문 정리

A Berkeley-led team asks what a personal computer could serve if the software stopped treating it as "a small datacenter GPU". The answer is startling: a 753B model on one workstation card, a 284B model on a gaming desktop, and a 35B model on an 8 GB laptop at 39 tok/s — faster than the median decode speed of Codex in production. The central idea is one line of algebra: when an expert misses the GPU cache, don't just fetch it — split the misses between PCIe transfer and in-place CPU execution in the exact ratio the machine's two measured bandwidths dictate. 버클리 주도 팀이 던지는 질문: 소프트웨어가 개인용 PC를 "작은 데이터센터 GPU"로 취급하기를 그만두면 무엇까지 서빙할 수 있는가. 답이 놀랍다 — 워크스테이션 카드 한 장으로 753B 모델, 게이밍 데스크톱으로 284B 모델, 8 GB 노트북으로 35B 모델을 39 tok/s에 돌린다. 프로덕션 Codex의 중앙값 디코드 속도보다 빠르다. 핵심 아이디어는 대수 한 줄이다: expert가 GPU 캐시에서 미스 났을 때 그냥 가져오지 말고, 그 미스들을 PCIe 전송과 CPU 직접 실행 사이에 그 기계의 측정된 두 대역폭이 정하는 정확한 비율로 나눠라.

one-line summary한 줄 요약 An MoE model activates few experts per token but stores all of them, so on a personal machine the expert pool lives in host RAM and every miss costs a PCIe transfer. Every prior system competes on predicting misses better. FreeToken's insight is that a missed expert is not only data to move but also work that can run where it already sits — so it splits each step's misses between PCIe fill and CPU execution at the ratio q* = m·B_P/B_H, derived from two bandwidths measured on the actual machine. Add full-layer double-buffered prefill, recurrent-state checkpoints anchored at the semantic boundaries agent harnesses actually edit, and an elastic GPU cache that resizes mid-session, and you get 1.5–2.3× decode over the best edge engine — with worst-case TTFT under 44 s where baselines hit 946 s. MoE 모델은 토큰당 소수의 expert만 활성화하지만 전부를 저장한다. 그래서 개인 PC에서는 expert 풀이 호스트 RAM에 살고, 미스가 날 때마다 PCIe 전송 비용을 낸다. 기존 시스템들은 전부 미스를 더 잘 예측하는 경쟁을 했다. FreeToken의 통찰은 미스 난 expert가 옮겨야 할 데이터일 뿐 아니라 이미 있는 자리에서 실행할 수 있는 일감이기도 하다는 것 — 그래서 매 스텝의 미스를 PCIe 채우기와 CPU 실행 사이에 q* = m·B_P/B_H 비율로 나눈다. 그 비율은 실제 기계에서 측정한 두 대역폭에서 유도된다. 여기에 레이어 단위 이중 버퍼 prefill, 에이전트 하네스가 실제로 편집하는 의미 경계에 앵커를 박은 recurrent state 체크포인트, 세션 도중 크기가 바뀌는 탄력적 GPU 캐시를 더하면 — 최고 성능 엣지 엔진 대비 디코드 1.5~2.3배, 그리고 베이스라인이 946초를 찍는 지점에서 최악 TTFT 44초 미만이 나온다.

📖 MoE, and why it's an edge story📖 MoE, 그리고 왜 엣지 이야기인가

A Mixture-of-Experts layer stores E experts but routes each token through only k ≪ E. DeepSeek-V4-Flash activates 6 of 256 experts in each of 43 layers — 13B of 284B parameters per token. The compute fits a consumer GPU; the storage does not.MoE 레이어는 expert를 E개 저장하지만 토큰마다 k ≪ E개만 거친다. DeepSeek-V4-Flash는 43개 레이어 각각에서 256개 중 6개를 활성화한다 — 토큰당 284B 중 13B. 연산량은 소비자용 GPU에 맞지만, 저장 용량은 안 맞는다.

📖 Prefill vs decode — opposite regimes📖 Prefill vs decode — 정반대 상황

Sparsity is a per-token property. Over a long prompt, the union of routes covers nearly every expert, so prefill is effectively dense. Decode is the opposite: genuinely sparse, but each miss is a separate stall. The two phases need opposite mechanisms.희소성은 토큰 단위 성질이다. 긴 프롬프트 전체에 대해서는 라우팅의 합집합이 거의 모든 expert를 덮으므로 prefill은 사실상 조밀하다. 디코드는 반대다 — 진짜 희소하지만 미스 하나하나가 별도의 지연이 된다. 두 단계에 정반대의 장치가 필요하다.

📖 BP and BH📖 BP와 BH

The two numbers the whole policy rests on. BP = measured host→device expert-transfer bandwidth over PCIe. BH = measured effective bandwidth of the CPU-side expert kernel. Both are measured on the deployed tensor shapes, not read off a spec sheet.정책 전체가 기대는 두 수치. BP = PCIe로 호스트→디바이스 expert 전송 대역폭 실측치. BH = CPU 쪽 expert 커널의 실효 대역폭 실측치. 둘 다 스펙 시트가 아니라 실제 배포된 텐서 모양에서 측정한 값이다.

📖 Expert cache miss📖 Expert 캐시 미스

The router picks experts; some are already in VRAM (hits, ℋ), some are not (misses, ℳ, count m). What to do with ℳ is the entire decode problem — and the question every prior system answered with "transfer it".라우터가 expert를 고르면 일부는 이미 VRAM에 있고(히트, ℋ) 일부는 없다(미스, ℳ, 개수 m). ℳ을 어떻게 할 것인가가 디코드 문제의 전부이고, 기존 시스템들은 전부 "전송한다"로 답했다.

📖 CUDA Graph📖 CUDA Graph

A pre-recorded, replayable sequence of GPU work that removes per-launch CPU overhead. The catch: the graph is static, so anything that changes per step — like which experts missed — normally forces a host sync and breaks it. §3 is about escaping that.미리 녹화해 두고 재생하는 GPU 작업 시퀀스로, 실행마다 드는 CPU 오버헤드를 없앤다. 함정은 그래프가 정적이라는 것 — 스텝마다 바뀌는 것(어떤 expert가 미스 났는지 같은)은 보통 호스트 동기화를 강제하고 그래프를 깬다. §3이 그걸 빠져나오는 이야기다.

📖 Agentic context editing📖 에이전트의 컨텍스트 편집

Agent harnesses rewrite history every turn — OpenClaw strips thinking blocks from all but the latest assistant turn, OpenCode replaces old tool outputs with a placeholder. Any cached state saved after the edited position becomes invalid, forcing re-prefill.에이전트 하네스는 턴마다 히스토리를 다시 쓴다 — OpenClaw는 최신 턴을 뺀 모든 어시스턴트 턴에서 thinking 블록을 제거하고, OpenCode는 오래된 도구 출력을 placeholder로 바꾼다. 편집 위치 이후에 저장된 캐시 상태는 전부 무효가 되어 re-prefill을 강제한다.

① Prefill: transfer cost + repeated recomputation (§2.1)① Prefill: 전송 비용 + 반복 재계산 (§2.1)

"A prefill pass therefore streams almost the complete expert pool through the CPU–GPU interconnect. This introduces a severe I/O overhead that a VRAM-resident deployment would not perform at all."

— §2.1 · 원문 보기 (§2.1)

Concretely, for FP4 DeepSeek-V4-Flash that is ~140 GB of expert weights per prefill: ~2 s on an RTX 5090 (PCIe 5.0 ×16, ~60 GB/s), ~5 s on 4090/3090-class desktops (PCIe 4.0 ×16, ~25 GB/s), and 10 s or more on the ×8 links common in laptops. An engine that fetches on demand exposes that entire window as GPU idle time.

구체적으로 FP4 DeepSeek-V4-Flash 기준 prefill 한 번에 약 140 GB의 expert 가중치입니다: RTX 5090에서 약 2초(PCIe 5.0 ×16, ~60 GB/s), 4090/3090급 데스크톱에서 약 5초(PCIe 4.0 ×16, ~25 GB/s), 노트북에 흔한 ×8 링크에서는 10초 이상. 필요할 때 가져오는 방식의 엔진은 그 시간 전체를 GPU 유휴 시간으로 노출합니다.

The second half of the prefill problem is subtler and is the part most systems ignore. Modern frontier models use hybrid attention — interleaving full attention with sliding-window attention (DeepSeek-V4-Flash, GPT-OSS) or with recurrent layers (gated DeltaNet in Qwen3.6-35B-A3B, Kimi Delta Attention in Kimi-K3). A recurrent layer compresses the entire prefix into one evolving state, which cannot be partially reused. Each saved state costs as much memory as hundreds of tokens of KV cache, so engines keep only a few checkpoints. Then the agent harness edits the context — and any checkpoint after the edit point is dead, forcing a re-prefill of thousands of tokens on a GPU that delivers roughly a fifth of an H100's dense BF16 throughput.

prefill 문제의 나머지 절반은 더 미묘하고, 대부분의 시스템이 무시하는 부분입니다. 요즘 프론티어 모델은 하이브리드 어텐션을 씁니다 — full attention과 sliding-window attention을 교대하거나(DeepSeek-V4-Flash, GPT-OSS), recurrent 레이어와 섞습니다(Qwen3.6-35B-A3B의 gated DeltaNet, Kimi-K3의 Kimi Delta Attention). recurrent 레이어는 prefix 전체를 진화하는 상태 하나로 압축하는데, 부분 재사용이 불가능합니다. 저장된 상태 하나가 수백 토큰치 KV 캐시만큼 메모리를 먹어서 엔진은 체크포인트를 몇 개만 유지합니다. 그런데 에이전트 하네스가 컨텍스트를 편집하면 — 편집 지점 이후의 체크포인트는 전부 죽고, H100의 약 5분의 1에 해당하는 dense BF16 성능을 가진 GPU에서 수천 토큰을 다시 prefill해야 합니다.

② Decode: static placement misses, and the CPU can't carry it alone (§2.2)② Decode: 정적 배치는 빗나가고, CPU 혼자로는 못 버틴다 (§2.2)

Three findings stack here. First, existing engines freeze expert placement at load or prefill time — llama.cpp assigns MoE tensors to devices at load, KTransformers pins a "hot" subset in VRAM and runs the rest on CPU:

여기서는 세 가지 발견이 겹칩니다. 첫째, 기존 엔진들은 expert 배치를 로드 시점이나 prefill 시점에 고정합니다 — llama.cpp는 로드할 때 MoE 텐서를 디바이스에 할당하고, KTransformers는 "hot" 부분집합을 VRAM에 고정하고 나머지는 CPU에서 돌립니다:

"However, routing shifts with every token and every workload. A placement frozen at prefill time captures only a small fraction of the routed traffic. Consequently, the majority of expert evaluations fall to the CPU, leaving both the GPU and the PCIe link idle."

— §2.2 · 원문 보기 (§2.2)

Second, the CPU cannot absorb the remainder. Consumer platforms attach the CPU to two DRAM channels: roughly 50 GB/s for dual-channel DDR4, 80–90 GB/s for DDR5 — against the 1–1.8 TB/s an RTX 4090 or 5090 draws from its on-package memory. At small decode batches expert execution is memory-bound, so that gap caps a CPU-only path at a small fraction of the VRAM rate regardless of core count.

둘째, CPU가 나머지를 흡수할 수 없습니다. 소비자용 플랫폼은 CPU에 DRAM 채널 2개를 붙입니다: 듀얼 채널 DDR4가 약 50 GB/s, DDR5가 80~90 GB/s — RTX 4090이나 5090이 온패키지 메모리에서 끌어오는 1~1.8 TB/s와 대비됩니다. 작은 디코드 배치에서 expert 실행은 메모리 바운드이므로, 이 격차는 코어 수와 무관하게 CPU 전용 경로를 VRAM 속도의 일부로 묶어 버립니다.

Third — and this is the hinge of the paper — the correct division between the two paths is machine-specific and not derivable from spec sheets:

셋째 — 그리고 이게 논문의 경첩입니다 — 두 경로 사이의 올바른 분배는 기계마다 다르고 스펙 시트에서 유도할 수 없습니다:

"Relying on transfer alone leaves residual host bandwidth and CPU cores idle whenever host memory can deliver more bytes than the link can move. Conversely, relying on CPU execution alone leaves the PCIe link idle and forfeits the future hits that a cache fill would buy. […] This optimal mixture cannot be read from specification sheets."

— §2.2 · 원문 보기 (§2.2)

③ Nothing on the edge is dedicated (§2.3)③ 엣지에서는 어떤 자원도 전용이 아니다 (§2.3)

A datacenter GPU serves one workload. A personal GPU shares VRAM with the desktop compositor, a browser, and possibly a game, each of which can claim gigabytes at any moment. Worse, the right split of the budget also moves: agentic sessions accumulate context, so KV demand grows while the expert working set stays roughly fixed — a split chosen on turn 1 is wrong by turn 20. And startup recurs, because users open and close the engine: reading a 140 GB pool from a 7 GB/s NVMe takes about 20 s before any warmup.

데이터센터 GPU는 워크로드 하나를 서빙합니다. 개인용 GPU는 데스크톱 컴포지터, 브라우저, 어쩌면 게임과 VRAM을 나눠 쓰고, 각각이 언제든 기가바이트 단위를 가져갈 수 있습니다. 더 나쁜 건 예산의 올바른 분배 비율도 움직인다는 것입니다: 에이전트 세션은 컨텍스트를 쌓으므로 KV 수요가 커지는데 expert 워킹셋은 대체로 고정입니다 — 1턴에 정한 분배가 20턴에는 틀립니다. 그리고 사용자가 엔진을 켰다 껐다 하므로 시작 비용이 반복됩니다: 7 GB/s NVMe에서 140 GB 풀을 읽는 데만 워밍업 전에 약 20초가 걸립니다.

2 Method — bandwidth-adaptive execution and semantic-aware caching 해결 방법 — 대역폭 적응 실행과 의미 인식 캐싱

모든 것이 구조적 결정 하나에 기댑니다: CPU에 상주하는 expert 풀이 진실의 원천이라는 것. expert가 아닌 가중치는 GPU에 영구 상주하고, 남는 GPU 메모리 전부가 모든 MoE 레이어가 공유하는 단일 탄력 expert 캐시가 됩니다. 슬롯 하나가 한 (레이어, expert) 쌍을 평가하는 데 필요한 텐서 전부를 담으므로, 상주·조회·실행이 텐서 조각이 아니라 논리적 (layer, expert) 식별자로 이야기합니다.

The crucial physical fact — and the reason this isn't just "do some of each" — is that both branches draw from the same host-memory subsystem. A DMA transfer to the GPU and a CPU kernel reading expert weights are competing for the same DRAM controllers. So a saturated PCIe transfer does not leave the CPU the full host bandwidth; it leaves only what's left over:

결정적인 물리적 사실 — 그리고 이게 그냥 "둘 다 조금씩 하자"가 아닌 이유 — 는 두 경로가 같은 호스트 메모리 서브시스템에서 읽는다는 것입니다. GPU로 가는 DMA 전송과 expert 가중치를 읽는 CPU 커널이 같은 DRAM 컨트롤러를 두고 경쟁합니다. 그래서 포화된 PCIe 전송은 CPU에 호스트 대역폭 전부를 남겨주지 않고, 남은 것만 남깁니다:

BR = max( BH − BP , 0 ) — Eq. 2, the residual bandwidth

Now let S be the size in bytes of one complete expert. The two branches run concurrently, and each is bandwidth-bound, so their times are just bytes ÷ bandwidth:

이제 S를 expert 하나의 바이트 크기라고 합시다. 두 경로는 동시에 돌고 각각 대역폭 바운드이므로, 시간은 그냥 바이트 ÷ 대역폭입니다:

Tfill(q) ≈ qS / BP Tcpu(m−q) ≈ (m−q)S / (BH − BP) — Eq. 3

Because they are concurrent, the exposed layer latency is the slower of the two. One term grows with q and the other shrinks with q, so the maximum is smallest exactly where they cross. Set them equal and turn the crank:

q⋆ ≈ m · BP / BH — Eq. 4

Two things are worth pausing on. First, S cancels — the answer doesn't depend on how big an expert is, only on the machine's bandwidth ratio. Second, the messy residual term B_H − B_P from Eq. 2 disappears from the final answer, leaving a plain ratio of the two raw measured bandwidths. That is why this is cheap enough to evaluate inside a GPU kernel every layer (§3).

Sanity check at the extreme: as BH → BP (host memory no faster than the link), q* → m — every miss goes to PCIe and the system gracefully degenerates into plain on-demand cache fill, with no separate branch needed.

두 가지를 짚어둘 만합니다. 첫째, S가 소거됩니다 — 답이 expert 크기와 무관하고 오직 기계의 대역폭 비율에만 의존합니다. 둘째, Eq. 2의 지저분한 잔여 항 B_H − B_P가 최종 답에서 사라지고 측정된 두 원시 대역폭의 단순한 비만 남습니다. 그래서 이 계산이 매 레이어마다 GPU 커널 안에서 평가할 만큼 싼 것입니다(§3).

3.1 — The problem: everything about this cache changes every step 3.1 — 문제: 이 캐시는 모든 것이 스텝마다 바뀐다

A CUDA Graph is a pre-recorded, replayable sequence of GPU work; replaying it removes per-launch CPU overhead, which matters enormously at small decode batch sizes where launch overhead is a real fraction of step time. The catch is that the graph is static. And FreeToken's cache is the opposite of static:

CUDA Graph는 미리 녹화해 재생하는 GPU 작업 시퀀스입니다. 재생하면 실행마다 드는 CPU 오버헤드가 사라지는데, 실행 오버헤드가 스텝 시간의 실질적인 몫을 차지하는 작은 디코드 배치에서 매우 중요합니다. 함정은 그래프가 정적이라는 것이고, FreeToken의 캐시는 정적의 정반대입니다:

"Expert caching is inherently dynamic: the specific experts that miss, the number of experts fetched, and the slots evicted all change at every step. Consequently, a host-controlled cache would reintroduce a costly device synchronization at every MoE layer."

— §4.1 · 원문 보기 (§4.1)

Think about what a naive implementation forces. The router runs on the GPU. To decide what to evict and fetch, the host needs those routing results — so it syncs, reads them back, decides in Python, and launches copies. That's a full device sync per MoE layer, per token. On a 43-layer model at 25 tok/s that's over a thousand synchronizations a second, each one draining the pipeline.

순진한 구현이 무엇을 강제하는지 생각해 봅시다. 라우터는 GPU에서 돕니다. 무엇을 evict하고 fetch할지 결정하려면 호스트가 그 라우팅 결과를 알아야 하니 — 동기화하고, 읽어오고, 파이썬에서 결정하고, 복사를 띄웁니다. MoE 레이어마다, 토큰마다 전체 디바이스 동기화입니다. 43레이어 모델을 25 tok/s로 돌리면 초당 천 번이 넘는 동기화이고, 매번 파이프라인을 비웁니다.

FreeToken's answer is a reframe: keep all routing-dependent control on the GPU, and express the dynamism as data flowing through fixed-shape buffers rather than as control flow the host has to see. The graph's shape never changes; only the numbers inside it do.

FreeToken의 답은 관점 전환입니다: 라우팅에 의존하는 제어를 전부 GPU에 두고, 동적인 부분을 호스트가 봐야 하는 제어 흐름이 아니라 고정된 모양의 버퍼를 흐르는 데이터로 표현하는 것. 그래프의 모양은 절대 안 바뀌고, 그 안의 숫자만 바뀝니다.

3.2 — One kernel does all the thinking 3.2 — 커널 하나가 모든 판단을 한다

Per MoE layer, a single GPU kernel performs the entire cache decision. Read the list slowly — this is a lot to put in one kernel:

Step 5 is the quiet trick: after this kernel, downstream code no longer needs to know why an expert is where it is. A slot ID means "read VRAM here", the CPU flag means "the host will handle it". The heterogeneity is erased into a uniform index list.

5번이 조용한 요령입니다. 이 커널 이후로 하류 코드는 어떤 expert가 왜 거기 있는지 알 필요가 없습니다. 슬롯 ID는 "여기 VRAM을 읽어라", CPU 플래그는 "호스트가 처리한다"는 뜻일 뿐입니다. 이질성이 균일한 인덱스 목록으로 지워집니다.

Single-pass victim selection한 번의 순회로 끝내는 희생자 선택

"Victim selection avoids the classic LRU trap of requiring one full-cache scan per evicted slot. Instead, a single-pass kernel identifies the K least-recently-used candidate slots for eviction in one go. The miss path then simply consumes the first q ≤ K of these slots. As a result, victim discovery always costs exactly one pass, regardless of the realized miss count."

— §4.1 ("Device-side cache control") · 원문 보기 (§4.1)

Plainly: a textbook LRU eviction scans the cache to find the single oldest entry, so evicting q entries costs q scans — and q varies per step, which would also make the work non-fixed-shape and thus un-capturable. Finding the K oldest in one pass and then taking however many you need makes the cost constant and the shape static. Two problems, one fix.

쉽게 말하면: 교과서적 LRU eviction은 가장 오래된 항목 하나를 찾으려고 캐시를 훑으므로 q개를 내보내려면 q번 훑어야 합니다 — 게다가 q는 스텝마다 달라지므로 작업 모양도 고정되지 않아 캡처가 불가능해집니다. 한 번의 순회로 K개의 가장 오래된 것을 찾아두고 필요한 만큼만 가져가면 비용이 상수가 되고 동시에 모양이 정적이 됩니다. 문제 두 개를 한 수로 해결합니다.

The resulting copy work list then drives a single fused transfer. Because every expert bank shares the same logical expert-to-slot mapping (§3.3 below), one device-resident source/destination index list applies to all banks in a single fixed-shape launch, with a valid count masking the unused entries.

그렇게 나온 복사 작업 목록이 하나의 융합된 전송을 구동합니다. 모든 expert bank가 같은 논리적 expert→슬롯 매핑을 공유하므로(아래 §3.3), 디바이스에 상주하는 source/destination 인덱스 목록 하나가 고정된 모양의 launch 한 번으로 모든 bank에 적용되고, valid count가 안 쓰는 항목을 마스킹합니다.

The CPU branch lives inside the graph tooCPU 분기도 그래프 안에 산다

This is the part I'd have expected to break. The CPU branch is captured into the same graph: for each supported decode batch size, FreeToken prepares stable pinned I/O buffers and persistent task descriptors, then captures the device-to-host copies, a host-function submit node, the concurrent GPU path, a synchronization node, and the host-to-device result copy — all together. Replay re-executes the full heterogeneous step with no per-token Python scheduling at all.

깨질 거라고 예상했던 부분이 이쪽입니다. CPU 분기가 같은 그래프 안에 캡처됩니다. 지원하는 디코드 배치 크기마다 안정적인 pinned I/O 버퍼와 영속 task descriptor를 준비한 뒤, device-to-host 복사, host-function submit 노드, 동시 실행되는 GPU 경로, 동기화 노드, host-to-device 결과 복사를 전부 함께 캡처합니다. 재생하면 토큰당 파이썬 스케줄링 없이 이질적인 스텝 전체가 다시 실행됩니다.

The workers themselves are a persistent C++ pool pinned to physical cores, using architecture-specific SIMD and in-kernel dequantization — which is what keeps that path bandwidth-bound rather than compute-bound, and therefore what makes BH a meaningful constant in Eq. 4. They return gate-weighted, per-token partial outputs, ready to merge.

워커 자체는 물리 코어에 고정된 영속 C++ 풀이고, 아키텍처별 SIMD와 커널 내 역양자화를 씁니다 — 이게 그 경로를 연산 바운드가 아니라 대역폭 바운드로 유지하고, 따라서 Eq. 4에서 BH를 의미 있는 상수로 만들어 줍니다. 워커는 gate 가중치가 적용된 토큰별 부분 출력을 반환해 병합할 준비를 마칩니다.

3.3 — Expert banks, the FTW format, and graceful degradation 3.3 — Expert bank, FTW 포맷, 그리고 우아한 성능 저하

Different checkpoints lay out MoE weights differently. FreeToken normalizes all of them into a small set of expert banks, each using the flattened identifier l·E + e as its leading dimension. Rows sharing that identifier across all banks collectively form one complete expert — so GPU kernels and the CPU executor share one logical expert identity regardless of the underlying physical format. That shared identity is exactly what makes the single fused index list of §3.2 possible.

체크포인트마다 MoE 가중치 배치가 다릅니다. FreeToken은 그걸 전부 소수의 expert bank로 정규화하고, 각 bank는 평탄화된 식별자 l·E + e를 선행 차원으로 씁니다. 모든 bank에서 그 식별자를 공유하는 행들이 모여 완전한 expert 하나를 이룹니다 — 그래서 GPU 커널과 CPU 실행기가 물리 포맷과 무관하게 하나의 논리적 expert 정체성을 공유합니다. 그 공유된 정체성이 정확히 §3.2의 단일 융합 인덱스 목록을 가능하게 만드는 것입니다.

The FTW (FreeToken Weight) format then stores expert weights pre-merged into that runtime bank layout, so launch skips tensor discovery and repacking entirely: it reads aligned chunks with parallel direct I/O straight into exact-size host banks, pinned only after they're filled (§2.3).

FTW (FreeToken Weight) 포맷은 expert 가중치를 그 런타임 bank 레이아웃으로 미리 병합해 저장합니다. 그래서 실행 시 텐서 탐색과 재포장을 통째로 건너뛰고, 정렬된 청크를 병렬 direct I/O로 정확한 크기의 호스트 bank에 바로 읽어 들인 뒤 다 채워지고 나서야 pin합니다(§2.3).

the fallback path is worth noting폴백 경로를 짚어둘 만하다 On some operating systems and driver configurations the complete expert pool cannot be pinned or registered for DMA. Rather than failing, FreeToken degrades to a pure-CPU MoE backend: expert weights stay in pageable host storage, all routed experts execute on the CPU, non-expert layers remain on the GPU, and only activation-sized inputs, routing metadata and aggregated outputs cross the boundary. It trades peak transfer bandwidth for deployability — which for software meant to run on machines users already own is the right trade, and a detail research prototypes usually skip. 일부 운영체제와 드라이버 구성에서는 완전한 expert 풀을 pin하거나 DMA용으로 등록할 수 없습니다. FreeToken은 실패하는 대신 순수 CPU MoE 백엔드로 낮춰 갑니다: expert 가중치는 pageable 호스트 저장소에 남고, 라우팅된 expert는 전부 CPU에서 실행되며, expert가 아닌 레이어는 GPU에 남고, 활성값 크기의 입력·라우팅 메타데이터·집계된 출력만 경계를 넘습니다. 최대 전송 대역폭을 배포 가능성과 맞바꾸는 것인데 — 사용자가 이미 가진 기계에서 돌아야 하는 소프트웨어에는 옳은 교환이고, 연구 프로토타입이 대개 건너뛰는 디테일입니다.

That's careful methodology — but it is still emulation, and the emulated boxes are where most of the headline numbers come from. 여섯 대 중 셋 — 3090, 4090, 5090 서버 — 은 엣지 기기가 아니라 임대한 듀얼 소켓 서버입니다. 저자들은 이를 솔직히 밝히고 올바른 예방책을 씁니다: 모든 실행을 CPU 스레드 6개로 제한하고 GPU의 NUMA 노드에 고정해 호스트 대역폭을 56.7~77.3 GB/s로 맞춥니다. 진짜 엣지 기계 두 대가 자연스러운 전체 스레드 수에서 내는 것과 같은 규모죠(데스크톱 16코어 53.8 GB/s, 노트북 14코어 47.5 GB/s). 데스크톱과 노트북은 제한 없이 돌려서 이 에뮬레이션을 검증하는 역할을 합니다. 신중한 방법론입니다 — 그래도 에뮬레이션이고, 대표 수치 대부분이 그 에뮬레이션된 기계에서 나옵니다.

4.3 — Where the gains actually come from 4.3 — 이득이 실제로 어디서 나오는가

Two ablations, each targeting one mechanism.

① Pipelined prefill makes prefill transfer-bound① 파이프라인 prefill이 prefill을 전송 바운드로 만든다

With overlap on, each 8,192-token prefill chunk completes in 1.19–1.22 s — which is exactly the time to stream the 64.4 GB expert pool once at 52.7 GB/s, the practical ceiling of a PCIe 5.0 ×16 link. Expert computation is therefore fully hidden, and throughput climbs to 6.7k tok/s at 16k tokens. Disabling the second buffer serializes transfer against computation and costs 19% / 25% / 26% of throughput at 4k / 8k / 16k tokens — the penalty growing with prompt length because there is more computation to hide.

오버랩을 켜면 8,192 토큰짜리 prefill 청크가 1.19~1.22초에 끝납니다 — 정확히 64.4 GB expert 풀을 52.7 GB/s로 한 번 스트리밍하는 시간이고, PCIe 5.0 ×16 링크의 실질적 상한입니다. 즉 expert 연산이 완전히 숨겨지고, 처리량이 16k 토큰에서 6.7k tok/s까지 오릅니다. 두 번째 버퍼를 끄면 전송과 연산이 직렬화되어 4k / 8k / 16k 토큰에서 처리량의 19% / 25% / 26%를 잃습니다 — 숨길 연산이 더 많아지므로 프롬프트가 길수록 손해가 커집니다.

4.5 — The limitations section that isn't there 4.5 — 없는 한계 절

editor's note — the paper states no limitations; these are mine편집자 주 — 논문에 한계 절이 없다, 아래는 내가 도출한 것 The word "limitation" does not appear anywhere in this paper, and there is no threats-to-validity discussion. For a systems paper this thorough that's a conspicuous gap, so here is what I'd want addressed:

① The emulation carries the headline numbers. Three of six machines are rented servers throttled to 6 threads. The validation against two real edge boxes is genuine and reassuring, but §5.2's main figure runs on the emulated 5090.
② No accuracy verification is reported. The exactness claim ("preserving the exact MoE output without algorithmic approximation") is architectural and I believe it — but with a CPU branch doing in-kernel dequantization in a different SIMD path from the GPU kernel, a numerical-parity check against a VRAM-resident reference is exactly the experiment a reader wants, and it isn't there.
③ q* uses statically profiled bandwidths. §2.3 argues forcefully that edge resources fluctuate — browsers, games, other apps. But BH and BP are "empirically profiled on the target hardware at deployment". If a background process is hammering DRAM, the real BH drops and q* is stale. The elastic memory manager adapts VRAM at runtime; the bandwidth model does not adapt at all. That's an odd asymmetry given the paper's own framing.
④ Single-stream, small-batch regime. The whole q* derivation assumes expert execution is memory-bound, which holds "at small decode batches". Concurrency shows up in W3 via subagents, but the batch-size boundary where the model stops holding is never characterized.
⑤ No power or thermal data. On a laptop — arguably the flagship result — sustained 39.3 tok/s with saturated PCIe and all cores busy raises battery and throttling questions that a datacenter paper could ignore and an edge paper cannot.
⑥ Trajectory divergence. §5.1 notes agent trajectories differ across engines so wall-clock totals aren't compared — a fair call, but it means "solves the SWE issue" is the only end-to-end equivalence, and per-request means are being compared across runs that did different amounts of work. 이 논문 어디에도 "limitation"이라는 단어가 없고 threats-to-validity 논의도 없습니다. 이만큼 꼼꼼한 시스템 논문치고는 눈에 띄는 공백이라, 제가 짚고 싶은 것들입니다:

① 대표 수치를 에뮬레이션이 떠받칩니다. 6대 중 3대가 스레드 6개로 조인 임대 서버입니다. 진짜 엣지 기계 두 대로 하는 검증은 진지하고 안심되지만, §5.2의 메인 그림은 에뮬레이션된 5090에서 돕니다.
② 정확도 검증이 보고되지 않습니다. 정확성 주장("preserving the exact MoE output without algorithmic approximation")은 구조적인 것이고 저도 믿습니다 — 하지만 CPU 분기가 GPU 커널과 다른 SIMD 경로에서 커널 내 역양자화를 하는 만큼, VRAM 상주 기준값과의 수치 동등성 검사야말로 독자가 원하는 실험인데 없습니다.
③ q*가 정적으로 프로파일링한 대역폭을 씁니다. §2.3은 엣지 자원이 요동친다고 강력히 주장합니다 — 브라우저, 게임, 다른 앱. 그런데 BH와 BP는 "배포 시점에 대상 하드웨어에서 경험적으로 프로파일링"됩니다. 백그라운드 프로세스가 DRAM을 두들기면 실제 BH가 떨어지고 q*는 낡은 값이 됩니다. 탄력적 메모리 관리자는 VRAM을 런타임에 조정하는데, 대역폭 모델은 전혀 조정되지 않습니다. 논문 자신의 문제 설정에 비춰 이상한 비대칭입니다.
④ 단일 스트림·소배치 영역. q* 유도 전체가 expert 실행이 메모리 바운드라는 가정 위에 있고, 이는 "작은 디코드 배치에서" 성립합니다. W3에서 서브에이전트로 동시성이 등장하지만, 이 모델이 성립하지 않게 되는 배치 크기 경계는 전혀 특성화되지 않습니다.
⑤ 전력·발열 데이터가 없습니다. 노트북에서 — 어쩌면 이 논문의 간판 결과에서 — PCIe를 포화시키고 전 코어를 굴리며 39.3 tok/s를 지속하는 것은 배터리와 스로틀링 질문을 낳습니다. 데이터센터 논문은 무시해도 되지만 엣지 논문은 그럴 수 없습니다.
⑥ 트레이젝토리 발산. §5.1이 에이전트 트레이젝토리가 엔진마다 달라 벽시계 총합을 비교하지 않는다고 밝힙니다 — 타당한 판단이지만, 그러면 "SWE 이슈를 푼다"가 유일한 end-to-end 동치 조건이 되고, 요청당 평균값을 서로 다른 양의 일을 한 실행끼리 비교하게 됩니다.

5.2 — Our read (not the paper's claims)5.2 — 우리 관점의 해석 (논문의 주장 아님)

editor's note — reading an edge paper from the cluster side편집자 주 — 엣지 논문을 클러스터 쪽에서 읽기 This is edge research and we work at cluster scale, so the honest question is which parts translate. My read:

① The reframe transfers; the formula does not. The durable idea is "a miss is work, not just data" — when something isn't where you need it, fetching is only one of two options, and the split should be sized from measured ratios per step rather than fixed in config. We already meet that shape elsewhere: CMX exists because reloading a cached prefix from NVMe (~6 s) became faster than recomputing it (~11 s at 128K) — the same fetch-vs-recompute decision, different tier. What does not transfer is q* = m·B_P/B_H itself: it assumes CPU expert execution is a real alternative, which needs consumer-class host bandwidth per GPU and an idle CPU. In a datacenter the interesting pair is remote-fetch vs local-recompute, or NVMe vs recompute — same algebra, different B's.

② "Tail TTFT is an availability boundary, not a latency statistic" is the line to steal. This is directly actionable for gateway/SLO work. Agent clients ship watchdogs — OpenClaw at 120 s, Claude Code at ~10 min — so a p99 TTFT past those isn't a slow request, it's a failed one, and a mean-based dashboard shows nothing. Any SLO we define for agentic traffic should have the client's abandonment threshold in it explicitly.

③ On semantic-aware routing. FreeToken's "semantic-aware" is narrower than the name suggests — it is checkpoint placement for recurrent state, anchored where agent harnesses truncate. The transferable insight for a prefix-cache-aware router is the same premise: harnesses edit at block boundaries marked by special tokens and preserve the exact prefix before them. If that's true, then cache keys, radix-tree split points and routing affinity should all be aligned to those boundaries rather than to arbitrary token offsets — you'd get higher reuse for free, and it costs only a tokenizer-level check. That premise is cheap to validate against our own traces.

④ On expert pinning vs EPLB — careful, these optimize different things. FreeToken's LRU decides which experts occupy scarce VRAM on one machine to minimize miss rate. EPLB / expert permutation decides how experts are distributed across ranks to minimize load imbalance. Different objectives, and FreeToken's result doesn't automatically carry over. What is suggestive is §5.3: routing-following residency beat placement-fixed-at-prefill-time by 2.6× and 1.5× in miss rate at equal capacity (16% vs 41%, 39% vs 59%). If an analogous gap exists between continuously-adapted and periodically-recomputed expert placement at cluster scale, that's worth measuring — but the economics differ sharply, since a VRAM slot fill is a PCIe copy while a cluster rebalance moves weights between ranks. The open question is whether rebalancing can be amortized the way a cache fill can; I'd want that measured before assuming it.

⑤ What I'd actually verify first. The artifact is Apache-2.0 and built on the same SGLang/vLLM substrate we use, so the mechanisms are architecturally portable. But §4.5's gaps bite hardest exactly where we'd care: the q* model assumes small-batch, memory-bound decode, and cluster serving runs large batches where expert execution turns compute-bound and the derivation stops holding. Before borrowing anything, I'd want the batch-size boundary characterized — the paper never does. 엣지 연구이고 우리는 클러스터 규모에서 일하므로, 정직한 질문은 어느 부분이 옮겨오는가입니다. 제 판단:

① 관점은 옮겨오고, 공식은 안 옮겨옵니다. 오래 남을 아이디어는 "미스는 데이터가 아니라 일감이다"입니다 — 필요한 곳에 없을 때 가져오는 건 두 선택지 중 하나일 뿐이고, 그 분배는 config에 고정할 게 아니라 스텝마다 측정된 비율로 정해야 한다는 것. 우리도 이미 같은 모양을 만납니다: CMX가 존재하는 이유가 NVMe에서 캐시된 prefix를 다시 읽는 게(~6초) 재계산보다 빨라졌기 때문(128K에서 ~11초)이죠 — 같은 fetch-vs-recompute 결정, 다른 계층. 안 옮겨오는 건 q* = m·B_P/B_H 자체입니다. CPU expert 실행이 실질적 대안이라는 가정이 필요한데, 그러려면 GPU당 소비자급 호스트 대역폭과 놀고 있는 CPU가 있어야 합니다. 데이터센터에서 흥미로운 쌍은 원격 fetch vs 로컬 재계산, 또는 NVMe vs 재계산입니다 — 같은 대수, 다른 B.

② "Tail TTFT는 지연 통계가 아니라 가용성 경계다"는 훔쳐올 문장입니다. 게이트웨이/SLO 작업에 바로 적용됩니다. 에이전트 클라이언트는 watchdog을 기본 탑재합니다 — OpenClaw 120초, Claude Code 약 10분 — 그러니 그걸 넘긴 p99 TTFT는 느린 요청이 아니라 실패한 요청이고, 평균 기반 대시보드에는 아무것도 안 보입니다. 에이전트 트래픽에 대해 정의하는 SLO에는 클라이언트의 포기 임계값이 명시적으로 들어가야 합니다.

③ Semantic-aware routing에 대해. FreeToken의 "semantic-aware"는 이름보다 좁습니다 — recurrent 상태의 체크포인트 배치이고, 에이전트 하네스가 자르는 자리에 앵커를 박는 것입니다. prefix-cache 인식 라우터로 옮겨올 통찰은 그 전제입니다: 하네스는 특수 토큰으로 표시된 블록 경계에서 편집하고 그 앞의 prefix는 정확히 보존한다는 것. 이게 사실이라면 캐시 키, radix 트리 분할 지점, 라우팅 어피니티를 임의의 토큰 오프셋이 아니라 그 경계에 맞춰야 합니다 — 재사용률을 공짜로 올리고, 비용은 토크나이저 수준 검사 하나입니다. 이 전제는 우리 트레이스로 싸게 검증할 수 있습니다.

④ Expert pinning vs EPLB — 주의, 둘은 다른 것을 최적화합니다. FreeToken의 LRU는 한 기계의 부족한 VRAM을 어떤 expert가 차지할지를 정해 미스율을 최소화합니다. EPLB/expert permutation은 expert를 랭크들에 어떻게 분산할지를 정해 부하 불균형을 최소화합니다. 목적이 다르고, FreeToken의 결과가 자동으로 이어지지 않습니다. 다만 시사적인 건 §5.3입니다: 라우팅을 따라가는 상주가 prefill 시점 고정 배치를 같은 용량에서 미스율 2.6배, 1.5배로 이겼습니다(16% vs 41%, 39% vs 59%). 클러스터 규모에서 연속 적응 배치와 주기적 재계산 배치 사이에 비슷한 격차가 있다면 측정해 볼 값어치가 있습니다 — 다만 경제성이 크게 다릅니다. VRAM 슬롯 채우기는 PCIe 복사인데 클러스터 재조정은 랭크 간 가중치 이동이니까요. 재조정 비용을 캐시 fill처럼 상각할 수 있는지가 열린 질문이고, 저라면 가정하기 전에 측정하겠습니다.

⑤ 먼저 검증할 것. 아티팩트가 Apache-2.0이고 우리가 쓰는 것과 같은 SGLang/vLLM 기반 위에 있어서 장치들이 구조적으로 이식 가능합니다. 그런데 §4.5의 공백이 하필 우리가 신경 쓰는 지점을 물어뜯습니다: q* 모델은 소배치·메모리 바운드 디코드를 가정하는데, 클러스터 서빙은 큰 배치로 돌고 그러면 expert 실행이 연산 바운드로 바뀌어 유도가 성립하지 않습니다. 무언가를 빌려오기 전에 배치 크기 경계를 특성화하고 싶습니다 — 논문은 그걸 하지 않습니다.
