FreeToken: Efficient Edge-Native MoE Serving with Bandwidth-Adaptive Execution — paper note FreeToken: Efficient Edge-Native MoE Serving with Bandwidth-Adaptive Execution · 논문 정리

A Berkeley-led team asks what a personal computer could serve if software stopped treating it as "a small datacenter GPU": a 753B model on one workstation card, a 284B model on a gaming desktop, and a 35B model on an 8 GB laptop at 39 tok/s, faster than the median decode speed of Codex in production. The core idea: split each step's expert-cache misses between PCIe transfer and in-place CPU execution, in the ratio set by the machine's two measured bandwidths. 버클리 주도 팀이 개인 PC를 "작은 데이터센터 GPU"로 보지 않으면 무엇까지 서빙할 수 있는지 묻는다. 워크스테이션 카드 한 장으로 753B, 게이밍 데스크톱으로 284B, 8 GB 노트북으로 35B 모델을 39 tok/s(프로덕션 Codex의 중앙값 디코드 속도 이상)로 돌린다. 핵심은 expert 캐시 미스를 PCIe 전송과 CPU 직접 실행으로 그 기계에서 측정한 두 대역폭의 비율대로 나누는 것이다.

one-line summary한 줄 요약
  • An MoE model activates few experts per token but stores all of them, so on a personal machine the expert pool lives in host RAM and every miss costs a PCIe transfer.
  • Prior systems compete on predicting misses. FreeToken treats a missed expert as work that can run where it already sits, and splits each step's misses between PCIe fill and CPU execution at q* = m·B_P/B_H, from two bandwidths measured on the actual machine.
  • It adds full-layer double-buffered prefill, recurrent-state checkpoints anchored at the semantic boundaries agent harnesses actually edit, and an elastic GPU cache that resizes mid-session.
  • Result: 1.5–2.3× decode over the best edge engine, and worst-case TTFT under 44 s where baselines hit 946 s.
  • MoE 모델은 토큰당 소수의 expert만 쓰지만 전부를 저장한다. 그래서 개인 PC에서는 expert 풀이 호스트 RAM에 있고, 미스마다 PCIe 전송 비용이 든다.
  • 기존 시스템은 미스를 더 잘 예측하는 데 집중했다. FreeToken은 미스 난 expert를 있는 자리에서 실행할 수 있는 일감으로 보고, 실제 기계에서 측정한 두 대역폭으로 정한 q* = m·B_P/B_H 비율에 따라 PCIe fill과 CPU 실행으로 나눈다.
  • 여기에 레이어 단위 이중 버퍼 prefill, 에이전트 하네스가 실제로 편집하는 의미 경계에 둔 recurrent state 체크포인트, 세션 중 크기가 바뀌는 GPU 캐시를 더한다.
  • 결과: 최고 엣지 엔진 대비 디코드 1.5~2.3배. 베이스라인이 946초까지 가는 최악 TTFT를 44초 미만으로 낮춘다.

The second half of the prefill problem is the part most systems ignore. Frontier models use hybrid attention: full attention interleaved with sliding-window attention (DeepSeek-V4-Flash, GPT-OSS) or recurrent layers (gated DeltaNet in Qwen3.6-35B-A3B, Kimi Delta Attention in Kimi-K3). A recurrent layer compresses the prefix into one evolving state that cannot be partially reused, and each saved state costs as much memory as hundreds of tokens of KV cache, so engines keep only a few checkpoints. When the harness edits the context, every checkpoint after the edit is dead, forcing a re-prefill of thousands of tokens on a GPU with roughly a fifth of an H100's dense BF16 throughput.

prefill의 나머지 절반은 대부분의 시스템이 놓친다. 요즘 프론티어 모델은 full attention에 sliding-window(DeepSeek-V4-Flash, GPT-OSS)나 recurrent 레이어(Qwen3.6-35B-A3B의 gated DeltaNet, Kimi-K3의 Kimi Delta Attention)를 섞는 하이브리드 어텐션을 쓴다. recurrent 레이어는 prefix를 상태 하나로 압축해 부분 재사용이 안 되고, 상태 하나가 수백 토큰치 KV만큼 커서 체크포인트는 몇 개만 둔다. 하네스가 컨텍스트를 고치면 그 뒤 체크포인트가 모두 무효가 되어, dense BF16 성능이 H100의 5분의 1 정도인 GPU로 수천 토큰을 다시 prefill해야 한다.

Three findings stack here. First, existing engines freeze expert placement at load or prefill time: llama.cpp assigns MoE tensors to devices at load, KTransformers pins a "hot" subset in VRAM and runs the rest on CPU.

First, shrink m: an LRU that tracks the router먼저 m 줄이기: 라우터를 따라가는 LRU

The key physical fact is that both branches draw from the same host-memory subsystem. A DMA transfer to the GPU and a CPU kernel reading expert weights compete for the same DRAM controllers, so a saturated PCIe transfer leaves the CPU only what's left over:

3.1 — The problem: everything about this cache changes every step 3.1 문제: 이 캐시는 스텝마다 모든 것이 바뀐다

Replaying a CUDA Graph removes per-launch CPU overhead, which matters at small decode batches where launch overhead is a real fraction of step time. But the graph is static, and FreeToken's cache is anything but:

CUDA Graph를 재생하면 실행마다 드는 CPU 오버헤드가 사라진다. 실행 오버헤드가 스텝 시간의 상당 부분인 작은 디코드 배치에서 특히 중요하다. 그런데 그래프는 정적이고 FreeToken의 캐시는 전혀 정적이지 않다.

"Expert caching is inherently dynamic: the specific experts that miss, the number of experts fetched, and the slots evicted all change at every step. Consequently, a host-controlled cache would reintroduce a costly device synchronization at every MoE layer."

— §4.1 · 원문 보기 (§4.1)

A naive implementation: the router runs on the GPU, so to decide evictions and fetches the host syncs, reads the routing results back, decides in Python, and launches copies. That is a full device sync per MoE layer, per token; on a 43-layer model at 25 tok/s, over a thousand syncs a second, each draining the pipeline.

순진하게 구현하면 호스트가 동기화해 GPU의 라우팅 결과를 읽고, 파이썬에서 evict와 fetch를 정하고, 복사를 띄워야 한다. MoE 레이어마다, 토큰마다 디바이스 동기화가 일어나므로 43레이어 모델을 25 tok/s로 돌리면 초당 천 번이 넘는다.

FreeToken keeps all routing-dependent control on the GPU and expresses the dynamism as data in fixed-shape buffers rather than as control flow the host must see. The graph's shape never changes; only the numbers inside it do.

FreeToken은 라우팅에 의존하는 제어를 전부 GPU에 둔다. 동적인 부분을 호스트가 봐야 하는 제어 흐름이 아니라 고정 모양 버퍼를 흐르는 데이터로 표현한다. 그래프 모양은 그대로이고 안의 숫자만 바뀐다.

Single-pass victim selection한 번의 순회로 끝내는 희생자 선택

"Victim selection avoids the classic LRU trap of requiring one full-cache scan per evicted slot. Instead, a single-pass kernel identifies the K least-recently-used candidate slots for eviction in one go. The miss path then simply consumes the first q ≤ K of these slots. As a result, victim discovery always costs exactly one pass, regardless of the realized miss count."

— §4.1 ("Device-side cache control") · 원문 보기 (§4.1)

Plainly: textbook LRU scans the cache once per evicted entry, so evicting q entries costs q scans, and since q varies per step the work isn't fixed-shape and can't be captured. Finding the K oldest in one pass and taking what you need makes the cost constant and the shape static.

교과서 LRU는 항목 하나를 내보낼 때마다 캐시를 훑어 q개면 q번이고, q가 스텝마다 달라 캡처도 안 된다. 한 번에 가장 오래된 K개를 찾아 필요한 만큼 쓰면 비용은 상수, 모양은 정적이 된다.

The resulting copy work list then drives a single fused transfer. Because every expert bank shares the same logical expert-to-slot mapping (§3.3 below), one device-resident source/destination index list applies to all banks in a single fixed-shape launch, with a valid count masking the unused entries.

이렇게 나온 복사 목록이 융합 전송 한 번을 구동한다. 모든 expert bank가 같은 논리 expert→슬롯 매핑을 쓰므로(§3.3), 디바이스의 source/destination 인덱스 목록 하나로 고정 모양 launch 한 번에 모든 bank를 처리하고, valid count로 안 쓰는 항목을 가린다.

This is the part I expected to break. The CPU branch is captured into the same graph: for each supported decode batch size, FreeToken prepares stable pinned I/O buffers and persistent task descriptors, then captures the device-to-host copies, a host-function submit node, the concurrent GPU path, a synchronization node, and the host-to-device result copy together. Replay runs the full heterogeneous step with no per-token Python scheduling at all.

깨질 거라 예상했던 부분이다. CPU 분기도 같은 그래프에 캡처된다. 배치 크기마다 고정 pinned I/O 버퍼와 영속 task descriptor를 준비하고, device-to-host 복사, host-function submit 노드, 동시 GPU 경로, 동기화 노드, host-to-device 결과 복사를 함께 캡처한다. 재생 시 토큰당 파이썬 스케줄링이 없다.

The workers are a persistent C++ pool pinned to physical cores, using architecture-specific SIMD and in-kernel dequantization. That keeps the path bandwidth-bound rather than compute-bound, which is what makes BH a meaningful constant in Eq. 4. They return gate-weighted, per-token partial outputs, ready to merge.

워커는 물리 코어에 고정된 영속 C++ 풀로 아키텍처별 SIMD와 커널 내 역양자화를 쓴다. 덕분에 이 경로가 대역폭 바운드로 유지되어 Eq. 4의 BH가 의미 있는 상수가 된다. 워커는 gate 가중치를 곱한 토큰별 부분 출력을 돌려준다.

3.3 — Expert banks, the FTW format, and graceful degradation 3.3 Expert bank, FTW 포맷, 그리고 폴백

Checkpoints lay out MoE weights differently. FreeToken normalizes all of them into a small set of expert banks, each using the flattened identifier l·E + e as its leading dimension. Rows sharing that identifier across banks form one complete expert, so GPU kernels and the CPU executor share one logical expert identity regardless of physical format. That shared identity is what makes the single fused index list of §3.2 possible.

체크포인트마다 MoE 가중치 배치가 달라, FreeToken은 이를 평탄화 식별자 l·E + e를 첫 차원으로 쓰는 소수의 expert bank로 정규화한다. 모든 bank에서 같은 식별자의 행을 모으면 expert 하나가 되므로, GPU 커널과 CPU 실행기가 물리 포맷과 관계없이 논리 expert 식별자 하나를 공유한다. §3.2의 융합 인덱스 목록이 가능한 이유다.

The FTW (FreeToken Weight) format then stores expert weights pre-merged into that runtime bank layout, so launch skips tensor discovery and repacking entirely: it reads aligned chunks with parallel direct I/O straight into exact-size host banks, pinned only after they're filled (§2.3).

FTW (FreeToken Weight) 포맷은 expert 가중치를 이 bank 레이아웃으로 미리 병합해 저장한다. 실행 시 텐서 탐색과 재포장을 건너뛰고, 정렬된 청크를 병렬 direct I/O로 정확한 크기의 호스트 bank에 바로 읽은 뒤 다 채우고 나서 pin한다(§2.3).

the fallback path is worth noting폴백 경로도 눈여겨볼 만하다 On some operating systems and driver configurations the complete expert pool cannot be pinned or registered for DMA. FreeToken then degrades to a pure-CPU MoE backend: experts run on the CPU from pageable host memory, non-expert layers stay on the GPU, and only activation-sized inputs, routing metadata and aggregated outputs cross the boundary. It trades peak transfer bandwidth for running on machines users already own, a detail research prototypes usually skip. 일부 OS와 드라이버 구성에서는 expert 풀 전체를 pin하거나 DMA용으로 등록할 수 없다. 이때 FreeToken은 순수 CPU MoE 백엔드로 내려간다. expert는 pageable 호스트 메모리에서 CPU로 실행하고, expert 외 레이어는 GPU에 남아 활성값 크기의 입력·라우팅 메타데이터·집계 출력만 오간다. 최대 전송 대역폭 대신 사용자가 이미 가진 기계에서 돌아가는 쪽을 택한 것으로, 연구 프로토타입이 대개 건너뛰는 부분이다.

4.5 — The limitations section that isn't there 4.5 없는 한계 절

editor's note — the paper states no limitations; these are mine편집자 주: 논문에 한계 절이 없어 직접 정리한 것
The word "limitation" appears nowhere in this paper, and there is no threats-to-validity discussion. For a systems paper this thorough that's a conspicuous gap, so here is what I'd want addressed:
  1. The emulation carries the headline numbers. Three of six machines are rented servers throttled to 6 threads. The validation against two real edge boxes is genuine, but §5.2's main figure runs on the emulated 5090.
  2. No accuracy verification is reported. The exactness claim ("preserving the exact MoE output without algorithmic approximation") is architectural and I believe it. But with the CPU branch dequantizing in-kernel on a different SIMD path, a numerical-parity check against a VRAM-resident reference is the experiment a reader wants, and it isn't there.
  3. q* uses statically profiled bandwidths. §2.3 argues that edge resources fluctuate, yet BH and BP are "empirically profiled on the target hardware at deployment". If a background process hammers DRAM, the real BH drops and q* goes stale: VRAM adapts at runtime, the bandwidth model does not.
  4. Single-stream, small-batch regime. The q* derivation assumes expert execution is memory-bound, which holds "at small decode batches". Concurrency appears in W3 via subagents, but the batch-size boundary where the model stops holding is never characterized.
  5. No power or thermal data. On a laptop, arguably the flagship result, sustaining 39.3 tok/s with saturated PCIe and all cores busy raises battery and throttling questions that an edge paper cannot ignore.
  6. Trajectory divergence. §5.1 notes agent trajectories differ across engines, so wall-clock totals aren't compared. Fair, but then "solves the SWE issue" is the only end-to-end equivalence, and per-request means compare runs that did different amounts of work.
논문 어디에도 "limitation"이라는 단어나 threats-to-validity 논의가 없다. 이만큼 꼼꼼한 시스템 논문에서는 눈에 띄는 공백이라, 다뤄졌으면 하는 점을 정리했다.
  1. 대표 수치를 에뮬레이션이 떠받친다. 6대 중 3대가 스레드 6개로 제한한 임대 서버다. 실제 엣지 기계 두 대로 한 검증은 믿을 만하지만, §5.2의 메인 그림은 에뮬레이션된 5090에서 나왔다.
  2. 정확도 검증이 없다. 정확성 주장("preserving the exact MoE output without algorithmic approximation")은 구조상 믿을 만하다. 그래도 CPU 분기가 GPU와 다른 SIMD 경로에서 커널 내 역양자화를 하므로, VRAM 상주 기준과의 수치 동등성 검사가 있어야 한다.
  3. q*가 정적으로 프로파일링한 대역폭을 쓴다. §2.3은 엣지 자원이 요동친다고 강조하지만 BH와 BP는 배포 시점에 한 번 측정한다. 백그라운드 프로세스가 DRAM을 쓰면 실제 BH가 떨어져 q*가 낡는다. VRAM은 런타임에 조정하면서 대역폭 모델은 고정인 비대칭이다.
  4. 단일 스트림·소배치 영역만 다룬다. q* 유도는 expert 실행이 메모리 바운드라는 가정, 즉 "작은 디코드 배치"를 전제한다. W3의 서브에이전트로 동시성이 생기지만, 이 모델이 깨지는 배치 크기 경계는 다루지 않는다.
  5. 전력·발열 데이터가 없다. 간판 결과인 노트북에서 PCIe를 포화시키고 전 코어를 돌리며 39.3 tok/s를 유지하면 배터리와 스로틀링이 문제가 된다. 엣지 논문이라면 피할 수 없는 질문이다.
  6. 트레이젝토리가 엔진마다 다르다. §5.1은 그래서 벽시계 총합을 비교하지 않는다. 합리적이지만, end-to-end 동치 조건은 "SWE 이슈를 푼다" 하나뿐이고 요청당 평균은 일의 양이 다른 실행끼리 비교한 값이다.

5.2 — Our read (not the paper's claims)5.2 우리 관점의 해석 (논문의 주장 아님)

editor's note — reading an edge paper from the cluster side편집자 주: 엣지 논문을 클러스터 쪽에서 읽기 (논문의 주장 아님)
This is edge research and we work at cluster scale, so the honest question is which parts translate.
  1. The reframe transfers; the formula does not. The durable idea is "a miss is work, not just data": fetching is only one of two options, and the split should be sized from measured ratios per step, not fixed in config. CMX exists for the same reason: reloading a cached prefix from NVMe (~6 s) became faster than recomputing it (~11 s at 128K). q* = m·B_P/B_H itself assumes consumer-class host bandwidth per GPU and an idle CPU; in a datacenter the pair is remote-fetch vs local-recompute, or NVMe vs recompute, with the same algebra and different B's.
  2. "Tail TTFT is an availability boundary, not a latency statistic" is the line to steal. Agent clients ship watchdogs (OpenClaw at 120 s, Claude Code at ~10 min), so a p99 TTFT past those is a failed request that a mean-based dashboard never shows. Any SLO for agentic traffic should state the client's abandonment threshold explicitly.
  3. On semantic-aware routing. FreeToken's "semantic-aware" is narrower than the name: checkpoint placement for recurrent state, anchored where harnesses truncate. For a prefix-cache-aware router the transferable premise is that harnesses edit at block boundaries marked by special tokens and preserve the exact prefix before them. If so, cache keys, radix-tree split points and routing affinity should align to those boundaries, raising reuse for the cost of a tokenizer-level check; the premise is cheap to validate against our own traces.
  4. Expert pinning vs EPLB optimize different things. FreeToken's LRU decides which experts occupy scarce VRAM on one machine to minimize miss rate; EPLB / expert permutation decides how experts are distributed across ranks to minimize load imbalance. Still, in §5.3 routing-following residency beat placement fixed at prefill time by 2.6× and 1.5× in miss rate at equal capacity (16% vs 41%, 39% vs 59%). A similar gap between continuously-adapted and periodically-recomputed placement at cluster scale is worth measuring, but a slot fill is a PCIe copy while a rebalance moves weights between ranks, so whether it amortizes is an open question.
  5. What I'd verify first. The artifact is Apache-2.0 and built on the same SGLang/vLLM substrate we use, so the mechanisms are architecturally portable. But the q* model assumes small-batch, memory-bound decode, and cluster serving runs large batches where expert execution turns compute-bound. Characterize the batch-size boundary before borrowing anything; the paper never does.
엣지 연구를 클러스터 규모에서 읽으므로 어느 부분이 옮겨오는가가 질문이다.
  1. 관점은 옮겨오고 공식은 아니다. "미스는 데이터가 아니라 일감"이라는 생각, 즉 가져오기는 두 선택지 중 하나이고 분배는 config가 아니라 스텝마다 측정한 비율로 정한다는 생각은 남는다. CMX도 NVMe에서 prefix를 다시 읽는 것(~6초)이 재계산보다 빨라져서(128K에서 ~11초) 생긴 같은 구조의 결정이다. 반면 q* = m·B_P/B_H 자체는 소비자급 호스트 대역폭과 놀고 있는 CPU를 전제하므로, 데이터센터에서는 원격 fetch vs 로컬 재계산, NVMe vs 재계산 쌍으로 다시 유도해야 한다.
  2. "Tail TTFT는 지연 통계가 아니라 가용성 경계다"는 가져올 문장이다. 에이전트 클라이언트에는 watchdog이 있어(OpenClaw 120초, Claude Code 약 10분) 이를 넘긴 p99 TTFT는 실패한 요청이고, 평균 기반 대시보드에는 보이지 않는다. 에이전트 트래픽 SLO에는 클라이언트의 포기 임계값을 명시해야 한다.
  3. Semantic-aware routing. FreeToken의 "semantic-aware"는 이름보다 좁아서, 하네스가 자르는 자리에 recurrent 상태 체크포인트를 두는 것이다. prefix-cache 인식 라우터에 가져올 것은 그 전제, 즉 하네스가 특수 토큰으로 표시된 블록 경계에서 편집하고 그 앞 prefix는 보존한다는 점이다. 그렇다면 캐시 키, radix 트리 분할 지점, 라우팅 어피니티를 그 경계에 맞춰 토크나이저 수준 검사만으로 재사용률을 올릴 수 있고, 이 전제는 우리 트레이스로 싸게 검증할 수 있다.
  4. Expert pinning과 EPLB는 다른 것을 최적화한다. FreeToken의 LRU는 한 기계의 VRAM에 어떤 expert를 둘지 정해 미스율을 줄이고, EPLB/expert permutation은 expert를 랭크에 어떻게 나눌지 정해 부하 불균형을 줄인다. 다만 §5.3에서 라우팅을 따라가는 상주가 prefill 시점 고정 배치보다 같은 용량에서 미스율을 2.6배, 1.5배 낮췄다(16% vs 41%, 39% vs 59%). 클러스터에서도 연속 적응과 주기적 재계산 사이에 비슷한 격차가 있는지 측정할 만하지만, 슬롯 fill은 PCIe 복사이고 재조정은 랭크 간 가중치 이동이라 상각이 되는지는 열린 질문이다.
  5. 먼저 검증할 것. 아티팩트는 Apache-2.0이고 우리와 같은 SGLang/vLLM 기반이라 구조적으로 이식할 수 있다. 하지만 q* 모델은 소배치·메모리 바운드 디코드를 가정하고, 클러스터의 큰 배치에서는 expert 실행이 연산 바운드가 된다. 무엇이든 빌려오기 전에 배치 크기 경계부터 확인해야 하고, 논문은 이를 다루지 않는다.
