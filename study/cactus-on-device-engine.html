Cactus — an on-device AI inference engine, explained Cactus — 온디바이스 AI 추론 엔진, 풀어 읽기

Most of this blog is about running models in a datacenter. Cactus is the opposite end: a source-available engine for running LLMs, vision, and speech models directly on a phone, watch, or Raspberry Pi — no server, works offline. It's a full stack in ~C/C++: hand-written CPU/GPU kernels, a mobile computation graph, a high-level engine with an OpenAI-compatible API, and — the most interesting part — a rotation-based quantization system that squeezes a 4.8 GB model down to ~0.9 GB so it fits in a phone's RAM. This note walks the whole thing for a reader who knows AI models but not the systems terms; every one (kernel, SIMD, quantization, FFI, KV cache…) is unpacked first, and the code path is pinned to a real commit. 이 블로그의 대부분은 데이터센터에서 모델을 돌리는 얘기다. Cactus는 정반대 끝이다: LLM·비전·음성 모델을 폰·워치·Raspberry Pi에서 직접 돌리는 소스 공개형 엔진 — 서버 없이, 오프라인으로. ~C/C++로 된 풀 스택이다: 손으로 짠 CPU/GPU 커널, 모바일용 계산 그래프, OpenAI 호환 API를 가진 상위 엔진, 그리고 — 가장 흥미로운 부분 — 4.8 GB 모델을 ~0.9 GB로 짜내 폰 RAM에 들어가게 하는 회전 기반 양자화(rotation-based quantization). 이 노트는 AI 모델은 알지만 시스템 용어는 모르는 독자를 위해 전체를 풀어 쓴다; 모든 용어(kernel, SIMD, quantization, FFI, KV cache…)를 먼저 설명하고, 코드 경로는 실제 커밋에 핀 고정한다.

one-line summary한 줄 요약 Cactus (YC S25) is a source-available engine for running LLMs / vision / speech models on the device itself — phone, watch, Mac, Raspberry Pi — with three layers: hand-written Kernels (ARM SIMD + Apple Metal), a zero-copy Graph ("PyTorch for mobile"), and an Engine with an OpenAI-compatible API. The binding constraint on-device is memory, so the star is quantization: CQ (a rotation-and-codebook scheme that quantizes every tensor from 4-bit to 1-bit and beats GPTQ/AWQ/HQQ badly below 4-bit — the "only survivor" at 2-bit) shrinks a Gemma-4-E2B from 4.79 GB to ~0.9 GB, and the research-preview TurboQuant-H uses Hadamard rotation to take the giant per-layer embedding tables down to ~2 bits. A distinctive twist: cloud handoff — when the on-device model's confidence drops below a threshold, it flags the request so the app can route to a cloud model. Numbers here are vendor-reported (their README benchmarks); read as such. Cactus(YC S25)는 LLM·비전·음성 모델을 기기 자체에서 돌리는 소스 공개형 엔진이다 — 폰·워치·Mac·Raspberry Pi — 세 계층으로: 손으로 짠 Kernels(ARM SIMD + Apple Metal), zero-copy Graph("모바일용 PyTorch"), OpenAI 호환 API의 Engine. 온디바이스의 병목은 메모리라, 주인공은 양자화다: CQ(모든 텐서를 4→1비트로 양자화하는 회전+코드북 방식으로, 4비트 미만에서 GPTQ/AWQ/HQQ를 크게 앞서고 2비트에선 "유일한 생존자")는 Gemma-4-E2B를 4.79 GB→~0.9 GB로 줄이고, 연구 프리뷰 TurboQuant-H는 Hadamard 회전으로 거대한 per-layer 임베딩 테이블을 ~2비트로 내린다. 독특한 반전: 클라우드 핸드오프 — 온디바이스 모델의 확신도가 임계값 아래로 떨어지면 요청에 플래그를 달아 앱이 클라우드 모델로 라우팅할 수 있게 한다. 여기 수치는 벤더 보고(README 벤치마크)이니 그렇게 읽을 것.

Glossary — the systems words, in plain language (read this first)용어집 — 시스템 용어를 쉬운 말로 (먼저 읽기)

on-device / edge inference온디바이스 / 엣지 추론

Running the model on the phone/watch itself, not on a server. Upsides: private, offline, no per-call cost, low latency. Downside: you're limited by a tiny device's RAM and battery.모델을 서버가 아니라 폰/워치 자체에서 실행. 장점: 프라이버시·오프라인·호출당 비용 없음·낮은 지연. 단점: 작은 기기의 RAM과 배터리에 묶임.

inference engine추론 엔진

The software that actually runs a trained model to produce output. Cactus is one, built specially for small ARM devices instead of datacenter GPUs.학습된 모델을 실제로 실행해 출력을 내는 소프트웨어. Cactus가 그 하나로, 데이터센터 GPU가 아니라 작은 ARM 기기를 위해 특별히 만들어짐.

quantization (bits)양자화 (비트)

Storing each weight in fewer bits (FP16→INT4→2-bit) to shrink the model. A 2B model is ~4 GB at FP16, ~1 GB at 4-bit, ~0.5 GB at 2-bit — the difference between fitting on a phone or not.각 가중치를 더 적은 비트로 저장(FP16→INT4→2비트)해 모델을 줄임. 2B 모델은 FP16에서 ~4 GB, 4비트 ~1 GB, 2비트 ~0.5 GB — 폰에 들어가느냐 마느냐의 차이.

kernel / SIMD / NEON / Metal커널 / SIMD / NEON / Metal

A kernel is a hand-optimized routine for one math op (e.g. matmul). SIMD = one instruction doing many numbers at once; NEON is ARM's SIMD, Metal is Apple's GPU API. This is where speed is won on a phone.커널은 한 수학 연산(예: matmul)을 위한 손 최적화 루틴. SIMD = 명령 하나가 여러 숫자를 동시에 처리; NEON은 ARM의 SIMD, Metal은 Apple GPU API. 폰에서 속도가 갈리는 곳.

computation graph계산 그래프

A model expressed as a graph of tensor operations (matmul → add → softmax…). "Zero-copy" means tensors are shared by reference, not duplicated in memory — precious on a device.모델을 텐서 연산의 그래프로 표현(matmul → add → softmax…). "zero-copy"는 텐서를 복제하지 않고 참조로 공유한다는 뜻 — 기기에선 귀한 절약.

per-layer embeddings (AltUp)per-layer 임베딩 (AltUp)

Newer models (Gemma 4/3n) give each layer its own embedding lookup table over a huge vocab. These tables can be 60%+ of the whole model — the biggest thing to compress.최신 모델(Gemma 4/3n)은 각 레이어마다 거대한 어휘에 대한 자체 임베딩 룩업 테이블을 둔다. 이 테이블이 모델 전체의 60%+가 될 수 있음 — 압축 1순위.

rotation quantization (Hadamard)회전 양자화 (Hadamard)

Before quantizing, rotate the numbers with a special matrix (a Hadamard matrix) so they spread out evenly — which makes low-bit rounding far more accurate. The rotation is undone at inference.양자화 전에 특수 행렬(Hadamard 행렬)로 숫자를 회전시켜 고르게 퍼뜨림 — 그러면 저비트 반올림이 훨씬 정확해진다. 회전은 추론 때 되돌린다.

codebook (Lloyd-Max)코드북 (Lloyd-Max)

Instead of even rounding steps, pick a small set of representative values ("centroids") that best fit the data, and store each number as an index into that set. Lloyd-Max finds the best centroids.균등한 반올림 대신, 데이터에 가장 잘 맞는 대표값("centroid") 소수를 골라, 각 숫자를 그 집합의 인덱스로 저장. Lloyd-Max가 최적 centroid를 찾음.

KV cacheKV 캐시

Cached per-token state so each new token doesn't re-read the whole prompt. On tiny models Cactus keeps it at INT8 (not lower) to avoid quality loss — a detail that shapes their quant choices.토큰별 상태를 캐시해 새 토큰마다 프롬프트 전체를 다시 안 읽게. 작은 모델에선 Cactus가 품질 손실을 피하려 INT8로 유지(더 낮추지 않음) — 양자화 선택을 좌우하는 디테일.

FFI / bindingsFFI / 바인딩

FFI (Foreign Function Interface) = calling C code from another language. Cactus's core is C/C++; bindings (Swift, Kotlin, Flutter, Python…) are thin wrappers so app developers call it in their own language.FFI(Foreign Function Interface) = 다른 언어에서 C 코드를 호출. Cactus 코어는 C/C++; 바인딩(Swift, Kotlin, Flutter, Python…)은 앱 개발자가 자기 언어로 부르게 하는 얇은 래퍼.

cloud handoff (hybrid)클라우드 핸드오프 (하이브리드)

"Edge-cloud hybrid": run on-device by default, but if the small model isn't confident enough, hand the query off to a big cloud model. Best of both — cheap/private when easy, accurate when hard."엣지-클라우드 하이브리드": 기본은 온디바이스로 돌리되, 작은 모델이 충분히 확신 못 하면 큰 클라우드 모델로 넘김. 양쪽의 장점 — 쉬우면 싸고 사적, 어려우면 정확.

prefill / decode tps, TTFTprefill / decode tps, TTFT

Prefill = reading your prompt; decode = writing the answer token by token. tps = tokens/second (higher = faster). TTFT = time to first token (how long before it starts replying).Prefill = 프롬프트 읽기; decode = 답을 토큰 단위로 쓰기. tps = 초당 토큰(높을수록 빠름). TTFT = 첫 토큰까지 시간(대답 시작까지 얼마나 걸리나).

1What it is, and why "on-device" is a different game무엇이고, 왜 "온디바이스"는 다른 게임인가

Cactus (from Cactus Compute, a YC S25 company) is a source-available, energy-efficient inference engine for running LLMs, vision-language models, and speech models on small devices — phones, wearables, Macs, and ARM boards like the Raspberry Pi. The pitch is "a hybrid edge-cloud AI engine for mobile devices & wearables": run locally by default, reach for the cloud only when needed. Cactus(YC S25 회사 Cactus Compute)는 LLM·비전언어모델·음성모델을 작은 기기에서 돌리는 소스 공개형·에너지 효율 추론 엔진이다 — 폰·웨어러블·Mac·Raspberry Pi 같은 ARM 보드. 슬로건은 "모바일·웨어러블용 하이브리드 엣지-클라우드 AI 엔진": 기본은 로컬, 필요할 때만 클라우드.

If you've read the datacenter-serving notes on this site (vLLM, SGLang, Netflix), this is the mirror image. There the enemy is GPU HBM and inter-node communication at huge batch sizes. On a phone there's no batch — it's one user, one request — and the enemies are total RAM, storage, and battery. A 2-billion-parameter model in full precision is about 4 GB; a phone might have 4–8 GB of RAM shared with the whole OS. So the entire design bends toward one goal: make the model small enough to fit, and cheap enough to run, without wrecking quality. 이 사이트의 데이터센터 서빙 노트(vLLM, SGLang, Netflix)를 읽었다면, 이건 그 거울상이다. 거기선 적이 큰 배치에서의 GPU HBM과 노드 간 통신이다. 폰엔 배치가 없다 — 한 사용자, 한 요청 — 적은 총 RAM·저장공간·배터리다. 20억 파라미터 모델은 풀 정밀도로 약 4 GB; 폰은 OS 전체와 공유하는 RAM이 4–8 GB뿐일 수 있다. 그래서 설계 전체가 한 목표로 굽는다: 품질을 망치지 않으면서 들어갈 만큼 작고, 돌릴 만큼 싸게 만들기.

Why bother running on-device at all?애초에 왜 온디바이스로?

The upside장점

Privacy (data never leaves the device), offline (works with no network), no per-request cost (no API bill), and low, predictable latency (no network round-trip). For always-on assistants, wearables, and robots, these matter more than raw quality.프라이버시(데이터가 기기를 안 떠남), 오프라인(네트워크 없이 동작), 호출당 비용 없음(API 요금 없음), 낮고 예측 가능한 지연(네트워크 왕복 없음). 상시 켜진 비서·웨어러블·로봇엔 이게 원시 품질보다 중요.

The cost비용

Small devices force small models, which are less capable. Cactus's answer is two-fold: squeeze the model hard with quantization (§3), and when the small model isn't sure, hand off to the cloud (§4) — so you only pay the cloud for the hard queries.작은 기기는 작은 모델을 강제하고, 작은 모델은 능력이 떨어진다. Cactus의 답은 둘: 양자화로 모델을 강하게 짜내고(§3), 작은 모델이 확신 없으면 클라우드로 넘긴다(§4) — 그래서 어려운 질의에만 클라우드 비용을 낸다.

the mental model to hold붙잡을 멘탈 모델 Cactus is a vertically integrated stack written mostly in C/C++: it does its own kernels, its own graph, its own quantization, and its own model conversion — because on a phone you can't lean on CUDA, cuDNN, or a big Python runtime. Think of it as "llama.cpp's ambition, but with a novel quantization scheme and an edge-cloud hybrid story built in." The single most differentiated piece is the quantization (§3); everything else is careful mobile engineering. Cactus는 대부분 C/C++로 된 수직 통합 스택이다: 커널도, 그래프도, 양자화도, 모델 변환도 자체 제작 — 폰에선 CUDA·cuDNN·큰 Python 런타임에 기댈 수 없기 때문. "llama.cpp의 야망에, 새로운 양자화 방식과 엣지-클라우드 하이브리드가 내장된 것"이라 생각하면 된다. 가장 차별화된 조각은 양자화(§3); 나머지는 꼼꼼한 모바일 엔지니어링.

Cactus is five named pieces. Three are the runtime layers a request flows through (Engine → Graph → Kernels); two are the offline pieces that prepare a model to run (Quants and the Transpiler). Here's each in plain terms. Cactus는 이름 붙은 다섯 조각이다. 셋은 요청이 흐르는 런타임 계층(Engine → Graph → Kernels); 둘은 모델이 돌 수 있게 준비하는 오프라인 조각(Quants와 Transpiler). 각각을 쉬운 말로.

Box by box상자별로

  • Engine (C API). The high-level surface an app calls: cactus_init(weights, rag_corpus, …) to load a model and cactus_complete(model, messages, …) to get a reply. Messages are JSON in the OpenAI chat shape; the response JSON carries the text plus confidence, cloud_handoff, tool function_calls, and timing (time_to_first_token_ms, decode_tps…). One API covers text, vision, audio, transcription, embeddings, RAG, and tools.Engine (C API). 앱이 부르는 상위 표면: 모델 로드는 cactus_init(weights, rag_corpus, …), 응답은 cactus_complete(model, messages, …). 메시지는 OpenAI 챗 형태의 JSON; 응답 JSON엔 텍스트 + confidence, cloud_handoff, 툴 function_calls, 타이밍(time_to_first_token_ms, decode_tps…). 하나의 API가 텍스트·비전·오디오·전사·임베딩·RAG·툴을 모두 커버.
  • Graph (C++). A tiny tensor framework — "PyTorch for mobile." You declare inputs and ops (graph.matmul(a, b), transpose, …), then execute(). "Zero-copy" means intermediate tensors are referenced, not copied — critical when RAM is scarce. It supports mixed precision (FP16, INT8) tensor by tensor.Graph (C++). 작은 텐서 프레임워크 — "모바일용 PyTorch." 입력과 연산을 선언(graph.matmul(a, b), transpose, …)한 뒤 execute(). "zero-copy"는 중간 텐서를 복사하지 않고 참조한다는 뜻 — RAM이 귀할 때 결정적. 텐서별 혼합 정밀도(FP16, INT8) 지원.
  • Kernels (C/C++). The hand-written inner loops for matmul, attention, convolution, quantization, and DSP, tuned for ARM NEON SIMD (Apple, Snapdragon, Tensor, Exynos, MediaTek, Raspberry Pi) and Apple Metal for GPU. This is the layer that turns "correct" into "fast enough to feel instant."Kernels (C/C++). matmul·attention·convolution·양자화·DSP를 위한 손으로 짠 내부 루프로, ARM NEON SIMD(Apple·Snapdragon·Tensor·Exynos·MediaTek·Raspberry Pi)와 GPU용 Apple Metal에 튜닝. "맞다"를 "즉각적으로 느껴질 만큼 빠르다"로 바꾸는 계층.
  • Quants (CQ). The offline compression recipe — rotation-and-codebook quantization from 4-bit down to 1-bit, applied to every tensor. This is §3.Quants (CQ). 오프라인 압축 레시피 — 4비트에서 1비트까지 회전+코드북 양자화를 모든 텐서에 적용. §3에서 다룸.
  • Transpiler (Python). Converts an arbitrary PyTorch / HuggingFace model into a Cactus runtime graph + CQ weights (a "bundle") via cactus convert. This is the offline bridge from the training world (PyTorch) to the on-device world.Transpiler (Python). 임의의 PyTorch / HuggingFace 모델을 cactus convert로 Cactus 런타임 그래프 + CQ 가중치("번들")로 변환. 학습 세계(PyTorch)에서 온디바이스 세계로의 오프라인 다리.

3The headline — rotation-based quantization (CQ & TurboQuant-H)핵심 — 회전 기반 양자화 (CQ & TurboQuant-H)

On a phone, storage and memory are the whole ballgame. A 2B model is ~4 GB at FP16, ~1 GB at 4-bit, ~0.5 GB at 2-bit — so the lower you can push the bits without wrecking quality, the more (and better) models fit. The catch: standard 4-bit methods (GPTQ, AWQ, HQQ) fall apart below 4 bits and don't handle the huge embedding tables at all. Cactus's answer is two related rotation-based schemes. 폰에선 저장공간과 메모리가 전부다. 2B 모델은 FP16 ~4 GB, 4비트 ~1 GB, 2비트 ~0.5 GB — 품질을 안 망치면서 비트를 낮출수록 더 많고 더 좋은 모델이 들어간다. 함정: 표준 4비트 방법(GPTQ·AWQ·HQQ)은 4비트 미만에서 무너지고 거대한 임베딩 테이블은 아예 못 다룬다. Cactus의 답은 두 개의 연관된 회전 기반 방식이다.

The shared idea: rotate, then use a codebook공통 아이디어: 회전한 뒤 코드북 사용

Both schemes share one trick. Raw model weights are lumpy — a few big outliers force a coarse rounding grid that wastes precision on everyone else. If you first rotate the numbers with a Hadamard matrix (a fixed pattern of +1/−1 that mixes coordinates evenly), the lumps spread into a smooth, well-behaved spread. Now a small codebook of representative values covers them accurately at very few bits. At inference the rotation is undone — and because a normalized Hadamard matrix is its own inverse, "undo" is the exact same cheap operation as "do." 두 방식 모두 한 트릭을 공유한다. 원시 가중치는 울퉁불퉁하다 — 큰 이상치 몇 개가 거친 반올림 격자를 강요해 나머지 모두의 정밀도를 낭비한다. 먼저 Hadamard 행렬(좌표를 고르게 섞는 +1/−1의 고정 패턴)로 숫자를 회전시키면 울퉁불퉁함이 매끄럽고 다루기 좋은 분포로 퍼진다. 이제 대표값의 작은 코드북이 아주 적은 비트로 그것들을 정확히 덮는다. 추론 때 회전을 되돌리는데 — 정규화된 Hadamard 행렬은 자기 자신이 역행렬이라 "되돌리기"가 "하기"와 정확히 같은 싼 연산이다.

A Hadamard rotation spreads lumpy weights so a tiny codebook can represent them at 1–4 bits; the (self-inverse) rotation is re-applied to decode. Schematic; math per the TurboQuant-H write-up.그림 2 — CQ와 TurboQuant-H가 공유하는 회전-후-코드북 아이디어. Hadamard 회전이 울퉁불퉁한 가중치를 퍼뜨려 작은 코드북이 1–4비트로 표현하게 하고; (자기역인) 회전을 다시 적용해 디코드. 개략도; 수식 출처 TurboQuant-H 글.

CQ (Cactus Quants) — the shipped, general schemeCQ (Cactus Quants) — 실제 배포되는 범용 방식

CQ is the default (--bits 4). Unlike GPTQ/AWQ/HQQ, which only quantize transformer linear layers, CQ applies one recipe to every tensor — linears, vision/audio towers, cross-modal bridges, and both embedding tables. The payoff shows up as you push the bits down: CQ가 기본값(--bits 4)이다. 트랜스포머 linear 레이어만 양자화하는 GPTQ/AWQ/HQQ와 달리, CQ는 하나의 레시피를 모든 텐서에 적용한다 — linear·비전/오디오 타워·크로스모달 브리지·양쪽 임베딩 테이블. 비트를 낮출수록 이득이 드러난다:

Read the story in that table: at 4-bit everyone's close; at 3-bit CQ pulls ahead by tens of points; at 2-bit the baselines collapse to near-random while CQ still functions. 표의 스토리: 4비트에선 다들 비슷하고; 3비트에선 CQ가 수십 점 앞서고; 2비트에선 baseline이 near-random으로 무너지는데 CQ는 여전히 작동한다.

"At 2-bit, every baseline collapses. CQ is the only method retaining usable accuracy."

— Cactus Quants docs · docs/cactus_quants.md

Because different tensors tolerate compression differently, CQ also does mixed precision: keep the sensitive layers at 4-bit, push the rest to 2–3. The production Gemma-4-E2B bundle uses 4-bit linears, 2-bit per-layer embeddings, 4-bit shared embeddings, and 2-bit vision/audio towers — 4.79 GB → ~0.9 GB, a 5.3× reduction, while holding MMLU 59.14 and GSM8K 74.00 (vs 62.33 / 73.67 at FP16). The runtime trick that makes this cheap: 텐서마다 압축 내성이 달라, CQ는 혼합 정밀도도 한다: 민감한 레이어는 4비트, 나머지는 2–3비트. 프로덕션 Gemma-4-E2B 번들은 linear 4비트, per-layer 임베딩 2비트, 공유 임베딩 4비트, 비전/오디오 타워 2비트 — 4.79 GB → ~0.9 GB, 5.3× 감소, MMLU 59.14·GSM8K 74.00 유지(FP16의 62.33 / 73.67 대비). 이걸 싸게 만드는 런타임 트릭:

"the kernel applies a Walsh-Hadamard transform to the FP16 activation (not the weight), then performs a fused codebook-lookup + norm-scale + matmul in a single NEON pass."

— Cactus Quants docs · docs/cactus_quants.md

Honest weak spots the docs name: 2-bit audio transcription degrades (LibriSpeech WER ~5.9 → ~10.4), 2-bit tool calling is near-zero for everyone including CQ, and on the LFM family HQQ wins at 4-bit. 문서가 밝히는 정직한 약점: 2비트 오디오 전사는 저하(LibriSpeech WER ~5.9 → ~10.4), 2비트 툴콜은 CQ 포함 모두 거의 0, LFM 계열에선 4비트에서 HQQ가 이김.

TurboQuant-H — squeezing the embedding tables (research preview)TurboQuant-H — 임베딩 테이블 짜내기 (연구 프리뷰)

A newer architecture pattern (AltUp, in Gemma 4/3n) gives every layer its own embedding table over a 262K-token vocabulary — and those tables balloon to 60%+ of the model. TurboQuant-H targets exactly them. It adapts TurboQuant (Zandieh et al., ICLR 2026) — which uses random rotation + optimal scalar quantizers for KV cache — into an offline weight scheme: swap the random rotation for a Hadamard one (deterministic, fast, self-inverse), train a per-position Lloyd-Max codebook, drop the extra correction stage. 최신 아키텍처 패턴(Gemma 4/3n의 AltUp)은 262K 토큰 어휘에 대해 각 레이어마다 자체 임베딩 테이블을 두고 — 그 테이블이 모델의 60%+로 부풀어 오른다. TurboQuant-H는 정확히 그것을 노린다. KV 캐시용으로 랜덤 회전 + 최적 스칼라 양자화기를 쓰는 TurboQuant(Zandieh 외, ICLR 2026)를 오프라인 가중치 방식으로 각색: 랜덤 회전을 Hadamard 회전(결정적·빠름·자기역)으로 바꾸고, 위치별 Lloyd-Max 코드북을 학습하고, 추가 보정 단계를 뺀다.

"On Gemma 4 E2B, TurboQuant-H compresses PLI weights from 2,496 MB to 624 MB (4x) at 2.125 effective bits per dimension, reducing total LLM storage by 40% (4,790 MB → 2,918 MB) with a perplexity increase of 0.06 (1.85 → 1.91) and no measured speed regression."

— TurboQuant-H, Abstract (Mosoyan & Ndubuaku, 2026) · blog/turboquant-h.md

The nice detail: the Hadamard butterfly costs ~56 vector ops per 128-element group (<2 µs per embedding lookup on an A15), but the compressed table is ~3.8× smaller to read from memory — so the rotation more than pays for itself in saved bandwidth. Status is important: TurboQuant-H is an explicit research preview — the blog says the weights "will ship in an upcoming release" and integration into cactus convert is listed as future work. So today the shipped compression is CQ; TurboQuant-H is the frontier. 멋진 디테일: Hadamard 버터플라이는 128 원소 그룹당 ~56 벡터 연산(A15에서 임베딩 룩업당 <2 µs)이지만, 압축된 테이블은 메모리에서 읽을 때 ~3.8× 작아서 — 회전 비용을 절약된 대역폭이 상회한다. 상태가 중요하다: TurboQuant-H는 명시적 연구 프리뷰 — 블로그는 가중치가 "곧 릴리스에서 배포될 것"이라 하고 cactus convert 통합은 향후 작업으로 적혀 있다. 그러니 오늘 배포되는 압축은 CQ이고, TurboQuant-H는 프런티어다.

4Engine features — OpenAI-compatible API, cloud handoff, RAG, tools엔진 기능 — OpenAI 호환 API·클라우드 핸드오프·RAG·툴

The Engine deliberately speaks the OpenAI-compatible shape (messages in, a chat completion out; cactus serve even starts a local OpenAI-compatible HTTP server). Same instinct as the Netflix and Cerebras notes: don't invent a new interface, so existing tools and app code just work. On top of that, three features are worth calling out. Engine는 일부러 OpenAI 호환 형태로 말한다(메시지 입력, 챗 컴플리션 출력; cactus serve는 로컬 OpenAI 호환 HTTP 서버까지 띄운다). Netflix·Cerebras 노트와 같은 본능: 새 인터페이스를 만들지 말자, 기존 도구·앱 코드가 그대로 동작하게. 그 위에 세 기능이 특히 눈에 띈다.

Cloud handoff — the "hybrid" in edge-cloud클라우드 핸드오프 — 엣지-클라우드의 "하이브리드"

This is the most distinctive idea. A small on-device model handles most queries, but for each answer the engine also reports a confidence score. When confidence falls below a threshold, the response is flagged cloud_handoff: true so the app can re-route that one hard query to a big cloud model. You pay cloud cost (and give up privacy) only on the queries the local model can't handle well — the easy majority stay on-device, free and private. 가장 독특한 아이디어. 작은 온디바이스 모델이 대부분의 질의를 처리하되, 각 답마다 엔진이 confidence 점수도 보고한다. confidence가 임계값 아래로 떨어지면 응답에 cloud_handoff: true 플래그가 달려 앱이 그 어려운 질의 하나를 큰 클라우드 모델로 다시 라우팅할 수 있다. 로컬 모델이 잘 못 하는 질의에만 클라우드 비용을 내고(프라이버시를 포기하고) — 쉬운 다수는 온디바이스에, 공짜로 사적으로 남는다.

{
  "success": true,
  "response": "Hi there!",
  "confidence": 0.8193,
  "confidence_threshold": 0.7,   // model-dependent
  "cloud_handoff": false,        // true → app routes to a cloud model
  "time_to_first_token_ms": 45.23,
  "decode_tps": 168.42
}

The server/CLI exposes it directly: --confidence-threshold <0..1>, --cloud-timeout-ms, and --no-cloud-handoff to turn it off. It's the on-device mirror of the "route hard queries elsewhere" logic a datacenter gateway does — just with the local model itself as the cheap first tier. 서버/CLI가 직접 노출: --confidence-threshold <0..1>, --cloud-timeout-ms, 끄려면 --no-cloud-handoff. 데이터센터 게이트웨이가 하는 "어려운 질의는 딴 데로 라우팅" 로직의 온디바이스 거울상 — 로컬 모델 자체가 싼 1차 계층인 셈.

Auto-RAG and tool calling — small models with a memory and handsAuto-RAG와 툴콜 — 기억과 손을 가진 작은 모델

Auto-RAG

Pass a folder of text at cactus_init and the engine automatically retrieves the relevant bits into context for each query — using an on-device vector index (cosine similarity). A small model punches above its weight when it can look things up.cactus_init에 텍스트 폴더를 넘기면 엔진이 매 질의마다 관련 조각을 자동으로 컨텍스트에 검색해 넣는다 — 온디바이스 벡터 인덱스(코사인 유사도)로. 작은 모델도 찾아볼 수 있으면 제 몸집 이상을 해낸다.

Tool calling + Tool RAG

Define tools as JSON; the model returns structured function_calls. When there are many tools, Tool RAG first retrieves the top-k most relevant tools per query so the small model isn't overwhelmed. Cactus even ships Needle, a 26M-param model built just for on-device tool calling.툴을 JSON으로 정의하면 모델이 구조화된 function_calls를 반환. 툴이 많으면 Tool RAG가 먼저 질의별 top-k 관련 툴을 검색해 작은 모델이 압도되지 않게 한다. Cactus는 온디바이스 툴콜 전용 26M 파라미터 모델 Needle도 배포.

Rounding it out: streaming (token callbacks), native vision and audio in messages (VLMs like Gemma 4 / LFM2-VL accept images and audio paths), on-device transcription (Whisper, Parakeet), embeddings, and a thinking mode for models that support chain-of-thought. One C API covers all of it. 마무리로: 스트리밍(토큰 콜백), 메시지 내 네이티브 비전·오디오(Gemma 4 / LFM2-VL 같은 VLM이 images·audio 경로를 받음), 온디바이스 전사(Whisper, Parakeet), 임베딩, chain-of-thought 지원 모델용 thinking 모드. 하나의 C API가 전부 커버.

6Using it, and status사용법, 그리고 상태

On a Mac it's two commands — brew install cactus-compute/cactus/cactus then cactus run google/gemma-4-E2B-it. editor's note — our angle (not a Cactus claim)편집자 주 — 우리 관점 (Cactus 주장 아님) Cactus is the far end of the spectrum from our MI250 datacenter work — one user, ARM SIMD + Metal, no batch — but three of its ideas travel back upstream. (1) Rotation-and-codebook quantization that stays usable at 2-bit where GPTQ/AWQ/HQQ collapse is directly interesting for datacenter serving too: the same "Hadamard-rotate to kill outliers, then codebook" recipe (cf. QuIP#) is what lets low-bit weight-only serving work, and CQ's "quantize every tensor including embeddings" is a reminder that on big-vocab models the embedding tables are the hidden cost. (2) Cloud handoff = confidence-gated routing, which is the on-device twin of the gateway routing we care about in llm-d/heimdall — here the cheap first tier is the local model and the "escalation" is the cloud, but it's the same shape (a confidence/uncertainty signal deciding whether to spend more). (3) OpenAI-compatible everywhere, again. Boundaries: it's ARM/Metal, not our ROCm/CUDA datacenter; all speed/quality numbers are the vendor's own README/blog, not independently reproduced; the license is source-available (not OSS); and the flashiest piece (TurboQuant-H) isn't shipped yet. Worth reading the CQ kernel and the cloud-handoff logic; not something that drops into our stack. Cactus는 우리 MI250 데이터센터 작업과 스펙트럼의 정반대 끝이다 — 사용자 한 명, ARM SIMD + Metal, 배치 없음 — 하지만 세 아이디어는 상류로 되돌아온다. (1) 회전+코드북 양자화가 GPTQ/AWQ/HQQ가 무너지는 2비트에서도 쓸 만한 건 데이터센터 서빙에도 직접 흥미롭다: 같은 "Hadamard로 회전해 이상치를 죽이고 코드북" 레시피(cf. QuIP#)가 저비트 weight-only 서빙을 가능케 하고, CQ의 "임베딩 포함 모든 텐서 양자화"는 대어휘 모델에서 임베딩 테이블이 숨은 비용임을 상기시킨다. (2) 클라우드 핸드오프 = confidence 게이팅 라우팅은 우리가 llm-d/heimdall에서 관심 있는 게이트웨이 라우팅의 온디바이스 쌍둥이다 — 여기선 싼 1차 계층이 로컬 모델, "에스컬레이션"이 클라우드지만, 같은 형태(더 쓸지를 결정하는 confidence/불확실성 신호)다. (3) 어디서나 OpenAI 호환, 또. 경계: ARM/Metal이지 우리 ROCm/CUDA 데이터센터가 아니고; 모든 속도/품질 수치는 벤더 자체 README/블로그이지 독립 재현이 아니며; 라이선스는 소스 공개형(OSS 아님); 가장 화려한 조각(TurboQuant-H)은 아직 미배포. CQ 커널과 클라우드 핸드오프 로직은 읽을 값어치가 있지만, 우리 스택에 바로 얹을 건 아니다.
