TileRT — the tile-based ultra-low-latency LLM runtime (and what's open vs binary) TileRT — 타일 기반 초저지연 LLM 런타임 (그리고 오픈 vs 바이너리)

TileRT (from the TileLang team) serves LLMs for ultra-low latency — millisecond time-per-output-token, 1000+ tokens/s on a 1-trillion-param model — by treating the whole model as fine-grained tile-level tasks that a runtime overlaps and schedules across 8 GPUs. This note starts from scratch — what a "tile" even is — then walks what TileRT is, how it works, how to run it, and a code-walk of the repo (pinned to 242f7b3). Honesty up front: the shipped repo is a thin Python orchestration layer; the runtime and every kernel live in a closed binary, and every speed number is vendor-reported. TileRT(TileLang 팀)는 LLM을 초저지연으로 서빙한다 — 밀리초 단위 토큰당 시간, 1조 파라미터 모델에서 1000+ 토큰/s — 모델 전체를 잘게 쪼갠 타일 단위 태스크로 보고 런타임이 8-GPU에 겹치며 스케줄한다. 이 노트는 "타일"이 뭔지부터 시작해 TileRT가 무엇이고, 어떻게 동작하고, 어떻게 돌리고, 레포 코드까지(242f7b3 핀) 짚는다. 먼저 솔직히: 공개 레포는 얇은 Python 오케스트레이션 층이고, 런타임과 모든 커널은 닫힌 바이너리에 있으며, 모든 속도 수치는 벤더 발표다.

(b) thread → warp → block → grid(b) thread → warp → block → grid

A GPU is thousands of cores grouped into SMs (Streaming Multiprocessors). CUDA exposes a matching hierarchy: you launch a grid of blocks; each block runs on one SM; inside a block, threads run in lockstep groups of 32 — a warp (SIMT: all 32 execute the same instruction at once); each thread is one lane on a core. Blocks share fast SRAM; the warp is the unit the hardware actually schedules.GPU는 수천 코어가 SM(Streaming Multiprocessor)으로 묶인 것. (c) A kernel's life & the "execution gap"(c) 커널의 생애와 "execution gap"

The host (CPU) launches the kernel — i.e. loads the op itself (its compiled code + grid/block config) onto the GPU and schedules it; this is separate from the data. Then each block loads its inputs HBM→SRAM/registers, computes (multiply-accumulate) in those fast levels, writes the result back to HBM, and the host usually syncs. A launch costs ~microseconds. When a model is a chain of ops, you pay launch + sync between every op — and at 1000 tokens/s each op is only microseconds, so those idle boundaries dominate. TileRT names this the "execution gap" and its whole design targets it (§3).호스트(CPU)가 커널을 launch — 즉 연산(op) 자체(컴파일된 코드 + grid/block 설정)를 GPU에 올려 스케줄한다; 데이터와는 별개다. 그다음 각 블록이 입력을 로드(HBM→SRAM/레지스터), 그 빠른 층에서 연산(곱셈-누적), 결과를 HBM에 쓰고, 호스트는 보통 동기화. launch는 ~마이크로초. 모델이 op 체인이면 op마다 launch + sync를 낸다 — 1000토큰/s에선 op가 마이크로초라 그 유휴 경계가 지배한다. 1What is a "tile"? (from scratch)"타일"이 뭔가? (기초부터)

Start with the one hardware fact everything follows from: a GPU has enormous compute but is starved for memory bandwidth. Reading a number from HBM (the GPU's main memory) is ~100× slower than doing arithmetic on it. So the whole game of fast GPU code is: read a chunk of data from HBM once, then reuse it many times out of the tiny fast on-chip memory (registers + shared memory / SRAM) before touching HBM again. 모든 것이 따라나오는 하드웨어 사실 하나부터: GPU는 연산은 엄청나지만 메모리 대역폭이 굶주려 있다. HBM(GPU 주메모리)에서 숫자 하나 읽는 게 그 위에서 산술하는 것보다 ~100배 느리다. 그래서 빠른 GPU 코드의 핵심은: HBM에서 데이터 덩어리를 한 번 읽어, 다시 HBM을 건드리기 전에 작은 빠른 온칩 메모리(레지스터 + shared memory / SRAM)에서 여러 번 재사용하는 것이다.

A tile is that chunk. Take a matrix multiply C = A × B (the core of every LLM layer). Instead of computing all of C at once, you cut it into small rectangular tiles — say 128×128. To compute one output tile of C, you load the matching tiles of A and B into fast memory, multiply-accumulate, and only then write the tile out. Each GPU thread-block owns one output tile. Loading a tile costs one slow HBM read but feeds thousands of fast multiply-adds — that reuse is where the speed comes from. Attention (QKᵀ, softmax·V) tiles the same way. This "tiling" is the single most important trick in high-performance GPU kernels. 타일이 바로 그 덩어리다. 행렬곱 C = A × B(모든 LLM 레이어의 핵심)를 보자. C 전체를 한 번에 계산하는 대신, 작은 직사각형 타일 — 예: 128×128 — 로 쪼갠다. C의 출력 타일 하나를 계산하려면 A·B의 대응 타일을 빠른 메모리에 올려 곱셈-누적하고, 그 다음에야 타일을 내보낸다. 각 GPU 스레드블록이 출력 타일 하나를 맡는다. 타일 하나 로드는 느린 HBM 읽기 한 번이지만 수천 번의 빠른 곱셈-덧셈을 먹인다 — 그 재사용에서 속도가 나온다. 어텐션(QKᵀ, softmax·V)도 같은 식으로 타일링한다. 이 "타일링"이 고성능 GPU 커널의 가장 중요한 트릭이다.

Classic GPU tiling of a matmul. TileLang lets you write kernels at exactly this level of abstraction (tile shapes + the HBM↔SRAM↔register moves), and the compiler emits the CUDA. TileRT takes the idea up a level: it treats each tile of work as a schedulable task.행렬곱의 고전적 GPU 타일링. TileLang은 바로 이 추상 수준(타일 모양 + HBM↔SRAM↔레지스터 이동)으로 커널을 쓰게 하고 컴파일러가 CUDA를 낸다. TileRT는 이를 한 단계 올려 각 타일 작업을 스케줄 가능한 태스크로 다룬다.

Two levels build on this: (1) TileLang — an open domain-specific language (built on Apache TVM) for writing GPU kernels at the tile level: you describe the tiles and the data movement, the compiler generates the kernel, instead of hand-writing threads. (2) TileRT — treats a whole LLM layer as many fine-grained tile-level tasks (a chunk of a matmul, an attention tile, a comm chunk) and its runtime dynamically schedules those tasks across 8 GPUs, overlapping compute with I/O and communication. So in TileRT "tile" is both the unit of computation and the unit of scheduling. 여기서 두 층이 올라간다: (1) TileLang — GPU 커널을 타일 수준으로 쓰는 오픈 DSL(Apache TVM 위): 스레드를 손으로 짜는 대신 타일과 데이터 이동을 기술하면 컴파일러가 커널을 낸다. (2) TileRT — LLM 레이어 전체를 잘게 쪼갠 타일 단위 태스크(행렬곱 조각·어텐션 타일·통신 조각)로 보고, 런타임이 그 태스크들을 8-GPU에 동적으로 스케줄하며 compute를 I/O·통신과 겹친다. 그래서 TileRT에서 "타일"은 연산의 단위이자 스케줄링의 단위다.

TileLang — the open language (and why it's not the runtime)TileLang — 오픈 언어 (그리고 왜 런타임이 아닌지)

Language vs runtime. TileLang is a kernel language + compiler: you write one kernel (a matmul, an attention) in Python tile primitives and it emits the GPU kernel. TileRT is a runtime: it takes a whole model's worth of kernels and schedules + overlaps them, persistently, across 8 GPUs. Language = how you author one kernel; runtime = how you run a model built from many. TileLang is fully open; the shipping TileRT kernels are the closed .so (§4–5).언어 vs 런타임. def matmul_relu(A, B, block_M=64, block_N=64, block_K=64, ...):
    C = T.empty([M, N], dtype)

    # ── the GRID of BLOCKS ─────────────────────────────────
    with T.Kernel(T.ceildiv(N, block_N),    # grid.x = N/block_N blocks
                  T.ceildiv(M, block_M),    # grid.y = M/block_M blocks
                  threads=128) as (bx, by): #  128 threads/block = 4 warps
        #   one (bx,by) == one BLOCK → owns one 64×64 output TILE

        A_shared = T.alloc_shared((block_M, block_K), dtype)    # A TILE in SRAM
        B_shared = T.alloc_shared((block_K, block_N), dtype)    # B TILE in SRAM
        C_local  = T.alloc_fragment((block_M, block_N), accum)  # accum TILE in registers
        T.clear(C_local)

        for ko in T.Pipelined(T.ceildiv(K, block_K), num_stages=3):  # SW-pipeline the K-loop
            T.copy(A[by*block_M, ko*block_K], A_shared)   # 128 threads co-load the tile
            T.copy(B[ko*block_K, bx*block_N], B_shared)
            T.gemm(A_shared, B_shared, C_local)           # tile-GEMM → cute/hip, warp-level Tensor Cores

        for i, j in T.Parallel(block_M, block_N):         # 128 threads spread over the tile
            C_local[i, j] = T.max(C_local[i, j], 0)       # relu
        T.copy(C_local, C[by*block_M, bx*block_N])        # write the tile back to HBM
    return C

What T.Pipelined(num_stages=3) does — software pipeliningT.Pipelined(num_stages=3)이 하는 일 — 소프트웨어 파이프라이닝

Each K-loop iteration does two things: load the next A/B tiles (HBM→SRAM, slow) and compute (gemm, fast). Done naively they alternate, so compute waits on every load. T.Pipelined(num_stages=3) tells the compiler to run the loads ahead: it allocates 3 rotating SRAM buffers, prefetches a few iterations, then in steady state loads tile k+3 while computing tile k — so compute streams without stalling.K-루프 각 반복은 두 가지: 다음 A/B 타일 로드(HBM→SRAM, 느림)와 연산(gemm, 빠름). 순진하게 하면 번갈아 하니 연산이 매 로드를 기다린다. T.Pipelined(num_stages=3)은 컴파일러에게 로드를 앞서 돌리라고 지시한다: SRAM 버퍼 3개를 돌려쓰며 몇 반복을 미리 당겨오고, 정상 상태에선 타일 k를 계산하는 동안 타일 k+3을 로드 — 연산이 멈춤 없이 흐른다.

Software pipelining (schematic, ours). num_stages=3 keeps three loop iterations in flight, so the compute lane runs without waiting on HBM. It's the loop-level cousin of double-buffering / warp specialization.소프트웨어 파이프라이닝(개념도, 우리 그림). num_stages=3은 루프 반복 3개를 동시 진행시켜 compute 레인이 HBM을 안 기다리게 한다. 더블버퍼링/warp specialization의 루프 레벨 사촌.

Warp specialization breaks the usual "all warps in a block do the same thing" (SIMT-uniform) model. Second Leap, in more detail — hardware–software co-designSecond Leap 더 자세히 — 하드웨어–소프트웨어 co-design

Once the runtime already sits near the hardware ceiling, you can't win more from the runtime alone — so TileRT co-tuned the model itself together with the runtime (with Xiaomi's MiMo team). "Co-design" here means changing the model's numerics and structure to remove microseconds, not just scheduling them better:런타임이 이미 HW 천장 근처면 런타임만으론 더 못 짜낸다 — 그래서 TileRT는 모델 자체를 런타임과 함께 튜닝했다(Xiaomi MiMo 팀과). 여기서 "co-design"은 스케줄을 더 잘 짜는 게 아니라 모델의 수치·구조를 바꿔 마이크로초를 없애는 것:

  • FP4 on the MoE experts only, FP8 elsewhere. TileRT's stated diagnosis: the bottleneck isn't raw kernel speed, it's "when the next computation can even begin" — the idle gaps at operator/kernel boundaries, compute↔communication stalls, and host↔device syncs. Their fixes: TileRT의 진단: 병목은 커널 자체 속도가 아니라 "다음 계산이 언제 시작될 수 있는가" — 연산자/커널 경계의 유휴 틈, compute↔통신 정체, host↔device 동기화다. 그 해법:

  • Persistent engine kernel.   • Tile-level overlap. Ops are decomposed into fine-grained tiles; the runtime overlaps compute, I/O, and communication so a GPU never waits at a boundary.타일 단위 겹침. 연산을 잘게 타일로 쪼개고, 런타임이 compute·I/O·통신을 겹쳐 GPU가 경계에서 기다리지 않게 한다.

  • DFlash (their MTP). "Isn't the top row already tile-level?" The naive row above is op-level: each op (a matmul, an all-reduce) runs to completion — using tiles internally — before the next op can start, with a launch+sync gap between. The waste is that the next op waits for the whole previous op, so the compute engine sits idle during comm and vice-versa. TileRT's overlap is at tile granularity across ops: the moment op-A finishes tile 0, op-B can consume tile 0 while op-A still computes tiles 1, 2, 3."위 행도 이미 tile level 아니야?" 위 naive 행은 op 단위다: 각 op(행렬곱·all-reduce)은 내부적으로 타일을 쓰긴 하지만 통째로 끝나야 다음 op이 시작하고 그 사이 launch+sync 틈이 있다. 낭비는 다음 op이 이전 op 전체를 기다린다는 것 — 그래서 통신 중엔 연산 엔진이 놀고 그 반대도 마찬가지. TileRT의 겹침은 op을 가로지르는 타일 단위다: op-A가 타일 0을 끝내는 순간, op-A가 타일 1, 2, 3을 계산하는 동안 op-B가 타일 0을 소비한다.

Op-level serial vs tile-level pipelined (schematic, ours). The gap in the figure above comes from ops running whole and serially; TileRT pipelines consecutive ops at tile granularity so one engine's work hides the other's.op 단위 직렬 vs 타일 단위 파이프라인(개념도, 우리 그림). 앞 그림의 틈은 op이 통째로·직렬로 돌아서 생긴다; TileRT는 연속 op을 타일 단위로 파이프라이닝해 한 엔진의 일이 다른 엔진의 일을 가린다.

"isn't this what CUDA Graphs already fix?""이거 CUDA Graph가 이미 해결한 거 아냐?" Partly — CUDA Graphs fix the host-side half of the gap. You capture the whole kernel sequence once and replay it with a single launch, so you stop paying the CPU launch/API cost per op and the GPU can run queued kernels back-to-back without waiting on the CPU. That's why vLLM / TRT-LLM lean on graphs in decode. But a graph is still a DAG of separate kernels, so it does not remove: (1) the GPU-side per-kernel launch/teardown boundary, (2) the HBM round-trip between kernels (kernel A writes results to global memory, kernel B reads them back — no SRAM handoff), (3) the lack of cross-op tile overlap (op B still waits for op A's whole output unless you hand-split streams). TileRT's persistent single kernel targets exactly that remainder: one kernel = no kernel boundaries, no inter-op HBM traffic, tiles handed warp→warp in SRAM. So it's "beyond CUDA Graphs," not the same thing. (This megakernel argument — graphs aren't enough, fuse into one resident kernel — is a known direction; TileRT's is a closed, vendor-described instance.) 부분적으로는 — CUDA Graph는 gap의 호스트 쪽 절반을 없앤다. 커널 시퀀스를 한 번 캡처해 한 번의 launch로 replay하니, op마다 내던 CPU launch/API 비용이 사라지고 GPU가 큐에 쌓인 커널을 CPU 대기 없이 연달아 돌린다. vLLM/TRT-LLM이 decode에서 graph를 쓰는 이유다. 하지만 graph는 여전히 분리된 커널들의 DAG라 다음을 못 없앤다: (1) GPU 쪽 커널별 launch/teardown 경계, (2) 커널 사이 HBM 왕복(커널 A가 결과를 global memory에 쓰고 커널 B가 다시 읽음 — SRAM 핸드오프 아님), (3) op을 가로지르는 타일 겹침 부재(스트림을 손으로 쪼개지 않으면 op B는 op A 전체 출력을 기다림). TileRT의 persistent 단일 커널은 바로 그 나머지를 노린다: 커널 하나 = 커널 경계 없음, op 간 HBM 트래픽 없음, 타일을 warp→warp로 SRAM에서 전달. 즉 "CUDA Graph 너머"지 같은 게 아니다. (graph로는 부족하니 하나의 상주 커널로 융합한다는 megakernel 논리는 알려진 방향; TileRT는 그 닫힌·벤더 서술 사례.)

Op-boundary overlap vs tile-continuous overlap (why "persistent")op 경계 겹침 vs 타일 연속 겹침 (왜 "persistent")

Overlap itself isn't new — FlashAttention, vLLM and NCCL all overlap compute with comm. TileRT's claimed difference is the unit and persistence: conventional op-level overlap still pays a host launch + sync at each op boundary and round-trips results through HBM; a single persistent kernel keeps warps resident and (per the vendor) passes tiles warp→warp through SRAM, so the boundary gap and the extra HBM traffic disappear. (Vendor-described mechanism; the kernel is closed, so this can't be confirmed from the repo.)겹침 자체는 새롭지 않다 — FlashAttention·vLLM·NCCL 모두 compute와 통신을 겹친다. TileRT가 주장하는 차이는 단위와 지속성: 기존 op 단위 겹침은 op마다 host launch + sync를 내고 결과를 HBM으로 왕복시킨다; 단일 persistent 커널은 warp을 상주시키고 (벤더 설명상) 타일을 warp→warp로 SRAM을 통해 넘겨 경계 틈과 추가 HBM 트래픽을 없앤다. (벤더 설명 메커니즘; 커널이 닫혀 있어 레포로 확인 불가.)

the odd function names — a poker metaphor, not a convention이상한 함수 이름 — 포커 은유, 표준 아님 prepare_money, show_hands, go_home are not standard API names — no other stack (PyTorch / vLLM / TVM) uses anything like them. Why this can't chase throughput / concurrency왜 처리량/동시성은 못 노리나

The design is the latency↔throughput trade-off taken to the latency extreme, for structural reasons: (1) a persistent kernel occupies the whole GPU, so there's no free slot to batch other requests the way vLLM's continuous batching does; (2) num_devices=8 is hardwired, one backend per process — a single request owns all 8 GPUs, with no multi-tenant sharing or dynamic scaling; (3) the headline "1000+ TPS" is single-user (batch≈1), not 1000 users each at 1000 TPS. The same 8× B200 under a batching engine trades per-user latency for far higher aggregate throughput. It's a different corner of the design space, not a better engine. (Our reading, from the constraints above.)이 설계는 지연↔처리량 트레이드오프를 지연 극단으로 민 것이고 구조적 이유가 있다: (1) persistent 커널이 GPU 전체를 점유해 vLLM의 continuous batching처럼 다른 요청을 끼워넣을 슬롯이 없다; (2) num_devices=8 하드코딩, 프로세스당 백엔드 하나 — 한 요청이 8 GPU를 통째로 점유, 멀티테넌트 공유·동적 스케일링 없음; (3) 헤드라인 "1000+ TPS"는 단일 사용자(batch≈1)지 1000명 각 1000 TPS가 아니다. 같은 8× B200을 batching 엔진으로 쓰면 사용자별 지연을 내주고 훨씬 높은 총 처리량을 낸다. 더 나은 엔진이 아니라 설계 공간의 다른 코너다.
