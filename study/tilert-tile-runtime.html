TileRT — the tile-based ultra-low-latency LLM runtime (and what's open vs binary) TileRT — 타일 기반 초저지연 LLM 런타임 (그리고 오픈 vs 바이너리)

TileRT (from the TileLang team) serves LLMs for ultra-low latency — millisecond time-per-output-token, 1000+ tokens/s on a 1-trillion-param model — by treating the whole model as fine-grained tile-level tasks that a runtime overlaps and schedules across 8 GPUs. This note starts from scratch — what a "tile" even is — then walks what TileRT is, how it works, how to run it, and a code-walk of the repo (pinned to 242f7b3). Honesty up front: the shipped repo is a thin Python orchestration layer; the runtime and every kernel live in a closed binary, and every speed number is vendor-reported. TileRT(TileLang 팀)는 LLM을 초저지연으로 서빙한다 — 밀리초 단위 토큰당 시간, 1조 파라미터 모델에서 1000+ 토큰/s — 모델 전체를 잘게 쪼갠 타일 단위 태스크로 보고 런타임이 8-GPU에 겹치며 스케줄한다. 이 노트는 "타일"이 뭔지부터 시작해 TileRT가 무엇이고, 어떻게 동작하고, 어떻게 돌리고, 레포 코드까지(242f7b3 핀) 짚는다. 먼저 솔직히: 공개 레포는 얇은 Python 오케스트레이션 층이고, 런타임과 모든 커널은 닫힌 바이너리에 있으며, 모든 속도 수치는 벤더 발표다.

Before "tiles", the ground floor: how a GPU actually runs a computation and the words for its parts — memory hierarchy, thread / warp / block / grid, kernel launch, and cross-GPU communication. Where a canonical diagram exists, the original is linked in the caption and redrawn here in the site palette."타일" 이전에 바닥부터: GPU가 실제로 연산을 어떻게 돌리는지, 그 부분들의 이름 — 메모리 계층, thread / warp / block / grid, 커널 launch, GPU 간 통신. 정본 그림이 있으면 캡션에 원본을 링크하고 사이트 팔레트로 다시 그렸다.

(a) Memory hierarchy — small = fast, big = slow(a) 메모리 계층 — 작을수록 빠르고, 클수록 느리다

The one fact everything follows from: GPU compute has outrun memory bandwidth, so speed comes from reusing data in the tiny fast on-chip memory (SRAM / registers) instead of re-reading slow HBM. FlashAttention's Fig. 1 puts numbers on it (A100): SRAM ~20 MB at 19 TB/s, HBM 40 GB at 1.5 TB/s (~13× slower), host DRAM >1 TB at 12.8 GB/s.모든 것이 따라나오는 사실 하나: GPU 연산이 메모리 대역폭을 앞질러서, 속도는 느린 HBM을 다시 읽는 대신 작고 빠른 온칩 메모리(SRAM/레지스터)에서 데이터를 재사용하는 데서 나온다. FlashAttention 그림 1이 수치를 준다(A100): SRAM ~20 MB @ 19 TB/s, HBM 40 GB @ 1.5 TB/s(~13× 느림), 호스트 DRAM >1 TB @ 12.8 GB/s.

(b) thread → warp → block → grid(b) thread → warp → block → grid

A GPU is thousands of cores grouped into SMs (Streaming Multiprocessors). CUDA exposes a matching hierarchy: you launch a grid of blocks; each block runs on one SM; inside a block, threads run in lockstep groups of 32 — a warp (SIMT: all 32 execute the same instruction at once); each thread is one lane on a core. Blocks share fast SRAM; the warp is the unit the hardware actually schedules.GPU는 수천 코어가 SM(Streaming Multiprocessor)으로 묶인 것. CUDA는 대응 계층을 노출한다: grid(블록 묶음)를 launch → 각 block이 SM 하나에서 → 블록 안 스레드는 32개씩 보조를 맞춰 도는 warp(SIMT: 32개가 같은 명령을 동시에 실행) → 각 thread는 코어의 한 레인. 블록은 빠른 SRAM을 공유하고, warp이 하드웨어가 실제로 스케줄하는 단위다.

(c) A kernel's life & the "execution gap"(c) 커널의 생애와 "execution gap"

The host (CPU) launches a kernel → each block loads its inputs HBM→SRAM/registers, computes (multiply-accumulate) in those fast levels, writes the result back to HBM, and the host usually syncs. A launch costs ~microseconds. When a model is a chain of ops, you pay launch + sync between every op — and at 1000 tokens/s each op is only microseconds, so those idle boundaries dominate. TileRT names this the "execution gap" and its whole design targets it (§3).호스트(CPU)가 커널을 launch → 각 블록이 입력을 HBM→SRAM/레지스터로 로드, 그 빠른 층에서 연산(곱셈-누적), 결과를 HBM에 쓰고, 호스트는 보통 동기화. launch는 ~마이크로초. 모델이 op 체인이면 op마다 launch + sync를 낸다 — 1000토큰/s에선 op가 마이크로초라 그 유휴 경계가 지배한다. TileRT는 이를 "execution gap"이라 부르고 설계 전체가 이를 겨냥한다(§3).

TileRT's own "Execution Gap" and "Microsecond War" figures illustrate exactly this op-boundary problem — see them in the vendor blog: Breaking 1000 TPS.TileRT 자신의 "Execution Gap"·"Microsecond War" 그림이 바로 이 op 경계 문제를 보여준다 — 벤더 블로그 참고: Breaking 1000 TPS.

(d) Communication — splitting across GPUs(d) 통신 — GPU 여러 장으로 쪼갤 때

A model too big for one GPU is split across several; they exchange partials with collectives over NVLink — all-reduce (sum partials into a shared full tensor), all-to-all (route tokens to their expert's GPU, for MoE), p2p (one→one). Communication is itself timed work; overlapping it with compute (compute one tile while sending another) is a central optimization. Full treatment of collectives & their cost: our Parallelism × communication note.GPU 하나에 안 들어가는 모델은 여러 장으로 쪼개고, NVLink 위 collective로 부분을 교환한다 — all-reduce(부분을 합쳐 공유 full 텐서로), all-to-all(토큰을 해당 expert의 GPU로 — MoE), p2p(1→1). 통신은 그 자체가 시간 드는 작업이고, compute와 겹치는 것(한 타일을 계산하며 다른 타일 전송)이 핵심 최적화다. collective와 비용의 전체 설명: 병렬화 × 통신 노트.

1What is a "tile"? (from scratch)"타일"이 뭔가? (기초부터)

Start with the one hardware fact everything follows from: a GPU has enormous compute but is starved for memory bandwidth. Reading a number from HBM (the GPU's main memory) is ~100× slower than doing arithmetic on it. So the whole game of fast GPU code is: read a chunk of data from HBM once, then reuse it many times out of the tiny fast on-chip memory (registers + shared memory / SRAM) before touching HBM again. 모든 것이 따라나오는 하드웨어 사실 하나부터: GPU는 연산은 엄청나지만 메모리 대역폭이 굶주려 있다. HBM(GPU 주메모리)에서 숫자 하나 읽는 게 그 위에서 산술하는 것보다 ~100배 느리다. 그래서 빠른 GPU 코드의 핵심은: HBM에서 데이터 덩어리를 한 번 읽어, 다시 HBM을 건드리기 전에 작은 빠른 온칩 메모리(레지스터 + shared memory / SRAM)에서 여러 번 재사용하는 것이다.

A tile is that chunk. Take a matrix multiply C = A × B (the core of every LLM layer). Instead of computing all of C at once, you cut it into small rectangular tiles — say 128×128. To compute one output tile of C, you load the matching tiles of A and B into fast memory, multiply-accumulate, and only then write the tile out. Each GPU thread-block owns one output tile. Loading a tile costs one slow HBM read but feeds thousands of fast multiply-adds — that reuse is where the speed comes from. Attention (QKᵀ, softmax·V) tiles the same way. This "tiling" is the single most important trick in high-performance GPU kernels. 타일이 바로 그 덩어리다. 행렬곱 C = A × B(모든 LLM 레이어의 핵심)를 보자. C 전체를 한 번에 계산하는 대신, 작은 직사각형 타일 — 예: 128×128 — 로 쪼갠다. C의 출력 타일 하나를 계산하려면 A·B의 대응 타일을 빠른 메모리에 올려 곱셈-누적하고, 그 다음에야 타일을 내보낸다. 각 GPU 스레드블록이 출력 타일 하나를 맡는다. 타일 하나 로드는 느린 HBM 읽기 한 번이지만 수천 번의 빠른 곱셈-덧셈을 먹인다 — 그 재사용에서 속도가 나온다. 어텐션(QKᵀ, softmax·V)도 같은 식으로 타일링한다. 이 "타일링"이 고성능 GPU 커널의 가장 중요한 트릭이다.

Classic GPU tiling of a matmul. TileLang lets you write kernels at exactly this level of abstraction (tile shapes + the HBM↔SRAM↔register moves), and the compiler emits the CUDA. TileRT takes the idea up a level: it treats each tile of work as a schedulable task.행렬곱의 고전적 GPU 타일링. TileLang은 바로 이 추상 수준(타일 모양 + HBM↔SRAM↔레지스터 이동)으로 커널을 쓰게 하고 컴파일러가 CUDA를 낸다. TileRT는 이를 한 단계 올려 각 타일 작업을 스케줄 가능한 태스크로 다룬다.

Two levels build on this: (1) TileLang — an open domain-specific language (built on Apache TVM) for writing GPU kernels at the tile level: you describe the tiles and the data movement, the compiler generates the kernel, instead of hand-writing threads. (2) TileRT — treats a whole LLM layer as many fine-grained tile-level tasks (a chunk of a matmul, an attention tile, a comm chunk) and its runtime dynamically schedules those tasks across 8 GPUs, overlapping compute with I/O and communication. So in TileRT "tile" is both the unit of computation and the unit of scheduling. 여기서 두 층이 올라간다: (1) TileLang — GPU 커널을 타일 수준으로 쓰는 오픈 DSL(Apache TVM 위): 스레드를 손으로 짜는 대신 타일과 데이터 이동을 기술하면 컴파일러가 커널을 낸다. (2) TileRT — LLM 레이어 전체를 잘게 쪼갠 타일 단위 태스크(행렬곱 조각·어텐션 타일·통신 조각)로 보고, 런타임이 그 태스크들을 8-GPU에 동적으로 스케줄하며 compute를 I/O·통신과 겹친다. 그래서 TileRT에서 "타일"은 연산의 단위이자 스케줄링의 단위다.

TileLang — the open language (and why it's not the runtime)TileLang — 오픈 언어 (그리고 왜 런타임이 아닌지)

Language vs runtime. TileLang is a kernel language + compiler: you write one kernel (a matmul, an attention) in Python tile primitives and it emits the GPU kernel. TileRT is a runtime: it takes a whole model's worth of kernels and schedules + overlaps them, persistently, across 8 GPUs. Language = how you author one kernel; runtime = how you run a model built from many. TileLang is fully open; the shipping TileRT kernels are the closed .so (§4–5).언어 vs 런타임. TileLang은 커널 언어 + 컴파일러다: 커널 하나(행렬곱·어텐션)를 Python 타일 프리미티브로 쓰면 GPU 커널을 내준다. TileRT는 런타임이다: 모델 전체 분량의 커널을 받아 8-GPU에 persistent하게 스케줄·겹친다. 언어 = 커널 하나를 작성하는 법; 런타임 = 그 커널들로 만든 모델을 실행하는 법. TileLang은 완전 공개, 배포되는 TileRT 커널은 닫힌 .so(§4–5).

vs other kernel languages. Against raw CUDA/HIP the win is concrete: no hand-written thread indexing, shared-memory staging, double-buffering, or warp-level MMA intrinsics — alloc_shared / copy / gemm / Pipelined are tile-level primitives and the compiler does layout inference + software pipelining, so a FlashMLA-class kernel is ~80 lines of Python. Relative to other tile DSLs (e.g. Triton) it exposes the memory hierarchy more explicitly (separate alloc_shared vs alloc_fragment, explicit num_stages pipelining, use_swizzle for L2) and targets many backends — CUDA, AMD/HIP, Metal, WebGPU, Huawei AscendC, and a CuTeDSL/CUTLASS backend. (The README states these capabilities and claims parity with hand-tuned AITER FlashMLA on MI300X / FlashMLA on H100; it does not make head-to-head "better than Triton/CUTLASS" claims — the Triton framing is ours.)다른 커널 언어 대비. raw CUDA/HIP 대비 이득은 구체적이다: 스레드 인덱싱·shared-memory staging·더블버퍼링·warp MMA intrinsic을 손으로 안 짜도 된다 — alloc_shared/copy/gemm/Pipelined이 타일 수준 프리미티브고 컴파일러가 layout 추론 + 소프트웨어 파이프라이닝을 해서, FlashMLA급 커널이 Python ~80줄이다. 다른 타일 DSL(예: Triton) 대비 메모리 계층을 더 명시적으로 드러내고(alloc_shared vs alloc_fragment 구분, 명시적 num_stages, L2용 use_swizzle) 백엔드가 많다 — CUDA·AMD/HIP·Metal·WebGPU·Huawei AscendC·CuTeDSL/CUTLASS. (README는 이 기능들과 hand-tuned AITER FlashMLA(MI300X)/FlashMLA(H100) 동급 성능을 주장; Triton/CUTLASS 대비 "더 낫다"는 head-to-head 주장은 없다 — Triton 대조는 우리 프레이밍.)

    with T.Kernel(T.ceildiv(N, block_N),    # grid.x = N/block_N blocks
                  T.ceildiv(M, block_M),    # grid.y = M/block_M blocks
                  threads=128) as (bx, by): #  128 threads/block = 4 warps
        #   one (bx,by) == one BLOCK → owns one 64×64 output TILE

        A_shared = T.alloc_shared((block_M, block_K), dtype)    # A TILE in SRAM
        B_shared = T.alloc_shared((block_K, block_N), dtype)    # B TILE in SRAM
        C_local  = T.alloc_fragment((block_M, block_N), accum)  # accum TILE in registers
        T.clear(C_local)

        for ko in T.Pipelined(T.ceildiv(K, block_K), num_stages=3):  # SW-pipeline the K-loop
            T.copy(A[by*block_M, ko*block_K], A_shared)   # 128 threads co-load the tile
            T.copy(B[ko*block_K, bx*block_N], B_shared)
            T.gemm(A_shared, B_shared, C_local)           # tile-GEMM → cute/hip, warp-level Tensor Cores

        for i, j in T.Parallel(block_M, block_N):         # 128 threads spread over the tile
            C_local[i, j] = T.max(C_local[i, j], 0)       # relu
        T.copy(C_local, C[by*block_M, bx*block_N])        # write the tile back to HBM
    return C
  • Grid = the first two args of T.Kernel(ceildiv(N,block_N), ceildiv(M,block_M), …) — the block counts in x, y. For M=N=K=1024, block=64 → 16×16 = 256 blocks.Grid = T.Kernel(ceildiv(N,block_N), ceildiv(M,block_M), …)의 앞 두 인자 — x, y 블록 개수. M=N=K=1024, block=64면 16×16 = 256 blocks.
  • Block = one (bx, by) iteration; it computes one 64×64 output tile of C. All 256 blocks are scheduled across the SMs.Block = (bx, by) 하나; C의 64×64 출력 타일 하나를 계산. 256 blocks가 SM들에 스케줄된다.
  • Tile = block_M×block_N = 64×64 (output), plus the A_shared/B_shared 64×64 input tiles staged in SRAM; block_K=64 is the reduction-tile depth stepped by the ko loop.Tile = block_M×block_N=64×64(출력), 그리고 SRAM에 올리는 A_shared/B_shared 64×64 입력 타일; block_K=64는 ko 루프가 밟는 reduction 타일 깊이.
  • Warp = you never name it; threads=128 → 128÷32 = 4 warps/block. T.gemm lowers to cute/hip, which uses warp-level Tensor-Core MMA. The compiler maps threads→warps for you.Warp = 직접 명시 안 함; threads=128 → 128÷32 = 4 warps/block. T.gemm이 cute/hip로 내려가 warp 단위 Tensor-Core MMA를 쓴다. 컴파일러가 스레드→warp 매핑을 대신한다.
  • Thread = one of the 128; T.copy and T.Parallel(block_M, block_N) are the compiler spreading the tile's per-element work across those 128 threads.Thread = 128개 중 하나; T.copy와 T.Parallel(block_M, block_N)은 타일의 원소별 작업을 그 128 스레드에 컴파일러가 분배하는 것.

2What TileRT is & why — speed as the goalTileRT란 & 왜 — 속도가 목표

Almost every serving stack (vLLM, SGLang, TRT-LLM) optimizes throughput — tokens/sec across a big batch of concurrent users. TileRT optimizes the opposite corner: the latency of a single request, the millisecond time-per-output-token one user waits between tokens. That matters when the individual request's speed is the product — agents, coding assistants, voice, real-time decisions. 거의 모든 서빙 스택(vLLM·SGLang·TRT-LLM)은 처리량을 최적화한다 — 많은 동시 사용자 배치에 대한 토큰/초. TileRT는 반대 코너를 최적화한다: 단일 요청의 지연, 한 사용자가 토큰 사이에 기다리는 밀리초 단위 토큰당 시간. 개별 요청의 속도 자체가 제품일 때 — 에이전트·코딩 보조·음성·실시간 결정 — 이게 중요하다.

"push the latency limits of LLMs without compromising model size or quality — enabling models with hundreds of billions of parameters to achieve millisecond-level time per output token (TPOT)."

— TileRT README · github.com/tile-ai/tilert (vendor)

TileRT's public thesis ("Speed as the next scaling law") frames three eras — Chat (quality) → Agentic (throughput) → Autonomous (speed) — and argues test-time scaling makes latency load-bearing: faster inference means more rollouts and deeper reasoning paths per unit time. The blog's slogan is literally "Speed is all you need." Treat this as a vendor's positioning argument, not a proven law. TileRT의 공개 주장("속도가 다음 스케일링 법칙")은 세 시대를 그린다 — Chat(품질) → Agentic(처리량) → Autonomous(속도) — 그리고 test-time scaling이 지연을 결정적으로 만든다고 본다: 더 빠른 추론 = 단위 시간당 더 많은 rollout과 더 깊은 추론 경로. 블로그 슬로건은 그대로 "Speed is all you need". 이는 벤더의 포지셔닝 주장이지 증명된 법칙이 아니다.

3How it works — the tile runtime (vendor's telling)어떻게 동작하나 — 타일 런타임 (벤더 설명)

source note출처 주의This section is TileRT's own description from its blogs. The actual implementation is inside the closed binary (§5), so none of it is verifiable from the source code.이 절은 블로그의 TileRT 자체 설명이다. 실제 구현은 닫힌 바이너리(§5) 안이라 소스에서 검증 불가.

TileRT's stated diagnosis: the bottleneck isn't raw kernel speed, it's "when the next computation can even begin" — the idle gaps at operator/kernel boundaries, compute↔communication stalls, and host↔device syncs. Their fixes: TileRT의 진단: 병목은 커널 자체 속도가 아니라 "다음 계산이 언제 시작될 수 있는가" — 연산자/커널 경계의 유휴 틈, compute↔통신 정체, host↔device 동기화다. 그 해법:

  • Persistent engine kernel. The whole forward pipeline is compiled AOT into one resident GPU kernel; the host launches it once and it runs continuously, enabling end-to-end prefetch and killing per-op launch/sync overhead.Persistent engine 커널. forward 파이프라인 전체를 AOT로 하나의 상주 GPU 커널로 컴파일; host가 한 번 실행하면 계속 돌아, end-to-end 프리페치가 가능해지고 op별 실행/동기화 오버헤드가 사라진다.
  • Tile-level overlap. Ops are decomposed into fine-grained tiles; the runtime overlaps compute, I/O, and communication so a GPU never waits at a boundary.타일 단위 겹침. 연산을 잘게 타일로 쪼개고, 런타임이 compute·I/O·통신을 겹쳐 GPU가 경계에서 기다리지 않게 한다.
  • Specialization hierarchy. warp → block → GPU specialization: dedicated warp groups / blocks / whole GPUs take distinct roles (compute vs data-movement vs communication). Concretely for GLM-5.1: "GPU 0 runs sparse-index worker; GPU 1–7 run MLA workers."특화 계층. warp → block → GPU 특화: 전용 warp 그룹/블록/GPU가 서로 다른 역할(연산 vs 데이터 이동 vs 통신)을 맡는다. GLM-5.1 구체 예: "GPU 0 = sparse-index 워커; GPU 1–7 = MLA 워커".
  • DFlash (their MTP). Instead of a naive extra LM-head per step, DFlash does block-level masked parallel prediction — a small draft (sliding-window attention, block size 8, trained with the Muon optimizer + self-distillation) fills a whole masked block in one pass, keeping acceptance high while bounding the head's compute.DFlash (그들의 MTP). 스텝마다 순진하게 LM-head를 하나 더 붙이는 대신, DFlash는 블록 단위 마스크 병렬 예측 — 작은 draft(sliding-window attention, 블록 크기 8, Muon 옵티마이저 + self-distillation 학습)가 마스크된 블록 전체를 한 번에 채워, acceptance는 높게 유지하며 head 연산을 묶는다.

The mechanism as TileRT describes it: a resident kernel that overlaps tile-level compute, communication and I/O across role-specialized GPUs, removing the idle "execution gap." Sources: Breaking 1000 TPS, Speed as the next scaling law (both vendor).TileRT가 설명하는 메커니즘: 역할 특화된 GPU들에 걸쳐 타일 단위 연산·통신·I/O를 겹치는 상주 커널로 유휴 "실행 틈"을 제거. 출처: Breaking 1000 TPS, Speed as the next scaling law(둘 다 벤더).

TileLang → TileScale → TileRT. TileLang is the open tile-level DSL; TileScale is its distributed extension (a "mega-device" abstraction with tile-level comm on NVSHMEM); TileRT is the closed runtime that packages these ideas. The README says the compiler techniques "will be gradually shared with the community as they are integrated into TileLang and TileScale" — i.e. TileRT ships as a binary now, the open pieces trail behind. TileLang → TileScale → TileRT. TileLang은 오픈 타일 DSL; TileScale은 그 분산 확장("mega-device" 추상 + NVSHMEM 위 타일 단위 통신); TileRT는 이 아이디어들을 담은 닫힌 런타임. README는 컴파일러 기법을 "TileLang·TileScale에 통합되며 점진적으로 공개"한다고 한다 — 즉 TileRT는 지금은 바이너리, 오픈 조각은 뒤따른다.

Op-boundary overlap vs tile-continuous overlap (why "persistent")op 경계 겹침 vs 타일 연속 겹침 (왜 "persistent")

Overlap itself isn't new — FlashAttention, vLLM and NCCL all overlap compute with comm. TileRT's claimed difference is the unit and persistence: conventional op-level overlap still pays a host launch + sync at each op boundary and round-trips results through HBM; a single persistent kernel keeps warps resident and (per the vendor) passes tiles warp→warp through SRAM, so the boundary gap and the extra HBM traffic disappear. (Vendor-described mechanism; the kernel is closed, so this can't be confirmed from the repo.)겹침 자체는 새롭지 않다 — FlashAttention·vLLM·NCCL 모두 compute와 통신을 겹친다. TileRT가 주장하는 차이는 단위와 지속성: 기존 op 단위 겹침은 op마다 host launch + sync를 내고 결과를 HBM으로 왕복시킨다; 단일 persistent 커널은 warp을 상주시키고 (벤더 설명상) 타일을 warp→warp로 SRAM을 통해 넘겨 경계 틈과 추가 HBM 트래픽을 없앤다. (벤더 설명 메커니즘; 커널이 닫혀 있어 레포로 확인 불가.)

What is verifiable is the order of fused ops the open Python registers per layer (the runtime then schedules them inside the .so). DeepSeek-V3.2, per device: MLA (RMSNorm → Q/KV projections → RoPE → flash_sparse_mla; device 0 on the sparse-select path, devices 1–7 pure MLA) → UnProjOAllReduce → MoE (RMSNormExpertProj → ExpertSelectUpGateSiLU → ExpertDownAllReduce). Note the fused compute+comm ops (down_allreduce, expert_down_allreduce) — the projection and its all-reduce are one op, so the overlap is built into the op boundary, not bolted on.확인 가능한 것은 공개 Python이 레이어당 등록하는 융합 op 순서다(런타임이 .so 안에서 스케줄). DeepSeek-V3.2, 디바이스당: MLA(RMSNorm → Q/KV projection → RoPE → flash_sparse_mla; device 0은 sparse-select, device 1–7은 pure MLA) → UnProjOAllReduce → MoE(RMSNormExpertProj → ExpertSelectUpGateSiLU → ExpertDownAllReduce). 융합 compute+comm op(down_allreduce·expert_down_allreduce)에 주목 — projection과 all-reduce가 한 op이라 겹침이 op 경계에 내장돼 있다.

the odd function names — a poker metaphor, not a convention이상한 함수 이름 — 포커 은유, 표준 아님 prepare_money, show_hands, go_home are not standard API names — no other stack (PyTorch / vLLM / TVM) uses anything like them. They're TileRT's own internal codenames, themed on a card table: prepare_money = ante up — stake all the weight / cache / scratch tensors into the runtime once before play (the registration step); show_hands = "show your hand" — run the entire forward and reveal the result (next-token logits); go_home = leave the table (teardown / cleanup). The names carry no technical meaning beyond "register / run forward / clean up" — it's a naming taste, and the opacity is itself a tell that this is an internal, experimental codebase.prepare_money·show_hands·go_home은 표준 API 이름이 아니다 — PyTorch/vLLM/TVM 어디도 이런 이름을 안 쓴다. TileRT 자체 내부 코드네임으로 카드 테이블(포커)에서 따왔다: prepare_money = 판돈 걸기 — 플레이 전 모든 가중치/캐시/스크래치 텐서를 런타임에 한 번 등록(register); show_hands = "패를 깐다" — forward 전체를 돌려 결과(다음 토큰 logits)를 드러냄; go_home = 테이블 떠나기(teardown/cleanup). 이름엔 "등록/실행/정리" 이상의 기술적 의미가 없다 — 작명 취향이고, 그 불투명함이 내부·실험적 코드베이스라는 방증이다.

④ Every op is a thin .so dispatch. Each file in ops/ is a docstring + input validation + weight-layout converter + one torch.ops.tilert.<name>_op(...) call. The fusion / tiling / comm-overlap is compiled into the binary — the Python only marshals tensors. Examples: ④ 모든 op은 얇은 .so 디스패치. ops/의 각 파일은 docstring + 입력 검증 + 가중치 배치 컨버터 + torch.ops.tilert.<name>_op(...) 호출 하나. 융합/타일링/통신 겹침은 바이너리에 컴파일돼 있고 Python은 텐서만 넘긴다. 예:

7Status & our take상태 & 우리 관점

Maturity: self-described "experimental preview." Distribution is a closed binary wheel, B200-only pinned ABI, two models (DeepSeek-V3.2 ≤160K ctx, GLM-5 ≤200K ctx), one backend per process, ~monthly releases (v0.1.0 → v0.1.4). MIT license covers the wrapper/repo, not the compiler internals (which aren't distributed as source). The open pieces are meant to land in TileLang/TileScale over time. 성숙도: 스스로 "experimental preview". 배포는 닫힌 바이너리 휠, B200 전용 핀 ABI, 두 모델(DeepSeek-V3.2 ≤160K, GLM-5 ≤200K), 프로세스당 백엔드 하나, ~월간 릴리스(v0.1.0 → v0.1.4). MIT는 래퍼/레포에만 적용, 컴파일러 내부(소스 미배포)엔 아님. 오픈 조각은 시간이 지나며 TileLang/TileScale로 들어갈 예정.

Why this can't chase throughput / concurrency왜 처리량/동시성은 못 노리나

The design is the latency↔throughput trade-off taken to the latency extreme, for structural reasons: (1) a persistent kernel occupies the whole GPU, so there's no free slot to batch other requests the way vLLM's continuous batching does; (2) num_devices=8 is hardwired, one backend per process — a single request owns all 8 GPUs, with no multi-tenant sharing or dynamic scaling; (3) the headline "1000+ TPS" is single-user (batch≈1), not 1000 users each at 1000 TPS. The same 8× B200 under a batching engine trades per-user latency for far higher aggregate throughput. It's a different corner of the design space, not a better engine. (Our reading, from the constraints above.)이 설계는 지연↔처리량 트레이드오프를 지연 극단으로 민 것이고 구조적 이유가 있다: (1) persistent 커널이 GPU 전체를 점유해 vLLM의 continuous batching처럼 다른 요청을 끼워넣을 슬롯이 없다; (2) num_devices=8 하드코딩, 프로세스당 백엔드 하나 — 한 요청이 8 GPU를 통째로 점유, 멀티테넌트 공유·동적 스케일링 없음; (3) 헤드라인 "1000+ TPS"는 단일 사용자(batch≈1)지 1000명 각 1000 TPS가 아니다. 같은 8× B200을 batching 엔진으로 쓰면 사용자별 지연을 내주고 훨씬 높은 총 처리량을 낸다. 더 나은 엔진이 아니라 설계 공간의 다른 코너다. (위 제약에서 나온 우리 해석.)

editor's note — our take (not tile-ai's claim)편집자 주 — 우리 관점(tile-ai 주장 아님) For our stack this is read-only inspiration, not a tool we can run: it's a B200/CUDA-only closed binary, and we serve on MI250/ROCm — TileRT won't load. But its ideas are exactly the ones we care about — a persistent kernel that overlaps compute with communication to kill the idle gap is the same instinct behind dual-batch-overlap and our SLO-aware P/D muxing (Tropical) work; and its diagnosis ("the bottleneck is when the next op can start") matches what we see profiling MI250 all-reduce/expert-dispatch. The transferable, verifiable part is the open path: TileLang / TileScale (tile-level kernels + NVSHMEM comm) — those we can read and adapt. The unverifiable part is every speed number and the runtime itself. Net: worth tracking TileLang/TileScale closely; treat TileRT's TPS claims as a vendor demo, not a benchmark. 우리 스택 관점에선 읽어볼 영감이지 돌릴 수 있는 도구가 아니다: B200/CUDA 전용 닫힌 바이너리이고 우리는 MI250/ROCm에서 서빙 — TileRT는 로드되지 않는다. 하지만 그 아이디어는 정확히 우리가 관심 있는 것 — compute를 통신과 겹치는 persistent 커널로 유휴 틈을 없애는 것은 dual-batch-overlap과 우리 SLO 인식 P/D 먹싱(Tropical) 작업과 같은 직관; 그 진단("병목은 다음 op이 언제 시작하느냐")도 MI250 all-reduce/expert-dispatch 프로파일에서 보는 것과 일치. 이전·검증 가능한 부분은 오픈 경로: TileLang / TileScale(타일 커널 + NVSHMEM 통신) — 이건 우리가 읽고 적용할 수 있다. 검증 불가한 부분은 모든 속도 수치와 런타임 자체. 결론: TileLang/TileScale은 가까이 추적할 가치가 있고, TileRT의 TPS 주장은 벤치마크가 아니라 벤더 데모로 취급.
