The path a request takes from arrival to response. Prefill builds the KV; Decode pulls that KV via READ (pull) to generate tokens. 하나의 request가 들어와 응답으로 나가기까지의 경로입니다. Prefill이 KV를 만들고, Decode가 그 KV를 READ(pull)로 당겨와 토큰을 생성합니다.

KV behavior by request scenario (4 variants) 요청 시나리오별 KV 동작 (4종)

ISL 1024 = 64 blocks (block_size 16), decode 5 tokens fixed across variants. We compare how KV READ behaves by prefix cache hit pattern. All map to branches in nixl/worker.py · _read_blocks. ISL 1024 = 64 blocks(block_size 16 기준), decode 5 토큰을 공통으로 두고, prefix cache hit 양상에 따라 KV READ가 어떻게 달라지는지 비교합니다. 모두 nixl/worker.py · _read_blocks의 분기에 대응합니다.

①

Prefill 1024 (cache miss) → Decode 5 Prefill 1024 (캐시 미스) → Decode 5

D has no cache, so all 64 prompt blocks are READ from P. num_local_blocks == num_remote_blocks → full read. D에 캐시가 없어 prompt 64 blocks 전부를 P에서 READ. num_local_blocks == num_remote_blocks → full read.

②

Prefill 1024, full prefix cache hit → Decode 5 Prefill 1024 전부 Prefix cache hit → Decode 5

All 64 prompt blocks already exist on D (full hit). No KV body transfer — just a notif to P so it can free the blocks. len(local_block_ids) == 0 → send_notif() only. prompt 64 blocks가 D에 이미 전부 존재(full hit). KV body 전송 없이 P에 notif만 보내 블록을 free. len(local_block_ids) == 0 → send_notif() only.

③

Prefill 1024 + Decode partial hit → READ remainder → Decode 5 Prefill 1024 + Decode 일부 hit → 나머지 READ → Decode 5

D has some of the prefix (hit). Only the missing blocks are READ. num_local_blocks < num_remote_blocks → remote_block_ids[-num_local_blocks:]. (docs example: local 1 / remote 32) D가 prefix 일부를 이미 보유(hit). 안 가진 나머지 blocks만 READ. num_local_blocks < num_remote_blocks → remote_block_ids[-num_local_blocks:]. (문서 예시: local 1 / remote 32)

④

Multi-turn (Turn 2) — new request, prefill again 멀티턴 (Turn 2) — 새 request, prefill 다시 거침

A follow-up turn is also an independent request, so proxy→prefill→decode always re-runs. If prior context is still in the cache, both P and D enjoy a prefix hit and only the new tokens are processed. But the generated tokens from Turn 1 live on D, not on P, so P recomputes those (yellow). get_num_new_matched_tokens follows the local+external cache path. 후속 턴도 독립된 request라 항상 proxy→prefill→decode를 다시 탄다. 이전 문맥이 캐시에 남아 있으면 prefix hit로 P/D 모두 새 토큰만 처리. 단, Turn 1의 생성 토큰은 D에서 만들어져 P엔 없으므로 P가 재계산(노랑). get_num_new_matched_tokens local+external 캐시 경로.

Big picture전체 그림

user → proxy → [Prefill] → proxy → [Decode] → proxy → user │ │ holds KV during lease _read_blocks pulls P's KV via NIXL READ
user → proxy → [Prefill] → proxy → [Decode] → proxy → user │ │ KV를 lease 동안 보유 _read_blocks 로 P의 KV를 NIXL READ (pull)

The key point is that NixlConnector is "READ"-based. Prefill (P) doesn't push KV; instead, Decode (D) pulls P's KV blocks directly (pull). As a result, save_kv_layer on P is a no-op, and the actual transfer is initiated from D's _read_blocks().

핵심은 NixlConnector가 "READ" 방식이라는 점입니다. Prefill(P)이 KV를 밀어주는 게 아니라, Decode(D)가 P의 KV 블록을 직접 읽어옵니다(pull). 그래서 P 쪽 save_kv_layer는 no-op이고, 실제 전송은 D의 _read_blocks()에서 시작됩니다.

An engine step is always three stages: schedule() → execute_model() → update_from_output().

엔진의 한 스텝은 항상 schedule() → execute_model() → update_from_output() 세 단계로 구성됩니다.

From the KV-transfer angle, the two important spots are schedule() (scheduler side) and execute_model() (worker side).

KV transfer 관점에서 중요한 건 schedule()(scheduler 쪽)와 execute_model()(worker 쪽) 두 곳입니다.

1 Proxy → Prefill PREFILL

Proxy sends the input plus kv_transfer_params to P. On the initial request, all remote info is None; to mark itself as the prefill side it sets do_remote_decode=True, do_remote_prefill=False, and runs a one-token prefill (max_tokens=1).

Proxy가 input과 함께 kv_transfer_params를 P로 전송합니다. 최초 요청이라 remote 정보는 전부 None, 자기가 prefill임을 알리기 위해 do_remote_decode=True, do_remote_prefill=False로 설정하고 max_tokens=1로 한 토큰만 prefill합니다.

2 Prefill: connector query in schedule() Prefill: schedule()의 connector 질의 PREFILL

When the scheduler asks about a new request's cache state, it calls the connector.

스케줄러가 새 request의 캐시 상태를 물어볼 때 connector를 호출합니다.

Since P doesn't have do_remote_prefill, NixlConnectorScheduler returns (0, False) → P runs a normal prefill.

P는 do_remote_prefill이 아니므로 NixlConnectorScheduler가 (0, False)를 반환 → 그냥 정상 prefill을 수행합니다.

3 Prefill: request_finished() — hold KV + return coords Prefill: request_finished()로 KV 보유 + 좌표 반환 PREFILL

When prefill finishes and the request closes, _free_request → _connector_finished → connector's request_finished() is called.

prefill이 끝나 request가 종료될 때 _free_request → _connector_finished → connector의 request_finished()가 호출됩니다.

P doesn't immediately free its blocks (delay_free_blocks=True); it registers them in _reqs_need_send with a lease TTL, and returns a dict with the coordinates D will read. Note that do_remote_prefill / decode flips relative to the initial request, and v0.22 fields like remote_request_id are filled in.

P는 블록을 즉시 해제하지 않고(delay_free_blocks=True) lease TTL을 걸어 _reqs_need_send에 등록한 뒤, D가 읽어갈 좌표를 채운 dict를 반환합니다. 여기서 do_remote_prefill / decode가 최초와 정반대로 뒤집히고 remote_request_id 등 신규 필드가 채워집니다.

This dict rides out to the proxy as part of EngineCoreOutput.kv_transfer_params.

이 dict는 EngineCoreOutput.kv_transfer_params로 응답에 실려 proxy로 나갑니다.

4 Proxy → Decode

Proxy forwards the kv_transfer_params P returned (now do_remote_prefill=True with coords filled) along with the original input to D.

Proxy가 P가 돌려준 kv_transfer_params(이제 do_remote_prefill=True + 좌표 채워짐)를 원래 input과 함께 D로 전달합니다.

5 Decode: recognize "pull from remote" Decode: "remote에서 당겨와야 함" 인지 DECODE

D's get_num_new_matched_tokens() sees do_remote_prefill=True this time and returns (prompt block count, True=async).

D의 get_num_new_matched_tokens()는 이번엔 do_remote_prefill=True를 보고 (prompt 블록 수, True=async)를 반환합니다.

If load_kv_async=True, D allocates only local blocks + registers the recv target, then parks the request in WAITING_FOR_REMOTE_KVS (a pre-processing phase).

load_kv_async=True면 D는 로컬 블록만 할당 + recv 대상 등록 후, request를 WAITING_FOR_REMOTE_KVS로 빼둡니다(전처리 성격).

update_state_after_alloc() registers the request in _reqs_need_recv (and sets do_remote_prefill=False so it only triggers once); build_connector_meta() turns that into metadata for the worker.

update_state_after_alloc()가 request를 _reqs_need_recv에 등록(+ do_remote_prefill=False로 1회만 트리거)하고, build_connector_meta()가 이를 worker로 넘길 메타데이터로 변환합니다.

6 Decode: actual READ kicks off in execute_model() Decode: execute_model()에서 실제 READ 시작 DECODE

In v0.22.0, the worker mixin's context manager calls bind → start_load_kv on entry and wait_for_save → get_finished on exit.

v0.22.0에서는 worker mixin의 context manager가 진입할 때 bind → start_load_kv를 호출하고, 빠져나갈 때 wait_for_save → get_finished를 호출합니다.

The call sites are in gpu_model_runner: maybe_get_kv_connector_output (L4226), and when there are no tokens to run, kv_connector_no_forward (L4023) handles transfer-only paths.

호출부는 gpu_model_runner의 maybe_get_kv_connector_output (L4226)이며, 돌릴 토큰이 없을 땐 kv_connector_no_forward (L4023) 경로로 전송만 수행합니다.

start_load_kv() — if no handshake yet, kick one off in the background and continue; if done, read right away. Finished requests are pulled from _ready_requests and read; lease/heartbeat are also handled.

start_load_kv() — handshake가 안 됐으면 백그라운드로 띄우고 continue, 됐으면 바로 read. 끝난 요청은 _ready_requests에서 꺼내 read하고, lease/heartbeat도 관리합니다.

Inside _read_blocks_for_req → _read_blocks: if it's a full prefix-hit, just send a notif; otherwise build descriptors and issue an async NIXL READ.

_read_blocks_for_req → _read_blocks 안에서 full prefix-hit이면 notif만 보내고, 아니면 descriptor 계산 후 NIXL READ를 async로 던집니다.

7 Decode: polling for completion (get_finished) Decode: 완료 폴링 (get_finished) DECODE PREFILL

At the end of each step, send/recv completions are tallied. D is the receiver, so _pop_done_transfers checks handles via check_xfer_state; failed requests are marked invalid and routed to recompute.

매 스텝 종료 시 송/수신 완료를 집계합니다. D는 수신측이라 _pop_done_transfers에서 check_xfer_state로 핸들을 확인하고, 실패한 요청은 invalid 처리 후 재계산 경로로 보냅니다.

The KVConnectorOutput goes back to the scheduler and is processed at the end of update_from_output. If D is still in WAITING_FOR_REMOTE_KVS, mark it ready; on P, freeing happens when send completes.

이 결과(KVConnectorOutput)가 스케줄러로 돌아와 update_from_output 끝에서 처리됩니다. D는 아직 WAITING_FOR_REMOTE_KVS면 ready 표시, P는 send 완료 시 블록을 해제합니다.

P's "finished sending" fires when it receives the notif (_get_new_notifs) that D has finished reading. Only then are the blocks held by lease in step 3 released — which is why you see sending/recving logs paired across P/D.
P 쪽 "Finished sending"은 D가 다 읽었다는 notif(_get_new_notifs)를 받은 시점입니다. 그제서야 3단계에서 lease로 붙잡아둔 블록을 해제합니다 — P/D 양쪽에서 sending/recving 로그가 짝지어 보이는 이유입니다.

8 Decode: return from WAITING → decoding Decode: WAITING 복귀 → 디코딩 DECODE

On the next schedule(), requests in WAITING_FOR_REMOTE_KVS attempt promotion.

다음 schedule()에서 WAITING_FOR_REMOTE_KVS 요청을 promote 시도합니다.

Promotion calls _update_waiting_for_remote_kv(), which registers the transferred blocks into the cache (for full-hit, it sets num_computed_tokens -= 1 so one token recomputes) and returns to WAITING.

promote가 호출하는 _update_waiting_for_remote_kv()가 전송된 블록을 캐시로 등록하고(full-hit이면 마지막 토큰 1개 재계산용으로 num_computed_tokens -= 1) WAITING으로 되돌립니다.

From here, with prompt KV in place (num_computed_tokens > 0), the request enters the regular decode loop and emits one token per step. Generated tokens flow out as EngineCoreOutput → output processor → proxy → user.

이후 request는 prompt KV를 갖춘 상태(num_computed_tokens > 0)로 일반 디코딩 루프에 진입해 매 스텝 토큰 1개씩 생성합니다. 생성 토큰은 EngineCoreOutput → output processor → proxy → user로 전달됩니다.
