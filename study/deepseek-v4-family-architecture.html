One-line summary한 줄 요약 V4 keeps the familiar decoder-only stack but swaps two things underneath: the residual connection becomes mHC, four parallel streams mixed by a Sinkhorn-normalised matrix, and attention becomes a per-layer compression schedule where each layer declares how many tokens collapse into one KV entry. V4.1 then splits that stack into a 20-layer causal encoder and a 20-layer decoder that reads global KV from the encoder's final states, and bolts on Engram — 196B parameters of hashed n-gram lookup in exactly two layers. Active parameters stay tiny throughout: 13B, 49B, and 8B/16B respectively.V4 는 익숙한 decoder-only 스택을 유지하면서 그 밑의 두 가지를 바꿨다. residual connection 이 mHC — Sinkhorn 으로 정규화된 행렬이 섞는 4개의 병렬 스트림 — 로 바뀌었고, attention 은 각 레이어가 "토큰 몇 개를 KV 항목 하나로 접을지" 를 선언하는 레이어별 압축 스케줄이 됐다. V4.1 은 그 스택을 20층 causal encoder + 20층 decoder 로 쪼개 decoder 가 encoder 최종 상태에서 global KV 를 읽게 하고, 거기에 Engram — 정확히 두 개 레이어에 들어간 196B 파라미터의 해시 n-gram 룩업 — 을 덧붙였다. 활성 파라미터는 내내 작다: 각각 13B, 49B, 8B/16B.

Glossary — the new vocabulary용어 정리 — 새로 생긴 말들

CSA Compressed Sparse Attention

Attention over a KV cache where several tokens are compressed into one entry. In V4 the compression ratio is 4.토큰 여러 개를 KV 항목 하나로 압축한 캐시 위의 attention. V4 에서 압축비는 4 다.

HCA Heavily Compressed Attention

The same idea, far more aggressive: ratio 128. V4 alternates CSA and HCA layer by layer.같은 아이디어를 훨씬 공격적으로 — 비율 128. V4 는 레이어마다 CSA 와 HCA 를 번갈아 쓴다.

CSA2

V4.1's revision, parameterised as CSA2(ratio, mode) where mode is Full / Reindex / Reuse — whether this layer builds, recomputes or borrows the KV and sparse indices.V4.1 의 개정판. CSA2(비율, 모드) 로 쓰고 모드는 Full / Reindex / Reuse — 이 레이어가 KV 와 희소 인덱스를 만드는지, 다시 계산하는지, 빌려 쓰는지를 뜻한다.

mHC manifold-constrained hyper-connections

Replaces x + F(x) with four parallel residual streams mixed by a learned matrix that is kept near-doubly-stochastic by Sinkhorn iterations.x + F(x) 를 4개의 병렬 residual 스트림으로 대체하고, Sinkhorn 반복으로 거의 이중확률행렬에 묶인 학습 행렬이 그것을 섞는다.

Engram

A hashed n-gram embedding bank — a learned lookup table read by hash and gated into the trunk. 196B parameters, in two layers only.해시된 n-gram 임베딩 뱅크. 해시로 읽어 trunk 에 게이팅해 넣는 학습된 룩업 테이블이다. 196B 파라미터, 단 두 레이어에만.

CED Global KV

Causal-Encoder-Decoder global KV: the decoder's long-range keys and values come from the encoder's final hidden states, computed once.Causal-Encoder-Decoder 전역 KV. decoder 의 장거리 key/value 가 encoder 최종 은닉 상태에서 오고, 한 번만 계산된다.

DSpark

V4.1's speculative decoding: 3 multi-token-prediction layers with their own small MoE, drafting in blocks of 5.V4.1 의 투기적 디코딩. 자체 소형 MoE 를 가진 multi-token-prediction 레이어 3개가 블록 5 단위로 draft 한다.

SWA sliding window attention

Attention restricted to the last w tokens. All three models use sliding_window: 128 and give the first layers SWA only.마지막 w 토큰으로 제한한 attention. 세 모델 모두 sliding_window: 128 을 쓰고 앞쪽 레이어엔 SWA 만 준다.

Active parameters활성 파라미터

How much of the model actually runs per token. In an MoE only the selected experts fire, so 1.6T total can mean 49B of work.토큰당 실제로 도는 모델의 양. MoE 에선 선택된 전문가만 발화하므로 총 1.6T 라도 연산은 49B 일 수 있다.

2One field decodes the attention zoo: compress_ratiosattention 용어를 한 방에 푸는 필드: compress_ratios

The figures label layers "CSA", "HCA", "SWA", "CSA2(2, Full)". Those labels are not separate mechanisms — they are one mechanism with a per-layer integer. Every config carries a compress_ratios array with one entry per layer, and the entry says how many tokens that layer folds into a single KV entry.그림은 레이어에 "CSA", "HCA", "SWA", "CSA2(2, Full)" 라고 이름을 붙인다. 이것들은 별개의 메커니즘이 아니라 레이어별 정수 하나를 가진 하나의 메커니즘이다. 모든 config 에 레이어당 한 항목씩 들어간 compress_ratios 배열이 있고, 그 값이 해당 레이어가 토큰 몇 개를 KV 항목 하나로 접는지를 말한다.

ratio  0  →  no global KV at all; sliding window only   ("SWA")
ratio  1  →  one token per KV entry, uncompressed       (V4.1 decoder)
ratio  2  →  2 tokens per entry                         (V4.1 encoder)
ratio  4  →  4 tokens per entry                         ("CSA")
ratio 128 →  128 tokens per entry                       ("HCA")

Laid out as a strip, the three models' schedules are immediately legible — and you can see three different design philosophies:띠로 펼쳐 놓으면 세 모델의 스케줄이 바로 읽힌다 — 그리고 서로 다른 설계 철학 셋이 보인다.

Drawn directly from the compress_ratios array in each config.json. V4-Pro's strip is truncated at 44 of 61 layers; the pattern continues.각 config.json 의 compress_ratios 배열을 그대로 그렸다. V4-Pro 는 61개 중 44개까지만 그렸고 패턴은 이어진다.

Why alternate 4 and 128?왜 4와 128을 번갈아 쓰나 A ratio-128 layer stores 1/128th of the KV a normal layer would. It cannot resolve individual tokens far away, but it can see the whole million-token context for almost nothing. A ratio-4 layer keeps enough resolution to pick out specific content. Alternating them means every pair of layers gets one cheap global sweep and one detailed look, and the average KV cost stays near the cheap end. That is how 1M context fits in 5.4 KiB per token.비율 128 레이어는 보통 레이어의 1/128 만큼만 KV 를 저장한다. 멀리 있는 개별 토큰을 분해하지는 못하지만, 백만 토큰 컨텍스트 전체를 거의 공짜로 볼 수 있다. 비율 4 레이어는 특정 내용을 집어낼 만큼의 해상도를 유지한다. 둘을 번갈아 쓰면 레이어 두 개마다 값싼 전역 훑기 한 번과 정밀한 보기 한 번이 생기고, KV 비용의 평균은 싼 쪽에 머문다. 1M 컨텍스트가 토큰당 5.4 KiB 에 들어가는 이유다.

Two supporting fields complete the picture. sliding_window: 128 gives every layer a cheap local window regardless of its ratio — the figure's note "CSA2 includes SWA" is exactly this. And compress_rope_theta (160,000 in V4.1, versus 10,000 for the normal path) gives the compressed stream its own RoPE base, because a position index means something different once 128 tokens share one slot.보조 필드 둘이 그림을 완성한다. sliding_window: 128 은 비율과 무관하게 모든 레이어에 값싼 지역 윈도를 준다 — 그림의 "CSA2 includes SWA" 주석이 바로 이것이다. 그리고 compress_rope_theta(V4.1 에서 160,000, 일반 경로는 10,000)는 압축 스트림에 자체 RoPE base 를 준다. 토큰 128개가 슬롯 하나를 공유하면 위치 인덱스의 의미가 달라지기 때문이다.

3mHC — replacing the residual connectionmHC — residual connection 을 대체하다

Since 2015 essentially every deep network has used x + F(x): one stream of activations, each layer adding its contribution. V4 replaces that with four parallel streams and a learned mixing step before and after every sublayer.2015년 이래 사실상 모든 심층 신경망이 x + F(x) 를 써 왔다 — 활성값 스트림 하나에 각 레이어가 자기 기여분을 더하는 방식. V4 는 그것을 네 개의 병렬 스트림과, 모든 서브레이어 앞뒤의 학습된 믹싱 단계로 대체한다.

Redrawn from the mHC insets of the DeepSeek V4-Flash, V4-Pro and V4.1-Flash cards in Raschka's gallery, annotated with hc_* fields from the configs.Raschka 갤러리의 DeepSeek V4-Flash · V4-Pro · V4.1-Flash 카드에 있는 mHC 삽화를 다시 그리고, config 의 hc_* 필드로 주석을 달았다.

All three models set hc_mult: 4 and hc_sinkhorn_iters: 20. The Sinkhorn part is the interesting half. A free 4×4 mixing matrix could learn to funnel everything into one stream, collapsing the whole thing back to a plain residual, or to blow one stream up and destabilise training. Sinkhorn normalisation alternately rescales rows and columns until the matrix is close to doubly stochastic — every row and column summing to one. The streams are then forced to redistribute signal rather than create or destroy it. That bounded-mixing property is what "manifold-constrained" names.세 모델 모두 hc_mult: 4, hc_sinkhorn_iters: 20 이다. 흥미로운 쪽은 Sinkhorn 이다. 제약 없는 4×4 믹싱 행렬은 모든 것을 한 스트림으로 몰아 전체를 평범한 residual 로 되돌리거나, 한 스트림을 폭주시켜 학습을 불안정하게 만들 수 있다. Sinkhorn 정규화는 행과 열을 번갈아 재조정해 행렬을 이중확률행렬에 가깝게 — 모든 행과 열의 합이 1이 되도록 — 만든다. 그러면 스트림들은 신호를 만들거나 없애는 게 아니라 재분배하도록 강제된다. 그 제한된 믹싱 성질이 "manifold-constrained" 가 가리키는 바다.

Where it shows up at serving time서빙 시점에 드러나는 곳 This is not an abstraction that disappears after training. In DeepSeek's own inference engine the hidden state is literally shaped [tokens, hc_mult, n_embed], there is an mHC head (4 to 1) that folds the streams back before the LM head, and the engine asserts hc_mult > 1. Four streams means four times the residual activation memory — a real cost, paid for whatever stability or capacity the mixing buys.학습 후 사라지는 추상이 아니다. DeepSeek 자체 추론 엔진에서 hidden state 는 문자 그대로 [tokens, hc_mult, n_embed] 모양이고, LM head 앞에서 스트림을 되접는 mHC head (4 to 1) 가 있으며, 엔진이 hc_mult > 1 을 단언한다. 스트림 4개는 residual 활성 메모리 4배를 뜻한다 — 믹싱이 사 오는 안정성이나 용량에 대해 실제로 치르는 비용이다.

4V4-Flash and V4-Pro: one block, repeatedV4-Flash · V4-Pro: 블록 하나의 반복

Structurally these two are the same model at two sizes. One block, repeated 43 or 61 times, with mHC wrapping each of its two sublayers.구조적으로 이 둘은 같은 모델의 두 크기다. 블록 하나를 43번 또는 61번 반복하고, mHC 가 그 안의 두 서브레이어를 각각 감싼다.

Redrawn from the DeepSeek V4-Flash and V4-Pro cards in Raschka's gallery; per-model numbers from each config.json.Raschka 갤러리의 DeepSeek V4-Flash · V4-Pro 카드를 다시 그렸다. 모델별 수치는 각 config.json 출처.

Hash routing in the first 3 blocks앞 3블록의 해시 라우팅

Early layers hold generic, low-level features, so a learned router has little signal to route on and tends to collapse onto a few experts. Hashing the token id to a fixed expert sidesteps the problem entirely: no router to train, perfectly balanced by construction.앞쪽 레이어는 일반적이고 저수준인 특징을 담고 있어 학습 라우터가 근거로 삼을 신호가 적고 소수 전문가로 붕괴하기 쉽다. 토큰 id 를 고정 전문가로 해싱하면 문제를 통째로 비켜 간다 — 학습할 라우터가 없고, 구성상 완벽히 균형 잡힌다.

What num_key_value_heads: 1 meansnum_key_value_heads: 1 의 뜻

64 or 128 query heads share a single KV head. That is the MLA lineage from V2/V3 taken to its limit — the KV cache stores one latent per token per layer, and the per-head keys and values are projected back out on the fly.query head 64개 또는 128개가 KV head 하나를 공유한다. V2/V3 에서 온 MLA 계보를 극단까지 민 것이다 — KV 캐시는 레이어·토큰당 latent 하나만 저장하고, head 별 key/value 는 그때그때 되펼친다.

5V4.1-Flash: the turn to a causal encoder-decoderV4.1-Flash: causal encoder-decoder 로의 전환

This is the structural break. V4.1 splits the 40 layers into a 20-layer causal encoder and a 20-layer decoder, and the decoder does not build its own long-range KV — it reads the encoder's.여기서 구조가 꺾인다. V4.1 은 40개 레이어를 20층 causal encoder 와 20층 decoder 로 쪼개고, decoder 는 자기 장거리 KV 를 만들지 않는다 — encoder 의 것을 읽는다.

Redrawn from the DeepSeek V4.1-Flash card in Raschka's gallery, with the layer-id lists taken from config.json. Vision encoder and DSpark omitted, as in the original figure.Raschka 갤러리의 DeepSeek V4.1-Flash 카드를 다시 그리고, 레이어 id 목록은 config.json 에서 가져왔다. 원 그림과 마찬가지로 vision encoder 와 DSpark 는 생략했다.

Why this saves so much왜 이렇게 많이 아끼나

Three effects stack. First, only four layers build global KV at all (kv_source_layer_ids: [2, 8, 14, 20]) and the other 36 share it. Second, only eight layers compute sparse indices; the Reindex layers reuse the KV and recompute just the index, and the Reuse layers take both. Third, the decoder's global KV comes from the encoder, so a million-token prompt is encoded once and every decode step reads that same frozen cache.세 효과가 쌓인다. 첫째, 전역 KV 를 만드는 레이어가 넷뿐이고(kv_source_layer_ids: [2, 8, 14, 20]) 나머지 36개는 공유한다. 둘째, 희소 인덱스를 계산하는 레이어는 여덟뿐이다 — Reindex 레이어는 KV 를 재사용하고 인덱스만 다시 계산하며, Reuse 레이어는 둘 다 가져다 쓴다. 셋째, decoder 의 전역 KV 가 encoder 에서 오므로 백만 토큰 프롬프트는 한 번만 인코딩되고 모든 decode 스텝이 그 고정된 캐시를 읽는다.

Why "causal" encoder왜 "causal" encoder 인가 A classic encoder-decoder (T5, BART) uses a bidirectional encoder, which makes it useless for streaming generation. V4.1's encoder stays causal — each position sees only its past — so the model is still an autoregressive LM and prompts can be extended incrementally. It takes the encoder-decoder's KV-sharing benefit without giving up the decoder-only property.고전적 encoder-decoder(T5, BART)는 양방향 encoder 를 써서 스트리밍 생성에 쓸 수 없다. V4.1 의 encoder 는 causal 을 유지한다 — 각 위치가 자기 과거만 본다 — 따라서 모델은 여전히 autoregressive LM 이고 프롬프트를 점진적으로 늘릴 수 있다. decoder-only 의 성질을 포기하지 않고 encoder-decoder 의 KV 공유 이득만 가져온 것이다.

One oddity worth noting: rms_norm_eps drops from 1e-6 in V4 to 1e-20 in V4.1 — effectively disabling the epsilon floor. With four mHC streams and FP8 weights in 32×32 blocks (V4 used 128×128), the normalisation statistics are evidently clean enough that the guard term was doing more harm than good. I have not seen this explained anywhere; it is an inference from the config.짚어 둘 특이점 하나 — rms_norm_eps 가 V4 의 1e-6 에서 V4.1 의 1e-20 으로 떨어진다. 사실상 epsilon 하한을 끈 셈이다. mHC 스트림 4개와 32×32 블록 FP8 가중치(V4 는 128×128)라면 정규화 통계가 충분히 깨끗해서 보호 항이 득보다 실이었던 모양이다. 어디서도 설명을 보지 못했고, config 에서 끌어낸 추론이다.

6Engram — 196B of hashed memory, derived from first principlesEngram — 196B 해시 메모리를 수치로 복원하기

Engram is the largest single thing in V4.1 and the hardest to see: 196B parameters, more than a third of the model's total, living in exactly two of its forty layers. It is not attention and not an FFN. It is a lookup table.Engram 은 V4.1 에서 가장 큰 단일 구성요소이면서 가장 눈에 안 띄는 것이다 — 196B 파라미터, 모델 총량의 3분의 1 이상이 마흔 개 레이어 중 정확히 두 개에 들어 있다. attention 도 FFN 도 아니다. 룩업 테이블이다.

The config gives eight fields, and together they fully determine the structure:config 가 필드 여덟 개를 주는데, 그것만으로 구조가 완전히 결정된다.

engram_layer_ids:             [1, 14]
engram_num_embeddings:        [384006168, 384016682]
engram_max_ngram_size:        4
engram_n_heads:               8
engram_head_dim:              256
engram_vocab_size:            16000000
engram_compressed_vocab_size: 99092      # from a 129,280 vocab
engram_pad_token_id:          2

Deriving the table layout테이블 레이아웃 복원하기

Start with the parameter count. (384006168 + 384016682) × 256 = 196.6B — which is exactly the "196B Engram" the gallery reports. So engram_num_embeddings counts rows, and every row is a 256-dim vector.파라미터 수에서 출발하자. (384006168 + 384016682) × 256 = 196.6B — 갤러리가 보고하는 "196B Engram" 과 정확히 같다. 즉 engram_num_embeddings 는 행 수이고, 모든 행은 256차원 벡터다.

Now the odd numbers. With max_ngram_size: 4 there are three n-gram orders (2, 3, 4-gram) and 8 heads, so 24 tables per layer. And 384,006,168 / 24 ≈ 16,000,257 — suspiciously just above engram_vocab_size: 16,000,000. The reason turns out to be exact:이제 저 어중간한 숫자들. max_ngram_size: 4 이므로 n-gram 차수가 셋(2·3·4-gram)이고 헤드가 8개이니 레이어당 테이블 24개다. 그리고 384,006,168 / 24 ≈ 16,000,257 — engram_vocab_size: 16,000,000 바로 위라는 게 수상하다. 이유는 정확히 떨어진다.

Computed from the config values; the inference-side generator is in engram_metadata.py of DeepSeek's engine.config 값에서 계산했다. 추론 쪽 생성 코드는 DeepSeek 엔진의 engram_metadata.py 에 있다.

Why prime-sized tables왜 소수 크기 테이블인가 Each head hashes the same n-gram into its own table. If two tables had sizes sharing a factor, keys colliding in one would tend to collide in the other, and the heads would carry redundant damage. With coprime sizes the collision patterns are structurally independent, so a key the first head confuses is very likely distinguishable by the second. Taking consecutive distinct primes guarantees coprimality for free. This is the hashing trick / hash-embedding construction, applied at a scale of 768 million rows.각 헤드가 같은 n-gram 을 자기 테이블로 해싱한다. 두 테이블 크기가 약수를 공유하면 한쪽에서 충돌한 키가 다른 쪽에서도 충돌하기 쉬워 헤드들이 똑같은 손상을 중복해 떠안는다. 서로소 크기라면 충돌 패턴이 구조적으로 독립이라, 첫 헤드가 헷갈린 키를 둘째 헤드가 구분할 가능성이 매우 높다. 서로 다른 연속 소수를 쓰면 서로소성이 공짜로 보장된다. 해싱 트릭 / 해시 임베딩 구성을 7억 6800만 행 규모로 적용한 것이다.

What the key actually is키의 실체

Not the raw token ids. The 129,280-entry vocabulary is first compressed to 99,092 by decoding each token to text and normalising it — NFKC, NFD, strip accents, lowercase, collapse whitespace runs. "The", "THE" and "thé" land on the same compressed id. Byte pieces that decode to invalid UTF-8 keep their raw spelling so distinct byte tokens cannot be merged. The n-gram of compressed ids is then hashed into each of the 24 tables.원래 토큰 id 가 아니다. 129,280개 어휘를 먼저 99,092 개로 압축한다 — 각 토큰을 텍스트로 디코드한 뒤 NFKC, NFD, 악센트 제거, 소문자화, 연속 공백 축약을 거친다. "The"·"THE"·"thé" 가 같은 압축 id 에 떨어진다. 깨진 UTF-8 로 디코드되는 바이트 조각은 원 철자를 유지해 서로 다른 바이트 토큰이 병합되지 않게 한다. 그렇게 만든 압축 id 의 n-gram 을 24개 테이블 각각으로 해싱한다.

So Engram keys on a normalised lexical pattern, not an exact string. 16 million slots per table for a key space of 99,092³ possible 3-grams means collisions are the normal case, not an edge case — which is precisely why there are eight heads.즉 Engram 은 정확한 문자열이 아니라 정규화된 어휘 패턴을 키로 삼는다. 99,092³ 가지 3-gram 키 공간에 테이블당 1600만 슬롯이면 충돌은 예외가 아니라 정상 상태다 — 헤드가 여덟 개인 이유가 바로 그것이다.

Editor's note — not a claim by DeepSeek편집자 주 — DeepSeek 의 주장 아님 What makes Engram worth your attention is the direction of causality. Everything else in V4 is an engineering decision inside a familiar shape. Engram is a modelling decision that forced infrastructure to change: DeepSeek's serving engine had to grow a parallel axis just for this table, one that can span more GPUs than the model itself, and reuse the MoE all-to-all fabric to gather rows by hash. A 196B lookup table is a bet that a lot of what a language model "knows" is lexical recall that does not need to be recomputed through 40 layers of attention. Whether that bet pays is not answerable from a config file — there is no public ablation, and the quality contribution of Engram is unmeasured here.Engram 이 주목할 가치가 있는 건 인과의 방향 때문이다. V4 의 나머지는 익숙한 형태 안의 엔지니어링 결정이다. Engram 은 인프라를 바꾸도록 강제한 모델링 결정이다 — DeepSeek 의 서빙 엔진은 이 테이블만을 위한 병렬 축을, 그것도 모델보다 더 많은 GPU 에 걸칠 수 있는 축을 새로 키워야 했고, 행을 해시로 모으려고 MoE all-to-all 패브릭을 재활용해야 했다. 196B 룩업 테이블은 "언어 모델이 아는 것의 상당 부분은 attention 40층을 거쳐 다시 계산할 필요가 없는 어휘적 회상" 이라는 베팅이다. 그 베팅이 맞는지는 config 파일로 답할 수 없다 — 공개된 ablation 이 없고, Engram 의 품질 기여는 여기서 측정되지 않았다.

The serving side of Engram — how the rows are sharded, prefetched over DeepEP and gated into the mHC trunk — is covered in the DeepInfer Engram note. That note was written before these config numbers were available and left the table sizes open; this section closes that gap.Engram 의 서빙 쪽 — 행을 어떻게 샤딩하고 DeepEP 로 prefetch 해 mHC trunk 에 게이팅하는지 — 는 DeepInfer Engram 노트에서 다룬다. 그 노트는 이 config 수치를 확보하기 전에 썼고 테이블 크기를 미결로 남겼다. 이 절이 그 빈칸을 메운다.

7DSpark, MoE routing, and the quantisation detailsDSpark · MoE 라우팅 · 양자화 디테일

DSpark

V4 and V4-Pro carry num_nextn_predict_layers: 1 — the single MTP head DeepSeek has shipped since V3. V4.1 raises it to 3 and gives the draft path its own machinery:V4 와 V4-Pro 는 num_nextn_predict_layers: 1 — V3 이래 DeepSeek 이 실어 온 단일 MTP 헤드다. V4.1 은 이를 3 으로 올리고 draft 경로에 자체 장치를 준다.

num_nextn_predict_layers: 3        dspark_target_layer_ids:  [37, 38, 39]
dspark_block_size:        5        dspark_markov_rank:       256
dspark_n_routed_experts:  128      dspark_num_experts_per_tok: 3
dspark_noise_token_id:    128799

Three points stand out. The draft layers have their own MoE — 128 experts, 3 active — separate from the backbone's 384/6, so drafting is genuinely cheaper rather than just shallower. dspark_block_size: 5 means tokens are drafted five at a time, which matches the default draft length in DeepSeek's serving engine. And dspark_markov_rank: 256 implies a low-rank Markov structure over the draft block rather than independent per-position heads — the draft positions are modelled as a chain, not guessed separately.세 가지가 눈에 띈다. draft 레이어가 자체 MoE 를 갖는다 — 전문가 128개 중 3개 활성 — backbone 의 384/6 과 별개라서, drafting 이 단지 얕기만 한 게 아니라 실제로 싸다. dspark_block_size: 5 는 토큰을 다섯 개씩 draft 한다는 뜻이고, DeepSeek 서빙 엔진의 기본 draft 길이와 일치한다. 그리고 dspark_markov_rank: 256 은 위치별 독립 헤드가 아니라 draft 블록에 대한 저차 Markov 구조를 시사한다 — draft 위치들을 따로 찍는 게 아니라 사슬로 모델링한다.

Precision정밀도

All three ship quantised by default, and the scheme is layered:세 모델 모두 기본적으로 양자화되어 배포되고, 방식이 계층적이다.

quant_method:      fp8        # weights
fmt:               e4m3
scale_fmt:         ue8m0      # exponent-only scale factors
weight_block_size: [128,128]  # V4      →  [32,32] in V4.1
expert_dtype:      fp4        # the MoE experts go further down
activation_scheme: dynamic

Weights are FP8 E4M3 with block-wise scales in ue8m0 — an exponent-only format, so a scale is a power of two and rescaling is an exponent add. The experts specifically are FP4, which is where the parameter count lives, and V4.1 shrinks the scale block from 128×128 to 32×32, buying finer-grained scaling at the cost of more scale metadata. swiglu_limit: 10.0 clamps the SwiGLU activation, a guard that matters more as precision drops.가중치는 FP8 E4M3 이고 블록 단위 스케일은 ue8m0 — 지수 전용 포맷이라 스케일이 2의 거듭제곱이고 재스케일이 지수 덧셈이 된다. 파라미터가 몰려 있는 전문가는 FP4 이며, V4.1 은 스케일 블록을 128×128 에서 32×32 로 줄여 스케일 메타데이터를 더 쓰는 대신 더 세밀한 스케일링을 산다. swiglu_limit: 10.0 은 SwiGLU 활성을 clamp 하는데, 정밀도가 낮아질수록 중요해지는 안전장치다.

Context extension컨텍스트 확장

The 1M window is not trained from scratch. All three use identical YaRN settings: original_max_position_embeddings: 65536 scaled by factor: 16 — 64K trained, 1M served. The compressed attention path gets its own base (compress_rope_theta: 160000 vs rope_theta: 10000), as noted in §2.1M 윈도는 처음부터 학습한 게 아니다. 세 모델 모두 동일한 YaRN 설정을 쓴다 — original_max_position_embeddings: 65536 에 factor: 16 을 곱해 64K 학습, 1M 서빙. 압축 attention 경로는 §2 에서 짚은 대로 자체 base 를 받는다(compress_rope_theta: 160000 대 rope_theta: 10000).

8Lineage and competitors계보와 경쟁 모델

What came from where무엇이 어디서 왔나

Component provenance, assembled from the DeepSeek V2/V3/V3.2/V4 entries in Raschka's gallery.Raschka 갤러리의 DeepSeek V2/V3/V3.2/V4 항목을 조합한 구성요소 계보.

The through-line is clear: DeepSeek has spent three generations attacking KV cache size. V2 introduced MLA to compress KV into a latent. V3 kept it and added MTP and FP8. V3.2 added sparse attention. V4 turns sparsity into a per-layer compression schedule, and V4.1 removes the decoder's KV entirely by borrowing the encoder's. Each step buys context length at roughly constant memory.관통하는 선이 분명하다 — DeepSeek 은 세 세대에 걸쳐 KV 캐시 크기를 공격해 왔다. V2 가 KV 를 latent 로 압축하는 MLA 를 도입했고, V3 이 그것을 유지하며 MTP 와 FP8 을 더했고, V3.2 가 희소 attention 을 붙였다. V4 는 희소성을 레이어별 압축 스케줄로 바꾸고, V4.1 은 decoder 의 KV 를 encoder 에서 빌려 아예 없앤다. 매 단계가 거의 일정한 메모리로 컨텍스트 길이를 사 온다.
