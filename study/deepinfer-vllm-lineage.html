Glossary용어 정리

Hard fork하드 포크

Code taken from a project once and then developed independently, with no intent to merge back or track upstream. The opposite of a live fork that rebases on new releases.프로젝트에서 코드를 한 번 떼어 온 뒤 독립적으로 발전시키는 것. 다시 합치거나 upstream 을 따라갈 의도가 없다. 새 릴리스에 리베이스하는 라이브 포크의 반대.

Control vs execution plane제어면 vs 실행면

Control decides what runs — batching, scheduling, request lifecycle. Execution does the arithmetic — kernels, model layers, memory movement.제어면은 무엇을 돌릴지 정한다 — 배칭·스케줄링·요청 수명. 실행면은 산수를 한다 — 커널·모델 레이어·메모리 이동.

TileLang

A tile-level DSL for GPU kernels: you write dataflow in Python, the compiler handles thread binding, layout and pipelining, and emits CUDA, HIP or other backends.GPU 커널용 타일 단위 DSL. 파이썬으로 데이터플로를 쓰면 컴파일러가 스레드 바인딩·레이아웃·파이프라이닝을 처리해 CUDA·HIP 등으로 내보낸다.

vLLM v0 vs v1vLLM v0 vs v1

vLLM's original architecture (llm_engine + worker/model_runner + cache_engine) versus the later v1 rewrite. DeepInfer's skeleton is recognisably v0.vLLM 초기 아키텍처(llm_engine + worker/model_runner + cache_engine)와 이후 v1 재작성. DeepInfer 의 골격은 분명히 v0 다.

SM100 / Ascend 950

NVIDIA's Blackwell-class compute capability, and Huawei's NPU generation. Two entirely different ISAs that DeepInfer must serve from one source tree.NVIDIA 의 Blackwell 급 compute capability, 그리고 Huawei 의 NPU 세대. DeepInfer 가 하나의 소스 트리로 감당해야 하는 완전히 다른 두 ISA.

Memory-bound kernel메모리 바운드 커널

A kernel whose runtime is set by data movement, not arithmetic — gathers, index math, normalisation. Vendor BLAS libraries do not cover these.실행 시간이 연산이 아니라 데이터 이동으로 결정되는 커널 — gather, 인덱스 연산, 정규화. 벤더 BLAS 라이브러리가 다루지 않는 영역.

4Zero CUDA, and a C++ schedulerCUDA 0줄, 그리고 C++ 스케줄러

The single most surprising fact in the repo: there is not one .cu or .cuh file outside the vendor submodules. A company whose kernel engineers are the reason anyone knows the name DeepSeek ships zero hand-written CUDA in its inference engine.이 레포에서 가장 놀라운 사실 하나 — vendor 서브모듈 밖에 .cu 나 .cuh 파일이 하나도 없다. DeepSeek 이라는 이름이 알려진 이유가 커널 엔지니어인 회사가, 자사 추론 엔진에 손으로 쓴 CUDA 를 한 줄도 넣지 않았다.

There is C++ — 33 files, 5,908 LOC in csrc/ — but look at what it does:C++ 는 있다 — csrc/ 에 33개 파일 5,908 LOC. 그런데 무엇을 하는지 보라.

csrc/engine/

  block_manager.hpp                  ← KV block allocation

Not a kernel in sight. This is the CPU-side hot path: the per-step work that happens between forward passes and that, at high batch rates, becomes the thing standing between you and the GPU. The README's "asynchronous scheduling (zero-overhead batch scheduler)" is this code.커널은 보이지 않는다. 이건 CPU 쪽 핫패스다 — forward pass 사이에 일어나는 스텝별 작업이고, 배치율이 높아지면 당신과 GPU 사이를 가로막는 바로 그것이 된다. README 의 "asynchronous scheduling (zero-overhead batch scheduler)" 가 이 코드다.

The inversion뒤집힌 구도 Conventional engines write kernels in C++/CUDA and the scheduler in Python. DeepInfer does the opposite: kernels go up into a DSL, the scheduler comes down into C++. Each move targets the constraint that actually binds in that layer — portability for kernels, per-step latency for scheduling. Whether or not you agree with it, it is a coherent position, not an accident.보통의 엔진은 커널을 C++/CUDA 로, 스케줄러를 파이썬으로 쓴다. DeepInfer 는 반대다 — 커널은 DSL 로 올리고, 스케줄러는 C++ 로 내린다. 각 이동이 그 계층에서 실제로 걸리는 제약을 겨냥한다 — 커널엔 이식성, 스케줄링엔 스텝당 지연. 동의하든 아니든, 사고가 아니라 일관된 입장이다.

5Why TileLang — the Ascend answer왜 TileLang 인가 — Ascend 라는 답

If every kernel is TileLang, the obvious question is why. The directory layout answers it before you read a line of kernel code.모든 커널이 TileLang 이라면 당연한 질문은 "왜" 다. 커널 코드를 한 줄도 읽기 전에 디렉터리 구조가 답한다.

29 ops, each with a public entry point, two DSL backends, a torch reference and a test that diffs them — all four living in one module per op.연산 29개 각각이 공개 진입점 하나, DSL 백엔드 둘, torch 레퍼런스 하나, 그 둘을 대조하는 테스트 하나를 갖고, 넷이 연산당 한 모듈에 모여 있다.

The top-level files are the interface, not just tests최상위 파일은 테스트가 아니라 인터페이스다 It is tempting to read the 29 top-level *.py as a test suite, since every one imports pytest. They are more than that: each is the backend-neutral public entry point that production code calls. layers/sampler_utils.py does from ...tilelang_ops.fused_sample import fused_sample; layers/vocab_parallel_embedding.py imports gather the same way. Breaking down those 9,668 LOC by what each top-level function actually is:최상위 *.py 29개는 전부 pytest 를 import 하니 테스트 스위트로 읽기 쉽다. 그 이상이다 — 각각이 프로덕션 코드가 호출하는 백엔드 중립 공개 진입점이다. layers/sampler_utils.py 가 from ...tilelang_ops.fused_sample import fused_sample 를 하고, layers/vocab_parallel_embedding.py 도 같은 식으로 gather 를 가져온다. 그 9,668 LOC 를 최상위 함수의 실제 역할로 쪼개면 이렇다. 
production interface (public entry points)   4,244 LOC   44%
torch reference implementations (*_ref)      1,609 LOC   17%
differential tests (test_*)                  2,913 LOC   30%
imports, constants, module level               902 LOC    9%
So verification is 4,522 LOC against 12,386 LOC of kernels — roughly 0.37:1, not the 1:1 a naive file-level count suggests. Still a serious investment, and still driven by the same cause: with two backends you cannot assert correctness by inspection, you have to diff them against a reference.따라서 검증은 커널 12,386 LOC 대비 4,522 LOC, 약 0.37:1 이다. 파일 단위로 뭉뚱그려 세면 1:1 처럼 보이지만 그렇지 않다. 그래도 상당한 투자이고, 원인은 같다 — 백엔드가 둘이면 눈으로 정합성을 주장할 수 없고 레퍼런스와 대조해야 한다.

And the platform object that drives it:그리고 그것을 구동하는 플랫폼 객체.

So: DeepSeek must run the same model on NVIDIA SM100 and Huawei Ascend 950. Hand-writing that kernel set twice — once in CUDA C++, once in AscendC — produces two unrelated codebases that drift apart immediately. TileLang gives one language, one set of tiling concepts, one test harness, two targets. Under export controls that is not a performance decision; it is closer to a survival one.정리하면 — DeepSeek 은 같은 모델을 NVIDIA SM100 과 Huawei Ascend 950 에서 돌려야 한다. 그 커널 세트를 CUDA C++ 로 한 번, AscendC 로 또 한 번 손으로 쓰면 즉시 서로 멀어지는 무관한 코드베이스 두 벌이 된다. TileLang 은 언어 하나, 타일링 개념 하나, 테스트 하네스 하나로 타깃 둘을 준다. 수출 규제 아래에서 이건 성능 결정이 아니라 생존 결정에 가깝다.

Portability is not free이식성은 공짜가 아니다 asc/ is 49% longer than cuda/ (7,418 vs 4,968 LOC) and reaches for Ascend-specific primitives — simd, get_num_vec_cores. This is not write-once-run-anywhere. It is same language, same concepts, same tests — still hand-written per target. The win is shared tooling and shared reasoning, not shared source — and the verification bill that comes with it is quantified in the callout above.asc/ 는 cuda/ 보다 49% 길다(7,418 대 4,968 LOC). simd, get_num_vec_cores 같은 Ascend 전용 프리미티브도 직접 쓴다. "한 번 쓰면 어디서나" 가 아니다. 같은 언어·같은 개념·같은 테스트로, 타깃별로 여전히 손으로 쓴다 가 맞다. 얻는 건 소스 공유가 아니라 툴링과 사고의 공유다 — 그에 따르는 검증 비용은 위 콜아웃에 수치로 정리했다.

How complete is the Ascend side, really?Ascend 쪽은 실제로 얼마나 완성됐나

LOC counts flatter it. Three things in the tree say CUDA is the lead backend and Ascend is following:LOC 수치는 후하게 쳐 준 것이다. 트리의 세 가지가 CUDA 가 선도 백엔드이고 Ascend 가 뒤따르는 중임을 말한다.

1 · Pairing is partial1 · 짝이 다 맞지 않는다

The two backends are not mirror images. Several kernels exist only on the CUDA side — candidate_blocks, dflash, flash_mla_utils, outlier_detection among them.두 백엔드는 거울상이 아니다. CUDA 쪽에만 있는 커널이 여럿이다 — candidate_blocks, dflash, flash_mla_utils, outlier_detection 등.

2 · Observability is CUDA-only2 · 관측은 CUDA 전용

Every entry point in csrc/graph_timer/graph_timer_asc.cpp throws "NPU graph timer primitives are not implemented yet". You cannot do in-graph timing on Ascend today.csrc/graph_timer/graph_timer_asc.cpp 의 모든 진입점이 "NPU graph timer primitives are not implemented yet" 를 던진다. 오늘 Ascend 에서는 in-graph 타이밍이 불가능하다.

3 · A rewrite, not a retarget3 · 리타깃이 아니라 재작성

CUDA kernels use fragments, T.Pipelined and PDL sync; Ascend ones use T.Persistent vector-core loops with explicit UB staging and inter-core flag barriers. Same DSL, different program.CUDA 커널은 fragment, T.Pipelined, PDL 동기화를 쓰고, Ascend 쪽은 명시적 UB 스테이징과 코어 간 플래그 배리어를 동반한 T.Persistent 벡터코어 루프를 쓴다. 같은 DSL, 다른 프로그램.

Even the dependency files admit the asymmetry: requirements-nvidia.txt installs torch==2.13.0+cu132 and flash-attn-4, while requirements-ascend.txt installs torch==2.13.0+cpu and gets device support entirely from torch-npu==2.13.0rc1 — an rc build.의존성 파일조차 비대칭을 인정한다. requirements-nvidia.txt 는 torch==2.13.0+cu132 와 flash-attn-4 를 깔지만, requirements-ascend.txt 는 torch==2.13.0+cpu 를 깔고 디바이스 지원을 전부 torch-npu==2.13.0rc1 에서 받는다 — rc 빌드다.

The delegated math is only half-ported — and you can trace the consequence위임한 연산도 절반만 이식됐고, 그 결과가 추적된다

Look at which vendor submodules have an Ascend twin, and which do not:어떤 vendor 서브모듈이 Ascend 쌍을 갖고 어떤 것이 없는지 보라.

vendor/DeepGEMM        vendor/DeepGEMM-Ascend     ← paired

Now the shim package makes sense. deepinfer/npu_ops/ exists to patch exactly the two gaps, and its own comments say so:그러면 shim 패키지가 이해된다. deepinfer/npu_ops/ 는 정확히 그 두 구멍을 메우려고 존재하고, 주석이 그렇다고 말한다.

npu_ops/deep_select.py:20  # TODO(NPU): To be removed when `topk` for sampler is ready
npu_ops/vit_attn.py:8      # TODO(NPU): To be removed when `_flash_attn_fwd` for ViT is ready

A clean causal chain: no Ascend build of DeepSelect and FlashMLA → sampler topk and ViT attention have no native NPU path → a shim package hooks builtins.__import__ to redirect those two imports to lazy replacements → both are marked for deletion once the real thing lands.깔끔한 인과 사슬이다 — DeepSelect 와 FlashMLA 의 Ascend 빌드 없음 → 샘플러 topk 와 ViT attention 에 네이티브 NPU 경로 없음 → shim 패키지가 builtins.__import__ 를 후킹해 그 두 import 를 지연 대체물로 돌림 → 진짜가 들어오면 삭제 예정으로 표시.

The best single illustration of portability friction이식성 마찰을 가장 잘 보여주는 한 장면 On an NPU-only host, torch_npu's transfer_to_npu maps torch.cuda.* onto torch.npu.* — so torch.cuda.is_available() returns True on a machine with no NVIDIA GPU. TileLang gates its CUDA probe on exactly that call. Left alone, it would compile every kernel for CUDA on an Ascend box. The fix is one line, and the comment above it is the honest story of cross-vendor work:NPU 전용 호스트에서 torch_npu 의 transfer_to_npu 가 torch.cuda.* 를 torch.npu.* 로 매핑한다 — 그래서 torch.cuda.is_available() 이 NVIDIA GPU 가 없는 기계에서 True 를 반환한다. TileLang 의 CUDA 탐지가 정확히 그 호출에 걸려 있다. 그대로 두면 Ascend 장비에서 모든 커널을 CUDA 로 컴파일한다. 수정은 한 줄이고, 그 위의 주석이 이종 벤더 작업의 정직한 실상이다. 
os.environ.setdefault("TILELANG_DEFAULT_TARGET", "ascend")

None of this makes the portability argument wrong. It makes it current: TileLang is the mechanism that makes a second backend tractable at all, and DeepSeek is visibly mid-port rather than done.이것이 이식성 논거를 틀리게 만들지는 않는다. 현재진행형으로 만들 뿐이다 — TileLang 은 두 번째 백엔드를 애초에 감당 가능하게 만드는 장치이고, DeepSeek 은 완료가 아니라 이식 중인 것이 눈에 보인다.

6"Only useful for low latency?" — correcting the premise"low latency 에서만 의미 있다?" — 전제 교정

There is a common intuition that tile DSLs only pay off in latency-bound regimes, because vendor libraries dominate big dense GEMM. That intuition is half right, and DeepInfer shows exactly which half.타일 DSL 은 벤더 라이브러리가 지배하는 큰 dense GEMM 때문에 지연 바운드 영역에서만 값을 한다는 직관이 흔하다. 그 직관은 절반은 맞고, DeepInfer 가 어느 절반인지 정확히 보여 준다.

DeepInfer does not use TileLang for heavy dense math at all. There are zero GEMM or matmul kernels in tilelang_ops/. The work is split:DeepInfer 는 무거운 dense 연산에 TileLang 을 전혀 쓰지 않는다. tilelang_ops/ 안에 GEMM·matmul 커널이 0개다. 분업은 이렇다.

Memory-bound, irregular, fused glue — the category where no vendor library exists and where a Triton-class DSL genuinely wins.gather, 인덱스 연산, KV 캐시 이동, 샘플링, 정규화, 양자화. 메모리 바운드 · 불규칙 · fused glue — 벤더 라이브러리가 아예 없고 Triton 계열 DSL 이 진짜로 이기는 범주다.

The premise, restated correctly전제를 바르게 다시 쓰면 "TileLang is pointless for dense GEMM" — true here, and DeepSeek agrees: that work goes to DeepGEMM. But "therefore it only matters for latency" does not follow. These glue kernels are pure overhead between the GEMMs. They dominate decode, yes — and they also tax throughput, because every microsecond spent gathering indices is a microsecond the tensor cores are idle. The right framing is not latency-vs-throughput. It is commodity dense math vs the long tail: buy the former, own the latter."dense GEMM 에서 TileLang 은 의미 없다" — 여기선 맞고, DeepSeek 도 동의한다. 그 일은 DeepGEMM 이 가져간다. 하지만 "따라서 지연에서만 중요하다" 는 따라오지 않는다. 이 glue 커널들은 GEMM 사이의 순수 오버헤드다. decode 를 지배하는 건 맞지만, throughput 에도 세금을 매긴다 — 인덱스를 모으는 1마이크로초는 텐서 코어가 노는 1마이크로초다. 옳은 구도는 지연 대 처리량이 아니다. 상품화된 dense 연산 대 롱테일 이다 — 전자는 사오고, 후자는 소유한다.
Editor's note — not a claim by DeepSeek편집자 주 — DeepSeek 의 주장 아님 What I would take from this for our own work. The dual-backend structure is the part worth copying, independent of TileLang: one dispatcher, two backends, and a shared differential test harness. We have the same shape of problem on MI250 whenever a kernel must exist for both ROCm and something else, and the ~0.37:1 verification-to-kernel ratio measured above is the honest price tag for it — worth knowing before committing. Note the shape as much as the number: the reference implementation and the test live in the same module as the public entry point, so there is no separate test tree to drift out of sync. What I would not conclude is that TileLang beats hand-written CUDA on NVIDIA; nothing in this repo measures that, and DeepSeek's own choice to delegate GEMM suggests they did not believe it either. None of this is benchmarked — it is a code read of one commit.우리 작업에 가져올 것. TileLang 과 무관하게 베낄 가치가 있는 건 이중 백엔드 구조다 — 디스패처 하나, 백엔드 둘, 공용 차분 테스트 하네스. MI250 에서도 어떤 커널이 ROCm 과 다른 무언가 양쪽에 존재해야 할 때마다 같은 모양의 문제를 만나고, 위에서 측정한 약 0.37:1 검증 비율이 그 정직한 가격표다 — 착수 전에 알아 둘 값어치가 있다. 숫자만큼이나 형태도 볼 것 — 레퍼런스 구현과 테스트가 공개 진입점과 같은 모듈에 산다. 따로 떨어져 나가 어긋날 테스트 트리가 없다. 반대로 내리지 않을 결론은 "NVIDIA 에서 TileLang 이 손으로 쓴 CUDA 를 이긴다" 는 것이다. 이 레포엔 그걸 측정한 게 없고, GEMM 을 위임한 DeepSeek 자신의 선택도 그렇게 믿지 않았음을 시사한다. 전부 벤치마크가 아니라 커밋 하나에 대한 코드 읽기다.
