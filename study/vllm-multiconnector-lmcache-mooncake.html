One-line summary한 줄 요약 MultiConnector loads KV from the first child (in config order) that reports a hit and saves to all of them. So [NixlConnector, LMCacheMPConnector] gives RDMA prefill→decode transfer on the fast path and a Mooncake-backed shared cache on the miss path. The cost is one extra scheduler step whenever LMCache's async lookup has not resolved yet.MultiConnector 는 설정 순서상 가장 먼저 히트를 보고한 자식에서 KV 를 읽고 전부에 저장한다. 그래서 [NixlConnector, LMCacheMPConnector] 는 빠른 경로에 RDMA prefill→decode 전송을, 미스 경로에 Mooncake 공유 캐시를 준다. 대가는 LMCache 비동기 lookup 이 덜 끝났을 때마다 스케줄러 스텝이 하나 더 든다는 것이다.

Glossary용어 정리

PD / disaggregation

Prefill and decode on separate engines, so the prompt's KV must be shipped from prefiller to decoder.prefill 과 decode 를 별도 엔진에서 돌리는 구성. 프롬프트 KV 를 prefiller 에서 decoder 로 옮겨야 한다.

KV connector

vLLM's plug-in for moving KV in or out of an engine: a scheduler half that plans, a worker half that moves bytes.KV 를 엔진에 넣고 빼는 vLLM 플러그인. 계획하는 scheduler 쪽과 바이트를 옮기는 worker 쪽으로 나뉜다.

NIXL

NVIDIA's transfer layer over UCX/RDMA: register memory, exchange agent metadata, then one-sided READ/WRITE.UCX/RDMA 위의 NVIDIA 전송 계층. 메모리 등록, agent 메타데이터 교환 후 단방향 READ/WRITE 를 한다.

L1 / L2 (LMCache)

L1: LMCache's CPU staging tier in POSIX shared memory. L2: a remote store behind an adapter (MooncakeStore, NIXL, S3, filesystem).L1 은 POSIX 공유 메모리의 CPU 스테이징 계층, L2 는 어댑터 뒤의 원격 스토어(MooncakeStore, NIXL, S3, 파일시스템)다.

MP mode

LMCache as a standalone lmcache server process owning the KV store, with vLLM engines attached over ZMQ. The alternative is in-process mode.KV 저장소를 가진 독립 lmcache server 프로세스에 vLLM 엔진들이 ZMQ 로 붙는 구성. 반대는 in-process 모드다.

HMA

Hybrid memory allocator for models mixing attention types (full + sliding-window + Mamba). Connectors opt in via SupportsHMA.attention 종류가 섞인 모델(full + sliding-window + Mamba)용 vLLM KV 관리자. 커넥터는 SupportsHMA 로 참여한다.

1What we are building, and what changed since June무엇을 만드는가, 그리고 6월 이후 달라진 것

The goal is one vLLM engine doing two jobs usually discussed separately: disaggregated prefill/decode, where the KV prefilled on one instance is shipped to another for decoding, and KV offload, where finished KV goes into a shared tiered cache so a later request with the same prefix can skip prefill, even on a different engine. vLLM models both through the KV connector interface, and MultiConnector lets you have both at once.목표는 보통 따로 다루는 두 일을 한 vLLM 엔진이 함께 하는 것이다. disaggregated prefill/decode 는 한 인스턴스에서 prefill 한 KV 를 다른 인스턴스로 보내 decode 한다. KV 오프로드는 끝난 KV 를 공유 계층형 캐시에 넣어, 같은 prefix 의 나중 요청이 다른 엔진에서도 prefill 을 건너뛰게 한다. vLLM 은 둘 다 KV 커넥터 인터페이스로 다루고, MultiConnector 가 둘을 동시에 쓰게 해 준다.

2Architecture: three repos, two processes, four transports아키텍처: 레포 3개, 프로세스 2개, 전송 4개

The key idea: the control plane and data plane do not travel together. Each hop carries either small metadata or KV bytes, almost never both. Mixing them up is the usual source of "why is my ZMQ socket slow".이 스택에서는 컨트롤 플레인과 데이터 플레인이 따로 움직인다. 각 홉은 작은 메타데이터나 KV 바이트 중 하나만 나른다. 둘을 혼동하면 "ZMQ 소켓이 왜 느리지" 같은 오해가 생긴다.

3MultiConnector: first hit loads, everyone savesMultiConnector: 첫 히트가 읽고, 전부가 쓴다

The whole composition policy is in the class docstring:합성 정책은 클래스 docstring 에 다 적혀 있다.

"A wrapper for using multiple KVConnectors at the same time. The current logic is: Load KV from the first connector that advertises available tokens from get_num_new_matched_tokens(), based on the order in the config. Save to all connectors."

— multi_connector.py#L128-L136

So ordering is policy. With [NixlConnector, LMCacheMPConnector], a decode instance that can pull from its prefiller does so, and the Mooncake-backed cache is consulted only when NIXL reports nothing. Reversing the order prefers the shared cache over the peer, which is usually wrong: the peer transfer is one RDMA hop, the cache at least two.그래서 순서가 곧 정책이다. [NixlConnector, LMCacheMPConnector] 이면 prefiller 에서 바로 당겨올 수 있는 decode 인스턴스는 NIXL 을 쓰고, NIXL 이 아무것도 보고하지 않을 때만 Mooncake 캐시를 본다. 순서를 뒤집으면 peer 보다 공유 캐시를 먼저 보는데, peer 전송은 RDMA 한 홉이고 캐시는 최소 두 홉이라 보통 손해다.

The selection loop, and the trap in it선택 루프, 그리고 그 안의 함정

# multi_connector.py:387-406
def get_num_new_matched_tokens(self, request, num_computed_tokens):
    to_return = (0, False)
    for i, c in enumerate(self._connectors):
        toks, load_async = c.get_num_new_matched_tokens(request, num_computed_tokens)
        # If there is a connector still looking up the matches,
        # we return None to indicate that we are not done yet.
        if toks is None:
            return (None, False)          # <-- abandons to_return
        if to_return[0] == 0 and toks > 0:
            self._requests_to_connector[request.request_id] = i
            to_return = (toks, load_async)
    return to_return

Two things. First, the loop calls every child even after one has won; the winner is just the first with toks > 0. Second, any child returning None aborts the scan and discards what was already found.볼 점이 두 가지다. 첫째, 승자가 정해진 뒤에도 루프는 모든 자식을 호출한다. 승자는 toks > 0 인 첫 자식일 뿐이다. 둘째, 자식 하나라도 None 을 반환하면 스캔이 중단되고 이미 찾은 결과도 버려진다.

LMCacheMPConnector returns exactly that while its lookup RPC is in flight: it fires the lookup, polls once, and gives up for this step.LMCacheMPConnector 는 lookup RPC 가 진행 중이면 바로 이 값을 반환한다. lookup 을 보내고 한 번 폴링한 뒤 이번 스텝은 포기한다.

Latency tax on the fast path빠른 경로에 붙는 지연 세금 A pending LMCache lookup throws away an already-found NIXL hit for that step. NIXL reports tokens and to_return is set, then LMCache returns None and the function bails with (None, False); the scheduler re-queries next step. So every request whose lookup does not resolve immediately pays at least one extra step even when the prefiller already had the blocks ready. Connector order does not help, because the loop calls every child.진행 중인 LMCache lookup 이 이미 찾은 NIXL 히트를 그 스텝에서 버린다. NIXL 이 토큰을 보고해 to_return 이 채워져도 LMCache 가 None 을 내면 함수는 (None, False) 로 빠져나가고, 스케줄러는 다음 스텝에 다시 묻는다. 그래서 lookup 이 즉시 안 끝나는 요청은 prefiller 가 블록을 준비해 뒀어도 스텝을 최소 하나 더 쓴다. 루프가 모든 자식을 호출하므로 커넥터 순서로도 피할 수 없다.

The cost is bounded: a scheduler step, not a storage round trip. Whether it matters depends on your TTFT budget and how often lookups miss the fast return. It is the first thing I would instrument.다만 비용은 스토리지 왕복이 아니라 스케줄러 스텝 하나다. 문제가 되는지는 TTFT 예산과 lookup 이 빠른 반환을 놓치는 빈도에 달렸다. 가장 먼저 계측할 지점이다.

Finishing: counting async saves, and a clash guard종료: 비동기 저장 카운트, 그리고 충돌 가드

1 · The Mooncake extension is not built by defaultMooncake 확장은 기본 빌드가 아니다 A plain pip install lmcache has no Mooncake support, and the failure shows up late, as a RuntimeError at adapter construction telling you to rebuild. Opt in with BUILD_MOONCAKE=1 pip install -e . --verbose, plus MOONCAKE_INCLUDE_DIR / MOONCAKE_LIB_DIR if the headers are not on the system include path. BUILD_MOONCAKE=0 takes top priority and overrides MOONCAKE_INCLUDE_DIR.pip install lmcache 만으로는 Mooncake 지원이 없고, 실패는 늦게 드러난다. 어댑터 생성 시점에 다시 빌드하라는 RuntimeError 가 난다. BUILD_MOONCAKE=1 pip install -e . --verbose 로 직접 켜고, 헤더가 시스템 include 경로에 없으면 MOONCAKE_INCLUDE_DIR / MOONCAKE_LIB_DIR 도 지정한다. BUILD_MOONCAKE=0 이 최우선이라 MOONCAKE_INCLUDE_DIR 을 덮어쓴다.
2 · The offloading shortcut flags silently replace MultiConnector오프로딩 단축 플래그가 MultiConnector 를 조용히 대체한다 vLLM's convenience flags --kv-offloading-size N --kv-offloading-backend lmcache work by overwriting kv_transfer_config.kv_connector:vLLM 편의 플래그 --kv-offloading-size N --kv-offloading-backend lmcache 는 kv_transfer_config.kv_connector 를 덮어쓴다.

3 · RDMA wants L1 fully allocated up frontRDMA 는 L1 이 미리 다 할당돼 있길 원한다 With protocol: "rdma", LMCache's docs recommend --no-l1-use-lazy so L1 exists in full before Mooncake registers it. A missing descriptor or a zero pointer/size makes adapter creation raise ValueError instead of silently falling back to non-RDMA. Right behaviour, but a lazy-allocated L1 fails at startup.protocol: "rdma" 이면 LMCache 문서는 Mooncake 등록 전에 L1 버퍼가 다 잡혀 있도록 --no-l1-use-lazy 를 권한다. 디스크립터가 없거나 포인터/크기가 0 이면 어댑터 생성은 비-RDMA 경로로 조용히 내려가지 않고 ValueError 를 던진다. 옳은 동작이지만 lazy 할당 L1 은 시작 시점에 실패한다.
4 · Two NIXL agents if you are not careful조심하지 않으면 NIXL agent 가 둘 LMCache has its own NIXL transport (enable_nixl, nixl_role: sender|receiver, nixl_buffer_size), and vLLM's shipped PD example uses that with LMCacheConnectorV1, not NixlConnector (prefiller config). These are two independent routes to NIXL PD; enabling both puts two NIXL agents on the same NICs. Pick one for the PD leg: vLLM-native NixlConnector (this note's assumption) or LMCache-internal NIXL.LMCache 에는 자체 NIXL 전송(enable_nixl, nixl_role: sender|receiver, nixl_buffer_size)이 있고, vLLM 의 PD 예제는 NixlConnector 대신 LMCacheConnectorV1 과 이것을 쓴다(prefiller config). NIXL PD 를 얻는 서로 다른 두 방법이라, 둘 다 켜면 NIXL agent 두 개가 같은 NIC 을 두고 다툰다. PD 쪽은 vLLM 네이티브 NixlConnector(이 노트의 가정)와 LMCache 내부 NIXL 중 하나만 고른다.
5 · Hash-seed alignment across instances인스턴스 간 해시 시드 정렬 LMCache derives chunk keys from a hash, so prefiller and decoder must agree or the decoder never finds what was stored. vLLM's example pins PYTHONHASHSEED and also warns that a fixed seed is a DoS vector: in production use a secret random value, not the demo's 123. UCX_TLS, set to cuda_ipc,cuda_copy,tcp in the example, is the same kind of concern.LMCache 는 청크 키를 해시로 만들므로 prefiller 와 decoder 의 해시가 같아야 decoder 가 저장된 KV 를 찾는다. vLLM 예제는 PYTHONHASHSEED 를 고정하면서, 고정 시드가 DoS 벡터라고도 경고한다. 프로덕션에서는 데모 값 123 대신 비밀 난수를 쓴다. 예제가 cuda_ipc,cuda_copy,tcp 로 설정하는 UCX_TLS 도 같은 종류의 주의사항이다.

Editor's note: not a claim by vLLM, LMCache or Mooncake편집자 주: vLLM · LMCache · Mooncake 의 주장 아님
  1. If the goal is just "PD plus a shared KV pool", benchmark MultiConnector[NixlConnector, MooncakeStoreConnector] first: two vLLM-native connectors that both declare HMA in-tree, no extra process, no native build, one fewer tier to debug.
  2. The LMCache route earns its complexity when you want what it adds: an L1 CPU tier absorbing writes off the critical path, chunk-level reuse below full-prefix granularity, tunable eviction, and a cache truly shared across many engines. That is features, not overhead; just buy it on purpose.
  3. Nothing here is measured. This is a code read, and on our MI250 boxes NIXL/UCX and RDMA availability would decide it in practice.
  1. 목표가 "PD + 공유 KV 풀"뿐이라면 먼저 벤치마크할 구성은 MultiConnector[NixlConnector, MooncakeStoreConnector] 다. vLLM 네이티브 커넥터 둘이 모두 인트리에서 HMA 를 선언하고, 추가 프로세스와 네이티브 빌드가 없으며, 지연을 따질 계층이 하나 적다.
  2. LMCache 경로는 그 기능이 실제로 필요할 때 복잡도 값을 한다. 크리티컬 패스 밖에서 쓰기를 받는 L1 CPU 계층, 전체 prefix 보다 잘게 나눈 청크 재사용, 튜닝 가능한 축출 정책, 여러 엔진이 함께 쓰는 캐시가 그것이다. 오버헤드가 아니라 기능이니 알고 고르면 된다.
  3. 측정치는 없다. 이 노트는 코드 읽기이고, 우리 MI250 장비에서는 NIXL/UCX 와 RDMA 가용성이 실제 선택을 좌우할 것이다.
