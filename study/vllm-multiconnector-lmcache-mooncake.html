Glossary용어 정리

PD / disaggregation

Running prefill and decode on separate engines so each can be batched and scaled independently. Requires shipping the prompt's KV cache from the prefiller to the decoder.prefill 과 decode 를 별도 엔진에서 돌려 각각 독립적으로 배칭·스케일하는 구성. 프롬프트의 KV 캐시를 prefiller 에서 decoder 로 옮겨야 한다.

KV connector

vLLM's plug-in point for getting KV cache in or out of an engine. One class, two roles: a scheduler half that plans, and a worker half that moves bytes.KV 캐시를 엔진에 넣고 빼는 vLLM 의 플러그인 지점. 클래스 하나에 역할 둘 — 계획을 세우는 scheduler 쪽과 바이트를 옮기는 worker 쪽.

NIXL

NVIDIA's transfer abstraction over UCX/RDMA. You register memory, exchange agent metadata, then issue one-sided READ/WRITE against a peer's registered buffers.UCX/RDMA 위에 얹은 NVIDIA 의 전송 추상화. 메모리를 등록하고 agent 메타데이터를 교환한 뒤, 상대의 등록된 버퍼에 대해 단방향 READ/WRITE 를 발행한다.

L1 / L2 (LMCache)

L1 is LMCache's CPU staging tier in POSIX shared memory. L2 is a remote store behind a pluggable adapter — MooncakeStore, NIXL, S3, filesystem.L1 은 POSIX 공유 메모리에 있는 LMCache 의 CPU 스테이징 계층. L2 는 교체 가능한 어댑터 뒤의 원격 스토어 — MooncakeStore, NIXL, S3, 파일시스템 등.

MP mode

LMCache running as a standalone lmcache server process that owns the KV storage, with one or more vLLM engines attached over ZMQ. The alternative is in-process mode.LMCache 가 KV 저장소를 소유하는 독립 lmcache server 프로세스로 뜨고, vLLM 엔진 하나 이상이 ZMQ 로 붙는 구성. 반대는 in-process 모드.

HMA

Hybrid memory allocator — vLLM's KV manager for models mixing attention types (full + sliding-window + Mamba). Connectors must opt in via SupportsHMA.하이브리드 메모리 할당자 — attention 종류가 섞인 모델(full + sliding-window + Mamba)을 위한 vLLM 의 KV 관리자. 커넥터는 SupportsHMA 로 명시적으로 참여해야 한다.

1What we are building, and what changed since June무엇을 만드는가, 그리고 6월 이후 달라진 것

The target is a single vLLM engine doing two jobs that are usually discussed separately. First, disaggregated prefill/decode: the prompt is prefilled on one instance and the KV cache is shipped to another for decoding. Second, KV offload: finished KV is pushed into a tiered cache so a later request with the same prefix can skip prefill entirely — and, because the cache is shared, so can a request that lands on a different engine.목표는 보통 따로 다루는 두 가지 일을 한 vLLM 엔진이 동시에 하게 만드는 것이다. 첫째, disaggregated prefill/decode — 프롬프트를 한 인스턴스에서 prefill 하고 KV 캐시를 다른 인스턴스로 보내 decode 한다. 둘째, KV 오프로드 — 끝난 KV 를 계층형 캐시에 밀어 넣어, 같은 prefix 를 가진 나중 요청이 prefill 을 통째로 건너뛰게 한다. 캐시가 공유되므로 다른 엔진에 떨어진 요청도 마찬가지다.

These are different problems with different transports, and vLLM models both through the same interface — the KV connector. MultiConnector is the piece that lets you have both at once.둘은 전송 경로가 다른 별개 문제인데, vLLM 은 둘 다 같은 인터페이스 — KV 커넥터 — 로 모델링한다. MultiConnector 가 이 둘을 동시에 갖게 해 주는 조각이다.

2Architecture: three repos, two processes, four transports아키텍처: 레포 3개, 프로세스 2개, 전송 4개

The single most useful thing to internalise is that this stack has a control plane and a data plane that do not travel together. Every hop below either carries small metadata messages or carries KV bytes — almost never both. Getting them confused is the main source of "why is my ZMQ socket slow" confusion.이 스택에서 가장 먼저 체화할 것은 컨트롤 플레인과 데이터 플레인이 같이 움직이지 않는다는 점이다. 아래 각 홉은 작은 메타데이터 메시지를 나르거나 KV 바이트를 나르거나 — 둘 다인 경우는 거의 없다. 이 둘을 혼동하는 것이 "왜 내 ZMQ 소켓이 느리지" 류 오해의 주된 원인이다.

3MultiConnector: first hit loads, everyone savesMultiConnector: 첫 히트가 읽고, 전부가 쓴다

The whole composition policy is stated in the class docstring, and it is worth quoting verbatim because everything else follows from it:합성 정책 전체가 클래스 docstring 에 적혀 있다. 나머지 모든 동작이 여기서 파생되므로 그대로 인용할 만하다.

"A wrapper for using multiple KVConnectors at the same time. The current logic is: Load KV from the first connector that advertises available tokens from get_num_new_matched_tokens(), based on the order in the config. Save to all connectors."

— multi_connector.py#L128-L136

So ordering is a policy decision, not cosmetics. With [NixlConnector, LMCacheMPConnector], a decode instance that can pull straight from its prefiller will do so; only when NIXL reports nothing does the Mooncake-backed cache get consulted. Reverse the order and you would prefer the shared cache over the peer — usually wrong, since the peer transfer is a single RDMA hop and the cache is at least two.따라서 순서는 겉치레가 아니라 정책 결정이다. [NixlConnector, LMCacheMPConnector] 라면, prefiller 에서 바로 당겨올 수 있는 decode 인스턴스는 그렇게 한다. NIXL 이 아무것도 보고하지 않을 때만 Mooncake 기반 캐시를 참조한다. 순서를 뒤집으면 peer 보다 공유 캐시를 우선하게 되는데 — peer 전송은 RDMA 한 홉이고 캐시는 최소 두 홉이므로 보통 잘못된 선택이다.

The selection loop, and the trap in it선택 루프, 그리고 그 안의 함정

# multi_connector.py:387-406
def get_num_new_matched_tokens(self, request, num_computed_tokens):
    to_return = (0, False)
    for i, c in enumerate(self._connectors):
        toks, load_async = c.get_num_new_matched_tokens(request, num_computed_tokens)
        # If there is a connector still looking up the matches,
        # we return None to indicate that we are not done yet.
        if toks is None:
            return (None, False)          # <-- abandons to_return
        if to_return[0] == 0 and toks > 0:
            self._requests_to_connector[request.request_id] = i
            to_return = (toks, load_async)
    return to_return

Two things to notice. First, the loop calls every child even after one has won — the winner is just the first with toks > 0. Second, and more consequentially, any child returning None aborts the whole scan and discards whatever was already found.두 가지를 보자. 첫째, 하나가 이긴 뒤에도 루프는 모든 자식을 호출한다 — 승자는 단지 toks > 0 인 첫 번째일 뿐이다. 둘째, 그리고 더 중요하게, 어떤 자식이든 None 을 반환하면 스캔 전체가 중단되고 이미 찾은 것도 버려진다.

That matters because LMCacheMPConnector returns exactly that while its lookup RPC is in flight — it fires the lookup, polls once, and gives up for this step:이게 중요한 이유는 LMCacheMPConnector 가 lookup RPC 진행 중에 정확히 그것을 반환하기 때문이다 — lookup 을 발행하고 한 번 폴링한 뒤, 이번 스텝은 포기한다.

Latency tax on the fast path빠른 경로에 붙는 지연 세금 Combine the two and you get this: a pending LMCache lookup throws away an already-found NIXL hit for that scheduling step. NIXL runs first, reports tokens, to_return is set — then LMCache returns None and the function bails with (None, False). The scheduler re-queries next step. So every request whose lookup does not resolve immediately pays at least one extra scheduler step even when the prefiller already had the blocks ready. Connector order does not protect you: the loop calls every child regardless of who already won.둘을 합치면 이렇게 된다 — 진행 중인 LMCache lookup 이 이미 찾아 둔 NIXL 히트를 그 스케줄링 스텝에서 버린다. NIXL 이 먼저 돌아 토큰을 보고하고 to_return 이 설정되는데, 그 다음 LMCache 가 None 을 반환해 함수가 (None, False) 로 빠져나간다. 스케줄러는 다음 스텝에 다시 물어본다. 결국 lookup 이 즉시 안 끝나는 모든 요청은 prefiller 가 이미 블록을 준비해 뒀더라도 스케줄러 스텝을 최소 하나 더 쓴다. 커넥터 순서로는 막을 수 없다 — 루프는 누가 이겼든 모든 자식을 호출한다.

This is a real cost but a bounded one: a scheduler step, not a round trip to storage. Whether it matters depends on your TTFT budget and how often lookups miss the fast return. It is the first thing I would instrument.실제 비용이지만 한도는 있다 — 스토리지 왕복이 아니라 스케줄러 스텝 하나다. 문제가 되는지는 TTFT 예산과 lookup 이 얼마나 자주 빠른 반환을 놓치는지에 달렸다. 내가 가장 먼저 계측할 지점이다.

Allocation: the winner gets tokens, the rest get zero할당: 승자는 토큰을, 나머지는 0 을

After the scheduler allocates blocks, every child is told about them — but only the chosen one is told there is external KV to load. The others still need the block list so they can plan their saves.스케줄러가 블록을 할당한 뒤 모든 자식에게 통보되지만, 로드할 외부 KV 가 있다는 사실은 선택된 자식에게만 전달된다. 나머지도 저장을 계획하려면 블록 목록은 알아야 한다.

Finishing: counting async saves, and a clash guard종료: 비동기 저장 카운트, 그리고 충돌 가드

Because saves fan out to all children, a request can have several asynchronous saves outstanding. MultiConnector counts them and propagates the surplus to the worker so blocks are not freed early:저장이 모든 자식으로 팬아웃되므로 한 요청에 비동기 저장이 여러 개 남아 있을 수 있다. MultiConnector 는 그 수를 세어 잉여분을 워커로 전파해 블록이 일찍 해제되지 않게 한다.

NIXL 은 전송 핸들과 알림에서, LMCacheMP 는 store 요청 회계에서 이를 도출한다.
    nixl/base_worker.py#L2026-L2147 · adapter.py#L1576-L1708

Scheduler: fan the worker output back in.스케줄러: 워커 출력 역팬인. update_connector_output slices the aggregated MultiKVConnectorWorkerMetadata and gives each child only its own slice — then restores the wrapper in a finally.update_connector_output 이 집계된 MultiKVConnectorWorkerMetadata 를 잘라 각 자식에게 자기 몫만 준 뒤, finally 에서 래퍼를 복원한다.

Request finished: count the stragglers.요청 종료: 남은 것 세기. request_finished aggregates across children, records async_saves - 1 as surplus so blocks survive until every save lands, merges kv_transfer_params (raising on key clashes), and drops the request→connector mapping.request_finished 가 자식들을 집계해 async_saves - 1 을 잉여로 기록해 모든 저장이 끝날 때까지 블록을 살려 두고, kv_transfer_params 를 병합하며(키 충돌 시 예외), 요청→커넥터 매핑을 지운다.

The shape to remember기억할 형태 The scheduler decides whether and how much; the worker moves bytes. Every connector, however exotic its transport, is bolted onto the same six-call worker loop: bind_connector_metadata → start_load_kv → wait_for_layer_load×N → wait_for_save → get_finished → clear_connector_metadata. If you only remember one thing from this note, remember that loop.스케줄러는 할지, 얼마나 할지를 결정하고 워커는 바이트를 옮긴다. 전송 방식이 아무리 특이하든 모든 커넥터는 같은 6-호출 워커 루프에 볼트로 고정된다 — bind_connector_metadata → start_load_kv → wait_for_layer_load×N → wait_for_save → get_finished → clear_connector_metadata. 이 노트에서 하나만 기억한다면 이 루프를 기억할 것.

Five traps, in the order you will hit them부딪히게 되는 순서대로, 함정 5개

1 · The Mooncake extension is not built by defaultMooncake 확장은 기본 빌드가 아니다 A plain pip install lmcache gives you no Mooncake support, and the failure surfaces late — at adapter construction, as a RuntimeError telling you to rebuild. You must opt in: BUILD_MOONCAKE=1 pip install -e . --verbose, plus MOONCAKE_INCLUDE_DIR / MOONCAKE_LIB_DIR if the headers are not on the system include path. Note BUILD_MOONCAKE=0 is highest-priority and will override MOONCAKE_INCLUDE_DIR.평범한 pip install lmcache 로는 Mooncake 지원이 없고, 실패가 늦게 드러난다 — 어댑터 생성 시점에 다시 빌드하라는 RuntimeError 로. 명시적으로 켜야 한다: BUILD_MOONCAKE=1 pip install -e . --verbose, 헤더가 시스템 include 경로에 없으면 MOONCAKE_INCLUDE_DIR / MOONCAKE_LIB_DIR 도 함께. BUILD_MOONCAKE=0 은 최우선이라 MOONCAKE_INCLUDE_DIR 을 덮어쓴다는 점에 주의.
2 · The offloading shortcut flags silently replace MultiConnector오프로딩 단축 플래그가 MultiConnector 를 조용히 대체한다 vLLM offers --kv-offloading-size N --kv-offloading-backend lmcache as a convenience. It works by overwriting kv_transfer_config.kv_connector:vLLM 은 편의를 위해 --kv-offloading-size N --kv-offloading-backend lmcache 를 제공한다. 그런데 이건 kv_transfer_config.kv_connector 를 덮어쓰는 방식으로 동작한다. 
# vllm/config/vllm.py:1032-1038
elif kv_offloading_backend == "lmcache":
    self.kv_transfer_config.kv_connector = "LMCacheMPConnector"
Pass those flags alongside your MultiConnector JSON and you lose NIXL entirely, with no warning. Use the explicit --kv-transfer-config form only. vllm.py#L1013-L1042그 플래그를 MultiConnector JSON 과 같이 넘기면 경고 없이 NIXL 을 통째로 잃는다. 명시적 --kv-transfer-config 형태만 쓸 것. vllm.py#L1013-L1042
3 · RDMA wants L1 fully allocated up frontRDMA 는 L1 이 미리 다 할당돼 있길 원한다 With protocol: "rdma", LMCache's docs recommend --no-l1-use-lazy so the L1 buffer exists in full before Mooncake registers it. If the descriptor is missing or has a zero pointer/size, adapter creation raises ValueError rather than silently degrading to a non-RDMA path — which is the right behaviour, but means a lazy-allocated L1 fails at startup.protocol: "rdma" 에서는 Mooncake 가 등록하기 전에 L1 버퍼가 온전히 존재하도록 --no-l1-use-lazy 를 권한다. 디스크립터가 없거나 포인터/크기가 0 이면 어댑터 생성이 조용히 비-RDMA 경로로 떨어지지 않고 ValueError 를 던진다 — 올바른 동작이지만, lazy 할당된 L1 은 시작 시점에 실패한다는 뜻이다.
4 · Two NIXL agents if you are not careful조심하지 않으면 NIXL agent 가 둘 LMCache has its own internal NIXL transport (enable_nixl, nixl_role: sender|receiver, nixl_buffer_size) — and vLLM's shipped PD example uses that, with LMCacheConnectorV1, not NixlConnector (prefiller config). Those are two independent ways to get NIXL PD. Enabling both gives you two NIXL agents competing for the same NICs. Pick one: vLLM-native NixlConnector for the PD leg (what this note assumes), or LMCache-internal NIXL — not both.LMCache 에는 자체 내부 NIXL 전송이 있다(enable_nixl, nixl_role: sender|receiver, nixl_buffer_size). 그리고 vLLM 이 배포하는 PD 예제는 NixlConnector 가 아니라 LMCacheConnectorV1 과 함께 그것을 쓴다(prefiller config). NIXL PD 를 얻는 독립적인 두 방법이다. 둘 다 켜면 같은 NIC 을 두고 NIXL agent 두 개가 경합한다. 하나만 고를 것 — PD 쪽에 vLLM 네이티브 NixlConnector(이 노트의 가정) 또는 LMCache 내부 NIXL, 둘 다는 아니다.
5 · Hash-seed alignment across instances인스턴스 간 해시 시드 정렬 LMCache derives chunk keys from a hash, so prefiller and decoder must agree or the decoder will never find what the prefiller stored. vLLM's example pins PYTHONHASHSEED and says so explicitly — and also warns that a fixed seed is a DoS vector, so use a secret random value in production, not the demo's 123. Same class of concern as UCX_TLS, which the example sets to cuda_ipc,cuda_copy,tcp.LMCache 는 청크 키를 해시에서 유도하므로 prefiller 와 decoder 가 일치해야 한다. 안 그러면 decoder 는 prefiller 가 저장한 것을 영원히 못 찾는다. vLLM 예제는 PYTHONHASHSEED 를 고정하며 이를 명시하고, 동시에 고정 시드가 DoS 벡터임을 경고한다 — 프로덕션에선 데모의 123 이 아니라 비밀 난수를 쓸 것. 예제가 cuda_ipc,cuda_copy,tcp 로 설정하는 UCX_TLS 도 같은 부류의 주의사항이다.

8Design alternatives설계 대안

There are three ways to put Mooncake behind a vLLM engine, and they differ in how many moving parts you accept:vLLM 엔진 뒤에 Mooncake 를 두는 방법이 셋 있고, 움직이는 부품을 얼마나 받아들이느냐에서 갈린다.

Route경로 Extra process추가 프로세스 You gain얻는 것 You give up포기하는 것
LMCacheMPConnector + mooncake_store L2 yes — lmcache server있음 — lmcache server L1 CPU tier, chunk-level reuse, eviction policies, cache shared across engines, one place to grow more L2 backendsL1 CPU 계층, 청크 단위 재사용, 축출 정책, 엔진 간 캐시 공유, L2 백엔드를 늘릴 단일 지점 a process to operate and monitor; the async-lookup step (§3); a native build step운영·모니터링할 프로세스, 비동기 lookup 스텝(§3), 네이티브 빌드 단계
MooncakeStoreConnector (vLLM-native) no없음 one fewer hop and process; declares SupportsHMA in vLLM itself홉과 프로세스가 하나씩 적음. vLLM 자체에서 SupportsHMA 명시 LMCache's L1 staging tier and its cache-management layer entirelyLMCache 의 L1 스테이징 계층과 캐시 관리 계층 전체

KVOffloadingBackend = Literal["native", "lmcache"] at cache.py#L72 — so the shortcut flag cannot express the MooncakeStoreConnector route; that one needs explicit --kv-transfer-config too.cache.py#L72 의 KVOffloadingBackend = Literal["native", "lmcache"] — 따라서 단축 플래그로는 MooncakeStoreConnector 경로를 표현할 수 없다. 그쪽도 명시적 --kv-transfer-config 가 필요하다.

Editor's note — not a claim by vLLM, LMCache or Mooncake편집자 주 — vLLM · LMCache · Mooncake 의 주장 아님 If the goal is simply "PD plus a shared KV pool", MultiConnector[NixlConnector, MooncakeStoreConnector] is the configuration I would benchmark first: two vLLM-native connectors, both declaring HMA in-tree, no extra process, no native build step, and one fewer tier to reason about when latency goes wrong. The LMCache route earns its complexity when you actually want what LMCache adds — the L1 CPU tier absorbing writes off the critical path, chunk-level reuse below full-prefix granularity, eviction policy you can tune, and a cache genuinely shared across many engines. That is a real feature set, not overhead; it is just worth being deliberate that you are buying it. Nothing here is measured — this note is a code read, not a benchmark, and on our MI250 boxes NIXL/UCX and RDMA availability is the variable that would decide it in practice.목표가 그냥 "PD + 공유 KV 풀"이라면, 내가 먼저 벤치마크할 구성은 MultiConnector[NixlConnector, MooncakeStoreConnector] 다 — vLLM 네이티브 커넥터 둘, 둘 다 인트리에서 HMA 명시, 추가 프로세스 없음, 네이티브 빌드 단계 없음, 지연이 나빠질 때 따져야 할 계층이 하나 적다. LMCache 경로는 LMCache 가 더해 주는 것을 실제로 원할 때 그 복잡도를 정당화한다 — 쓰기를 크리티컬 패스 밖에서 흡수하는 L1 CPU 계층, 전체 prefix 보다 잔 단위의 청크 재사용, 튜닝 가능한 축출 정책, 여러 엔진이 진짜로 공유하는 캐시. 이건 오버헤드가 아니라 실제 기능 세트다. 다만 그걸 사고 있다는 걸 의식적으로 아는 게 좋다. 여기 측정치는 하나도 없다 — 이 노트는 코드 읽기지 벤치마크가 아니고, 우리 MI250 장비에서는 NIXL/UCX 와 RDMA 가용성이 실제로 결정을 좌우할 변수다.
