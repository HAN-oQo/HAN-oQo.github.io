In-House LLM Serving at Netflix — a plain-language walkthrough Netflix의 자체 LLM 서빙 — 쉬운 말로 풀어 읽기

Most companies just call an LLM through someone else's API. Netflix instead runs the whole thing itself — building a production platform on top of two open-source pieces (the vLLM inference engine and NVIDIA's Triton model server) and wiring it into the systems that already serve their recommendation models. This note walks through that platform for a reader who knows AI models but not systems jargon: every term (JVM, gRPC, the GIL, batching, KV cache…) is unpacked in plain language before it's used. The most interesting part is the ending — how they make a model produce valid JSON by construction, and the subtle bottleneck that only showed up under real traffic. 대부분의 회사는 남의 API로 LLM을 불러 쓴다. Netflix는 대신 전부 직접 굴린다 — 오픈소스 두 조각(추론 엔진 vLLM과 NVIDIA의 모델 서버 Triton) 위에 프로덕션 플랫폼을 짓고, 이미 추천 모델을 서빙하던 시스템에 연결한다. 이 노트는 그 플랫폼을 AI 모델은 알지만 시스템 용어는 모르는 독자를 위해 풀어 쓴다: 모든 용어(JVM, gRPC, GIL, 배칭, KV 캐시…)를 쓰기 전에 쉬운 말로 먼저 설명한다. 가장 흥미로운 대목은 끝부분 — 모델이 올바른 JSON을 애초에 틀릴 수 없게 만드는 방법과, 실제 트래픽에서만 드러난 미묘한 병목이다.

one-line summary한 줄 요약 Netflix built its own LLM serving platform — the machinery that takes a request, runs it through a model on a GPU, and returns the answer at production scale — on top of open-source vLLM + NVIDIA Triton, plugged into the same JVM system that already serves their non-LLM models so that "an LLM is not a special snowflake." The write-up is really a list of honest production lessons: pick an engine on operational fit not just speed; package models so they and the frontend can evolve independently; expose the OpenAI-compatible API so moving from a hosted model to a self-hosted one is a one-line change; and — the highlight — enforce output rules (valid JSON) inside the token-generation loop, which hit a sneaky CPU bottleneck (the Python GIL) that was invisible in single-request tests and only appeared under real concurrency. The blog gives no hard latency/throughput numbers; the wins are described qualitatively. Netflix는 자체 LLM 서빙 플랫폼 — 요청을 받아 GPU의 모델에 태우고 답을 돌려주는, 그걸 프로덕션 규모로 하는 기계장치 — 을 오픈소스 vLLM + NVIDIA Triton 위에 지었고, 이미 비-LLM 모델을 서빙하던 같은 JVM 시스템에 꽂아 "LLM은 특별한 눈송이가 아니다"를 실현했다. 글의 본질은 정직한 프로덕션 교훈 모음이다: 엔진은 속도만이 아니라 운영 적합성으로 고르라; 모델과 프런트엔드가 따로 진화하도록 패키징하라; OpenAI 호환 API를 노출해 호스팅 모델→자체 호스팅 전환을 한 줄 변경으로 만들라; 그리고 — 하이라이트 — 출력 규칙(올바른 JSON)을 토큰 생성 루프 안에서 강제하는데, 이게 단일 요청 테스트에선 안 보이고 실제 동시성에서만 나타나는 얄미운 CPU 병목(Python GIL)에 부딪혔다. 블로그는 구체적 지연/처리량 수치를 주지 않는다; 이득은 정성적으로 서술된다.

Glossary — every jargon word, in plain language (read this first)용어집 — 모든 전문용어를 쉬운 말로 (먼저 읽기)

inference / serving추론 / 서빙

Inference = running a trained model to get an answer (as opposed to training it). Serving = the whole production plumbing around that: accept a request, run inference, return the result — reliably, for many users at once.추론 = 학습된 모델을 돌려 답을 얻는 것(학습의 반대). 서빙 = 그 주변의 프로덕션 배관 전부: 요청 받고, 추론 돌리고, 결과 반환 — 많은 사용자에게 동시에, 안정적으로.

inference engine (vLLM / TensorRT-LLM)추론 엔진 (vLLM / TensorRT-LLM)

The piece that actually runs the model math on the GPU fast. vLLM is a popular open-source one; TensorRT-LLM is NVIDIA's. Think "the engine of a car" — you build the rest of the car around it.GPU에서 모델 연산을 실제로 빠르게 돌리는 조각. vLLM은 인기 오픈소스, TensorRT-LLM은 NVIDIA 것. "자동차 엔진"이라 생각하면 됨 — 나머지 차는 그 주위에 짓는다.

Triton (model server)Triton (모델 서버)

NVIDIA's model server: it loads models, groups requests, and schedules them on the GPU — for any model type (XGBoost, TensorFlow, LLMs), not just LLMs. The engine (vLLM) plugs in underneath it.NVIDIA의 모델 서버: 모델을 로드하고, 요청을 묶고, GPU에 스케줄링 — LLM만이 아니라 모든 모델(XGBoost, TensorFlow, LLM)에. 엔진(vLLM)이 그 아래에 꽂힌다.

JVM

Java Virtual Machine — the runtime that Java (and similar) programs run on. "A JVM-based serving system" just means "the serving software is written in Java and runs on the JVM." Netflix's existing model-serving stack is Java; the LLM work plugs into it.Java Virtual Machine — Java(및 유사) 프로그램이 돌아가는 런타임. "JVM 기반 서빙 시스템"은 그냥 "서빙 소프트웨어가 Java로 짜여 JVM에서 돈다"는 뜻. Netflix의 기존 모델 서빙 스택이 Java이고, LLM 작업이 거기 꽂힌다.

gRPC vs HTTP/RESTgRPC vs HTTP/REST

Two ways one program calls another over the network. HTTP/REST is the familiar web style (what browsers and most APIs use). gRPC is a faster, more structured style common inside big companies' internal systems. Netflix supports both doors into inference.한 프로그램이 다른 프로그램을 네트워크로 부르는 두 방식. HTTP/REST는 익숙한 웹 방식(브라우저·대부분 API). gRPC는 대기업 내부 시스템에서 흔한, 더 빠르고 구조적인 방식. Netflix는 추론으로 들어가는 두 문을 다 연다.

throughput vs latency처리량 vs 지연

Latency = how long one request takes (speed for you). Throughput = how many requests you finish per second (total volume). Serving is a constant tug-of-war between the two.지연(latency) = 한 요청이 걸리는 시간(내 체감 속도). 처리량(throughput) = 초당 끝내는 요청 수(총량). 서빙은 이 둘 사이의 끊임없는 줄다리기.

batching (continuous)배칭 (연속 배칭)

Running many requests together in one GPU pass so the expensive hardware stays busy. Continuous batching = requests can join and leave the batch mid-flight instead of waiting for a fixed group. Raises throughput.여러 요청을 GPU 한 번의 통과에서 함께 돌려 비싼 하드웨어를 계속 바쁘게. 연속 배칭 = 고정된 묶음을 기다리지 않고 요청이 도중에 배치에 합류/이탈. 처리량을 올린다.

prefill / decode / KV cache프리필 / 디코드 / KV 캐시

An LLM answers in two phases: prefill reads your whole prompt at once; decode then writes the answer one token at a time. The KV cache stores the prompt's processed state so each new token doesn't re-read everything — fast, but it eats GPU memory.LLM은 두 단계로 답한다: 프리필은 프롬프트 전체를 한 번에 읽고, 디코드는 답을 토큰 하나씩 쓴다. KV 캐시는 프롬프트의 처리된 상태를 저장해 새 토큰마다 전부 다시 읽지 않게 함 — 빠르지만 GPU 메모리를 먹는다.

GIL

Global Interpreter Lock — a rule inside standard Python that lets only one thread run Python code at a time. So Python can't do CPU work on many requests in parallel on multiple cores. This is the villain of §5. (C++ code isn't bound by it.)Global Interpreter Lock — 표준 Python 내부 규칙으로, 한 번에 하나의 스레드만 Python 코드를 실행하게 함. 그래서 Python은 여러 요청의 CPU 작업을 여러 코어에서 병렬로 못 한다. §5의 악당. (C++ 코드는 여기 안 묶임.)

guided / constrained decoding가이드 / 제약 디코딩

Forcing the model's output to follow a shape (e.g. valid JSON) by blocking illegal next-tokens at each step, so it literally can't produce a wrong character. Also called structured output / guided decoding.각 단계에서 불법 다음-토큰을 차단해 모델 출력이 정해진 형태(예: 올바른 JSON)를 따르게 강제 — 잘못된 글자를 애초에 못 만들게. 구조화 출력 / 가이드 디코딩이라고도.

control plane / autoscaling컨트롤 플레인 / 오토스케일링

Control plane = the "manager" layer that deploys, versions, health-checks, and scales the actual model servers (the "workers"). Autoscaling = automatically adding/removing GPU machines as traffic rises and falls.컨트롤 플레인 = 실제 모델 서버("일꾼")를 배포·버전관리·헬스체크·확장하는 "관리자" 층. 오토스케일링 = 트래픽 증감에 따라 GPU 머신을 자동으로 늘리고 줄임.

OpenAI-compatible APIOpenAI 호환 API

The request/response format OpenAI popularized (/v1/chat/completions, etc.). It became the de facto standard, so tools everywhere speak it. Exposing it means callers can point the same code at any model.OpenAI가 대중화한 요청/응답 형식(/v1/chat/completions 등). 사실상 표준이 되어 어디의 도구든 이 말을 한다. 이걸 노출하면 호출자가 같은 코드로 어떤 모델이든 가리킬 수 있다.

1What "serving" means, and why Netflix runs it in-house"서빙"이 뭔지, 그리고 Netflix가 왜 직접 굴리나

If you've only ever used AI models, "serving" is the part you never see. You type a prompt; somewhere a request travels over the network to a machine with a GPU, waits its turn among thousands of other requests, gets run through the model, and the answer comes back. Serving is all the plumbing that makes that happen reliably, fast, and cheaply for many users at once. It's a systems problem, not a modeling problem — which is exactly why it's full of the jargon we just defined. AI 모델을 써보기만 했다면, "서빙"은 한 번도 본 적 없는 부분이다. 프롬프트를 입력하면 — 어딘가에서 요청이 네트워크를 타고 GPU가 있는 머신으로 가서, 수천 개의 다른 요청 사이에서 차례를 기다리고, 모델에 태워지고, 답이 돌아온다. 서빙은 그 일을 많은 사용자에게 동시에 안정적·빠르게·저렴하게 되게 하는 배관 전부다. 모델링 문제가 아니라 시스템 문제 — 그래서 방금 정의한 전문용어로 가득하다.

Most companies skip this entirely by calling a hosted API (OpenAI, Anthropic, a cloud vendor). Netflix chose the opposite: 대부분의 회사는 호스팅 API(OpenAI, Anthropic, 클라우드 벤더)를 불러 이 전부를 건너뛴다. Netflix는 반대를 택했다:

"Most organizations consume LLMs through hosted APIs. Netflix went further — we run the full stack ourselves, from model deployment through inference, inside our existing production environment rather than a separate ML silo."

— Netflix TechBlog, "In-House LLM Serving at Netflix" · netflixtechblog.com

Two phrases there matter. "The full stack ourselves" means they own everything from the moment a model is deployed to the moment an answer is returned — not just the model, but the servers, the routing, the scaling, the monitoring. "Inside our existing production environment rather than a separate ML silo" means they did not stand up a separate AI system off to the side; they plugged LLMs into the same machinery that already serves Netflix's recommendation and ranking models to hundreds of millions of members. That single choice — "don't make LLMs special" — drives half the design decisions in this note. 여기서 두 구절이 중요하다. "전체 스택을 직접" — 모델이 배포되는 순간부터 답이 반환되는 순간까지 전부를 소유한다는 뜻. 모델뿐 아니라 서버·라우팅·확장·모니터링까지. "별도의 ML 사일로가 아니라 기존 프로덕션 환경 안에서" — 옆에 별도 AI 시스템을 세운 게 아니라, 이미 수억 명 회원에게 추천·랭킹 모델을 서빙하던 그 기계장치에 LLM을 꽂았다는 뜻. 이 한 가지 선택 — "LLM을 특별하게 만들지 말자" — 이 노트의 설계 결정 절반을 이끈다.

Why bother? What you get by not using a hosted API왜 이 고생을? 호스팅 API를 안 써서 얻는 것

Running it yourself is more work, so the payoff has to be real. Netflix names four: low latency (their own network, no round-trip to an outside vendor), deep customization (they can change how the model generates text token-by-token — the §5 story), cost and data privacy (a fine-tuned model they host can be cheaper and keeps member data in-house), and a smooth path from experiment to production (a researcher's prototype becomes a served model with minimal rewrite). The blog frames the win as removing friction, not as a benchmark number — there are no throughput/latency figures in the post. 직접 굴리는 건 더 많은 일이라, 보상이 진짜여야 한다. Netflix는 넷을 든다: 낮은 지연(자기 네트워크, 외부 벤더로의 왕복 없음), 깊은 커스터마이징(모델이 텍스트를 토큰 단위로 생성하는 방식을 바꿀 수 있음 — §5 이야기), 비용과 데이터 프라이버시(직접 호스팅하는 파인튜닝 모델이 더 싸고 회원 데이터를 내부에 둠), 실험→프로덕션의 매끄러운 경로(연구자의 프로토타입이 최소 재작성으로 서빙 모델이 됨). 블로그는 이득을 벤치마크 숫자가 아니라 마찰 제거로 설명한다 — 글에 처리량/지연 수치는 없다.

the mental model to hold붙잡을 멘탈 모델 Netflix did not write a new inference engine. They took two proven open-source pieces — the vLLM engine (the fast model-runner) and NVIDIA Triton (the model server that manages many models on GPUs) — and did the unglamorous integration work: packaging, APIs, deployment, monitoring, and one deep customization. The value is in the assembly and the production hardening, not in a novel algorithm. Netflix는 새 추론 엔진을 만들지 않았다. 검증된 오픈소스 두 조각 — vLLM 엔진(빠른 모델 실행기)과 NVIDIA Triton(GPU에서 여러 모델을 관리하는 모델 서버) — 을 가져와, 화려하지 않은 통합 작업을 했다: 패키징·API·배포·모니터링, 그리고 하나의 깊은 커스터마이징. 가치는 새 알고리즘이 아니라 조립과 프로덕션 견고화에 있다.

Here's the whole path from "a caller wants an answer" to "a GPU runs the model," with each box explained in plain terms. Read it top to bottom. "호출자가 답을 원함"에서 "GPU가 모델을 돌림"까지의 전체 경로를, 각 상자를 쉬운 말로 풀어 아래로 읽자.

Box by box상자별로

  • Two front doors. Existing recommendation/ranking apps call inference over gRPC (the fast internal style) through the JVM system. Newer LLM apps can also go directly over HTTP using the OpenAI-compatible API. Same destination, two entrances.두 정문. 기존 추천/랭킹 앱은 JVM 시스템을 통해 gRPC(빠른 내부 방식)로 추론을 부른다. 새 LLM 앱은 OpenAI 호환 API로 HTTP를 통해 직접도 갈 수 있다. 같은 목적지, 두 입구.
  • The JVM serving system. Netflix's existing Java serving layer. It does everything around the model: decides which model/variant to use (A/B tests), fetches the input features, runs any pre- and post-processing, and logs each stage. Small models that run on CPU execute right here in the same process — no network hop, so no remote-call overhead. Big models that need a GPU get forwarded.JVM 서빙 시스템. Netflix의 기존 Java 서빙 층. 모델 주변의 모든 걸 한다: 어느 모델/변형을 쓸지 결정(A/B 테스트), 입력 피처 가져오기, 전·후처리, 각 단계 로깅. CPU에서 도는 작은 모델은 같은 프로세스 안에서 바로 실행 — 네트워크 홉 없음, 원격 호출 오버헤드 없음. GPU가 필요한 큰 모델은 넘겨진다.
  • MSS (Model Scoring Service). The shared GPU backend. Crucially, it serves every kind of model — classic ML (XGBoost), TensorFlow, PyTorch, and LLMs — behind one interface. That uniformity is the whole point: an LLM is just another model to MSS.MSS (Model Scoring Service). 공유 GPU 백엔드. 핵심은, 모든 종류의 모델을 서빙한다 — 고전 ML(XGBoost), TensorFlow, PyTorch, LLM — 하나의 인터페이스 뒤에서. 이 균일함이 요점: MSS에게 LLM은 그저 또 하나의 모델일 뿐.
  • Java control plane. The "manager." It deploys models, tracks versions, runs health checks, autoscales GPU machines with traffic, and does multi-region rollout. Model authors just package their model and set config; the control plane provisions the GPUs, configures Triton, and does zero-downtime upgrades.Java 컨트롤 플레인. "관리자." 모델을 배포하고, 버전을 추적하고, 헬스체크를 돌리고, 트래픽에 맞춰 GPU 머신을 오토스케일하고, 멀티 리전 롤아웃을 한다. 모델 작성자는 모델을 패키징하고 설정만 하면 됨; 컨트롤 플레인이 GPU를 프로비저닝하고 Triton을 구성하고 무중단 업그레이드를 한다.
  • Triton, then vLLM. Triton is the model server that loads the model, batches requests, and schedules them on the GPU. Underneath it, for LLMs, sits the vLLM engine doing the actual token generation. Triton is the shell; vLLM is the engine inside it.Triton, 그다음 vLLM. Triton은 모델을 로드하고 요청을 배칭하고 GPU에 스케줄링하는 모델 서버. 그 아래, LLM의 경우 vLLM 엔진이 실제 토큰 생성을 한다. Triton은 껍데기, vLLM은 그 안의 엔진.

3The four big decisions — engine, packaging, API, rollout네 가지 큰 결정 — 엔진·패키징·API·배포

Netflix says four decisions shaped the platform, and they're presented "in dependency order, since each one constrains the next": which engine to run → how to package models for it → what API callers use → how to roll out new versions. Netflix는 네 결정이 플랫폼을 형성했고, "각각이 다음을 제약하므로 의존 순서대로" 제시한다고 말한다: 어떤 엔진을 돌릴지 → 그 엔진용으로 모델을 어떻게 패키징할지 → 호출자가 어떤 API를 쓸지 → 새 버전을 어떻게 배포할지.

3.1 — Engine: they switched from TensorRT-LLM to vLLM (for operational reasons, not raw speed)3.1 — 엔진: TensorRT-LLM에서 vLLM으로 (속도가 아니라 운영상 이유로)

The platform started on TensorRT-LLM (NVIDIA's engine — very fast, already integrated with Triton). By summer 2025 two things changed: open-source engines had "largely closed the performance gap," and Netflix's workloads had broadened beyond chat to embeddings, prefill-only inference (for ranking/retrieval), and custom models with per-step logic. So they re-benchmarked and picked vLLM — not because it was fastest, but on operational fit: 플랫폼은 TensorRT-LLM(NVIDIA 엔진 — 매우 빠르고 Triton에 이미 통합됨)에서 시작했다. 2025년 여름 두 가지가 바뀌었다: 오픈소스 엔진이 "성능 격차를 거의 좁혔고", Netflix의 워크로드가 챗을 넘어 임베딩, 프리필 전용 추론(랭킹/검색용), 스텝별 로직이 있는 커스텀 모델로 넓어졌다. 그래서 재벤치마크 후 vLLM을 골랐다 — 가장 빨라서가 아니라 운영 적합성으로:

  • Loads custom model shapes without a compile step. "Compiled" engines like TensorRT-LLM turn a model into optimized GPU machine code first (a multi-step pipeline); great for speed, slow to iterate on unusual models. vLLM can just load them — faster iteration.커스텀 모델 형태를 컴파일 단계 없이 로드. TensorRT-LLM 같은 "컴파일" 엔진은 모델을 먼저 최적화된 GPU 기계어로 변환(다단계 파이프라인)한다; 속도엔 좋지만 특이한 모델을 빠르게 반복하기 어렵다. vLLM은 그냥 로드 — 반복이 빠르다.
  • Extensibility hooks for custom decoding. vLLM lets you inject your own logic into the generation loop — the exact feature the §5 constrained-decoding work depends on.커스텀 디코딩용 확장 훅. vLLM은 생성 루프에 자기 로직을 주입하게 해준다 — §5 제약 디코딩 작업이 의존하는 바로 그 기능.
  • Debuggability & familiarity. Easier to inspect failures than a compiled engine, and many researchers already used vLLM — so moving a prototype to production costs less.디버깅 용이성 & 친숙함. 컴파일 엔진보다 실패를 들여다보기 쉽고, 많은 연구자가 이미 vLLM을 써서 프로토타입을 프로덕션으로 옮기는 비용이 적다.
the lesson교훈 "Fastest engine on a benchmark" and "best engine for a real team" are different questions. Netflix optimized for iteration speed, extensibility, and debuggability — because in production those save more time than a few percent of raw throughput. "벤치마크에서 가장 빠른 엔진"과 "실제 팀에 최선인 엔진"은 다른 질문이다. Netflix는 반복 속도·확장성·디버깅 용이성을 최적화했다 — 프로덕션에선 그것들이 원시 처리량 몇 %보다 더 많은 시간을 아끼기 때문.

3.2 — Packaging: let the model and the frontend evolve independently3.2 — 패키징: 모델과 프런트엔드가 따로 진화하게

"Packaging" = how you bundle a model so the server can load it. Triton offers two ways, and the difference is about coupling — how tightly the model's bundle is tied to the frontend software. "패키징" = 서버가 로드할 수 있게 모델을 묶는 방법. Triton은 두 방식을 제공하고, 차이는 결합도(coupling) — 모델 묶음이 프런트엔드 소프트웨어에 얼마나 단단히 묶이는지 — 에 있다.

Way방식What the author does작성자가 하는 일Coupling결합도
Python backendHand-writes the exact input/output data shapes ("tensor specs"), frozen into the bundle.입출력 데이터 형태("텐서 스펙")를 손으로 적어 묶음에 고정.Tight — the frozen specs must match the frontend; every frontend upgrade touching I/O needs a coordinated packaging change, or requests fail.단단함 — 고정 스펙이 프런트엔드와 맞아야 함; I/O를 건드리는 프런트엔드 업그레이드마다 패키징도 함께 바꿔야 하고, 안 그러면 요청 실패.
vLLM backendJust writes a small JSON config pointing at the weights + tokenizer. Triton figures out the I/O shapes automatically at deploy time.가중치 + 토크나이저를 가리키는 작은 JSON 설정만 작성. Triton이 배포 시 I/O 형태를 자동으로 알아냄.Loose — model and frontend evolve independently. This is the "architecturally correct" default.느슨함 — 모델과 프런트엔드가 따로 진화. 이것이 "구조적으로 올바른" 기본값.

The loose (vLLM-backend) way is the default — but production bit them twice: 느슨한(vLLM-백엔드) 방식이 기본이지만 — 프로덕션이 두 번 물었다:

  • Version mismatch. Triton's vLLM backend is compiled against a specific vLLM version. When they drift — e.g. Triton 25.09 tried to import vllm.engine.metrics, a module removed in vLLM 0.11.2 — the backend fails to load entirely. Fix: pin compatible versions when building the service image, and stop model authors from overriding the vLLM version.버전 불일치. Triton의 vLLM 백엔드는 특정 vLLM 버전에 맞춰 컴파일됨. 둘이 어긋나면 — 예: Triton 25.09가 vLLM 0.11.2에서 제거된 모듈 vllm.engine.metrics를 임포트하려 함 — 백엔드가 통째로 로드 실패. 해결: 서비스 이미지 빌드 시 호환 버전을 핀 고정하고, 모델 작성자가 vLLM 버전을 덮어쓰지 못하게 함.
  • Custom logic needs the escape hatch. The tidy vLLM backend only handles standard HuggingFace-style models. Anything with custom preprocessing, custom tokenization, or a multi-model pipeline must fall back to the Python backend and its full-control execute() method. That escape hatch will stay necessary for some models.커스텀 로직엔 탈출구가 필요. 깔끔한 vLLM 백엔드는 표준 HuggingFace식 모델만 다룬다. 커스텀 전처리·커스텀 토크나이제이션·멀티모델 파이프라인이 있으면 Python 백엔드와 완전 제어 execute()로 돌아가야 함. 이 탈출구는 일부 모델에 계속 필요할 것.

3.3 — API: "an LLM is not a special snowflake"3.3 — API: "LLM은 특별한 눈송이가 아니다"

"A key design goal of our system was that LLM models should NOT be special snowflakes. Every model — XGBoost ensemble or large-scale LLMs — is scored via the same gRPC call, so we reuse the same client libraries, health checking, and deployment pipelines."

— Netflix TechBlog · netflixtechblog.com

"Not a special snowflake" means: don't build a separate pipeline just for LLMs. Every model is called the same way, so all the existing tooling (client libraries, health checks, deployment) is reused. But the LLM world has standardized on the OpenAI-compatible API — every tool speaks it — so Netflix exposes that too, alongside gRPC. The payoff: moving from a hosted model to a self-hosted fine-tuned one is "nearly seamless. Same API, minimal code changes." "특별한 눈송이가 아니다"는: LLM만을 위한 별도 파이프라인을 짓지 말자는 뜻. 모든 모델을 같은 방식으로 부르니 기존 도구(클라이언트 라이브러리·헬스체크·배포)를 전부 재사용. 하지만 LLM 세계는 OpenAI 호환 API로 표준화됐고 — 모든 도구가 이 말을 함 — 그래서 Netflix는 gRPC와 나란히 그것도 노출한다. 보상: 호스팅 모델에서 자체 호스팅 파인튜닝 모델로 옮기는 게 "거의 매끄럽다. 같은 API, 최소한의 코드 변경."

the bug this caused — a silent one이게 부른 버그 — 소리 없는 것 They reused NVIDIA's ready-made OpenAI-compatible frontend. But it silently dropped the response_format field (the "give me JSON" instruction) before it reached vLLM. So a caller asking for JSON got no guided-decoding constraint — and could receive malformed JSON with no error reported. Silent failures are the worst kind. Netflix pulled the frontend into their own tree (git subtree) and patched it to translate response_format into vLLM's guided-decoding parameters. This is exactly the feature the §5 deep-dive is about. NVIDIA의 기성 OpenAI 호환 프런트엔드를 재사용했다. 그런데 그게 response_format 필드("JSON으로 줘" 지시)를 vLLM에 닿기 전에 조용히 버렸다. 그래서 JSON을 요청한 호출자가 가이드 디코딩 제약을 전혀 못 받고 — 에러 보고도 없이 깨진 JSON을 받을 수 있었다. 소리 없는 실패가 최악이다. Netflix는 프런트엔드를 자기 트리로 가져와(git subtree) response_format을 vLLM의 가이드 디코딩 파라미터로 번역하도록 패치했다. 바로 §5 딥다이브의 그 기능.

3.4 — Rollout: two ways to ship a new version without dropping requests3.4 — 배포: 요청을 흘리지 않고 새 버전을 내보내는 두 방법

GPU deployments are slow to bring up, and a new model version can change its input/output shapes — so upgrading is a coordination problem. Two strategies (think "blue-green deployment" if you know that term): GPU 배포는 띄우는 데 오래 걸리고, 새 모델 버전은 입출력 형태가 바뀔 수 있다 — 그래서 업그레이드는 조율 문제다. 두 전략("blue-green 배포"를 안다면 그것):

Strategy전략How방법When to use언제 쓰나
Red-BlackBring the new version up next to the old; once it's healthy, shift traffic in phases (new up, old down together); auto-rollback if any step fails.새 버전을 옛것 옆에 띄움; 건강해지면 단계적으로 트래픽 이동(새것↑, 옛것↓ 동시에); 한 단계라도 실패하면 자동 롤백.Cheaper & default — when the model's input/output interface is stable.더 싸고 기본 — 모델 입출력 인터페이스가 안정적일 때.
VersionedKeep an independent deployment for every (model, version) pair; many versions serve at once. The caller switches only after the new one is fully ready; the old keeps serving legacy traffic.모든 (모델, 버전) 쌍마다 독립 배포 유지; 여러 버전이 동시에 서빙. 호출자는 새것이 완전히 준비된 뒤에만 전환; 옛것은 레거시 트래픽을 계속 처리.When a version changes its I/O shape — Red-Black would send "old" requests to the "new" model mid-migration and they'd fail. Costs extra GPU during overlap.버전이 I/O 형태를 바꿀 때 — Red-Black은 마이그레이션 도중 "옛" 요청을 "새" 모델로 보내 실패시킴. 겹치는 동안 GPU 비용 추가.

Netflix's advice: bake variable settings (like tensor shapes) into the model so it's version-agnostic and can use the cheaper Red-Black path; reserve Versioned for the rare unavoidable breaking change. Netflix의 조언: 가변 설정(텐서 형태 등)을 모델 안에 넣어 버전 무관하게 만들고 더 싼 Red-Black을 쓰라; Versioned는 피할 수 없는 드문 breaking change용으로 아껴라.

4Things that only broke in production프로덕션에서만 터진 것들

Two operational details that the design phase didn't anticipate — both are small, both are the kind of thing you only learn by running the system for real. 설계 단계가 예상 못 한 두 운영 디테일 — 둘 다 작고, 둘 다 시스템을 실제로 굴려봐야만 배우는 종류.

Cold starts: cache the model on a fast file system, not object storage콜드 스타트: 오브젝트 스토리지 말고 빠른 파일 시스템에 모델 캐시

A cold start is the time from "spin up a new server" to "ready to serve." For LLMs, most of it is just downloading the model weights — tens of gigabytes. Netflix found that pulling weights straight from S3 (Amazon's object storage — great for durability, not for fast bulk reads) or Hugging Face at boot was slow enough to blow past what their scheduler will wait for. Fix: pre-load ("materialize") each model onto Amazon FSx — a high-performance shared file system — when the model is announced, so a starting server reads from a fast disk instead of over the network from object storage. 콜드 스타트는 "새 서버를 띄움"부터 "서빙 준비 완료"까지의 시간. LLM에선 대부분이 그냥 모델 가중치 다운로드 — 수십 GB. Netflix는 부팅 때 S3(Amazon의 오브젝트 스토리지 — 내구성엔 좋지만 빠른 대량 읽기엔 부적합)나 Hugging Face에서 가중치를 바로 당기는 게 스케줄러가 기다려주는 시간을 넘길 만큼 느리다는 걸 발견했다. 해결: 모델이 announce될 때 각 모델을 Amazon FSx(고성능 공유 파일 시스템)에 미리 올려("materialize"), 시작하는 서버가 오브젝트 스토리지에서 네트워크로 받는 대신 빠른 디스크에서 읽게 함.

The rest of the boot is mechanical: unpack the model, install any custom vLLM plugins, clean the metrics scratch directory, and — importantly — keep the gRPC port closed until the engine is actually ready, so no request arrives before the server can answer it. 나머지 부팅은 기계적: 모델 압축 해제, 커스텀 vLLM 플러그인 설치, 메트릭 스크래치 디렉터리 청소, 그리고 — 중요하게 — 엔진이 실제로 준비될 때까지 gRPC 포트를 닫아 둠, 서버가 답할 수 있기 전에 요청이 도착하지 않도록.

Metrics: two systems that couldn't see each other메트릭: 서로를 못 보는 두 시스템

Metrics are the numbers a system emits about itself (requests/sec, memory used, errors) so dashboards and alerts can watch it; Prometheus is the popular tool that collects them. The problem: vLLM and Triton each report metrics their own way and neither knows about the other. Triton's built-in bridge exposed only 9 of 40+ vLLM metrics — missing the ones that actually matter for an LLM: token throughput, KV cache utilization, and prefix-cache hit rate. 메트릭은 시스템이 자기 상태에 대해 내보내는 숫자(초당 요청, 사용 메모리, 에러)로 대시보드·알림이 지켜보게 함; Prometheus는 그걸 수집하는 인기 도구. 문제: vLLM과 Triton이 각자의 방식으로 메트릭을 보고하고 서로를 모른다. Triton의 내장 브리지는 40여 개 vLLM 메트릭 중 9개만 노출 — LLM에 정작 중요한 것들이 빠짐: 토큰 처리량, KV 캐시 사용률, 프리픽스 캐시 히트율.

Fix: a small HTTP proxy that fetches Triton's metrics and reads vLLM's from disk, then merges both into a single /metrics endpoint — so existing dashboards and alerts keep working unchanged. Unglamorous glue, but it's the difference between "we can see what the GPU is doing" and flying blind. 해결: Triton 메트릭을 가져오고 vLLM 것을 디스크에서 읽어 둘을 하나의 /metrics 엔드포인트로 합치는 작은 HTTP 프록시 — 기존 대시보드·알림이 그대로 동작. 화려하지 않은 접착제지만, "GPU가 뭘 하는지 볼 수 있다"와 "깜깜이 비행"의 차이다.

5The headline problem — making JSON valid "by construction" at scale핵심 문제 — 대규모에서 JSON을 "애초에 올바르게" 만들기

This is the most interesting part, and it needs three small ideas first. 가장 흥미로운 부분이고, 먼저 작은 개념 셋이 필요하다.

logits로짓 (logits)

At each step the model outputs a raw score for every possible next token — one number per vocabulary word. The highest usually wins. Those scores are the logits.매 단계 모델은 모든 가능한 다음 토큰에 원시 점수를 낸다 — 어휘 단어당 숫자 하나. 보통 가장 높은 게 이긴다. 그 점수들이 로짓.

logits processor로짓 프로세서

Code that edits the logits before a token is picked. To force valid JSON, set the score of every illegal next token to minus-infinity — now the model literally cannot pick it.토큰이 선택되기 전에 로짓을 수정하는 코드. 올바른 JSON을 강제하려면 모든 불법 다음-토큰의 점수를 마이너스 무한대로 — 이제 모델은 그걸 절대 못 고른다.

state machine상태 기계

A tiny tracker that remembers "where are we in the JSON so far?" and from that decides which tokens are legal next. It advances one step each time a token is generated."지금까지 JSON의 어디쯤인가?"를 기억하고, 그로부터 다음에 어떤 토큰이 합법인지 정하는 작은 추적기. 토큰이 생성될 때마다 한 걸음 전진.

Netflix's idea: instead of letting the model write whatever, then checking it afterward (and paying to re-run it when it's wrong), push the rules inside the generation loop so the output is correct by construction: Netflix의 아이디어: 모델이 아무거나 쓰게 두고 나중에 검사(틀리면 재실행 비용을 물기)하는 대신, 규칙을 생성 루프 안에 밀어넣어 출력이 애초에 올바르게:

"Rather than applying business logic after inference — paying for invalid generations, then retrying or repairing — we push constraints inside the decode loop, so the model generates outputs that are compliant by construction."

— Netflix TechBlog, "Constrained Decoding at Scale" · netflixtechblog.com

Why the first version didn't scale — a CPU bottleneck hiding behind the GPU첫 버전이 확장 안 된 이유 — GPU 뒤에 숨은 CPU 병목

The first implementation was pure Python on vLLM V0, and it worked — for one request. Under real concurrency it fell over, for a reason that's a perfect example of a systems gotcha invisible to model people: 첫 구현은 vLLM V0 위의 순수 Python이었고, 작동했다 — 한 요청에 대해선. 실제 동시성에선 무너졌는데, 그 이유가 모델 하는 사람에겐 안 보이는 시스템 함정의 완벽한 예다:

"…constraint logic runs sequentially for each request — sequentially because the GIL prevents Python from parallelizing the per-request work. CPU time in logit processing therefore grows linearly with batch size, hitting tail latencies. End-to-end latency becomes CPU-bound even though the model's forward pass is batched efficiently on GPU."

— Netflix TechBlog · netflixtechblog.com

Unpacked: the GPU efficiently computes logits for the whole batch at once. But then the mask-computing code (the constraint logic) ran one request at a time on the CPU — because the Python GIL (from the glossary: only one thread runs Python at a time) forbids doing them in parallel. So if the batch has 50 requests, you pay 50 mask computations back-to-back, on the CPU, every single token step. The GPU is fast and batched; the CPU is serial and slow — and the CPU becomes the bottleneck. Worst of all, you'd never see it in a single-request benchmark (one request = no serial pile-up); it only appears under production concurrency. 풀어 보면: GPU는 배치 전체의 로짓을 한 번에 효율적으로 계산한다. 그런데 마스크 계산 코드(제약 로직)는 CPU에서 한 요청씩 돌았다 — Python GIL(용어집: 한 번에 한 스레드만 Python 실행)이 병렬을 금지하기 때문. 그래서 배치에 요청이 50개면, 매 토큰 단계마다 CPU에서 50번의 마스크 계산을 줄줄이 문다. GPU는 빠르고 배치화됐는데, CPU는 직렬이고 느리다 — 그리고 CPU가 병목이 된다. 최악은, 단일 요청 벤치마크에선 절대 안 보인다(요청 1개 = 직렬 쌓임 없음); 프로덕션 동시성에서만 나타난다.

Fig 2 — V0 (top): the GPU batches the logits, but the CPU computes one request's mask after another because the GIL blocks parallelism, so CPU time grows with batch size and dominates. V1 (bottom): masks are computed for the whole batch together, in multi-threaded C++, so the time stays flat. Schematic — the blog shows this shape (Figs 2–3) but publishes no axis numbers.그림 2 — V0(위): GPU는 로짓을 배치화하지만, GIL이 병렬을 막아 CPU가 요청 마스크를 하나씩 계산 → CPU 시간이 배치 크기에 따라 커지고 지배한다. V1(아래): 마스크를 배치 전체에 대해 함께, 멀티스레드 C++로 계산 → 시간이 평평하게 유지. 개략도 — 블로그는 이 형태(Fig 2–3)를 보이지만 축 수치는 공개하지 않음.

The fix — vLLM V1 moved masking to batch level해결 — vLLM V1이 마스킹을 배치 레벨로 옮김

The structural fix came with vLLM V1 (Netflix migrated in Q4 2025), which processes logits at the batch level instead of per request. Two changes did it: 구조적 해결은 vLLM V1(Netflix는 2025 Q4에 이전)과 함께 왔고, 로짓을 요청별이 아니라 배치 레벨에서 처리한다. 두 변경이 해냈다:

  • Compute all masks together. Rewrite the processor to work on batch-level data structures — build the eligibility masks for many requests at once, not in a loop.모든 마스크를 함께 계산. 프로세서를 배치 레벨 자료구조 위에서 동작하도록 재작성 — 여러 요청의 적격 마스크를 루프가 아니라 한꺼번에.
  • Move the hot path to C++. They reimplemented the heavy part in C++ with multi-threading — and C++ isn't bound by Python's GIL, so it can genuinely use many CPU cores in parallel. (Their words: "reimplemented the hot path in C++ with multi-threading to step around the GIL.")핫 패스를 C++로. 무거운 부분을 멀티스레드 C++로 재구현 — C++은 Python GIL에 안 묶여 여러 CPU 코어를 진짜 병렬로 쓴다. (원문: "reimplemented the hot path in C++ with multi-threading to step around the GIL.")

The cost of the fix: V1's API is harder. Because the batch is constantly changing (requests join and finish), the processor must explicitly track who's in the batch via update_state(batch_update) — more bookkeeping than V0's simple per-request call, but that's what keeps the state machines correct in a moving batch. The result: logits-processing time stays flat as batch size grows, so it's no longer the bottleneck. 해결의 비용: V1의 API는 더 어렵다. 배치가 계속 바뀌므로(요청이 합류·종료), 프로세서가 update_state(batch_update)로 배치 멤버십을 명시적으로 추적해야 한다 — V0의 단순 요청별 호출보다 장부 일이 많지만, 그게 움직이는 배치에서 상태 기계를 올바르게 유지한다. 결과: 로짓 처리 시간이 배치 크기에 따라 평평하게 유지 → 더는 병목이 아니다.

Operational hardening — two ways a stateful decoder breaks운영 견고화 — 상태 있는 디코더가 깨지는 두 방식

Once speed was solved, keeping a stateful state machine correct inside a real serving loop surfaced two subtle bugs: 속도가 해결되자, 실제 서빙 루프 안에서 상태 있는 상태 기계를 올바르게 유지하는 데서 미묘한 버그 둘이 드러났다:

  • Partial prefills. V1 reads a long prompt in chunks over several steps ("chunked prefill"), but the batch-update signal couldn't say whether a request was fully or only partially prefilled. If the state machine thinks the prompt is done when it isn't, it advances too early. Fix: Netflix added their own internal tracking of prefill completeness.부분 프리필. V1은 긴 프롬프트를 여러 단계에 걸쳐 조각으로 읽는데("chunked prefill"), 배치 업데이트 신호가 요청이 완전히 프리필됐는지 부분만 됐는지 말하지 못했다. 상태 기계가 프롬프트가 안 끝났는데 끝났다고 여기면 너무 일찍 전진한다. 해결: Netflix가 프리필 완료 여부를 자체 추적.
  • Preemption. When GPU memory runs short, vLLM can evict a half-finished request's KV cache to make room, then reschedule it later. The rescheduled request may come back with a different prompt/output token list — which breaks the state machine's assumption that the generated text only ever grows. Fix: detect when the token history shrinks between steps, reset the state machine, and re-initialize from the new prompt.선점(preemption). GPU 메모리가 부족하면 vLLM은 반쯤 끝난 요청의 KV 캐시를 축출해 자리를 만들고 나중에 다시 스케줄한다. 재스케줄된 요청은 다른 프롬프트/출력 토큰 리스트로 돌아올 수 있고 — 이는 생성 텍스트가 오직 커지기만 한다는 상태 기계의 가정을 깬다. 해결: 단계 사이에 토큰 히스토리가 줄어드는 걸 감지하면 상태 기계를 리셋하고 새 프롬프트로 재초기화.
why this section is the whole point이 섹션이 요점인 이유 This is the payoff of choosing vLLM for its extensibility hooks (§3.1) and of owning the stack (§1). A hosted API won't let you rewrite the decode loop in C++ or track prefill state — Netflix could, because they run it all. The lesson generalizes: a bottleneck can live in the "cheap" CPU glue around a fast GPU, be invisible in single-request tests, and only surface under concurrency. 이것이 vLLM을 확장 훅(§3.1) 때문에 고르고 스택을 소유한(§1) 것의 보상이다. 호스팅 API는 디코드 루프를 C++로 다시 쓰거나 프리필 상태를 추적하게 해주지 않는다 — Netflix는 전부 직접 굴리니 가능했다. 교훈은 일반화된다: 병목은 빠른 GPU 주변의 "싼" CPU 접착제에 살 수 있고, 단일 요청 테스트엔 안 보이며, 동시성에서만 드러난다.
