In-House LLM Serving at Netflix — a plain-language walkthrough Netflix의 자체 LLM 서빙: 쉬운 말로 풀어 읽기

Netflix runs its own LLM serving platform on open-source vLLM + NVIDIA Triton, wired into the systems that already serve its recommendation models. This note explains it for readers who know AI models but not systems jargon, based on the Netflix TechBlog post. Netflix는 오픈소스 vLLM과 NVIDIA Triton 위에 자체 LLM 서빙 플랫폼을 짓고, 추천 모델을 서빙하던 기존 시스템에 연결했다. 이 노트는 Netflix TechBlog 글을 바탕으로, AI 모델은 알지만 시스템 용어는 낯선 독자를 위해 그 구조를 풀어 쓴다.

one-line summary한 줄 요약
  • Netflix built its LLM serving platform on open-source vLLM + NVIDIA Triton and plugged it into the JVM system that already serves its other models ("an LLM is not a special snowflake").
  • It picked the engine on operational fit, not raw speed, and packaged models so they and the frontend evolve independently.
  • It exposes the OpenAI-compatible API, so moving from a hosted model to a self-hosted one takes minimal code change.
  • The highlight: enforcing valid JSON inside the decode loop hit a CPU bottleneck (the Python GIL) that only appeared under real concurrency. The blog gives no latency/throughput numbers.
  • Netflix는 오픈소스 vLLM + NVIDIA Triton 위에 LLM 서빙 플랫폼을 짓고, 다른 모델을 서빙하던 JVM 시스템에 그대로 연결했다("LLM은 특별한 눈송이가 아니다").
  • 엔진은 속도보다 운영 적합성으로 골랐고, 모델과 프런트엔드가 따로 바뀔 수 있게 패키징했다.
  • OpenAI 호환 API를 열어 호스팅 모델에서 자체 호스팅 모델로 옮길 때 코드 변경이 거의 없다.
  • 하이라이트는 디코드 루프 안에서 JSON 형식을 강제하는 작업이다. 이 작업은 실제 동시성에서만 드러나는 CPU 병목(Python GIL)에 부딪혔다. 블로그에 지연/처리량 수치는 없다.

Glossary (read this first)용어집 (먼저 읽기)

inference / serving추론 / 서빙

Inference runs a trained model to get an answer. Serving is the production plumbing around it, for many users at once.추론은 학습된 모델을 돌려 답을 얻는 일이다. 서빙은 이를 많은 사용자에게 안정적으로 제공하는 배관 전체다.

inference engine (vLLM / TensorRT-LLM)추론 엔진 (vLLM / TensorRT-LLM)

Runs the model math on the GPU fast. vLLM is open-source; TensorRT-LLM is NVIDIA's.GPU에서 모델 연산을 빠르게 돌리는 부품이다. vLLM은 오픈소스, TensorRT-LLM은 NVIDIA 제품이다.

Triton (model server)Triton (모델 서버)

NVIDIA's model server: loads, batches and schedules any model type (XGBoost, TensorFlow, LLMs). vLLM plugs in underneath.NVIDIA의 모델 서버로, XGBoost·TensorFlow·LLM 등 모든 모델을 로드·배칭·스케줄링한다. vLLM은 그 아래에 붙는다.

JVM

Java Virtual Machine. Netflix's existing model-serving stack is Java on the JVM; the LLM work plugs into it.Java Virtual Machine. Netflix의 기존 모델 서빙 스택은 JVM 위의 Java이고, LLM도 여기에 붙는다.

gRPC vs HTTP/RESTgRPC vs HTTP/REST

Two ways programs call each other. HTTP/REST is the familiar web style; gRPC is faster and common internally. Netflix supports both.프로그램끼리 네트워크로 부르는 두 방식이다. HTTP/REST는 익숙한 웹 방식, gRPC는 사내 시스템에서 흔한 더 빠른 방식이다. Netflix는 둘 다 연다.

throughput vs latency처리량 vs 지연

Latency is how long one request takes; throughput is requests finished per second.지연(latency)은 요청 하나에 걸리는 시간, 처리량(throughput)은 초당 끝내는 요청 수다.

batching (continuous)배칭 (연속 배칭)

Running many requests together per GPU pass. Continuous batching lets requests join and leave mid-flight.여러 요청을 GPU 한 번에 함께 돌리는 것이다. 연속 배칭은 요청이 도중에 배치에 들어오고 나갈 수 있게 한다.

prefill / decode / KV cache프리필 / 디코드 / KV 캐시

Prefill reads the whole prompt; decode writes one token at a time. The KV cache keeps the prompt's state in GPU memory.프리필은 프롬프트 전체를 읽고, 디코드는 토큰을 하나씩 쓴다. KV 캐시는 그 상태를 GPU 메모리에 저장한다.

GIL

Global Interpreter Lock: only one thread runs Python at a time, so Python can't parallelize CPU work. The villain of §5. (C++ isn't bound by it.)Global Interpreter Lock. Python 코드는 한 번에 하나의 스레드만 실행할 수 있어 CPU 작업을 병렬로 못 돌린다. §5의 악당이다(C++은 해당 없음).

guided / constrained decoding가이드 / 제약 디코딩

Forcing output to follow a shape (e.g. valid JSON) by blocking illegal next-tokens at each step.매 단계 규칙에 어긋나는 다음 토큰을 막아 출력이 정해진 형식(예: JSON)을 따르게 하는 방법이다.

control plane / autoscaling컨트롤 플레인 / 오토스케일링

Control plane: the manager layer that deploys, versions, health-checks and scales model servers. Autoscaling adds/removes GPU machines with traffic.컨트롤 플레인은 모델 서버를 배포·버전 관리·헬스체크·확장하는 관리 층이다. 오토스케일링은 트래픽에 따라 GPU 머신 수를 조절한다.

OpenAI-compatible APIOpenAI 호환 API

The de facto standard request format (/v1/chat/completions, etc.), so callers can point the same code at any model.사실상 표준이 된 요청 형식(/v1/chat/completions 등)이다. 같은 코드로 어떤 모델이든 부를 수 있다.

1What "serving" means, and why Netflix runs it in-house"서빙"이 뭔지, 그리고 Netflix가 왜 직접 굴리나

When you type a prompt, the request travels to a GPU machine, waits its turn among thousands of others, runs through the model, and the answer comes back. Serving is the plumbing that makes this reliable, fast and cheap for many users at once. It is a systems problem, not a modeling problem. 프롬프트를 입력하면 요청이 GPU 머신으로 가서 수천 개의 다른 요청과 함께 차례를 기다리고, 모델을 거쳐 답이 돌아온다. 서빙은 이 과정을 많은 사용자에게 안정적이고 빠르고 싸게 제공하는 배관이다. 모델링이 아니라 시스템 문제다.

Most companies skip this by calling a hosted API (OpenAI, Anthropic, a cloud vendor). Netflix chose the opposite: 대부분의 회사는 호스팅 API(OpenAI, Anthropic, 클라우드 벤더)를 불러 이 일을 건너뛴다. Netflix는 반대를 택했다.

"Most organizations consume LLMs through hosted APIs. Netflix went further — we run the full stack ourselves, from model deployment through inference, inside our existing production environment rather than a separate ML silo."

— Netflix TechBlog, "In-House LLM Serving at Netflix" · netflixtechblog.com

They own everything from deployment to the returned answer: servers, routing, scaling, monitoring. And they did not build a separate AI system; LLMs plug into the same machinery that serves recommendation and ranking models to hundreds of millions of members. "Don't make LLMs special" drives half the design decisions below. 배포부터 답 반환까지 서버·라우팅·확장·모니터링을 모두 직접 운영한다. 별도 AI 시스템을 세우지 않고, 수억 명 회원에게 추천·랭킹 모델을 서빙하던 기존 시스템에 LLM을 붙였다. "LLM을 특별 취급하지 않는다"는 원칙이 아래 설계 결정의 절반을 이끈다.

Why bother? What you get by not using a hosted API왜 이 고생을? 호스팅 API를 안 써서 얻는 것

  • Low latency: their own network, no round-trip to an outside vendor.
  • Deep customization: they can change how the model generates text token-by-token (§5).
  • Cost and data privacy: a self-hosted fine-tuned model can be cheaper and keeps member data in-house.
  • A smooth path from experiment to production with minimal rewrite.
  • 낮은 지연: 자사 네트워크 안에서 처리해 외부 벤더 왕복이 없다.
  • 깊은 커스터마이징: 토큰 단위 생성 방식까지 바꿀 수 있다(§5).
  • 비용과 데이터 프라이버시: 직접 호스팅하는 파인튜닝 모델은 더 쌀 수 있고 회원 데이터가 밖으로 나가지 않는다.
  • 실험에서 프로덕션까지 매끄러운 경로: 연구자의 프로토타입을 거의 고치지 않고 서빙한다.

The blog frames these as removing friction; there are no throughput/latency figures in the post.블로그는 이를 마찰 제거로 설명할 뿐, 처리량/지연 수치는 내놓지 않는다.

the mental model to hold기억할 그림 Netflix did not write a new inference engine. It assembled vLLM (the model-runner) and NVIDIA Triton (the model server) and did the integration work: packaging, APIs, deployment, monitoring, and one deep customization. Netflix는 새 추론 엔진을 만들지 않았다. vLLM(모델 실행기)과 NVIDIA Triton(모델 서버)을 조립하고 패키징·API·배포·모니터링, 그리고 깊은 커스터마이징 하나를 직접 했다.

2The architecture, one box at a time아키텍처, 상자 하나씩

The full path from "a caller wants an answer" to "a GPU runs the model," top to bottom. "호출자가 답을 원한다"에서 "GPU가 모델을 돌린다"까지의 경로를 위에서 아래로 그렸다.

Fig 1 · Two front doors fold into one JVM serving system; big models go to MSS → Triton → vLLM. Redrawn from the Netflix TechBlog "Serving Architecture Overview" (Fig 1).그림 1 · 두 정문이 하나의 JVM 서빙 시스템으로 모이고, 큰 모델은 MSS → Triton → vLLM으로 간다. Netflix TechBlog "Serving Architecture Overview"(Fig 1) 재구성.

Box by box상자별로

  • Two front doors. Existing recommendation/ranking apps call inference over gRPC through the JVM system. Newer LLM apps can also go directly over HTTP with the OpenAI-compatible API.두 정문. 기존 추천/랭킹 앱은 JVM 시스템을 거쳐 gRPC로 추론을 부른다. 새 LLM 앱은 OpenAI 호환 API로 HTTP 직접 호출도 할 수 있다.
  • The JVM serving system. Netflix's Java serving layer handles everything around the model: A/B variant choice, feature fetching, pre/post-processing, logging. Small CPU models run right here in-process, with no network hop. GPU models get forwarded.JVM 서빙 시스템. Netflix의 Java 서빙 층으로, A/B 변형 선택·피처 조회·전후처리·로깅처럼 모델 주변 일을 맡는다. CPU용 작은 모델은 같은 프로세스에서 바로 돈다. 네트워크 홉이 없다. GPU가 필요한 모델은 다음 단계로 넘긴다.
  • MSS (Model Scoring Service). The shared GPU backend serving XGBoost, TensorFlow, PyTorch and LLMs behind one interface. To MSS, an LLM is just another model.MSS (Model Scoring Service). XGBoost·TensorFlow·PyTorch·LLM을 하나의 인터페이스로 서빙하는 공유 GPU 백엔드다. MSS에게 LLM은 그냥 모델 하나다.
  • Java control plane. Deploys models, tracks versions, health-checks, autoscales GPUs and rolls out across regions. Authors just package the model and set config; the control plane provisions GPUs, configures Triton and does zero-downtime upgrades.Java 컨트롤 플레인. 배포·버전 추적·헬스체크·GPU 오토스케일·멀티 리전 롤아웃을 맡는다. 작성자는 모델을 패키징하고 설정만 하면 되고, GPU 할당·Triton 구성·무중단 업그레이드는 컨트롤 플레인이 한다.
  • Triton, then vLLM. Triton loads the model, batches requests and schedules them on the GPU; underneath, the vLLM engine generates the tokens.Triton, 그다음 vLLM. Triton이 모델 로드·배칭·GPU 스케줄링을 하고, 그 아래에서 vLLM 엔진이 실제 토큰을 생성한다.

3The four big decisions — engine, packaging, API, rollout네 가지 큰 결정: 엔진·패키징·API·배포

Netflix presents four decisions "in dependency order, since each one constrains the next": engine → packaging → API → rollout. Netflix는 네 결정을 "각각이 다음을 제약하므로 의존 순서대로" 제시한다. 엔진 → 패키징 → API → 배포 순이다.

3.1 — Engine: they switched from TensorRT-LLM to vLLM (for operational reasons, not raw speed)3.1 엔진: TensorRT-LLM에서 vLLM으로 (속도가 아니라 운영상 이유로)

The platform started on TensorRT-LLM (fast, already integrated with Triton). By summer 2025 open-source engines had "largely closed the performance gap," and workloads had grown beyond chat to embeddings, prefill-only inference (ranking/retrieval) and custom models with per-step logic. A re-benchmark picked vLLM on operational fit: 플랫폼은 Triton과 이미 통합된 빠른 엔진 TensorRT-LLM에서 시작했다. 2025년 여름이 되자 오픈소스 엔진이 "성능 격차를 거의 좁혔고", 워크로드도 챗을 넘어 임베딩, 프리필 전용 추론(랭킹/검색), 스텝별 로직이 있는 커스텀 모델로 넓어졌다. 다시 벤치마크한 끝에 운영 적합성을 기준으로 vLLM을 골랐다.

  • No compile step for custom model shapes. Compiled engines like TensorRT-LLM first turn a model into optimized GPU code through a multi-step pipeline, which slows iteration on unusual models. vLLM just loads them.커스텀 모델도 컴파일 없이 로드. TensorRT-LLM 같은 컴파일형 엔진은 다단계 파이프라인으로 모델을 GPU 코드로 바꿔야 해서 특이한 모델을 빨리 고쳐 보기 어렵다. vLLM은 바로 로드한다.
  • Extensibility hooks for custom decoding, which the §5 work depends on.커스텀 디코딩용 확장 훅. §5 작업이 이 기능에 기대고 있다.
  • Debuggability & familiarity. Failures are easier to inspect, and many researchers already used vLLM.디버깅 용이성 & 친숙함. 실패 원인을 들여다보기 쉽고, 연구자 다수가 이미 vLLM을 써서 프로덕션 이전 비용이 적다.
the lesson교훈 "Fastest on a benchmark" and "best for a real team" are different questions. In production, iteration speed, extensibility and debuggability save more time than a few percent of raw throughput. "벤치마크 1등"과 "실제 팀에 맞는 엔진"은 다른 질문이다. 프로덕션에서는 반복 속도·확장성·디버깅 용이성이 처리량 몇 %보다 더 많은 시간을 아낀다.

3.2 — Packaging: let the model and the frontend evolve independently3.2 패키징: 모델과 프런트엔드가 따로 진화하게

Triton offers two ways to bundle a model, and they differ in coupling: how tightly the bundle is tied to the frontend. Triton은 모델을 묶는 방식 두 가지를 제공한다. 둘의 차이는 묶음이 프런트엔드에 얼마나 단단히 묶이는지, 즉 결합도(coupling)다.

Way방식What the author does작성자가 하는 일Coupling결합도
Python backendHand-writes the input/output "tensor specs," frozen into the bundle.입출력 "텐서 스펙"을 손으로 적어 묶음에 고정한다.Tight: every frontend upgrade touching I/O needs a coordinated packaging change, or requests fail.단단함: I/O를 건드리는 프런트엔드 업그레이드마다 패키징도 같이 바꿔야 하고, 아니면 요청이 실패한다.
vLLM backendWrites a small JSON config pointing at weights + tokenizer; Triton infers I/O shapes at deploy time.가중치 + 토크나이저를 가리키는 작은 JSON 설정만 쓴다. I/O 형태는 Triton이 배포 때 알아낸다.Loose: model and frontend evolve independently. The "architecturally correct" default.느슨함: 모델과 프런트엔드가 따로 바뀐다. "구조적으로 올바른" 기본값이다.

The vLLM backend is the default, but production bit them twice: 기본값은 vLLM 백엔드지만, 프로덕션에서 두 번 문제가 났다.

  • Version mismatch. Triton's vLLM backend is built against a specific vLLM version. Triton 25.09 tried to import vllm.engine.metrics, removed in vLLM 0.11.2, so the backend failed to load entirely. Fix: pin compatible versions in the service image and stop authors from overriding the vLLM version.버전 불일치. Triton의 vLLM 백엔드는 특정 vLLM 버전에 맞춰 빌드된다. Triton 25.09가 vLLM 0.11.2에서 제거된 vllm.engine.metrics를 임포트하려다 백엔드가 통째로 로드에 실패했다. 서비스 이미지에서 호환 버전을 고정하고, 작성자가 vLLM 버전을 덮어쓰지 못하게 막아 해결했다.
  • Custom logic needs the escape hatch. The vLLM backend only handles standard HuggingFace-style models. Custom preprocessing, tokenization or multi-model pipelines fall back to the Python backend's full-control execute(), and some models will keep needing it.커스텀 로직엔 탈출구가 필요하다. vLLM 백엔드는 표준 HuggingFace식 모델만 다룬다. 커스텀 전처리·토크나이제이션·멀티모델 파이프라인은 Python 백엔드의 execute()로 돌아가야 하고, 일부 모델은 앞으로도 그렇다.

3.3 — API: "an LLM is not a special snowflake"3.3 API: "LLM은 특별한 눈송이가 아니다"

"A key design goal of our system was that LLM models should NOT be special snowflakes. Every model — XGBoost ensemble or large-scale LLMs — is scored via the same gRPC call, so we reuse the same client libraries, health checking, and deployment pipelines."

— Netflix TechBlog · netflixtechblog.com

No separate LLM pipeline: every model is called the same way, so existing client libraries, health checks and deployment are reused. Since the LLM world standardized on the OpenAI-compatible API, Netflix exposes that too, alongside gRPC. Moving from a hosted model to a self-hosted fine-tuned one is then "nearly seamless. Same API, minimal code changes." LLM 전용 파이프라인을 따로 만들지 않았다. 모든 모델을 같은 방식으로 부르니 기존 클라이언트 라이브러리·헬스체크·배포를 그대로 쓴다. 다만 LLM 생태계는 OpenAI 호환 API로 표준화됐기 때문에 Netflix는 gRPC와 함께 이것도 연다. 덕분에 호스팅 모델에서 자체 호스팅 파인튜닝 모델로 옮기는 일이 "거의 매끄럽다. 같은 API, 최소한의 코드 변경."

the bug this caused — a silent one이 결정이 부른 조용한 버그 NVIDIA's ready-made OpenAI-compatible frontend silently dropped the response_format field ("give me JSON") before it reached vLLM. Callers asking for JSON got no guided-decoding constraint and could receive malformed JSON with no error reported. Netflix pulled the frontend into its own tree (git subtree) and patched it to translate response_format into vLLM's guided-decoding parameters, the feature §5 covers. NVIDIA의 기성 OpenAI 호환 프런트엔드가 response_format 필드("JSON으로 줘")를 vLLM에 넘기기 전에 조용히 버렸다. JSON을 요청해도 가이드 디코딩 제약이 전혀 걸리지 않아, 에러 없이 깨진 JSON이 나올 수 있었다. Netflix는 프런트엔드를 자체 트리로 가져와(git subtree) response_format을 vLLM 가이드 디코딩 파라미터로 바꾸도록 패치했다. §5에서 다루는 바로 그 기능이다.

3.4 — Rollout: two ways to ship a new version without dropping requests3.4 배포: 요청을 흘리지 않고 새 버전을 내보내는 두 방법

GPU deployments are slow to start, and a new version can change its input/output shapes, so upgrades need coordination. Two strategies (similar to "blue-green deployment"): GPU 배포는 띄우는 데 오래 걸리고 새 버전은 입출력 형태가 바뀔 수 있어서, 업그레이드에는 조율이 필요하다. 전략은 두 가지다("blue-green 배포"와 비슷하다).

Strategy전략How방법When to use언제 쓰나
Red-BlackBring the new version up beside the old; once healthy, shift traffic in phases; auto-rollback if any step fails.새 버전을 옛 버전 옆에 띄우고, 정상이 되면 트래픽을 단계적으로 옮긴다. 한 단계라도 실패하면 자동 롤백한다.Cheaper default, when the I/O interface is stable.더 싼 기본값. 입출력 인터페이스가 안정적일 때 쓴다.
VersionedAn independent deployment per (model, version) pair; many versions serve at once. Callers switch only when the new one is ready; the old keeps serving legacy traffic.(모델, 버전) 쌍마다 독립 배포를 두고 여러 버전을 동시에 서빙한다. 호출자는 새 버전이 준비된 뒤에 전환하고, 옛 버전은 레거시 트래픽을 계속 받는다.When a version changes its I/O shape; Red-Black would route old requests to the new model and fail them. Netflix's advice: bake variable settings (like tensor shapes) into the model so it stays version-agnostic and can use Red-Black; save Versioned for rare unavoidable breaking changes. Netflix의 조언은 텐서 형태 같은 가변 설정을 모델 안에 넣어 버전과 무관하게 만들고 Red-Black을 쓰라는 것이다. Versioned는 피할 수 없는 드문 breaking change에만 쓴다.

4Things that only broke in production프로덕션에서만 터진 것들

Two small operational details that design didn't anticipate. 설계 단계에서 예상하지 못한 작은 운영 문제 두 가지다.

Cold starts: cache the model on a fast file system, not object storage콜드 스타트: 오브젝트 스토리지 말고 빠른 파일 시스템에 모델 캐시

A cold start is the time from "spin up a server" to "ready to serve," and for LLMs it is mostly downloading tens of gigabytes of weights. Pulling them from S3 (object storage: durable, not fast for bulk reads) or Hugging Face at boot took longer than the scheduler would wait. Fix: when a model is announced, pre-load ("materialize") it onto Amazon FSx, a high-performance shared file system, so new servers read from fast disk. 콜드 스타트는 서버를 띄운 뒤 서빙 준비가 끝날 때까지의 시간이다. LLM에서는 대부분이 수십 GB 가중치 다운로드다. 부팅 때 S3(오브젝트 스토리지: 내구성은 좋지만 대량 읽기는 느리다)나 Hugging Face에서 받으면 스케줄러가 기다려 주는 시간을 넘겼다. 그래서 모델이 announce될 때 고성능 공유 파일 시스템인 Amazon FSx에 미리 올려 두고("materialize"), 새 서버는 빠른 디스크에서 읽게 했다.

The rest of boot: unpack the model, install custom vLLM plugins, clean the metrics scratch directory, and keep the gRPC port closed until the engine is ready, so no request arrives too early. 나머지 부팅 과정은 모델 압축 해제, 커스텀 vLLM 플러그인 설치, 메트릭 스크래치 디렉터리 정리다. 엔진이 준비될 때까지 gRPC 포트를 닫아 두어 요청이 먼저 들어오지 않게 한다.

Metrics: two systems that couldn't see each other메트릭: 서로를 못 보는 두 시스템

Metrics are numbers a system emits about itself for dashboards and alerts; Prometheus collects them. vLLM and Triton each report metrics their own way, and Triton's built-in bridge exposed only 9 of 40+ vLLM metrics, missing token throughput, KV cache utilization and prefix-cache hit rate. 메트릭은 시스템이 대시보드·알림용으로 내보내는 숫자이고, Prometheus가 이를 수집한다. vLLM과 Triton은 메트릭을 각자 방식으로 내보내는데, Triton 내장 브리지는 40여 개 vLLM 메트릭 중 9개만 노출했다. 토큰 처리량, KV 캐시 사용률, 프리픽스 캐시 히트율처럼 LLM에 정작 중요한 값이 빠졌다.

Fix: a small HTTP proxy fetches Triton's metrics, reads vLLM's from disk, and merges both into one /metrics endpoint, so existing dashboards and alerts keep working. 해결책은 작은 HTTP 프록시다. Triton 메트릭을 가져오고 vLLM 메트릭은 디스크에서 읽어 하나의 /metrics 엔드포인트로 합친다. 기존 대시보드와 알림은 그대로 동작한다.

5The headline problem — making JSON valid "by construction" at scale핵심 문제: 대규모에서 JSON을 "애초에 올바르게" 만들기

Three small ideas first. 먼저 작은 개념 세 가지다.

logits로짓 (logits)

The raw score the model gives every possible next token at each step.매 단계 모델이 모든 다음 토큰 후보에 매기는 원시 점수다.

logits processor로짓 프로세서

Code that edits the logits before picking. Setting illegal tokens to minus-infinity makes them unpickable.토큰을 고르기 전에 로짓을 고치는 코드다. 규칙 위반 토큰을 마이너스 무한대로 만들면 절대 뽑히지 않는다.

state machine상태 기계

Tracks "where are we in the JSON?" to decide which tokens are legal next; advances per token."지금 JSON의 어디쯤인가"를 기억해 다음에 허용할 토큰을 정한다. 토큰마다 한 칸씩 나아간다.

Instead of checking output afterward and paying to re-run it, Netflix pushes the rules inside the generation loop: Netflix는 출력을 나중에 검사하고 틀리면 다시 돌리는 대신, 규칙을 생성 루프 안으로 넣었다.

"Rather than applying business logic after inference — paying for invalid generations, then retrying or repairing — we push constraints inside the decode loop, so the model generates outputs that are compliant by construction."

— Netflix TechBlog, "Constrained Decoding at Scale" · netflixtechblog.com

Why the first version didn't scale — a CPU bottleneck hiding behind the GPU첫 버전이 확장 안 된 이유: GPU 뒤에 숨은 CPU 병목

The first implementation was pure Python on vLLM V0. It worked for one request and fell over under real concurrency: 첫 구현은 vLLM V0 위의 순수 Python이었다. 요청 하나일 때는 잘 돌았지만 실제 동시성에서는 무너졌다.

"…constraint logic runs sequentially for each request — sequentially because the GIL prevents Python from parallelizing the per-request work. CPU time in logit processing therefore grows linearly with batch size, hitting tail latencies. End-to-end latency becomes CPU-bound even though the model's forward pass is batched efficiently on GPU."

— Netflix TechBlog · netflixtechblog.com

The GPU computes logits for the whole batch at once, but the mask code then ran one request at a time on the CPU because of the GIL. With 50 requests in a batch, that is 50 mask computations back-to-back at every token step, and the CPU becomes the bottleneck. A single-request benchmark never shows this; it only appears under production concurrency. GPU는 배치 전체의 로짓을 한 번에 계산하지만, 그 뒤 마스크 계산은 GIL 때문에 CPU에서 한 요청씩 돌았다. 배치에 요청이 50개면 토큰 한 단계마다 마스크 계산 50번을 줄줄이 해야 하고, CPU가 병목이 된다. 단일 요청 벤치마크로는 절대 보이지 않고 프로덕션 동시성에서만 드러난다.

Fig 2 · V0 serial per-request masks vs V1 batched C++ masks. Schematic: the blog shows this shape (Figs 2–3) but publishes no axis numbers.그림 2 · V0의 요청별 직렬 마스크 vs V1의 배치 C++ 마스크. 개략도: 블로그는 이 형태(Fig 2–3)만 보이고 축 수치는 공개하지 않는다.

The fix — vLLM V1 moved masking to batch level해결: vLLM V1이 마스킹을 배치 레벨로 옮김

vLLM V1 (Netflix migrated in Q4 2025) processes logits at the batch level. Two changes did it: vLLM V1(Netflix는 2025 Q4에 이전)은 로짓을 요청별이 아니라 배치 레벨에서 처리한다. 바뀐 점은 두 가지다.

  • Compute all masks together on batch-level data structures, not in a per-request loop.모든 마스크를 함께 계산한다. 요청별 루프 대신 배치 레벨 자료구조 위에서 한꺼번에 만든다.
  • Move the hot path to C++. Multi-threaded C++ isn't bound by the GIL, so it uses many cores in parallel. (Their words: "reimplemented the hot path in C++ with multi-threading to step around the GIL.")핫 패스를 C++로 옮긴다. 멀티스레드 C++은 GIL에 묶이지 않아 여러 코어를 병렬로 쓴다. (원문: "reimplemented the hot path in C++ with multi-threading to step around the GIL.")

The cost: since requests constantly join and finish, the processor must track batch membership via update_state(batch_update), more bookkeeping than V0's per-request call. The result: logits-processing time stays flat as batch size grows. 대가는 API가 어려워진 것이다. 요청이 계속 들어오고 끝나므로, 프로세서가 update_state(batch_update)로 배치 구성을 직접 추적해야 한다. 그 결과 배치가 커져도 로짓 처리 시간이 평평하게 유지된다.

Operational hardening — two ways a stateful decoder breaks운영 견고화: 상태 있는 디코더가 깨지는 두 방식

  • Partial prefills. V1 reads long prompts in chunks over several steps ("chunked prefill"), but the batch-update signal couldn't say whether a request was fully or partially prefilled, so the state machine could advance too early. Fix: Netflix tracks prefill completeness itself.부분 프리필. V1은 긴 프롬프트를 여러 단계에 나눠 읽는다("chunked prefill"). 그런데 배치 업데이트 신호로는 프리필이 끝났는지 일부만 됐는지 알 수 없어, 상태 기계가 너무 일찍 나아갈 수 있었다. Netflix는 프리필 완료 여부를 직접 추적해 해결했다.
  • Preemption. When GPU memory runs short, vLLM can evict a request's KV cache and reschedule it later, possibly with a different token list. That breaks the assumption that generated text only grows. Fix: detect when token history shrinks, reset the state machine, and re-initialize from the new prompt.선점(preemption). GPU 메모리가 모자라면 vLLM은 요청의 KV 캐시를 축출했다가 나중에 다시 스케줄하는데, 이때 토큰 리스트가 달라질 수 있다. 생성 텍스트가 늘기만 한다는 가정이 깨진다. 토큰 히스토리가 줄어든 것을 감지하면 상태 기계를 리셋하고 새 프롬프트로 다시 초기화해 해결했다.
why this section is the whole point이 섹션이 요점인 이유 This is the payoff of choosing vLLM for its hooks (§3.1) and owning the stack (§1): a hosted API won't let you rewrite the decode loop in C++. The general lesson: a bottleneck can hide in the CPU glue around a fast GPU and only surface under concurrency. 확장 훅 때문에 vLLM을 고르고(§3.1) 스택을 직접 운영한(§1) 보상이다. 호스팅 API로는 디코드 루프를 C++로 다시 쓸 수 없다. 일반화하면, 병목은 빠른 GPU 주변의 CPU 접착 코드에 숨어 있다가 동시성에서만 드러날 수 있다.

6What's open-source vs. Netflix-only (why there's no code-walk)오픈소스 vs Netflix 전용 (왜 코드 분석이 없나)

Our deep dives usually link to exact lines of code. Not this one: Netflix's own code is proprietary. MSS, the Java control plane, the packaging workflow, the metrics proxy and the constrained-decoding processors have no public repository. This note is an architecture-and-lessons explainer. 딥다이브 노트는 보통 실제 코드 줄을 링크로 짚지만 이 노트는 그럴 수 없다. Netflix 자체 코드는 비공개다. MSS, Java 컨트롤 플레인, 패키징 워크플로, 메트릭 병합 프록시, 제약 디코딩 프로세서 모두 공개 저장소가 없다. 그래서 이 노트는 아키텍처와 교훈을 다룬다.

The building blocks are open-source, and the concepts here map onto their public docs/code: 대신 구성 블록은 오픈소스다. 더 파고들고 싶다면 아래 공개 문서와 코드를 보면 된다.

NVIDIA Triton

The model server. Its vLLM backend, Python backend and OpenAI-compatible frontend (the one Netflix git-subtreed and patched) are public.모델 서버. vLLM 백엔드, Python 백엔드, OpenAI 호환 프런트엔드(Netflix가 git-subtree로 가져와 패치한 것)가 공개돼 있다.

KServe / FastAPI

The HTTP/gRPC serving frontends and the Python web framework the OpenAI-compatible frontend runs on.HTTP/gRPC 서빙 프런트엔드와, OpenAI 호환 프런트엔드가 돌아가는 Python 웹 프레임워크다.

PyTorch, XGBoost, TensorFlowPyTorch, XGBoost, TensorFlow
