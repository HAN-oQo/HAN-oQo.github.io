NVIDIA Dynamo Snapshot — CRIU-based fast startup, 21× faster cold start DynamoJun 5

On Jun 5 NVIDIA released Dynamo Snapshot, which uses CRIU and cuda-checkpoint to freeze and restore single-GPU inference workers on Kubernetes instead of cold-starting them from scratch. A key trick is unmapping the KV cache before checkpoint (cuMemUnmap/cuMemRelease), shrinking the artifact for Qwen3-0.6B on a B200 from ~190 GiB down to ~6 GiB; in a PoC over 8 striped NVMe SSDs it cut gpt-oss-120b startup 21× to under 5s. For autoscaling and spot/preemptible fleets, sub-5s restores change the economics of scaling inference up and down.

6/5 NVIDIA가 Dynamo Snapshot을 공개했다 — CRIU와 cuda-checkpoint로 단일 GPU 추론 워커를 처음부터 콜드스타트하는 대신 동결·복원한다. 핵심 트릭은 체크포인트 전에 KV 캐시를 언맵(cuMemUnmap/cuMemRelease)해, B200의 Qwen3-0.6B 아티팩트를 ~190 GiB에서 ~6 GiB로 줄인 것 — 8개 스트라이프 NVMe SSD PoC에서 gpt-oss-120b 시작을 21× 단축해 5초 미만으로 만들었다. 오토스케일링·스팟/선점형 플릿에서 5초 미만 복원은 추론을 켜고 끄는 경제성을 바꾼다.

Problem문제 정의In long-context inference the KV cache grows linearly with sequence length, so attending to all of it is infeasible. Sparse attention helps, but it still pays an O(T²)-style cost just to select which KV blocks each query should attend to — and that selection sits on the critical path of every layer, so the GPU stalls waiting for "which blocks?" before it can compute "attend to them." On million-token prompts this selection-plus-fetch overhead, not the attention math itself, becomes the real bottleneck.롱컨텍스트 추론에서 KV 캐시는 시퀀스 길이에 비례해 선형으로 커져 전체를 어텐션하기가 비현실적이다. 희소 어텐션이 돕긴 하지만, 각 쿼리가 어느 KV 블록에 주목할지 선택하는 데만 여전히 O(T²)급 비용이 들고, 이 선택이 매 레이어의 임계 경로에 놓여 GPU가 "어느 블록?"을 기다린 뒤에야 "그 블록을 어텐션"할 수 있다. 백만 토큰 프롬프트에서는 어텐션 연산 자체가 아니라 이 선택+페치 오버헤드가 진짜 병목이 된다.
Method방법SparDA decouples block selection from attention computation. A lightweight "Forecast" projection runs during layer L and predicts which KV blocks layer L+1 will need, before L finishes. With that prediction in hand the system can prefetch the required blocks from CPU/host memory to the GPU while layer L is still computing, so by the time L+1 starts, its KV is already resident. Selection thus stops being a serial stall and becomes work that overlaps with useful compute.SparDA는 블록 선택과 어텐션 연산을 분리한다. 가벼운 "Forecast" 프로젝션이 레이어 L 처리 중에 돌면서, L이 끝나기 전에 다음 레이어 L+1이 필요로 할 KV 블록을 미리 예측한다. 이 예측이 있으면 레이어 L이 아직 연산 중인 동안 필요한 블록을 CPU/호스트 메모리에서 GPU로 프리페치할 수 있어, L+1이 시작될 때 KV가 이미 상주해 있다. 선택이 직렬 멈춤이 아니라 유용한 연산과 겹치는 작업이 되는 것이다.
Results결과By hiding both selection and CPU→GPU transfer latency behind layer compute, SparDA shrinks the long-context attention bottleneck and improves decode throughput, while preserving the accuracy of dense and prior sparse-attention baselines (the same blocks get attended to — they're just fetched earlier).선택과 CPU→GPU 전송 지연을 모두 레이어 연산 뒤로 숨겨, 롱컨텍스트 어텐션 병목을 줄이고 디코드 처리량을 높이면서, 밀집·기존 희소 어텐션 베이스라인의 정확도를 유지한다(결국 같은 블록을 어텐션하되, 더 일찍 가져올 뿐이다).

AsymCache — Multi-Segment Attention KV managementKV cache2606.02964
AsymCache / Multi-Segment Attention (arXiv 2606.02964) ↗AsymCache / Multi-Segment Attention (arXiv 2606.02964) ↗
Problem문제 정의In real serving, the context a request reuses is rarely one clean contiguous block: some token ranges are still cached (a hit), while others were evicted and must be recomputed. Standard cache policies treat eviction uniformly and ignore a key asymmetry — the cost of recomputing a dropped range depends on where it sits in the sequence (early tokens are cheaper to redo than late ones).
