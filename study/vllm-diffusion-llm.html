Diffusion LLMs in vLLM — how they differ, forward count, KV cache, code flow vLLM의 Diffusion LLM — 트랜스포머와 뭐가 다른가, forward 횟수, KV cache, 코드 흐름

A diffusion LLM generates text by starting from a fully-masked answer and un-masking many tokens in parallel over a few denoising steps, instead of one token at a time left-to-right. The architecture is the same Transformer backbone — the differences are bidirectional attention + a masked-denoising objective. That bidirectionality is exactly what breaks the normal KV cache. This note: how it differs, how many forwards make N tokens, what vLLM ships today (DiffusionGemma), how it manages the KV cache, and the code flow with permalinks. Diffusion LLM은 완전히 마스킹된 답에서 시작해 몇 번의 denoising 스텝 동안 여러 토큰을 병렬로 un-mask해서 문장을 만든다 — 좌→우 한 토큰씩이 아니라. 아키텍처는 동일한 트랜스포머 백본이고, 차이는 양방향(bidirectional) 어텐션 + 마스크 denoising 목적함수다. 바로 그 양방향성이 일반 KV cache를 깨뜨린다. 이 노트: 무엇이 다른가, N개 토큰에 forward 몇 번인가, vLLM이 현재 무엇을 지원하는가(DiffusionGemma), KV cache를 어떻게 관리하는가, 코드 흐름(permalink).

one-line summary한 줄 요약 Same Transformer, two changes: bidirectional attention + masked-denoising objective (Dream is even initialized from AR Qwen). Generation = T denoising steps over the whole sequence (T can be ≪N for speed, up to N for AR-like quality), not N sequential steps. The bidirectional attention breaks the standard KV cache, so systems move to block diffusion: finalize a block, cache its KV like a causal prefix, denoise the next block. vLLM's one native dLLM is DiffusionGemma — it cleverly reuses the speculative-decoding path (the "canvas" = draft tokens) and runs the backbone in two modes: a causal encoder that writes KV and a bidirectional decoder that reads KV but doesn't write. 같은 트랜스포머, 두 가지 변경: 양방향 어텐션 + 마스크 denoising 목적함수(Dream은 AR Qwen에서 초기화까지 함). 생성 = 전체 시퀀스에 대한 T번의 denoising 스텝(속도용 T≪N, AR급 품질엔 T=N까지), N번 순차가 아님. 양방향 어텐션이 표준 KV cache를 깨뜨려서 시스템들은 block diffusion으로 간다: 한 블록을 확정하고 그 KV를 causal prefix처럼 캐시한 뒤 다음 블록을 denoise. vLLM의 유일한 네이티브 dLLM은 DiffusionGemma — speculative-decoding 경로를 영리하게 재사용("canvas"=draft 토큰)하고, 백본을 두 모드로 돌린다: KV를 쓰는 causal encoder와 KV를 읽되 안 쓰는 bidirectional decoder.

1What a diffusion LLM is — and is the architecture the same?Diffusion LLM이란 — 아키텍처는 동일한가?

An AR Transformer factorizes text left-to-right: each token conditions on all previous tokens, decoded one at a time. A masked diffusion LLM defines a forward process that progressively masks tokens, and learns the reverse: start from a fully-masked response and iteratively un-mask, predicting all masked positions simultaneously at each step [LLaDA] [Dream]. AR 트랜스포머는 문장을 좌→우로 분해한다 — 각 토큰이 이전 토큰들에 조건부, 한 번에 하나씩 디코딩. 마스크 diffusion LLM은 토큰을 점진적으로 마스킹하는 forward 과정을 정의하고 그 역과정을 학습한다: 완전 마스킹된 답에서 시작해 반복적으로 un-mask하며, 각 스텝에서 마스킹된 모든 위치를 동시에 예측한다 [LLaDA] [Dream].

The architecture is the same Transformer — with two changes아키텍처는 같은 트랜스포머 — 두 가지만 다름

This is the crux. dLLMs are not a new architecture; they're a Transformer with (a) the causal mask removed and (b) a different training objective: 이게 핵심이다. dLLM은 새 아키텍처가 아니라, (a) causal mask를 없애고 (b) 학습 목적함수를 바꾼 트랜스포머다:

"LLaDA does not use a causal mask, as its formulation allows it to see the entire input for predictions."

— LLaDA §2.2 · arXiv:2502.09992

The strongest evidence the backbone is shared: Dream 7B is initialized from Qwen2.5 AR weights — the team found AR-initialization "more effective than training the diffusion language model from scratch" [Dream blog]. You can literally take an autoregressive model and adapt it into a diffusion one (also shown by DiffuLLaMA, ICLR 2025 [repo]). The upside of bidirectionality: dLLMs can "consider multiple conditioning directions," which breaks the AR "reversal curse" [LLaDA §3.1]. The downside: removing the causal mask is exactly what breaks KV caching (§3). 백본이 공유된다는 가장 강한 증거: Dream 7B는 Qwen2.5 AR 가중치에서 초기화된다 — 팀은 AR 초기화가 "diffusion LM을 처음부터 학습하는 것보다 효과적"임을 발견 [Dream blog]. 말 그대로 자기회귀 모델을 가져와 diffusion으로 적응시킬 수 있다(DiffuLLaMA, ICLR 2025도 입증 [repo]). 양방향성의 장점: dLLM은 "여러 조건 방향을 고려"할 수 있어 AR의 "reversal curse"를 깬다 [LLaDA §3.1]. 단점: causal mask 제거가 바로 KV caching을 깨뜨린다(§3).

2How many forward passes to make N tokens?N개 토큰에 forward 몇 번?

Forwards for N tokensN토큰당 forwardCost per forwardforward당 비용
ARAR≈ N (1 committed token / forward)(forward당 1토큰 확정)cheap — KV cache means you process only the new token쌈 — KV cache로 새 토큰만 처리
DiffusionDiffusion= T denoising steps (T can be ≪ N up to T = N)(T는 ≪N부터 T=N까지)expensive — each step is a full forward over the whole sequence비쌈 — 각 스텝이 시퀀스 전체 forward

So diffusion decouples token count from step count. Fewer steps → more tokens committed per step → faster but lower quality, because parallel un-masking assumes the tokens are conditionally independent (they aren't). LLaDA states the tradeoff bluntly: 즉 diffusion은 토큰 수와 스텝 수를 분리한다. 스텝이 적을수록 → 스텝당 더 많은 토큰 확정 → 빠르지만 품질↓ — 병렬 un-mask가 토큰 간 조건부 독립을 가정하기 때문(실제론 아님). LLaDA는 이 트레이드오프를 단도직입적으로 말한다:

"LLaDA achieves optimal performance when the number of sampling steps equals the response length … reducing the number of sampling steps leads to a decrease in performance."

— LLaDA repo FAQ · github.com/ML-GSAI/LLaDA

The fix for the quality cliff is confidence-aware parallel decoding: only commit tokens above a confidence threshold each step, so the step count adapts to difficulty. Fast-dLLM reports "up to 27.6× throughput improvement with minimal accuracy loss" this way [Fast-dLLM]. The other axis is block / semi-AR diffusion: generate a block of L tokens with K steps, finalize it, move on — interpolating between AR (block=1) and full diffusion (block=full length) [Block Diffusion / BD3-LM]. So a practical forward count is (N / L blocks) × (K steps per block). 품질 절벽의 해법은 confidence-aware 병렬 디코딩: 스텝마다 확신 임계값을 넘는 토큰만 확정 → 스텝 수가 난이도에 적응. Fast-dLLM은 이 방식으로 "최대 27.6× 처리량, 정확도 손실 최소"를 보고 [Fast-dLLM]. 다른 축은 block / semi-AR diffusion: L개 블록을 K 스텝으로 생성·확정 후 다음 — AR(블록=1)과 full diffusion(블록=전체) 사이를 보간 [Block Diffusion / BD3-LM]. 따라서 실전 forward 수는 (N / L 블록) × (블록당 K 스텝).

3KV cache — why it's hard, and how it's doneKV cache — 왜 어렵고 어떻게 하나

AR KV caching is exact because the causal mask guarantees a token's K/V never change once computed. dLLMs break that on two counts: AR의 KV caching은 정확하다 — causal mask가 한 토큰의 K/V는 한 번 계산되면 변하지 않음을 보장하기 때문. dLLM은 이를 두 가지로 깬다:

  1. Bidirectional attention → no causal prefix to cache. "Traditional ARM acceleration techniques, such as Key-Value caching, are incompatible with dLLMs due to their bidirectional attention mechanism" [dLLM-Cache].양방향 어텐션 → 캐시할 causal prefix가 없음. "KV caching 같은 전통적 ARM 가속 기법은 양방향 어텐션 때문에 dLLM과 호환되지 않는다" [dLLM-Cache].
  2. Tokens at every position change across steps → cached K/V go stale. Caching has to become approximate or delayed [dKV-Cache].매 스텝 모든 위치의 토큰이 바뀜 → 캐시된 K/V가 오래됨. 캐싱이 근사 또는 지연 방식이 되어야 함 [dKV-Cache].

Two families of fix, and it's worth keeping them distinct: 두 갈래의 해법이 있고, 구분해 두는 게 좋다:

Approach방식Exact?정확?Idea아이디어
Block diffusion (BD3-LM)exact (between blocks)정확 (블록 간)finalized blocks form a causal prefix → cache their KV exactly, like AR. [BD3-LM]확정된 블록이 causal prefix를 이룸 → 그 KV를 AR처럼 정확히 캐시. [BD3-LM]
Fast-dLLM / dLLM-Cache / dKV-Cacheapproximate근사K/V drift slowly between adjacent steps → reuse them anyway ("adjacent steps … highly similar" [Fast-dLLM]).인접 스텝 간 K/V가 느리게 변함 → 그냥 재사용("인접 스텝 … 매우 유사" [Fast-dLLM]).

This is why production systems converge on block diffusion: it's the version where a normal prefix KV cache (and vLLM's automatic prefix caching) works again. vLLM's DiffusionGemma takes exactly this route — see §4. 그래서 프로덕션 시스템들이 block diffusion으로 수렴한다 — 일반 prefix KV cache(그리고 vLLM의 automatic prefix caching)가 다시 작동하는 버전이기 때문. vLLM의 DiffusionGemma가 정확히 이 길을 택한다 — §4 참고.

4What vLLM ships — DiffusionGemma, and how it's optimizedvLLM이 지원하는 것 — DiffusionGemma와 최적화

Mainline vLLM natively supports exactly one diffusion model today: DiffusionGemma (Google's dLLM on the Gemma backbone), landed in PR #45163 (merged 2026-06-12) and announced as "the first dLLM natively supported in vLLM" [PR #45163]. LLaDA / Dream are not in mainline (there's a separate, still-mock dllm-plugin + RFC #36155). The design is deliberately minimal — it reuses existing machinery rather than adding diffusion-specific core types: 메인라인 vLLM은 현재 정확히 하나의 diffusion 모델을 네이티브 지원한다: DiffusionGemma(Gemma 백본의 Google dLLM), PR #45163(2026-06-12 병합)로 안착, "vLLM 최초의 네이티브 dLLM"으로 발표 [PR #45163]. LLaDA/Dream은 메인라인에 없음(별도의, 아직 mock인 dllm-plugin + RFC #36155). 설계는 의도적으로 미니멀 — diffusion 전용 코어 타입을 추가하지 않고 기존 장치를 재사용한다:

① Reuse the spec-decode path① spec-decode 경로 재사용

The denoising "canvas" is delivered through vLLM's speculative-decoding draft-token path — draft tokens = the canvas. No new request type; metrics are reinterpreted as denoising-step metrics.denoising "canvas"를 vLLM의 speculative-decoding draft-token 경로로 전달 — draft 토큰 = canvas. 새 요청 타입 없음; 지표는 denoising-step 지표로 재해석.

② Block-based → prefix caching works② 블록 기반 → prefix caching 작동

It's block diffusion (canvas = a block), so "vLLM's automatic prefix caching works out of the box" [blog].block diffusion이라(canvas=블록) "vLLM의 automatic prefix caching이 그대로 작동" [블로그].

③ Dual-mode backbone (one set of weights)③ 이중 모드 백본(가중치 한 벌)

Same Gemma layers run as a causal encoder that writes KV (prefill/commit) or a bidirectional decoder that reads KV (denoise) — a per-request causal flag (dynamic_causal) lets one batch mix both.같은 Gemma 레이어가 KV를 쓰는 causal encoder(prefill/commit) 또는 KV를 읽는 bidirectional decoder(denoise)로 — 요청별 causal 플래그(dynamic_causal)로 한 배치에 둘 혼합.

④ Entropy-bound sampler④ entropy-bound 샘플러

A custom sampler accepts confident positions and re-noises the rest each step; a block "commits" when it converges or hits max_denoising_steps (48).커스텀 샘플러가 스텝마다 확신 위치를 수락하고 나머지를 re-noise; 수렴하거나 max_denoising_steps(48)에 도달하면 블록 "commit".

Attention backend constraints follow from the per-request causal flag: FlashAttention is auto-upgraded to FA4 (or use TRITON_ATTN); FlashInfer is rejected; structured outputs are rejected (a parallel canvas isn't a left-to-right FSM); and max_num_seqs is capped to 8 (the fp32 [seqs, canvas, vocab] logits are memory-bound). 어텐션 백엔드 제약은 요청별 causal 플래그에서 따라온다: FlashAttention은 FA4로 자동 업그레이드(또는 TRITON_ATTN); FlashInfer 거부; structured output 거부(병렬 canvas는 좌→우 FSM이 아님); max_num_seqs는 8로 제한(fp32 [seqs, canvas, vocab] logits가 메모리 바운드).

On convergence a commit pass appends the block's KV.   8. Convergence → commit. A canvas converges when stable+confident, or at max_denoising_steps; next step flips to encoder mode to commit the block (causal, writes KV).수렴 → commit. 안정+확신 시, 또는 max_denoising_steps에서 canvas 수렴; 다음 스텝에 encoder 모드로 전환해 블록 commit(causal, KV write).
    diffusion_gemma.py#L614-L622

Forwards for N tokens, precisely: block-wise. Per block of canvas_length (256): ~1 causal prefill share + up to max_denoising_steps (48) bidirectional denoise forwards (early-stop on convergence) + 1 commit forward. So N tokens ≈ ceil(N / 256) blocks; each denoise forward refines the entire 256-token canvas in parallel. N토큰당 forward, 정확히: 블록 단위. canvas_length(256) 블록당: causal prefill ~1 + 최대 max_denoising_steps(48) bidirectional denoise forward(수렴 시 조기 종료) + commit 1. 따라서 N토큰 ≈ ceil(N / 256) 블록; 각 denoise forward가 256토큰 canvas 전체를 병렬로 다듬음.

6Status & how to run it구현 상태 & 실행법

Mainline: DiffusionGemma only, merged & not behind a feature flag (PR #45163, 2026-06-12; follow-ups #45468, #45643). Diffusion mode is implicit — triggered by the model's canvas_length config, there is no --diffusion flag. Plugin/RFC: general dLLMs (LLaDA 2.0) live in the out-of-tree dllm-plugin (RFC #36155), which currently ships a mock model and needs a vLLM fork — not production-ready. LLaDA/Dream are not in mainline. 메인라인: DiffusionGemma만, 병합됨·플래그 뒤 아님(PR #45163, 2026-06-12; 후속 #45468, #45643). diffusion 모드는 암묵적 — 모델의 canvas_length config로 트리거, --diffusion 플래그 없음. 플러그인/RFC: 일반 dLLM(LLaDA 2.0)은 out-of-tree dllm-plugin(RFC #36155)에 있고, 현재 mock 모델 + vLLM fork 필요 — 프로덕션 미준비. LLaDA/Dream은 메인라인에 없음.

# DiffusionGemma (mainline) — no --diffusion flag; canvas_length in the model config triggers it
vllm serve google/diffusiongemma-26B-A4B-it \
    --max-num-seqs 4 --attention-backend TRITON_ATTN \
    --diffusion-config '{"canvas_length": 256}' \
    --hf-overrides '{"diffusion_sampler":"entropy_bound","diffusion_entropy_bound":0.1}'
# constraints: max_num_seqs ≤ 8 · FA4 or TRITON_ATTN (FlashInfer rejected) ·
#              structured outputs rejected · entropy-bound sampler config required

Other systems for context: SGLang added day-0 LLaDA 2.0 (block-diffusion) support, citing "the inefficient utilization of the KV Cache" of full bidirectional diffusion as the reason the field is moving to block diffusion [LMSYS/SGLang blog]. Commercial dLLMs: Mercury (Inception, claims >1000 tok/s) and Gemini Diffusion (DiffusionGemma's closed sibling). 참고로 다른 시스템: SGLang은 LLaDA 2.0(block-diffusion) day-0 지원을 추가하며, full bidirectional diffusion의 "KV Cache 비효율"을 업계가 block diffusion으로 이동하는 이유로 지목 [LMSYS/SGLang 블로그]. 상용 dLLM: Mercury(Inception, >1000 tok/s 주장), Gemini Diffusion(DiffusionGemma의 비공개 형제).
