Not a fork of SGLang, and not an orchestrator either. A serving engine whose unit of scheduling is the stage, built because a speech model is not one transformer but three to seven pieces with opposite compute profiles. This note reads the code and the two official design blogs together, and ends with the one component you would actually copy when building a voice agent yourself. SGLang 의 포크도 아니고 오케스트레이터도 아닙니다. 스케줄링의 단위가 스테이지인 서빙 엔진이며, 음성 모델이 하나의 트랜스포머가 아니라 계산 성격이 정반대인 서너 개에서 일곱 개의 조각이기 때문에 그렇게 만들어졌습니다. 코드와 공식 설계 블로그 두 편을 함께 읽고, 마지막에는 voice agent 를 직접 만들 때 실제로 베껴 쓰게 될 한 부분까지 내려갑니다.

1What it actually is — and the 1.4% that misleads정체 — 오해를 부르는 1.4%

Open the repository looking for "how do I build a voice agent", and you land in models/streaming_cascade/: a declarative graph that wires an ASR server, an LLM server and a TTS server into a conversation. It reads like the whole product. It is not. It is 3,683 lines out of 271,850. "voice agent 를 어떻게 만드나"를 찾으며 저장소를 열면 models/streaming_cascade/ 에 닿습니다. ASR 서버와 LLM 서버와 TTS 서버를 선언적으로 엮어 대화를 만드는 그래프입니다. 이것이 제품 전체처럼 읽히지만 사실이 아닙니다. 271,850 줄 가운데 3,683 줄입니다.

Line counts measured at commit fc8da09 with find … -name '*.py' | xargs cat | wc -l.커밋 fc8da09 에서 find … -name '*.py' | xargs cat | wc -l 로 측정했습니다.

The other 98.6% is an inference engine in the same seat as vLLM or SGLang: it loads models onto GPUs and runs them. The distinction matters because the two halves answer different questions, and the repository lets you use either without the other. 나머지 98.6% 는 vLLM 이나 SGLang 과 같은 자리의 추론 엔진입니다. 모델을 GPU 에 올려 직접 돌립니다. 이 구분이 중요한 이유는 두 부분이 서로 다른 질문에 답하며, 저장소가 한쪽만 떼어 쓰는 것도 허용하기 때문입니다.

Its relationship to SGLang is a patch layer, not a forkSGLang 과의 관계는 포크가 아니라 패치 계층

The dependency is pinned (sglang==0.5.22 in pyproject.toml) and every upstream symbol re-enters through one door, sglang_omni/vendor/sglang/, where the handful of needed patches live with comments saying they can be deleted once upstream merges the equivalent change. The sharpest expression of this restraint is OmniScheduler: 4,224 lines, 126 methods, and it does not inherit from upstream Scheduler. It borrows unbound methods through __getattr__ and binds them to itself, keeping upstream's batch-selection logic without taking on inheritance coupling. 의존성이 pyproject.toml 에 sglang==0.5.22 로 고정되어 있고, 상류의 모든 심벌은 sglang_omni/vendor/sglang/ 이라는 단일 창구를 거칩니다. 그곳에 몇 개 되지 않는 패치가 "상류가 동등한 변경을 머지하면 삭제할 수 있다"는 주석과 함께 놓여 있습니다. 이 절제를 가장 날카롭게 보여 주는 것이 OmniScheduler 입니다. 4,224 줄에 126 개 메서드를 가지면서도 상류 Scheduler 를 상속하지 않습니다. __getattr__ 로 언바운드 메서드를 빌려 자기에게 바인딩함으로써, 상류의 배치 선택 로직은 그대로 쓰면서 상속으로 인한 결합은 지지 않습니다.

The division of labor역할 분담 SGLang owns autoregressive scheduling, KV cache and kernels — the inside of one stage. SGLang-Omni owns the pipeline topology, stage lifecycle, inter-stage transport, model-family integration and the OpenAI-compatible surface — everything between stages. Where a stage happens to be autoregressive, it is handed to SGLang. SGLang 은 자기회귀 스케줄링과 KV 캐시와 커널, 곧 스테이지 하나의 안쪽을 소유합니다. SGLang-Omni 는 파이프라인 토폴로지, 스테이지 수명주기, 단계 간 전송, 모델 패밀리 통합, OpenAI 호환 표면, 곧 스테이지 사이의 모든 것을 소유합니다. 어떤 스테이지가 마침 자기회귀라면 그 안쪽은 SGLang 에 넘깁니다.

2The stage graph: why one model becomes five스테이지 그래프: 모델 하나가 다섯이 되는 이유

An LLM serving engine can assume one kind of step: take tokens, produce a token. Everything downstream of that assumption — continuous batching, paged KV, prefix reuse — is built on its uniformity. A speech model breaks it. Qwen3-Omni is not a transformer you call; it is a graph you traverse, and the pieces disagree about almost everything. LLM 서빙 엔진은 한 종류의 단계만 가정하면 됩니다. 토큰을 받아 토큰을 내놓는 것입니다. 연속 배칭, 페이지 KV, 접두사 재사용 같은 하위 설계가 전부 그 균질함 위에 서 있습니다. 음성 모델은 그 가정을 깹니다. Qwen3-Omni 는 호출하는 트랜스포머가 아니라 통과하는 그래프이며, 조각들이 거의 모든 면에서 서로 다릅니다.

Redrawn from Figure 1 of the SPG topology blog. Stage names match examples/configs/qwen3_omni_colocated_h200.yaml. SPG 토폴로지 블로그의 Figure 1 을 다시 그렸습니다. 스테이지 이름은 examples/configs/qwen3_omni_colocated_h200.yaml 과 일치합니다.

Three properties that decide where a boundary goes경계를 어디 그을지 정하는 세 가지 성질

The blog names the measurable properties that make this graph a design problem rather than a drawing. The first one is the reason talker and code predictor sit inside one box above. 블로그는 이 그래프를 그림이 아니라 설계 문제로 만드는 측정 가능한 성질들을 지목합니다. 그중 첫 번째가 위 그림에서 talker 와 code predictor 가 한 상자 안에 들어간 이유입니다.

Synchronization granularity동기화 입도

One-shot handoff, bufferable stream, or per-step feedback. Per-step feedback means a stage boundary would cost a round trip every decode step — so those modules fuse into one stage.한 번의 인계, 버퍼링 가능한 스트림, 매 스텝 피드백 중 하나입니다. 매 스텝 피드백이라면 스테이지 경계마다 디코드 스텝마다 왕복 비용이 붙으므로, 그런 모듈들은 한 스테이지로 융합됩니다.

Bottleneck resource병목 자원

Device-bound or host-bound. preprocessing is host-side CPU work; replicating it costs almost nothing and relieves a real queue. Replicating thinker costs 77% of a GPU.장치 병목인지 호스트 병목인지입니다. preprocessing 은 호스트 측 CPU 작업이라 복제 비용이 거의 없으면서 실제 대기열을 덜어 줍니다. thinker 복제는 GPU 의 77% 를 또 씁니다.

Resident state size상주 상태 크기

Decides memory budgets and how many stages fit on one device. This is what the per-stage gpu_memory_fraction in the YAML is expressing.메모리 예산과 한 장치에 몇 개의 스테이지가 들어가는지를 결정합니다. YAML 의 스테이지별 gpu_memory_fraction 이 표현하는 것이 바로 이것입니다.

"The execution strategy affects serving performance as strongly as the efficiency of any individual stage, and that the model architecture should not dictate it."

Read it as a statement about the problem rather than about tuning: the language model is 77% of the budget and the vocoder is 1.4%, yet the vocoder is what the listener actually hears first and is the stage whose latency you notice. Giving them one scheduler and one memory pool would let the large one starve the small one. 이 숫자들을 튜닝 값이 아니라 문제에 대한 진술로 읽으시면 좋습니다. 언어 모델이 예산의 77% 이고 보코더가 1.4% 인데, 듣는 사람이 가장 먼저 듣는 것은 보코더의 출력이고 지연이 체감되는 지점도 보코더입니다. 둘에게 하나의 스케줄러와 하나의 메모리 풀을 주면, 큰 쪽이 작은 쪽을 굶길 수 있습니다.

3SPG topology: separating what runs from where it runsSPG 토폴로지: 무엇이 도는지와 어디서 도는지의 분리

Once stages exist, a second question appears that the model architecture cannot answer: which stages share an OS process, how many copies of each run, and which device each copy lands on. SGLang-Omni gives this its own name and its own notation. For a stage graph G = (S, E), a topology is 스테이지가 생기고 나면 모델 구조가 답할 수 없는 두 번째 질문이 따라옵니다. 어떤 스테이지들이 하나의 OS 프로세스를 공유하는지, 각각을 몇 벌 띄우는지, 각 벌이 어느 장치에 놓이는지입니다. SGLang-Omni 는 여기에 고유한 이름과 표기를 부여합니다. 스테이지 그래프 G = (S, E) 에 대하여 토폴로지는 다음과 같습니다.

SPG

T = (G, π, r, q, μ)

π assigns stages to logical process groups · r replica count per group · q tensor-parallel ranks per replica · μ places physical processes on hosts and devices. π 는 스테이지를 논리 프로세스 그룹에 배정하고, r 은 그룹별 복제 수, q 는 복제본당 텐서 병렬 랭크 수, μ 는 물리 프로세스를 호스트와 장치에 배치합니다.

Redrawn from Figure 3 of the SPG topology blog: the same seven stages, deployed with the two latency-critical ones replicated across GPUs 1 and 2. SPG 토폴로지 블로그의 Figure 3 을 다시 그렸습니다. 똑같은 일곱 스테이지를, 지연에 민감한 두 개만 GPU 1 과 2 에 복제해 배치한 모습입니다.

The payoff: one notation covers strategies usually named separately이 표기가 주는 것: 보통 따로 부르는 전략들이 하나의 표현으로

The reason to formalize this is that ideas normally discussed as distinct architectures turn out to be points in the same space. The blog lists them, and each is a different setting of π, r and μ over an unchanged G. 이것을 형식화하는 이유는, 보통 서로 다른 아키텍처로 논의되는 아이디어들이 사실 같은 공간의 점들로 드러나기 때문입니다. 블로그가 그 목록을 제시하는데, 하나하나가 변하지 않은 G 위에서 π, r, μ 를 달리 잡은 결과입니다.

Where this lands in the code코드에서의 위치 config/topology.py holds two plans and is explicit that only the first decides membership. LogicalProcessPlan is compiled from config alone — "the single place where Process membership is decided" — and ProcessTopologyPlan is built after replica expansion and GPU placement, answering only which expanded stages share an OS process. Neither decides placement; that is config/placement.py. Three questions, three files, no overlap. config/topology.py 에 두 개의 계획이 있고, 멤버십을 결정하는 것은 첫 번째뿐이라고 명시합니다. LogicalProcessPlan 은 설정만으로 컴파일되며 독스트링이 "Process 멤버십이 결정되는 유일한 장소"라고 적고 있습니다. ProcessTopologyPlan 은 복제 확장과 GPU 배치가 끝난 뒤에 만들어지고, 확장된 스테이지들이 어떤 OS 프로세스를 공유하는지만 답합니다. 둘 다 배치를 결정하지 않으며 그것은 config/placement.py 의 일입니다. 질문 셋에 파일 셋이고 겹치지 않습니다.

4Runtime layers, control plane, data plane런타임 계층, 제어 평면, 데이터 평면

Each stage materializes as a worker process with the same three layers inside it, and only the middle one differs per stage. That is the whole trick: a uniform shell around a scheduler chosen to match the stage's workload. 각 스테이지는 워커 프로세스로 구체화되고, 그 안에는 똑같은 세 계층이 들어 있으며, 스테이지마다 달라지는 것은 가운데 한 층뿐입니다. 이것이 요령의 전부입니다. 균일한 껍데기 안에, 그 스테이지의 작업 성격에 맞춘 스케줄러를 끼워 넣습니다.

Redrawn from Figure 4 of the SPG topology blog, with the relay backend list taken from sglang_omni/relay/. SPG 토폴로지 블로그의 Figure 4 를 다시 그렸고, relay 백엔드 목록은 sglang_omni/relay/ 에서 가져왔습니다.

Why two planes instead of one평면을 둘로 나눈 이유

Control messages are small, ordered and must never block; tensors are large and must never be copied twice. Putting both on one channel forces a bad compromise, so they are split. pipeline/control_plane.py opens with a one-line docstring — "Control plane for inter-stage communication via ZMQ" — and carries typed messages (SubmitMessage, DataReadyMessage, DataAckMessage, AbortMessage, KVTransferPrepareMessage …) over msgpack. The payload itself moves on whichever relay backend the placement implies. 제어 메시지는 작고 순서가 있으며 결코 막히면 안 되고, 텐서는 크고 두 번 복사되면 안 됩니다. 둘을 한 채널에 태우면 나쁜 타협을 하게 되므로 갈라놓았습니다. pipeline/control_plane.py 의 첫 줄 독스트링이 "ZMQ 를 통한 단계 간 통신의 제어 평면" 이고, SubmitMessage, DataReadyMessage, DataAckMessage, AbortMessage, KVTransferPrepareMessage 같은 타입이 있는 메시지를 msgpack 으로 실어 나릅니다. 실제 페이로드는 배치가 함의하는 relay 백엔드를 타고 따로 움직입니다.

Redrawn from the interaction-approaches figure of the interactive runtime blog. The cascaded panel is outlined because §6 opens it up. 인터랙티브 런타임 블로그의 interaction-approaches 그림을 다시 그렸습니다. 캐스케이드 패널만 테두리를 강조한 것은 §6 에서 그것을 펼치기 때문입니다.

6The cascaded session, dissected캐스케이드 세션 해부

Calling three HTTP endpoints in sequence is the easy part and takes an afternoon. What takes longer to discover is that a conversation needs a state machine between them, and that its hardest requirement is not interruption itself but what the model is told it said after an interruption. HTTP 엔드포인트 셋을 순서대로 호출하는 것은 쉬운 부분이고 반나절이면 됩니다. 알아차리는 데 오래 걸리는 것은, 대화에는 그 사이를 메우는 상태 기계가 필요하며, 가장 어려운 요구가 끼어들기 자체가 아니라 끼어든 뒤에 모델에게 "네가 말한 것"으로 무엇을 알려 주느냐 라는 사실입니다.

Redrawn from the cascaded-session figure of the interactive runtime blog; node names match examples/streaming_cascade/profiles/*/launch.yaml. 인터랙티브 런타임 블로그의 cascaded-session 그림을 다시 그렸습니다. 노드 이름은 examples/streaming_cascade/profiles/*/launch.yaml 과 일치합니다.

The same picture, as the config that produces it같은 그림을, 그것을 만들어 내는 설정으로

Three of the nodes are nothing but HTTP clients. The declaration says where to call, not what to run — which is why the same graph works whether those endpoints are SGLang-Omni, vLLM, llama.cpp or a cloud API. 노드 가운데 셋은 HTTP 클라이언트에 지나지 않습니다. 선언이 말하는 것은 어디로 호출할지이지 무엇을 돌릴지가 아니며, 그래서 그 엔드포인트가 SGLang-Omni 든 vLLM 이든 llama.cpp 든 클라우드 API 든 같은 그래프가 작동합니다. 

session_nodes:
  vad:    { stages: [vad], inputs: [input] }            # in-process, CPU
  asr:    { kind: openai_transcription, base_url: "http://127.0.0.1:8002/v1", … }
  dialog:
    kind: dialog
    inputs:
      - asr
      - { source: "llm:text_delta", feedback: true, overflow: drop_oldest, capacity: 1024 }
      - { source: "tts:session",    feedback: true, overflow: drop_oldest, capacity: 1024 }
      - "vad:session"
      - { kind: control, source: input,   event: interrupt }      # user barged in
      - { kind: control, source: aligner, event: reply.progress } # what was heard
    system_prompt: You are a helpful voice assistant. Answer in one spoken
                   sentence of at most 25 words, in the language the user speaks.
  llm:    { kind: openai_chat,   base_url: "…:8003/v1", inputs: [dialog, {kind: control, source: dialog, event: interrupt}] }
  tts:    { kind: openai_speech, base_url: "…:8005/v1", inputs: [llm,    {kind: control, source: dialog, event: interrupt}] }
  aligner:{ kind: alignment, method: forced, alignment_url: "http://127.0.0.1:8010", … }

Two details in that block carry most of the design. The feedback: true edges are what make it a loop rather than a chain: dialog reads back from llm and tts, with a bounded queue and drop_oldest so a slow consumer degrades instead of blocking. And the control edges carry interrupt from dialog to both llm and tts, because cancelling generation without cancelling playback leaves the user listening to an answer the system has already abandoned. 이 블록의 두 가지 세부가 설계의 대부분을 담고 있습니다. feedback: true 간선들이 이것을 사슬이 아니라 고리로 만듭니다. dialog 가 llm 과 tts 로부터 되읽으며, 유계 큐와 drop_oldest 덕분에 느린 소비자가 막는 대신 degrade 합니다. 그리고 control 간선이 interrupt 를 dialog 에서 llm 과 tts 양쪽으로 전달하는데, 생성만 취소하고 재생을 취소하지 않으면 사용자는 시스템이 이미 버린 답변을 계속 듣게 되기 때문입니다.

The 800 ms that someone measured누군가 측정한 800 ms

Turn boundaries come from silence, and the threshold is not a round number chosen for neatness. models/vad/node.py carries the reason inline. 턴 경계는 침묵에서 나오고, 그 임계값은 보기 좋으라고 고른 어림수가 아닙니다. models/vad/node.py 가 이유를 코드 안에 적어 두었습니다.

"A pause after a comma or a short 'Sorry.' often runs past 500 ms and split one utterance into two turns, which 800 ms avoided in our zh and en runs."

— sglang_omni/models/vad/node.py, note on주석 위치 silence_duration_ms

The part worth copying: playback-aware history베낄 가치가 있는 부분: 재생을 아는 이력

When the user interrupts, the system has generated more text than the listener heard. Writing the generated text into history is wrong — the model would believe it said things nobody heard. But truncating at the exact heard millisecond is also wrong, and the code says why. 사용자가 끼어들면, 시스템은 듣는 사람이 들은 것보다 많은 텍스트를 이미 생성한 상태입니다. 생성된 텍스트를 그대로 이력에 적으면 틀립니다. 모델이 아무도 듣지 않은 말을 했다고 믿게 되기 때문입니다. 그런데 들린 밀리초에서 정확히 자르는 것도 틀리며, 코드가 그 이유를 적어 놓았습니다.

"a cut reply shown as is reads to the model as how it answers, and after a few interruptions it replies with fragments (#3063)."

— sglang_omni/models/streaming_cascade/dialog.py, note above다음 함수 위의 주석 prompt_messages

So heard_prefix() cuts at the last sentence boundary whose audio ended at or before the heard position, and separately reports whether the listener heard past that boundary into text the cut discards. Getting there needs a character-offset-to-milliseconds map for text that was generated token by token and spoken sentence by sentence — which is the entire reason the aligner node and its separate forced-alignment worker exist. 그래서 heard_prefix() 는 들린 위치 이전에 오디오가 끝나는 마지막 문장 경계에서 자르고, 듣는 사람이 그 경계를 넘어 잘려 나가는 텍스트까지 들었는지를 따로 보고합니다. 여기에 도달하려면 토큰 단위로 생성되고 문장 단위로 발화된 텍스트에 대해 문자 오프셋과 밀리초를 잇는 지도가 필요하며, 그것이 aligner 노드와 별도의 강제 정렬 워커가 존재하는 이유 전부입니다.

Streaming into TTSTTS 로의 스트리밍

OpenAISpeechSynthesizer speaks "sentence by sentence; turn.done follows the reply's audio", capped by max_sentence_words: 24. Waiting for the full reply would add its whole generation time to first-audio latency.OpenAISpeechSynthesizer 는 "문장 단위로 발화하며 turn.done 은 답변 오디오를 뒤따른다"고 적혀 있고 max_sentence_words: 24 로 제한됩니다. 답변 전체를 기다리면 생성 시간 전부가 첫 오디오 지연에 더해집니다.

Deltas after the cancel취소 뒤에 오는 델타

A generator does not stop instantly. The synthesizer keeps a set of interrupted turns and drops their late deltas — "the generator may emit a few deltas after the interrupt before it stops."생성기는 즉시 멈추지 않습니다. 합성기는 인터럽트된 턴의 집합을 유지하며 뒤늦게 오는 델타를 버립니다. "생성기는 인터럽트 이후 멈추기 전까지 델타를 몇 개 더 내보낼 수 있다"는 주석이 붙어 있습니다.

7If you build it yourself직접 만든다면

Two facts in the code decide how much of SGLang-Omni you have to take on to get a cascaded voice agent running, and both point the same way: you can take very little. 캐스케이드 voice agent 를 돌리기 위해 SGLang-Omni 를 얼마나 떠안아야 하는지는 코드의 두 사실이 결정하며, 둘 다 같은 방향을 가리킵니다. 아주 조금만 가져오면 됩니다.

Fact 1 — the services block is optional사실 1 — services 블록은 선택 사항

config/schema.py:785 declares services: list[ServiceConfig] = Field(default_factory=list). Leave it empty and the pipeline starts no model process at all; the three base_url values are then just addresses of servers you started yourself. The cascade becomes a pure orchestrator over whatever you already run. config/schema.py:785 가 services: list[ServiceConfig] = Field(default_factory=list) 로 선언되어 있습니다. 비워 두면 파이프라인은 모델 프로세스를 하나도 띄우지 않으며, 세 개의 base_url 은 직접 띄워 둔 서버의 주소일 뿐입니다. 캐스케이드가 이미 돌고 있는 것들 위의 순수한 오케스트레이터가 됩니다.

Fact 2 — the process manager is 101 lines and has one contract사실 2 — 프로세스 관리자는 101 줄이고 계약이 하나

If you do fill it in, serve/services.py runs subprocess.Popen(service.command) with no validation of the command whatsoever, and considers the service ready when http://127.0.0.1:<port>/v1/models returns 200. That is the entire interface. Three behaviors in it are worth lifting into your own code regardless of whether you use the rest. 반대로 채워 넣는다면, serve/services.py 가 subprocess.Popen(service.command) 를 실행하는데 명령에 대한 검증이 전혀 없고, http://127.0.0.1:<port>/v1/models 가 200 을 돌려주면 준비된 것으로 봅니다. 인터페이스가 이것뿐입니다. 나머지를 쓰든 쓰지 않든 자기 코드로 가져갈 만한 동작이 셋 있습니다.

Adopt, don't restart이미 떠 있으면 그대로

If the port already answers, it logs and returns — and the process is never added to the kill list. Model servers survive pipeline restarts, which is most of your iteration speed.포트가 이미 응답하면 로그만 남기고 반환하며, 그 프로세스는 종료 목록에 들어가지 않습니다. 모델 서버가 파이프라인 재시작을 견디고, 이것이 반복 속도의 대부분을 좌우합니다.

Kill the group그룹째 종료

start_new_session=True then os.killpg, SIGTERM with a 15 s grace before SIGKILL. Servers that spawn children die with them.start_new_session=True 로 띄우고 os.killpg 로 종료하며, SIGTERM 뒤 15초를 기다리고 SIGKILL 합니다. 자식을 또 띄우는 서버도 함께 죽습니다.

Fail loudly on exit죽으면 바로 실패

A watcher polls poll() every second; a dead service fails the whole pipeline with its exit code instead of leaving a hung graph.감시자가 1초마다 poll() 을 확인하고, 죽은 서비스가 있으면 멈춘 그래프를 방치하는 대신 종료 코드와 함께 전체를 실패시킵니다.
