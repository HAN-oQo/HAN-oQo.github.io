Engram — DeepSeek V4.1's hash-indexed memory layer, and why it needs its own parallel axisEngram — DeepSeek V4.1 의 해시 메모리 레이어, 그리고 자기 병렬 축이 필요한 이유

Reading DeepInfer's parallelism code, one axis has no counterpart in any other serving engine: alongside data, context and expert parallel sits engram_parallel. Following it leads to a component that is not an optimisation at all but part of the model — a bank of hashed n-gram embeddings, sharded across every available rank, fetched over the MoE all-to-all fabric and gated into the residual trunk. This note reconstructs it from the inference code: how the key is built, where the table lives, how it is prefetched, and what it costs.DeepInfer 의 병렬화 코드를 읽다 보면 다른 어떤 서빙 엔진에도 대응물이 없는 축이 하나 있다 — data · context · expert 병렬 옆에 engram_parallel 이 있다. 따라가 보면 최적화가 아니라 모델의 일부인 구성요소가 나온다. 해시된 n-gram 임베딩 뱅크를 가용 rank 전체에 샤딩해 두고, MoE all-to-all 패브릭으로 가져와, residual trunk 에 게이팅해 넣는다. 이 노트는 그것을 추론 코드에서 재구성한다 — 키를 어떻게 만들고, 테이블이 어디 살고, 어떻게 미리 가져오고, 비용이 무엇인지.

One-line summary한 줄 요약 Engram hashes each token's preceding n-grams — after aggressively normalising away case, accents and whitespace — into several prime-sized tables, fetches the matching FP8 embeddings from whichever rank holds them, and gates them into the residual stream at selected layers. It is a learned lookup table bolted onto the model, and because its size is bounded by memory rather than compute, it gets a parallel axis of its own that can span more ranks than the model does.Engram 은 각 토큰의 선행 n-gram 을 — 대소문자·악센트·공백을 공격적으로 정규화해 지운 뒤 — 소수 크기 테이블 여러 개에 해싱하고, 그 키를 가진 rank 에서 FP8 임베딩을 가져와, 선택된 레이어에서 residual stream 에 게이팅해 넣는다. 모델에 덧붙인 학습된 룩업 테이블이고, 크기가 연산이 아니라 메모리로 제한되기 때문에 모델보다 더 많은 rank 에 걸칠 수 있는 자기 병렬 축을 갖는다.

Glossary용어 정리

n-gramn-gram

A run of n consecutive tokens. Here, the n tokens immediately preceding the current position — so each position has one n-gram per order (2-gram, 3-gram, …).연속된 토큰 n개. 여기서는 현재 위치 바로 앞의 n개 토큰이라, 각 위치가 차수별로(2-gram, 3-gram, …) n-gram 하나씩을 갖는다.

Hash embedding해시 임베딩

Instead of one row per vocabulary item, hash the item into a fixed-size table. Lets you index an unbounded key space with bounded memory, at the price of collisions.어휘 항목마다 한 행을 두는 대신, 항목을 고정 크기 테이블로 해싱한다. 무한한 키 공간을 유한한 메모리로 인덱싱하되 충돌을 대가로 치른다.

mHC

Multi-way hyper-connections: V4.1 carries hc_mult parallel residual trunks instead of one, mixing them around each sub-layer and folding them back before the LM head.다중 hyper-connection. V4.1 은 residual trunk 를 하나가 아니라 hc_mult 개 들고 다니며, 각 서브레이어 둘레에서 섞고 LM head 앞에서 다시 접는다.

DeepEP

DeepSeek's expert-parallel communication library — the all-to-all fabric that normally ships MoE tokens between ranks. Engram reuses it.DeepSeek 의 expert-parallel 통신 라이브러리. 평소 MoE 토큰을 rank 간에 나르는 all-to-all 패브릭인데, Engram 이 이것을 재활용한다.

UserbufferUserbuffer

A registered memory region that remote ranks can read directly, without going through a copy and a send. Where the engram shards are written once at startup.원격 rank 가 복사·전송 없이 직접 읽을 수 있는 등록된 메모리 영역. engram 샤드가 기동 시 한 번 기록되는 곳.

ue8m0

An 8-bit exponent-only scale format for FP8 blocks. Stored packed — four per int32 on CUDA, two per int16 on Ascend.FP8 블록용 지수 전용 8비트 스케일 포맷. 팩해서 저장한다 — CUDA 는 int32 에 4개, Ascend 는 int16 에 2개.

1An axis that shouldn't exist있을 수 없는 축

DeepInfer's process-group setup creates the axes you expect — and one you do not:DeepInfer 의 프로세스 그룹 설정은 예상 가능한 축들을 만든다 — 그리고 예상 못 한 것 하나를.

# deepinfer/model_executor/parallel_utils/parallel_state.py
def data_parallel_group(self)    -> ProcessGroup: ...
def context_parallel_group(self) -> ProcessGroup: ...
def expert_parallel_group(self)  -> ProcessGroup: ...
def engram_parallel_group(self)  -> ProcessGroup: ...   # ← this one
def world_group(self)            -> ProcessGroup: ...

Note also what is absent: there is no tensor-parallel group. grep -ri 'tensor.parallel' deepinfer/ returns zero hits across the whole engine.그리고 없는 것도 보라 — tensor-parallel 그룹이 없다. 엔진 전체에 대해 grep -ri 'tensor.parallel' deepinfer/ 가 0건이다.

The sizing rule is the tell. Every other axis divides the model; this one does not have to:크기 규칙이 단서다. 다른 모든 축은 모델을 나누는데, 이 축은 그럴 필요가 없다.

# deepinfer/config.py:171-173
self.model_parallel_size  = self.context_parallel_size
self.engram_parallel_size = engram_parallel_size or (self.model_parallel_size * data_parallel_size)
self.world_size           = max(self.model_parallel_size * data_parallel_size,
                                self.engram_parallel_size)
Read that last line again마지막 줄을 다시 보라 world_size is the max of the model's rank count and engram's. So the engram table may be spread over more ranks than the model occupies. That only makes sense for something whose size is set by memory capacity, not by the compute graph — which is exactly what a big lookup table is.world_size 가 모델 rank 수와 engram rank 수의 최댓값이다. 즉 engram 테이블이 모델이 차지한 것보다 더 많은 rank 에 퍼질 수 있다. 이건 크기가 연산 그래프가 아니라 메모리 용량으로 정해지는 대상에서만 말이 된다 — 큰 룩업 테이블이 정확히 그렇다.

2Building the key: erase the surface form키 만들기 — 표면형을 지운다

Before anything is hashed, the tokenizer's vocabulary is rebuilt into a compressed one. The normalisation chain is unusually aggressive:해싱하기 전에, 토크나이저 어휘가 압축된 어휘로 다시 만들어진다. 정규화 체인이 이례적으로 공격적이다.

# deepinfer/model_executor/models/v4_modules/engram_metadata.py
normalizer = normalizers.Sequence([
    normalizers.NFKC(),
    normalizers.NFD(),
    normalizers.StripAccents(),
    normalizers.Lowercase(),
    normalizers.Replace(Regex(r"[ \t\r\n]+"), " "),
    normalizers.Strip(),
    ...
])

The compression mapping is built once on CPU from the tokenizer file, then mirrored to GPU as a lookup tensor.압축 매핑은 토크나이저 파일에서 CPU 에서 한 번 만들어진 뒤 GPU 에 룩업 텐서로 복제된다.

Case, accents and whitespace runs are all erased. That is a deliberate statement about what this table is for: it is not meant to memorise exact strings but to key on a normalised lexical pattern, so that the same phrase in different casing hits the same row. The one exception is guarded explicitly — pieces that decode to invalid UTF-8 keep their raw vocabulary spelling, so distinct byte-level tokens cannot be folded together.대소문자·악센트·연속 공백이 전부 지워진다. 이 테이블이 무엇을 위한 것인지에 대한 의도적 선언이다 — 정확한 문자열을 외우려는 게 아니라 정규화된 어휘 패턴을 키로 삼으려는 것이고, 그래야 같은 구절이 대소문자만 달라도 같은 행에 닿는다. 유일한 예외는 명시적으로 방어된다 — 깨진 UTF-8 로 디코드되는 조각은 원래 어휘 철자를 유지해, 바이트 단위 토큰끼리 합쳐지지 않게 한다.

The n-gram windows themselves are built host-side in C++, into pinned memory, including the speculative draft positions:n-gram 윈도 자체는 호스트 쪽 C++ 에서 pinned 메모리에 만들어지고, 투기적 draft 위치까지 포함한다.

# csrc/engine/zos.cpp
result.ngram_token_ids = torch::full({total_q, max_ngram_size},
                                     engram_compressed_pad_token, pinned(torch::kInt32));
...
fill_engram_row(ngram_token_ids + (offset + q) * max_ngram_size, ...,
                compressed, seq->mtp.draft_tokens, lookup_table, ...);

That seq->mtp.draft_tokens matters: engram lookups cover the speculative draft too, so a draft token that is later accepted already had its memory contribution computed.seq->mtp.draft_tokens 가 중요하다 — engram 조회가 투기적 draft 까지 덮으므로, 나중에 채택될 draft 토큰은 이미 메모리 기여분이 계산돼 있다.

3Many heads, many primes여러 헤드, 여러 소수

Hashing an unbounded key space into a fixed table means collisions. Engram's answer is the classic one, and the table-sizing code states it plainly:무한한 키 공간을 고정 테이블로 해싱하면 충돌이 난다. Engram 의 답은 고전적인 것이고, 테이블 크기 코드가 그대로 말한다.

# engram_metadata.py — one distinct prime per head, never reused
start = int(vocab_size) - 1
sizes = []
for _ in range(num_heads):
    prime = int(nextprime(start))
    while prime in seen:
        prime = int(nextprime(prime))
    seen.add(prime)
    sizes.append(prime)
    start = prime

Each head gets its own prime-sized table, and no size is reused anywhere in the model. Two n-grams that collide under one head's modulus are very unlikely to collide under another's, so the concatenation of all heads' rows disambiguates what any single row could not. Table sizes are tracked per layer × per n-gram order × per head.헤드마다 자기 소수 크기 테이블을 받고, 모델 전체에서 같은 크기가 재사용되지 않는다. 한 헤드의 모듈러스에서 충돌한 두 n-gram 이 다른 헤드에서도 충돌할 확률은 매우 낮으므로, 모든 헤드 행을 이어 붙이면 한 행으로는 불가능한 구분이 가능해진다. 테이블 크기는 레이어 × n-gram 차수 × 헤드 별로 관리된다.

Why primes, specifically왜 하필 소수인가 Using coprime table sizes makes the collision patterns of different heads structurally independent: a hash that maps two keys together mod p has no reason to map them together mod q when p and q share no factors. Picking distinct primes guarantees that cheaply. This is the standard hash-embedding construction, not something exotic — what is unusual is seeing it at this scale inside a frontier model's inference path.서로소인 테이블 크기를 쓰면 헤드별 충돌 패턴이 구조적으로 독립이 된다. p 로 나눈 나머지에서 두 키를 같은 곳에 보내는 해시가, 약수를 공유하지 않는 q 에서도 그럴 이유는 없다. 서로 다른 소수를 고르면 그게 값싸게 보장된다. 특별할 것 없는 표준 해시 임베딩 구성이다 — 특이한 건 이게 프런티어 모델의 추론 경로 안에서 이 규모로 보인다는 점이다.

4Where the table lives테이블이 사는 곳

Each rank holds a shard of the n-gram table, written once into a DeepEP userbuffer at startup — and then the local copy is thrown away:각 rank 가 n-gram 테이블의 샤드를 들고 있고, 기동 시 DeepEP userbuffer 에 한 번 기록된 뒤 로컬 사본은 버려진다.

# v4_modules/engram.py — EngramRuntime.initialize
self._buffer.write(weights, sfs=sfs)
for embedding in embeddings:
    embedding.release_storage()        # the shard now lives only in the userbuffer

The shards are written once and never move; only the selected rows travel, per step.샤드는 한 번 쓰이고 움직이지 않는다. 스텝마다 선택된 행만 이동한다.

Storage is FP8 with ue8m0 scales, and the packing is platform-specific — four scales per int32 on CUDA, two per int16 on Ascend, following PLATFORM.fp8_sf_type. Weight loading happens in roughly 256 MB row chunks, with alignment rows zero-filled at unit scale.저장은 ue8m0 스케일을 가진 FP8 이고 패킹이 플랫폼별로 다르다 — CUDA 는 int32 당 스케일 4개, Ascend 는 int16 당 2개, PLATFORM.fp8_sf_type 을 따른다. 가중치 로딩은 약 256 MB 행 청크 단위이고, 정렬용 행은 단위 스케일로 0 채움한다.

One platform note: DEEPINFER_ENGRAM_FORCE_GPU_STORAGE is forced on whenever the accelerator is Ascend, so the host-memory fallback for the table is NVIDIA-only.플랫폼 메모 하나 — DEEPINFER_ENGRAM_FORCE_GPU_STORAGE 는 가속기가 Ascend 이면 강제로 켜진다. 즉 테이블의 호스트 메모리 폴백은 NVIDIA 전용이다.

5One hash, one fetch, deferred hooks해시 한 번, fetch 한 번, 지연 훅

A naive implementation would gather embeddings inside each engram layer, paying a cross-rank round trip every time. DeepInfer does the opposite: it hashes and fetches once at model level, before the layer loop, and hands each layer a callable.순진한 구현이라면 engram 레이어마다 임베딩을 모아 매번 rank 간 왕복을 치를 것이다. DeepInfer 는 반대로 한다 — 레이어 루프 전에 모델 레벨에서 한 번 해시하고 가져온 뒤, 각 레이어에 호출 가능한 객체를 건넨다.

# deepinfer/model_executor/models/deepseek.py — before the layer loop
hashes = tile_kernels.engram.engram_hash(
    input_metadata.ngram_token_ids,   # [total_q, max_ngram_size], built in C++
    self.ngram_multipliers, self.ngram_vocab_sizes, self.ngram_offsets,
    getattr(input_metadata, "images_seq_mask", None),
)
ngram_embed_hooks = self.engram_runtime.fetch(hashes)   # → {layer_id: callable}

for i in range(self.num_layers):
    ...

The gather is launched before any layer runs, so its latency overlaps the layers that precede the first engram layer.gather 가 어떤 레이어보다 먼저 발사되므로, 그 지연이 첫 engram 레이어 앞의 레이어들과 겹친다.

The return value of fetch is not a tensor — it is a dict of hooks, one per engram layer. Nothing is awaited at fetch time. Each layer calls its hook when it actually needs the data, by which point the all-to-all has had the whole preceding stack of layers to complete in. This is the same prefetch-and-overlap discipline MoE dispatch uses, which is unsurprising given it is running on the same DeepEP machinery.fetch 의 반환값은 텐서가 아니라 engram 레이어당 하나씩의 훅 딕셔너리다. fetch 시점에 기다리는 것이 없다. 각 레이어는 데이터가 실제로 필요할 때 자기 훅을 호출하고, 그 시점이면 all-to-all 은 앞선 레이어 스택 전체를 완료 시간으로 썼다. MoE dispatch 가 쓰는 prefetch-and-overlap 규율과 같은데, 같은 DeepEP 장치 위에서 도니 놀랍지 않다.

6Injection into the hyper-connected trunkhyper-connected trunk 에 주입

Engram does not attach to every layer — only to those listed in engram_layer_ids. Where it does attach, it enters as a trunk intervention hook, after the mHC post-mix:Engram 은 모든 레이어에 붙지 않는다 — engram_layer_ids 에 올라온 레이어에만 붙는다. 붙는 곳에서는 mHC post-mix 이후의 trunk 개입 훅으로 들어간다.

# models/decoder_layer.py
if model_metadata.engram_enabled and layer_idx in model_metadata.engram_cfg.engram_layer_ids:
    self.engram = Engram(layer.engram_embedding, layer_idx, cfg)
...
# engram as the trunk intervention hook after hc post
hc_post_intervention = lambda trunk: self.engram(trunk, ...)

Recall that V4.1 carries hc_mult parallel residual trunks rather than one, so the hidden state arriving here is shaped [total_q, hc_mult, n_embed]. Engram's own module asserts hc_mult > 1 — it is built for the hyper-connected model and would not make sense without it.V4.1 이 residual trunk 를 하나가 아니라 hc_mult 개 들고 다닌다는 점을 떠올리면, 여기 도착하는 hidden state 는 [total_q, hc_mult, n_embed] 모양이다. Engram 모듈 자신이 hc_mult > 1 을 단언한다 — hyper-connected 모델을 위해 만들어졌고 그것 없이는 성립하지 않는다.

The gating itself is one fused kernel, with the constant weights pre-folded at construction:게이팅 자체는 융합 커널 하나이고, 상수 가중치는 생성 시점에 미리 접어 둔다.

# v4_modules/engram.py
# weight_hidden / weight_embed stay constant during inference, so fuse them once up front
self.weight_fused = tile_kernels.engram.fused_weight(weight_hidden.data, weight_embed.data)
...
kv = self.fused_kv_projection(embed_hook()).unflatten(-1, (hc_mult + 1, n_embed))
gated, *_ = tile_kernels.engram.engram_gate_fwd(
    hidden_states, kv, self.weight_fused, self.eps, self.clamp_value,
    save_for_backward=False, image_token_mask=images_seq_mask, inplace=True)

embed_hook() is where the deferred fetch from §5 is finally awaited. inplace=True means the trunk is modified in place rather than copied. And image_token_mask is threaded all the way down: image tokens get a sentinel id and are excluded, so a picture does not accidentally key the text n-gram table.embed_hook() 이 §5 의 지연된 fetch 를 비로소 기다리는 지점이다. inplace=True 는 trunk 를 복사하지 않고 제자리에서 수정한다는 뜻이다. 그리고 image_token_mask 가 끝까지 전달된다 — 이미지 토큰은 sentinel id 를 받아 제외되므로, 그림이 실수로 텍스트 n-gram 테이블을 키잉하지 않는다.

7Constraints, costs, and what stays unknown제약 · 비용 · 남은 미지

Incompatible with YOCO consumer layersYOCO consumer 레이어와 공존 불가

The model init asserts outright that a yoco layer cannot be an engram layer, and separately that engram layers must sit before the YOCO boundary under compaction. Two features that both rewrite the prefill trunk cannot share a layer.모델 초기화가 yoco 레이어는 engram 레이어일 수 없다고 바로 단언하고, 별도로 compaction 하에서 engram 레이어가 YOCO 경계 앞에 있어야 한다고도 단언한다. prefill trunk 를 둘 다 고쳐 쓰는 두 기능은 한 레이어를 공유할 수 없다.

It shows up in the cost model비용 모델에 등장한다

csrc/engine/flops_estimator.hpp carries an explicit Engram term. The scheduler's FLOP accounting — which drives MFU reporting and batch sizing — treats engram as real work, not a free lookup.csrc/engine/flops_estimator.hpp 에 Engram 항이 명시적으로 있다. MFU 보고와 배치 사이징을 구동하는 스케줄러의 FLOP 회계가 engram 을 공짜 조회가 아니라 실제 작업으로 취급한다.

Editor's note — not a claim by DeepSeek편집자 주 — DeepSeek 의 주장 아님 Why I find this the most interesting thing in the repo. Everything else in DeepInfer is an engineering choice you could adopt piecemeal — a C++ scheduler, a kernel DSL, a dual backend. Engram is not: it is a modelling decision that forced an infrastructure consequence. Someone decided V4.1 should carry a large sparse lookup memory, and the serving stack then had to grow a parallel axis, reuse the MoE fabric for a non-MoE purpose, and invent a prefetch discipline to hide the resulting round trip. That is the direction of causality worth noticing: the architecture bent the runtime, not the other way round. For our own work the transferable idea is narrower but real — a capacity-bound component deserves its own sharding axis, decoupled from the compute-bound one. That is just as true of a KV cache tier as it is of an embedding table.왜 이게 이 레포에서 가장 흥미로운지. DeepInfer 의 나머지는 전부 조각조각 채택 가능한 엔지니어링 선택이다 — C++ 스케줄러, 커널 DSL, 이중 백엔드. Engram 은 아니다. 인프라 결과를 강제한 모델링 결정이다. 누군가 V4.1 이 큰 희소 룩업 메모리를 들고 다녀야 한다고 정했고, 그러자 서빙 스택이 병렬 축을 하나 키우고, MoE 패브릭을 MoE 아닌 용도로 재활용하고, 그 왕복을 숨길 prefetch 규율을 발명해야 했다. 눈여겨볼 건 인과의 방향이다 — 아키텍처가 런타임을 휘게 했지, 그 반대가 아니다. 우리 작업에 옮길 아이디어는 더 좁지만 실재한다 — 용량 바운드 구성요소는 연산 바운드 축과 분리된 자기 샤딩 축을 가질 자격이 있다. 임베딩 테이블만큼이나 KV 캐시 계층에도 그대로 해당된다.
