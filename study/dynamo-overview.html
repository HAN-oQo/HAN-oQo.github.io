1 · What it is & why use it무엇이고 왜 쓰나

Dynamo is the orchestration layer above inference engines. It does not replace vLLM, SGLang, or TensorRT-LLM — it turns a fleet of them into a single coordinated, datacenter-scale inference system. It is an open-source project by NVIDIA (ai-dynamo org, Apache-2.0), built in Rust for the hot path and Python for engine integration. The successor in spirit to Triton Inference Server for the LLM era. Dynamo는 추론 엔진 위에 얹히는 오케스트레이션 레이어입니다. vLLM·SGLang·TensorRT-LLM을 대체하는 게 아니라, 여러 대를 묶어 하나의 조율된 데이터센터 규모 추론 시스템으로 만듭니다. NVIDIA가 만든 오픈소스(ai-dynamo org, Apache-2.0)이며, 핫패스는 Rust, 엔진 연동은 Python으로 작성됩니다. LLM 시대의 Triton Inference Server 후속 격입니다.

One-line mental model. A single vLLM server already maxes out one GPU/node. Dynamo is what you put in front of many of them so requests land on the right worker, prefill and decode scale independently, and the KV cache is shared instead of recomputed. 한 줄 요약. vLLM 서버 한 대는 이미 GPU/노드 하나를 꽉 채웁니다. Dynamo는 그런 워커가 여러 대일 때 앞단에 두어, 요청이 올바른 워커로 가고, prefill·decode가 독립적으로 스케일되며, KV 캐시를 재계산 대신 공유하게 만드는 물건입니다.

The four reasons to reach for it쓰게 되는 네 가지 이유

KV-aware routingKV 인지 라우팅

Routes by KV (key–value attention cache) overlap + load, not round-robin. Avoids redundant prefill → up to 2× faster TTFT (time to first token).KV(key–value, 어텐션 캐시) 오버랩+부하로 라우팅(라운드로빈 아님). 중복 prefill 제거 → TTFT(time to first token, 첫 토큰까지 지연) 최대 2배.

Disaggregated P/DP/D 분리 서빙

P/D (prefill/decode) run on separate GPU pools, scaled independently, KV moved by NIXL (NVIDIA Inference Xfer Library).P/D(prefill/decode)를 별도 GPU 풀에서 독립 스케일, KV는 NIXL(NVIDIA Inference Xfer Library)로 전송.

Multi-tier KV (KVBM)다계층 KV (KVBM)

KVBM (KV Block Manager) offloads the cache GPU → CPU → SSD → remote, extending effective context beyond VRAM (GPU video memory).KVBM(KV Block Manager)이 캐시를 GPU→CPU→SSD→원격으로 오프로드, VRAM(GPU 비디오 메모리) 너머로 유효 컨텍스트 확장.

SLA planner + fast cold-startSLA 플래너 + 빠른 콜드스타트

Autoscales pools to hit TTFT / ITL (inter-token latency) targets at minimum TCO (total cost of ownership); ModelExpress streams weights for 7× faster startup.TTFT / ITL(inter-token latency, 토큰 간 지연) 목표를 최소 TCO(total cost of ownership, 총소유비용)로 맞춰 자동 스케일; ModelExpress 가중치 스트리밍으로 기동 7배.

NVIDIA's own positioning is blunt: "If you're running a single model on a single GPU, your inference engine alone is probably sufficient." Dynamo earns its keep at multi-GPU / multi-node scale. NVIDIA 스스로의 표현도 단호합니다: "단일 GPU에서 단일 모델만 돌린다면 추론 엔진 하나로 충분할 것". Dynamo는 멀티 GPU·멀티 노드 규모에서 값을 합니다.

1Start the Frontend (HTTP :8000 + KV Router)Frontend 기동 (HTTP :8000 + KV Router)

The Frontend owns the /v1/chat/completions endpoint, the tokenizer, and (in --router-mode kv) the router that picks a worker per request. Workers self-register with it on startup — you do not list worker addresses anywhere. Frontend가 /v1/chat/completions 엔드포인트, 토크나이저, 그리고(--router-mode kv일 때) 요청마다 워커를 고르는 라우터를 소유합니다. 워커는 기동 시 스스로 등록하므로 워커 주소를 어디에도 적지 않습니다.

2Start two vLLM workers (one per GPU)vLLM 워커 2대 기동 (GPU 당 1대)

Two identical workers, pinned to GPU 0 and GPU 1, each emitting KV cache events over its own ZMQ port. Those events are what let the router know which blocks each worker already holds. --model takes any vLLM-supported model; vLLM's native engine args pass straight through. 동일한 워커 2대를 GPU 0·1에 핀하고, 각자 자기 ZMQ 포트로 KV 캐시 이벤트를 발행합니다. 이 이벤트 덕분에 라우터가 각 워커가 이미 들고 있는 블록을 압니다. --model엔 vLLM 지원 모델 아무거나 넣을 수 있고, vLLM 네이티브 엔진 인자는 그대로 통과합니다.

How the three commands wire together세 명령이 어떻게 연결되나

Nobody is told anyone's address. The two workers register in etcd on startup; the Frontend watches etcd and discovers them; the workers publish KV events to NATS; the router subscribes to those events and then dispatches each request straight to the chosen worker over the request plane. 아무도 상대의 주소를 듣지 않습니다. 워커 2대가 기동 시 etcd에 등록하고, Frontend는 etcd를 watch해 그들을 발견하며, 워커는 KV 이벤트를 NATS에 발행하고, 라우터는 그 이벤트를 구독한 뒤 각 요청을 선택된 워커로 요청 평면을 통해 직접 보냅니다.

Solid green = the live request path · dashed blue = etcd discovery · dashed purple = NATS KV-event bus.초록 실선 = 실제 요청 경로 · 파란 점선 = etcd 디스커버리 · 보라 점선 = NATS KV 이벤트 버스.

“But I never gave a port — how does the Frontend find the worker?”“포트도 안 줬는데 Frontend가 워커를 어떻게 찾지?”

Right — you pass --model but never a worker address or port. Nothing is statically wired. Instead the worker advertises its own address in etcd under a lease, and the Frontend watches etcd and learns it. Only the names are hardcoded defaults; the port is OS-assigned and published. 맞습니다 — --model만 주고 워커 주소·포트는 안 줍니다. 정적으로 연결되는 게 하나도 없습니다. 대신 워커가 자기 주소를 lease 걸어 etcd에 광고하고, Frontend는 etcd를 watch해 그걸 배워옵니다. 하드코딩된 건 이름 기본값뿐이고, 포트는 OS가 할당해서 광고됩니다.

Where the port comes from. Unless you set DYN_TCP_RPC_PORT, the worker binds its request-plane TCP server to port 0 → the OS hands back a free ephemeral port. The worker then reads that actual port and bakes it into the address it registers. That is why no port appears in the launch script — the worker picks one and tells etcd. (DYN_SYSTEM_PORT in the script is a different, metrics/system port, set per-worker only to avoid clashes.) 포트의 출처. DYN_TCP_RPC_PORT를 직접 주지 않으면, 워커는 request-plane TCP 서버를 포트 0으로 bind → OS가 빈 ephemeral 포트를 돌려줍니다. 워커는 그 실제 포트를 읽어 자기가 등록할 주소에 박습니다. 그래서 런치 스크립트에 포트가 안 보이는 겁니다 — 워커가 직접 골라 etcd에 알립니다. (스크립트의 DYN_SYSTEM_PORT는 별개의 메트릭/시스템 포트로, 충돌 방지용으로만 워커마다 다르게 줍니다.)

1) Worker startup — one lease, then bind, then advertise. The runtime opens an etcd lease and ties its own lifetime to it (lease expires → worker considered dead; worker dies → lease revoked). 1) 워커 기동 — lease 하나 만들고, bind하고, 광고. 런타임이 etcd lease를 열고 자기 수명을 거기 묶습니다(lease 만료 → 워커 사망 간주, 워커 사망 → lease revoke).

2) Register two keys in etcd, both lease-bound. An instance key holds the transport address; a model key holds the model card. Keys are named by namespace/component/endpoint/instance_id — defaults dynamo / backend / generate. 2) etcd에 키 두 개 등록 — 둘 다 lease에 묶여서. instance 키는 transport 주소를, model 키는 모델 카드를 담습니다. 키 이름은 namespace/component/endpoint/instance_id — 기본값 dynamo / backend / generate.

3) Frontend watches, learns the address, connects. The model watcher list+watches the v1/models/… prefix to build each model's engine; the router list+watches v1/instances/… for the live address set. To send, it resolves the chosen instance's transport and connects over TCP (or a NATS subject) — no configuration needed. 3) Frontend가 watch해서 주소를 배우고 연결. 모델 watcher가 v1/models/… prefix를 list+watch해 모델별 엔진을 구성하고, 라우터가 v1/instances/…를 list+watch해 살아있는 주소 집합을 유지합니다. 보낼 때는 선택된 인스턴스의 transport를 풀어 TCP(또는 NATS subject)로 연결합니다 — 설정 불필요.

So the chain is: worker → (lease + self-assigned address) → etcd → (watch) → Frontend → connect. etcd is the registry that makes the port you never typed discoverable; with --discovery-backend file a local file plays the same role for laptop runs. 즉 사슬은: 워커 → (lease + 자기 주소) → etcd → (watch) → Frontend → 연결. etcd가, 당신이 한 번도 안 친 그 포트를 발견 가능하게 만드는 레지스트리입니다. --discovery-backend file이면 노트북 실행에서 로컬 파일이 같은 역할을 합니다.

3Call it — exactly the OpenAI API호출 — 그냥 OpenAI API

Client points at the Frontend (:8000) and never at a worker. The router transparently fans requests across the two GPUs by cache affinity. 클라이언트는 Frontend(:8000)만 바라보고 워커는 절대 직접 호출하지 않습니다. 라우터가 캐시 친화도로 두 GPU에 요청을 알아서 분배합니다.

Want disaggregation instead? Swap to launch/disagg.sh: same Frontend, but worker A starts with --disaggregation-mode decode and worker B with --disaggregation-mode prefill, both using --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_both"}'. Now the two GPUs play different roles instead of being replicas. 분리 서빙을 원하면? launch/disagg.sh로 바꾸면 됩니다: Frontend는 동일, 워커 A는 --disaggregation-mode decode, 워커 B는 --disaggregation-mode prefill로 띄우고 둘 다 --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_both"}'를 씁니다. 이제 두 GPU는 복제본이 아니라 서로 다른 역할을 맡습니다.

3 · Code structure코드 구조

Two worlds: lib/ is the Rust core (the hot path — HTTP, tokenize, route, transport, KV); components/ is the Python layer that wraps each inference engine. The Rust talks to Python over the runtime's transport. 두 세계로 나뉩니다: lib/는 Rust 코어(핫패스 — HTTP·토크나이즈·라우팅·전송·KV), components/는 각 추론 엔진을 감싸는 Python 레이어. Rust가 런타임 전송을 통해 Python과 대화합니다.

The key architectural choice: the tokenizer lives in the Rust Frontend, not in the GPU engine. Workers exchange only token_ids / input_ids — pure token-in-token-out (TITO). That is precisely what lets the front compute prefix hashes over prompt tokens and do KV-aware routing before any GPU is touched. 핵심 설계 결정: 토크나이저가 GPU 엔진이 아니라 Rust Frontend에 있습니다. 워커는 token_ids / input_ids만 주고받는 순수 TITO입니다. 이 덕분에 앞단이 prompt 토큰의 prefix 해시를 계산해, GPU를 건드리기 전에 KV 인지 라우팅을 할 수 있습니다.

1HTTP handler receives the requestHTTP 핸들러가 요청 수신 Frontend

The Axum route /v1/chat/completions lands in handler_chat_completions, which spawns chat_completions. After validation it fetches the per-model engine and calls engine.generate(request) — that single call is the whole pipeline. Axum 라우트 /v1/chat/completions가 handler_chat_completions로 들어오고 chat_completions를 spawn합니다. 검증 후 모델별 engine을 가져와 engine.generate(request)를 호출 — 이 한 번의 호출이 곧 파이프라인 전체입니다.

2Pipeline assembly + tokenize파이프라인 조립 + 토크나이즈 Frontend

That engine is a chain of operators built once at startup: frontend → preprocessor → backend → routed engine, with the response edges linked in reverse. The preprocessor is where text becomes tokens (and tokens become text on the way back). 그 engine은 기동 시 한 번 조립되는 오퍼레이터 체인입니다: frontend → preprocessor → backend → routed engine, 응답 엣지는 역순으로 연결됩니다. 텍스트가 토큰이 되는(그리고 돌아올 때 토큰이 텍스트가 되는) 지점이 preprocessor입니다.

Inside gather_tokens the literal encode call is self.encode_with_timing(prompt, tracker) → tokenizer.encode(s). From here the request carries token_ids only. gather_tokens 내부의 실제 encode 호출은 self.encode_with_timing(prompt, tracker) → tokenizer.encode(s)입니다. 이후 요청은 token_ids만 들고 다닙니다.

3KV-aware routing — pick the best workerKV 인지 라우팅 — 최적 워커 선택 Frontend

In --router-mode kv the engine is a KvPushRouter. For each candidate worker it computes a logit = prefill_cost + decode_cost, where prefill cost is the remaining prefill blocks after subtracting KV-cache overlap (device/host/disk). Lower is better → fewer redundant tokens to prefill. --router-mode kv에서 engine은 KvPushRouter입니다. 후보 워커마다 logit = prefill_cost + decode_cost를 계산하는데, prefill 비용은 KV 캐시 오버랩(device/host/disk)을 뺀 뒤 남은 prefill 블록 수입니다. 낮을수록 좋음 → 다시 prefill할 토큰이 적다는 뜻.

4Dispatch to the chosen worker선택된 워커로 발송 Frontend → Worker

The router stamps the dp_rank and calls self.inner.direct(request, instance_id) to send to that specific worker. The runtime resolves whether that worker is reached over TCP or a NATS subject and performs the send. 라우터가 dp_rank를 찍고 self.inner.direct(request, instance_id)로 해당 워커에 보냅니다. 런타임이 그 워커가 TCP인지 NATS subject인지 해석해 실제 전송을 수행합니다.

5Python vLLM worker generatesPython vLLM 워커가 생성 Worker

The worker bound its handler.generate to a Dynamo endpoint at startup and registered the model with the Frontend. On each request it forwards token_ids straight into vLLM's AsyncLLM.generate and streams the output tokens back. 워커는 기동 시 handler.generate를 Dynamo 엔드포인트에 바인딩하고 모델을 Frontend에 등록해 둡니다. 요청마다 token_ids를 그대로 vLLM AsyncLLM.generate에 넘기고 출력 토큰을 스트리밍으로 돌려줍니다.

If disaggregated (disagg.sh): the Rust PrefillRouter operator sits in the pipeline before decode. If prefill workers are active, it clones the request, caps it at max_tokens=1, routes it to a prefill worker, and pulls out disaggregated_params — the handle the decode worker uses to receive the KV blocks via NIXL. The Python decode worker just consumes those params. 분리 서빙(disagg.sh)이면: Rust PrefillRouter 오퍼레이터가 decode 앞에 들어갑니다. prefill 워커가 활성이면 요청을 복제해 max_tokens=1로 자르고 prefill 워커로 보낸 뒤 disaggregated_params(decode가 NIXL로 KV 블록을 받을 때 쓰는 핸들)를 꺼냅니다. Python decode 워커는 그 params를 받아 쓰기만 합니다.

6Detokenize + stream back as SSE디토크나이즈 + SSE로 스트리밍 Worker → Frontend → Client

Returned token_ids flow back through the backend.backward_edge, where a streaming Decoder turns them into text; the preprocessor's backward edge wraps them as OpenAI chat deltas; openai.rs serializes each delta as an SSE event. 돌아온 token_ids는 backend.backward_edge를 거치며 스트리밍 Decoder가 텍스트로 바꾸고, preprocessor 역방향 엣지가 OpenAI 챗 델타로 감싸며, openai.rs가 각 델타를 SSE 이벤트로 직렬화합니다.

The whole loop in one breath: client → Frontend tokenizes → router picks the worker with the most KV overlap → decode worker generates (optionally pulling KV from a prefill worker via NIXL) → tokens stream back → Frontend detokenizes → SSE to client. The GPU engine only ever sees token IDs. 한 호흡으로 본 전체 루프: client → Frontend 토크나이즈 → 라우터가 KV 오버랩이 가장 큰 워커 선택 → decode 워커가 생성(필요 시 prefill 워커에서 NIXL로 KV 당겨옴) → 토큰 스트리밍 → Frontend 디토크나이즈 → 클라이언트로 SSE. GPU 엔진은 토큰 ID만 봅니다.

What the Frontend and worker actually exchangeFrontend와 워커가 실제로 주고받는 것

Two internal types travel between them, both JSON-serialized over TCP (default) or NATS. The contract is token-in-token-out: the request carries token_ids, not text, and the response carries new token_ids, not detokenized text. 둘 사이를 오가는 내부 타입은 두 개이며, 모두 JSON 직렬화로 TCP(기본) 또는 NATS를 탑니다. 계약은 token-in-token-out입니다: 요청은 텍스트가 아니라 token_ids를, 응답은 디토크된 텍스트가 아니라 새 token_ids를 담습니다.

Frontend → Worker — PreprocessedRequest.Frontend → Worker — PreprocessedRequest.

Worker → Frontend — a stream of Annotated<LLMEngineOutput>. Each chunk is one engine output; Annotated is the SSE-style envelope. Worker → Frontend — Annotated<LLMEngineOutput> 스트림. 각 청크가 엔진 출력 하나이고, Annotated는 SSE 스타일 봉투입니다.

tokens / text are usually None. The GPU engine returns only token ids; detokenization happens back in the Frontend's Backend operator. 5 · Dynamo vs plain Docker vLLM그냥 Docker로 띄운 vLLM 대비

The honest comparison. Baseline = docker run vllm/vllm-openai --model … (one container, OpenAI server) ×N behind some load balancer. 솔직한 비교. 기준점 = docker run vllm/vllm-openai --model … (컨테이너 1개, OpenAI 서버)를 로드밸런서 뒤에 N개 둔 구성.

Where Dynamo winsDynamo가 이기는 곳

  • KV-aware routing. A plain LB (load balancer) is cache-blind — round-robin re-prefills the same prompt on whichever GPU it lands. Dynamo routes to the GPU that already holds the prefix. Big win for multi-turn chat, shared system prompts, RAG (retrieval-augmented generation). (~2× TTFT.)KV 인지 라우팅. 일반 LB(load balancer, 로드밸런서)는 캐시를 못 봐서, 라운드로빈으로 같은 프롬프트를 닿는 GPU마다 다시 prefill합니다. Dynamo는 prefix를 이미 가진 GPU로 보냅니다. 멀티턴·공유 시스템 프롬프트·RAG(retrieval-augmented generation, 검색 증강 생성)에서 큰 이득. (TTFT 약 2배.)
  • Disaggregated prefill/decode. Plain vLLM couples both phases on one GPU; a long prefill stalls others' decoding. Dynamo splits them into independently-scaled pools with NIXL KV transfer.prefill/decode 분리. 일반 vLLM은 두 단계가 한 GPU에 묶여, 긴 prefill이 남의 decode를 막습니다. Dynamo는 NIXL KV 전송으로 둘을 독립 스케일 풀로 분리합니다.
  • Multi-tier KV (KVBM). Offload KV to CPU/SSD/remote, so effective context isn't capped by VRAM — impossible with a lone container.다계층 KV (KVBM). KV를 CPU/SSD/원격으로 오프로드해 유효 컨텍스트가 VRAM에 갇히지 않습니다 — 단일 컨테이너로는 불가능.
  • SLA (service-level agreement) planner + fast cold-start. Autoscales pools to hit TTFT/ITL at min TCO; ModelExpress streams weights (~7× faster replica startup).SLA(service-level agreement, 서비스 수준 협약) 플래너 + 빠른 콜드스타트. TTFT/ITL을 최소 TCO로 맞춰 자동 스케일; ModelExpress 가중치 스트리밍(복제본 기동 약 7배).
  • One OpenAI endpoint, many heterogeneous workers — and in-flight request migration when a worker dies.OpenAI 엔드포인트 1개로 이종 워커 다수 — 워커 사망 시 진행 중 요청 마이그레이션까지.

Where plain vLLM wins그냥 vLLM이 나은 곳

  • Simplicity. One docker run vs Frontend + Router + N workers (+ optional etcd/NATS, +K8s for production). More moving parts, more to debug.단순함. docker run 하나 vs Frontend+Router+워커 N개(+선택적 etcd/NATS, +프로덕션이면 K8s). 조각이 많고 디버깅 거리도 늘어납니다.
  • Single GPU / single node. With no second worker there's nothing to route or disaggregate — Dynamo adds a hop and overhead for zero benefit. NVIDIA says so themselves.단일 GPU·단일 노드. 두 번째 워커가 없으면 라우팅·분리할 게 없어, Dynamo는 홉과 오버헤드만 더합니다. NVIDIA도 같은 말을 합니다.
  • Operational maturity. Plain vLLM containers are battle-tested and trivially portable; Dynamo is younger and its richest features assume NVIDIA GPUs + NIXL.운영 성숙도. 일반 vLLM 컨테이너는 검증됐고 이식이 쉽습니다; Dynamo는 더 젊고, 풍부한 기능 상당수가 NVIDIA GPU + NIXL을 전제합니다.
  • Latency floor for tiny loads. At low QPS (queries per second) the extra front/route hop is pure added latency you don't recoup.저부하 지연 하한. QPS(queries per second, 초당 요청)가 낮으면 앞단·라우팅 홉이 회수되지 않는 순수 추가 지연이 됩니다.

Bottom line. Dynamo isn't a faster vLLM — it's the coordination layer that makes a fleet of vLLMs behave like one efficient system. Below ~2 GPUs it's the wrong tool. Above that, the cache-aware routing and P/D disaggregation are hard to replicate with a dumb load balancer. 결론. Dynamo는 더 빠른 vLLM이 아니라, vLLM 여러 대를 하나의 효율적 시스템처럼 동작시키는 조율 레이어입니다. GPU 2개 미만이면 잘못된 도구입니다. 그 이상에서는 캐시 인지 라우팅과 P/D 분리를 멍청한 로드밸런서로 재현하기 어렵습니다.
