one-line summary한 줄 요약
  • Agent memory is reframed as a stateful data-management system = ⟨Representation&Storage, Extraction, Retrieval&Routing, Maintenance⟩ and benchmarked on five axes prior work ignored.
  • No single system dominates. Composite hybrids win chat QA; graphs win single-hop facts but fail temporal reasoning.
  • Without lifecycle management, stores return stale facts ("hallucinations of the past"), and heavily-structured systems cost orders of magnitude more latency without proportional accuracy.
  • For time-dependent queries, consolidation destroys chronological cues, so raw long-context still beats most memory systems. Testbed and paper list are open-sourced.
  • 에이전트 메모리를 상태를 가진 데이터 관리 시스템 ⟨표현·저장, 추출, 검색·라우팅, 유지관리⟩로 재정의하고, 선행 연구가 놓친 다섯 축으로 잰다.
  • 모든 상황을 이기는 시스템은 없다. 복합 하이브리드는 대화 QA에서 앞서고, 그래프는 단일 홉 사실에 강하지만 시간 추론에는 약하다.
  • 라이프사이클 관리가 없으면 낡은 사실을 돌려주고("과거의 환각"), 고도 구조화 시스템은 정확도에 비해 레이턴시가 자릿수 단위로 크다.
  • 시간 의존 쿼리에서는 통합이 시간 단서를 지워 순정 롱컨텍스트가 대부분의 메모리 시스템을 이긴다. 테스트베드와 논문 리스트는 오픈소스다.

🗺️ Orientation — memory as a system, not a lookup 오리엔테이션: 조회가 아니라 시스템으로서의 메모리

A chatbot that "remembers" your name across sessions does four jobs under the hood: extract what's worth keeping, represent and store it (text? a vector? a graph?), retrieve the right pieces later, and maintain the store as facts change (you moved; your old address is now wrong). The paper stops scoring these systems by a single end-task number, treats memory as a data-management system with those four jobs, and asks whether any current system gets all four right.

세션을 넘어 이름을 "기억"하는 챗봇도 안에서는 네 가지 일을 한다. 남길 것을 추출하고, 텍스트·벡터·그래프로 표현·저장하고, 필요할 때 검색하고, 사실이 바뀌면(이사로 옛 주소가 틀려지면) 유지관리한다. 논문은 메모리를 종단 점수 하나가 아니라 이 네 일을 하는 데이터 관리 시스템으로 평가하고, 넷을 모두 잘하는 시스템이 있는지 묻는다.

Execution workflows of agent memory (write path, read path, maintenance).에이전트 메모리의 실행 흐름(쓰기 경로, 읽기 경로, 유지관리). · Figure 1, arXiv:2606.24775

the DB-community lensDB 커뮤니티의 렌즈 The paper is written "from a data management perspective," so it separates memory from traditional DBs on three counts: access is semantic (not predicate-based SQL), contents evolve under conflicting observations (not clean transactional writes), and workloads are heterogeneous in access pattern and granularity. Memory is a new kind of stateful store, not OLTP/OLAP with embeddings bolted on. 이 논문은 "데이터 관리 관점"에서 쓰였고, 그래서 메모리를 전통 DB와 세 가지로 구분한다. 접근이 술어 기반 SQL이 아니라 의미 기반이고, 내용은 깨끗한 트랜잭션 쓰기가 아니라 상충하는 관측 속에서 진화하며, 워크로드의 접근 패턴·입도가 이질적이다. 메모리는 OLTP/OLAP에 임베딩을 얹은 것이 아니라 새로운 종류의 상태 저장소다.

1 Problem — memory grew up; evaluation didn't 문제 정의: 메모리는 자랐는데 평가는 그대로

1.1 — Memory is now infrastructure, still tested like a feature 1.1 메모리는 이제 인프라인데, 아직 기능처럼 평가된다

Agent memory has grown from a retrieval trick into a stateful system with storage, retrieval, update, consolidation, and lifecycle governance. The paper asks whether the field is ready to treat it that way:

에이전트 메모리는 검색 트릭에서 저장·검색·갱신·통합·라이프사이클 관리를 갖춘 상태 기반 시스템으로 자랐다. 논문은 이 분야가 메모리를 그렇게 다룰 준비가 됐는지 묻는다.

"However, this rapid proliferation has also led to a highly fragmented landscape that lacks systematic evaluation from a data management perspective, raising a natural question: Are we ready for an agent-native memory system?"

— §1, ¶2 · 원문 보기 (§1)

The definition is system-flavored too: memory is a persistent store separate from both the weights and the context window.

정의도 시스템 쪽이다. 메모리는 가중치와도, 컨텍스트 창과도 분리된 지속 저장소다.

"It is the persistent data management system that maintains information beyond a single inference step (e.g., historical interactions, environmental observations, and intermediate tool executions) decoupled from the LLMs' parametric weights and volatile context windows."

— §1, ¶3 · 원문 보기 (§1)

1.2 — Four things prior benchmarks miss 1.2 기존 벤치마크가 놓친 네 가지

The gap the paper stakes out (§1):

논문이 짚는 기존 평가의 빈자리는 넷이다(§1).

  1. Many architectures are omitted. MemoChat, MemTree, LightMem were never tested under unified workloads; DB-flavored efforts stop at LoCoMo + LongMemEval and ignore agentic execution.
  2. Single-sided end-task metrics (F1, BLEU) never isolate retrieval fidelity, update robustness, or long-horizon stability.
  3. Operational cost is rarely measured (index-build time, query latency).
  4. Memory is treated as a black box instead of being decomposed into modules.
  1. 많은 아키텍처가 빠졌다. MemoChat·MemTree·LightMem 등은 통일된 워크로드에서 검증된 적이 없다. DB 쪽 연구는 LoCoMo+LongMemEval에 머물러 에이전트 실행을 다루지 않는다.
  2. 종단 지표(F1·BLEU) 하나에 기댄다. 검색 충실도·업데이트 강건성·장기 안정성을 따로 보지 못한다.
  3. 운영 비용을 거의 재지 않는다(인덱스 구축 시간, 쿼리 레이턴시).
  4. 메모리를 블랙박스로 다룬다. 모듈로 나눠 분석하지 않는다.

"Last, they treat memory systems as monolithic black boxes rather than decomposing them into fundamental data management modules for isolated, fine-grained analysis."

— §1, ¶4 · 원문 보기 (§1)

1.3 — Why "agent-native," and not RAG / long-context / cognitive taxonomies 1.3 왜 "에이전트 네이티브"인가: RAG·롱컨텍스트·인지 분류와의 차이

"Agent-native" separates the concept from three neighbors:

"에이전트 네이티브"는 이 개념을 세 이웃과 구분하려고 붙인 말이다.

  • RAG: stateless, read-only lookup over a fixed corpus.
  • Context engineering: curating the finite window each turn to fight "context rot".
  • Human-memory-inspired taxonomies: memory as an algorithmic component, not a system.
  • RAG: 고정 코퍼스 위의 무상태·읽기 전용 조회.
  • 컨텍스트 엔지니어링: 매 턴 유한한 창을 큐레이션해 "컨텍스트 부패"를 막는 일.
  • 인간 기억 기반 분류: 메모리를 시스템이 아니라 알고리즘 요소로 보는 관점.

RAG is the one people most often conflate with memory:

이 중 메모리와 가장 많이 혼동되는 것이 RAG다.

"Retrieval-Augmented Generation (RAG) typically operates as a stateless, read-only retrieval primitive: given a query, it fetches relevant passages from a static corpus to augment a single generation step."

— §2 (Distinction from RAG) · 원문 보기 (§2)

2 Method — the four-module taxonomy 해결 방법: 4-모듈 분류 체계

The framework is the survey-side contribution: define a memory system as a tuple of four modules, each owning one lifecycle phase, then classify every existing system along those axes. Formally, ℳ_sys = ⟨ℛ, 𝒮, 𝒬, 𝒰⟩.

서베이 쪽 기여가 이 프레임워크다. 메모리 시스템을 네 모듈의 튜플로 정의하고(모듈마다 라이프사이클의 한 단계를 맡는다), 기존 시스템을 모두 이 축으로 분류한다. 형식적으로는 ℳ_sys = ⟨ℛ, 𝒮, 𝒬, 𝒰⟩이다.

2.1 — ℛ Representation & Storage 2.1 ℛ 표현·저장

  • Logical representation: Token-Level Sequence (explicit discrete text or implicit continuous vector) → Graph & Tree Topology (temporal KG or hierarchical tree) → Heterogeneous Composite (e.g. MemCube).
  • Physical storage: Transient In-Context Register / Specialized Single-Engine (vector, graph, SQL, or file) / Heterogeneous Multi-Engine.
  • 논리적 표현: 토큰 수준 시퀀스(명시적 이산 텍스트 또는 암묵적 연속 벡터) → 그래프·트리 토폴로지(시간 KG 또는 계층 트리) → 이질적 복합(예: MemCube).
  • 물리적 저장: 일시적 인컨텍스트 레지스터 / 특화 단일 엔진(벡터·그래프·SQL·파일) / 이질적 멀티 엔진.

2.2 — 𝒮 Extraction 2.2 𝒮 추출

Three strategies, in increasing aggressiveness: Raw Sequence Concatenation (keep everything verbatim) → Schema-Free Semantic Extraction (LLM summarizes/extracts facts, no fixed schema) → Schema-Constrained Structured Extraction (typed slots / triplets / JSON). As the results show, aggressive extraction can raise precision but destroys multi-hop reasoning.

공격성 순으로 세 전략이 있다. 원시 시퀀스 연결(전부 원문 그대로 보존) → 스키마 프리 의미 추출(LLM이 고정 스키마 없이 요약·사실 추출) → 스키마 제약 구조화 추출(타입 슬롯/트리플/JSON). 결과에서 보듯 공격적 추출은 양날의 검이다. 정밀도는 올라가도 멀티 홉 추론이 무너진다.

2.3 — 𝒬 Retrieval & Routing 2.3 𝒬 검색·라우팅

  • Native Attention: the model attends over in-context memory.
  • Semantic Dense: KNN over embeddings.
  • Topological Subgraph Traversal: walk a graph from seed nodes.
  • Autonomous Agentic Routing: the agent decides via function calls or generative query expansion.
  • Multi-Stage Hybrid: sequential routing or parallel ensembles that fuse the above.
  • Native Attention: 모델이 인컨텍스트 메모리에 그대로 어텐션한다.
  • Semantic Dense: 임베딩 KNN.
  • 위상 서브그래프 순회: 시드 노드에서 그래프를 탐색한다.
  • 자율 에이전트 라우팅: 에이전트가 함수 호출이나 생성적 쿼리 확장으로 정한다.
  • 다단계 하이브리드: 위 방식들을 순차 라우팅이나 병렬 앙상블로 섞는다.

2.4 — 𝒰 Maintenance 2.4 𝒰 유지관리

  • Timestamp Multi-Versioning: keep versions, resolve by recency/precedence.
  • Capacity-Driven Eviction: hard FIFO/token limits, or score-based priority with temporal decay.
  • LLM-Driven Consolidation: an LLM merges redundant assertions inline, or runs tool-based CRUD.
  • Continuous Parametric Optimization: train the memory (e.g. MemoRAG's RLGF).
  • 타임스탬프 다중버전: 버전을 보관하고 최신성·우선순위로 해소한다.
  • 용량 기반 축출: FIFO·토큰 한도 같은 하드 제약, 또는 시간 감쇠 점수 우선순위.
  • LLM 기반 통합: LLM이 중복 주장을 인라인 병합하거나 도구 기반 CRUD를 실행한다.
  • 지속 파라미터 최적화: 메모리를 학습한다(예: MemoRAG의 RLGF).

"Hallucinations of the past" live here: a store with no versioning/eviction keeps serving superseded facts.

"과거의 환각"은 이 모듈에서 생긴다. 버전 관리나 축출이 없는 저장소는 이미 갱신된 사실을 계속 내놓는다.

3.2 — The five evaluation dimensions 3.2 다섯 평가 축

Two layers. End-to-end (§4) probes RQ1 effectiveness, RQ2 retrieval fidelity, RQ3 update robustness, RQ4 long-horizon stability, RQ5 operational cost. Fine-grained ablations (§5) then modify one module at a time (M1 representation/storage, M2 extraction, M3 retrieval/routing, M4 maintenance).

평가는 두 층이다. End-to-end(§4)는 RQ1 효과성, RQ2 검색 충실도, RQ3 업데이트 강건성, RQ4 장기 안정성, RQ5 운영 비용을 본다. 세밀 어블레이션(§5)은 한 번에 한 모듈씩(M1 표현/저장, M2 추출, M3 검색/라우팅, M4 유지) 바꿔 모듈별 효과를 분리한다.

3.3 — Metrics in plain language 3.3 지표를 쉬운 말로

  • The system tuple ℳ_sys = ⟨ℛ, 𝒮, 𝒬, 𝒰⟩. A definition more than math: the system is those four machines, and ℳ (unscripted) is the data they write, read, and age.
  • EM & Answer F1 (LoCoMo). EM = exact string match with gold (1/0); F1 = token-overlap F1. Both are the unweighted mean over LoCoMo's 4 query categories.
  • Substring EM, ROUGE-L, LLM-Judge (LongMemEval). Substring EM = gold appears inside the answer; ROUGE-L = longest-common-subsequence overlap (F1 & recall); LLM-Judge Accuracy = a GPT-5.4 judge rates correctness and catches paraphrased-but-correct answers.
  • Task Success Rate (DB-Bench). Did the executed DB operations reach the correct end state? That's why Long Context can win DB-Bench EM yet lose Task Success Rate.
  • Recall@K over evidence-distance bins (RQ2). A hit needs the top-K source-id groups to contain the gold evidence, reported over 6 bins of "gap" (session distance from the query to its earliest supporting evidence), so it measures long-range retrieval.
  • The cost model (RQ5). Avg. Operation Latency/Query = construction time + query time (amortized per query). Normalized Utility = mean of 6 min–max-normalized quality metrics.
  • 시스템 튜플 ℳ_sys = ⟨ℛ, 𝒮, 𝒬, 𝒰⟩. 수식이라기보다 정의다. 시스템은 네 기계의 묶음이고, 첨자 없는 ℳ은 그 기계들이 쓰고 읽고 늙히는 데이터다.
  • EM & Answer F1 (LoCoMo). EM은 답 문자열이 정답과 정확히 같은지(1/0), F1은 토큰 겹침 F1이다. 둘 다 LoCoMo 4개 쿼리 범주의 비가중 평균이다.
  • Substring EM, ROUGE-L, LLM-Judge (LongMemEval). Substring EM은 정답이 답 안에 있는지, ROUGE-L은 최장 공통 부분수열 겹침(F1·recall)을 본다. LLM-Judge 정확도는 GPT-5.4 판정자가 매기며, 표현이 달라도 맞는 답을 잡는다.
  • Task Success Rate (DB-Bench). 실행된 DB 조작이 올바른 최종 상태에 도달했는지 본다. 그래서 Long Context는 DB-Bench EM은 이겨도 Task Success Rate는 질 수 있다.
  • 증거 거리 구간별 Recall@K (RQ2). 상위 K개 소스-id 그룹에 정답 증거가 있으면 적중이다. 쿼리와 최초 지지 증거 사이의 세션 거리("갭")를 6구간으로 나눠 장거리 검색을 잰다.
  • 비용 모델 (RQ5). 쿼리당 평균 연산 레이턴시 = 구축 시간 + 쿼리 시간(쿼리당 상각). 정규화 유틸리티 = min–max 정규화한 품질 지표 6개의 평균.

5 Discussion — are we ready? and our read 시사점: 준비됐나? 그리고 우리 관점

5.1 — The answer to the title, and the design recipe 5.1 제목에 대한 답과 설계 레시피

The implicit verdict is not yet. The conclusion doesn't declare a winner or ship a finished "agent-native" design; it gives users a way to pick an architecture by their bottleneck, plus an open testbed. The recurring thesis is Workload-Aligned Memory: match the structure to the dominant bottleneck.

암묵적 답은 아직 아니다. 결론은 승자나 완성된 "에이전트 네이티브" 설계 대신, 병목에 맞춰 아키텍처를 고르는 법과 오픈 테스트베드를 내놓는다. 핵심 논지는 구조를 지배적 병목에 맞추는 워크로드 정렬 메모리다.

  • Dispersed cross-session reasoning: relation/time-aware retrieval (Zep, Cognee)
  • Exact grounding in coherent dialogue: coarse-to-fine filtering (MemOS, MemoryOS)
  • Stateful execution: trace preservation (Long Context)
  • 흩어진 세션 간 추론: 관계/시간 인지 검색(Zep, Cognee)
  • 일관된 대화의 정확한 grounding: coarse-to-fine 필터링(MemOS, MemoryOS)
  • 상태 기반 실행: trace 보존(Long Context)

Concrete design recommendations:

설계 권고는 여섯 가지다.

  1. Build revisability into the representation: bind later facts to the same entity/event instead of appending undifferentiated text.
  2. Treat early localization and evidence assembly as separate targets.
  3. Preserve coverage at write time and filter late.
  4. Prefer conservative consolidation.
  5. Localize maintenance to bounded subsets to control cost.
  6. Scale the backbone only after grounding already works.
  1. 나중 사실을 같은 엔티티/이벤트에 묶어 수정할 수 있게 표현한다. 구분 없는 텍스트를 덧붙이지 않는다.
  2. 초기 위치추정과 증거 조립을 별개 목표로 다룬다.
  3. 쓰기 시점에는 커버리지를 보존하고 필터링은 늦게 한다.
  4. 통합은 보수적으로 한다.
  5. 비용을 잡으려면 유지관리를 한정된 부분집합으로 국소화한다.
  6. 백본은 grounding이 된 뒤에 키운다.

Open challenges: retrieval that doesn't decay with time, lifecycle management that resolves stale-vs-current, consolidation that preserves order, and structure that avoids global recomputation.

남은 과제는 시간에 감쇠하지 않는 검색, 낡은 사실과 최신 사실을 가리는 라이프사이클 관리, 순서를 지키는 통합, 전역 재계산 없는 구조다.

5.3 — Our read (not the paper's claims) 5.3 우리 관점 (논문의 주장 아님)

editor's note — implications for serving & agents편집자 주: 서빙·에이전트 관점의 함의 (논문의 주장 아님)
  1. Write propagation is the latency tax. Cost tracks how widely each write propagates, like write-amplification in an LSM-tree store. Global re-embedding / graph-rebuild on every write is the anti-pattern; bounded, localized updates are the frontier.
  2. Don't reflexively swap long context for a memory store. For time-sensitive workloads the KV-cache of a long window preserves order that consolidation throws away, and prefix-caching makes re-reading it cheaper than people assume.
  3. Spend eval budget on the memory tier. Grounding happens before generation (backbone-invariance), so test memory designs on a cheap backbone first.
  4. Recipe for our agent stacks: preserve raw evidence, filter at retrieval, consolidate conservatively, and measure write-path latency as a first-class metric alongside answer quality.
  1. 쓰기 전파 범위가 곧 레이턴시 세금이다. 비용은 쓰기 하나가 퍼지는 범위를 따르며, LSM-tree의 write-amplification과 같은 구조다. 쓰기마다 전역 재임베딩·그래프 재구축을 하는 것은 안티패턴이고, 국소 업데이트가 프론티어다.
  2. 롱컨텍스트를 반사적으로 메모리 저장소로 바꾸지 말자. 시간 민감 워크로드에서는 긴 창의 KV-cache가 통합이 버리는 순서를 지킨다. prefix caching이 있으면 다시 읽는 비용도 싸다.
  3. 평가 예산은 메모리 계층에 쓴다. grounding은 생성 전에 끝나므로(백본 불변성) 메모리 설계는 값싼 백본으로 먼저 시험하면 된다.
  4. 우리 에이전트 스택의 레시피는 원시 증거 보존, 검색 시점 필터링, 보수적 통합이다. 쓰기 경로 레이턴시도 답 품질만큼 중요한 지표로 잰다.
