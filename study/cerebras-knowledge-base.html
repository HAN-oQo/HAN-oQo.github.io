one-line summary한 줄 요약
  • Cerebras built an internal knowledge base (search-and-answer over company data) that gets 15,000+ questions/day from humans, automations, and agents.
  • Two ideas carry it: "meet data where it lives" (pull from Slack, GitHub, Jira, and docs directly) and one Postgres embeddings table that every source lands in.
  • Plain vector search wasn't enough, so they layered full-text + embeddings + rarity (IDF) + age-decay, had an LLM distill each Slack thread, fused results with Reciprocal Rank Fusion, then finished with a small reranker and a synthesis LLM.
  • The pieces are exposed as MCP tools so an agent (e.g. Claude Code) can orchestrate. A single vendor blog with almost no performance numbers: read it as a design retrospective, not a benchmark.
  • Cerebras는 사람·자동화·에이전트가 하루 15,000개 이상 질문하는 사내 지식베이스(회사 데이터 위 검색·응답 시스템)를 만들었다.
  • 두 아이디어가 바탕이다. "데이터가 사는 곳으로"(Slack·GitHub·Jira·문서에서 직접 가져온다), 그리고 모든 소스가 모이는 Postgres 임베딩 테이블 하나다.
  • 벡터 검색만으로는 부족해서 full-text + 임베딩 + 희귀도(IDF) + 시간 감쇠를 겹쳐 쓰고, LLM으로 Slack 스레드를 증류(distill)하고, Reciprocal Rank Fusion으로 결과를 합친 뒤 작은 reranker와 종합 LLM으로 마무리한다.
  • 부품은 MCP 도구로 노출되어 에이전트(예: Claude Code)가 조합한다. 성능 수치가 거의 없는 단일 벤더 블로그라 벤치마크가 아니라 설계 회고로 읽어야 한다.

Glossary: the retrieval words, in plain language용어집: 검색 용어를 쉬운 말로

embedding / vector search임베딩 / 벡터 검색

An embedding turns text into a vector of numbers that captures its meaning, and vector search finds the nearest ones. Good for paraphrase, blurry on exact strings.임베딩은 글을 의미를 담은 숫자 벡터로 바꾸고, 벡터 검색은 질의와 가장 가까운 벡터를 찾는다. 패러프레이즈에 강하고 정확한 문자열에 약하다.

RAG

Retrieval-Augmented Generation: retrieve relevant documents, then have an LLM generate a cited answer from them. This whole system is one big RAG pipeline.Retrieval-Augmented Generation. 관련 문서를 검색한 뒤 LLM이 그 문서로 인용 달린 답을 생성한다. 이 시스템 전체가 큰 RAG 파이프라인이다.

full-text / lexical search풀텍스트 / 어휘 검색

Keyword search on the exact words (a GIN index in Postgres). Ideal for error strings, flag names, hostnames.정확한 단어로 찾는 전통 키워드 검색이다(Postgres는 GIN 인덱스). 에러 문자열·플래그명·호스트명에 강하다.

IDF

Inverse Document Frequency, a rarity score: common words ("thanks!") count little, rare ones (an obscure config flag) count a lot.Inverse Document Frequency는 희귀도 점수다. 흔한 단어("고마워요!")는 낮고, 희귀한 단어(잘 안 쓰는 설정 플래그)는 높다.

RRF

Reciprocal Rank Fusion merges ranked lists by summing 1/(k+rank) votes, so consensus wins with no weight tuning.Reciprocal Rank Fusion은 목록마다 1/(k+순위) 표를 더해 순위를 합친다. 가중치 튜닝 없이 여러 검색기가 함께 높게 본 문서가 이긴다.

reranker

A small model that scores the query and each shortlisted candidate together. Slower, so it runs only on the top candidates.질의와 후보를 함께 읽고 점수를 매기는 작은 모델이다. 느려서 상위 후보에만 쓴다.

distillation (here)증류 (여기선)

Not model distillation: an LLM boils a messy Slack thread down to a clean record (question, summary, resolution, systems mentioned), and that record is embedded.모델 증류가 아니다. LLM이 지저분한 Slack 스레드를 압축해 질문·요약·해결책·언급된 시스템을 담은 레코드로 만들고, 이 레코드를 임베딩한다.

chunking청킹

Splitting long docs or code into pieces embedded separately. Cerebras splits code by structure (class → method → block).긴 문서나 코드를 조각으로 나눠 따로 임베딩하는 것이다. Cerebras는 코드를 구조(클래스 → 메서드 → 블록)로 나눈다.

MCP

Model Context Protocol, a standard for exposing agent-callable tools. Each search primitive is an MCP tool, so an agent like Claude Code becomes the orchestrator.Model Context Protocol은 AI 에이전트가 호출할 도구를 노출하는 표준이다. 검색 기능마다 MCP 도구로 노출해 Claude Code 같은 에이전트가 오케스트레이터가 된다.

1What it is, and the problem: "meet data where it lives"무엇이고 어떤 문제인가: "데이터가 사는 곳으로"

"Cerebras Knowledge" is an internal search-and-answer system: an employee asks a question in plain English and gets a cited answer drawn from the company's Slack, code, wikis, and databases. It launched three months before the post and is already one of the most-used internal tools. "Cerebras Knowledge"는 사내 검색·응답 시스템이다. 직원이 평범한 말로 물으면 회사 Slack·코드·위키·DB에서 찾은 답을 인용과 함께 돌려준다. 글이 나오기 3개월 전에 출시됐는데 벌써 사내에서 가장 많이 쓰는 도구 중 하나가 됐다.

"Employees ask our internal knowledge base more than 15,000 questions every day. It's become one of the most widely adopted internal tools at the company since launching 3 months ago. Used by humans, automations and agents."

— Cerebras, "How Cerebras Built Its Enterprise Knowledge Base" · cerebras.ai

Note "used by humans, automations and agents": the same system answers a person in a web UI and feeds an AI coding agent. That dual audience shapes the design (§6). "사람·자동화·에이전트가 사용"한다는 점이 중요하다. 같은 시스템이 웹 UI에서 사람에게 답하고, AI 코딩 에이전트에도 결과를 넘긴다. 이 이중 청중이 설계를 정한다(§6).

The problem: information is scattered, and "put it all in one place" never works문제: 정보는 흩어져 있고, "한 곳에 모으자"는 늘 실패한다

With hundreds of new hires a year, the same questions ("where's X? who knows Y? what's Z?") kept clogging chat. Forcing everyone to record everything in one platform is the tempting fix, and a trap: 해마다 수백 명이 입사하니 "X 어디 있어? Y 누가 알아? Z가 뭐야?" 같은 질문이 채팅을 계속 메웠다. 모두에게 한 플랫폼에만 기록하라고 강제하는 해법은 솔깃하지만 함정이다.

"The dream of a single source of truth, of course, rarely works in practice. Information is generated wherever it is convenient and ergonomic: suggested edits in a document, threads in Slack, code references in GitHub, and status metadata in Jira."

— Cerebras blog · cerebras.ai

So they inverted it: don't move the data, meet it where it lives. Extract from each platform directly and change no one's habits. Let Slack be Slack and GitHub be GitHub, and index across all of them. 그래서 거꾸로 했다. 데이터를 옮기지 않고 데이터가 있는 곳으로 찾아간다. 각 플랫폼에서 직접 추출하니 누구의 습관도 바꿀 필요가 없다. Slack은 Slack대로, GitHub은 GitHub대로 두고 전부를 가로질러 인덱싱한다.

expectation check: this is a RAG post, not a chip post기대 점검: 칩이 아니라 RAG 글이다 Cerebras is famous for wafer-scale chips and very fast inference, but this post barely mentions hardware. Read it for RAG design patterns, not a speed benchmark. Cerebras는 웨이퍼 스케일 칩과 초고속 추론으로 유명하지만, 이 글은 하드웨어를 거의 다루지 않는다. 속도 벤치마크가 아니라 RAG 설계 패턴을 보는 글이다.

2The whole thing is one embeddings table전부가 임베딩 테이블 하나

The knowledge base provides three things: a place to collect and store internal data, a way to query it, and a layer that enforces authentication and authorization (who may see what) with auditing and analytics. The storage is surprisingly simple: 지식베이스는 세 가지를 제공한다. 사내 데이터를 수집·저장하는 곳, 이를 질의하는 방법, 그리고 감사·분석과 함께 인증·인가(누가 무엇을 볼 수 있나)를 강제하는 층이다. 저장 구조는 의외로 단순하다.

"At the core is a single Postgres table that holds embeddings, raw summaries, and metadata from many sources… every source, from Slack threads to netlists, lands in the same embeddings table, and anything in that table is immediately queryable through the same interface."

— Cerebras blog · cerebras.ai

(Netlists are chip-design files, so "from Slack threads to netlists" means "from casual chat to deeply technical artifacts, same table.") Each data source declares what the data is, how to connect to it, and how often to re-fetch. Its output must be shaped like a standard embeddings row, so the rest of the system never needs to know where a row came from. (넷리스트(netlist)는 칩 설계 파일이다. "Slack 스레드부터 넷리스트까지"는 가벼운 잡담부터 깊은 기술 산출물까지 같은 테이블에 넣는다는 뜻이다.) 각 데이터 소스는 데이터가 무엇인지, 어떻게 연결하는지, 얼마나 자주 다시 가져올지를 선언한다. 출력은 표준 임베딩 행 형태여야 하므로 나머지 시스템은 행의 출처를 몰라도 된다.

Fig 1 · Ingestion: many sources, one Postgres table, one query interface. Redrawn from the Cerebras blog.그림 1 · 수집: 여러 소스, Postgres 테이블 하나, 질의 인터페이스 하나. Cerebras 블로그 재구성.

Why this matters: because the schema is uniform, adding a new kind of data (a team's private database) is just a small script that emits rows in this shape. It's the same "don't make it a special snowflake" instinct from the Netflix note, applied to data sources instead of models. 스키마가 균일하니 새 종류의 데이터(팀의 사설 DB)를 붙일 때는 이 형태의 행을 내보내는 작은 스크립트 하나면 된다. Netflix 노트에서 본 "특별한 눈송이로 만들지 말자"는 감각을 모델 대신 데이터 소스에 적용한 셈이다.

3The hard part: making messy Slack searchable어려운 부분: 지저분한 Slack을 검색 가능하게

Slack is the most valuable source (live engineering discussion happens there) and the hardest to search. Embedding raw messages for vector search failed fast: Slack은 살아 있는 엔지니어링 토론이 오가는 가장 값진 소스이자, 검색하기 가장 어려운 소스다. 원문 메시지를 임베딩해 벡터 검색하는 단순한 방식은 금방 한계를 드러냈다.

"We quickly realized that vector search alone was insufficient for matching all relevant data."

— Cerebras blog · cerebras.ai

Why: message length and quality vary wildly ("hey yeah sure mike" vs a detailed kernel explanation), short messages often win on raw similarity, and meaning depends on context. The fix is a hybrid of four scorers that cover each other's blind spots. 메시지 길이와 품질이 제각각이고("ㅇㅇ 그래 마이크" vs 상세한 커널 설명), 원시 유사도에서는 짧은 메시지가 긴 메시지를 자주 이기며, 의미가 주변 문맥에 달려 있기 때문이다. 해법은 서로의 사각지대를 메우는 스코어러 네 개를 섞은 하이브리드다.

Four signals, one worked example네 가지 신호, 하나의 실제 예

Take the query "restore hangs after manifest load". Here's how each signal votes on candidate messages: 질의 "restore hangs after manifest load"로 각 신호가 후보 메시지에 어떻게 투표하는지 보자.

Signal신호Catches잡는 것In the example예에서
Full-text (GIN)exact tokens: error strings, flags, hostnames정확한 토큰: 에러 문자열·플래그·호스트명a message literally saying ERR_MANIFEST_TIMEOUT: restore hangs… is a near-perfect lexical hitERR_MANIFEST_TIMEOUT: restore hangs…라고 그대로 쓴 메시지가 거의 완벽한 어휘 매칭

"When an engineer pastes a literal error message, an exact lexical match is almost always the best evidence, and no amount of semantic similarity should outrank it."

— Cerebras blog (on why full-text search stays in the mix) · cerebras.ai

No single scorer is trusted alone. Each produces its own ranking and they're fused at query time (§5). Embeddings are necessary but not sufficient: real search also needs exact match, rarity, and recency. 어떤 스코어러도 혼자 믿지 않는다. 각자 순위를 내고 질의 시점에 융합한다(§5). 임베딩은 필요하지만 충분하지 않다. 실제 검색에는 정확 매칭, 희귀도, 최신성도 필요하다.

Real-time ingestion, and re-fetching the whole thread실시간 수집, 그리고 스레드 전체 다시 가져오기

A Slack bot runs in Socket Mode: Slack pushes every message over a persistent connection (a WebSocket), so updates arrive in real time without polling into rate limits. On each message they acknowledge it, de-duplicate by event ID, and re-fetch the entire thread (parent + all replies), storing the whole conversation as one row. The stored version is never a half-conversation. Slack 봇은 Socket Mode로 돈다. Slack이 상시 연결(WebSocket)로 모든 메시지를 밀어 주므로, 폴링하다 rate limit에 걸리지 않고 실시간으로 받는다. 메시지가 오면 확인(ack)하고, 이벤트 ID로 중복을 거른 뒤 스레드 전체를 다시 가져와(부모 + 모든 답글) 대화 전체를 한 행으로 저장한다. 그래서 저장본이 반쪽 대화일 일이 없다.

Distillation: let an LLM turn a thread into a clean record증류(distillation): LLM으로 스레드를 깔끔한 레코드로

Raw Slack text is keyword-searchable immediately via the full-text index. For vector search, an LLM first distills each thread into a structured record: a one-line question an engineer would actually search for, a short summary, the resolution, and the systems/code it references. Those fields, not the raw chat, are embedded into a 3,072-dimension vector. 원문 Slack 텍스트는 풀텍스트 인덱스로 바로 키워드 검색된다. 벡터 검색용으로는 원문을 그대로 임베딩하지 않고, LLM이 먼저 스레드를 구조화된 레코드로 증류한다. 레코드에는 엔지니어가 실제로 검색할 한 줄 질문, 짧은 요약, 해결책, 언급된 시스템/코드가 들어간다. 원시 채팅이 아니라 이 필드들을 3,072차원 벡터로 임베딩한다.

"In our experiments, accuracy increased significantly when the thread was normalized into a consistent format. The additional metadata also gives the semantic match more useful signal."

— Cerebras blog · cerebras.ai

Bursting: rescue the good sentence buried in a long threadbursting: 긴 스레드에 묻힌 좋은 한 문장 구하기

A thread-level summary can miss a crucial aside, so they also use bursting: a "burst" is a run of consecutive messages from one author, embedded on its own with the thread's topic prepended. To keep junk out, a burst is embedded only if it contains a rare token (IDF ≥ 4.0), is at least 200 characters, and ideally has emoji reactions (a social signal that it mattered). 스레드 요약 하나가 결정적인 곁가지 발언을 놓칠 수 있어서 bursting도 쓴다. "burst"는 한 작성자의 연속 메시지 묶음이고, 스레드 주제를 앞에 붙여 따로 임베딩한다. 잡음을 막기 위해 희귀 토큰(IDF ≥ 4.0)을 포함하고 최소 200자이며, 가급적 이모지 반응(중요했다는 사회적 신호)이 있는 burst만 임베딩한다.

4Beyond Slack: code and custom sourcesSlack 너머: 코드와 커스텀 소스

Code: is embedding it even worth it?코드: 임베딩할 가치가 있나?

They hesitated: with Claude Code and command-line tools, "grep is all you need" felt plausible. After reading Cursor's findings on semantic search in large codebases, they tried it anyway. The challenge was scale: some internal repos are larger than 40 GB, and re-embedding everything on every change is wasteful. 처음엔 망설였다. Claude Code와 명령줄 도구가 있으니 "grep이면 충분하다"는 말이 그럴듯했다. 그러다 대규모 코드베이스 시맨틱 검색에 관한 Cursor의 결과를 읽고 시도했다. 문제는 규모였다. 일부 사내 레포는 40 GB 이상이라 변경마다 전부 다시 임베딩하면 낭비다.

Solution: CocoIndex, an open-source framework for embedding codebases. Two things make it fit: 해법은 코드베이스 임베딩용 오픈소스 프레임워크 CocoIndex다. 두 가지가 잘 맞았다.

  • Language-aware chunking. Split code coarse to fine: class boundaries first, then methods, then smaller blocks if a chunk is still too big. One file can yield file-level and function-level embeddings, so both "what does this file do" and "where's this exact function" are searchable.언어 인식 청킹. 코드를 굵은 단위부터 쪼갠다. 먼저 클래스 경계로 나누고, 여전히 크면 메서드, 그다음 더 작은 블록으로 내려간다. 한 파일에서 파일 레벨과 함수 레벨 임베딩이 함께 나오므로 "이 파일이 뭘 하나"와 "이 함수가 어디 있나"를 모두 검색할 수 있다.
  • Incremental updates. CocoIndex tracks sync metadata in Postgres and re-embeds only the changed chunks on each commit. It fits well because the sync state and the embedding store live in the same database.증분 업데이트. CocoIndex는 동기화 메타데이터를 Postgres에 기록하고, 커밋마다 바뀐 청크만 다시 임베딩한다. 동기화 상태와 임베딩이 같은 DB에 있어서 특히 잘 맞았다.

Repo onboarding moved into config files teams submit themselves, with per-file-path allowlists and denylists. 레포 온보딩은 팀이 직접 제출하는 설정 파일로 옮겼고, 파일 경로별 allowlist/denylist를 지원한다.

Custom sources: a pull request, not a meeting커스텀 소스: 회의가 아니라 풀 리퀘스트

Some teams already had their own databases and didn't want to move data just to be searchable. So custom sources are plugin scripts: a team opens a pull request with a small Python module that reads its system and emits standard embeddings rows, plus a data-source entry. Everything downstream (search, ranking, the UI) then works with no special handling. This is the payoff of the "one table, one shape" decision from §2. 일부 팀은 이미 자체 DB가 있어서 검색을 위해 데이터를 옮기고 싶어 하지 않았다. 그래서 커스텀 소스는 플러그인 스크립트로 붙인다. 팀은 자기 시스템을 읽어 표준 임베딩 행을 내보내는 작은 Python 모듈과 데이터 소스 항목을 풀 리퀘스트로 올린다. 그러면 검색·랭킹·UI가 특별 처리 없이 동작한다. §2의 "테이블 하나, 형태 하나" 결정이 여기서 효과를 낸다.

5Answering a query: plan → fan out → rerank → synthesize질의에 답하기: 계획 → 병렬 → 재랭킹 → 종합

A question runs through a four-stage pipeline, not a single search: 질문은 검색 하나로 바로 가지 않고 네 단계 파이프라인을 거친다.

Fig 2 · Query pipeline: LLM planner, parallel executor, RRF + reranker, synthesis LLM. Redrawn from the Cerebras blog.그림 2 · 질의 파이프라인: LLM 플래너, 병렬 실행기, RRF + reranker, 종합 LLM. Cerebras 블로그 재구성.

The tools the planner can pick플래너가 고를 수 있는 도구들

The tools go beyond text search:도구는 텍스트 검색에 그치지 않는다.

  • search: the unified vector pipeline across all sources모든 소스를 가로지르는 통합 벡터 파이프라인
  • search_slack, recent_prs
  • search_code: plain ripgrep over repos (not everything needs embeddings)레포에 대한 단순 ripgrep(모든 것에 임베딩이 필요하진 않다)
  • subsystem_index: per-file LLM summaries파일별 LLM 요약
  • who_knows: returns people with demonstrated expertise, answering "who should I ask?" rather than "what's the answer?"검증된 전문성을 가진 사람을 돌려준다. "정답이 뭐야?"가 아니라 "누구에게 물어야 해?"에 답한다.

Reranking: fuse first (RRF), then let a model judge재랭킹: 먼저 융합(RRF), 그다음 모델이 판단

The searchers return incompatible lists (a vector score and a full-text score aren't on the same scale). Cerebras merges them with Reciprocal Rank Fusion (RRF): for each document, add up weight / (60 + rank) across every list it appears in (default weight 1.0, smoothing constant 60). Ranks, not raw scores, are combined, so the scale mismatch stops mattering. 검색기마다 점수 척도가 다르다(벡터 점수와 풀텍스트 점수는 비교할 수 없다). Cerebras는 이를 Reciprocal Rank Fusion (RRF)으로 합친다. 문서가 등장한 모든 목록에서 weight / (60 + 순위)를 더한다(기본 weight 1.0, smoothing 상수 60). 원시 점수가 아니라 순위를 합치므로 척도 차이가 문제되지 않는다.

"The smoothing constant makes consensus matter more than a single strong vote: a document that shows up near the top across several retrievers can beat one that ranks first in only one of them."

— Cerebras blog · cerebras.ai

After fusing to a diverse top-20 (duplicate chunks merged back to their source, with a cap on how many results one file can contribute), a small reranker model reads the query and each candidate together, scores it 0–10, and keeps the top 10. Then they add context back: if a wiki section matched, its two neighboring sections come along, so the heading, preconditions, and caveats that chunking split apart aren't lost. The output is "a rich packet of evidence" for the synthesis LLM. 융합으로 다양한 top-20을 만든 뒤(중복 청크는 원 소스로 병합하고, 한 파일이 차지할 결과 수에 상한을 둔다) 작은 reranker 모델이 질의와 후보를 함께 읽어 0–10점을 매기고 top 10만 남긴다. 마지막으로 남은 문서에 문맥을 되붙인다. 위키 섹션이 매칭되면 이웃한 두 섹션을 함께 가져와, 청킹 과정에서 떨어져 나간 제목·전제조건·주의사항을 살린다. 이렇게 만든 "풍부한 증거 묶음"이 종합 LLM으로 간다.

The per-file cap and neighbor pull answer two known RAG failure modes: one document crowding out diversity, and a lone chunk stripped of its heading/caveats misleading the reader (the "lost in the middle" and context-loss problems the blog cites). 파일별 상한과 이웃 섹션 보강은 알려진 RAG 실패 양상 두 가지에 대한 대응이다. 한 문서가 결과를 독차지하면 다양성이 사라지고, 제목과 주의사항이 떨어진 청크는 오해를 부른다(블로그가 인용하는 "lost in the middle"과 문맥 손실 문제).

6Two front-ends over the same parts: MCP & the Web UI같은 부품 위 두 앞단: MCP & 웹 UI

The audience is "humans, automations, and agents," and Cerebras serves both with the same retrieval primitives, exposed two ways. Cerebras는 같은 검색 프리미티브를 두 방식으로 노출해 사람과 에이전트 양쪽을 서빙한다.

MCP: hand the agent the raw tools, let it orchestrateMCP: 에이전트에게 raw 도구를 주고 오케스트레이션은 맡긴다

Instead of one "answer this question" endpoint, each retrieval primitive is its own MCP tool (search_slack, search_code, search, who_knows), deliberately simple, LLM-free, cheap to call, with narrow, stable inputs/outputs. Then: "이 질문에 답해줘" 엔드포인트 하나에 전부 숨기지 않고, 검색 프리미티브마다 별도 MCP 도구로 노출한다(search_slack, search_code, search, who_knows). 일부러 단순하게 만들어 LLM 없이 돌고, 호출 비용이 싸며, 입출력이 좁고 안정적이다. 그 결과는 이렇다.

"Claude Code, or any MCP-compatible agent, becomes the orchestration engine. It decides which tools to call, in what order, and how to assemble the results… The retrieval layer itself does not depend on those LLM decisions in order to serve requests."

— Cerebras blog · cerebras.ai

The retrieval layer is a set of fast, dumb, reliable primitives. The intelligence (which tool, what order, how to combine) lives in the calling agent and can change without touching retrieval. It's the same "keep the serving layer simple, put smarts at the edge" instinct as exposing an OpenAI-compatible API. 검색 층은 빠르고 단순하고 믿을 만한 프리미티브 모음이다. 어떤 도구를 어떤 순서로 불러 어떻게 결합할지 같은 지능은 호출하는 에이전트가 맡고, 검색 층을 건드리지 않고 바꿀 수 있다. OpenAI 호환 API를 노출할 때의 "서빙 층은 단순하게, 똑똑함은 가장자리에"와 같은 발상이다.

Web UI: the same tools, wired into the full pipeline웹 UI: 같은 도구를 풀 파이프라인에 연결

For humans, the same tools are wired end-to-end into the §5 pipeline: a planner LLM pass picks tools, an executor fans them out and normalizes results, and a synthesis LLM writes the cited answer. It's the same planner → executor → synthesizer that an MCP agent would recreate explicitly. One set of parts, two audiences. 사람을 위해서는 같은 도구를 §5 파이프라인에 end-to-end로 연결한다. 플래너 LLM이 도구를 고르고, 실행기가 병렬로 호출해 결과를 정규화하고, 종합 LLM이 인용 달린 답을 쓴다. MCP 에이전트가 직접 재현할 planner → executor → synthesizer 구조와 같다. 부품 한 벌로 두 청중을 받는다.

Projects: because "search everything" stops being usefulProjects: "전부 검색"이 쓸모없어지므로

As the corpus grew, searching everything got noisy: compiler engineers didn't want infrastructure runbooks in their results, and vice versa. So a project is a named bundle of data sources (specific Slack channels, repos, databases, doc spaces) for a team or initiative, and sources can be shared across projects instead of duplicated. At onboarding a user picks a default project (ML Training Infra, Compiler, Data Center Ops…) that scopes their queries automatically, so a new engineer gets high-signal answers without first learning which channels and repos matter. 코퍼스가 커지자 전체 검색 결과가 시끄러워졌다. 컴파일러 엔지니어는 인프라 런북이 결과에 섞이길 원하지 않았고, 반대도 마찬가지였다. 그래서 팀이나 이니셔티브별로 데이터 소스(특정 Slack 채널·레포·DB·문서 공간)를 묶어 이름 붙인 project를 만들었다. 소스는 복제하지 않고 여러 프로젝트가 공유한다. 사용자가 온보딩 때 기본 프로젝트(ML Training Infra, Compiler, Data Center Ops…)를 고르면 질의 범위가 자동으로 좁혀진다. 신규 엔지니어는 어떤 채널과 레포가 중요한지 몰라도 쓸모 있는 답을 받는다.

7What's reusable, and honest limits (no code-walk)재사용 가능한 것, 그리고 정직한 한계 (코드 분석 없음)

Our deep-dives usually trace real code with commit-pinned links. Not here: Cerebras Knowledge is an internal tool with no public repository. But it's built from public, reusable parts, and the design patterns transfer even if the code doesn't: 우리 딥다이브는 보통 commit에 고정한 링크로 실제 코드를 따라간다. 이번엔 그럴 수 없다. Cerebras Knowledge는 공개 저장소가 없는 사내 도구다. 다만 공개된 부품으로 만들어졌고, 코드는 못 옮겨도 설계 패턴은 옮길 수 있다.

MCP

No accuracy, latency, or precision/recall figures, and no independent verification. The post's interactive diagrams illustrate patterns, not measurements. 한계: Cerebras 자체 서술인 단일 회사 블로그이고 구체 수치가 거의 없다(하루 15,000 질문, 출시 3개월, 3,072차원 임베딩, IDF ≥ 4.0, RRF 상수 60, top-20 → top-10). 정확도·지연·정밀도/재현율 수치도, 독립 검증도 없다. 글의 인터랙티브 다이어그램은 측정이 아니라 패턴 예시다.

editor's note: our angle (not a Cerebras claim)편집자 주: 우리 관점 (Cerebras 주장 아님)
  1. The retrieval recipe is directly reusable. "Embeddings alone are not enough → fuse full-text + vector + rarity + recency with RRF, rerank, re-attach context" is the current best-practice shape for production RAG over real, messy internal data.
  2. The MCP separation is the sharpest idea. Keep retrieval as fast, LLM-free primitives and let an agent be the brain. It mirrors the "serving layer stays simple, intelligence at the edge" pattern we like in llm-d / agentic serving, and it's how an MCP-tool + Claude Code setup would consume our own infra.
  3. Boundaries. No performance data, and much of the value is Cerebras-specific data plumbing (Slack Socket Mode, per-channel freshness, distillation prompts). What transfers is the shape of the pipeline, not the wiring.
  1. 검색 레시피를 그대로 가져다 쓸 수 있다. "임베딩만으론 부족 → full-text + 벡터 + 희귀도 + 최신성을 RRF로 융합 → rerank → 문맥 재부착"은 지저분한 사내 데이터를 다루는 프로덕션 RAG의 현재 모범 형태다.
  2. MCP 분리가 가장 날카로운 아이디어다. 검색 층은 LLM 없는 빠른 프리미티브로 두고 에이전트가 두뇌 역할을 한다. llm-d / agentic serving에서 선호하는 "서빙 층은 단순, 지능은 가장자리" 패턴과 같고, MCP 도구 + Claude Code 조합이 우리 인프라를 쓰는 방식 그대로다.
  3. 한계. 성능 데이터가 없고, 가치의 상당 부분은 Cerebras 도구에 특화된 데이터 배관(Slack Socket Mode, 채널별 신선도, distillation 프롬프트)이다. 옮겨 갈 수 있는 건 배선이 아니라 파이프라인의 형태다.
