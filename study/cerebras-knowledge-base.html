one-line summary한 줄 요약 Cerebras built an internal knowledge base (a search-and-answer system over company data) that gets 15,000+ questions/day from humans, automations, and agents. Two ideas carry it: (1) "meet data where it lives" — pull from Slack, GitHub, Jira, and docs directly rather than forcing a single source of truth; and (2) one Postgres embeddings table that every source lands in and is queried through. The real engineering is retrieval quality: plain vector search wasn't enough, so they layered full-text + embeddings + rarity (IDF) + age-decay, used an LLM to distill each Slack thread into a clean record, fused results with Reciprocal Rank Fusion, and finished with a small reranker and a synthesis LLM. They expose the pieces as MCP tools so an agent (e.g. Claude Code) can orchestrate. It's a single vendor blog with almost no performance numbers — read it as a design retrospective, not a benchmark. Cerebras는 사람·자동화·에이전트가 하루 15,000개 이상 질문하는 사내 지식베이스(회사 데이터 위 검색·응답 시스템)를 만들었다. 두 아이디어가 떠받친다: (1) "데이터가 사는 곳으로" — 단일 진실 공급원을 강요하는 대신 Slack·GitHub·Jira·문서에서 직접 긁어옴; (2) Postgres 임베딩 테이블 하나 — 모든 소스가 여기 들어가고 여기로 검색됨. 진짜 엔지니어링은 검색 품질: 단순 벡터 검색으론 부족해서 full-text + 임베딩 + 희귀도(IDF) + 시간 감쇠를 층층이 쌓고, LLM으로 각 Slack 스레드를 깔끔한 레코드로 증류(distill)하고, 결과를 Reciprocal Rank Fusion으로 융합한 뒤, 작은 reranker와 종합 LLM으로 마무리. 부품들을 MCP 도구로 노출해 에이전트(예: Claude Code)가 오케스트레이션. 성능 수치가 거의 없는 단일 벤더 블로그 — 벤치마크가 아니라 설계 회고로 읽을 것.

Glossary — the retrieval words, in plain language (read this first)용어집 — 검색 용어를 쉬운 말로 (먼저 읽기)

embedding / vector search임베딩 / 벡터 검색

An embedding turns a piece of text into a list of numbers (a "vector") that captures its meaning — similar meanings sit close together. Vector search finds the texts whose vectors are nearest to the query's. Great for paraphrase, blurry on exact strings.임베딩은 글을 의미를 담은 숫자 목록("벡터")으로 바꾼다 — 뜻이 비슷하면 가까이 위치. 벡터 검색은 질의 벡터에 가장 가까운 글을 찾음. 패러프레이즈엔 강하고, 정확한 문자열엔 흐릿.

RAG

Retrieval-Augmented Generation: first retrieve relevant documents, then feed them to an LLM to generate a grounded answer with citations — instead of relying on the model's memory. This whole system is a big RAG pipeline.Retrieval-Augmented Generation: 먼저 관련 문서를 검색하고, 그걸 LLM에 넣어 인용 있는 근거 답변을 생성 — 모델 기억에 의존하지 않고. 이 시스템 전체가 큰 RAG 파이프라인.

full-text / lexical search풀텍스트 / 어휘 검색

Old-school keyword search on the exact words (Postgres does it with a GIN index). Perfect for error strings, flag names, hostnames — the things embeddings blur.정확한 단어에 대한 전통 키워드 검색(Postgres는 GIN 인덱스로). 에러 문자열·플래그명·호스트명 — 임베딩이 흐리는 것들 — 에 완벽.

IDF

Inverse Document Frequency — a rarity score. Words that appear everywhere ("thanks!") count for little; rare words (an obscure config flag) count for a lot. Separates signal from filler.Inverse Document Frequency — 희귀도 점수. 어디나 나오는 단어("고마워요!")는 값이 작고, 희귀한 단어(무명 설정 플래그)는 큼. 신호와 잡음을 가른다.

RRF

Reciprocal Rank Fusion — a simple way to merge several ranked lists into one: each list votes with 1/(k+rank). A doc that several searchers rank highly beats one that a single searcher loved. No tuning weights needed.Reciprocal Rank Fusion — 여러 순위 목록을 하나로 합치는 단순한 방법: 각 목록이 1/(k+순위)로 투표. 여러 검색기가 상위에 올린 문서가 한 검색기만 사랑한 문서를 이김. 가중치 튜닝 불필요.

reranker

A small model that looks at the query and a shortlist of candidates together and scores how well each truly answers it. Slower per item than search, so it's run only on the top candidates, as a final filter.질의와 후보 목록을 함께 보고 각 후보가 얼마나 잘 답하는지 점수 매기는 작은 모델. 검색보다 항목당 느려서, 상위 후보에만 최종 필터로 실행.

distillation (here)증류 (여기선)

Not model distillation — here it means using an LLM to boil a messy Slack thread down to a clean record: a one-line question, a summary, the resolution, and the systems/code it mentions. That clean record is what gets embedded.모델 증류가 아니라, 여기선 LLM으로 지저분한 Slack 스레드를 압축해 깔끔한 레코드로: 한 줄 질문, 요약, 해결책, 언급된 시스템/코드. 그 깔끔한 레코드를 임베딩한다.

chunking청킹

Splitting a long document (or big code file) into smaller pieces so each can be embedded and retrieved on its own. Cerebras chunks code by language structure (class → method → block).긴 문서(또는 큰 코드 파일)를 작은 조각으로 쪼개 각각 임베딩·검색되게. Cerebras는 코드를 언어 구조로 쪼갬(클래스 → 메서드 → 블록).

MCP

Model Context Protocol — a standard way to expose "tools" that an AI agent can call. Cerebras exposes each search primitive as an MCP tool, so an agent like Claude Code becomes the orchestrator that decides which tools to call.Model Context Protocol — AI 에이전트가 호출할 "도구"를 노출하는 표준. Cerebras는 각 검색 기능을 MCP 도구로 노출해, Claude Code 같은 에이전트가 어떤 도구를 부를지 정하는 오케스트레이터가 되게 한다.

1What it is, and the problem — "meet data where it lives"무엇이고 어떤 문제인가 — "데이터가 사는 곳으로"

"Cerebras Knowledge" is an internal search-and-answer system: an employee asks a question in plain English and gets an answer drawn from the company's own Slack, code, wikis, and databases — with citations. It launched three months before the post and is already one of the most-used internal tools: "Cerebras Knowledge"는 사내 검색·응답 시스템이다: 직원이 평범한 말로 질문하면 회사의 Slack·코드·위키·DB에서 끌어온 답을 — 인용과 함께 — 받는다. 글이 나오기 3개월 전 출시됐고 이미 가장 많이 쓰이는 사내 도구 중 하나다:

"Employees ask our internal knowledge base more than 15,000 questions every day. It's become one of the most widely adopted internal tools at the company since launching 3 months ago. Used by humans, automations and agents."

— Cerebras, "How Cerebras Built Its Enterprise Knowledge Base" · cerebras.ai

Note "used by humans, automations and agents" — the same system answers a person in a web UI and feeds an AI coding agent. That dual audience shapes the design (see §6). "사람·자동화·에이전트가 사용"에 주목 — 같은 시스템이 웹 UI의 사람에게 답하고 동시에 AI 코딩 에이전트에도 공급한다. 이 이중 청중이 설계를 형성한다(§6 참고).

The problem: information is scattered, and "put it all in one place" never works문제: 정보는 흩어져 있고, "한 곳에 모으자"는 늘 실패한다

With hundreds of new hires a year, the same questions ("where's X? who knows Y? what's Z?") kept clogging chat. The tempting fix — force everyone to record everything in one platform — is a trap: 연간 수백 명이 입사하니 같은 질문("X 어디 있어? Y 누가 알아? Z가 뭐야?")이 채팅을 계속 막았다. 솔깃한 해법 — 모두에게 모든 걸 한 플랫폼에 기록하게 강제 — 은 함정이다:

"The dream of a single source of truth, of course, rarely works in practice. Information is generated wherever it is convenient and ergonomic: suggested edits in a document, threads in Slack, code references in GitHub, and status metadata in Jira."

— Cerebras blog · cerebras.ai

So they inverted it: don't move the data, meet it where it lives — extract from each platform directly, changing no one's habits. Discussing a pull request in Google Docs would be miserable; let Slack be Slack and GitHub be GitHub, and index across all of them. 그래서 뒤집었다: 데이터를 옮기지 말고 있는 곳으로 찾아간다 — 각 플랫폼에서 직접 추출하되 누구의 습관도 안 바꾼다. 풀 리퀘스트를 Google Docs에서 논하는 건 끔찍하다; Slack은 Slack, GitHub은 GitHub이게 두고, 그 전부를 가로질러 인덱싱한다.

expectation check — this is a RAG post, not a chip post기대 점검 — 칩이 아니라 RAG 글이다 Cerebras is famous for wafer-scale chips and very fast inference, so you might expect this to be about tokens-per-second. It isn't. The post barely mentions their hardware; it's a practical retrieval-engineering write-up. Read it for the RAG design patterns, not for a speed benchmark. Cerebras는 웨이퍼 스케일 칩과 초고속 추론으로 유명해서 이 글도 초당 토큰 얘기일 것 같지만, 아니다. 글은 하드웨어를 거의 언급하지 않는다; 실전 검색 엔지니어링 글이다. 속도 벤치마크가 아니라 RAG 설계 패턴을 보러 읽으라.

2The whole thing is one embeddings table전부가 임베딩 테이블 하나

The knowledge base provides three things: a place to collect and store internal data, a way to query it, and a layer that enforces authentication and authorization (who's allowed to see what) with auditing and analytics. The surprising part is how simple the storage is: 지식베이스는 세 가지를 제공한다: 사내 데이터를 수집·저장할 곳, 그걸 질의할 방법, 그리고 인증·인가(누가 무엇을 볼 수 있나)를 감사·분석과 함께 강제하는 층. 놀라운 건 저장이 얼마나 단순한가다:

"At the core is a single Postgres table that holds embeddings, raw summaries, and metadata from many sources… every source, from Slack threads to netlists, lands in the same embeddings table, and anything in that table is immediately queryable through the same interface."

— Cerebras blog · cerebras.ai

(Netlists are chip-design files — Cerebras is a chip company — so "from Slack threads to netlists" just means "from casual chat to deeply technical artifacts, same table.") Each data source declares three things: what the data is, how to connect to it, and how often to re-fetch. Whatever it produces must come out shaped like a standard embeddings row — so the rest of the system never needs to know where a row came from. (넷리스트(netlist)는 칩 설계 파일이다 — Cerebras는 칩 회사 — 그러니 "Slack 스레드부터 넷리스트까지"는 "가벼운 채팅부터 깊이 기술적인 산출물까지, 같은 테이블"이란 뜻.) 각 데이터 소스는 셋을 선언한다: 데이터가 무엇인지, 어떻게 연결하는지, 얼마나 자주 다시 가져오는지. 무엇을 만들든 표준 임베딩 행 형태로 나와야 한다 — 그래서 시스템의 나머지는 행이 어디서 왔는지 알 필요가 없다.

Data stays in its home tool; a per-source connector pulls it, an LLM distills/chunks it, and every result lands as an identically-shaped row in one Postgres table (embedding + summary + metadata, with a full-text index alongside). One table → one query interface. Redrawn from the Cerebras blog.그림 1 — 수집. 데이터는 원래 도구에 남고, 소스별 커넥터가 당겨오고, LLM이 증류/청킹하고, 모든 결과가 동일한 형태의 행으로 하나의 Postgres 테이블에 안착(임베딩 + 요약 + 메타데이터, 옆에 풀텍스트 인덱스). 테이블 하나 → 질의 인터페이스 하나. Cerebras 블로그 재구성.

Why this matters: because the storage schema is uniform, adding a brand-new kind of data (a team's private database) is just "write a small script that emits rows in this shape" — no changes anywhere else. That's the same "don't make it a special snowflake" instinct we saw in the Netflix note, applied to data sources instead of models. 왜 중요한가: 저장 스키마가 균일하니, 완전히 새로운 종류의 데이터(팀의 사설 DB)를 추가하는 건 그저 "이 형태의 행을 뱉는 작은 스크립트 작성" — 다른 어디도 안 바꿈. Netflix 노트에서 본 "특별한 눈송이로 만들지 말자" 본능을 모델 대신 데이터 소스에 적용한 것.

3The hard part — making messy Slack searchable어려운 부분 — 지저분한 Slack을 검색 가능하게

Slack is the single most valuable source (it's where live engineering discussion happens) and the hardest to search. The naive approach — embed the raw messages and do vector search — failed fast: Slack은 가장 값진 단일 소스(살아있는 엔지니어링 토론이 벌어지는 곳)이자 검색이 가장 어렵다. 순진한 접근 — 원문 메시지를 임베딩하고 벡터 검색 — 은 금방 실패했다:

"We quickly realized that vector search alone was insufficient for matching all relevant data."

— Cerebras blog · cerebras.ai

Why: message length and quality vary wildly ("hey yeah sure mike" vs a detailed kernel explanation), short messages often beat long ones in raw similarity, and meaning depends on surrounding context. The fix is a hybrid: four different scorers, each covering the others' blind spots, fused together. 이유: 메시지 길이·품질이 극단적으로 다르고("ㅇㅇ 그래 마이크" vs 상세한 커널 설명), 짧은 메시지가 원시 유사도에서 긴 것을 자주 이기며, 의미가 주변 문맥에 의존한다. 해법은 하이브리드: 서로의 사각지대를 메우는 네 개의 스코어러를 융합.

Four signals, one worked example네 가지 신호, 하나의 실제 예

Take the query "restore hangs after manifest load". Here's how each signal votes on candidate messages: 질의 "restore hangs after manifest load"를 보자. 각 신호가 후보 메시지에 어떻게 투표하는지:

Full-text (GIN)exact tokens — error strings, flags, hostnames정확한 토큰 — 에러 문자열·플래그·호스트명a message literally saying ERR_MANIFEST_TIMEOUT: restore hangs… is a near-perfect lexical hitERR_MANIFEST_TIMEOUT: restore hangs…라고 그대로 쓴 메시지가 거의 완벽한 어휘 매칭

"When an engineer pastes a literal error message, an exact lexical match is almost always the best evidence, and no amount of semantic similarity should outrank it."

— Cerebras blog (on why full-text search stays in the mix) · cerebras.ai

No single scorer is trusted alone; each produces its own ranked view and they're fused at query time (the fusion math is in §5). The lesson: embeddings are necessary but not sufficient — real search needs exact-match and rarity and recency too. 어떤 스코어러도 혼자 신뢰받지 않는다; 각자 순위 뷰를 내고 질의 때 융합된다(융합 수식은 §5). 교훈: 임베딩은 필요하지만 충분하지 않다 — 실제 검색엔 정확 매칭·희귀도·최신성도 필요.

Real-time ingestion, and re-fetching the whole thread실시간 수집, 그리고 스레드 전체 다시 가져오기

A Slack bot runs in Socket Mode — Slack pushes every message to Cerebras over a persistent connection (a WebSocket), so they get updates in real time without constantly polling and hitting rate limits. When a message arrives they acknowledge it, de-duplicate by its event ID, and — importantly — re-fetch the entire thread (parent + all replies) and store the whole conversation as one row. A single new reply refreshes the complete thread, so the stored version is never a half-conversation. Slack 봇이 Socket Mode로 돈다 — Slack이 모든 메시지를 상시 연결(WebSocket)로 밀어줘서, 계속 폴링해 rate limit에 부딪히지 않고 실시간으로 받는다. 메시지가 오면 확인(ack)하고, 이벤트 ID로 중복 제거하고, 중요하게 — 스레드 전체를 다시 가져와(부모 + 모든 답글) 대화 전체를 한 행으로 저장한다. 새 답글 하나가 전체 스레드를 갱신하니, 저장본이 반쪽 대화인 적이 없다.

Distillation — let an LLM turn a thread into a clean record증류(distillation) — LLM으로 스레드를 깔끔한 레코드로

Raw Slack text is keyword-searchable immediately (the full-text index). But for good vector search, they don't embed the raw transcript — an LLM first distills each thread into a structured record: a one-line question an engineer would actually search for, a short summary, the resolution, and the systems/code it references. Those fields (not the raw chat) are embedded into a 3,072-dimension vector. 원문 Slack 텍스트는 즉시 키워드 검색 가능하다(풀텍스트 인덱스). 하지만 좋은 벡터 검색을 위해 원문 대화를 임베딩하지 않고 — LLM이 먼저 각 스레드를 구조화된 레코드로 증류한다: 엔지니어가 실제 검색할 한 줄 질문, 짧은 요약, 해결책, 참조된 시스템/코드. 그 필드들(원시 채팅이 아니라)을 3,072차원 벡터로 임베딩.

"In our experiments, accuracy increased significantly when the thread was normalized into a consistent format. The additional metadata also gives the semantic match more useful signal."

— Cerebras blog · cerebras.ai

Bursting — rescue the good sentence buried in a long threadbursting — 긴 스레드에 묻힌 좋은 한 문장 구하기

One thread-level summary can miss a crucial aside. So they also use bursting: a "burst" is a run of consecutive messages from the same author, embedded on its own (with the thread's topic prepended for context), so an answer that lived in one tangent message is still findable. To keep junk out, a burst is only embedded if it clears a bar — it contains a rare token (IDF ≥ 4.0), is at least 200 characters, and ideally has emoji reactions (a social signal that it mattered). 스레드 레벨 요약 하나가 결정적 곁가지를 놓칠 수 있다. 그래서 bursting도 쓴다: "burst"는 같은 작성자의 연속 메시지 묶음으로, (문맥용으로 스레드 주제를 앞에 붙여) 따로 임베딩 — 그래서 한 곁가지 메시지에 있던 답도 찾을 수 있다. 쓰레기를 막으려고, burst는 문턱을 넘어야만 임베딩됨 — 희귀 토큰 포함(IDF ≥ 4.0), 최소 200자, 그리고 가급적 이모지 반응 있음(중요했다는 사회적 신호).

4Beyond Slack — code and custom sourcesSlack 너머 — 코드와 커스텀 소스

Code: is embedding it even worth it?코드: 임베딩할 가치가 있나?

They hesitated — in the era of Claude Code and command-line tools, "grep is all you need" felt plausible (plain keyword search over code often works). But after reading Cursor's findings on semantic search in large codebases, they tried it. The challenge was scale: some internal repos are larger than 40 GB, and re-embedding everything on every change is wasteful. 망설였다 — Claude Code와 명령줄 도구 시대에 "grep이면 충분"이 그럴듯했다(코드에 대한 단순 키워드 검색이 자주 통함). 하지만 대규모 코드베이스의 시맨틱 검색에 대한 Cursor의 결과를 읽고 시도했다. 난점은 규모: 일부 사내 레포는 40 GB 이상이라, 변경마다 전부 다시 임베딩하는 건 낭비다.

Solution: CocoIndex, an open-source framework for embedding codebases. Two things make it fit: 해법: 코드베이스 임베딩용 오픈소스 프레임워크 CocoIndex. 두 가지가 잘 맞았다:

  • Language-aware chunking. Split code by structure, coarse to fine — try class boundaries first; if a chunk is still too big, fall back to methods, then smaller blocks. One file can produce several embeddings at different granularity (file-level and function-level), so both "what does this file do" and "where's this exact function" are searchable.언어 인식 청킹. 코드를 구조로, 굵게→가늘게 쪼갬 — 먼저 클래스 경계 시도; 조각이 여전히 크면 메서드로, 그다음 더 작은 블록으로. 한 파일이 서로 다른 granularity의 임베딩 여럿을 낼 수 있음(파일 레벨 과 함수 레벨) — "이 파일이 뭘 하나"와 "이 정확한 함수가 어디 있나" 둘 다 검색 가능.
  • Incremental updates. CocoIndex tracks sync metadata in Postgres, so on each commit it re-embeds only the changed chunks — not the whole repo. It works especially well here because the sync state and the embedding store live in the same database.증분 업데이트. CocoIndex는 동기화 메타데이터를 Postgres에 추적해, 커밋마다 바뀐 청크만 다시 임베딩 — 레포 전체가 아니라. 동기화 상태와 임베딩 저장소가 같은 DB에 살아 특히 잘 맞았다.

Repo onboarding moved into config files teams submit themselves, with per-file-path allowlists and denylists — the same self-service instinct as everywhere else in this system. 레포 온보딩은 팀이 직접 제출하는 설정 파일로 옮겼고, 파일 경로별 allowlist/denylist 지원 — 이 시스템 전반의 셀프서비스 본능 그대로.

Custom sources: a pull request, not a meeting커스텀 소스: 회의가 아니라 풀 리퀘스트

Some teams already had their own databases and didn't want to move data just to be searchable. So custom sources are plugin scripts: a team opens a pull request with a small Python module that reads its system and emits rows shaped like the standard embeddings row, plus a data-source entry. As long as it writes the shared schema, everything downstream — search, ranking, the UI — works with zero special handling. This is the payoff of the "one table, one shape" decision from §2. 일부 팀은 자기 DB가 이미 있어 검색되려고 데이터를 옮기고 싶지 않았다. 그래서 커스텀 소스는 플러그인 스크립트다: 팀이 자기 시스템을 읽어 표준 임베딩 행 형태로 뱉는 작은 Python 모듈과 데이터 소스 항목을 풀 리퀘스트로 올린다. 공유 스키마로 쓰기만 하면, 하류 전부 — 검색·랭킹·UI — 가 특별 처리 없이 동작. §2의 "테이블 하나, 형태 하나" 결정의 보상.

5Answering a query — plan → fan out → rerank → synthesize질의에 답하기 — 계획 → 병렬 → 재랭킹 → 종합

A question doesn't go straight to one search. It runs through a four-stage pipeline: 질문은 곧장 하나의 검색으로 가지 않는다. 네 단계 파이프라인을 거친다:

Fig 2 — Query pipeline. (1) A lightweight LLM planner picks which tools matter; (2) the executor fans those tool calls out in parallel and normalizes results into one evidence format; (3) results are fused with RRF to a top-20, then a small reranker cuts to a top-10; (4) a synthesis LLM writes the final cited answer. Redrawn from the Cerebras blog.그림 2 — 질의 파이프라인. (1) 가벼운 LLM 플래너가 어떤 도구가 중요한지 고르고; (2) 실행기가 그 도구 호출을 병렬로 펼쳐 결과를 한 증거 형식으로 정규화하고; (3) RRF로 융합해 top-20, 이어 작은 reranker가 top-10으로 줄이고; (4) 종합 LLM이 인용 포함 최종 답을 작성. Cerebras 블로그 재구성.

The tools the planner can pick플래너가 고를 수 있는 도구들

Notice the tools go beyond text search: search (the unified vector pipeline across all sources), search_slack, search_code (plain ripgrep over repos — not everything needs embeddings), recent_prs, subsystem_index (per-file LLM summaries), and who_knows — which returns people with demonstrated expertise, answering "who should I ask?" not just "what's the answer?" 도구가 텍스트 검색을 넘어선다는 데 주목: search(모든 소스를 가로지르는 통합 벡터 파이프라인), search_slack, search_code(레포에 대한 단순 ripgrep — 전부 임베딩이 필요한 건 아님), recent_prs, subsystem_index(파일별 LLM 요약), 그리고 who_knows — 이건 "정답이 뭐야?"가 아니라 "누구에게 물어야 해?"에 답하는, 검증된 전문성을 가진 사람을 반환.

Reranking: fuse first (RRF), then let a model judge재랭킹: 먼저 융합(RRF), 그다음 모델이 판단

The different searchers return incompatible lists (a vector score and a full-text score aren't on the same scale). To merge them, Cerebras uses Reciprocal Rank Fusion (RRF): for each document, add up weight / (60 + rank) across every list it appears in (default weight 1.0, smoothing constant 60). Ranks — not raw scores — are what's combined, so incompatible scales stop mattering. 서로 다른 검색기는 호환 안 되는 목록을 낸다(벡터 점수와 풀텍스트 점수는 같은 척도가 아니다). 이를 합치려고 Cerebras는 Reciprocal Rank Fusion (RRF)을 쓴다: 각 문서에 대해, 그 문서가 등장한 모든 목록에서 weight / (60 + 순위)를 더함(기본 weight 1.0, smoothing 상수 60). 원시 점수가 아니라 순위를 합치니, 호환 안 되는 척도가 문제되지 않는다.

"The smoothing constant makes consensus matter more than a single strong vote: a document that shows up near the top across several retrievers can beat one that ranks first in only one of them."

— Cerebras blog · cerebras.ai

After fusing to a diverse top-20 (duplicate chunks merged back to their source, and a cap on how many results any one file can contribute), a small reranker model reads the query and each candidate together and scores it 0–10; they keep the top 10. Finally they add context back to the winners — e.g. if a wiki section matched, they pull in the two neighboring sections so the heading, preconditions, and caveats that chunking split apart aren't lost. The output is "a rich packet of evidence" handed to the synthesis LLM. 다양한 top-20로 융합한 뒤(중복 청크는 원 소스로 병합, 한 파일이 기여할 결과 수에 상한), 작은 reranker 모델이 질의와 각 후보를 함께 읽어 0–10점을 매기고 top 10만 남긴다. 마지막으로 이긴 문서에 문맥을 되붙인다 — 예: 위키 섹션이 매칭되면 이웃 두 섹션을 끌어와, 청킹이 갈라놓은 제목·전제조건·주의사항을 잃지 않게. 그 출력이 "풍부한 증거 묶음"으로 종합 LLM에 전달된다.

Why cap per-file and pull neighbors? Two nods to known RAG failure modes: over-representing one document crowds out diversity, and a lone chunk stripped of its heading/caveats can mislead (the "lost in the middle" and context-loss problems the blog cites). 왜 파일별 상한을 두고 이웃을 끌어오나? 알려진 RAG 실패 양상 둘에 대한 대응: 한 문서 과대표현은 다양성을 밀어내고, 제목/주의사항이 벗겨진 외톨이 청크는 오도할 수 있다(블로그가 인용하는 "lost in the middle"과 문맥 손실 문제).

6Two front-ends over the same parts — MCP & the Web UI같은 부품 위 두 앞단 — MCP & 웹 UI

Remember the audience is "humans, automations, and agents." Cerebras serves both with the same retrieval primitives, exposed two ways. 청중이 "사람·자동화·에이전트"였음을 기억하자. Cerebras는 같은 검색 프리미티브를 두 방식으로 노출해 양쪽을 서빙한다.

MCP — hand the agent the raw tools, let it orchestrateMCP — 에이전트에게 raw 도구를 주고 오케스트레이션은 맡긴다

Instead of hiding everything behind one "answer this question" endpoint, they expose each retrieval primitive as its own MCP tool — search_slack, search_code, search, who_knows — deliberately kept simple, LLM-free, and cheap to call, with narrow, stable inputs/outputs. Then: 모든 걸 "이 질문에 답해줘" 엔드포인트 하나 뒤에 숨기는 대신, 각 검색 프리미티브를 각자의 MCP 도구로 노출한다 — search_slack, search_code, search, who_knows — 일부러 단순하게, LLM 없이, 호출이 싸게, 좁고 안정적인 입출력으로. 그러면:

"Claude Code, or any MCP-compatible agent, becomes the orchestration engine. It decides which tools to call, in what order, and how to assemble the results… The retrieval layer itself does not depend on those LLM decisions in order to serve requests."

— Cerebras blog · cerebras.ai

This is a clean separation: the retrieval layer is a set of fast, dumb, reliable primitives; the intelligence (which tool, what order, how to combine) lives in whatever agent is calling — and can change without touching retrieval. It's the same "keep the serving layer simple, put smarts at the edge" instinct as exposing an OpenAI-compatible API. 깔끔한 분리다: 검색 층은 빠르고 멍청하고 신뢰할 수 있는 프리미티브 집합; 지능(어떤 도구·어떤 순서·어떻게 결합)은 호출하는 에이전트에 살고 — 검색을 건드리지 않고 바꿀 수 있다. OpenAI 호환 API를 노출하는 것과 같은 "서빙 층은 단순하게, 똑똑함은 가장자리에" 본능.

Web UI — the same tools, wired into the full pipeline웹 UI — 같은 도구를 풀 파이프라인에 배선

For humans, the same tools are connected end-to-end into the §5 pipeline: a planner LLM pass picks tools, an executor fans them out and normalizes results, and a synthesis LLM writes the cited answer. From the user's side it's just "ask a question, get an answer" — but under the hood it's the same planner → executor → synthesizer that an MCP agent would recreate explicitly. One set of parts, two audiences. 사람을 위해, 같은 도구가 §5 파이프라인에 end-to-end로 연결된다: 플래너 LLM 패스가 도구를 고르고, 실행기가 펼쳐 결과를 정규화하고, 종합 LLM이 인용 답을 쓴다. 사용자 쪽에선 그냥 "질문하면 답" — 하지만 내부는 MCP 에이전트가 명시적으로 재현할 그 planner → executor → synthesizer 그대로. 부품 한 벌, 청중 둘.

Projects — because "search everything" stops being usefulProjects — "전부 검색"이 쓸모없어지므로

As the corpus grew, searching everything at once got noisy — compiler engineers didn't want infrastructure runbooks in their results, and vice versa. So a project is a named bundle of data sources (specific Slack channels, repos, databases, doc spaces) for a team or initiative. Sources can be shared across projects instead of duplicated. During onboarding a user picks a default project (ML Training Infra, Compiler, Data Center Ops…), which then scopes their queries automatically — so a new engineer gets high-signal answers without first learning which channels and repos matter. 코퍼스가 커지자 한 번에 전부 검색하는 게 시끄러워졌다 — 컴파일러 엔지니어는 인프라 런북이 결과에 섞이길 원치 않고, 반대도 마찬가지. 그래서 project는 팀/이니셔티브를 위한 데이터 소스의 명명된 묶음(특정 Slack 채널·레포·DB·문서 공간)이다. 소스는 복제 대신 프로젝트 간 공유 가능. 온보딩 때 사용자가 기본 프로젝트(ML Training Infra, Compiler, Data Center Ops…)를 고르면, 그게 질의 범위를 자동으로 좁힌다 — 그래서 신규 엔지니어가 어느 채널·레포가 중요한지 먼저 배우지 않고도 고신호 답을 받는다.

First, the retrieval recipe is directly reusable: "embeddings alone are not enough → fuse full-text + vector + rarity + recency with RRF, then rerank, then re-attach context" is the current best-practice shape for production RAG, and it maps onto anything we build that has to search real, messy internal data. Second, the MCP separation is the sharpest architectural idea — keep the retrieval layer as fast, LLM-free primitives and let an agent be the brain. That mirrors the "serving layer stays simple, intelligence at the edge" pattern we like in llm-d / agentic serving, and it's exactly how an MCP-tool + Claude Code setup would consume our own infra. Boundaries: no performance data, and much of the value here is unglamorous data-plumbing (Slack Socket Mode, per-channel freshness, distillation prompts) that's specific to Cerebras's toolset — the transferable part is the shape of the pipeline, not the wiring. 서빙 처리량 얘기가 아님에도 우리가 볼 값어치가 있는 두 가지. 첫째, 검색 레시피가 바로 재사용 가능: "임베딩만으론 부족 → full-text + 벡터 + 희귀도 + 최신성을 RRF로 융합, 그다음 rerank, 그다음 문맥 재부착"은 프로덕션 RAG의 현재 베스트프랙티스 형태이고, 실제의 지저분한 사내 데이터를 검색해야 하는 우리 무엇에든 대응된다. 둘째, MCP 분리가 가장 날카로운 아키텍처 아이디어 — 검색 층은 빠르고 LLM 없는 프리미티브로 두고 에이전트를 두뇌로. 이는 우리가 llm-d / agentic serving에서 선호하는 "서빙 층은 단순, 지능은 가장자리" 패턴을 반영하며, MCP 도구 + Claude Code 셋업이 우리 인프라를 소비할 바로 그 방식이다. 경계: 성능 데이터 없음, 그리고 여기 가치의 상당수는 Cerebras 도구 특정적인 화려하지 않은 데이터 배관(Slack Socket Mode, 채널별 신선도, distillation 프롬프트) — 옮겨지는 건 배선이 아니라 파이프라인의 형태다.
