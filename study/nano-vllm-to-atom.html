one-line summary한 줄 요약
  • nano-vLLM is the shape of vLLM with everything hard removed: one model, no quantization, MoE, server or speculative decoding, temperature-only sampling with greedy explicitly forbidden, and TP over one hardcoded 1 MB shared-memory buffer.
  • That is why it is readable, and why its "comparable to vLLM" benchmark holds only in the corner it was measured in.
  • ATOM kept the skeleton (class names, global forward context, xxhash block manager, linear-layer hierarchy) and added back what was removed, mostly by re-importing it from vLLM.
  • The result is 308× the code, and the hardest problems are no longer engine problems.
  • nano-vLLM은 어려운 부분을 전부 걷어낸 vLLM의 형태다. 모델 1개, quantization·MoE·서버·speculative decoding 없음, temperature 샘플링만 되고 greedy는 명시적으로 금지, tensor parallel은 하드코딩된 1 MB 공유메모리 버퍼 하나로 돈다.
  • 그래서 읽기 쉽고, "vLLM에 준한다"는 벤치마크도 측정한 조건에서만 성립한다.
  • ATOM은 뼈대(클래스 이름, 전역 forward context, xxhash block manager, linear 레이어 계층)를 유지하고 걷어낸 기능을 되살렸다. 대부분 vLLM에서 다시 가져왔다.
  • 코드는 308배가 됐고, 가장 어려운 문제는 이제 엔진 바깥에 있다.

The three ideas it does keep그래도 지킨 세 가지 아이디어

What survives is vLLM's load-bearing ideas, which is why AMD could build on it. 남은 것은 vLLM의 핵심 아이디어다. 그래서 AMD가 그 위에 지을 수 있었다.

1. Paged KV cache with hash-based prefix sharing. BlockManager ref-counts fixed blocks and hashes each block with xxhash64 chained through the previous hash, so identical prefixes share physical blocks. 1. 해시 기반 prefix 공유 paged KV cache. BlockManager는 고정 블록의 ref-count를 세고, 블록마다 이전 해시를 이어 xxhash64로 해싱한다. prefix가 같으면 물리 블록을 공유한다. 

@classmethod
def compute_hash(cls, token_ids: list[int], prefix: int = -1):
    h = xxhash.xxh64()
    if prefix != -1:
        h.update(prefix.to_bytes(8, "little"))     # 이전 블록 해시를 체인
    h.update(np.array(token_ids).tobytes())
    return h.intdigest()

2. Prefill-first continuous batching with preemption. Scheduler.schedule() fills prefill under max_num_seqs and max_num_batched_tokens and returns if it got any; otherwise it batches decode. Out of blocks, it evicts the last running sequence to the front of the queue. 92 lines, same policy as ATOM's 3,146. 2. preemption 있는 prefill 우선 continuous batching. Scheduler.schedule()은 max_num_seqs·max_num_batched_tokens 안에서 prefill을 채우고, 하나라도 잡으면 바로 반환한다. 없으면 decode를 묶는다. 블록이 모자라면 마지막 running 시퀀스를 대기 큐 맨 앞으로 돌려보낸다. 92줄이지만 ATOM의 3,146줄 버전과 정책이 같다.

Tensor parallelism over a 1 MB shared-memory buffer1 MB 공유메모리 버퍼로 구현한 tensor parallel

This code shows where "minimal" stops being a virtue. Rank 0 runs in-process; ranks 1..N-1 are spawned processes in a loop(). They communicate by pickling a method name and arguments into shared memory and setting a multiprocessing.Event. "최소주의"가 미덕이기를 멈추는 지점이 이 코드에서 보인다. rank 0은 같은 프로세스에서, rank 1..N-1은 spawn된 프로세스의 loop()에서 돈다. 메서드 이름과 인자를 pickle해 공유메모리에 쓰고 multiprocessing.Event를 켜서 통신한다.

three hardcoded values, three hard limits하드코딩 셋, 한계 셋
  1. SharedMemory(name="nanovllm"): a constant name, so two instances cannot share a machine.
  2. dist.init_process_group("nccl", "tcp://localhost:2333"): literal localhost and port 2333, so single-node only, and instances collide again.
  3. A 2**20-byte buffer: a batch whose pickled sequences exceed 1 MB silently corrupts.
Harmless in a teaching repo, disqualifying for a service.
  1. SharedMemory(name="nanovllm"): 이름이 상수라 한 머신에 인스턴스를 둘 띄울 수 없다.
  2. dist.init_process_group("nccl", "tcp://localhost:2333"): localhost와 포트 2333이 리터럴이라 단일 노드 전용이고, 여기서도 인스턴스끼리 충돌한다.
  3. 버퍼가 2**20 바이트라 pickle된 시퀀스가 1 MB를 넘으면 배치가 조용히 깨진다.
학습용 레포에선 문제없지만 서비스라면 셋 다 실격이다.

The Gumbel-max sampler divides logits by temperature, so temperature=0 would divide by zero. Production engines special-case greedy; nano-vLLM asserts. So you cannot get deterministic output, which rules out most evaluation and regression testing. Gumbel-max sampler가 logits를 temperature로 나누므로 temperature=0이면 0으로 나누게 된다. 프로덕션 엔진은 greedy를 따로 처리하지만 nano-vLLM은 assert로 막는다. 결국 결정론적 출력을 얻을 수 없어 평가와 회귀 테스트 대부분이 불가능하다. 

@torch.compile
def forward(self, logits, temperatures):
    logits = logits.float().div_(temperatures.unsqueeze(dim=1))
    probs = torch.softmax(logits, dim=-1)
    return probs.div_(torch.empty_like(probs).exponential_(1).clamp_min_(1e-10)).argmax(dim=-1)

editor's note — my reading, not the author's claim편집자 주: 저자의 주장이 아닌 내 해석
  1. The result is real and reproducible. It does not show that vLLM carries 5% of avoidable fat: that overhead buys MoE, quantization, multi-node, LoRA, structured output, streaming, cancellation and a hundred architectures.
  2. One step outside the measured setup, nano-vLLM does not run slower; it does not run. A 671B MoE in FP8 on 8 GPUs needs MoE, quantization and multi-node transport. That capability gap is what AMD had to close to get to ATOM.
  1. 결과는 실재하고 재현된다. 하지만 vLLM에 5%의 군살이 있다는 근거는 아니다. 그 오버헤드는 MoE, quantization, 멀티노드, LoRA, structured output, 스트리밍, 취소, 수백 개 아키텍처를 위한 비용이다.

src/policies/ has six routing strategies. The default, cache_aware, uses tree.rs, a multi-tenant radix tree over raw request text (tenant = worker URL).
  • Characters, not token IDs: no tokenizer needed, so it works on the HTTP path where the gateway is a pure JSON proxy.
  • Per request it computes matched_chars / input_chars and routes to the matching worker above a threshold.
  • If load is imbalanced by both an absolute and a relative margin, it falls back to shortest-queue but still inserts the text.
  • LRU timestamps update probabilistically, 1 match in 8, to cut DashMap contention.
src/policies/에는 라우팅 전략이 6종 있다. CLI 기본값 cache_aware는 tree.rs를 쓴다. 요청 텍스트 원문 위의 멀티테넌트 radix tree이고, 테넌트는 worker URL이다.

Two patches stand out for what they override. cudagraph_memory_profiler_patch.py: "Skip vLLM's temporary CUDA graph capture on ROCm." rocm_dcp_full_graph_patch.py: "Remove vLLM's blanket DCP-to-PIECEWISE downgrade on ROCm." ATOM is reversing decisions vLLM's own ROCm path made: two AMD-supported paths disagree on how to run AMD hardware. 눈여겨볼 패치가 둘 있다. cudagraph_memory_profiler_patch.py는 ROCm에서 vLLM의 임시 CUDA graph 캡처를 건너뛰고, rocm_dcp_full_graph_patch.py는 ROCm에서 DCP를 PIECEWISE로 일괄 강등하는 동작을 없앤다. 기능 추가가 아니라 vLLM 자체 ROCm 경로의 결정을 되돌린다. AMD가 지원하는 두 경로가 AMD 하드웨어 운용 방식을 두고 엇갈린다.

diffusion — a second engine that shares nothingdiffusion: 아무것도 공유하지 않는 두 번째 엔진

7,395 lines. atom/diffusion/ generates video with audio; ATOM's CLAUDE.md calls it "a sibling of atom/model_engine/ rather than an extension of it — no KV cache, one fixed N-step denoise loop per job, four heterogeneous networks, and sequence parallelism across a single request". It mirrors the LLM stack's shape without reusing it: 7,395줄짜리 atom/diffusion/은 오디오가 붙은 비디오를 만든다. ATOM CLAUDE.md는 이를 atom/model_engine/의 확장이 아닌 형제로 설명한다. KV cache가 없고, job마다 고정 N-스텝 denoise 루프를 돌고, 이종 네트워크 4개를 쓰며, 단일 요청을 sequence parallelism으로 나눈다. LLM 스택과 모양은 같지만 코드는 재사용하지 않는다.

6ATOM's weaknessesATOM의 약점

Code quality is not the problem. Comment density, recorded rationale (kernels explain why a Triton port exists, schedulers name the invariant a guard protects) and almost no unfinished markers in 53k lines of Rust are above average. The weaknesses are structural. 코드 품질은 문제가 아니다. 주석 밀도, 기록된 설계 근거(커널은 Triton 포팅을 왜 했는지, 스케줄러는 가드가 어떤 불변식을 지키는지 적어 둔다), Rust 5만 3천 줄에 미완성 표식이 거의 없다는 점 모두 평균 이상이다. 약점은 구조에 있다.

Group 1 — dependency: ATOM is only as good as AITER on the day1군. 의존성: ATOM은 그날의 AITER만큼만 좋다

ATOM delegates every heavy op to AITER. When an AITER kernel breaks on a GPU generation, ATOM does not degrade gracefully; it loses its reason to exist. SemiAnalysis saw this at DeepSeek-V4 Day 0: ATOM은 무거운 연산을 전부 AITER에 맡긴다. 어떤 GPU 세대에서 AITER 커널이 깨지면 ATOM은 존재 이유를 잃는다. SemiAnalysis가 DeepSeek-V4 Day 0에 이를 확인했다.

"ATOM also ran with almost every hot path on a fallback: the FP4 MoE was forced onto Triton because AITER's fused_moe was broken on GFX950, and the mHC pre-projection patched to Torch because AITER's kernel crashed, forcing eager execution."

— SemiAnalysis, InferenceX, 2026-06-09

On fallbacks with eager execution, ATOM is a slow reimplementation of vLLM. vLLM can swap attention backends; ATOM has no second source. AITER fix #2916 restored the kernel, but the failure mode is permanent. fallback과 eager로 도는 ATOM은 느린 vLLM 재구현일 뿐이다. vLLM은 attention 백엔드를 바꿔 끼우면 되지만 ATOM에는 대안이 없다. AITER fix #2916으로 커널은 회복됐어도 이런 실패는 언제든 다시 올 수 있다.

Group 2 — position: AMD has already ranked ATOM third2군. 포지션: AMD가 이미 ATOM을 3순위로 매겼다

SGLang is where the depth is깊이가 있는 쪽은 SGLang

The gateway forks SGLang's sgl-model-gateway and depends on seven SGLang crates. The SGLang bridge (21,418 lines) beats vLLM's (16,398), more so with ~1,030 SGLang lines in shared register.py, where the vLLM part is commented out.게이트웨이는 sgl-model-gateway 포크다. SGLang 브리지(21,418줄)가 vLLM용(16,398줄)보다 크고, 공용 register.py에서도 SGLang 코드 ~1,030줄은 살아 있고 vLLM 쪽은 주석 처리돼 있다.

the in-tree RFC was rejectedin-tree RFC는 거절당했다

vllm#33478 asked to put ATOM inside vLLM and was closed on governance grounds. The plugin is the fallback, not the plan.vllm#33478은 ATOM을 vLLM 안에 넣자는 제안이었고 거버넌스 문제로 닫혔다. 플러그인은 원래 계획이 아니라 타협안이다.

adoption채택

168 stars vs nano-vLLM's 15,252. No discussion found outside GitHub and SemiAnalysis, who assert "zero production customers" (unrebutted, unverified).별 168개로 nano-vLLM(15,252개)과 비교가 안 된다. GitHub과 SemiAnalysis 밖에선 논의를 찾지 못했다. SemiAnalysis는 "zero production customers"라고 단언하는데, 반박도 검증도 없는 주장이다.

Group 3 — the plugin path is not as cheap as advertised3군. 플러그인 경로는 광고만큼 싸지 않다

Following from §5: the pitch "you don't have to leave vLLM, just install us alongside" assumes a thin, stable adapter. It is not. §5에서 바로 나오는 결론이다. "vLLM을 떠날 필요 없이 옆에 설치만 하면 된다"는 논리는 브리지가 얇고 안정적이라는 전제에 기댄다. 실제로는 그렇지 않다.

  • An exact commit pin. VLLM_COMMIT=6e448d0e…, VLLM_VERSION=0.27.1. Not a range. AMD's vLLM-ATOM blog still says "tested against vLLM v0.17.x".커밋 하나에 고정. VLLM_COMMIT=6e448d0e…, VLLM_VERSION=0.27.1. 범위가 아니다. AMD vLLM-ATOM 블로그의 "tested against vLLM v0.17.x"는 이미 코드와 맞지 않는다.
  • 176 imports into vLLM, including private symbols like _max_memory_usage_bytes_from_groups. Private names carry no compatibility promise across versions.vLLM import 176개. _max_memory_usage_bytes_from_groups 같은 private 심볼도 있는데, private 이름은 버전 간 호환을 보장하지 않는다.
  • Nine monkey-patch modules rewriting vLLM methods at import. If an upstream signature changes, you get wrong behaviour, not an ImportError.monkey-patch 모듈 9개가 import 시점에 vLLM 메서드를 덮어쓴다. 상류에서 시그니처가 바뀌면 ImportError 없이 조용히 잘못 동작한다.
  • Two patches reverse vLLM's own ROCm decisions ("Skip vLLM's temporary CUDA graph capture on ROCm", "Remove vLLM's blanket DCP-to-PIECEWISE downgrade on ROCm"). If the two AMD-supported ROCm paths disagree about correct behaviour, upstreaming is harder than the RFC implies.패치 둘은 vLLM 자체 ROCm 결정을 뒤집는다(§5). AMD가 지원하는 두 ROCm 경로가 서로 다른 답을 낸다면 upstream은 RFC가 말하는 것보다 어렵다.
  • It fires automatically. vLLM's two entry points activate on any vllm serve in the environment: installing atom beside vllm silently changes vLLM's behaviour, and ATOM_DISABLE_VLLM_PLUGIN=1 is opt-out. The SGLang and RTP-LLM bridges are opt-in by contrast (an env var and a CLI flag respectively).자동으로 켜진다. vLLM entry point 둘이 환경 안의 모든 vllm serve에서 활성화된다. atom을 vllm 옆에 설치만 해도 vLLM 동작이 바뀌고, 끄려면 ATOM_DISABLE_VLLM_PLUGIN=1(opt-out)을 줘야 한다. SGLang·RTP-LLM 브리지는 opt-in이다(각각 환경변수, CLI 플래그).

Group 4 — things that fail silently or not at all4군. 조용히 실패하거나 아예 실패하지 않는 것들

From §5: --api-key authenticates nothing inbound, and --policy prefix_hash fails 100% of HTTP requests. Add the engine's own traps (stale compile cache failing silently, /health returning OK with no model loaded) and the pattern is clear: the failure modes are quiet. Things succeed while doing the wrong thing. §5에서 본 대로 --api-key는 인바운드를 전혀 인증하지 않고, --policy prefix_hash는 HTTP 요청의 100%를 실패시킨다. 엔진 자체의 운영 함정(낡은 컴파일 캐시의 조용한 실패, 모델이 없어도 OK를 주는 /health)까지 더하면 공통점이 보인다. 실패가 조용하다. 요란하게 깨지지 않고, 잘못된 일을 하면서 성공으로 보고한다.

editor's note — my reading편집자 주: 내 해석
  1. AMD chose nano-vLLM because it was small enough to move fast in. Moving fast meant adding back everything it removed: ATOM is now 426k lines with 26 architectures, a Rust gateway, three framework bridges and a diffusion engine, maintained by one vendor. The minimalism that justified the choice is gone, replaced by the maintenance surface AMD least wanted to own.
  2. So the consensus framing (reference implementation and upstreaming incubator, not production engine) is less a concession than the only stable resting place.
  3. The question to check in a year: has anything actually been upstreamed? Both RFCs promise it; I found no list confirming it. If yes, ATOM is a well-run proving ground. If not, it is a 426,000-line AMD-only fork of an engine layer AMD's own tooling ranks third.
  1. AMD가 nano-vLLM을 고른 건 빠르게 움직일 만큼 작아서였다. 그런데 빠르게 가려면 걷어낸 것을 전부 되살려야 했고, 지금 ATOM은 42만 6천 줄에 아키텍처 26종, Rust 게이트웨이, 프레임워크 브리지 3개, diffusion 엔진을 벤더 팀 하나가 떠안고 있다. 선택의 근거였던 최소주의는 사라졌고, 그 자리를 AMD가 가장 피하고 싶던 유지보수 부담이 채웠다.
  2. 그래서 모두가 합의한 규정(프로덕션 엔진이 아닌 레퍼런스 구현이자 upstream 인큐베이터)은 양보라기보다 유일하게 안정적인 자리로 보인다.
  3. 1년 뒤 확인할 질문은 실제로 upstream된 게 있는가이다. 두 RFC 모두 약속했지만 이를 확인해 주는 목록은 찾지 못했다. 이뤄진다면 ATOM은 잘 운영된 실험장이고, 아니라면 AMD 자체 도구가 3순위로 매긴 엔진 계층의 42만 6천 줄짜리 AMD 전용 포크다.
