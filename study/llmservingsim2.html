1 Problem definition 문제 정의

Modern LLM serving stacks have started mixing two trends that used to be studied separately:

현대 LLM 서빙은 그동안 따로 연구되던 두 흐름이 점점 같이 섞여서 돌아갑니다:

  • Heterogeneous hardware — GPU + TPU + NPU + PIM, multi-tier memory (HBM, CPU DRAM, CXL).
  • Disaggregated serving — prefill–decode split, expert parallelism, prefix caching pools, MoE routing.
  • 이종 하드웨어 — GPU + TPU + NPU + PIM, 다중 메모리 계층(HBM, CPU DRAM, CXL).
  • 분리형 서빙 — prefill–decode 분리, expert parallelism, prefix-cache 풀, MoE 라우팅.
paper's core claim논문의 핵심 주장 "LLM serving performance is no longer determined by hardware or software choices in isolation" — it's the runtime interaction between the two that matters, and existing simulators don't capture it inside one framework. "이제 LLM 서빙 성능은 하드웨어나 소프트웨어 한쪽만 봐서는 알 수 없다" — 둘의 런타임 상호작용이 본질이고, 기존 시뮬레이터들은 그 상호작용을 한 프레임워크 안에서 잡지 못한다.

One-liner takeaway: there's no single simulator where you can configure "GPU cluster + CPU memory pool + PIM offload + prefill/decode split + MoE" and watch realistic batch dynamics emerge. That's the v2 niche.

한 줄 요약: "GPU 클러스터 + CPU 메모리 풀 + PIM 오프로드 + prefill/decode 분리 + MoE"를 한 번에 설정하고 사실적인 배치 동작을 관찰할 수 있는 시뮬레이터가 없었다. 그 자리를 v2가 메운다.

2 Solution — architecture & runtime 해결 방법 — 아키텍처와 런타임

v2 is a single Python frontend driving an ASTRA-Sim C++ analytical backend. The whole thing is structured into four cooperating components plus a profile-based hardware model.

v2는 Python 프런트엔드가 ASTRA-Sim(C++) 분석 백엔드를 끌고 가는 구조입니다. 전체 시스템은 4개의 협력 컴포넌트와 프로파일 기반 하드웨어 모델로 구성됩니다.

Architecture overview — 4 components inside the Python frontend, the ASTRA-Sim subprocess, plus offline profile data and online workload/output files. 전체 구조 — Python 프런트엔드 안 4 컴포넌트, ASTRA-Sim 서브프로세스, 오프라인 프로파일 데이터와 온라인 워크로드/출력 파일.

2-1. The four components 네 가지 컴포넌트

① Execution Planner

Initializes the Serving Engine: assigns devices to instances, installs serving policies (batch size, parallelism, PD split, etc.), validates the cluster config.

서빙 엔진 초기화 — 디바이스를 인스턴스에 배정, 서빙 정책(배치 크기, 병렬화, PD 분리 등) 설치, 클러스터 설정 검증.

② Model Serving Group (MSG)

A logical unit per LLM instance, bundling: device pool, request queue, batch scheduler, multi-tier memory model, power model, operation mapper. One MSG per "vLLM-like worker."

LLM 인스턴스 1개에 해당하는 논리 단위 — 디바이스 풀 + 요청 큐 + 배치 스케줄러 + 다층 메모리 모델 + 파워 모델 + 오퍼레이션 매퍼. vLLM 워커 1개 ≈ MSG 1개.

③ System Simulator

Extends ASTRA-Sim + Chakra to evaluate cluster-scale timing — network contention, memory hierarchy, synchronization. Given an execution graph, it tells you how long it takes.

ASTRA-Sim + Chakra 확장 — 네트워크 경쟁·메모리 계층·동기화까지 포함한 클러스터 규모의 타이밍 평가. 실행 그래프를 받아 소요 시간을 산출.

④ Request Router

Front-door dispatcher. Receives incoming requests, picks an MSG using a policy (round-robin / random / least-load / custom), and hands them off.

앞단 라우터. 들어오는 요청을 받아 정책(RR / 랜덤 / 부하 최소 / 커스텀)으로 MSG를 골라 전달.

2-2. The runtime loop 런타임 루프

One iteration of the runtime loop — annotated with the exact function calls and the side-channel through controller.py. 런타임 루프 1회 반복 — 실제 함수 호출과 controller.py 의 측면 채널까지 표시.

From the paper: "After this setup, execution proceeds in a runtime loop. The Request Router dispatches incoming requests to the appropriate MSG, which generates an execution graph for each request batch. The System Simulator then evaluates the graph, accounting for communication, synchronization, and multi-tier memory access. The loop repeats until all requests are complete."

논문 원문: "세팅이 끝난 뒤 런타임 루프가 돈다. 라우터가 들어오는 요청을 MSG로 분배하고, MSG는 요청 배치마다 실행 그래프를 만든다. 시스템 시뮬레이터는 그 그래프를 평가하면서 통신·동기화·다층 메모리 접근까지 반영한다. 모든 요청이 끝날 때까지 이 루프가 반복된다."

2-3. Profile-based hardware modeling 프로파일 기반 하드웨어 모델링

Instead of simulating every cuBLAS kernel from scratch, the authors do a one-time profiling pass:

cuBLAS 커널을 처음부터 다 시뮬레이션하지 않고, 일회성 프로파일링으로 대체합니다:

  • Run vLLM-based layerwise profiler on one model × one device pair (e.g. Llama-3.1-70B on H100).
  • It only needs a single decode block to measure operator-level latency and power.
  • Typical wall-clock: ~2.1 hours per pair.
  • Output: per-op latency/power tables that the simulator looks up at runtime.
  • 모델 × 디바이스 1쌍에 대해 vLLM 기반 레이어 단위 프로파일러를 한 번 돌림 (예: H100에서 Llama-3.1-70B).
  • decode block 1개만 측정해도 충분 — 오퍼레이터 단위 지연·전력을 추출.
  • 실제 소요 시간: 1쌍당 약 2.1시간.
  • 결과물은 op별 지연/전력 테이블 → 시뮬레이션 런타임에 룩업.
why this works왜 성립하나 LLM inference is dominated by a few repeating operator types (attention, dense, MoE, layer-norm, RMS, all-reduce). Profile them once at canonical shapes, then scale via fitted skew/alpha curves — that's enough fidelity to land within 1–2% of measured throughput in the experiments. LLM 추론은 몇 종류 안 되는 오퍼레이터(attention, dense, MoE, layer-norm/RMS, all-reduce)가 반복됩니다. 표준 shape에서 한 번 측정하고 skew/alpha 곡선으로 스케일링하면, 실측 대비 1~2% 오차에 들어가는 충분한 정밀도가 나옵니다.

2-4. What it can model that v1 / others couldn't v1·타 시뮬레이터 대비 새로 가능해진 것

  • Multi-tier KV cache placement across HBM ↔ CPU DRAM ↔ CXL — with migration latency.
  • Operator-level heterogeneous offloading (e.g. attention → PIM, dense → GPU, automatic data-movement insertion).
  • MoE routing with per-layer token dispatch + all-to-all communication cost.
  • PD disaggregation across multiple MSGs with layer-wise KV transfer ops inserted automatically.
  • Power modeling — 7 major components tracked, three power states (idle/active/standby).
  • Sub-Batch Interleaving (SBI) as a configurable strategy for GPU+PIM.
  • 다층 KV 캐시 배치 — HBM ↔ CPU DRAM ↔ CXL 사이 마이그레이션 지연까지 반영.
  • 오퍼레이터 단위 이종 오프로딩 (예: attention → PIM, dense → GPU, 데이터 이동 자동 삽입).
  • MoE 라우팅 — 레이어별 토큰 디스패치 + all-to-all 통신 비용.
  • PD 분리 — 여러 MSG 간 레이어 단위 KV 전송 연산 자동 삽입.
  • 파워 모델링 — 7개 주요 컴포넌트, idle/active/standby 3가지 전력 상태.
  • Sub-Batch Interleaving (SBI) — GPU+PIM 전략으로 설정 가능.

3 Concrete usage scenarios 구체적 사용 시나리오

Direct answer to "does this thing predict vLLM performance for my model on my hardware?" — yes, that's literally the purpose. The flow always looks the same: (a) profile the (device, model) pair once against real vLLM, (b) drop a workload trace + cluster config, (c) run python -m serving …, (d) read a CSV with per-request TTFT/TPOT/ITL/latency plus an aggregate power summary.

"이거 진짜 내 모델·내 하드웨어에서 vLLM 성능 예측해주는 거야?" 에 대한 직답 — 네, 그게 정확히 목적입니다. 흐름은 늘 같습니다: (a) (디바이스, 모델) 쌍을 한 번 vLLM 실측으로 프로파일 → (b) 워크로드 trace + 클러스터 설정 준비 → (c) python -m serving … 실행 → (d) 요청별 TTFT/TPOT/ITL/latency CSV + 전력 요약 읽기.

3-3. Scenario B — "Should I PD-split for Qwen3-30B-A3B (MoE)?" 시나리오 B — "Qwen3-30B-A3B(MoE)에 PD 분리 도입할까?"

The decision: dedicate some GPUs to prefill, some to decode (and ship KV between) vs. keeping every instance doing both. Real answer depends on prompt length distribution, decode length, batch dynamics.

결정: GPU 일부를 prefill, 일부를 decode 전용으로 분리(그 사이 KV 전송)할지 vs 모든 인스턴스가 둘 다 처리할지. 답은 프롬프트 길이 분포·decode 길이·배치 동학에 따라 달라짐.

python3 - <<'PY'
import pandas as pd
A = pd.read_csv("outputs/qwen3moe_unified.csv")
B = pd.read_csv("outputs/qwen3moe_pd.csv")
for name, df in [("unified", A), ("pd_split", B)]:
    print(name,
          "p50 TTFT (ms):", df["TTFT"].quantile(0.5)/1e6,
          "p99 TTFT (ms):", df["TTFT"].quantile(0.99)/1e6,
          "mean TPOT (ms):", df["TPOT"].mean()/1e6,
          "throughput (tok/s):",
          (df["input"]+df["output"]).sum() /
          ((df["end_time"].max()-df["arrival"].min())/1e9))
PY
how to read the diff차이 해석 If PD-split shows lower p99 TTFT but higher mean TPOT in the CSV, it means the dedicated prefill nodes absorb long-prompt requests away from decode (good for tail TTFT), but the cross-GPU KV transfer adds per-token overhead (bad for steady-state TPOT). Pick based on which metric your SLO cares about — typically TTFT-bound chatbots = split, TPOT-bound long-generation = unified. PD-split이 p99 TTFT는 낮은데 mean TPOT은 높게 나오면, 전용 prefill 노드가 긴 프롬프트를 흡수해 decode 큐 안정화(꼬리 TTFT 개선)지만 GPU 간 KV 전송이 토큰당 오버헤드를 더한 것. SLO가 어느 쪽이냐로 결정 — TTFT가 깐깐한 챗봇은 split, TPOT 중심 긴 생성은 unified가 보통.

The point: this whole A/B costs you ~20 minutes of wall-clock (two ~10min sims) instead of provisioning two real cluster shapes.

핵심: 이 A/B 비교가 실제 클러스터 2종을 띄우는 대신 약 20분(10분짜리 시뮬 2개)이면 끝납니다.

3-4. Scenario C — "What if I offload attention to PIM?" 시나리오 C — "attention을 PIM에 오프로드하면?"

The hypothesis: attention is bandwidth-bound at decode, so moving just the attention op to a PIM device (with the rest on GPU) should free GPU bandwidth and cut energy. The paper validates: GPU+PIM → 1.43× decode throughput, −14.8% energy/token at decode.

가설: decode 단계에서 attention은 대역폭 bound이므로, attention만 PIM으로 옮기면 GPU 대역폭이 풀리고 에너지가 줄어들 것. 논문 결과: GPU+PIM → decode throughput 1.43×, 토큰당 에너지 −14.8%.

python -m serving \
  --cluster-config configs/cluster/single_node_pim_instance.json \
  --dtype bfloat16 --dataset workloads/my_trace.jsonl \

5-3. End-to-end flow inside __main__.py 엔트리 포인트의 end-to-end 흐름

The docstring at the top of serving/__main__.py spells it out exactly:

serving/__main__.py 상단 docstring이 흐름을 그대로 적어두었습니다:

"""Simulation entry point: ``python -m serving --cluster-config <...> [...]``.

Parses CLI args, generates ASTRA-Sim input files via ``serving.core.config_builder``,
spawns the ASTRA-Sim subprocess, and runs the iteration loop:
``router.route -> scheduler.schedule -> trace_generator -> graph -> ASTRA-Sim
-> scheduler.add_done`` until every request completes.
"""

Mapped step-by-step:

단계별로 풀면:

  1. Argparse → cluster + model + run params. Picks one of the 15 configs/cluster/*.json blueprints (single-node, dual-node, PD-split, MoE, PIM, CXL…).
  2. config_builder emits ASTRA-Sim inputs — system / network / workload files derived from the cluster config and profiler CSVs.
  3. Spawn the ASTRA-Sim subprocess via subprocess.Popen; stdin/stdout become the communication channel.
  4. Iteration loop:
    • router.route(...) picks an MSG for each new request based on the routing policy.
    • scheduler.schedule(current, sys, batch_id) forms the next batch under vLLM-style constraints (max_num_seqs, max_num_batched_tokens, pp_size, prefix cache, chunked prefill…).
    • graph_generator turns the batch into a computation graph; trace_generator serializes it for ASTRA-Sim.
    • The graph is fed to ASTRA-Sim; the C++ side reports back lines like sys[N] iteration M finished, X cycles, exposed communication Y cycles.
    • Controller.parse_output(...) parses that line, and scheduler.add_done(...) marks the batch complete.
  5. Loop terminates when every scheduler reports its requests finished. Per-instance stats are written to outputs/*.csv.
  1. argparse → 클러스터 + 모델 + 실행 파라미터. configs/cluster/*.json 15개 청사진(단일/이중 노드, PD 분리, MoE, PIM, CXL …) 중 하나 선택.
  2. config_builder가 ASTRA-Sim 입력 생성 — 클러스터 설정 + 프로파일러 CSV를 조합해 system / network / workload 파일 산출.
  3. ASTRA-Sim 서브프로세스 생성 — subprocess.Popen으로 띄우고 stdin/stdout이 통신 채널.
  4. 반복 루프:
    • router.route(...) — 라우팅 정책에 따라 새 요청마다 MSG 선택.
    • scheduler.schedule(current, sys, batch_id) — vLLM 스타일 제약(max_num_seqs, max_num_batched_tokens, pp_size, prefix cache, chunked prefill 등) 안에서 다음 배치 형성.
    • graph_generator가 배치 → 계산 그래프, trace_generator가 ASTRA-Sim용으로 직렬화.
    • 그래프를 ASTRA-Sim에 투입 → C++ 측이 sys[N] iteration M finished, X cycles, exposed communication Y cycles. 형식으로 응답.
    • Controller.parse_output(...)이 그 한 줄을 파싱하고, scheduler.add_done(...)가 배치 완료 처리.
  5. 모든 스케줄러가 자기 요청 완료를 보고하면 루프 종료. 인스턴스별 통계는 outputs/*.csv로 저장.

5-4. Scheduler internals — the vLLM-like batcher 스케줄러 내부 — vLLM 스타일 배처

Scheduler (in scheduler.py) is the heart of an MSG. It holds three lists per instance:

Scheduler(scheduler.py)가 MSG의 심장. 인스턴스마다 3개의 리스트를 유지:

  • self.request — pending requests, sorted by arrival.
  • self.inflight — batches currently inside ASTRA-Sim (pipeline depth limited by pp_size).
  • self.done — completed.
  • self.request — 도착 순으로 정렬된 대기 요청.
  • self.inflight — 현재 ASTRA-Sim 안에서 도는 배치들 (파이프라인 깊이 = pp_size로 제한).
  • self.done — 완료된 것.

The schedule call branches on prefix caching:

schedule 호출은 prefix-cache 사용 여부에 따라 분기:

def schedule(self, current, sys, batch_id=-1):
    if self.enable_prefix_caching:
        return self.schedule_with_prefix(current, sys, batch_id)
    else:
        return self.schedule_base(current, sys, batch_id)

Both branches enforce the same vLLM-style caps:

두 분기 모두 vLLM과 동일한 상한 강제:

  • max_num_seqs — total concurrent sequences동시 시퀀스 수 상한
  • max_num_batched_tokens — total tokens in a single forward한 forward의 총 토큰 수
  • pp_size — in-flight batches (pipeline parallelism)동시 진행 배치 수(파이프라인 병렬)
  • prioritize_prefill · enable_chunked_prefill · long_prefill_token_threshold

When DP padding is needed (e.g. MoE all-reduce across DP ranks), the helper _pad_batch_to_max in __main__.py bumps the high-level counters but deliberately leaves decode_k_list/prefill lists untouched, so attention still sees only real decodes (matches FlashAttention varlen behavior).

DP 패딩이 필요한 경우(예: DP 랭크 간 MoE all-reduce), __main__.py의 _pad_batch_to_max가 상위 카운터만 부풀리고 decode_k_list/prefill 리스트는 손대지 않습니다 — attention은 실제 decode만 봄(FlashAttention varlen과 동일).

5-5. Router — 4 routing policies 라우터 — 4가지 라우팅 정책

From router.py:

router.py 발췌:

if self.routing_policy == "RR":
    self._select_instance = self._rr_select        # round-robin
elif self.routing_policy == "RAND":
    self._select_instance = self._rand_select      # uniform random
elif self.routing_policy == "LOAD":
    self._select_instance = self._least_load_select # vLLM-style least-loaded
elif self.routing_policy == "CUSTOM":
    self._select_instance = self._custom_select    # user-pluggable hook

Notable bits:

눈여겨 볼 점:

  • Prefill / decode pools are split — prefill_schedulers vs decode_schedulers with independent round-robin counters. This is what makes PD-disaggregated routing first-class.
  • Agentic session dependency tracking — _deferred_sessions, _request_to_session let multi-turn requests preserve cache locality.
  • Random seed pinned (seed=42 default) — reproducible RAND policy runs.
  • prefill / decode 풀이 분리되어 있음 — prefill_schedulers vs decode_schedulers, 각각 독립적인 round-robin 카운터. 이게 PD-분리 라우팅의 1급 시민화 포인트.
  • Agentic 세션 의존성 추적 — _deferred_sessions, _request_to_session으로 멀티턴 요청의 캐시 지역성 유지.
  • 랜덤 시드 고정(기본 seed=42) — RAND 정책도 재현 가능.

5-6. Controller — talking to ASTRA-Sim 컨트롤러 — ASTRA-Sim과 대화

controller.py is a thin synchronization layer that reads ASTRA-Sim's stdout in lock-step:

controller.py는 ASTRA-Sim의 stdout을 lock-step으로 읽는 얇은 동기화 레이어:

# 1. wait for "Waiting" prompt (sim ready for input)
def read_wait(self, p):
    while "Waiting" not in out[-1] and ...: out.append(p.stdout.readline())

# 2. push the trace
def write_flush(self, p, input):
    p.stdin.write(input + '\n'); p.stdin.flush()

# 3. parse iteration completion
pattern = r"sys\[(\d+)\] iteration (\d+) finished, (\d+) cycles, "
          r"exposed communication (\d+) cycles."

So one batch's lifecycle on the wire is: Python forms a trace → blocks on a "Waiting" prompt → writes the trace to the subprocess stdin → blocks reading stdout → gets back the cycle count → marks the batch done. The Controller maintains end_dict[sys] = id so it knows the latest finished iteration per simulated system.

한 배치의 전송 사이클: Python이 trace를 만든 뒤 "Waiting" 프롬프트를 기다림 → trace를 stdin으로 푸시 → stdout 읽으며 대기 → 사이클 수를 받음 → 배치 완료 처리. Controller가 end_dict[sys] = id로 시뮬레이션 시스템별 최신 완료 iteration을 보관.

6 Takeaways 정리

what's actually new in v2v2가 새로 가져온 것
  • One simulator that jointly models heterogeneous HW + disaggregated SW, validated to ~1% on real H100/A6000.
  • Architecture cleanly factored into Router → MSG → System Simulator, with a one-time profile-driven HW model.
  • First-class support for MoE routing, PD split, CPU/CXL pooling, PIM offload, power, SBI.
  • 이종 HW + 분리 SW를 함께 모델링하는 단일 시뮬레이터. H100/A6000 실측 대비 ~1% 오차.
  • Router → MSG → System Simulator로 깔끔하게 분리된 구조 + 일회성 프로파일 기반 HW 모델.
  • MoE 라우팅, PD 분리, CPU/CXL 풀링, PIM 오프로드, 파워, SBI를 1급으로 지원.
