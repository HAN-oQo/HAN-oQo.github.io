NVIDIA CMX (ICMSP) — tiering the KV cache down to NVMe NVIDIA CMX (ICMSP) — KV 캐시를 NVMe까지 계층화하기

A summary of NVIDIA's CMX — "Context Memory Storage Platform" (its announcement URL calls it the Inference Context Memory Storage Platform, hence the community abbreviation ICMSP), unveiled at CES 2026. Two questions organize this note: why now, and what's actually new. The short version: long context, reasoning, and agents have blown the KV cache past what GPU memory can hold — and reloading it from an SSD is now faster than recomputing it. CMX standardizes tiering the KV cache GPU HBM → CPU DRAM → NVMe SSD, and offloads the storage I/O to a BlueField-4 DPU so the GPU never stalls. Sourced from the Spheron guide and cross-checked against NVIDIA's own announcement. CES 2026에서 공개된 NVIDIA CMX(Context Memory Storage Platform — 발표 URL은 Inference Context Memory Storage Platform이라 커뮤니티 약어가 ICMSP) 요약. 두 질문으로 꿴다: 왜 지금인가, 그리고 뭐가 새로운가. 짧게: 긴 컨텍스트·추론·에이전트가 KV 캐시를 GPU 메모리가 감당 못 할 만큼 키웠고 — 그걸 SSD에서 다시 읽는 게 이제 재계산보다 빠르다. CMX는 KV 캐시를 GPU HBM → CPU DRAM → NVMe SSD로 계층화하는 걸 표준화하고, 스토리지 I/O를 BlueField-4 DPU에 떠넘겨 GPU가 멈추지 않게 한다. Spheron 가이드 요약 + NVIDIA 공식 발표로 교차검증.

one-line summary한 줄 요약 The KV cache for one Llama-3.1-70B user at a 1M-token context is ~320 GB — 4× an H100's whole HBM (NVIDIA's own figure). It can't live on the GPU. CMX makes the KV cache a tiered, cluster-wide memory: hot blocks on GPU HBM, warm on CPU DRAM, cold on NVMe SSD — moved by cuFile (GPU↔NVMe direct), scheduled by a BlueField-4 DPU (off the host CPU), shared across nodes by NIXL. The reason it pays off: reloading a cached prefix from NVMe is faster than recomputing it. What's new isn't the idea (LMCache / Mooncake / DeepSeek already tier KV to disk) — it's the standardization + hardware offload. 1M 토큰 컨텍스트에서 Llama-3.1-70B 사용자 한 명의 KV 캐시가 ~320 GB — H100 HBM 전체의 4배(NVIDIA 공식 수치). GPU에 못 올린다. CMX는 KV 캐시를 계층화된 클러스터 전역 메모리로 만든다: hot은 GPU HBM, warm은 CPU DRAM, cold는 NVMe SSD — cuFile(GPU↔NVMe 직접)로 옮기고, BlueField-4 DPU가 (호스트 CPU 밖에서) 스케줄링하고, NIXL로 노드 간 공유. 수지가 맞는 이유: 캐시된 prefix를 NVMe에서 다시 읽는 게 재계산보다 빠르기 때문. 새로운 건 아이디어가 아니라(LMCache/Mooncake/DeepSeek이 이미 KV를 디스크로 계층화) — 표준화 + 하드웨어 오프로드다.

Glossary용어집

KV cacheKV 캐시

The per-token keys/values attention reuses so it doesn't recompute the whole prompt each step. Grows linearly with context length — the thing that overflows GPU memory.어텐션이 매 스텝 프롬프트 전체를 재계산하지 않으려 재사용하는 토큰별 key/value. 컨텍스트 길이에 선형 증가 — GPU 메모리를 넘치게 하는 주범.

CMX / ICMSP

NVIDIA's platform that standardizes KV-cache tiering across GPU HBM → CPU DRAM → NVMe. Official name CMX; "ICMSP" is the longer form from the announcement URL.KV 캐시를 GPU HBM → CPU DRAM → NVMe로 계층화하는 걸 표준화한 NVIDIA 플랫폼. 공식명 CMX; "ICMSP"는 발표 URL의 롱폼.

cuFile / GPUDirect StoragecuFile / GPUDirect Storage

A GPU-direct NVMe transfer API — data moves between GPU memory and the SSD without routing through the CPU, cutting latency and CPU overhead.GPU 직접 NVMe 전송 API — GPU 메모리와 SSD 사이 데이터가 CPU를 거치지 않고 이동, 지연·CPU 부담 절감.

BlueField-4 DPUBlueField-4 DPU

A data-processing unit (800 Gb/s net + 64-core Grace CPU) that runs the KV I/O scheduling, eviction, and tier movement off the host CPU. Ships H2 2026.KV I/O 스케줄링·축출·계층 이동을 호스트 CPU 밖에서 돌리는 데이터 처리 장치(800 Gb/s 네트워크 + 64코어 Grace CPU). H2 2026 출시.

NIXL

NVIDIA Inference Transfer Library — moves KV blocks across a cluster (NVLink single-node, InfiniBand RDMA multi-node, PCIe local, TCP fallback). Dynamo orchestrates on top.NVIDIA Inference Transfer Library — 클러스터 전역으로 KV 블록 이동(NVLink 단일노드, InfiniBand RDMA 다중노드, PCIe 로컬, TCP 폴백). 위에서 Dynamo가 오케스트레이션.

prefix reuseprefix 재사용

Reusing an already-computed KV cache for a shared prefix (system prompt, RAG doc, chat history) instead of recomputing it. The workload CMX is built for.공유 prefix(시스템 프롬프트·RAG 문서·대화 이력)의 이미 계산된 KV 캐시를 재계산 대신 재사용. CMX가 겨냥한 워크로드.

1Why now — the KV-cache memory wall왜 지금 — KV 캐시 메모리 벽

Three shifts landed at once: million-token context windows, reasoning models that emit long chains of thought, and agents that carry context across many turns. All three inflate the one thing that scales linearly with context — the KV cache. It has hit a wall: NVIDIA's own framing is that at a 1M-token context, one Llama-3.1-70B user's KV cache is ~320 GB, four times an entire H100's HBM. You physically cannot keep it on the GPU. 세 변화가 한꺼번에 왔다: 100만 토큰 컨텍스트, 긴 사고사슬을 뿜는 추론 모델, 여러 턴에 걸쳐 컨텍스트를 나르는 에이전트. 셋 다 컨텍스트에 선형 증가하는 그 하나 — KV 캐시 — 를 부풀린다. 그게 벽에 부딪혔다: NVIDIA 표현으로, 1M 토큰에서 Llama-3.1-70B 사용자 한 명의 KV 캐시가 ~320 GB로 H100 HBM 전체의 4배. 물리적으로 GPU에 못 둔다.

Fig 1 — The memory wall. At 128K tokens one user's KV cache (~40 GB) already fills most of an H100, capping concurrency at 1–2 users; at 1M tokens (~320 GB) it overflows every current GPU, so a bigger tier is not an optimization but a requirement. Figures are NVIDIA's / the Spheron guide's.그림 1 — 메모리 벽. 128K에서 사용자 한 명의 KV 캐시(~40 GB)가 이미 H100 대부분을 채워 동시 사용자를 1–2명으로 제한하고; 1M(~320 GB)에선 현존 모든 GPU를 넘쳐, 더 큰 계층이 최적화가 아니라 필수가 된다. 수치는 NVIDIA/Spheron 가이드 기준.

2The unlock — loading beats recomputing전환점 — 읽는 게 재계산보다 빠르다

Tiering to disk only makes sense if fetching the cache back is cheaper than just redoing the work. That crossover has now flipped. Per the Spheron guide: reloading ~40 GB of KV blocks from NVMe takes about 6 s — slow until you compare it to recomputing a 128K-token prefix from scratch (~11 s on an H100). And when the block is still warm (a real prefix-cache hit), the load is ~0.8 s. For a 1M-token RAG prefill the gap is starker: ~90 s to recompute vs ~8 s to load. Fast SSDs plus GPU-direct transfer made storage cheaper than compute for long, reused prefixes — that is the reason CMX exists now. 디스크 계층화는 캐시를 되가져오는 게 그 작업을 다시 하는 것보다 쌀 때만 의미가 있다. 그 손익분기가 이제 뒤집혔다. Spheron 가이드 기준: NVMe에서 ~40 GB KV 블록을 다시 읽는 데 약 6초 — 느려 보이지만 128K prefix를 처음부터 재계산(H100에서 ~11초)과 비교하면 다르다. 블록이 아직 warm이면(진짜 prefix 캐시 히트) 로드는 ~0.8초. 1M 토큰 RAG prefill이면 격차가 더 크다: 재계산 ~90초 vs 로드 ~8초. 빠른 SSD + GPU 직접 전송이 길고 재사용되는 prefix에선 스토리지를 연산보다 싸게 만들었다 — CMX가 지금 존재하는 이유.

Fig 2 — Why tiering pays off. Reloading a long prefix's KV from NVMe is faster than recomputing it, and a warm hit is far faster still — so caching to a cheaper tier beats redoing the prefill whenever the prefix is reused. Numbers are the Spheron guide's illustrative figures.그림 2 — 계층화가 수지 맞는 이유. 긴 prefix의 KV를 NVMe에서 다시 읽는 게 재계산보다 빠르고, warm 히트는 훨씬 더 빠르다 — prefix가 재사용되면 더 싼 계층에 캐시하는 게 prefill을 다시 하는 것보다 낫다. 수치는 Spheron 가이드의 예시값.

3What CMX is — three tiers + a DPUCMX란 — 3계층 + DPU

CMX treats the KV cache like a CPU treats memory: a hierarchy where the hottest data sits in the fastest, scarcest tier and everything else spills downward. Hot blocks (active generation) stay in GPU HBM; warm blocks (finished requests likely to be reused) move to CPU DRAM; cold blocks (historical context, evicted prefixes) land on NVMe SSD. Three pieces make the movement cheap enough to be worth it: CMX는 KV 캐시를 CPU가 메모리를 다루듯 다룬다: 가장 뜨거운 데이터가 가장 빠르고 희소한 계층에 있고 나머지는 아래로 흘러내리는 위계. Hot 블록(활성 생성)은 GPU HBM에; warm 블록(재사용 가능성 있는 완료 요청)은 CPU DRAM으로; cold 블록(과거 컨텍스트·축출된 prefix)은 NVMe SSD로. 이동을 감당할 만큼 싸게 만드는 세 조각:

Fig 3 — The three-tier KV hierarchy. Hot/warm/cold blocks flow down as they cool; cuFile moves them GPU↔NVMe without the CPU, a BlueField-4 DPU schedules the movement off the host CPU so the GPU never waits, and NIXL shares blocks across the cluster. Bandwidth/latency figures per the Spheron guide & NVIDIA.그림 3 — 3계층 KV 위계. hot/warm/cold 블록이 식으면서 아래로 흐르고; cuFile이 CPU 없이 GPU↔NVMe로 옮기며, BlueField-4 DPU가 이동을 호스트 CPU 밖에서 스케줄링해 GPU가 안 기다리게 하고, NIXL이 클러스터 전역으로 블록을 공유. 대역폭/지연 수치는 Spheron 가이드·NVIDIA 기준.

The BlueField-4 is the genuinely new hardware: 800 Gb/s networking, a 64-core Grace CPU complex, and hardware crypto/CRC — a whole storage-and-network computer sitting between the GPUs and the SSDs. It ships in H2 2026, so today the same tiering runs software-only (§4). BlueField-4가 진짜 새 하드웨어다: 800 Gb/s 네트워킹, 64코어 Grace CPU 복합체, 하드웨어 암호/CRC — GPU와 SSD 사이에 앉은 스토리지·네트워크 컴퓨터 한 대. H2 2026 출시라, 지금은 같은 계층화가 소프트웨어로만 돈다(§4).

4What's special, and when it helps뭐가 특별한가, 언제 도움되나

The idea — spilling the KV cache to CPU DRAM and NVMe — is not new. LMCache (open-source, Apache-2.0) does it in software today; Mooncake and DeepSeek's NVMe cache are production proofs. So what is NVIDIA actually adding? Two things: standardization — one platform plus a storage-partner ecosystem (VAST, WEKA, DDN, Dell, HPE, IBM, Pure Storage…) so KV tiering becomes a product you buy, not a system you hand-build; and hardware offload — the BlueField-4 DPU moves the I/O scheduling, eviction, and tier movement off the host CPU, which is meant to cut tail latency at high concurrency. In one line: CMX turns the KV cache from an ephemeral, GPU-only thing into a tiered, persistent, cluster-shared memory — and drags the storage industry into the inference stack. 아이디어 — KV 캐시를 CPU DRAM·NVMe로 흘려보내기 — 는 새롭지 않다. LMCache(오픈소스, Apache-2.0)가 오늘 소프트웨어로 하고 있고; Mooncake·DeepSeek의 NVMe 캐시가 프로덕션 증거다. 그럼 NVIDIA가 실제로 더하는 건? 둘: 표준화 — 한 플랫폼 + 스토리지 파트너 생태계(VAST·WEKA·DDN·Dell·HPE·IBM·Pure Storage…)로 KV 계층화를 직접 짜는 시스템이 아니라 사는 제품으로 만듦; 그리고 하드웨어 오프로드 — BlueField-4 DPU가 I/O 스케줄링·축출·계층 이동을 호스트 CPU 밖으로 옮겨 고동시성에서 tail latency를 줄이려 함. 한 줄로: CMX는 KV 캐시를 휘발성·GPU 전용에서 계층화·영속·클러스터 공유 메모리로 바꾸고 — 스토리지 산업을 추론 스택 안으로 끌어들인다.

✓ Helps most when prefixes repeat✓ prefix가 반복될 때 이득

Multi-turn agents; reasoning models (long CoT); 1M-token RAG with reused documents; a shared system prompt across thousands of chats; 512K+ context serving.멀티턴 에이전트; 추론 모델(긴 CoT); 문서 재사용하는 1M RAG; 수천 챗에 걸친 공유 시스템 프롬프트; 512K+ 컨텍스트 서빙.

✗ No benefit (or slightly worse)✗ 이득 없음 (혹은 약간 손해)

Short-context, single-turn inference with no prefix overlap — there's nothing cached to reload, and the guide notes DPU scheduling overhead can add a little latency.짧은 컨텍스트·단일턴에 prefix 겹침 없음 — 다시 읽을 캐시가 없고, 가이드는 DPU 스케줄링 오버헤드가 약간의 지연을 더할 수 있다고 함.

NVIDIA의 대표 수치 "최대 5× tokens/sec", "5× 전력효율"은 CES 2026 발표; "최대 20× TTFT"는 파트너 벤치마크 — 전부 가장 유리한 고-prefix-재사용 워크로드에서. 가이드의 백만 토큰당 비용 표는 Spheron의 2026년 6월 가격. 전부 보장이 아니라 베스트케이스 마케팅 수치로 보라; 이식 가능하고 검증 가능한 사실은 §2의 로드 vs 재계산 손익분기다.

Editor's note — our take (not NVIDIA's claim)편집자 주 — 우리 관점 (NVIDIA 주장 아님)

Separate the idea from the hardware. The load-beats-recompute crossover and three-tier KV cache are vendor-neutral and available now via LMCache — that's the part worth adopting on any stack, including our MI250 / AMD boxes, where the win is just fast NVMe + software tiering + prefix caching. The BlueField-4 / cuFile / NIXL layer is the NVIDIA-locked accelerator on top; it lowers CPU overhead and tail latency but arrives H2 2026 and ties you to NVIDIA DPUs + partner storage. For a heimdall-style gateway the practical takeaway is upstream of any DPU: maximize prefix reuse and give the cache a real second tier before reaching for special hardware. 아이디어와 하드웨어를 분리하라. 로드-우세 손익분기와 3계층 KV 캐시는 벤더 중립이고 LMCache로 지금 쓸 수 있다 — MI250/AMD 박스 포함 어느 스택에서든 채택할 가치가 있는 부분이고, 거기서 이득은 그냥 빠른 NVMe + 소프트웨어 계층화 + prefix 캐싱이다. BlueField-4/cuFile/NIXL 계층은 그 위의 NVIDIA 종속 가속기; CPU 부담·tail latency를 낮추지만 H2 2026 출시에 NVIDIA DPU + 파트너 스토리지에 묶인다. heimdall류 게이트웨이엔 특수 하드웨어보다 먼저 오는 실무 교훈: prefix 재사용을 극대화하고 캐시에 진짜 두 번째 계층을 줘라.
