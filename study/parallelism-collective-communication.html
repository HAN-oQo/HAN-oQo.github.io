1Communication primitives & their cost통신 primitive와 비용

Cost model. Any collective costs α·(rounds/hops) + β·(bytes moved) — α = per-message latency, β = per-byte transfer (the alpha-beta / Hockney model) [1]. Small messages are latency-bound (α dominates → fewer rounds win); large messages are bandwidth-bound (β dominates → bytes moved win). 비용 모델. 어떤 collective든 비용 = α·(라운드/홉) + β·(이동 바이트) — α=메시지당 지연, β=바이트당 전송(alpha-beta/Hockney 모델) [1]. 작은 메시지는 지연 바운드(α 지배 → 라운드 적은 게 유리), 큰 메시지는 대역폭 바운드(β 지배 → 이동 바이트가 관건).

two facts that explain everything전부를 설명하는 두 사실 ① all-reduce = reduce-scatter + all-gather. NCCL says it verbatim: "Executing ReduceScatter, followed by AllGather, is equivalent to the AllReduce operation" [2]. This is why sequence-parallel TP can swap one all-reduce for AG+RS at identical bytes. ② Ring vs Tree. Ring all-reduce is bandwidth-optimal — per-rank traffic ≈ 2(N−1)/N · data, independent of N [3] — but its latency grows linearly with N; NCCL's double-binary trees give O(log N) latency for small/medium messages and auto-switch back to rings for bandwidth [4]. ① all-reduce = reduce-scatter + all-gather. NCCL 원문: "ReduceScatter 후 AllGather 실행은 AllReduce와 동등" [2]. 그래서 sequence-parallel TP가 all-reduce 하나를 같은 바이트로 AG+RS로 바꿀 수 있다. ② Ring vs Tree. Ring all-reduce는 대역폭 최적 — rank당 트래픽 ≈ 2(N−1)/N · data, N 무관 [3] — 그러나 지연이 N에 선형; NCCL의 double-binary tree는 작은/중간 메시지에 O(log N) 지연이고 대역폭이 필요하면 ring으로 자동 전환 [4].

Ring vs Tree — how NCCL actually lays a collective on the wireRing vs Tree — NCCL이 collective를 실제 배선에 까는 방식

Ring and Tree are not collectives — they are the two main schedules of point-to-point sends NCCL uses to realize a mesh collective (above all, all-reduce) across N GPUs. Same result, different message order. NCCL picks one automatically from message size, GPU count, and topology; you only override (NCCL_ALGO=Ring|Tree|NVLS) to debug. Ring과 Tree는 collective가 아니다 — mesh collective(특히 all-reduce)를 N개 GPU에서 실현하려고 NCCL이 쓰는 두 가지 point-to-point 송신 스케줄이다. 결과는 같고 메시지 순서만 다르다. NCCL이 메시지 크기·GPU 수·토폴로지로 자동 선택하며, 디버깅할 때만 NCCL_ALGO=Ring|Tree|NVLS로 강제한다.

Ring. Put the N GPUs in a logical circle; each GPU only ever talks to its 2 neighbors. All-reduce = a reduce-scatter phase (N−1 steps: forward a chunk to the right neighbor, adding as it goes) then an all-gather phase (N−1 steps: the finished chunks circulate). Per-GPU traffic = 2(N−1)/N · size — independent of N → bandwidth-optimal [3]. The catch: 2(N−1) sequential hops → latency grows linearly with N. Best for large messages. Ring. N개 GPU를 논리적 원으로 배치; 각 GPU는 양옆 2개하고만 통신. all-reduce = reduce-scatter 단계(N−1스텝: 오른쪽 이웃으로 청크 전달하며 합산) + all-gather 단계(N−1스텝: 완성 청크 순환). GPU당 트래픽 = 2(N−1)/N · size — N 무관 → 대역폭 최적 [3]. 단점: 2(N−1) 순차 홉 → 지연이 N에 선형 증가. 큰 메시지에 유리.

Tree. Arrange the GPUs as a (binary) tree: reduce up to the root (≈log₂N steps), then broadcast back down (≈log₂N steps) → latency O(log N), far better when N is large or the message is small. The catch: a plain tree drives only half the links per phase, so NCCL uses double binary trees (two interleaved trees) to use full bandwidth in both directions [4]. Tree. GPU를 (이진) 트리로 배치: root까지 reduce 올림(≈log₂N스텝) 후 다시 broadcast 내림(≈log₂N스텝) → 지연 O(log N), N이 크거나 메시지가 작을 때 훨씬 유리. 단점: 단순 트리는 단계마다 링크의 절반만 써서, NCCL은 double binary tree(두 트리를 엇갈리게)로 양방향 풀 대역폭을 쓴다 [4].

TP shards each GEMM (first weight column-parallel, second row-parallel) so GeLU needs no sync; the row-parallel output is summed with an all-reduce. Megatron: "two all-reduces in the forward path and two in the backward path" — at inference (no backward) that's 2 per layer [5]. Each all-reduce moves the b·s·h activation tensor, not weights. TP는 각 GEMM을 샤딩(첫 가중치 column-parallel, 둘째 row-parallel)해 GeLU에 동기가 필요 없게 하고, row-parallel 출력을 all-reduce로 합산. Megatron: "forward 2회 + backward 2회 all-reduce" — 추론(backward 없음)은 레이어당 2회 [5]. 각 all-reduce는 가중치가 아니라 b·s·h activation을 옮긴다.

EP shards experts; each MoE layer routes tokens to the GPU holding their expert (all-to-all dispatch) and sends results back (all-to-all combine) [8]. Buffers are fixed-size (expert capacity; overflow tokens skip via the residual) [7]. Cross-node all-to-all dominates: DeepSeek-V3 measures a "computation-to-communication ratio of approximately 1:1" [8]. EP는 expert를 샤딩; 각 MoE 레이어가 토큰을 해당 expert의 GPU로(all-to-all dispatch) 보내고 결과를 돌려받음(all-to-all combine) [8]. 버퍼는 고정 크기(expert capacity; 초과 토큰은 residual로 우회) [7]. 노드 간 all-to-all이 지배적: DeepSeek-V3는 "연산-통신 비 ≈1:1" 측정 [8].

DP at inference replicates the full model on independent request batches → no per-layer collective (unlike DP-training, which all-reduces gradients). The exception is vLLM's DP-attention for MoE/MLA: attention runs DP (avoids duplicating the KV cache) while experts run EP/TP, so all ranks must step in lockstep — vLLM inserts "empty 'dummy' forward passes … in all ranks that don't currently have any requests" and runs "a collective operation … every N steps to determine when all ranks become idle" [15]. DP는 추론에선 모델 전체를 독립 요청 배치에 복제 → 레이어당 collective 없음(gradient를 all-reduce하는 DP-학습과 다름). 예외는 MoE/MLA용 vLLM DP-attention: attention은 DP(KV cache 중복 회피), expert는 EP/TP라 전 rank가 lockstep이어야 함 — vLLM은 "요청 없는 rank에 빈 dummy forward를 넣고", "N스텝마다 collective로 전 rank idle 여부 판정" [15].

4The hardware underneath + how to check그 아래 하드웨어 + 확인법

When ncclAllReduce runs, NCCL/RCCL has already (at init) chosen the physical link per GPU pair — a first-match walk P2P → SHM → NET ranked by a distance hierarchy PATH_NVL(NVLink) < PATH_PIX/PXB(PCIe) < PATH_SYS(cross-NUMA) < PATH_NET [NCCL graph.h]. Note: NVLink and PCIe-P2P are the same "P2P transport" (not a code branch); NVSwitch is subsumed as PATH_NVL. Cross-node uses GPUDirect RDMA over InfiniBand/RoCE (or host-staged TCP fallback) [7H]. ncclAllReduce가 돌 때 NCCL/RCCL은 이미(init 때) GPU 쌍별 물리 링크를 선택해 둠 — P2P → SHM → NET 첫-매치 순회, 거리 계층 PATH_NVL(NVLink) < PATH_PIX/PXB(PCIe) < PATH_SYS(NUMA간) < PATH_NET로 랭킹 [NCCL graph.h]. NVLink와 PCIe-P2P는 같은 "P2P transport"(코드 분기 아님); NVSwitch는 PATH_NVL로 포함. 노드 간은 InfiniBand/RoCE 위 GPUDirect RDMA(또는 host-staged TCP 폴백) [7H].

busbw vs algbw — the number to trustbusbw vs algbw —믿을 수치

nccl-tests prints two bandwidths. algbw = size/time scales with rank count (don't compare to peak). busbw = algbw × a per-collective factor → rank-independent, so it maps onto the hardware peak [25]: all-reduce ×2(n−1)/n; reduce-scatter / all-gather / all-to-all ×(n−1)/n; broadcast/reduce ×1. Workflow: run the collective → read busbw → compare to the peak for the link NCCL_DEBUG says you're on. busbw ≪ peak = you're on a slower path than you think. nccl-tests는 대역폭 둘을 찍음. algbw = size/time은 rank 수에 비례(피크와 비교 X). busbw = algbw × collective별 계수 → rank 무관, HW 피크에 대응 [25]: all-reduce ×2(n−1)/n; reduce-scatter/all-gather/all-to-all ×(n−1)/n; broadcast/reduce ×1. 흐름: collective 실행 → busbw 읽기 → NCCL_DEBUG가 알려준 링크의 피크와 비교. busbw ≪ 피크 = 생각보다 느린 경로.

Live example — MI250 node (mi250-052)실측 예시 — MI250 노드 (mi250-052)

$ rocm-smi --showtopotype        # all 8 GCDs report XGMI fabric
        GPU0  GPU1  GPU2 ...      (XGMI between every pair)

$ rocm-smi --shownodesbw         # but actual DIRECT links are a partial mesh (min-max, MB/s)
        GPU0          GPU1          GPU4          GPU6          GPU2/3/5/7
GPU0    N/A           50000-200000  50000-100000  50000-50000   0-0   ← "0-0" = NOT directly connected
                      (≈200 GB/s)   (≈100 GB/s)   (≈50 GB/s)         (routed multi-hop)

$ rocm-smi --showbus             # GPU0-3 on PCIe root 0000:29-32, GPU4-7 on 0000:AD-B6 (two domains)

Reading it: every pair is XGMI fabric, but only some pairs have a direct link (200/100/50 GB/s by link count); 0-0 pairs hop through an intermediate GCD (PATH_NVB-style). So RCCL routes GPU0↔GPU3 multi-hop. Same idea as nvidia-smi topo -m showing NV12 vs NV1 vs SYS. (Captured live on mi250-052, 2026-06-16.) 읽는 법: 모든 쌍이 XGMI 패브릭이지만 일부 쌍만 직결(링크 수에 따라 200/100/50 GB/s); 0-0 쌍은 중간 GCD를 거침(PATH_NVB 식). 그래서 RCCL은 GPU0↔GPU3을 다홉 라우팅. nvidia-smi topo -m의 NV12 vs NV1 vs SYS와 같은 개념.
