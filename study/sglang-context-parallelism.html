SGLang Context Parallelism — why long context needs it, and what's actually in main SGLang Context Parallelism — 긴 컨텍스트에 왜 필요한가, 그리고 main에 실제로 뭐가 있나

Context parallelism (CP) is the one form of parallelism that splits a single sequence across GPUs — along the token/length axis. You need it when one request's context is so long that its KV cache won't fit on a GPU, or its prefill attention (which is O(length²)) is too slow on one GPU. Tensor/data/pipeline parallelism can't help here: TP still keeps the full length of KV on every rank, DP splits requests not one long request, PP splits layers. This note explains the why first (with KV-size numbers), then the menu of CP attention algorithms (ring attention vs all-to-all/Ulysses vs all-gather), then — honestly — what SGLang has actually merged vs. what the #21788 roadmap still only proposes. The merged path is prefill-only and uses all-gather of KV (not ring attention), on the FlashAttention-3 backend, Hopper-tested. Code flow with permalinks pinned to d86a7e7. Context parallelism(CP)은 하나의 시퀀스를 GPU들에 쪼개는 유일한 병렬화다 — 토큰/길이 축을 따라. 한 요청의 컨텍스트가 너무 길어 KV 캐시가 GPU에 안 들어가거나, prefill 어텐션(길이²)이 한 GPU에서 너무 느릴 때 필요하다. 텐서/데이터/파이프라인 병렬화는 여기서 못 돕는다: TP는 모든 rank에 KV의 전체 길이를 그대로 두고, DP는 한 긴 요청이 아니라 요청들을 나누며, PP는 레이어를 나눈다. 이 노트는 먼저 왜(KV 크기 수치와 함께)를, 다음 CP 어텐션 알고리즘 메뉴(ring attention vs all-to-all/Ulysses vs all-gather)를, 그리고 — 정직하게 — SGLang이 실제로 머지한 것 vs #21788 로드맵이 아직 제안만 하는 것을 설명한다. 머지된 경로는 prefill 전용이고 (ring attention이 아니라) KV all-gather를 쓰며, FlashAttention-3 백엔드, Hopper에서 테스트됨. 코드 흐름은 d86a7e7에 핀.

one-line summary한 줄 요약 A long prompt's KV cache grows linearly with length and its prefill attention grows quadratically, so one very long sequence can overflow a GPU or stall it — and TP/DP/PP can't fix it because none of them splits the sequence. CP does: it shards the tokens across GPUs, then makes attention work across the shards (ring attention rotates K/V; Ulysses does an all-to-all; SGLang's merged path simply all-gathers K/V and runs FlashAttention-3 locally). Honest status: SGLang's #21788 is a 2026-Q2 roadmap; what's actually in main today is prefill-only CP via all-gather (not ring attention), FA3-only, single-machine (tp≤8), Hopper-tested, "still under experiment". Decode CP, Helix, and ring/seq-dim KV sharding are proposed, not shipped — and a unified layers/cp/ module exists but its methods are NotImplementedError stubs. 긴 프롬프트의 KV 캐시는 길이에 선형으로, prefill 어텐션은 제곱으로 커져, 아주 긴 시퀀스 하나가 GPU를 넘치게 하거나 멈춰 세운다 — 그리고 TP/DP/PP는 시퀀스를 쪼개지 않으므로 못 고친다. CP는 쪼갠다: 토큰을 GPU들에 분산하고, 어텐션이 그 조각들 사이에서 동작하게 만든다(ring attention은 K/V를 회전; Ulysses는 all-to-all; SGLang 머지 경로는 단순히 K/V를 all-gather해 로컬에서 FlashAttention-3). 정직한 상태: SGLang #21788은 2026-Q2 로드맵; 오늘 main에 실제 있는 건 all-gather 기반 prefill 전용 CP(ring attention 아님), FA3 전용, 단일 머신(tp≤8), Hopper 테스트, "아직 실험 중". Decode CP, Helix, ring/seq-dim KV 샤딩은 제안일 뿐 미배포 — 통합 layers/cp/ 모듈은 있으나 메서드가 NotImplementedError 스텁.

1Why CP exists — the long-context wall, and why TP/DP/PP don't helpCP가 존재하는 이유 — 긴 컨텍스트의 벽, TP/DP/PP가 안 되는 이유

Picture one request with a very long prompt — say 1,000,000 tokens. Two things blow up, both tied to that single sequence: 아주 긴 프롬프트 — 가령 100만 토큰 — 를 가진 요청 하나를 떠올려보자. 두 가지가 터지고, 둘 다 그 하나의 시퀀스에 묶여 있다:

  • KV cache grows linearly with length. Every token you process leaves a key/value entry per layer that later tokens must attend to. For a 70B-class model that is hundreds of KB per token, so a million-token context needs hundreds of GB of KV — more than one GPU has. KV 캐시가 길이에 선형으로 증가. 처리하는 모든 토큰이 레이어당 key/value 항목을 남기고, 이후 토큰이 그걸 어텐션해야 한다. 70B급 모델이면 토큰당 수백 KB라, 100만 토큰 컨텍스트는 수백 GB의 KV가 필요 — GPU 하나보다 크다.
  • Prefill attention grows quadratically. Prefill computes attention among all prompt tokens — O(length²). At a million tokens that is an enormous amount of work to do on one device. Prefill 어텐션이 제곱으로 증가. Prefill은 모든 프롬프트 토큰 사이의 어텐션을 계산 — O(길이²). 100만 토큰이면 한 장치에서 하기엔 엄청난 양.

"Dense attention FLOPs scale quadratically with context length … The KV cache grows linearly with context."

— Meta Engineering, "Scaling LLM inference" · engineering.fb.com [blog]

Why the parallelisms you already know don't solve it이미 아는 병렬화가 못 푸는 이유

This is the crux that confuses people. We have several parallelisms — but only CP splits the sequence itself: 사람들을 헷갈리게 하는 핵심이다. 병렬화가 여럿 있지만 — CP만이 시퀀스 자체를 쪼갠다:

"TP2: each rank holds a full KV cache copy … DP2: a single sequence's KV cache still lives on one device … CP2: partitions the KV cache across devices."

— SGLang issue #12196 · github.com/sgl-project/sglang/issues/12196 [issue]

2What CP is — split the sequence, then deal with global attentionCP란 — 시퀀스를 쪼개고, 전역 어텐션을 처리

Mechanically CP is simple to state: give each of the CP ranks a slice of the token positions (and that slice's K/V). Now the hard part: attention is global — every query token must attend to all earlier key tokens, but those keys are scattered across ranks. So CP is really about how the ranks exchange K (or Q) so every query can see every key, without any single GPU ever holding the whole thing for too long. 메커니즘적으로 CP는 말하기 쉽다: CP rank 각각에 토큰 위치 한 조각(과 그 조각의 K/V)을 준다. 이제 어려운 부분: 어텐션은 전역 — 모든 query 토큰이 모든 이전 key 토큰을 어텐션해야 하는데, 그 key들이 rank에 흩어져 있다. 그래서 CP의 본질은 어느 GPU도 전체를 너무 오래 들고 있지 않으면서, 모든 query가 모든 key를 볼 수 있도록 rank들이 K(또는 Q)를 어떻게 교환하느냐다.

One subtlety worth knowing because SGLang relies on it: under a causal mask, a naive contiguous split is unfair — the rank holding the first tokens attends to almost nothing, the rank holding the last tokens attends to everything. So implementations use a "zigzag" assignment (each rank gets one early block and one late block) to even out the work. SGLang이 의존하므로 알아둘 미묘함 하나: 인과 마스크 하에서 단순 연속 분할은 불공평하다 — 앞 토큰을 가진 rank는 거의 어텐션할 게 없고, 뒤 토큰을 가진 rank는 전부 어텐션한다. 그래서 구현은 "zigzag" 배정(각 rank가 앞 블록 하나 + 뒤 블록 하나)으로 일을 고르게 만든다.

3The menu — ring attention vs all-to-all vs all-gather메뉴 — ring attention vs all-to-all vs all-gather

There are three common ways to make attention work across CP ranks. It helps to know all three, because the literature is mostly about the first two while SGLang's merged code uses the third. CP rank 간 어텐션을 동작시키는 흔한 방법이 셋 있다. 셋 다 알아두면 좋다 — 문헌은 대개 앞의 둘을 말하지만 SGLang의 머지된 코드는 셋째를 쓴다.

① Ring attention① Ring attention

Each rank keeps its query block; K/V blocks rotate around a ring, and each rank merges partial attention via online softmax. Memory per rank is independent of total length; comm overlaps compute. Scales to near-infinite context. (arXiv:2310.01889)각 rank가 query 블록 유지; K/V 블록이 ring을 따라 회전, 각 rank가 online softmax로 부분 어텐션 병합. rank당 메모리가 전체 길이와 무관; 통신이 연산과 겹침. 거의 무한 컨텍스트까지 확장. (arXiv:2310.01889)

② All-to-all (Ulysses)② All-to-all (Ulysses)

An all-to-all turns the sequence-sharded tensor into a head-sharded one: each GPU gets all tokens for a few heads, runs full local attention, then all-to-all back. Simple & low comm, but the parallelism degree is capped by the number of heads. (arXiv:2309.14509)all-to-all이 시퀀스-샤딩을 head-샤딩으로 전환: 각 GPU가 head 몇 개의 전체 토큰을 받아 로컬 전체 어텐션 후 다시 all-to-all. 단순·저통신이나 병렬도가 head 수에 막힘. (arXiv:2309.14509)

③ All-gather K/V (SGLang today)③ All-gather K/V (SGLang 현재)

Each rank simply all-gathers the full K/V from all CP ranks, writes it into its local pool, and runs ordinary FlashAttention-3 on its query shard. Simplest; every rank re-holds full-length KV (so it saves compute, not KV memory, vs a single GPU).각 rank가 단순히 모든 CP rank로부터 전체 K/V를 all-gather해 로컬 풀에 쓰고, query 조각에 평범한 FlashAttention-3를 돌림. 가장 단순; 모든 rank가 전체 길이 KV를 다시 들음(즉 단일 GPU 대비 KV 메모리가 아니라 연산을 아낌).

"each host sends key-value blocks to the next host while receives key-value blocks from the preceding host."

— Ring Attention, §3 · arXiv:2310.01889 [paper]

"each GPU receives the full sequence but only for a non-overlapping subset of the attention heads."

— DeepSpeed-Ulysses, §1 · arXiv:2309.14509 [paper]

important — SGLang's merged CP does NOT (yet) save KV memory the way ring attention would중요 — SGLang의 머지된 CP는 (아직) ring attention처럼 KV 메모리를 아끼지 않는다 Because the merged path all-gathers the full K/V onto every CP rank before running local FlashAttention-3, each rank still materializes the full-length KV. The PR author describes it plainly: "we allocate a full-sequence KV cache on each CP rank" then all-gather → FlashAttention [PR #18233]. So today's win is splitting the prefill attention compute (and query work) across ranks, not reducing KV memory per GPU. The memory-saving variant — sharding the KV by sequence dimension with ring attention — is exactly the roadmap item #25846 that is not yet shipped. Don't assume "SGLang CP" means "ring attention" or "fits a 1M-token KV that wouldn't fit on one GPU"; not yet. 머지된 경로는 로컬 FlashAttention-3 전에 전체 K/V를 모든 CP rank로 all-gather하므로, 각 rank가 여전히 전체 길이 KV를 만든다. PR 저자가 분명히 적는다: "각 CP rank에 full-sequence KV 캐시를 할당" 후 all-gather → FlashAttention [PR #18233]. 즉 오늘의 이득은 prefill 어텐션 연산(과 query 작업)을 rank들에 나누는 것이지 GPU당 KV 메모리 감소가 아니다. 메모리 절감 변형 — ring attention으로 시퀀스 차원 KV 샤딩 — 이 바로 아직 미배포인 로드맵 #25846이다. "SGLang CP"가 "ring attention"이나 "단일 GPU에 안 들어갈 1M 토큰 KV를 담는다"는 뜻이라고 가정하지 말 것; 아직 아니다.

7Status & sources상태 & 출처

Status: prefill CP is merged and usable but explicitly experimental (Hopper, FA3, single-machine tp≤8); it splits prefill compute via all-gather, not KV memory. Decode CP, Helix, ring-attention seq-dim KV sharding, and the unified layers/cp/ module are roadmap (#21788), not shipped. For comparison, vLLM ships a decode context-parallel knob (-dcp / --decode-context-parallel-size) that "reduces the KV cache duplication" across the TP domain [vLLM docs] — a different point in the same design space (decode vs SGLang's prefill). 상태: prefill CP는 머지·사용 가능하나 명시적 실험(Hopper, FA3, 단일 머신 tp≤8); all-gather로 prefill 연산을 나누지 KV 메모리를 나누지 않는다. Decode CP, Helix, ring-attention 시퀀스-dim KV 샤딩, 통합 layers/cp/ 모듈은 로드맵(#21788), 미배포. 비교로, vLLM은 TP 도메인의 "KV 캐시 중복을 줄이는" decode context-parallel 노브(-dcp / --decode-context-parallel-size)를 제공한다 [vLLM docs] — 같은 설계 공간의 다른 지점(decode vs SGLang의 prefill).

editor's note — our angle (not an SGLang claim)편집자 주 — 우리 관점 (SGLang 주장 아님) For our MI250 lab, SGLang CP is doubly out of reach today: it's FA3-only and Hopper-verified, and explicitly single-machine (tp≤8) with "cross-machine precision issues" — i.e. not the multi-node long-context vehicle one might hope for, yet. But CP is the right mental slot to hold: it's the only parallelism that attacks the long-context wall directly, and it pairs with everything else (we covered the collectives it leans on — all-gather/reduce-scatter — in the parallelism × communication note). The thing to watch on the roadmap is #25846 (sequence-dim KV sharding with ring attention): that's the version that would actually let a single 1M-token KV live across GPUs instead of being re-gathered onto each — the real long-context memory lever. Until then, "SGLang CP" means "split the prefill attention compute," which is useful but narrower than the name suggests. 우리 MI250 랩엔 SGLang CP가 오늘 이중으로 닿지 않는다: FA3 전용·Hopper 검증이고, 명시적으로 단일 머신(tp≤8)에 "노드 간 정밀도 문제" — 즉 기대할 법한 멀티노드 롱컨텍스트 수단이 아직 아니다. 그래도 CP는 잡아둘 옳은 자리다: 긴 컨텍스트 벽을 직접 치는 유일한 병렬화이고 나머지 전부와 짝이 된다(그것이 기대는 collective — all-gather/reduce-scatter — 는 병렬화 × 통신 노트에서 다뤘다). 로드맵에서 주목할 건 #25846(ring attention 기반 시퀀스-dim KV 샤딩): 단일 1M-토큰 KV를 각 GPU에 재수집하는 대신 GPU들에 걸쳐 실제로 두게 하는 버전 — 진짜 롱컨텍스트 메모리 지렛대다. 그 전까진 "SGLang CP"는 "prefill 어텐션 연산을 나눈다"는 뜻이고, 유용하지만 이름이 풍기는 것보다 좁다.
