vLLM Dual Batch Overlap (DBO) — theory, effects, code flow, status vLLM Dual Batch Overlap (DBO) — 이론·효과·코드 흐름·구현 상태

DBO splits one inference batch into two micro-batches and ping-pongs them so that while one micro-batch is doing the MoE all-to-all communication, the other is doing GPU compute — hiding communication behind computation. In vLLM it currently targets only data-parallel + expert-parallel (DP+EP) MoE deployments. This note covers the theory, the expected (and measured) pros & cons, how to turn it on, the code path with vLLM permalinks, and the implementation status. DBO는 추론 배치 하나를 두 개의 마이크로배치로 쪼개 번갈아 돌려서, 한 마이크로배치가 MoE all-to-all 통신을 하는 동안 다른 마이크로배치는 GPU 연산을 하게 — 통신을 연산 뒤에 숨긴다. vLLM에서는 현재 data-parallel + expert-parallel (DP+EP) MoE 배포에서만 동작한다. 이 노트는 이론, 예상·실측 장단점, 켜는 법, vLLM permalink로 짚는 코드 경로, 구현 상태를 다룬다.

one-line summary한 줄 요약 In large MoE serving, every layer must shuffle tokens to the GPUs holding their experts (all-to-all dispatch) and back (combine); across nodes this communication can roughly equal the compute (DeepSeek-V3 reports a ≈1:1 ratio). DBO splits the batch in two and overlaps µbatch-A's all-to-all with µbatch-B's compute. It helps when communication is the bottleneck (multi-node, high expert-parallelism); it hurts on a single node (one measurement: 38 ms → 49 ms per step) because the model weights get loaded twice. It is off by default, opt-in via --enable-dbo, and only implemented for the MoE all-to-all path — not generic tensor-parallel all-reduce. 대규모 MoE 서빙에선 매 레이어마다 토큰을 해당 전문가(expert)가 있는 GPU로 보냈다가(all-to-all dispatch) 다시 가져와야(combine) 한다. 노드를 넘어가면 이 통신이 연산과 거의 맞먹을 수 있다(DeepSeek-V3는 ≈1:1 비율 보고). DBO는 배치를 둘로 쪼개 µbatch-A의 all-to-all을 µbatch-B의 연산과 겹친다. 통신이 병목일 때(멀티노드·높은 expert-parallel) 이득, 단일노드에선 손해(한 측정: 스텝당 38ms→49ms) — 모델 가중치를 두 번 로드하기 때문. 기본 꺼짐, --enable-dbo로 opt-in, 그리고 MoE all-to-all 경로에만 구현됨(일반 tensor-parallel all-reduce는 아직 아님).

1Theory — why communication is the bottleneck, and what DBO hides이론 — 통신이 왜 병목이고 DBO가 무엇을 숨기나

A GPU forward pass is normally compute-bound: matrix multiplies keep the SMs busy. But distributed inference inserts collective communication into every layer, and that communication often cannot overlap with compute by default — the next compute needs the communicated result, so the GPU sits idle while bytes move over the wire. GPU forward는 보통 연산 바운드다 — 행렬곱이 SM을 바쁘게 한다. 그러나 분산 추론은 매 레이어에 집합통신을 끼워 넣고, 이 통신은 기본적으로 연산과 겹치지 않는다 — 다음 연산이 통신 결과를 필요로 하므로, 바이트가 선을 타는 동안 GPU는 논다.

Two regimes of communication통신의 두 가지 형태

Tensor parallel (TP) shards each weight matrix across GPUs and does two all-reduces per layer (after attention, after the MLP) — this is the original Megatron pattern [Megatron-LM]. It is blocking and not cheap: for a 70B model at TP=8 it can be ~38% of inference latency even over NVLink [Ladder-residual §2], and ~23% end-to-end on a single 8×H100 node [TokenWeave §1]. Tensor parallel(TP)는 각 가중치 행렬을 GPU에 쪼개고 레이어당 all-reduce 2회(attention 후, MLP 후)를 한다 — 원조 Megatron 패턴 [Megatron-LM]. 블로킹이고 싸지 않다: 70B·TP=8이면 NVLink로도 추론 지연의 ~38% [Ladder-residual §2], 단일 8×H100에서도 end-to-end ~23% [TokenWeave §1].

Expert parallel (EP) for MoE is worse, and it's the regime DBO targets. Each MoE layer must route every token to whichever GPU holds its chosen experts — an all-to-all dispatch — run the experts, then all-to-all combine the outputs back. As you scale experts across more nodes, more of this traffic crosses the slow inter-node fabric. MoE의 Expert parallel(EP)은 더 나쁘고, DBO가 노리는 영역이다. 매 MoE 레이어가 모든 토큰을 선택된 expert가 있는 GPU로 보내야 하고(all-to-all dispatch), expert를 돌린 뒤 결과를 다시 모은다(all-to-all combine). expert를 더 많은 노드에 펼칠수록 이 트래픽의 더 많은 부분이 느린 노드 간 패브릭을 건넌다.

"the communication overhead introduced by cross-node expert parallelism results in an inefficient computation-to-communication ratio of approximately 1:1."

— DeepSeek-V3 Technical Report, §3.2.1 · arXiv:2412.19437

A ≈1:1 ratio is the whole motivation: if communication takes about as long as compute and the two run back-to-back, you spend nearly double the time you "should". DeepSeek further notes the cross-node link (InfiniBand ~50 GB/s) is ~3.2× slower than intra-node NVLink (~160 GB/s), and that for MoE inference "the upper limit of MoE inference speed is dictated by interconnection bandwidth" [Insights into DeepSeek-V3 §2.3.2]. When comm is that large a fraction, hiding it behind compute is the single highest-leverage optimization. ≈1:1 비율이 곧 동기 전체다: 통신이 연산만큼 걸리고 둘이 차례로 돌면 "원래 걸려야 할" 시간의 거의 두 배를 쓴다. DeepSeek은 노드 간 링크(InfiniBand ~50 GB/s)가 노드 내 NVLink(~160 GB/s)보다 ~3.2배 느리며, MoE 추론에서 "MoE 추론 속도의 상한은 인터커넥트 대역폭이 결정한다"고 덧붙인다 [Insights into DeepSeek-V3 §2.3.2]. 통신이 그만큼 큰 비중이면 그걸 연산 뒤에 숨기는 게 가장 레버리지 큰 최적화다.

important — what vLLM DBO actually overlaps중요 — vLLM DBO가 실제로 겹치는 것 The TP all-reduce numbers above are background for why comm-overlap matters in general. vLLM's DBO is specifically the MoE expert-parallel all-to-all, not TP all-reduce — the design doc says "this system currently only targets DP+EP deployments" [vLLM DBO doc]. Overlapping TP all-reduce with compute is a separate, not-yet-merged effort (open PR #44677). Many secondary write-ups blur this; don't. 위의 TP all-reduce 수치는 통신-겹침이 왜 중요한지에 대한 배경이다. vLLM DBO가 겹치는 건 구체적으로 MoE expert-parallel all-to-all이지 TP all-reduce가 아니다 — 설계 문서는 "이 시스템은 현재 DP+EP 배포만 대상으로 한다"고 명시 [vLLM DBO doc]. TP all-reduce 겹치기는 별개의 미병합 작업(open PR #44677). 2차 글들이 이를 흐리니 주의.

2How it works — two micro-batches, two streams, a ping-pong동작 원리 — 두 마이크로배치·두 스트림·핑퐁

DBO's idea is straight from DeepSeek's inference-side dual-microbatch overlap — vLLM's own blog calls it "DeepSeek's microbatching strategy" [vLLM blog]: DBO의 아이디어는 DeepSeek의 추론용 dual-microbatch overlap에서 곧장 왔다 — vLLM 블로그도 "DeepSeek의 microbatching 전략"이라 부른다 [vLLM blog]:

"while one micro-batch executes a portion of MLA or MoE computation, the other micro-batch simultaneously performs the corresponding dispatch communication … seamless overlap of all-to-all communication with ongoing computation."

— Insights into DeepSeek-V3, §2.3.1 · arXiv:2505.09343v1

The mechanics in vLLM: split the batch into 2 micro-batches, run each on its own CPU worker thread, with two CUDA streams (one compute, one communication). Only one thread runs at a time; at fixed dbo_yield points inside the MoE kernel a thread launches its async all-to-all and then hands the GPU to the other thread, whose compute now runs over the in-flight communication. The receiving side is finished later via a stashed "recv hook" [PR #23693]. vLLM의 메커니즘: 배치를 2개 마이크로배치로 쪼개고, 각각을 자기 CPU 워커 스레드에서 돌리며, CUDA 스트림 2개(연산용·통신용)를 쓴다. 한 번에 한 스레드만 실행되고, MoE 커널 안의 고정된 dbo_yield 지점에서 한 스레드가 비동기 all-to-all을 띄운 뒤 GPU를 다른 스레드에 넘긴다 — 그 스레드의 연산이 진행 중인 통신 위에서 돈다. 수신 측은 저장해둔 "recv hook"으로 나중에 마무리 [PR #23693].

Orchestration in one line: Python threading (2 worker threads, one active at a time) + 2 CUDA streams + CUDA events for cross-stream ordering + a coroutine-like dbo_yield ping-pong driven from inside the fused-MoE kernel. Not asyncio. The two halves are concatenated back along the batch dimension at the end. 오케스트레이션 한 줄 요약: Python threading(워커 스레드 2개, 한 번에 하나) + CUDA 스트림 2개 + 스트림 간 순서용 CUDA event + fused-MoE 커널 내부에서 구동되는 코루틴 같은 dbo_yield 핑퐁. asyncio 아님. 두 절반은 마지막에 배치 차원으로 다시 이어 붙인다.

3Pros & cons — theory vs. what's actually been reported장단점 — 이론 vs 실제로 리포트된 것

Split into (a) what theory predicts and (b) numbers people have actually published. The honest headline: no public source isolates vLLM-DBO's standalone speedup, and the one direct vLLM micro-measurement is a single-node regression. The strong wins are reported for the multi-node MoE regime DBO is built for. (a) 이론이 예측하는 것과 (b) 사람들이 실제로 공개한 수치로 나눈다. 정직한 헤드라인: vLLM-DBO 단독 속도 향상을 분리해 보고한 공개 출처는 없고, 직접적인 vLLM 마이크로 측정 하나는 단일노드에서 회귀(느려짐)다. 강한 이득은 DBO가 만들어진 멀티노드 MoE 영역에서 보고된다.

editor's note — our angle (not a vLLM claim)편집자 주 — 우리 관점 (vLLM 주장 아님) For our work this is a clean "know when to use it" feature. On a single MI250 node (our usual lab), DBO would almost certainly regress — comm is local and the weights-loaded-twice cost dominates, exactly the 38→49 ms case. It earns its keep only once a large MoE is spread across multiple nodes with expert parallelism (the llm-d / wide-EP serving regime). So: relevant to plan for at fleet scale, not something to flip on for a single-box benchmark. It also pairs with the EP all-to-all backends (DeepEP) we'd need for wide-EP anyway. 우리 작업엔 "언제 쓸지 아는 게 핵심"인 기능이다. 단일 MI250 노드(우리 평소 랩)에선 DBO가 거의 확실히 회귀 — 통신이 로컬이고 가중치 이중 로드 비용이 지배, 딱 38→49ms 사례다. 큰 MoE를 expert parallel로 여러 노드에 펼쳤을 때(llm-d / wide-EP 서빙 영역)에만 값을 한다. 즉 fleet 스케일에서 계획할 거리이지 단일 박스 벤치에서 켜볼 스위치는 아니다. 또한 wide-EP에 어차피 필요한 EP all-to-all 백엔드(DeepEP)와 함께 간다.

The collectives, in one breath집합통신, 한 호흡에

all-reduce (TP)

Every rank contributes a partial result; everyone ends with the sum. TP uses it to add up the partial outputs of a sharded matmul. Blocking — the next op needs the summed result.모든 rank가 부분 결과를 기여하고, 모두가 합을 받음. TP가 sharded matmul의 부분 출력을 합산하는 데 사용. 블로킹 — 다음 연산이 합산 결과를 필요로 함.

all-to-all (EP) = dispatch + combine

Every rank sends a different chunk to every other rank (a transpose). MoE does it twice: dispatch scatters each token to its expert's GPU; combine gathers the expert outputs back to the token's home GPU.각 rank가 모든 rank에 서로 다른 조각을 보냄(transpose). MoE는 두 번: dispatch는 각 토큰을 expert의 GPU로 흩뿌리고, combine은 expert 출력을 원래 토큰의 GPU로 모음.

point-to-point (PP)

One rank sends directly to one other (send/recv). PP passes a stage's activations to the next stage.한 rank가 다른 한 rank로 직접(send/recv). PP가 한 stage의 activation을 다음 stage로 전달.

KV transfer (P/D · offload)

Not a collective — a one-shot move of an already-computed KV cache: prefill→decode (P/D), or GPU→CPU/remote (offload/tiering). Carried by NIXL/RDMA, LMCache, etc.집합통신 아님 — 이미 계산된 KV cache를 1회 이동: prefill→decode(P/D), 또는 GPU→CPU/원격(offload/tiering). NIXL/RDMA, LMCache 등이 운반.

Fig 4 — Three communication shapes around an LLM: all-reduce (TP, sum-and-broadcast), all-to-all (EP, the token↔expert transpose = dispatch+combine), and KV transfer (P/D, a one-shot point-to-point move). DBO overlaps the middle one. Schematic.그림 4 — LLM 주변의 세 가지 통신 형태: all-reduce(TP, 합산-브로드캐스트), all-to-all(EP, 토큰↔expert transpose = dispatch+combine), KV transfer(P/D, 1회성 point-to-point 이동). DBO는 가운데 것을 겹친다. 개략도.

where DBO fitsDBO의 위치 DBO overlaps the EP all-to-all (dispatch/combine) with compute. It does not overlap TP all-reduce (separate, unmerged PR #44677), and KV transfer is a P/D concern, not DBO's. So: DBO ⊂ Expert Parallel, and its enabling backend is whatever runs the all-to-all (DeepEP — and now NIXL EP, below). DBO는 EP의 all-to-all(dispatch/combine)을 연산과 겹친다. TP all-reduce는 겹치지 않고(별개·미병합 PR #44677), KV transfer는 P/D의 일이지 DBO가 아니다. 즉 DBO ⊂ Expert Parallel이고, 그 enabling backend는 all-to-all을 돌리는 것(DeepEP — 그리고 이제 아래 NIXL EP).

editor's note — prediction (not a vLLM claim)편집자 주 — 예측 (vLLM 주장 아님) What this should buy, in order of confidence: (1) Wider reach. Until now DBO required a DeepEP all-to-all backend; now it also runs on NIXL EP. NIXL (NVIDIA Inference Xfer Library) is the same backend-pluggable transfer layer vLLM already uses for P/D KV transfer — so a fleet that picked NIXL EP for its all-to-all (or wants one transfer stack for both KV transfer and EP) can now get DBO's comm-hiding without switching to DeepEP. (2) One fabric, composable. Because NIXL abstracts UCX/RDMA/GPUDirect and is the shared transport for P/D + wide-EP, DBO-over-NIXL-EP should compose cleanly with disaggregated / wide-EP MoE serving on a single coherent fabric — exactly the multi-node regime where DBO actually pays off. (3) Full CUDA graphs on decode. The PR adds nixl_ep to the decode-optimized cudagraph guidance, so DBO+NIXL EP can keep full CUDA graphs — which DBO needs to minimize the CPU ping-pong overhead. Caveat: this is enablement, not a speedup kernel. The realized gain depends on whether NIXL EP's all-to-all is as fast as DeepEP's low-latency kernels; if NIXL EP is slower, DBO over it hides comm but the comm it hides is larger. Net: it broadens where DBO can run more than it speeds up a fixed DeepEP setup. For us, the interesting part is the convergence — NIXL becoming the single transfer layer under P/D KV transfer, wide-EP all-to-all, and DBO overlap. 이게 가져다줄 것, 확신 순서대로: (1) 적용 범위 확대. 지금까진 DBO가 DeepEP all-to-all backend를 요구했는데, 이제 NIXL EP에서도 돈다. NIXL(NVIDIA Inference Xfer Library)은 vLLM이 P/D KV transfer에 이미 쓰는 backend-pluggable 전송 계층이라 — all-to-all로 NIXL EP를 고른(또는 KV transfer와 EP를 한 전송 스택으로 묶고 싶은) fleet이 DeepEP로 갈아타지 않고도 DBO의 통신 숨김을 얻는다. (2) 한 fabric, 조합 가능. NIXL이 UCX/RDMA/GPUDirect를 추상화하고 P/D + wide-EP의 공용 전송이므로, DBO-over-NIXL-EP는 분리/wide-EP MoE 서빙과 한 fabric 위에서 깔끔히 조합될 것 — DBO가 실제로 값을 하는 멀티노드 영역이 바로 그것. (3) decode에서 full CUDA graph. PR이 nixl_ep를 decode 최적화 cudagraph 가이던스에 추가 → DBO+NIXL EP가 full CUDA graph 유지 가능(DBO가 CPU 핑퐁 오버헤드 최소화에 필요). 단서: 이건 enablement이지 속도 커널이 아니다. 실제 이득은 NIXL EP의 all-to-all이 DeepEP low-latency 커널만큼 빠른지에 달렸다; NIXL EP가 더 느리면 DBO가 통신을 숨기되 숨기는 통신 자체가 더 크다. 요약: 고정된 DeepEP 셋업을 빠르게 한다기보다 DBO가 돌 수 있는 곳을 넓힌다. 우리에겐 흥미로운 지점이 수렴 — NIXL이 P/D KV transfer·wide-EP all-to-all·DBO overlap 아래 단일 전송 계층이 되는 것.
