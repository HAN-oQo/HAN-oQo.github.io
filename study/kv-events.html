1 · Why KV events existKV 이벤트가 존재하는 이유

Dynamo's router wants to send each request to the worker that already holds the most of that prompt's KV blocks — that's the whole point of KV-aware routing. But the prefix cache lives inside each GPU worker, and it changes every engine step as blocks are cached and evicted. The router runs in a separate Rust process. So how does it know what's in a cache it can't see? Dynamo 라우터는 각 요청을 그 프롬프트의 KV 블록을 이미 가장 많이 들고 있는 워커로 보내려 합니다 — 이게 KV 인지 라우팅의 핵심입니다. 그런데 prefix 캐시는 각 GPU 워커 안에 있고, 매 엔진 스텝마다 블록이 캐시되고 쫓겨나며 바뀝니다. 라우터는 별도의 Rust 프로세스에서 돕니다. 그럼 볼 수도 없는 캐시 안의 내용을 어떻게 알까요?

KV events are the answer. Every time a vLLM worker caches or evicts a KV block, it emits a tiny event — BlockStored / BlockRemoved — carrying only block hashes, not tensors. Dynamo subscribes to that stream and rebuilds a mirror of every worker's cache as a radix tree of block hashes. The router then scores candidates against that mirror. No GPU memory is ever shipped — just hashes. KV 이벤트가 그 답입니다. vLLM 워커가 KV 블록을 캐시하거나 쫓아낼 때마다 작은 이벤트(BlockStored / BlockRemoved)를 내보냅니다 — 텐서가 아니라 블록 해시만 담아서요. Dynamo는 그 스트림을 구독해 모든 워커 캐시의 거울을 블록 해시 radix 트리로 재구성합니다. 라우터는 그 거울을 상대로 후보를 점수 매깁니다. GPU 메모리는 한 바이트도 안 옮기고 해시만 흐릅니다.

2 · The data model — three event types데이터 모델 — 3가지 이벤트

All KV events are defined in one vLLM file. There are exactly three, plus a batch wrapper. The base class is a msgspec.Struct with tag=True (so the wire carries a type tag) and array_like=True (encoded as a compact tuple, not a map). 모든 KV 이벤트는 vLLM의 한 파일에 정의돼 있습니다. 정확히 3가지 + 배치 래퍼입니다. 베이스 클래스는 tag=True(전송에 타입 태그를 실음)와 array_like=True(맵이 아니라 압축 튜플로 인코딩)를 가진 msgspec.Struct입니다.

The only payload that matters is block_hashes + parent_block_hash. A block hash is computed from that block's token ids and its parent's hash — so identical prompt prefixes hash to identical chains across every worker. That is what makes cross-worker overlap measurable from hashes alone. 중요한 페이로드는 block_hashes + parent_block_hash뿐입니다. 블록 해시는 그 블록의 토큰 id와 부모 해시로 계산됩니다 — 그래서 동일한 프롬프트 prefix는 모든 워커에서 동일한 체인으로 해시됩니다. 이 덕분에 해시만으로 워커 간 오버랩을 측정할 수 있습니다.

3 · vLLM — when & where events firevLLM — 언제·어디서 발생하나 vLLM

Events are produced in the block pool (the prefix-cache allocator) and flushed once per engine step by the scheduler. Two layers: emit → drain+publish. All three event types are emitted from the same block pool, just on different triggers: 이벤트는 block pool(prefix 캐시 할당자)에서 생산되고, 스케줄러가 엔진 스텝마다 한 번 비웁니다(flush). 두 계층: 발생 → 모아서 발행. 세 가지 이벤트 모두 같은 block pool에서, 서로 다른 트리거로 발생합니다:

1Emit: a block gets cached → BlockStored발생: 블록이 캐시될 때 → BlockStored

When the scheduler finishes prefilling enough tokens to fill whole blocks, cache_full_blocks turns them into prefix-cache entries. If KV events are enabled, it appends a BlockStored to an in-memory queue (no I/O here — just a list push). 스케줄러가 블록을 꽉 채울 만큼 토큰을 prefill하면 cache_full_blocks가 이를 prefix 캐시 항목으로 만듭니다. KV 이벤트가 켜져 있으면 메모리 큐에 BlockStored를 추가합니다(여기선 I/O 없음 — 리스트 push만).

Eviction is symmetric — when the LRU frees blocks, BlockRemoved is queued (block_pool.py L393); a full reset queues AllBlocksCleared (L492). eviction도 대칭입니다 — LRU가 블록을 해제하면 BlockRemoved가 큐에 들어가고(block_pool.py L393), 전체 리셋이면 AllBlocksCleared가 들어갑니다(L492).

Only full blocks fire events — the remainder is dropped. The block count is a floor division, so a partial block never gets hashed, cached, or announced. With block_size=32 and a 31-token prompt, 31 // 32 = 0 → cache_full_blocks early-returns and no BlockStored is emitted at all. The 32nd token completes the block and only then does one event fire. So a 100-token prompt at block_size 32 caches 100 // 32 = 3 blocks (96 tokens); the trailing 4 tokens are invisible to routing. 꽉 찬 블록만 이벤트가 나고, 자투리는 버려집니다. 블록 수는 floor 나눗셈이라, partial 블록은 해시·캐시·발행 어디에도 안 들어갑니다. block_size=32에 prompt 31토큰이면 31 // 32 = 0 → cache_full_blocks가 곧바로 early-return하고 BlockStored가 아예 발생하지 않습니다. 32번째 토큰이 블록을 완성해야 비로소 이벤트 하나가 납니다. 즉 block_size 32에서 100토큰 prompt는 100 // 32 = 3블록(96토큰)만 캐시되고, 남는 4토큰은 라우팅에서 안 보입니다.

This is why routing precision is quantized to the block: a larger block_size (e.g. the launch script's 64) discards more trailing tokens and coarsens the KV-overlap signal on short prompts; a smaller one sharpens it but produces more events and tree nodes. 그래서 라우팅 정밀도는 블록 단위로 양자화됩니다: block_size가 크면(예: 런치 스크립트의 64) 자투리 토큰을 더 많이 버려 짧은 프롬프트의 KV 오버랩 신호가 거칠어지고, 작으면 정밀해지지만 이벤트·트리 노드가 늘어납니다.

1bEmit: eviction → BlockRemoved · reset → AllBlocksCleared발생: 축출 → BlockRemoved · 리셋 → AllBlocksCleared

The other two events come from the same queue. When the pool is under pressure and the LRU reclaims a cached block, it queues a BlockRemoved carrying just that block's hash. When the whole prefix cache is reset, a single AllBlocksCleared is queued. 나머지 두 이벤트도 같은 큐에서 나옵니다. 풀이 압박을 받아 LRU가 캐시 블록을 회수하면 그 블록 해시만 담은 BlockRemoved를 큐잉하고, prefix 캐시 전체가 리셋되면 AllBlocksCleared 하나를 큐잉합니다.

Why eviction matters to routing. A worker that cached a long prefix but then evicted it under load must stop attracting requests for that prefix — otherwise the router sends a request expecting a hit and the worker re-prefills anyway. BlockRemoved is what keeps the router's mirror honest as caches churn. 축출이 라우팅에 중요한 이유. 긴 prefix를 캐시했다가 부하로 축출한 워커는 그 prefix 요청을 더 이상 끌어오면 안 됩니다 — 안 그러면 라우터가 히트를 기대하고 보냈는데 워커가 다시 prefill하게 됩니다. BlockRemoved는 캐시가 요동칠 때 라우터의 거울을 정직하게 유지하는 장치입니다.

2Drain + publish: once per engine step모아서 발행: 엔진 스텝마다 한 번

At the end of every scheduler.step() the queued events are drained via take_events(), wrapped in a timestamped KVEventBatch, and handed to the publisher. This is the "when": one batch per engine iteration, so the cadence matches the decode loop, not individual tokens. 매 scheduler.step() 끝에서 큐에 쌓인 이벤트를 take_events()로 비우고, 타임스탬프가 찍힌 KVEventBatch로 감싸 publisher에 넘깁니다. 이게 "언제"의 답입니다: 엔진 반복마다 배치 하나 — 즉 개별 토큰이 아니라 decode 루프 주기와 같습니다.

4 · The wire — ZMQ publish전송 — ZMQ 발행 vLLM

publish() just drops the batch on a queue; a dedicated daemon thread does the network send so the engine step never blocks on I/O. The publisher is a reliable PUB socket with a sequence number and a replay buffer (a late subscriber can request missed events). publish()는 배치를 큐에 넣을 뿐이고, 전용 데몬 스레드가 네트워크 전송을 합니다 — 엔진 스텝이 I/O로 막히지 않게요. publisher는 시퀀스 번호와 리플레이 버퍼를 가진 신뢰성 PUB 소켓입니다(늦게 붙은 구독자가 놓친 이벤트를 재요청 가능).

Each message is three frames: topic (for SUB filtering), 8-byte sequence (gap detection + replay), and the msgpack payload. The endpoint comes from --kv-events-config — recall the launch script bound each worker to its own port: 각 메시지는 3프레임입니다: topic(SUB 필터링용), 8바이트 시퀀스(누락 감지 + 리플레이), 그리고 msgpack 페이로드. 엔드포인트는 --kv-events-config에서 옵니다 — 런치 스크립트가 워커마다 다른 포트에 바인딩했던 그것입니다:

tcp://*:20080 = the worker binds a PUB socket on 20080. Worker B uses 20081. Dynamo will connect a SUB socket to each. tcp://*:20080 = 워커가 20080에 PUB 소켓을 bind. 워커 B는 20081. Dynamo가 각각에 SUB 소켓을 connect합니다.

5 · Dynamo — subscribe & indexDynamo — 구독 & 인덱싱 Dynamo

1Wire it up: who subscribes to whom연결: 누가 누구를 구독하나

The same dynamo.vllm process that runs vLLM also starts a Dynamo-side subscriber. setup_kv_event_publisher reads vLLM's own --kv-events-config endpoint, rewrites the bind form tcp://*:PORT into a connect form tcp://127.0.0.1:PORT, and hands it to a Rust KvEventPublisher. vLLM을 돌리는 바로 그 dynamo.vllm 프로세스가 Dynamo 측 구독자도 함께 시작합니다. setup_kv_event_publisher가 vLLM의 --kv-events-config 엔드포인트를 읽어, bind 형태 tcp://*:PORT를 connect 형태 tcp://127.0.0.1:PORT로 바꾼 뒤 Rust KvEventPublisher에 넘깁니다.

Decode workers skip this. setup_kv_event_publisher returns early for DisaggregationMode.DECODE and when enable_prefix_caching is off — only caches worth routing on publish events. decode 워커는 건너뜁니다. setup_kv_event_publisher는 DisaggregationMode.DECODE이거나 enable_prefix_caching이 꺼져 있으면 일찍 반환합니다 — 라우팅 가치가 있는 캐시만 이벤트를 발행합니다.

2Receive + decode the msgpack batchmsgpack 배치 수신 + 디코드

The Rust zmq_listener connects a SUB socket and decodes each batch with decode_event_batch — a msgpack deserializer that understands vLLM's tag=True, array_like=True encoding and maps the variant tag to a RawKvEvent. Rust zmq_listener가 SUB 소켓을 연결하고 각 배치를 decode_event_batch로 디코드합니다 — vLLM의 tag=True, array_like=True 인코딩을 이해하고 variant 태그를 RawKvEvent로 매핑하는 msgpack 디시리얼라이저입니다.

3Process → batch → dedup → apply to the radix tree처리 → 배치 → 디덥 → radix 트리 반영

The decoded events run a short pipeline (event_processor → batching → dedup → sinks; see the module's own README diagram) and land in sinks::emit, which applies each RouterEvent to the local indexer. 디코드된 이벤트는 짧은 파이프라인(event_processor → batching → dedup → sinks; 모듈 자체 README 다이어그램 참고)을 거쳐 sinks::emit에 도착하고, 각 RouterEvent를 로컬 인덱서에 반영합니다.

apply_stored walks from parent_block_hash down and inserts the new hashes as child nodes, tagged with the worker id. The tree is now a live, per-worker mirror of every GPU's prefix cache — built entirely from hashes. apply_stored는 parent_block_hash에서 아래로 내려가며 새 해시들을 워커 id 태그와 함께 자식 노드로 삽입합니다. 이제 트리는 모든 GPU prefix 캐시의 워커별 실시간 거울이며, 전부 해시로만 구성됩니다.

4The shape of the data — one shared radix tree자료구조의 모양 — 공유 radix 트리 하나

All workers feed one tree. A node represents a single cached block (keyed by its token-hash), and it holds the set of workers that currently have that block. A second per-worker map gives O(1) access to any node by hash for fast removes. 모든 워커가 하나의 트리에 들어갑니다. 노드 하나 = 캐시된 블록 하나(토큰 해시로 키잉)이고, 그 블록을 현재 가진 워커들의 집합을 들고 있습니다. 워커별 보조 맵이 해시로 어떤 노드든 O(1) 접근을 줘서 remove가 빠릅니다.

What arrives vs what is kept. A BlockStored event carries a fair amount — including the raw token_ids — but almost all of it is consumed at ingestion to compute a hash and then dropped. Only hashes and the worker set survive into the tree. 들어오는 것 vs 보관하는 것. BlockStored 이벤트는 꽤 많은 걸 싣고 옵니다 — 원본 token_ids까지 — 하지만 대부분은 들어오는 순간 해시 계산에 쓰이고 버려집니다. 트리에는 해시와 워커 집합만 남습니다.

Where token_ids actually live. Only the Frontend (the preprocessor / tokenizer) handles raw token_ids, and only per request, transiently — it tokenizes the prompt and hashes its blocks to query the tree. Neither the event tree nor the router keeps token_ids as state. Everything persistent is a hash. token_ids가 실제로 사는 곳. 원본 token_ids를 다루는 건 Frontend(preprocessor/토크나이저)뿐이고, 그것도 요청마다 일시적으로입니다 — 프롬프트를 토크나이즈하고 그 블록을 해시해 트리에 질의합니다. 이벤트 트리도 라우터도 token_ids를 상태로 보관하지 않습니다. 영구적인 건 전부 해시입니다.

Two hashes per block — token hash vs block hash, by example블록당 해시 두 개 — token hash vs block hash, 예시로

A block carries two hashes and they are not redundant. Take block_size = 4 and a prompt where the same 4 tokens repeat: 블록은 해시를 두 개 갖고, 둘은 중복이 아닙니다. block_size = 4에 같은 4토큰이 반복되는 프롬프트로 보죠:

tokens = [10,11,12,13, 10,11,12,13] └─ block1 ─┘ └─ block2 ─┘ # 내용이 동일 token hash (이 블록의 토큰만): block1 = TH block2 = TH # 똑같음! block hash (이 블록 + 앞 prefix): block1 = seq1=TH block2 = hash(seq1,TH)=seq2 # 다름

That ambiguity is the whole reason both exist: token hash addresses content (good for tree branching & overlap), block hash addresses identity (good for pinpointing one block to remove). vLLM's remove event ships only the identity hash and no tokens, so token hash can't even be recomputed there. So apply_stored registers each node under both keys: 이 모호함이 둘 다 존재하는 이유 전부입니다: token hash는 내용 주소(트리 분기·overlap에 좋음), block hash는 정체성 주소(제거할 블록 하나를 콕 집기에 좋음). vLLM의 remove 이벤트는 정체성 해시만 보내고 토큰은 안 보내서 token hash를 재계산할 수도 없습니다. 그래서 apply_stored는 각 노드를 두 키로 등록합니다:

Mental model. Like a library shelving one book on a subject shelf (by content = token hash, how you browse) and also in the call-number catalog (by unique id = block hash, how you reclaim a specific copy). Browse by shelf, reclaim by call number. 비유. 도서관이 책 하나를 주제별 서가(내용 = token hash, 탐색용)에도 꽂고 청구기호 목록(고유 id = block hash, 회수용)에도 등록하는 것과 같습니다. 탐색은 서가로, 특정 책 회수는 청구기호로.

The two destructive events are cheap and surgical. apply_removed uses the worker's lookup map to find the node in O(1) and drops the worker from its set — it deliberately does not cascade to descendants (the query reconciles stale descendants lazily). clear_all_blocks walks the worker's entries and removes it everywhere. 파괴적인 두 이벤트는 싸고 정밀합니다. apply_removed는 워커 lookup 맵으로 노드를 O(1)에 찾아 그 노드의 집합에서 워커만 뺍니다 — 의도적으로 자손까지 전파하지 않습니다(자손의 stale 항목은 query가 지연 보정). clear_all_blocks는 워커의 항목들을 돌며 모든 곳에서 워커를 제거합니다.

So what does the router actually do with this tree? On each incoming request it hashes the prompt's blocks and calls find_matches, which walks the tree top-down. The active worker set can only shrink as it descends (a worker missing the next block drops out), so the depth each worker survives to is its overlap — how many leading blocks of this prompt that worker already holds. The result is an OverlapScores map: worker → overlap_blocks. 그럼 라우터는 이 트리로 실제로 뭘 하나? 요청이 올 때마다 프롬프트 블록을 해시해 find_matches를 부르고, 트리를 위에서 아래로 탑니다. 내려갈수록 활성 워커 집합은 줄기만 합니다(다음 블록이 없는 워커는 탈락). 그래서 각 워커가 살아남은 깊이가 곧 그 워커의 overlap — 이 프롬프트의 앞쪽 블록을 몇 개나 이미 갖고 있는지입니다. 결과는 OverlapScores 맵: worker → overlap_blocks.

Important: it does NOT just pick the longest-cache worker. The overlap is one input to a cost function. For each candidate the router computes a logit, and the lowest logit wins (argmin): 중요: 단순히 "캐시가 가장 긴 워커"를 고르는 게 아닙니다. overlap은 비용 함수의 한 입력일 뿐입니다. 후보마다 logit을 계산하고 가장 낮은 logit이 당첨입니다(argmin):

In words: logit = (prefill blocks left after subtracting cache overlap) + current decode load. A big KV overlap shrinks the first term — that's the whole payoff of the event tree — but a worker that's already saturated with decode work carries a high second term and can still lose to a less-loaded peer with slightly smaller overlap. So the router selects the cheapest worker (best reuse and capacity), not merely the one holding the most cache. The full cost function and the argmin/softmax pick are in section 6. 말로 풀면: logit = (캐시 overlap을 뺀 남은 prefill 블록) + 현재 decode 부하. KV overlap이 크면 첫 항이 줄어듭니다 — 이게 이벤트 트리의 보상 전부입니다 — 하지만 decode 작업으로 이미 포화된 워커는 둘째 항이 커서, overlap이 조금 작아도 덜 바쁜 워커에게 질 수 있습니다. 즉 라우터는 캐시를 가장 많이 든 워커가 아니라 가장 비용이 낮은 워커(재사용 이득 과 여력 둘 다)를 고릅니다. 전체 비용 함수와 argmin/softmax 선택은 섹션 6에 있습니다.

6 · Closing the loop — from events to a routing decision루프 닫기 — 이벤트에서 라우팅 결정까지 Dynamo

When a request arrives, the router hashes the prompt's blocks the same way and queries the tree. find_matches returns OverlapScores — how many blocks each worker already has — and that number flows straight into the cost function from the overview. 요청이 들어오면 라우터는 프롬프트 블록을 같은 방식으로 해시해 트리를 조회합니다. find_matches가 OverlapScores(각 워커가 이미 가진 블록 수)를 반환하고, 그 숫자가 개요 문서의 비용 함수로 바로 들어갑니다.

The full life of one event: vLLM caches a block → block_pool queues BlockStored → scheduler.step() publishes a KVEventBatch over ZMQ → Dynamo's zmq_listener decodes it → pipeline applies it to the radix tree → a later request's find_matches sees that block as overlap → worker_logit subtracts it from prefill cost → the request routes to that worker → which produces a cache hit instead of re-prefilling. The event is the feedback signal that makes the cache visible to a process that can't touch the GPU. 이벤트 한 개의 일생: vLLM이 블록 캐시 → block_pool이 BlockStored 큐잉 → scheduler.step()이 ZMQ로 KVEventBatch 발행 → Dynamo zmq_listener가 디코드 → 파이프라인이 radix 트리에 반영 → 이후 요청의 find_matches가 그 블록을 오버랩으로 인식 → worker_logit이 prefill 비용에서 차감 → 요청이 그 워커로 라우팅 → 재-prefill 대신 캐시 히트. 이벤트는 GPU를 만질 수 없는 프로세스에게 캐시를 보이게 만드는 피드백 신호입니다.
What if you turn events off? Setting enable_kv_cache_events:false means the tree is never populated. Dynamo then falls back to prediction-based routing (the router estimates overlap from the prompts it has itself dispatched) or to plain load-based modes. Events make the signal exact rather than predicted — but cost a small ZMQ stream per worker. 이벤트를 끄면? enable_kv_cache_events:false면 트리가 채워지지 않습니다. 그러면 Dynamo는 예측 기반 라우팅(자기가 보낸 프롬프트로 오버랩을 추정)이나 단순 부하 기반 모드로 폴백합니다. 이벤트는 신호를 예측이 아니라 정확하게 만들지만, 워커당 작은 ZMQ 스트림 비용이 듭니다.

7 · Worked scenarios시나리오별 그림

Three concrete cases, all at block_size = 32. The rule to keep in mind: an event fires only when a block becomes full, and prompt-prefill events are published in the engine step right after prefill, while decode events fire as later blocks top off. 1024 = 32×32 is block-aligned; 1055 = 1024 + 31 leaves a 31-token tail. 세 가지 구체 사례, 모두 block_size = 32 기준입니다. 기억할 규칙: 블록이 full이 될 때만 이벤트가 나고, prompt prefill 이벤트는 prefill 직후 스텝에 발행되며 decode 이벤트는 뒤 블록이 채워질 때 발생합니다. 1024 = 32×32는 블록 정렬이고, 1055 = 1024 + 31은 31토큰 자투리가 남습니다.

Legend. green = block cached at prefill · blue = block filled (cached) during decode · dashed gray = partial block, not full → no event · ● marks a BlockStored publish. 범례. 초록 = prefill에 캐시된 블록 · 파랑 = decode 중 채워져 캐시된 블록 · 회색 점선 = partial 블록(미완성) → 이벤트 없음 · ● 는 BlockStored 발행 시점.

A · Single turn — prompt 1024, output 32A · 싱글턴 — prompt 1024, output 32

1024 is exactly 32 blocks, so prefill caches all of them and emits one batch of 32 hashes. The 32 output tokens form one more block (positions 1024–1055) that becomes full precisely on the last generated token → one final BlockStored. Total: 33 blocks, 2 publishes (32 + 1). 1024는 정확히 32블록이라 prefill이 전부 캐시하고 해시 32개를 한 배치로 발행합니다. output 32토큰이 블록 하나(위치 1024–1055)를 이루는데, 마지막 생성 토큰에서 딱 full이 됩니다 → 마지막 BlockStored 1개. 합계: 33블록, 발행 2회(32 + 1).

B · Single turn — prompt 1055, output 32B · 싱글턴 — prompt 1055, output 32

The extra 31 prompt tokens do not add a prefill event — they sit in a partial block (B33, 31/32). That block fills only when the first output token arrives, so B33's event is deferred into decode. Then 31 of the 32 outputs land in B34, which ends 31/32 and never fires. Total full blocks = 33, same as A, but the timing differs and a 31-token tail stays uncached. Lesson: a longer prompt does not mean more (or earlier) events — only crossed block boundaries do. 추가된 31개의 prompt 토큰은 prefill 이벤트를 늘리지 않습니다 — partial 블록(B33, 31/32)에 들어가 있을 뿐입니다. 이 블록은 첫 output 토큰이 와야 full이 되므로, B33의 이벤트는 decode로 미뤄집니다. 이후 output 32개 중 31개가 B34에 들어가 31/32로 끝나 이벤트가 안 납니다. full 블록 수는 33으로 A와 같지만 타이밍이 다르고 31토큰 꼬리는 캐시되지 않은 채 남습니다. 교훈: prompt가 길다고 이벤트가 더(또는 더 일찍) 나는 게 아니라, 블록 경계를 넘을 때만 납니다.

C · Multi-turn — turn 2 reuses turn 1's cacheC · 멀티턴 — 턴2가 턴1 캐시를 재사용

Turn 2's prompt is the entire turn-1 conversation plus new text. The first 33 blocks are a prefix-cache hit: num_cached_blocks already covers them, so cache_full_blocks skips them — no recompute and no new events. Only the appended content emits — here one new full block (B34); the 8-token tail (B35) stays partial. Because the shared prefix produced no events but is already in the router's radix tree from turn 1, find_matches reports a large overlap and the request routes back to the same worker. 턴2의 prompt는 턴1 대화 전체 + 새 텍스트입니다. 앞 33블록은 prefix 캐시 히트입니다: num_cached_blocks가 이미 포함하므로 cache_full_blocks가 건너뜁니다 — 재계산도, 새 이벤트도 없음. 새로 붙은 내용만 발행되어, 여기선 새 full 블록 B34 1개; 8토큰 꼬리(B35)는 partial로 남습니다. 공유 prefix는 이벤트를 안 냈지만 턴1에서 이미 라우터 radix 트리에 들어가 있으므로 find_matches가 큰 오버랩을 보고 요청을 같은 워커로 되돌립니다.

D · Eviction & reset — BlockRemoved / AllBlocksClearedD · 축출 & 리셋 — BlockRemoved / AllBlocksCleared

The first three scenarios only produced BlockStored because the cache was growing. The destructive events appear once a worker is under memory pressure or is reset. 앞의 세 시나리오는 캐시가 커지기만 해서 BlockStored만 났습니다. 파괴적 이벤트는 워커가 메모리 압박을 받거나 리셋될 때 등장합니다.

So the full event vocabulary keeps the router's mirror in sync in both directions: BlockStored grows a worker's footprint and attracts matching requests; BlockRemoved / AllBlocksCleared shrink it so the router stops sending requests to a cache that no longer exists. Without the destructive events the router would keep routing to phantom hits and waste prefill. 즉 전체 이벤트 어휘가 라우터의 거울을 양방향으로 동기화합니다: BlockStored는 워커의 캐시 영역을 키워 매칭 요청을 끌어오고, BlockRemoved / AllBlocksCleared는 그것을 줄여 더 이상 존재하지 않는 캐시로 요청을 보내지 않게 합니다. 파괴적 이벤트가 없으면 라우터는 유령 히트로 계속 라우팅하며 prefill을 낭비하게 됩니다.
