vLLM PagedAttention v1 vs v2 — what the two decode kernels do, and where they went vLLM PagedAttention v1 vs v2 — 두 디코드 커널이 뭐가 다른가, 그리고 어디로 갔나

vLLM's original attention had two kernels: paged_attention_v1 and paged_attention_v2. They compute the same thing but parallelize differently — v2 borrows the Flash-Decoding trick of splitting the KV cache along the sequence axis to keep the GPU busy when the batch is small and the context is long. This note explains the exact difference, when vLLM picked one over the other, and the twist you'll find if you look at the repo today: on CUDA these kernels have been removed (replaced by FlashAttention/FlashInfer/Triton backends), and the v1/v2 split now survives mainly in the ROCm/AMD path. Written so a reader who knows AI models but not GPU-kernel jargon (SM, occupancy, warp, split-K…) can follow every step; code is pinned to real commits. vLLM의 초기 어텐션엔 커널이 둘 있었다: paged_attention_v1과 paged_attention_v2. 같은 걸 계산하지만 병렬화가 다르다 — v2는 배치가 작고 컨텍스트가 길 때 GPU를 바쁘게 하려고 KV 캐시를 시퀀스 축으로 쪼개는 Flash-Decoding 트릭을 빌려온다. 이 노트는 정확한 차이, vLLM이 언제 어느 쪽을 골랐는지, 그리고 오늘 레포를 보면 마주치는 반전을 설명한다: CUDA에선 이 커널들이 제거됐고(FlashAttention/FlashInfer/Triton 백엔드로 대체), v1/v2 구분은 이제 주로 ROCm/AMD 경로에만 살아 있다. AI 모델은 알지만 GPU 커널 용어(SM, occupancy, warp, split-K…)는 모르는 독자도 따라오게 썼고, 코드는 실제 커밋에 핀 고정.

one-line summary한 줄 요약 Both kernels compute paged-KV attention for one decode step; the difference is how they use the GPU. v1 assigns one GPU thread block to each (sequence, head) and that block sweeps the entire KV history in a single pass — fine when there are enough sequences × heads to fill the GPU. v2 splits each sequence's KV cache into fixed-size partitions (512 tokens), computes a partial softmax per partition in parallel, then runs a second reduction kernel to stitch the partials together with the log-sum-exp trick — this is Flash-Decoding, and it exists because at small batch + long context v1 leaves most of the GPU idle. vLLM picked v1 vs v2 with a heuristic on sequence length and batch size. The twist: at HEAD (2026-07-30) the CUDA v1/v2 kernels have been removed — the design doc is now marked "historical" — and the split-and-reduce shape survives mainly in vLLM's ROCm/AITER path (partition size 256). On CUDA, FlashAttention/FlashInfer/Triton backends do the equivalent job. 두 커널 모두 한 디코드 스텝의 paged-KV 어텐션을 계산한다; 차이는 GPU를 어떻게 쓰느냐다. v1은 각 (시퀀스, 헤드)에 GPU thread block 하나를 배정하고, 그 블록이 KV 히스토리 전체를 한 번에 훑는다 — 시퀀스 × 헤드가 GPU를 채울 만큼 많으면 괜찮다. v2는 각 시퀀스의 KV 캐시를 고정 크기 파티션(512 토큰)으로 쪼개 파티션마다 부분 softmax를 병렬 계산한 뒤, 두 번째 reduction 커널이 log-sum-exp 트릭으로 부분들을 이어 붙인다 — 이게 Flash-Decoding이고, 작은 배치 + 긴 컨텍스트에선 v1이 GPU 대부분을 놀려서 존재한다. vLLM은 시퀀스 길이와 배치 크기로 v1/v2를 골랐다. 반전: HEAD(2026-07-30)에선 CUDA v1/v2 커널이 제거됐고 — 설계 문서엔 "historical" 표시 — split-and-reduce 형태는 주로 vLLM의 ROCm/AITER 경로(파티션 크기 256)에 살아 있다. CUDA에선 FlashAttention/FlashInfer/Triton 백엔드가 동등한 일을 한다.

Glossary — the GPU-kernel words, in plain language (read this first)용어집 — GPU 커널 용어를 쉬운 말로 (먼저 읽기)

prefill vs decodeprefill vs decode

A model answers in two phases: prefill reads the whole prompt at once (many query tokens); decode then generates one token at a time (one query token per step). These kernels are for decode.모델은 두 단계로 답한다: prefill은 프롬프트 전체를 한 번에 읽고(쿼리 토큰 많음); decode는 토큰을 하나씩 생성(스텝당 쿼리 토큰 1개). 이 커널들은 decode용.

paged KV cachepaged KV 캐시

The stored Key/Value state of past tokens, split into fixed-size blocks (like memory pages) instead of one contiguous chunk — vLLM's core idea. The attention kernel must gather these scattered blocks via a block table.과거 토큰의 Key/Value 상태를 하나의 연속 덩어리가 아니라 고정 크기 블록(메모리 페이지처럼)으로 쪼개 저장 — vLLM의 핵심 아이디어. 어텐션 커널은 block table로 흩어진 블록을 모아야 한다.

SM / occupancySM / occupancy

A GPU has many SMs (Streaming Multiprocessors — ~108 on an A100). Occupancy = how many are actually busy. If your work makes fewer thread blocks than there are SMs, most of the GPU sits idle. This is the whole reason v2 exists.GPU엔 SM(Streaming Multiprocessor — A100에 ~108개)이 많다. occupancy = 실제로 바쁜 개수. 작업이 SM 수보다 적은 thread block을 만들면 GPU 대부분이 논다. v2가 존재하는 이유 전부.

thread block / warpthread block / warp

A thread block is a group of GPU threads that share fast on-chip memory and run on one SM; a warp is 32 threads inside it that execute in lockstep. In v1, one thread block handles one (sequence, head).thread block은 빠른 온칩 메모리를 공유하고 한 SM에서 도는 GPU 스레드 묶음; warp는 그 안의 32스레드로 보조를 맞춰 실행. v1에선 thread block 하나가 (시퀀스, 헤드) 하나 담당.

online softmax (log-sum-exp)online softmax (log-sum-exp)

Softmax normally needs to see all scores at once. The online trick lets you process scores in chunks while tracking a running max and running sum, so partial results can be combined later without error. This is what makes splitting possible.softmax는 보통 모든 점수를 한 번에 봐야 한다. online 트릭은 running max와 running sum을 추적하며 점수를 조각으로 처리하게 해, 부분 결과를 오차 없이 나중에 합칠 수 있다. 쪼개기를 가능케 하는 것.

partition / split-K파티션 / split-K

Cutting each sequence's KV history into fixed-length chunks (vLLM: 512 tokens) so many GPU blocks can work on one sequence in parallel. "Split-K" = parallelizing over the reduction (here, the KV-length) axis.각 시퀀스의 KV 히스토리를 고정 길이 조각(vLLM: 512 토큰)으로 잘라, 많은 GPU 블록이 한 시퀀스를 병렬 처리하게. "split-K" = reduction(여기선 KV 길이) 축으로 병렬화.

reduction kernelreduction 커널

A second, small kernel that combines the partial outputs from all partitions into the final answer — rescaling each partition's contribution by its log-sum-exp so the math is exact. v2 has one; v1 doesn't need one.모든 파티션의 부분 출력을 최종 답으로 합치는 두 번째 작은 커널 — 각 파티션 기여를 log-sum-exp로 재조정해 수학이 정확하게. v2엔 있고, v1엔 필요 없다.

FlashAttention / Flash-DecodingFlashAttention / Flash-Decoding

FlashAttention = a fast, memory-efficient attention kernel (tiled online softmax). Flash-Decoding = its decode-time variant that adds KV-axis splitting for small-batch long-context — exactly what v2 does.FlashAttention = 빠르고 메모리 효율적인 어텐션 커널(타일 online softmax). Flash-Decoding = 작은 배치·긴 컨텍스트용으로 KV 축 쪼개기를 더한 디코드 변형 — v2가 하는 바로 그것.

attention backend어텐션 백엔드

vLLM can run attention through different implementations (FlashAttention, FlashInfer, Triton, the old PagedAttention kernels, ROCm/AITER…). A registry picks one per hardware/config. "v1/v2" were the original built-in backend.vLLM은 어텐션을 여러 구현으로 돌릴 수 있다(FlashAttention, FlashInfer, Triton, 옛 PagedAttention 커널, ROCm/AITER…). registry가 하드웨어/설정별로 하나 고른다. "v1/v2"는 원조 내장 백엔드였다.

1Background — PagedAttention and the decode-time kernel배경 — PagedAttention과 디코드 시점 커널

PagedAttention is the idea that made vLLM famous (Kwon et al., 2023): store each sequence's KV cache in fixed-size blocks scattered around GPU memory — like OS memory pages — instead of one big contiguous buffer. That removes the memory fragmentation that used to waste huge amounts of GPU RAM. But it creates a problem for the attention math: the kernel can no longer assume the KV cache is one contiguous array; it has to gather scattered blocks through a block table. PagedAttention은 vLLM을 유명하게 만든 아이디어다(Kwon 외, 2023): 각 시퀀스의 KV 캐시를 하나의 큰 연속 버퍼가 아니라 GPU 메모리 여기저기 흩어진 고정 크기 블록으로 — OS 메모리 페이지처럼 — 저장한다. 예전에 GPU RAM을 크게 낭비하던 메모리 단편화를 없앤다. 하지만 어텐션 계산엔 문제를 만든다: 커널이 더는 KV 캐시가 하나의 연속 배열이라 가정할 수 없고, block table로 흩어진 블록을 모아야 한다.

So vLLM wrote its own CUDA attention kernel that understands paged KV. During decode — the phase we care about here — every step has exactly one query token per sequence, which must attend to that sequence's entire past (its whole KV cache). vLLM's own kernel design doc describes the layout precisely; note the warning at the top, which is the whole punchline of §5: 그래서 vLLM은 paged KV를 이해하는 자체 CUDA 어텐션 커널을 짰다. decode — 여기서 다루는 단계 — 에선 매 스텝 시퀀스당 정확히 쿼리 토큰 1개가, 그 시퀀스의 과거 전체(KV 캐시 전부)에 어텐션해야 한다. vLLM의 커널 설계 문서가 레이아웃을 정확히 서술하는데, 맨 위 경고에 주목하라 — §5의 핵심이다:

"This is a historical document based on the original paper for vLLM. It no longer describes the code used in vLLM today."

— vLLM docs, docs/design/paged_attention.md (banner) · @ 8700f86

Here's the key structural fact both kernels share. The kernel is launched on a grid — a 3-D array of thread blocks — shaped (num_heads, num_seqs, max_num_partitions). Each thread block handles exactly one head, one sequence, and one partition: 두 커널이 공유하는 핵심 구조는 이것. 커널은 grid — thread block의 3차원 배열 — 위에서 실행되고, 모양은 (num_heads, num_seqs, max_num_partitions)이다. 각 thread block이 정확히 헤드 하나, 시퀀스 하나, 파티션 하나를 담당한다:

"In this kernel, the shape is (num_heads, num_seqs, max_num_partitions). Therefore, each thread block only handles the calculation for one head, one sequence, and one partition."

— vLLM kernel design doc, "Grid" · @ 8700f86

That third dimension, max_num_partitions, is the entire difference between v1 and v2. In v1 it is always 1 (no splitting). In v2 it can be many (the sequence is split). Everything else — how a block reads query/key vecs, does the QK dot product, the online softmax, the value multiply — is the same shared code. Keep that in mind through the next two sections. 그 세 번째 차원 max_num_partitions가 v1과 v2의 차이 전부다. v1에선 항상 1(쪼개지 않음). v2에선 여럿일 수 있다(시퀀스를 쪼갬). 나머지 — 블록이 query/key vec를 읽는 법, QK 내적, online softmax, value 곱 — 은 같은 공유 코드다. 다음 두 섹션 내내 이걸 기억하라.

2v1 — one kernel, one pass over the whole contextv1 — 커널 하나로 전체 컨텍스트를 한 번에

v1 is the straightforward design. Launch the grid as (num_heads, num_seqs) — one thread block per (sequence, head), with max_num_partitions = 1. That single block is responsible for the sequence's entire KV history: it walks every KV block in the block table, computes the query·key scores, runs the online softmax across the whole context, multiplies by the values, and writes the final output. One block, one pass, done — no second kernel. v1은 직관적인 설계다. grid를 (num_heads, num_seqs)로 실행 — (시퀀스, 헤드)당 thread block 하나, max_num_partitions = 1. 그 블록 하나가 시퀀스의 전체 KV 히스토리를 책임진다: block table의 모든 KV 블록을 훑고, query·key 점수를 계산하고, 전체 컨텍스트에 online softmax를 돌리고, value를 곱해 최종 출력을 쓴다. 블록 하나, 한 번의 통과, 끝 — 두 번째 커널 없음.

When is this great? When there are enough sequences × heads to fill the GPU. If you're serving a big batch — say 64 sequences × 32 heads = 2,048 thread blocks — you have far more blocks than the GPU has SMs (~108), so every SM stays busy and there's no wasted work. v1 is also the cheaper option: no extra memory traffic for partial results, no reduction launch. 언제 좋은가? 시퀀스 × 헤드가 GPU를 채울 만큼 많을 때. 큰 배치를 서빙하면 — 예: 64 시퀀스 × 32 헤드 = 2,048 thread block — GPU의 SM 수(~108)보다 블록이 훨씬 많아, 모든 SM이 바쁘고 낭비가 없다. v1은 더 싼 선택이기도 하다: 부분 결과용 추가 메모리 트래픽도, reduction 실행도 없다.

where v1 falls downv1이 무너지는 곳 Small batch + long context. Imagine 1 sequence × 32 heads = 32 thread blocks, each attending over a 32K-token history. You've launched only 32 blocks onto a GPU with ~108 SMs — two-thirds of the GPU is idle — and each of those 32 blocks has to grind sequentially through 32K tokens of KV. The work is huge and the parallelism is tiny. That is exactly the case v2 was built for. 작은 배치 + 긴 컨텍스트. 1 시퀀스 × 32 헤드 = 32 thread block, 각자 32K 토큰 히스토리에 어텐션한다고 상상하라. ~108 SM의 GPU에 블록을 32개만 띄웠으니 — GPU의 3분의 2가 논다 — 그 32개 블록 각각이 32K 토큰 KV를 순차로 갈아야 한다. 일은 거대하고 병렬성은 미미하다. 바로 v2가 만들어진 경우다.

3v2 — split the KV cache, then reduce (Flash-Decoding)v2 — KV 캐시를 쪼갠 뒤 합친다 (Flash-Decoding)

v2 imports the Flash-Decoding idea (Stanford, Oct 2023). The diagnosis is exactly the v1 problem above — during decode the query length is 1, so plain FlashAttention only parallelizes over batch × heads, and when that's smaller than the number of SMs the GPU starves: v2는 Flash-Decoding 아이디어(Stanford, 2023-10)를 들여온다. 진단은 위 v1 문제 그대로다 — decode 땐 쿼리 길이가 1이라 plain FlashAttention은 배치 × 헤드로만 병렬화하고, 그게 SM 수보다 작으면 GPU가 굶는다:

"if the batch size is smaller than the number of streaming multiprocessors (SMs) on the GPU (108 for an A100), the operation will only use a small part of the GPU! … With batch size 1 and long sequences, FlashAttention will use less than 1% of the GPU."

— Flash-Decoding for long-context inference (Dao, Haziza, Massa, Sizov) · crfm.stanford.edu

The fix: parallelize over a new axis — the KV-length axis. Split each sequence's KV cache into fixed-size partitions (vLLM uses PARTITION_SIZE = 512 tokens) and do it in two kernels: 해법: 새로운 축 — KV 길이 축 — 으로 병렬화. 각 시퀀스의 KV 캐시를 고정 크기 파티션(vLLM은 PARTITION_SIZE = 512 토큰)으로 쪼개고, 두 커널로 한다:

  1. Partition kernel. Now the grid is (num_heads, num_seqs, num_partitions). Each block computes a partial softmax over just its 512-token slice, and writes three things to scratch memory: the partial output (tmp_out), the partition's exp-sum (exp_sums), and its max logit (max_logits). With, say, 64 partitions per sequence, one lonely sequence now launches 32 heads × 64 = 2,048 blocks instead of 32 — the GPU is full.Partition 커널. 이제 grid는 (num_heads, num_seqs, num_partitions). 각 블록이 자기 512 토큰 조각에 대해서만 부분 softmax를 계산하고, 스크래치 메모리에 셋을 쓴다: 부분 출력(tmp_out), 파티션의 exp-sum(exp_sums), 최대 logit(max_logits). 시퀀스당 파티션이 64개면, 외로운 시퀀스 하나가 이제 32개가 아니라 32 헤드 × 64 = 2,048 블록을 띄운다 — GPU가 꽉 찬다.
  2. Reduction kernel. A second, small kernel combines all partitions of one (sequence, head) into the final answer. It can't just add the partial outputs — each was normalized against its own local max. So it uses the log-sum-exp trick: rescale each partition's contribution by exp(local_max − global_max) weighted by its exp_sum, so the combined result is mathematically identical to attending over the whole context at once.Reduction 커널. 두 번째 작은 커널이 한 (시퀀스, 헤드)의 모든 파티션을 최종 답으로 합친다. 부분 출력을 그냥 더하면 안 된다 — 각각 자기 로컬 max로 정규화됐으니까. 그래서 log-sum-exp 트릭을 쓴다: 각 파티션 기여를 exp(local_max − global_max)로, exp_sum으로 가중해 재조정 — 그러면 합친 결과가 전체 컨텍스트에 한 번에 어텐션한 것과 수학적으로 동일하다.

Fig 1 — Same computation, opposite parallelism. v1 (top): one sequence launches only ~32 blocks, leaving most SMs idle while each grinds the full 32K-token KV. v2 (bottom): splitting the KV into 512-token partitions launches thousands of short blocks that fill the GPU, then a cheap reduction kernel combines them via log-sum-exp. Schematic.그림 1 — 같은 계산, 반대의 병렬성. v1(위): 시퀀스 하나가 ~32 블록만 띄워 대부분 SM이 노는 동안 각자 32K 토큰 KV를 간다. v2(아래): KV를 512 토큰 파티션으로 쪼개 수천 개의 짧은 블록이 GPU를 채우고, 싼 reduction 커널이 log-sum-exp로 합친다. 개략도.

v2 isn't freev2는 공짜가 아니다 v2 writes every partition's partial output to global memory and then reads it all back in the reduction kernel — extra memory traffic and a second kernel launch. When v1 already fills the GPU (big batch, or short context), that overhead is pure loss. So neither kernel is universally better; vLLM chooses per step (§4). v2는 모든 파티션의 부분 출력을 global memory에 썼다가 reduction 커널에서 다시 읽는다 — 추가 메모리 트래픽 + 두 번째 커널 실행. v1이 이미 GPU를 채우면(큰 배치, 또는 짧은 컨텍스트) 그 오버헤드는 순손해다. 그러니 어느 커널도 보편적으로 낫지 않다; vLLM은 스텝마다 고른다(§4).

4Choosing between them — the dispatch heuristic둘 중 고르기 — dispatch 휴리스틱

Because v1 wins when the GPU is already full and v2 wins when it isn't, vLLM decided per decode step with a small heuristic. Compute how many partitions the longest sequence would need, then pick v1 unless the context is long and the batch is small (the exact condition is pinned in §6): v1은 GPU가 이미 꽉 찼을 때, v2는 안 찼을 때 이기므로, vLLM은 작은 휴리스틱으로 디코드 스텝마다 결정했다. 가장 긴 시퀀스가 파티션을 몇 개 필요로 하는지 계산한 뒤, 컨텍스트가 길고 동시에 배치가 작지 않으면 v1을 고른다(정확한 조건은 §6에 핀 고정):

_PARTITION_SIZE = 512
max_num_partitions = ceil(max_seq_len / _PARTITION_SIZE)

use_v1 = (max_seq_len <= 8192
          and (max_num_partitions == 1 or num_seqs * num_heads > 512))

Unpack the two ways v1 stays selected: v1이 선택되는 두 경우를 풀어 보면:

Condition조건Meaning의미
max_num_partitions == 1The longest sequence fits in one 512-token partition (short context) — there's nothing to split, so splitting would only add overhead. Use v1.가장 긴 시퀀스가 512 토큰 파티션 하나에 들어감(짧은 컨텍스트) — 쪼갤 게 없으니 쪼개면 오버헤드만. v1 사용.
num_seqs * num_heads > 512There are already >512 (sequence, head) blocks — plenty to keep the SMs busy without splitting. v2's extra parallelism isn't needed, so its overhead isn't worth it. Use v1.이미 (시퀀스, 헤드) 블록이 512개 초과 — 쪼개지 않아도 SM을 채우기 충분. v2의 추가 병렬성이 불필요하니 오버헤드가 손해. v1 사용.
otherwise (long context, small batch)그 외 (긴 컨텍스트, 작은 배치)Use v2 — few blocks and a long KV per block; splitting fills the idle SMs.v2 사용 — 블록은 적고 블록당 KV는 길다; 쪼개서 노는 SM을 채운다.

The max_seq_len <= 8192 guard is there for a hardware reason the code comment states plainly — "For context len > 8192, use V2 kernel to avoid shared memory shortage" (v1 keeps the whole context's logits in one block's shared memory, which runs out past ~8K tokens). In short: v2 is the long-context, small-batch decode kernel; v1 is everything else. max_seq_len <= 8192 가드는 코드 주석이 분명히 밝히는 하드웨어 이유 때문이다 — "컨텍스트 8192 초과면 shared memory 부족을 피하려 V2 커널 사용"(v1은 전체 컨텍스트의 logits를 한 블록의 shared memory에 유지하는데 ~8K 토큰을 넘으면 부족해진다). 요약: v2는 긴 컨텍스트·작은 배치 디코드 커널; v1은 그 외 전부.

5The twist — where v1/v2 went (deprecated on CUDA, alive on ROCm)반전 — v1/v2는 어디로 갔나 (CUDA 폐기, ROCm 생존)

Here's the part that surprises people who go looking for these kernels today. At the HEAD commit (8700f86, 2026-07-30), the CUDA paged_attention_v1/v2 kernels are gone. The csrc/attention/ directory now contains only datatype headers — no paged_attention_v1.cu, no paged_attention_v2.cu. They were renamed out of csrc/attention/ in May 2026 (a "migrate to torch stable ABI" change, PR #43717) and then deleted outright on 2026-07-02 by PR #47361 — literally titled "Delete PagedAttention," its entire description reading "It is time." The kernel design doc was stamped "historical … no longer describes the code used in vLLM today." 오늘 이 커널들을 찾으러 가는 사람을 놀라게 하는 대목이다. HEAD 커밋(8700f86, 2026-07-30)에선 CUDA paged_attention_v1/v2 커널이 사라졌다. csrc/attention/ 디렉터리엔 이제 데이터타입 헤더만 있다 — paged_attention_v1.cu도, paged_attention_v2.cu도 없다. 2026년 5월 csrc/attention/에서 rename됐고("torch stable ABI 이관", PR #43717), 2026-07-02 PR #47361이 완전히 삭제했다 — 제목이 문자 그대로 "Delete PagedAttention", 설명 전문이 "It is time."였다. 커널 설계 문서엔 "historical … 오늘 vLLM 코드를 더는 서술하지 않음" 도장이 찍혔다.

Why: the whole attention layer got modular backends이유: 어텐션 계층이 모듈형 백엔드로

vLLM's rewrite (the "V1" engine) replaced the single built-in kernel with a backend registry: attention now runs through FlashAttention, FlashInfer, Triton, FlexAttention, or hardware-specific paths, chosen per platform and config (you can see them all in vllm/v1/attention/backends/). Those libraries already do Flash-Decoding-style KV splitting internally and are faster and better-maintained than the hand-written v1/v2 kernels — so on CUDA, the old kernels became redundant and were dropped. The v2 idea didn't die; it moved inside FlashAttention/FlashInfer. vLLM 재작성("V1" 엔진)은 단일 내장 커널을 백엔드 registry로 바꿨다: 어텐션은 이제 FlashAttention, FlashInfer, Triton, FlexAttention, 또는 하드웨어별 경로로 실행되고, 플랫폼·설정별로 선택된다(vllm/v1/attention/backends/에서 전부 볼 수 있다). 그 라이브러리들은 이미 내부적으로 Flash-Decoding식 KV 쪼개기를 하고, 손으로 짠 v1/v2보다 빠르고 유지보수가 낫다 — 그래서 CUDA에선 옛 커널이 불필요해져 빠졌다. v2 아이디어가 죽은 게 아니라 FlashAttention/FlashInfer 안으로 들어갔다.

Where it survives: the ROCm / AMD path살아남은 곳: ROCm / AMD 경로

If you grep the whole repo for paged_attention_v1 at HEAD, you get essentially one place: the ROCm AITER backend. There, vllm/v1/attention/backends/rocm_aiter_fa.py still calls torch.ops.aiter.paged_attention_v1(...), and it uses the identical v2-shaped machinery — a partition size (_PARTITION_SIZE_ROCM = 256 on AMD, vs 512 on the old CUDA path), and pre-allocated tmp_output / exp_sums / max_logits scratch buffers sized by max_num_partitions. Underneath, csrc/rocm/attention.cu holds the AMD kernels: the paged_attention_ll4mi_QKV_* partition kernels and a paged_attention_ll4mi_reduce_kernel — that reduce kernel is the v2 reduction, alive and well. The same 256-token partitioning also appears in the Triton chunked_prefill_paged_decode path. HEAD에서 레포 전체를 paged_attention_v1으로 grep하면 사실상 한 곳이 나온다: ROCm AITER 백엔드. 거기 vllm/v1/attention/backends/rocm_aiter_fa.py가 여전히 torch.ops.aiter.paged_attention_v1(...)을 호출하고, 동일한 v2 형태의 장치를 쓴다 — 파티션 크기(AMD는 _PARTITION_SIZE_ROCM = 256, 옛 CUDA는 512)와 max_num_partitions로 크기 잡힌 tmp_output / exp_sums / max_logits 스크래치 버퍼. 그 아래 csrc/rocm/attention.cu가 AMD 커널을 담는다: paged_attention_ll4mi_QKV_* 파티션 커널과 paged_attention_ll4mi_reduce_kernel — 그 reduce 커널이 바로 v2 reduction, 멀쩡히 살아 있다. 같은 256 토큰 파티셔닝이 Triton chunked_prefill_paged_decode 경로에도 나온다.

so, the honest answer to "what's the difference?"그래서, "뭐가 다른가?"에 대한 정직한 답 The difference between v1 and v2 is parallelization strategy: v1 = one block sweeps the whole context; v2 = split the context into partitions across many blocks, then reduce. That distinction is timeless (it's the FlashAttention-vs-Flash-Decoding distinction). But if you clone vLLM today expecting to find two CUDA kernels named v1 and v2, you won't — on CUDA they've been replaced by FlashAttention/FlashInfer/Triton; the named kernels now live in the ROCm/AITER path (with a 256-token partition instead of 512). v1과 v2의 차이는 병렬화 전략이다: v1 = 블록 하나가 전체 컨텍스트를 훑음; v2 = 컨텍스트를 파티션으로 쪼개 여러 블록에 분산한 뒤 reduce. 이 구분은 시대를 안 탄다(FlashAttention vs Flash-Decoding 구분이다). 하지만 오늘 vLLM을 클론해서 v1/v2라는 CUDA 커널 둘을 찾을 생각이면 못 찾는다 — CUDA에선 FlashAttention/FlashInfer/Triton으로 대체됐고, 이름 붙은 커널은 이제 ROCm/AITER 경로(512 대신 256 토큰 파티션)에 산다.

Classic v1 — one block, whole context (@ 710f0776)고전 v1 — 블록 하나, 전체 컨텍스트 (@ 710f0776)

The shared body makes the "whole context" explicit — with partitioning off, the block iterates from block 0 to the last block: v1 커널은 부분 출력 버퍼로 nullptr을 넘기고 PARTITION_SIZE = 0으로 돌아, 블록 하나가 시퀀스의 softmax 전체를 소유한다. 공유 본문이 "전체 컨텍스트"를 명시한다 — 파티셔닝이 꺼지면 블록이 0번부터 마지막 블록까지 순회:

constexpr bool USE_PARTITIONING = PARTITION_SIZE > 0;   // v1: PARTITION_SIZE = 0

const int end_block_idx   = MIN(start_block_idx + num_blocks_per_partition, num_seq_blocks);

editor's note — our angle (not a vLLM claim)편집자 주 — 우리 관점 (vLLM 주장 아님) Three takeaways for our work. (1) The v2 = Flash-Decoding insight is the one to keep: as context lengths grow and batches stay small (agents, long-doc RAG), the decode attention kernel must parallelize over the KV-length axis or it starves the GPU — that's true no matter whose kernel you run, and it's the regime we increasingly serve. (2) For MI250/ROCm specifically, this isn't history — it's our code path. On CUDA the v1/v2 kernels are gone, but our AMD vLLM decode literally runs rocm_aiter_fa.py → csrc/rocm/attention.cu's ll4mi_QKV + ll4mi_reduce, i.e. the v2 partition+reduce shape with a 256-token partition and an AITER dependency. Worth knowing which knob (partition size) and which library (AITER) actually govern our decode latency. (3) It's a lesson in serving-stack churn: a paper-famous, named kernel ("PagedAttention") got deleted with a two-word PR ("It is time") once FlashAttention/FlashInfer absorbed its job. The idea — paged KV cache — is permanent; the specific kernels were not. Boundary: everything above about the CUDA v1/v2 kernels is their historical design (pinned to pre-deletion commits), not a fresh benchmark; on CUDA today the equivalent work happens inside FlashAttention/FlashInfer. 우리 작업을 위한 세 가지. (1) v2 = Flash-Decoding 통찰이 남길 것: 컨텍스트가 길어지고 배치가 작게 유지되면(에이전트, 롱닥 RAG), 디코드 어텐션 커널은 KV 길이 축으로 병렬화하지 않으면 GPU를 굶긴다 — 누구의 커널을 돌리든 참이고, 우리가 점점 더 서빙하는 영역이다. (2) MI250/ROCm엔 이게 역사가 아니라 우리 코드 경로다. (3) 서빙 스택 churn의 교훈: 논문으로 유명한 이름 붙은 커널("PagedAttention")이, FlashAttention/FlashInfer가 그 일을 흡수하자 두 단어 PR("It is time")로 삭제됐다. 아이디어 — paged KV 캐시 — 는 영구적이지만, 특정 커널은 아니었다. 경계: 위의 CUDA v1/v2 커널 얘기는 삭제 전 커밋에 핀된 역사적 설계이지 새 벤치마크가 아니다; 오늘 CUDA에선 동등한 일이 FlashAttention/FlashInfer 안에서 일어난다.
