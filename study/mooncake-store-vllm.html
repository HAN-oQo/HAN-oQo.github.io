Mooncake in vLLM — design, code flow, and how it differs from LMCache vLLM 속의 Mooncake: 설계, 코드 흐름, LMCache 와의 차이

Mooncake pools a GPU cluster's idle CPU DRAM and SSD into one cluster-wide KV cache, so a prefix computed on instance A can be reused by instance B. This note follows vLLM's two Mooncake connectors through commit-pinned code and compares the design with LMCache. Mooncake 는 GPU 클러스터에서 놀고 있는 CPU DRAM 과 SSD 를 묶어 클러스터 전체가 공유하는 KV 캐시로 만든다. 인스턴스 A 가 계산한 프리픽스를 인스턴스 B 가 재사용할 수 있다. 이 노트는 vLLM 의 Mooncake 커넥터 두 개를 커밋 고정 코드로 따라가고 LMCache 와 설계를 비교한다.

Glossary용어

KV cache

Per-token attention keys/values kept so seen tokens are not recomputed. 이미 본 토큰을 다시 계산하지 않으려고 보관하는 토큰별 attention key/value 다.

prefix caching프리픽스 캐싱

Reusing a shared prompt prefix's KV. Standard vLLM does it within one instance's GPU memory only. 공유 프롬프트 앞부분의 KV 를 재사용한다. 기본 vLLM 은 한 인스턴스의 GPU 메모리 안에서만 한다.

KVConnector

vLLM's plug-in interface for getting/putting KV elsewhere. Mooncake and LMCache both implement it. KV 를 외부에서 가져오고 내보내는 vLLM 플러그인 인터페이스다. Mooncake 와 LMCache 모두 이것의 구현체다.

RDMA · GPUDirect

NIC reads/writes remote memory without the remote CPU. GPUDirect extends it to GPU HBM, skipping a CPU staging copy. NIC 가 상대 CPU 없이 원격 메모리를 읽고 쓴다. GPUDirect 는 이를 GPU HBM 까지 넓혀 CPU 임시 복사를 없앤다.

Transfer Engine

Mooncake's bottom layer: one API over RDMA / TCP / NVMe-oF. Mooncake 의 맨 아래 층으로, RDMA·TCP·NVMe-oF 를 하나의 API 로 감싼다.

PD disaggregation

Prefill and decode on separate instances, so KV must be shipped between them. 프리필과 디코드를 다른 인스턴스에서 돌려서 KV 를 둘 사이로 보내야 하는 구성이다.

In one line한 줄 요약
  • Mooncake is a memory fabric, not a cache library. It gives vLLM a cluster-wide, RDMA-addressable object store keyed by block hashes.
  • vLLM's own connector code decides what goes in. LMCache is the opposite: a thick external library with a thin vLLM adapter.
  • Result: Mooncake is fastest at "same prefix, another node, right now" and deliberately skips compression and non-prefix blending.
  • Mooncake 는 캐시 라이브러리가 아니라 메모리 패브릭이다. 블록 해시를 키로 쓰고 RDMA 로 접근하는 클러스터 전역 오브젝트 스토어를 vLLM 에 제공한다.
  • 무엇을 담을지는 vLLM 안의 커넥터 코드가 정한다. LMCache 는 반대로 두꺼운 외부 라이브러리가 로직을 갖고 vLLM 에는 얇은 어댑터만 있다.
  • 그래서 Mooncake 는 "같은 프리픽스를 다른 노드에서 지금 당장" 쓰는 경우에 가장 빠르고, 압축과 비-프리픽스 blending 은 일부러 하지 않는다.

1 The problem: a prefix cache that dies with the instance 문제: 인스턴스와 함께 사라지는 프리픽스 캐시

vLLM's prefix caching (on by default) lets requests sharing a prefix reuse KV blocks. It has two walls: the cache lives in this instance's GPU memory, and it only gets the GPU blocks left after the model weights. vLLM 의 프리픽스 캐싱(기본 켜짐)은 앞부분이 같은 요청끼리 KV 블록을 재사용하게 한다. 벽은 둘이다. 캐시가 이 인스턴스의 GPU 메모리에만 있고, 크기는 모델 가중치를 뺀 나머지 GPU 블록만큼이다.

Chat copes. Agentic workloads do not: turn n shares almost everything with turn n−1, but between turns the blocks get evicted and the load balancer may route the next turn to a replica that never saw the prefix. The vLLM blog quantifies it: 채팅은 버틴다. 에이전트 워크로드는 다르다. n 번째 턴은 n−1 번째와 거의 같지만, 턴 사이 몇 분 동안 블록이 축출되고 로드밸런서가 다음 턴을 프리픽스를 본 적 없는 replica 로 보내기 쉽다. vLLM 블로그의 수치는 이렇다.

"cache hit rate ... from 1.7% to 92.2%"

vLLM blog, Codex agentic traces on 1P1D — the 1.7% is the baseline, i.e. local prefix caching alone.vLLM 블로그, 1P1D 에서 Codex 에이전트 트레이스. 1.7% 는 로컬 프리픽스 캐싱만 켠 베이스라인이다. · vllm.ai/blog/2026-05-06-mooncake-store

At 1.7%, nearly every turn re-prefills a transcript some GPU computed minutes ago, while hundreds of GB of CPU DRAM and TBs of NVMe sit idle. That gap is Mooncake's entire premise. 1.7% 면 거의 매 턴, 몇 분 전 어느 GPU 가 계산해 둔 트랜스크립트를 다시 프리필한다는 뜻이다. 그동안 수백 GB CPU DRAM 과 수 TB NVMe 는 놀고 있다. 이 간극이 Mooncake 의 전제다.

2 What Mooncake actually is — three layers, two vLLM connectors Mooncake 의 실체: 3개 층, 2개의 vLLM 커넥터

"Mooncake" names a whole stack of three layers: "Mooncake" 는 층 세 개로 된 스택 전체의 이름이다.

1 · Transfer Engine

Transport over RDMA / TCP / NVMe-oF. Moves bytes between registered memory; knows nothing about KV. RDMA·TCP·NVMe-oF 전송 계층이다. 등록된 메모리 사이로 바이트만 옮기고 KV 는 모른다.

2 · Mooncake Store

Distributed object store pooling each node's DRAM (optionally SSD). Keys are strings; values are byte ranges. 각 노드의 DRAM(선택적으로 SSD)을 묶은 분산 오브젝트 스토어다. 키는 문자열, 값은 바이트 범위다.

3 · Master

Metadata service (key location, replica state, liveness), not on the data path. mooncake_master --port 50051 키 위치·replica 상태·생존 여부를 관리하는 메타데이터 서비스로, 데이터 경로에는 없다. mooncake_master --port 50051

No layer knows what a KV cache is. Which blocks to save, how to name them and when to look them up all live in vLLM. Section 5 builds on this. 어느 층도 KV 캐시를 모른다. 어느 블록을 저장할지, 어떻게 이름 붙일지, 언제 조회할지는 모두 vLLM 안에 있다. 5절의 비교가 이 사실에서 출발한다.

P2P answers "hand this request to that decoder now". The store answers "has anyone computed these blocks recently?". Hence the documented disaggregated setup runs both under MultiConnector. P2P 는 "이 요청을 저 디코더에 지금 넘겨라" 를, 스토어는 "누구든 이 블록을 최근에 계산했나?" 를 푼다. 그래서 문서의 분리 구성은 MultiConnector 아래 둘을 함께 돌린다.

4 Five design decisions worth naming 짚어둘 설계 결정 다섯 가지

① Zero-copy means "no serialization step exists"① zero-copy 는 직렬화 단계가 아예 없다는 뜻

Most caches serialize a tensor into a buffer and send it. Mooncake registers the KV storage with the NIC up front, so blocks are addressable and read/written in place. The vLLM blog: "This path requires no staging buffer and does not consume SMs." No staging buffer also means no copy kernel, so offloading steals no compute from the model. 대부분의 캐시는 텐서를 버퍼로 직렬화해서 보낸다. Mooncake 는 KV 저장소를 미리 NIC 에 등록해 두므로 블록을 주소로 바로 읽고 쓴다. vLLM 블로그 표현으로는 "This path requires no staging buffer and does not consume SMs." staging buffer 가 없으니 복사용 GPU 커널도 없고, 오프로딩이 모델의 연산을 빼앗지 않는다.

② The key embeds the parallel layout — and that sets the sharing boundary② 키에 박힌 병렬 레이아웃이 공유 경계를 정한다

The key is not just hash(tokens): it carries model_name, tp_rank, pcp, dcp, pp_rank and a KV-group id. Correct, since a TP-4 rank 2 shard is not interchangeable with a TP-8 shard, but with a blunt consequence: 키는 단순한 hash(tokens) 가 아니다. model_name, tp_rank, pcp, dcp, pp_rank, KV 그룹 id 가 붙는다. TP-4 의 rank 2 샤드는 TP-8 샤드와 호환되지 않으니 옳은 설계지만, 운영상 대가가 있다.

Practical consequence실무적 귀결 Cache is shared only between instances with the same model at the same parallel layout. Change TP and you get a separate namespace: no error, just a silent hit-rate collapse. In the blog's setup, prefill TP4 and decode DP8 share no entries; the store pays off across turns and across replicas of the same role. 같은 모델, 같은 병렬 레이아웃인 인스턴스끼리만 캐시를 공유한다. TP 를 바꾸면 별도 네임스페이스가 되고, 에러 없이 히트율만 조용히 떨어진다. 블로그 구성의 프리필 TP4 와 디코드 DP8 도 엔트리를 공유하지 않는다. 스토어의 이득은 턴 사이와 같은 역할의 replica 사이에서 나온다.

③ Everything is asynchronous by construction③ 비동기는 구조에 박혀 있다

Lookup can be non-blocking (lookup_async) and return None for "ask again next step"; loads and saves go to queue-fed threads. The scheduler comment: "Returns (None, False) when an async lookup is still in flight, signaling the scheduler to retry this request on a later step." A remote cache that blocked the scheduler would be worse than none. 조회는 논블로킹(lookup_async)으로 돌 수 있고, 루프를 멈추지 않고 None 을 돌려 다음 스텝에 다시 묻게 한다. 로드와 저장은 큐 기반 스레드로 간다. 스케줄러 쪽 주석은 이렇다. "Returns (None, False) when an async lookup is still in flight, signaling the scheduler to retry this request on a later step." 스케줄러를 막는 원격 캐시는 없느니만 못하다.

It is an operational fork, not a tuning knob: in embedded mode a rank restart takes its slice of the pool with it. 튜닝 옵션이 아니라 운영 방식의 분기다. embedded 모드에서는 랭크가 재시작하면 그 랭크 몫의 풀도 사라진다.

⑤ Hash block size is decoupled from the engine block size⑤ 해시 블록 크기와 엔진 블록 크기의 분리

The connector keeps the scheduler's block_size and a separate hash_block_size; with partial hits on, lookups align to the finer one. Otherwise a shared prefix shorter than one physical block is invisible, which decides whether short-prefix workloads benefit at all. 커넥터는 스케줄러의 block_size 와 hash_block_size 를 따로 두고, 부분 히트가 켜져 있으면 더 작은 쪽에 맞춰 조회한다. 그렇지 않으면 물리 블록 하나보다 짧은 공유 프리픽스는 보이지 않는다. 짧은 프리픽스 워크로드가 이득을 보느냐가 여기서 갈린다.

5 How it differs from LMCache and the rest LMCache 및 나머지와의 차이

What separates Mooncake from LMCache is not performance but where the caching logic lives. factory.py 레지스트리에는 커넥터가 열 개 넘게 있고, 전체 지도는 이전 노트(vLLM KV-cache 커넥터: 전송 방향 지도)에 있다. Editor's note — not a claim by vLLM or Mooncake편집자 주: vLLM·Mooncake 의 주장 아님
  1. The two answer different questions; they are not competitors.
  2. Mooncake optimises the hot path: the same prefix, another node, seconds later, with no copy and no compute.
  3. LMCache optimises coverage: hits even when KV must be compressed, or when the reusable text is not a prefix.
  4. Agentic multi-turn on a homogeneous fleet fits Mooncake exactly. RAG with shared-but-not-prefixed chunks does not, and no amount of RDMA fixes that.

  2. Mooncake 는 핫 패스를 최적화한다. 같은 프리픽스를 다른 노드에서 몇 초 뒤에, 복사도 연산도 없이 가져온다.
  3. LMCache 는 커버리지를 최적화한다. KV 를 압축해야 하거나 재사용할 텍스트가 프리픽스가 아닐 때도 히트를 낸다.
  4. 동질적인 fleet 위의 에이전트 멀티턴이면 Mooncake 가 딱 맞다. shared-but-not-prefixed 청크를 쓰는 RAG 라면 맞지 않고, RDMA 로도 해결되지 않는다.

Read these ratios carefully이 배수들을 조심해서 읽자
  • The baseline is 1.7% hit rate. "46× TTFT" means prefill nearly vanished for 33-turn transcripts, not that the connector is 46× faster at anything. 베이스라인 히트율이 1.7% 다. "TTFT 46배" 는 33턴 트랜스크립트에서 프리필이 거의 사라졌다는 뜻이지, 커넥터가 무언가를 46배 빠르게 한다는 뜻이 아니다.
  • Best-case workload. Codex traces with a median of 33 turns are the most favourable shape; short single-turn traffic would show ~nothing. 최선의 워크로드다. 중앙값 33턴 Codex 트레이스는 프리픽스 재사용에 가장 유리하다. 짧은 단일 턴 트래픽에서는 효과가 거의 없다.
  • Not isolated. The store runs stacked with the P2P connector under MultiConnector, so the full gain is not the store's alone. 단독 측정이 아니다. 스토어는 P2P 커넥터와 MultiConnector 아래 겹쳐 돌았으므로 이득 전부를 스토어 몫으로 볼 수 없다.
  • Hardware matters. GB200 with GPUDirect RDMA is the premise. TCP-only clusters weaken the zero-copy argument; the docs call TCP a "fallback". 하드웨어가 전제다. GPUDirect RDMA 가 되는 GB200 기준이다. TCP 뿐인 클러스터에서는 zero-copy 논지가 약해지고, 문서도 TCP 를 "fallback" 이라 부른다.
  • No published head-to-head with LMCache that we could find. Section 5 is a structural comparison, not a benchmark. LMCache 와의 공개 직접 비교는 찾지 못했다. 5절은 코드와 문서 기반의 구조 비교이지 벤치마크가 아니다.

8 Status, constraints, sources 상태·제약·출처

Where it stands현재 위치

  • Both connectors are in-tree and registered by default at ba1cdcf, with documentation pages under docs/features/ and a unit-test suite (test_mooncake_store_worker.py, …_scheduler.py, …_coordinator.py, HMA e2e). 두 커넥터 모두 ba1cdcf 기준 in-tree, 기본 등록 상태이고 docs/features/ 문서와 단위 테스트가 있다(test_mooncake_store_worker.py, …_scheduler.py, …_coordinator.py, HMA e2e).
  • The store connector declares SupportsHMA, i.e. it participates in vLLM's hybrid memory allocator, and handles Mamba-style layers whose entries are tensor lists. 스토어 커넥터는 SupportsHMA 를 선언해 vLLM 의 hybrid memory allocator 에 참여하고, 항목이 텐서 리스트인 Mamba 계열 레이어도 처리한다.
  • The docs describe "mode": "embedded" as the "PR-40900 baseline", so the standalone-store topology is the newer of the two. 문서는 "mode": "embedded" 를 "PR-40900 baseline" 이라 부른다. standalone-store 토폴로지가 나중에 추가된 쪽이다.
  • The transfer-thread scaffolding is credited to vllm-ascend in the source header, and the blog repeats the acknowledgement. 전송 스레드 뼈대의 출처는 소스 헤더와 블로그 모두 vllm-ascend 로 밝힌다.

Constraints to plan around미리 계산에 넣을 제약

  • Same model and same parallel layout to share cache (§4②); a mismatch is a silent hit-rate cliff. Prefix-only, no compression, no non-prefix blending. 같은 모델, 같은 병렬 레이아웃이어야 캐시를 공유한다(§4②). 어기면 에러 없이 히트율이 떨어진다. 프리픽스 전용이며 압축과 비-프리픽스 blending 은 없다.
  • RDMA is the design point; TCP is explicitly a fallback. RDMA 가 설계 전제이고 TCP 는 폴백이다.
  • Extra processes to run: mooncake_master, plus mooncake_client in standalone mode. In embedded mode the pool lives only as long as its ranks. 운영할 프로세스로 mooncake_master 가, standalone 모드면 mooncake_client 도 늘어난다. embedded 모드의 풀은 랭크가 살아 있는 동안만 유지된다.
Editor's note — our angle, not a claim by the sources편집자 주: 우리 관점, 출처의 주장 아님
  1. For our MI250 / ROCm work, the question is the transport premise, not the headline ratio. Mooncake's edge comes from GPUDirect RDMA: no staging buffer, no SMs consumed.
  2. Without that path it degrades toward "a remote cache reached over TCP", a much less compelling product.
  3. The test: do cross-instance hits still beat local recompute on a slower transport? We have not measured it; it would be our first measurement.
  1. 우리 MI250 / ROCm 작업에서 중요한 건 헤드라인 배수보다 전송 전제다. Mooncake 의 이점은 GPUDirect RDMA 에서 나온다. staging buffer 도, SM 소모도 없다.
  2. 그 경로가 없으면 설계는 "TCP 로 접근하는 원격 캐시" 에 가까워지고, 매력이 크게 줄어든다.
  3. 확인할 것은 전송이 느릴 때도 인스턴스 간 히트가 로컬 재계산보다 빠른가이다. 아직 측정하지 않았고, 측정한다면 이것부터 하겠다.
