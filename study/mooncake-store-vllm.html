Mooncake in vLLM — design, code flow, and how it differs from LMCache vLLM 속의 Mooncake — 설계, 코드 흐름, 그리고 LMCache 와 무엇이 다른가

Mooncake turns the idle CPU DRAM and SSD sitting in a GPU cluster into one cluster-wide KV cache pool, so a prefix computed on instance A can be reused by instance B. vLLM ships two separate Mooncake integrations — a point-to-point transfer connector for PD disaggregation, and a shared-store connector — and they are meant to be stacked, not chosen between. This note walks the real code path with commit-pinned permalinks, draws the flow, and contrasts the design against LMCache and the other offload connectors in the same registry. Mooncake 는 GPU 클러스터에서 놀고 있는 CPU DRAM 과 SSD 를 묶어 클러스터 전체가 공유하는 KV 캐시 풀로 만든다. 인스턴스 A 가 계산한 프리픽스를 인스턴스 B 가 그대로 재사용한다는 뜻이다. vLLM 에는 Mooncake 통합이 둘 있다 — PD 분리를 위한 P2P 전송 커넥터와 공유 스토어 커넥터인데, 둘 중 고르는 게 아니라 겹쳐 쓰도록 설계돼 있다. 이 노트는 커밋 고정 permalink 로 실제 코드 경로를 따라가고, 흐름을 그림으로 그리고, LMCache 및 같은 레지스트리의 다른 오프로드 커넥터들과 설계를 대조한다.

Glossary — the six words this note leans on용어 — 이 노트가 기대는 여섯 단어

KV cache

Per-token attention keys/values kept so already-seen tokens are not recomputed. It is the memory that makes generation cheap, and the thing everything here moves around. 이미 본 토큰을 다시 계산하지 않으려고 보관하는 토큰별 attention key/value. 생성을 싸게 만들어 주는 메모리이고, 이 글에서 옮겨 다니는 대상 전부가 이것이다.

prefix caching프리픽스 캐싱

Reusing the KV of a shared prompt prefix across requests. Standard vLLM does this within one instance's GPU memory — that boundary is the whole story below. 여러 요청이 공유하는 프롬프트 앞부분의 KV 를 재사용하는 것. 기본 vLLM 은 이걸 한 인스턴스의 GPU 메모리 안에서만 한다. 아래 내용은 전부 그 경계에 관한 이야기다.

KVConnector

vLLM's plug-in interface for "get KV from somewhere else / put KV somewhere else". Both Mooncake integrations and LMCache are implementations of it. "KV 를 딴 데서 가져오고 / 딴 데로 내보내는" vLLM 의 플러그인 인터페이스. Mooncake 통합 둘도, LMCache 도 전부 이것의 구현체다.

RDMA · GPUDirect

RDMA lets a NIC read/write remote memory without the remote CPU. GPUDirect RDMA extends that to GPU HBM, so KV can leave the GPU without a CPU staging copy. RDMA 는 상대 CPU 를 거치지 않고 NIC 가 원격 메모리를 직접 읽고 쓰게 한다. GPUDirect RDMA 는 그걸 GPU HBM 까지 확장해서, CPU 임시 복사 없이 KV 가 GPU 를 빠져나간다.

Transfer Engine

Mooncake's bottom layer: a transport that abstracts RDMA / TCP / NVMe-oF behind one API. Everything else in Mooncake is built on it. Mooncake 의 맨 아래 층. RDMA·TCP·NVMe-oF 를 하나의 API 뒤로 감춘 전송 계층이다. Mooncake 의 나머지는 전부 이 위에 올라간다.

PD disaggregation

Running prefill and decode on separate instances. Creates the need to ship KV from the prefiller to the decoder — the original reason a KV connector exists. 프리필과 디코드를 서로 다른 인스턴스에서 돌리는 것. 프리필러가 만든 KV 를 디코더로 보내야 하는 필요가 여기서 생기고, KV 커넥터가 존재하는 원래 이유다.

In one line한 줄 요약 Mooncake is not a cache library — it is a memory fabric. It gives vLLM a cluster-wide, RDMA-addressable object store whose keys are block hashes, and vLLM's own connector code decides what to put in it. That split is the opposite of LMCache, where a thick external library owns the caching logic and vLLM holds a thin adapter. The practical consequence: Mooncake is fastest at "the same prefix, on another node, right now", and deliberately does not do compression or non-prefix blending. Mooncake 는 캐시 라이브러리가 아니라 메모리 패브릭이다. 블록 해시를 키로 하는, RDMA 로 주소 지정되는 클러스터 전역 오브젝트 스토어를 vLLM 에 제공할 뿐이고, 거기에 무엇을 담을지는 vLLM 안의 커넥터 코드가 정한다. 이 분담은 LMCache 와 정반대다 — 그쪽은 두꺼운 외부 라이브러리가 캐싱 로직을 다 갖고 vLLM 은 얇은 어댑터만 든다. 실질적 결과: Mooncake 는 "같은 프리픽스를, 다른 노드에서, 지금 당장" 에 가장 빠르고, 압축이나 비-프리픽스 blending 은 의도적으로 하지 않는다.

1 The problem: a prefix cache that dies with the instance 문제 — 인스턴스와 함께 사라지는 프리픽스 캐시

vLLM already has prefix caching. Two requests sharing a prompt prefix reuse the same KV blocks, and the second one skips that much prefill. It works well and it is on by default. It also has two hard walls: the cache lives in this instance's GPU memory, and it is only as big as the GPU blocks left over after the model weights. vLLM 에는 이미 프리픽스 캐싱이 있다. 프롬프트 앞부분을 공유하는 두 요청은 같은 KV 블록을 재사용하고, 두 번째 요청은 그만큼 프리필을 건너뛴다. 잘 작동하고 기본으로 켜져 있다. 다만 벽이 둘 있다 — 캐시가 이 인스턴스의 GPU 메모리에 살고, 크기는 모델 가중치를 뺀 나머지 GPU 블록만큼뿐이다.

For chat that is fine. For agentic workloads it falls apart. An agent session is many turns over a growing transcript, so turn n shares almost everything with turn n−1 — the ideal case for prefix caching. But between turns the session may wait minutes, the blocks get evicted, and the load balancer may well send the next turn to a different replica that never saw the prefix at all. The vLLM blog puts a number on how bad that gets: 채팅이라면 괜찮다. 에이전트 워크로드에서는 무너진다. 에이전트 세션은 점점 길어지는 트랜스크립트 위에서 여러 턴을 도는 것이라, n 번째 턴은 n−1 번째와 거의 전부를 공유한다 — 프리픽스 캐싱에 가장 이상적인 조건이다. 그런데 턴 사이에 몇 분씩 쉬는 동안 블록은 축출되고, 로드밸런서는 그 프리픽스를 본 적 없는 다른 replica 로 다음 턴을 보내기 십상이다. vLLM 블로그가 그 정도를 숫자로 보여준다.

"cache hit rate ... from 1.7% to 92.2%"

vLLM blog, Codex agentic traces on 1P1D — the 1.7% is the baseline, i.e. local prefix caching alone.vLLM 블로그, 1P1D 에서 Codex 에이전트 트레이스. 1.7% 가 베이스라인 — 로컬 프리픽스 캐싱만 켠 상태다. · vllm.ai/blog/2026-05-06-mooncake-store

A 1.7% hit rate means the prefix cache is doing essentially nothing: nearly every turn re-prefills a transcript that some GPU in the cluster computed minutes ago. Meanwhile the same cluster has hundreds of gigabytes of CPU DRAM and terabytes of NVMe doing nothing at all. That gap — hot data thrown away next to cold capacity sitting idle — is the entire premise of Mooncake. 히트율 1.7% 는 프리픽스 캐시가 사실상 아무 일도 못 하고 있다는 뜻이다. 클러스터 안 어느 GPU 가 몇 분 전에 계산해 둔 트랜스크립트를, 거의 매 턴 다시 프리필한다. 그러는 동안 같은 클러스터의 수백 GB CPU DRAM 과 수 TB NVMe 는 아무것도 안 하고 있다. 뜨거운 데이터는 버려지는데 옆에서 차가운 용량이 놀고 있는 이 간극이 Mooncake 의 전제 전부다.

2 What Mooncake actually is — three layers, two vLLM connectors Mooncake 의 실체 — 3개 층, 2개의 vLLM 커넥터

"Mooncake" names a whole stack, which is why the docs can feel like they are describing three different products. They are three layers: "Mooncake" 는 스택 전체의 이름이다. 문서가 서로 다른 제품 셋을 설명하는 것처럼 느껴지는 이유가 이것인데, 사실은 층이 셋이다.

1 · Transfer Engine

The transport. One API over RDMA / TCP / NVMe-oF. Knows nothing about KV cache — it moves bytes between registered memory regions. 전송 계층. RDMA·TCP·NVMe-oF 를 하나의 API 로. KV 캐시가 뭔지 모른다 — 등록된 메모리 영역 사이로 바이트를 옮길 뿐이다.

2 · Mooncake Store

A distributed object store on top of it, pooling each node's DRAM (and optionally SSD) into one address space. Keys are strings; values are byte ranges. 그 위의 분산 오브젝트 스토어. 각 노드의 DRAM(선택적으로 SSD)을 하나의 주소 공간으로 묶는다. 키는 문자열, 값은 바이트 범위다.

3 · Master

A metadata service: which key lives where, replica state, client liveness. mooncake_master --port 50051. Not on the data path. 메타데이터 서비스. 어느 키가 어디 있는지, replica 상태, 클라이언트 생존 여부. mooncake_master --port 50051. 데이터 경로에는 없다.

Notice what is not in that list: nothing knows what a KV cache is. The store takes a key and some memory addresses. All the inference-specific logic — which blocks to save, how to name them, when to look them up — lives in vLLM. That is the single most important structural fact in this note, and section 5 is where it pays off. 이 목록에 없는 것을 보자 — 어느 층도 KV 캐시가 뭔지 모른다. 스토어는 키와 메모리 주소 몇 개를 받을 뿐이다. 추론에 특화된 로직 전부(어느 블록을 저장할지, 어떻게 이름 붙일지, 언제 조회할지)는 vLLM 안에 있다. 이 노트에서 구조적으로 가장 중요한 사실이고, 5절에서 값을 한다.

Two connectors, meant to be stacked두 개의 커넥터, 겹쳐 쓰라고 만든 것

vLLM's connector registry has both Mooncake integrations side by side — different modules, different classes: vLLM 의 커넥터 레지스트리에는 Mooncake 통합 둘이 나란히 등록돼 있다. 모듈도 클래스도 다르다.

The distinction the vLLM docs draw is exact and worth quoting, because most confusion about Mooncake starts here: vLLM 문서가 긋는 구분이 정확하다. Mooncake 에 대한 혼란은 대개 여기서 시작하니 그대로 인용한다.

"Unlike MooncakeConnector which does direct point-to-point KV transfer between prefiller and decoder, MooncakeStoreConnector enables KV cache offloading to an external distributed store"

docs/features/mooncake_store_connector_usage.md

P2P answers "this prefiller must hand this request to that decoder, now". The store answers "has anyone computed these blocks recently?". They solve different problems, which is why the documented disaggregated setup runs both under MultiConnector rather than picking one. P2P 는 "이 프리필러가 이 요청을 저 디코더에게 지금 넘겨야 한다" 에 답한다. 스토어는 "누구든 이 블록들을 최근에 계산한 적 있나?" 에 답한다. 서로 다른 문제라서, 문서에 나온 분리 구성은 하나를 고르는 대신 MultiConnector 아래에 둘 다 돌린다.

The path, step by step경로, 단계별로

  1. Startup — hand the KV tensors to the store.기동 — KV 텐서를 스토어에 넘긴다.
    The worker walks every KV cache tensor, takes untyped_storage().data_ptr(), and registers that region. It also sniffs the layout by stride to split FlashAttn's (2, num_blocks, …) K/V-first tensors into two segments, while FlashInfer/MLA's blocks-first layout stays one. 워커가 모든 KV 캐시 텐서를 돌면서 untyped_storage().data_ptr() 를 꺼내 그 영역을 등록한다. stride 를 보고 레이아웃도 판별한다 — FlashAttn 의 (2, num_blocks, …) K/V-우선 텐서는 두 세그먼트로 쪼개고, FlashInfer/MLA 의 블록-우선 레이아웃은 하나로 둔다.
    store.register_buffer(base_addr, region_len) store/worker.py#L1501-L1570
  2. Scheduler — ask how much of this prompt already exists.스케줄러 — 이 프롬프트가 얼마나 이미 있는지 묻는다.
    vLLM already computed request.block_hashes for its own prefix cache; the connector reuses them verbatim as store keys. A hit returns a token count, and the scheduler allocates blocks for it instead of prefilling. vLLM 은 자기 프리픽스 캐시를 위해 이미 request.block_hashes 를 계산해 뒀다. 커넥터는 그걸 그대로 스토어 키로 쓴다. 히트하면 토큰 수가 돌아오고, 스케줄러는 프리필 대신 그만큼 블록을 할당한다.
    num_external_hit_tokens = self.client.lookup(request.request_id, request.num_tokens, request.block_hashes, non_block=self.lookup_async) store/scheduler.py#L81-L134
  3. The key — what makes two instances agree.키 — 두 인스턴스가 합의하는 지점.
    A store key is the block hash prefixed with the model identity and the parallel layout. Read this line carefully; section 4 argues it is the most consequential design decision in the whole integration. 스토어 키는 블록 해시 앞에 모델 정체성 그리고 병렬 레이아웃을 붙인 것이다. 이 줄을 잘 봐 두자 — 4절에서 이 통합 전체에서 가장 파급이 큰 설계 결정이라고 주장할 것이다.
    f"{prefix}{model_name}@tp_rank:{tp}@pcp{pcp}@dcp{dcp}@pp_rank:{pp}@group:{group_id}"
# then:  key = f"{key_prefix}@{chunk_hash}"
    store/data.py#L116-L165
  4. Address math — the zero-copy handle.주소 계산 — zero-copy 의 정체.
    There is no serialization step. A "value" is simply base_addr + block_id × block_len per KV segment, vectorized with numpy over all chunks at once. This is what makes the RDMA land inside the live KV tensor rather than in a buffer that must then be copied. 직렬화 단계가 없다. "값" 은 KV 세그먼트마다 base_addr + block_id × block_len 일 뿐이고, 모든 청크에 대해 numpy 로 한 번에 벡터화해 계산한다. RDMA 가 별도 버퍼가 아니라 살아 있는 KV 텐서 안으로 바로 내려앉는 이유다.
    addrs = base[None, :] + bids[:, None] * blen[None, :]
sizes = blen[None, :] * block_counts[:, None]
    store/data.py#L210-L240
  5. Load — RDMA straight into the block slots.로드 — 블록 슬롯 안으로 직접 RDMA.
    The receiving thread issues one batched call per batch of keys. Any key whose return value is negative is recorded as a failed block, and those block ids are reported back so the scheduler can recompute them rather than serve garbage. 수신 스레드가 키 배치마다 배치 호출 하나를 날린다. 반환값이 음수인 키는 실패 블록으로 기록되고, 그 block id 들이 되보고돼서 스케줄러가 쓰레기를 내보내는 대신 다시 계산하게 한다.
    res = self.store.batch_get_into_multi_buffers(batch_keys, batch_addrs, batch_sizes) store/worker.py#L1140-L1142
  6. Save — the mirror image, after prefill.저장 — 프리필 후, 정확히 대칭.
    Newly computed blocks are written back with the same address list and the same key scheme, so the next instance to see this prefix finds it. 새로 계산된 블록은 같은 주소 목록과 같은 키 규칙으로 되쓰인다. 다음에 이 프리픽스를 만나는 인스턴스가 그걸 찾을 수 있게.
    res = self.store.batch_put_from_multi_buffers(...) store/worker.py#L684-L700
  7. Off the critical path.크리티컬 패스 밖으로.
    Both directions run on dedicated threading.Thread workers fed by queues, so an RDMA round trip never blocks the thread launching GPU kernels. 4 Five design decisions worth naming 짚어둘 설계 결정 다섯 가지

① Zero-copy means "no serialization step exists"① zero-copy 는 "직렬화 단계가 아예 없다" 는 뜻

Most caches serialize a tensor into a buffer, then send the buffer. Mooncake skips the concept: because the KV tensor storage was registered with the NIC up front, a block is addressable, and the store reads and writes it in place. The vLLM blog states the intent plainly — "This path requires no staging buffer and does not consume SMs." The second half matters as much as the first: no staging buffer also means no GPU kernel doing the copy, so offloading does not steal compute from the model. 대부분의 캐시는 텐서를 버퍼로 직렬화한 다음 그 버퍼를 보낸다. Mooncake 는 그 개념 자체를 건너뛴다. KV 텐서 저장소를 미리 NIC 에 등록해 뒀기 때문에 블록이 주소로 지정 가능하고, 스토어가 그 자리에서 읽고 쓴다. vLLM 블로그의 표현이 명확하다 — "This path requires no staging buffer and does not consume SMs." 뒷절이 앞절만큼 중요하다. staging buffer 가 없다는 건 복사를 수행할 GPU 커널도 없다는 뜻이고, 오프로딩이 모델에게서 연산을 빼앗지 않는다.

② The key embeds the parallel layout — and that sets the sharing boundary② 키에 병렬 레이아웃이 박힌다 — 그게 공유 경계를 정한다

The key is not just hash(tokens). It carries model_name, tp_rank, pcp, dcp, pp_rank and a KV-group id. That is correct — a TP-4 rank 2 shard is genuinely not interchangeable with a TP-8 shard — but it has a blunt operational consequence: 키는 그냥 hash(tokens) 가 아니다. model_name, tp_rank, pcp, dcp, pp_rank, KV 그룹 id 를 달고 있다. 옳은 설계다 — TP-4 의 rank 2 샤드는 TP-8 샤드와 실제로 호환되지 않는다. 다만 운영상 무딘 결과가 따라온다.

Practical consequence실무적 귀결 Two instances only share cache if they run the same model at the same parallel layout. Change TP for one deployment and its cache is a separate namespace — you do not get errors, you get a silent hit-rate collapse. Prefill TP4 and decode DP8 in the blog's own setup therefore do not share store entries with each other; the store pays off across turns and across replicas of the same role, not across roles. 두 인스턴스는 같은 모델을 같은 병렬 레이아웃으로 돌릴 때만 캐시를 공유한다. 한쪽 배포의 TP 를 바꾸면 그 캐시는 별도 네임스페이스가 된다 — 에러가 나는 게 아니라 히트율이 조용히 무너진다. 블로그의 구성(프리필 TP4, 디코드 DP8)에서도 둘은 서로 스토어 엔트리를 공유하지 않는다. 스토어가 값을 하는 건 턴 사이, 그리고 같은 역할의 replica 사이이지 역할을 가로질러서가 아니다.

③ Everything is asynchronous by construction③ 비동기가 기본값이 아니라 구조다

Lookup can be non-blocking (lookup_async), returning None to mean "ask me again next scheduler step" rather than stalling the loop. Loads and saves go onto queue-fed threads. The scheduler-side comment is explicit about the contract: "Returns (None, False) when an async lookup is still in flight, signaling the scheduler to retry this request on a later step." A remote cache that blocks the scheduler would be worse than no cache; this is the design detail that prevents it. 조회는 논블로킹일 수 있고(lookup_async), 루프를 멈추는 대신 None 을 돌려 "다음 스케줄러 스텝에 다시 물어봐" 를 뜻한다. 로드와 저장은 큐가 먹여주는 스레드로 간다. 스케줄러 쪽 주석이 계약을 명시한다 — "Returns (None, False) when an async lookup is still in flight, signaling the scheduler to retry this request on a later step." 스케줄러를 막는 원격 캐시는 캐시가 없느니만 못하다. 그걸 막는 설계 디테일이 이것이다.

④ Two topologies: pool inside the ranks, or pool outside them④ 두 가지 토폴로지 — 랭크 안에 풀, 랭크 밖에 풀

⑤ Hash block size is decoupled from the engine block size⑤ 해시 블록 크기와 엔진 블록 크기의 분리

The connector resolves two separate sizes — the scheduler's block_size and a hash_block_size — and when partial hits are enabled it aligns lookups on the finer one. Without that, a shared prefix shorter than one physical block is simply invisible. It is a small thing that decides whether short-prefix workloads see any benefit at all. 커넥터는 스케줄러의 block_size 와 hash_block_size 를 따로 해석하고, 부분 히트가 켜져 있으면 더 잘게 쪼갠 쪽에 맞춰 조회한다. 이게 없으면 물리 블록 하나보다 짧은 공유 프리픽스는 아예 안 보인다. 작아 보이지만, 짧은 프리픽스 워크로드가 이득을 보느냐 마느냐를 가르는 지점이다.

Editor's note — not a claim by vLLM or Mooncake편집자 주 — vLLM·Mooncake 의 주장 아님 Read the two as answers to different questions rather than competitors. Mooncake optimises the hot path: the same prefix, on another node, seconds later, moved with no copy and no compute. LMCache optimises coverage: get a hit even when the KV must be compressed to fit, or when the reusable text is not a prefix at all. If your traffic is agentic multi-turn on a homogeneous fleet, Mooncake's boundary conditions are exactly your workload. LMCache 는 커버리지를 최적화한다 — 압축해야 들어가는 상황에서도, 재사용할 텍스트가 프리픽스가 아닐 때도 히트를 만든다. 트래픽이 동질적인 fleet 위의 에이전트 멀티턴이라면 Mooncake 의 경계 조건이 곧 당신의 워크로드다. shared-but-not-prefixed 청크를 쓰는 RAG 라면 그렇지 않고, RDMA 를 아무리 깔아도 그건 해결되지 않는다.

Read these ratios carefully이 배수들을 조심해서 읽자
  • The baseline is 1.7% hit rate. Any cache looks spectacular against a baseline that is recomputing nearly everything. The honest reading of "46× TTFT" is "prefill was almost entirely eliminated for a workload built out of 33-turn transcripts", not "the connector is 46× faster at anything". 베이스라인이 히트율 1.7% 다. 거의 전부를 다시 계산하는 베이스라인 앞에서는 어떤 캐시든 극적으로 보인다. "TTFT 46배" 의 정직한 해석은 "33턴짜리 트랜스크립트로 구성된 워크로드에서 프리필이 거의 통째로 사라졌다" 이지, "커넥터가 뭔가를 46배 빠르게 한다" 가 아니다.
  • Best-case workload. Codex agentic traces with a median of 33 turns are the single most favourable shape for cross-instance prefix reuse. Short single-turn traffic has nothing to reuse and would show ~nothing. 최선의 워크로드다. 중앙값 33턴짜리 Codex 에이전트 트레이스는 인스턴스 간 프리픽스 재사용에 가장 유리한 형태다. 짧은 단일 턴 트래픽은 재사용할 게 없어 거의 아무 효과도 안 난다.
  • Not isolated. The documented disaggregated setup runs the store connector stacked with the P2P connector under MultiConnector. Attributing the full gain to the store alone would be wrong. 단독 측정이 아니다. 문서의 분리 구성은 스토어 커넥터를 P2P 커넥터와 MultiConnector 아래 겹쳐서 돌린다. 이득 전부를 스토어에 귀속하면 틀린다.
  • Hardware matters. GB200 with GPUDirect RDMA is the premise. On a TCP-only cluster the transport falls back and the whole zero-copy argument weakens; the docs themselves call TCP a "fallback". 하드웨어가 전제다. GPUDirect RDMA 가 되는 GB200 이 기준이다. TCP 뿐인 클러스터에서는 전송이 폴백되고 zero-copy 논지 자체가 약해진다. 문서도 TCP 를 "fallback" 이라고 부른다.
  • No published head-to-head with LMCache that we could find. The comparison in section 5 is structural, drawn from code and docs — not a benchmark. LMCache 와의 공개 직접 비교는 찾지 못했다. 5절의 비교는 코드와 문서에서 끌어낸 구조적 비교이지 벤치마크가 아니다.

Where it stands현재 위치

  • Both connectors are in-tree and registered by default at ba1cdcf, with documentation pages under docs/features/ and a unit-test suite (test_mooncake_store_worker.py, …_scheduler.py, …_coordinator.py, HMA e2e). 두 커넥터 모두 ba1cdcf 기준 in-tree 이고 기본 등록돼 있다. docs/features/ 아래 문서가 있고 단위 테스트도 있다(test_mooncake_store_worker.py, …_scheduler.py, …_coordinator.py, HMA e2e).
  • The store connector declares SupportsHMA, i.e. it participates in vLLM's hybrid memory allocator, and handles Mamba-style layers whose entries are tensor lists. 스토어 커넥터는 SupportsHMA 를 선언한다 — vLLM 의 hybrid memory allocator 에 참여하고, 항목이 텐서 리스트인 Mamba 계열 레이어도 처리한다.
  • The docs describe "mode": "embedded" as the "PR-40900 baseline", so the standalone-store topology is the newer of the two. 문서가 "mode": "embedded" 를 "PR-40900 baseline" 이라 부른다. 즉 standalone-store 토폴로지가 둘 중 나중에 붙은 쪽이다.
  • The transfer-thread scaffolding is credited to vllm-ascend in the source header, and the blog repeats the acknowledgement. 전송 스레드 뼈대는 소스 헤더에서 vllm-ascend 에 공을 돌리고 있고, 블로그도 같은 감사를 반복한다.

Constraints to plan around미리 계산에 넣을 제약

  • Same model and same parallel layout to share cache (§4②) — a silent hit-rate cliff, not an error. 캐시 공유 조건은 같은 모델 그리고 같은 병렬 레이아웃(§4②). 에러가 아니라 조용한 히트율 절벽이다.
  • Prefix-only. No compression, no non-prefix blending. 프리픽스 전용. 압축도, 비-프리픽스 blending 도 없다.
  • RDMA is the design point; TCP is explicitly a fallback. RDMA 가 설계 전제. TCP 는 명시적으로 폴백이다.
  • One more control-plane process to run and monitor (mooncake_master), plus mooncake_client in standalone mode. 운영·모니터링할 control-plane 프로세스가 하나 늘어난다(mooncake_master). standalone 모드면 mooncake_client 까지.
  • In embedded mode the pool is only as durable as the ranks contributing to it. embedded 모드에서 풀의 내구성은 기여 중인 랭크만큼이다.
Editor's note — our angle, not a claim by the sources편집자 주 — 우리 관점, 출처의 주장 아님 For our MI250 / ROCm work the interesting question is not the headline ratio but the transport premise. Mooncake's advantage compounds from GPUDirect RDMA: no staging buffer, no SMs consumed. On a fabric where that path is unavailable the design degrades toward "a remote cache reached over TCP", which is a different and much less compelling product — and the honest test is whether cross-instance hits still beat local recompute once the transport is slower. That is a measurement we have not made, and it is the one we would make first. 우리 MI250 / ROCm 작업 관점에서 흥미로운 건 헤드라인 배수가 아니라 전송 전제다. Mooncake 의 이점은 GPUDirect RDMA 에서 복리로 불어난다 — staging buffer 없음, SM 소모 없음. 그 경로가 없는 패브릭에서는 설계가 "TCP 로 접근하는 원격 캐시" 쪽으로 퇴화하는데, 그건 전혀 다르고 훨씬 덜 매력적인 물건이다. 정직한 시험은 전송이 느려졌을 때도 인스턴스 간 히트가 로컬 재계산을 이기는가이다. 우리는 아직 그 측정을 하지 않았고, 한다면 그것부터 할 것이다.
