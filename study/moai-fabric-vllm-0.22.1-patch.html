MoAI-Fabric — the vLLM 0.22.1 cross-vendor P/D patch, line by line MoAI-Fabric — vLLM 0.22.1 크로스벤더 P/D 패치, 라인 바이 라인

MoAI-Fabric runs prefill↔decode disaggregated (P/D) inference across mixed-vendor GPUs — an NVIDIA H100 (CUDA) prefill node feeding an AMD MI300X/MI250 (ROCm) decode node over InfiniBand RDMA. Three small patches on top of stock vLLM 0.22.1 make the KV cache actually transferable across the vendor gap. This note walks each patch line by line: what it changes, why, what broke before it, and the principle behind the fix. All snippets are from the repo at commit 4917a08. MoAI-Fabric는 prefill↔decode 분리(P/D) 추론을 서로 다른 벤더 GPU 사이에서 돌린다 — NVIDIA H100(CUDA) prefill 노드가 AMD MI300X/MI250(ROCm) decode 노드에 InfiniBand RDMA로 KV를 넘긴다. 스톡 vLLM 0.22.1 위 작은 패치 3개가 그 벤더 간극을 넘어 KV 캐시를 실제로 전송 가능하게 만든다. 이 노트는 각 패치를 라인 바이 라인으로 — 무엇을 바꾸고, 왜, 그 전엔 뭐가 깨졌고, 고치는 원리가 무엇인지 — 짚는다. 스니펫은 전부 커밋 4917a08 기준.

1The problem — one KV cache, two vendors문제 — 하나의 KV 캐시, 두 벤더

In P/D disaggregation, the prefill node computes the prompt's KV cache and RDMA-copies it into the decode node's cache, which then generates tokens. Within one vendor this "just works" — both sides agree on dtype, memory layout, and block size. Across vendors it does not. An H100/CUDA prefill and an MI300/ROCm decode disagree on four axes at once, and every one of them silently corrupts the KV bytes or aborts the transfer: P/D 분리에서 prefill 노드가 프롬프트 KV 캐시를 계산해 RDMA로 decode 노드 캐시에 복사하면, decode가 토큰을 생성한다. 같은 벤더 안에선 "그냥 된다" — dtype·메모리 레이아웃·블록 크기가 서로 같으니까. 벤더가 다르면 안 된다. H100/CUDA prefill과 MI300/ROCm decode는 네 축에서 동시에 어긋나고, 각각이 KV 바이트를 조용히 오염시키거나 전송을 중단시킨다:

fn layout: NHD block: 16 (or FLASHMLA 64) attn: FLASH_ATTN / FLASHMLA computes prompt KV → DECODE · MI300 / ROCm dtype: fp8 e4m3fnuz layout: HND block: 16 (or AITER_MLA 1) attn: ROCM_AITER_MLA → generates tokens NIXL/UCX RDMA · InfiniBand GDR-direct zero-copy — patch 03 handshake: exchange KVTransferCapabilities — patch 02 (PR3) transform chain (applied on the D side, on receive) ① fp8 fn→fnuz byte LUT — patch 02 (PR4) ② NHD→HND permute (swap axes) — patch 02 ③ block-size ratio align — patch 01 (+PR2*)

The four mismatches: fp8 encoding (fn vs fnuz), KV layout (NHD vs HND), block size (16↔16, or 64↔1 for MLA), and attention backend. The three patches make the transfer compose — a capability handshake to agree/fail (PR3), a byte LUT + layout permute applied on receive (PR4 + permute), block-size ratio (PR1), and GDR-direct so the RDMA path exists at all (patch 03).네 불일치: fp8 인코딩(fn vs fnuz), KV 레이아웃(NHD vs HND), 블록 크기(16↔16, MLA는 64↔1), attention 백엔드. 세 패치가 전송을 성립시킨다 — 합의/실패용 capability 핸드셰이크(PR3), 수신 시 적용하는 바이트 LUT + 레이아웃 permute(PR4+permute), 블록 크기 비율(PR1), 그리고 RDMA 경로 자체가 존재하게 하는 GDR-direct(패치 03).

All three patches are byte-identical for the CUDA and ROCm builds — the same diff is applied to both official images (vllm/vllm-openai:v0.22.1 and vllm/vllm-openai-rocm:v0.22.1). They were re-based from the production-validated vLLM 0.17.0 tree onto 0.22.1's heavily-refactored NIXL connector (single file → a v1/nixl/ package). 세 패치는 CUDA·ROCm 빌드에서 바이트 동일 — 같은 diff를 두 공식 이미지(vllm/vllm-openai:v0.22.1, vllm/vllm-openai-rocm:v0.22.1)에 적용한다. 프로덕션 검증된 vLLM 0.17.0 트리에서 0.22.1의 대폭 리팩터된 NIXL 커넥터(단일 파일 → v1/nixl/ 패키지)로 재베이스했다.

2Patch 01 — signed block_size_ratio패치 01 — 부호 있는 block_size_ratio

File: distributed/kv_transfer/kv_connector/utils.py · method: TransferTopology.block_size_ratio(). Purpose: P and D can use different KV block sizes; the connector needs the ratio to map remote blocks onto local ones. For MLA the P side (FLASHMLA, block 64) can be bigger than the D side (ROCM_AITER_MLA, block 1) — the "remote bigger" direction. 파일: distributed/kv_transfer/kv_connector/utils.py · 메서드: TransferTopology.block_size_ratio(). 목적: P와 D는 서로 다른 KV 블록 크기를 쓸 수 있고, 커넥터는 원격 블록을 로컬 블록에 매핑하려면 그 비율이 필요하다. MLA에선 P 쪽(FLASHMLA, block 64)이 D 쪽(ROCM_AITER_MLA, block 1)보다 클 수 있다 — "원격이 더 큰" 방향.

Before — a hard assert that crashed if remote was bigger이전 — 원격이 크면 죽어버리는 하드 assert

def block_size_ratio(self, remote_block_size: int) -> int:
    assert self.block_size % remote_block_size == 0, (   # dies if remote > local
        f"Local block size ... is not divisible by remote block size or vice versa."
    )
    return self.block_size // remote_block_size          # always positive

Stock 0.22.1 assumes local % remote == 0. If the remote block is larger (64 vs 1), the modulo is non-zero and the assert fires — the transfer can't even be described. 스톡 0.22.1은 local % remote == 0을 가정한다. 원격 블록이 더 크면(64 vs 1) 나머지가 0이 아니라 assert가 터진다 — 전송을 표현조차 못 한다.

After — signed ratio (sign = direction)이후 — 부호 있는 비율(부호 = 방향)

def block_size_ratio(self, remote_block_size: int) -> int:
    # positive when local >= remote (D aggregates P blocks)
    if self.block_size >= remote_block_size:
        assert self.block_size % remote_block_size == 0, (...)
        return self.block_size // remote_block_size
    # negative when remote block is larger (FLASHMLA 64 -> AITER_MLA 1)
    assert remote_block_size % self.block_size == 0, (...)
    return -(remote_block_size // self.block_size)

Principle: encode direction in the sign, mirroring the file's existing tp_ratio() convention (which already returns a negative value when the remote TP size is bigger). Positive = D block ≥ P block (D aggregates several P blocks). Negative = P block bigger (one P block scatters into several D blocks). Callers take abs() for magnitude and read the sign for which way to map. 원리: 방향을 부호로 인코딩 — 이 파일에 이미 있는 tp_ratio() 관례를 그대로 따른다(원격 TP 크기가 크면 음수 반환). 양수 = D 블록 ≥ P 블록(D가 여러 P 블록을 합침). 음수 = P 블록이 더 큼(하나의 P 블록이 여러 D 블록으로 흩어짐). 호출부는 크기엔 abs(), 매핑 방향엔 부호를 읽는다.

PR4 — the fp8 fn↔fnuz byte LUTPR4 — fp8 fn↔fnuz 바이트 LUT

The core cross-vendor bug. CUDA stores the fp8 KV cache as e4m3fn; ROCm as e4m3fnuz. Same 8 bits, but the two formats assign them to different real values (fnuz has no ±inf, a single NaN at 0x80, and an exponent bias of 8 vs fn's 7). RDMA-copy the raw bytes and reinterpret them in the other format and every KV value is subtly wrong. Since fp8 is a tiny finite alphabet (256 codes), the exact conversion is a precomputed 256-entry byte lookup table. 핵심 크로스벤더 버그. CUDA는 fp8 KV 캐시를 e4m3fn으로, ROCm은 e4m3fnuz로 저장한다. 같은 8비트지만 두 포맷은 이를 다른 실수값에 배정한다(fnuz는 ±inf 없음, NaN 하나 0x80, exponent bias 8 vs fn의 7). 원시 바이트를 RDMA로 복사해 다른 포맷으로 재해석하면 모든 KV 값이 미묘하게 틀린다. fp8은 유한한 256개 코드뿐이라, 정확한 변환은 미리 계산한 256-엔트리 바이트 룩업 테이블이다.

# metadata.py — two 256-entry tables (byte-for-byte identical to the 0.17.0 tree)
_FN_TO_FNUZ_LUT = [0, 2, 4, 6, 8, ... 127, 126, 126, ..., 128, 0, 130, ...]   # 256 uint8
_FNUZ_TO_FN_LUT = [0, 0, 1, 2, 2, 2, 3, 4, ...]                                # 256 uint8

def _make_peer_dtype_lut(self_dtype, peer_dtype):
    if self_dtype == peer_dtype: return None, "same dtype"
    if peer_dtype=="fp8_e4m3fn"   and self_dtype=="fp8_e4m3fnuz":  # CUDA->ROCm
        return torch.tensor(_FN_TO_FNUZ_LUT, dtype=torch.uint8), "fn -> fnuz"
    if peer_dtype=="fp8_e4m3fnuz" and self_dtype=="fp8_e4m3fn":    # ROCm->CUDA
        return torch.tensor(_FNUZ_TO_FN_LUT, dtype=torch.uint8), "fnuz -> fn"
    return None, "unsupported pair"

The table is installed at handshake (keyed by peer engine id) and applied on receive in get_finished(), right after the RDMA GET completes: 테이블은 핸드셰이크에서 설치(peer 엔진 id 키)되고, RDMA GET 완료 직후 get_finished()에서 수신 시 적용된다:

def _apply_peer_dtype_lut(self, peer_engine_id, grouped_block_ids):
    lut_host = self._peer_dtype_luts.get(peer_engine_id)
    if lut_host is None: return                       # no-op if no LUT for peer
    lut = self._peer_dtype_luts_device.get(peer_engine_id) or lut_host.to(self.device_type)
    for group_block_ids in grouped_block_ids:         # 0.22.1: grouped list[list[int]]
        indices = torch.tensor(group_block_ids, device=..., dtype=torch.long)
        for cache in ...device_kv_caches (split K and V):
            blocks = cache[indices]
            flat = blocks.reshape(-1).view(torch.uint8)   # reinterpret as raw bytes
            converted = lut[flat.long()]                  # out = LUT[in], vectorized
            cache[indices] = converted.view(orig_shape).view(orig_dtype)

# get_finished(): ... after transfer done
self._apply_peer_dtype_lut(meta.remote.engine_id, meta.local_physical_block_ids)  # PR4

Principle: view the received fp8 block as raw uint8, index the 256-entry table (a single vectorized gather on the GPU), and write it back in place. Exact and cheap — no float round-trip, one kernel over the just-received blocks. Before this: raw fp8 bytes crossed the vendor gap unmodified → the decode node read garbage KV → wrong tokens. 원리: 수신한 fp8 블록을 원시 uint8로 보고 256-엔트리 테이블을 인덱싱(GPU에서 벡터화 gather 한 번), 제자리에 다시 쓴다. 정확하고 싸다 — float 왕복 없음, 방금 받은 블록에 커널 한 번. 이전엔: 원시 fp8 바이트가 벤더 간극을 그대로 건너가 decode 노드가 쓰레기 KV를 읽음 → 틀린 토큰.

Bidirectional HND↔NHD permute양방향 HND↔NHD permute

CUDA FlashAttention lays a KV block out as NHD (tokens, heads, dim); ROCm AITER as HND (heads, tokens, dim). Reconciling them is a single axis swap (1↔2). Stock 0.22.1's experimental support only accepted one direction — remote HND → local NHD: CUDA FlashAttention은 KV 블록을 NHD(토큰·헤드·차원)로, ROCm AITER는 HND(헤드·토큰·차원)로 둔다. 맞추는 건 축 하나 스왑(1↔2). 스톡 0.22.1의 실험 지원은 한 방향만 받았다 — 원격 HND → 로컬 NHD:

Before: operators set the flag at launch (export UCX_IB_GPU_DIRECT_RDMA=yes). But 0.22.1 hardened the EngineCore: the multiprocessing transfer worker inherits only an allowlisted env, and UCX_* is scrubbed. So the flag reached the API server but not the process doing the RDMA. UCX then fell back to a host-staged rndv GET, and UCX protov2 cannot compose that path cross-vendor — it errors cannot find remote protocol … get(multi) into rocm/GPU0 from cuda → NIXL_ERR_CANCELED. The transfer simply never happened. 이전: 운영자가 실행 시 플래그를 걸었다(export UCX_IB_GPU_DIRECT_RDMA=yes). 하지만 0.22.1은 EngineCore를 강화 — 멀티프로세싱 전송 worker는 allowlist env만 상속하고 UCX_*는 지워진다. 그래서 플래그는 API 서버엔 닿아도 RDMA를 실제 하는 프로세스엔 안 닿았다. This forces GDR-direct zero-copy — the one rndv path UCX can compose across CUDA↔ROCm. PR2 — MLA cross-block-size scatter — is deliberately NOT ported. In 0.17.0 a negative block_size_ratio drove a "scatter |ratio| sub-descriptors per remote block" path (for FLASHMLA block=64 → AITER_MLA block=1). In 0.22.1 TransferTopology is unsigned by construction and the "remote bigger" case is routed through a different axis (tp_ratio<0 + the new _compute_desc_ids / _apply_prefix_caching / get_mapped_blocks machinery that didn't exist before). A textual transplant is impossible — PR2 needs a fresh redesign on 0.22.1's path (or a check that upstream select_common_block_size already covers it). PR2 — MLA 교차 블록 크기 scatter — 는 일부러 미이식. 0.17.0에선 음수 block_size_ratio가 "원격 블록당 |ratio|개 서브 디스크립터로 흩뿌리는" 경로를 몰았다(FLASHMLA 64 → AITER_MLA 1). 0.22.1의 TransferTopology는 구조상 부호 없음이고 "원격이 큰" 경우는 다른 축(tp_ratio<0 + 예전엔 없던 _compute_desc_ids/_apply_prefix_caching/get_mapped_blocks)으로 라우팅된다. 텍스트 이식 불가 — PR2는 0.22.1 경로 위 재설계 필요(또는 업스트림 select_common_block_size가 이미 커버하는지 확인).

editor's note — why this shape of fix편집자 주 — 왜 이런 형태의 수정인가 All three patches share one philosophy: keep stock vLLM untouched on the hot path, and reconcile vendor differences at the transfer boundary. The fp8 LUT and layout permute run only on received blocks; the capability handshake adds a trailing optional field (no wire break); the UCX knob is a setdefault. This is what lets the same diff apply to both official images and keeps same-vendor performance byte-identical to upstream — the mismatch handling is pure overlay, invisible unless a cross-vendor peer connects. 세 패치는 한 철학을 공유한다: hot path의 스톡 vLLM은 건드리지 않고, 벤더 차이는 전송 경계에서 화해. fp8 LUT와 레이아웃 permute는 수신 블록에만 돌고; capability 핸드셰이크는 말미 optional 필드만 추가(와이어 안 깨짐); UCX 노브는 setdefault. 덕분에 같은 diff가 두 공식 이미지에 적용되고 동일 벤더 성능은 업스트림과 바이트 동일 — 불일치 처리는 순수 오버레이라, 크로스벤더 peer가 붙기 전엔 보이지 않는다.
