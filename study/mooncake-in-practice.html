In one line한 줄 요약 Mooncake lets one GPU's finished work be reused by a different GPU minutes later, by turning the cluster's idle CPU memory into a shared pool that the network card can write into directly. The value is not "a faster cache" — it is deleting prefill work that would otherwise be repeated, and it only shows up when your traffic actually repeats long prefixes. 0 Zero background: what a KV cache is and why anyone offloads it 배경 0 — KV 캐시가 뭐고 왜 밖으로 빼는가

Skip this if you already know. If not, the rest of the note is unreadable without it, and it is only four ideas. 아는 분은 건너뛰어도 된다. 모른다면 이 네 가지 없이는 나머지가 안 읽힌다. 딱 네 개다.

① Generation has two phases with wildly different costs① 생성은 비용이 전혀 다른 두 단계로 나뉜다

When you send a prompt, the model first has to "read" all of it — that is prefill, and it processes every token at once, so it is compute-heavy and scales with prompt length. Then it writes the answer one token at a time — that is decode. A 30,000-token prompt can spend seconds in prefill before the first output character appears. That delay is TTFT (time to first token), and it is the number users feel. 프롬프트를 보내면 모델은 먼저 그걸 전부 "읽어야" 한다 — 이게 프리필이고, 모든 토큰을 한꺼번에 처리하므로 연산이 무겁고 프롬프트 길이에 비례한다. 그다음 답을 한 토큰씩 쓴다 — 이게 디코드다. 3만 토큰짜리 프롬프트는 첫 글자가 나오기까지 프리필에만 수 초를 쓸 수 있다. 그 지연이 TTFT(첫 토큰까지의 시간)이고, 사용자가 체감하는 숫자다.

② The KV cache is prefill's saved homework② KV 캐시는 프리필이 해 둔 숙제다

While reading the prompt, the model produces two vectors per token — a key and a value — that every later token needs to look at. Keeping them is what makes decode cheap. That pile of vectors is the KV cache. It is big: it grows with prompt length and model size, and it lives in GPU memory alongside the weights. 프롬프트를 읽는 동안 모델은 토큰마다 벡터 두 개 — key 와 value — 를 만든다. 이후의 모든 토큰이 이걸 참조해야 한다. 이걸 갖고 있어서 디코드가 싸진다. 그 벡터 더미가 KV 캐시다. 크다 — 프롬프트 길이와 모델 크기에 비례해 커지고, 가중치와 함께 GPU 메모리에 산다.

③ Prefix caching: if the start is the same, reuse it③ 프리픽스 캐싱 — 앞부분이 같으면 재사용

Two requests starting with the same text produce, for that shared start, bit-identical KV. So vLLM keeps finished blocks around and reuses them. This is on by default and it is why a repeated system prompt is nearly free the second time. The catch: those blocks sit in one instance's GPU memory, and GPU memory is small and gets evicted fast. 같은 텍스트로 시작하는 두 요청은 그 공유 구간에 대해 비트 단위로 동일한 KV 를 만든다. 그래서 vLLM 은 끝난 블록을 남겨 두고 재사용한다. 기본으로 켜져 있고, 반복되는 시스템 프롬프트가 두 번째부터 거의 공짜인 이유다. 문제는 그 블록들이 한 인스턴스의 GPU 메모리에 있다는 것 — GPU 메모리는 작고 금방 밀려난다.

④ Offloading: move the cache somewhere bigger and shared④ 오프로딩 — 캐시를 더 크고 공유되는 곳으로

A GPU node typically has hundreds of gigabytes of CPU DRAM and terabytes of NVMe doing nothing for inference. Offloading means parking KV blocks there instead of throwing them away. Do it across nodes and it becomes a shared pool: instance B can use what instance A computed. That is what Mooncake provides. GPU 노드에는 보통 수백 GB CPU DRAM 과 수 TB NVMe 가 추론에 아무 기여 없이 놀고 있다. 오프로딩은 KV 블록을 버리는 대신 거기 세워 두는 것이다. 노드를 가로질러 하면 공유 풀이 된다 — 인스턴스 A 가 계산한 걸 인스턴스 B 가 쓴다. Mooncake 가 제공하는 게 이것이다.

The one sentence to carry forward여기서 하나만 가져간다면 Everything below is about moving a pile of numbers out of GPU memory and back in, fast enough that it beats recomputing them. If loading is slower than recomputing, none of this is worth doing — and that ratio is the whole engineering problem. 아래 내용 전부는 숫자 더미를 GPU 메모리 밖으로 뺐다가 다시 넣는 이야기다. 다시 계산하는 것보다 빠를 만큼 빠르게. 불러오는 게 재계산보다 느리면 이걸 할 이유가 전혀 없다 — 그 비율이 공학 문제의 전부다.

0At startup: tell the network card where the KV cache lives기동 시 — 네트워크 카드에게 KV 캐시 위치를 알려준다
In plain words쉽게 말하면 Normally, sending data over a network means: copy it into a send buffer, hand that to the OS, the OS hands it to the card. RDMA skips all of that — but only for memory regions you have registered in advance. Registering is a one-time "this address range is mine, and the card is allowed to touch it directly" handshake. vLLM does this once at boot for the whole KV cache. After that, "block 42" is just an address the card can write into. 보통 네트워크로 데이터를 보내려면 전송 버퍼에 복사하고, 그걸 OS 에 넘기고, OS 가 카드에 넘긴다. RDMA 는 그 전부를 건너뛴다 — 단 미리 등록해 둔 메모리 영역에 한해서. 등록은 "이 주소 범위는 내 것이고, 카드가 직접 건드려도 된다" 는 일회성 악수다. vLLM 은 부팅 때 KV 캐시 전체에 대해 이걸 한 번 한다. 그 뒤로 "블록 42" 는 카드가 써넣을 수 있는 주소일 뿐이다. 
ret = self.store.register_buffer(base_addr, region_len)

There is a subtlety worth knowing because it differs per attention backend. The code inspects tensor strides to figure out the memory layout, and splits the registration accordingly: 어텐션 백엔드마다 달라서 알아둘 만한 디테일이 하나 있다. 코드가 텐서의 stride 를 보고 메모리 레이아웃을 판별해서 등록을 쪼갠다. 

outer_dims = [d for d in range(cache.ndim) if cache.stride(d) * el > page_size_bytes]
if not outer_dims:
    # Blocks-first layout (FlashInfer / MLA): one segment.
else:
    # K/V-first layout (FlashAttn / ROCm): split segments.

Why it matters: FlashAttn-style tensors are shaped (2, num_blocks, …) — K and V are two far-apart regions, so one block's data is not contiguous and must be registered as two segments. FlashInfer/MLA put blocks outermost, so one block is one contiguous run. Same connector, different number of registered segments. 왜 중요한가: FlashAttn 계열 텐서는 (2, num_blocks, …) 모양이라 K 와 V 가 멀리 떨어진 두 영역이고, 한 블록의 데이터가 연속적이지 않아 세그먼트 둘로 등록해야 한다. FlashInfer/MLA 는 블록이 가장 바깥이라 한 블록이 연속 구간 하나다. 같은 커넥터인데 등록 세그먼트 수가 달라진다.

1Request arrives: ask the master "how much of this already exists?"요청 도착 — master 에게 "이 중 얼마나 이미 있나?" 를 묻는다
In plain words쉽게 말하면 vLLM already chops the prompt into fixed-size blocks and hashes each one for its own prefix cache. The connector does not invent a new scheme — it takes those same hashes and asks the store "do you have these?". The answer is a token count: "the first N tokens of this prompt are already stored". The scheduler then allocates space for N tokens instead of prefilling them. vLLM 은 이미 프롬프트를 고정 크기 블록으로 자르고 각각을 해싱한다 — 자기 프리픽스 캐시를 위해서. 커넥터는 새 방식을 만들지 않고 그 해시를 그대로 가져다 스토어에 "이거 있어?" 라고 묻는다. 답은 토큰 개수다 — "이 프롬프트의 앞 N 토큰은 이미 저장돼 있다". 그러면 스케줄러는 그 N 토큰을 프리필하는 대신 자리만 잡는다. 
num_external_hit_tokens = self.client.lookup(
    request.request_id, request.num_tokens, request.block_hashes,
    non_block=self.lookup_async)

Two design details in this one call. Reusing vLLM's hashes means the store agrees with the engine's own notion of "same prefix" for free — no second hashing pass, no drift. And non_block makes the lookup optional-async: it can return None meaning "not ready, ask me next step" instead of stalling the scheduler loop. A remote cache that blocks scheduling would be worse than no cache at all. 이 호출 하나에 설계 포인트가 둘이다. vLLM 의 해시를 재사용하므로 "같은 프리픽스" 에 대한 엔진의 정의와 스토어가 공짜로 일치한다 — 두 번 해싱할 일도, 어긋날 일도 없다. 그리고 non_block 이 조회를 선택적 비동기로 만든다. 스케줄러 루프를 멈추는 대신 None("아직, 다음 스텝에 다시 물어봐")을 돌려줄 수 있다. 스케줄링을 막는 원격 캐시는 캐시가 없느니만 못하다.

2The key: what makes two instances agree they mean the same thing키 — 두 인스턴스가 "같은 것" 이라고 합의하는 방법
In plain words쉽게 말하면 A shared store needs names. If instance A stores something under name X, instance B must compute exactly the same X for the same content — otherwise it will never find it. The name here is the block hash, but with a prefix identifying whose KV this is. 공유 스토어에는 이름이 필요하다. 인스턴스 A 가 X 라는 이름으로 저장했으면, 같은 내용에 대해 인스턴스 B 도 정확히 같은 X 를 계산해야 한다. 아니면 영원히 못 찾는다. 여기서 이름은 블록 해시인데, 앞에 누구의 KV 인지를 밝히는 접두사가 붙는다. 
f"{prefix}{model_name}@tp_rank:{tp}@pcp{pcp}@dcp{dcp}@pp_rank:{pp}@group:{group_id}"
# 그리고:  key = f"{key_prefix}@{chunk_hash}"

Read the middle of that string. tp_rank, pp_rank and friends are the parallelism ranks — which shard of a split-up model this is. That is correct: with tensor parallelism the model is cut across GPUs, and rank 2 of a 4-way split holds genuinely different numbers than rank 2 of an 8-way split. Mixing them would be silent corruption. 저 문자열의 가운데를 보자. tp_rank, pp_rank 같은 것들은 병렬화 랭크다 — 쪼개진 모델의 어느 조각인지. 옳은 설계다. 텐서 병렬에서는 모델이 GPU 들에 걸쳐 잘리고, 4-way 의 rank 2 와 8-way 의 rank 2 는 진짜로 다른 숫자를 갖는다. 섞이면 조용한 데이터 손상이다.

The operational consequence운영상 귀결 Two deployments share cache only if the model name and the parallel layout both match. Change TP from 4 to 8 on one of them and its keys become a separate namespace — you get no error, just a hit rate that quietly goes to zero. If you plan to run mixed layouts against one master, isolate them explicitly (there is a cache_prefix and a tenant_id for exactly this). 두 배포가 캐시를 공유하려면 모델 이름과 병렬 레이아웃이 둘 다 같아야 한다. 한쪽 TP 를 4 에서 8 로 바꾸면 그쪽 키는 별도 네임스페이스가 된다 — 에러는 없고 히트율만 조용히 0 으로 간다. 서로 다른 레이아웃을 한 master 에 물릴 계획이면 명시적으로 격리해야 한다 (cache_prefix 와 tenant_id 가 정확히 그 용도다).
store/data.py#L116-L165
3The address: why there is no "serialize" step주소 — "직렬화" 단계가 없는 이유
In plain words쉽게 말하면 Most caching systems turn an object into a byte string, hand the string to the storage layer, and reverse it on the way back. Mooncake's connector does none of that. The KV cache is already a flat slab of memory divided into equal blocks, so "block 42" is arithmetic: start of the slab + 42 × block size. It hands the store that number. The store's job is to fill those exact bytes. 대부분의 캐시 시스템은 객체를 바이트 문자열로 바꿔 스토리지에 넘기고, 돌아올 때 되돌린다. Mooncake 커넥터는 그걸 전혀 안 한다. KV 캐시는 이미 균등한 블록으로 나뉜 평평한 메모리 덩어리라서, "블록 42" 는 산수다 — 덩어리 시작 주소 + 42 × 블록 크기. 그 숫자를 스토어에 넘긴다. 스토어가 할 일은 바로 그 바이트들을 채우는 것이다. 
addrs = base[None, :] + bids[:, None] * blen[None, :]
sizes = blen[None, :] * block_counts[:, None]

(The [None, :] business is just numpy broadcasting so all blocks of all segments are computed in one vectorized shot rather than a Python loop.) The consequence is the headline property: the RDMA write lands inside the live KV tensor. There is no intermediate buffer to allocate, fill, and free — and no GPU kernel doing a copy, which means offloading does not steal compute from the model. ([None, :] 는 numpy 브로드캐스팅으로, 파이썬 루프 대신 모든 세그먼트의 모든 블록을 한 번에 벡터 연산하려는 것뿐이다.) 결과가 곧 이 설계의 간판 특성이다 — RDMA 쓰기가 살아 있는 KV 텐서 안으로 바로 내려앉는다. 할당하고 채우고 해제할 중간 버퍼가 없고, 복사를 수행할 GPU 커널도 없다. 즉 오프로딩이 모델에게서 연산을 빼앗지 않는다.

5 The customer value proposition, honestly 고객 가치 제안, 정직하게

The trade, in one sentence거래의 정체, 한 문장

You are spending idle CPU memory, idle SSD, and network bandwidth to avoid spending GPU prefill. The pitch is only strong when the thing you avoid is expensive and happens often. 놀고 있는 CPU 메모리, 놀고 있는 SSD, 네트워크 대역폭을 써서 GPU 프리필을 안 쓰는 거래다. 피하려는 그것이 비싸고 자주 일어날 때만 이 제안이 강해진다.

That framing is worth insisting on, because it tells you which customer conversations are worth having. GPU time is the most expensive resource in the building; DRAM sitting unused in the same chassis is nearly free. Mooncake is an arbitrage between those two prices. If a customer's prompts do not repeat, there is no arbitrage — and no amount of RDMA creates one. 이 프레이밍을 고집할 가치가 있다. 어떤 고객 대화가 할 만한지 알려주기 때문이다. GPU 시간은 건물에서 가장 비싼 자원이고, 같은 섀시에서 안 쓰이는 DRAM 은 거의 공짜다. Mooncake 는 두 가격 사이의 차익거래다. 고객의 프롬프트가 반복되지 않으면 차익 자체가 없고, RDMA 를 아무리 깔아도 만들어지지 않는다.

Who this is for — and who it is not누구를 위한 것이고, 누구는 아닌가

Qualifying questions — ask these before promising anything자격 질문 — 무엇을 약속하기 전에 물어볼 것

Question질문Why it decides the outcome왜 이게 결과를 가르나
"How long is a typical prompt, and how much of it is identical to the previous request in the same session?""전형적인 프롬프트 길이가 얼마고, 그중 같은 세션의 직전 요청과 동일한 부분이 얼마입니까?" This single answer bounds the entire benefit. Long and highly repeated → strong. Short or unique → stop here.이 답 하나가 전체 이득의 상한을 정한다. 길고 반복 많음 → 강함. 짧거나 고유함 → 여기서 멈춘다.
"Does a follow-up request go back to the same replica?""후속 요청이 같은 replica 로 돌아갑니까?" If yes, the local cache may already cover it and the shared pool adds less. If no — round-robin — that gap is exactly what Mooncake fills.그렇다면 로컬 캐시가 이미 커버할 수 있어 공유 풀의 추가분이 적다. 아니라면(라운드로빈) 그 빈틈이 정확히 Mooncake 가 메우는 곳이다.
"How long between turns?""턴 사이 간격이 얼마입니까?" Seconds → GPU cache survives. Minutes → it is evicted, and only an external pool still has it. Hours → you need the SSD tier.초 단위 → GPU 캐시가 살아남는다. 분 단위 → 축출되고, 외부 풀만 갖고 있다. 시간 단위 → SSD 티어가 필요하다.
"Can the NICs register GPU memory on this cluster?""이 클러스터의 NIC 이 GPU 메모리를 등록할 수 있습니까?" Determines whether they get the design or its degraded form. Answer this with a test, not a spec sheet.이 설계를 얻는지 그 열화판을 얻는지를 가른다. 스펙 시트가 아니라 테스트로 답해야 한다.
"Will all instances run the same model at the same TP/PP layout?""모든 인스턴스가 같은 모델을 같은 TP/PP 레이아웃으로 돌립니까?" Mixed layouts do not share cache (§2 step 2). A fleet that autoscales between shapes will see a hit rate far below the demo.레이아웃이 섞이면 캐시를 공유하지 않는다(§2 단계 2). 형태를 바꿔가며 오토스케일하는 fleet 은 데모보다 훨씬 낮은 히트율을 본다.
"How much DRAM per node is genuinely spare, and is anyone else planning to use it?""노드당 DRAM 이 실제로 얼마나 남고, 다른 데서 쓸 계획은 없습니까?" The pool has to come from somewhere. This is also the moment to choose embedded vs standalone-store.풀이 어디선가 나와야 한다. embedded 냐 standalone-store 냐를 고르는 시점이기도 하다.

The one-slide version한 장짜리 버전

The problem문제

Agent sessions re-read the same growing transcript every turn. The GPU cache is too small and too local to hold it, so the cluster pays for the same prefill again and again.에이전트 세션은 매 턴 같은(그리고 점점 길어지는) 트랜스크립트를 다시 읽는다. GPU 캐시는 그걸 담기엔 너무 작고 너무 로컬이라, 클러스터가 같은 프리필을 반복해서 지불한다.

The mechanism메커니즘

Pool the idle DRAM (and SSD) into one store the NIC can write into directly, name blocks by content so any instance finds any other's work, and keep the coordinator off the data path.놀고 있는 DRAM(과 SSD)을 NIC 이 직접 써넣을 수 있는 스토어 하나로 묶고, 블록 이름을 내용으로 지어 어느 인스턴스든 남의 결과를 찾게 하고, 코디네이터는 데이터 경로에서 뺀다.

The proof to run돌려볼 증명

Their own traffic, working set forced above GPU KV capacity, both hit counters logged, TTFT percentiles before/after. Anything less is a demo, not evidence.고객 자기 트래픽으로, 워킹셋을 GPU KV 용량 위로 강제하고, 두 히트 카운터를 다 기록하고, 전후 TTFT 퍼센타일. 이보다 적으면 증거가 아니라 데모다.

Editor's note — our angle, not a claim by the sources편집자 주 — 우리 관점, 출처의 주장 아님 The most useful thing to say to a customer is usually the disqualifying one. "If your follow-up turns land on the same replica within seconds, you may not need this yet" buys more credibility than a 46× slide, and it is often true. The cases where Mooncake is genuinely irreplaceable are narrow and identifiable in advance: long shared prefixes, minutes between turns, many replicas, an RDMA fabric. When all four hold, nothing else in the ecosystem does the same job as directly. When one is missing, say so early. 고객에게 가장 쓸모 있는 말은 대개 자격을 깎는 말이다. "후속 턴이 몇 초 안에 같은 replica 로 돌아간다면 아직 필요 없을 수도 있습니다" 가 46배 슬라이드보다 신뢰를 더 얻고, 사실인 경우도 많다. Mooncake 가 진짜로 대체 불가한 경우는 좁고, 미리 식별 가능하다 — 긴 공유 프리픽스, 턴 사이 분 단위 간격, 여러 replica, RDMA 패브릭. 넷이 다 성립하면 생태계에 이 일을 이만큼 직접 하는 게 없다. 하나라도 빠지면 일찍 말하는 게 낫다.
