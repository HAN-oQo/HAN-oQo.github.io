Skip this if you already know. If not, the rest of the note is unreadable without it, and it is only four ideas. 아는 분은 건너뛰어도 된다. 모른다면 이 네 가지 없이는 나머지가 안 읽힌다. 딱 네 개다.

① Generation has two phases with wildly different costs① 생성은 비용이 전혀 다른 두 단계로 나뉜다

When you send a prompt, the model first has to "read" all of it — that is prefill, and it processes every token at once, so it is compute-heavy and scales with prompt length. Then it writes the answer one token at a time — that is decode. A 30,000-token prompt can spend seconds in prefill before the first output character appears. That delay is TTFT (time to first token), and it is the number users feel. 프롬프트를 보내면 모델은 먼저 그걸 전부 "읽어야" 한다 — 이게 프리필이고, 모든 토큰을 한꺼번에 처리하므로 연산이 무겁고 프롬프트 길이에 비례한다. 그다음 답을 한 토큰씩 쓴다 — 이게 디코드다. 3만 토큰짜리 프롬프트는 첫 글자가 나오기까지 프리필에만 수 초를 쓸 수 있다. 그 지연이 TTFT(첫 토큰까지의 시간)이고, 사용자가 체감하는 숫자다.

② The KV cache is prefill's saved homework② KV 캐시는 프리필이 해 둔 숙제다

While reading the prompt, the model produces two vectors per token — a key and a value — that every later token needs to look at. Keeping them is what makes decode cheap. That pile of vectors is the KV cache. It is big: it grows with prompt length and model size, and it lives in GPU memory alongside the weights. 프롬프트를 읽는 동안 모델은 토큰마다 벡터 두 개 — key 와 value — 를 만든다. 이후의 모든 토큰이 이걸 참조해야 한다. 이걸 갖고 있어서 디코드가 싸진다. 그 벡터 더미가 KV 캐시다. 크다 — 프롬프트 길이와 모델 크기에 비례해 커지고, 가중치와 함께 GPU 메모리에 산다.

③ Prefix caching: if the start is the same, reuse it③ 프리픽스 캐싱 — 앞부분이 같으면 재사용

Two requests starting with the same text produce, for that shared start, bit-identical KV. So vLLM keeps finished blocks around and reuses them. This is on by default and it is why a repeated system prompt is nearly free the second time. The catch: those blocks sit in one instance's GPU memory, and GPU memory is small and gets evicted fast. 같은 텍스트로 시작하는 두 요청은 그 공유 구간에 대해 비트 단위로 동일한 KV 를 만든다. 그래서 vLLM 은 끝난 블록을 남겨 두고 재사용한다. 기본으로 켜져 있고, 반복되는 시스템 프롬프트가 두 번째부터 거의 공짜인 이유다. 문제는 그 블록들이 한 인스턴스의 GPU 메모리에 있다는 것 — GPU 메모리는 작고 금방 밀려난다.

④ Offloading: move the cache somewhere bigger and shared④ 오프로딩 — 캐시를 더 크고 공유되는 곳으로

A GPU node typically has hundreds of gigabytes of CPU DRAM and terabytes of NVMe doing nothing for inference. Offloading means parking KV blocks there instead of throwing them away. Do it across nodes and it becomes a shared pool: instance B can use what instance A computed. That is what Mooncake provides. GPU 노드에는 보통 수백 GB CPU DRAM 과 수 TB NVMe 가 추론에 아무 기여 없이 놀고 있다. 오프로딩은 KV 블록을 버리는 대신 거기 세워 두는 것이다. 노드를 가로질러 하면 공유 풀이 된다 — 인스턴스 A 가 계산한 걸 인스턴스 B 가 쓴다. Mooncake 가 제공하는 게 이것이다.

⑤ RDMA: writing straight into someone else's memory⑤ RDMA — 남의 메모리에 직접 쓰기

This note leans on RDMA constantly, so it is worth building from zero. Start with what happens normally when one program sends data to another over a network: 이 글이 RDMA 에 계속 기대므로 밑바닥부터 쌓자. 먼저 프로그램 하나가 네트워크로 다른 프로그램에 데이터를 보낼 때 평소에 무슨 일이 벌어지는지부터.

DMA — Direct Memory Access — already exists inside one machine: a device like a disk or a NIC reads and writes RAM without the CPU shuffling the bytes. RDMA is that, extended across the network: my NIC writes directly into your memory. The remote CPU does nothing. It does not even know the data arrived until something tells it. DMA(Direct Memory Access)는 이미 한 기계 안에 있는 개념이다 — 디스크나 랜카드 같은 장치가 CPU 가 바이트를 나르지 않아도 RAM 을 직접 읽고 쓴다. RDMA 는 그걸 네트워크 건너까지 늘린 것이다 — 내 랜카드가 상대 메모리에 직접 쓴다. 상대 CPU 는 아무것도 안 한다. 알려주기 전까지는 데이터가 도착한 줄도 모른다.

The analogy비유 Normal TCP is a courier. You pack the parcel, hand it to the driver, the driver leaves it at their door, and they have to come out and bring it in. Both sides have to move. RDMA is having their house key and permission to put things on shelf 3. You just walk in and put it there. They can be asleep and the item is on the shelf. 평소 TCP 는 택배다. 물건을 포장해 기사에게 주고, 기사가 상대 집 앞에 두면, 상대가 나와서 받아 안으로 들여야 한다. 양쪽 다 움직여야 한다. RDMA 는 상대 집 열쇠와 "3번 선반에 놓아도 된다" 는 허락을 미리 받아둔 것이다. 그냥 들어가서 놓고 온다. 상대는 자고 있어도 물건이 선반에 올라가 있다.

The key and the shelf agreement have to be arranged in advance, and that setup is exactly the two things this note keeps mentioning: 열쇠와 선반 약속은 미리 해둬야 한다. 그 준비가 정확히 이 글에 계속 나오는 두 가지다.

Not every network card can do this아무 랜카드나 되는 게 아니다

The NIC has to support it, and there are two ways to get there. InfiniBand (IB) is a separate network built for this from the start — dedicated cards, cables and switches. RoCE does RDMA over ordinary Ethernet, reusing the switching gear but still needing a capable card. Both are programmed through the same interface, which is why one Mooncake transport handles both. 랜카드가 지원해야 하고, 가는 길이 둘이다. InfiniBand(IB) 는 애초에 이걸 하려고 만든 별도 네트워크로 카드·케이블·스위치가 전용이다. RoCE 는 평범한 이더넷 위에서 RDMA 를 한다 — 스위치 장비는 재활용하지만 카드는 여전히 지원 모델이어야 한다. 둘 다 같은 인터페이스로 프로그래밍하고, 그래서 Mooncake transport 하나가 양쪽을 다 처리한다.

GPUDirect RDMA — one step furtherGPUDirect RDMA — 한 발 더

So far the shelf has been in CPU RAM. GPUDirect RDMA is when the shelf is in GPU memory. Normally, sending something from a GPU over the network means GPU → CPU RAM → network. With GPUDirect it is GPU → network: CPU RAM is never touched. 여기까지는 선반이 CPU RAM 에 있었다. GPUDirect RDMA 는 그 선반이 GPU 메모리인 경우다. 보통 GPU 의 데이터를 네트워크로 보내려면 GPU → CPU RAM → 네트워크 를 거친다. GPUDirect 가 되면 GPU → 네트워크 로 끝난다. CPU RAM 을 아예 안 거친다.

This is the prerequisite the whole note hangs on이 글 전체가 매달린 전제 Every "zero-copy" claim below assumes GPUDirect works on your hardware. If it does not, the transport falls back to copying through the host and Mooncake loses the property that made it special. That is why "can the NIC register GPU memory here?" is the first thing to test, not the last. 아래의 모든 "zero-copy" 주장이 당신 하드웨어에서 GPUDirect 가 된다는 걸 전제한다. 안 되면 전송이 호스트를 경유해 복사하는 쪽으로 폴백하고, Mooncake 를 특별하게 만들던 성질이 사라진다. "여기서 NIC 이 GPU 메모리를 등록할 수 있나?" 가 마지막이 아니라 첫 시험인 이유다.

  • It does not cross the internet. This is a datacenter-internal technology.인터넷을 못 건넌다. 데이터센터 안에서 쓰는 기술이다.

Tying it back: a KV cache is large and moves constantly. Over TCP each block would be copied twice, and that CPU is CPU the model does not get. Over RDMA the card writes into the live KV tensor and neither CPU nor GPU spends anything on it. That is the whole reason this design exists — and also why only the bulk KV traffic goes this way, while the small lookups and metadata chatter stay on ordinary TCP (§2). 본론과 이어보면 — KV 캐시는 크고 끊임없이 오간다. TCP 로 하면 블록마다 두 번 복사하고, 그 CPU 는 모델이 못 쓰는 CPU 다. RDMA 로 하면 카드가 살아 있는 KV 텐서에 바로 쓰고 CPU 도 GPU 도 그 일에 아무것도 안 쓴다. 이 설계가 존재하는 이유 전부가 이것이고, 동시에 덩치 큰 KV 트래픽만 이 길로 가고 작은 조회·메타데이터 잡담은 평범한 TCP 에 남는 이유이기도 하다(§2).

⑥ Zero-copy: what "copy" actually costs⑥ zero-copy — "복사" 가 실제로 무슨 비용인가

This phrase appears everywhere in this note, so here is what it means concretely. Moving bytes from one place in memory to another is not free. It costs CPU cycles (or a GPU kernel) to do the moving, and it costs memory bandwidth twice — once reading, once writing. At a few megabytes nobody notices. At gigabytes per second it is a real tax, and worse, it is a tax paid out of the same budget the model needs. 이 말이 이 글에 계속 나오니 뭘 뜻하는지 구체적으로 짚자. 메모리의 한 곳에서 다른 곳으로 바이트를 옮기는 건 공짜가 아니다. 옮기는 데 CPU 사이클(또는 GPU 커널)이 들고, 메모리 대역폭을 두 번 먹는다 — 읽을 때 한 번, 쓸 때 한 번. 몇 MB 면 아무도 눈치 못 챈다. 초당 GB 단위면 실제 세금이고, 더 나쁜 건 그 세금이 모델이 써야 할 예산에서 나간다는 것이다.

Sending a KV block to a remote store could look like this: KV 블록 하나를 원격 스토어로 보내는 게 이렇게 될 수도 있고: 

GPU 의 KV 텐서  →(복사)→  임시 버퍼  →  네트워크  →  임시 버퍼  →(복사)→  상대 메모리

or like this: 이렇게 될 수도 있다: 

GPU 의 KV 텐서  →  네트워크  →  상대 메모리          ← zero-copy

The second one is zero-copy: no intermediate buffer is ever filled. Two things make it possible, and both have already appeared above — the memory was registered in advance (⑤), so the NIC can read it where it lies; and the connector never serializes anything, because a "value" here is just an address and a length rather than a packed byte string. 두 번째가 zero-copy 다. 중간 버퍼를 채우는 일이 한 번도 없다. 이걸 가능하게 하는 게 둘인데, 둘 다 위에서 이미 나왔다 — 메모리를 미리 등록해 뒀으므로(⑤) NIC 이 있는 자리에서 그대로 읽고, 커넥터가 아무것도 직렬화하지 않는다. 여기서 "값" 은 포장된 바이트열이 아니라 그냥 주소와 길이이기 때문이다.

Three things you save, not one아끼는 게 하나가 아니라 셋 Memory — no staging buffer to allocate, which matters when the buffer would have to be as large as the transfers in flight. Compute — no copy kernel, so the GPU's SMs stay on the model instead of shuffling bytes. Latency — two fewer passes over the data. The compute one is the one people forget, and on an inference server it is often the one that matters most. 메모리 — 할당할 스테이징 버퍼가 없다. 진행 중인 전송만큼 커야 하는 버퍼라 작지 않다. 연산 — 복사 커널이 없으니 GPU 의 SM 이 바이트를 나르는 대신 모델에 남는다. 지연 — 데이터를 두 번 덜 훑는다. 사람들이 잊는 건 두 번째이고, 추론 서버에서는 대개 그게 제일 중요하다.

And it is worth knowing how zero-copy breaks, because it is not a property you get by asking for it: 그리고 zero-copy 가 어떻게 깨지는지도 알아둘 값이 있다. 달라고 해서 얻는 성질이 아니기 때문이다.

  • The transport falls back to TCP — the engine then copies through the host internally, and the property is gone even though your config still says the same thing.전송이 TCP 로 폴백되면 — 엔진이 내부적으로 호스트를 경유해 복사하고, 설정 파일은 그대로인데 성질만 사라진다.
  • GPUDirect is unavailable — the NIC cannot address VRAM, so the data has to land in host memory first.GPUDirect 가 안 되면 — NIC 이 VRAM 을 주소로 못 잡으니 데이터가 호스트 메모리를 먼저 거쳐야 한다.
  • Something in the middle rearranges the KV — any layer that repacks blocks into its own format (to compress them, say) has to materialize that format somewhere, and that somewhere is a copy. This is a design trade, not a bug: you buy features with it. In plain words — IPC, and why it keeps coming up쉽게 말하면 — IPC, 그리고 왜 자꾸 나오나 IPC = inter-process communication. The starting fact is that the OS deliberately isolates programs: process A cannot see process B's memory, even on the same machine. IPC is the set of sanctioned ways to punch a hole in that wall on purpose.

GPU IPC is the same idea applied to GPU memory. A allocates some, calls cudaIpcGetMemHandle() and gets back a small opaque token; it passes that token to B by any ordinary means; B calls cudaIpcOpenMemHandle() and now holds a pointer into A's GPU memory. From then on B reads and writes it as if it were its own — no copy and no network, because nothing was transferred. The memory was mapped, not moved. The hard limit is that a handle is meaningless on another machine, which is exactly why the engine drops these transports for a cross-host target. IPC = inter-process communication, 프로세스 간 통신. 출발점은 OS 가 프로그램들을 일부러 격리한다는 사실이다 — 같은 기계 안이라도 프로세스 A 는 B 의 메모리를 볼 수 없다. IPC 는 그 벽에 의도적으로 구멍을 내는 공인된 방법들이다.

GPU IPC 는 같은 발상을 GPU 메모리에 적용한 것이다. A 가 메모리를 할당하고 cudaIpcGetMemHandle() 을 부르면 작은 불투명 토큰이 나온다. 그걸 아무 방법으로나 B 에게 건네고, B 가 cudaIpcOpenMemHandle() 을 부르면 이제 B 는 A 의 GPU 메모리를 가리키는 포인터를 쥔다. 그 뒤로 B 는 그걸 자기 것처럼 읽고 쓴다 — 복사도 네트워크도 없다. 아무것도 전송되지 않았으니까. 메모리가 옮겨진 게 아니라 매핑된 것이다. 결정적 한계는 핸들이 다른 기계에서는 의미가 없다는 것이고, 엔진이 cross-host 타깃에서 이 transport 들을 후보에서 빼는 이유가 정확히 그것이다.

What an "NVLink fabric domain" actually is"NVLink fabric 도메인" 이란 게 실제로 뭔가

That term is doing a lot of work above, so build it up. NVLink is a dedicated high-speed link between GPUs — NVIDIA's answer to PCIe being too slow for GPU-to-GPU traffic. Once you have more than a handful of GPUs you cannot wire them all directly to each other, so an NVSwitch chip sits in the middle and any GPU can reach any other through it. Same idea as a network switch, but NVLink-only. 이 용어가 위에서 많은 일을 하고 있으니 쌓아 올리자. NVLink 는 GPU 사이를 잇는 전용 고속 배선이다 — GPU 끼리의 트래픽에 PCIe 가 너무 느려서 NVIDIA 가 따로 만든 것이다. GPU 가 몇 장을 넘어가면 서로 전부 직접 잇는 게 불가능하므로, 가운데 NVSwitch 칩을 두고 아무 GPU 나 그걸 통해 서로 닿게 한다. 네트워크 스위치와 같은 발상인데 NVLink 전용이다.

For most of NVLink's life the boundary was the chassis. Inside one server: NVLink. Outside: the network. "Cross a node, cross to InfiniBand" was simply how the world was arranged. NVL72 moved that boundary from the server to the rack. NVLink 는 그 역사 대부분 동안 경계가 섀시였다. 서버 한 대 안이면 NVLink, 밖이면 네트워크. "노드를 넘으면 InfiniBand" 가 그냥 세상의 배치였다. NVL72 가 그 경계를 서버에서 랙으로 옮겼다.

This is a different kind of thing from RDMARDMA 와는 종류가 다른 물건이다 RDMA: my NIC writes into your memory. It is still a transfer — there is a card, a wire, and a completion to wait for. RDMA: 내 NIC 이 상대 메모리에 쓴다. 여전히 전송이다 — 카드가 있고, 선이 있고, 완료를 기다린다. NVLink fabric: 상대 메모리가 내 주소 공간 안에 나타난다. 다른 섀시에 있을 뿐인 공유 메모리다. 둘 다 "복사 없음" 을 주지만, 네트워크 스택이 관여하는 건 한쪽뿐이다.

The one asset with a hard prerequisite전제 조건이 붙는 자산 하나

The first row — registered-memory transport — is the biggest advantage and the one that is conditional. Writing directly into GPU memory from the network requires the NIC to be able to address that memory (GPUDirect RDMA). The connector still works — you just lost the argument that made it special. 첫 줄 — 등록 메모리 전송 — 이 가장 큰 이점이자 조건부인 항목이다. 네트워크에서 GPU 메모리로 직접 쓰려면 NIC 가 그 메모리를 주소로 지정할 수 있어야 한다(GPUDirect RDMA). 그게 안 되는 환경에서는 전송이 폴백되고 엔진 내부에서 호스트를 경유해 복사한다. vLLM 문서가 TCP 를 "fallback" 이라 부르는 이유가 정확히 이것이다. 커넥터는 여전히 동작한다 — 다만 이걸 특별하게 만들었던 논거를 잃는다.

Check this before anything else다른 무엇보다 먼저 확인할 것 "Can this fabric register GPU memory with the NIC?" is the first question of any Mooncake evaluation, not the last. The answer decides whether you are evaluating the design or a degraded version of it — and it is a property of the hardware and driver stack, not of the connector. 6 The customer value proposition, honestly 고객 가치 제안, 정직하게

The trade, in one sentence거래의 정체, 한 문장

You are spending idle CPU memory, idle SSD, and network bandwidth to avoid spending GPU prefill. The pitch is only strong when the thing you avoid is expensive and happens often. 놀고 있는 CPU 메모리, 놀고 있는 SSD, 네트워크 대역폭을 써서 GPU 프리필을 안 쓰는 거래다. 피하려는 그것이 비싸고 자주 일어날 때만 이 제안이 강해진다.

That framing is worth insisting on, because it tells you which customer conversations are worth having. GPU time is the most expensive resource in the building; DRAM sitting unused in the same chassis is nearly free. Mooncake is an arbitrage between those two prices. If a customer's prompts do not repeat, there is no arbitrage — and no amount of RDMA creates one. 이 프레이밍을 고집할 가치가 있다. 어떤 고객 대화가 할 만한지 알려주기 때문이다. GPU 시간은 건물에서 가장 비싼 자원이고, 같은 섀시에서 안 쓰이는 DRAM 은 거의 공짜다. Mooncake 는 두 가격 사이의 차익거래다. 고객의 프롬프트가 반복되지 않으면 차익 자체가 없고, RDMA 를 아무리 깔아도 만들어지지 않는다.

Turning on enable_offload makes vLLM allocate a DirectIO staging buffer, and reads are then split into sub-batches that fit the owner's staging budget. The splitting is graceful — but there is a hard cap: enable_offload 를 켜면 vLLM 이 DirectIO 스테이징 버퍼를 할당하고, 읽기가 소유자의 스테이징 예산에 맞는 서브 배치로 쪼개진다. 쪼개는 건 부드럽게 되는데, 단단한 상한이 하나 있다. 

# store/worker.py — _split_disk_offload_batches
key_bytes = _estimate_disk_offload_staging_bytes(size)
if key_bytes > raw_budget_bytes:
    return [], key      # ← 배치를 못 만들고 그 요청의 로드를 통째로 포기

If one key is bigger than the hard per-key budget, the function aborts and returns no batches at all — that request's load is skipped and those blocks are recomputed. Since a key covers one KV block, this is a function of block_size: raise the block size far enough and a single block can exceed the staging budget, at which point offloaded reads quietly stop paying off. It does not error; the hit rate just fails to convert into TTFT. 키 하나가 키당 하드 예산보다 크면 함수가 중단하고 배치를 아예 안 돌려준다 — 그 요청의 로드는 건너뛰고 해당 블록들은 재계산된다. 키 하나가 KV 블록 하나에 대응하므로 이건 block_size 의 함수다. 블록 크기를 충분히 키우면 블록 하나가 스테이징 예산을 넘길 수 있고, 그 순간부터 오프로드된 읽기가 조용히 값을 못 한다. 에러가 나는 게 아니라, 히트율이 TTFT 로 환산되지 않을 뿐이다.

Two practical notes that follow. The usable budget is the raw one scaled by VLLM_MOONCAKE_DISK_STAGING_USABLE_RATIO, so the effective cap is lower than the buffer you configured. And the SSD path only works if three settings agree — --enable_offload on mooncake_master, the same on the owning mooncake_client, and "enable_offload": true in the vLLM-side JSON (a config key, not an environment variable). Miss one and offload silently does not happen (§5). 여기서 실무 메모 둘. 쓸 수 있는 예산은 raw 예산에 VLLM_MOONCAKE_DISK_STAGING_USABLE_RATIO 를 곱한 값이라, 실효 상한은 설정한 버퍼보다 낮다. 그리고 SSD 경로는 설정 셋이 맞아야 동작한다 — mooncake_master 의 --enable_offload, 소유자 mooncake_client 의 같은 플래그, 그리고 vLLM 쪽 JSON 의 "enable_offload": true(환경변수가 아니라 설정 키다). 하나라도 빠지면 오프로드가 조용히 일어나지 않는다(§5).

What to take from the picture그림에서 가져갈 것 Three separate wires do three different jobs, and only one of them is big. The thin purple line decides whether there is a hit; the thick teal line determines how fast the hit pays off; the HTTP line is just traffic arriving. If the purple line breaks the cache goes dark on a healthy fabric. If the teal line breaks you fall back to recomputation and lose only speed. And if step 5 comes back "I have nothing" — because the layouts differ, or the tenant differs, or the working set never exceeded GPU memory — then steps 5 and 6 are pure overhead and Mooncake is costing you rather than paying. 서로 다른 선 셋이 서로 다른 일을 하고, 그중 굵은 건 하나뿐이다. 얇은 보라색은 히트가 있는지를 정하고, 굵은 청록색은 그 히트가 얼마나 빨리 값을 하는지를 정하고, HTTP 선은 그냥 트래픽이 도착하는 길이다. 보라색이 끊기면 패브릭이 멀쩡해도 캐시가 어두워진다. 청록색이 끊기면 재계산으로 떨어지고 속도만 잃는다. 그리고 5단계가 "가진 게 없다" 고 답하면 — 레이아웃이 다르거나, 테넌트가 다르거나, 워킹셋이 애초에 GPU 메모리를 안 넘었거나 — 5·6 단계는 순수 오버헤드이고 Mooncake 는 값을 하는 게 아니라 비용만 쓰고 있는 것이다.

Quota enforcement is an admin HTTP API on the master, entirely outside vLLM.커넥터가 tenant_id 를 setup() 에 넘기긴 한다 — 기본값과 다를 때만. 그런데 문서상 마스터가 enable_multi_tenants=false(기본) 로 돌면 "request tenant IDs are ignored" 다. 즉 vLLM 에만 tenant_id 를 넣고 마스터를 안 건드리면 얻는 게 정확히 없다. 쿼터 강제는 마스터의 admin HTTP API 이고 vLLM 밖의 이야기다.

Three things that fall out of this mapping이 대조에서 떨어져 나오는 것 세 가지

1. The lease is the reason a "hit" can evaporate before it is read1. 히트가 읽히기 전에 증발할 수 있는 이유가 lease 다

Two different processes are involved at two different times. The scheduler asks batch_is_exist() and, per the docs, that grants a lease with a default 10-second TTL. The worker later calls the actual read, which grants a fresh lease of its own. Between those two moments the request sits in a queue. 서로 다른 두 프로세스가 서로 다른 시점에 관여한다. 스케줄러가 batch_is_exist() 로 물으면 문서상 그 순간 기본 10초짜리 lease 가 부여된다. 워커는 나중에 실제 읽기를 하고 거기서 또 새 lease 를 받는다. 그 두 시점 사이에 요청은 큐에 앉아 있다.

Under load that gap can exceed the TTL. If the pool is also above its eviction watermark, the object can be gone by the time the worker asks — the scheduler counted a hit that never materialised. The docs add a second, narrower case: "if the lease expires before a Get operation finishes reading the data, the operation will be considered failed" — a very large or very slow read can time out mid-transfer. 부하가 걸리면 그 간격이 TTL 을 넘길 수 있다. 풀이 축출 수위 위에 있기까지 하면, 워커가 물을 때쯤 객체가 사라져 있을 수 있다 — 스케줄러는 실현되지 않은 히트를 하나 센 것이다. 문서는 더 좁은 경우를 하나 더 든다. "if the lease expires before a Get operation finishes reading the data, the operation will be considered failed" — 아주 크거나 아주 느린 읽기는 전송 도중에 만료될 수 있다.

The signature증상의 모양 Hit rate that is fine on a quiet cluster and sags only under load, with no errors anywhere. This is exactly why §5 insists on reading the scheduler-side and worker-side counters separately — a single blended number cannot show you this. The lever is the master_service lease-TTL parameter, and secondarily the eviction watermark; the cheaper fix is usually reducing queue time. 한산할 땐 멀쩡하다가 부하가 걸릴 때만 히트율이 처지고, 어디에도 에러가 없다. §5 가 스케줄러 쪽 카운터와 워커 쪽 카운터를 따로 보라고 고집한 이유가 정확히 이것이다 — 하나로 섞은 숫자로는 이게 안 보인다. 레버는 master_service 의 lease TTL 파라미터, 그다음이 축출 수위다. 더 싼 해법은 대개 큐 대기시간을 줄이는 쪽이다.

2. Soft Pin is unused — and the docs' own example is your workload2. Soft Pin 을 안 쓴다 — 그런데 문서가 든 예시가 바로 당신의 워크로드다

In plain words — a pin is one of three ways to say "don't delete this"쉽게 말하면 — pin 은 "이건 지우지 마" 라고 말하는 세 방법 중 하나다 When the pool crosses 90% full, the master's approximate-LRU eviction frees about 5% of it. A pin is how an object asks to be spared. There are three levels of asking, and they differ in how long they last and how hard they push — which is the whole point. 풀이 90% 를 넘으면 마스터의 근사 LRU 축출이 5% 정도를 비운다. pin 은 객체가 거기서 빼 달라고 요청하는 방법이다. 요청의 단계가 셋이고, 얼마나 오래 가느냐와 얼마나 세게 미느냐가 다르다 — 그게 전부다.

Hard pin is almost always the wrong tool for a KV cacheKV 캐시에 hard pin 은 대개 틀린 도구다 Look at the examples the docs choose for it: "model weights, critical metadata" — things that are supposed to live for the process's whole lifetime. Hard-pin a KV chunk and that space never comes back; do it at scale and the pool fills permanently until PutStart starts failing for everything else. Soft pin is the cache-shaped one: it expires on its own if the object stops being useful, and re-arms itself if it becomes useful again. That self-healing behaviour is exactly what you want for a prefix whose popularity changes with traffic. 문서가 hard pin 예시로 고른 것들을 보라 — "model weights, critical metadata". 프로세스가 사는 내내 있어야 할 것들이다. KV 청크에 hard pin 을 걸면 그 공간은 영영 안 돌아오고, 규모 있게 걸면 풀이 영구히 차서 결국 다른 모든 것의 PutStart 가 실패하기 시작한다. 캐시 모양에 맞는 건 soft pin 이다 — 객체가 쓸모없어지면 알아서 풀리고, 다시 쓸모 있어지면 알아서 다시 걸린다. 트래픽에 따라 인기가 변하는 프리픽스에는 그 자가 치유가 정확히 원하는 동작이다.

The Store docs introduce soft pin like this: "For important and frequently used objects, such as system prompts, Mooncake Store provides a soft pin mechanism." Soft-pinned objects are skipped by eviction until nothing else is eligible, and the pin lapses on its own after 30 minutes of no access. Store 문서는 soft pin 을 이렇게 소개한다. "For important and frequently used objects, such as system prompts, Mooncake Store provides a soft pin mechanism." soft pin 된 객체는 다른 후보가 없을 때까지 축출에서 제외되고, 30분간 접근이 없으면 핀이 알아서 풀린다.

That is a precise description of a long shared system prompt — the single highest-value thing in most offload deployments, because every request pays for it. The connector never sets the flag, so those blocks sit in the same approximate-LRU queue as a one-off 200-token chat. On a pool that cycles hard, the block worth the most is evicted on exactly the same terms as the block worth the least. 이건 길게 공유되는 시스템 프롬프트에 대한 정확한 묘사다 — 모든 요청이 그 값을 치르니 대개 오프로드 배포에서 가장 값이 큰 대상이다. 커넥터는 그 플래그를 세팅하지 않으므로, 그 블록들은 일회성 200토큰 채팅과 똑같은 근사 LRU 큐에 놓인다. 회전이 빠른 풀에서는 가장 값비싼 블록이 가장 값싼 블록과 정확히 같은 조건으로 축출된다.
