0 Zero background: what a KV cache is and why anyone offloads it 배경 0: KV 캐시가 뭐고 왜 밖으로 빼는가

Skip this if you already know it. Otherwise the rest of the note depends on these ideas. 아는 분은 건너뛰어도 된다. 모른다면 나머지를 읽는 데 이 개념들이 필요하다.

① Generation has two phases with wildly different costs① 생성은 비용이 전혀 다른 두 단계로 나뉜다

The model first reads the whole prompt at once. That is prefill: compute-heavy and proportional to prompt length. Then it writes the answer one token at a time, which is decode. A 30,000-token prompt can spend seconds in prefill before the first character appears. That delay is TTFT (time to first token), the number users feel. 모델은 먼저 프롬프트 전체를 한꺼번에 읽는다. 이게 프리필이고, 연산이 무겁고 프롬프트 길이에 비례한다. 그다음 답을 한 토큰씩 쓰는 단계가 디코드다. 30,000 토큰 프롬프트는 첫 글자가 나오기까지 프리필에만 수 초를 쓸 수 있다. 이 지연이 TTFT(첫 토큰까지의 시간)이고, 사용자가 체감하는 숫자다.

② The KV cache is prefill's saved homework② KV 캐시는 프리필이 해 둔 숙제다

While reading the prompt the model produces a key and a value vector per token, which every later token looks at. Keeping them is what makes decode cheap. That pile is the KV cache. It grows with prompt length and model size and lives in GPU memory next to the weights. 프롬프트를 읽는 동안 모델은 토큰마다 key 와 value 벡터를 만들고, 이후 토큰은 모두 이걸 참조한다. 이걸 보관하기 때문에 디코드가 싸다. 이 벡터 더미가 KV 캐시다. 프롬프트 길이와 모델 크기에 비례해 커지고, 가중치와 함께 GPU 메모리에 있다.

③ Prefix caching: if the start is the same, reuse it③ 프리픽스 캐싱: 앞부분이 같으면 재사용

Two requests with the same start produce bit-identical KV for that start, so vLLM keeps finished blocks and reuses them. It is on by default, which is why a repeated system prompt is nearly free the second time. The catch: those blocks sit in one instance's GPU memory, which is small and evicted fast. 같은 텍스트로 시작하는 두 요청은 그 구간에서 비트 단위로 동일한 KV 를 만든다. 그래서 vLLM 은 끝난 블록을 남겨 두고 재사용한다. 기본으로 켜져 있고, 반복되는 시스템 프롬프트가 두 번째부터 거의 공짜인 이유다. 다만 그 블록은 한 인스턴스의 GPU 메모리에 있고, GPU 메모리는 작아서 금방 밀려난다.

④ Offloading: move the cache somewhere bigger and shared④ 오프로딩: 캐시를 더 크고 공유되는 곳으로

A GPU node typically has hundreds of gigabytes of CPU DRAM and terabytes of NVMe idle during inference. Offloading parks KV blocks there instead of discarding them. Across nodes it becomes a shared pool where instance B uses what instance A computed. That is what Mooncake provides. GPU 노드에는 보통 수백 GB 의 CPU DRAM 과 수 TB 의 NVMe 가 추론 중에 놀고 있다. 오프로딩은 KV 블록을 버리지 않고 거기 보관하는 것이다. 여러 노드에 걸치면 인스턴스 A 가 계산한 걸 B 가 쓰는 공유 풀이 된다. Mooncake 가 제공하는 것이 이것이다.

⑤ RDMA: writing straight into someone else's memory⑤ RDMA: 남의 메모리에 직접 쓰기

This note relies on RDMA throughout, so start with what happens normally when one program sends data to another over a network: 이 글은 RDMA 를 계속 다루므로, 먼저 프로그램이 네트워크로 데이터를 보낼 때 평소에 무슨 일이 일어나는지 보자.

DMA (Direct Memory Access) already exists inside one machine: a disk or NIC reads and writes RAM without the CPU moving the bytes. RDMA extends that across the network: my NIC writes directly into your memory. The remote CPU does nothing and does not know the data arrived until told. DMA(Direct Memory Access)는 한 기계 안의 개념이다. 디스크나 랜카드가 CPU 의 도움 없이 RAM 을 직접 읽고 쓴다. RDMA 는 이걸 네트워크 너머로 늘려 내 랜카드가 상대 메모리에 직접 쓴다. 상대 CPU 는 아무 일도 하지 않고, 알려 주기 전에는 데이터가 왔는지도 모른다.

The analogy비유 Normal TCP is a courier. The driver leaves the parcel at the door and they have to come out and bring it in. RDMA is having their house key and permission to use shelf 3. You walk in and put it there, even while they sleep. 평소 TCP 는 택배다. 기사가 문 앞에 두면 상대가 나와서 들여가야 한다. RDMA 는 상대 집 열쇠와 "3번 선반을 써도 된다" 는 허락을 미리 받아 둔 것이다. 상대가 자고 있어도 들어가서 선반에 놓고 나온다.

The key and the shelf have to be arranged in advance. That setup is two things this note keeps mentioning: 열쇠와 선반은 미리 약속해 둬야 한다. 이 준비가 글에 계속 나오는 두 가지다.

Not every network card can do this아무 랜카드나 되는 게 아니다

The NIC must support it, in one of two ways. InfiniBand (IB) is a separate network built for this, with dedicated cards, cables and switches. RoCE runs RDMA over ordinary Ethernet, reusing switches but still needing a capable card. Both use the same programming interface, so one Mooncake transport handles both. 랜카드가 지원해야 하고, 방법은 두 가지다. InfiniBand(IB) 는 이 용도로 만든 별도 네트워크로, 카드·케이블·스위치가 전용이다. RoCE 는 일반 이더넷 위에서 RDMA 를 돌린다. 스위치는 재활용하지만 카드는 지원 모델이어야 한다. 둘은 같은 인터페이스로 프로그래밍하므로 Mooncake transport 하나가 둘 다 처리한다.

GPUDirect RDMA — one step furtherGPUDirect RDMA: 한 발 더

So far the shelf was in CPU RAM. With GPUDirect RDMA the shelf is in GPU memory. Instead of GPU → CPU RAM → network, data goes GPU → network without touching CPU RAM. 여기까지 선반은 CPU RAM 에 있었다. GPUDirect RDMA 는 선반이 GPU 메모리에 있는 경우다. 보통은 GPU → CPU RAM → 네트워크 를 거치지만, GPUDirect 에서는 GPU → 네트워크 로 끝나고 CPU RAM 을 거치지 않는다.

This is the prerequisite the whole note hangs on이 글 전체가 매달린 전제 Every "zero-copy" claim below assumes GPUDirect works on your hardware. Otherwise the transport falls back to copying through the host and Mooncake loses what made it special. So "can the NIC register GPU memory here?" is the first thing to test. 아래의 "zero-copy" 주장은 모두 당신 하드웨어에서 GPUDirect 가 된다고 전제한다. 안 되면 전송이 호스트를 거쳐 복사하는 방식으로 폴백하고, Mooncake 의 장점이 사라진다. 그래서 "여기서 NIC 이 GPU 메모리를 등록할 수 있나?" 를 가장 먼저 시험해야 한다.

Then why doesn't everything use RDMA?그럼 왜 다들 안 쓰나

  • It needs special hardware: cards, often switches. That costs money.전용 하드웨어가 필요하다. 카드, 대개는 스위치까지 사야 한다.
  • It does not cross the internet. This is a datacenter-internal technology.인터넷을 못 건넌다. 데이터센터 안에서 쓰는 기술이다.
  • The security model is "someone else can write into my memory". Fine on a trusted fabric, not something you expose.보안 모델이 "남이 내 메모리에 직접 쓸 수 있음" 이다. 신뢰하는 패브릭에서는 괜찮지만 외부에 노출할 것은 아니다.
  • It is awkward to program, which is exactly what Mooncake's transfer engine does for you.프로그래밍이 까다롭다. Mooncake 의 전송 엔진이 대신 해 주는 일이 바로 이것이다.

⑥ Zero-copy: what "copy" actually costs⑥ zero-copy: "복사" 가 실제로 무슨 비용인가

Moving bytes in memory is not free. It costs CPU cycles (or a GPU kernel) and memory bandwidth twice, once to read and once to write. At a few megabytes nobody notices. At gigabytes per second it is a real tax, paid from the budget the model needs. 메모리에서 바이트를 옮기는 일은 공짜가 아니다. CPU 사이클(또는 GPU 커널)이 들고, 읽을 때와 쓸 때 메모리 대역폭을 두 번 쓴다. 몇 MB 면 티가 안 나지만 초당 GB 단위면 실제 비용이 되고, 그 비용은 모델이 쓸 예산에서 나간다.

Sending a KV block to a remote store could look like this: KV 블록을 원격 스토어로 보내는 방식은 이럴 수도 있고 

GPU 의 KV 텐서  →(복사)→  임시 버퍼  →  네트워크  →  임시 버퍼  →(복사)→  상대 메모리

or like this: 이렇게 될 수도 있다: 

GPU 의 KV 텐서  →  네트워크  →  상대 메모리          ← zero-copy

The second is zero-copy: no intermediate buffer is ever filled. Two things make it possible, both covered above. The memory was registered in advance (⑤), so the NIC reads it in place. And the connector never serializes anything, because a "value" here is an address and a length, not a packed byte string. 두 번째가 zero-copy 다. 중간 버퍼를 한 번도 채우지 않는다. 조건은 두 가지로, 둘 다 앞에서 나왔다. 메모리를 미리 등록했으므로(⑤) NIC 이 제자리에서 읽는다. 그리고 커넥터는 아무것도 직렬화하지 않는다. 여기서 "값" 은 포장된 바이트열이 아니라 주소와 길이이기 때문이다.

Three things you save, not one아끼는 게 하나가 아니라 셋 Memory: no staging buffer as large as the transfers in flight. Compute: no copy kernel, so the GPU's SMs stay on the model. Latency: two fewer passes over the data. People forget the compute saving, and on an inference server it often matters most. 메모리: 진행 중인 전송만큼 큰 스테이징 버퍼가 필요 없다. 연산: 복사 커널이 없어 GPU 의 SM 이 모델 계산에 남는다. 지연: 데이터를 두 번 덜 훑는다. 흔히 연산 절약을 잊는데, 추론 서버에서는 대개 그게 가장 중요하다.

Zero-copy is not something you get by asking. It breaks in these cases: zero-copy 는 설정만으로 얻는 성질이 아니다. 다음 경우에 깨진다.

  • The transport falls back to TCP: the engine copies through the host internally, though your config looks the same.전송이 TCP 로 폴백될 때. 엔진이 내부에서 호스트를 거쳐 복사한다. 설정 파일은 그대로라 눈에 띄지 않는다.
  • GPUDirect is unavailable: the NIC cannot address VRAM, so data lands in host memory first.GPUDirect 가 안 될 때. NIC 이 VRAM 을 주소로 잡지 못해 데이터가 호스트 메모리를 먼저 거친다.
  • Something in the middle rearranges the KV: a layer that repacks blocks into its own format (to compress them, say) must materialize that format, and that is a copy. It is a design trade that buys features, not a bug. Our companion note covers where it lands.중간에서 KV 를 재배치할 때. 블록을 자기 포맷으로 다시 담는 계층(예: 압축)은 그 포맷을 어딘가에 만들어야 하고, 그게 곧 복사다. 버그가 아니라 기능과 맞바꾸는 설계 선택이다. 자세한 건 함께 보는 노트에서 다룬다.

In plain words: IPC, and why it keeps coming up쉽게 말하면: IPC 와 그게 자꾸 나오는 이유 IPC = inter-process communication. The OS isolates processes, so A cannot see B's memory even on one machine; IPC is the sanctioned way through that wall.

The trade, in one sentence한 문장으로 본 거래

You spend idle CPU memory, idle SSD, and network bandwidth to avoid spending GPU prefill. The pitch is strong only when what you avoid is expensive and frequent. 놀고 있는 CPU 메모리, 놀고 있는 SSD, 네트워크 대역폭을 내주고 GPU 프리필을 아끼는 거래다. 아끼는 쪽이 비싸고 자주 일어날 때만 설득력이 있다.

The trap: one oversized block cancels the whole load함정: 블록 하나가 크면 로드 전체가 취소된다

enable_offload makes vLLM allocate a DirectIO staging buffer and split reads into sub-batches that fit the owner's staging budget. The splitting is graceful, but there is a hard cap: enable_offload 를 켜면 vLLM 이 DirectIO 스테이징 버퍼를 할당하고, 읽기를 소유자의 스테이징 예산에 맞는 서브 배치로 나눈다. 나누기는 무리 없이 되지만 하드 상한이 있다. 

# store/worker.py — _split_disk_offload_batches
key_bytes = _estimate_disk_offload_staging_bytes(size)
if key_bytes > raw_budget_bytes:
    return [], key      # ← 배치를 못 만들고 그 요청의 로드를 통째로 포기

If one key exceeds the hard per-key budget, the function returns no batches: the request's load is skipped and those blocks are recomputed. A key is one KV block, so this depends on block_size. Raise it far enough and one block exceeds the budget, and offloaded reads quietly stop paying off. No error; the hit rate just fails to turn into TTFT. 키 하나가 키당 하드 예산보다 크면 함수가 배치를 하나도 돌려주지 않는다. 그 요청의 로드는 건너뛰고 해당 블록은 재계산한다. 키 하나가 KV 블록 하나이므로 이는 block_size 에 달렸다. 블록 크기를 많이 키우면 블록 하나가 예산을 넘고, 그때부터 오프로드 읽기가 조용히 효과를 잃는다. 에러는 없고 히트율이 TTFT 개선으로 이어지지 않을 뿐이다.

Two practical notes. The usable budget is the raw one scaled by VLLM_MOONCAKE_DISK_STAGING_USABLE_RATIO, so the effective cap is below the configured buffer. And the SSD path works only if three settings agree: --enable_offload on mooncake_master, the same on the owning mooncake_client, and "enable_offload": true in the vLLM-side JSON (a config key, not an env var). Miss one and offload silently does not happen (§5). 실무 메모가 둘 있다. 실제 예산은 raw 예산에 VLLM_MOONCAKE_DISK_STAGING_USABLE_RATIO 를 곱한 값이라, 실효 상한이 설정한 버퍼보다 낮다. 또 SSD 경로는 설정 셋이 맞아야 동작한다. mooncake_master 의 --enable_offload, 소유자 mooncake_client 의 같은 플래그, vLLM 쪽 JSON 의 "enable_offload": true(환경변수가 아니라 설정 키)다. 하나라도 빠지면 오프로드가 조용히 일어나지 않는다(§5).

Three things that fall out of this mapping이 대조에서 얻는 세 가지

1. The lease is the reason a "hit" can evaporate before it is read1. 히트가 읽히기 전에 증발할 수 있는 이유가 lease 다

Two processes act at two different times. The scheduler calls batch_is_exist(), which per the docs grants a lease with a default 10-second TTL. The worker later does the actual read and gets a fresh lease. In between, the request waits in a queue. 두 프로세스가 서로 다른 시점에 관여한다. 스케줄러가 batch_is_exist() 로 물으면 문서상 기본 10초짜리 lease 가 부여된다. 워커는 나중에 실제로 읽으면서 새 lease 를 받는다. 그 사이 요청은 큐에서 기다린다.

Under load the gap can exceed the TTL. If the pool is also above its eviction watermark, the object may be gone when the worker reads, so the scheduler counted a hit that never materialised. The docs add a narrower case: "if the lease expires before a Get operation finishes reading the data, the operation will be considered failed". 부하가 걸리면 이 간격이 TTL 을 넘을 수 있다. 풀이 축출 수위를 넘은 상태라면 워커가 읽으려 할 때 객체가 이미 없어, 스케줄러는 실현되지 않은 히트를 센 셈이 된다. 문서는 좁은 경우도 하나 더 든다. "if the lease expires before a Get operation finishes reading the data, the operation will be considered failed".

The signature증상의 모양 Hit rate is fine on a quiet cluster and sags only under load, with no errors. That is why §5 insists on reading scheduler-side and worker-side counters separately; a blended number hides this. Levers: the master_service lease-TTL parameter, then the eviction watermark. Reducing queue time is usually cheaper. 한산할 때는 멀쩡하다가 부하가 걸릴 때만 히트율이 떨어지고, 에러는 어디에도 없다. §5 에서 스케줄러 쪽과 워커 쪽 카운터를 따로 보라고 한 이유다. 섞은 숫자로는 이 현상이 보이지 않는다. 손볼 곳은 master_service 의 lease TTL 파라미터, 다음이 축출 수위다. 대개는 큐 대기시간을 줄이는 쪽이 더 싸다.

2. Soft Pin is unused, yet the docs' own example is your workload2. Soft Pin 을 쓰지 않는데, 문서가 든 예시가 바로 이 워크로드다

In plain words: a pin is one of three ways to say "don't delete this"쉽게 말하면: pin 은 "지우지 마" 라고 말하는 세 방법 중 하나다 When the pool passes 90% full, the master's approximate-LRU eviction frees about 5%. A pin is how an object asks to be spared. The three levels differ in how long they last and how hard they push. 풀이 90% 를 넘으면 마스터의 근사 LRU 축출이 5% 정도를 비운다. pin 은 객체가 축출 대상에서 빼 달라고 요청하는 방법이다. 세 단계는 얼마나 오래 가는지와 얼마나 강한지가 다르다.

Hard pin is almost always the wrong tool for a KV cacheKV 캐시에 hard pin 은 대개 틀린 도구다 The docs' examples for it are "model weights, critical metadata": things meant to live for the whole process lifetime. Hard-pin a KV chunk and that space never comes back; at scale the pool fills permanently until PutStart fails for everything else. Soft pin fits a cache: it expires when the object stops being useful and re-arms when it becomes useful again, which suits a prefix whose popularity shifts with traffic. 문서가 hard pin 예시로 든 것은 "model weights, critical metadata", 즉 프로세스 수명 내내 있어야 할 것들이다. KV 청크에 걸면 공간이 돌아오지 않고, 많이 걸면 풀이 영구히 차서 다른 PutStart 가 모두 실패한다. 캐시에 맞는 건 soft pin 이다. 쓸모가 없어지면 풀리고 다시 쓰이면 걸리므로, 인기가 변하는 프리픽스에 맞는다.

"For important and frequently used objects, such as system prompts, Mooncake Store provides a soft pin mechanism." soft pin 된 객체는 다른 후보가 없을 때까지 축출에서 제외되고, 30분간 접근이 없으면 핀이 알아서 풀린다.
