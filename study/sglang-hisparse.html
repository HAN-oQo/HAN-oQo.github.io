SGLang HiSparse — hierarchical KV offloading for sparse attention: theory, mechanism, effects, code flow SGLang HiSparse — 희소 어텐션을 위한 계층적 KV 오프로딩: 이론·동작·효과·코드 흐름

Sparse attention (top-k) cuts the compute per decode step — but the full KV cache still has to sit in GPU HBM, because which tokens matter shifts as generation goes on. So sparse serving becomes capacity-bound, not compute-bound, and HBM caps the batch size. HiSparse is SGLang's decode-side answer: keep only a small hot KV buffer on the GPU, push the full token history to host (CPU pinned) RAM, and swap each step's top-k tokens back with a custom CUDA kernel + LRU. It targets DSA models (DeepSeek-V3.2/V4, GLM-5.x) in PD-disaggregated decode. This note covers the theory (with the HySparse architecture paper as the theory backbone — a different, similarly-named work), the mechanism, the reported effects and their caveats, how to run it, the SGLang code path with commit-pinned permalinks, and status. 희소 어텐션(top-k)은 decode 스텝당 연산을 줄인다 — 그런데 어떤 토큰이 중요한지가 생성이 진행되며 바뀌므로, 전체 KV 캐시는 여전히 GPU HBM에 남아 있어야 한다. 그래서 희소 서빙은 연산 바운드가 아니라 용량 바운드(capacity-bound)가 되고, HBM이 배치 크기를 막는다. HiSparse는 SGLang의 decode 측 해법이다: GPU에는 작은 hot KV 버퍼만 두고, 전체 토큰 히스토리는 호스트(CPU pinned) RAM으로 밀어낸 뒤, 매 스텝의 top-k 토큰을 커스텀 CUDA 커널 + LRU로 다시 불러온다. 대상은 PD 분리(disaggregated) decode의 DSA 모델(DeepSeek-V3.2/V4, GLM-5.x)이다. 이 노트는 이론(HySparse 아키텍처 논문을 이론 backbone으로 — 이름만 비슷한 별개 연구), 동작 원리, 보고된 효과와 그 단서, 실행법, commit에 핀된 permalink로 짚는 SGLang 코드 경로, 그리고 구현 상태를 다룬다.

one-line summary한 줄 요약 HiSparse keeps a small hot KV working set on GPU HBM and offloads the full token history to host (CPU pinned) memory, swapping each step's top-k KV back to device via a custom CUDA kernel with LRU eviction. Because sparse attention is capacity-bound (the whole KV must stay resident even though only top-k is active), freeing HBM raises decode batch size — the LMSYS blog reports over 3× throughput at 256 concurrent requests (GLM-5.1-FP8, 32k-in/8k-out, PD-colocated 8×H200) and up to 5× on long-context sweeps, with modest overhead at low concurrency. It's experimental, decode-side only, needs PD disaggregation and a DSA model. Don't confuse it with the HySparse paper (Xiaomi) — a training-time model architecture with a similar name and theme, which we use only as the theory backbone. HiSparse는 GPU HBM에 작은 hot KV 작업 집합만 두고 전체 토큰 히스토리는 호스트(CPU pinned) 메모리로 오프로드한 뒤, 매 스텝의 top-k KV를 LRU 축출이 있는 커스텀 CUDA 커널로 디바이스에 다시 불러온다. 희소 어텐션은 용량 바운드(capacity-bound)라서(top-k만 활성이어도 전체 KV가 상주해야 함), HBM을 비우면 decode 배치 크기가 커진다 — LMSYS 블로그는 256 동시 요청에서 3배 이상 처리량(GLM-5.1-FP8, 32k입력/8k출력, PD-colocated 8×H200), 롱컨텍스트 스윕에서 최대 5배를 보고하며, 낮은 동시성에선 약간의 오버헤드가 있다. 실험적이고 decode 측 전용, PD 분리와 DSA 모델이 필요하다. 이름이 비슷한 HySparse 논문(Xiaomi)과 혼동하지 말 것 — 그건 학습 시점의 모델 아키텍처이고, 여기선 이론 backbone으로만 쓴다.

KV cache

Per-token Key/Value tensors cached so attention doesn't recompute the whole history each step. Its size grows with context length × batch — the thing that fills HBM.토큰별 Key/Value 텐서를 캐시해 매 스텝 전체 히스토리를 재계산하지 않게 한다. 크기가 컨텍스트 길이 × 배치로 커진다 — HBM을 채우는 주범.

Sparse attention (top-k)희소 어텐션 (top-k)

Attend to only the top-k most relevant past tokens per step, not all. Cuts FLOPs — but the non-selected KV must still be kept, because importance shifts over time.매 스텝 전체가 아니라 관련도 top-k 과거 토큰에만 어텐션. FLOPs를 줄인다 — 단, 선택 안 된 KV도 남겨야 한다(중요도가 시간에 따라 바뀌므로).

DSA

DeepSeek Sparse Attention — a trainable sparse-attention family (DeepSeek-V3.2, GLM-5.x, DeepSeek-V4) that natively selects a token subset, so keeping only top-k on GPU is lossless. HiSparse only works on DSA models.DeepSeek Sparse Attention — 토큰 부분집합을 native하게 선택하는 학습형 희소 어텐션 계열(DeepSeek-V3.2, GLM-5.x, DeepSeek-V4). 그래서 GPU에 top-k만 둬도 무손실. HiSparse는 DSA 모델에서만 동작.

capacity- vs compute-bound용량 vs 연산 바운드

Compute-bound = limited by GPU FLOPs; capacity-bound = limited by HBM. Sparse decode is capacity-bound: the compute is small but the full KV still occupies HBM.연산 바운드 = GPU FLOPs 한계; 용량 바운드 = HBM 한계. 희소 decode는 용량 바운드다 — 연산은 작지만 전체 KV가 HBM을 차지한다.

hot buffer / host poolhot 버퍼 / 호스트 풀

Hot buffer = a small fixed-size per-request KV kept on GPU (device_buffer_size slots). Host pool = the full KV history in CPU pinned RAM (host_to_device_ratio× larger).hot 버퍼 = GPU에 두는 요청별 고정 크기 KV(device_buffer_size 슬롯). 호스트 풀 = CPU pinned RAM의 전체 KV 히스토리(host_to_device_ratio배 큼).

HiSparse = SGLang serving feature (KV offload, inference). HySparse = a Xiaomi model-architecture paper (KV sharing across layers, training). Similar names, different layers of the stack — see §1.HiSparse = SGLang 서빙 기능(KV 오프로드, 추론). HySparse = Xiaomi의 모델 아키텍처 논문(레이어 간 KV 공유, 학습). 이름은 비슷하나 스택의 다른 층 — §1 참고.

1Theory — sparse attention saves compute, not memory이론 — 희소 어텐션은 연산을 아끼지 메모리를 아끼지 않는다

Sparse attention is usually sold as a compute win: instead of attending to all past tokens, attend to the top-k most relevant, so the per-step FLOPs stop growing with context length. For serving, though, the binding constraint is usually not FLOPs — it's HBM capacity. And here dynamic (top-k) sparse attention gives you nothing: you must still keep the entire KV cache resident, because the set of "important" tokens changes from step to step, so you cannot safely evict any of it. 희소 어텐션은 보통 연산 이득으로 팔린다: 모든 과거 토큰이 아니라 관련도 top-k에만 어텐션하니 스텝당 FLOPs가 컨텍스트 길이에 따라 커지지 않는다. 그런데 서빙에서 병목은 대개 FLOPs가 아니라 HBM 용량이다. 그리고 여기선 동적(top-k) 희소 어텐션이 아무것도 해결하지 못한다: "중요한" 토큰 집합이 스텝마다 바뀌므로 어느 것도 안전하게 축출할 수 없어, 전체 KV 캐시를 그대로 상주시켜야 한다.

"As a result, sparse attention is often capacity-bound rather than compute-bound, limiting the achievable batch size and overall throughput."

— LMSYS blog, "SGLang HiSparse" · lmsys.org/blog/2026-04-10-sglang-hisparse

The HySparse paper states the same limitation in general form — this is the theory backbone we lean on (it is a different work; see the callout below). It splits the failure modes of sparse attention into two, and the second is exactly the memory problem HiSparse attacks: HySparse 논문은 같은 한계를 일반적인 형태로 정리한다 — 우리가 기대는 이론 backbone이다(별개 연구다; 아래 콜아웃 참고). 희소 어텐션의 실패 양상을 둘로 나누는데, 두 번째가 바로 HiSparse가 공격하는 메모리 문제다:

"While dynamic sparse attention can effectively reduce computation, it provides no relief for memory consumption. Maintaining a full-sized KV cache therefore remains a dominant bottleneck for serving throughput and maximum batch size, limiting the practical benefits of sparse attention in long-context settings."

— HySparse, §1 Introduction · arXiv:2602.03560

Two ways to make sparse attention also save memory희소 어텐션이 메모리도 아끼게 하는 두 갈래

There are two levels at which you can fix "compute drops but memory doesn't": "연산은 줄지만 메모리는 안 준다"를 고치는 층위는 둘이다:

Architecture level — HySparse (the paper)아키텍처 층위 — HySparse (논문)

Change the model: interleave each full-attention layer with several sparse layers, use the full layer as an oracle for token selection, and let the sparse layers reuse the full layer's KV cache. In their 80B MoE with a 1:11 ratio, only 5 of 49 layers keep full attention — "reducing KV cache storage by nearly 10×." This is a training-time change; it needs a new model.모델을 바꾼다: full 어텐션 레이어마다 여러 sparse 레이어를 끼우고, full 레이어를 토큰 선택의 oracle로 쓰며, sparse 레이어가 full 레이어의 KV 캐시를 재사용하게 한다. 80B MoE 1:11 비율에선 49개 중 5개만 full 어텐션 — "KV 캐시 저장량을 거의 10× 감소". 학습 시점 변경이라 새 모델이 필요하다.

Serving level — HiSparse (SGLang)서빙 층위 — HiSparse (SGLang)

Take the model as given (a DSA model) and change where the KV lives: keep the hot top-k on the GPU, keep the full history in host RAM, and stream the misses in on demand. No model change — an inference-time memory-tiering system, in the spirit of LMSYS's earlier HiCache.모델은 그대로 두고(DSA 모델) KV가 어디 사는지를 바꾼다: hot top-k는 GPU, 전체 히스토리는 호스트 RAM, 미스는 필요할 때 스트리밍. 모델 변경 없음 — LMSYS의 이전 HiCache 계열인 추론 시점 메모리 티어링 시스템.

important — HiSparse ≠ HySparse (don't conflate)중요 — HiSparse ≠ HySparse (혼동 금지) The names collide and both are about "sparse attention should also save memory," but they are different works at different layers of the stack. HySparse (Yizhao Gao et al., LLM-Core Xiaomi, arXiv:2602.03560, 3 Feb 2026) is a model architecture — a training-time change that reduces KV storage via cross-layer sharing. HiSparse (Zhiqiang Xie, Zhangheng Huang, Tingwei Huang et al., with the SGLang community + Alibaba Cloud TairKVCache + AntGroup SCT teams) is a serving system — an inference-time KV offload for existing DSA models. The HiSparse blog links no paper. We use HySparse only to frame the problem; do not attribute HySparse's ~10× KV-storage figure to HiSparse — that is an architecture result, not a serving-throughput result. 이름이 겹치고 둘 다 "희소 어텐션이 메모리도 아껴야 한다"를 다루지만, 스택의 다른 층에 있는 별개 연구다. HySparse(Yizhao Gao 외, LLM-Core Xiaomi, arXiv:2602.03560, 2026-02-03)는 모델 아키텍처 — 레이어 간 공유로 KV 저장량을 줄이는 학습 시점 변경. HiSparse(Zhiqiang Xie·Zhangheng Huang·Tingwei Huang 외, SGLang 커뮤니티 + Alibaba Cloud TairKVCache + AntGroup SCT 팀)는 서빙 시스템 — 기존 DSA 모델을 위한 추론 시점 KV 오프로드. HiSparse 블로그는 논문을 링크하지 않는다. 여기선 HySparse를 문제 정의용으로만 쓴다; HySparse의 ~10× KV 저장 감소를 HiSparse의 수치로 갖다 붙이지 말 것 — 그건 아키텍처 결과이지 서빙 처리량 결과가 아니다.

2How HiSparse works — hot buffer, host pool, swap-in kernel동작 원리 — hot 버퍼·호스트 풀·swap-in 커널

HiSparse is a two-tier memory hierarchy per request. On the GPU it keeps a small, fixed-size hot device buffer (device_buffer_size token slots — e.g. 4096 or 6144). In CPU pinned RAM it keeps the full KV history in a host pool sized host_to_device_ratio× the on-device pool. Each decode step, a CUDA swap-in kernel resolves the step's top-k tokens to device slots, evicting cold slots by LRU and fetching any misses from host. HiSparse는 요청별 2단 메모리 계층이다. GPU엔 작고 고정 크기인 hot 디바이스 버퍼(device_buffer_size 토큰 슬롯 — 예: 4096 또는 6144)를 둔다. CPU pinned RAM엔 전체 KV 히스토리를 host_to_device_ratio배 크기의 호스트 풀에 둔다. 매 decode 스텝, CUDA swap-in 커널이 그 스텝의 top-k 토큰을 디바이스 슬롯에 매핑하고, 차가운 슬롯을 LRU로 축출하며, 미스는 호스트에서 가져온다.

"HiSparse proactively offloads inactive KV cache entries to host memory, significantly reducing GPU memory pressure, while maintaining a hot device buffer on GPU HBM for frequently accessed KV regions to minimize data movement on the critical path. This enables much larger decoding batch sizes, improving throughput…"

— LMSYS blog, "Design of HiSparse" · lmsys.org/blog/2026-04-10-sglang-hisparse

The per-step decode loop스텝별 decode 루프

  1. Forward decode — generate the next token.Forward decode — 다음 토큰 생성.
  2. Top-k selection — the DSA indexer picks the most relevant token positions from attention scores.Top-k 선택 — DSA indexer가 어텐션 점수로 가장 관련도 높은 토큰 위치를 고른다.
  3. Swap-in — the CUDA kernel loads the top-k KV from host into the device buffer: short sequences (seq_len ≤ device_buffer_size) hit a fast path (all KV already resident); long sequences do hit-detection → LRU reordering → miss handling (host→device copy).Swap-in — CUDA 커널이 top-k KV를 호스트에서 디바이스 버퍼로 로드: 짧은 시퀀스(seq_len ≤ device_buffer_size)는 fast path(전부 이미 상주); 긴 시퀀스는 히트 탐지 → LRU 재정렬 → 미스 처리(host→device 복사).

PD direct-to-host, and why the hot buffer size mattersPD direct-to-host, 그리고 hot 버퍼 크기가 중요한 이유

HiSparse is decode-side only and assumes PD disaggregation. In that mode the prefill node RDMA-writes the prompt's KV directly into the decode instance's host pool, bypassing the decode GPU entirely — so admission just allocates the small device buffer, with no transient GPU memory spike and no staging DMA. The prefill instance is unaware of HiSparse and needs no changes. HiSparse는 decode 측 전용이고 PD 분리를 전제한다. 그 모드에선 prefill 노드가 프롬프트 KV를 decode 인스턴스의 호스트 풀로 직접 RDMA 기록해 decode GPU를 완전히 우회한다 — 그래서 admission은 작은 디바이스 버퍼만 할당하고, 일시적 GPU 메모리 스파이크도 staging DMA도 없다. prefill 인스턴스는 HiSparse를 모르며 변경이 필요 없다.

The one knob that most affects the critical path is the hot buffer size: a bigger buffer holds more of the working set, so fewer top-k tokens miss and have to be fetched from host each step. 임계경로에 가장 크게 영향을 주는 노브는 hot 버퍼 크기다: 버퍼가 크면 작업 집합을 더 많이 담아, 매 스텝 호스트에서 가져와야 하는 top-k 미스가 줄어든다.

"With a larger hot device buffer (4096 vs. 2048 slots) and LRU eviction, miss counts drop substantially, directly translating to lower swap-in latency on the critical path."

— LMSYS blog · lmsys.org/blog/2026-04-10-sglang-hisparse

3Effects — theory vs what's actually been reported효과 — 이론 vs 실제로 보고된 것

Split into (a) what the mechanism should do and (b) the numbers actually published. The honest headline: every reported number is from the LMSYS/SGLang blog (vendor), on DSA models, at high concurrency or long context — the regime HiSparse is built for. There is no independent third-party measurement yet, and no isolated ablation of swap-in overhead vs. plain sparse decode. (a) 메커니즘이 해야 하는 것과 (b) 실제 공개된 수치로 나눈다. 정직한 헤드라인: 보고된 수치는 전부 LMSYS/SGLang 블로그(벤더)에서, DSA 모델·높은 동시성 또는 롱컨텍스트 — HiSparse가 노리는 영역에서 나온 것이다. 아직 독립적인 제3자 측정도, plain 희소 decode 대비 swap-in 오버헤드를 분리한 ablation도 없다.

In order:순서대로:

  • Fast path — if seq_len ≤ HOT_BUFFER_SIZE, all tokens are resident and in order; just map top-k → existing slots and return (#L242-L251).Fast path — seq_len ≤ HOT_BUFFER_SIZE면 전 토큰이 순서대로 상주; top-k → 기존 슬롯 매핑 후 반환(#L242-L251).

6Implementation status & roadmap구현 상태 & 로드맵

Experimental. HiSparse is decode-side only, requires PD disaggregation + --disable-radix-cache, and works only on DSA/DeepSeek-V4 models. Supported today: DeepSeek-V3.2, GLM-5.x (e2e/accuracy tests exist for GLM-5.1 and GLM-5.2, incl. AMD MI30x/MI35x), and DeepSeek-V4 via a separate dsv4 code path (compress-ratio 4). 실험적. decode 측 전용, PD 분리 + --disable-radix-cache 필요, DSA/DeepSeek-V4 모델에서만. 현재 지원: DeepSeek-V3.2, GLM-5.x(GLM-5.1·5.2 e2e/정확도 테스트 존재, AMD MI30x/MI35x 포함), 그리고 별도 dsv4 경로의 DeepSeek-V4(compress-ratio 4).

Roadmap (issue #28874)로드맵 (issue #28874)

The open roadmap issue "HiSparse Roadmap for Long-Context Sparse Serving" (opened 2026-06-22 by hzh0425) lists four tracks: (1) more sparse models — MiniMax-M3, DeepSeek-V4, GLM-5.2/5.1; (2) 1 MB long-context perf — IO prefetch/compute overlap, MTP compatibility (with "dynamic balancing: MTP for small batches, HiSparse for large batches"), kernel opt, and TwoBatch Overlap; (3) PD decode integration — L2 RadixTree, NIXL DRAM support, cross-TP CPU-memory sharing; (4) more training-free algorithms — "extension points for Quest and other training-free sparse attention algorithms." Linked PRs include #28523, #26445, #28753, #28752, #27563, #27370, #25288, #28879. 공개 로드맵 이슈 "HiSparse Roadmap for Long-Context Sparse Serving"(2026-06-22, hzh0425 개설)는 네 갈래를 든다: (1) 더 많은 sparse 모델 — MiniMax-M3, DeepSeek-V4, GLM-5.2/5.1; (2) 1 MB 롱컨텍스트 성능 — IO prefetch/compute overlap, MTP 호환("dynamic balancing: 작은 배치엔 MTP, 큰 배치엔 HiSparse"), 커널 최적화, TwoBatch Overlap; (3) PD decode 통합 — L2 RadixTree, NIXL DRAM 지원, TP 간 CPU 메모리 공유; (4) 더 많은 training-free 알고리즘 — "Quest 등 training-free 희소 어텐션 알고리즘용 확장점." 링크된 PR: #28523, #26445, #28753, #28752, #27563, #27370, #25288, #28879.

editor's note — our angle (not an LMSYS/SGLang claim)편집자 주 — 우리 관점 (LMSYS/SGLang 주장 아님) HiSparse is squarely in the KV-tiering family we care about (GPU↔host KV movement, à la HiCache / LMCache / NIXL DRAM), but with a sharp scope: it only helps a DSA model, decode-side, under PD disaggregation, when you're HBM-capped. For our MI250/ROCm lab that last point plus the explicit ROCm DSv4 guard means it's not a flip-a-switch win yet — the bf16→flashmla_sparse / tilelang/aiter backends exist, but V4 on ROCm unified-KV is blocked in-code. Where it connects to our work: it's the serving-side dual of the HySparse architecture idea (both make "sparse attention actually save memory" true — one at training time, one at serve time), and it needs the same host-memory + RDMA transfer fabric (NIXL DRAM is on its roadmap) that our P/D + wide-EP interest already leans on. Practical boundary to keep honest: the 3×/5× are vendor, best-case, high-pressure numbers; at low concurrency it's a documented regression, and it costs 1–2 TB of host RAM. Worth planning for at fleet scale on DSA models, not a single-box default. HiSparse는 우리가 관심 있는 KV 티어링 계열(GPU↔host KV 이동, HiCache / LMCache / NIXL DRAM 류)에 정확히 들어가지만 범위가 좁다: DSA 모델·decode 측·PD 분리·HBM에 막혔을 때만 이득. 우리 MI250/ROCm 랩에선 그 마지막 조건 + 명시적 ROCm DSv4 가드 때문에 아직 스위치 하나로 되는 이득이 아니다 — bf16→flashmla_sparse / tilelang/aiter 백엔드는 있지만 ROCm unified-KV의 V4는 코드에서 막혀 있다. 우리 작업과의 접점: HySparse 아키텍처 아이디어의 서빙 측 쌍이고(둘 다 "희소 어텐션이 실제로 메모리를 아끼게" 만든다 — 하나는 학습 시점, 하나는 서빙 시점), 우리 P/D + wide-EP 관심이 이미 기대는 host 메모리 + RDMA 전송 fabric(NIXL DRAM이 로드맵에 있음)을 똑같이 필요로 한다. 정직히 지킬 경계: 3×/5×는 벤더·최선·고압박 수치; 낮은 동시성에선 문서화된 회귀이고, host RAM 1–2 TB가 든다. DSA 모델에서 fleet 스케일로 계획할 거리이지 단일 박스 기본값은 아니다.
