SGLang HiSparse — hierarchical KV offloading for sparse attention: theory, mechanism, effects, code flow SGLang HiSparse: 희소 어텐션을 위한 계층적 KV 오프로딩 (이론·동작·효과·코드 흐름)

HiSparse is SGLang's decode-side fix for the capacity problem of sparse attention: keep a small hot KV buffer on the GPU, move the full token history to host (CPU pinned) RAM, and swap each step's top-k back with a custom CUDA kernel + LRU. This note covers theory (framed with the similarly-named HySparse paper, a different work), mechanism, reported effects, usage, and the SGLang code path at a pinned commit. HiSparse는 희소 어텐션의 용량 문제를 푸는 SGLang의 decode 측 기능이다. GPU에는 작은 hot KV 버퍼만 두고 전체 토큰 히스토리는 호스트(CPU pinned) RAM으로 옮긴 뒤, 매 스텝의 top-k를 커스텀 CUDA 커널과 LRU로 다시 불러온다. 이 노트는 이론(이름만 비슷한 별개 연구인 HySparse 논문으로 문제를 정리), 동작, 보고된 효과, 사용법, 고정 커밋 기준 SGLang 코드 경로를 다룬다.

one-line summary한 줄 요약
  • HiSparse keeps a small hot KV working set on GPU HBM, offloads the full history to host (CPU pinned) memory, and swaps each step's top-k back via a custom CUDA kernel with LRU eviction.
  • Sparse attention is capacity-bound: only top-k is active, yet the whole KV must stay resident. Freeing HBM raises the decode batch size.
  • The LMSYS blog reports over 3× throughput at 256 concurrent requests (GLM-5.1-FP8, 32k-in/8k-out, PD-colocated 8×H200) and up to 5× on long-context sweeps, with modest overhead at low concurrency.
  • Experimental, decode-side only, needs PD disaggregation and a DSA model. Not the HySparse paper (Xiaomi), a training-time architecture we use only as theory backbone.
  • GPU HBM에는 작은 hot KV 작업 집합만 두고 전체 히스토리는 호스트(CPU pinned) 메모리로 옮긴다. 매 스텝의 top-k KV는 LRU 축출을 하는 커스텀 CUDA 커널이 다시 불러온다.
  • 희소 어텐션은 용량 바운드(capacity-bound)다. top-k만 쓰는데도 전체 KV가 상주해야 하므로, HBM을 비우면 decode 배치를 키울 수 있다.
  • LMSYS 블로그는 256 동시 요청에서 3배 이상 처리량(GLM-5.1-FP8, 32k입력/8k출력, PD-colocated 8×H200)과 롱컨텍스트 스윕에서 최대 5배를 보고한다. 낮은 동시성에서는 약간 느려진다.
  • 실험적 기능이고 decode 측 전용이며 PD 분리와 DSA 모델이 필요하다. 이름이 비슷한 HySparse 논문(Xiaomi)은 학습 시점 아키텍처이고, 여기서는 이론 정리에만 쓴다.

Compute-bound: limited by FLOPs. Capacity-bound: limited by HBM. Sparse decode is the latter.연산 바운드는 FLOPs가, 용량 바운드는 HBM이 한계다. 희소 decode는 후자다.

1Theory: sparse attention saves compute, not memory이론: 희소 어텐션은 연산만 아끼고 메모리는 못 아낀다

Sparse attention is usually sold as a compute win: per-step FLOPs stop growing with context length. In serving, though, the binding limit is usually HBM capacity, and dynamic (top-k) sparsity doesn't help there. The set of "important" tokens changes every step, so nothing can be safely evicted and the entire KV cache must stay resident. 희소 어텐션은 보통 연산 이득으로 소개된다. 스텝당 FLOPs가 컨텍스트 길이에 따라 늘지 않기 때문이다. 하지만 서빙의 병목은 대개 HBM 용량이고, 동적(top-k) 희소성은 여기에 도움이 안 된다. "중요한" 토큰이 스텝마다 바뀌어 아무것도 지울 수 없으니 전체 KV 캐시를 상주시켜야 한다.

"As a result, sparse attention is often capacity-bound rather than compute-bound, limiting the achievable batch size and overall throughput."

— LMSYS blog, "SGLang HiSparse" · lmsys.org/blog/2026-04-10-sglang-hisparse

The HySparse paper (a different work, see the callout below) states the same limit in general form. Of the two failure modes it names, the second is the memory problem HiSparse attacks: HySparse 논문(별개 연구, 아래 콜아웃 참고)도 같은 한계를 일반화해 정리한다. 논문이 꼽는 두 가지 실패 양상 중 두 번째가 HiSparse가 겨냥하는 메모리 문제다.

"While dynamic sparse attention can effectively reduce computation, it provides no relief for memory consumption. Maintaining a full-sized KV cache therefore remains a dominant bottleneck for serving throughput and maximum batch size, limiting the practical benefits of sparse attention in long-context settings."

— HySparse, §1 Introduction · arXiv:2602.03560

Two ways to make sparse attention also save memory희소 어텐션이 메모리도 아끼게 하는 두 갈래

There are two levels at which to fix "compute drops but memory doesn't": "연산은 줄지만 메모리는 그대로"인 문제를 고치는 층위는 둘이다.

Architecture level: HySparse (the paper)아키텍처 층위: HySparse (논문)

Change the model: interleave full-attention layers with sparse layers, use the full layer as an oracle for token selection, and let sparse layers reuse its KV cache. In their 80B MoE (1:11), only 5 of 49 layers keep full attention, "reducing KV cache storage by nearly 10×." A training-time change that needs a new model.모델을 바꾼다. full 어텐션 레이어 사이에 sparse 레이어를 끼우고, full 레이어를 토큰 선택 oracle로 쓰며, sparse 레이어가 그 KV 캐시를 재사용한다. 80B MoE(1:11)에서는 49개 중 5개만 full 어텐션이고 "KV 캐시 저장량을 거의 10× 감소"시킨다. 학습 시점 변경이라 새 모델이 필요하다.

Serving level: HiSparse (SGLang)서빙 층위: HiSparse (SGLang)

Keep the DSA model as is and change where the KV lives: hot top-k on GPU, full history in host RAM, misses streamed on demand. An inference-time memory tier in the spirit of LMSYS's earlier HiCache.DSA 모델은 그대로 두고 KV의 위치를 바꾼다. hot top-k는 GPU, 전체 히스토리는 호스트 RAM에 두고 미스는 필요할 때 가져온다. LMSYS의 이전 HiCache와 같은 계열인 추론 시점 메모리 티어링이다.

important: HiSparse ≠ HySparse (don't conflate)중요: HiSparse ≠ HySparse (혼동 금지) Similar names, same theme, but different works at different layers of the stack. HySparse (Yizhao Gao et al., LLM-Core Xiaomi, arXiv:2602.03560, 3 Feb 2026) is a training-time model architecture that cuts KV storage via cross-layer sharing. HiSparse (Zhiqiang Xie, Zhangheng Huang, Tingwei Huang et al., with the SGLang community + Alibaba Cloud TairKVCache + AntGroup SCT teams) is an inference-time serving system for existing DSA models, and its blog links no paper. Do not attribute HySparse's ~10× KV-storage figure to HiSparse: it is an architecture result, not a serving-throughput result. 이름과 주제는 비슷하지만 스택의 다른 층에 있는 별개 연구다. HySparse(Yizhao Gao 외, LLM-Core Xiaomi, arXiv:2602.03560, 2026-02-03)는 레이어 간 공유로 KV 저장량을 줄이는 학습 시점 모델 아키텍처다. HiSparse(Zhiqiang Xie·Zhangheng Huang·Tingwei Huang 외, SGLang 커뮤니티 + Alibaba Cloud TairKVCache + AntGroup SCT 팀)는 기존 DSA 모델용 추론 시점 서빙 시스템이고, 블로그는 논문을 링크하지 않는다. HySparse의 ~10× KV 저장 감소를 HiSparse 수치로 쓰면 안 된다. 아키텍처 결과이지 서빙 처리량 결과가 아니다.

2How HiSparse works: hot buffer, host pool, swap-in kernel동작 원리: hot 버퍼·호스트 풀·swap-in 커널

HiSparse is a two-tier memory hierarchy per request. The GPU holds a small, fixed-size hot device buffer (device_buffer_size token slots, e.g. 4096 or 6144). CPU pinned RAM holds the full KV history in a host pool sized host_to_device_ratio× the device pool. Each decode step, a CUDA swap-in kernel maps top-k tokens to device slots, evicts cold slots by LRU, and fetches misses from host. HiSparse는 요청마다 2단 메모리 계층을 둔다. GPU에는 작은 고정 크기 hot 디바이스 버퍼(device_buffer_size 토큰 슬롯, 예: 4096 또는 6144)가 있다. CPU pinned RAM에는 디바이스 풀의 host_to_device_ratio배 크기인 호스트 풀에 전체 KV 히스토리를 둔다. decode 스텝마다 CUDA swap-in 커널이 top-k 토큰을 디바이스 슬롯에 매핑하고, 차가운 슬롯을 LRU로 비우고, 미스는 호스트에서 가져온다.

"HiSparse proactively offloads inactive KV cache entries to host memory, significantly reducing GPU memory pressure, while maintaining a hot device buffer on GPU HBM for frequently accessed KV regions to minimize data movement on the critical path. This enables much larger decoding batch sizes, improving throughput…"

— LMSYS blog, "Design of HiSparse" · lmsys.org/blog/2026-04-10-sglang-hisparse

The per-step decode loop스텝별 decode 루프

The in-repo guide's decode flow, which the code (§5) follows step for step: 레포 가이드의 decode 흐름이다. 코드(§5)도 이 순서를 그대로 따른다.

  1. Forward decode: generate the next token.Forward decode: 다음 토큰을 만든다.
  2. Top-k selection: the DSA indexer picks the most relevant token positions from attention scores.Top-k 선택: DSA indexer가 어텐션 점수로 관련도 높은 토큰 위치를 고른다.
  3. Swap-in: the CUDA kernel loads top-k KV from host into the device buffer. Short sequences (seq_len ≤ device_buffer_size) take a fast path (all KV already resident). Long sequences go through hit-detection → LRU reordering → miss handling (host→device copy).Swap-in: CUDA 커널이 top-k KV를 호스트에서 디바이스 버퍼로 올린다. 짧은 시퀀스(seq_len ≤ device_buffer_size)는 이미 전부 상주하므로 fast path로 끝난다. 긴 시퀀스는 히트 탐지 → LRU 재정렬 → 미스 처리(host→device 복사)를 거친다.
  4. Decode attention: compute attention over the top-k device locations.Decode 어텐션: top-k 디바이스 위치로 어텐션을 계산한다.
  5. Eager backup: asynchronously copy the previous token's KV device→host on a side stream, so the kernel can recover it later.Eager backup: 직전 토큰의 KV를 사이드 스트림에서 비동기로 device→host 복사해 둔다. 나중에 커널이 이 값을 복구한다.

PD direct-to-host, and why the hot buffer size mattersPD direct-to-host, 그리고 hot 버퍼 크기가 중요한 이유

HiSparse is decode-side only and assumes PD disaggregation. The prefill node RDMA-writes the prompt's KV directly into the decode instance's host pool, bypassing the decode GPU. Admission just allocates the small device buffer: no transient GPU memory spike, no staging DMA. The prefill instance is unaware of HiSparse and needs no changes. HiSparse는 decode 측 전용이고 PD 분리를 전제한다. prefill 노드가 프롬프트 KV를 decode 인스턴스의 호스트 풀로 직접 RDMA 기록하므로 decode GPU를 거치지 않는다. 그래서 admission은 작은 디바이스 버퍼만 할당하고, 일시적인 GPU 메모리 스파이크나 staging DMA가 생기지 않는다. prefill 인스턴스는 HiSparse를 몰라도 되고 바꿀 것도 없다.

The knob that most affects the critical path is the hot buffer size: a bigger buffer means fewer top-k misses fetched from host each step. 임계경로에 가장 큰 영향을 주는 노브는 hot 버퍼 크기다. 버퍼가 클수록 매 스텝 호스트에서 가져올 top-k 미스가 줄어든다.

"With a larger hot device buffer (4096 vs. 2048 slots) and LRU eviction, miss counts drop substantially, directly translating to lower swap-in latency on the critical path."

— LMSYS blog · lmsys.org/blog/2026-04-10-sglang-hisparse

In order:순서대로:

  • Fast path: if seq_len ≤ HOT_BUFFER_SIZE, all tokens are resident and in order; just map top-k → existing slots and return (#L242-L251).Fast path: seq_len ≤ HOT_BUFFER_SIZE면 전 토큰이 순서대로 상주한다. top-k를 기존 슬롯에 매핑하고 반환한다(#L242-L251).
  • Hit detection: a shared-memory open-addressing hash of the top-k token ids; the newest token is special-cased into a reserved extra-page slot (#L294-L313).히트 탐지: top-k 토큰 id를 shared-memory 오픈어드레싱 해시에 넣는다. 최신 토큰은 예약된 extra-page 슬롯으로 따로 처리한다(#L294-L313).
  • LRU compaction: warp-ballot prefix sums pack hits to the MRU end and evictables to the LRU front; misses claim the LRU-front slots (#L319-L461).LRU 압축: warp-ballot prefix sum으로 히트는 MRU 끝에, 축출 대상은 LRU 앞에 모은다. 미스는 LRU 앞 슬롯을 차지한다(#L319-L461).
  • Host→device fetch: each warp copies one missing token's KV from the host pool into its evicted device slot (#L500-L543).Host→device fetch: warp 하나가 미스 토큰 1개의 KV를 호스트 풀에서 축출된 디바이스 슬롯으로 복사한다(#L500-L543).

6Implementation status & roadmap구현 상태 & 로드맵

Experimental. HiSparse is decode-side only, requires PD disaggregation + --disable-radix-cache, and works only on DSA/DeepSeek-V4 models. Supported today: DeepSeek-V3.2, GLM-5.x (e2e/accuracy tests exist for GLM-5.1 and GLM-5.2, incl. AMD MI30x/MI35x), and DeepSeek-V4 via a separate dsv4 code path (compress-ratio 4). 실험적 기능이다. decode 측 전용이고 PD 분리와 --disable-radix-cache가 필요하며 DSA/DeepSeek-V4 모델에서만 돈다. 현재 지원 모델은 DeepSeek-V3.2, GLM-5.x(GLM-5.1·5.2 e2e/정확도 테스트 있음, AMD MI30x/MI35x 포함), 별도 dsv4 경로의 DeepSeek-V4(compress-ratio 4)다.

editor's note: our angle (not an LMSYS/SGLang claim)편집자 주: 우리 관점 (LMSYS/SGLang 주장 아님)
  1. HiSparse is squarely in the KV-tiering family we care about (GPU↔host KV movement, à la HiCache / LMCache / NIXL DRAM), but its scope is sharp: a DSA model, decode-side, under PD disaggregation, when you're HBM-capped.
  2. For our MI250/ROCm lab it's not a flip-a-switch win yet. The bf16→flashmla_sparse / tilelang/aiter backends exist, but the explicit ROCm DSv4 guard blocks V4 on ROCm unified-KV in-code.
  3. It's the serving-side dual of the HySparse idea (one at training time, one at serve time), and it needs the same host-memory + RDMA transfer fabric (NIXL DRAM is on its roadmap) our P/D + wide-EP interest leans on.
  4. The 3×/5× are vendor, best-case, high-pressure numbers; at low concurrency it's a documented regression, and it costs 1–2 TB of host RAM. Worth planning for at fleet scale on DSA models, not a single-box default.
  1. HiSparse는 우리가 관심 있는 KV 티어링 계열(GPU↔host KV 이동, HiCache / LMCache / NIXL DRAM 류)에 속한다. 다만 DSA 모델·decode 측·PD 분리·HBM에 막힌 상황에서만 이득이다.
  2. 우리 MI250/ROCm 랩에서는 아직 스위치만 켜면 되는 기능이 아니다. bf16→flashmla_sparse / tilelang/aiter 백엔드는 있지만, 명시적인 ROCm DSv4 가드가 ROCm unified-KV의 V4를 코드에서 막는다.
  3. HySparse 아이디어의 서빙 측 짝이다(하나는 학습 시점, 하나는 서빙 시점). 우리 P/D + wide-EP 관심사가 기대는 host 메모리 + RDMA 전송 fabric(NIXL DRAM이 로드맵에 있음)도 똑같이 필요하다.
  4. 3×/5×는 벤더가 고압박 조건에서 낸 최선 수치다. 낮은 동시성에선 느려진다고 문서에 나와 있고 host RAM이 1–2 TB 든다. 단일 박스 기본값이 아니라 DSA 모델 fleet 규모에서 계획할 기능이다.
