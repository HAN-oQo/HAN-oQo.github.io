AgentX methodology — how SemiAnalysis turns real Claude Code traces into a replayable benchmark AgentX 방법론 — 실제 Claude Code 트레이스를 재현 가능한 벤치마크로 바꾸는 법

Almost every inference benchmark you have seen sends independent requests of a fixed shape. Agentic traffic is not that: it is one long conversation that fans out into subagents, re-sends a 140k-token prefix on every turn, and spends 95% of its tokens reading cache it wrote itself. AgentX is SemiAnalysis's attempt to benchmark that workload honestly — by recording real Claude Code sessions through an opt-in proxy, stripping every byte of content out of them, and replaying what remains as a dependency graph. This note walks the whole methodology, and pays particular attention to the parts that are hard: how you replay a session you are not allowed to read, why "concurrency" stops meaning what you think, and the two knobs they had to add to serving engines before the numbers could be compared at all. 여러분이 본 대부분의 추론 벤치마크는 정해진 모양의 독립적인 요청을 쏜다. 에이전트 트래픽은 그렇지 않다. 하나의 긴 대화가 서브에이전트로 갈라지고, 매 턴 14만 토큰짜리 프리픽스를 다시 보내며, 토큰의 95%를 자기가 쓴 캐시를 읽는 데 쓴다. AgentX 는 그 워크로드를 정직하게 재는 SemiAnalysis 의 시도다 — 실제 Claude Code 세션을 옵트인 프록시로 기록하고, 내용은 한 바이트도 남기지 않고 벗겨낸 뒤, 남은 것을 의존성 그래프로 재생한다. 이 노트는 방법론 전체를 따라가되 어려운 부분에 특히 공을 들인다. 읽을 수 없는 세션을 어떻게 재생하는가, 왜 "동시성" 이 생각하던 의미를 잃는가, 그리고 숫자를 비교라도 하려면 서빙 엔진에 먼저 넣어야 했던 손잡이 두 개.

In one line한 줄 요약 AgentX converts opt-in Claude Code proxy traces into deterministic AIPerf workloads. It keeps request lengths, timing, branch structure, and KV-prefix reuse and throws away everything else — then replays the result as a DAG under a fixed one-hour profiling window. It measures how a serving system behaves under real agentic shape; it explicitly does not measure whether the model's answers are any good. AgentX 는 옵트인으로 수집한 Claude Code 프록시 트레이스를 결정적인 AIPerf 워크로드로 바꾼다. 요청 길이·타이밍·분기 구조·KV 프리픽스 재사용만 남기고 나머지는 전부 버린 뒤, 그 결과를 DAG 로 고정된 1시간 프로파일링 창 안에서 재생한다. 서빙 시스템이 진짜 에이전트 모양의 부하에서 어떻게 동작하는지를 재고, 모델의 답이 좋은지는 재지 않는다고 명시한다.

1 Collection — recording a session you are not allowed to read 수집 — 읽으면 안 되는 세션을 기록하기

Participants opt in to an HTTP proxy. It records request arrival and completion times, input and output token counts, conversation IDs, and subagent IDs. The published corpus does not contain prompts, source code, tool arguments, or tool results — which immediately raises the question the rest of this section answers: if you kept none of the content, what exactly are you replaying? 참가자가 HTTP 프록시에 옵트인한다. 프록시는 요청 도착·완료 시각, 입출력 토큰 수, 대화 ID, 서브에이전트 ID 를 기록한다. 공개 코퍼스에는 프롬프트·소스코드·툴 인자·툴 결과가 들어 있지 않다. 그러면 곧바로 이 절의 나머지가 답할 질문이 생긴다 — 내용을 하나도 안 남겼는데 대체 무엇을 재생한다는 것인가?

The trick: 64-token hash blocks핵심 장치 — 64토큰 해시 블록

The proxy represents each input as session-scoped chained hashes in 64-token blocks. Matching block IDs preserve shared prefixes within a session. AIPerf then replaces the blocks with deterministic synthetic coding and tool-use tokens before replay. 프록시는 각 입력을 세션 범위의 연쇄 해시, 64토큰 블록 단위로 표현한다. 블록 ID 가 일치하면 그 세션 안의 공유 프리픽스가 보존된다. 재생 직전에 AIPerf 가 그 블록들을 결정적인 합성 코딩·툴 사용 토큰으로 바꿔치기한다.

Why this is the right abstraction왜 이게 올바른 추상화인가 A serving system does not care what your prompt says. It cares how long it is, and which earlier prompt it shares a prefix with — because that is what decides whether a block is a KV-cache hit or a recompute. Hashing to 64-token blocks throws away the semantics and keeps exactly the property the cache is keyed on. The synthetic tokens then restore realistic length and token mix without restoring any content. It is the smallest thing you can keep that still reproduces the cost. 서빙 시스템은 프롬프트의 내용에 관심이 없다. 길이가 얼마인지, 그리고 앞선 어떤 프롬프트와 프리픽스를 공유하는지에 관심이 있다. 그게 블록이 KV 캐시 히트냐 재계산이냐를 정하기 때문이다. 64토큰 블록으로 해싱하면 의미는 버려지고 캐시가 키로 삼는 성질만 정확히 남는다. 그다음 합성 토큰이 현실적인 길이와 토큰 구성을 복원하되 내용은 복원하지 않는다. 비용을 재현하면서 남길 수 있는 최소한이다.

How accurate is the reconstruction?재구성은 얼마나 정확한가

A median ratio of 1.004 means the replayed request is about 0.4% longer than what the provider actually billed — close enough that length is not the thing distorting your result. Note the honesty of the caption: the shaded band is a distribution, not a guarantee. Individual requests can be further off. 중앙값 1.004 는 재생되는 요청이 공급자가 실제로 청구한 것보다 약 0.4% 길다는 뜻이다. 길이가 결과를 왜곡하는 요인은 아닐 만큼 가깝다. 캡션의 정직함도 눈여겨볼 만하다 — 음영대는 보장이 아니라 분포다. 개별 요청은 더 벗어날 수 있다.

What the client provably cannot see클라이언트가 원리상 볼 수 없는 것

A proxy sits outside the provider. It cannot see provider-side chat templates, proprietary tokenizers, server tools, encrypted reasoning content, or the exact token expansion of images and documents. AgentX approximates those with model-specific padding and deterministic placeholders — and states plainly that the placeholders and padding contain no original prompts, code, or tool payloads. 프록시는 공급자 바깥에 있다. 공급자 쪽 채팅 템플릿, 독자 토크나이저, 서버 툴, 암호화된 추론 콘텐츠, 이미지·문서의 정확한 토큰 전개는 볼 수 없다. AgentX 는 그것들을 모델별 패딩과 결정적 플레이스홀더로 근사하고, 그 패딩·플레이스홀더에 원본 프롬프트·코드·툴 페이로드가 없다고 분명히 밝힌다.

This record is worth reading closely, because it is the entire input to everything downstream. Each request carries a timestamp t, an input count in, an output count out, an api_time, and a hash_ids array. Subagents appear as nested objects with their own agent_id, duration_ms, and request list. That is the whole language — five fields and a nesting rule. 이 레코드는 아래 모든 것의 유일한 입력이라 꼼꼼히 볼 가치가 있다. 요청마다 타임스탬프 t, 입력 수 in, 출력 수 out, api_time, 그리고 hash_ids 배열이 붙는다. 서브에이전트는 자기 agent_id·duration_ms·요청 목록을 가진 중첩 객체로 나타난다. 이게 언어의 전부다 — 필드 다섯 개와 중첩 규칙 하나.

2 The v1.0 dataset, in distributions v1.0 데이터셋을 분포로 보기

The v1.0 release contains 393 sessions built on June 21, 2026. Selection rules: at least 20 requests per session, Claude Code 2.1.139 or newer, no more than 10 concurrent subagents. Processing removes exact duplicates, short classifier calls used for security monitoring or title generation, and requests whose reconstructed input exceeds 990k tokens. v1.0 릴리스는 2026년 6월 21일 기준 393개 세션이다. 선별 규칙 — 세션당 요청 20건 이상, Claude Code 2.1.139 이상, 동시 서브에이전트 10개 이하. 처리 과정에서 완전 중복, 보안 모니터링·제목 생성용 짧은 분류기 호출, 재구성 입력이 990k 토큰을 넘는 요청을 제거한다.

Two variants ship. The full variant keeps contexts up to 1M tokens. The 256k variant drops requests above its cap while retaining the relative timing and subagent overlap of what remains. Both use the WEKA trace format. 변형이 둘이다. full 은 컨텍스트를 1M 토큰까지 유지한다. 256k 는 상한을 넘는 요청을 버리되 남은 요청들의 상대적 타이밍과 서브에이전트 겹침은 유지한다. 둘 다 WEKA trace 포맷을 쓴다.

142,016 in, 444 out입력 142,016, 출력 444 A 320:1 input-to-output ratio at the median. This is the number that should reset your intuition about what an agentic serving system spends its time on. Classic chat benchmarks run somewhere near 1:1 to 10:1. At 320:1 the prefill path, the prefix cache, and the memory that holds it are not one concern among several — they are effectively the entire workload, and the decode path is a rounding error on token count (though not on latency, since those 444 tokens are what the user waits for). 중앙값에서 입력:출력 = 320:1. 에이전트 서빙 시스템이 시간을 어디에 쓰는지에 대한 직관을 이 숫자가 다시 맞춰 준다. 고전적인 채팅 벤치마크는 1:1 에서 10:1 어딘가다. 320:1 에서는 prefill 경로와 프리픽스 캐시, 그리고 그걸 담는 메모리가 여러 관심사 중 하나가 아니라 사실상 워크로드 전부이고, decode 경로는 토큰 수 기준으로는 반올림 오차다 (지연 기준으로는 아니다 — 사용자가 기다리는 게 바로 그 444 토큰이니까).

The 256k variant exists because not every system under test can serve a 1M-token context. Note what capping does to the median: input drops from 142k to 89k, but the ratio is still 236:1. Truncating the tail does not turn this into a normal workload. 256k 변형이 있는 이유는 시험 대상 시스템 전부가 1M 컨텍스트를 서빙할 수 있는 건 아니기 때문이다. 상한이 중앙값에 무엇을 하는지 보라 — 입력이 142k 에서 89k 로 내려가지만 비율은 여전히 236:1 이다. 꼬리를 자른다고 평범한 워크로드가 되지는 않는다.

Fewer than half the sessions (175 of 393) use subagents at all — but when they do, a group runs for 2.27 minutes at the median and 18.5 minutes at p95. That p95 is the number that matters for a serving system: it means a branch of the dependency graph can hold state open for a third of the entire profiling hour. 서브에이전트를 쓰는 세션은 절반이 안 된다(393개 중 175개). 그런데 쓰면 그룹 하나가 중앙값 2.27분, p95 18.5분을 돈다. 서빙 시스템 입장에서 중요한 건 그 p95 다 — 의존성 그래프의 한 가지가 프로파일링 1시간의 3분의 1 동안 상태를 열어 둘 수 있다는 뜻이니까.

3 From trace to replay graph 트레이스에서 리플레이 그래프로

AIPerf converts each trace into a directed acyclic graph. Main-agent requests form a linear chain. Subagent requests form separate chains that spawn after an eligible parent request and join before the next dependent main-agent request. One-off auxiliary requests can run without a join edge. AIPerf 는 트레이스마다 방향성 비순환 그래프를 만든다. 메인 에이전트 요청이 선형 사슬을 이룬다. 서브에이전트 요청은 별도 사슬을 이뤄, 자격을 갖춘 부모 요청 뒤에 spawn 되고 다음 의존 메인 요청 앞에서 join 한다. 일회성 보조 요청은 join 간선 없이 돌 수 있다.

The honest caveat, stated by the authors저자들이 직접 밝힌 단서 The trace contains request timestamps and observed branch IDs — not the tool-level event that caused each branch. So replay preserves recorded ordering, branch overlap, and inter-turn delays without claiming a provider-internal causal history. In other words: the graph is a faithful record of what happened when, not a model of why. That is enough to reproduce load shape, and not enough to reason about agent behaviour. 트레이스에는 요청 타임스탬프와 관측된 분기 ID 가 있을 뿐 각 분기를 유발한 툴 수준 이벤트는 없다. 그래서 재생은 기록된 순서·분기 겹침·턴 간 지연을 보존하되 공급자 내부의 인과 이력을 주장하지 않는다. 달리 말해 그래프는 무엇이 언제 일어났는지의 충실한 기록이지 왜의 모델이 아니다. 부하 모양을 재현하기엔 충분하고, 에이전트 행동을 논하기엔 부족하다.

The graph vocabulary, one shape at a time그래프 어휘를 한 모양씩

The methodology page builds the vocabulary up case by case. Each figure shows the same three panels: the raw trace JSON on the left, the recorded timeline top-right, and the replay dependency graph AIPerf derives from it bottom-right. 방법론 페이지는 이 어휘를 사례별로 쌓아 올린다. 그림마다 같은 세 패널이 나온다 — 왼쪽 원본 트레이스 JSON, 오른쪽 위 기록된 타임라인, 오른쪽 아래 AIPerf 가 유도한 리플레이 의존성 그래프.

What the join gate buys youjoin 게이트가 사주는 것 A join is a barrier: the main chain cannot resume until every branch under that gate finishes. That single rule is what makes the replay load-bearing. If you replayed the same requests without joins, a fast system would simply fire everything at once and you would measure peak batch throughput. With joins, a fast system finishes each branch sooner and arrives at the next barrier earlier — which is exactly how a real agent session speeds up. The barrier is what converts raw speed into session progress, and session progress is the thing users actually feel. join 은 배리어다. 그 게이트 아래 모든 가지가 끝나기 전엔 메인 사슬이 재개되지 않는다. 이 규칙 하나가 재생을 의미 있게 만든다. 같은 요청들을 join 없이 재생하면 빠른 시스템은 전부 한꺼번에 쏴 버리고, 우리는 최대 배치 throughput 을 재게 된다. join 이 있으면 빠른 시스템은 각 가지를 더 빨리 끝내고 다음 배리어에 더 일찍 도착한다 — 실제 에이전트 세션이 빨라지는 방식 그대로다. 배리어가 날속도를 세션 진척으로 환산해 주고, 사용자가 실제로 체감하는 건 세션 진척이다.

4 Concurrency stops meaning what you think 동시성이 생각하던 의미를 잃는다

In AgentX, concurrency is the number of live agent clients. It is not a fixed HTTP request batch, because one client can fan out into several subagent requests. The consequence is stated bluntly on the page: the server can have more in-flight requests than the configured client concurrency. AgentX 에서 동시성은 살아 있는 에이전트 클라이언트 수다. 고정된 HTTP 요청 배치가 아니다. 클라이언트 하나가 여러 서브에이전트 요청으로 갈라질 수 있기 때문이다. 그 결과를 페이지가 직설적으로 적는다 — 서버의 in-flight 요청 수가 설정한 클라이언트 동시성보다 많을 수 있다.

This matters when you compare AgentX numbers with anything else. "Concurrency 50" in a conventional benchmark means 50 requests are in flight. Here it means 50 sessions are alive, and the in-flight count is an emergent, time-varying quantity. Two systems tested at the same client concurrency can be running under quite different instantaneous batch sizes. AgentX 숫자를 다른 것과 비교할 때 이게 중요하다. 일반 벤치마크의 "동시성 50" 은 요청 50개가 in-flight 라는 뜻이다. 여기서는 세션 50개가 살아 있다는 뜻이고, in-flight 수는 시간에 따라 변하는 창발적 값이다. 같은 클라이언트 동시성에서 시험한 두 시스템이 서로 꽤 다른 순간 배치 크기로 돌고 있을 수 있다.

Closed loop — and the confound it creates닫힌 루프 — 그리고 거기서 생기는 교란

AgentX runs closed loop: a client submits its next eligible request after dependencies complete. The page then admits the consequence directly — faster systems progress farther through their sampled sessions during the same hour, so the exact request mix can vary, especially at low concurrency. AgentX 는 닫힌 루프로 돈다. 클라이언트는 의존성이 끝나면 다음 자격 요청을 낸다. 그리고 페이지가 그 결과를 직접 인정한다 — 빠른 시스템은 같은 1시간 동안 샘플된 세션을 더 멀리 진행하므로, 정확한 요청 구성이 달라질 수 있다. 특히 낮은 동시성에서.

This is a real confound, not a footnote이건 각주가 아니라 진짜 교란이다 Two systems measured for the same hour do not process the same set of requests. The faster one gets further into its sessions — and later requests in an agentic session tend to have longer prefixes and higher cache hit rates. So being fast can hand you a slightly easier remaining workload. AgentX's mitigations are the fixed seed, the fixed start range, and the fixed one-hour window, which make a given system's run reproducible; they do not make two different systems' runs identical in content. The right way to read AgentX results is as throughput at an interactivity level, never as a single scalar. 같은 1시간을 잰 두 시스템은 같은 요청 집합을 처리하지 않는다. 빠른 쪽이 세션 안으로 더 깊이 들어가는데, 에이전트 세션의 뒤쪽 요청일수록 프리픽스가 길고 캐시 히트율이 높은 경향이 있다. 즉 빠르다는 것이 남은 워크로드를 조금 더 쉽게 만들어 줄 수 있다. AgentX 의 완화책은 고정 시드·고정 시작 구간·고정 1시간 창이고, 이것들은 한 시스템의 실행을 재현 가능하게 만들지 서로 다른 두 시스템의 실행 내용을 동일하게 만들지는 않는다. AgentX 결과를 읽는 올바른 방법은 어떤 interactivity 수준에서의 throughput 이지, 스칼라 하나가 아니다.

Which is precisely what the page prescribes: results should report throughput with time to first token (TTFT) and interactivity. A single latency value does not describe the run. The Pareto curve is the intended output format. 그리고 그게 정확히 페이지가 처방하는 것이다 — 결과는 throughput 을 TTFT 및 interactivity 와 함께 보고해야 한다. 단일 지연 값으로는 실행을 설명할 수 없다. 파레토 곡선이 의도된 출력 형식이다.

Read the endpoints: from C=1 to C=30 throughput per chip goes from roughly 5k to 42k tok/s — about 8× — while P90 interactivity falls from roughly 333 to 70 tok/s/user, about 4.8× worse. There is no single "performance" number hiding in there; there is a curve, and where you sit on it is a product decision. 양 끝을 보라. C=1 에서 C=30 으로 가면 칩당 throughput 이 약 5k 에서 42k tok/s 로 약 8배 오르고, P90 interactivity 는 약 333 에서 70 tok/s/user 로 약 4.8배 나빠진다. 저 안에 숨은 단일 "성능" 숫자는 없다. 곡선이 있고, 그 위 어디에 앉을지는 제품 결정이다.

Worth noticing — where KV offload turns on눈여겨볼 것 — KV 오프로드가 켜지는 지점 The dashed-circle marker in that chart means KV offload ON, and it appears on exactly the two highest-throughput points, C=20 and C=30. That is the offloading story showing up as a measured artifact rather than an argument: at low concurrency the working set fits in HBM and offload buys nothing, and past some concurrency the only way to keep going up the throughput axis is to put KV somewhere else. 저 차트의 점선 원 표식은 KV 오프로드 ON 이고, 정확히 throughput 이 가장 높은 두 점 C=20·C=30 에만 붙어 있다. 오프로딩 이야기가 주장이 아니라 측정된 흔적으로 나타난 것이다. 동시성이 낮을 땐 워킹셋이 HBM 에 들어가서 오프로드가 사줄 게 없고, 어느 동시성을 넘어서면 throughput 축을 계속 올라가는 유일한 방법이 KV 를 다른 데 두는 것이다.

5 Warmup, timing, determinism 워밍업·타이밍·결정성

If 95% of your token traffic is cache reads, then the state of the cache when the clock starts decides the result. Measure from cold and you are benchmarking prefill. Measure from warm and you are benchmarking the thing the workload actually does. AgentX spends a whole protocol on getting this right. 토큰 트래픽의 95%가 캐시 읽기라면, 시계가 시작될 때 캐시가 어떤 상태인지가 결과를 정한다. 차가운 상태에서 재면 prefill 을 벤치마킹하는 것이고, 데워진 상태에서 재면 이 워크로드가 실제로 하는 일을 재는 것이다. AgentX 는 이걸 제대로 하려고 프로토콜 하나를 통째로 쓴다.

6 Synthetic payloads break speculative decoding — and the fix 합성 페이로드가 speculative decoding 을 깨뜨린다 — 그 해결

Here is a problem that only appears once you have decided to replay with synthetic tokens. Those tokens preserve input length and prefix structure, but their draft-token acceptance does not match natural model output. Speculative decoding works by having a small draft model propose tokens that the big model then accepts or rejects; how many get accepted depends on how predictable the text is. Feed a system deterministic filler and the acceptance rate is an artifact of the filler, not of the serving stack. 합성 토큰으로 재생하기로 정하는 순간에만 생기는 문제가 있다. 합성 토큰은 입력 길이와 프리픽스 구조는 보존하지만 초안 토큰 수용률(draft-token acceptance)은 자연스러운 모델 출력과 다르다. speculative decoding 은 작은 초안 모델이 토큰을 제안하면 큰 모델이 받아들이거나 거부하는 방식이고, 몇 개가 수용되는지는 텍스트가 얼마나 예측 가능한지에 달렸다. 결정적 채움 문자열을 먹이면 수용률은 서빙 스택이 아니라 그 채움 문자열의 산물이 된다.

AgentX's answer: use a measured acceptance length from the coding category of SPEED-Bench, for each model, speculative method, draft length, and thinking mode — and force it. AgentX 의 답 — SPEED-Bench 의 코딩 카테고리에서 실측한 수용 길이를 모델·speculative 방식·초안 길이·thinking 모드별로 가져와 강제한다.

They had to patch four engines to make this comparison possible이 비교가 가능하려면 엔진 넷을 고쳐야 했다 Forced-acceptance controls were merged into SGLang, TensorRT-LLM, vLLM, and ATOM. That is the part of this methodology I find most instructive: a benchmark that wanted to be fair discovered the serving stacks had no way to hold one variable constant, so it went and added one to each of them — upstream, in public, with PR numbers you can read. The stated purpose is exactly right: this separates serving-system performance from acceptance variation caused by the synthetic payload. 강제 수용 제어가 SGLang, TensorRT-LLM, vLLM, ATOM 에 병합됐다. 이 방법론에서 가장 배울 만한 대목이다. 공정해지려던 벤치마크가 서빙 스택들에 변수 하나를 고정할 방법이 없다는 걸 발견하고는, 각각에 그 방법을 직접 추가했다 — 업스트림에, 공개적으로, 읽을 수 있는 PR 번호와 함께. 밝힌 목적도 정확하다. 합성 페이로드가 유발하는 수용률 변동으로부터 서빙 시스템 성능을 분리한다.

7 DRAM offload rules DRAM 오프로드 규칙

KV-cache offload changes the capacity available to long-running sessions — and with a 320:1 input-to-output ratio, capacity is the whole game. So the rules have to be written down, or every vendor picks the DRAM configuration that flatters them. KV 캐시 오프로드는 장시간 세션이 쓸 수 있는 용량을 바꾼다. 입력:출력이 320:1 인 판에서는 용량이 전부다. 그래서 규칙을 명문화하지 않으면 벤더마다 자기에게 유리한 DRAM 구성을 고르게 된다.

Non-standard servers: capped at 3 TB비표준 서버 — 3 TB 상한

Servers without a standardized DRAM configuration are capped, so an unusually fat host cannot buy an advantage that a buyer could not reproduce.표준 DRAM 구성이 없는 서버는 상한이 걸린다. 유별나게 큰 호스트가, 구매자가 재현할 수 없는 이점을 사지 못하게.

Standard systems: installed capacity표준 시스템 — 설치된 용량 그대로

GB200 NVL72, GB300 NVL72, and TPUv7 may use what they ship with, because "what they ship with" is a well-defined thing.GB200 NVL72, GB300 NVL72, TPUv7 은 출하 구성을 그대로 쓸 수 있다. "출하 구성" 이 명확히 정의된 대상이기 때문이다.

The proportional rule is the clever one비례 규칙이 영리하다 A benchmark configuration can access only the fraction of host DRAM proportional to its GPU allocation. Without this, you could take one eighth of a server's GPUs, hand that partition the server's entire host memory, and post a spectacular KV-offload number that nobody running a full node could ever match. It closes the most obvious way to game an offload benchmark. 벤치마크 구성은 자기 GPU 할당량에 비례하는 만큼의 호스트 DRAM 만 쓸 수 있다. 이게 없으면 서버 GPU 의 8분의 1만 떼어 놓고 그 파티션에 서버 전체 호스트 메모리를 몰아준 뒤, 노드를 꽉 채워 돌리는 사람은 결코 낼 수 없는 화려한 KV 오프로드 숫자를 발표할 수 있다. 오프로드 벤치마크를 속이는 가장 뻔한 방법을 막는다.

9 Editor's note 편집자 주

Editor's note — my reading, not SemiAnalysis's claims편집자 주 — SemiAnalysis 의 주장이 아니라 내 독해 Three things I take away.

1. The 95% cache-read number reframes what an inference platform is for. If nineteen out of twenty tokens a serving system touches are re-reads of context it already has, then the platform's core competency is not matrix multiplication throughput — it is keeping a very large amount of KV addressable, cheaply, for a long time. That is a storage-and-fabric problem wearing a compute problem's clothes, and it is exactly why the Pareto chart flips KV offload on at the top of the curve. It also lines up with the Mooncake notes here: a cluster-wide KV pool stops being an optimisation and starts being the substrate.

2. The methodology's best idea is the forced acceptance length. Not because speculative decoding is the most important thing, but because of what it demonstrates: when a variable could not be held constant, they changed the systems under test — upstream, in four engines, in public. Most benchmarks in this space would have added a caveat paragraph instead. It is a higher standard and it is worth naming.

3. The closed-loop confound deserves more attention than it gets. The page discloses it honestly in one sentence, but its implication is structural: faster systems measure a different request mix, and later requests in an agentic session are cheaper per token. That is a mild positive feedback on the reported number, and it is strongest exactly where the curve is most quoted — the low-concurrency, high-interactivity end. It does not invalidate anything; it does mean cross-system deltas at low C should be read with more suspicion than deltas at high C. 가져갈 것 셋.

1. 95% 캐시 읽기라는 숫자가 추론 플랫폼의 정체를 다시 정의한다. 서빙 시스템이 만지는 토큰 스무 개 중 열아홉이 이미 갖고 있는 컨텍스트의 재독이라면, 플랫폼의 핵심 역량은 행렬곱 처리량이 아니라 아주 많은 양의 KV 를 싸게, 오래, 주소 지정 가능한 상태로 유지하는 것이다. 연산 문제의 옷을 입은 스토리지·패브릭 문제이고, 파레토 차트가 곡선 꼭대기에서 KV 오프로드를 켜는 이유가 정확히 그것이다. 이 사이트의 Mooncake 노트와도 맞물린다 — 클러스터 전역 KV 풀이 최적화가 아니라 기반이 되기 시작한다.

2. 이 방법론의 최고 아이디어는 강제 수용 길이다. speculative decoding 이 제일 중요해서가 아니라, 그게 보여 주는 태도 때문이다. 변수를 고정할 수 없자 그들은 시험 대상 시스템 자체를 고쳤다 — 업스트림으로, 엔진 네 개에, 공개적으로. 이 바닥의 대부분의 벤치마크라면 대신 단서 문단 하나를 붙였을 것이다. 더 높은 기준이고, 짚어 둘 가치가 있다.

3. 닫힌 루프 교란은 받는 관심보다 더 받을 만하다. 페이지는 한 문장으로 정직하게 공개하지만 함의는 구조적이다. 빠른 시스템은 다른 요청 구성을 잰다, 그리고 에이전트 세션의 뒤쪽 요청은 토큰당 더 싸다. 보고되는 숫자에 약한 양의 피드백이 걸리는 셈이고, 그게 가장 강하게 작용하는 곳이 하필 곡선에서 가장 많이 인용되는 쪽 — 낮은 동시성, 높은 interactivity 끝이다. 무엇도 무효화하지 않지만, 낮은 C 에서의 시스템 간 차이는 높은 C 에서의 차이보다 더 의심하며 읽어야 한다는 뜻이다.
