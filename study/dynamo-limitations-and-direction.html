one-line summary한 줄 요약 Dynamo (NVIDIA's disaggregated LLM-serving control plane) keeps most of its critical state inside a single process — router affinity, the prefix index, the KV cache. That was fine at one replica; at scale it leaks, scatters sessions, and loses cache on crash. Almost every top limitation is a symptom, and the cure the project is betting on is GMS (GPU Memory Service): externalize KV/state so engines become stateless and restartable. Whether GMS finishes is the single variable that decides Dynamo's trajectory. Dynamo(NVIDIA의 disaggregated LLM 서빙 컨트롤 플레인)는 핵심 상태 대부분을 단일 프로세스 안에 둔다 — 라우터 affinity, prefix 인덱스, KV 캐시. 레플리카 하나일 땐 괜찮았지만, 스케일에서는 새고, 세션이 흩어지고, 크래시 시 캐시를 잃는다. 상위 한계점 거의 전부가 그 증상이고, 프로젝트가 거는 처방은 GMS(GPU Memory Service)다: KV/상태를 프로세스 밖으로 빼 엔진을 스테이트리스·재시작 가능하게. GMS 완주 여부가 Dynamo의 궤적을 가르는 단일 변수다.

📖 Disaggregated serving📖 분산(disaggregated) 서빙

Split prefill and decode onto separate GPU pools so each scales independently; the KV cache must then be handed off between them. Dynamo is a control plane for exactly this.prefill과 decode를 별도 GPU 풀로 분리해 각각 독립 스케일; 그러면 KV 캐시를 둘 사이에 넘겨줘야 한다. Dynamo가 바로 이걸 위한 컨트롤 플레인.

📖 The KV-aware Router📖 KV-aware 라우터

Dynamo's headline feature: route a request to the worker that already holds the most of its prompt's KV (prefix reuse), not just the least-loaded one.Dynamo의 간판 기능: 요청을 단순히 덜 바쁜 워커가 아니라, 그 프롬프트의 KV(prefix)를 이미 가장 많이 가진 워커로 보낸다.

📖 KVBM · NIXL

KVBM = KV Block Manager (tiered offload of KV blocks to host/remote). NIXL = NVIDIA Inference Xfer Library, the cross-node KV transfer layer under disaggregation.KVBM = KV Block Manager(KV 블록을 호스트/원격으로 계층 오프로드). NIXL = NVIDIA Inference Xfer Library, disaggregation 밑의 노드 간 KV 전송 계층.

📖 GMS

GPU Memory Service — an in-flight subsystem that makes KV allocations process-independent (GMS-owned, leased/fenced) so a worker can crash and restart without losing/corrupting its cache. Dynamo's big bet.GPU Memory Service — KV 할당을 프로세스 독립으로 만드는 진행 중 서브시스템(GMS 소유, lease/fencing). 워커가 크래시·재시작해도 캐시를 잃거나 손상하지 않게. Dynamo의 큰 베팅.

📖 Planner + DGDR📖 Planner + DGDR

Planner = SLA-driven autoscaler picking prefill/decode replica counts. DGDR = the Kubernetes custom resource (Dynamo Graph Deployment) that describes a deployment.Planner = prefill/decode 레플리카 수를 정하는 SLA 기반 오토스케일러. DGDR = 배포를 기술하는 쿠버네티스 커스텀 리소스(Dynamo Graph Deployment).

📖 Backends📖 백엔드

Dynamo doesn't run models itself — it wraps vLLM / SGLang / TensorRT-LLM as "worker" engines behind its runtime and router.Dynamo는 모델을 직접 돌리지 않는다 — vLLM / SGLang / TensorRT-LLM을 런타임·라우터 뒤의 "워커" 엔진으로 감싼다.

1 What Dynamo is, and how we read it Dynamo란 무엇이고, 우리가 어떻게 읽었나

Dynamo is NVIDIA's open-source control plane for disaggregated LLM inference: a Rust core (runtime, discovery over etcd/NATS, a KV-cache-aware router) that orchestrates backend engines (vLLM / SGLang / TensorRT-LLM) as workers, moves KV between prefill and decode pools (KVBM + NIXL), autoscales them (Planner), and deploys on Kubernetes (an operator + the DGDR custom resource). It is very active — 7.4K stars, ~800–1,100 PRs/month at peak, 14% of PRs from external contributors.

Dynamo는 NVIDIA의 오픈소스 disaggregated LLM 추론 컨트롤 플레인이다: Rust 코어(런타임, etcd/NATS 기반 디스커버리, KV-aware 라우터)가 백엔드 엔진(vLLM / SGLang / TensorRT-LLM)을 워커로 오케스트레이션하고, prefill↔decode 풀 사이로 KV를 옮기고(KVBM + NIXL), 오토스케일하고(Planner), 쿠버네티스에 배포한다(operator + DGDR 커스텀 리소스). 매우 활발하다 — ⭐7.4K, 피크 월 800~1,100 PR, PR의 14%가 외부 기여자.

The 5 cross-cutting limitations5대 횡단 한계점

1. State is process-local everywhere.상태가 어디나 프로세스-로컬이다. Router affinity lives in an in-process map, so behind a round-robin load balancer multi-turn sessions scatter across replicas and prefix-cache reuse collapses (#11035). The prefix radix tree "splits but never merges," leaking ~20 GB/h to OOM (#10774). KV is engine-owned, so a crash loses or unsafely reuses cache. 라우터 affinity가 in-process 맵에 있어, round-robin LB 뒤에서 멀티턴 세션이 레플리카로 흩어지고 prefix 캐시 재사용이 붕괴한다(#11035). prefix 라딕스 트리는 "split만 하고 merge를 안 해" ~20GB/h 누수로 OOM(#10774). KV는 엔진 소유라 크래시 시 캐시를 잃거나 위험하게 재사용한다.

2. Fault tolerance is bolt-on, not designed-in.Fault tolerance가 설계가 아니라 땜빵이다. A 250K-concurrency post-mortem found a oneshot map that leaks with no timeout, hanging the frontend when workers die mid-queue (#7826). etcd watchers don't resync after reconnect, so dead instances look alive (#11144). CRIU restore breaks NATS/health rebinding (#10664). Failover itself is an unfinished 18-part GMS epic (#11049). 25만 동시성 post-mortem에서 타임아웃 없이 새는 oneshot 맵이 발견돼, 워커가 큐 도중 죽으면 프론트엔드가 영원히 행(#7826). etcd watcher가 재연결 후 resync를 안 해 죽은 인스턴스가 살아 보인다(#11144). CRIU 복원이 NATS/health 재바인딩을 깬다(#10664). failover 자체가 미완성 18단계 GMS 서사시(#11049).

3. Everything external is a moving contract.외부와의 모든 계약이 움직이는 표적이다. Three engines are chased version-by-version and parity is best-effort, not guaranteed — same model passes on vLLM, fails elsewhere (#10106); SGLang drops logprobs (#8548); TRT-LLM has no engine watchdog so a crash leaves a zombie worker (#7535). The CRD churns v1alpha1↔v1beta1 (#10419), and hardware is NVIDIA-hardcoded in the operator (#10716). 엔진 3개를 버전마다 추격하고 parity가 계약이 아닌 best-effort — 같은 모델이 vLLM은 통과, 딴 데선 실패(#10106); SGLang은 logprobs 누락(#8548); TRT-LLM은 엔진 watchdog이 없어 크래시가 좀비 워커를 남긴다(#7535). CRD는 v1alpha1↔v1beta1로 churn(#10419), HW는 operator에 NVIDIA 하드코딩(#10716).

4. The Planner isn't production-trustworthy yet.Planner가 아직 프로덕션 신뢰 불가다. It can't scale down at zero traffic (NaN metrics skip all adjustment, stranding GPUs, #6985); it returns SUCCESS when the deployment is not-ready, silently losing the scale-down (#10525); and it models service time only, ignoring queue/burst latency (#10528). The offline profiler gate is heavy and brittle. 무트래픽에서 스케일다운 불가(NaN 메트릭이 모든 조정을 스킵해 GPU 방치, #6985); 배포가 not-ready인데 SUCCESS 반환해 스케일다운을 조용히 잃음(#10525); service time만 모델링하고 큐/버스트 지연을 무시(#10528). 오프라인 프로파일러 게이트가 무겁고 취약하다.

5. Topology & security debt trails the features.토폴로지·보안 부채가 기능에 뒤처진다. Placement is NUMA/PCI-root-blind, so cross-root NIXL costs ~50% throughput / ~30× latency (#10171). All NATS/TCP transport is plaintext — no TLS/mTLS (#10809). Both are known and scoped, but sit behind the feature rush. 배치가 NUMA/PCI-root를 모른다 → cross-root NIXL이 ~50% 처리량 / ~30× 지연 손실(#10171). 모든 NATS/TCP 전송이 평문 — TLS/mTLS 없음(#10809). 둘 다 인지·스코프됐지만 기능 러시에 밀려 있다.

meta-debt메타 부채 Above the code: Stale marks 186 issues + 630 PRs, and 1,293 PRs are external contributions — inflow exceeds maintainer bandwidth. And the reliability label taxonomy is broken (issues and PRs don't share the vocabulary), which hides how much reliability work is actually happening. 코드 위에서: Stale가 이슈 186 + PR 630개에 붙었고, PR 1,293개가 외부 기여 — 유입이 유지보수 대역폭을 넘는다. 그리고 신뢰성 라벨 체계가 깨져(이슈와 PR이 어휘를 공유 안 함) 실제 신뢰성 작업량이 가려진다.

4 Direction prediction (6–12 months) 방향성 예측 (6~12개월)

Reading what's actively in flight (open + recently-merged PRs), here's where Dynamo is going — ordered by how much it matters.

지금 활발히 진행 중인 것(open + 최근 머지 PR)을 읽으면 Dynamo의 방향은 이렇다 — 중요도 순.

1. GMS is the headline bet.GMS가 핵심 베팅. KV/state leaves the engine process → stateless, restartable workers + fast failover, spanning vLLM/SGLang/TRT-LLM and Intel XPU. If it lands, it fixes limitations #1, #3, half of #7, and much of backend-parity at once. If it slips, Dynamo stays scale-out-fragile. This is the single variable to watch. KV/상태가 엔진 프로세스를 떠남 → 스테이트리스·재시작 가능 워커 + 빠른 failover, vLLM/SGLang/TRT-LLM + Intel XPU 관통. 성공하면 한계점 #1·#3·#7 절반·백엔드 parity 상당수를 한 번에 해결. 밀리면 스케일아웃 취약 유지. 지켜볼 단일 변수.

2. Two deployment modes diverge.배포가 두 갈래로 분화. The full NATS/etcd runtime vs a runtime-free, gateway-native router (Gateway API Inference Extension) for k8s-Gateway shops who don't want Dynamo's control plane. 풀 NATS/etcd 런타임 vs, Dynamo 컨트롤 플레인을 원치 않는 k8s-Gateway 사용자를 위한 런타임-프리 게이트웨이-네이티브 라우터(Gateway API Inference Extension).

3. Contracts formalize.계약이 형식화된다. An engine ABC / OpenEngine RPC to stop per-backend drift; a vendor-agnostic Device spec; a v1beta1-stable CRD. Dynamo is trying to convert its moving targets into interfaces. per-backend 드리프트를 멈출 엔진 ABC / OpenEngine RPC; vendor-agnostic Device 스펙; v1beta1 안정 CRD. 움직이는 표적을 인터페이스로 전환하려는 시도.

4. The Planner grows up via simulation.Planner가 시뮬레이션으로 성숙. Mocker/Replay (GPU-free) validation + queue/latency/power-aware policy move it from best-effort toward advisory → auto-execution. Mocker/Replay(GPU 없는) 검증 + 큐/지연/전력 인지 정책으로 best-effort에서 advisory → 자동 실행으로.

5. Multimodal is the current feature frontier.멀티모달이 현재 기능 프론티어. ≈398 PRs; the next efficiency unlock is a shared vision-embedding cache + encoder-cache-aware routing (so identical images aren't re-encoded per request). ≈398 PR; 다음 효율 언락은 공유 비전 임베딩 캐시 + 인코더-캐시 인지 라우팅(동일 이미지를 요청마다 재인코딩 안 하도록).

5.2 — Our read (editorial, not the repo's claim) 5.2 — 우리 관점 (편집자 주 — 레포의 주장 아님)

editor's note편집자 주 Dynamo is betting that disaggregation's control plane can be a general distributed system (shared KV via GMS, gateway routing, multi-vendor) rather than a tightly-coupled single-engine optimizer. Its biggest risk is execution surface area: it is simultaneously chasing 3 engines, 2+ hardware vendors, a CRD migration, an autoscaler, and a KV-ownership rewrite — with visible maintainer-bandwidth strain (Stale backlog, dead reliability labels). For anyone building or betting on disaggregated serving, the read is simple: the team that finishes state-externalization + failover wins. GMS is Dynamo's answer, and its completion — not any single feature — is what to track. Dynamo는 disaggregation의 컨트롤 플레인을 단일 엔진에 밀착된 최적화기가 아니라 범용 분산 시스템(GMS로 공유 KV, 게이트웨이 라우팅, 멀티벤더)으로 만들 수 있다에 베팅 중이다. 최대 리스크는 실행 표면적: 엔진 3개 + HW 2개 이상 + CRD 마이그레이션 + 오토스케일러 + KV 소유권 재작성을 동시에 추격하며, 유지보수 대역폭 부족이 가시적(Stale 백로그, 죽은 신뢰성 라벨)이다. disaggregated 서빙을 만들거나 베팅하는 입장에서 결론은 단순하다: state 외부화 + failover를 먼저 완성하는 쪽이 이긴다. GMS가 Dynamo의 답이고, 어떤 단일 기능이 아니라 그 완주 여부가 추적할 지표다.
