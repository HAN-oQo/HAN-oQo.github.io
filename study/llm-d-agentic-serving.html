llm-d Agentic Serving — the coding-agent well-lit path, and why it differs from plain LLM serving llm-d Agentic Serving — 코딩 에이전트 well-lit path는 일반 LLM 서빙과 뭐가 다른가

A coding agent resends a huge, mostly-unchanged context (system prompt + repo + history + tool outputs) on every turn — ~160K tokens, ~540 turns, 15 s idle gaps. So the bottleneck isn't FLOPs, it's cache-hit rate: route each turn to the replica that already holds its prefix in KV, and don't recompute the 160K prefill. llm-d's answer is the "Agentic Serving" well-lit path — really a composition of prefix-cache-aware routing + KV offloading + P/D. This note: what a well-lit path is, why agentic differs, the exact optimization knobs, the config/code flow with permalinks, and how to deploy it. 코딩 에이전트는 거의 안 바뀌는 거대한 컨텍스트(시스템 프롬프트 + 레포 + 히스토리 + 도구 출력)를 매 턴 다시 보낸다 — ~16만 토큰, ~540턴, 15초 유휴. 그래서 병목은 FLOPs가 아니라 캐시 적중률: 각 턴을 그 prefix를 이미 KV에 가진 replica로 라우팅하고 16만 prefill을 재계산하지 않는 것. llm-d의 답이 "Agentic Serving" well-lit path — 사실은 prefix-cache-aware 라우팅 + KV offload + P/D의 조합이다. 이 노트: well-lit path란, agentic이 왜 다른가, 정확한 최적화 knob, config/코드 흐름(permalink), 배포법.

one-line summary한 줄 요약 Agentic coding is prefill-heavy + high-locality + bursty: a 160K-token context dominates TTFT, is resent ~540× with high reuse, and goes idle ~15 s between tool calls. The well-lit path optimizes for cache-hit rate, not FLOPs: (1) an EPP scorer that routes by prefix-cache locality (weight 3, above the two load scorers at 2), using either an approximate routing-side LRU index or a precise index fed by vLLM KV-events over ZMQ; (2) KV offloading to host DRAM so an idle session restores instead of re-prefilling; (3) P/D disaggregation so a giant prefill never stalls decode. Naming note: the path is officially "Agentic Serving"; coding agents are its reference workload, not a separate path. Agentic 코딩은 prefill-heavy + 높은 locality + bursty: 16만 토큰 컨텍스트가 TTFT를 지배하고, 높은 재사용으로 ~540회 재전송되며, 도구 호출 사이 ~15초 유휴. well-lit path는 FLOPs가 아니라 캐시 적중률에 최적화: (1) prefix-cache locality로 라우팅하는 EPP scorer(weight 3, 부하 scorer 2보다 높음) — approximate 라우팅측 LRU 인덱스 또는 vLLM KV-events를 ZMQ로 받는 precise 인덱스; (2) 유휴 세션이 재-prefill 대신 복원되도록 KV offload(호스트 DRAM); (3) 거대 prefill이 decode를 막지 않게 P/D 분리. 이름 주의: 공식 명칭은 "Agentic Serving"이고 코딩 에이전트는 별도 path가 아니라 레퍼런스 워크로드.

1What a "well-lit path" is, and why agentic ≠ chat"well-lit path"란, 그리고 agentic ≠ chat인 이유

In llm-d a well-lit path is a documented, tested, benchmarked deployment recipe — not a feature, but "the recommended, cohesive deployment" for a capability, shipped as a router Helm chart + Kustomize model-server overlays + a reference config [guides index]. A workload guide goes one level up: it composes several well-lit paths for a use case. "Agentic Serving" is a workload guide, and its reference workload is coding agents: llm-d에서 well-lit path는 문서화·테스트·벤치된 배포 레시피다 — 기능이 아니라 한 역량에 대한 "권장되는 응집된 배포"이며, router Helm chart + Kustomize 모델서버 overlay + 레퍼런스 config로 제공된다 [guides 인덱스]. workload guide는 한 단계 위다: 한 유스케이스를 위해 여러 well-lit path를 조합한다. "Agentic Serving"이 workload guide이고, 그 레퍼런스 워크로드가 코딩 에이전트다:

"serve long, multi-turn, tool-using agentic workloads (e.g. coding agents) by composing prefix-aware routing, KV-cache offloading, and P/D disaggregation."

— llm-d Agentic Serving guide · guides/agentic-serving/README.md

2The differentiator — a composition, not one feature차별점 — 단일 기능이 아니라 조합

A plain LLM deployment is a model server behind a round-robin/least-load Service. The agentic path keeps the same model servers but changes how requests are routed and how KV is kept, by stacking four capability paths — each mapped to one workload pressure: 일반 LLM 배포는 round-robin/least-load Service 뒤의 모델 서버다. agentic path는 같은 모델 서버를 두되 요청 라우팅 방식과 KV 보존 방식을 바꾼다 — 네 개의 역량 path를 쌓아서, 각각을 하나의 워크로드 압력에 대응시킨다:

Layer (capability path)계층 (역량 path)Relieves which pressure어떤 압력을 해소
Optimized Baseline (prefix + load routing)routes a turn to the replica already holding its prefix; load scorers keep bursts off hot replicas턴을 그 prefix를 가진 replica로; 부하 scorer가 burst를 hot replica에서 분산
Tiered KV Offloading"idle sessions restore on resume instead of recomputing prefill" — the cross-turn reuse for the 15 s gaps"유휴 세션이 prefill 재계산 대신 복원" — 15초 공백의 턴 간 재사용
Precise Prefix-Cache Routingexact global KV-cache view via vLLM KV-events, beyond the approximate LRU guessapproximate LRU 추정을 넘어, vLLM KV-events로 정확한 전역 KV-cache 뷰
P/D Disaggregation"heavy prefill never stalls token generation, stabilizing ITL" (large models / interactivity)"무거운 prefill이 토큰 생성을 멈추지 않게 → ITL 안정"(큰 모델 / 상호작용성)

Reference deploy: Qwen/Qwen3-Coder-480B-A35B-Instruct-FP8, 8 replicas, on Google TPU v7 (tpu7x), TP=8, expert-parallel on. 5How to deploy it배포법

Current deploy model = a llm-d-router Helm chart (OCI) + Kustomize model-server overlays (not the old helmfile/llm-d-deployer). Two steps: 현재 배포 모델 = llm-d-router Helm chart(OCI) + Kustomize 모델서버 overlay(구 helmfile/llm-d-deployer 아님). 2단계:

git clone https://github.com/llm-d/llm-d.git && cd llm-d
export GAIE_VERSION=v1.5.0 NAMESPACE=llm-d-agentic-serving REPO_ROOT=$(git rev-parse --show-toplevel)
kubectl create namespace ${NAMESPACE}
kubectl create secret generic llm-d-hf-token --from-literal="HF_TOKEN=${HF_TOKEN}" -n ${NAMESPACE}

# 1) router / EPP (scorer config comes from the values files, NOT a --config flag)
helm install agentic-serving oci://ghcr.io/llm-d/charts/llm-d-router-standalone-dev \
    -f ${REPO_ROOT}/guides/recipes/router/base.values.yaml \
    -f ${REPO_ROOT}/guides/agentic-serving/router/agentic-workloads.values.yaml \
    -n ${NAMESPACE} --version v0

# 2) model server (Kustomize overlay — here the TPU vLLM overlay)
kubectl apply -n ${NAMESPACE} -k ${REPO_ROOT}/guides/agentic-serving/modelserver/tpu/vllm/

What distinguishes this from a baseline deploy: prefix-cache scorer weighted above load scorers (3 vs 2/2); vLLM run with KV offload + --max-model-len 262144 --block-size 256; 8 replicas, EP, fp8 KV. The EPP scheduler config is passed as Helm values (router.epp.pluginsCustomConfig), not --config-text. Image pins are pre-GA (-dev/:main/v0) and will change. 베이스라인 배포와의 차이: prefix-cache scorer를 부하 scorer 위로(3 vs 2/2); vLLM을 KV offload + --max-model-len 262144 --block-size 256로; 8 replica, EP, fp8 KV. EPP 스케줄러 config는 --config-text가 아니라 Helm values(router.epp.pluginsCustomConfig)로 전달. 이미지 핀은 pre-GA(-dev/:main/v0)라 바뀔 것.

Two cautions for us: (1) the headline numbers are TPU-only and pre-GA — treat as directional; (2) P/D and precise KV-events routing only pay off at multi-replica/multi-node scale (on a single box they add overhead), exactly the boundary we saw with DBO. 이건 우리 Heimdall 작업과 직결된다: 여기 EPP가 바로 우리가 역분석한 inference-scheduler 계열이고, agentic path는 코딩에이전트 워크로드를 위해 "scorer 가중치를 뭘로, 어떤 KV 계층을 조합할지"다. llm-d와 무관하게 가져갈 교훈: agentic/코딩 서빙에선 캐시 적중률이 곧 제품 지표 — 지배 비용이 이미 계산한 16만 컨텍스트의 재-prefill이라, prefix-cache-aware 라우팅 + KV offload가 순수 모델 throughput보다 중요하다. 주의 둘: (1) 대표 수치는 TPU 전용·pre-GA라 방향성으로만; (2) P/D·precise KV-events 라우팅은 멀티 replica/노드 규모에서만 값을 한다(단일 박스에선 오버헤드) — DBO에서 본 그 경계와 같다.
