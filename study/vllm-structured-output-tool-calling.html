vLLM structured output & tool calling — constrain the tokens, parse the text vLLM structured output & tool calling — 토큰을 제약하고, 텍스트를 파싱한다

How vLLM guarantees JSON-schema-valid output, calls tools, and splits a reasoning model's thinking from its answer — a code-walk on the latest main. One idea organizes everything: the sampler divides the work into two planes. Structured/guided output constrains generation at the logit level inside the engine (a per-step token bitmask forcing illegal tokens to −inf); tool & reasoning parsing is pure post-processing of the decoded text in the serving layer. The sections below walk each plane in order; §8 then shows every request type in action, from curl to tokens. Pinned to vLLM commit 34bb795 — see the TOC for the full map. vLLM이 JSON-스키마 유효 출력을 보장하고, 도구를 호출하고, 추론 모델의 생각을 답에서 분리하는 방식을 최신 main 기준으로 추적한 코드워크. 하나의 아이디어가 전부를 꿴다: sampler를 기준으로 작업이 두 평면으로 갈린다. Structured/guided output은 엔진 안에서 logit 레벨로 생성을 제약하고(스텝마다 토큰 bitmask로 불법 토큰을 −inf로), tool & reasoning 파싱은 서빙에서 디코드된 텍스트를 후처리할 뿐이다. 아래 섹션이 두 평면을 차례로 걷고, §8이 모든 요청 타입을 curl부터 토큰까지 실제로 보여준다. vLLM 커밋 34bb795에 핀 고정 — 전체 지도는 목차 참고.

one-line summary한 줄 요약 vLLM does two very different jobs under one banner. (1) Structured output = constrain what token can come next: a grammar/FSM (compiled by xgrammar by default, else guidance/outlines/lm-format-enforcer) emits a packed token bitmask each step; the engine masked_fills disallowed tokens to −inf on the raw logits before the sampler. (2) Tool & reasoning parsing = post-process the generated text: a unified DelegatingParser first splits reasoning (e.g. everything before </think>), then extracts tool calls (regex / JSON / pythonic-AST / structural-tag). tool_choice="required" bridges the two — it builds a JSON schema (or structural tag) from the tools and routes it through structured output so the tool JSON is guaranteed valid. The one thing linking both halves is reasoning_ended: until the model finishes thinking, the engine skips the grammar bitmask and the serving layer stays in the "reasoning" phase. vLLM은 한 깃발 아래 아주 다른 두 일을 한다. (1) Structured output = 다음에 올 수 있는 토큰을 제약: 문법/FSM(기본 xgrammar, 아니면 guidance/outlines/lm-format-enforcer)이 스텝마다 packed 토큰 bitmask를 내고, 엔진이 sampler 전에 raw logit에서 금지 토큰을 −inf로 masked_fill한다. (2) Tool & reasoning 파싱 = 생성된 텍스트를 후처리: 통합 DelegatingParser가 먼저 reasoning을 분리하고(예: </think> 이전 전부), 그다음 tool call을 추출(regex / JSON / pythonic-AST / structural-tag). tool_choice="required"가 둘을 잇는다 — tool들에서 JSON 스키마(또는 structural tag)를 만들어 structured output으로 태워 tool JSON을 보장한다. 두 반쪽을 잇는 단 하나는 reasoning_ended: 모델이 생각을 끝낼 때까지 엔진은 문법 bitmask를 건너뛰고 서빙은 "reasoning" 단계에 머문다.

1The big picture — two planes큰 그림 — 두 평면

The single most clarifying fact: structured output and tool/reasoning parsing live on opposite sides of the sampler. One shapes tokens before they exist; the other interprets text after it's generated. Keep them apart and the whole subsystem falls into place. 가장 명료하게 해주는 사실 하나: structured output과 tool/reasoning 파싱은 sampler의 반대편에 산다. 하나는 토큰이 존재하기 전에 토큰을 빚고, 다른 하나는 생성된 후에 텍스트를 해석한다. 둘을 나누면 전체 서브시스템이 제자리를 찾는다.

Right: tool/reasoning parsers post-process decoded text in the serving layer, after sampling. tool_choice="required" is the bridge (§5). Two consequences worth internalizing up front: (1) structured output cannot fix bad text after the fact — it can only stop illegal tokens from being sampled in the first place, so it needs a grammar that knows the legal next-token set at every step. (2) tool parsing can never guarantee validity on its own — a plain tool_choice="auto" parser just hopes the model emitted parseable markers; the guarantee only appears when a request routes its tools through the structured-output plane (§5). The rest of this note walks the left plane (§2–4), the right plane (§6–7), and the bridge between them (§5). 미리 새겨둘 두 결과: (1) structured output은 나온 텍스트를 사후에 못 고친다 — 애초에 불법 토큰이 sampling되지 않게 막을 뿐이라, 매 스텝의 합법 다음-토큰 집합을 아는 문법이 필요하다. (2) tool 파싱만으론 유효성을 절대 보장 못 한다 — 순수 tool_choice="auto" 파서는 모델이 파싱 가능한 마커를 냈길 바랄 뿐이고, 보장은 요청이 tool들을 structured-output 평면 으로 태울 때만 생긴다(§5). 이 노트의 나머지는 왼쪽 평면(§2–4), 오른쪽 평면(§6–7), 그리고 그 사이의 다리(§5)를 걷는다.

2Structured output — grammar → bitmask → −infStructured output — 문법 → bitmask → −inf

The left plane. A request that asks for JSON-schema-valid output carries a StructuredOutputsParams (one of json / regex / grammar / choice / json_object / structural_tag). The engine turns that spec into a grammar — a per-request state machine that, given the tokens generated so far, can produce the exact set of tokens that keep the output valid. Each decode step, that set becomes a bitmask, and the engine forces every other token's logit to −inf so it can never be sampled. 왼쪽 평면. JSON-스키마 유효 출력을 요구하는 요청은 StructuredOutputsParams(json / regex / grammar / choice / json_object / structural_tag 중 하나)를 지닌다. 엔진은 그 스펙을 문법으로 바꾼다 — 지금까지 생성된 토큰에서 출력을 유효하게 유지하는 토큰 집합을 정확히 낼 수 있는 요청별 상태기계. 매 디코드 스텝, 그 집합이 bitmask가 되고, 엔진은 나머지 모든 토큰의 logit을 −inf로 강제해 sampling되지 못하게 한다.

The grammar fills a bitmask of legal next-tokens; the engine masks all others to −inf on the raw logits; the sampler picks among what's left; the chosen token advances the FSM. Original diagram; per structured_output/__init__.py & gpu_model_runner.py.그림 2 — structured-output 한 스텝. 문법이 합법 다음-토큰 bitmask를 채우고; 엔진이 나머지를 raw logit에서 −inf로 마스킹하고; sampler가 남은 것 중 고르고; 고른 토큰이 FSM을 전진. 직접 작성한 다이어그램; 출처 structured_output/__init__.py & gpu_model_runner.py.

The manager, the backend interface, the apply매니저·백엔드 인터페이스·적용

StructuredOutputManager (one per engine core) compiles the grammar asynchronously on a thread pool and stores a Future on the request, so a slow compile never blocks the engine — the request just waits in a special WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR state until its grammar is ready, and a compile error fails only that one request: StructuredOutputManager(엔진 코어당 하나)는 문법을 스레드풀에서 비동기 컴파일하고 요청에 Future를 저장한다 — 느린 컴파일이 엔진을 막지 않게. 요청은 특별한 WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR 상태로 문법이 준비될 때까지 대기하고, 컴파일 에러는 그 요청 하나만 실패시킨다:

3The 4 backends & auto-fallback4개 백엔드와 auto-fallback

vLLM doesn't write its own grammar engine — it wraps four libraries behind the one interface from §2. The default (backend="auto") tries xgrammar first and falls back to guidance (or outlines for Mistral/unsupported schemas). They differ in which constraint types they support and whether they work with speculative decoding: vLLM은 자체 문법 엔진을 쓰지 않는다 — §2의 단일 인터페이스 뒤로 네 라이브러리를 감싼다. 기본(backend="auto")은 xgrammar를 먼저 시도하고 guidance(또는 Mistral/미지원 스키마엔 outlines)로 fallback한다. 지원 제약 타입과 speculative decoding 호환 여부가 다르다:

4Surviving speculative decoding — validate / advance / rollbackspeculative decoding 견디기 — validate / advance / rollback

Structured output and speculative decoding collide head-on. Spec decode proposes several draft tokens per step and only some survive verification — but the grammar is a stateful FSM that can only be advanced by tokens it's sure about. If you advanced it through a draft that later gets rejected, the FSM would be in the wrong state. vLLM solves this with three grammar operations working together: structured output과 speculative decoding은 정면충돌한다. spec decode는 스텝마다 여러 draft 토큰을 제안하고 일부만 검증을 통과한다 — 그런데 문법은 확실한 토큰으로만 전진할 수 있는 상태기계다. 나중에 거부될 draft로 전진시켰다면 FSM이 잘못된 상태가 된다. vLLM은 세 문법 연산의 협력으로 해결한다:

Fig 4 — Speculative decoding + a grammar. Top: the draft model guesses several tokens; the target verifies them all in one pass and keeps the correct prefix. Bottom: the grammar's FSM is just a position on a state track — it ① validates without moving, ② temp-advances to read each slot's bitmask, ③ rolls back, then ④ commits only the accepted guesses, so a rejected draft can never leave it in the wrong state. Original diagram; per structured_output/__init__.py & scheduler.py.그림 4 — speculative decoding + 문법. 위: draft 모델이 여러 토큰을 추측하고, target이 한 번에 검증해 맞는 prefix만 남긴다. 아래: 문법 FSM은 상태 트랙 위의 위치일 뿐 — ① 이동 없이 검증, ② 각 슬롯 bitmask를 읽으려 임시 전진, ③ rollback, ④ 통과한 추측만 commit해서, 거부된 draft가 FSM을 잘못된 상태로 남기지 못한다. 직접 작성한 다이어그램; 출처 structured_output/__init__.py & scheduler.py.

grammar.rollback(state_advancements)           # undo — drafts aren't confirmed yet

The non-advancing validate_tokens is what lets the scheduler pre-filter drafts against the grammar before they're even scheduled (rejected ones become a −1 sentinel that flips apply_bitmask=False for that slot). The whole dance means a grammar-constrained request gets the full throughput of speculative decoding without ever letting a rejected draft corrupt the FSM. (This has been a real source of subtle bugs — the code cites fixes in PRs #43388 and #44006.) 전진하지 않는 validate_tokens 덕에 스케줄러는 draft가 스케줄되기도 전에 문법으로 미리 걸러낸다(거부된 건 −1 센티널이 되어 그 슬롯의 apply_bitmask=False로). 이 전체 춤 덕에 문법 제약 요청도 speculative decoding의 처리량을 온전히 누리면서 거부된 draft가 FSM을 오염시키지 않는다. (실제로 미묘한 버그의 원천 — 코드가 PR #43388, #44006의 수정을 인용.)

Path B — structural tag. Some models (Mistral, and any parser with a structural_tag_model when VLLM_ENFORCE_STRICT_TOOL_CALLING is on — the default) emit native markers like [TOOL_CALLS]…, so a plain JSON schema doesn't fit. 7Reasoning parsers & the post-processing pipelinereasoning 파서와 후처리 파이프라인

The last piece of the right plane. A reasoning model interleaves its "thinking" with its answer — DeepSeek-R1 wraps thoughts in <think>…</think>, gpt-oss uses Harmony channels, Granite uses English phrases ("Here is my thought process:"). A reasoning parser splits the two so the API can return reasoning_content separately from content. Its core method is deceptively simple: 오른쪽 평면의 마지막 조각. 추론 모델은 "생각"을 답과 섞는다 — DeepSeek-R1은 <think>…</think>로 감싸고, gpt-oss는 Harmony 채널, Granite는 영어 문구("Here is my thought process:"). reasoning 파서가 둘을 분리해 API가 reasoning_content를 content와 따로 반환한다. 핵심 메서드는 의외로 단순하다:

# vllm/reasoning/basic_parsers.py:72  (is_reasoning_end — the <think> family)
for i in range(len(input_ids) - 1, -1, -1):     # scan backwards
    if input_ids[i] == start_token_id: return False   # saw <think> last → still thinking
    if input_ids[i] == end_token_id:   return True    # saw </think> last → done

Now the whole post-processing order. A crucial fact: by the time the serving layer sees output, the text is already detokenized — the V1 engine's OutputProcessor ran an IncrementalDetokenizer (with stop-string handling) upstream. Serving then runs one DelegatingParser that does reasoning-split then tool-extract, in that order: 이제 전체 후처리 순서. 중요한 사실: 서빙이 출력을 볼 때쯤 텍스트는 이미 디코드돼 있다 — V1 엔진의 OutputProcessor가 상류에서 IncrementalDetokenizer(stop-string 처리 포함)를 돌렸다. 서빙은 그다음 하나의 DelegatingParser로 reasoning 분리 그다음 tool 추출을 순서대로 한다:

Grammar masking happens in the engine before sampling; detokenization in the front-end; reasoning-split then tool-parse in serving. reasoning_ended gates both the engine (skip the grammar while thinking) and serving (reasoning phase → tool phase). This reasoning_ended gate is the elegant hinge of the whole subsystem. On the engine side, structured output checks it before ever filling a bitmask — so a JSON-constrained request with a reasoning model thinks in free-form prose and only starts being forced into JSON after </think>: 이 reasoning_ended 게이트가 전체 서브시스템의 우아한 경첩이다. 엔진 쪽에서 structured output은 bitmask를 채우기 전에 이걸 확인한다 — JSON 제약 요청도 추론 모델이면 자유 산문으로 생각하고 </think> 후에야 JSON으로 강제되기 시작한다:

# vllm/v1/structured_output/__init__.py:361  (should_fill_bitmask)

On the serving side, the same signal (is_reasoning_end_streaming) is what flips parse_delta from emitting reasoning to emitting content/tool_calls. One concept, gating both halves. (One caveat: parsers like Granite that split on prose phrases don't implement is_reasoning_end, so they do content-splitting only and can't gate structured output.) 서빙 쪽에선 같은 신호(is_reasoning_end_streaming)가 parse_delta를 reasoning 방출에서 content/tool_calls 방출로 뒤집는다. 하나의 개념이 두 반쪽을 게이팅. (주의: Granite처럼 산문 문구로 나누는 파서는 is_reasoning_end를 구현 안 해서 콘텐츠 분리만 하고 structured output을 게이팅 못 한다.)

When exactly does the answer start? (the token-level boundary)답변은 정확히 언제 시작하나? (토큰 단위 경계)

The gate above is described per-step; zoom into the token stream and the "start point" becomes precise. Two cases — and the key insight is that the grammar never parses or understands the reasoning; it is simply switched off, then woken up right after the model's own end-marker: 위 게이트는 스텝 단위 설명이고, 토큰 스트림으로 확대하면 "시작 지점"이 또렷해진다. 두 경우 — 핵심은 문법이 reasoning을 파싱하거나 이해하는 게 절대 아니라, 그냥 꺼져 있다가 모델 자신의 끝-마커 바로 다음에 깨어난다는 것:

Fig 8 — The token-level start of a constrained answer. "Does the grammar wait until the model types {?" — No. It forces the start; it doesn't detect it."모델이 {를 칠 때까지 문법이 기다리나?" — 아니오. 시작을 강제하지, 감지하지 않는다.

There is no code that watches the output stream for a { and then "switches the grammar on". The grammar produces the { by masking every other token to −inf. The only thing that ever delays the grammar is a reasoning-end marker. So the trigger depends on the mode: 출력 스트림에서 {를 지켜보다가 "문법을 켜는" 코드는 없다. 문법이 다른 토큰을 전부 −inf로 막아 {를 만들어낸다. 문법을 지연시키는 유일한 것은 reasoning-끝 마커. 그래서 트리거는 모드에 따라 다르다:

  "model":"...", "messages":[{"role":"user","content":"Weather in Seoul as JSON."}],
  "response_format": {"type":"json_object"}
}'

Fig 10 — json_object. Same engine, weaker constraint: the grammar only guarantees the output parses as a JSON object; the model decides the keys and values. Use it when you want "valid JSON" but not a fixed shape.그림 10 — json_object. 같은 엔진, 약한 제약: 문법은 출력이 JSON 객체로 파싱되는 것만 보장하고, 키·값은 모델이 정한다. "유효 JSON"은 원하지만 고정 형태는 아닐 때.

3 · guided_regex (match a pattern)

curl .../v1/completions -d '{
  "model":"...", "prompt":"Call me at ",
  "guided_regex": "\\d{3}-\\d{4}"
}'

Fig 11 — guided_regex. The regex compiles to an FSM; every position exposes only its legal character class. The model still chooses among legal characters (which digit), so it's not scripted — just bounded.그림 11 — guided_regex. regex가 FSM으로 컴파일되고, 각 위치는 합법 문자 클래스만 노출. 모델은 합법 문자 중에서(어느 숫자) 여전히 고르므로 각본이 아니라 경계가 지어진 것.

4 · guided_choice (pick one of a list)

curl .../v1/chat/completions -d '{
  "model":"...", "messages":[{"role":"user","content":"Sentiment of: I love it!"}],
  "extra_body": {"guided_choice": ["positive","negative","neutral"]}
}'

Fig 12 — guided_choice. Compiled to an a|b|c grammar. At the first step all three prefixes are legal; the model's pick collapses the choice, and once the prefix is unique the remaining characters are forced. Output is always exactly one of the options.그림 12 — guided_choice. a|b|c 문법으로 컴파일. 첫 스텝엔 세 prefix 모두 합법; 모델의 선택이 분기를 좁히고, prefix가 유일해지면 나머지 문자는 강제. 출력은 항상 옵션 중 정확히 하나.

5 · guided_grammar (EBNF / Lark)

curl .../v1/completions -d '{
  "model":"...", "prompt":"SQL: ",
  "guided_grammar": "root ::= \"SELECT \" col \" FROM \" tbl\n
                     col  ::= \"id\" | \"name\"\n
                     tbl  ::= \"users\" | \"orders\""
}'

Fig 13 — guided_grammar. An EBNF/Lark context-free grammar (only xgrammar & guidance support this). Terminals are forced, nonterminals are choice points — so you can constrain to a whole DSL, not just JSON.그림 13 — guided_grammar. EBNF/Lark 문맥자유문법(xgrammar·guidance만 지원). 종단은 강제, 비종단은 선택 지점 — JSON뿐 아니라 DSL 전체로 제약 가능.

6 · structural_tag (constrain only a region)

curl .../v1/chat/completions -d '{
  "model":"...", "messages":[{"role":"user","content":"Weather in Seoul?"}],
  "extra_body": {"structured_outputs": {"structural_tag": "{...triggers + JSON-schema tags...}"}}
}'

Fig 14 — structural_tag. A grammar that only activates inside a triggered region, leaving surrounding text unconstrained. This is exactly the mechanism behind the strict tool-calling path (§5B) — the model keeps its native markers, but the bytes between them are forced valid.그림 14 — structural_tag. 트리거된 영역 안에서만 활성화되고 주변 텍스트는 제약하지 않는 문법. strict tool-calling 경로(§5B)의 바로 그 메커니즘 — 모델은 고유 마커를 유지하되 그 사이 바이트는 유효로 강제된다.

B. Tool calling — the 4 tool_choice modesB. Tool calling — 4가지 tool_choice 모드

All four use the same tools list; only tool_choice changes. Each pipeline below shows: the request → whether a constraint is applied (the bridge to structured output) → the model's raw generation → the parser → the final tool_calls. The server is assumed started with --enable-auto-tool-choice --tool-call-parser hermes. 넷 다 같은 tools 목록을 쓰고 tool_choice만 바뀐다. 아래 각 파이프라인: 요청 → 제약 적용 여부(structured output로의 다리) → 모델의 raw 생성 → 파서 → 최종 tool_calls. 서버는 --enable-auto-tool-choice --tool-call-parser hermes로 시작했다고 가정.

1 · tool_choice = "auto" (model decides & emits markers)

curl .../v1/chat/completions -d '{
  "model":"...", "messages":[{"role":"user","content":"Weather in Seoul?"}],
  "tools":[{"type":"function","function":{"name":"get_weather",
    "parameters":{"type":"object","properties":{"city":{"type":"string"}}}}}],
  "tool_choice":"auto"
}'

Fig 15 — tool_choice="auto". No constraint is applied; the model freely emits its native tool-call markers and the parser extracts them. Best-effort — the guarantee is only as good as the model's formatting.그림 15 — tool_choice="auto". 제약 없음; 모델이 고유 마커를 자유 방출하고 파서가 추출. best-effort — 보장은 모델 포맷팅 수준에 달림.

2 · tool_choice = "required" (force ≥1 valid call)

curl .../v1/chat/completions -d '{ ...same tools...,
  "tool_choice":"required"
}'

Fig 16 — tool_choice="required". The tools become a JSON-schema array constraint routed through structured output (§5A), so the output is guaranteed-valid and the parse is a one-line validate_json. This is the "auto" pipeline with the left plane switched on.그림 16 — tool_choice="required". tool들이 JSON-스키마 배열 제약이 되어 structured output(§5A)으로 태워지므로 출력은 유효 보장, 파싱은 한 줄 validate_json. "auto" 파이프라인에 왼쪽 평면을 켠 것.

3 · tool_choice = named function (force exactly this tool)

curl .../v1/chat/completions -d '{ ...same tools...,
  "tool_choice":{"type":"function","function":{"name":"get_weather"}}
}'

Fig 17 — named tool_choice. The schema is reduced to the single named tool's parameters, so the model's whole output is the arguments object; the parser re-attaches the (already-known) function name. Exactly one call, guaranteed.그림 17 — named tool_choice. 스키마가 지정된 tool 하나의 parameters로 축소돼 모델 출력 전체가 인자 객체; 파서가 (이미 아는) 함수 이름을 다시 붙인다. 정확히 한 번 호출, 보장.

4 · tool_choice = "none" (never call — plain answer)

curl .../v1/chat/completions -d '{ ...same tools...,
  "tool_choice":"none"
}'
--exclude-tools-when-tool-choice-none controls whether the tool definitions are even shown to the model. Either way, no tool call is produced.

Fig 18 — tool_choice="none". No constraint, no tool extraction; the model just answers in prose. The tool definitions may be withheld from the prompt entirely (a server flag).그림 18 — tool_choice="none". 제약도 tool 추출도 없음; 모델은 산문으로 답할 뿐. tool 정의는 프롬프트에서 아예 제외될 수도(서버 플래그).

Reading the two galleries together두 갤러리를 함께 읽기

The structured-output examples (A) and the required/named tool pipelines (B2, B3) are the same machine: a schema/grammar → a per-step bitmask → guaranteed-valid tokens. The only difference is where the schema comes from — you write it (A) or vLLM derives it from your tools (B). And auto (B1) is the one pipeline that skips the left plane entirely, which is exactly why it's the only one without a guarantee. structured-output 예시(A)와 required/named tool 파이프라인(B2, B3)은 같은 기계다: 스키마/문법 → 스텝별 bitmask → 유효 보장 토큰. 유일한 차이는 스키마의 출처 — 직접 쓰거나(A) vLLM이 tools에서 파생(B). 그리고 auto(B1)만 왼쪽 평면을 건너뛰는 유일한 파이프라인이라, 그래서 유일하게 보장이 없다.

Editor's note — our take (not a vLLM claim)편집자 주 — 우리 관점 (vLLM의 주장 아님)

This subsystem is exactly the compatibility surface an OpenAI/Anthropic-compatible gateway (our heimdall / AIGateway work) has to reproduce, so three things are worth flagging. (1) The tool-JSON "guarantee" is not in the parser — it's in structured output. If a gateway claims tool_choice="required" support but doesn't route the tools through a grammar backend, it's really doing best-effort auto and will occasionally emit malformed tool calls under load; the honest coverage question is "which backend, and does it fall back?", not "do you parse tool calls?". (2) The 42-parser zoo is the real compatibility cost. Per-model tool syntax (Hermes XML vs Llama pythonic vs Mistral [TOOL_CALLS] vs Harmony channels) means "supports tool calling" is per-model, not a single feature — matching vLLM's model coverage means shipping (or reusing) that many parsers, and the streaming partial-JSON diffing is where subtle client-visible bugs hide. (3) The reasoning_ended gate is a correctness requirement, not a nicety — for a reasoning model, applying a JSON grammar during the chain-of-thought would force the thinking into JSON and destroy quality; any gateway that adds structured output in front of a reasoning model must replicate this gate. For MI250/vLLM serving specifically, note the grammar bitmask is cheap host+one-kernel work off the attention hot path, but the async compile pool and xgrammar cache (VLLM_XGRAMMAR_CACHE_MB) are the things to watch under a flood of distinct schemas. 이 서브시스템은 OpenAI/Anthropic 호환 게이트웨이(우리 heimdall / AIGateway 작업)가 그대로 재현해야 하는 호환 표면이라, 셋을 짚는다. (1) tool-JSON "보장"은 파서가 아니라 structured output에 있다. 게이트웨이가 tool_choice="required"를 지원한다면서 tool을 문법 백엔드로 태우지 않으면 사실상 best-effort auto이고 부하 시 가끔 깨진 tool call을 낸다; 정직한 커버리지 질문은 "tool call 파싱하냐?"가 아니라 "어느 백엔드고, fallback 하냐?"다. (2) 42개 파서 동물원이 진짜 호환 비용. 모델별 tool 문법(Hermes XML vs Llama pythonic vs Mistral [TOOL_CALLS] vs Harmony 채널)이라 "tool calling 지원"은 단일 기능이 아니라 모델별이다 — vLLM 모델 커버리지를 맞추려면 그만큼의 파서를 내야 하고, 스트리밍 부분-JSON 디핑에 미묘한 클라이언트 버그가 숨는다. (3) reasoning_ended 게이트는 편의가 아니라 정확성 요건 — 추론 모델에 chain-of-thought 동안 JSON 문법을 적용하면 생각을 JSON으로 강제해 품질을 파괴한다; 추론 모델 앞에 structured output을 붙이는 게이트웨이는 이 게이트를 반드시 재현해야 한다. MI250/vLLM 서빙 관점에선, 문법 bitmask는 어텐션 핫패스 밖 값싼 호스트+커널 한 번 작업이지만, 서로 다른 스키마가 폭주할 땐 async 컴파일 풀과 xgrammar 캐시(VLLM_XGRAMMAR_CACHE_MB)를 주시해야 한다.
