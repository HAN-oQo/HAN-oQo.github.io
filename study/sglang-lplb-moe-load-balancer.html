SGLang LPLB: a linear-programming load balancer for MoE expert parallelism SGLang LPLB: MoE expert parallelism을 위한 선형계획 부하 분산기

Commit 92b42c8 (PR #24515) ports DeepSeek's LPLB ("Linear-Programming-Based Load Balancer") into SGLang as --ep-dispatch-algorithm lp. Every MoE layer solves a tiny linear program on a single GPU SM to split token load across expert replicas so the busiest GPU is as light as possible. This note covers the mechanism and the code flow pinned to 92b42c8. Heads-up: this is MoE expert-parallel load balancing, not context parallelism. 커밋 92b42c8(PR #24515)은 DeepSeek의 LPLB("Linear-Programming-Based Load Balancer")를 SGLang의 --ep-dispatch-algorithm lp로 포팅한다. 매 MoE 레이어마다 GPU SM 하나에서 작은 선형계획을 풀어 토큰 부하를 expert 복제본들에 나누고, 가장 바쁜 GPU를 최대한 가볍게 만든다. 이 노트는 메커니즘과 92b42c8에 핀된 코드 흐름을 정리한다. 주의: MoE expert-parallel 부하 분산이며 context parallelism과는 별개다.

one-line summary한 줄 요약
  • Under EP, a MoE step ends when the busiest GPU ends, and routing skew makes one GPU busy.
  • EPLB replicates hot experts (static placement). LPLB adds the per-batch layer: a small linear program each MoE forward spreads load across replicas to minimize the max GPU load.
  • SGLang PR #24515 ports DeepSeek's on-GPU LP solver (single-SM interior-point, cuBLASDx/cuSolverDx) behind --ep-dispatch-algorithm lp.
  • Caveats: LPLB was written for training; SGLang applies it to inference. NVIDIA-only (cuBLASDx/MathDx), opt-in, model allowlist, and the PR's speedup is an n=3 self-bench with p>0.05 (not statistically significant).
  • expert parallelism에서 MoE 스텝은 가장 바쁜 GPU가 끝나야 끝난다. 라우팅이 쏠리면 GPU 하나만 바빠진다.
  • EPLB는 hot expert를 복제한다(정적 배치). LPLB는 매 MoE forward마다 작은 선형계획을 풀어 복제본 간 분배를 정하고 최대 GPU 부하를 줄인다.
  • SGLang PR #24515는 DeepSeek의 on-GPU LP solver(single-SM interior-point, cuBLASDx/cuSolverDx)를 --ep-dispatch-algorithm lp로 포팅했다.
  • 단서: LPLB는 학습용으로 만들어졌고 SGLang은 추론에 쓴다. NVIDIA 전용(cuBLASDx/MathDx), opt-in, 모델 allowlist 한정이다. PR의 속도 수치는 n=3 셀프벤치이며 p>0.05(통계적으로 유의하지 않음)다.

1The problem: the MoE straggler, and why EPLB isn't enough문제: MoE straggler와 EPLB만으로 부족한 이유

A MoE router picks a few experts per token. Under expert parallelism the experts live on different GPUs, so each layer ships tokens to their experts (all-to-all dispatch), runs the expert FFNs, and ships results back (combine). A collective finishes at the pace of the slowest participant. If routing is uneven, one GPU's expert GEMMs run longer and the rest idle at the combine barrier. MoE 라우터는 토큰마다 expert 몇 개를 고른다. expert parallelism에선 expert가 서로 다른 GPU에 있어서, 매 레이어가 토큰을 expert 쪽으로 보내고(all-to-all dispatch) expert FFN을 돌린 뒤 결과를 가져온다(combine). 집합통신은 가장 느린 참여자 속도로 끝난다. 라우팅이 고르지 않으면 한 GPU의 expert GEMM이 길어지고, 나머지 GPU는 combine 배리어에서 기다린다.

A concrete skew example구체적 쏠림 예시

Assume 256 experts over 8 GPUs (32 each), top-8 routing. Perfectly balanced, each GPU handles 1/8 of routed tokens. If one GPU's experts draw ~2× the average, its GEMMs take ~2× as long and the whole MoE layer runs at that pace: about 2× slower than the balanced ideal, with 7 GPUs partly idle. (Illustrative; the factor depends on the skew.) 256개 expert를 8 GPU에 32개씩 두고 top-8 라우팅을 한다고 하자. 완벽히 고르면 GPU마다 라우팅된 토큰의 1/8을 처리한다. 한 GPU의 expert가 평균의 ~2× 토큰을 받으면 그 GPU의 GEMM도 ~2× 걸리고, MoE 레이어 전체가 그 속도로 돈다. 균형 상태보다 약 2× 느리고 7개 GPU는 일부 시간을 논다. (예시 수치이며, 배수는 쏠림 정도에 따라 다르다.)

EPLB: duplicate the hot experts (the static fix)EPLB: hot expert 복제 (정적 해법)

DeepSeek's EPLB (Expert-Parallel Load Balancer) gives heavy experts more than one home. DeepSeek의 EPLB(Expert-Parallel Load Balancer)는 무거운 expert를 여러 GPU에 두는 방식으로 이 문제를 푼다.

"we adopt a redundant experts strategy that duplicates heavy-loaded experts" … "we heuristically pack the duplicated experts to GPUs to ensure load balancing across different GPUs."

— DeepSeek EPLB README · github.com/deepseek-ai/EPLB

EPLB fixes this placement ahead of time from historical statistics. It helps the long-run average but can't react to the batch in front of you: routing fluctuates, and a placement tuned for the average can still be lopsided now. LPLB fills that residual, dynamic gap. EPLB는 과거 통계로 배치를 미리 정한다. 장기 평균에는 도움이 되지만 지금 들어온 배치에는 반응하지 못한다. 라우팅은 배치마다 출렁이므로 평균에 맞춘 배치도 이번 배치에선 쏠릴 수 있다. LPLB는 이 남은 동적 불균형을 메운다.

Fig 1 · A MoE all-to-all step finishes at the busiest GPU's pace. Schematic.그림 1 · MoE all-to-all 스텝은 가장 바쁜 GPU 속도로 끝난다. 개략도.

2What LPLB is: balancing as a linear program, solved on one SMLPLB: 부하 분산을 SM 하나에서 푸는 선형계획으로

LPLB is an open-source DeepSeek project that extends EPLB into the dynamic, per-batch regime. LPLB는 EPLB를 동적 per-batch 영역으로 확장한 DeepSeek 오픈소스 프로젝트다.

"LPLB is a parallel load balancer that leverages linear programming to optimize expert parallel workload distribution."

— DeepSeek LPLB README · github.com/deepseek-ai/LPLB

Given EPLB's replicas, LPLB asks for the current batch: what fraction of each logical expert's tokens should go to each physical copy so the most-loaded GPU is as light as possible? It writes this min-max problem ("every token is placed", "each replica's capacity") as a linear program and solves it with an interior-point ("barrier") method. The SGLang kernel header states the formulation and its origin. EPLB 복제본이 주어지면 LPLB는 현재 배치에 대해 묻는다. 각 논리 expert의 토큰을 물리 복제본들에 어떤 비율로 보내야 가장 바쁜 GPU가 가장 가벼워질까? "모든 토큰 배치"와 "복제본 용량" 제약 아래 최대 부하를 최소화하는 이 문제를 선형계획으로 쓰고 interior-point("barrier") 방법으로 푼다. SGLang 커널 헤더에 공식과 출처가 적혀 있다.

"min c^T x subject to A x = b, x >= 0 with a barrier method … Adapted from DeepSeek-AI/LPLB's minilp.cu."

— SGLang jit_kernel/csrc/lplb/ipm.cuh (PR #24515) · ipm.cuh §L1-18 @ 92b42c8

The LP is solved on the GPU, on a single SM, every MoE layer, every batch. DeepSeek's README calls it a "single-SM Interior Point Method (IPM)" that "leverages NVIDIA's cuSolverDx and cuBLASDx libraries" [LPLB README]. The balancer sits on the hot path before every MoE dispatch, so it must be nearly free (the SGLang port replaces a slower Numba/nvmath-python implementation). An LP solve that costs about a small kernel launch is what makes per-batch balancing affordable. 이 LP는 GPU의 SM 하나에서, 매 MoE 레이어·매 배치마다 풀린다. DeepSeek README는 이를 "single-SM Interior Point Method (IPM)"라 부르고 "NVIDIA의 cuSolverDx와 cuBLASDx 라이브러리를 활용"한다고 쓴다 [LPLB README]. 분산기는 매 MoE dispatch 직전의 hot path에 있어서 지연이 거의 없어야 한다(SGLang 포트는 Numba/nvmath-python 기반의 느린 이전 구현을 대체한다). LP 한 번이 작은 커널 런치 정도 시간에 끝나야 per-batch 분산이 수지가 맞는다.

Fig 2 · LPLB's per-batch loop. Source: SGLang eplb/lplb_solver.py @ 92b42c8; DeepSeek LPLB README.그림 2 · LPLB의 per-batch 루프. 출처: SGLang eplb/lplb_solver.py @ 92b42c8, DeepSeek LPLB README.

3What this commit (#24515) does: porting LPLB into SGLang이 커밋(#24515)이 하는 일: LPLB를 SGLang에 포팅

Commit 92b42c8 ("LPLB: linear-programming load balancer for MoE expert parallelism", PR #24515) is a 19-file, +2,324-line change that brings DeepSeek's solver into SGLang's serving runtime. It has two halves. 커밋 92b42c8("LPLB: linear-programming load balancer for MoE expert parallelism", PR #24515)는 19개 파일, +2,324줄 규모로 DeepSeek 솔버를 SGLang 서빙 런타임에 들여온다. 크게 두 부분이다.

  • The solver (new JIT CUDA kernels) under jit_kernel/csrc/lplb/: ipm.cuh (interior-point LP solver), lp_prep.cuh / lp_post.cuh (build LP inputs / read the solution into log2phy_prob), dispatch_probability.cuh (per-token dispatch), plus the Python wrapper cuda_solver.py and a pure-torch reference torch_solver.py. 솔버(새 JIT CUDA 커널): jit_kernel/csrc/lplb/ 아래의 ipm.cuh(interior-point LP 솔버), lp_prep.cuh/lp_post.cuh(LP 입력 구성, 해를 log2phy_prob로 변환), dispatch_probability.cuh(per-token dispatch로 변환). Python 래퍼 cuda_solver.py와 순수 torch 레퍼런스 torch_solver.py도 있다.
  • The serving integration under srt/: the LPLBSolver host class, a new "lp" dispatch path, routing hooks in the MoE top-k layer, per-layer solver init in the model runner, and the --ep-dispatch-algorithm lp flag. 서빙 통합: srt/ 아래의 LPLBSolver 호스트 클래스, 새 "lp" dispatch 경로, MoE top-k 레이어의 라우팅 훅, model runner의 레이어별 솔버 init, --ep-dispatch-algorithm lp 플래그.
the subtle part: every rank must solve, even an empty one미묘한 지점: 빈 rank도 반드시 풀어야 한다 Each EP rank all-reduces its local token counts and solves the same LP, so every rank gets the identical answer with no leader or broadcast. An all-reduce is a collective: if any rank skips it, the others hang. A rank with zero tokens would normally skip the MoE math, so the commit makes the empty path still call solve() just to join the all-reduce. A hard model allowlist (DeepSeek-V2/V3/V3.2, GLM, Mistral-Large-3) refuses models that might not reach the collective under DP-attention and could deadlock. 각 EP rank는 로컬 토큰 카운트를 all-reduce한 뒤 같은 LP를 푼다. 리더나 broadcast 없이 모든 rank가 같은 답을 얻는다. all-reduce는 집합통신이라 rank 하나라도 빠지면 나머지가 멈춘다. 토큰을 0개 받은 rank는 보통 MoE 연산을 건너뛰므로, 커밋은 빈 경로에서도 solve()를 호출해 all-reduce에 참여시킨다. 또 모델 allowlist(DeepSeek-V2/V3/V3.2, GLM, Mistral-Large-3)를 두어, DP-attention에서 집합통신에 도달하지 못해 deadlock이 날 수 있는 모델은 거부한다.

Not context parallelismcontext parallelism 아님

This commit touches zero CP machinery: no cp_size, no ring/all-to-all attention, no sequence sharding. Its only new collective is an EP-group all-reduce of token counts inside solve(). Coming from the CP roadmap (#21788)? This is a different subsystem (MoE EP load balancing).이 커밋은 CP 장치를 전혀 건드리지 않는다. cp_size, ring/all-to-all 어텐션, 시퀀스 샤딩 모두 없다. 추가되는 집합통신은 solve() 안의 EP-group 토큰 카운트 all-reduce뿐이다. CP 로드맵(#21788)에서 왔다면 이건 다른 서브시스템(MoE EP 부하 분산)이다.

Status: merged into SGLang (PR #24515); opt-in, NVIDIA-only, model-allowlisted. It replaces an earlier Numba/nvmath-python solver with JIT-CUDA for hot-path speed. It ports DeepSeek's open-source LPLB (MIT), which has no paper; the README is the primary source. 상태: SGLang에 머지됐다(PR #24515). opt-in이고 NVIDIA 전용이며 모델 allowlist가 있다. hot path 속도를 위해 이전 Numba/nvmath-python 솔버를 JIT-CUDA 솔버로 바꿨다. DeepSeek 오픈소스 LPLB(MIT)의 포트이고 논문은 없어서 README가 1차 출처다.

honesty: the speedup is not statistically significant, and the framing differs정직하게: 속도 향상은 통계적으로 유의하지 않고 전제도 다르다
  1. The PR's own benchmark is an n=3 self-bench with p>0.05, not statistically significant. Don't quote its headline speedup as a real gain.
  2. DeepSeek built LPLB for training ("dynamic load imbalance in MoE training", "small-batch randomness during training" [LPLB README]). Inference has different per-batch routing and latency budgets, so training results don't transfer automatically.
  3. No published isolated measurement of LPLB's effect on at-scale inference exists. The objective (minimizing max load) is sound; the magnitude of the win is unquantified as of this commit.
  1. PR 자체 벤치는 n=3 셀프벤치이고 p>0.05라서 통계적으로 유의하지 않다. 여기서 나온 속도 향상을 실제 이득처럼 인용하면 안 된다.
  2. DeepSeek은 LPLB를 학습용으로 만들었다("MoE 학습의 동적 부하 불균형", "학습 중 small-batch 무작위성" [LPLB README]). 추론은 per-batch 라우팅 분포와 지연 예산이 달라서 학습 결과가 그대로 옮겨오지 않는다.
  3. 대규모 추론에서 LPLB 단독 효과를 따로 잰 공개 자료는 없다. 최대 부하 최소화라는 목적은 타당하지만, 이득의 크기는 이 커밋 시점에 정량화되지 않았다.
editor's note: our angle (not a DeepSeek/SGLang claim)편집자 주: 우리 관점 (DeepSeek/SGLang 주장 아님)
  1. In our MI250 lab the solver is not runnable: it JIT-compiles against NVIDIA cuBLASDx/cuSolverDx with no ROCm path.
  2. The problem still bites any wide-EP MoE deployment: the all-to-all combine waits on the straggler. The DBO note already showed EP all-to-all dominating at scale. DBO hides the all-to-all behind compute, while EPLB+LPLB shrink the imbalance behind it.
  3. Mental model: EPLB = static placement (where the replicas live), LPLB = dynamic per-batch routing (how this batch's tokens fill them).
  4. On AMD we'd need an equivalent balancer. The LP-on-GPU trick is NVIDIA-specific, but the objective and EPLB-style redundant-expert placement are portable.
  1. 우리 MI250 랩에선 이 솔버를 돌릴 수 없다. NVIDIA cuBLASDx/cuSolverDx로 JIT 컴파일하고 ROCm 경로가 없다.
  2. 그래도 LPLB가 노리는 문제는 wide-EP MoE 배포라면 피할 수 없다. all-to-all combine은 straggler를 기다린다. DBO 노트에서 EP all-to-all이 스케일에서 지배적이라는 것을 이미 봤다. DBO는 all-to-all을 연산 뒤에 숨기고, EPLB+LPLB는 그 원인인 쏠림 자체를 줄인다.
  3. 두 층으로 기억하면 된다. EPLB = 정적 배치(복제본이 어디 사는가), LPLB = 동적 per-batch 라우팅(이 배치의 토큰이 그걸 어떻게 채우는가).
  4. AMD에선 동등한 분산기가 필요하다. LP-on-GPU 트릭은 NVIDIA 한정이지만 목적함수와 EPLB식 중복 expert 배치는 이식할 수 있다.
