SGLang LPLB — a linear-programming load balancer for MoE expert parallelism SGLang LPLB — MoE expert parallelism을 위한 선형계획 부하 분산기

The commit you asked about (92b42c8, PR #24515) ports DeepSeek's LPLB ("Linear-Programming-Based Load Balancer") into SGLang as a new expert-parallel dispatch algorithm, --ep-dispatch-algorithm lp. The problem it attacks: in a Mixture-of-Experts model spread across GPUs (expert parallelism), token routing is skewed — some experts are "hot" — so the GPU holding the busiest experts becomes a straggler that the whole all-to-all step waits on. DeepSeek's EPLB already fixes the static part by duplicating hot experts onto multiple GPUs. LPLB fixes the dynamic, per-batch part: every MoE layer it solves a tiny linear program on a single GPU SM (an interior-point method built on NVIDIA cuBLASDx/cuSolverDx) to decide, given those replicas, how to split each token's load across copies so the busiest GPU is as light as possible. Heads-up: this is MoE expert-parallel load balancing — it is not context parallelism (a separate topic). This note: the why, the mechanism, what this commit changes, the code flow with permalinks pinned to 92b42c8, usage, and an honest read of its (statistically insignificant) self-benchmark. 질문하신 커밋(92b42c8, PR #24515)은 DeepSeek의 LPLB("Linear-Programming-Based Load Balancer", 선형계획 기반 부하 분산기)를 SGLang에 새 expert-parallel dispatch 알고리즘 --ep-dispatch-algorithm lp로 포팅한 것이다. 노리는 문제: MoE 모델을 여러 GPU에 펼치면(expert parallelism) 토큰 라우팅이 치우쳐 — 일부 expert가 "hot" — 가장 바쁜 expert를 가진 GPU가 straggler가 되어 all-to-all 스텝 전체가 그걸 기다린다. DeepSeek의 EPLB는 hot expert를 여러 GPU에 복제해 정적 부분을 이미 해결한다. LPLB는 동적인 per-batch 부분을 해결한다: 매 MoE 레이어마다 GPU SM 하나에서 작은 선형계획(NVIDIA cuBLASDx/cuSolverDx 기반 interior-point)을 풀어, 그 복제본들에 각 토큰의 부하를 어떻게 나눠야 가장 바쁜 GPU가 최대한 가벼워지는지 결정한다. 주의: 이건 MoE expert-parallel 부하 분산이지 context parallelism이 아니다(별개 주제). 이 노트: 왜·메커니즘·이 커밋이 바꾸는 것·92b42c8에 핀된 permalink 코드 흐름·사용법, 그리고 (통계적으로 유의하지 않은) 셀프벤치의 정직한 해석.

1The problem — the MoE straggler, and why EPLB isn't enough문제 — MoE straggler, 그리고 EPLB만으론 부족한 이유

In a Mixture-of-Experts layer, a router picks a few experts per token. With expert parallelism the experts live on different GPUs, so each layer ships tokens to wherever their experts are (an all-to-all dispatch), runs the expert FFNs, and ships results back (combine). The catch: a collective finishes at the pace of the slowest participant. If routing is uneven, one GPU's experts get a flood of tokens, that GPU's expert GEMMs take longer, and every other GPU sits idle at the combine barrier waiting for it. MoE 레이어에선 라우터가 토큰마다 expert 몇 개를 고른다. expert parallelism에선 expert가 서로 다른 GPU에 있으므로, 매 레이어가 토큰을 해당 expert가 있는 곳으로 보내고(all-to-all dispatch), expert FFN을 돌리고, 결과를 가져온다(combine). 함정: 집합통신은 가장 느린 참여자 속도로 끝난다. 라우팅이 고르지 않으면 한 GPU의 expert에 토큰이 몰리고, 그 GPU의 expert GEMM이 더 오래 걸리며, 나머지 GPU는 combine 배리어에서 그걸 기다리며 논다.

A concrete skew example구체적 쏠림 예시

Assume 256 experts over 8 GPUs (32 each), top-8 routing, a batch of tokens. If the load were perfectly even each GPU would handle 1/8 of the routed tokens. But real routing concentrates — say one GPU's experts draw ~2× the average while others are under-loaded. Its expert GEMMs take ~2× as long, and since the layer can't finish until the all-to-all combine returns from all ranks, the whole MoE layer runs at roughly the straggler's pace — about 2× slower than the balanced ideal, with 7 GPUs partly idle. (Assumptions illustrative; the exact factor depends on the skew.) 256개 expert를 8 GPU에 (각 32개), top-8 라우팅, 토큰 배치 가정. 부하가 완벽히 고르면 각 GPU가 라우팅된 토큰의 1/8을 처리. 그러나 실제 라우팅은 집중된다 — 예컨대 한 GPU의 expert가 평균의 ~2× 토큰을 끌고 나머지는 덜 받는다. 그 GPU의 expert GEMM이 ~2× 오래 걸리고, 레이어는 all-to-all combine이 모든 rank에서 돌아와야 끝나므로 MoE 레이어 전체가 대략 straggler 속도로 — 균형 이상 대비 약 2× 느리게, 7개 GPU는 부분적으로 유휴. (수치는 예시; 정확한 배수는 쏠림 정도에 따름.)

EPLB: duplicate the hot experts (the static fix)EPLB: hot expert 복제 (정적 해법)

DeepSeek's EPLB (Expert-Parallel Load Balancer) addresses this by giving heavy experts more than one home: DeepSeek의 EPLB(Expert-Parallel Load Balancer)는 무거운 expert에 거처를 둘 이상 주어 이를 해결한다:

"we adopt a redundant experts strategy that duplicates heavy-loaded experts" … "we heuristically pack the duplicated experts to GPUs to ensure load balancing across different GPUs."

— DeepSeek EPLB README · github.com/deepseek-ai/EPLB

EPLB decides this placement ahead of time from historical/average statistics — it's a static map of which logical expert is replicated where. That helps the long-run average, but it can't react to the specific batch in front of you right now: routing fluctuates batch to batch, and a placement tuned for the average can still be lopsided for this batch. That residual, dynamic imbalance is exactly the gap LPLB fills. EPLB는 이 배치를 과거/평균 통계로부터 미리 정한다 — 어느 논리 expert가 어디에 복제되는지의 정적 지도다. 장기 평균엔 도움되지만, 지금 눈앞의 특정 배치엔 반응하지 못한다: 라우팅은 배치마다 출렁이고, 평균에 맞춘 배치도 이 배치엔 여전히 한쪽으로 쏠릴 수 있다. 그 잔여 동적 불균형이 바로 LPLB가 메우는 빈자리다.

2What LPLB is — balancing as a linear program, solved on one SMLPLB란 — 부하 분산을 선형계획으로, SM 하나에서

LPLB is an open-source DeepSeek project that extends EPLB into the dynamic, per-batch regime: LPLB는 EPLB를 동적 per-batch 영역으로 확장한 오픈소스 DeepSeek 프로젝트다:

"LPLB is a parallel load balancer that leverages linear programming to optimize expert parallel workload distribution."

— DeepSeek LPLB README · github.com/deepseek-ai/LPLB

Given EPLB's replicas (each logical expert may have several physical copies on different GPUs), LPLB asks, for the batch in hand: what fraction of each logical expert's tokens should go to each of its physical copies, so that the most-loaded GPU is as light as possible? That is a textbook optimization — minimize the maximum load subject to "every token is placed" and "each replica's capacity" constraints — and LPLB writes it as a linear program and solves it with an interior-point ("barrier") method. The SGLang port transcribes DeepSeek's solver; its kernel header states the formulation and its origin verbatim: EPLB의 복제본(각 논리 expert가 서로 다른 GPU에 물리 복제본 여럿)을 전제로, LPLB는 눈앞의 배치에 대해 묻는다: 각 논리 expert의 토큰을 그 물리 복제본들에 어떤 비율로 보내야 가장 부하 큰 GPU가 최대한 가벼워지나? 이건 교과서적 최적화 — "모든 토큰 배치"와 "각 복제본 용량" 제약 하에 최대 부하 최소화 — 이고, LPLB는 이를 선형계획으로 적어 interior-point("barrier") 방법으로 푼다. SGLang 포트는 DeepSeek 솔버를 옮겼고, 커널 헤더가 공식과 출처를 그대로 적는다:

"min c^T x subject to A x = b, x >= 0 with a barrier method … Adapted from DeepSeek-AI/LPLB's minilp.cu."

— SGLang jit_kernel/csrc/lplb/ipm.cuh (PR #24515) · ipm.cuh §L1-18 @ 92b42c8

The striking engineering choice: this LP is solved on the GPU, on a single SM, every MoE layer, every batch. DeepSeek's README describes it as a "single-SM Interior Point Method (IPM)" that "leverages NVIDIA's cuSolverDx and cuBLASDx libraries" [LPLB README]. Why so exotic? Because the balancer sits on the hot path — it must run before every MoE dispatch with negligible latency (the SGLang port replaces a slower prior implementation that used Numba/nvmath-python). A whole LP solve that finishes in roughly the time of a small kernel launch is what makes per-batch balancing affordable at all. 인상적인 엔지니어링 선택: 이 LP를 GPU에서, SM 하나에서, 매 MoE 레이어, 매 배치 푼다. DeepSeek README는 이를 "single-SM Interior Point Method (IPM)"로, "NVIDIA의 cuSolverDx와 cuBLASDx 라이브러리를 활용"한다고 설명한다 [LPLB README]. 왜 이렇게까지? 부하 분산기가 hot path에 있기 때문 — 매 MoE dispatch 전에 무시할 만한 지연으로 돌아야 한다(SGLang 포트는 Numba/nvmath-python을 쓰던 더 느린 이전 구현을 대체한다). 작은 커널 런치 정도 시간에 끝나는 LP 풀이가 per-batch 분산을 비로소 감당 가능하게 만든다.

3What this commit (#24515) does — porting LPLB into SGLang이 커밋(#24515)이 하는 일 — LPLB를 SGLang에 포팅

Commit 92b42c8 ("LPLB: linear-programming load balancer for MoE expert parallelism", PR #24515) is a 19-file, +2,324-line change that brings DeepSeek's solver into SGLang's serving runtime. It splits into two halves: 커밋 92b42c8("LPLB: linear-programming load balancer for MoE expert parallelism", PR #24515)는 19파일·+2,324줄 변경으로, DeepSeek 솔버를 SGLang 서빙 런타임에 들여온다. 두 부분으로 나뉜다:

  • The solver (new JIT CUDA kernels) under jit_kernel/csrc/lplb/ — ipm.cuh (the interior-point LP solver), lp_prep.cuh / lp_post.cuh (build LP inputs / read the solution into log2phy_prob), dispatch_probability.cuh (turn it into per-token dispatch) — plus the Python wrappers cuda_solver.py and a pure-torch reference torch_solver.py. 솔버(새 JIT CUDA 커널) — jit_kernel/csrc/lplb/ 아래 ipm.cuh(interior-point LP 솔버), lp_prep.cuh/lp_post.cuh(LP 입력 구성 / 해를 log2phy_prob로 읽기), dispatch_probability.cuh(per-token dispatch로 변환) — 그리고 Python 래퍼 cuda_solver.py와 순수 torch 레퍼런스 torch_solver.py.
  • The serving integration under srt/ — the LPLBSolver host class, a new "lp" dispatch path, the routing hooks in the MoE top-k layer, per-layer solver init in the model runner, and the --ep-dispatch-algorithm lp flag. 서빙 통합 — srt/ 아래 LPLBSolver 호스트 클래스, 새 "lp" dispatch 경로, MoE top-k 레이어의 라우팅 훅, model runner의 레이어별 솔버 init, 그리고 --ep-dispatch-algorithm lp 플래그.
the subtle part — every rank must solve, even an empty one미묘한 지점 — 빈 rank도 반드시 풀어야 한다 LPLB needs the global token-per-expert counts, so each EP rank all-reduces its local counts and then solves the same LP — no leader, no broadcast, every rank computes the identical answer. The trap: an all-reduce is a collective, so every rank must call it or the others hang forever. A rank that happens to receive zero tokens this step would normally skip the MoE math entirely — so the commit makes the empty path still call solve() (on an empty problem) purely to participate in the all-reduce. There is also a hard model allowlist (DeepSeek-V2/V3/V3.2, GLM, Mistral-Large-3): models outside it would not reliably reach the collective under DP-attention and could deadlock, so they're refused. LPLB는 전역 expert별 토큰 카운트가 필요하므로, 각 EP rank가 로컬 카운트를 all-reduce한 뒤 같은 LP를 푼다 — 리더도 broadcast도 없이 모든 rank가 동일 답을 계산. 함정: all-reduce는 집합통신이라 모든 rank가 호출해야 하고 안 그러면 나머지가 영원히 멈춘다. 이번 스텝에 토큰을 0개 받은 rank는 보통 MoE 연산을 통째로 건너뛰는데 — 그래서 커밋은 빈 경로도 (빈 문제로) solve()를 호출해 오직 all-reduce에 참여하게 한다. 또한 강한 모델 allowlist(DeepSeek-V2/V3/V3.2, GLM, Mistral-Large-3)가 있다: 이 밖의 모델은 DP-attention 하에서 집합통신에 확실히 도달하지 못해 deadlock 가능 → 거부.

6Effects & status — read the benchmark carefully효과 & 상태 — 벤치마크를 주의해서

Status: merged into SGLang (PR #24515), opt-in, NVIDIA-only, model-allowlisted. The SGLang version replaces an earlier Numba/nvmath-python solver with the JIT-CUDA one for speed on the hot path. It is a port of DeepSeek's open-source LPLB (MIT), which has no accompanying paper — the README is the primary source. 상태: SGLang에 머지됨(PR #24515), opt-in, NVIDIA 전용, 모델 allowlist. SGLang 판은 hot path 속도를 위해 이전 Numba/nvmath-python 솔버를 JIT-CUDA로 대체. DeepSeek 오픈소스 LPLB(MIT)의 포트이며 논문은 없다 — README가 1차 출처.

honesty — the speedup is not statistically significant, and the framing differs정직 — 속도 향상은 통계적으로 유의하지 않고, 전제도 다르다 (1) The PR's own benchmark is an n=3 self-bench with p>0.05 — i.e. it did not reach statistical significance. Do not quote a headline speedup from it as a real gain. (2) DeepSeek built LPLB for training ("dynamic load imbalance in MoE training", "small-batch randomness during training" [LPLB README]); SGLang applies it to inference, where the per-batch routing distribution and latency budget differ — the training results don't transfer automatically. (3) There is no published isolated measurement of LPLB's standalone effect on inference throughput/latency at scale. The mechanism is sound (minimizing max load is the right objective); the magnitude of the win in inference is, as of this commit, unquantified. (1) PR 자체 벤치는 n=3 셀프벤치로 p>0.05 — 즉 통계적 유의성에 도달하지 못했다. 거기서 나온 헤드라인 속도 향상을 실제 이득으로 인용하지 말 것. (2) DeepSeek은 LPLB를 학습용으로 만들었다("MoE 학습의 동적 부하 불균형", "학습 중 small-batch 무작위성" [LPLB README]); SGLang은 이를 추론에 적용하는데, per-batch 라우팅 분포와 지연 예산이 달라 학습 결과가 자동으로 옮겨오지 않는다. (3) 대규모 추론에서 LPLB 단독의 처리량/지연 효과를 분리 측정한 공개 자료는 없다. 메커니즘은 타당하나(최대 부하 최소화는 옳은 목적), 추론에서의 이득 크기는 이 커밋 기준 정량화되지 않았다.
editor's note — our angle (not a DeepSeek/SGLang claim)편집자 주 — 우리 관점 (DeepSeek/SGLang 주장 아님) For our MI250 lab the LP solver is not runnable — it JIT-compiles against NVIDIA cuBLASDx/cuSolverDx, with no ROCm path. But the problem LPLB targets is exactly the one that bites any wide-EP MoE deployment we'd build: the all-to-all combine waits on the straggler, and a hot expert wastes the whole step. We've already noted that EP all-to-all dominates at scale in the DBO note; LPLB is the complementary lever — DBO hides the all-to-all behind compute, EPLB+LPLB shrink the imbalance that makes the all-to-all (and the expert GEMMs) uneven in the first place. The two-layer mental model is worth keeping: EPLB = static placement (where the replicas live), LPLB = dynamic per-batch routing (how this batch's tokens fill them). On AMD we'd need an equivalent balancer; the LP-on-GPU trick is NVIDIA-specific, but the objective and the EPLB-style redundant-expert placement are portable ideas. 우리 MI250 랩에선 이 LP 솔버를 돌릴 수 없다 — NVIDIA cuBLASDx/cuSolverDx로 JIT 컴파일하고 ROCm 경로가 없다. 그러나 LPLB가 노리는 문제는 우리가 만들 wide-EP MoE 배포를 정확히 괴롭히는 것: all-to-all combine이 straggler를 기다리고, hot expert 하나가 스텝 전체를 낭비한다. EP all-to-all이 스케일에서 지배적이란 건 DBO 노트에 이미 적었다; LPLB는 보완 지렛대다 — DBO는 all-to-all을 연산 뒤에 숨기고, EPLB+LPLB는 애초에 all-to-all(과 expert GEMM)을 불균형하게 만드는 쏠림 자체를 줄인다. 두 층 모델을 기억할 만하다: EPLB = 정적 배치(복제본이 어디 사는가), LPLB = 동적 per-batch 라우팅(이 배치의 토큰이 그걸 어떻게 채우는가). AMD에선 동등한 분산기가 필요하다; LP-on-GPU 트릭은 NVIDIA 한정이지만, 목적함수와 EPLB식 중복-expert 배치는 이식 가능한 아이디어다.
