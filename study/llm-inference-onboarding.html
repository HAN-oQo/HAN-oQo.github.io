Foundations of LLM Inference

LLM을 한 번 호출했을 때 안에서 무슨 일이 일어나는지 설명할 수 있다. 여기 개념은 뒤 섹션 전부에서 쓰이므로 대충 넘기면 B3 이후가 막힌다.

B1-1서술형

"대한민국의 수도는"이라는 프롬프트를 보내 "서울입니다."라는 응답을 받았다. 요청이 들어온 순간부터 응답이 끝날 때까지, 서버 안에서 일어나는 일을 순서대로 설명하라.

  • 텍스트가 모델에 들어가기 전에 무엇으로 바뀌는가?
  • 모델의 한 번의 forward pass는 무엇을 출력하는가? "다음 토큰"은 그 출력에서 어떻게 정해지는가?
  • 토큰이 여러 개 생성되려면 forward pass를 몇 번 돌아야 하는가? 왜 한 번에 다 못 만드는가?
  • 언제 생성이 멈추는가?
정답 · 채점 포인트
  1. Tokenization: tokenizer(BPE 등)가 텍스트를 정수 ID 시퀀스로 바꾼다. 이때 chat template이 시스템/유저 역할 마커를 붙인다. "몇 토큰짜리 요청인가"가 여기서 정해지고, 이것이 뒤의 모든 비용을 좌우한다.
  2. Embedding: embedding table이 각 토큰 ID를 d_model 차원 실수 벡터로 바꾼다.
  3. Forward pass: 전체 시퀀스가 N개의 transformer block을 통과하고, 마지막에 LM head(d_model → vocab_size)를 거쳐 각 위치마다 vocab 크기의 logits을 낸다. 실제로 쓰는 것은 마지막 위치의 logits 하나뿐이다.
  4. Sampling: 그 logits에 temperature / top-p / top-k를 적용해 확률분포로 만들고 토큰 하나를 뽑는다. greedy면 argmax를 고른다. 모델은 문장이 아니라 "다음 토큰 1개의 확률분포"만 출력한다.
  5. Autoregressive loop: 뽑은 토큰을 입력 뒤에 붙여 다시 forward한다. 다음 토큰은 이전 토큰에 조건부이므로 병렬화가 불가능하다. 출력이 T개면 forward도 T번 돈다.
  6. 종료: EOS 토큰이 샘플링되거나, max_tokens에 도달하거나, stop string에 걸리거나, 클라이언트가 연결을 끊으면 멈춘다.
  7. Detokenization: 생성된 토큰 ID를 텍스트로 복원해 반환한다(스트리밍이면 조각 단위로).
이 키워드가 나와야 통과
  • 모델의 출력은 "다음 토큰 1개의 확률분포(logits)"라는 점
  • 출력 토큰 수만큼 forward를 반복한다는 점 (autoregressive)
  • 그래서 생성은 본질적으로 순차적이라는 점
B1-2서술형

위 과정을 prefill과 decode의 두 단계로 나눈다.

  • 각 단계는 정확히 무엇을 하는가? 입력 텐서의 shape가 어떻게 다른가?
  • 한쪽은 compute-bound, 다른 쪽은 memory-bound라고 한다. 어느 쪽이 어느 쪽이며, 왜 그런가?
  • 프롬프트 2,000토큰 / 출력 200토큰인 요청에서, 각 단계는 forward를 몇 번 도는가?
정답 · 채점 포인트

Prefill: 프롬프트 전체를 한 번의 forward로 처리해 (a) 첫 출력 토큰의 logits과 (b) 프롬프트 전 구간의 KV cache를 만든다. 입력 shape는 [batch, prompt_len, d_model]이다. 프롬프트의 모든 토큰이 동시에 들어가 GEMM이 크고, GPU 연산 유닛이 포화된다. 그래서 compute-bound다.

Decode: 토큰을 하나씩 생성한다. 입력 shape는 [batch, 1, d_model]이다. 이전 토큰의 K·V는 캐시에서 읽으므로 새로 계산할 것은 토큰 1개분뿐이다. 수십 GB의 weight와 KV cache를 HBM에서 전부 읽어 와서 토큰 1개에 대한 연산만 한다. 연산량에 비해 읽을 바이트가 압도적으로 많으므로 memory-bound(정확히는 memory-bandwidth-bound)다.

같은 weight인데 단계에 따라 병목이 정반대라는 사실이 LLM 서빙 설계 결정 대부분의 출발점이다(B3에서 숫자로 확인한다).

Forward 횟수

Prefill 1번(2,000토큰을 한꺼번에), decode 199번으로 총 200번이다. 첫 토큰은 prefill이 만들기 때문에 decode step은 199번이다.

이 키워드가 나와야 통과
  • prefill = 병렬 처리 가능한 큰 GEMM → compute-bound
  • decode = 토큰당 weight 전체를 읽음 → memory-bandwidth-bound
  • "decode는 GPU 연산 유닛이 놀고 있다"는 감각
B1-3서술형

KV cache를 아예 쓰지 않고 구현했다고 하자. 매 decode step마다 지금까지의 전체 시퀀스를 다시 forward에 넣는 방식이다.

  • 결과(생성되는 텍스트)는 달라지는가?
  • T개의 토큰을 생성할 때, 총 연산량은 KV cache를 쓸 때와 비교해 어떤 차수로 커지는가?
  • KV cache는 결국 무엇과 무엇을 맞바꾸는 것인가?
  • Q(query)는 왜 캐시하지 않는가?
정답 · 채점 포인트

결과는 동일하다. KV cache는 수학적으로 동등한 결과를 주는 순수한 재연산 제거이며 근사(approximation)가 아니다. fp 누적 순서 차이로 생기는 비트 단위 차이는 별개 문제다.

연산량: 캐시가 없으면 t번째 step에서 길이 t의 시퀀스를 통째로 다시 계산한다. 총합 1+2+…+T = O(T²). 캐시가 있으면 각 step이 O(1)(새 토큰 1개분)이므로 총 O(T)다. 선형 대 제곱의 차이이고, T가 커질수록 격차가 벌어진다.

맞바꾸는 것: 메모리를 써서 연산을 산다. 그 대가로 GPU 메모리에 KV cache가 계속 쌓이고(B1-6에서 계산), 이 메모리가 곧 동시 처리 가능한 요청 수의 상한이 된다(B5-5). LLM 서빙 최적화의 상당수는 이 캐시를 아끼고, 재사용하고, 어디에 둘지의 문제다.

Q를 캐시하지 않는 이유: attention은 현재 토큰의 Q가 과거 전부의 K·V를 참조하는 구조다. 과거 토큰의 Q는 그 토큰을 계산할 때 한 번 쓰이고 다시는 필요 없다. 반면 K·V는 앞으로 생성될 모든 토큰이 계속 참조한다(B2-2에서 다시 다룬다).

B1-4서술형

다음 지표를 각각 정의하고, 어느 단계(prefill/decode)에 지배되는지 밝혀라.

  • TTFT (Time To First Token)
  • ITL (Inter-Token Latency). TPOT라고도 부른다
  • E2E latency
  • Throughput. 이 지표는 왜 두 종류(요청 단위 / 토큰 단위)로 나뉘는가?

사용자가 "응답이 느리다"고 불평할 때, 어떤 질문을 되물어야 어느 지표를 봐야 할지 알 수 있는가?

정답 · 채점 포인트
  • TTFT: 요청 도착부터 첫 토큰이 클라이언트에 닿을 때까지의 시간으로, 큐 대기 + prefill + 첫 샘플링이다. prefill이 지배하며 프롬프트 길이에 비례해 커진다. 사용자는 스트리밍 UI의 "반응성"으로 느낀다.
  • ITL / TPOT: 연속한 두 출력 토큰 사이의 간격, 즉 decode step 1회의 시간이다. decode가 지배하며 프롬프트 길이가 아니라 모델 크기·배치 크기·메모리 대역폭에 좌우된다. 사용자는 "글자가 흘러나오는 속도"로 느낀다.
  • E2E latency: 요청 시작부터 마지막 토큰까지의 시간이다. 근사적으로 TTFT + ITL × (출력토큰수 − 1)이다.
  • Throughput: 단위 시간당 처리량이다. requests/s는 서비스 용량 관점이고(요청 길이가 제각각이면 비교가 왜곡된다), output tokens/s는 GPU가 실제로 한 일 관점이다. 둘을 구분하지 않으면 "짧은 요청만 잔뜩 처리해서 RPS가 높아 보이는" 벤치마크에 속는다. 보통 output tok/s와 total(in+out) tok/s를 함께 본다.
되물어야 할 질문
  • "첫 글자가 늦게 나오나요, 아니면 나오기 시작한 뒤가 느린가요?": 전자면 TTFT(prefill·큐), 후자면 ITL(decode).
  • "프롬프트가 긴가요?": TTFT 문제라면 프롬프트 길이 / prefix cache 히트 여부를 먼저 본다.
  • "항상 느린가요, 특정 시간대만인가요?": 후자면 개별 요청 지연이 아니라 큐 대기(부하) 문제다. 이때는 latency가 아니라 throughput과 큐 깊이를 봐야 한다.
이 키워드가 나와야 통과
  • TTFT↔prefill, ITL↔decode의 대응
  • TTFT는 프롬프트 길이에, ITL은 프롬프트 길이에 (거의) 무관하다는 점
  • throughput을 토큰 단위로 봐야 한다는 점
B1-5서술형

batch size를 1 → 8 → 64로 키운다고 하자.

  • throughput(output tok/s)과 개별 요청의 ITL은 각각 어떻게 변하는가? 왜 그런가? (B1-2의 답과 연결하라)
  • batch를 무한정 키우지 못하게 막는 것은 무엇인가? (두 가지 이상)
  • "latency SLO를 지키면서 throughput을 최대화하라"는 요구가 실제로 어떤 튜닝 문제가 되는지 한 문장으로 설명하라.
정답 · 채점 포인트

Throughput은 거의 선형으로 오른다. decode는 memory-bound라서 batch 1이면 GPU 연산 유닛이 대부분 논다. weight를 HBM에서 한 번 읽는 비용은 batch가 1이든 64든 같으므로, 한 번 읽어 64개 요청의 토큰을 함께 계산하면 읽기 비용이 64개로 나뉜다. batching이 LLM 서빙에서 그토록 잘 듣는 이유다.

ITL은 처음엔 거의 안 늘다가, 어느 지점부터 늘기 시작한다. memory-bound 구간에서는 batch를 키워도 step 시간이 별로 안 늘지만(무료 점심), arithmetic intensity가 ridge point를 넘어 compute-bound가 되면 그때부터는 batch에 비례해 step 시간이 늘어난다(B3-4에서 그 지점을 계산한다). 또 attention 부분은 KV cache를 읽어야 하므로 시퀀스가 길면 batch에 따라 비용이 곧바로 늘어난다.

batch를 막는 것
  • KV cache 메모리: 실제로 가장 흔한 상한이다. 요청 × 컨텍스트 길이에 비례해 늘고, GPU 메모리를 넘으면 더 담지 못한다(B5-5에서 계산).
  • Latency SLO: batch가 커지면 ITL이 늘어 개별 사용자 체감이 나빠진다.
  • compute 포화: ridge point를 넘으면 더 키워도 throughput 이득이 줄어든다.
  • activation 메모리와 큐 대기 시간도 제약이다(들어온 요청을 배치에 태우려 기다리면 TTFT가 늘어난다).

튜닝 문제로서: ITL(또는 TTFT) p99가 SLO를 넘지 않는 선에서 최대 배치 크기와 KV 메모리 배분을 찾는 문제, 즉 SLO를 제약조건으로 둔 배치 크기 탐색이다. 실무에서는 max_num_seqs, max_num_batched_tokens, gpu_memory_utilization을 이 목적으로 조정한다.

B1-6계산형

Llama-3-8B를 bf16으로 서빙한다. KV cache 크기를 손으로 계산하라.

Given
  • layers = 32, num_attention_heads = 32, num_key_value_heads = 8 (GQA), head_dim = 128
  • dtype = bf16 (2 bytes)
  1. 토큰 1개의 KV cache는 몇 바이트인가? 공식부터 세우고 대입하라.
  2. 컨텍스트 8,192토큰짜리 요청 1개는 몇 GiB인가?
  3. 그런 요청을 32개 동시에 처리하면? H100 80GB 한 장에서 weight(16GiB)와 함께 올릴 수 있는가?
  4. 만약 이 모델이 GQA가 아니라 MHA(KV head도 32개)였다면 3번의 답은 어떻게 바뀌는가?
정답 · 채점 포인트
KV bytes/token = 2 (K와 V) × layers × num_kv_heads × head_dim × dtype_bytes
  1. 토큰 1개
    2 × 32 × 8 × 128 × 2 B = 131,072 B = 128 KiB / token
    Llama-3-8B는 토큰당 128 KiB로 외워 두면 편하다.
  2. 8,192토큰 1개
    128 KiB × 8,192 = 1,048,576 KiB = 1 GiB
    이 모델에서 8K 컨텍스트는 정확히 1 GiB다.
  3. 32개 동시
    1 GiB × 32 = 32 GiB weight 16 GiB + KV 32 GiB = 48 GiB < 80 GB
    올라간다. 여유 ~30GiB로 activation·CUDA graph·framework overhead를 감당하고 배치를 더 키울 여지도 있다.
  4. MHA였다면: num_kv_heads가 8 → 32이므로 KV가 4배.

  • prefix cache 히트를 모르고 측정: 같은 프롬프트를 반복하면 두 번째부터 prefill이 거의 공짜가 되어 TTFT가 뚝 떨어진다. 순수 prefill을 재려면 --random-*처럼 매번 다른 프롬프트를 쓰거나 --no-enable-prefix-caching으로 끈다(B4-6).
  • 클라이언트가 병목: 단일 파이썬 프로세스로 동시성을 크게 주면 클라이언트 쪽이 먼저 막혀 서버 성능을 과소평가하게 된다.
  • 평균만 보기: p50만 보지 말고 p99를 함께 봐라. 배치가 커질수록 꼬리가 길어진다.

B2-2서술형

self-attention을 Attention(Q,K,V) = softmax(QKᵀ/√d)·V라고 쓴다.

  • Q, K, V가 각각 무슨 역할인지, 수식이 아니라 말로 설명하라.
  • decode step 하나에서 Q, K, V의 shape는 각각 무엇인가? (batch=1, 이미 t개 토큰이 처리된 상태)
  • 왜 K와 V만 캐시하고 Q는 캐시하지 않는가? B1-3에서 답한 것을 이번엔 shape로 설명하라.
  • KV cache에 RoPE를 적용한 K를 저장하는가, 적용 전 K를 저장하는가? 왜인가?
정답 · 채점 포인트
  • Q (query): "지금 이 토큰이 무엇을 찾고 있는가"로, 검색어에 해당한다.
  • K (key): "각 토큰이 스스로를 어떻게 광고하는가"로, 색인에 해당한다. Q와의 내적이 곧 관련도 점수다.
  • V (value): "그 토큰이 실제로 전달할 내용"으로, 점수로 가중평균되어 나간다.

QKᵀ가 "무엇을 볼지"를 정하고, ·V가 본 것을 실제로 가져온다.

decode 1 step의 shape (batch=1, 기존 t 토큰, GQA 8 kv-head)
Q : [1, 32, 1, 128] ← 새 토큰 1개분만 K : [1, 8, t+1, 128] ← 캐시에서 읽은 t개 + 새로 계산한 1개 V : [1, 8, t+1, 128] scores = Q·Kᵀ : [1, 32, 1, t+1] ← 새 토큰이 과거 전체를 훑는다

여기에 답이 그대로 들어 있다. Q는 seq 축의 길이가 항상 1이다. 매 step 새로 계산되고 그 step에서만 쓰인 뒤 버려진다. 반면 K·V는 seq 축이 t+1로 계속 자라고, 앞으로의 모든 step이 이를 다시 읽는다. 캐시는 다시 쓸 것을 저장하는 곳이므로 K·V만 저장한다. 과거 토큰의 Q는 저장해도 아무도 읽지 않는다.

RoPE 적용 후의 K를 저장한다

RoPE는 절대 위치에만 의존하는 회전이므로, 토큰이 자기 위치에서 한 번 회전되고 나면 그 값은 이후에 바뀌지 않는다. 미리 적용해 저장하면 매 step 재적용을 아낄 수 있다. 반대로 캐시 블록을 다른 위치에서 재사용하려는 경우처럼 위치가 바뀔 수 있는 구조에서는 이 선택이 제약이 된다. prefix cache가 접두사, 즉 위치가 보존되는 구간에서만 재사용되는 이유도 여기에 있다(B4-6).

이 키워드가 나와야 통과
  • Q의 seq 길이는 1, K·V는 t+1로 자란다는 것을 shape로 설명
  • "미래의 모든 step이 과거의 K·V를 다시 읽는다"
B2-3서술형

causal(autoregressive) mask에 대해 답하라.

  • 무엇을 막는가? 구현상으로는 어떻게 하는가?
  • 이 mask를 제거하면 학습된 모델의 추론 결과가 어떻게 되는가? 왜인가?
  • prefill과 decode에서 mask의 모양이 어떻게 다른가? decode에서는 mask가 필요한가?
  • Decoder-only 모델과 encoder-only 모델(BERT류)의 차이를 mask 관점에서 한 문장으로 정리하라.
정답 · 채점 포인트

무엇을 막는가: 위치 i의 토큰이 j > i인 미래 토큰을 보지 못하게 한다. 구현은 softmax 직전 score 행렬의 상삼각 영역에 −inf(실제로는 dtype의 최소값)를 더해, softmax 후 그 자리의 가중치가 0이 되게 하는 것이다. 0이 아니라 −inf를 더한다는 점이 핵심이다. 0을 더하면 그 자리가 "점수 0인 정상 후보"가 되어 오히려 미래를 보게 된다.

제거하면: 학습 때와 추론 때의 조건이 어긋나 출력이 망가진다. 학습은 "미래를 못 본다"는 전제로 이뤄졌으므로, 추론에서 미래를 보게 하면 입력이 학습 분포 밖으로 나간다. 게다가 KV cache와 근본적으로 충돌한다. causal이기 때문에 "이미 계산한 K·V는 앞으로도 안 변한다"가 성립하고, 그래서 캐시가 유효하다. 양방향이면 토큰이 하나 추가될 때마다 과거 토큰들의 표현까지 전부 다시 계산해야 하므로 KV cache 자체가 불가능해진다.

decode에서는 causal mask가 사실상 필요 없다. 새 토큰은 정의상 가장 마지막 위치이므로 볼 수 있는 것이 곧 전부다. 다만 배치 안에서 길이가 서로 다른 시퀀스를 함께 처리할 때의 padding mask는 여전히 필요하다(PagedAttention을 쓰면 padding 자체가 사라져 이마저 불필요하다. B4-1).

한 문장 정리: decoder-only는 causal mask로 미래를 가려 "다음 토큰 예측"을 학습하므로 생성에 쓰이고, encoder-only는 mask 없이 양방향 문맥을 보므로 표현(embedding)·분류에 쓰인다. 그래서 encoder-only에는 KV cache도 autoregressive decode도 없다.

계산 방식: Q head는 32개 그대로 두고, KV head 하나를 여러 Q head가 공유한다. GQA(32 Q / 8 KV)면 Q head 4개가 한 그룹이 되어 같은 K·V를 본다. 구현상으로는 K·V를 그룹 크기만큼 repeat(broadcast)해서 쓰거나, 커널이 인덱싱으로 직접 처리한다. 핵심은 계산량(FLOPs)은 거의 그대로이고 KV cache의 메모리와 메모리 트래픽이 줄어든다는 점이다.

얻는 것 / 잃는 것
  • 얻는 것: KV cache가 1/4로 줄면 (a) 같은 GPU에 4배 많은 요청을 담을 수 있고(B1-6에서 32 vs 8 요청으로 확인), (b) decode에서 읽을 KV 바이트가 1/4이라 긴 컨텍스트에서 ITL이 개선된다. memory-bound인 decode에서는 메모리 트래픽이 곧 속도다.
  • 잃는 것: head마다 다른 것을 보는 표현력을 잃는다. MQA처럼 극단으로 가면 품질 저하가 분명해진다. GQA는 거의 잃지 않으면서 대부분을 얻는 절충점이다.
  • 그래서 표준이 됐다: 서빙 비용이 KV cache 용량으로 정해지므로, 품질을 거의 내주지 않고 배치를 4배 키우는 거래는 매우 유리하다. Llama-3, Mistral, Qwen 등 최근 모델은 대부분 GQA다.

MLA는 KV cache를 줄인다는 같은 축에서 더 공격적인 답이다. KV head를 줄이는 대신 K·V를 저차원 latent 벡터로 압축해서 저장하고 사용 시점에 복원한다. GQA보다 훨씬 작은 KV cache로 MHA급 품질을 노린다. 대신 커널 구현이 복잡하고 엔진 지원이 필요하다.

정답 · 채점 포인트

  4. 16×10⁹ ÷ 989×10¹² = 16.2 µs ← 연산만 따지면 실측 10 ms → 16.2 µs / 10,000 µs ≈ 0.16 %

채점 포인트

  • 3번의 배수가 프롬프트 길이와 같다는 것을 발견했는가
  • 4번에서 "연산 성능을 거의 안 쓴다 = memory-bound"로 연결했는가

KV cache를 텐서로 직접 확인한다. B1-6과 B2-2에서 계산·서술한 것이 실제로 그런지 본다.

import torch

mid = "meta-llama/Llama-3.1-8B-Instruct"

확인할 것
  1. K의 shape가 B2-2에서 쓴 것과 일치하는가? num_kv_heads가 32가 아니라 8인가?
  2. 출력된 bytes를 토큰 수로 나눠라. B1-6에서 계산한 128 KiB/token이 나오는가?
  3. out.logits.shape가 [1, prompt_len, vocab]인데, 실제로 쓰는 것은 어느 부분인가? (B1-1)
  4. 이제 생성을 use_cache=True와 use_cache=False로 각각 돌려 시간을 재라. max_new_tokens를 32 → 128 → 512로 늘리며 비율이 어떻게 변하는지 보라.
import time
for uc in (True, False):
    for n in (32, 128, 512):
        t0 = time.time()
        m.generate(**ids, max_new_tokens=n, use_cache=uc, do_sample=False)

이런 결과가 나와야 정상
  • K : [1, 8, prompt_len, 128]: 8이어야 한다. 32가 나왔다면 GQA가 아닌 모델이다.
  • 토큰당 131,072 B = 128 KiB가 정확히 나온다. K와 V를 둘 다 더했는지 확인하라(위 코드의 for t in l이 그 역할).
  • logits는 [1, prompt_len, 128256]이지만 실제로 쓰는 것은 logits[:, -1, :] 하나뿐이다. 나머지 위치의 logits은 학습에서는 전부 쓰이지만(모든 위치가 학습 신호) 추론에서는 버려진다. 그래서 추론 엔진은 마지막 위치만 LM head에 통과시킨다.

흔히 빠지는 함정
  • torch.cuda.synchronize()를 빼먹고 시간 측정: CUDA는 비동기라 커널이 큐에 들어가자마자 파이썬은 다음 줄로 간다. 동기화 없이 잰 시간은 무의미하다.

  • past_key_values가 최신 transformers에서는 tuple이 아닌 Cache 객체다. 버전에 따라 kv.key_cache[0].shape처럼 접근해야 할 수 있다.
  • use_cache=False로 512토큰을 생성하면 꽤 오래 걸린다. 기다리거나 256에서 끊어라. 오래 걸린다는 것 자체가 이 실습의 결론이다.

B3-1서술형

GPU의 구조와 메모리 계층을 설명하라.

  • SM(Streaming Multiprocessor)은 무엇이며, CPU 코어와 무엇이 다른가? warp란?
  • HBM과 SRAM(shared memory / L1 / L2)은 용량과 대역폭이 각각 대략 어느 정도 차이인가?
  • "GPU가 빠르다"는 말은 실제로 무엇이 빠르다는 뜻인가? 연산 성능과 메모리 대역폭 중 어느 쪽이 더 빠르게 발전해 왔는가?

정답 · 채점 포인트

SM: GPU의 연산 단위로, H100 SXM에는 132개가 있다. CPU 코어가 "복잡한 제어 흐름을 빠르게 처리하는 소수의 강한 코어"라면, SM은 "같은 명령을 수천 개 데이터에 동시에 적용하는(SIMT) 단순하고 넓은 유닛"이다. 분기(branch)에 약하고 처리량에 강하다. warp는 32개 스레드 묶음으로, GPU 스케줄링의 최소 단위다. warp 안의 스레드가 서로 다른 분기를 타면 순차 실행되어 성능이 떨어진다(warp divergence).

핵심은 계단마다 용량과 속도가 반대로 간다는 것이다. 용량이 큰 쪽이 느리다. 최적화는 대부분 데이터를 빠른 계층에 올려 두고 느린 계층 왕복을 줄이는 일이며, FlashAttention(B4-2)이 바로 이 일을 한다.

어느 쪽이 더 빨리 발전했나: 연산 성능이다. 세대를 거치며 FLOPS는 메모리 대역폭보다 훨씬 가파르게 올랐다(이른바 memory wall). 그 결과 ridge point가 계속 오른쪽으로 밀리고, 예전에 compute-bound였던 워크로드가 memory-bound가 된다. LLM decode가 memory-bound인 것도 이 추세의 결과이며, 앞으로 더 심해진다.

Tensor Core: 작은 행렬 블록의 곱셈-누산(MMA)을 한 명령으로 처리하는 전용 유닛으로, 저정밀(bf16/fp8/fp4)에서 특히 강하다. "989 TFLOPS"는 Tensor Core 수치이며 일반 CUDA Core의 fp32 성능(~67 TFLOPS)과 자릿수가 다르다. 뒤집어 말하면 Tensor Core를 못 쓰는 연산은 GPU 성능을 거의 못 쓴다.

B3-2서술형

arithmetic intensity(연산 강도)를 정의하고, 이를 이용해 compute-bound / memory-bound를 판정하는 방법을 설명하라.

  • 단위는 무엇인가? 무엇을 무엇으로 나누는가?
  • 같은 연산이라도 하드웨어에 따라 병목이 달라질 수 있는가?
  • Horace He는 세 번째 범주로 overhead-bound를 든다. 그것은 무엇이며, LLM 추론에서 언제 문제가 되는가?
  • 각 병목 상태에서 해야 할 일이 어떻게 달라지는지 하나씩 예를 들라.
정답 · 채점 포인트
arithmetic intensity = FLOPs 수행량 / HBM에서 옮긴 바이트 수 [FLOP/byte]

이 값이 하드웨어의 ridge point(= 최대 FLOPS ÷ 메모리 대역폭)보다 크면 compute-bound, 작으면 memory-bound다. 직관적으로는 메모리에서 1바이트를 가져올 때마다 계산을 몇 번 하느냐이며, 적게 하면 GPU는 데이터를 기다리며 논다.

하드웨어에 따라 달라진다. intensity는 연산의 성질이지만 ridge point는 칩의 성질이다. 같은 커널이 대역폭 대비 연산이 강한 칩에서는 memory-bound, 그렇지 않은 칩에서는 compute-bound일 수 있다. 그래서 "이 연산은 memory-bound다"라는 말은 항상 특정 하드웨어를 전제로 한다.

overhead-bound

GPU가 연산도 메모리도 아닌 "일을 시키는 비용"에 막힌 상태다. 커널 런치 지연, 파이썬 인터프리터, CPU가 다음 커널을 준비하는 시간이 여기에 해당한다. 커널 하나가 µs 단위인데 런치 오버헤드도 µs 단위라면 GPU는 계속 굶는다.

LLM 추론에서는 decode에서 정확히 이 문제가 생긴다. batch가 작으면 각 커널이 너무 짧아(수십 µs) 런치 오버헤드가 무시되지 않는다. 그래서 vLLM 같은 엔진은 CUDA Graph(커널 시퀀스를 통째로 캡처해 한 번에 재생)를 쓴다. enforce_eager=True로 이를 끄면 ITL이 눈에 띄게 나빠진다.

B3-3서술형

roofline 모델을 설명하라. 그래프의 축이 무엇이고, "지붕"의 두 구간이 각각 무엇을 의미하는가? ridge point는 어떻게 구하는가?

그리고 prefill과 decode를 이 그래프 위에 각각 찍어라. 대략 어디에 놓이는가?

정답 · 채점 포인트
달성 성능 [FLOPS] ▲ 989 T │ ┌────────────────── ← compute roof (칩의 최대 FLOPS) │ ╱ │ │ ╱ │ │ ╱ │ │ ╱ │ ● prefill (~수백 FLOP/byte) │ ╱ │ │ ╱ ← memory roof (기울기 = 대역폭 3.35 TB/s) │╱ │ │ ● decode(b=1) │ └──────────────┴──────────────────▶ arithmetic intensity [FLOP/byte] 1 295 = ridge point
  • x축은 arithmetic intensity, y축은 실제로 달성 가능한 성능(FLOPS)이며 로그-로그 스케일로 그린다.
  • 왼쪽 경사 구간(memory roof): 대역폭에 막힌 영역이다. 달성 성능 = intensity × 대역폭이므로 기울기가 곧 대역폭이다. 여기서는 연산을 아무리 최적화해도 성능이 오르지 않는다.
  • 오른쪽 평평한 구간(compute roof): 연산 유닛에 막힌 영역이다. 여기서는 메모리를 아무리 아껴도 성능이 오르지 않는다.
  • ridge point: 두 선이 만나는 지점으로 최대 FLOPS ÷ 메모리 대역폭이다. 이 칩에서 본전을 뽑으려면 바이트당 몇 번 계산해야 하는지를 뜻한다.

위치: prefill은 큰 GEMM이라 intensity가 높아(수백 FLOP/byte) ridge point 근처나 오른쪽, 즉 compute roof에 붙어 있다. 실제로 잘 튜닝된 prefill은 peak의 절반 이상을 낸다. decode(batch=1)는 intensity가 1 근처라 왼쪽 끝, 즉 memory roof의 바닥에 있다. B2-5에서 계산한 "peak의 0.16%"가 바로 이 위치다.

이 그림이 B4 전체의 지도다. 최적화는 두 갈래로, decode를 오른쪽으로 밀어내거나(batching, speculative decoding) memory roof 자체를 위로 올린다(quantization으로 읽을 바이트 줄이기).

B3-4계산형

H100 SXM에서 decode가 언제 compute-bound로 바뀌는지 계산하라.

Given
  • H100 SXM: bf16 dense 989 TFLOPS, HBM3 대역폭 3.35 TB/s
  • 모델 파라미터 P, bf16 (2 bytes/param), batch size B, 컨텍스트는 짧다고 가정 (KV 읽기 무시)
  1. 이 칩의 ridge point는 몇 FLOP/byte인가?
  2. decode 1 step에서 (a) HBM에서 읽는 바이트 수와 (b) 수행하는 FLOPs를 P와 B로 표현하라. batch를 키우면 읽는 바이트는 늘어나는가?
  3. 둘로 arithmetic intensity를 구하라. 놀랄 만큼 단순한 결과가 나온다.
  4. 따라서 decode가 compute-bound가 되려면 batch size가 얼마 이상이어야 하는가? 이 수치가 실제 서빙에서 뜻하는 바는?
  5. 컨텍스트가 길어 KV cache 읽기를 무시할 수 없다면, 위 결론은 어떻게 달라지는가?
정답 · 채점 포인트
  1. ridge point = 989×10¹² FLOPS ÷ 3.35×10¹² B/s ≈ 295 FLOP/byte
  2. (a) 읽는 바이트 = 2P ← weight 전체를 한 번 읽는다 (b) FLOPs = 2 × P × B ← 배치 안의 B개 토큰 각각에 대해
    읽는 바이트는 B와 무관하다. weight를 배치가 공유하기 때문이다. batching이 강력한 이유는 이 한 줄로 설명된다.
  3. intensity = (2PB) / (2P) = B [FLOP/byte]
    arithmetic intensity가 곧 batch size다. 모델 크기 P가 약분되므로 8B든 70B든 결론이 같다.
  4. B ≥ 295 → 대략 batch 300 이상에서 compute-bound로 전환
    뒤집어 말하면 batch 300 미만의 decode는 모두 memory-bound다. 실서비스에서 동시 요청이 수백 개에 이르는 경우는 흔치 않으므로 실제 decode는 거의 전부 memory-bound 영역에 있다. 그래서 (a) 배치를 키우면 거의 항상 이득이고(B1-5), (b) 최적화의 1순위는 읽는 바이트 줄이기(quantization·GQA)다.
  5. KV cache 읽기는 시퀀스마다 별도라서 batch에 비례해서 늘어난다. 분모의 2P 옆에 B × (KV 바이트)가 붙는 셈이다.
    intensity = 2PB / (2P + B·KV_bytes) → B가 커져도 KV 항이 함께 커져 intensity가 무한정 오르지 않는다
    결과적으로 긴 컨텍스트에서는 batch를 키워도 memory-bound에서 벗어나지 못한다. attention 부분은 항상 memory-bound로 남는다. 긴 컨텍스트에서 ITL이 나빠지는 이유이자, KV cache 자체를 줄이거나(GQA·MLA·KV quantization) 다른 곳에 두려는(KV offloading) 시도가 계속 나오는 이유다.
채점 포인트
  • "읽는 바이트가 B와 무관"을 스스로 짚었는가(이 문제의 핵심)
  • intensity = B라는 결과에 도달했는가
  • 5번에서 KV 항이 B에 비례한다는 비대칭을 이해했는가

  2. 따라서 batch=1에서 이론상 최대 몇 tok/s인가?

  4. 실측 대역폭이 이론치의 75%밖에 안 나오고, 여기에 커널 런치 오버헤드가 붙는다면 실측 ITL이 10 ms 정도인 것은 설명이 되는가?

정답 · 채점 포인트
  1. 16×10⁹ B ÷ 3.35×10¹² B/s = 4.78 ms
    decode step 하나마다 모델의 모든 weight를 최소 한 번은 HBM에서 읽어야 한다. 연산을 공짜로 만들어도 이 읽기는 사라지지 않으므로 이 시간이 ITL의 물리적 하한이다.
  2. 1 / 4.78 ms ≈ 209 tokens/s
    H100 한 장, 8B 모델, batch 1의 이론적 천장이다. 어떤 엔진도 이 값을 넘지 못한다. 예외는 speculative decoding처럼 한 번의 읽기로 여러 토큰을 내는 기법이다(B4-5).
  3. (16 + 1.07)×10⁹ ÷ 3.35×10¹² = 5.10 ms → 약 196 tok/s
    8K 컨텍스트에서도 KV는 weight의 6~7% 수준이라 영향이 작다. 하지만 128K 컨텍스트라면 KV가 16 GiB로 weight와 맞먹어 ITL이 거의 2배가 된다. "긴 대화일수록 느려지는" 현상의 정체다.
  4. 4.78 ms ÷ 0.75 ≈ 6.4 ms + 커널 런치·샘플링·스케줄러 오버헤드 ≈ 10 ms
    설명된다. 실측 ITL은 대체로 이론 하한의 1.5~2배 범위에 들어온다. 5배 이상 차이가 나면 정상이 아니므로 overhead-bound(CUDA graph 꺼짐, 파이썬 경로, 동기화)를 의심한다. 이 계산은 지금 성능이 정상인지 판정하는 실용적인 도구다. 새 모델을 배포하면 이 어림부터 해 보라.
  5. weight가 8 GB로 절반이 되어 2.39 ms, 약 418 tok/s다. 읽는 바이트가 절반이니 속도가 2배다. memory-bound 구간의 quantization은 연산이 아니라 메모리 트래픽을 줄여서 빨라진다(B4-7).

B4-1서술형

PagedAttention이 없던 시절, 엔진은 요청마다 max_model_len 만큼의 KV cache를 연속된 메모리로 미리 통째 할당했다.

  • 이 방식에서 낭비가 생기는 경로를 세 가지 짚어라. (요청이 최대 길이를 다 쓰지 않는 경우를 떠올려라)
  • PagedAttention은 이를 어떻게 해결하는가? OS의 어떤 개념을 빌려 왔는가?
  • 이것이 가능하게 만든 새로운 기능은 무엇인가? (단순히 메모리를 아끼는 것 이상의 이득이 있다)
  • 공짜인가? 어떤 비용을 치르는가?
정답 · 채점 포인트
세 가지 낭비
  • 내부 단편화(internal fragmentation): max_model_len=8192로 잡아 두고 300토큰만 쓰면 나머지 7,892토큰분이 통째로 논다. 요청 대부분이 최대 길이를 다 쓰지 않으므로 이 낭비가 가장 크다.
  • 예약 낭비(reservation): 아직 생성되지 않은 미래 토큰을 위해 미리 잡아 둔 공간은 그 요청이 끝날 때까지 다른 요청이 쓰지 못한다.
  • 외부 단편화(external fragmentation): 요청이 들고 나면서 빈 공간이 조각조각 흩어지면, 총합은 충분해도 연속된 큰 덩어리가 없어 새 요청을 받지 못한다.

vLLM 논문은 이 때문에 기존 시스템이 KV 메모리의 60~80%를 낭비하고 있었다고 보고했다.

해법: OS의 가상 메모리와 페이징을 그대로 빌려 온다. KV cache를 고정 크기 block(예: 16토큰)으로 쪼개고, 논리적으로 연속된 시퀀스를 물리적으로는 흩어진 block에 담는다. 시퀀스마다 block table(페이지 테이블에 해당)이 논리 블록 → 물리 블록 매핑을 들고 있고, attention 커널이 이 테이블을 따라가며 KV를 읽는다. 낭비는 마지막 블록의 일부(평균 반 블록, 즉 8토큰분)로 줄어든다.

메모리 절약 이상의 이득: 공유(sharing)

물리 블록이 분리되니 여러 시퀀스가 같은 블록을 가리킬 수 있다. 여기서 두 가지가 따라온다.

  • prefix sharing: 같은 시스템 프롬프트를 쓰는 요청 100개가 그 구간의 KV 블록을 하나만 두고 공유한다. prefix caching의 토대다(B4-6).
  • copy-on-write: parallel sampling(n>1)이나 beam search에서 공통 접두사를 공유하다가 갈라지는 지점에서만 복사한다.

KV를 블록 단위로 관리하므로 padding이 사라지고, 메모리가 부족할 때 특정 시퀀스만 preemption / swap할 수도 있다.

비용: attention 커널이 block table을 통한 간접 참조를 하게 되어 메모리 접근이 비연속적이 되고, 전용 커널이 필요하다(그냥 torch.matmul로 안 된다). 블록 관리 오버헤드도 있다. 그래도 얻는 메모리가 훨씬 커서 사실상 모든 현대 엔진의 표준이 되었다.

B4-2서술형

FlashAttention에 대해 답하라. 이름이 비슷해 PagedAttention과 자주 혼동된다.

  • 표준 attention 구현이 HBM에 무엇을 쓰고 읽는가? 그 크기는 시퀀스 길이에 대해 어떤 차수인가?
  • FlashAttention은 이를 어떻게 없애는가? 두 가지 핵심 기법의 이름을 대라.
  • 연산량(FLOPs)은 줄어드는가? 그런데도 왜 빨라지는가?
  • PagedAttention과 무엇이 다른가? 둘은 배타적인가?
  • prefill과 decode 중 어느 쪽에서 더 큰 이득을 보는가? 왜인가?
정답 · 채점 포인트

표준 구현의 문제: S = QKᵀ를 계산해 HBM에 쓰고, 읽어서 softmax하고 다시 쓰고, 또 읽어서 ·V를 한다. 중간 행렬 S의 크기는 [seq × seq], 즉 O(N²)이다. 시퀀스 8K, head 32개, bf16이면 head당 128 MB, 전체로는 GB 단위가 HBM을 왕복한다. attention이 느린 진짜 이유는 연산이 아니라 이 중간 행렬의 HBM 왕복이다.

해법: tiling과 online softmax.

  • tiling: Q·K·V를 작은 타일로 잘라 SRAM에 올려놓고, 그 안에서 QKᵀ → softmax → ·V를 한 번에 끝낸다(kernel fusion). 중간 행렬 S가 HBM에 아예 쓰이지 않는다.
  • online softmax: softmax는 원래 전체 행을 봐야 최댓값과 분모를 알 수 있어 타일 단위로 쪼개기 어렵다. online softmax는 타일을 훑으며 running max와 running sum을 갱신하고 이전 부분합을 재조정해, 수학적으로 동일한 결과를 순차적으로 계산한다. 이 트릭 덕분에 tiling이 가능하다.

FLOPs는 오히려 조금 는다(재조정 때문에). 그런데도 훨씬 빠른 이유는 attention이 memory-bound였기 때문이다. HBM 왕복을 없앤 이득이 추가 연산 비용보다 훨씬 크다. B3-2의 "병목을 알아야 최적화가 통한다"의 교과서적 사례다. 부수 효과로 메모리 사용량도 O(N²) → O(N)이 되어 긴 컨텍스트 자체가 가능해졌다.

  • 새 요청이 들어왔는데 KV 메모리가 부족하면 엔진은 무엇을 할 수 있는가?
정답 · 채점 포인트

static batching: 배치를 짜서 시작하면 배치 전체가 끝날 때까지 그 구성이 고정된다. 10토큰짜리 요청은 990 step 동안 할 일 없이 슬롯을 붙잡고, 패딩으로 계산까지 되며 대기한다. 큐의 새 요청은 배치가 통째로 끝날 때까지 들어오지 못한다. 그래서 GPU가 놀고, TTFT가 길어지고, throughput이 떨어진다. 출력 길이 편차가 큰 LLM 워크로드에서 특히 치명적이다.

continuous batching: 스케줄링 단위를 "요청 단위"에서 "iteration(decode step) 단위"로 바꾼다. 스케줄러는 매 step 다시 판단해, 끝난 요청은 즉시 배치에서 빼서 결과를 반환하고 빈 슬롯에 대기 중인 새 요청을 그 자리에서 넣는다. 배치 구성이 매 step 바뀐다.

전제: 요청이 서로 다른 시점에 들어오고 나가려면, 각 시퀀스의 KV cache가 독립적으로 할당·해제 가능해야 한다. 연속 메모리를 통째로 예약하는 방식으로는 불가능하다. PagedAttention(블록 단위 KV 관리)이 continuous batching을 실용적으로 만든 토대이고, 두 기법이 vLLM에서 함께 등장한 것도 그래서다. 시퀀스 길이가 제각각이어도 padding이 필요 없다는 점도 여기서 나온다.

메모리가 부족할 때
  • 대기(queue): 새 요청을 배치에 넣지 않고 waiting 상태로 둔다. 가장 흔한 경우이며 TTFT 증가로 나타난다.
  • preemption: 실행 중인 요청을 골라 내보낸다. 방식은 두 가지다.
    • swap: 그 요청의 KV 블록을 CPU 메모리로 내렸다가 나중에 되돌린다. PCIe를 타므로 느리다.
    • recompute: KV를 버리고 나중에 prefill부터 다시 한다. 짧은 시퀀스에서는 이쪽이 더 싸다.

vLLM 로그의 Preemption 경고나 num_preemptions 지표가 올라가면 KV 메모리가 부족하다는 신호다. gpu_memory_utilization을 올리거나 max_num_seqs·max_model_len을 줄인다.

B4-4서술형

chunked prefill에 대해 답하라.

  • chunked prefill이 없을 때, 32,000토큰짜리 프롬프트가 들어오면 이미 decode 중이던 다른 요청들에게 무슨 일이 생기는가? 이 현상을 뭐라고 부르는가?
  • chunked prefill은 무엇을 하는가?
  • 이 기법이 TTFT와 ITL에 각각 어떤 영향을 주는가? 무엇을 무엇과 맞바꾸는 것인가?
  • B3의 관점에서, prefill 청크와 decode를 같은 배치에 섞는 것이 왜 GPU 활용에도 유리한가?
  • max_num_batched_tokens를 크게/작게 잡으면 각각 어떤 트레이드오프가 생기는가?
정답 · 채점 포인트

문제 상황: 32K prefill은 단일 forward로 수백 ms가 걸린다. 그동안 GPU는 그 한 요청에 붙잡혀 있고, decode 중이던 다른 요청 수십 개는 한 토큰도 만들지 못하고 멈춘다. 사용자에게는 잘 흘러나오던 글자가 갑자기 멎었다가 다시 흐르는 ITL 스파이크로 보인다. 긴 요청 하나가 짧은 요청들의 지연을 망치는 이 현상을 head-of-line blocking(또는 generation stall)이라 하며, p99 ITL을 망가뜨리는 대표 원인이다.

chunked prefill: 긴 prefill을 max_num_batched_tokens 크기의 청크로 쪼개 여러 iteration에 나눠 처리하고, 각 iteration에서 남는 토큰 예산을 decode 요청으로 채운다. 한 배치에 "prefill 청크 512토큰 + decode 60개"처럼 섞어 넣는 것이다(hybrid batch).

TTFT ↔ ITL의 교환
  • ITL은 크게 안정된다: decode가 멈추지 않으므로 스파이크가 사라지고 p99가 좋아진다.
  • 그 긴 요청의 TTFT는 다소 나빠진다: prefill이 여러 iteration에 나뉘어 처리되고 중간에 decode와 자원을 나누므로 첫 토큰까지 더 걸린다.

한 요청의 TTFT를 내주고 전체 요청의 ITL 안정성을 사는 셈이다. 다수 사용자를 상대하는 서비스에서는 거의 항상 남는 장사다.

GPU 활용 관점

prefill은 compute-bound, decode는 memory-bound다(B1-2). 둘을 같은 배치에 섞으면 서로 놀던 자원을 채운다. decode만 돌 때 놀던 연산 유닛을 prefill 청크가 쓰고, prefill만 돌 때 남던 대역폭을 decode가 쓴다. 그래서 공정성뿐 아니라 처리량 자체에도 이득이다. PD disaggregation은 반대 방향의 답으로, 섞지 않고 아예 다른 기계로 분리한다.

max_num_batched_tokens
  • 크게: prefill이 덩어리째 처리되어 TTFT·prefill 처리량이 좋아지지만, decode가 밀려 ITL 스파이크가 되살아난다. 너무 크면 chunked prefill을 쓰지 않은 것과 같아진다.
  • 작게: ITL이 매끄러워지지만 prefill이 잘게 쪼개져 GEMM이 작아지고, TTFT와 전체 처리량이 나빠진다.
  • 값은 워크로드로 정한다. 긴 프롬프트 + 다수 동시 사용자(RAG·에이전트)면 작게, 짧은 프롬프트 위주면 크게 잡는다.
B4-5서술형

speculative decoding에 대해 답하라.

  • 동작 방식을 순서대로 설명하라. draft model과 target model은 각각 무엇을 하는가?
  • 초심자가 가장 헷갈리는 부분: 작은 모델이 만든 토큰을 쓰는데 왜 품질이 안 떨어지는가?
  • B3-4의 결과(intensity = batch size)를 이용해, 왜 이 기법이 빠른지를 roofline 관점에서 설명하라.
  • draft model 없이 하는 변형들(n-gram/prompt lookup, Medusa, EAGLE)은 무엇을 대신 쓰는가?
  • 이 기법이 이득이 없거나 오히려 손해가 되는 상황은?
정답 · 채점 포인트
동작
  1. draft: 작고 빠른 모델이 앞으로 나올 토큰 k개를 추측해서 만든다(autoregressive하게 k번 돌지만 작아서 싸다).
  2. verify: 큰 target model이 그 k개를 한 번의 forward로 동시에 검증한다. prefill처럼 여러 토큰을 병렬로 넣을 수 있기 때문이다.
  3. accept / reject: 앞에서부터 target의 분포와 맞는 토큰까지 받아들이고, 처음 틀린 지점에서 잘라낸다. 그 자리는 target의 분포로 다시 샘플링한다.
  4. 한 번의 verify로 최소 1개, 최대 k+1개의 토큰이 확정된다.
품질이 안 떨어지는 이유

최종 출력의 확률분포가 target model 단독으로 생성했을 때와 수학적으로 동일하도록 accept/reject 규칙(rejection sampling)이 설계되어 있기 때문이다. draft는 후보를 제안할 뿐이고 채택 여부는 항상 target이 결정한다. draft가 엉터리여도 품질은 그대로이고, 채택률이 낮아져 속도 이득이 사라질 뿐이다. 품질은 걸려 있지 않고 속도만 걸린 거래라는 점이 핵심이다.

왜 빠른가: roofline 관점

B3-4에서 decode의 intensity는 곧 batch size였고, batch가 작으면 심하게 memory-bound였다. target model의 weight를 한 번 읽는 비용은 토큰 1개를 내든 5개를 내든 같다. 평소에는 그 비싼 읽기로 토큰 하나만 뽑았지만, speculative decoding은 한 번의 읽기로 여러 토큰을 확정한다. 일종의 "시간축 batching"으로, 놀던 연산 유닛을 검증에 쓴다.

그래서 이 기법은 memory-bound일 때만 통한다. B3-5에서 계산한 "batch 1의 이론 상한 209 tok/s"를 넘어설 수 있는 거의 유일한 방법이기도 하다.

draft model 없는 변형
  • n-gram / prompt lookup decoding: 별도 모델 없이 프롬프트나 지금까지의 출력에서 같은 패턴을 찾아 이어질 토큰을 제안한다. 요약·코드 편집·RAG처럼 입력 문자열이 출력에 그대로 반복되는 워크로드에서 잘 맞고, 비용이 거의 0이라 손해 볼 일이 적다.
  • Medusa: target model에 여러 개의 추가 head를 붙여 "2칸 뒤, 3칸 뒤" 토큰을 한꺼번에 예측하게 한다. 별도 모델이 필요 없다.
  • EAGLE: 토큰이 아니라 feature(hidden state) 수준에서 추측해 채택률을 크게 끌어올렸다. 현재 실측 성능이 가장 좋은 축에 속한다.
손해가 되는 상황
  • batch가 큰 고부하 상황: 이미 compute-bound에 가까워 연산 여유가 없다. 검증에 드는 추가 연산이 그대로 비용이 되어 전체 throughput이 오히려 떨어진다. 그래서 부하에 따라 speculation을 끄는 적응형 정책을 쓰기도 한다.
  • 채택률이 낮을 때: draft가 자주 틀리면 draft 비용만 쓰고 버린다(B4-8에서 수치로 확인).
  • draft가 너무 클 때: target보다 충분히 싸지 않으면 이득이 상쇄된다. 보통 1/10 이하 크기를 쓴다.
  • k를 너무 크게 잡을 때: 뒤쪽 토큰일수록 맞을 확률이 지수적으로 떨어지는데 draft 비용은 선형으로 는다.
B4-6서술형

prefix caching(automatic prefix caching, prompt caching)에 대해 답하라.

  • 무엇을 캐시하는가? B1의 KV cache와 같은 것인가, 다른 것인가?
  • 왜 접두사(prefix)여야만 하는가? 프롬프트 중간이 같으면 재사용할 수 없는 이유는? (B2-2, B2-3과 연결하라)
  • 어떤 워크로드에서 이득이 큰가? 세 가지를 들라.
  • 어느 지표가 개선되는가? TTFT인가 ITL인가? 왜인가?
  • 주의할 점은? (성능 측정과 운영 양쪽에서)
정답 · 채점 포인트

같은 KV cache이고, 다른 점은 수명이다. 일반 KV cache는 요청이 끝나면 해제되지만, prefix caching은 요청이 끝난 뒤에도 KV 블록을 남겨 두었다가 다음 요청이 같은 접두사로 시작하면 재사용한다. 토큰 블록의 해시로 인덱싱하고, 메모리가 부족하면 LRU로 내보낸다. PagedAttention의 블록 공유(B4-1)를 그대로 쓴다.

왜 접두사여야 하는가

토큰의 K·V는 자기 위치(RoPE, B2-2)와 자기 앞의 모든 토큰(causal attention, B2-3)에 의해 결정된다. 그래서 어떤 구간의 KV를 재사용하려면 그 앞부분과 위치가 완전히 같아야 하고, 접두사가 바로 그 조건이다.

반대로 프롬프트 중간이 같아도 앞이 다르면 그 구간의 K·V는 다른 값이 되므로 재사용할 수 없다. 그래서 공통 부분을 앞에 두는 것이 프롬프트 설계 원칙이 된다. 시스템 프롬프트·툴 정의·few-shot 예제를 앞에, 사용자 입력을 뒤에 둔다. 순서만 바꿔도 캐시 히트율이 크게 달라진다.

이득이 큰 워크로드
  • 멀티턴 대화: n번째 턴의 프롬프트는 n−1번째 프롬프트 + 답변의 연장이다. 대화가 길어질수록 접두사 비중이 커져 히트율이 올라간다.
  • 긴 시스템 프롬프트 / 툴 정의를 공유하는 에이전트: 수천 토큰짜리 툴 스펙이 모든 요청 앞에 붙고, 툴을 호출할 때마다 이 구간이 반복된다.
  • 같은 문서에 대한 반복 질의(RAG·문서 QA·코드베이스 질의): 문서를 컨텍스트에 넣고 여러 질문을 던지는 패턴이다.
개선되는 지표

TTFT다. 재사용되는 것이 prefill의 산출물이므로 그 구간의 prefill 연산이 통째로 생략된다. 캐시된 접두사가 길수록 TTFT가 크게 떨어진다(수 초 → 수십 ms도 흔하다). decode 단계의 일은 그대로이므로 ITL은 거의 변하지 않는다. prefill 부하가 줄어 전체 처리량도 오른다.

주의할 점
  • 벤치마크 오염: 같은 프롬프트를 반복해 측정하면 두 번째부터 TTFT가 비현실적으로 좋게 나온다. 순수 prefill 성능을 재려면 끈다(B1-8의 함정과 같다).
  • KV 메모리를 차지한다: 캐시로 남은 블록만큼 새 요청에 쓸 공간이 준다. 히트율이 낮은 워크로드에서는 오히려 손해다.
  • 라우팅과 얽힌다: 여러 replica로 부하를 분산하면 캐시가 없는 워커로 요청이 가서 히트를 놓칠 수 있다. 이 문제를 푸는 것이 KV-cache-aware routing이다.
  • 보안: 캐시 히트 여부가 응답 시간으로 드러나므로, 테넌트가 다른 요청끼리 캐시를 공유하면 정보가 샐 수 있다. 격리 정책을 확인한다.
B4-7서술형

quantization에 대해 답하라. 아래 세 가지는 줄이는 대상과 효과가 서로 다르다.

  • weight-only (예: AWQ, GPTQ, INT4): 무엇이 줄고, 어느 지표가 좋아지는가? 왜 batch가 커지면 이득이 줄어드는가?
  • weight + activation (예: FP8 W8A8): 추가로 무엇이 가능해지는가?
  • KV cache quantization (fp8/int8 KV): 무엇이 줄고, 그 결과 무엇이 늘어나는가?

세 가지 중 decode의 ITL을 batch=1에서 가장 확실히 줄이는 것은 어느 것인가? 품질 손실은 어디를 봐야 알 수 있는가?

정답 · 채점 포인트
방식줄이는 것주 효과
weight-only
INT4 / AWQ / GPTQ		weight 저장 크기 + 읽는 바이트모델이 GPU에 들어가게 하고, memory-bound decode를 빠르게
W8A8
FP8 / INT8		weight + activation위에 더해 연산 자체를 저정밀 Tensor Core로 → prefill(compute-bound)까지 빨라진다
KV quantizationKV cache 바이트담을 수 있는 요청 수·컨텍스트 길이 증가, 긴 컨텍스트 ITL 개선

weight-only: 저장은 INT4지만 연산 직전에 bf16으로 되돌려(dequantize) 계산한다. FLOPs는 줄지 않고 오히려 dequant 오버헤드가 붙는다. 그래도 빨라지는 이유는 읽는 바이트가 1/4이고 decode가 memory-bound이기 때문이다(B3-5의 5번 계산과 같다).
batch가 커지면 이득이 준다: batch가 커질수록 compute-bound 쪽으로 이동하는데(B3-4), 그 영역에서는 메모리를 아껴도 소용이 없고 dequant 오버헤드만 남는다. 그래서 고부하 서빙에서는 W4가 오히려 느릴 수도 있다.

W8A8 (FP8): activation까지 낮추면 Tensor Core가 fp8로 직접 계산할 수 있어 연산 처리량이 실제로 오른다. 그래서 compute-bound인 prefill과 큰 batch의 decode까지 빨라진다. H100/H200·MI300X처럼 fp8을 하드웨어로 지원하는 칩에서는 현재 가장 실용적인 선택으로 꼽힌다. 대신 activation은 outlier가 커서 스케일링(per-tensor/per-channel, SmoothQuant 등)에 신경 써야 한다.

KV quantization: B1-6의 dtype_bytes를 2 → 1로 줄이므로 KV cache가 절반이 된다. 그만큼 동시 요청 수나 컨텍스트 길이를 늘릴 수 있고, 긴 컨텍스트에서 KV 읽기가 줄어 ITL도 개선된다(B3-5의 3번). 단, KV는 attention 점수에 직접 들어가므로 정밀도 손실이 긴 컨텍스트에서 누적되기 쉽다.

batch=1 decode ITL

weight-only(또는 W8A8의 weight 부분)가 가장 확실하다. batch=1 decode 시간의 거의 전부가 weight를 읽는 시간이므로, 읽는 바이트를 절반으로 줄이면 ITL이 거의 절반이 된다. KV quantization은 컨텍스트가 아주 길지 않으면 KV가 weight의 몇 % 수준이어서 효과가 작다.

품질 손실을 확인하는 곳
  • perplexity만 보면 안 된다: 양자화 손실은 평균 지표에는 잘 드러나지 않고 특정 능력에서 무너진다.
  • 실제 태스크 벤치마크(코드 생성, 수학·추론, 긴 컨텍스트 검색), 다국어(한국어는 영어보다 먼저 무너지는 경우가 많다), 구조화 출력/tool call의 JSON 유효성, 긴 생성에서의 반복·발산을 본다.
  • 운영에서는 양자화 전후 같은 프롬프트 세트의 출력을 나란히 비교하는 회귀 세트가 가장 확실하다.
B4-8계산형

speculative decoding의 기대 이득을 계산하라.

Given
  • draft 길이 k = 4, 토큰별 채택 확률 α = 0.8 (독립이라고 가정)
  • draft model은 target의 1/10 비용. verify forward는 토큰 1개짜리 decode step의 1.1배 비용 (여러 토큰을 넣어도 memory-bound라 거의 같다)
  • 비용 단위는 "일반 decode step 1회" = 1.0
  1. 한 번의 draft-verify 사이클에서 기대 확정 토큰 수는? (거부된 자리에서 target이 1개를 내주는 bonus 토큰을 포함하라)
  2. 한 사이클의 비용은 몇 단위인가?
  3. 따라서 speedup은 몇 배인가?
  4. 채택률이 α = 0.4로 떨어지면? 결론이 어떻게 바뀌는가?
  5. α = 0.8에서 k를 8로 늘리면 speedup이 얼마나 더 좋아지는가? k를 계속 키우는 것이 답이 아닌 이유를 수치로 보여라.
정답 · 채점 포인트

기대 확정 토큰 수의 일반식(등비급수):

E[tokens] = 1 + α + α² + … + α^k = (1 − α^(k+1)) / (1 − α)

(앞의 1은 항상 확정되는 bonus 토큰이고, 나머지는 draft에서 채택되는 기대값이다)

  1. E = (1 − 0.8⁵) / (1 − 0.8) = (1 − 0.32768) / 0.2 = 3.36 tokens
  2. 비용 = draft 4회 × 0.1 + verify 1.1 = 0.4 + 1.1 = 1.5 단위
  3. speedup = 3.36 tokens / 1.5 단위 ÷ (1 token / 1.0 단위) = 2.24 배
    B3-5의 209 tok/s 상한이 대략 470 tok/s가 된다.
  4. E = (1 − 0.4⁵) / 0.6 = (1 − 0.01024) / 0.6 = 1.65 tokens speedup = 1.65 / 1.5 = 1.10 배
    이득이 거의 사라진다. draft 비용(0.4)과 verify의 추가 비용(0.1)은 그대로 나가는데 확정 토큰은 1.65개뿐이다. draft 모델이 조금만 더 비싸거나(1/5 크기라면 비용 = 0.8+1.1 = 1.9 → 0.87배, 즉 오히려 느려진다) 채택률이 더 낮으면 손해로 뒤집힌다. 채택률이 이 기법의 생명줄이며, draft 모델이 target과 같은 계열·같은 tokenizer일 때 채택률이 높다.
  5. k = 8 : E = (1 − 0.8⁹) / 0.2 = (1 − 0.1342) / 0.2 = 4.33 tokens 비용 = 8 × 0.1 + 1.1 = 1.9 speedup = 4.33 / 1.9 = 2.28 배 (k=4의 2.24배에서 거의 제자리)
    토큰은 3.36 → 4.33으로 29% 늘었지만 비용은 1.5 → 1.9로 27% 늘어 상쇄된다. 채택 확률은 α^i로 지수적으로 감소하는데(8번째 토큰이 살아남을 확률은 0.8⁸ = 0.17) draft 비용은 선형으로 증가하기 때문이다. 뒤쪽 draft 토큰은 거의 버려지는데 값은 다 치른다.
    최적 k는 α에 따라 정해지는 유한한 값이며, α가 높을수록 큰 k가 유리하다. 실무에서는 3~5 정도가 흔하고, 채택률을 보며 k를 동적으로 조절하는 구현도 있다.
채점 포인트
  • bonus 토큰(항상 나오는 1개)을 포함했는가(빼먹으면 이득을 과소평가한다)
  • 4번에서 "손해로 뒤집힐 수 있다"까지 갔는가
  • 5번에서 지수적 감소 vs 선형 증가의 대비를 짚었는가

확인할 것
  1. 각 실험에서 TTFT p50/p99와 ITL p50/p99, output tok/s를 표로 정리하라.
  2. ④는 요약 태스크(입력을 그대로 인용하는 출력)와 창작 태스크 두 가지로 각각 재라. 채택률 차이가 speedup에 어떻게 나타나는가?
  3. curl localhost:8000/metrics에서 vllm:gpu_prefix_cache_hit_rate, vllm:num_preemptions_total, vllm:gpu_cache_usage_perc를 확인하라.
정답 · 채점 포인트
이런 결과가 나와야 정상
  • ① chunked prefill: 끄면 ITL p99가 크게 튄다(head-of-line blocking). 켜면 p99가 안정되는 대신 긴 요청의 TTFT는 다소 늘어난다. p50만 보면 차이가 잘 안 보이니 반드시 p99를 보라. 최근 vLLM에서는 기본으로 켜져 있다.
  • ② prefix caching: 켜면 두 번째 요청부터 TTFT가 극적으로 떨어지고(공통 접두사가 길수록 크다) ITL은 거의 그대로다. gpu_prefix_cache_hit_rate가 올라가는 것으로 확인한다. 매번 다른 프롬프트를 쓰면 히트율이 0에 가깝고 이득도 없는데, 이것이 정상이다.
  • ③ quantization: batch 1에서 ITL이 눈에 띄게 개선된다(fp8이면 이론상 최대 2배 근처). 반면 동시성을 크게 준 고부하에서는 개선폭이 줄어든다(B4-7의 "batch가 커지면 이득이 준다"). 두 조건을 따로 재지 않으면 결론을 잘못 내린다.
  • ④ speculative decoding: 요약처럼 입력을 인용하는 태스크에서는 ngram의 채택률이 높아 ITL이 크게 개선되고, 창작 태스크에서는 채택률이 낮아 이득이 거의 없거나 소폭 손해다. 또 동시성을 크게 주면 이득이 사라지거나 역전된다(B4-5의 "batch가 크면 손해"). 벤치마크 결과의 acceptance rate를 B4-8의 식에 넣어 예측치와 비교해 보라.
흔히 빠지는 함정
  • 한 번에 두 가지를 바꾼다: 반드시 하나씩 바꿔라. 특히 prefix caching은 다른 실험의 TTFT를 오염시키므로, 다른 것을 잴 때는 끄거나 매번 다른 프롬프트를 써라.
  • p50만 본다: chunked prefill과 preemption의 효과는 대부분 꼬리(p99)에서 나타난다.
  • 동시성 조건을 고정하지 않는다: ③④는 부하에 따라 결론이 뒤집힌다. concurrency 1과 32를 모두 재고 표에 함께 적어라.
  • 서버를 재시작하지 않고 옵션만 바꿨다고 믿는다: 대부분의 엔진 옵션은 기동 시 결정된다.

정답 · 채점 포인트
HTTP 요청 → [API server] OpenAI 스키마 파싱 · chat template 적용 · tokenize → [EngineCore] 요청을 waiting 큐에 넣음 → ┌ 매 step 반복 ────────────────────────────────┐ │ [Scheduler] 이번 step에 누구를 태울지 결정 │ │ [KVCacheMgr] KV 블록 할당 / prefix 재사용 │ │ [ModelRunner] 배치 구성 → forward → sampling │ │ [OutputProc] detokenize → 스트리밍 전송 │ └────────────────────────────────────────────┘ → EOS / max_tokens → 요청 종료, KV 블록 해제
한 step에서 스케줄러가 내리는 결정
  1. 토큰 예산 배분: max_num_batched_tokens 안에서 이번 step에 처리할 토큰을 나눈다. running 중인 decode 요청은 각 1토큰, 남는 예산을 waiting 요청의 prefill 청크로 채운다(chunked prefill, B4-4).
  2. 새 요청 admission: waiting 큐에서 몇 개를 running으로 올릴지 정한다. max_num_seqs와 가용 KV 블록이 제약이다.
  3. KV 블록 할당: 각 요청에 필요한 블록을 확보한다. 이때 prefix cache를 조회해 이미 계산된 접두사 블록이 있으면 재사용하고 그만큼 prefill을 건너뛴다(B4-6).
  4. preemption 판단: 블록이 모자라면 running 중인 요청을 골라 swap하거나 recompute로 되돌린다(B4-3).
  5. 완료 처리: EOS·stop·max_tokens에 도달한 요청을 배치에서 빼고 블록을 반납한다. 그 자리는 다음 step에 바로 다른 요청이 쓴다(continuous batching).

API server 분리: HTTP 파싱·tokenize·detokenize·스트리밍은 CPU 작업이고 파이썬 GIL을 잡는다. 이것이 GPU를 먹이는 엔진 루프와 같은 프로세스에 있으면 CPU 작업이 밀릴 때 GPU가 굶는다(B3-2의 overhead-bound). 프로세스를 분리하면 두 루프가 독립적으로 돌고 CPU 쪽을 따로 스케일할 수 있다. 고부하에서는 실제로 차이가 난다.

  • 그 모델을 지원하는가: 최신 아키텍처는 엔진별 지원 시점이 다르다. 지원하지 않으면 성능 논의가 무의미하다.
  • 그 하드웨어를 지원하는가: NVIDIA / AMD ROCm / TPU / CPU 지원 범위가 다르다.
  • 필요한 기능이 있는가: 구조화 출력, tool calling 파서, LoRA, 멀티모달, PD disaggregation 등이다.
  • 운영 요소: 지표(Prometheus) 노출, 안정적인 릴리스, 이슈 대응 속도, 팀의 운영 경험을 본다.

성능 차이는 대개 버전이 올라가며 좁혀지지만, 지원하지 않는 모델은 튜닝으로 해결되지 않는다.

SGLang의 RadixAttention을 설명하라.

radix tree(compressed trie)로 KV cache를 관리한다. 트리의 각 경로가 토큰 시퀀스이고, 노드가 그 구간의 KV 블록을 들고 있다. 여러 요청이 같은 접두사를 공유하면 트리에서 같은 경로를 타고 가다가 갈라지는 지점에서 분기한다. eviction은 트리 위에서 LRU로 한다. 접두사 공유는 본질적으로 트리 구조이므로 자료구조가 문제의 모양과 정확히 맞는다는 것이 이 설계의 핵심이다.

B5-4서술형

모델이 GPU 한 장에 들어가지 않을 때의 병렬화 방식을 비교하라.

  • TP(tensor) / PP(pipeline) / EP(expert) / DP(data)는 각각 무엇을 쪼개는가?
  • 각 방식의 통신 패턴은? 얼마나 자주, 무엇을 주고받는가?
  • 단일 노드 추론에서 TP가 주로 쓰이고 PP는 잘 안 쓰이는 이유는? 반대로 PP가 유리한 상황은?
  • TP를 8까지 키우면 ITL이 8배 좋아지는가?
정답 · 채점 포인트
방식쪼개는 것통신
TP각 weight 행렬을 행/열로 분할. 모든 GPU가 모든 layer에 참여layer마다 all-reduce: 매우 잦음(수십 회/step), 지연에 민감
PPlayer를 그룹으로 분할. GPU 0이 1~8층, GPU 1이 9~16층…스테이지 경계에서 activation point-to-point: 드묾, 대역폭 요구도 작음
EPMoE의 expert들을 GPU에 분산MoE layer마다 all-to-all(토큰을 해당 expert로 보내고 회수)
DP모델을 쪼개지 않고 복제. 요청을 나눔추론에서는 통신 거의 없음 (단, EP와 함께 쓰면 attention 쪽 DP + MoE 쪽 EP 조합)
왜 단일 노드에서는 TP인가

지연(latency) 때문이다. PP는 layer를 순차 스테이지로 나누므로 요청 하나는 모든 스테이지를 차례로 거쳐야 해서 지연이 줄지 않는다. 게다가 decode처럼 배치가 작으면 파이프라인을 채울 마이크로배치가 부족해 bubble(놀고 있는 스테이지)이 크게 생긴다. 반면 TP는 모든 GPU가 같은 layer를 동시에 나눠 계산하므로 각 GPU가 읽어야 할 weight가 1/N로 줄어 memory-bound인 decode의 ITL이 실제로 개선된다(B3-5).

대신 TP는 layer마다 all-reduce가 필요해 빠른 인터커넥트가 필수다. 노드 안에서는 NVLink(수백 GB/s)가 이를 감당하지만, 노드를 넘어가면(이더넷/InfiniBand) 통신이 병목이 된다. 그래서 보통 노드 안은 TP, 노드 사이는 PP로 조합한다. PP가 유리한 상황은 인터커넥트가 느린 환경이거나, 지연보다 처리량이 중요해 마이크로배치를 충분히 흘릴 수 있는 경우다.

TP 8이면 ITL 8배?

아니다. weight 읽기는 1/8이 되지만 all-reduce 통신 비용이 새로 붙고, 이 비용은 TP를 키울수록 커진다. 또 각 GPU의 GEMM이 작아져 효율이 떨어지고, 커널 런치 오버헤드는 그대로다. 실제로는 TP 2 → 4까지는 꽤 잘 붙다가 8에서는 수확체감이 뚜렷하다. TP를 키우는 1차 목적은 속도보다 모델과 KV cache를 담을 메모리 확보로 보는 편이 정확하다. 속도 이득은 따라오지만 선형이 아니다.

B5-5계산형

이 배포가 동시에 몇 개의 요청을 담을 수 있는지 계산하라. 운영에서 가장 자주 하는 계산이다.

Given
  • H100 80 GB × 1장, Llama-3-8B bf16 (weight 16 GB), KV 128 KiB/token (B1-6)
  • gpu_memory_utilization = 0.9, activation·CUDA graph·프레임워크 오버헤드 ≈ 4 GB
  • max_num_seqs = 256
  1. KV cache에 쓸 수 있는 메모리는 몇 GB인가? 몇 토큰분인가?
  2. 평균 컨텍스트가 4,096토큰이면 동시 요청 수는? 이때 실제 상한은 max_num_seqs인가 KV 메모리인가?
  3. 컨텍스트가 32,768토큰으로 늘면?
  4. 4,096토큰 컨텍스트로 256개를 정말 동시에 처리하려면 KV가 얼마나 필요한가? 어떤 방법들이 있는가?
  5. KV cache를 fp8로 바꾸면 2번의 답은?
정답 · 채점 포인트
  1. 사용 가능 = 80 × 0.9 = 72 GB KV 풀 = 72 − 16 − 4 = 52 GB 토큰 수 = 52×10⁹ / 131,072 ≈ 396,000 tokens
    vLLM 기동 로그의 GPU KV cache size: 396,xxx tokens가 바로 이 값이다. 배포의 실제 수용량이 여기 적혀 있으므로 기동할 때마다 이 줄을 확인하라.
  2. 396,000 / 4,096 ≈ 96 requests
    KV 메모리가 상한이다(96 < 256). max_num_seqs=256에는 도달할 수 없고, 97번째 요청부터는 waiting 큐에서 대기하거나 preemption이 일어난다. 두 값을 함께 보지 않으면 "왜 설정한 만큼 동시 처리가 안 되지?"에서 막힌다.
  3. 396,000 / 32,768 ≈ 12 requests
    컨텍스트를 8배로 늘리면 동시 요청 수가 1/8이 된다. 긴 컨텍스트는 공짜가 아니라 처리량을 지불하고 사는 것이다.
  4. 256 × 4,096 × 128 KiB = 137 GB (필요한 KV만) + weight 16 GB + 오버헤드 → 단일 H100 80GB로는 불가능
    방법:
    • TP를 키운다: TP=4면 weight와 KV가 4장에 분산되어 KV 풀이 대략 4배가 된다(B5-4).
    • KV quantization: fp8이면 KV가 절반(B4-7).
    • 컨텍스트 제한: max_model_len을 낮춰 요청당 상한을 줄인다.
    • replica를 늘린다: DP로 수평 확장한다. 다만 replica가 늘면 prefix cache가 분산되므로 라우팅이 중요해진다.
    • 더 작은 모델 / GQA·MLA가 더 공격적인 모델로 바꾼다.
  5. KV 64 KiB/token → 52×10⁹ / 65,536 ≈ 793,000 tokens 793,000 / 4,096 ≈ 193 requests (96 → 193, 약 2배)
    max_num_seqs=256에 한결 가까워진다.
채점 포인트
  • gpu_memory_utilization과 오버헤드를 빼고 시작했는가(80 GB 전부를 KV로 쓸 수 있다고 계산하면 틀린다)
  • 2번에서 둘 중 작은 쪽이 실제 상한임을 명시했는가
  • 3번에서 컨텍스트와 동시성이 반비례한다는 구조를 이해했는가

부하를 올릴 때의 전형적인 순서
  1. num_requests_running이 오르고 gpu_cache_usage_perc가 따라 오른다. 이 구간에서는 throughput이 잘 늘고 ITL은 크게 나빠지지 않는다(B1-5의 무료 점심 구간).
  2. gpu_cache_usage_perc가 90%대에 붙으면 num_requests_waiting이 쌓이기 시작한다. running은 더 늘지 않고 TTFT가 급격히 나빠진다(큐 대기).
  3. 더 밀어붙이면 num_preemptions_total이 증가한다. 이때부터는 처리하던 요청을 되돌리느라 낭비가 생기고 전체 throughput이 오히려 꺾인다.

이 구분이 핵심이다. (a)는 지표상 지연이 나쁘지만 엔진은 정상이고 용량 문제다. (c)는 부하가 없는데도 느린 것이므로 배포 설정 문제다. 둘을 섞으면 엉뚱한 곳을 튜닝하게 된다.
