1 Problem definition 문제 정의

LLM serving has split, in two years, into several architectural species — vanilla co-located inference, Prefill–Decode Disaggregation (PDD), Attention–FFN Disaggregation (AFD), reasoning/agentic stacks with stateful sessions, RL rollout fleets. Yet capacity planning today is still mostly "spin up a real cluster and measure" or "use a simulator that bakes in one fixed architecture."

LLM 서빙은 최근 2년 사이에 여러 아키텍처 종으로 분기했습니다 — 전통적 co-location, Prefill–Decode 분리(PDD), Attention–FFN 분리(AFD), 상태가 유지되는 reasoning/agent 스택, RL rollout 함대. 그런데 캐파시티 플래닝은 여전히 "실 클러스터 띄워 측정" 또는 "한 아키텍처에 고정된 시뮬레이터"로 처리되고 있습니다.

paper's core claim논문의 핵심 주장 Existing simulators' "monolithic-replica abstractions are ill-suited to disaggregated serving, while average-case analytical proxies can distort SLA predictions and even reverse optimization conclusions." → You can't just patch them; you need a simulator built for disaggregation + runtime opts + stateful flows. 기존 시뮬레이터의 "monolithic-replica 추상화는 분리형 서빙에 안 맞고, 평균 기반 분석식은 SLA 예측을 왜곡하거나 심지어 최적화 결론을 뒤집을 수도 있다" → 패치로 해결되지 않고, 분리형 + 런타임 최적화 + 상태 보존을 처음부터 염두에 둔 시뮬레이터가 필요.

Concrete gaps the authors call out저자가 짚는 구체적 빈자리

Capability missing놓친 능력 Why it matters중요한 이유
Disaggregated execution (PDD, AFD)분리형 실행 (PDD, AFD) A "single replica" model can't represent prefill nodes shipping KV to decode nodes, or attention rolls separated from FFN rolls. "한 replica" 모델로는 prefill 노드가 decode 노드에 KV 전달하는 구조나, attention과 FFN이 분리된 구조를 표현할 수 없음.

Stateful workloads (reasoning / agents / RL)상태 보존 워크로드 (reasoning · 에이전트 · RL) A reasoning trace has hidden plan phases; an agent loops; RL rollouts switch parallelism mid-flight. Stateless request abstractions break. reasoning 추적엔 hidden plan 페이즈, 에이전트는 루프, RL rollout은 도중에 병렬화 전환. stateless request 추상화로는 안 됨.
Scalability확장성 Modern fleets exceed 1K GPUs; you need a sim that runs on a CPU host, not "rent matching cluster." 요즘 함대는 GPU 1,000대 이상. CPU 호스트에서 도는 시뮬이 필요(매칭 클러스터를 임대할 순 없음).

One-liner: Frontier asks "what if a single simulator could express co-location and PDD and AFD, with CUDA Graphs + speculative + prefix caching turned on, against stateful reasoning traces — and still hit ±4% throughput?"

한 줄: Frontier는 "한 시뮬레이터가 co-location · PDD · AFD를 모두 표현하고, CUDA Graphs + speculative + prefix caching을 켠 상태에서 상태 보존 reasoning trace까지 처리하면서도 throughput ±4%를 지킬 수 있나?"라는 질문에 답합니다.

2 Solution — architecture 해결 — 아키텍처

Frontier is organized into three planes and exposed through four modules:

Frontier는 3개의 plane으로 조직되고 4개 모듈로 노출됩니다:

2-1. The three planes 세 plane

Control Plane

"Compiles a user-level serving specification into a runnable simulation." Sets up Cluster Workers, Replica Workers, Runtime Adapters. Defines what will run. "사용자 서빙 스펙을 실행 가능한 시뮬로 컴파일." Cluster Workers · Replica Workers · Runtime Adapters를 세팅. 무엇이 돌지를 정의.

Fidelity Plan

"Runtime-estimation layer queried by the Execution Plane for every batch iteration." Op-level cost tables for attention / linear / GroupedGEMM / comm. Defines how fast. "Execution Plane이 매 배치 iteration마다 조회하는 런타임 추정 레이어." attention · linear · GroupedGEMM · 통신의 op-level 비용 테이블. 얼마나 빠른지를 정의.

Execution Plane

"Advances the request lifecycle within each replica: admission, batch composition." The discrete-event loop. Defines when things happen. "각 replica의 요청 수명주기를 진행 — admission · 배치 구성." 이산 사건 루프. 언제 일어나는지를 정의.

2-2. The four modules 네 모듈

From the paper: "organized into four modules. ➀ Workload and Config. ➁ Fidelity Plan. ➂ Control Plane. ➃ Execution Plane."

논문: "네 모듈로 조직됨. ➀ Workload and Config. ➁ Fidelity Plan. ➂ Control Plane. ➃ Execution Plane."

#Module모듈Role역할
➀Workload & Config request trace + cluster topology + parallelism tuple (pp, tp_attn, dp_attn, tp_ffn, ep_ffn) 요청 trace + 클러스터 토폴로지 + 병렬화 튜플 (pp, tp_attn, dp_attn, tp_ffn, ep_ffn)
➁Fidelity Plan per-op latency tables (BF16 / FP8) for attention, linear, GroupedGEMM, allreduce/alltoall attention · linear · GroupedGEMM · allreduce/alltoall의 op별 지연 테이블 (BF16/FP8)
➂Control Plane spawns Cluster Workers (one per role) → Replica Workers → installs Runtime Adapters Cluster Workers(역할당 1개) → Replica Workers → Runtime Adapters 설치
➃Execution Plane discrete-event loop driving Scheduler ↔ Batch Engine per replica, with Runtime Adapters in between replica별 Scheduler ↔ Batch Engine 루프를 이산 사건으로 진행, 사이에 Runtime Adapters

2-3. Worker hierarchy — the heart of "disaggregated abstraction" Worker 계층 — "분리형 추상화"의 핵심

The key abstraction: a Cluster Worker "represents a logical device group serving a specific role." For co-location, there's one role. For PDD, two roles (prefill, decode). For AFD, two roles (attention, FFN). The Control Plane builds whichever shape matches your config — no special-case code per architecture.

핵심 추상화: Cluster Worker는 "특정 역할을 수행하는 논리 디바이스 그룹". Co-location은 역할 1개, PDD는 2개(prefill, decode), AFD도 2개(attention, FFN). Control Plane이 설정에 맞는 형태를 빌드 — 아키텍처별 분기 코드 없음.

2-4. Runtime Adapters — features as middleware Runtime Adapters — 기능을 미들웨어처럼

From the paper: "Runtime Adapters are feature-specific rules attached to the Scheduler–Batch Engine loop." Each runtime optimization is one Adapter that reshapes a batch before execution:

논문: "Runtime Adapter는 Scheduler–Batch Engine 루프에 부착되는 기능별 규칙." 각 런타임 최적화가 Adapter 1개로 표현되며 실행 직전에 배치를 재구성합니다:

  • CUDA Graph adapter — pads decode batches to graph-friendly shapes; the Fidelity Plan returns the (much faster) graph latency for those shapes.
  • Speculative decoding adapter — multiplies the per-iteration token yield based on accept rate, with an extra verify-pass cost.
  • Chunked prefill adapter — slices long prompts into fixed-size chunks across iterations.
  • Prefix caching adapter — hits the cache before scheduling, updates the cache after eviction.
  • CUDA Graph adapter — decode 배치를 그래프 친화적 shape으로 패딩; Fidelity Plan이 그 shape에서의 (훨씬 빠른) 그래프 지연을 반환.
  • Speculative decoding adapter — accept rate에 따라 iteration당 토큰 산출량을 곱해주고, verify-pass 비용을 추가.
  • Chunked prefill adapter — 긴 프롬프트를 iteration들에 걸쳐 고정 chunk로 분할.
  • Prefix caching adapter — 스케줄링 전 캐시 조회, 축출 시 캐시 갱신.

Why this matters: adding a new feature = writing a new Adapter, not patching the scheduler. The paper claims this is why Frontier alone reproduces the 2.86–3.05× CUDA Graph speedup envelope within ~2–6% — older simulators can't even express it.

의미: 새 기능 추가 = Adapter 1개 새로 작성, 스케줄러 패치 불필요. Frontier가 CUDA Graph speedup 2.86–3.05× 영역을 ~2~6% 내로 재현하는 이유 — 구버전 시뮬레이터들은 그 동작 자체를 표현 못 함.

3 Concrete usage 구체적 사용

Frontier's spec is "compile a user-level serving specification into a runnable simulation." So the user input is a config that names the architecture, parallelism, optimizations, and workload — and Frontier produces per-request metrics. Below: first the fundamental trick (so you trust what's happening), then four worked use cases.

Frontier의 사양은 "사용자 서빙 스펙을 실행 가능한 시뮬로 컴파일". 사용자 입력은 아키텍처·병렬화·최적화·워크로드를 명시한 config, 출력은 요청별 메트릭. 먼저 핵심 트릭(시뮬을 믿을 수 있는 이유) → 그 다음 4개 use case.

3-1. The cost-table trick — "you DO run vLLM, but only once" cost-table 트릭 — "vLLM을 안 돌리는 게 아니라 한 번만 돌린다"

the question everyone asks first처음 듣고 다 하는 질문 "How can the simulator predict vLLM behavior on workloads it never actually ran?" — short answer: it did run vLLM, exactly once, and it bottled the measurements. Every later "prediction" is looking up that bottle. "시뮬레이터가 한 번도 안 돌려본 워크로드에서 어떻게 vLLM 동작을 예측하지?" — 짧은 답: vLLM을 딱 한 번 돌렸고, 그때 측정값을 병에 담아뒀다. 이후의 모든 "예측"은 그 병을 들여다보는 것.

(a) The two phases 두 단계 구조

┌─────────────────────────────────────┐ ┌────────────────────────────────┐ │ PHASE A — Profile (ONCE per HW) │ │ PHASE B — Simulate (MANY) │ │ │ │ │ │ Run real vLLM on real HW │ → │ No HW, no vLLM, runs on CPU │ │ ~2 hours, sweep batch & seq │ CSVs │ ~10 min per config │ │ hook into vLLM's forward pass │ │ reads the CSVs at every step │ │ emit per-op latency CSVs │ │ outputs TTFT/TPOT/throughput │ └─────────────────────────────────────┘ └────────────────────────────────┘

Phase A is paid once per (device, model) pair. The bottled CSVs work forever after that — for any cluster shape, any workload trace, any combination of runtime flags.

Phase A는 (device, model) 쌍당 1회만 지불. 한 번 채워둔 CSV는 이후 영원히 — 어떤 cluster 형태든, 어떤 워크로드든, 어떤 런타임 플래그 조합이든 — 그대로 사용.

(b) What's actually in a profile (concrete) 프로파일이 실제로 담고 있는 것 (구체)

A profile is a folder of CSVs, one per operator category. Concrete example from the sister project LLMServingSim 2.0 (which uses the identical idea and has its profiles public — Frontier's own format isn't released but the structure is the same):

프로파일은 op 카테고리별 CSV가 든 폴더. 자매 프로젝트 LLMServingSim 2.0의 실제 예시 (Frontier 자체 포맷은 미공개지만 구조는 동일):

profiler/perf/RTXPRO6000/meta-llama/Llama-3.1-8B/bf16/tp1/
├── attention.csv      ← (batch_size, seq_len_q, kv_len) → latency_ns
├── dense.csv          ← (M, N, K) → latency_ns         # 그냥 행렬곱
├── moe.csv            ← (top_k, num_experts, hidden) → latency_ns
├── per_sequence.csv   ← 시퀀스 단위 부수 비용
├── skew.csv           ← 측정 분산 (variance over repeated measures)
├── skew_fit.csv       ← α-law fit 계수 (미관측 shape 외삽용)
└── meta.yaml          ← (dtype, tp, device 정보)

This is just a function: latency = f(op, shape), sampled at concrete points. Phase B asks "what's f(attention, batch=5, seq=1500)?" and the simulator looks up the table or interpolates via skew_fit.csv if the shape wasn't measured.

(c) How the profile is generated — vLLM with hooks 프로파일은 어떻게 만들어지나 — vLLM에 후크 부착

The profiler is not a separate inference engine — it's vLLM with timing hooks plugged into its forward path. Concretely (LLMServingSim's profiler, which mirrors what Frontier's also does):

프로파일러는 별도의 추론 엔진이 아니라, vLLM의 forward 경로에 측정 후크를 꽂은 것입니다. 구체 (LLMServingSim의 프로파일러; Frontier도 동일 구조):

# conceptual pseudocode — what runs during profiling
for batch_size in [1, 2, 4, 8, 16, 32, 64, 128, ...]:
    for seq_len in [128, 256, 512, 1024, 2048, 4096, 8192, ...]:
        # build a synthetic batch of this shape
        prompts = make_batch(batch_size, seq_len)

        with attach_hooks(vllm_engine.model):  # torch hooks on attention/dense/moe/...
            for _ in range(N_warmup): vllm_engine.forward(prompts)  # warm CUDA
            for _ in range(N_measure):
                t = vllm_engine.forward(prompts)             # hooks fire
                # hooks record (op_category, shape) → latency into a buffer

        flush_to_csv(buffer, output_dir)                    # attention.csv etc.

# at the end: fit α-law curves for extrapolation
fit_alpha(attention_data) → skew_fit.csv

The hooks themselves are tiny — they sit between PyTorch ops and record GPU timestamps via CUDA events. The profiler doesn't replace vLLM's logic; it just observes vLLM running normally and writes down what happened.

후크 자체는 작습니다 — PyTorch op들 사이에 끼어들어가 CUDA event로 GPU 타임스탬프를 기록. vLLM의 로직을 교체하지 않고, 그냥 vLLM이 정상적으로 도는 걸 관찰하면서 무슨 일이 일어났는지 적습니다.

For Frontier specifically, the paper says: "Frontier characterizes ops at the granularity of attention, linear (GEMM), GroupedGEMM (MoE), allreduce, alltoall" — same categorical decomposition, same hook-based capture, written to internal tables instead of CSVs.

Frontier 논문 표현: "Frontier는 attention, linear (GEMM), GroupedGEMM (MoE), allreduce, alltoall 단위로 op를 측정" — 동일한 카테고리 분해, 동일한 후크 기반 캡처, CSV 대신 내부 테이블에 저장.

how long does this take?시간이 얼마나 걸리나 LLMServingSim's profiler quotes ~2.1 hours per (device, model) pair on H100 for Llama-3.1-70B. Smaller models are faster. The bottleneck is the number of (batch, seq) sweep points × number of measurement reps for noise reduction. You pay this once, ever. LLMServingSim 프로파일러는 Llama-3.1-70B를 H100에서 측정할 때 (device, model) 쌍당 약 2.1시간. 작은 모델은 더 빠름. 병목은 (batch, seq) sweep 점 개수 × noise 줄이려고 반복 측정하는 횟수. 평생 한 번만 지불.

(d) Two parts that imitate vLLM — cost model + behavior model vLLM을 흉내내는 두 부분 — 비용 모델 + 동작 모델

The cost table answers "how long does this op take?" — but that's not enough to predict a serving system. You also need to know which ops get scheduled together, when KV cache evicts, which requests get batched. That's the second half:

cost 테이블은 "이 op이 얼마나 걸리나?"에는 답하지만, 서빙 시스템 예측엔 그것만으론 부족. 어떤 op들이 한 배치에 묶이는지, KV 캐시가 언제 축출되는지, 어느 요청이 함께 배치되는지도 알아야 함. 이게 후반부:

Part부분 What it does하는 일 Where it comes from출처
Cost model비용 모델 "this op with this shape takes X ns""이 op이 이 shape에서 X ns 걸린다" profile CSVs (data, captured from real vLLM run)프로파일 CSV (실 vLLM 측정 데이터)

In Frontier specifically: the cost model is the Fidelity Plan (§2), and the behavior model is the Execution Plane + Runtime Adapters (§2). Each Runtime Adapter encodes one piece of vLLM's behavior (CUDA Graph padding, speculative draft logic, prefix-cache lookup, ...).

Frontier에선: 비용 모델 = Fidelity Plan(§2), 동작 모델 = Execution Plane + Runtime Adapters(§2). 각 Runtime Adapter가 vLLM의 한 동작(CUDA Graph 패딩, speculative draft, prefix-cache 룩업, …)을 인코딩.

(e) Why it generalizes to new scenarios 새 시나리오로 일반화되는 이유

Three reasons the "measure once, simulate many" trick actually works:

"한 번 측정해서 많이 시뮬"이 실제로 동작하는 세 가지 이유:

  1. LLM inference repeats the same few ops. Attention, dense GEMM, MoE GroupedGEMM, layer-norm, all-reduce. There are no rare ops to miss.
  2. Op latency is a smooth function of shape. Once you have measurements at (batch=4, seq=512), (batch=4, seq=1024), …, you can interpolate (batch=5, seq=800) with low error. The skew_fit.csv stores the curve coefficients.
  3. Cluster topology is orthogonal to op cost. The same attention takes the same time whether you're running co-location or PDD. What changes is which ops happen on which device and when — and that's the simulator's behavior model handling it, not the cost model.
  1. LLM 추론은 같은 몇 종류 op의 반복. attention, dense GEMM, MoE GroupedGEMM, layer-norm, all-reduce. 놓칠 만한 희귀 op이 거의 없음.
  2. op 지연은 shape에 대해 매끄러운 함수. (batch=4, seq=512), (batch=4, seq=1024), … 측정값이 있으면 (batch=5, seq=800)을 낮은 오차로 보간 가능. skew_fit.csv가 곡선 계수 저장.
  3. 클러스터 토폴로지는 op 비용과 직교. 같은 attention은 co-location이든 PDD이든 같은 시간이 걸림. 달라지는 건 어느 op이 어느 디바이스에서 언제 일어나느냐 — 그건 비용 모델이 아니라 시뮬레이터의 동작 모델이 처리.

(f) What this means for validation accuracy 검증 정확도에 미치는 의미

When the paper claims "±4% throughput vs real vLLM," it's saying: cost model + behavior model, evaluated on a workload that was held out from profile generation, predicted the same TTFT/throughput as a real vLLM run within 4%. That's a strong claim because:

논문이 "실 vLLM 대비 ±4% throughput"이라 주장할 때 의미: 비용 모델 + 동작 모델이 프로파일 생성에 안 쓰인 워크로드에 대해 실 vLLM과 TTFT/throughput을 4% 이내로 일치시킴. 강력한 주장인 이유:

  • The held-out workload uses (batch, seq) shapes that may not be exact profile sample points → tests the interpolation.
  • The cluster config may be different from profiling → tests the behavior model.
  • Optional flags (CUDA Graph, speculative) toggle on/off → tests the Runtime Adapters.
  • held-out 워크로드는 정확한 프로파일 sample 점이 아닌 (batch, seq)를 씀 → 보간 정확도 시험.
  • cluster config가 프로파일 때와 다를 수 있음 → 동작 모델 정확도 시험.
  • 옵션 플래그(CUDA Graph, speculative) on/off → Runtime Adapter 정확도 시험.

If your workload's distribution is way outside the profile sweep (e.g. batches of 500+, prompts of 100K tokens — typically not sampled), accuracy can degrade. Profile coverage = the simulator's "knowledge horizon." 워크로드 분포가 프로파일 sweep 범위를 한참 벗어나면(예: 배치 500+, 10만 토큰 프롬프트 — 보통 샘플링 안 됨) 정확도가 떨어질 수 있음. 프로파일 커버리지 = 시뮬레이터의 "지식 범위".

논문은 각 Adapter가 "Scheduler–Batch Engine 루프에 부착되는 규칙"이라고 명시. 구체적인 루프 단계:

while not events.empty():
    ev = events.pop_min_time()
    sim_clock = ev.time

    if isinstance(ev, ArrivalEvent):
        replica = router.pick(ev.request)
        replica.scheduler.admit(ev.request)

    if isinstance(ev, IterationTick):
        replica = ev.replica
        batch = replica.scheduler.compose()
        for a in replica.adapters:
            batch = a.reshape_batch(batch)
        cost = replica.fidelity_plan.estimate(batch)
        for a in replica.adapters:
            cost = a.amend_cost(cost)
        replica.batch_engine.step(batch, cost)
        events.push(IterationTick(time=sim_clock + cost.latency, replica=replica))
        for req in batch.completed():
            emit(req.metrics)

5-3. Why this design scales to 1K+ GPUs on CPU 왜 이 구조가 CPU에서 GPU 1K+ 까지 확장되는가

  • Discrete-event loop is O(events), not O(GPU-cycles). Number of events grows with requests × iterations, not with GPU count.
  • Fidelity Plan is table lookup (interpolated over (batch_size, seq_len, dtype)), not kernel simulation. Roughly μs per query.
  • Replicas are independent state machines; their cross-replica events are the only synchronization. Easy to parallelize, but even single-threaded handles thousands.
  • The 70K LoC is mostly the variety of Adapters / KVCacheModels / Workload types — the core loop is small.
  • 이산 사건 루프는 O(이벤트 수)이지 O(GPU 사이클)이 아님. 이벤트는 요청 × iteration에 비례, GPU 수에 비례 안 함.
  • Fidelity Plan은 테이블 룩업((batch_size, seq_len, dtype) 보간), 커널 시뮬 아님. 쿼리당 μs급.
  • Replica들은 독립 상태기계, 동기화는 cross-replica 이벤트뿐. 병렬화도 쉽지만 싱글 스레드로도 수천 개 처리 가능.
  • 70K LoC는 대부분 Adapter · KVCacheModel · Workload 유형의 다양성 — 코어 루프는 작음.

6 Takeaways 정리

what's actually new새로운 것
  • Disaggregated abstraction as a first-class primitive (Cluster Worker × role × Replica Worker × parallelism tuple) — same code path for co-location, PDD, AFD.
  • Runtime features as middleware Adapters — CUDA Graphs, speculative, chunked prefill, prefix caching are pluggable rules, not patches to the scheduler.
  • Stateful workloads supported — reasoning sessions, agentic loops, RL rollouts; phase-aware scheduling and dynamic parallelism reconfiguration testable end-to-end.
  • ±4% throughput, ±2.6–6.4% latency on 16-H800, scalable to 1K+ GPU sims on CPU.
  • 분리형 추상화가 1급 primitive (Cluster Worker × 역할 × Replica Worker × 병렬화 튜플) — co-location · PDD · AFD가 같은 코드 경로.
  • 런타임 기능을 미들웨어 Adapter로 — CUDA Graphs · speculative · chunked prefill · prefix caching이 플러그형 규칙, 스케줄러 패치 아님.
  • 상태 보존 워크로드 지원 — reasoning 세션 · 에이전트 루프 · RL rollout. phase-aware 스케줄링과 동적 병렬화 재구성을 end-to-end로 테스트 가능.
  • throughput ±4%, latency ±2.6~6.4% (16× H800), CPU에서 GPU 1K+ 시뮬까지 확장.

If I were to extend Frontier Frontier를 확장한다면

  • A Runtime Adapter for EAGLE / Medusa-style draft models alongside MTP, so you can A/B different speculation schemes.
  • A Cluster Worker role for retrieval (RAG) — separate "embedding-and-vectordb" replicas with their own SLO, since long-context flows are increasingly RAG-mixed.
  • Plug a real vLLM event stream (BlockStored/Removed, completed-request) into Frontier's event queue for hybrid sim+real shadow tests.
  • MTP 외에 EAGLE / Medusa 스타일 draft 모델용 Runtime Adapter — speculation 기법 A/B.
  • retrieval(RAG)용 Cluster Worker 역할 — "embedding + vectordb" replica를 자체 SLO로 분리. 롱컨텍스트 흐름이 점점 RAG와 결합되는 추세 반영.
  • 실제 vLLM 이벤트 스트림(BlockStored/Removed, completed-request)을 Frontier 이벤트 큐에 꽂아 hybrid sim+real shadow 테스트.

7-4. Same question, two answers — a worked example 같은 질문, 두 시뮬레이터의 답 — 실측 예시

Question: "For Llama-3.1-70B serving with 80% prompts ≤ 1K tokens and 20% ≥ 8K tokens, how should I split prefill and decode across 64× H100?"

질문: "Llama-3.1-70B 서빙에서 프롬프트의 80%가 ≤ 1K 토큰, 20%가 ≥ 8K 토큰일 때, 64× H100을 prefill/decode로 어떻게 나눠야 할까?"

Frontier로 푸는 방법

Sweep (pp, tp_attn, dp_attn, tp_ffn, ep_ffn) tuples × (P:D) ratios from 16:48 to 48:16. Frontier runs each as a discrete-event sim; output is a Pareto frontier in (throughput, p99 TTFT) space. CUDA Graph Adapter on. Reads back the answer as the (P:D, parallelism) that maximizes throughput at SLO. (pp, tp_attn, dp_attn, tp_ffn, ep_ffn) 튜플 × (P:D) 비율(16:48부터 48:16까지) 스윕. Frontier가 각각을 이산 사건 시뮬로 돌리고, (throughput, p99 TTFT) 공간의 Pareto 프런티어 출력. CUDA Graph Adapter 켬. SLO 안에서 throughput 최대화하는 (P:D, 병렬화) 조합을 답으로 반환.

# paper의 256× H800 예시 결과: PDD P:D = 112:144 → 137.4K tok/s
# 64× H100 스케일로 해석하면 비례적으로 P:D ≈ 28:36 근처가 최적이라 추정

LLMServingSim 2.0으로 푸는 방법

Copy single_node_pd_per_instance_config.json, edit instance counts; run the profiler once on H100 if not shipped, then python -m serving --cluster-config ... --dataset workloads/my_trace.jsonl --output outputs/llama70b_64h100.csv for each split. Pandas-diff the CSVs over p50/p99 TTFT and TPOT. Also gets a power summary at the end (idle/active/standby joules). single_node_pd_per_instance_config.json을 복사해 인스턴스 수만 수정; H100용 프로파일이 없으면 1회 프로파일 후, 각 분할마다 python -m serving --cluster-config ... --dataset workloads/my_trace.jsonl --output outputs/llama70b_64h100.csv. Pandas로 p50/p99 TTFT·TPOT diff. 마지막에 파워 요약(idle/active/standby joules)도 함께.

# 각 sweep 점이 ~10분, 10점이면 약 1.5h
# 동시에 토큰당 에너지 비용도 함께 떨어짐 → 운영비 추정까지

key difference in the answer답의 핵심 차이 Frontier gives you a Pareto front in performance space with CUDA-Graph/speculative effects modeled — closer to "what's the best architecture-and-flag combo?" LLMServingSim 2.0 gives you the same throughput/latency numbers + an energy bill via an explicit power model — closer to "what's the total cost of ownership?" Frontier는 CUDA-Graph·speculative 효과까지 반영한 성능 공간 Pareto 프런티어를 줌 — "어떤 아키텍처 + 플래그 조합이 최선?"에 가까움. LLMServingSim 2.0은 같은 throughput/latency 수치에 명시 파워 모델로 에너지 청구서까지 줌 — "총 소유 비용은?"에 가까움.

7-5. Combined workflow — use both? 조합 워크플로 — 둘 다 쓰면?

They're not mutually exclusive. A reasonable two-stage flow:

서로 배타적이지 않습니다. 합리적인 2단계 흐름:

  1. LLMServingSim 2.0 to pick the HW envelope — sweep "GPU vs GPU+PIM vs GPU+CXL pool" with explicit power, narrow down to 1–2 hardware configurations that hit your energy / cost budget.
  2. Frontier to optimize the serving stack on the chosen HW — sweep CUDA Graphs on/off × speculative on/off × PDD ratios × scheduler choice within the hardware Frontier won.
  1. LLMServingSim 2.0으로 HW 영역 좁히기 — "GPU vs GPU+PIM vs GPU+CXL 풀"을 명시 파워 모델과 함께 스윕, 에너지·비용 예산 안에 드는 HW 후보 1~2개로 좁힘.
  2. Frontier로 선택된 HW 위 서빙 스택 최적화 — CUDA Graphs on/off × speculative on/off × PDD 비율 × 스케줄러 선택을 그 HW 안에서 스윕.

The two are answering "what hardware to buy" vs "how to serve on it" — orthogonal questions, both worth asking before you sign a cluster order.

두 도구는 "어떤 HW를 살까" vs "그 위에서 어떻게 서빙할까"라는 직교 질문에 답합니다. 클러스터 주문서에 사인하기 전 둘 다 짚어볼 만함.
