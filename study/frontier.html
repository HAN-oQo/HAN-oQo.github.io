1 Problem definition 문제 정의

LLM serving has split, in two years, into several architectural species — vanilla co-located inference, Prefill–Decode Disaggregation (PDD), Attention–FFN Disaggregation (AFD), reasoning/agentic stacks with stateful sessions, RL rollout fleets. Yet capacity planning today is still mostly "spin up a real cluster and measure" or "use a simulator that bakes in one fixed architecture."

LLM 서빙은 최근 2년 사이에 여러 아키텍처 종으로 분기했습니다 — 전통적 co-location, Prefill–Decode 분리(PDD), Attention–FFN 분리(AFD), 상태가 유지되는 reasoning/agent 스택, RL rollout 함대. 그런데 캐파시티 플래닝은 여전히 "실 클러스터 띄워 측정" 또는 "한 아키텍처에 고정된 시뮬레이터"로 처리되고 있습니다.

paper's core claim논문의 핵심 주장 Existing simulators' "monolithic-replica abstractions are ill-suited to disaggregated serving, while average-case analytical proxies can distort SLA predictions and even reverse optimization conclusions." → You can't just patch them; you need a simulator built for disaggregation + runtime opts + stateful flows. 기존 시뮬레이터의 "monolithic-replica 추상화는 분리형 서빙에 안 맞고, 평균 기반 분석식은 SLA 예측을 왜곡하거나 심지어 최적화 결론을 뒤집을 수도 있다" → 패치로 해결되지 않고, 분리형 + 런타임 최적화 + 상태 보존을 처음부터 염두에 둔 시뮬레이터가 필요.

Concrete gaps the authors call out저자가 짚는 구체적 빈자리

One-liner: Frontier asks "what if a single simulator could express co-location and PDD and AFD, with CUDA Graphs + speculative + prefix caching turned on, against stateful reasoning traces — and still hit ±4% throughput?"

한 줄: Frontier는 "한 시뮬레이터가 co-location · PDD · AFD를 모두 표현하고, CUDA Graphs + speculative + prefix caching을 켠 상태에서 상태 보존 reasoning trace까지 처리하면서도 throughput ±4%를 지킬 수 있나?"라는 질문에 답합니다.

2 Solution — architecture 해결 — 아키텍처

Frontier is organized into three planes and exposed through four modules:

Frontier는 3개의 plane으로 조직되고 4개 모듈로 노출됩니다:

2-1. The three planes 세 plane

Control Plane

"Compiles a user-level serving specification into a runnable simulation." Sets up Cluster Workers, Replica Workers, Runtime Adapters. Defines what will run. "사용자 서빙 스펙을 실행 가능한 시뮬로 컴파일." Cluster Workers · Replica Workers · Runtime Adapters를 세팅. 무엇이 돌지를 정의.

Fidelity Plan

"Runtime-estimation layer queried by the Execution Plane for every batch iteration." Op-level cost tables for attention / linear / GroupedGEMM / comm. Defines how fast. "Execution Plane이 매 배치 iteration마다 조회하는 런타임 추정 레이어." attention · linear · GroupedGEMM · 통신의 op-level 비용 테이블. 얼마나 빠른지를 정의.

Execution Plane

"Advances the request lifecycle within each replica: admission, batch composition." The discrete-event loop. Defines when things happen. "각 replica의 요청 수명주기를 진행 — admission · 배치 구성." 이산 사건 루프. 언제 일어나는지를 정의.

2-2. The four modules 네 모듈

From the paper: "organized into four modules. ➀ Workload and Config. ➁ Fidelity Plan. ➂ Control Plane. ➃ Execution Plane."

논문: "네 모듈로 조직됨. ➀ Workload and Config. ➁ Fidelity Plan. ➂ Control Plane. ➃ Execution Plane."

#Module모듈Role역할
➀Workload & Config request trace + cluster topology + parallelism tuple (pp, tp_attn, dp_attn, tp_ffn, ep_ffn) 요청 trace + 클러스터 토폴로지 + 병렬화 튜플 (pp, tp_attn, dp_attn, tp_ffn, ep_ffn)
➁Fidelity Plan per-op latency tables (BF16 / FP8) for attention, linear, GroupedGEMM, allreduce/alltoall attention · linear · GroupedGEMM · allreduce/alltoall의 op별 지연 테이블 (BF16/FP8)
➂Control Plane spawns Cluster Workers (one per role) → Replica Workers → installs Runtime Adapters Cluster Workers(역할당 1개) → Replica Workers → Runtime Adapters 설치
➃Execution Plane discrete-event loop driving Scheduler ↔ Batch Engine per replica, with Runtime Adapters in between replica별 Scheduler ↔ Batch Engine 루프를 이산 사건으로 진행, 사이에 Runtime Adapters

2-3. Worker hierarchy — the heart of "disaggregated abstraction" Worker 계층 — "분리형 추상화"의 핵심

The key abstraction: a Cluster Worker "represents a logical device group serving a specific role." For co-location, there's one role. For PDD, two roles (prefill, decode). For AFD, two roles (attention, FFN). The Control Plane builds whichever shape matches your config — no special-case code per architecture.

핵심 추상화: Cluster Worker는 "특정 역할을 수행하는 논리 디바이스 그룹". Co-location은 역할 1개, PDD는 2개(prefill, decode), AFD도 2개(attention, FFN). Control Plane이 설정에 맞는 형태를 빌드 — 아키텍처별 분기 코드 없음.

2-4. Runtime Adapters — features as middleware Runtime Adapters — 기능을 미들웨어처럼

From the paper: "Runtime Adapters are feature-specific rules attached to the Scheduler–Batch Engine loop." Each runtime optimization is one Adapter that reshapes a batch before execution:

논문: "Runtime Adapter는 Scheduler–Batch Engine 루프에 부착되는 기능별 규칙." 각 런타임 최적화가 Adapter 1개로 표현되며 실행 직전에 배치를 재구성합니다:

  • CUDA Graph adapter — pads decode batches to graph-friendly shapes; the Fidelity Plan returns the (much faster) graph latency for those shapes.
  • Speculative decoding adapter — multiplies the per-iteration token yield based on accept rate, with an extra verify-pass cost.
  • Chunked prefill adapter — slices long prompts into fixed-size chunks across iterations.
  • Prefix caching adapter — hits the cache before scheduling, updates the cache after eviction.
  • CUDA Graph adapter — decode 배치를 그래프 친화적 shape으로 패딩; Fidelity Plan이 그 shape에서의 (훨씬 빠른) 그래프 지연을 반환.
  • Speculative decoding adapter — accept rate에 따라 iteration당 토큰 산출량을 곱해주고, verify-pass 비용을 추가.
  • Chunked prefill adapter — 긴 프롬프트를 iteration들에 걸쳐 고정 chunk로 분할.
  • Prefix caching adapter — 스케줄링 전 캐시 조회, 축출 시 캐시 갱신.

Why this matters: adding a new feature = writing a new Adapter, not patching the scheduler. The paper claims this is why Frontier alone reproduces the 2.86–3.05× CUDA Graph speedup envelope within ~2–6% — older simulators can't even express it.

의미: 새 기능 추가 = Adapter 1개 새로 작성, 스케줄러 패치 불필요. Frontier가 CUDA Graph speedup 2.86–3.05× 영역을 ~2~6% 내로 재현하는 이유 — 구버전 시뮬레이터들은 그 동작 자체를 표현 못 함.

3 Concrete usage 구체적 사용

Frontier's spec is "compile a user-level serving specification into a runnable simulation." So the user input is a config that names the architecture, parallelism, optimizations, and workload — and Frontier produces per-request metrics. Below are the four use cases the paper itself walks through, each of which is a worked example of "what would I actually use this for?"

Frontier의 사양은 "사용자 서빙 스펙을 실행 가능한 시뮬로 컴파일". 사용자 입력은 아키텍처·병렬화·최적화·워크로드를 명시한 config, 출력은 요청별 메트릭. 아래는 논문이 직접 다루는 4개 use case — 각각 "실제로 이걸 뭐에 쓸 건데?"의 답.

3-4. Use case 4 — RL rollout reconfiguration Use case 4 — RL rollout 재구성

Question: "An RL rollout cycle has a trajectory-generation phase (decode-heavy) and a reward-update phase. Should I switch parallelism layout mid-flight?"

질문: "RL rollout 사이클엔 trajectory 생성(decode 중심) 단계와 reward 업데이트 단계가 있음. 도중에 병렬화 레이아웃 전환을 해야 하나?"

while not events.empty():
    ev = events.pop_min_time()
    sim_clock = ev.time

    if isinstance(ev, ArrivalEvent):
        replica = router.pick(ev.request)
        replica.scheduler.admit(ev.request)

    if isinstance(ev, IterationTick):
        replica = ev.replica
        batch = replica.scheduler.compose()
        for a in replica.adapters:
            batch = a.reshape_batch(batch)
        cost = replica.fidelity_plan.estimate(batch)
        for a in replica.adapters:
            cost = a.amend_cost(cost)
        replica.batch_engine.step(batch, cost)
        events.push(IterationTick(time=sim_clock + cost.latency, replica=replica))
        for req in batch.completed():
            emit(req.metrics)

5-3. Why this design scales to 1K+ GPUs on CPU 왜 이 구조가 CPU에서 GPU 1K+ 까지 확장되는가

  • Discrete-event loop is O(events), not O(GPU-cycles). Number of events grows with requests × iterations, not with GPU count.
  • Fidelity Plan is table lookup (interpolated over (batch_size, seq_len, dtype)), not kernel simulation. Roughly μs per query.
  • Replicas are independent state machines; their cross-replica events are the only synchronization. Easy to parallelize, but even single-threaded handles thousands.
  • The 70K LoC is mostly the variety of Adapters / KVCacheModels / Workload types — the core loop is small.
  • 이산 사건 루프는 O(이벤트 수)이지 O(GPU 사이클)이 아님. 이벤트는 요청 × iteration에 비례, GPU 수에 비례 안 함.
  • Fidelity Plan은 테이블 룩업((batch_size, seq_len, dtype) 보간), 커널 시뮬 아님. 쿼리당 μs급.
  • Replica들은 독립 상태기계, 동기화는 cross-replica 이벤트뿐. 병렬화도 쉽지만 싱글 스레드로도 수천 개 처리 가능.
  • 70K LoC는 대부분 Adapter · KVCacheModel · Workload 유형의 다양성 — 코어 루프는 작음.

6 Takeaways 정리

what's actually new새로운 것
  • Disaggregated abstraction as a first-class primitive (Cluster Worker × role × Replica Worker × parallelism tuple) — same code path for co-location, PDD, AFD.
  • Runtime features as middleware Adapters — CUDA Graphs, speculative, chunked prefill, prefix caching are pluggable rules, not patches to the scheduler.
  • Stateful workloads supported — reasoning sessions, agentic loops, RL rollouts; phase-aware scheduling and dynamic parallelism reconfiguration testable end-to-end.
  • ±4% throughput, ±2.6–6.4% latency on 16-H800, scalable to 1K+ GPU sims on CPU.
  • 분리형 추상화가 1급 primitive (Cluster Worker × 역할 × Replica Worker × 병렬화 튜플) — co-location · PDD · AFD가 같은 코드 경로.
  • 런타임 기능을 미들웨어 Adapter로 — CUDA Graphs · speculative · chunked prefill · prefix caching이 플러그형 규칙, 스케줄러 패치 아님.
  • 상태 보존 워크로드 지원 — reasoning 세션 · 에이전트 루프 · RL rollout. phase-aware 스케줄링과 동적 병렬화 재구성을 end-to-end로 테스트 가능.
  • throughput ±4%, latency ±2.6~6.4% (16× H800), CPU에서 GPU 1K+ 시뮬까지 확장.

One-line picker: if your bottleneck is "do I split prefill–decode and turn on speculative for this LLM stack?" → Frontier. If your bottleneck is "what does a CXL-pooled, PIM-augmented cluster look like with this LLM?" → LLMServingSim 2.0. Both can answer the other's question but each is sharper on its home turf.

한 줄 선택 기준: 병목이 "이 LLM 스택에 prefill–decode 분리하고 speculative을 켤까?" 면 → Frontier. 병목이 "CXL 풀 + PIM 보강된 클러스터에서 이 LLM이 어떻게 도나?" 면 → LLMServingSim 2.0. 둘 다 상대 영역도 다루지만 자기 영역에서 더 날카로움.

If I were to extend Frontier Frontier를 확장한다면

  • A Runtime Adapter for EAGLE / Medusa-style draft models alongside MTP, so you can A/B different speculation schemes.
  • A Cluster Worker role for retrieval (RAG) — separate "embedding-and-vectordb" replicas with their own SLO, since long-context flows are increasingly RAG-mixed.
  • Plug a real vLLM event stream (BlockStored/Removed, completed-request) into Frontier's event queue for hybrid sim+real shadow tests.
  • MTP 외에 EAGLE / Medusa 스타일 draft 모델용 Runtime Adapter — speculation 기법 A/B.
  • retrieval(RAG)용 Cluster Worker 역할 — "embedding + vectordb" replica를 자체 SLO로 분리. 롱컨텍스트 흐름이 점점 RAG와 결합되는 추세 반영.
  • 실제 vLLM 이벤트 스트림(BlockStored/Removed, completed-request)을 Frontier 이벤트 큐에 꽂아 hybrid sim+real shadow 테스트.
