one-line summary한 줄 요약 vLLM's V1 scheduler has no separate prefill and decode phases. Every step it walks two queues — running (decodes + in-flight prefill chunks) then waiting (brand-new requests) — and hands each request just enough tokens to advance, draining one shared token budget (max_num_batched_tokens) until it hits zero or the running count hits max_num_seqs (effective defaults are hardware/usage-dependent — e.g. 8192/1024 on a big-GPU server, not the 2048/128 class fallback; §7). So a single step can start many prefills at once — not one — limited only by those two numbers; a long prompt is simply chunked across steps while decodes ride along. When there aren't enough KV blocks, allocation refuses and the scheduler preempts a running request back to the waiting queue. The V0 → V1 story: continuous batching (requests joining/leaving each iteration) always existed; mixing prefill+decode in one forward pass is chunked prefill, which was opt-in on V0 and is the only, always-on path on V1. vLLM V1 스케줄러엔 prefill 단계와 decode 단계 구분이 없다. 매 스텝 두 큐를 훑는다 — running(decode + 진행 중인 prefill 청크) 다음 waiting(새 요청) — 각 요청에 전진할 만큼만 토큰을 주며 하나의 공유 token budget(max_num_batched_tokens)을 0이 되거나 running 수가 max_num_seqs에 닿을 때까지 소진한다(실효 기본값은 하드웨어/용도에 따라 다름 — 예: 대형 GPU 서버에서 8192/1024, 클래스 fallback 2048/128이 아님; §7). 그래서 한 스텝이 prefill을 여러 개 동시에 시작할 수 있다 — 하나가 아니라 — 오직 그 두 숫자로만 제한된다; 긴 프롬프트는 그냥 스텝에 걸쳐 청크로 잘리고 decode가 같이 탄다. KV block이 모자라면 할당이 거부되고 스케줄러는 running 요청을 waiting 큐로 preempt한다. V0 → V1 이야기: continuous batching(요청이 iteration마다 들고 남)은 늘 있었고; prefill+decode를 한 forward에 섞는 게 chunked prefill인데, V0에선 opt-in, V1에선 유일·상시 경로다.

1The one idea: there is no prefill phase한 가지 생각: prefill 단계는 없다

If you remember one thing about the V1 scheduler, make it this — and it's the maintainers' own opening comment on the algorithm: V1 스케줄러에서 하나만 기억한다면 이것 — 그리고 이건 알고리즘에 대한 관리자들 자신의 첫 주석이다:

"There's no "decoding phase" nor "prefill phase" in the scheduler. Each request just has the num_computed_tokens and num_tokens_with_spec … At each step, the scheduler tries to assign tokens to the requests so that each request's num_computed_tokens can catch up its num_tokens_with_spec."

— vllm/v1/core/sched/scheduler.py, schedule() · L442–L450

Every request carries two numbers: num_computed_tokens (how far it's been processed) and num_tokens (how far it needs to go — prompt, plus any tokens generated so far, plus speculative tokens). The scheduler's whole job each step is to give each request some new tokens to close that gap: 모든 요청은 두 숫자를 지닌다: num_computed_tokens(얼마나 처리됐나)와 num_tokens(얼마나 가야 하나 — 프롬프트 + 지금까지 생성한 토큰 + speculative 토큰). 스케줄러의 매 스텝 일은 그 격차를 좁히도록 각 요청에 새 토큰을 주는 것뿐이다:

  • A fresh request has num_computed_tokens = 0 and a 4000-token gap → give it a chunk. That's "prefill."새 요청은 num_computed_tokens = 0이고 4000토큰 격차 → 청크를 준다. 그게 "prefill".
  • A generating request has closed its prompt gap → give it exactly 1 new token. That's "decode."생성 중 요청은 프롬프트 격차를 닫음 → 정확히 새 토큰 1개를 준다. 그게 "decode".

Prefill and decode aren't modes the scheduler is in — they're just two sizes of the same "give this request N new tokens" action (a big N vs N=1). That is why they can trivially sit in the same batch: to the scheduler they're the same operation. Everything below follows from this. prefill과 decode는 스케줄러가 처한 모드가 아니라 — 같은 "이 요청에 새 토큰 N개 줘라" 동작의 두 크기일 뿐이다(큰 N vs N=1). 그래서 둘은 자연스럽게 한 배치에 앉을 수 있다: 스케줄러에겐 같은 연산이다. 아래 전부가 여기서 따라 나온다.

2Static vs continuous vs chunked — and why mixing ≠ continuous batchingstatic vs continuous vs chunked — 왜 혼합 ≠ continuous batching

This is the knot worth untangling carefully, because "continuous batching" and "mixing prefill with decode" get conflated. They are two different levels. Here are all three batching regimes on one timeline: 이건 조심히 풀 만한 매듭이다. "continuous batching"과 "prefill을 decode와 섞기"가 뒤섞여 쓰이기 때문. 둘은 다른 층위다. 세 가지 배칭 방식을 한 타임라인에 놓으면:

Fig 1 — Three regimes. ① static: slots idle until all finish. ② continuous batching (early V0): a new request joins, but via its own prefill step that stalls running decodes. ③ chunked prefill (V0 opt-in, V1 always): the new request's prefill is chunked and shares each step with decodes — no stall. Continuous batching is the ①→② jump; mixing is the ②→③ jump. Original diagram.그림 1 — 세 방식. ① static: 다 끝날 때까지 슬롯 idle. ② continuous batching(초기 V0): 새 요청이 합류하되 running decode를 멈추는 자체 prefill 스텝을 통해. ③ chunked prefill(V0 opt-in, V1 상시): 새 요청 prefill이 청크로 잘려 매 스텝을 decode와 공유 — stall 없음. continuous batching은 ①→② 도약; 혼합은 ②→③ 도약. 직접 작성한 다이어그램.

So the answer to "if they don't mix, isn't continuous batching broken?" is no. Regime ② is fully continuous — request C joins the running batch the moment its prefill step finishes, and finished requests free their slots immediately. What ② lacks is only the smoothness: C's prefill monopolizes one step, so A and B emit no token that tick (a latency hiccup, not a batching failure). Chunked prefill (③) removes that hiccup by letting C's prefill share the step. Mixing is a latency/utilization optimization layered on top of continuous batching, not a precondition for it. 그래서 "섞지 않으면 continuous batching이 깨지는 거 아니냐?"의 답은 아니오다. 방식 ②는 완전히 continuous다 — 요청 C는 자기 prefill 스텝이 끝나는 순간 running 배치에 합류하고, 끝난 요청은 즉시 슬롯을 반납한다. ②에 없는 건 오직 매끄러움뿐: C의 prefill이 한 스텝을 독점해 A·B가 그 텀에 토큰을 못 낸다(지연 딸꾹질이지, 배칭 실패가 아니다). chunked prefill(③)은 C의 prefill이 스텝을 공유하게 해서 그 딸꾹질을 없앤다. 혼합은 continuous batching 위에 얹은 지연/활용 최적화이지, 그 전제가 아니다.

3Inside schedule() — two loops, one token budgetschedule() 내부 — 두 루프, 하나의 token budget

Each step, schedule() starts with a fresh token budget and spends it across two loops in order. Think of the budget as a jar of max_num_batched_tokens coins; each request scheduled takes some coins out. 매 스텝 schedule()는 새 token budget으로 시작해 두 루프에 순서대로 쓴다. budget을 max_num_batched_tokens개 동전이 든 항아리라 생각하자; 스케줄되는 요청마다 동전을 꺼내 간다.

# vllm/v1/core/sched/scheduler.py:459
token_budget = self.max_num_scheduled_tokens   # = max_num_batched_tokens (default 2048)

Fig 2 — One step of schedule(). A single token_budget is drained by the running loop (decodes + continuing prefill chunks) then the waiting loop (new requests), which keeps admitting prefills until the budget hits 0 or the running count reaches max_num_seqs. The resulting mixed batch is one GPU forward pass. Original diagram; per scheduler.py:459/485/687.그림 2 — schedule() 한 스텝. 하나의 token_budget을 running 루프(decode + 이어지는 prefill 청크)가, 이어 waiting 루프(새 요청)가 소진하며, budget이 0이 되거나 running 수가 max_num_seqs에 닿을 때까지 prefill을 계속 admit한다. 결과인 혼합 배치가 GPU forward 한 번. 직접 작성한 다이어그램; 출처 scheduler.py:459/485/687.

Loop 1 — the running set (decodes + in-flight prefills)루프 1 — running 집합 (decode + 진행 중 prefill)

The first loop walks self.running. A decode wants 1 new token (plus speculative tokens if any); an in-flight prefill chunk wants as many as the budget allows. Either way it's the same subtraction: 첫 루프는 self.running을 훑는다. decode는 새 토큰 1개(있으면 speculative 포함)를, 진행 중 prefill 청크는 budget이 허락하는 만큼을 원한다. 어느 쪽이든 같은 뺄셈이다:

# vllm/v1/core/sched/scheduler.py:485
while req_index < len(self.running) and token_budget > 0:
    ...
    num_new_tokens = min(num_new_tokens, token_budget)   # decode → 1; prefill → a chunk
    ...
    token_budget -= num_new_tokens                       # scheduler.py:637

Loop 2 — the waiting set (this is where new prefills enter)루프 2 — waiting 집합 (새 prefill이 들어오는 곳)

The second loop is a while over the waiting queue — and because it's a while, not an if, it admits as many new requests as fit. Its two stop conditions are the entire answer to "how many prefills per step?": 둘째 루프는 waiting 큐에 대한 while이고 — if가 아니라 while이라 — 들어맞는 만큼 새 요청을 admit한다. 그 두 정지 조건이 "한 스텝에 prefill 몇 개?"의 답 전부다:

# vllm/v1/core/sched/scheduler.py:687
while (self.waiting or self.skipped_waiting) and token_budget > 0:   # ← STOP if budget spent
    num_running = len(self.running) + self.num_waiting_for_streaming_input
    if num_running >= self.max_num_running_reqs:                     # ← STOP at max_num_seqs
        break
    ...
    token_budget -= num_new_tokens                                   # scheduler.py:1073

No third condition. In particular there is no cap on the number of concurrent partial prefills in V1 — the old V0 knob max_num_partial_prefills does not exist in this scheduler. Only the token budget and max_num_seqs gate it. 세 번째 조건은 없다. 특히 V1엔 동시 부분-prefill 개수 상한이 없다 — 옛 V0 노브 max_num_partial_prefills는 이 스케줄러에 존재하지 않는다. 오직 token budget과 max_num_seqs만 통제한다.

4How many prefills per step? (a worked example)한 스텝에 prefill 몇 개? (예시로)

Now the concrete answer. Take a budget of max_num_batched_tokens = 2048 and max_num_seqs = 128 (the SchedulerConfig fallback — real per-context defaults are higher, §7; the arithmetic is identical at any budget), and suppose 48 decodes are already running (they eat 48 tokens — one each). That leaves 2000 tokens for the waiting loop to admit new prefills. How many it admits depends entirely on the prompt lengths: 이제 구체적인 답. budget max_num_batched_tokens = 2048, max_num_seqs = 128(SchedulerConfig fallback — 실제 용도별 기본값은 더 큼, §7; 계산은 어떤 budget에서도 동일)이고, decode 48개가 이미 돌고 있다 하자(각 1토큰씩 48토큰 소비). 그러면 waiting 루프가 새 prefill을 admit할 2000토큰이 남는다. 몇 개를 admit하느냐는 오직 프롬프트 길이에 달렸다:

Fig 3 — Prefills per step is a budget-division outcome, not a fixed limit. With 2000 tokens free, four 500-token prompts all start in one step; a single 5000-token prompt takes a 2000-token chunk and fills the budget alone. Both obey the exact same waiting loop. Original diagram.그림 3 — 스텝당 prefill 수는 budget 나눗셈의 결과이지 고정 한도가 아니다. 2000토큰이 남으면 500토큰 프롬프트 4개가 한 스텝에 다 시작하고; 5000토큰 프롬프트 하나는 2000토큰 청크를 가져가 혼자 budget을 채운다. 둘 다 똑같은 waiting 루프를 따른다. 직접 작성한 다이어그램.

The chunk size for each new prefill is exactly this clamp — take the whole remaining prompt, unless a long_prefill_token_threshold caps it, then never exceed the remaining budget: 각 새 prefill의 청크 크기는 정확히 이 클램프다 — 남은 프롬프트 전부를 가져오되, long_prefill_token_threshold가 있으면 그걸로 캡하고, 남은 budget을 절대 넘지 않는다:

# vllm/v1/core/sched/scheduler.py:899  (waiting-loop chunk sizing)
threshold = self.scheduler_config.long_prefill_token_threshold
if 0 < threshold < num_new_tokens:
    num_new_tokens = threshold              # cap one prefill's per-step size
...
num_new_tokens = min(num_new_tokens, token_budget)   # never exceed the jar
the two ways to change the answer답을 바꾸는 두 방법

1. --long-prefill-token-threshold. In Scenario B, set it to 1024 and prompt C's chunk becomes 1024, not 2000 — leaving 976 tokens for the waiting loop to admit a second new prefill this same step. It's the knob for "don't let one giant prompt hog the batch." 2. --max-num-seqs. If 128 requests are already running, the waiting loop breaks on its very first check (num_running ≥ max_num_seqs) and admits zero new prefills this step no matter how much budget is free — the count cap, not the token cap, is binding. 1. --long-prefill-token-threshold. Scenario B에서 1024로 두면 프롬프트 C의 청크가 2000이 아니라 1024가 되고 — 976토큰이 남아 waiting 루프가 같은 스텝에 두 번째 새 prefill을 admit한다. "거대한 프롬프트 하나가 배치를 독점하지 못하게" 하는 노브다. 2. --max-num-seqs. 이미 128개가 돌고 있으면 waiting 루프는 첫 확인(num_running ≥ max_num_seqs)에서 break해 budget이 아무리 남아도 새 prefill을 0개 admit한다 — token 상한이 아니라 개수 상한이 걸리는 경우.

  • chunk sizing (threshold + budget clamp) · defaults 2048 / 128 · long_prefill_token_threshold

5Chunked prefill across steps — following one long prompt스텝을 가로지르는 chunked prefill — 긴 프롬프트 하나 따라가기

Scenario B left prompt C with 3000 tokens still to prefill. Here's what happens over the next steps — and notice C moves from the waiting loop to the running loop the moment its first chunk is scheduled (it's now an "in-flight prefill"), and it flips to decode the moment its prompt is fully computed: Scenario B는 프롬프트 C에 아직 prefill할 3000토큰을 남겼다. 다음 스텝들에서 벌어지는 일 — 그리고 C가 첫 청크가 스케줄되는 순간 waiting 루프에서 running 루프로 이동(이제 "진행 중 prefill")하고, 프롬프트가 완전히 계산되는 순간 decode로 전환되는 것에 주목:

This is the trade the token budget controls: it's the TTFT ⇄ decode-smoothness dial. A big max_num_batched_tokens gives fat prefill chunks (a prompt finishes in fewer steps → lower time-to-first-token) but a fatter prefill can crowd the decodes' share of a step, adding inter-token jitter. A small budget does the reverse. There is no separate "prefill vs decode priority" flag to tune — you tune this one number, and the running-loop-first ordering already gives decodes first claim on the budget. 이게 token budget이 조절하는 거래다: TTFT ⇄ decode 매끄러움 다이얼. 큰 max_num_batched_tokens는 두꺼운 prefill 청크를 줘(프롬프트가 더 적은 스텝에 끝남 → 낮은 TTFT) 하지만 두꺼운 prefill이 한 스텝에서 decode 몫을 밀어내 토큰 간 지터를 더할 수 있다. 작은 budget은 반대. 별도의 "prefill vs decode 우선순위" 플래그는 없다 — 이 숫자 하나를 튜닝하면 되고, running-루프-먼저 순서가 이미 decode에 budget 우선권을 준다.

6Preemption — when a step runs out of blocksPreemption — 스텝에 block이 모자랄 때

The token budget caps compute per step, but there's a second, harder limit: KV-cache blocks. A decode needs a fresh block every time its current block fills up (every 16 tokens). If the block pool has no free block, the allocator returns None — and the scheduler must make room by preempting a running request: token budget은 스텝당 연산을 제한하지만, 더 딱딱한 두 번째 한계가 있다: KV 캐시 block. decode는 현재 block이 찰 때마다(16토큰마다) 새 block이 필요하다. block 풀에 free block이 없으면 할당기는 None을 반환하고 — 스케줄러는 running 요청을 preempt해 자리를 만들어야 한다:

Fig 5 — Preemption. When block allocation returns None, the scheduler pops a running request (FCFS: the newest; PRIORITY: the lowest-priority), frees its KV blocks back to the pool, and returns it to the waiting queue as PREEMPTED. It re-prefills later — partially, if its prefix is still cached. Editor's note — our take (not a vLLM claim)편집자 주 — 우리 관점 (vLLM의 주장 아님)

For MI250/MI300x serving, the practical reading: (1) report the effective defaults, don't quote 2048/128. On a ≥70GB AMD GPU via vllm serve you're actually at 8192/1024 — benchmarks that assume the class fallback will misjudge concurrency. (2) The token budget is your single most important latency knob, and it's a TTFT ⇄ ITL trade, not a throughput free-lunch — raise it and long prompts prefill faster but decodes jitter; the A100 regression baked into the code (PR #17885) is a live warning that "bigger budget = faster" is false on some hardware, so measure per-GPU. (3) When you see decode latency cliffs under load, suspect preemption (§6), not the kernel — it's driven by block exhaustion, i.e. the KV budget from the block-management note, and is tuned with gpu_memory_utilization + max_num_seqs, not by touching the scheduler. The scheduler itself is cheap host-side bookkeeping; its whole job is to keep the GPU's one forward pass per step as full as the budget and the block pool allow. MI250/MI300x 서빙 관점의 실무 독법: (1) 실효 기본값을 보고하라, 2048/128을 인용하지 말고. ≥70GB AMD GPU에서 vllm serve면 실제로 8192/1024다 — 클래스 fallback을 가정한 벤치는 동시성을 오판한다. (2) token budget이 가장 중요한 지연 노브이고, throughput 공짜가 아니라 TTFT ⇄ ITL 거래다 — 올리면 긴 프롬프트 prefill은 빨라지지만 decode가 지터; 코드에 박힌 A100 회귀(PR #17885)는 "budget 크면 빠르다"가 일부 하드웨어에선 거짓이라는 살아있는 경고니 GPU별로 측정하라. (3) 부하 하 decode 지연 절벽이 보이면 커널이 아니라 preemption(§6)을 의심하라 — block 고갈, 즉 block 관리 노트의 KV budget이 원인이고, 스케줄러가 아니라 gpu_memory_utilization + max_num_seqs로 튜닝한다. 스케줄러 자체는 값싼 호스트 장부질이고, 그 일 전부는 스텝당 GPU forward 한 번을 budget과 block 풀이 허락하는 만큼 꽉 채우는 것이다.
