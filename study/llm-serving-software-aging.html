one-line summary한 줄 요약 Run six LLM serving deployments for 36 hours each under identical Poisson stress, and all of them develop a statistically significant private-memory leak — but the rates span two orders of magnitude (vLLM V1 standalone +1.8 KB/h … Triton+V0 +157 KB/h), none of it visible in latency/throughput, all of it living in the runtime around the model rather than the inference path. 6개 LLM 서빙 배포를 동일한 Poisson 스트레스로 36시간씩 돌리면 전부 통계적으로 유의한 프로세스 전용 메모리 누수가 생긴다 — 단, 누수율은 두 자릿수 배율로 갈리고(vLLM V1 단독 +1.8 KB/h … Triton+V0 +157 KB/h), 레이턴시/스루풋에는 전혀 안 보이며, 원인은 추론 경로가 아니라 모델을 둘러싼 런타임에 있다.

vLLM and NVIDIA Triton run continuously on expensive GPUs and are expected to behave predictably for days or months. Yet virtually everything we know about them comes from short benchmarks.

vLLM과 NVIDIA Triton은 비싼 GPU 위에서 상시 구동되고, 며칠~몇 달 단위로 예측 가능하게 동작해야 합니다. 그런데 우리가 아는 거의 모든 수치는 짧은 벤치마크에서 나온 것입니다.

1.3 — Background: the engines under study (§II-A) 1.3 — 배경: 연구 대상 엔진들 (§II-A)

A serving engine is a long-running process that loads the model into GPU memory once and answers requests by autoregressive generation. Each active request drags along a KV-cache that "can occupy hundreds of megabytes of GPU memory and grows for the entire duration of that request" (§II-A ¶1) — so the central engineering problem is GPU memory management, attacked with continuous batching and paged attention (vLLM being the reference implementation).

서빙 엔진은 모델을 GPU 메모리에 한 번 적재한 뒤 자가회귀 생성으로 요청에 응답하는 장기 실행 프로세스입니다. 활성 요청 하나하나가 KV-cache를 끌고 다니는데, 이는 "수백 MB의 GPU 메모리를 점유하며 요청이 살아있는 내내 자란다"(§II-A ¶1)고 합니다. 그래서 핵심 엔지니어링 문제는 GPU 메모리 관리이고, continuous batching과 paged attention(vLLM이 레퍼런스 구현)으로 대응합니다.

Inside vLLM, two engine generations coexist — and whether the choice matters for reliability was an open question this paper sets out to answer:

vLLM 내부에는 두 엔진 세대가 공존하는데, 이 선택이 신뢰성에 영향을 주는지는 이 논문이 답하려는 미해결 질문이었습니다:

"The two engines share the same paged-attention algorithm and the same external API; they differ in how requests are scheduled and batched and in how per-request resources are acquired and released. Whether this choice has reliability consequences over long-running operation is, to our knowledge, an open question."

— §II-A, ¶3 (V0 = 동기식 레거시, V1 = 비동기 재설계·현재 기본값이지만 experimental) · 원문 보기 (§II-A)

2.2 — Workload & stress calibration 2.2 — 워크로드와 스트레스 캘리브레이션

  • Open-loop Poisson client, one per engine.
  • Prompts: drawn from 3000 arXiv abstracts/titles, concatenated to log-normal lengths 256–7500 tokens (median 1500).
  • Output: log-normal, median 200 / max 1500 tokens; streaming with probability 0.7.
  • Calibration: sweep the request rate until throughput stops growing → that's the engine's mechanical ceiling; the aging run then targets 85% of the ceiling.
  • Open-loop Poisson 클라이언트, 엔진당 1개.
  • 프롬프트: arXiv 초록/제목 3000개 코퍼스에서 추출, 로그정규 길이 256–7500 토큰(중앙값 1500)으로 이어붙임.
  • 출력: 로그정규, 중앙값 200 / 최대 1500 토큰; 확률 0.7로 스트리밍.
  • 캘리브레이션: 처리량이 더 늘지 않을 때까지 요청률을 올려 기계적 천장(ceiling)을 찾고, 에이징 본 실험은 천장의 85%를 목표율로 고정.

"We use the ceiling rather than the highest rate at which the client does not yet drop, because the ceiling is a property of the engine itself, while the no-drop rate is partly an artefact of the client-side concurrency cap."

2.5 — The statistical pipeline: built for autocorrelated traces 2.5 — 통계 파이프라인: 자기상관 데이터 전용 설계

"the resident memory of a process at time t is almost identical to its value at t−1, and naive tests that treat samples as independent produce drastically deflated p-values."

— §III, "Statistical Analysis" · 원문 보기 (§III)
  • Existence of trend: Mann-Kendall with the Hamed-Rao correction — inflates test variance by an effective-sample-size factor from the empirical autocorrelation function.
  • Magnitude: Theil-Sen slope with an exact confidence interval from order statistics of pairwise slopes, variance inflated by the lag-1 AR(1) factor (1+ρ)/(1−ρ).
  • Decision rule: a trend is significant only when both agree — Mann-Kendall rejects the null AND the 95% Theil-Sen interval excludes zero.
  • Multiple testing: ~34 indicators × 6 runs ≈ 200 tests → Benjamini-Hochberg FDR at q = 0.10.
  • Pre-registration de facto: the indicator list is fixed by the monitor schemas before any long-run data is examined; cumulative counters (ctx-switches, I/O bytes) are converted to per-second rates "since they trend monotonically by construction and would yield trivially significant 'aging'".
  • 추세 존재: Mann-Kendall + Hamed-Rao 보정 — 경험적 자기상관 함수에서 유효 표본 크기 계수를 구해 검정 분산을 부풀림.
  • 추세 크기: Theil-Sen 기울기 + 쌍별 기울기의 순서통계량으로 만든 정확 신뢰구간, lag-1 AR(1) 계수 (1+ρ)/(1−ρ)로 분산 보정.
  • 판정 규칙: 둘 다 동의할 때만 유의 — Mann-Kendall이 귀무가설을 기각하고 95% Theil-Sen 구간이 0을 제외해야 함.
  • 다중검정: 지표 ~34개 × 6런 ≈ 200회 검정 → Benjamini-Hochberg FDR q = 0.10.
  • 사실상의 사전등록: 지표 목록은 장기 데이터를 보기 전에 모니터 스키마로 고정; 누적 카운터(ctx-switch, I/O bytes)는 "구조적으로 단조 증가해 자명하게 유의한 '에이징'을 만들어내므로" 초당 비율로 변환.

Across all runs, end-to-end latency (p50/p95/p99), TTFT (p50/p99), output throughput, and drop rate are stationary — Theil-Sen CIs include zero. The only exceptions are tiny trends on E1 (p50 +≈5 ms/h, TTFT a fraction of a ms/h, throughput slightly rising — the wrong direction for aging), about 2% of baseline over 36 h. E3's 15.6% drop rate is a steady capacity ceiling, not a growing loss.

"for all practical purposes, none of the engines degrades visibly to a production operator over 36 hours of sustained high load. As the next section shows, this stability is only skin-deep: once we look inside the engine process, a different picture emerges."

The localization argument — all three run the same model and the same inference computations, so:

누수 위치를 좁히는 논증 — 셋 다 같은 모델, 같은 추론 연산을 수행하므로:

"If the leak originated from the inference path, we would expect similar leak rates across all deployments. Instead, the observed rates differ by nearly two orders of magnitude. Everything else is quiet: CPU, threads, FDs, context-switch and I/O rates stay essentially flat ("aging manifests as a memory issue rather than as scheduler drift, descriptor leakage, or I/O degradation", §IV-C ¶4). 그 외는 전부 조용합니다: CPU, 스레드 수, FD 수, 컨텍스트 스위치·I/O 비율 모두 사실상 평탄("이 시간 척도에서 에이징은 스케줄러 드리프트나 디스크립터 누수, I/O 열화가 아니라 메모리 문제로 나타난다", §IV-C ¶4). GPU 쪽도 — 저자들 스스로 캐싱 할당기 단편화를 예상했음에도 — 어떤 배포에서도 VRAM에 유의한 추세가 없습니다 (§IV-C ¶5).

3.4 — Low-load ablation: the leak is time-driven, not request-driven (§IV-D) 3.4 — 저부하 ablation: 누수는 요청이 아니라 시간이 만든다 (§IV-D)

Re-running the naive server at 0.05 RPS (E3b, far below saturation): the leak persists and actually grows — from +31 KB/h (saturated) to +103 KB/h (sub-saturated).

순정 서버를 0.05 RPS(포화점보다 한참 아래)로 다시 돌린 결과(E3b): 누수는 사라지기는커녕 오히려 커집니다 — 포화 시 +31 KB/h에서 저부하 시 +103 KB/h로.

"This result indicates that the leak is not caused by queueing effects or saturation-related behavior. Instead, it appears to be intrinsic to the runtime environment. The higher leak rate at lower load also suggests that memory growth is driven primarily by elapsed time rather than by the number of processed requests."

— §IV-D · 원문 보기 (§IV-D)

Bonus finding in both PyTorch runs: virtual memory grows far faster than resident memory — in E3b, VMS +≈127 MB/h (~7.5 GB over 36 h) vs RSS +≈20 MB total, while threads and FDs stay flat. That rules out thread/descriptor leakage and "points to ongoing reservation of anonymous address space, which is consistent with the host-side management performed by the CUDA caching allocator" (§IV-D). Whether this VMS growth ever becomes a resident-memory cost is left open.

PyTorch 두 런의 추가 발견: 가상 메모리가 상주 메모리보다 훨씬 빨리 자랍니다 — E3b에서 VMS는 시간당 +≈127 MB(36시간에 ~7.5 GB)인데 RSS는 총 +≈20 MB뿐, 스레드와 FD는 평탄. 따라서 스레드/디스크립터 누수는 배제되고 "익명 주소 공간의 지속적 예약을 가리키며, 이는 CUDA 캐싱 할당기의 호스트 측 관리와 부합한다"(§IV-D). 이 VMS 증가가 언젠가 상주 메모리 비용으로 전환되는지는 미해결로 남습니다.

기울기 추정으로는 안 잡히는 정성적 시그니처도 있습니다: E2만 계단식으로 자랍니다. 상위 1% 메모리 증분이 1.8 MB에 육박하고, RSS와 VMS가 함께 점프합니다(동시점 상관 ρ ≈ 0.83, 나머지 구성은 증분이 0 근처에 머물며 ρ < 0.35):

4 Takeaways 시사점

4.1 — The paper's three findings (§VI) 4.1 — 논문의 세 가지 결론 (§VI)

  • Software aging exists in GPU LLM serving. "Every deployment exhibits a small but statistically significant process-private memory leak over a 36-hour window."
  • It is not a property of the model or inference path. "Deployments running the same model and serving the same workload can differ by nearly two orders of magnitude in leak rate, showing that the runtime and hosting environment play a central role."
  • Not all leaks look the same. "Most deployments exhibit smooth memory growth, whereas Triton+V0 shows a distinctive step-wise pattern in RSS and VMS, suggesting a different underlying mechanism."
  • GPU LLM 서빙에도 소프트웨어 에이징이 존재한다. "모든 배포가 36시간 윈도우에서 작지만 통계적으로 유의한 프로세스 전용 메모리 누수를 보인다."
  • 모델이나 추론 경로의 속성이 아니다. "같은 모델, 같은 워크로드를 서빙하는 배포끼리 누수율이 거의 두 자릿수 배율로 갈린다 — 런타임과 호스팅 환경이 중심 역할을 한다는 뜻."
  • 누수의 모양도 제각각이다. "대부분은 매끄럽게 자라지만 Triton+V0만 RSS·VMS의 계단식 패턴을 보인다 — 다른 기저 메커니즘을 시사."

4.2 — For practitioners: your dashboards won't show this 4.2 — 운영자에게: 대시보드에는 이게 안 뜬다

"Notably, none of these effects is visible through client-side metrics over the timescale of our experiments. For practitioners, the results highlight that monitoring LLM serving systems cannot rely solely on latency, throughput, or error rates. Memory-related aging may remain invisible to users while steadily accumulating inside the serving stack. More generally, deployment choices have reliability implications that are not captured by short-term performance benchmarks."

— §VI · 원문 보기 (§VI)

4.3 — Open directions named by the authors (§VI) 4.3 — 저자들이 지목한 후속 과제 (§VI)

  • Replicated runs to quantify run-to-run variability; other GPU platforms and larger models.
  • Longer windows to catch late-onset effects.
  • Targeted heap profiling of the V0 engine to identify the source of the step-wise accumulation.
  • "whether specific request patterns can trigger or accelerate these memory-growth mechanisms."
  • 런 간 변동을 정량화할 반복 실험; 다른 GPU 플랫폼과 더 큰 모델.
  • 늦게 발현되는 효과를 잡을 더 긴 관측 윈도우.
  • 계단식 누적의 출처를 찾을 V0 엔진 힙 프로파일링.
  • "특정 요청 패턴이 이 메모리 증가 메커니즘을 촉발하거나 가속할 수 있는지."

4.4 — Our read (not the paper's claims) 4.4 — 우리 관점의 해석 (논문의 주장 아님)

editor's note — implications for our own serving work편집자 주 — 우리 서빙 작업에 주는 함의 ① For long-running vLLM benchmarks and PD-disaggregation experiments like ours, add per-process USS (psutil) to the monitoring set — client-side metrics provably miss this class of degradation. ② When wrapping vLLM in an orchestration layer (Triton, gateways, sidecars), the wrapper is part of the aging surface: re-measure, don't assume. ③ The absolute rates (KB/h) are harmless on monthly timescales, but the E2-style step-wise RSS+VMS pattern is the one to alert on, since it's the candidate for unbounded growth. ④ Multi-component deployments (P/D disaggregation, router + engine pools) multiply the number of runtimes that can age independently — "the deployment is the aging surface" cuts harder there. ① 우리처럼 vLLM 장기 벤치마크나 PD 분리 실험을 돌릴 때 모니터링 항목에 프로세스별 USS(psutil)를 추가할 것 — 클라이언트 측 지표가 이런 열화를 못 본다는 게 입증됐다. ② vLLM을 오케스트레이션 계층(Triton, 게이트웨이, 사이드카)으로 감쌀 때는 그 래퍼도 에이징 표면의 일부다: 가정하지 말고 재측정할 것. ③ 절대 누수율(KB/h)은 월 단위로는 무해하지만, E2식 계단형 RSS+VMS 패턴은 무한 증가 후보이므로 알림을 걸 가치가 있는 쪽이다. ④ 멀티 컴포넌트 배포(P/D 분리, 라우터 + 엔진 풀)는 독립적으로 늙을 수 있는 런타임 수를 늘린다 — "배포 전체가 에이징 표면"이라는 결론이 거기서 더 아프게 적용된다.
