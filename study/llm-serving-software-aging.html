one-line summary한 줄 요약 Six LLM serving setups, 36 hours each, identical traffic. All six slowly leak memory inside the serving process. The leak is invisible in latency/throughput, it's not caused by the model or the GPU — and depending on how you package the engine, the leak rate differs by ~100× (best: vLLM V1 standalone, worst: Triton wrapping the old V0 engine). LLM 서빙 구성 6개를 동일한 트래픽으로 36시간씩 돌렸다. 여섯 개 전부, 서빙 프로세스 안에서 메모리가 조금씩 샌다. 이 누수는 레이턴시/스루풋에는 안 보이고, 모델이나 GPU 탓도 아니며 — 엔진을 어떻게 포장했느냐에 따라 누수 속도가 약 100배까지 갈린다 (최선: vLLM V1 단독, 최악: 구형 V0 엔진을 Triton으로 감싼 조합).

📖 Software aging?📖 소프트웨어 에이징?

A long-running program slowly getting worse — leaked memory piles up, performance drifts. A restart resets it; that's why the field's classic cure is called "rejuvenation" (= planned restarts).오래 켜둔 프로그램이 서서히 나빠지는 현상. 누수된 메모리가 쌓이고 성능이 슬금슬금 밀린다. 재시작하면 리셋된다 — 그래서 이 분야의 고전적 처방 이름이 "회춘(rejuvenation)", 즉 계획된 재시작이다.

📖 USS · RSS · VMS

Three ways to count a process's memory. USS = pages only this process uses (the most honest leak signal). RSS = everything physically in RAM, shared libs included. VMS = address space merely reserved, not necessarily used.프로세스 메모리를 세는 세 가지 방법. USS = 이 프로세스만 쓰는 메모리(누수 측정에 가장 정직한 지표). RSS = 공유 라이브러리까지 포함해 실제 RAM에 올라간 전부. VMS = 실제 사용이 아니라 "찜"만 해둔 주소 공간.

📖 Open-loop Poisson load📖 Open-loop Poisson 부하

A traffic generator that keeps firing requests at random intervals whether or not the server keeps up — like real users, who don't politely wait for your server to catch its breath.서버가 버거워하든 말든 무작위 간격으로 요청을 계속 쏘는 부하 방식. 서버 숨 고를 때까지 기다려주지 않는 실제 사용자 트래픽과 비슷하다.

📖 vLLM V0 / V1

Two generations of vLLM's internal engine. Same paged-attention algorithm, same API. V0 = older synchronous design; V1 = newer async redesign (today's default).vLLM 내부 엔진의 두 세대. paged attention 알고리즘도 API도 같다. V0 = 구형 동기식 설계, V1 = 비동기로 재설계한 신형(현재 기본값).

📖 "Triton-wrapped"📖 "Triton 래핑"

NVIDIA Triton runs vLLM as a child process and adds production extras on top: request queue, dynamic batcher, OpenAI-compatible API.NVIDIA Triton이 vLLM을 자식 프로세스로 띄우고 그 위에 요청 큐, dynamic batcher, OpenAI 호환 API 같은 프로덕션 기능을 얹는 구조.

📖 How big is "+157 KB/h"?📖 "+157 KB/h"는 얼마나 큰가?

The worst leak found ≈ 110 MB per month. Not an outage tomorrow. The point is that it exists at all, that it's invisible, and that deployments differ ~100×.발견된 최악의 누수도 한 달에 약 110 MB. 내일 장애 날 수준은 아니다. 핵심은 "샌다는 사실 자체", "안 보인다는 것", 그리고 "배포마다 100배 차이"다.

🗺️ Before we start — what exactly leaks, and why would it ever hurt? 시작 전에 — 정확히 뭐가 새고, 그게 왜 문제가 되나?

"Memory leak in LLM serving" sounds like a GPU problem. It isn't — and getting this picture right makes the whole paper click. When you run vllm serve, what actually starts is a Python process on the Linux host. The model weights and the KV-cache live in GPU VRAM, but the process that drives the GPU lives in ordinary host RAM (the CPU side):

"LLM 서빙에서 메모리 누수"라고 하면 GPU 문제처럼 들리지만, 아닙니다 — 그리고 이 그림 하나만 제대로 잡으면 논문 전체가 술술 읽힙니다. vllm serve를 실행하면 실제로 뜨는 것은 리눅스 호스트 위의 Python 프로세스 하나입니다. 모델 가중치와 KV-cache는 GPU VRAM에 있지만, 그 GPU를 부리는 프로세스 자체는 호스트의 일반 RAM(CPU 쪽)에서 삽니다:

Where the leak actually lives. The paper's USS metric measures the blue box; the green box stayed flat in every run.누수가 실제로 사는 곳. 논문의 USS 지표가 재는 건 파란 상자이고, 초록 상자는 모든 런에서 평탄했다.

Which part of the blue box leaks? 파란 상자 안에서도 "어떤 부분"이 새나?

The paper's detective logic: all three deployments run the same model and the same inference math (same CUDA kernels). If the inference path were leaking, all three would leak at a similar rate. Instead they differ ~100× — so the leak must live in the wrapping: the scheduler and request-lifecycle code (why old V0 leaks 7–27× more than V1), the queue/batcher/frontend layers Triton adds (why wrapping amplifies both engines), and the CUDA runtime's host-side bookkeeping (why the PyTorch runs kept reserving address space). Which exact data structure? Unknown — that needs heap profiling, which the paper leaves as future work.

논문의 추리는 이렇습니다: 세 배포는 같은 모델, 같은 추론 연산(같은 CUDA 커널)을 돌립니다. 추론 경로가 새는 거라면 셋의 누수 속도가 비슷해야 하는데, 실제로는 ~100배 차이가 났죠. 그러니 누수는 포장에 사는 겁니다 — 스케줄러와 요청 수명주기 코드(구형 V0가 V1보다 7~27배 더 새는 이유), Triton이 얹는 큐/배처/프론트엔드 계층(래핑이 두 엔진 모두를 증폭시키는 이유), CUDA 런타임의 호스트 쪽 장부(PyTorch 런들이 주소 공간을 계속 예약만 하던 이유). 정확히 어느 자료구조인지는? 미상 — 힙 프로파일링이 필요하고, 논문은 그걸 후속 과제로 남겼습니다.

analogy비유 The kitchen (GPU) is spotless and cooking at full speed. But the front counter (host process) keeps a receipt from time to time and never throws it away. Service speed doesn't change one bit — until the day the counter is buried. 주방(GPU)은 깨끗하고 풀스피드로 요리 중입니다. 그런데 카운터(호스트 프로세스)에 영수증이 가끔 한 장씩 쌓이고, 아무도 버리지 않아요. 손님 응대 속도는 조금도 안 변합니다 — 카운터가 파묻히는 날까지는.

And how does host RAM ever hurt LLM inference performance? 호스트 RAM이 대체 어떻게 LLM 추론 성능을 해치나?

Within the 36-hour runs: it didn't, at all — latency and throughput stayed flat (§IV-B). That's exactly the danger. A leak like this doesn't degrade performance gradually; it ends in a cliff:

36시간 실험 안에서는: 전혀 안 해쳤습니다 — 레이턴시와 스루풋이 끝까지 평탄했어요(§IV-B). 그런데 바로 그게 위험한 지점입니다. 이런 누수는 성능을 서서히 깎는 게 아니라 절벽으로 끝납니다:

① RAM fills up → swapping① RAM이 차면 → 스왑

The OS starts paging the Python orchestrator to disk. The GPU is fine, but the conductor stutters — batching slows, tail latency explodes.OS가 파이썬 오케스트레이터를 디스크로 내리기 시작. GPU는 멀쩡한데 지휘자가 버벅임 — 배칭이 늦어지고 tail latency가 폭발.

② Or: OOM kill → outage② 또는: OOM kill → 장애

The kernel kills the serving process. Restart = minutes of model reloading, and every KV-cache on the GPU evaporates.커널이 서빙 프로세스를 죽임. 재시작 = 수 분짜리 모델 재로딩, GPU에 쌓아둔 KV-cache 전부 증발.

③ In k8s: OOMKilled loop③ k8s라면: OOMKilled 반복

With a container memory limit, a leaking process eventually hits it → restart → leak again → restart. Availability blips and cold starts on a schedule you didn't choose.컨테이너 메모리 리밋이 있으면 새는 프로세스는 언젠가 리밋에 닿음 → 재시작 → 또 샘 → 또 재시작. 내가 정하지 않은 주기로 가용성 구멍과 콜드 스타트 발생.

the shape of the risk위험의 모양 Not "slowly getting worse" but fine → fine → fine → bang — and the dashboard (latency, throughput, errors) shows nothing until just before the bang. That's why the paper's bottom line is "monitor the process memory itself". To be fair on magnitude: the measured rates (worst ≈ 110 MB/month) buy you months of headroom — the one genuinely scary pattern is E2's staircase (§3.5), because nobody knows when it jumps or by how much. "서서히 나빠짐"이 아니라 멀쩡 → 멀쩡 → 멀쩡 → 쾅입니다 — 그리고 대시보드(레이턴시·스루풋·에러율)에는 쾅 직전까지 아무것도 안 보입니다. 논문의 결론이 "프로세스 메모리 자체를 모니터링하라"인 이유죠. 규모는 공정하게 말하면: 측정된 속도(최악 ≈ 월 110 MB)면 몇 달은 여유가 있습니다 — 진짜 무서운 건 언제 얼마나 점프할지 모르는 E2의 계단 패턴(§3.5) 하나입니다.

1 Problem definition 문제 정의

1.1 — We benchmark for minutes, then run for months 1.1 — 벤치마크는 몇 분, 실제 운영은 몇 달

vLLM and Triton sit on expensive GPUs and stay up for weeks or months. But almost every number we have about them comes from short benchmarks — peak throughput, p99 latency, measured over minutes. Nobody has really asked: what happens to these processes after hour 30?

vLLM과 Triton은 비싼 GPU 위에서 몇 주, 몇 달씩 떠 있습니다. 그런데 우리가 아는 수치는 거의 전부 짧은 벤치마크 — 몇 분짜리 측정에서 나온 피크 스루풋, p99 레이턴시입니다. 정작 "이 프로세스, 30시간째에는 어떤 상태일까?"를 물어본 사람이 없었습니다.

"Yet the literature on these engines focuses almost entirely on peak metrics measured in minutes. What happens to them over longer windows is mostly unknown."

— §I, ¶1 · 원문 보기 (arXiv HTML §I)

Funny thing is, there's a whole research field for exactly this question. "Software aging and rejuvenation" (SAR) has spent ~30 years measuring how long-running software slowly rots — in databases, hypervisors, operating systems, blockchains. They just never got around to LLM serving:

재미있는 건, 정확히 이 질문을 다루는 연구 분야가 이미 있다는 점입니다. "소프트웨어 에이징·회춘(SAR)" 분야는 약 30년간 DB, 하이퍼바이저, OS, 블록체인에서 장기 실행 소프트웨어가 서서히 상하는 과정을 측정해 왔습니다. 다만 LLM 서빙까지는 아직 손이 닿지 않았을 뿐:

"The SAR community has not yet engaged with LLM serving on the GPU."

— §I, ¶2 · 원문 보기 (§I)

1.2 — Why can't we just reuse the old aging playbook? 1.2 — 기존 에이징 연구 방법을 그대로 쓰면 안 되나?

Because LLM serving violates every assumption the old studies were built on:

안 됩니다. LLM 서빙은 기존 연구가 깔고 있던 가정을 전부 깨기 때문입니다:

"Traditional aging studies target CPU-bound systems with mature allocators and workloads of regular cost. LLM serving on the GPU breaks all three assumptions."

— §I, ¶3 · 원문 보기 (§I)

1.3 — Meet the three contestants (§II-A) 1.3 — 세 명의 선수 소개 (§II-A)

Quick background. A serving engine loads the model onto the GPU once, then generates answers token by token. Each in-flight request drags along a KV-cache — hundreds of MB of GPU memory that keeps growing while the request lives (§II-A ¶1). So the whole game is GPU memory management, and modern engines play it with continuous batching (many requests share each forward pass) and paged attention (KV-cache in small fixed blocks, like OS virtual-memory paging). vLLM is the reference implementation of that idea.

짧은 배경 설명. 서빙 엔진은 모델을 GPU에 한 번 올려놓고, 토큰을 하나씩 생성해 응답합니다. 진행 중인 요청마다 KV-cache를 끌고 다니는데, 이건 요청이 살아있는 동안 계속 자라는 수백 MB짜리 GPU 메모리입니다(§II-A ¶1). 그래서 승부처는 GPU 메모리 관리이고, 현대 엔진들은 continuous batching(여러 요청이 한 forward pass를 나눠 씀)과 paged attention(KV-cache를 OS의 가상 메모리 페이징처럼 작은 고정 블록으로 관리)으로 싸웁니다. 이 아이디어의 원조 구현이 vLLM입니다.

The paper lines up three deployments that all run the same model but package it very differently:

논문은 같은 모델을 전혀 다르게 포장한 세 배포를 출전시킵니다:

🏎️ vLLM standalone

The optimized engine, served bare: paged attention + its own minimal HTTP server. Runs the new V1 engine.최적화 엔진을 날것으로: paged attention + 자체 미니멀 HTTP 서버. 신형 V1 엔진으로 구동.

🏭 Triton + vLLM

The "enterprise packaging": Triton runs vLLM as a subprocess and adds queue/batcher/OpenAI API. NVIDIA's patched build inside runs the old V0 engine."엔터프라이즈 포장": Triton이 vLLM을 서브프로세스로 돌리며 큐/배처/OpenAI API를 얹음. 내장된 NVIDIA 패치판은 구형 V0 엔진.

🧪 Naive PyTorch + HF

The "weekend project": transformers + FastAPI, one request at a time. No batching, no paged attention, no custom memory manager."주말 토이 프로젝트": transformers + FastAPI, 요청을 한 번에 하나씩. 배칭도 paged attention도 커스텀 메모리 관리자도 없음.

One open question hangs over the vLLM pair — V0 and V1 share the algorithm and the API, but differ in how requests are scheduled and how per-request resources are grabbed and released. Does that choice matter for reliability?

vLLM 두 세대에는 미해결 질문이 하나 걸려 있습니다 — V0와 V1은 알고리즘도 API도 같지만, 요청을 스케줄링하는 방식과 요청별 자원을 잡았다 놓는 방식이 다릅니다. 이 선택이 신뢰성에 영향을 줄까?

"Whether this choice has reliability consequences over long-running operation is, to our knowledge, an open question."

— §II-A, ¶3 · 원문 보기 (§II-A)

There's also a nice contrast with the systems community (the vLLM/PagedAttention world): they treat memory problems as something to design away; this paper treats them as something to watch accumulate:

시스템즈 커뮤니티(vLLM/PagedAttention 진영)와의 대비도 흥미롭습니다: 그쪽은 메모리 문제를 설계로 없애버릴 대상으로 보고, 이 논문은 쌓이는 걸 지켜볼 대상으로 봅니다:

"PagedAttention and a family of memory management strategies treat fragmentation and KV-cache pressure as architectural problems to be eliminated by design, not as time-accumulating signatures to be detected through long-window analysis."

— §II-B, ¶3 · 원문 보기 (§II-B)

2 Method 해결 방법

The experiment design answers four needs the authors set up front: realistic configurations, enough monitoring to locate any aging, statistics that won't lie on this kind of data, and full reproducibility.

실험 설계는 저자들이 처음에 못 박은 네 가지 요구를 따라갑니다: 현실적인 구성, 에이징이 있다면 어디인지 짚어낼 만큼의 모니터링, 이런 데이터에서 거짓말하지 않는 통계, 그리고 끝까지 재현 가능할 것.

"the campaign must compare practical deployment configurations under a controlled but realistic workload; monitor enough of the system to localize aging if present; use a statistical pipeline robust to the autocorrelation of monitoring traces; and remain reproducible end to end."

— §III, ¶1 · 원문 보기 (§III)

2.1 — The setup at a glance 2.1 — 실험 구도 한 장

Layout of the primary comparison (paper Fig. 1 redrawn). Three engines run at the same time on one host, one GPU each.본 비교 실험의 구도 (논문 Fig. 1 재구성). 세 엔진이 한 호스트에서 GPU 하나씩 차지하고 동시에 돈다.

Why run them together on one host? Because that's what real fleets look like — and the authors say so explicitly:

왜 셋을 한 호스트에서 같이 돌렸을까요? 실제 운영 환경이 그렇게 생겼기 때문입니다. 저자들도 명시합니다:

"This reproduces a realistic multi-tenant deployment, where several engines are co-located on one machine rather than measured in isolation."

— §I, ¶4 · 원문 보기 (§I)

2.2 — The traffic: hard but fair 2.2 — 트래픽: 혹독하되 공정하게

Each engine gets its own open-loop Poisson client. Prompts are built from 3000 arXiv abstracts, stretched to random lengths between 256 and 7500 tokens (median 1500); outputs run up to 1500 tokens (median 200); 70% of requests stream. The clever part is calibration: before the real run, they crank the request rate up until throughput stops growing — that point is the engine's own speed limit ("ceiling") — and then run the 36-hour experiment at 85% of each engine's ceiling. So the slow naive server isn't unfairly crushed, and the fast engines aren't coasting: everyone works equally hard relative to their own ability.

엔진마다 전용 open-loop Poisson 클라이언트가 붙습니다. 프롬프트는 arXiv 초록 3000개를 이어붙여 256~7500토큰(중앙값 1500) 사이 무작위 길이로 만들고, 출력은 최대 1500토큰(중앙값 200), 요청의 70%는 스트리밍입니다. 영리한 부분은 캘리브레이션입니다: 본 실험 전에 요청 속도를 처리량이 더 안 늘 때까지 끌어올려 그 엔진 고유의 한계 속도("천장")를 찾고, 36시간 본 실험은 각자 천장의 85%로 돌립니다. 느린 순정 서버가 억울하게 깔리지도, 빠른 엔진이 놀지도 않게 — 각자의 능력 대비 똑같이 힘들게 만드는 거죠.

"We use the ceiling rather than the highest rate at which the client does not yet drop, because the ceiling is a property of the engine itself, while the no-drop rate is partly an artefact of the client-side concurrency cap."

— §III, "Workload and stress regime" · 원문 보기 (§III)

2.4 — The statistics: why so much machinery for "is the line going up?" 2.4 — 통계: "선이 우상향인가?" 하나 보는데 왜 이리 거창한가

Here's the trap. A process's memory reading at 12:00:05 is nearly identical to its reading at 12:00:00 — monitoring samples are not independent data points, they're near-copies of each other (the paper measures correlation ρ ≈ 0.99). Naive statistics counts every sample as fresh evidence, so it becomes wildly overconfident:

함정은 이렇습니다. 12:00:05의 메모리 값은 12:00:00의 값과 거의 같습니다 — 모니터링 샘플은 독립적인 데이터가 아니라 서로의 복사본에 가깝습니다(논문 측정으로 상관 ρ ≈ 0.99). 순진한 통계는 샘플 하나하나를 새 증거로 세기 때문에 터무니없이 과신하게 됩니다:

"the resident memory of a process at time t is almost identical to its value at t−1, and naive tests that treat samples as independent produce drastically deflated p-values."

— §III, "Statistical Analysis" · 원문 보기 (§III)

So the paper makes every candidate trend pass through a funnel of three filters:

그래서 논문은 모든 추세 후보를 3중 필터 깔때기에 통과시킵니다:

The decision funnel (§III, "Statistical Analysis"). A trend must convince two different tests and survive multiple-testing correction.판정 깔때기 (§III "Statistical Analysis"). 추세는 서로 다른 두 검정을 모두 설득하고, 다중검정 보정까지 살아남아야 한다.

Two more honesty devices worth noting: the list of indicators was frozen before looking at any long-run data (so they can't cherry-pick), and always-increasing counters like "total I/O bytes" were converted to per-second rates — otherwise they'd register as "aging" trivially, by construction.

정직 장치가 두 개 더 있습니다: 지표 목록은 장기 데이터를 보기 전에 고정했고(입맛대로 고르기 차단), "누적 I/O 바이트"처럼 원래 늘기만 하는 카운터는 초당 비율로 바꿨습니다 — 안 그러면 구조적으로 무조건 "에이징"으로 잡히니까요.

"for all practical purposes, none of the engines degrades visibly to a production operator over 36 hours of sustained high load. As the next section shows, this stability is only skin-deep: once we look inside the engine process, a different picture emerges."

3.3 — Inside the process: everyone leaks, and the ranking is upside-down (§IV-C) 3.3 — 프로세스 안: 전원 누수 중, 그리고 순위가 뒤집혀 있다 (§IV-C)

Now the USS trace (the "memory only this process owns" metric). After all three statistical filters, every primary deployment shows a real, steady leak. Intuition says the hand-rolled FastAPI server should leak most and the polished engines least. The data says otherwise:

이제 USS(이 프로세스만의 메모리) 그래프를 봅니다. 3중 통계 필터를 다 통과하고도 본 비교 세 배포 전부에서 진짜 누수가 확인됩니다. 직관적으로는 손으로 짠 FastAPI 서버가 제일 많이 새고, 잘 다듬어진 엔진들이 제일 적게 새야 할 것 같죠. 데이터는 다르게 말합니다:

"The naive PyTorch baseline, the textbook example of what production teams avoid, is not the cleanest: it sits in the middle at +31 KB/h. The cleanest is vLLM standalone (E1) at +1.8 KB/h, an engine built specifically to optimize serving. The heaviest is Triton-wrapped vLLM (E2) at +157 KB/h."

— §IV-C, ¶2 ("the order is the surprise of the campaign") · 원문 보기 (§IV-C)

And this upside-down ranking is itself the biggest clue. All three run the same model, the same math. If the model/inference path were leaking, all three would leak at similar rates. They differ by ~100× — so the leak must live in the wrapping: the Python runtime, the server framework, the orchestration around the model.

이 뒤집힌 순위 자체가 가장 큰 단서입니다. 셋은 같은 모델, 같은 연산을 돌립니다. 모델/추론 경로가 새는 거라면 셋의 누수율이 비슷해야 합니다. 그런데 약 100배 차이가 난다 — 즉 누수는 포장에 사는 겁니다: Python 런타임, 서버 프레임워크, 모델을 둘러싼 오케스트레이션 말이죠.

"If the leak originated from the inference path, we would expect similar leak rates across all deployments. Instead, the observed rates differ by nearly two orders of magnitude. This strongly suggests that the source of the leak lies in the serving infrastructure rather than in the model execution itself."

— §IV-C, ¶3 · 원문 보기 (§IV-C)

Everything else stays quiet: CPU, threads, file descriptors, context switches, I/O — flat. GPU VRAM too, in every deployment, which surprised even the authors (they expected the allocator to fragment under wildly varying request sizes). At this timescale, aging here = a host-side memory story, full stop.

나머지는 전부 조용합니다: CPU, 스레드, 파일 디스크립터, 컨텍스트 스위치, I/O — 평평. GPU VRAM도 모든 배포에서 평평한데, 이건 저자들도 놀란 부분입니다(요청 크기가 널뛰니 할당기 단편화를 예상했거든요). 이 시간 척도에서 에이징은 호스트 쪽 메모리 이야기, 그게 전부입니다.

3.4 — Plot twist: lower the load, leak gets worse (§IV-D) 3.4 — 반전: 부하를 낮췄더니 누수가 더 심해진다 (§IV-D)

Maybe the naive server only leaks because it's drowning at 100% capacity? They rerun it at a stroll — 0.05 RPS, no drops at all. The leak doesn't just survive; it triples: +31 → +103 KB/h. Counter-intuitive, but it pins down the mechanism — the leak tracks wall-clock time, not request count:

순정 서버가 새는 건 용량 100%로 허덕여서 아닐까? 그래서 산책 수준 — 0.05 RPS, 드롭 0% — 으로 다시 돌립니다. 그런데 누수는 사라지기는커녕 3배가 됩니다: +31 → +103 KB/h. 직관에 어긋나지만, 덕분에 메커니즘이 못 박힙니다 — 누수는 요청 개수가 아니라 흐른 시간을 따라갑니다:

"This result indicates that the leak is not caused by queueing effects or saturation-related behavior. Instead, it appears to be intrinsic to the runtime environment. The higher leak rate at lower load also suggests that memory growth is driven primarily by elapsed time rather than by the number of processed requests."

— §IV-D · 원문 보기 (§IV-D)

Side observation in the PyTorch runs: reserved address space (VMS) balloons ~127 MB/h (≈7.5 GB over the run) while actually-used memory grows only ~20 MB total, and thread/FD counts stay flat. Translation: nothing is "leaking objects" in the classic sense — something (consistent with the CUDA caching allocator's host-side bookkeeping) keeps reserving address space it never gives back. Whether that ever turns into real memory pressure is left open.

PyTorch 런들의 곁다리 관찰: "찜"해 둔 주소 공간(VMS)은 시간당 ~127 MB(런 전체로 ≈7.5 GB)씩 부푸는데, 실제 사용 메모리는 총 ~20 MB만 늘고 스레드/FD 수는 평평합니다. 풀이하면: 고전적 의미의 "객체 누수"가 아니라, 무언가가(CUDA 캐싱 할당기의 호스트 측 관리와 부합) 주소 공간을 계속 예약만 하고 반납하지 않는 겁니다. 이게 언젠가 실제 메모리 압박으로 바뀌는지는 미해결로 남습니다.

3.5 — The 2×2 grid: who's the culprit? Both, together (§IV-E) 3.5 — 2×2 그리드: 범인은 누구? 정답은 "조합" (§IV-E)

E1 vs E2 differ in two ways at once (V1 vs V0, bare vs Triton). The two ablation runs fill in the missing corners, giving a full 2×2 grid — engine generation × packaging:

E1과 E2는 두 가지가 동시에 다릅니다(V1 vs V0, 단독 vs Triton). ablation 런 두 개가 빈 모서리를 채워서 엔진 세대 × 포장의 2×2 그리드가 완성됩니다:

Left: the factorial grid (Table V, §IV-E). Right: growth shape sketches based on Fig. 2 and the increment analysis in §IV-E.왼쪽: 요인설계 그리드 (Table V, §IV-E). 오른쪽: Fig. 2와 §IV-E의 증분 분석을 바탕으로 한 증가 모양 스케치.

Read the grid: the old V0 engine leaks more than V1 in both rows (≈7× bare, ≈27× under Triton), and Triton amplifies both engines — but the combination Triton×V0 explodes. One nuance: E1 actually climbs for the first few hours then settles, while A1 keeps creeping — so E1's cumulative growth isn't the smallest even though its steady-state rate is (§IV-E ¶3).

그리드를 읽어보면: 구형 V0는 두 행 모두에서 V1보다 많이 새고(단독 ≈7배, Triton 아래 ≈27배), Triton은 두 엔진 모두를 증폭시키는데 — Triton×V0 조합에서 폭발합니다. 뉘앙스 하나: E1은 처음 몇 시간 오르다가 안정되는 반면 A1은 계속 기어오릅니다. 그래서 E1의 정상 상태 누수율이 최저인데도 누적 증가량은 최소가 아닙니다 (§IV-E ¶3).

The staircase on the right is the scariest part. E2 doesn't drift — it sits still, then jumps several MB at once, and never gives the memory back (biggest 1% of jumps ≈ 1.8 MB; RSS and VMS jump together with correlation ρ ≈ 0.83, vs < 0.35 everywhere else):

오른쪽 계단이 제일 섬뜩한 부분입니다. E2는 드리프트가 아니라 — 가만히 있다가 한 번에 수 MB씩 점프하고, 그 메모리를 절대 반납하지 않습니다(점프 상위 1%가 ≈1.8 MB, RSS와 VMS가 상관 ρ≈0.83으로 동반 점프, 다른 구성은 <0.35):

"Its memory footprint remains stable for extended periods and then increases through discrete jumps of several megabytes. […] One plausible explanation is that the engine periodically maps new memory regions from the operating system and retains them over time. […] this behavior is the strongest clue emerging from the experimental campaign and the most plausible candidate for unbounded growth over multi-day timescales."

— §IV-E, ¶4–5 (확정하려면 힙 프로파일링이 필요 — 이 논문 범위 밖) · 원문 보기 (§IV-E)

GPU side: still nothing — "Once the model is loaded, VRAM occupancy remains essentially stable" (§IV-E ¶6). One honest caveat from the authors: the four grid cells run three different vLLM versions (0.7.3 / 0.10.1.1 / 0.21.0), because newer releases removed the V0 switch. So "V0 vs V1" is partly tangled with "old version vs new version" — the gaps are too big to be just that, but a clean attribution is open (§IV-E ¶7).

GPU 쪽은 여전히 잠잠합니다 — "모델이 올라가고 나면 VRAM 점유는 사실상 안정적" (§IV-E ¶6). 저자들의 정직한 단서 하나: 그리드 4칸이 서로 다른 vLLM 버전 3개(0.7.3 / 0.10.1.1 / 0.21.0)로 돌았습니다. 최신 릴리스에서 V0 선택 스위치가 사라졌기 때문인데, 그래서 "V0 vs V1" 효과에 "구버전 vs 신버전" 효과가 일부 섞여 있습니다 — 차이가 너무 커서 버전 탓만은 아니겠지만, 깔끔한 귀속은 미해결입니다 (§IV-E ¶7).

3.6 — How far do these numbers reach? (§V) 3.6 — 이 숫자들, 어디까지 믿어도 되나? (§V)

The authors list their own limits, roughly by severity. Short version: trust the existence of aging and the ordering of deployments; treat the exact KB/h numbers as single-run estimates.

저자들이 스스로 한계를 심각한 순서대로 나열합니다. 요약하면: 에이징의 존재와 배포 간 순서는 믿어도 되고, 정확한 KB/h 숫자는 한 번 측정한 추정치로 받아들이라는 것.

4 Takeaways 시사점

4.1 — The paper's three findings (§VI) 4.1 — 논문의 세 가지 결론 (§VI)

  • GPU LLM serving ages. "Every deployment exhibits a small but statistically significant process-private memory leak over a 36-hour window."
  • The model isn't the leaker — the packaging is. "Deployments running the same model and serving the same workload can differ by nearly two orders of magnitude in leak rate."
  • Leaks have different personalities. Most drift smoothly; "Triton+V0 shows a distinctive step-wise pattern in RSS and VMS, suggesting a different underlying mechanism."
  • GPU LLM 서빙도 늙는다. "모든 배포가 36시간 윈도우에서 작지만 통계적으로 유의한 프로세스 전용 메모리 누수를 보인다."
  • 새는 건 모델이 아니라 포장이다. "같은 모델, 같은 워크로드를 서빙해도 배포에 따라 누수율이 거의 100배 갈린다."
  • 누수에도 성격이 있다. 대부분은 매끄럽게 드리프트하지만, "Triton+V0만 RSS·VMS의 계단식 패턴 — 다른 기저 메커니즘을 시사."

4.2 — For operators: your dashboard is blind to this 4.2 — 운영자에게: 당신의 대시보드는 이걸 못 본다

The most actionable sentence in the paper — none of this showed up in latency, throughput, or error rate. If your alerting is built entirely on those, this whole class of degradation is invisible until it isn't:

이 논문에서 가장 실용적인 문장 — 이 모든 것이 레이턴시, 스루풋, 에러율에는 전혀 나타나지 않았습니다. 알림 체계가 그 셋 위에만 서 있다면, 이런 부류의 열화는 터지기 전까지 보이지 않습니다:

"Notably, none of these effects is visible through client-side metrics over the timescale of our experiments. For practitioners, the results highlight that monitoring LLM serving systems cannot rely solely on latency, throughput, or error rates. Memory-related aging may remain invisible to users while steadily accumulating inside the serving stack. More generally, deployment choices have reliability implications that are not captured by short-term performance benchmarks."

— §VI · 원문 보기 (§VI)

4.3 — What the authors want to do next (§VI) 4.3 — 저자들이 다음에 하고 싶은 것 (§VI)

  • Repeat runs (quantify run-to-run noise); other GPUs and bigger models.
  • Longer windows — catch effects that need more than 36 h to show.
  • Heap-profile the V0 engine to find where the staircase jumps come from.
  • Check whether specific request patterns can trigger or accelerate the leaks.
  • 반복 실험 (런 간 노이즈 정량화); 다른 GPU와 더 큰 모델.
  • 더 긴 관측 윈도우 — 36시간으로는 안 보이는 효과 잡기.
  • V0 엔진 힙 프로파일링 — 계단식 점프의 출처 찾기.
  • 특정 요청 패턴이 누수를 촉발/가속하는지 확인.

4.4 — Our read (not the paper's claims) 4.4 — 우리 관점의 해석 (논문의 주장 아님)

editor's note — implications for our own serving work편집자 주 — 우리 서빙 작업에 주는 함의 ① Add per-process USS (one psutil call) to long-running vLLM benchmarks and PD-disaggregation experiments — this paper proves client-side metrics miss the whole category. ② Any layer you wrap around vLLM (Triton, gateways, sidecars) becomes part of the aging surface — measure it, don't vouch for it. ③ The KB/h magnitudes are harmless on monthly timescales; the thing worth an alert is the E2-style staircase (RSS+VMS jumping together), the one candidate for unbounded growth. ④ Multi-component setups like P/D disaggregation multiply the number of independently-aging runtimes — "the deployment is the aging surface" bites hardest exactly there. ① 우리 장기 vLLM 벤치마크나 PD 분리 실험의 모니터링에 프로세스별 USS(psutil 한 줄)를 추가할 것 — 클라이언트 측 지표가 이 범주를 통째로 놓친다는 게 이 논문의 증명이다. ② vLLM을 감싸는 모든 계층(Triton, 게이트웨이, 사이드카)은 에이징 표면의 일부가 된다 — 보증하지 말고 측정할 것. ③ KB/h 수준의 절대량은 월 단위로는 무해하다; 알림을 걸 가치가 있는 건 E2식 계단 패턴(RSS+VMS 동반 점프) — 무한 증가의 유일한 후보다. ④ P/D 분리 같은 멀티 컴포넌트 구성은 따로따로 늙는 런타임 수를 늘린다 — "배포 전체가 에이징 표면"이라는 결론이 가장 아프게 적용되는 지점.
