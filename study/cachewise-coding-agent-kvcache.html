CacheWise — KVCache management for serving LLM coding agents — paper note CacheWise: KVCache management for serving LLM coding agents · 논문 정리

"CacheWise: Understanding Workloads and Optimizing KVCache Management for Efficiently Serving LLM Coding Agents" — Tiwari et al. (UW + UVA). Coding agents reuse one huge, growing prefix across dozens of tool-call turns, and vLLM's FCFS + LRU thrash it. CacheWise adds prefix-aware scheduling and an eviction policy that predicts when a session returns from the tool it's running. "CacheWise: Understanding Workloads and Optimizing KVCache Management for Efficiently Serving LLM Coding Agents"(Tiwari 외, 워싱턴대 + 버지니아대). vLLM의 FCFS + LRU가 코딩 에이전트의 프리픽스 캐시를 갈아엎는(thrash) 문제를, prefix-aware 스케줄링과 tool로 세션 복귀 시점을 예측하는 축출로 푼다.

one-line summary한 줄 요약
  • A coding-agent session is a closed loop: tool call → tool runs (grep 0.1 s, pytest 80 s) → the next request reuses the whole growing prefix. Tool-initiated turns are ~20× more frequent than user ones; prefixes are ~21× more prefill-heavy than chat.
  • vLLM's FCFS + LRU ignore this and evict prefixes about to be reused: KVCache thrashing.
  • CacheWise: (1) prefix-aware scheduling dispatches the request reusing the most resident cache; (2) predictive eviction evicts the session idle longest, estimating "time to next reuse" from the tool's name + arguments.
  • Result: 2–2.6× fewer evictions, up to 3.5× lower session completion time, negligible CPU overhead.
  • 코딩 에이전트 세션은 닫힌 루프다. tool(grep 0.1초, pytest 80초)이 끝나면 다음 요청이 자라난 프리픽스 전체를 재사용한다. tool 촉발 턴이 사용자 턴의 ~20×, prefill 비중은 채팅의 ~21×다.
  • vLLM의 FCFS + LRU는 이를 모른 채 곧 다시 쓸 프리픽스를 축출한다. 이것이 KVCache thrashing이다.
  • CacheWise는 (1) 남은 캐시를 가장 많이 재사용하는 요청부터 보내는 prefix-aware 스케줄링과 (2) tool 이름+인자로 "다음 재사용까지 시간"을 추정하는 예측 축출을 쓴다.
  • 결과는 축출 2–2.6× 감소, 세션 완료시간 최대 3.5× 단축이고 CPU 오버헤드는 미미하다.

📖 KVCache & paged blocks📖 KVCache와 페이지 블록

The per-token key/value tensors a Transformer caches so it doesn't recompute attention over the whole context each step. Modern engines store it in fixed-size blocks (like OS memory pages); evicting/reusing happens block by block.attention 재계산을 피하려고 캐싱한 토큰별 key/value 텐서다. 엔진은 이를 고정 크기 블록(OS 메모리 페이지와 비슷)으로 저장하고 블록 단위로 축출·재사용한다.

📖 Session · turn · closed loop📖 세션·턴·닫힌 루프

A turn = one LLM request building on the previous request+result. A coding session = the whole multi-turn task. "Closed loop" = most turns are triggered by a tool returning, not by a human typing.턴은 LLM 요청 한 번, 세션은 멀티턴 작업 전체다. "닫힌 루프"는 대부분의 턴을 사람이 아니라 tool 결과 반환이 촉발한다는 뜻이다.

📖 Eviction & thrashing📖 축출과 thrashing

When KVCache memory is full, some session's blocks are evicted (dropped). If they're needed again right away, they must be recomputed or copied back — repeat that and you get thrashing: lots of work, little progress.메모리가 차면 블록을 축출(버림)한다. 곧 다시 필요해 재계산·복사를 반복하면 일만 많고 진척이 없는 thrashing이 된다.

📖 Token goodput📖 토큰 goodput

Throughput counts all tokens processed; goodput counts only the useful ones — after subtracting tokens spent re-prefilling evicted prefixes. Less thrashing → higher goodput.throughput에서 축출된 프리픽스를 다시 prefill한 토큰을 뺀 유용한 처리량이 goodput이다. thrashing이 적을수록 높다.

📖 τ & Belady's rule📖 τ와 Belady 규칙

τi = "time to next reuse" of session i's blocks. The provably optimal eviction (Belady, 1966) evicts whatever will be reused furthest in the future. You can't normally know τ — CacheWise predicts it.τi는 세션 i 블록의 "다음 재사용까지 시간"이다. 최적 축출(Belady, 1966)은 가장 먼 미래에 쓰일 것을 버리는데, τ는 보통 모르므로 CacheWise가 예측한다.

📖 LRU vs prefix-aware vs predictive📖 LRU vs prefix-aware vs 예측

LRU evicts by past recency (looks backward). Prefix-aware scheduling picks the request that reuses the most resident cache. Predictive eviction looks forward — keep what returns soonest.LRU는 과거 사용 시점을, 예측 축출은 미래 재사용 시점을 본다. Prefix-aware 스케줄링은 남은 캐시를 가장 많이 재사용하는 요청을 고른다.

1 Problem definition 문제 정의

1.1 — We tuned serving for chatbots; coding agents look nothing like chatbots 1.1 서빙은 챗봇에 맞춰져 있지만 코딩 에이전트는 챗봇과 전혀 다르다

A chatbot asks and answers, done. A coding agent (Claude Code, Codex, SWE-agent…) plans and loops through tool calls (tests, grep, edits) between the LLM and the environment. Nobody had studied this traffic on a serving engine, mostly because no public traces existed, so the authors collected their own.

챗봇은 묻고 답하면 끝이다. 코딩 에이전트(Claude Code, Codex, SWE-agent…)는 계획을 세우고 테스트·grep·코드 수정 같은 tool call로 LLM과 환경 사이를 오간다. 이런 트래픽이 서빙 엔진에서 어떻게 움직이는지는 공개 트레이스가 없어 연구된 적이 없었고, 저자들은 직접 모았다.

"Compared to chatbot workloads, coding-agent sessions are long-running, accumulate substantially larger contexts, and are dominated by tool-initiated turns rather than direct user input."

— §1, ¶3 · 원문 보기 (§1)

This changes the optimization target. Chat chases per-request latency (TTFT, time-between-tokens); inside an agent loop nobody waits on a single request. What matters is when the whole session finishes.

그래서 최적화 목표가 바뀐다. 채팅은 요청별 레이턴시(TTFT, 토큰 간 시간)를 쫓지만, 에이전트 루프 안의 개별 요청은 아무도 기다리지 않는다. 중요한 것은 세션 전체의 완료 시점이다.

"the key objective is not the latency of an individual request, but the completion time of the full multi-turn session."

— §1, ¶3 · 원문 보기 (§1)

1.4 — Why FCFS + LRU is the wrong default (§1, §4) 1.4 FCFS + LRU가 잘못된 기본값인 이유 (§1, §4)

vLLM and Mooncake batch First-Come-First-Served and evict Least-Recently-Used. Both are workload-agnostic, so they ignore high intra-session prefix overlap and tool-dependent reuse timing.

vLLM과 Mooncake는 요청을 FCFS로 배칭하고 KVCache를 LRU로 축출한다. 둘 다 workload-agnostic이라 세션 내 높은 프리픽스 중첩과 tool에 따라 달라지는 재사용 시점을 무시한다.

"Under memory pressure, these policies therefore trigger KVCache thrashing, reducing useful work and lowering token goodput (i.e., the rate of useful token processing after excluding recomputation and KVCache movement overheads)."

— §1, ¶4 · 원문 보기 (§1)

Existing agent-aware engines (Pie, Autellix) make you rewrite the agent against their abstraction, a non-starter for deployed clients like Claude Code. CacheWise changes only the serving system and leaves the agent untouched.

기존 에이전트-aware 엔진(Pie, Autellix)은 에이전트를 자기 프로그래밍 추상화에 맞춰 다시 짜게 한다. Claude Code처럼 이미 배포된 클라이언트에는 쓸 수 없으므로, CacheWise는 서빙 시스템만 바꾸고 에이전트는 건드리지 않는다.

"they tightly couple the agent implementation framework with the LLM serving system, and thus are ill-suited for large-scale deployments, which must support diverse clients."

— §1, ¶4 · 원문 보기 (§1)

2 Method 해결 방법

2.1 — A tiny memory model that makes the problem precise (§4) 2.1 문제를 정확히 정의하는 작은 메모리 모델 (§4)

Every design choice references this lightweight model of node memory.

모든 설계 선택이 아래의 노드 메모리 모델을 기준으로 한다.

M = KVCache block capacity of a node  ·  𝒮ₜ = {S₁, S₂, …} active sessions at time t
Sᵢ has a growing prefix of dᵢ blocks, of which kᵢ(t) are resident in XPU memory
Working set:   W(t) = Σᵢ kᵢ(t)   →   no eviction needed while W(t) ≤ M
New request rᵢ needs dᵢ total; extra blocks to allocate:   aᵢ(t) = dᵢ − kᵢ(t)
Admit immediately if W(t) + aᵢ(t) ≤ M  —  else evict aᵢ(t) blocks from other sessions

M is GPU memory left for KVCache after weights. Session Sᵢ owns a prefix, of which kᵢ(t) is in GPU memory. The next request needs only aᵢ(t) = "total − already-resident" new blocks; if they don't fit, someone gets evicted. "XPU" is the authors' term for GPU/TPU. (Nit: the prose once writes the working set with dᵢ, but Fig. 10 and the rest of the model use resident kᵢ(t), the consistent reading.)

M은 가중치를 빼고 KVCache에 남은 GPU 메모리다. 세션 Sᵢ의 프리픽스 중 kᵢ(t)만큼이 GPU에 있다. 다음 요청은 "전체 − 이미 있는 양"인 aᵢ(t)개의 새 블록만 필요하고, 자리가 없으면 누군가를 축출한다. "XPU"는 GPU/TPU를 묶어 부르는 저자들의 표현이다. (표기 주의: 본문 한 곳은 working set을 dᵢ로 쓰지만 Fig 10과 나머지 모델은 resident 블록 kᵢ(t)를 쓰며, 이쪽이 일관적이다.)

Memory pressure. Redrawn from Fig. 10.메모리 압박의 순간. Fig. 10 재구성.

Implication #1 — FCFS thrashes함의 #1: FCFS는 thrashing을 부른다

A session is active (on the XPU), queued (waiting for memory), or inactive (waiting on user/tool). FCFS interleaves many queued sessions, raising kᵢ for all at once:

  1. The working set balloons past M.
  2. One session's blocks are evicted to fit another's.
  3. The same session soon reuses that state, so it is recomputed, and the cycle repeats.

세션은 active(XPU에서 실행), queued(메모리 대기), inactive(사용자/tool 대기) 중 하나다. FCFS는 여러 queued 세션을 끼워 넣어 모두의 kᵢ를 한꺼번에 올린다.

  1. working set이 M을 넘는다.
  2. 한 세션의 블록을 축출해 다른 세션을 넣는다.
  3. 같은 세션이 곧 그 상태를 다시 써서 재계산하고, 이 과정이 반복된다.

"Since this evicted state is often reused by subsequent requests within the same session, FCFS scheduling leads to repeated eviction and recomputation (or movement) of state, resulting in KVCache thrashing."

— §4, "Implication #1" · 원문 보기 (§4)

Implication #2 — LRU is blind to the future함의 #2: LRU는 미래를 못 본다

Victims don't cost the same. Let τᵢ = time until Sᵢ next touches its blocks. Evicting a small-τ session costs a recompute almost immediately; a large-τ one is cheap. The ideal victim has the largest τ.

희생자마다 비용이 다르다. τᵢ를 세션 Sᵢ가 블록을 다시 건드릴 때까지의 시간이라 하자. τ가 작은 세션을 버리면 거의 즉시 재계산 비용을 치르고, τ가 크면 그동안 메모리를 빌려 쓸 수 있어 싸다. 그래서 τ가 가장 큰 세션을 버리는 게 이상적이다.

j* = argmax j ∈ 𝒮ₜ, j ≠ i  τⱼ   ←  evict the session whose reuse is furthest away

"An ideal eviction policy therefore selects j*=argmax_{j∈𝒮ₜ, j≠i} τⱼ, retaining sessions whose KVCache will be needed soonest."

— §4, "Implication #2" · 원문 보기 (§4)

LRU sees only past recency, so it suffers priority inversions: it evicts a small-τ block that just wasn't touched lately and pays to bring it back. The design goal: schedule to keep the working set small, and evict by predicted future reuse.

LRU는 과거 recency만 봐서 우선순위 역전을 겪는다. τ가 작은데 최근에 안 건드렸을 뿐인 블록을 버리고 다시 가져온다. 따라서 설계 목표는 working set을 작게 유지하도록 스케줄하고, 예측한 미래 재사용으로 축출하는 것이다.

2.2 — Idea 1: prefix-aware scheduling (§5.1) 2.2 아이디어 1: prefix-aware 스케줄링 (§5.1)

Instead of FCFS, dispatch the request needing the fewest new blocks, i.e., reusing the most resident cache.

FCFS 대신 새 블록이 가장 적게 필요한 요청, 곧 이미 올라온 캐시를 가장 많이 재사용하는 요청을 먼저 보낸다.

"at time t, CacheWise selects request rᵢ which requires fewest additional blocks aᵢ(t) to be allocated as the next request to dispatch."

— §5.1 · 원문 보기 (§5.1)

This shrinks the working set, and dispatching by ascending aᵢ(t) approximates shortest-job-first: less total queueing at the cost of per-request responsiveness. For agents that's the right trade.

working set이 줄어 다른 세션의 thrashing이 준다. aᵢ(t) 오름차순 디스패치는 shortest-job-first에 가까워서, 요청별 응답성을 내주고 전체 큐잉을 줄인다. 에이전트에는 맞는 거래다.

"optimizing end-to-end session completions is more important than minimizing per-request TTFT or TBT, as no user is waiting on any individual request."

— §5.1 · 원문 보기 (§5.1)

Greedy prefix-aware scheduling already exists (SGLang); the paper's point is that it's especially effective for long-running closed-loop sessions, where the evicted blocks are guaranteed to come back.greedy prefix-aware 스케줄링은 SGLang에 이미 있다. 논문은 축출된 블록이 반드시 돌아오는 장기 닫힌 루프 세션에서 이 방식이 특히 잘 듣는다고 본다.

2.3 — Idea 2: predictive eviction (§5.2) 2.3 아이디어 2: 예측 축출 (§5.2)

Scheduling can't eliminate evictions since context keeps growing. Belady's rule needs τ, but CacheWise only needs τ's relative order, and in practice just the single largest-τ session.

문맥이 계속 자라므로 스케줄링만으로는 축출이 사라지지 않는다. Belady 규칙에는 τ가 필요한데, CacheWise는 정확한 값 대신 세션 간 상대 순서만, 실제로는 τ가 가장 큰 세션 하나만 맞히면 된다.

"CacheWise only needs to predict the relative order of τ(t) across sessions to identify which blocks to evict. … accurately identifying the session with the highest τᵢ(t) is sufficient."

— §5.2 · 원문 보기 (§5.2)

τ comes from the tool a session waits on. When Sᵢ launches a tool call with metadata m = (tool_name, tool_args) at time Tᵢ, the predictor estimates the remaining time as a conditional expectation:

τ는 세션이 기다리는 tool에서 얻는다. 세션 Sᵢ가 시각 Tᵢ에 메타데이터 m = (tool_name, tool_args)로 tool call을 시작하면, 예측기는 남은 시간을 조건부 기댓값으로 추정한다.

𝔼[ τᵢ(t) | τᵢ(t) − Tᵢ > t − Tᵢ ]

Reading the formula. τᵢ(t) − Tᵢ is the tool's total duration; t − Tᵢ is time run so far; the condition means "not finished yet." So: "it has run (t − Tᵢ) and isn't done; how much longer, on average?", the expected-residual-life question. It is estimated from past durations of tool calls with similar m (same user, same project) and refreshed as time passes.

수식 읽기. τᵢ(t) − Tᵢ는 tool의 전체 실행시간, t − Tᵢ는 지금까지 돈 시간이고, 조건은 "아직 안 끝났다"는 뜻이다. 즉 "(t − Tᵢ)만큼 돌았는데 안 끝났다면 평균 얼마나 더 걸리나"를 묻는 기대 잔여수명이다. 비슷한 m을 가진 과거 tool call(같은 사용자·같은 프로젝트)의 실행시간 분포로 추정하고, 시간이 흐르면 갱신한다.

3.1 — The predictor: TF-IDF + KMeans over tool arguments (§5.2) 3.1 예측기: tool 인자에 TF-IDF + KMeans (§5.2)

3.2 — Inside vLLM: block metadata + an eviction heap (§5.3) 3.2 vLLM 내부: 블록 메타데이터와 축출 힙 (§5.3)

CacheWise is ~2,500 lines of Python on top of vLLM, touching the batch scheduler and the KVCache block manager:

CacheWise는 vLLM 위 ~2,500줄의 Python이고, batch scheduler와 KVCache 블록 매니저를 고쳤다.

"We have implemented CacheWise using vLLM … in ~2,500 lines of Python code and extend the batch scheduler and KVCache manager to support CacheWise's predictive block eviction mechanisms."

— §5.3 · 원문 보기 (§5.3)
  • Each block is tagged with engine-parseable session metadata: tool_name, tool_args, Tᵢ (tool call issue time).
  • A block whose refcount hits 0 keeps its metadata and enters an eviction heap ordered by predicted 𝔼[τᵢ(t)], replacing vLLM's LRU. The predictor runs once per session; its blocks share the estimate.
  • Predictions go stale, so the heap is rebuilt every N_rebuild iterations (smaller = fresher, more CPU); the authors use N_rebuild = 3.
  • 각 블록에 세션 메타데이터 tool_name, tool_args, Tᵢ(tool call 시각)를 붙인다.
  • 참조 카운트가 0이 된 블록은 메타데이터를 유지한 채 예측 𝔼[τᵢ(t)] 순의 축출 힙에 들어가며, 이것이 vLLM 기본 LRU를 대체한다. 예측기는 세션당 한 번 호출하고 같은 세션의 블록이 값을 공유한다.
  • 예측은 시간이 지나면 낡으므로 N_rebuild iteration마다 힙을 다시 만든다. N이 작을수록 신선하지만 CPU를 더 쓰며, 저자들은 N_rebuild = 3을 썼다.

4.4 — Is the CPU overhead worth it? (§6.6) 4.4 CPU 오버헤드는 감수할 만한가 (§6.6)

CacheWise does 2.4–3× more CPU scheduling than vLLM, which is noise next to the GPU savings. At N=40, scheduling rises 0.33 s → 0.99 s (~6% → ~9% of request time) while model execution drops 16.6 s → 11.2 s (1.48×). Net: ~4.7 s saved per request.

CPU 스케줄링 일은 vLLM보다 2.4–3× 많지만 GPU 절감에 비하면 작다. N=40에서 스케줄링은 0.33초에서 0.99초(요청시간의 ~6%에서 ~9%)로 늘고, 모델 실행은 16.6초에서 11.2초(1.48×)로 준다. 결과적으로 요청당 ~4.7초를 아낀다.

  4. 예측기는 가벼워서(TF-IDF + KMeans + 생존곡선 적분, ~2,500줄) 미공개 스케줄러 훅만 vLLM 포크에 직접 짜 붙이면 된다.
