"CacheWise: Understanding Workloads and Optimizing KVCache Management for Efficiently Serving LLM Coding Agents" — Tiwari et al. (UW + UVA). A coding agent replays one huge, ever-growing prefix across dozens of tool-call turns. vLLM's FCFS scheduling + LRU eviction thrash that cache. CacheWise adds prefix-aware scheduling and an eviction policy that predicts when a session will come back — from the tool it's running. "CacheWise: Understanding Workloads and Optimizing KVCache Management for Efficiently Serving LLM Coding Agents" — Tiwari 외 (워싱턴대 + 버지니아대). 코딩 에이전트는 거대하고 계속 자라는 프리픽스 하나를 수십 번의 tool-call 턴에 걸쳐 다시 던진다. vLLM의 FCFS 스케줄링 + LRU 축출은 이 캐시를 마구 갈아엎는다(thrash). one-line summary한 줄 요약 A coding-agent session is a closed loop: the LLM emits a tool call, an external tool runs (a grep in 0.1 s, a pytest in 80 s), the result comes back, and the next request reuses the whole growing prefix. Tool-initiated turns are ~20× more frequent than user ones, and prefixes are ~21× more prefill-heavy than chat. vLLM's FCFS + LRU don't know any of this, so they evict prefixes that are about to be reused — KVCache thrashing. CacheWise fixes two knobs at the inference node: (1) prefix-aware scheduling dispatches the request that reuses the most resident cache first, and (2) predictive eviction evicts the session whose cache will be idle longest, estimating "time to next reuse" from the tool's name + arguments. Result: 2–2.6× fewer evictions and up to 3.5× lower session completion time, with negligible CPU overhead. 코딩 에이전트 세션은 닫힌 루프다: LLM이 tool call을 내뱉고, 외부 tool이 돌고(grep은 0.1초, pytest는 80초), 결과가 돌아오면 다음 요청이 자라난 프리픽스 전체를 재사용한다. tool이 촉발한 턴이 사용자 턴보다 ~20× 잦고, 프리픽스는 채팅보다 ~21× prefill 편중이다. vLLM의 FCFS + LRU는 이걸 전혀 모르니, 곧 다시 쓸 프리픽스를 축출해버린다 — KVCache thrashing. CacheWise는 추론 노드에서 두 손잡이를 고친다: (1) prefix-aware 스케줄링은 GPU에 남아있는 캐시를 가장 많이 재사용하는 요청을 먼저 보내고, (2) 예측 축출은 캐시가 가장 오래 놀게 될 세션을 먼저 비우되, "다음 재사용까지 시간"을 tool의 이름+인자로 추정한다. 결과: 축출 2–2.6× 감소, 세션 완료시간 최대 3.5× 단축, CPU 오버헤드는 미미.

📖 KVCache & paged blocks📖 KVCache와 페이지 블록

The per-token key/value tensors a Transformer caches so it doesn't recompute attention over the whole context each step. Modern engines store it in fixed-size blocks (like OS memory pages); evicting/reusing happens block by block.Transformer가 매 스텝마다 전체 문맥에 대한 attention을 다시 계산하지 않으려고 토큰별 key/value 텐서를 캐싱한 것. 현대 엔진은 이를 고정 크기 블록(OS 메모리 페이지처럼)으로 저장하고, 축출·재사용도 블록 단위로 한다.

📖 Session · turn · closed loop📖 세션·턴·닫힌 루프

A turn = one LLM request building on the previous request+result. A coding session = the whole multi-turn task. "Closed loop" = most turns are triggered by a tool returning, not by a human typing.턴 = 이전 요청+결과 위에 쌓는 한 번의 LLM 요청. 코딩 세션 = 멀티턴 작업 전체. "닫힌 루프" = 대부분의 턴이 사람의 타이핑이 아니라 tool이 결과를 반환해서 촉발됨.

📖 Eviction & thrashing📖 축출과 thrashing

When KVCache memory is full, some session's blocks are evicted (dropped). If they're needed again right away, they must be recomputed or copied back — repeat that and you get thrashing: lots of work, little progress.KVCache 메모리가 차면 어떤 세션의 블록을 축출(버림)한다. 곧바로 다시 필요해지면 재계산하거나 다시 복사해와야 한다 — 이게 반복되면 thrashing: 일은 많고 진척은 없는 상태.

📖 Token goodput📖 토큰 goodput

Throughput counts all tokens processed; goodput counts only the useful ones — after subtracting tokens spent re-prefilling evicted prefixes. Less thrashing → higher goodput.throughput는 처리한 모든 토큰을 세지만, goodput은 유용한 토큰만 — 축출된 프리픽스를 다시 prefill하느라 쓴 토큰을 뺀 값. thrashing이 적을수록 goodput이 높다.

📖 τ & Belady's rule📖 τ와 Belady 규칙

τi = "time to next reuse" of session i's blocks. The provably optimal eviction (Belady, 1966) evicts whatever will be reused furthest in the future. You can't normally know τ — CacheWise predicts it.τi = 세션 i 블록의 "다음 재사용까지 시간". 이론적 최적 축출(Belady, 1966)은 가장 먼 미래에 재사용될 것을 버린다. 보통 τ는 알 수 없다 — CacheWise는 그걸 예측한다.

📖 LRU vs prefix-aware vs predictive📖 LRU vs prefix-aware vs 예측

LRU evicts by past recency (looks backward). Prefix-aware scheduling picks the request that reuses the most resident cache. Predictive eviction looks forward — keep what returns soonest.LRU는 과거 사용 시점으로 축출(뒤를 봄). Prefix-aware 스케줄링은 남은 캐시를 가장 많이 재사용하는 요청을 고른다. 예측 축출은 앞을 본다 — 가장 빨리 돌아올 것을 남긴다.

1 Problem definition 문제 정의

1.1 — We tuned serving for chatbots; coding agents look nothing like chatbots 1.1 — 서빙은 챗봇에 맞춰 튜닝됐는데, 코딩 에이전트는 챗봇과 전혀 다르다

A chatbot turn is simple: user asks, model answers, done. A coding agent (Claude Code, Codex, SWE-agent…) instead makes a multi-step plan and executes it through tool calls — run a test, grep a file, edit code — looping between the LLM and the environment. The authors' first move is to point out that nobody has actually studied how this kind of traffic behaves on a serving engine, mostly because no public traces existed. So they collected their own.

챗봇 턴은 단순하다: 사용자가 묻고, 모델이 답하면 끝. 반면 코딩 에이전트(Claude Code, Codex, SWE-agent…)는 여러 단계 계획을 세우고 tool call로 실행한다 — 테스트 돌리고, 파일 grep하고, 코드 수정하고 — LLM과 환경 사이를 오가며 루프를 돈다. 저자들의 첫 한 수는, 이런 트래픽이 서빙 엔진에서 어떻게 행동하는지 아무도 제대로 연구한 적이 없다는 지적이다. 공개 트레이스가 없었던 게 큰 이유. 그래서 직접 모았다.

"Compared to chatbot workloads, coding-agent sessions are long-running, accumulate substantially larger contexts, and are dominated by tool-initiated turns rather than direct user input."

— §1, ¶3 · 원문 보기 (§1)

The consequence reframes the whole optimization target. In chat serving we chase per-request latency (TTFT, time-between-tokens). For an agent, no human is waiting on any single request inside the loop — what matters is when the whole session finishes:

그 결과가 최적화 목표 자체를 바꾼다. 채팅 서빙에선 요청별 레이턴시(TTFT, 토큰 간 시간)를 쫓는다. 에이전트에선 루프 안의 개별 요청을 기다리는 사람이 없다 — 중요한 건 세션 전체가 언제 끝나느냐다:

"the key objective is not the latency of an individual request, but the completion time of the full multi-turn session."

— §1, ¶3 · 원문 보기 (§1)

1.4 — Why FCFS + LRU is the wrong default (§1, §4) 1.4 — 왜 FCFS + LRU가 잘못된 기본값인가 (§1, §4)

vLLM and Mooncake batch requests First-Come-First-Served and evict KVCache Least-Recently-Used. Both are workload-agnostic, and that's the problem — they ignore the two facts above (high intra-session prefix overlap, tool-dependent reuse timing):

vLLM과 Mooncake는 요청을 FCFS로 배칭하고 KVCache를 LRU로 축출한다. 둘 다 워크로드-무관(workload-agnostic)인데, 그게 문제다 — 위의 두 사실(세션 내 높은 프리픽스 중첩, tool 의존적 재사용 타이밍)을 무시한다:

"Under memory pressure, these policies therefore trigger KVCache thrashing, reducing useful work and lowering token goodput (i.e., the rate of useful token processing after excluding recomputation and KVCache movement overheads)."

— §1, ¶4 · 원문 보기 (§1)

There's also a "why not an existing agent-serving system" beat. Recent agent-aware engines (Pie, Autellix) require you to rewrite the agent against their programming abstraction — a non-starter when you must serve diverse, already-deployed clients like Claude Code. CacheWise deliberately changes only the serving system, leaving the agent untouched:

"이미 있는 에이전트 서빙 시스템을 쓰면 되지 않나"에 대한 답도 있다. 최근 에이전트-aware 엔진(Pie, Autellix)은 에이전트를 그들의 프로그래밍 추상화에 맞춰 다시 짜야 한다 — Claude Code처럼 이미 배포된 다양한 클라이언트를 서빙해야 할 땐 불가능한 요구다. CacheWise는 의도적으로 서빙 시스템만 바꾸고 에이전트는 손대지 않는다:

"they tightly couple the agent implementation framework with the LLM serving system, and thus are ill-suited for large-scale deployments, which must support diverse clients."

— §1, ¶4 · 원문 보기 (§1)

2 Method 해결 방법

2.1 — A tiny memory model that makes the problem precise (§4) 2.1 — 문제를 정밀하게 만드는 작은 메모리 모델 (§4)

Before proposing anything, the paper writes down a lightweight model of node memory. It's worth walking symbol by symbol because every design choice references it.

무언가 제안하기 전에, 논문은 노드 메모리의 가벼운 모델을 적어둔다. 모든 설계 선택이 이걸 참조하니 기호 하나씩 짚어보자.

M = KVCache block capacity of a node  ·  𝒮ₜ = {S₁, S₂, …} active sessions at time t
Sᵢ has a growing prefix of dᵢ blocks, of which kᵢ(t) are resident in XPU memory
Working set:   W(t) = Σᵢ kᵢ(t)   →   no eviction needed while W(t) ≤ M
New request rᵢ needs dᵢ total; extra blocks to allocate:   aᵢ(t) = dᵢ − kᵢ(t)
Admit immediately if W(t) + aᵢ(t) ≤ M  —  else evict aᵢ(t) blocks from other sessions

In words: M is the GPU memory left for KVCache after weights. Each live session Sᵢ owns a prefix; kᵢ(t) is how much of it is currently in GPU memory. When a session fires its next request, most of its context is already cached (the reusable overlap), so it only needs aᵢ(t) = "total − already-resident" new blocks. If those fit, great; if not, the system must evict someone. "XPU" is just the authors' umbrella term for GPU/TPU. (One notational nit: the prose at one point writes the working set with dᵢ, but Fig. 10 and the rest of the model use the resident blocks kᵢ(t) — the resident-blocks reading is the consistent one.)

말로 풀면: M은 가중치를 빼고 KVCache에 남은 GPU 메모리. 살아있는 각 세션 Sᵢ는 프리픽스를 갖고, kᵢ(t)는 그중 지금 GPU에 올라온 양. 세션이 다음 요청을 쏘면 문맥 대부분은 이미 캐시돼 있으니(재사용 가능한 중첩분), "전체 − 이미 있는 양" = aᵢ(t) 만큼의 새 블록만 필요하다. 들어가면 OK, 아니면 누군가를 축출해야 한다. "XPU"는 GPU/TPU를 묶어 부르는 저자들의 표현. (사소한 표기 주의: 본문 한 곳은 working set을 dᵢ로 쓰지만 Fig 10과 모델 나머지는 resident 블록 kᵢ(t)를 쓴다 — resident 해석이 일관적이다.)

The memory pressure moment (Fig. 10). FCFS decides which request runs; LRU/CacheWise decides whose blocks get evicted when r₅ doesn't fit.메모리 압박의 순간 (Fig. 10). FCFS는 어떤 요청을 돌릴지, LRU/CacheWise는 r₅가 안 들어갈 때 누구 블록을 축출할지를 정한다.

Implication #1 — FCFS thrashes함의 #1 — FCFS는 thrashing을 부른다

A session is active (running on the XPU), queued (waiting for memory), or inactive (waiting on the user/tool). FCFS interleaves requests from many queued sessions, so it tries to raise kᵢ for lots of sessions at once → the working set balloons past M → it evicts one session's blocks to fit another's → that evicted state is usually reused soon by the same session → evict, recompute, repeat:

세션은 active(XPU에서 실행 중), queued(메모리 대기), inactive(사용자/tool 대기) 중 하나다. FCFS는 여러 queued 세션의 요청을 끼워 넣으니 한꺼번에 많은 세션의 kᵢ를 올리려 한다 → working set이 M을 넘어 부풀고 → 한 세션 블록을 축출해 다른 세션을 끼우고 → 그 축출된 상태는 보통 같은 세션이 곧 다시 쓰고 → 축출·재계산·반복:

"Since this evicted state is often reused by subsequent requests within the same session, FCFS scheduling leads to repeated eviction and recomputation (or movement) of state, resulting in KVCache thrashing."

— §4, "Implication #1" · 원문 보기 (§4)

Implication #2 — LRU is blind to the future함의 #2 — LRU는 미래를 못 본다

When eviction is forced, not all victims cost the same. Define τᵢ = time until session Sᵢ next touches its blocks. Evicting a small-τ session means a recompute penalty almost immediately; evicting a large-τ session is cheap (its memory is free to lend out for that whole stretch). So the ideal victim is the session with the largest τ:

축출이 강제될 때, 모든 희생자의 비용이 같지는 않다. τᵢ = 세션 Sᵢ가 자기 블록을 다음에 건드릴 때까지의 시간. τ가 작은 세션을 축출하면 거의 즉시 재계산 벌점을 문다. τ가 큰 세션을 축출하면 싸다(그 메모리를 그 기간 내내 빌려줄 수 있으니). 그래서 이상적 희생자는 τ가 가장 큰 세션:

j* = argmax j ∈ 𝒮ₜ, j ≠ i  τⱼ   ←  evict the session whose reuse is furthest away

"An ideal eviction policy therefore selects j*=argmax_{j∈𝒮ₜ, j≠i} τⱼ, retaining sessions whose KVCache will be needed soonest."

— §4, "Implication #2" · 원문 보기 (§4)

LRU can't do this: it only sees past recency, not future τ. So it suffers priority inversions — it evicts a high-reuse-value block (one with small τ that just hasn't been touched lately) and pays to bring it back. The whole design problem is now sharp: schedule to keep the working set small, and evict by predicted future reuse, not past recency.

LRU는 이걸 못한다: 과거 recency만 보고 미래 τ를 못 보니까. 그래서 우선순위 역전이 생긴다 — 재사용 가치가 높은 블록(τ가 작은데 최근에 안 건드려졌을 뿐)을 축출하고, 다시 가져오는 비용을 문다. 이제 설계 문제가 또렷하다: working set을 작게 유지하도록 스케줄하고, 과거 recency가 아니라 예측된 미래 재사용으로 축출하라.

2.2 — Idea 1: prefix-aware scheduling (§5.1) 2.2 — 아이디어 1: prefix-aware 스케줄링 (§5.1)

Instead of FCFS, dispatch the request that needs the fewest new blocks — i.e., the one that reuses the most cache already resident:

FCFS 대신, 새 블록이 가장 적게 필요한 요청 — 즉 이미 올라온 캐시를 가장 많이 재사용하는 요청 — 을 보낸다:

"at time t, CacheWise selects request rᵢ which requires fewest additional blocks aᵢ(t) to be allocated as the next request to dispatch."

— §5.1 · 원문 보기 (§5.1)

Two things fall out. First, it directly shrinks the working set, so it minimizes the thrashing other sessions suffer. Second, dispatching by ascending aᵢ(t) approximates shortest-job-first — which minimizes total queueing at the cost of per-request responsiveness. For agents that's the right trade, because (again) no human is waiting on any single request:

두 가지가 따라온다. 첫째, working set을 직접 줄이니 다른 세션이 겪는 thrashing을 최소화한다. 둘째, aᵢ(t) 오름차순 디스패치는 shortest-job-first를 근사한다 — 요청별 응답성을 희생하는 대신 전체 큐잉을 최소화한다. 에이전트엔 이게 옳은 거래다. (다시) 개별 요청을 기다리는 사람이 없으니까:

"optimizing end-to-end session completions is more important than minimizing per-request TTFT or TBT, as no user is waiting on any individual request."

— §5.1 · 원문 보기 (§5.1)

Greedy prefix-aware scheduling already exists (SGLang); the paper's point is that it's especially effective for long-running closed-loop sessions, where the evicted blocks are guaranteed to come back.greedy prefix-aware 스케줄링 자체는 이미 있다(SGLang). 논문의 포인트는, 축출된 블록이 반드시 돌아오는 장기 닫힌-루프 세션에서 이게 특히 효과적이라는 것.

2.3 — Idea 2: predictive eviction (§5.2) 2.3 — 아이디어 2: 예측 축출 (§5.2)

Scheduling reduces evictions but can't eliminate them — context keeps growing. The optimal eviction is Belady's rule (evict the furthest-future reuse), which needs τ. CacheWise's key trick: you don't need τ's exact value, only its relative order across sessions — and in practice, just nailing the single largest-τ session is enough:

스케줄링은 축출을 줄이지만 없애진 못한다 — 문맥은 계속 자라니까. 최적 축출은 Belady 규칙(가장 먼 미래 재사용을 버림)이고 τ가 필요하다. CacheWise의 핵심 트릭: τ의 정확한 값이 아니라 세션 간 상대 순서만 있으면 되고 — 실제론 가장 τ 큰 세션 하나만 맞혀도 충분하다:

"CacheWise only needs to predict the relative order of τ(t) across sessions to identify which blocks to evict. … accurately identifying the session with the highest τᵢ(t) is sufficient."

— §5.2 · 원문 보기 (§5.2)

How to estimate τ? From the tool a session is waiting on. When session Sᵢ launches a tool call with metadata m = (tool_name, tool_args) at time Tᵢ, the predictor estimates the expected remaining time until it returns. The exact quantity is a conditional expectation:

τ는 어떻게 추정하나? 세션이 기다리는 tool로부터. 세션 Sᵢ가 시각 Tᵢ에 메타데이터 m = (tool_name, tool_args)로 tool call을 시작하면, 예측기는 결과가 돌아올 때까지의 기대 잔여 시간을 추정한다. 정확한 양은 조건부 기댓값이다:

𝔼[ τᵢ(t) | τᵢ(t) − Tᵢ > t − Tᵢ ]

Reading the formula. τᵢ(t) − Tᵢ is the tool's total duration (from launch Tᵢ to completion). t − Tᵢ is how long it has run so far. The condition "total > elapsed-so-far" just means "it hasn't finished yet." So this is: "given the tool has already been running for (t − Tᵢ) and isn't done, how much longer, on average?" — the classic expected-residual-life question. The estimate comes from the empirical distribution of durations for tool calls with similar metadata m drawn from history (same user, same project). As time passes the answer shifts, so the estimate is refreshed.

수식 읽기. τᵢ(t) − Tᵢ는 tool의 전체 실행시간(시작 Tᵢ부터 완료까지). t − Tᵢ는 지금까지 돌린 시간. 조건 "전체 > 지금까지"는 "아직 안 끝났다"는 뜻일 뿐. 그래서 이 식은: "이 tool이 이미 (t − Tᵢ)만큼 돌았고 아직 안 끝났다면, 평균적으로 얼마나 더 걸리나?" — 고전적인 기대 잔여수명 질문이다. 추정값은 비슷한 메타데이터 m을 가진 과거 tool call들의 실행시간 분포(같은 사용자·같은 프로젝트)에서 나온다. 시간이 흐르면 답이 바뀌므로 추정값을 갱신한다.

The two mechanisms (redrawn from Fig. 11 B/C). Eviction ranks sessions by predicted time-to-reuse from the tool they're blocked on, not by recency.두 메커니즘 (Fig. 11 B/C 재구성). 축출은 recency가 아니라, 세션이 막혀 기다리는 tool로부터 예측한 재사용 시간으로 순위를 매긴다.

3 Implementation 구현 방법

3.1 — The predictor: TF-IDF + KMeans over tool arguments (§5.2) 3.1 — 예측기: tool 인자에 대한 TF-IDF + KMeans (§5.2)

Conditioning on tool name alone isn't enough — a bash call can be a 0.1 s python -c or a 80 s pytest. So CacheWise looks at the arguments. It encodes each tool's arguments as a TF-IDF vector (a term gets a high weight if it's frequent in this argument string but rare across others — so distinctive tokens like pytest or docker dominate), then KMeans-clusters those vectors and keeps a duration distribution per cluster rather than per tool name.

tool 이름만으로 조건을 거는 건 부족하다 — bash 호출이 0.1초짜리 python -c일 수도, 80초짜리 pytest일 수도 있으니. 그래서 CacheWise는 인자를 본다. 각 tool의 인자를 TF-IDF 벡터로 인코딩하고(어떤 단어가 이 인자 문자열엔 자주 나오는데 다른 인자엔 드물면 높은 가중치 — 그래서 pytest, docker 같은 특징적 토큰이 지배), 그 벡터를 KMeans로 군집화한 뒤, tool 이름별이 아니라 군집별 실행시간 분포를 유지한다.

3.2 — Inside vLLM: block metadata + an eviction heap (§5.3) 3.2 — vLLM 내부: 블록 메타데이터 + 축출 힙 (§5.3)

CacheWise is ~2,500 lines of Python on top of vLLM, touching the batch scheduler and the KVCache block manager:

CacheWise는 vLLM 위 ~2,500줄의 Python으로, batch scheduler와 KVCache 블록 매니저를 건드린다:

"We have implemented CacheWise using vLLM … in ~2,500 lines of Python code and extend the batch scheduler and KVCache manager to support CacheWise's predictive block eviction mechanisms."

— §5.3 · 원문 보기 (§5.3)
  • Each KVCache block is tagged with session-level metadata: tool_name, tool_args, and Tᵢ (when the tool call was issued) — parseable by the vLLM engine itself.
  • When a request completes and a block's reference count hits 0, the block (keeping its metadata) goes into an eviction heap ordered by predicted 𝔼[τᵢ(t)]. This replaces vLLM's default LRU. The predictor is invoked once per session, not once per block — blocks sharing a session share the estimate.
  • Predictions go stale as time elapses, so the heap is rebuilt every N_rebuild engine iterations. Small N = fresher but more CPU; the authors use N_rebuild = 3.
  • 각 KVCache 블록에 세션 메타데이터를 붙인다: tool_name, tool_args, Tᵢ(tool call 발생 시각) — vLLM 엔진이 직접 파싱 가능.
  • 요청이 끝나 블록 참조 카운트가 0이 되면, 그 블록은(메타데이터 유지) 예측된 𝔼[τᵢ(t)] 순으로 정렬된 축출 힙에 들어간다. vLLM 기본 LRU를 대체. 예측기는 블록당이 아니라 세션당 한 번 호출 — 같은 세션 블록은 추정값을 공유.
  • 시간이 지나면 예측이 낡으므로 N_rebuild 엔진 iteration마다 힙을 재구축. 작은 N = 더 신선하지만 CPU 더 씀. 저자들은 N_rebuild = 3 사용.

4.4 — Is the CPU overhead worth it? (§6.6) 4.4 — CPU 오버헤드는 그만한 값을 하나? (§6.6)

CacheWise does 2.4–3× more CPU scheduling work than vLLM — but in absolute terms that's noise next to the GPU savings. At N=40, scheduling rises from 0.33 s to 0.99 s, while GPU model-execution drops from 16.6 s to 11.2 s (1.48×). Net: ~4.7 s saved per request. Scheduling goes from ~6% to ~9% of request time; the model-exec reduction is what drives the end-to-end gains.

CacheWise는 vLLM보다 CPU 스케줄링 일을 2.4–3× 더 한다 — 하지만 절대값으론 GPU 절감 옆에서 노이즈 수준이다. N=40에서 스케줄링은 0.33초→0.99초로 늘지만, GPU 모델 실행은 16.6초→11.2초(1.48×)로 준다. 순효과: 요청당 ~4.7초 절감. 스케줄링은 요청시간의 ~6%→~9%로, 엔드투엔드 이득을 끄는 건 모델 실행 시간 감소다.

5.4 — Our read (not the paper's claims) 5.4 — 우리 관점의 해석 (논문의 주장 아님)

editor's note — connections to our other notes편집자 주 — 우리 다른 노트들과의 연결 ① This is the per-node twin of the cross-node story in our llm-d Agentic Serving note: llm-d routes a session to the node holding its prefix (prefix-cache-aware routing); CacheWise then decides, inside that node, what to keep and what to evict. They compose — routing gets the session to the cache, scheduling+eviction keeps the cache alive. ② The reuse signal is the interesting bit. Our prefix-cache routing note tracks what overlaps; CacheWise adds when it will be reused, and gets that for free from tool metadata the engine already sees — no agent changes, which is the same "don't couple agent and engine" stance llm-d takes. ③ Practical caveat for our own benches: the headline 3.5× is at N>10 on a single 2×H200 with one model; the mechanism (predict τ from the tool) should transfer, but the magnitude won't — re-measure on MI250 / our models before quoting it. ④ The conditional-expectation predictor is genuinely lightweight (TF-IDF + KMeans + a survival-curve integral, ~2,500 LOC) — a realistic thing to prototype against a vLLM fork, since the released repo gives us the predictor and the traces but not the scheduler hook. ① 이건 우리 llm-d Agentic Serving 노트의 노드-간 이야기에 대한 노드-내 쌍둥이다: llm-d는 세션을 그 프리픽스를 가진 노드로 라우팅(prefix-cache-aware routing)하고, CacheWise는 그 노드 안에서 무엇을 남기고 무엇을 축출할지 정한다. 둘은 합쳐진다 — 라우팅이 세션을 캐시로 데려오고, 스케줄링+축출이 캐시를 살려둔다. ② 재미있는 건 재사용 신호다. 우리 prefix-cache 라우팅 노트는 무엇이 겹치는지를 추적하는데, CacheWise는 언제 다시 쓰일지를 더하고, 그걸 엔진이 이미 보는 tool 메타데이터에서 공짜로 얻는다 — 에이전트 변경 없이, llm-d와 같은 "에이전트와 엔진을 결합하지 말라" 입장. ③ 우리 벤치를 위한 실무 주의: 핵심 3.5×는 단일 2×H200·단일 모델·N>10에서다. 메커니즘(tool로 τ 예측)은 이전될 테지만 배수는 안 된다 — MI250/우리 모델에서 재측정 후 인용할 것. ④ 조건부 기댓값 예측기는 진짜로 가볍다(TF-IDF + KMeans + 생존곡선 적분, ~2,500줄) — 공개 레포가 예측기와 트레이스는 주되 스케줄러 훅은 안 주니, vLLM 포크에 직접 프로토타이핑해볼 만한 현실적 대상이다.
