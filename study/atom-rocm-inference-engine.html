Its README says it plainly: the project was adapted from nano-vllm — a ~1.2k-line teaching reimplementation of vLLM — and AMD grew that skeleton into a production engine whose every hot operation calls an AITER kernel instead of a generic PyTorch op. This note walks the architecture, traces one request end-to-end through the real code with commit-pinned permalinks, shows the exact commands to run it, and asks the honest question: what does ATOM actually give you that vLLM-on-ROCm doesn't? one-line summary한 줄 요약 ATOM is vLLM's architecture re-implemented small enough for AMD to move fast in: same continuous batching, paged KV cache, prefill-first scheduler, CUDA graphs and speculative decoding, but ~300 Python files instead of vLLM's thousands, and every compute-heavy call routed to an AITER kernel (ASM / Composable Kernel / Triton). It has a dual identity — a standalone OpenAI-compatible server and a plugin backend that installs itself into vLLM and SGLang through their official entry-point hooks, so the community can get AMD-tuned execution without leaving vLLM. That plugin shape was not AMD's first choice — vLLM's maintainers rejected the in-tree proposal and AMD reframed. And the honest performance picture is narrower than the marketing: the only apple-to-apple comparison AMD itself published is +2.8% to +6.9% over vLLM, not the "2–3×" its README once claimed and then deleted. ATOM은 AMD가 빠르게 움직일 수 있을 만큼 작게 다시 구현한 vLLM 아키텍처다. continuous batching, paged KV cache, prefill-first scheduler, CUDA graph, speculative decoding까지 개념은 같지만, vLLM의 수천 개 파일 대신 Python 파일 ~300개이고, 무거운 연산은 전부 AITER 커널(ASM / Composable Kernel / Triton)로 내려간다. 정체성이 둘이다 — 독립 실행되는 OpenAI 호환 서버이면서, 동시에 vLLM·SGLang의 공식 entry-point 훅으로 자기를 꽂아 넣는 플러그인 백엔드이기도 하다. 덕분에 사용자는 vLLM을 떠나지 않고도 AMD 최적화 실행 경로를 쓸 수 있다. 다만 이 플러그인 형태는 AMD의 1지망이 아니었다 — vLLM 메인테이너들이 in-tree 제안을 거절했고 AMD가 방향을 다시 짰다. 그리고 성능의 실상은 마케팅보다 좁다. AMD가 직접 공개한 유일한 동일 조건 비교는 vLLM 대비 +2.8%~+6.9%이지, README가 한때 주장했다가 삭제한 "2~3배"가 아니다.

paged KV cachepaged KV cache

Most inference engines are coy about their ancestry. ATOM is not — the last real section of its README is two lines long: 대부분의 추론 엔진은 자기 계보를 흐릿하게 둔다. ATOM은 아니다 — README의 마지막 실질 섹션은 두 줄이다:

"## Acknowledgements
This project was adapted from nano-vllm."

— ROCm/ATOM README.md · README.md#L281-L283 @ cd161f1

nano-vllm is a personal MIT-licensed project by GeeeekExplorer (Xingkai Yu, whose GitHub profile lists @deepseek-ai — that profile field is the only evidence of affiliation; nothing states nano-vllm is a DeepSeek project). Its README describes itself as "A lightweight vLLM implementation built from scratch", with a "Readable codebase — clean implementation in ~ 1,200 lines of Python code" and an "Optimization Suite — Prefix caching, Tensor Parallelism, Torch compilation, CUDA graph, etc." Cloning it and counting gives 1,385 lines across 19 files today, so the claim has drifted up ~15% but is honest. Notably it implements exactly one model (models/qwen3.py) and has no MoE, no quantization, no OpenAI server, and no speculative decoding — everything ATOM has, ATOM added. nano-vllm은 GeeeekExplorer(Xingkai Yu, GitHub 프로필에 @deepseek-ai가 적혀 있다 — 소속 근거는 그 프로필 항목뿐이고, nano-vllm이 DeepSeek 프로젝트라는 언급은 어디에도 없다)의 MIT 라이선스 개인 프로젝트다. README는 스스로를 "A lightweight vLLM implementation built from scratch"라 소개하고, "Readable codebase — clean implementation in ~ 1,200 lines of Python code", "Optimization Suite — Prefix caching, Tensor Parallelism, Torch compilation, CUDA graph, etc."를 내세운다. 직접 클론해 세어 보면 현재 19개 파일 1,385줄이니, 주장이 15%쯤 늘어났을 뿐 정직한 수치다. 눈여겨볼 점은 모델이 정확히 하나(models/qwen3.py)이고 MoE도, quantization도, OpenAI 서버도, speculative decoding도 없다는 것이다 — ATOM이 가진 건 전부 ATOM이 붙인 것이다.

The adoption gap between parent and fork is worth a moment: nano-vllm has 15,252 stars; ROCm/ATOM has 168. A teaching repo by one person is two orders of magnitude more widely starred than a chip vendor's production engine — which tells you something real about who ATOM is actually for. 부모와 포크의 채택 격차는 잠깐 볼 만하다. nano-vllm은 별 15,252개, ROCm/ATOM은 168개다. 한 사람이 만든 학습용 레포가 칩 벤더의 프로덕션 엔진보다 별이 두 자릿수 배 많다 — ATOM이 실제로 누구를 위한 물건인지에 대해 이 숫자가 말해주는 바가 있다.

So the lineage is not a vague "inspired by". ATOM started as a fork of a 1,200-line educational repo and became a ~300-file engine serving 2.4-trillion-parameter models on 8-GPU nodes. That history explains a lot about how the code reads: the class names (LLMEngine, Scheduler, BlockManager, Sequence, ModelRunner) are vLLM's vocabulary, the scheduling policy is vLLM's continuous batching, and several files carry explicit "Adapted from vllm-project/vllm" headers — the model implementations (llama.py, qwen3.py, gpt_oss.py, mimo_v2.py), the weight loader, and the WeightsMapper. Some utilities are adapted from SGLang, and the linear-attention kernels from flash-linear-attention. 그러니까 계보가 막연한 "영감을 받았다"가 아니다. ATOM은 1,200줄짜리 교육용 레포의 포크로 출발해, 8-GPU 노드에서 2.4조 파라미터 모델을 서빙하는 ~300파일 엔진이 됐다. 이 내력이 코드의 인상을 상당 부분 설명한다. 클래스 이름(LLMEngine, Scheduler, BlockManager, Sequence, ModelRunner)은 vLLM의 어휘 그대로고, 스케줄링 정책도 vLLM의 continuous batching이며, 여러 파일에 "Adapted from vllm-project/vllm" 헤더가 명시적으로 붙어 있다 — 모델 구현(llama.py, qwen3.py, gpt_oss.py, mimo_v2.py), weight loader, WeightsMapper가 그렇다. 일부 유틸은 SGLang에서, linear attention 커널은 flash-linear-attention에서 가져왔다.

An internal positioning draft that ships in the repo (atom_overview_draft.md, marked "Draft – Internal Review Only") states the motive in the plainest terms available — and it names nano-vllm as the model: 레포에 함께 들어 있는 내부 포지셔닝 초안(atom_overview_draft.md, "Draft – Internal Review Only" 표기)이 동기를 가장 직설적으로 적어 놨다 — 그리고 nano-vllm을 본보기로 지목한다:

"ATOM's embrace the same minimalist mindset of nano-vllm 'minimalist' architecture allows it to evolve at the speed of AMD silicon. By stripping away layers of abstraction found in generic frameworks, ATOM connects the model directly to the metal via the AITER kernel library."

The same draft sets out ATOM's dual role, which is the single most important thing to understand about the project: 같은 초안이 ATOM의 이중 역할을 정리해 두는데, 이 프로젝트에서 가장 중요한 한 가지가 바로 이것이다:

"Standalone Optimization Platform: It serves as a 'Proving Ground' for rapid iteration, allowing AMD to develop and validate internal system-level optimizations, compiler-driven graph enhancements, and kernel acceleration.
Integrated Plugin Backend: It integrates as a high-performance backend for popular frameworks like vLLM and SGLang, ensuring that the broader AI community can access AMD-specific optimizations without changing their existing workflows."

— atom_overview_draft.md §A Dual-Purpose Architecture · atom_overview_draft.md#L15-L17 @ cd161f1

Read that carefully, because it resolves the obvious objection — "vLLM already runs on ROCm, why build a second engine?" AMD's answer is that ATOM is not primarily competing with vLLM for users. It is a fast-moving lab where AMD can land a new kernel, a new fused op, or a Day-0 model on its own schedule, and then expose the result through vLLM via a plugin. The standalone server is how AMD proves the optimization; the plugin is how you consume it. 이 대목을 잘 읽어야 한다. "vLLM은 이미 ROCm에서 돌아가는데 왜 엔진을 하나 더 만드나"라는 당연한 반론이 여기서 풀리기 때문이다. AMD의 답은, ATOM이 사용자를 두고 vLLM과 경쟁하는 게 주 목적이 아니라는 것이다. ATOM은 새 커널·새 fused op·Day-0 모델을 AMD 자신의 일정대로 얹을 수 있는 빠른 실험실이고, 그 결과물을 플러그인을 통해 vLLM 으로 내보낸다. 독립 서버는 최적화를 증명하는 자리이고, 플러그인은 그걸 소비하는 통로다.

What that line hides is that these are not all in one process. ATOM fans out into a process tree: the API server and tokenizer stay in the parent, each data-parallel rank gets its own EngineCore process, and each tensor-parallel rank inside it gets its own ModelRunner subprocess holding one GPU. The pieces talk over ZeroMQ with pickled payloads. 저 한 줄이 감추는 사실은, 이것들이 한 프로세스 안에 있지 않다는 점이다. ATOM은 프로세스 트리로 펼쳐진다. API 서버와 tokenizer는 부모 프로세스에 남고, data-parallel rank마다 EngineCore 프로세스가 하나씩, 그 안의 tensor-parallel rank마다 GPU 하나를 쥔 ModelRunner 서브프로세스가 하나씩 붙는다. 조각들은 pickle 페이로드를 실은 ZeroMQ로 대화한다.

Two details worth pausing on잠깐 멈춰 볼 만한 두 지점

Preemption is a full rollback, not a pause. When decode cannot get a block, the scheduler evicts the last running sequence: it deallocates every block, strips the speculative placeholder and rejected tokens that postprocess() had appended, zeroes the speculation state, and pushes the sequence to the front of the waiting queue to be re-prefilled from scratch. ATOM has no swap-to-host path for this case — the work is simply redone. preemption은 일시정지가 아니라 완전 롤백이다. decode가 블록을 못 얻으면 스케줄러는 마지막 running 시퀀스를 쫓아낸다. 블록을 전부 반납하고, postprocess()가 붙여 놨던 speculative placeholder와 rejected 토큰을 떼어내고, speculation 상태를 0으로 만든 뒤, 그 시퀀스를 대기 큐 맨 앞에 밀어 넣어 처음부터 다시 prefill한다. 이 경우에 대한 host swap 경로가 ATOM에는 없다 — 그냥 다시 계산한다.

The companion trick is the global ForwardContext. Rather than threading attention metadata down through every function signature, ATOM sets a module-level global before the forward pass and has backends call get_forward_context(). That keeps the compiled subgraphs' signatures stable across steps — a parameter that changes shape would invalidate the capture. It is an unusual choice for readability and a deliberate one for CUDA-graph compatibility. 짝을 이루는 요령이 전역 ForwardContext다. attention 메타데이터를 모든 함수 시그니처로 타고 내려보내는 대신, ATOM은 forward 전에 모듈 레벨 전역을 세팅하고 백엔드가 get_forward_context()로 꺼내 쓰게 한다. 그래야 컴파일된 서브그래프의 시그니처가 스텝마다 안정적으로 유지된다 — 형태가 바뀌는 파라미터가 있으면 캡처가 무효화되니까. 가독성 관점에선 특이한 선택이지만, CUDA graph 호환성 관점에선 의도적인 선택이다.

editor's note — my read, not AMD's claim편집자 주 — AMD의 주장이 아닌 내 해석 The most interesting thing about ATOM is not its performance — it is the organisational move, and the fact that it was negotiated down. AMD's problem was never "can vLLM run on ROCm"; it was that shipping an AMD kernel optimization meant landing it in someone else's multi-vendor repo on someone else's schedule. AMD's first answer was to put ATOM in-tree; vLLM said no, on governance grounds that have nothing to do with whether ATOM's kernels are good. The plugin is the settlement.

What is striking is that four independent parties converged on the same description of what ATOM is: simon-mo proposed it ("a speed-of-light reference implementation to set the performance bar"), AMD accepted it ("working as the incubator of the optimizations"), the ATOMesh blog restates it ("consistent with ATOM's role as the reference path"), and SemiAnalysis confirms it from the demand side ("zero production customers"). So the honest framing is not "AMD's answer to vLLM" — it is a reference implementation and upstreaming staging area, and it is a much more defensible thing to be. The failure mode to watch for is the "upstreamed immediately" half never arriving, leaving ATOM a permanent AMD-only fork of the engine layer instead of a staging area. ATOM에서 가장 흥미로운 건 성능이 아니라 조직적 수이고, 그것이 협상으로 깎였다는 사실이다. AMD의 문제는 애초에 "vLLM이 ROCm에서 도느냐"가 아니었다. AMD 커널 최적화를 출시하려면 남의 다중 벤더 레포에, 남의 일정에 맞춰 넣어야 한다는 게 문제였다. AMD의 첫 답은 ATOM을 in-tree로 넣는 것이었고, vLLM은 거절했다 — ATOM 커널이 좋으냐 나쁘냐와 무관한, 거버넌스를 근거로. 플러그인은 그 합의의 결과물이다.

인상적인 건 서로 독립적인 네 주체가 ATOM의 정체를 같은 말로 수렴시켰다는 점이다. simon-mo가 제안했고("a speed-of-light reference implementation to set the performance bar"), AMD가 받아들였고("working as the incubator of the optimizations"), ATOMesh 블로그가 반복했고("consistent with ATOM's role as the reference path"), SemiAnalysis가 수요 쪽에서 확인했다("zero production customers"). 그러니 솔직한 규정은 "AMD판 vLLM"이 아니다. 레퍼런스 구현이자 upstream 대기 구역이고, 그편이 훨씬 방어하기 좋은 정체성이다. 경계할 실패 양상은 "upstreamed immediately"의 나머지 절반이 끝내 오지 않아, ATOM이 스테이징 구역이 아니라 엔진 계층의 영구적인 AMD 전용 포크로 굳는 것이다.
