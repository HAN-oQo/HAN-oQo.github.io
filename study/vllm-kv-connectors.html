What's a KV connector?KV 커넥터란?

A plug-in that moves a request's KV-cache out of one vLLM engine and into another place — a peer engine (for P/D disaggregation), a shared store (for prefix reuse), or CPU/disk (for offload).요청의 KV-cache를 한 vLLM 엔진 밖으로 옮겨 다른 곳으로 보내는 플러그인 — 다른 엔진(P/D 분리 서빙), 공유 스토어(prefix 재사용), CPU/디스크(오프로드).

Push (prefill→decode)Push (prefill→decode)

The producer (prefill) initiates the network transfer — it writes KV into the consumer's memory after computing it.생산자(prefill)가 전송을 시작 — 계산을 마친 KV를 소비자 메모리로 써넣는다.

Pull (decode→prefill)Pull (decode→prefill)

The consumer (decode) initiates — it reads the KV from the producer when it knows where to look. The producer just registers/exposes its KV and waits.소비자(decode)가 시작 — 출처를 알게 되면 생산자에서 KV를 읽어온다. 생산자는 KV를 등록·노출하고 대기.

Bidirectional (kv_both)양방향 (kv_both)

One instance can be both producer and consumer (role kv_both) — needed for one engine serving both prefill and decode, or multi-turn where roles flip.한 인스턴스가 생산자이자 소비자(kv_both 역할) — 한 엔진이 prefill·decode를 모두 맡거나, 역할이 뒤바뀌는 멀티턴에 필요.

Store-mediated스토어 경유

No direct P↔D socket: producer writes KV to an external store/FS keyed by content hash; consumer looks up + reads later. Decoupled "write-then-read".직접 P↔D 소켓 없음: 생산자가 내용 해시 키로 외부 스토어/FS에 쓰고, 소비자가 나중에 조회·읽기. 비결합 "쓰고-나중에-읽기".

Offload (intra-instance)오프로드 (인스턴스 내)

Not P/D at all: moves KV between GPU and CPU/disk within one engine for memory relief or prefix reuse. No second instance.P/D가 아예 아님: 한 엔진 안에서 KV를 GPU↔CPU/디스크로 옮겨 메모리 확보·prefix 재사용. 두 번째 인스턴스 없음.

1Direct prefill↔decode transfer connectors직접 prefill↔decode 전송 커넥터

These move KV over the network between two engines — exactly the push/pull/bidirectional question. (NIXL split into explicit Pull/Push variants; the plain NixlConnector is now an alias of the Pull one.)

이들이 두 엔진 사이에서 KV를 네트워크로 옮깁니다 — 정확히 push/pull/양방향 질문에 해당. (NIXL은 Pull/Push 변형으로 분리됐고, 일반 NixlConnector는 이제 Pull의 별칭.)

The four patterns. Push/Pull/Bidirectional are direct engine↔engine; Store-mediated decouples through a shared pool.네 가지 패턴. Push/Pull/양방향은 엔진↔엔진 직접, Store 경유는 공유 풀로 비결합.

2Store / cache-mediated connectors스토어 · 캐시 경유 커넥터

These don't open a P↔D socket. The producer writes KV into an external store keyed by content hash; any consumer can look it up and read it later. Primarily for prefix-cache reuse / KV offload across instances — though LMCache can also do real P→D push when its enable_pd mode is set.

이들은 P↔D 소켓을 열지 않습니다. 생산자가 내용 해시 키로 외부 스토어에 KV를 쓰고, 어떤 소비자든 나중에 조회·읽기. 주로 인스턴스 간 prefix-cache 재사용 / KV 오프로드용 — 단 LMCache는 enable_pd 모드에서 실제 P→D push도 가능.

4Notes & what changed메모 · 달라진 점

removed since earlier versions이전 버전에서 제거됨 P2pNcclConnector (the one-way P→D-push NCCL connector from PR #18242, present in v0.10/v0.11) is gone from main — no longer in the factory or the tree. Its direct-P2P role is now served by the NIXL Push/Pull connectors and MoRIIO. SharedStorageConnector is also gone — superseded by ExampleConnector (same filesystem-safetensors demo). P2pNcclConnector(PR #18242의 단방향 P→D-push NCCL 커넥터, v0.10/v0.11에 존재)는 main에서 사라졌습니다 — 팩토리에도 트리에도 없음. 그 직접 P2P 역할은 이제 NIXL Push/Pull 커넥터와 MoRIIO가 맡습니다. SharedStorageConnector도 사라졌고 — ExampleConnector(같은 파일시스템-safetensors 데모)로 대체됐습니다.
how to read "direction" honestly"방향"을 정직하게 읽는 법 Only the NIXL/Mooncake/MoRIIO connectors do a genuine direct engine↔engine transfer where push vs pull is a real socket distinction. The store/cache connectors are all "write-then-read" through a pool — calling them "push" or "pull" is a category error; the right label is store-mediated. Offload connectors never leave the instance. So the clean answer to "push / pull / bidirectional?" lives in §1. push vs pull이 실제 소켓 구분으로 의미 있는 건 NIXL/Mooncake/MoRIIO뿐입니다. 스토어·캐시 커넥터는 전부 풀을 통한 "쓰고-나중에-읽기"라, push/pull로 부르는 건 범주 오류 — 올바른 표현은 스토어 경유입니다. 오프로드 커넥터는 인스턴스를 떠나지 않습니다. 그러니 "push / pull / 양방향?"의 깔끔한 답은 §1에 있습니다.
one-line takeaway한 줄 정리 Pull: NixlConnector (default), NixlPullConnector. Push: NixlPushConnector, MooncakeConnector, MoRIIO (default). Pull opt-in: MoRIIO (read_mode). Bidirectional (kv_both): only MooncakeConnector among the direct-transfer ones (LMCache/FlexKV/HF3FS support kv_both but as store-mediated, not direct P/D). Pull: NixlConnector(기본), NixlPullConnector. Push: NixlPushConnector, MooncakeConnector, MoRIIO(기본). Pull 옵션: MoRIIO(read_mode). 양방향(kv_both): 직접 전송 중에서는 MooncakeConnector만(LMCache/FlexKV/HF3FS도 kv_both 지원하나 스토어 경유이지 직접 P/D 아님).
