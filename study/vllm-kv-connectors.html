What's a KV connector?KV 커넥터란?

A plug-in that moves a request's KV-cache out of one vLLM engine and into another place — a peer engine (for P/D disaggregation), a shared store (for prefix reuse), or CPU/disk (for offload).요청의 KV-cache를 한 vLLM 엔진 밖으로 옮겨 다른 곳으로 보내는 플러그인 — 다른 엔진(P/D 분리 서빙), 공유 스토어(prefix 재사용), CPU/디스크(오프로드).

Push (prefill→decode)Push (prefill→decode)

The producer (prefill) initiates the network transfer — it writes KV into the consumer's memory after computing it.생산자(prefill)가 전송을 시작 — 계산을 마친 KV를 소비자 메모리로 써넣는다.

Pull (decode→prefill)Pull (decode→prefill)

The consumer (decode) initiates — it reads the KV from the producer when it knows where to look. The producer just registers/exposes its KV and waits.소비자(decode)가 시작 — 출처를 알게 되면 생산자에서 KV를 읽어온다. 생산자는 KV를 등록·노출하고 대기.

Bidirectional (kv_both)양방향 (kv_both)

One instance can be both producer and consumer (role kv_both) — needed for one engine serving both prefill and decode, or multi-turn where roles flip.한 인스턴스가 생산자이자 소비자(kv_both 역할) — 한 엔진이 prefill·decode를 모두 맡거나, 역할이 뒤바뀌는 멀티턴에 필요.

Store-mediated스토어 경유

No direct P↔D socket: producer writes KV to an external store/FS keyed by content hash; consumer looks up + reads later. Decoupled "write-then-read".직접 P↔D 소켓 없음: 생산자가 내용 해시 키로 외부 스토어/FS에 쓰고, 소비자가 나중에 조회·읽기. 비결합 "쓰고-나중에-읽기".

Offload (intra-instance)오프로드 (인스턴스 내)

Not P/D at all: moves KV between GPU and CPU/disk within one engine for memory relief or prefix reuse. No second instance.P/D가 아예 아님: 한 엔진 안에서 KV를 GPU↔CPU/디스크로 옮겨 메모리 확보·prefix 재사용. 두 번째 인스턴스 없음.

These move KV over the network between two engines — exactly the push/pull/bidirectional question. (NIXL split into explicit Pull/Push variants; the plain NixlConnector is now an alias of the Pull one.)

이들이 두 엔진 사이에서 KV를 네트워크로 옮깁니다 — 정확히 push/pull/양방향 질문에 해당. (NIXL은 Pull/Push 변형으로 분리됐고, 일반 NixlConnector는 이제 Pull의 별칭.)

2Store / cache-mediated connectors스토어 · 캐시 경유 커넥터

These don't open a P↔D socket. The producer writes KV into an external store keyed by content hash; any consumer can look it up and read it later. Primarily for prefix-cache reuse / KV offload across instances — though LMCache can also do real P→D push when its enable_pd mode is set.

이들은 P↔D 소켓을 열지 않습니다. 생산자가 내용 해시 키로 외부 스토어에 KV를 쓰고, 어떤 소비자든 나중에 조회·읽기. 주로 인스턴스 간 prefix-cache 재사용 / KV 오프로드용 — 단 LMCache는 enable_pd 모드에서 실제 P→D push도 가능.

4Speed — what actually determines it속도 — 무엇이 실제로 좌우하나

first, the question this raises: are all connectors the same speed?먼저, 여기서 나오는 질문: 커넥터마다 속도가 같은가? No — and they do not all take the same hardware path. The interconnect sets a ceiling (max possible bandwidth); the connector decides (a) which physical path it even uses and (b) how close to that ceiling it gets. A filesystem/store connector copies GPU→host-CPU→disk→CPU→GPU; NIXL/Mooncake/MoRIIO do GPU→NIC→RDMA→NIC→GPU with GPUDirect, bypassing the host entirely — completely different paths, orders-of-magnitude apart. And even on the identical link, software still matters: LMCache loads KV from CPU at 400 Gbps vs vLLM-native 88 Gbps — 4.5× on the same hardware, purely from chunk-wise vs page-wise transfer (LMCache §8.6). So "bandwidth-bound" means the link is the ceiling, not that the connector is irrelevant. 아니다 — 그리고 모두 같은 하드웨어 경로를 따라가지도 않는다. 인터커넥트는 천장(가능한 최대 대역폭)을 정할 뿐이고, 커넥터가 (a) 어떤 물리 경로를 쓰는지, (b) 그 천장에 얼마나 근접하는지를 결정한다. 파일시스템/스토어 커넥터는 GPU→호스트CPU→디스크→CPU→GPU로 복사하고, NIXL/Mooncake/MoRIIO는 GPUDirect로 호스트를 통째로 우회해 GPU→NIC→RDMA→NIC→GPU로 간다 — 완전히 다른 경로이고 자릿수 단위로 차이 난다. 게다가 똑같은 링크 위에서도 소프트웨어가 좌우한다: LMCache는 CPU에서 KV를 400 Gbps로, vLLM 기본은 88 Gbps로 — 같은 하드웨어에서 4.5배 차이가 나는데, 순전히 chunk 단위 vs page 단위 전송 차이다(LMCache §8.6). 즉 "대역폭 바운드"는 링크가 천장이라는 뜻이지, 커넥터가 무관하다는 뜻이 아니다.

Why "bandwidth-bound" still matters: transfer_time ≈ KV_bytes / link_bandwidth. Once a connector is on the fast path (RDMA/GPUDirect) and saturating it, the remaining cost is just bytes ÷ link — so the interconnect becomes the dominant lever. vLLM's docs put it the same way: overhead "depends on … the interconnect or network bandwidth, size of KV cache, the prefill/decode instance configurations" (disagg_prefill docs). DistServe's worked example: one 512-token request on OPT-66B ≈ 1.13 GB of KV, so 10 rps needs ~90 Gbps to stay invisible; intra-node over NVLink (600 GB/s on A100) it's "negligible" — measured at <0.1% of total latency on OPT-175B (DistServe, OSDI'24 §3.3/§6.3).

그래도 "대역폭 바운드"가 중요한 이유: 전송시간 ≈ KV바이트 / 링크대역폭. 커넥터가 일단 빠른 경로(RDMA/GPUDirect)에 올라타 링크를 꽉 채우면, 남는 비용은 바이트 ÷ 링크뿐 — 그래서 그때부터는 인터커넥트가 지배적 지렛대가 된다. vLLM 문서도 같은 말을 한다: 오버헤드는 "인터커넥트/네트워크 대역폭, KV 캐시 크기, prefill/decode 인스턴스 구성에 달렸다"(disagg_prefill 문서). DistServe 예시: OPT-66B의 512토큰 요청 하나가 KV ≈ 1.13 GB, 10 rps면 ~90 Gbps 있어야 안 보임; 노드 내 NVLink(A100 600 GB/s)에선 "무시 가능" — OPT-175B에서 총 지연의 <0.1%로 실측(DistServe, OSDI'24 §3.3/§6.3).

Intra-node NVLink dwarfs inter-node fabric: keep P&D in one NVLink domain and transfer is ~free; crossing nodes is where the transport matters. Bars approximate, log-scaled. NVLink: NVIDIA specs; IB/RoCE/PCIe: vendor docs & third-party guides (links in table).노드 내 NVLink가 노드 간 패브릭을 압도: P·D를 한 NVLink 도메인에 두면 전송은 ~공짜, 노드를 건널 때 전송 수단이 의미를 가짐. 막대는 근사·로그 스케일. NVLink는 NVIDIA 스펙, IB/RoCE/PCIe는 벤더 문서·제3자 가이드(표에 링크).

Two different speeds, don't conflate them. "KV-cache transfer" between two engines (§1 connectors, over the network) and "KV offload" to CPU/disk within one engine (§3 connectors) are different operations on different links — so the published numbers split into two tables.

서로 다른 두 속도라 섞으면 안 됩니다. 두 엔진 사이의 "KV-cache 전송"(§1 커넥터, 네트워크 경유)과 한 엔진 안에서 CPU/디스크로 내리는 "KV 오프로드"(§3 커넥터)는 다른 링크에서 일어나는 다른 작업입니다 — 그래서 공개 수치도 두 표로 나눕니다.

push vs pull — a latency difference, NOT a bandwidth onepush vs pull — 대역폭이 아니라 지연 차이 Same link, same bytes → same bandwidth. What differs is who initiates and whether the decode-side memory registration overlaps prefill compute. Push removes a proxy round-trip from the critical path. vLLM's own measurement (AWS P5en): "KV push mode showed 1.2× – 3.0× improvements over pull mode" on TTFT (e.g. TP4 512/128 conc8: 2948 ms → 1212 ms; P99 740 ms → 100 ms). vLLM RFC #36923 같은 링크·같은 바이트 → 같은 대역폭. 다른 건 누가 시작하느냐, 그리고 decode 측 메모리 등록이 prefill 연산과 겹치느냐입니다. push는 임계경로에서 프록시 왕복을 없앱니다. vLLM 실측(AWS P5en): TTFT에서 "push 모드가 pull 대비 1.2×–3.0× 개선"(예: TP4 512/128 conc8: 2948 ms → 1212 ms; P99 740 ms → 100 ms). vLLM RFC #36923
store-mediated: slower per transfer, but that's not the point스토어 경유: 전송당 느리지만, 그게 핵심이 아님 Putting a store/filesystem (and the host CPU) in the data path is higher-latency than RDMA P2P (which keeps the host out and goes zero-copy at hardware speed — UCCL). The payoff is reuse: Mooncake Store in vLLM showed 46× lower P50 TTFT — but that came from cache hit rate 1.7% → 92.2%, i.e. prefix reuse, not faster bytes (vLLM blog). So store-mediated wins when requests share prefixes, loses on a one-shot handoff. 스토어/파일시스템(과 호스트 CPU)을 데이터 경로에 두면 RDMA P2P(호스트를 빼고 하드웨어 속도로 zero-copy — UCCL)보다 지연이 큽니다. 대신 얻는 건 재사용: vLLM의 Mooncake Store는 P50 TTFT 46× 개선을 보였지만, 그건 캐시 적중률 1.7% → 92.2%(prefix 재사용)에서 온 것이지 바이트가 빨라서가 아닙니다(vLLM 블로그). 즉 요청들이 prefix를 공유할 때 이기고, 일회성 핸드오프에선 집니다.
honesty flag — read these numbers carefully정직 단서 — 이 수치들 조심해서 읽기 Almost everything above is vendor/first-party, and there is no independent three-way NixlConnector vs Mooncake vs LMCache benchmark. The numbers use different models, workloads, and baselines — Mooncake's 46× and the 252 GB/s storage figures are not like-for-like with NIXL P2P transport. The connectors are also partly layered, not competing: "Both LMCache and Mooncake can use NIXL under the hood" (vLLM docs). For a real comparison you must benchmark on your own hardware. 위 수치는 거의 전부 vendor/1차 출처이고, NixlConnector vs Mooncake vs LMCache 독립 3자 벤치마크는 없습니다. 모델·워크로드·기준이 제각각 — Mooncake의 46×나 252 GB/s 스토리지 수치는 NIXL P2P 전송과 동일 조건이 아닙니다. 커넥터들은 경쟁이 아니라 계층적으로 겹치기도 합니다: "LMCache와 Mooncake 모두 내부적으로 NIXL을 쓸 수 있다"(vLLM 문서). 진짜 비교는 본인 하드웨어에서 직접 측정해야 합니다.

5Hardware & dependencies per connector커넥터별 하드웨어 · 의존성

Which hardware a connector runs on is decided by the transport library it depends on. Three things matter: (1) GPU vendor (NVIDIA CUDA / AMD ROCm / NPU), (2) the interconnect/NIC it needs (RDMA NIC for cross-node, NVLink/XGMI/PCIe intra-node), and (3) extra deps (a store cluster, GDS, etc.). Verified against each project's repo/docs.

the practical catch — wheel/build in your image, not just "support"실전 함정 — "지원 여부"가 아니라 이미지에 들어간 휠/빌드 "Supported" ≠ "works in your container." A connector runs only if the matching transport wheel/build is actually installed for your platform. Concrete example from our own MI250/ROCm PD test: the rocm/vllm image shipped a CUDA-linked Mooncake wheel (libcudart.so.12) and no NIXL, so both failed to import on AMD even though the projects list ROCm/non-CUDA support upstream. On AMD today, MoRIIO is the natively-built path; NIXL/Mooncake need the ROCm/non-CUDA wheel present. "지원함" ≠ "내 컨테이너에서 됨". 커넥터는 해당 전송 휠/빌드가 내 플랫폼용으로 실제 설치돼 있어야 돕니다. 우리 MI250/ROCm PD 실험의 구체적 사례: rocm/vllm 이미지에 CUDA로 링크된 Mooncake 휠(libcudart.so.12)과 NIXL 부재로, 업스트림은 ROCm/non-CUDA를 지원해도 AMD에서 둘 다 import 실패했습니다. 현재 AMD에선 MoRIIO가 네이티브 빌드 경로이고, NIXL/Mooncake는 ROCm/non-CUDA 휠이 깔려 있어야 합니다.

how to read "direction" honestly"방향"을 정직하게 읽는 법 Only the NIXL/Mooncake/MoRIIO connectors do a genuine direct engine↔engine transfer where push vs pull is a real socket distinction. The store/cache connectors are all "write-then-read" through a pool — calling them "push" or "pull" is a category error; the right label is store-mediated. Offload connectors never leave the instance. So the clean answer to "push / pull / bidirectional?" lives in §1. push vs pull이 실제 소켓 구분으로 의미 있는 건 NIXL/Mooncake/MoRIIO뿐입니다. 스토어·캐시 커넥터는 전부 풀을 통한 "쓰고-나중에-읽기"라, push/pull로 부르는 건 범주 오류 — 올바른 표현은 스토어 경유입니다. 오프로드 커넥터는 인스턴스를 떠나지 않습니다. 그러니 "push / pull / 양방향?"의 깔끔한 답은 §1에 있습니다.
