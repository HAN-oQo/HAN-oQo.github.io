AMD's 4-bit KV in LMCache — what the numbers say, and what's actually upstream AMD 의 4-bit KV in LMCache — 수치가 말하는 것, 그리고 업스트림에 실제로 있는 것

AMD reports 2× serving goodput on 2×MI355X (385 vs 189 requests, p95 TTFT 53 s vs 140 s) by packing KV to 4 bits and letting LMCache catch the overflow in a 128 GB DRAM tier. TurboQuant keeps the first two and last two layers in bf16 and packs the middle 58 to 4-bit, making each token ~3.76× smaller — which puts 3.2× more KV resident in HBM (648k vs 201k tokens). This note summarises the post, then checks its central code claim against the LMCache tree, and the check changes the reading: upstream LMCache already has TurboQuant — presets, Hadamard + Lloyd-Max codebook, even the exact skip_first_layers=2 / skip_last_layers=2 split — but it's a serde on the L1→L2 path, so it saves storage and bandwidth and does not increase HBM residency. The group-aware connector that does is not upstream (no group_aware/transfer_group anywhere in the tree); it lives in AMD's fork, which is why they ship a pinned Docker image. So the headline 3.2× is a vLLM-side property, not an LMCache one. Also surfaces what the framing buries: at a 68 GB DRAM tier plain FP8 beat 4-bit on goodput in AMD's own numbers, so the honest claim is "4-bit wins when DRAM is the binding constraint," and the durable argument is efficiency (same goodput at ¼ the RAM). Accuracy holds within ~1 pt (RULER ≤0.4 pt); the bit-exact DRAM round-trip result follows trivially from byte-transparency rather than being evidence about tiering. Vendor-reported throughout — code claims verified, performance claims not. AMD 는 MI355X 2장에서 KV 를 4비트로 압축하고 128 GB DRAM 계층이 넘치는 분량을 받아내게 해 서빙 goodput 2배(385 대 189 요청, p95 TTFT 53초 대 140초)를 보고한다. TurboQuant 는 처음 두 개·마지막 두 개 레이어를 bf16 으로 두고 가운데 58개를 4비트로 압축해 토큰당 약 3.76배를 줄이고, 그 결과 HBM 상주 KV 가 3.2배(64.8만 대 20.1만 토큰)가 된다. 이 노트는 글을 정리한 뒤 핵심 코드 주장을 LMCache 트리에 직접 대조했고, 그 대조가 해석을 바꾼다 — 업스트림 LMCache 에 TurboQuant 는 이미 있다. 프리셋도, Hadamard + Lloyd-Max 코드북도, 심지어 skip_first_layers=2 / skip_last_layers=2 분할까지 그대로. 그런데 그건 L1→L2 경로의 serde 라서 저장 용량과 대역폭을 아낄 뿐 HBM 상주량을 늘리지는 않는다. 그걸 해내는 group-aware 커넥터는 업스트림에 없다(트리 어디에도 group_aware/transfer_group 없음). AMD 포크에 있고, 그래서 고정 Docker 이미지를 배포한다. 결국 헤드라인 3.2배는 vLLM 쪽 속성이지 LMCache 쪽이 아니다. 글의 구성이 묻어 둔 것도 짚는다: DRAM 68 GB 지점에선 AMD 자신의 수치에서도 평범한 FP8 이 4비트를 goodput 으로 이겼다. 정직한 주장은 "DRAM 이 병목일 때 4비트가 이긴다" 이고, 오래 가는 논거는 효율(RAM 1/4 로 같은 goodput)이다. 정확도는 약 1 pt 이내(RULER 0.4 pt 이하) 유지. 비트 정확한 DRAM 왕복 결과는 계층화에 대한 증거가 아니라 바이트 투명성에서 자명하게 따라 나온다. 전부 벤더 보고 수치 — 코드 주장은 검증했고 성능 주장은 하지 않았다.

From nano-vLLM to ATOM — how 1,385 lines became 426,000 nano-vLLM에서 ATOM까지 — 1,385줄이 42만 줄이 되기까지

ATOM's README credits nano-vllm as its origin in one sentence and stops there. This note reads all 1,385 lines of nano-vLLM to establish what the starting point actually was — and it is not "a small vLLM", it is the shape of vLLM with everything hard removed: one model, no MoE, no quantization, no server, no speculative decoding, temperature-only sampling with greedy explicitly forbidden by an assert, and tensor parallelism over a single hardcoded 1 MB shared-memory segment on a hardcoded port (so two instances cannot coexist on one machine). Its famous "comparable to vLLM" benchmark turns out to run Qwen3-0.6B on a laptop GPU with random token IDs — exercising none of the prefix caching it advertises, in exactly the regime where a thin engine wins by construction. Then the delta, measured file by file: attention 75 → 18,821 lines (250×), Config 25 → 2,132 (85×), Scheduler 92 → 3,146 (34×) — plus 15 subsystems with no counterpart at all, most of which AMD did not invent but re-imported from vLLM. Finally the ATOM components the earlier deep dive excluded: ATOMesh (a routing gateway that is itself a fork of SGLang's sgl-model-gateway, still depending on seven SGLang-published crates — so ATOM's lineage runs through two forks, not one; its docs and quickstart route to SGLang while AMD's own nightly CI routes to ATOM, and --api-key turns out to authenticate nothing inbound), the plugin bridges (the SGLang one is larger than the vLLM one; the vLLM one pins an exact commit, makes 176 imports including private symbols, and monkey-patches nine modules — two of which reverse vLLM's own ROCm decisions), and the diffusion engine. Ends on a consolidated weakness analysis. ATOM README는 nano-vllm을 출발점으로 한 문장 밝히고 만다. 이 노트는 nano-vLLM 1,385줄 전부를 읽어 출발점이 실제로 무엇이었는지 확인한다 — "작은 vLLM"이 아니라 어려운 걸 전부 걷어낸 vLLM의 형태다. 모델 1개, MoE 없음, quantization 없음, 서버 없음, speculative decoding 없음, temperature 샘플링만 되고 greedy는 assert로 명시적 금지, tensor parallel은 하드코딩된 1 MB 공유메모리와 하드코딩된 포트로 구현돼 한 머신에 인스턴스 둘을 못 띄운다. 유명한 "vLLM에 준한다" 벤치마크는 노트북 GPU에서 Qwen3-0.6B를 무작위 토큰 ID로 돌린 것이라, 광고하는 prefix caching을 전혀 건드리지 않으며 얇은 엔진이 구조적으로 이기는 구간에서 측정됐다. 이어서 파일 단위로 잰 델타 — attention 75 → 18,821줄(250배), Config 25 → 2,132(85배), Scheduler 92 → 3,146(34배), 그리고 대응물이 아예 없는 서브시스템 15개. 그중 대부분은 AMD가 발명한 게 아니라 vLLM에서 다시 가져온 것이다. 마지막으로 앞선 딥다이브가 제외했던 ATOM 구성요소들 — ATOMesh(그 자체가 SGLang sgl-model-gateway의 포크이고 지금도 SGLang 배포 크레이트 7개에 의존하는 라우팅 게이트웨이 — 즉 ATOM의 계보는 포크 둘을 지난다. 문서와 퀵스타트는 SGLang으로 보내는데 AMD 자체 nightly CI는 ATOM으로 보내고, --api-key는 인바운드로 아무것도 인증하지 않는다), 플러그인 브리지(SGLang용이 vLLM용보다 크다. vLLM용은 정확한 커밋을 핀으로 박고 private 심볼 포함 176개를 import하며 모듈 9개를 monkey-patch하는데, 그중 둘은 vLLM 자체 ROCm 결정을 뒤집는다), 그리고 diffusion 엔진. 약점 종합 분석으로 마무리.

Starts with the lineage, which the repo states outright: ATOM was adapted from nano-vllm, a ~1,200-line teaching reimplementation of vLLM — and its pyproject.toml still carries nano-vllm's tagline verbatim. Then the architecture: the openai_server → LLMEngine → CoreManager → EngineCore → Scheduler → ModelRunner spine, fanned out over a process tree wired with ZMQ (one EngineCore per DP rank, one ModelRunner subprocess per TP rank). Traces one request end to end in 11 steps with commit-pinned permalinks, including the details the docs no longer describe — preemption as a full rollback, the 26-entry model registry, the cross-DP prefill delayer. Then the part that is genuinely AMD-specific: 106 files of AITER kernel bindings (ASM / Composable Kernel / Triton), with the GEMM and attention dispatch tables reconstructed; and the compilation subsystem, where attention is deliberately marked opaque to Dynamo so piecewise CUDA-graph capture can work at all. Ends with how to actually run it (install, serve, benchmark, profile, or install it into vLLM as a plugin) and an honest comparison against vLLM, SGLang and vLLM-on-ROCm. That last part is the real story: AMD's first RFC asked to put ATOM in-tree in vLLM and was rejected on governance grounds — the plugin is the settlement. AITER's own README ranks vLLM and SGLang on ROCm as Production and ATOM as Active development; SemiAnalysis InferenceX — the one same-harness head-to-head that exists — has a section titled "AMD ATOM Inference Engine Disappointment", though it also records the recovery.
