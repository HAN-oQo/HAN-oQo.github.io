1Introduction소개

Large language models support a wide range of applications, but serving them at scale requires careful optimization. Standard autoregressive decoding is the baseline used by most LLM serving systems: the model generates one token, appends it to the sequence, and then uses the updated sequence to generate the next token. This process is simple and reliable, but the serving loop still advances one committed token at a time because output tokens must be produced in strict left-to-right order.

대규모 언어 모델은 다양한 응용을 지원하지만, 대규모로 서빙하려면 세심한 최적화가 필요합니다. 표준 자기회귀 디코딩은 대부분의 LLM 서빙 시스템이 쓰는 기준선입니다. 모델이 토큰 하나를 생성하고, 그것을 시퀀스에 덧붙인 뒤, 갱신된 시퀀스로 다음 토큰을 생성합니다. 이 과정은 단순하고 안정적이지만, 출력 토큰이 반드시 왼쪽에서 오른쪽 순서로 나와야 하기 때문에 서빙 루프는 여전히 확정된 토큰 하나씩만 전진합니다.

Speculative decoding [1] builds on this baseline through a draft-and-verify mechanism. A lightweight draft component proposes candidate future tokens, and the target model verifies those candidates before they are committed. When several draft tokens are accepted, the system can commit multiple output tokens from a single target-model verification step while preserving the target model's output behavior.

Speculative decoding [1]은 이 기준선 위에 draft-and-verify(초안 작성 후 검증) 메커니즘을 얹습니다. 가벼운 draft 구성요소가 미래 토큰 후보를 제안하고, 타깃 모델이 그 후보들을 확정 전에 검증합니다. 여러 draft 토큰이 수용되면, 시스템은 타깃 모델의 검증 스텝 한 번으로 여러 출력 토큰을 확정할 수 있으면서도 타깃 모델의 출력 동작은 그대로 보존합니다.

This post explores how speculative decoding works in vLLM and shares measurements from our test environment. We first review the autoregressive decoding baseline and the draft-and-verify process. We then examine five speculative-drafting approaches: native MTP, Gemma 4 MTP, EAGLE-3, DFlash, and DSpark. These methods differ in how the draft component receives information from the target model and whether candidate tokens are generated sequentially, autoregressively, in parallel, or through a hybrid approach. Finally, we show how to enable the methods tested in our environment, report measurements from our experiments on AMD Instinct™ MI300X and MI355X GPUs using the ROCm™ open software platform, and discuss practical tuning and observability considerations.

이 글은 vLLM에서 speculative decoding이 어떻게 동작하는지 살펴보고, 저희 테스트 환경에서 측정한 결과를 공유합니다. 먼저 자기회귀 디코딩 기준선과 draft-and-verify 과정을 짚습니다. 그다음 다섯 가지 speculative drafting 방식(native MTP, Gemma 4 MTP, EAGLE-3, DFlash, DSpark)을 살펴봅니다. 이 방법들은 draft 구성요소가 타깃 모델로부터 어떤 정보를 받는지, 그리고 후보 토큰을 순차적으로 생성하는지, 자기회귀적으로 생성하는지, 병렬로 생성하는지, 아니면 혼합 방식으로 생성하는지에서 차이가 납니다. 마지막으로 저희 환경에서 테스트한 방법들을 켜는 방법을 보이고, AMD Instinct™ MI300X 및 MI355X GPU에서 ROCm™ 오픈 소프트웨어 플랫폼을 사용해 수행한 실험 결과를 보고하며, 실무적인 튜닝과 관측성 고려사항을 논의합니다.

2The autoregressive decoding baseline자기회귀 디코딩 기준선

In standard autoregressive decoding, each decode step produces and commits one new token. For example, generating four output tokens requires four sequential decode steps:

표준 자기회귀 디코딩에서는 디코드 스텝마다 새 토큰 하나를 만들어 확정합니다. 예를 들어 출력 토큰 4개를 생성하려면 순차적인 디코드 스텝 4번이 필요합니다:

Step 1:  context → model → T1
Step 2:  context + T1 → model → T2
Step 3:  context + T1 T2 → model → T3
Step 4:  context + T1 T2 T3 → model → T4

After each step, the generated token is appended to the sequence and becomes part of the input for the next step. This makes the decoding loop straightforward, but it also requires one model decode step for every output token. During long generations, this token-by-token loop can dominate latency and limit serving throughput.

각 스텝이 끝나면 생성된 토큰이 시퀀스에 덧붙어 다음 스텝의 입력 일부가 됩니다. 덕분에 디코딩 루프는 단순해지지만, 출력 토큰 하나마다 모델 디코드 스텝 하나가 필요해집니다. 긴 생성에서는 이 토큰 단위 루프가 지연 시간을 지배하고 서빙 처리량을 제한할 수 있습니다.

The key question behind speculative decoding is therefore:

따라서 speculative decoding의 바탕에 깔린 핵심 질문은 이것입니다:

Can we preserve the output behavior of the original model while reducing how often generation advances by only one token at a time? 원래 모델의 출력 동작은 보존하면서, 생성이 한 번에 토큰 하나씩만 전진하는 횟수를 줄일 수 있을까?

Speculative decoding addresses this by separating proposal from verification. A draft component first proposes several candidate future tokens. The original model, acting as the target model, then verifies those candidates before they are committed.

Speculative decoding은 제안(proposal)과 검증(verification)을 분리해 이 문제에 접근합니다. 먼저 draft 구성요소가 미래 토큰 후보 여럿을 제안합니다. 그다음 원래 모델이 타깃 모델 역할을 하며, 확정되기 전에 그 후보들을 검증합니다.

3Core idea of speculative decodingSpeculative decoding의 핵심 아이디어

Speculative decoding does not replace the original model. Instead, it keeps the original model as the target model, which remains responsible for the final output, and adds a faster proposal stage in front of it.

Speculative decoding은 원래 모델을 대체하지 않습니다. 대신 원래 모델을 타깃 모델로 두어 최종 출력에 대한 책임을 계속 지게 하고, 그 앞에 더 빠른 제안 단계를 덧붙입니다.

The process has two parts:

과정은 두 부분으로 나뉩니다:

  • Draft: propose several candidate future tokens.
  • Verify: use the target model to check those candidates.
  • Draft: 미래 토큰 후보 여럿을 제안한다.
  • Verify: 타깃 모델로 그 후보들을 검사한다.

During each speculative decoding round, as illustrated in Figure 1, a lightweight draft component proposes one or more future tokens. These tokens are only candidates and are not committed immediately. The target model then evaluates the candidate token sequence in one verification pass.

Figure 1에 나타낸 것처럼, 각 speculative decoding 라운드에서 가벼운 draft 구성요소가 미래 토큰을 하나 이상 제안합니다. 이 토큰들은 후보일 뿐 즉시 확정되지 않습니다. 그다음 타깃 모델이 후보 토큰 시퀀스를 한 번의 검증 패스로 평가합니다.

Verification proceeds from left to right. Each draft token is checked using the target model's result at the corresponding position. Accepted tokens are committed to the output sequence. When a draft token is rejected, later candidates from the same proposal are no longer accepted.

검증은 왼쪽에서 오른쪽으로 진행됩니다. 각 draft 토큰은 해당 위치에서의 타깃 모델 결과로 검사됩니다. 수용된 토큰은 출력 시퀀스에 확정됩니다. draft 토큰 하나가 거부되면, 같은 제안에 속한 이후 후보들은 더 이상 수용되지 않습니다.

If a draft token is rejected, the target model provides the next token. The remaining draft tokens are discarded, and generation continues from the updated sequence.

draft 토큰이 거부되면 타깃 모델이 다음 토큰을 제공합니다. 남은 draft 토큰들은 버려지고, 생성은 갱신된 시퀀스에서 이어집니다.

Conceptually, standard autoregressive decoding advances like this:

개념적으로 표준 자기회귀 디코딩은 이렇게 전진합니다:

target model → T1    target model → T2    target model → T3    target model → T4

Speculative decoding instead allows several candidate positions to be evaluated together:

반면 speculative decoding은 여러 후보 위치를 한꺼번에 평가할 수 있게 합니다:

draft proposes   T1 T2 T3 T4
model verifies   ✓   ✓   ✗   stop
commit          T1 T2 replacement token —

This can reduce the number of target-model decoding rounds when multiple candidates are accepted. When the draft component produces tokens that the target model accepts, several output tokens can be committed from one target-model verification step. When a proposal is rejected, the target-side result determines how generation continues.

후보 여럿이 수용되면 타깃 모델의 디코딩 라운드 수를 줄일 수 있습니다. draft 구성요소가 타깃 모델이 수용하는 토큰을 만들어내면, 타깃 모델의 검증 스텝 한 번으로 여러 출력 토큰을 확정할 수 있습니다. 제안이 거부되면 타깃 쪽 결과가 생성이 어떻게 이어질지를 결정합니다.

Suppose the current prompt is The weather today is. The draft component proposes several future tokens: sunny, and, warm, outside. The target model verifies the draft tokens from left to right:

현재 프롬프트가 The weather today is라고 합시다. draft 구성요소가 미래 토큰 여럿을 제안합니다: sunny, and, warm, outside. 타깃 모델은 draft 토큰들을 왼쪽에서 오른쪽으로 검증합니다:

draft proposes   sunny and warm outside
model verifies   ✓       ✓     ✗      stop
commit          sunny and clear —

The first two draft tokens, sunny and and, are accepted. At the third position, the draft proposes warm, but the target model selects clear. The remaining candidate, outside, is discarded because it follows the first rejected position. The next decoding round therefore continues from The weather today is sunny and clear.

첫 두 draft 토큰 sunny와 and는 수용됩니다. 세 번째 위치에서 draft는 warm을 제안하지만 타깃 모델은 clear를 선택합니다. 남은 후보 outside는 처음 거부된 위치 뒤에 있으므로 버려집니다. 따라서 다음 디코딩 라운드는 The weather today is sunny and clear에서 이어집니다.

4How the drafting methods work드래프팅 방법들의 작동 원리

Although all speculative decoding methods follow the same overall draft-and-verify process, they differ in how the draft component is designed and how it works with the target model. The main differences are: the type of information received from the target model; how this information is incorporated into the drafting process; and whether candidate tokens are generated sequentially or in parallel.

모든 speculative decoding 방법이 큰 틀에서 같은 draft-and-verify 과정을 따르지만, draft 구성요소를 어떻게 설계했고 타깃 모델과 어떻게 협력하는지가 다릅니다. 주요 차이는 세 가지입니다: 타깃 모델로부터 받는 정보의 종류, 그 정보를 드래프팅 과정에 어떻게 통합하는지, 그리고 후보 토큰을 순차적으로 생성하는지 병렬로 생성하는지.

Based on these differences, the drafting methods discussed in this post can be grouped into three broad categories:

이 차이를 기준으로, 이 글에서 다루는 드래프팅 방법들은 크게 세 범주로 묶을 수 있습니다:

  • Native MTP modules: built directly into the target-model architecture; use a model-native auxiliary prediction path; generate candidate tokens sequentially.
  • Separate MTP drafters: use a separate checkpoint paired with a specific target model; use target-model activations and shared KV-cache information during inference; generate candidate tokens sequentially.
  • Dedicated target-conditioned draft networks: use separate speculator models trained for a specific target model, including EAGLE-3, DFlash, and DSpark. EAGLE-3 drafts autoregressively from target-model hidden states, DFlash drafts parallel blocks from target-model hidden states, and DSpark adds lightweight causal correction and confidence-based prefix selection.
  • Native MTP 모듈: 타깃 모델 아키텍처에 직접 내장됨. 모델 고유의 보조 예측 경로를 사용하고, 후보 토큰을 순차적으로 생성합니다.
  • 별도 MTP drafter: 특정 타깃 모델과 짝지어진 별도 체크포인트를 사용합니다. 추론 시 타깃 모델의 activation과 공유 KV 캐시 정보를 사용하고, 후보 토큰을 순차적으로 생성합니다.
  • 전용 target-conditioned draft 네트워크: 특정 타깃 모델을 위해 학습된 별도 speculator 모델을 사용하며, EAGLE-3·DFlash·DSpark가 여기 해당합니다. EAGLE-3는 타깃 모델의 hidden state로부터 자기회귀적으로 draft하고, DFlash는 타깃 모델 hidden state로부터 블록을 병렬로 draft하며, DSpark는 가벼운 인과적 보정과 신뢰도 기반 prefix 선택을 더합니다.

These categories describe the draft component architecture, not the target-model family. A target model may support native MTP while also having separately trained EAGLE-3, DFlash, or DSpark draft models. The draft component does not operate entirely on its own. Depending on the method, it may receive: a hidden representation from the target model; hidden states from several selected target layers; the target model's KV cache; or features produced by combining multiple target-model representations.

이 범주는 draft 구성요소의 아키텍처를 설명하는 것이지 타깃 모델 패밀리를 설명하는 게 아닙니다. 한 타깃 모델이 native MTP를 지원하면서 동시에 별도로 학습된 EAGLE-3·DFlash·DSpark draft 모델을 가질 수도 있습니다. draft 구성요소가 완전히 혼자 동작하는 것도 아닙니다. 방법에 따라 다음을 받을 수 있습니다: 타깃 모델의 hidden representation, 선택된 여러 타깃 레이어의 hidden state, 타깃 모델의 KV 캐시, 또는 여러 타깃 모델 표현을 결합해 만든 feature.

Native MTPNative MTP

Multi-Token Prediction, or MTP, refers to a family of model-native mechanisms for predicting tokens beyond the immediate next token. In vLLM, native MTP is available when the target model includes a compatible auxiliary prediction component [2]. The exact MTP architecture varies across model families, but each implementation provides an auxiliary path for proposing future tokens.

MTP(Multi-Token Prediction)는 바로 다음 토큰 너머를 예측하기 위한, 모델에 내장된 메커니즘 계열을 가리킵니다. vLLM에서는 타깃 모델이 호환되는 보조 예측 구성요소를 포함하고 있을 때 native MTP를 쓸 수 있습니다 [2]. 정확한 MTP 아키텍처는 모델 패밀리마다 다르지만, 각 구현은 미래 토큰을 제안하는 보조 경로를 제공합니다.

At the first speculative step, the MTP component combines a hidden representation from the target model with information from the current token to predict the first draft token. At subsequent steps, the newly drafted token and the hidden state produced by the previous MTP step are used to predict the next candidate. After the configured number of candidates has been proposed, the target model evaluates them together in one verification pass.

첫 speculative 스텝에서 MTP 구성요소는 타깃 모델의 hidden representation과 현재 토큰의 정보를 결합해 첫 draft 토큰을 예측합니다. 이후 스텝에서는 새로 draft된 토큰과 직전 MTP 스텝이 만든 hidden state를 사용해 다음 후보를 예측합니다. 설정된 개수만큼 후보가 제안되면, 타깃 모델이 그것들을 한 번의 검증 패스로 함께 평가합니다.

First draft token
Target-model hidden representation → MTP component → Draft token 1 + updated hidden state

Subsequent draft tokens
Previous MTP hidden state + latest draft token → MTP component → Next draft token + updated hidden state

→ Configured draft sequence complete → Target model evaluates all proposed tokens together in one verification pass

Many native MTP implementations follow a similar pattern. A hidden representation from the target model or from the previous MTP prediction is combined with the embedding of a shifted input token or the latest drafted token, then passed through a model-specific fusion or projection into an auxiliary prediction layer producing draft-token logits.

많은 native MTP 구현이 비슷한 패턴을 따릅니다. 타깃 모델 또는 직전 MTP 예측의 hidden representation을, shift된 입력 토큰이나 최신 draft 토큰의 임베딩과 결합한 뒤, 모델별 fusion 또는 projection을 거쳐 보조 예측 레이어로 넣어 draft 토큰 logit을 얻습니다.

The two inputs serve different purposes: (1) the hidden representation carries information about the preceding sequence; and (2) the token embedding identifies the latest token from which drafting continues. In common implementations, they are combined along the hidden dimension and transformed before entering the auxiliary prediction layer.

두 입력은 서로 다른 역할을 합니다: (1) hidden representation은 앞선 시퀀스에 대한 정보를 담고, (2) 토큰 임베딩은 드래프팅이 이어질 최신 토큰을 지목합니다. 일반적인 구현에서는 둘을 hidden 차원을 따라 결합하고 변환한 뒤 보조 예측 레이어로 넣습니다.

The number of physical MTP layers and the configured speculative length are separate concepts. When num_speculative_tokens exceeds the prediction depth directly provided by the checkpoint, vLLM can reuse the MTP path through additional forward passes. A larger value therefore proposes more candidates before verification, but also introduces more sequential drafting work.

물리적인 MTP 레이어 수와 설정된 speculative 길이는 별개의 개념입니다. num_speculative_tokens가 체크포인트가 직접 제공하는 예측 깊이를 넘어서면, vLLM은 추가 forward pass를 통해 MTP 경로를 재사용할 수 있습니다. 따라서 값을 키우면 검증 전에 더 많은 후보를 제안하지만, 그만큼 순차적인 드래프팅 작업도 늘어납니다.

Native MTP is closely tied to the target-model architecture. In many implementations, parts of the MTP path share components with the target model, which can keep the additional memory overhead relatively modest. However, generating multiple speculative tokens still requires sequential drafting before verification.

Native MTP는 타깃 모델 아키텍처와 밀접하게 묶여 있습니다. 많은 구현에서 MTP 경로의 일부가 타깃 모델과 구성요소를 공유하므로 추가 메모리 오버헤드가 비교적 작게 유지될 수 있습니다. 다만 speculative 토큰을 여러 개 생성하려면 여전히 검증 전에 순차적인 드래프팅이 필요합니다.

Gemma 4 MTPGemma 4 MTP

Gemma 4 uses a separately packaged MTP draft component paired with a specific target model [3]. Although the draft component has its own checkpoint, it remains closely connected to the target model during inference. The draft component uses activations produced by the target model and shares the target model's KV cache. This allows it to reuse contextual information that the target has already computed instead of processing the accepted prefix independently.

Gemma 4는 특정 타깃 모델과 짝지어진, 별도로 패키징된 MTP draft 구성요소를 사용합니다 [3]. draft 구성요소가 자체 체크포인트를 갖지만, 추론 중에는 타깃 모델과 긴밀히 연결된 상태를 유지합니다. draft 구성요소는 타깃 모델이 만들어낸 activation을 사용하고 타깃 모델의 KV 캐시를 공유합니다. 덕분에 수용된 prefix를 독립적으로 처리하는 대신, 타깃이 이미 계산해 둔 문맥 정보를 재사용할 수 있습니다.

Gemma 4 target model → Target-model activations · Shared target KV cache → Gemma 4 MTP draft component → Candidate tokens

As with native MTP, the number of layers in the draft component is separate from the configured speculative length. When several candidate tokens are requested, the draft component generates them sequentially, and the target model then verifies the proposed sequence.

native MTP와 마찬가지로, draft 구성요소의 레이어 수는 설정된 speculative 길이와 별개입니다. 후보 토큰을 여러 개 요청하면 draft 구성요소가 순차적으로 생성하고, 그다음 타깃 모델이 제안된 시퀀스를 검증합니다.

EAGLE-3EAGLE-3

EAGLE-3 uses a dedicated draft network trained for a specific target model. The draft component has its own execution path, but it remains closely conditioned on information produced by the target model [4].

EAGLE-3는 특정 타깃 모델을 위해 학습된 전용 draft 네트워크를 사용합니다. draft 구성요소는 자체 실행 경로를 갖지만, 타깃 모델이 만들어낸 정보에 강하게 조건화된 상태를 유지합니다 [4].

During the target-model forward pass, EAGLE-3 records hidden states from three stages of the target Transformer: near the beginning, around the middle, and near the end. These are contextual representations of the same accepted sequence at different stages of target-model processing. The three hidden states are concatenated and projected into a single fused target feature. This fused representation is then combined with the embedding of the sampled token before entering the EAGLE-3 draft decoder.

타깃 모델의 forward pass 동안 EAGLE-3는 타깃 Transformer의 세 지점(앞쪽, 중간쯤, 뒤쪽)에서 hidden state를 기록합니다. 이것들은 같은 수용 시퀀스를, 타깃 모델 처리의 서로 다른 단계에서 본 문맥 표현입니다. 세 hidden state는 concatenate된 뒤 하나의 융합된 타깃 feature로 projection됩니다. 이 융합 표현은 sampling된 토큰의 임베딩과 결합된 다음 EAGLE-3 draft 디코더로 들어갑니다.

Early-layer + Middle-layer + Late-layer hidden state → Concatenate + projection → Fused target feature
Fused target feature + Sampled-token embedding → Concatenate + projection → EAGLE-3 draft decoder → Draft token

The two inputs serve different purposes: the fused target feature summarizes the accepted sequence using information from several stages of the target-model forward pass, and the sampled-token embedding identifies the token from which drafting continues.

두 입력의 역할은 다릅니다. 융합된 타깃 feature는 타깃 모델 forward pass의 여러 단계 정보를 사용해 수용된 시퀀스를 요약하고, sampling된 토큰 임베딩은 드래프팅이 이어질 토큰을 지목합니다.

EAGLE-3 generates draft tokens autoregressively. For the first draft token, it uses the fused target feature computed from the accepted sequence together with the sampled-token embedding. After a draft token is produced, its embedding is fed into the next drafting stage. Because the target model has not yet processed the later speculative positions, target-model hidden states for those positions are not available. EAGLE-3 therefore uses the previous draft-component output when continuing the draft sequence.

EAGLE-3는 draft 토큰을 자기회귀적으로 생성합니다. 첫 draft 토큰에는 수용된 시퀀스로부터 계산한 융합 타깃 feature와 sampling된 토큰 임베딩을 함께 사용합니다. draft 토큰이 만들어지면 그 임베딩이 다음 드래프팅 단계로 들어갑니다. 타깃 모델이 뒤쪽 speculative 위치들을 아직 처리하지 않았으므로 그 위치의 타깃 모델 hidden state는 사용할 수 없습니다. 그래서 EAGLE-3는 draft 시퀀스를 이어갈 때 직전 draft 구성요소의 출력을 사용합니다.

This sequential feedback gives later draft tokens direct dependence on earlier drafted tokens along the proposed sequence. However, generating more speculative tokens also requires more sequential drafting work before verification.

이 순차적 피드백 덕분에 뒤쪽 draft 토큰이 제안 시퀀스 상의 앞선 draft 토큰에 직접 의존하게 됩니다. 다만 speculative 토큰을 더 많이 생성할수록 검증 전에 필요한 순차 드래프팅 작업도 늘어납니다.

DFlashDFlash

DFlash uses a dedicated draft network trained for a specific target model. Unlike MTP and EAGLE-3, which generate candidate tokens sequentially, DFlash predicts a whole block of future positions in parallel [5].

DFlash는 특정 타깃 모델을 위해 학습된 전용 draft 네트워크를 사용합니다. 후보 토큰을 순차적으로 생성하는 MTP·EAGLE-3와 달리, DFlash는 미래 위치 블록 전체를 병렬로 예측합니다 [5].

DFlash begins each draft block with an anchor token. The anchor is a known token produced or confirmed by the target model, so DFlash does not need to predict it. Instead, it provides a known starting point for the masked positions that follow. In later decoding rounds, this is typically the additional target token returned by the previous verification pass.

DFlash는 각 draft 블록을 anchor 토큰으로 시작합니다. anchor는 타깃 모델이 만들었거나 확인한 알려진 토큰이므로 DFlash가 예측할 필요가 없습니다. 대신 뒤따르는 마스킹된 위치들에 대해 알려진 출발점을 제공합니다. 이후 디코딩 라운드에서는 보통 직전 검증 패스가 돌려준 추가 타깃 토큰이 anchor가 됩니다.

Position  0    1     2     3     4     5     6
Input     anchor mask mask mask mask mask mask
Output    anchor draft1 draft2 draft3 draft4 draft5 draft6

Like EAGLE-3, DFlash first combines hidden states from several target-model layers into a fused representation. The main difference is how this fused representation is used. EAGLE-3 combines it with the sampled-token embedding at the input of its autoregressive draft network. DFlash instead converts the fused target context into additional Key and Value representations that are available in every layer of the draft network.

EAGLE-3와 마찬가지로 DFlash도 먼저 여러 타깃 모델 레이어의 hidden state를 융합 표현으로 결합합니다. 주된 차이는 그 융합 표현을 어떻게 쓰느냐입니다. EAGLE-3는 자기회귀 draft 네트워크의 입력에서 sampling된 토큰 임베딩과 결합합니다. 반면 DFlash는 융합된 타깃 문맥을 추가적인 Key·Value 표현으로 변환해, draft 네트워크의 모든 레이어에서 사용할 수 있게 합니다.

Queries from the masked draft positions can therefore attend to both Key/Value representations derived from the target model and Key/Value representations produced from the draft block itself. The target-model context therefore remains available throughout the draft network, rather than being supplied only once at its input.

따라서 마스킹된 draft 위치의 query는 타깃 모델에서 유도된 Key/Value와 draft 블록 자체에서 나온 Key/Value 양쪽에 attend할 수 있습니다. 즉 타깃 모델 문맥이 입력에서 한 번만 주어지는 게 아니라 draft 네트워크 전체에 걸쳐 계속 사용 가능한 상태로 남습니다.

After the draft block has been generated, the target model evaluates all proposed tokens in one verification pass. The acceptance decision is then applied from left to right: accepted tokens are committed until the first rejection, and the remaining candidates are discarded.

draft 블록이 생성되고 나면 타깃 모델이 제안된 토큰 전부를 한 번의 검증 패스로 평가합니다. 그다음 수용 판정을 왼쪽에서 오른쪽으로 적용합니다. 첫 거부 전까지의 토큰이 확정되고, 남은 후보들은 버려집니다.

draft proposal    D1 D2 D3 D4 D5
acceptance       accept accept reject discard discard
committed       D1 D2 target-model token — —

A defining characteristic of DFlash is that all masked positions are predicted together in one draft-network forward pass, rather than sequentially. Because all masked positions are predicted together, a later position is not conditioned on the sampled output of an earlier position during the same pass. This removes the token-by-token feedback used by autoregressive drafting. The effectiveness of later positions therefore depends on the trained checkpoint and workload, particularly when longer draft blocks are used.

DFlash를 규정하는 특징은 마스킹된 모든 위치를 순차적으로가 아니라 draft 네트워크의 단일 forward pass에서 함께 예측한다는 점입니다. 모든 위치를 함께 예측하므로, 같은 pass 안에서 뒤쪽 위치가 앞쪽 위치의 sampling 결과에 조건화되지 않습니다. 자기회귀 드래프팅이 쓰던 토큰 단위 피드백이 사라지는 것이죠. 따라서 뒤쪽 위치의 효과는 학습된 체크포인트와 워크로드에 달려 있으며, 특히 draft 블록이 길어질수록 그렇습니다.

DSparkDSpark

DSpark extends parallel drafting with two additional mechanisms: a lightweight sequential head that introduces dependence between tokens within the draft block, and confidence-based selection of the prefix submitted for target-model verification.

DSpark는 병렬 드래프팅에 두 가지 장치를 더합니다: draft 블록 내 토큰들 사이에 의존성을 도입하는 가벼운 순차 head, 그리고 타깃 모델 검증에 제출할 prefix를 신뢰도 기반으로 선택하는 기능입니다.

DSpark uses a modified DFlash model as its parallel backbone [6]. The backbone performs the main draft computation for all positions in one forward pass, producing a hidden state and a set of base logits for each draft position. It therefore inherits the target-context conditioning described in the DFlash section.

DSpark는 수정된 DFlash 모델을 병렬 backbone으로 사용합니다 [6]. backbone은 모든 위치에 대한 주요 draft 계산을 한 번의 forward pass로 수행해, draft 위치마다 hidden state와 base logit 집합을 만들어냅니다. 따라서 DFlash 절에서 설명한 타깃 문맥 조건화를 그대로 물려받습니다.

A fully parallel draft component predicts every position without first seeing the tokens selected at earlier positions in the same block. When several continuations are plausible, this can produce inconsistent combinations. For example, both "of course" and "no problem" may be reasonable continuations, but independent position-wise predictions could produce "of problem."

완전히 병렬인 draft 구성요소는 같은 블록의 앞선 위치에서 어떤 토큰이 선택됐는지 보지 않은 채로 모든 위치를 예측합니다. 그럴듯한 이어쓰기가 여럿일 때 이 방식은 일관성 없는 조합을 만들 수 있습니다. 예를 들어 "of course"와 "no problem"이 모두 타당한 이어쓰기지만, 위치별로 독립 예측하면 "of problem"이 나올 수 있습니다.

DSpark addresses this behavior by applying a lightweight sequential head after the parallel backbone. The backbone still computes the base logits for every position together. The sequential head then selects tokens from left to right, adjusting each position using information from the previously selected draft tokens. Specifically, DSpark applies a lightweight Markov head: for each position, it uses the immediately preceding selected token to produce a small bias that adjusts the base logits.

DSpark는 병렬 backbone 뒤에 가벼운 순차 head를 붙여 이 문제를 다룹니다. backbone은 여전히 모든 위치의 base logit을 한꺼번에 계산합니다. 그다음 순차 head가 왼쪽에서 오른쪽으로 토큰을 선택하면서, 앞서 선택된 draft 토큰의 정보로 각 위치를 조정합니다. 구체적으로 DSpark는 가벼운 Markov head를 적용합니다. 각 위치에서 바로 앞에 선택된 토큰을 사용해 작은 bias를 만들고, 그것으로 base logit을 조정합니다.

Base logits for position k  +  Bias from draft token k−1 → Adjusted distribution for position k

One parallel backbone pass + lightweight sequential correction → token 1 → token 2 → token 3 → … → token N

The main draft network processes all candidate positions together in one forward pass. After that, only the lightweight Markov head runs from left to right to adjust each position using the previously selected draft token. This allows later draft tokens to depend on tokens already selected within the same block without running the full draft network again for every position.

주 draft 네트워크는 모든 후보 위치를 한 번의 forward pass로 함께 처리합니다. 그 뒤에는 가벼운 Markov head만 왼쪽에서 오른쪽으로 돌면서 앞서 선택된 draft 토큰으로 각 위치를 조정합니다. 덕분에 위치마다 전체 draft 네트워크를 다시 돌리지 않고도, 뒤쪽 draft 토큰이 같은 블록 안에서 이미 선택된 토큰에 의존할 수 있습니다.

The DSpark design also includes a confidence head that can select a shorter draft prefix for target-model verification. This feature was not active in the vLLM path used for our experiments, so the benchmark results reflect only the parallel draft network and lightweight Markov correction. DSpark 설계에는 타깃 모델 검증에 제출할 draft prefix를 더 짧게 고를 수 있는 confidence head도 있습니다. 이 기능은 저희 실험에 사용한 vLLM 경로에서 활성화되지 않았으므로, 벤치마크 결과는 병렬 draft 네트워크와 가벼운 Markov 보정만 반영합니다.

Native MTP does not load a separate draft checkpoint and may share components such as the embedding table or output head with the target model. The actual overhead depends on the draft-component size, numerical precision, tensor-parallel configuration, and runtime buffers.

Native MTP는 별도 draft 체크포인트를 로드하지 않으며 임베딩 테이블이나 출력 head 같은 구성요소를 타깃 모델과 공유할 수 있습니다. Gemma 4 MTP, EAGLE-3, DFlash, DSpark는 추가 draft 가중치를 로드하므로 충분한 GPU 메모리 여유를 확보해야 합니다. 실제 오버헤드는 draft 구성요소 크기, 수치 정밀도, 텐서 병렬 구성, 런타임 버퍼에 따라 달라집니다.

7Experimental setup and measurements실험 환경과 측정 결과

After enabling speculative decoding, the practical question is whether the additional drafting work improves end-to-end serving performance. Candidate tokens do not need to be correct at every position because the target model evaluates them before they are committed. Performance therefore depends on how many proposed tokens are accepted and whether the saved target-model decoding work outweighs the cost of drafting and verification.

speculative decoding을 켠 뒤의 실무적 질문은, 추가된 드래프팅 작업이 end-to-end 서빙 성능을 개선하느냐입니다. 후보 토큰이 모든 위치에서 맞을 필요는 없습니다. 확정 전에 타깃 모델이 평가하니까요. 따라서 성능은 제안된 토큰이 얼마나 수용되는지, 그리고 절약된 타깃 모델 디코딩 작업이 드래프팅·검증 비용을 넘어서는지에 달려 있습니다.

We evaluate model quality and serving performance using task-grounded benchmarks rather than random token sequences. Acceptance behavior depends on the structure and predictability of actual model outputs, so task-based prompts provide a more representative view of practical performance. The main performance indicators are: output-token throughput and speedup over the non-speculative baseline; mean accepted length and draft-token acceptance rates, where available; and model quality relative to the non-speculative baseline.

모델 품질과 서빙 성능은 무작위 토큰 시퀀스가 아니라 과제 기반 벤치마크로 평가합니다. 수용 동작은 실제 모델 출력의 구조와 예측 가능성에 의존하므로, 과제 기반 프롬프트가 실무 성능을 더 대표성 있게 보여줍니다. 주요 성능 지표는 다음과 같습니다: 비-speculative 기준선 대비 출력 토큰 처리량과 속도 향상, 가능한 경우 평균 수용 길이와 draft 토큰 수용률, 그리고 비-speculative 기준선 대비 모델 품질.

8Tuning considerations튜닝 시 고려사항

Speculative decoding should be treated as a runtime optimization rather than a fixed setting that works equally well for every workload. The value of num_speculative_tokens associated with the highest throughput depends on how many proposed tokens are accepted and whether the avoided target-model decode work outweighs the cost of drafting and verification.

Speculative decoding은 모든 워크로드에 똑같이 잘 듣는 고정 설정이 아니라 런타임 최적화로 다뤄야 합니다. 최고 처리량을 내는 num_speculative_tokens 값은 제안된 토큰이 얼마나 수용되는지, 그리고 회피한 타깃 모델 디코드 작업이 드래프팅·검증 비용을 넘어서는지에 달려 있습니다.

Observability is therefore important. A model-card recommendation or example configuration provides a useful starting point, but the final setting should be selected using representative workloads and end-to-end measurements. Useful signals include throughput, mean accepted length, overall acceptance rate, and per-position acceptance rate.

그래서 관측성이 중요합니다. 모델 카드의 권장값이나 예시 설정은 유용한 출발점이지만, 최종 설정은 대표성 있는 워크로드와 end-to-end 측정으로 골라야 합니다. 유용한 신호로는 처리량, 평균 수용 길이, 전체 수용률, 위치별 수용률이 있습니다.

A larger proposal window gives the system more opportunities to commit several tokens in one verification pass. However, acceptance may decrease at later draft positions. When this happens, the additional candidates contribute little while still adding drafting and verification work, causing throughput to flatten or regress.

제안 윈도우가 크면 검증 한 번에 여러 토큰을 확정할 기회가 늘어납니다. 다만 뒤쪽 draft 위치일수록 수용률이 떨어질 수 있습니다. 그렇게 되면 추가 후보들이 기여는 거의 없으면서 드래프팅·검증 작업만 늘려, 처리량이 정체되거나 뒷걸음질합니다.

Start from a supported configuration지원되는 설정에서 시작하기

For native MTP, N=1 is a conservative starting point because it introduces the least additional sequential drafting work: {"method": "mtp", "num_speculative_tokens": 1}. After confirming correctness and stability, sweep larger values such as 2, 3, 4, 5, 6, and 7.

Native MTP에서는 추가되는 순차 드래프팅 작업이 가장 적은 N=1이 보수적인 출발점입니다: {"method": "mtp", "num_speculative_tokens": 1}. 정확성과 안정성을 확인한 뒤 2, 3, 4, 5, 6, 7 같은 큰 값들을 훑어 보세요.

In our measurements, the native-MTP setting associated with the largest measured throughput varied by target model and workload. For Qwen3.5-27B, the largest measured throughput occurred at N=5 for GSM8K and MATH500, N=4 for HumanEval and MBPP, and N=3 for MT-Bench. For Qwen3.5-122B-A10B, the largest measured throughput across the four listed reasoning and code datasets occurred at N=7. The Qwen3.6 measurements also show that this setting can change between models in the same family: for Qwen3.6-27B the largest measured values occurred at N=4 or N=5, while throughput for the tested Qwen3.6-35B-A3B configurations increased through N=6.

저희 측정에서 최대 처리량을 낸 native MTP 설정은 타깃 모델과 워크로드에 따라 달랐습니다. Qwen3.5-27B에서는 GSM8K·MATH500이 N=5, HumanEval·MBPP가 N=4, MT-Bench가 N=3에서 최대였습니다. Qwen3.5-122B-A10B에서는 나열된 네 개의 추론·코드 데이터셋 전부 N=7에서 최대였습니다. Qwen3.6 측정치는 같은 패밀리 안에서도 이 설정이 달라질 수 있음을 보여줍니다. Qwen3.6-27B는 N=4 또는 N=5에서 최대였던 반면, 테스트한 Qwen3.6-35B-A3B 구성은 N=6까지 처리량이 계속 올랐습니다.

For Gemma 4 MTP and EAGLE-3, increasing N also adds sequential drafting work. A short sweep is therefore useful even when the checkpoint provides a recommended configuration. In our Gemma 4 and EAGLE-3 experiments, measured throughput generally increased over the first few values of N before reaching a plateau.

Gemma 4 MTP와 EAGLE-3에서도 N을 키우면 순차 드래프팅 작업이 늘어납니다. 그래서 체크포인트가 권장 설정을 제공하더라도 짧게 스윕해 보는 게 유용합니다. 저희 Gemma 4·EAGLE-3 실험에서는 N의 처음 몇 값에서 처리량이 오르다가 정체되는 것이 일반적이었습니다.

For DFlash, begin with the proposal lengths recommended or supported by the draft checkpoint. Many DFlash checkpoints are trained with a fixed block size. For example, when block_size = 16, the maximum proposal length is normally num_speculative_tokens = 15, because the first position is the confirmed anchor token and the remaining 15 positions are draft candidates. This is the maximum supported proposal length, not necessarily the highest-throughput setting. In practice, it is useful to test smaller values such as N = 3, 7, 11, 15. Across our DFlash experiments, N=7 was frequently among the higher-throughput settings; for some workloads, the largest measured throughput occurred at N=11.

DFlash에서는 draft 체크포인트가 권장하거나 지원하는 제안 길이에서 시작하세요. 많은 DFlash 체크포인트가 고정된 블록 크기로 학습됩니다. 예를 들어 block_size = 16이면 최대 제안 길이는 보통 num_speculative_tokens = 15입니다. 첫 위치가 확정된 anchor 토큰이고 나머지 15개가 draft 후보이기 때문입니다. 이는 지원되는 최대 제안 길이이지 반드시 최고 처리량 설정은 아닙니다. 실무에서는 N = 3, 7, 11, 15 같은 더 작은 값들도 테스트해 보는 게 좋습니다. 저희 DFlash 실험 전반에서 N=7이 높은 처리량 설정에 자주 포함됐고, 일부 워크로드에서는 N=11에서 최대치가 나왔습니다.

For DSpark, num_speculative_tokens sets the number of candidate tokens generated in each speculative round. In our vLLM experiments, the full configured proposal was submitted for target-model verification, so values such as N=3 and N=7 should be compared using end-to-end throughput.

DSpark에서 num_speculative_tokens는 speculative 라운드마다 생성할 후보 토큰 개수를 정합니다. 저희 vLLM 실험에서는 설정된 제안 전체가 타깃 모델 검증에 제출됐으므로, N=3과 N=7 같은 값들은 end-to-end 처리량으로 비교해야 합니다.

Match the sweep to the workload스윕을 워크로드에 맞추기

Different workloads can produce different acceptance patterns. In our GSM8K and MATH500 measurements, medium or deeper proposal lengths were often associated with higher measured throughput within the tested sweeps. For native MTP on Qwen3.5-122B-A10B, measured throughput increased through N=7. For DFlash, higher measured values frequently occurred at N=7 or N=11. For HumanEval and MBPP, moderate proposal lengths were often among the higher-throughput settings. Code contains predictable local structure, but formatting, identifiers, and implementation choices can cause an otherwise plausible continuation to diverge.

워크로드가 다르면 수용 패턴도 달라질 수 있습니다. 저희 GSM8K·MATH500 측정에서는 테스트한 스윕 내에서 중간 또는 더 깊은 제안 길이가 높은 처리량과 짝을 이루는 경우가 많았습니다. Qwen3.5-122B-A10B의 native MTP에서는 N=7까지 처리량이 올랐습니다. DFlash에서는 N=7이나 N=11에서 높은 값이 자주 나왔습니다. HumanEval·MBPP에서는 중간 정도의 제안 길이가 높은 처리량 설정에 자주 들었습니다. 코드에는 예측 가능한 국소 구조가 있지만, 서식·식별자·구현 선택 때문에 그럴듯해 보이던 이어쓰기가 갈라질 수 있습니다.

Example tuning workflow튜닝 워크플로 예시

  1. Begin with a configuration supported or recommended for the checkpoint.
  2. Benchmark using representative prompts and generation settings.
  3. Record throughput, mean accepted length, and acceptance rates.
  4. Sweep several smaller and larger proposal lengths.
  5. Select a setting based on the metric most relevant to the intended workload. In these experiments, end-to-end serving throughput was the primary selection metric.
  1. 체크포인트가 지원하거나 권장하는 설정에서 시작한다.
  2. 대표성 있는 프롬프트와 생성 설정으로 벤치마크한다.
  3. 처리량, 평균 수용 길이, 수용률을 기록한다.
  4. 더 작은 값과 더 큰 값의 제안 길이를 여럿 훑는다.
  5. 의도한 워크로드에 가장 관련 있는 지표를 기준으로 설정을 고른다. 이번 실험에서는 end-to-end 서빙 처리량이 주된 선택 지표였다.

The selected configuration does not necessarily have the longest proposal, the highest acceptance rate, or the largest mean accepted length. Selection should consider the trade-off among drafting cost, verification cost, accepted tokens, and the metric most relevant to the intended workload.

선택된 설정이 반드시 제안이 가장 길거나, 수용률이 가장 높거나, 평균 수용 길이가 가장 큰 것은 아닙니다. 선택할 때는 드래프팅 비용, 검증 비용, 수용된 토큰, 그리고 의도한 워크로드에 가장 관련 있는 지표 사이의 트레이드오프를 함께 고려해야 합니다.

Prepare representative prompts대표성 있는 프롬프트 준비

Start with prompts that reflect the expected workload, such as chat, mathematics, code generation, tool use, or multilingual tasks. Keep a separate set of prompts for evaluation. The responses used for training should be generated by the exact target model that the speculator will support. The tokenizer, chat template, thinking mode, and generation configuration should also match the intended deployment. The vLLM documentation emphasizes that applying the target model's tokenizer or chat template to existing responses does not make the data target-specific; the responses themselves must come from the target model.

Collect target-model information타깃 모델 정보 수집

A vLLM server can run the target model and expose hidden states from the layers required by the selected drafting method. When custom target layers are chosen, the same layer selections must also be used in the speculator-training configuration. The information collected depends on the method: EAGLE-3 uses hidden states from selected target-model layers for autoregressive drafting [4]; DFlash uses target-model features to train a network that predicts a block of future positions in parallel [16]; DSpark adds lightweight sequential and confidence heads to a DFlash-style draft network [6]; and MTP training fine-tunes the target model's own MTP component and therefore requires a target model that already contains compatible MTP layers [13].

vLLM 서버로 타깃 모델을 실행하면서, 선택한 드래프팅 방법이 요구하는 레이어의 hidden state를 노출시킬 수 있습니다. 커스텀 타깃 레이어를 고른 경우, speculator 학습 설정에서도 같은 레이어 선택을 써야 합니다. 수집할 정보는 방법에 따라 다릅니다. EAGLE-3는 자기회귀 드래프팅을 위해 선택된 타깃 모델 레이어의 hidden state를 사용하고 [4], DFlash는 미래 위치 블록을 병렬로 예측하는 네트워크를 학습시키기 위해 타깃 모델 feature를 사용하며 [16], DSpark는 DFlash 방식 draft 네트워크에 가벼운 순차 head와 confidence head를 더합니다 [6]. MTP 학습은 타깃 모델 자체의 MTP 구성요소를 파인튜닝하므로, 호환되는 MTP 레이어를 이미 갖춘 타깃 모델이 필요합니다 [13].

Train and test the speculatorSpeculator 학습과 테스트

The speculator configuration must match the target model's hidden size, vocabulary, tokenizer, and selected target layers. Method-specific settings such as draft-network depth, block size, sequence length, and learning rate must also be selected. After training, inspect the checkpoint and serve it together with the target model in vLLM. Training loss alone is not enough to judge the result; the important measurements are accepted length, acceptance rate, draft latency, GPU memory use, and end-to-end serving throughput. When acceptance is weak for a particular workload, the prompt mixture or training configuration can be adjusted and the process repeated. The main principle is to use the same target model, generation mode, and representative workload that the speculator is expected to support.

Summary요약

This blog explored speculative decoding in vLLM as a draft-and-verify approach for LLM serving. A draft component proposes candidate future tokens, and the target model evaluates the proposal before any tokens are committed. We examined five drafting approaches: native MTP, Gemma 4 MTP, EAGLE-3, DFlash, and DSpark. They differ mainly in how they use information from the target model and whether candidate tokens are generated sequentially, in parallel, or through a combination of parallel prediction and lightweight sequential correction.

이 글은 LLM 서빙을 위한 draft-and-verify 접근으로서 vLLM의 speculative decoding을 살펴봤습니다. draft 구성요소가 미래 토큰 후보를 제안하고, 어떤 토큰도 확정되기 전에 타깃 모델이 그 제안을 평가합니다. 다섯 가지 드래프팅 방식(native MTP, Gemma 4 MTP, EAGLE-3, DFlash, DSpark)을 살펴봤습니다. 이들은 주로 타깃 모델의 정보를 어떻게 쓰는지, 그리고 후보 토큰을 순차적으로 생성하는지, 병렬로 생성하는지, 아니면 병렬 예측과 가벼운 순차 보정을 조합하는지에서 차이가 납니다.

The experiments covered selected Gemma, Qwen, MiniMax, and Kimi models on AMD Instinct™ MI300X and MI355X GPUs using the ROCm™ software platform. Measured throughput varied across target models, draft checkpoints, workloads, proposal lengths, and serving configurations. Across the tested configurations, some settings produced smaller changes or throughput below the non-speculative baseline, while several model-workload combinations produced throughput ratios above 2×. Examples at the upper end of the observed range included 2.87× for DFlash on gemma-4-26B-A4B-it, 2.83× for Gemma 4 MTP on the same target, and 2.68× for DFlash on Kimi-K2.5.

실험은 AMD Instinct™ MI300X·MI355X GPU에서 ROCm™ 소프트웨어 플랫폼으로 Gemma, Qwen, MiniMax, Kimi 계열 일부 모델을 대상으로 했습니다. 측정된 처리량은 타깃 모델·draft 체크포인트·워크로드·제안 길이·서빙 설정에 따라 달랐습니다. 테스트한 구성 전반에서, 어떤 설정은 변화가 작거나 비-speculative 기준선보다 낮은 처리량을 냈고, 여러 모델-워크로드 조합에서는 2배를 넘는 처리량 비가 나왔습니다. 관측 범위 상단의 예로는 gemma-4-26B-A4B-it에서 DFlash 2.87×, 같은 타깃에서 Gemma 4 MTP 2.83×, Kimi-K2.5에서 DFlash 2.68×가 있습니다.

Proposal length was also an important experimental variable. Increasing num_speculative_tokens sometimes increased throughput over the first few settings, while larger values could lead to a plateau or lower throughput. Checkpoint recommendations can provide starting points, but representative workload measurements and acceptance metrics are needed when selecting a deployment configuration.

제안 길이도 중요한 실험 변수였습니다. num_speculative_tokens를 키우면 처음 몇 설정에서는 처리량이 오르기도 했지만, 값이 더 커지면 정체되거나 낮아질 수 있었습니다. 체크포인트 권장값이 출발점은 되지만, 배포 설정을 고를 때는 대표 워크로드 측정치와 수용 지표가 필요합니다.

Future work향후 과제

  • Future benchmarking could include non-learned approaches such as n-gram speculation and suffix decoding, particularly for workloads with repeated token patterns such as code editing and agentic loops.
  • Broader evaluation across concurrency levels, prompt and output lengths, batch sizes, and sampling settings would also help show how speculative decoding behaves under different serving conditions.
  • Another useful direction is to study how speculator training data affects acceptance across code, mathematics, chat, multilingual prompts, tool use, and structured output.
  • Finally, deeper profiling of draft generation, target verification, KV-cache behavior, graph execution, and scheduling would help explain the performance differences observed across target models and workloads.
  • 향후 벤치마킹에는 n-gram speculation이나 suffix decoding 같은 비학습 방식도 포함할 수 있습니다. 특히 코드 편집이나 에이전트 루프처럼 토큰 패턴이 반복되는 워크로드에서 그렇습니다.
  • 동시성 수준, 프롬프트·출력 길이, 배치 크기, 샘플링 설정에 걸친 폭넓은 평가도 speculative decoding이 다양한 서빙 조건에서 어떻게 동작하는지 보여주는 데 도움이 될 것입니다.
  • 또 하나 유용한 방향은 speculator 학습 데이터가 코드·수학·챗·다국어 프롬프트·도구 사용·구조화 출력 전반의 수용률에 어떤 영향을 주는지 연구하는 것입니다.
  • 마지막으로, draft 생성·타깃 검증·KV 캐시 동작·그래프 실행·스케줄링에 대한 더 깊은 프로파일링은 타깃 모델과 워크로드에 따라 관측된 성능 차이를 설명하는 데 도움이 될 것입니다.
