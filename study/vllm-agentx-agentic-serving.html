1Characterizing agentic workloads: a second lookagentic 워크로드 다시 보기

Since our first post on serving agentic workloads in May, the share of agentic traffic has continued to grow. As of June 2026, OpenAI reported that Codex generated 64% of combined Codex and ChatGPT output tokens among enterprise customers.

5월에 agentic 워크로드 서빙에 대한 첫 글을 낸 이후로 agentic 트래픽의 비중은 계속 커졌다. 2026년 6월 기준 OpenAI는 엔터프라이즈 고객에서 Codex가 Codex+ChatGPT 합산 출력 토큰의 64%를 생성했다고 밝혔다.

This growing token consumption stresses serving infrastructure along two axes: cost and latency. Cost efficiency determines how many concurrent agents fit in a fixed hardware budget; latency determines how quickly each agent progresses through its reasoning and tool-use cycles. Optimizing agentic serving therefore means improving the latency-cost frontier as a whole.

이렇게 늘어나는 토큰 소비는 서빙 인프라를 두 축으로 압박한다 — 비용과 지연. 비용 효율은 고정된 하드웨어 예산에 동시 에이전트를 몇 개 넣을 수 있는지를 정하고, 지연은 각 에이전트가 추론·도구 사용 사이클을 얼마나 빨리 진행하는지를 정한다. 따라서 agentic 서빙을 최적화한다는 것은 지연-비용 프론티어 전체를 개선한다는 뜻이다.

These statistics follow from how an agentic session is built. Each turn appends the latest tool result to the accumulated context and sends the whole thing back to the model, so the input keeps growing while each turn adds only a short new prefill, and almost all of the request is a prefix the engine has already seen. Subagents either fork from that context or start fresh, and their results are joined back into the parent before the final answer.

이 통계들은 agentic 세션이 어떻게 만들어지는지에서 따라 나온다. 매 턴은 최신 도구 결과를 누적된 컨텍스트에 덧붙여 그 전체를 모델에 다시 보낸다. 그래서 입력은 계속 자라는데 턴마다 새로 붙는 prefill은 짧고, 요청의 거의 전부가 엔진이 이미 본 prefix다. 서브에이전트는 그 컨텍스트에서 갈라져 나오거나 새로 시작하며, 그 결과는 최종 답변 전에 부모로 합쳐진다.

2Challenges in serving agentic workloadsagentic 워크로드 서빙의 난제

These workload characteristics create three challenges for efficient serving.

이런 워크로드 특성은 효율적인 서빙에 세 가지 난제를 만든다.

  • Prefix cache pressure. Every turn of a multi-turn session replays the full conversation so far. To keep many sessions running at once, the engine has to offload KV caches between turns. This becomes harder at scale, where KV cache management, prefix caching, and offloading must work efficiently across GPUs, prefill/decode disaggregated instances, and replicas.
  • Execution efficiency. Agentic workloads feature long contexts and tight latency requirements, so the engine has to process more tokens and do more work per token in less time. This requires adapting parallelism, kernels, scheduling, speculative decoding, and other engine optimizations to the new request shape.
  • Finding the right P/D ratio. Context lengths and cache hit rates vary wildly across sessions and subagents, and routing must efficiently balance cache affinity and load across ranks. These factors make it difficult to find the throughput-optimal P/D ratio, which also shifts with concurrency.
  • Prefix 캐시 압박. 멀티턴 세션의 매 턴은 지금까지의 대화 전체를 다시 재생한다. 많은 세션을 동시에 돌리려면 엔진이 턴 사이에 KV 캐시를 오프로드해야 한다. 규모가 커지면 더 어려워진다 — KV 캐시 관리, prefix 캐싱, 오프로딩이 GPU들과 prefill/decode 분리 인스턴스들, 그리고 replica들에 걸쳐 효율적으로 동작해야 한다.
  • 실행 효율. agentic 워크로드는 긴 컨텍스트와 촘촘한 지연 요구를 함께 갖는다. 그래서 엔진은 더 많은 토큰을 처리하고 토큰당 더 많은 일을 더 짧은 시간에 해내야 한다. 병렬화, 커널, 스케줄링, speculative decoding, 그 외 엔진 최적화를 새로운 요청 모양에 맞춰야 한다는 뜻이다.
  • 올바른 P/D 비율 찾기. 컨텍스트 길이와 캐시 히트율이 세션·서브에이전트마다 크게 다르고, 라우팅은 캐시 어피니티와 부하를 rank들에 걸쳐 효율적으로 균형 잡아야 한다. 이런 요인들 때문에 처리량 최적 P/D 비율을 찾기가 어렵고, 그 비율은 동시성에 따라 또 달라진다.

Hybrid KV cache management: a foundation that keeps evolvingHybrid KV 캐시 관리 — 계속 진화하는 토대

KV cache management has been central to vLLM since PagedAttention, and agentic workloads with long contexts put heavier pressure on KV cache capacity. Modern hybrid models complicate allocation further by combining sliding-window and linear attention with full attention, whose cached blocks differ in size and lifetime.

KV 캐시 관리는 PagedAttention 이래로 vLLM의 중심이었고, 긴 컨텍스트를 갖는 agentic 워크로드는 KV 캐시 용량을 더 강하게 압박한다. 요즘의 hybrid 모델들은 sliding-window와 linear attention을 full attention과 섞어 쓰면서 할당을 더 복잡하게 만드는데, 이들의 캐시 블록은 크기와 수명이 서로 다르다.

vLLM's hybrid KV cache manager tackles this complexity with a simple core idea: a uniform memory page as the basic allocation unit, managed through one shared block pool (Figure 4).

vLLM의 hybrid KV 캐시 관리자는 이 복잡성을 단순한 핵심 아이디어로 다룬다: 균일한 메모리 페이지를 기본 할당 단위로 삼고, 하나의 공유 블록 풀로 관리한다(Figure 4).

A shared pool lets vLLM reallocate memory dynamically on demand instead of statically partitioning capacity by attention type. This matters because full-attention KV grows with sequence length, while sliding-window and recurrent state follow different lifetimes and scaling rules. The best partition therefore changes with concurrency, context length, and prefix-reuse patterns.

공유 풀 덕분에 vLLM은 어텐션 종류별로 용량을 정적으로 쪼개는 대신 필요에 따라 메모리를 동적으로 재할당할 수 있다. 이게 중요한 이유는 full attention의 KV는 시퀀스 길이에 따라 자라는 반면 sliding-window와 순환 상태는 다른 수명과 스케일링 규칙을 따르기 때문이다. 따라서 최적 분할 비율은 동시성·컨텍스트 길이·prefix 재사용 패턴에 따라 바뀐다.

Figure 4: vLLM's hybrid KV cache manager. One page size serves all attention types, and a single block pool is shared between them.Figure 4: vLLM의 hybrid KV 캐시 관리자. 하나의 페이지 크기가 모든 어텐션 종류를 커버하고, 블록 풀 하나를 그들이 공유한다.

The abstraction continues to evolve as new architectures expose fragmentation and transfer inefficiencies. For example, DeepSeek V4's initial KV cache layout fragmented the different cache types into three size buckets and allocated 92 separate tensors. As Figure 5 shows, this fragmentation wastes memory on padding and is inefficient for P/D transfer and KV cache offloading.

이 추상화는 새 아키텍처가 단편화와 전송 비효율을 드러낼 때마다 계속 진화한다. 예를 들어 DeepSeek V4의 초기 KV 캐시 레이아웃은 서로 다른 캐시 종류를 세 개의 크기 버킷으로 쪼개고 92개의 별도 텐서를 할당했다. Figure 5가 보여주듯 이 단편화는 padding에 메모리를 낭비하고 P/D 전송과 KV 캐시 오프로딩에 비효율적이다.

The new packed KV cache layout instead stores all cache groups and layers in one contiguous backing allocation per block rather than 92 fragmented ones. This reduces descriptor and P/D transfer overhead, and also permits a smaller allocation unit when the FP4 indexer is enabled, saving roughly 10% of KV cache memory.

새로운 packed KV 캐시 레이아웃은 대신 모든 캐시 그룹과 레이어를 블록당 하나의 연속된 backing 할당에 저장한다 — 92개로 쪼개는 대신에. 이로써 descriptor와 P/D 전송 오버헤드가 줄고, FP4 indexer를 켰을 때는 더 작은 할당 단위도 가능해져 KV 캐시 메모리의 약 10%를 절약한다.

Hierarchical KV cache offloading: distributed pool with smart retention policies계층적 KV 캐시 오프로딩 — 영리한 보존 정책을 갖춘 분산 풀

To preserve prefix caches beyond GPU memory capacity and across each engine, vLLM has integrated Mooncake Store as a distributed KV cache pool. Adoption has grown steadily since, and we keep shipping new features and performance improvements for capacity, efficiency, and retention on agentic workloads.

GPU 메모리 용량을 넘어서, 그리고 엔진 경계를 넘어서 prefix 캐시를 보존하기 위해 vLLM은 Mooncake Store를 분산 KV 캐시 풀로 통합했다. 이후 채택이 꾸준히 늘었고, agentic 워크로드에서의 용량·효율·보존을 위한 새 기능과 성능 개선을 계속 내보내고 있다.

Model architecture parity. KV cache offloading remains a first-class citizen in vLLM, with full support for new model architectures including sparse attention, compressed attention, and linear attention. This is done while keeping other engine features fully functional and performant, including asynchronous scheduling, P/D disaggregation, speculative decoding, and parallelism.

모델 아키텍처 대응. KV 캐시 오프로딩은 vLLM에서 계속 일급 시민이며, sparse attention·compressed attention·linear attention을 포함한 새 모델 아키텍처를 완전히 지원한다. 그러면서 비동기 스케줄링, P/D 분리, speculative decoding, 병렬화 같은 다른 엔진 기능들도 온전히 동작하고 성능을 유지하도록 한다.

Hierarchical KV cache offloading. vLLM supports hierarchical tiers for the distributed KV cache pool to further extend capacity with disks and extra CPU-only nodes. This is achieved with vLLM's Mooncake Store standalone-store mode, which makes an external Mooncake client own the CPU pool and disk tier, and turns vLLM workers into pure requesters. By launching a standalone Mooncake client on each node, we can freely expand the KV cache pool with CPU memory and disks. We have also integrated the distributed shared KV cache pool with routers such as Dynamo and llm-d, which simplifies the routing policy because requests can get cache hits on any instance.

계층적 KV 캐시 오프로딩. vLLM은 분산 KV 캐시 풀에 계층(tier)을 지원해 디스크와 CPU 전용 노드로 용량을 더 확장한다. 이는 vLLM의 Mooncake Store standalone-store 모드로 구현되는데, 외부 Mooncake 클라이언트가 CPU 풀과 디스크 tier를 소유하게 하고 vLLM 워커는 순수한 요청자로 만든다. 각 노드에 standalone Mooncake 클라이언트를 띄우면 CPU 메모리와 디스크로 KV 캐시 풀을 자유롭게 늘릴 수 있다. 또한 이 분산 공유 KV 캐시 풀을 Dynamo와 llm-d 같은 라우터와 통합했는데, 요청이 어느 인스턴스에서든 캐시 히트를 얻을 수 있게 되므로 라우팅 정책이 단순해진다.

Performance optimizations. Hybrid models must construct keys and perform lookups separately for each attention type, which multiplies CPU overhead. We reduced this cost through more efficient data structures, asynchronous lookups, work moved off the scheduler's critical path, and parallel send and receive operations. Implementation details are in PR#46188, PR#45444, PR#45659, and PR#47317.

성능 최적화. hybrid 모델은 어텐션 종류마다 따로 키를 만들고 조회해야 해서 CPU 오버헤드가 배로 늘어난다. 더 효율적인 자료구조, 비동기 조회, 스케줄러의 임계 경로 밖으로 작업 이동, 송수신 병렬화로 이 비용을 줄였다. 구현 세부는 PR#46188, PR#45444, PR#45659, PR#47317에 있다.

Session-aware prefix-cache retention세션 인식 prefix 캐시 보존

For hybrid models with linear or sliding-window layers alongside full attention, prefix reuse requires preserving the linear state or sliding-window cache at the reuse boundary. Keeping these snapshots at every token is expensive, so we combine two complementary policies:

full attention과 함께 linear 또는 sliding-window 레이어를 갖는 hybrid 모델에서는, prefix 재사용을 위해 재사용 경계에서 linear 상태나 sliding-window 캐시를 보존해야 한다. 이 스냅샷을 매 토큰마다 유지하는 것은 비싸므로, 서로 보완하는 두 정책을 조합한다:

  • Interval-based retention automatically preserves prompt-end caches / linear states at each turn. Subsequent turns and forked subagents, which typically replay and extend an earlier turn's context, can then reuse the cached context.
  • Marconi-style selective retention retains a checkpoint when a prefix is observed a second time. When a request encounters a previously observed prefix without a retained checkpoint, vLLM recomputes the missing state and saves a checkpoint at that boundary. Subsequent requests sharing the prefix can then reuse it.
  • Interval 기반 보존은 매 턴의 prompt 끝 캐시/linear 상태를 자동으로 보존한다. 보통 앞선 턴의 컨텍스트를 재생하고 연장하는 이후 턴들과 갈라져 나온 서브에이전트들이 그 캐시된 컨텍스트를 재사용할 수 있다.
  • Marconi 스타일 선택적 보존은 어떤 prefix가 두 번째로 관측될 때 체크포인트를 남긴다. 요청이 이전에 관측된 prefix를 만났는데 보존된 체크포인트가 없으면, vLLM은 빠진 상태를 재계산하고 그 경계에 체크포인트를 저장한다. 그 prefix를 공유하는 이후 요청들이 이를 재사용할 수 있다.

However, shared prefixes typically end within a turn, so interval-based retention may not preserve a checkpoint — which is why the second policy exists. Together, these policies preserve a high cache hit rate without excessive storage overhead on large-scale agentic workloads.

다만 공유되는 prefix는 보통 턴 중간에서 끝나므로 interval 기반 보존이 체크포인트를 남기지 못할 수 있다 — 두 번째 정책이 존재하는 이유다. 두 정책을 함께 쓰면 대규모 agentic 워크로드에서 과도한 저장 오버헤드 없이 높은 캐시 히트율을 유지할 수 있다.

4Execution plane: model-specific parallelism실행 플레인 — 모델별 병렬화

Modern inference systems expose several axes of parallelism: tensor parallelism (TP), data parallelism (DP), expert parallelism (EP), pipeline parallelism (PP), and context parallelism (CP). The optimal parallelism, however, depends on the model architecture, hardware topology, workload patterns, and latency SLOs.

요즘의 추론 시스템은 여러 병렬화 축을 제공한다 — tensor parallelism(TP), data parallelism(DP), expert parallelism(EP), pipeline parallelism(PP), context parallelism(CP). 그런데 최적 병렬화는 모델 아키텍처, 하드웨어 토폴로지, 워크로드 패턴, 지연 SLO에 따라 달라진다.

Kimi K3

Kimi K3 features multi-head latent attention (MLA) and Kimi Delta Attention (KDA). Since MLA compresses KV into a single latent space with one head, plain tensor parallelism (TP), which replicates that latent cache across ranks, is not very efficient.

Kimi K3은 multi-head latent attention(MLA)과 Kimi Delta Attention(KDA)을 쓴다. MLA는 KV를 head 하나의 단일 latent 공간으로 압축하므로, 그 latent 캐시를 rank마다 복제하는 평범한 TP는 효율이 별로 좋지 않다.

As an alternative to TP, we have found strong performance gains from decode context parallelism (DCP), which shards the cache along the sequence dimension, leaving each rank with 1/N of the KV state. DCP offers two benefits for agentic workloads:

TP의 대안으로 decode context parallelism(DCP)에서 큰 성능 이득을 확인했다. DCP는 캐시를 시퀀스 차원으로 샤딩해 각 rank가 KV 상태의 1/N만 갖게 한다. DCP는 agentic 워크로드에 두 가지 이득을 준다:

  • Lower decode latency. MLA attention is memory-bound, and its cost grows with context length. As agentic prefixes grow, attention becomes a larger share of each decode step, and sharding it across ranks shortens that step.
  • Higher throughput and KV capacity. Avoiding KV cache replication lets the engine keep more sequences in flight without stalling on KV admission, and hence achieve higher throughput.
  • 더 낮은 decode 지연. MLA 어텐션은 메모리 바운드이고 그 비용은 컨텍스트 길이에 따라 자란다. agentic prefix가 길어질수록 어텐션이 decode 스텝에서 차지하는 비중이 커지므로, 이를 rank들에 샤딩하면 그 스텝이 짧아진다.
  • 더 높은 처리량과 KV 용량. KV 캐시 복제를 피하면 엔진이 KV admission에서 막히지 않고 더 많은 시퀀스를 동시에 유지할 수 있어 처리량이 올라간다.

Figure 6: For Kimi K3, DCP8 achieves lower decode latency than TP8 and scales to higher concurrency.Figure 6: Kimi K3에서 DCP8은 TP8보다 낮은 decode 지연을 달성하고 더 높은 동시성까지 확장된다.

DCP's tradeoff is extra communication: the KV cache is sharded by sequence, so every MLA decode layer needs a query gather before attention and a partial-output reduction after it.

DCP의 대가는 추가 통신이다. KV 캐시가 시퀀스로 샤딩되므로 모든 MLA decode 레이어가 어텐션 전에 query gather를, 어텐션 후에 partial-output reduction을 필요로 한다.

We carefully optimized the DCP compute path to bypass NCCL operations and avoid these overheads. We use symmetric-memory buffers that peer GPUs can load from and store to directly. Queries are multicast straight into the buffers consumed by the attention kernels. Each GPU then writes its partial attention outputs and log-sum-exp (LSE) statistics directly into its peers' receive slots, where each rank locally merges the results with online softmax. These GPU-to-GPU writes are fused with the computation into the same kernels, cutting latency by about 13% per layer compared with the default DCP8 implementation.

DCP 연산 경로를 세심하게 최적화해 NCCL 연산을 우회하고 이 오버헤드를 없앴다. peer GPU가 직접 읽고 쓸 수 있는 symmetric-memory 버퍼를 쓴다. query는 어텐션 커널이 소비하는 버퍼로 곧바로 multicast된다. 그다음 각 GPU가 자기 partial 어텐션 출력과 log-sum-exp(LSE) 통계를 peer의 수신 슬롯에 직접 쓰고, 각 rank는 online softmax로 결과를 로컬에서 병합한다. 이 GPU-to-GPU 쓰기는 연산과 같은 커널로 융합되어, 기본 DCP8 구현 대비 레이어당 지연을 약 13% 줄인다.

Figure 7: MLA decode path under DCP4 using symmetric memory. Each step is fused into a single kernel, replacing the NCCL all-gather, staging copy, all-to-all, and unpack steps.Figure 7: symmetric memory를 쓴 DCP4에서의 MLA decode 경로. 각 단계가 단일 커널로 융합되어 NCCL all-gather·staging 복사·all-to-all·unpack 단계를 대체한다.

A larger scale-up domain can change the best strategy. On an NVL72-class system, for example, wide EP with data parallelism (DEP) can scale better than DCP and deliver higher throughput at the same decode latency SLO. At larger, multi-node DCP sizes, the communication cost of sharded attention outweighs the compute it saves. DEP assigns requests and their KV caches to different data-parallel ranks, avoiding DCP's attention collectives while sharding the MoE experts across ranks.

scale-up 도메인이 커지면 최적 전략이 바뀔 수 있다. 예컨대 NVL72급 시스템에서는 data parallelism을 결합한 wide EP(DEP)가 DCP보다 잘 확장되고 같은 decode 지연 SLO에서 더 높은 처리량을 낸다. 멀티노드로 DCP 크기가 커지면 샤딩된 어텐션의 통신 비용이 절약한 연산을 넘어선다. DEP는 요청과 그 KV 캐시를 서로 다른 data-parallel rank에 배정해 DCP의 어텐션 collective를 피하면서, MoE expert를 rank들에 샤딩한다.

DeepSeek V4

DeepSeek V4 also has MLA-style KV caches that replicate under TP, leading to inefficient memory use. In addition, its compressed sparse attention makes TP head sharding compute-inefficient for three reasons:

DeepSeek V4도 TP에서 복제되는 MLA 계열 KV 캐시를 갖고 있어 메모리 사용이 비효율적이다. 게다가 compressed sparse attention 때문에 TP head 샤딩이 연산 측면에서 비효율적인데, 이유가 셋이다:

  • The compressor paths produce only one shared KV representation per compressed position rather than independent per-head states. TP therefore cannot shard compute along the KV-head dimension, and every rank repeats the compressor work.
  • The indexer, while having 64 heads, produces only one global top-k selection per token. The current TP path therefore replicates the full indexer on every rank, avoiding a dense score reduction before top-k but duplicating the work.
  • Sparse MLA is dominated by scanning and gathering top-k KV cache entries, not by attention arithmetic. TP repeats much of this memory-bound work on every rank while dividing only the cheaper head-wise computation.
  • compressor 경로는 압축된 위치마다 head별 독립 상태가 아니라 공유된 KV 표현 하나만 만든다. 따라서 TP는 KV-head 차원으로 연산을 샤딩할 수 없고, 모든 rank가 compressor 작업을 반복한다.
  • indexer는 head가 64개지만 토큰당 전역 top-k 선택 하나만 만든다. 그래서 현재 TP 경로는 indexer 전체를 모든 rank에 복제한다 — top-k 전의 dense score reduction은 피하지만 작업을 중복한다.
  • sparse MLA는 어텐션 산술이 아니라 top-k KV 캐시 항목을 스캔하고 모으는 일이 지배한다. TP는 이 메모리 바운드 작업의 상당 부분을 모든 rank에서 반복하면서, 정작 더 싼 head별 연산만 나눈다.

In practice, prefill context parallelism (PCP) performs best for long prefills, while data and expert parallelism (DEP) works well across a broader range of serving conditions.

실무적으로는 긴 prefill에는 prefill context parallelism(PCP)이 가장 좋고, 더 넓은 범위의 서빙 조건에서는 data and expert parallelism(DEP)이 잘 동작한다.

PCP shards the prompt sequence (the query tensor), distributing compressor and indexer work across ranks, while giving sparse MLA a wider, more efficient head-local shape. For a 32K prompt, PCP8 achieves a 2.65× prefill speedup over TP8, substantially reducing TTFT. However, it still replicates decode-side state across ranks, so it is best suited to dedicated prefill workers.

PCP는 프롬프트 시퀀스(query 텐서)를 샤딩해 compressor와 indexer 작업을 rank들에 분산시키고, sparse MLA에는 더 넓고 효율적인 head-local 모양을 준다. 32K 프롬프트에서 PCP8은 TP8 대비 prefill을 2.65배 가속해 TTFT를 크게 줄인다. 다만 decode 쪽 상태는 여전히 rank마다 복제하므로, 전용 prefill 워커에 가장 잘 맞는다.

DCP is less effective for DeepSeek V4 than for Kimi K3 because of V4's more complex model architecture (see the bitter lessons). DEP instead distributes requests and decoded tokens across data-parallel ranks and keeps the attention path completely local. This makes DEP our default for most DeepSeek V4 configurations.

DCP는 V4의 더 복잡한 모델 아키텍처 때문에 Kimi K3보다 DeepSeek V4에서 효과가 덜하다(쓰라린 교훈 절 참고). DEP는 대신 요청과 디코딩된 토큰을 data-parallel rank들에 분산시키고 어텐션 경로를 완전히 로컬로 유지한다. 그래서 대부분의 DeepSeek V4 구성에서 DEP가 우리의 기본값이다.

5Scheduling mixed agentic traffic at two levels혼합 agentic 트래픽을 두 층위에서 스케줄링

Agentic serving mixes frequent append-only requests, which reuse long prefixes and need only short prefills, with occasional long fresh prefills spanning tens of thousands of tokens. This creates two scheduling problems: within an instance, a long prefill can block short interactive turns; across DEP ranks, uneven prefill placement creates load imbalance.

agentic 서빙은 긴 prefix를 재사용하고 짧은 prefill만 필요한 빈번한 append 요청과, 수만 토큰에 걸친 간헐적인 긴 fresh prefill을 섞는다. 여기서 스케줄링 문제가 둘 생긴다. 인스턴스 안에서는 긴 prefill이 짧은 대화형 턴을 막을 수 있고, DEP rank 사이에서는 prefill이 고르지 않게 배치되어 부하 불균형이 생긴다.

Breaking head-of-line blockinghead-of-line blocking 깨뜨리기

By default, vLLM's chunked-prefill scheduler runs in first-in, first-out order. One long prefill can claim the entire token budget step after step, and the short turns queued on the same rank cannot be scheduled at all until the long prefill finishes. This is known as head-of-line blocking.

기본적으로 vLLM의 chunked-prefill 스케줄러는 선입선출로 돈다. 긴 prefill 하나가 스텝마다 토큰 예산 전체를 차지할 수 있고, 같은 rank에 줄 서 있는 짧은 턴들은 그 긴 prefill이 끝날 때까지 아예 스케줄되지 못한다. 이를 head-of-line blocking이라 한다.

Figure 9: Head-of-line blocking in the prefill queue, session view of one rank. Left: without a chunk cap, a long prefill claims the whole budget and the short cached turns wait. Right: with a 512-token cap, short turns join every step and begin decoding sooner.Figure 9: prefill 큐에서의 head-of-line blocking, rank 하나의 세션 뷰. 왼쪽: chunk 상한이 없으면 긴 prefill이 예산 전체를 차지하고 짧은 캐시된 턴들이 대기한다. 오른쪽: 512 토큰 상한을 두면 짧은 턴들이 매 스텝 합류해 더 빨리 디코딩을 시작한다.

We tackle this issue with a simple scheduling policy: we use --long-prefill-token-threshold to cap how many tokens one request may schedule per step. With a 512-token threshold, a long prefill leaves room for short turns to join the same batch and begin decoding sooner. With DeepSeek V4 Pro on B300s, this increases total tokens per GPU-second (TPGS) by up to 93% and improves P90 interactivity by roughly 2.3×. The trade-off is a higher TTFT for the long request itself, so TTFT-sensitive deployments should use a larger threshold.

이 문제를 단순한 스케줄링 정책으로 다룬다. --long-prefill-token-threshold로 한 요청이 스텝당 스케줄할 수 있는 토큰 수에 상한을 둔다. 512 토큰 상한이면 긴 prefill이 짧은 턴들이 같은 배치에 합류할 여지를 남겨 주어 더 빨리 디코딩을 시작하게 한다. B300에서 DeepSeek V4 Pro의 경우 이것이 GPU-초당 총 토큰(TPGS)을 최대 93% 올리고 P90 interactivity를 약 2.3배 개선한다. 대가는 그 긴 요청 자체의 TTFT가 높아지는 것이라, TTFT에 민감한 배포는 상한을 더 크게 잡아야 한다.

Align DEP prefill schedule cadenceDEP prefill 스케줄 주기 맞추기

DEP introduces a second inefficiency: MoE all-to-all communication forces ranks to advance in lockstep, so a rank processing prefill work slows the entire group. When prefills arrive on different steps on different ranks, this penalty is paid repeatedly.

DEP는 두 번째 비효율을 만든다. MoE all-to-all 통신이 rank들을 lockstep으로 전진하게 강제하므로, prefill 작업을 처리하는 rank 하나가 그룹 전체를 느리게 만든다. prefill이 rank마다 다른 스텝에 도착하면 이 대가를 반복해서 치른다.

To alleviate this imbalance, we set --prefill-schedule-interval to admit prefill work only every Nth engine step, using a counter aligned across data-parallel ranks. This concentrates prefill work onto the same steps across ranks and increases the fraction of the remaining steps devoted entirely to decode.

이 불균형을 완화하기 위해 --prefill-schedule-interval을 설정해, data-parallel rank 전체에 정렬된 카운터를 써서 N번째 엔진 스텝마다만 prefill 작업을 받아들인다. 그러면 prefill 작업이 rank들에 걸쳐 같은 스텝으로 모이고, 나머지 스텝 중 전적으로 decode에만 쓰이는 비율이 올라간다.

Right: with an interval of 4, prefills coalesce onto the cadence steps and the steps in between are decode-only.Figure 10: DEP8 그룹에서의 prefill 스케줄 주기. 왼쪽: prefill이 서로 다른 스텝에 도착해 lockstep 그룹을 반복적으로 멈춘다. 오른쪽: interval을 4로 두면 prefill이 주기 스텝으로 모이고 그 사이 스텝들은 decode 전용이 된다.

6Scaling with optimal P/D disaggregation configurations최적 P/D 분리 구성으로 확장하기

Optimizing a single engine is not enough to find the best latency-cost point for a distributed deployment, and more GPUs or disaggregation will not automatically improve the frontier. The prefill and decode stages must be rate-matched.

분산 배포에서 최적 지연-비용 지점을 찾는 데는 엔진 하나를 최적화하는 것으로 충분하지 않고, GPU를 더 넣거나 분리한다고 해서 프론티어가 자동으로 개선되지도 않는다. prefill 단계와 decode 단계는 처리율이 서로 맞아야(rate-matched) 한다.

We use a standardized two-phase rate-matching methodology that can be automated by an agentic workflow:

에이전트 워크플로로 자동화할 수 있는, 표준화된 2단계 rate-matching 방법론을 쓴다:

Phase 1 · Saturation profiling1단계 · 포화 프로파일링

8The bitter lessons: where we failed and what we learned쓰라린 교훈 — 어디서 실패했고 무엇을 배웠나

Every failed idea narrows the search space. We observed several cases where plausible intuitions did not survive end-to-end measurement.

실패한 아이디어 하나하나가 탐색 공간을 좁힌다. 그럴듯한 직관이 end-to-end 측정에서 살아남지 못한 경우가 몇 있었다.

① Pipeline parallelism (PP) does not fit warm agentic turns① Pipeline parallelism(PP)은 따뜻한 agentic 턴에 맞지 않는다

PP, including chunked pipeline parallelism (CPP), performs well on long, fresh prompts. Large prefills provide enough work to keep pipeline stages occupied, and throughput can scale nearly linearly with little communication cost.

chunked pipeline parallelism(CPP)을 포함한 PP는 길고 새로운 프롬프트에서 잘 동작한다. 큰 prefill은 파이프라인 단계들을 채울 만큼 일감을 주고, 통신 비용이 적어 처리량이 거의 선형으로 확장된다.

Most agentic turns, however, already have system prompts and previous turns cached, and each new request may add only a few hundred or a few thousand tokens. There is not enough fresh computation to fill the pipeline efficiently, and pipeline bubbles consume much of the potential gain.

그런데 대부분의 agentic 턴은 시스템 프롬프트와 이전 턴이 이미 캐시돼 있고, 새 요청마다 붙는 건 수백 내지 수천 토큰뿐일 수 있다. 파이프라인을 효율적으로 채울 만큼의 새 연산이 없고, 파이프라인 버블이 잠재 이득의 상당 부분을 먹는다.

The lesson is not that PP is ineffective. It is effective for cold, compute-heavy prefills, but it should not be the default for warm, prefix-heavy turns that dominate agentic sessions.

교훈은 PP가 쓸모없다는 게 아니다. 차갑고 연산이 무거운 prefill에는 효과적이지만, agentic 세션을 지배하는 따뜻하고 prefix 위주인 턴에서는 기본값이어서는 안 된다는 것이다.

② Decode context parallelism (DCP) does not transfer cleanly to DeepSeek V4② DCP는 DeepSeek V4로 깔끔하게 옮겨지지 않는다

DCP works well for pure MLA models (e.g., DeepSeek R1, Kimi K2.5, and K2.7) and hybrid MLA models (e.g., Kimi K3). However, realizing a similar benefit for DeepSeek V4 is considerably harder because of its more complex attention stack. The compressed sparse attention and highly compressed attention include an indexer, an additional compressor, and the main attention operation. Context parallelism must partition and coordinate all of these sublayers, introducing substantial communication and implementation complexity.

DCP는 순수 MLA 모델(DeepSeek R1, Kimi K2.5·K2.7)과 hybrid MLA 모델(Kimi K3)에서 잘 동작한다. 그런데 DeepSeek V4에서 비슷한 이득을 내는 것은 훨씬 어렵다 — 어텐션 스택이 더 복잡하기 때문이다. compressed sparse attention과 highly compressed attention은 indexer, 추가적인 compressor, 그리고 주 어텐션 연산을 포함한다. context parallelism은 이 서브레이어들을 전부 분할하고 조율해야 하고, 그 과정에서 상당한 통신·구현 복잡도가 생긴다.

We invested heavily in overlapping communication with computation and in optimizing the corresponding kernels. Even after those improvements, DCP only matched DEP rather than surpassing it. The result reinforces a broader point: parallelism must follow model architecture. A strategy that succeeds for one latent-attention model may not generalize to another.

통신과 연산을 겹치는 데, 그리고 해당 커널을 최적화하는 데 많이 투자했다. 그 개선들 이후에도 DCP는 DEP를 넘어서지 못하고 겨우 맞먹는 수준이었다. 이 결과는 더 큰 논점을 강화한다 — 병렬화는 모델 아키텍처를 따라야 한다. 어떤 latent-attention 모델에서 성공한 전략이 다른 모델로 일반화되지 않을 수 있다.

③ Load balance does not guarantee better performance③ 부하 균형이 더 나은 성능을 보장하지 않는다

In aggregated DEP deployments, we observed substantial imbalance in KV cache usage across ranks. The natural response was to balance requests according to queue depth, running tokens, or current KV utilization.

집계된 DEP 배포에서 rank 간 KV 캐시 사용량에 상당한 불균형을 관측했다. 자연스러운 대응은 큐 깊이, 실행 중 토큰 수, 현재 KV 사용률에 따라 요청을 균형 잡는 것이었다.

However, in our experiments with AgentX, all of these policies underperformed simple session-aware sticky routing. The reason is cache locality: many agentic sessions have short inter-turn delays, so the next turn frequently arrives while its prefix is still resident on the previous GPU. Moving the session to a less-loaded rank forces the system to retrieve the KV cache, even though the prefix is preserved in the distributed KV cache pool. The transfer is asynchronous and overlaps with computation, but it is not free. Prefetched blocks temporarily occupy GPU KV cache capacity, reducing the number of sequences the destination rank can admit. The system can therefore achieve a more balanced queue while processing fewer concurrent requests overall.

그런데 AgentX 실험에서는 이 정책들 모두가 단순한 세션 인식 sticky 라우팅보다 못했다. 이유는 캐시 지역성이다. 많은 agentic 세션은 턴 간 간격이 짧아서, 다음 턴이 자기 prefix가 아직 이전 GPU에 상주해 있는 동안 도착하는 일이 잦다. 세션을 덜 바쁜 rank로 옮기면 — prefix가 분산 KV 캐시 풀에 보존돼 있더라도 — 시스템이 KV 캐시를 가져와야 한다. 그 전송은 비동기이고 연산과 겹치지만 공짜가 아니다. 프리페치된 블록이 GPU KV 캐시 용량을 일시적으로 차지해 목적지 rank가 받을 수 있는 시퀀스 수를 줄인다. 그래서 시스템은 큐는 더 균형 잡히는데 전체적으로는 더 적은 동시 요청을 처리하는 상태가 될 수 있다.

For workloads with short inter-turn delays, preserving session locality is more valuable than perfectly balancing instantaneous load. Routing decisions must account for the state already resident on each worker, not only the amount of queued work. 턴 간 간격이 짧은 워크로드에서는 세션 지역성을 지키는 것이 순간 부하를 완벽히 균형 잡는 것보다 값어치가 크다. 라우팅 결정은 큐에 쌓인 작업량만이 아니라 각 워커에 이미 상주해 있는 상태를 함께 고려해야 한다.

9The path ahead: planned optimizations and future work앞으로의 길 — 계획된 최적화와 향후 과제

The next step is to make agentic structure explicit throughout the serving stack.

다음 단계는 agentic 구조를 서빙 스택 전반에서 명시적으로 만드는 것이다.

In the control plane, we can make routing more explicit for first-turn requests, which tend to need long fresh prefills to fill up the prefix cache, and turn 2+ requests, which get high cache reuse and relatively short append prefill. This separation avoids head-of-line blocking and lets us configure engine setups and parallelism differently on each side, for example with PCP and CPP, to maximize efficiency on both.

제어 플레인에서는 첫 턴 요청과 2턴 이후 요청에 대해 라우팅을 더 명시적으로 만들 수 있다. 첫 턴은 prefix 캐시를 채우기 위해 길고 새로운 prefill이 필요한 편이고, 2턴 이후는 캐시 재사용률이 높고 append prefill이 비교적 짧다. 이 분리는 head-of-line blocking을 피하게 하고, 양쪽에 엔진 구성과 병렬화를 다르게 — 예컨대 PCP와 CPP로 — 설정해 각각의 효율을 극대화할 수 있게 한다.

In the execution plane and data plane, we are working with the community to support:

실행 플레인과 데이터 플레인에서는 커뮤니티와 함께 다음을 지원하려 한다:

  • Agent hints. Agentic frameworks or harnesses could carry hints along with the requests, such as session structure, potential branching points and cache positions, tool-call latencies, or session lifecycle. Our first step is to consume these hints through standardized APIs, and then use them to guide the engine on scheduling, cache eviction policies, and other optimizations.
  • Programmable KV cache. Different workloads require different placement, retention, replication, and eviction policies. A programmable interface would let users control prefetching, eviction, or soft-pinning of KV caches to match their workload patterns.
  • Session-based KV cache management. Inter-turn gaps create an opportunity to move the retained KV state toward the worker likely to serve the next turn. Prefetching during this idle interval can hide transfer latency and reduce cold resumptions.
  • Agent hints. agentic 프레임워크나 하네스가 요청과 함께 힌트를 실어 보낼 수 있다 — 세션 구조, 분기 가능 지점과 캐시 위치, 도구 호출 지연, 세션 수명주기 같은 것들. 첫 단계는 표준화된 API로 이 힌트를 받아들이는 것이고, 그다음 이를 써서 스케줄링·캐시 eviction 정책·기타 최적화를 엔진에 안내하는 것이다.
  • Programmable KV cache. 워크로드마다 필요한 배치·보존·복제·eviction 정책이 다르다. 프로그래밍 가능한 인터페이스가 있으면 사용자가 자기 워크로드 패턴에 맞춰 KV 캐시의 프리페치·eviction·soft-pinning을 제어할 수 있다.
  • Session 기반 KV 캐시 관리. 턴 간 간격은 보존된 KV 상태를 다음 턴을 서빙할 가능성이 높은 워커 쪽으로 옮길 기회를 만든다. 이 유휴 구간에 프리페치하면 전송 지연을 숨기고 cold 재개를 줄일 수 있다.

GLM-5.2 is 744B/40B and keeps full MLA on every layer, sparsifying which tokens to attend to with a shared learned indexer, over a smaller 256-expert standard MoE, text-only. Kimi K3 does the opposite: it replaces most attention with linear KDA — a fixed-size recurrent state — over an 896-expert latent-MoE.

이 사실 하나가 무엇을 채택하고 무엇을 건너뛸지를 대부분 결정합니다. GLM-5.2는 744B/40B이고 모든 레이어에 full MLA를 유지하면서, 공유 학습 indexer로 어느 토큰에 어텐션할지를 희소화합니다. 그 아래는 더 작은 256-expert 표준 MoE이고 텍스트 전용입니다. Kimi K3는 정반대로 어텐션 대부분을 선형 KDA(고정 크기 순환 상태)로 대체하고 896-expert latent-MoE 위에 올립니다.

So when the post says "DCP works for K3 but not V4 because of the indexer and compressor", GLM-5.2 sits on the V4 side of that line. And when it says "session-aware retention is needed for hybrid models with linear or sliding-window layers", GLM-5.2 sits on the other side — it has no recurrent state to checkpoint.

그래서 원문이 "DCP는 K3에서는 되고 V4에서는 안 되는데 indexer와 compressor 때문"이라고 말할 때, GLM-5.2는 그 선의 V4 쪽에 있습니다. 그리고 "session-aware 보존은 linear/sliding-window 레이어를 가진 hybrid 모델에 필요하다"고 말할 때, GLM-5.2는 반대 쪽에 있습니다 — 체크포인트할 순환 상태가 없습니다.

10.3 — The cache point you guessed at — right instinct, different mechanism10.3 — 짚으신 캐시 지점 — 직관은 맞고 메커니즘이 다르다

You guessed the applicable part would be cache-side. It is — but not the retention machinery the post spends most of its cache section on. That one needs a recurrent state GLM-5.2 doesn't have (point E). GLM-5.2's cache problem is a different one, and it is arguably harder:

적용될 부분이 캐시 쪽이라고 짚으셨습니다. 맞습니다 — 다만 원문이 캐시 절의 대부분을 쓴 그 보존 장치는 아닙니다. 그건 GLM-5.2에 없는 순환 상태를 필요로 합니다(포인트 E). GLM-5.2의 캐시 문제는 다른 것이고, 어쩌면 더 어렵습니다:

Sparse attention sparsifies compute, not capacity. Because the top-k token selection changes as generation proceeds, the full KV history must stay resident — you cannot evict what the next step might select. So sparse serving becomes capacity-bound rather than compute-bound, and HBM caps the batch size. That is our HiSparse note's opening argument, and GLM-5.x is one of its named targets. 희소 어텐션은 연산을 희소화하지만 용량은 희소화하지 않습니다. top-k 토큰 선택이 생성이 진행되며 바뀌므로 전체 KV 히스토리가 상주해 있어야 합니다 — 다음 스텝이 고를 수 있는 것을 미리 버릴 수 없습니다. 그래서 희소 서빙은 연산 바운드가 아니라 용량 바운드가 되고, HBM이 배치 크기를 막습니다. 우리 HiSparse 노트의 첫 논증이 정확히 이것이고, GLM-5.x가 그 대상 모델로 거명됩니다.

Now put the AgentX shape on top of that: median 142K input × 43 turns per session, with the session's KV needing to survive the inter-turn gap. Per-session KV is large and long-lived, and none of it can be dropped because the indexer might reach for any of it. Capacity is the concurrency limit, which is exactly what our conc-128/256 SLO failures would look like once the context is 142K instead of 8K.

여기에 AgentX 모양을 올려 보면: 세션당 입력 중앙값 142K × 43턴이고, 그 세션의 KV가 턴 간 간격을 버텨야 합니다. 세션당 KV가 크고 동시에 오래 살며, indexer가 그중 아무 것에나 손을 뻗을 수 있으니 어느 것도 버릴 수 없습니다. 용량이 곧 동시성 한계이고, 컨텍스트가 8K가 아니라 142K가 되면 우리 conc 128·256 SLO 실패가 바로 그 모습일 것입니다.

So the two levers that matter for GLM-5.2 are the two the post frames as capacity work, not retention work:

따라서 GLM-5.2에 중요한 레버는, 원문이 보존 작업이 아니라 용량 작업으로 분류한 그 둘입니다:

  • Hierarchical offload via Mooncake standalone-store mode — an external Mooncake client owns the CPU pool and disk tier, vLLM workers become pure requesters, and the pool expands with CPU-only nodes. This is the capacity lever, and we already have the Mooncake/vLLM material to build on.
  • HiSparse-style hot-buffer decode — keep a small hot KV buffer on the GPU, push the full history to host pinned RAM, and pull back each step's top-k. This attacks the same capacity wall from the engine side.
  • Mooncake standalone-store 모드를 통한 계층적 오프로드 — 외부 Mooncake 클라이언트가 CPU 풀과 디스크 tier를 소유하고, vLLM 워커는 순수 요청자가 되며, CPU 전용 노드로 풀을 확장합니다. 이게 용량 레버이고, 기반으로 삼을 Mooncake/vLLM 자료를 이미 갖고 있습니다.
  • HiSparse식 hot-buffer decode — GPU에는 작은 hot KV 버퍼만 두고, 전체 히스토리를 호스트 pinned RAM으로 밀어낸 뒤 매 스텝의 top-k를 다시 불러옵니다. 같은 용량 벽을 엔진 쪽에서 공격합니다.
Upstream is going exactly there, which is a useful signal: the post published immediately after this one is "GLM 5.3 Optimizations, Part 1: Hybrid HiSparse Offloading in vLLM". If we are going to invest on the cache side for GLM, that is the thread to follow rather than re-deriving it ourselves. 업스트림이 정확히 그쪽으로 가고 있다는 게 유용한 신호입니다 — 이 글 바로 다음에 게시된 글이 "GLM 5.3 Optimizations, Part 1: Hybrid HiSparse Offloading in vLLM"입니다. GLM 쪽에서 캐시에 투자할 거라면, 직접 다시 유도하는 대신 그 줄기를 따라가는 게 맞습니다.

10.4 — What does not transfer10.4 — 옮겨오지 않는 것

  • The absolute numbers. All of the post's figures are GB300/B300. We are on MI355X. TPGS, TCO and the 14.6–106× cost multiples do not carry over; the methodology and the architecture arguments (D, E) do.
  • The flags, until verified. --long-prefill-token-threshold and --prefill-schedule-interval are upstream vLLM flags. Whether they exist in the Moreh vLLM build we benchmarked is an open question, not an assumption.
  • Their P/D ratios. Rate-matching is a per-model, per-hardware result. The two-phase method is what we take.
  • 절대 수치. 원문의 모든 수치는 GB300/B300입니다. 우리는 MI355X입니다. TPGS·TCO와 14.6~106배 비용 배수는 옮겨오지 않습니다. 방법론과 아키텍처 논증(D·E)이 옮겨옵니다.
  • 플래그는 확인 전까지 유보. --long-prefill-token-threshold와 --prefill-schedule-interval은 업스트림 vLLM 플래그입니다. 우리가 벤치마크한 Moreh vLLM 빌드에 있는지는 가정이 아니라 열린 질문입니다.
