one-line summary한 줄 요약 vLLM manages the KV cache as a pool of fixed-size blocks (default 16 tokens each) on the CPU-side engine. At startup it runs a memory profiling pass to decide how many blocks fit — roughly num_blocks ≈ (gpu_mem_util × total − weights − peak_activation − overhead) ÷ (per-block bytes × layers-per-block) — and builds a BlockPool: an array of block objects plus a doubly-linked free queue used as an LRU. Each request gets a block table (req_to_blocks, one list of blocks, shared across all layers). Every step, allocate_slots pulls just enough new blocks (cdiv(tokens, 16) − len(blocks)) from the pool; if there aren't enough, it returns None and the request is preempted. Blocks are reference-counted — a block is free ⇔ ref_cnt 0 and sitting in the queue. Prefix caching hashes full blocks so two requests with the same prefix point their block tables at the same physical blocks (refcount > 1); a partial hit triggers copy-on-write. Freed blocks go back to the queue — un-hashed to the front (evict first), hashed to the tail (linger as cache) until reused. vLLM은 KV 캐시를 CPU 쪽 엔진에서 고정 크기 block(기본 16 토큰) 풀로 관리한다. 시작 시 메모리 프로파일링으로 block을 몇 개 담을지 정하고 — 대략 num_blocks ≈ (gpu_mem_util × 전체 − 가중치 − 피크 활성 − 오버헤드) ÷ (block당 바이트 × block당 레이어수) — BlockPool을 만든다: block 객체 배열 + LRU로 쓰는 이중 연결 free 큐. 각 요청은 block table(req_to_blocks, block 리스트 하나, 전 레이어 공유)을 갖는다. 매 스텝 allocate_slots가 딱 필요한 만큼 새 block(cdiv(토큰, 16) − len(blocks))을 풀에서 당기고; 부족하면 None을 반환해 요청이 선점(preempt)된다. block은 참조 카운트된다 — free ⇔ ref_cnt 0 이고 큐에 있음. Prefix 캐싱은 꽉 찬 block을 해시해, 같은 prefix의 두 요청이 block table로 같은 물리 block을 가리키게 한다(refcount > 1); 부분 일치는 copy-on-write. 반납된 block은 큐로 — 해시 없으면 앞(먼저 축출), 해시 있으면 뒤(캐시로 잔류)에 붙어 재사용될 때까지 남는다.

1Two planes — the engine owns blocks, the kernel just reads them두 평면 — 엔진이 block을 소유하고, 커널은 읽기만

The confusion people hit (including in the discussion that prompted this note) is that "PagedAttention" mixes two very different jobs under one name. Split them and everything clarifies: 사람들이 부딪히는 혼란(이 노트를 촉발한 대화 포함)은 "PagedAttention"이 한 이름 아래 아주 다른 두 일을 섞는다는 것. 나누면 전부 명확해진다:

Control plane (this note)컨트롤 플레인 (이 노트)

The engine, on the CPU: it owns the pool of physical blocks, allocates them to requests, reference-counts them, shares them for common prefixes, evicts, and builds each request's block table. This is KVCacheManager + BlockPool.CPU의 엔진: 물리 block 풀을 소유하고, 요청에 할당하고, 참조 카운트하고, 공통 prefix에 공유하고, 축출하고, 요청별 block table을 만든다. KVCacheManager + BlockPool.

Data plane (the other note)데이터 플레인 (다른 노트)

The attention kernel, on the GPU: it just reads the block table the engine built and gathers the scattered KV. It never allocates or frees a block. That's the PagedAttention v1/v2 note.GPU의 어텐션 커널: 엔진이 만든 block table을 읽어 흩어진 KV를 모을 뿐. block을 할당하거나 해제하지 않는다. 그게 PagedAttention v1/v2 노트.

So yes — blocks are absolutely managed at the engine level. Everything below is the CPU-side control plane in vLLM's "V1" engine. The code is Apache-2.0 and lives almost entirely in vllm/v1/core/. Four objects do the work: the BlockPool (owns all blocks), the per-attention-type SingleTypeKVCacheManager (owns each request's block list), the KVCacheCoordinator (fans out across attention types), and the KVCacheManager (the front door the scheduler calls). We'll build them up in the order a block's life actually flows: how many exist → the pool → allocate → cache/share/evict → look up. 그러니 맞다 — block은 분명히 엔진 레벨에서 관리된다. 아래 전부가 vLLM "V1" 엔진의 CPU 쪽 컨트롤 플레인이다. 코드는 Apache-2.0이고 거의 전부 vllm/v1/core/에 있다. 네 객체가 일한다: BlockPool(모든 block 소유), 어텐션 타입별 SingleTypeKVCacheManager(요청별 block 리스트 소유), KVCacheCoordinator(어텐션 타입 간 분배), KVCacheManager(스케줄러가 부르는 정문). block의 생애가 실제 흐르는 순서로 쌓아 올린다: 몇 개 있나 → 풀 → 할당 → 캐시/공유/축출 → 조회.

2How many blocks does the engine get? (the memory math)엔진은 block을 몇 개 갖나? (메모리 계산)

The block count isn't a config knob you set directly — the engine measures it at startup. The logic is: take a slice of the GPU's memory, subtract everything that isn't KV cache, and divide the rest by the size of one block. block 개수는 직접 설정하는 노브가 아니다 — 엔진이 시작 시 측정한다. 로직은: GPU 메모리의 일부를 떼고, KV 캐시가 아닌 모든 것을 빼고, 남은 걸 block 하나의 크기로 나눈다.

Fig 1 — Deciding num_blocks. The engine caps memory at gpu_memory_utilization × total, subtracts model weights + peak activation + non-torch + a CUDA-graph reserve (measured by a real profiling forward pass), then divides the remainder by one block's size × layers-per-block. Original diagram; logic per gpu_worker.py / kv_cache_utils.py.그림 1 — num_blocks 결정. 엔진은 gpu_memory_utilization × 전체로 메모리를 상한 잡고, 모델 가중치 + 피크 활성 + non-torch + CUDA-graph 예약(실제 프로파일링 forward로 측정)을 뺀 뒤, 나머지를 block 하나 크기 × block당 레이어수로 나눈다. 직접 작성한 다이어그램; 로직 출처 gpu_worker.py / kv_cache_utils.py.

The three steps, in code세 단계, 코드로

Step A — the byte budget. Cap the GPU memory at the utilization fraction, then subtract everything that isn't KV cache. What counts as "not KV" is measured during a profiling forward pass — model weights and non-torch allocations (captured as total_consumed) plus the peak transient activation (transient_peak_headroom): Step A — 바이트 예산. GPU 메모리를 utilization 비율로 상한 잡고, KV 캐시가 아닌 모든 걸 뺀다. "KV가 아닌 것"은 프로파일링 forward 중에 측정된다 — 모델 가중치 + non-torch 할당(total_consumed) + 피크 일시 활성(transient_peak_headroom):

# vllm/v1/worker/gpu_worker.py:544
available_kv_cache_memory_bytes = (
    requested_memory                       # ceil(total × gpu_memory_utilization)
    - profile_result.non_kv_cache_memory   # weights + non-torch + peak activation
    - cudagraph_memory_estimate_applied)

Step B — one block's size. For standard attention a block holds block_size tokens, times 2 (K and V), times the KV heads and head dimension, times the dtype size: Step B — block 하나 크기. 표준 어텐션에서 block은 block_size 토큰 × 2(K와 V) × KV head × head 차원 × dtype 크기를 담는다:

# vllm/v1/kv_cache_interface.py:203  (real_page_size_bytes)
return 2 * self.block_size * self.num_kv_heads * head_dim * get_dtype_size(self.dtype)

Step C — bytes → blocks. Divide the budget by the per-block size — and, importantly, by the number of layers, because one logical block index is stacked across every layer in the group (that's why the naive "budget ÷ page_size" is off by a factor of num_layers): Step C — 바이트 → block. 예산을 block당 크기로 나누고 — 중요하게 — 레이어 수로도 나눈다. 하나의 논리 block 인덱스가 그룹의 모든 레이어에 걸쳐 쌓이기 때문(그래서 순진한 "예산 ÷ page_size"는 num_layers배 어긋난다):

# vllm/v1/core/kv_cache_utils.py:1008
num_blocks = int(available_memory // page_size // num_layers)

The finalized count lands in KVCacheConfig.num_blocks, is clamped to the minimum across tensor/pipeline-parallel workers (so every rank agrees), and can be forced with --num-gpu-blocks-override. The default block size is 16: 확정된 개수는 KVCacheConfig.num_blocks에 들어가고, tensor/pipeline 병렬 워커 간 최솟값으로 클램프되며(모든 rank 합의), --num-gpu-blocks-override로 강제 가능. 기본 block 크기는 16:

DEFAULT_BLOCK_SIZE: ClassVar[int] = 16

3The BlockPool — physical blocks & the free-block LRU queueBlockPool — 물리 block과 free-block LRU 큐

Once the engine knows it has, say, num_blocks blocks, it creates that many block objects and threads the free ones onto a queue. A block object is pure bookkeeping — a block_id (its slot number in the GPU KV tensors), a reference count, an optional content hash, and two pointers so it can live in a linked list: 엔진이 num_blocks개 block을 가진다는 걸 알면, 그만큼 block 객체를 만들고 free한 것들을 큐에 엮는다. block 객체는 순수 장부다 — block_id(GPU KV 텐서에서의 슬롯 번호), 참조 카운트, 선택적 콘텐츠 해시, 그리고 연결 리스트에 살 수 있게 하는 포인터 둘:

# vllm/v1/core/kv_cache_utils.py:117
@dataclass(slots=True)
class KVCacheBlock:
    block_id: int
    ref_cnt: int = 0
    _block_hash: BlockHashWithGroupId | None = None
    prev_free_block: "KVCacheBlock | None" = None
    next_free_block: "KVCacheBlock | None" = None
    is_null: bool = False

The free blocks live in a FreeKVCacheBlockQueue — a hand-rolled doubly-linked list (with fake head/tail sentinels) used as an LRU. Why not a plain Python list or deque? Because vLLM needs O(1) removal from the middle (when a cached block in the queue gets a prefix-cache hit, it must be pulled out of the free list without a linear scan), and it allocates no per-op Python objects. The two ends have distinct meaning: free block들은 FreeKVCacheBlockQueue에 산다 — LRU로 쓰는 손수 만든 이중 연결 리스트(가짜 head/tail 센티널). 왜 그냥 리스트나 deque가 아니라? vLLM은 중간에서 O(1) 제거가 필요하고(큐에 있던 캐시 block이 prefix 히트를 받으면 선형 스캔 없이 free 리스트에서 빼야 함), op마다 Python 객체를 할당하지 않기 때문. 양 끝은 뜻이 다르다:

Fig 2 — The free-block queue. Allocation pops from the head (evict-first); freed blocks are appended by hash-status — hashless to the front (reuse/evict first), hashed to the tail so they linger as prefix-cache candidates. A cached block that gets a prefix hit is removed from the middle in O(1). Original diagram; per block_pool.py & kv_cache_utils.py.그림 2 — free-block 큐. 할당은 head에서 pop(먼저 축출); 반납 block은 해시 상태로 붙임 — 해시 없으면 앞(먼저 재사용/축출), 해시 있으면 뒤에 붙어 prefix 캐시 후보로 잔류. prefix 히트를 받은 캐시 block은 중간에서 O(1)로 제거. 직접 작성한 다이어그램; 출처 block_pool.py & kv_cache_utils.py.

The BlockPool ties it together: it builds every block, wraps them in the free queue, keeps the prefix-cache map, and reserves block 0 as a null block (a shared placeholder for "no real block here," e.g. masked-out sliding-window positions): BlockPool이 묶는다: 모든 block을 만들고, free 큐로 감싸고, prefix 캐시 맵을 두고, block 0을 null block으로 예약한다(공유 자리표시자 — "여기 진짜 block 없음", 예: 마스킹된 sliding-window 위치):

# vllm/v1/core/block_pool.py:175
self.blocks = [KVCacheBlock(idx) for idx in range(num_gpu_blocks)]
self.free_block_queue = FreeKVCacheBlockQueue(self.blocks)
self.cached_block_hash_to_block = BlockHashToBlockMap()   # the prefix cache
self.null_block = self.free_block_queue.popleft()
self.null_block.is_null = True

Allocating fresh blocks is just pop N from the front, evict any stale cached content on those slots, and bump their refcount to 1: 새 block 할당은 그저 앞에서 N개 pop, 그 슬롯의 낡은 캐시 내용을 축출, refcount를 1로 올림:

# vllm/v1/core/block_pool.py:661  (get_new_blocks)
ret = self.free_block_queue.popleft_n(num_blocks)
for block in ret:
    self._maybe_evict_cached_block(block)   # if this slot was cached, drop it
    block.ref_cnt += 1
return ret

4Allocating on every step — get_computed_blocks → allocate_slots스텝마다 할당 — get_computed_blocks → allocate_slots

The KVCacheManager is the object the scheduler calls. It doesn't touch GPU tensors — it just decides which block ids a request owns. Every scheduler step, for a request that will run, it does two things: KVCacheManager는 스케줄러가 호출하는 객체다. GPU 텐서는 건드리지 않고 — 요청이 어떤 block id를 소유하는지만 정한다. 스케줄러 스텝마다, 실행될 요청에 대해 두 가지를 한다:

Fig 3 — One scheduler step through KVCacheManager. ① a prefix-cache lookup finds already-computed blocks; the manager counts blocks for the still-uncached tokens; if the free pool (minus a reserved slice and a watermark) can't cover it, it returns None so the scheduler waits or preempts; otherwise ② it touches the reused blocks, pops fresh ones, and caches any block that just filled up. Original diagram; per kv_cache_manager.py.그림 3 — KVCacheManager를 지나는 스케줄러 한 스텝. ① prefix 캐시 조회로 이미 계산된 block을 찾고; 아직 캐시 안 된 토큰용 block 수를 세고; free 풀(예약분+워터마크 제외)이 못 덮으면 None을 반환해 스케줄러가 대기/축출; 아니면 ② 재사용 block을 touch, 새 block을 pop, 방금 꽉 찬 block을 캐시. 직접 작성한 다이어그램; 출처 kv_cache_manager.py.

① Find what's already cached. Before allocating anything, ask the prefix cache how much of this request's prompt is already sitting in blocks (from an earlier request that shared the same prefix): ① 이미 캐시된 것 찾기. 뭔가 할당하기 전에, 이 요청 프롬프트의 얼마가 이미 block에 있는지 prefix 캐시에 묻는다(같은 prefix를 공유한 이전 요청이 남긴 것):

computed_blocks, num_new_computed_tokens, num_uncached = (
    self.coordinator.find_longest_cache_hit(

② Allocate the rest — but only if there's room. The manager counts how many new blocks the uncached tokens need, and refuses (returns None) if that would eat into the reserved headroom or the admission watermark. This None is the exact hinge between "schedule" and "preempt": ② 나머지 할당 — 단, 자리가 있을 때만. 매니저는 캐시 안 된 토큰이 필요로 하는 새 block 수를 세고, 그게 예약 여유분이나 admission 워터마크를 침범하면 거부(None 반환)한다. 이 None이 "스케줄"과 "축출"을 가르는 바로 그 경첩이다:

# vllm/v1/core/kv_cache_manager.py:522
available_blocks = self.block_pool.get_num_free_blocks() - reserved_blocks
required_blocks = num_blocks_to_allocate + watermark_blocks
if required_blocks > available_blocks:
    return None                              # scheduler will wait / preempt
...
new_blocks = self.coordinator.allocate_new_blocks(...)   # popleft from pool
self.coordinator.cache_blocks(request, num_tokens_to_cache)  # hash full blocks

The watermark (default from --kv-cache-memory policy, applied only to waiting/preempted admissions) keeps a sliver of blocks free so a burst of new requests can't starve the running ones into a deadlock. 워터마크(대기/축출된 admission에만 적용)는 block을 조금 남겨둬, 신규 요청 폭주가 실행 중 요청을 굶겨 교착에 빠뜨리지 못하게 한다.

  • get_computed_blocks · allocate_slots (watermark check L522) · get_num_free_blocks

5Sharing a prefix — content hashing, reference counts & evictionprefix 공유 — 콘텐츠 해싱, 참조 카운트, 축출

This is the payoff of the paged design, and the answer to "what happens when two sequences share a prefix?" They point at the same physical block. Nothing is copied. The machinery is three pieces: a content hash per full block, a hash → block map, and a reference count per block. 이게 paged 설계의 결실이자 "두 시퀀스가 prefix를 공유하면 어떻게 되나?"의 답이다. 둘은 같은 물리 block을 가리킨다. 아무것도 복사되지 않는다. 장치는 셋: full block마다의 콘텐츠 해시, 해시 → block 맵, block마다의 참조 카운트.

Fig 4 — Prefix sharing by reference count. Two requests with the same system prompt hash to the same block ids; find_longest_cache_hit returns them and touch() raises ref_cnt to 2 — one physical copy, two readers. Here the shared prefix ends on a block boundary, so each request's divergent continuation lands in its own private tail block — this block-aligned case needs no copy (sub-block partial hits do; see below). Original diagram; per block_pool.py / single_type_kv_cache_manager.py.그림 4 — 참조 카운트로 하는 prefix 공유. 같은 시스템 프롬프트를 가진 두 요청은 같은 block id로 해시되고, find_longest_cache_hit이 그걸 돌려주며 touch()가 ref_cnt를 2로 올린다 — 물리 사본 하나, 독자 둘. 여기선 공유 prefix가 block 경계에서 끝나 각 요청의 갈라지는 뒷부분이 자기 전용 tail block으로 가므로 이 block-정렬 경우엔 복사가 필요 없다(sub-block partial hit은 필요; 아래 참조). 직접 작성한 다이어그램; 출처 block_pool.py / single_type_kv_cache_manager.py.

The hash is computed the moment a block fills up, chaining the parent block's hash with this block's token ids (so position matters — the same tokens at a different offset get a different hash). Identical prefixes therefore produce identical hash chains: 해시는 block이 꽉 차는 순간 계산되며, 부모 block 해시와 이 block의 토큰 id를 연쇄한다(그래서 위치가 중요 — 같은 토큰이라도 오프셋이 다르면 다른 해시). 따라서 동일한 prefix는 동일한 해시 사슬을 만든다:

# vllm/v1/core/kv_cache_utils.py:691  (get_request_block_hasher)
# hash(block) = hash(parent_block_hash, tuple(block_token_ids), extra_keys)

The lookup walks the request's block hashes against the cache map and returns the longest matching run of physical blocks — the "longest cache hit": 조회는 요청의 block 해시들을 캐시 맵과 대조해, 가장 긴 물리 block 연속을 돌려준다 — "longest cache hit":

# vllm/v1/core/single_type_kv_cache_manager.py:547  (find_longest_cache_hit)
# returns the longest common-prefix run of cached blocks (≤ max_length),
# null-block-padded per group; used by get_computed_blocks (§4)

Freeing and eviction are two different moments. When a request frees its blocks, each block's ref_cnt drops; at 0 the block returns to the free queue's tail — but it keeps its content and its cache entry. It is only truly evicted later, when the pool pops it off the head to satisfy a fresh allocation and calls _maybe_evict_cached_block, which drops its hash from the map: 반납과 축출은 다른 순간이다. 요청이 block을 반납하면 각 block의 ref_cnt가 내려가고; 0이 되면 free 큐 tail로 돌아간다 — 하지만 내용과 캐시 항목은 유지한다. 진짜 축출은 나중에, 풀이 새 할당을 위해 head에서 pop하며 _maybe_evict_cached_block을 불러 해시를 맵에서 지울 때 일어난다:

# vllm/v1/core/block_pool.py:679  (_maybe_evict_cached_block)
evicted_hashes = self._remove_cached_block_hashes(block)   # forget its content
# → the slot's KV is now free to be overwritten by the next allocation

That lazy eviction is exactly why prefix caching works across requests: a finished request's blocks stay reusable in the free queue until their space is actually needed. 이 지연 축출이 바로 prefix 캐싱이 요청 간에 작동하는 이유다: 끝난 요청의 block은 그 공간이 실제로 필요해질 때까지 free 큐에서 재사용 가능하게 남는다.

Where copy-on-write actually comes incopy-on-write는 정확히 어디서 나오나

In the common case, a prefix hit ends on a block boundary: whole blocks are shared read-only and each request writes only into its own newly-popped tail block (Fig 4) — no copy. But the fine-grained managers (full-attention, Mamba "align") can register a hit that ends inside a block — a partial hit. Now the shared tail block is both a cached block (ref'd by others) and the block this request must keep writing into. Writing in place would corrupt the shared copy, so vLLM does a copy-on-write: it redirects that one block slot in the request's table to a private cow_block, queues the physical copy to run on the worker, and keeps both endpoints ref-retained until it does: 흔한 경우, prefix 히트는 block 경계에서 끝난다: block 전체가 읽기전용으로 공유되고 각 요청은 자기 새 tail block에만 쓴다(그림 4) — 복사 없음. 하지만 fine-grained 매니저(full-attention, Mamba "align")는 히트가 block 내부에서 끝나는 걸 등록할 수 있다 — partial hit. 이제 공유 tail block은 캐시 block(남들이 참조)이면서 동시에 이 요청이 계속 써야 할 block이다. 제자리에 쓰면 공유본이 오염되므로, vLLM은 copy-on-write를 한다: 요청 테이블의 그 block 슬롯을 사설 cow_block으로 재지정하고, 물리 복사를 워커에서 실행하도록 큐잉하며, 복사가 끝날 때까지 양 끝 block을 참조 유지한다:

# vllm/v1/core/single_type_kv_cache_manager.py:412  (redirect partial hit → private CoW block)
req_blocks[block_idx] = cow_block                     # request now points at its private copy
self._pending_cow_copies.append((source_block, cow_block))
cow_block.ref_cnt += 1                                # retained until the worker runs the copy

So the accurate rule is: block-aligned prefix reuse is copy-free (shared read-only + refcount); a sub-block partial hit is where copy-on-write kicks in, and only in the fine-grained managers. 그러니 정확한 규칙은: block 정렬 prefix 재사용은 복사 없음(읽기전용 공유 + refcount); sub-block partial hit이 copy-on-write가 발동하는 지점이고, fine-grained 매니저에서만 그렇다.

6Looking blocks up — one block table per sequence, stacked across layersblock 조회 — 시퀀스마다 block table 하나, 레이어에 걸쳐 쌓임

Where does a request's list of blocks actually live? In the SingleTypeKVCacheManager, as a plain dict from request id to a list of blocks — the block table. There is one table per sequence per group, not one per layer: 요청의 block 목록은 실제로 어디 사나? SingleTypeKVCacheManager 안, 요청 id → block 리스트의 평범한 dict — 이게 block table이다. 시퀀스마다·그룹마다 테이블 하나이지, 레이어마다가 아니다:

# vllm/v1/core/single_type_kv_cache_manager.py:97
self.req_to_blocks: defaultdict[str, list[KVCacheBlock]] = defaultdict(list)

This is the crux of the "is the block table per layer?" question from the PagedAttention note. It is not. A single block id — say block 6 — refers to the same slot in every layer's KV tensor within its group. That's exactly why §2 divided the byte budget by num_layers: allocating one logical block consumes one slot in all of the group's layers at once. 이게 PagedAttention 노트의 "block table이 레이어마다인가?" 질문의 핵심이다. 아니다. 하나의 block id — 예: block 6 — 는 그 그룹 모든 레이어 KV 텐서의 같은 슬롯을 가리킨다. §2에서 바이트 예산을 num_layers로 나눈 게 바로 이 때문: 논리 block 하나를 할당하면 그룹의 모든 레이어에서 슬롯 하나씩을 한꺼번에 쓴다.

Fig 5 — The block table indexes every layer. One list of block ids per sequence (per group), layer-agnostic; block id 6 selects the same physical slot in layer 0, 1, 2… of the group. Original diagram; per single_type_kv_cache_manager.py & kv_cache_interface.py (KVCacheGroupSpec.layer_names).그림 5 — block table가 모든 레이어를 인덱싱한다. 시퀀스마다(그룹마다) block id 리스트 하나, 레이어 무관; block id 6은 그룹의 layer 0·1·2…에서 같은 물리 슬롯을 고른다. 직접 작성한 다이어그램; 출처 single_type_kv_cache_manager.py & kv_cache_interface.py (KVCacheGroupSpec.layer_names).

Reading it back is trivial — the manager just returns the id list (one per group): 되읽기는 간단하다 — 매니저가 id 리스트(그룹마다 하나)를 돌려줄 뿐:

# vllm/v1/core/kv_cache_manager.py:707
def get_block_ids(self, request_id: str) -> tuple[list[int], ...]:
    return self.get_blocks(request_id).get_block_ids()

If a model mixes attention types — e.g. full-attention layers plus sliding-window layers plus Mamba layers — vLLM splits them into KV-cache groups, each with its own spec and its own block table; that's why get_block_ids returns a tuple of lists. A plain transformer has exactly one group, so the tuple has one element and the mental model is simply "one block table per sequence." 모델이 어텐션 타입을 섞으면 — 예: full-attention + sliding-window + Mamba — vLLM은 이를 KV-cache 그룹으로 나누고, 각 그룹이 자체 spec과 자체 block table을 갖는다; 그래서 get_block_ids가 리스트의 튜플을 돌려준다. 평범한 transformer는 그룹이 정확히 하나라, 튜플 원소도 하나이고 멘탈 모델은 그냥 "시퀀스마다 block table 하나"다.

Editor's note — our take (not a vLLM claim)편집자 주 — 우리 관점 (vLLM의 주장 아님)

For our MI250 serving work, three of these knobs are the ones worth watching. (1) num_blocks is measured, not set — so the same YAML on two GPUs with different free memory yields different KV capacity; if you benchmark concurrency, pin gpu_memory_utilization and log the resolved num_gpu_blocks, don't assume it. (2) Prefix caching is free throughput for any workload with shared system prompts or multi-turn chat — the free-queue-as-cache means it costs nothing until memory pressure forces eviction, so a low gpu_memory_utilization silently throws that reuse away. (3) The watermark / returns-None path is where preemption lives — when we see recompute-thrashing under load, this allocation refusal, not the kernel, is the thing to instrument. The block manager is pure bookkeeping on the host; none of this is on the attention hot path, which is why it can afford content hashing and an LRU on every step. 우리 MI250 서빙 작업에선 이 노브 중 셋을 볼 만하다. (1) num_blocks는 설정이 아니라 측정된다 — 같은 YAML도 free 메모리가 다른 두 GPU에선 KV 용량이 달라진다; 동시성을 벤치할 땐 gpu_memory_utilization을 고정하고 결정된 num_gpu_blocks를 로깅하라, 가정하지 말고. (2) prefix 캐싱은 공짜 처리량이다 — 시스템 프롬프트 공유나 멀티턴 챗이면 free-큐-가-캐시 구조 덕에 메모리 압박으로 축출이 강제되기 전까진 비용이 0이라, 낮은 gpu_memory_utilization은 그 재사용을 조용히 버린다. (3) 워터마크 / None-반환 경로가 축출이 사는 곳이다 — 부하 하에서 recompute 스래싱이 보이면, 커널이 아니라 이 할당 거부를 계측해야 한다. block 매니저는 호스트에서 순수 장부질이라 어텐션 핫패스에 없고, 그래서 매 스텝 콘텐츠 해싱과 LRU를 감당할 수 있다.
