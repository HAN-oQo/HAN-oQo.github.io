All traced through vLLM's V1 core — KVCacheManager, BlockPool, and the memory-profiling path — pinned to a real commit. This is the answer to "who actually manages the blocks?": the engine does, on the CPU, and here's exactly how. PagedAttention 노트와 짝을 이루는 글이다. 그 노트가 block table을 읽는 GPU 커널을 다뤘다면, 이 글은 block을 소유하고 관리하는 엔진 쪽 장치를 다룬다. 엔진이 block을 몇 개 갖는지와 그 수를 정하는 메모리 계산부터 시작해서, 스텝마다 block을 할당하고 참조 카운트로 관리하는 방식, 공통 prefix 공유와 축출, copy-on-write, 그리고 요청의 block 리스트가 block table이 되는 과정까지 차례로 본다. vLLM V1 코어의 KVCacheManager, BlockPool, 메모리 프로파일링 경로를 실제 커밋에 고정해서 따라간다. one-line summary한 줄 요약
  • Unit. vLLM manages the KV cache as a pool of fixed-size blocks (default 16 tokens each) on the CPU-side engine.
  • How many. At startup a memory profiling pass decides how many blocks fit: roughly num_blocks ≈ (gpu_mem_util × total − weights − peak_activation − overhead) ÷ (per-block bytes × layers-per-block).
  • Pool. The BlockPool is an array of block objects plus a doubly-linked free queue used as an LRU.
  • Per request. Each request gets a block table (req_to_blocks, one list of blocks, shared across all layers).
  • Every step. allocate_slots pulls just enough new blocks (cdiv(tokens, 16) − len(blocks)) from the pool; if there aren't enough, it returns None and the request is preempted.
  • Refcount. A block is free ⇔ ref_cnt 0 and sitting in the queue.
  • Prefix caching. Full blocks are hashed, so two requests with the same prefix point their block tables at the same physical blocks (refcount > 1); a partial hit triggers copy-on-write.
  • Free. Freed blocks go back to the queue: un-hashed to the front (evict first), hashed to the tail (linger as cache) until reused.
  • 단위. vLLM은 CPU 쪽 엔진에서 KV 캐시를 고정 크기 block(기본 16 토큰)의 풀로 관리한다.
  • 개수. 시작할 때 메모리 프로파일링을 돌려 block을 몇 개 담을지 정한다. 대략 num_blocks ≈ (gpu_mem_util × 전체 − 가중치 − 피크 활성 − 오버헤드) ÷ (block당 바이트 × block당 레이어수)이다.
  • 풀. BlockPool은 block 객체 배열과, LRU로 쓰는 이중 연결 free 큐로 이루어진다.
  • 요청별. 요청마다 block table(req_to_blocks)이 하나씩 있다. block 리스트 하나를 모든 레이어가 같이 쓴다.
  • 스텝마다. allocate_slots가 필요한 만큼만 새 block(cdiv(토큰, 16) − len(blocks))을 풀에서 꺼낸다. 모자라면 None을 반환하고, 그 요청은 선점(preempt)된다.
  • 참조 카운트. ref_cnt가 0이면서 큐에 들어 있는 block만 free 상태다.
  • Prefix 캐싱. 꽉 찬 block을 해시해 두기 때문에, prefix가 같은 두 요청은 block table에서 같은 물리 block을 가리킨다(refcount > 1). 부분 일치일 때는 copy-on-write가 일어난다.
  • 반납. 반납된 block은 큐로 돌아간다. 해시가 없으면 앞쪽에 붙어 먼저 축출되고, 해시가 있으면 뒤쪽에 붙어 재사용될 때까지 캐시로 남는다.

1Two planes — the engine owns blocks, the kernel just reads them두 평면: block은 엔진이 소유하고 커널은 읽기만 한다

The confusion people hit (including in the discussion that prompted this note) is that "PagedAttention" mixes two very different jobs under one name. Split them and everything clarifies: 흔히 겪는 혼란은(이 노트를 쓰게 된 대화도 그랬다) "PagedAttention"이라는 한 이름에 성격이 전혀 다른 두 가지 일이 섞여 있어서 생긴다. 둘을 나눠 보면 정리가 된다.

Control plane (this note)컨트롤 플레인 (이 노트)

The engine, on the CPU: it owns the pool of physical blocks, allocates them to requests, reference-counts them, shares them for common prefixes, evicts, and builds each request's block table. This is KVCacheManager + BlockPool.CPU에서 도는 엔진이다. 물리 block 풀을 소유하면서 요청에 block을 할당하고, 참조 카운트를 관리하고, 공통 prefix를 공유시키고, 축출하고, 요청마다 block table을 만든다. 코드로는 KVCacheManager와 BlockPool이다.

Data plane (the other note)데이터 플레인 (다른 노트)

The attention kernel, on the GPU: it just reads the block table the engine built and gathers the scattered KV. It never allocates or frees a block. That's the PagedAttention v1/v2 note.GPU에서 도는 어텐션 커널이다. 엔진이 만든 block table을 읽어서 흩어진 KV를 모으기만 하고, block을 할당하거나 해제하지는 않는다. 이쪽은 PagedAttention v1/v2 노트에서 다뤘다.

So yes — blocks are absolutely managed at the engine level. Everything below is the CPU-side control plane in vLLM's "V1" engine. The code is Apache-2.0 and lives almost entirely in vllm/v1/core/. Four objects do the work: 결론부터 말하면 block은 분명히 엔진 레벨에서 관리한다. 이 아래는 모두 vLLM "V1" 엔진의 CPU 쪽 컨트롤 플레인 이야기다. 코드는 Apache-2.0이고 거의 전부 vllm/v1/core/에 있다. 일을 나눠 맡는 객체는 넷이다.

We'll build them up in the order a block's life actually flows: how many exist → the pool → allocate → cache/share/evict → look up. 설명은 block의 일생이 실제로 흘러가는 순서를 따른다. 몇 개 있나 → 풀 → 할당 → 캐시·공유·축출 → 조회 순이다.

2How many blocks does the engine get? (the memory math)엔진은 block을 몇 개 갖나? (메모리 계산)

The block count isn't a config knob you set directly — the engine measures it at startup. The logic is: take a slice of the GPU's memory, subtract everything that isn't KV cache, and divide the rest by the size of one block. block 개수는 사용자가 직접 정하는 노브가 아니다. 엔진이 시작할 때 측정해서 정한다. GPU 메모리에서 쓸 몫을 떼어 내고, KV 캐시가 아닌 것을 모두 뺀 다음, 남은 양을 block 하나의 크기로 나누는 방식이다.

Fig 1 — Deciding num_blocks. The engine caps memory at gpu_memory_utilization × total, subtracts model weights + peak activation + non-torch + a CUDA-graph reserve (measured by a real profiling forward pass), then divides the remainder by one block's size × layers-per-block. Original diagram; logic per gpu_worker.py / kv_cache_utils.py.그림 1 · num_blocks를 정하는 과정. 엔진은 gpu_memory_utilization × 전체 메모리를 상한으로 잡고, 실제 프로파일링 forward로 측정한 모델 가중치·피크 활성·non-torch·CUDA-graph 예약분을 뺀다. 남은 양을 block 하나 크기 × block당 레이어 수로 나눈다. 직접 그린 다이어그램이며 로직 출처는 gpu_worker.py / kv_cache_utils.py다.

The three steps, in code코드로 보는 세 단계

Step A — the byte budget. Cap the GPU memory at the utilization fraction, then subtract everything that isn't KV cache. What counts as "not KV" is measured during a profiling forward pass — model weights and non-torch allocations (captured as total_consumed) plus the peak transient activation (transient_peak_headroom): Step A · 바이트 예산. GPU 메모리를 utilization 비율로 제한하고, KV 캐시가 아닌 것을 모두 뺀다. "KV가 아닌 것"은 프로파일링 forward를 돌리면서 측정한다. 모델 가중치와 non-torch 할당(total_consumed), 그리고 순간적인 피크 활성(transient_peak_headroom)이 여기에 들어간다.

# vllm/v1/worker/gpu_worker.py:544
available_kv_cache_memory_bytes = (
    requested_memory                       # ceil(total × gpu_memory_utilization)
    - profile_result.non_kv_cache_memory   # weights + non-torch + peak activation
    - cudagraph_memory_estimate_applied)

Step B — one block's size. For standard attention a block holds block_size tokens, times 2 (K and V), times the KV heads and head dimension, times the dtype size: Step B · block 하나의 크기. 표준 어텐션이라면 block 크기는 block_size 토큰 × 2(K와 V) × KV head 수 × head 차원 × dtype 크기다.

# vllm/v1/kv_cache_interface.py:203  (real_page_size_bytes)
return 2 * self.block_size * self.num_kv_heads * head_dim * get_dtype_size(self.dtype)

Step C — bytes → blocks. Divide the budget by the per-block size — and, importantly, by the number of layers, because one logical block index is stacked across every layer in the group (that's why the naive "budget ÷ page_size" is off by a factor of num_layers): Step C · 바이트를 block 수로. 예산을 block당 크기로 나눈 뒤, 레이어 수로 한 번 더 나눈다. 이 부분이 중요하다. 논리 block 인덱스 하나가 그룹의 모든 레이어에 걸쳐 쌓이기 때문에, 단순히 "예산 ÷ page_size"로 계산하면 num_layers배만큼 틀린다.

# vllm/v1/core/kv_cache_utils.py:1008
num_blocks = int(available_memory // page_size // num_layers)

The finalized count lands in KVCacheConfig.num_blocks, is clamped to the minimum across tensor/pipeline-parallel workers (so every rank agrees), and can be forced with --num-gpu-blocks-override. The default block size is 16: 확정된 개수는 KVCacheConfig.num_blocks에 저장된다. tensor/pipeline 병렬 워커들 사이에서는 가장 작은 값으로 맞추므로 모든 rank가 같은 값을 쓴다. --num-gpu-blocks-override로 강제로 지정할 수도 있다. 기본 block 크기는 16이다.

3The BlockPool — physical blocks & the free-block LRU queueBlockPool: 물리 block과 LRU로 쓰는 free 큐

Once the engine knows it has, say, num_blocks blocks, it creates that many block objects and threads the free ones onto a queue. A block object is pure bookkeeping — a block_id (its slot number in the GPU KV tensors), a reference count, an optional content hash, and two pointers so it can live in a linked list: block이 num_blocks개라는 것이 정해지면, 엔진은 그 수만큼 block 객체를 만들고 free 상태인 것을 큐에 엮는다. block 객체는 장부일 뿐이다. block_id(GPU KV 텐서 안의 슬롯 번호), 참조 카운트, 선택적인 콘텐츠 해시, 그리고 연결 리스트에 들어가기 위한 포인터 두 개를 갖는다.

# vllm/v1/core/kv_cache_utils.py:117
@dataclass(slots=True)
class KVCacheBlock:
    block_id: int
    ref_cnt: int = 0
    _block_hash: BlockHashWithGroupId | None = None
    prev_free_block: "KVCacheBlock | None" = None
    next_free_block: "KVCacheBlock | None" = None
    is_null: bool = False

The free blocks live in a FreeKVCacheBlockQueue — a hand-rolled doubly-linked list (with fake head/tail sentinels) used as an LRU. Why not a plain Python list or deque? Because vLLM needs O(1) removal from the middle (when a cached block in the queue gets a prefix-cache hit, it must be pulled out of the free list without a linear scan), and it allocates no per-op Python objects. The two ends have distinct meaning: free block은 FreeKVCacheBlockQueue에 들어 있다. 가짜 head/tail 센티널을 둔 이중 연결 리스트를 직접 구현해서 LRU로 쓴다. 평범한 리스트나 deque를 쓰지 않는 이유는 두 가지다. 첫째, 큐에 있던 캐시 block이 prefix 히트를 받으면 선형 탐색 없이 free 리스트에서 빼내야 하므로 중간에서 O(1)로 제거할 수 있어야 한다. 둘째, 연산마다 Python 객체를 새로 만들지 않는다. 큐의 양 끝은 의미가 다르다.

Fig 2 — The free-block queue. Allocation pops from the head (evict-first); freed blocks are appended by hash-status — hashless to the front (reuse/evict first), hashed to the tail so they linger as prefix-cache candidates. A cached block that gets a prefix hit is removed from the middle in O(1). Original diagram; per block_pool.py & kv_cache_utils.py.그림 2 · free-block 큐. 할당할 때는 head에서 꺼내므로 앞쪽이 먼저 축출된다. 반납된 block은 해시 여부에 따라 위치가 갈린다. 해시가 없으면 앞에 붙어 먼저 재사용되고, 해시가 있으면 뒤에 붙어 prefix 캐시 후보로 남는다. prefix 히트를 받은 캐시 block은 중간에서 O(1)로 빠진다. 직접 그린 다이어그램이며 출처는 block_pool.py & kv_cache_utils.py다.

The BlockPool ties it together: it builds every block, wraps them in the free queue, keeps the prefix-cache map, and reserves block 0 as a null block (a shared placeholder for "no real block here," e.g. masked-out sliding-window positions): 이것들을 하나로 묶는 것이 BlockPool이다. 모든 block을 만들어 free 큐에 넣고, prefix 캐시 맵을 관리하며, block 0을 null block으로 예약해 둔다. null block은 "여기에는 실제 block이 없다"는 뜻의 공용 자리표시자로, 마스킹된 sliding-window 위치 같은 곳에 쓰인다.

# vllm/v1/core/block_pool.py:175
self.blocks = [KVCacheBlock(idx) for idx in range(num_gpu_blocks)]
self.free_block_queue = FreeKVCacheBlockQueue(self.blocks)
self.cached_block_hash_to_block = BlockHashToBlockMap()   # the prefix cache
self.null_block = self.free_block_queue.popleft()
self.null_block.is_null = True

Allocating fresh blocks is just pop N from the front, evict any stale cached content on those slots, and bump their refcount to 1: 새 block을 할당하는 과정은 단순하다. 앞에서 N개를 꺼내고, 그 슬롯에 남아 있던 오래된 캐시 내용을 축출한 뒤, refcount를 1로 올린다.

# vllm/v1/core/block_pool.py:661  (get_new_blocks)
ret = self.free_block_queue.popleft_n(num_blocks)
for block in ret:
    self._maybe_evict_cached_block(block)   # if this slot was cached, drop it
    block.ref_cnt += 1
return ret

4Allocating on every step — get_computed_blocks → allocate_slots스텝마다 할당한다: get_computed_blocks → allocate_slots

The KVCacheManager is the object the scheduler calls. It doesn't touch GPU tensors — it just decides which block ids a request owns. Every scheduler step, for a request that will run, it does two things: KVCacheManager는 스케줄러가 호출하는 객체다. GPU 텐서는 건드리지 않고, 요청이 어떤 block id를 가질지만 정한다. 스케줄러 스텝마다 실행할 요청에 대해 두 가지 일을 한다.

Fig 3 — One scheduler step through KVCacheManager. ① a prefix-cache lookup finds already-computed blocks; the manager counts blocks for the still-uncached tokens; if the free pool (minus a reserved slice and a watermark) can't cover it, it returns None so the scheduler waits or preempts; otherwise ② it touches the reused blocks, pops fresh ones, and caches any block that just filled up. Original diagram; per kv_cache_manager.py.그림 3 · KVCacheManager를 거치는 스케줄러 한 스텝. ① prefix 캐시를 조회해 이미 계산된 block을 찾고, 아직 캐시되지 않은 토큰에 필요한 block 수를 센다. free 풀(예약분과 워터마크 제외)로 감당할 수 없으면 None을 반환하고, 스케줄러는 기다리거나 다른 요청을 축출한다. 감당할 수 있으면 ② 재사용할 block을 touch하고, 새 block을 꺼내고, 방금 꽉 찬 block을 캐시에 올린다. 직접 그린 다이어그램이며 출처는 kv_cache_manager.py다.

① Find what's already cached. Before allocating anything, ask the prefix cache how much of this request's prompt is already sitting in blocks (from an earlier request that shared the same prefix): ① 이미 캐시된 부분 찾기. 할당하기 전에 먼저 prefix 캐시를 조회한다. 같은 prefix를 썼던 이전 요청이 남긴 block이 있다면, 이번 요청의 프롬프트 중 어디까지가 이미 block에 들어 있는지 알 수 있다.

② Allocate the rest — but only if there's room. The manager counts how many new blocks the uncached tokens need, and refuses (returns None) if that would eat into the reserved headroom or the admission watermark. This None is the exact hinge between "schedule" and "preempt": ② 나머지 할당(자리가 있을 때만). 매니저는 캐시되지 않은 토큰에 필요한 새 block 수를 센다. 그만큼 할당하면 예약 여유분이나 admission 워터마크를 침범하게 될 경우 거부하고 None을 반환한다. "스케줄"과 "축출"이 갈리는 지점이 바로 이 None이다.

The watermark (default from --kv-cache-memory policy, applied only to waiting/preempted admissions) keeps a sliver of blocks free so a burst of new requests can't starve the running ones into a deadlock. 워터마크는 대기 중이거나 축출됐던 요청을 다시 받아들일 때만 적용된다. block을 조금 남겨 두어서, 새 요청이 한꺼번에 몰려도 실행 중인 요청이 block을 못 받아 교착에 빠지는 일을 막는다.

5Sharing a prefix — content hashing, reference counts & evictionprefix를 공유하는 방법: 콘텐츠 해싱, 참조 카운트, 축출

This is the payoff of the paged design, and the answer to "what happens when two sequences share a prefix?" They point at the same physical block. Nothing is copied. The machinery is three pieces: a content hash per full block, a hash → block map, and a reference count per block. paged 설계가 주는 이득이 가장 잘 드러나는 부분이고, "두 시퀀스가 prefix를 공유하면 어떻게 되나?"에 대한 답이기도 하다. 두 시퀀스는 같은 물리 block을 가리키고, 아무것도 복사하지 않는다. 이를 위한 장치는 세 가지다. full block마다 붙는 콘텐츠 해시, 해시 → block 맵, 그리고 block마다 있는 참조 카운트다.

Fig 4 — Prefix sharing by reference count. Two requests with the same system prompt hash to the same block ids; find_longest_cache_hit returns them and touch() raises ref_cnt to 2 — one physical copy, two readers. Here the shared prefix ends on a block boundary, so each request's divergent continuation lands in its own private tail block — this block-aligned case needs no copy (sub-block partial hits do; see below). Original diagram; per block_pool.py / single_type_kv_cache_manager.py.그림 4 · 참조 카운트를 이용한 prefix 공유. 시스템 프롬프트가 같은 두 요청은 같은 block id로 해시된다. find_longest_cache_hit이 그 block을 돌려주고 touch()가 ref_cnt를 2로 올린다. 물리 사본은 하나인데 읽는 쪽은 둘인 셈이다. 이 예에서는 공유 prefix가 block 경계에서 끝나기 때문에, 갈라지는 뒷부분은 각자의 전용 tail block에 들어간다. 이렇게 block 경계에 맞는 경우에는 복사가 필요 없다(sub-block partial hit일 때는 필요하며, 아래에서 다룬다). 직접 그린 다이어그램이며 출처는 block_pool.py / single_type_kv_cache_manager.py다.

The hash is computed the moment a block fills up, chaining the parent block's hash with this block's token ids (so position matters — the same tokens at a different offset get a different hash). Identical prefixes therefore produce identical hash chains: 해시는 block이 꽉 차는 순간에 계산한다. 부모 block의 해시와 이 block의 토큰 id를 이어서 해시하므로 위치가 결과에 영향을 준다. 같은 토큰이라도 오프셋이 다르면 해시가 달라진다. 그래서 prefix가 같으면 해시 사슬도 똑같이 만들어진다.

# hash(block) = hash(parent_block_hash, tuple(block_token_ids), extra_keys)

The lookup walks the request's block hashes against the cache map and returns the longest matching run of physical blocks — the "longest cache hit": 조회할 때는 요청의 block 해시를 캐시 맵과 차례로 대조해서, 일치하는 물리 block이 가장 길게 이어지는 구간을 돌려준다. 이것이 "longest cache hit"이다.

# null-block-padded per group; used by get_computed_blocks (§4)

Freeing and eviction are two different moments. When a request frees its blocks, each block's ref_cnt drops; at 0 the block returns to the free queue's tail — but it keeps its content and its cache entry. It is only truly evicted later, when the pool pops it off the head to satisfy a fresh allocation and calls _maybe_evict_cached_block, which drops its hash from the map: 반납과 축출은 서로 다른 시점에 일어난다. 요청이 block을 반납하면 각 block의 ref_cnt가 줄고, 0이 되면 free 큐의 tail로 돌아간다. 하지만 이때도 내용과 캐시 항목은 그대로 남는다. 실제 축출은 나중에 일어난다. 풀이 새로 할당하려고 head에서 block을 꺼내면서 _maybe_evict_cached_block을 호출하고, 그 해시를 맵에서 지울 때다.

# vllm/v1/core/block_pool.py:679  (_maybe_evict_cached_block)
evicted_hashes = self._remove_cached_block_hashes(block)   # forget its content
# → the slot's KV is now free to be overwritten by the next allocation

That lazy eviction is exactly why prefix caching works across requests: a finished request's blocks stay reusable in the free queue until their space is actually needed. prefix 캐싱이 요청 사이에서도 동작하는 것은 이렇게 축출을 미루기 때문이다. 끝난 요청의 block은 그 공간이 정말 필요해질 때까지 free 큐에 남아 있고, 그동안은 다시 쓸 수 있다.

Where copy-on-write actually comes incopy-on-write가 실제로 일어나는 곳

In the common case, a prefix hit ends on a block boundary: whole blocks are shared read-only and each request writes only into its own newly-popped tail block (Fig 4) — no copy. But the fine-grained managers (full-attention, Mamba "align") can register a hit that ends inside a block — a partial hit. Now the shared tail block is both a cached block (ref'd by others) and the block this request must keep writing into. Writing in place would corrupt the shared copy, so vLLM does a copy-on-write: it redirects that one block slot in the request's table to a private cow_block, queues the physical copy to run on the worker, and keeps both endpoints ref-retained until it does: 대부분의 경우 prefix 히트는 block 경계에서 끝난다. 이때는 block 전체를 읽기 전용으로 공유하고, 각 요청은 새로 받은 자기 tail block에만 쓰므로 복사가 없다(그림 4). 그런데 fine-grained 매니저(full-attention, Mamba "align")는 block 안쪽에서 끝나는 히트, 즉 partial hit을 인정할 수 있다. 그러면 공유 tail block은 다른 요청이 참조하는 캐시 block이면서, 동시에 이 요청이 이어서 써야 하는 block이 된다. 그 자리에 그대로 쓰면 공유본이 망가지기 때문에 vLLM은 copy-on-write를 한다. 요청 테이블에서 해당 block 슬롯을 전용 cow_block으로 바꾸고, 물리 복사를 워커에서 실행하도록 큐에 넣고, 복사가 끝날 때까지 원본과 사본 block의 참조를 유지한다.

# vllm/v1/core/single_type_kv_cache_manager.py:412  (redirect partial hit → private CoW block)
req_blocks[block_idx] = cow_block                     # request now points at its private copy
self._pending_cow_copies.append((source_block, cow_block))
cow_block.ref_cnt += 1                                # retained until the worker runs the copy

So the accurate rule is: block-aligned prefix reuse is copy-free (shared read-only + refcount); a sub-block partial hit is where copy-on-write kicks in, and only in the fine-grained managers. 정리하면 규칙은 이렇다. block 경계에 맞는 prefix 재사용은 읽기 전용 공유와 refcount만으로 끝나므로 복사가 없다. copy-on-write는 sub-block partial hit일 때만 일어나며, 그것도 fine-grained 매니저에 한정된다.

6Looking blocks up — one block table per sequence, stacked across layersblock table은 시퀀스마다 하나이고 모든 레이어가 같이 쓴다

Where does a request's list of blocks actually live? In the SingleTypeKVCacheManager, as a plain dict from request id to a list of blocks — the block table. There is one table per sequence per group, not one per layer: 요청의 block 목록은 실제로 어디에 있을까? SingleTypeKVCacheManager 안에 요청 id를 block 리스트로 매핑하는 평범한 dict가 있는데, 이것이 block table이다. 테이블은 레이어마다가 아니라 시퀀스마다, 그룹마다 하나씩 있다.

# vllm/v1/core/single_type_kv_cache_manager.py:97
self.req_to_blocks: defaultdict[str, list[KVCacheBlock]] = defaultdict(list)

This is the crux of the "is the block table per layer?" question from the PagedAttention note. It is not. A single block id — say block 6 — refers to the same slot in every layer's KV tensor within its group. That's exactly why §2 divided the byte budget by num_layers: allocating one logical block consumes one slot in all of the group's layers at once. PagedAttention 노트에서 나온 "block table은 레이어마다 있나?"라는 질문의 답이 여기에 있다. 그렇지 않다. block 6 같은 block id 하나는 그 그룹에 속한 모든 레이어 KV 텐서의 같은 슬롯을 가리킨다. §2에서 바이트 예산을 num_layers로 나눈 이유도 이것이다. 논리 block 하나를 할당하면 그룹의 모든 레이어에서 슬롯을 하나씩 동시에 차지한다.

Fig 5 — The block table indexes every layer. One list of block ids per sequence (per group), layer-agnostic; block id 6 selects the same physical slot in layer 0, 1, 2… of the group. Original diagram; per single_type_kv_cache_manager.py & kv_cache_interface.py (KVCacheGroupSpec.layer_names).그림 5 · block table 하나로 모든 레이어를 인덱싱한다. block id 리스트는 레이어와 무관하게 시퀀스마다(그룹마다) 하나이고, block id 6은 그룹의 layer 0·1·2… 모두에서 같은 물리 슬롯을 가리킨다. 직접 그린 다이어그램이며 출처는 single_type_kv_cache_manager.py & kv_cache_interface.py (KVCacheGroupSpec.layer_names)다.

Reading it back is trivial — the manager just returns the id list (one per group): 다시 읽어 오는 것은 간단하다. 매니저가 그룹마다 하나씩 id 리스트를 돌려주면 된다.

If a model mixes attention types — e.g. full-attention layers plus sliding-window layers plus Mamba layers — vLLM splits them into KV-cache groups, each with its own spec and its own block table; that's why get_block_ids returns a tuple of lists. A plain transformer has exactly one group, so the tuple has one element and the mental model is simply "one block table per sequence." full-attention, sliding-window, Mamba처럼 어텐션 타입이 섞인 모델이라면 vLLM은 레이어를 KV-cache 그룹으로 나눈다. 그룹마다 spec과 block table이 따로 있기 때문에 get_block_ids가 리스트의 튜플을 돌려준다. 평범한 transformer는 그룹이 하나뿐이라 튜플에도 원소가 하나다. 그러니 "시퀀스마다 block table 하나"라고 이해하면 충분하다.

Editor's note — our take (not a vLLM claim)편집자 주: 우리 관점 (vLLM의 주장 아님)

For our MI250 serving work, three of these knobs are the ones worth watching. 우리 MI250 서빙 작업에서는 이 가운데 세 가지를 눈여겨볼 만하다.

  1. num_blocks is measured, not set — so the same YAML on two GPUs with different free memory yields different KV capacity; if you benchmark concurrency, pin gpu_memory_utilization and log the resolved num_gpu_blocks, don't assume it.
  2. Prefix caching is free throughput for any workload with shared system prompts or multi-turn chat — the free-queue-as-cache means it costs nothing until memory pressure forces eviction, so a low gpu_memory_utilization silently throws that reuse away.
  3. The watermark / returns-None path is where preemption lives — when we see recompute-thrashing under load, this allocation refusal, not the kernel, is the thing to instrument.
  1. num_blocks는 설정값이 아니라 측정값이다. 같은 YAML이라도 free 메모리가 다른 두 GPU에서는 KV 용량이 달라진다. 동시성을 벤치마크할 때는 gpu_memory_utilization을 고정하고, 실제로 결정된 num_gpu_blocks를 로그로 남겨야 한다. 짐작으로 넘기면 안 된다.
  2. prefix 캐싱은 공짜로 얻는 처리량이다. 시스템 프롬프트를 공유하거나 멀티턴 챗을 하는 워크로드라면, free 큐가 캐시를 겸하는 구조 덕분에 메모리 압박으로 축출이 일어나기 전까지는 비용이 들지 않는다. 그래서 gpu_memory_utilization을 낮게 잡으면 이 재사용 기회를 모르는 사이에 버리게 된다.
  3. 선점은 워터마크와 None 반환 경로에서 일어난다. 부하가 걸릴 때 recompute 스래싱이 보인다면, 커널이 아니라 이 할당 거부 지점을 계측해야 한다.

The block manager is pure bookkeeping on the host; none of this is on the attention hot path, which is why it can afford content hashing and an LRU on every step. block 매니저는 호스트에서 장부만 관리할 뿐 어텐션 핫패스에는 끼지 않는다. 그래서 매 스텝 콘텐츠 해싱과 LRU를 돌려도 감당할 수 있다.
