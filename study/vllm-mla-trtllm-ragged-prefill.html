vLLM MLA × TRT-LLM Ragged Prefill — what it is, how it works, code flow, status vLLM MLA × TRT-LLM Ragged Prefill — 무엇인지·동작 원리·코드 흐름·구현 상태

MLA models (DeepSeek-V2/V3, GLM) compress the KV cache into a small latent vector, which makes their prefill attention not a drop-in for the usual FlashAttention path — the latent has to be up-projected and the query/key vs value head dimensions are asymmetric. TrtllmRaggedPrefillBackend is one of four pluggable MLA-prefill backends in vLLM; it wraps NVIDIA's FlashInfer kernel trtllm_ragged_attention_deepseek (a TRT-LLM-gen kernel) to do MLA prefill on Blackwell (SM100) only, over variable-length ("ragged") batches packed with cumulative sequence lengths — both the chunked context pass (non-causal) and the new-tokens pass (causal). This note covers what "ragged" and "MLA prefill" mean, the mechanism, how the backend is selected (spoiler: FlashAttention still wins auto-selection), honest effects, how to turn it on, the code path with permalinks pinned to commit 4bf699d, and status. MLA 모델(DeepSeek-V2/V3, GLM)은 KV 캐시를 작은 latent 벡터로 압축한다. 그래서 prefill 어텐션이 평소의 FlashAttention 경로에 그대로 들어가지 않는다 — latent를 다시 up-project 해야 하고, query/key와 value의 head 차원이 비대칭이다. TrtllmRaggedPrefillBackend는 vLLM의 4개 pluggable MLA-prefill 백엔드 중 하나로, NVIDIA FlashInfer 커널 trtllm_ragged_attention_deepseek(TRT-LLM-gen 커널)을 감싸 Blackwell(SM100) 전용으로 MLA prefill을 한다. 가변 길이("ragged") 배치를 누적 시퀀스 길이로 패킹해 처리 — 청크 단위 context 패스(비인과)와 new-tokens 패스(인과) 둘 다. 이 노트는 "ragged"·"MLA prefill"의 의미, 메커니즘, 백엔드가 어떻게 선택되는지(스포일러: auto 선택에선 FlashAttention이 여전히 이김), 정직한 효과, 켜는 법, 커밋 4bf699d에 핀된 permalink 코드 경로, 구현 상태를 다룬다.

1What & why — MLA prefill, and what "ragged" means무엇·왜 — MLA prefill, 그리고 "ragged"의 의미

MLA: the KV cache is a compressed latentMLA: KV 캐시가 압축된 latent

Multi-head Latent Attention is DeepSeek-V2's trick for shrinking the KV cache. Instead of storing a full key and value vector for every head of every token, MLA stores one small "latent" vector per token, from which the per-head keys and values are reconstructed on demand. Multi-head Latent Attention은 KV 캐시를 줄이는 DeepSeek-V2의 트릭이다. 모든 토큰의 모든 head마다 전체 key·value 벡터를 저장하는 대신, MLA는 토큰당 작은 "latent" 벡터 하나를 저장하고, 거기서 head별 key·value를 필요할 때 복원한다.

"MLA guarantees efficient inference through significantly compressing the Key-Value (KV) cache into a latent vector."

— DeepSeek-V2 abstract · arXiv:2405.04434

That compression is what makes MLA prefill awkward for a generic attention kernel. Two consequences matter here: 바로 그 압축이 MLA prefill을 범용 어텐션 커널엔 까다롭게 만든다. 여기서 중요한 두 결과:

  • An up-projection step. Before attention can run, the cached latent must be expanded back into per-head k_nope and v through a weight kv_b_proj. A vanilla prefill kernel just reads K and V; an MLA prefill path has to produce them first. up-projection 단계. 어텐션을 돌리기 전에, 캐시된 latent를 가중치 kv_b_proj를 통해 head별 k_nope·v로 다시 펼쳐야 한다. 평범한 prefill 커널은 K·V를 읽기만 하지만, MLA prefill 경로는 그걸 먼저 만들어야 한다.
  • Asymmetric head dimensions. MLA decouples position into a small RoPE part, so a query/key head is qk_nope + qk_rope (e.g. 128+64 = 192) while the value head is only v_head_dim (e.g. 128). Many kernels assume head_dim_qk == head_dim_v; MLA breaks that. The two shapes vLLM's TRT-LLM backend supports are exactly the DeepSeek family (qk_nope 128 / rope 64 / v 128) and a larger GLM-style one (192 / 64 / 256). 비대칭 head 차원. MLA는 위치를 작은 RoPE 부분으로 분리하므로, query/key head는 qk_nope + qk_rope(예: 128+64 = 192)인데 value head는 v_head_dim(예: 128)뿐이다. 많은 커널이 head_dim_qk == head_dim_v를 가정하는데 MLA는 이를 깬다. vLLM의 TRT-LLM 백엔드가 지원하는 두 형태는 정확히 DeepSeek 계열(qk_nope 128 / rope 64 / v 128)과 더 큰 GLM류(192 / 64 / 256)다.

"Ragged" = un-padded variable-length batching"Ragged" = 무패딩 가변 길이 배칭

Prefill processes whole prompts at once, and prompts have different lengths. The naive way is to pad every sequence up to the longest and run a dense rectangular batch — wasting compute on padding. The "ragged" (a.k.a. varlen) layout instead concatenates all sequences into one flat tensor with no padding, and uses a small cumulative-length index array to find where each sequence starts and ends. FlashInfer's docs define it precisely: prefill은 프롬프트 전체를 한 번에 처리하고, 프롬프트마다 길이가 다르다. 단순한 방법은 모든 시퀀스를 가장 긴 것까지 패딩해 빽빽한 직사각형 배치를 돌리는 것 — 패딩에 연산을 낭비한다. "ragged"(=varlen) 레이아웃은 대신 모든 시퀀스를 패딩 없이 한 평평한 텐서로 이어붙이고, 작은 누적 길이 인덱스 배열로 각 시퀀스의 시작·끝을 찾는다. FlashInfer 문서가 정확히 정의한다:

"indptr[i+1]-indptr[i] is the sequence length of request i" … the indptr array has "num_requests+1 elements, the first element is always zero."

— FlashInfer, KV-Layout tutorial (Ragged Tensor) · docs.flashinfer.ai/tutorials/kv_layout

In vLLM this index array is query_start_loc — the cumulative count of query tokens per request. The TRT-LLM ragged kernel takes the flat q/k/v plus these cumulative lengths and never sees a padding token. The "deepseek" in the kernel name is because it also natively understands MLA's asymmetric qk-vs-v head dims, so the same kernel covers DeepSeek/GLM-style MLA prefill in one call. vLLM에서 이 인덱스 배열은 query_start_loc — 요청당 query 토큰의 누적 개수다. TRT-LLM ragged 커널은 평평한 q/k/v와 이 누적 길이를 받고 패딩 토큰을 전혀 보지 않는다. 커널 이름의 "deepseek"은 MLA의 비대칭 qk-vs-v head 차원도 네이티브로 이해하기 때문 — 그래서 같은 커널이 DeepSeek/GLM류 MLA prefill을 한 번의 호출로 처리한다.

2How it works — up-project the latent, two ragged passes, one kernel동작 원리 — latent up-project, ragged 두 패스, 커널 하나

vLLM's MLA prefill splits attention into two passes, both feeding the same ragged kernel with a different is_causal flag: vLLM의 MLA prefill은 어텐션을 두 패스로 나누고, 둘 다 같은 ragged 커널에 다른 is_causal 플래그로 넣는다:

  • Context-chunk pass (non-causal). If some of the prompt's KV is already cached (chunked prefill / prefix reuse), the new queries attend over that already-computed context. Because the context is entirely "in the past", this pass is not causal. vLLM walks the cached context in chunks and merges the partial results with merge_attn_states (an online-softmax / log-sum-exp merge), which is why the kernel returns the LSE alongside the output. Context-chunk 패스(비인과). 프롬프트 KV 일부가 이미 캐시됐다면(chunked prefill / prefix 재사용), 새 query가 그 이미 계산된 context를 어텐션한다. context가 전부 "과거"이므로 이 패스는 인과가 아니다. vLLM은 캐시된 context를 청크 단위로 훑고 부분 결과를 merge_attn_states(online-softmax / log-sum-exp 병합)로 합친다 — 그래서 커널이 출력과 함께 LSE를 반환한다.
  • New-tokens pass (causal). The prompt's own new tokens attend to each other with the usual causal mask. This is the is_causal=True call. New-tokens 패스(인과). 프롬프트 자신의 새 토큰들이 평소의 인과 마스크로 서로 어텐션한다. 이게 is_causal=True 호출이다.

Both passes first up-project the latent: the cached compressed KV goes through kv_b_proj to produce per-head k_nope and v, and the key is assembled as k = [k_nope | k_pe] (content part + the shared RoPE part). Then the flat ragged q/k/v + cu_seqlens go to trtllm_ragged_attention_deepseek, which handles the asymmetric qk/v head dims itself. One small bookkeeping detail the backend does: the kernel returns the log-sum-exp as (q_len, num_heads) and vLLM transposes it to (num_heads, q_len) for the merge step. 두 패스 모두 먼저 latent를 up-project 한다: 캐시된 압축 KV가 kv_b_proj를 거쳐 head별 k_nope·v를 만들고, key는 k = [k_nope | k_pe](내용 부분 + 공유 RoPE 부분)로 조립된다. 그다음 평평한 ragged q/k/v + cu_seqlens가 trtllm_ragged_attention_deepseek로 가고, 커널이 비대칭 qk/v head 차원을 스스로 처리한다. 백엔드가 하는 작은 정리 하나: 커널이 log-sum-exp를 (q_len, num_heads)로 반환하면 vLLM이 병합 단계를 위해 (num_heads, q_len)로 전치한다.

why prefill gets its own kernel — un-absorbed MLA왜 prefill엔 전용 커널이 — 비흡수 MLA MLA runs attention two different ways. Decode is memory-bound, so it "absorbs" the up-projection into the weights and runs an MQA directly over the compressed latent — cheap on memory traffic. Prefill is compute-bound (many query tokens at once), so it does the opposite — "un-absorb": expand the latent back to full per-head K/V and run ordinary MHA, which is FLOP-efficient when there are many queries. trtllm_ragged is the un-absorbed prefill path, and the up-projection in Fig 2 is exactly that un-absorption. The vLLM forum frames it as prefill being "compute-friendly" while decode is "data-movement-friendly" [vLLM forum]. MLA는 어텐션을 두 방식으로 돌린다. Decode는 메모리 바운드라 up-projection을 가중치에 "흡수"해 압축 latent 위에서 곧장 MQA를 돈다 — 메모리 트래픽이 쌈. Prefill은 연산 바운드(query 토큰이 한꺼번에 많음)라 반대로 — "비흡수": latent를 head별 전체 K/V로 다시 펼쳐 평범한 MHA를 돈다(query가 많을 때 FLOP 효율적). trtllm_ragged는 비흡수 prefill 경로이고, 그림 2의 up-projection이 바로 그 비흡수다. vLLM 포럼은 prefill을 "compute-friendly", decode를 "data-movement-friendly"로 표현한다 [vLLM forum].

Selection happens in get_mla_prefill_backend(). There are two ways in: 선택은 get_mla_prefill_backend()에서 일어난다. 들어가는 길은 둘:

  1. Explicit override — if you set the config field mla_prefill_backend=TRTLLM_RAGGED, the override branch validates it (right hardware, is_available()) and uses it. 명시적 override — 설정 필드 mla_prefill_backend=TRTLLM_RAGGED를 주면, override 분기가 검증(올바른 하드웨어, is_available()) 후 사용.
  2. Auto — otherwise it walks a hardware-specific priority list and picks the first that's available and valid. Auto — 아니면 하드웨어별 우선순위 목록을 훑어 사용 가능·유효한 첫 번째를 고른다.
the surprising part — auto-selection does NOT pick it의외의 지점 — auto 선택은 이걸 안 고른다 On Blackwell the priority order is FLASH_ATTN → TRTLLM_RAGGED → FLASHINFER → TOKENSPEED_MLA (read straight from selector.py L59-69 @ 4bf699d), and on Hopper/older the list is FLASH_ATTN only. Since FlashAttention is ranked first and is broadly valid, TRTLLM_RAGGED is never chosen in pure auto-mode unless FlashAttention is unavailable/invalid for the config. In practice you reach this kernel by explicitly selecting it (or via a config FA can't serve). So "is it used by default?" — no. (Heads-up: some vLLM docs / secondary write-ups describe TRTLLM_RAGGED as the auto-selected Blackwell MLA-prefill backend. The selector source at this commit ranks FLASH_ATTN ahead of it, so treat "auto-selected on Blackwell" as docs lagging the code.) Blackwell의 우선순위는 FLASH_ATTN → TRTLLM_RAGGED → FLASHINFER → TOKENSPEED_MLA(selector.py L59-69 @ 4bf699d에서 그대로 읽음)이고, Hopper/이전은 FLASH_ATTN만. FlashAttention이 1순위이고 폭넓게 유효하므로, 설정상 FA가 불가/무효가 아닌 한 TRTLLM_RAGGED는 순수 auto-mode에서 절대 선택되지 않는다. 실제로 이 커널엔 명시적으로 골라서 도달한다(또는 FA가 못 다루는 설정을 통해). 따라서 "기본으로 쓰이나?" — 아니다. (주의: 일부 vLLM 문서/2차 글은 TRTLLM_RAGGED를 Blackwell의 auto-선택 MLA-prefill 백엔드로 서술한다. 이 커밋의 selector 소스는 FLASH_ATTN을 그 위에 두므로, "Blackwell에서 auto-선택"은 문서가 코드보다 뒤처진 것으로 보면 된다.)

Mechanism, precisely메커니즘 정확히

One FlashInfer kernel (trtllm_ragged_attention_deepseek) serves both prefill passes — flipped by is_causal. The backend is thin: declare dims, gate on SM100 + flashinfer, reserve a workspace, build cu_seqlens, call the kernel, transpose the LSE. All the MLA-specific work (latent up-projection, k assembly, chunk merge) lives in mla_attention.py, shared across the four backends.FlashInfer 커널 하나(trtllm_ragged_attention_deepseek)가 두 prefill 패스 모두 담당 — is_causal로 전환. 백엔드는 얇다: 차원 선언, SM100 + flashinfer 게이트, workspace 예약, cu_seqlens 구성, 커널 호출, LSE 전치. MLA 고유 작업(latent up-projection, k 조립, 청크 병합)은 4개 백엔드가 공유하는 mla_attention.py에 있다.
