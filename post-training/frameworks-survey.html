1The one axis that matters핵심은 한 축

Pick a framework by where your work sits on a single spectrum: SFT / efficiency-focused (single- or few-GPU supervised & preference tuning) vs RL-at-scale (multi-node PPO/GRPO with a separate rollout engine). Some libraries sit in the middle and do both. The mistake is using a heavy RL-at-scale system for a LoRA SFT job, or a single-GPU SFT tool for a 70B GRPO run.

프레임워크는 작업이 한 스펙트럼의 어디에 있는지로 고릅니다: SFT/효율 중심(단일~소수 GPU 지도·선호 튜닝) vs 대규모 RL(별도 롤아웃 엔진을 둔 멀티노드 PPO/GRPO). 가운데서 둘 다 하는 것도 있습니다. 흔한 실수는 LoRA SFT에 무거운 대규모 RL 시스템을 쓰거나, 70B GRPO에 단일 GPU SFT 도구를 쓰는 것.

3RL-at-scale frameworks대규모 RL 프레임워크

These run PPO/GRPO/DAPO across many nodes, with a separate high-throughput rollout engine (vLLM/SGLang) and a training backend (FSDP/Megatron), often on Ray. Use when the model is large and the bottleneck is RL throughput, not the SFT loop.

이들은 PPO/GRPO/DAPO를 여러 노드에서 돌립니다 — 별도의 고처리량 롤아웃 엔진(vLLM/SGLang) + 학습 백엔드(FSDP/Megatron), 종종 Ray 위에서. 모델이 크고 병목이 SFT 루프가 아니라 RL 처리량일 때 씁니다.

new — vLLM's own: vime신규 — vLLM 자체: vime vime (created 2026-05-11) is the vLLM community's own RL post-training framework: per its README, "an LLM post-training framework for RL scaling, built on slime," keeping slime's Megatron training stack but swapping the rollout backend to vLLM (with vllm-router). So the picture is: THUDM's slime (Megatron + SGLang) → vime re-targets it onto the vLLM engine. It's young (0.24k★, no tagged release yet) but it's the canonical vLLM-ecosystem entry — worth watching since the rollout engine is the same vLLM our inference notes dissect. vime(2026-05-11 생성)는 vLLM 커뮤니티의 자체 RL 후학습 프레임워크입니다. README 표현: "slime 위에 만든, RL 스케일링용 LLM 후학습 프레임워크" — slime의 Megatron 학습 스택은 유지하되 롤아웃 백엔드를 vLLM(+vllm-router)로 교체. 즉 THUDM slime(Megatron + SGLang) → vime가 이를 vLLM 엔진에 맞춘 것. 아직 어리지만(0.24k★, 정식 릴리스 0) vLLM 생태계의 정본 진입점이라 주목할 만합니다 — 롤아웃 엔진이 우리 추론 노트가 해부하는 그 vLLM이라.

5How we'll pick우리는 어떻게 고를까

editor's note — our plan편집자 주 — 우리 계획 For learning + small experiments on our shared GPU nodes (Docker-only, per our infra rules), TRL is the right first tool — SFT, DPO, and a small GRPO/RLVR loop all in one, runs single-node. Step up to veRL or OpenRLHF only when a run needs multi-node rollout throughput. Note the serving tie-in: these RL frameworks embed vLLM/SGLang as the rollout engine — the same engines our inference notes dissect — so post-training and serving share infrastructure. 공유 GPU 노드에서의 학습 + 소규모 실험엔(인프라 규칙상 Docker 전용) TRL이 첫 도구로 적합 — SFT·DPO·작은 GRPO/RLVR 루프를 하나로, 단일 노드로 실행. 멀티노드 롤아웃 처리량이 필요할 때만 veRL/OpenRLHF로 올라갑니다. 서빙 연결고리: 이 RL 프레임워크들은 롤아웃 엔진으로 vLLM/SGLang을 내장 — 우리 추론 노트가 해부하는 바로 그 엔진들 — 이라 포스트트레이닝과 서빙이 인프라를 공유합니다.
