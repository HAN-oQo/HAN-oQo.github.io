0 먼저, 우리가 만들던 것

거대 언어모델(GLM-5)을 여러 GPU 서버에 나눠 띄워 서비스하고 있습니다. 구조는 프리필/디코드 분리(disaggregation)입니다.

  • Prefill pod — 입력 프롬프트를 한 번에 읽어 KV cache를 만드는 단계 (서버 4대 × rank 8 = 32개)
  • Decode pod — 그 뒤로 토큰을 한 개씩 생성하는 단계 (서버 2대 × rank 8 = 16개)

핵심 아이디어는 prefix cache입니다. 여러 요청이 같은 프롬프트 앞부분(예: 동일한 system prompt)을 공유하면, 이미 계산해 둔 KV cache를 재사용해 연산을 아낄 수 있습니다. 그래서 게이트웨이(라우터)가 "이 요청의 앞부분이 이미 캐시돼 있는 pod"로 보내주면 빨라집니다. 이게 prefix cache-aware 라우팅입니다.

전체 그림: 라우터가 요청마다 "어느 prefill pod이 이 prefix를 들고 있나"를 점수로 따져 보냅니다.

이 위에서 네 가지 문제가 차례로 드러났습니다. 하나씩 보겠습니다.

1 라우터를 어떻게 똑똑하게 만들까 — 로지스틱 스코어링

라우터는 후보 pod마다 점수(score)를 매겨 비교합니다. prefix_cache 스코어러가 보는 입력은 각 pod의 hit_rate — 이 요청의 앞부분 중 그 pod에 이미 캐시된 비율(0~1)입니다.

문제는 "hit_rate를 어떻게 점수로 바꿀까?"입니다. 그냥 그대로 쓰면(선형) hit_rate 0.4와 0.5의 차이나 0.9와 1.0의 차이가 똑같이 0.1이라, "거의 완벽히 겹친 pod"로 강하게 몰아주는 힘이 약합니다. 반대로 "0.93 넘으면 1, 아니면 0"으로 칼같이 자르면(계단함수) 경계에서 뚝 끊겨 불안정하고, 점수가 정확히 0이 되면 그 pod엔 트래픽이 영영 안 갑니다.

핵심 아이디어 — 로지스틱(시그모이드) 스코어링 hit_rate를 S자 곡선에 한 번 통과시켜 점수로 바꾼다. 임계값 근처에서는 민감하게 갈라주고, 양 끝에서는 부드럽게 0~1로 수렴한다.
score(h) = 1 / ( 1 + e−k · (h − x₀) )
기호의미실제 값
h그 pod의 prefix hit_rate (0~1)입력값
x₀변곡점 / 임계값. score=0.5가 되는 지점. "몇 % 겹쳐야 의미 있나"0.93
k기울기. 클수록 계단에 가까워짐1000 → 100 (후술)

곡선이 직접 보이면 이해가 빠릅니다. 아래는 x₀=0.93 고정, k만 바꾼 모습입니다.

k=20 (완만) k=100 k=500 (계단에 가까움) x₀ = 0.93
h가 0.93을 넘는 순간 점수가 솟구칩니다. 그래서 "충분히 겹친 pod"만 골라낼 수 있어요.

"점수는 절대 0이 안 된다"의 의미

수식이 1 / (1 + e^…) 꼴이라 분모가 항상 유한합니다. 즉 점수는 0에 한없이 가까워질 뿐 정확히 0이 되지 않습니다. 이게 중요한 이유 — 점수에 비례해 확률적으로 뿌리는 weighted-random picker를 쓸 때, 0이 아니어야 모든 pod에 아주 작게라도 트래픽이 갈 수 있기 때문입니다.

스코어러 + picker가 만드는 자동 동작

① 누군가 임계값을 넘으면

그 pod 점수만 1에 가깝게 압도적 → 항상 거기로 → hit 보장, miss 제거 (exploit)

② 아무도 못 넘으면

전부 점수 ≈ 0으로 비슷 → 사실상 균등 랜덤 → 부하 분산 (explore)

최종 점수는 여러 스코어러의 가중합입니다. constant는 모든 pod에 1.0을 주는 baseline(동점 처리·기본 분산용)이고, 거기에 prefix 점수를 큰 가중치로 더합니다.

# 한 요청에 대해, 후보 pod마다 점수를 계산
def score_pod(pod, req, k=100, x0=0.93):
    h = prefix_hit_rate(pod, req)          # 0 ~ 1
    prefix = 1.0 / (1.0 + math.exp(-k * (h - x0)))   # 로지스틱
    constant = 1.0                          # 모든 pod 동일
    # prefix에 절대 우위를 주되 0은 아님 → weighted-random에서도 분산 가능
    return W_PREFIX * prefix + W_CONST * constant

picked = max(pods, key=score_pod)          # max-picker
# 또는 weighted-random: score에 비례해 확률적으로 선택

강원님이 weighted-random을 선호한 이유: 노드가 죽었다 살아날 때 max-picker는 그 빈 노드를 "영구히 맛이 간 것"처럼 외면할 수 있는 반면, weighted-random은 "잠깐 느려진 것"으로 보고 회복 기회를 주기 때문입니다.

2 GPU가 6시간마다 죽는다 — 하드웨어 장애

특정 구간(ISL 64K, concurrency 16)부터 갑자기 cache miss가 터지기 시작했습니다. 처음엔 라우팅 알고리즘 문제로 의심했지만, 로그를 위로 올려보니 서버가 재부팅된 흔적이 있었습니다. dmesg에 AMD GPU 하드웨어 에러가 찍혀 있었어요.

[Sat Jun  6 04:27:07 2026] amdgpu 0000:c6:00.0: {7}uncorrectable
    hardware error (ERREVENT_ATHUB_INTERRUPT) detected!
[Sat Jun  6 04:27:07 2026] amdgpu: Couldn't get PPT limit ...

mi300-6 서버의 1번 GPU가 약 6시간에 한 번꼴로 HBM 에러로 죽는 문제였습니다. pod이 죽었다 다시 뜨면 그 안의 KV cache가 통째로 사라지므로, 재부팅 직후엔 거의 전부 cache miss가 납니다.

"16,64K부터 miss"는 알고리즘 탓이 아니라, 그 시점에 노드가 죽었다 살아난 탓이었습니다.
대응 수동으로 AMD GPU device plugin을 재시작해 살리다가, 현기님이 모니터링(Mimir)에서 10분마다 metric exporter를 보고 에러가 있으면 device plugin을 자동 재시작하도록 걸어 반자동화했습니다. 또 mi300-6을 prefix cache를 안 쓰는 decode 쪽으로 돌려, 죽어도 성능 타격을 줄이는 안도 검토했습니다.

3 로그가 거짓말을 한다 — prefix_map의 함정

디버깅을 가장 헷갈리게 만든 함정입니다. 어떤 로그는 block_count=985 (found 985, 100.0% hit)이라고 자신만만하게 찍히는데, 실제로는 cache miss가 나서 다시 계산하느라 느려지고 있었습니다. "캐시 완벽함"이라는 로그와 "사실은 miss"라는 현실이 어긋난 거예요. 원인은 pod이 들고 있는 기록이 두 종류인데, 로그가 그중 거짓말하는 쪽만 읽었기 때문입니다.

먼저 — prefix_map은 원래 뭐 하는 물건인가

오해하면 안 되는 게, prefix_map은 쓸모없는 게 아니라 prefix-aware 라우팅을 가능하게 하는 핵심 색인(카탈로그)입니다. 프롬프트를 통째로 비교하면 무거우니, 64토큰 블록으로 자르고 각 블록을 해시로 바꿔서 "어떤 프롬프트가 어떤 블록들로 쪼개지는지, 그 블록을 어느 pod이 보유했다고 보고했는지"를 기록해 둡니다. 라우터는 새 요청이 오면 이 색인을 뒤져 "캐시 가진 pod"을 찾아 보냅니다 — 즉 라우팅의 지도예요.

# prefix_map = 게이트웨이의 "프롬프트 ↔ 블록 해시" 색인
"안녕 너는…"  →  [h1, h2, h3, …]  →  pod-A, pod-C
"오늘 날씨…"  →  [h4, h5, …]      →  pod-B
# ⚠ 한 번 등록되면 그 pod이 evict 해도 지우지 않음 → 계속 쌓이기만 함

장부 ① vs 창고 ② — 핵심 그림

그래서 pod 하나를 들여다보면 사실상 기록이 두 개 있는 셈입니다. 장부①(prefix_map)은 "본 적 있는 것"을 절대 안 지우고 쌓기만 하고, 창고②(실제 KV 캐시)는 자리가 한정돼 오래된 건 버립니다(evict).

📒 장부 ① — prefix_map 로그가 읽는 곳

"내가 본 적 있는 prefix 목록". free(해제)가 안 되고 누적만 됨 → 뭘 물어봐도 "있음" → 항상 100%. "본 적 있나"에만 답할 수 있음.

📦 창고 ② — 실제 KV 캐시 진실

진짜 데이터가 든 곳. evict 이벤트로 갱신되어 줄어듦. 최신 것 몇 개만 남음 → "지금 실제 있나"에 답함.

로그는 위(장부①)를 읽어서 100%라 우기고, 실제 성능은 아래(창고②)를 따라 miss가 납니다.

그 100%는 무엇에 대한 100%인가 (분모의 정체)

퍼센트니까 전체(분모)가 있죠. 그 전체는 "그 요청 하나가 필요로 하는 블록 수"입니다. pod 캐시 용량 전체도, 데이터셋 전체도 아니고 요청마다 따로 셉니다.

# 로그의 실제 숫자로 맞춰보면
input_tokens = 63040
block_count  = 63040 ÷ 64  ≈ 985 블록     ← 이게 "전체"(분모)
found        = 985                  ← 분자

장부① 기준 hit = 985 / 985 = 100%   # "본 적 있나" → 다 있음 (거짓)
창고② 기준 hit = 165 / 985 ≈ 16.7%  # "지금 실제 있나" → 일부만 (진실)

누가 무엇을 어떻게 말했나

  1. 지민님(발견·질문) — "로그는 모든 요청에 100% hit인데 성능은 miss 같다. 이 hit율은 prefix_map 기준인데, prefix_map 정보는 free가 안 되는 값일까요?"라고 모순을 짚고 P팀에 질문.
  2. 인범님 — "prefix_map은 free가 없다. 실제인지 확인하려면 KvBlockIndex에서 그 블록 해시가 진짜 존재하는지 추가 검사가 필요하다."
  3. 봉우님(핵심 설명) — "prefix_map은 안 비워지지만 라우팅을 망가뜨리진 않는다. pod별 실제 보유 block은 별도 맵으로 추적하고 evict 이벤트로 갱신된다. 그러니 hit/miss를 진단하려면 pod별 prefix_cache 점수 컬럼(=trace hit_rate)을 봐야 한다."
  4. 지민님(자기 오해 정리) — "prefix_map은 100%인데 실제 pod은 0%대라, 유효한 블록이 여러 pod에 흩어져 있는 줄 알았다. 이 정보가 의미적으로 주는 게 있나 싶어 물었다."
  5. 강원님(개념 요약) — "그 tokens/kv 로그는 prefix_map을 보는 거고, 이건 보유 prefix의 superset 역할만 하는, 시간이 지날수록 증가만 하는 map이다. 거기서 hit%를 뽑는 건 앞으로도 misleading하겠다."
  6. 봉우님(마무리) — "맞다. prefix_map은 프롬프트↔block 매칭 map이다. 로그를 덜 헷갈리게 고칠 필요가 있겠다."

그래서 진짜 봐야 할 것

실제 hit/miss 진단은 prefix_map이 아니라 trace의 hit_rate(스코어러가 실제 창고를 보고 계산한 값)를 봐야 합니다. 라우팅 표 괄호 안 숫자가 바로 이거예요.

4 오래 돌리면 캐시가 샌다 — KV cache "leak"

가장 핵심적인 문제입니다. 하드웨어가 멀쩡한데도, 장시간 돌리면 hit율 99%를 유지하다가 어느 순간 miss가 늘기 시작했습니다. 강원님 표현으로는 "KV cache가 실행 내내 계속 할당·사용되다가, 결국 prefix cache에 저장돼 있던 항목들이 evict되는 — 일종의 leak"입니다.

먼저 — 여기서 leak은 메모리 누수가 아님 메모리를 free 안 해서 새는 게 아니라, 정작 남아 있어야 할 유용한 prefix 캐시가 야금야금 쫓겨나(evict) 시간이 지날수록 miss가 느는 현상입니다. 캐시가 "새어 나간다"는 비유예요.

원인 = LRU free block queue 관리 방식

vLLM은 KV cache를 64토큰짜리 block 단위로 끊어 관리하고, 비어 있는 block들을 LRU 큐로 둡니다. LRU에서 tail = 방금 쓴 것(늦게 쫓겨남), head = 오래된 것(먼저 쫓겨남)이죠.

문제의 방아쇠는 단순합니다 — 입력 길이(ISL)가 정확히 64의 배수가 아니라는 점. 그래서 모든 요청이 끝에 "꽉 차지 않은 자투리 block 1개"를 새로 씁니다. 이 자투리는 안 꽉 찼으니 곧바로 free되는데, 문제는 이게 진짜 캐시 블록과 함께 LRU의 tail로 들어간다는 것입니다.

# 한 요청이 들어오면 (앞부분 99.9%는 이미 캐시 hit)
prefill(req):
    hit_blocks   = lookup(req.prefix)     # 재사용 (좋음)
    last_block   = alloc_one_block()      # 자투리 1개 (64토큰 안 채움)
    ...compute...
    free_blocks([... hit_blocks, last_block])
    # ⚠ vLLM v0.21.0: free된 블록을 전부 LRU TAIL에 append
    #   → 자투리(곧 버릴 것)가 '최근 사용' 자리를 차지하고,
    #     정작 재사용할 캐시 블록이 head 쪽으로 밀려나 evict됨

매 요청마다 자투리가 tail로 들어가니, 유용한 캐시 블록들은 점점 head(먼저 쫓겨나는 자리)로 밀려납니다. 누적 요청이 쌓일수록 진짜 필요한 캐시가 evict되고 → miss가 폭발합니다. 그래서 "문제가 누적 요청 수에 비례"했던 거예요.

강원님 말 그대로: "hit난 블록만 LRU 줄을 빙글빙글 돌아야 하는데, (실제론 곧 free되는) 자투리 1블록이 같이 줄을 서던" 것. 수정은 그 줄 서는 자리를 tail→head로 바꿉니다.

참고로 자투리 block이 우연히 64토큰을 꽉 채우면 정상적으로 tail로 빠지지만, 대부분은 그렇지 않아 계속 남아 캐시를 갉아먹습니다. 지민님 계산상 64k 데이터가 한 번에 천 개 가까운 블록을 쓰니, 평균 대비 20%가량이 이렇게 쫓겨날 수 있었습니다.

✓ 해결 — 무엇을 바꿨고 결과는

① KV cache leak — vLLM 패치

최근 vLLM PR #43447이 정확히 이 문제를 고칩니다. 꽉 차지 않은 block은 tail이 아니라 free queue의 HEAD로 넣도록 변경 — 자투리가 가장 먼저 재사용·evict되어 진짜 캐시를 밀어내지 않습니다. 이 패치를 적용한 뒤 hit율이 99%대로 안정됐습니다.

# 개념적 변경
- free_queue.append(block)      # 전: 무조건 TAIL
+ if block.is_full():
+     free_queue.append(block)    # 꽉 찬 정상 캐시 → TAIL (오래 보존)
+ else:
+     free_queue.appendleft(block)# 자투리 → HEAD (먼저 재사용/evict)

② 스코어러 가중치 · k 튜닝

prefix를 더 강하게 밀어주려고 가중치를 1억:1 → 100억:1(prefix:constant)로 올렸습니다. 단, k=1000은 너무 가팔라서 지수항이 부동소수점 범위를 넘어(Excel에서도 #NUM!) 확률분포가 깨질 수 있어, k=100으로 낮췄습니다(0.96~0.97 구간 변별력은 충분).

③ 하드웨어 장애 — 자동 복구

모니터링이 10분마다 GPU 상태를 보고, 에러가 감지되면 AMD GPU device plugin을 자동 재시작하도록 했습니다. 죽어도 사람이 안 붙어 살아납니다.

prefix_map(누적 superset)과 실제 보유 block을 구분하고, 진단은 trace의 hit_rate 기준으로 보도록 정리했습니다.

📊 결과 읽기 — 숫자 해석과 헷갈리는 수치

Zhipu POC 진행 상황을 Ambre팀에 공유한 내용과, 그 안의 성능 수치를 "있는 그대로(naive)" 먼저 본 뒤 해석합니다.

현황 한 줄 요약

상태 KST 00:40부터 full script 재가동 → 지난번 문제(KV cache leak)는 더 이상 발생하지 않음. 원인은 원본 vLLM의 KV cache 메모리 leak이었고, 3일 전 vLLM에 머지된 패치를 적용해 해결. 본 POC는 현재 스크립트로 conc=96(오늘 17~18시 KST 완료 예정) 또는 conc=112(내일 05~06시 완료 예정)까지 돌리면 충분히 설득력 있다고 판단 → 이후 Zhipu와 커뮤니케이션. (전체 실험은 ~5일 소요)
하드웨어 주의사항 (현재 진행형) 최근 클러스터에 실제 하드웨어 이슈 2건. ① NIC 카드 1장 고장 → 제외하고 운영, 성능 영향 없음. ② decode용 MI300X 서버의 GPU 1개가 약 6시간마다 HBM 에러 → 6노드가 다 필요하고 예비 서버가 없어 그대로 진행. 장애 시 그 노드의 소프트웨어만 재시작되고 전체 추론은 멈추지 않음(Zhipu 스크립트도 안 멈춤). 단 conc > 64 실험 중 장애가 나면 TTFT가 튈 수 있어, 장애 시간대를 공유하고 이상 데이터가 보이면 해당 케이스만 재실행할지 Zhipu와 협의 예정.

해석 ① — 좋은 신호

  • TPOT가 모든 ISL에서 거의 일정(mean 26~30 ms, p90 30~33 ms). 디코드가 건강하고 안정적이라는 뜻. 헤드라인인 64K의 p90 TPOT 32.2 ms는 SLO에 여유가 있음.
  • 64K·conc128의 p90 TTFT 7.7초도 SLO 대비 마진이 남음 → 더 높은 concurrency도 가능할 것으로 보임. 다만 우선 현재 스크립트로 POC를 마치고, 필요하면 후속 논의에서 고-concurrency 테스트를 제안하는 게 낫다는 판단.
  • decode tps(스트림당 34~37 tok/s)도 ISL 전반에서 안정적.

해석 ② — "나이브하게 보면 이상한" 수치

직관과 반대 보통 "입력이 길수록 prefill이 무거워 TTFT가 길다"고 기대합니다. 그런데 표는 반대예요 — 4K·8K의 TTFT(≈7.5 s, p90 10.4 s)가 16K~64K(3~4.7 s)보다 오히려 높습니다. 게다가 4K·8K는 완료 요청 수도 더 적습니다(≈6,800 vs 16K의 17,514).

왜 그럴까 (추정): 같은 시간 동안 도는 벤치마크에서 짧은 입력이 더 적게 처리되고 TTFT까지 높다는 건, 그 구간이 정상 상태가 아니었음을 시사합니다. 가장 유력한 설명은 하드웨어 장애 윈도우와 겹쳤을 가능성입니다 — 위에서 명시했듯 conc > 64 실험 중 decode 노드의 HBM 에러가 나면 TTFT가 튀고, 노드 재시작 동안 처리량이 줄어듭니다. 따라서 4K·8K의 높은 TTFT는 입력 길이 자체의 성질이 아니라, 그때 마침 장애 구간에 걸린 artifact로 보는 것이 합리적입니다.

그래서 행동 이런 케이스는 "이상 데이터"로 분류해, 장애 시간대 로그와 대조한 뒤 해당 케이스만 재실행할지 Zhipu와 협의합니다. 즉 숫자를 곧이곧대로 "짧은 입력이 더 느리다"로 결론짓지 않고, 원인(장애 윈도우)을 분리해 본 것이 핵심입니다.

※ 이 해석은 스레드에서 단정된 게 아니라 현재까지 정보로 가장 가능성 높은 가설입니다. 장애 시간대 로그와 케이스 시작 시각을 대조하면 확정할 수 있습니다.
