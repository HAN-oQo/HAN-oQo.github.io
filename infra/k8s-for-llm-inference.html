The short version한 줄 요약 A model server is a Deployment that makes Pods, reachable through a Service, configured by a ConfigMap, isolated in a Namespace. llm-d adds one thing on top: a CRD called InferencePool that groups those pods so a router can score them. That is 90% of what you need on day one.모델 서버는 Pod 를 만드는 Deployment 이고, Service 로 접근되며, ConfigMap 으로 설정되고, Namespace 안에 격리된다. llm-d 는 그 위에 하나를 더한다 — 라우터가 점수를 매길 수 있도록 그 파드들을 묶는 InferencePool 이라는 CRD. 첫날에 필요한 것의 90% 가 이것이다.

1Why any of this exists이게 왜 존재하나

You can run vLLM with docker run. Kubernetes earns its complexity only when you need things Docker does not give you: restart a crashed server automatically, roll out a new model without dropping requests, put four replicas behind one address, schedule onto the node that actually has a free GPU, and describe all of it as files in git.vLLM 은 docker run 으로도 돌릴 수 있다. 쿠버네티스가 그 복잡도값을 하는 건 도커가 안 주는 것이 필요해질 때다 — 죽은 서버 자동 재시작, 요청을 흘리지 않는 모델 롤아웃, 주소 하나 뒤에 레플리카 넷, GPU 가 실제로 비어 있는 노드로 스케줄, 그리고 그 전부를 git 안의 파일로 기술하기.

The mental model that matters most: you never tell Kubernetes what to do, you tell it what you want to be true. You submit desired state; a control loop keeps reality matching it. Every confusing behaviour later — a pod you deleted coming back, a change you made by hand getting reverted — is that loop doing its job.가장 중요한 멘탈 모델: 쿠버네티스에 무엇을 하라고 시키는 게 아니라, 무엇이 참이어야 하는지를 말한다. 원하는 상태를 제출하면 컨트롤 루프가 현실을 거기에 맞춘다. 나중에 헷갈리는 모든 동작 — 지운 파드가 되살아나고, 손으로 고친 게 되돌려지는 것 — 이 그 루프가 제 일을 하는 것이다.

This is also why GitOps followsGitOps 가 따라오는 이유이기도 하다 If the cluster is a loop converging on declared state, the natural place to declare it is a git repo. That is the whole idea behind the ArgoCD series — this page is the prerequisite for it.클러스터가 선언된 상태로 수렴하는 루프라면, 그 상태를 선언할 자연스러운 장소는 git 저장소다. ArgoCD 시리즈의 전제가 그것이고, 이 페이지는 그 시리즈의 선행 문서다.

2Six objects, and what each looks like for a model server객체 6개, 그리고 모델 서버에선 각각 뭐로 보이나

The same pods are selected twice — once by the Service for plain traffic, once by the InferencePool for inference-aware routing.같은 파드가 두 번 선택된다 — 평범한 트래픽용으로 Service 가 한 번, 추론 인지 라우팅용으로 InferencePool 이 한 번.

Object객체 What it is무엇인가 For a model server모델 서버에서는
Pod One or more containers scheduled together on one node. The smallest thing you can run.한 노드에 함께 스케줄되는 컨테이너 하나 이상. 실행 가능한 최소 단위. One vLLM process holding its GPUs. Pods are disposable — never fix one by hand, fix what created it.GPU 를 쥔 vLLM 프로세스 하나. 파드는 일회용이다 — 손으로 고치지 말고 그걸 만든 쪽을 고쳐라.
Deployment "Keep N healthy copies of this pod spec." Handles replacement and rolling updates."이 파드 명세의 정상 복제본 N개를 유지하라." 교체와 롤링 업데이트를 담당. How you scale replicas and how you change model or engine args without downtime.레플리카를 늘리는 방법이자, 무중단으로 모델·엔진 인자를 바꾸는 방법.
Service A stable name and IP in front of whatever pods match a label selector.라벨 셀렉터에 맞는 파드들 앞에 놓이는 안정된 이름과 IP. Pods die and get new IPs; the Service name does not change. This is what your client talks to.파드는 죽고 새 IP 를 받지만 Service 이름은 안 변한다. 클라이언트가 말을 거는 대상.
Namespace A folder for objects, plus a boundary for quota and permissions.객체를 담는 폴더이자 쿼터·권한의 경계. Almost every command needs -n <ns>. Forgetting it is the #1 reason "my pod doesn't exist".거의 모든 명령에 -n <ns> 가 필요하다. 이걸 빼먹는 게 "파드가 없다" 의 1순위 원인.
ConfigMap
/ Secret		 Key-value config injected as env vars or mounted files. Secret is the same thing, for credentials.환경변수나 마운트 파일로 주입되는 키-값 설정. Secret 은 자격증명용 같은 물건. Engine flags, sampling defaults, HF_TOKEN. Changing a ConfigMap does not restart pods by itself.엔진 플래그, 샘플링 기본값, HF_TOKEN. ConfigMap 을 바꿔도 파드가 저절로 재시작되지는 않는다.
CRD A custom object type someone added to the cluster's API. Once registered, it behaves like a built-in.누군가 클러스터 API 에 추가한 커스텀 객체 타입. 등록되면 기본 객체처럼 동작한다. This is how llm-d ships. InferencePool and friends are CRDs — see §5.llm-d 가 배포되는 방식이 이것이다. InferencePool 등이 CRD 다 — §5 참고.
The ConfigMap trapConfigMap 함정 You edit a ConfigMap, nothing happens, and you conclude the change didn't apply. It did — the object changed, but running pods keep the values they started with (env vars are set at container start; mounted files update eventually but the process won't re-read them). You have to restart: kubectl -n serving rollout restart deploy/model-server. Under ArgoCD this bites differently: the sync succeeds and reports Healthy while the pods still run the old config.ConfigMap 을 고쳤는데 아무 일도 안 일어나서 반영이 안 됐다고 결론 내린다. 반영은 됐다 — 객체는 바뀌었지만 떠 있는 파드는 시작할 때의 값을 유지한다(환경변수는 컨테이너 시작 시 고정, 마운트 파일은 언젠가 갱신되지만 프로세스가 다시 읽지 않는다). 재시작해야 한다: kubectl -n serving rollout restart deploy/model-server. ArgoCD 아래선 양상이 다르게 아프다 — sync 는 성공하고 Healthy 라고 보고하는데 파드는 여전히 옛 설정으로 돈다.

3GPUs: why your pod is stuck in PendingGPU: 파드가 Pending 에 멈춘 이유

GPUs are not like CPU and memory. Kubernetes treats them as an extended resource advertised by a device plugin running on each node. Two consequences follow immediately: they are integers only (no 0.5), and they cannot be oversubscribed — requests and limits must be equal, so you just write limits.GPU 는 CPU·메모리와 다르다. 쿠버네티스는 GPU 를 각 노드의 device plugin 이 광고하는 확장 리소스로 다룬다. 여기서 두 가지가 곧바로 따라온다 — 정수만 가능하고(0.5 불가), 오버서브스크립션이 안 된다. requests 와 limits 가 같아야 하므로 그냥 limits 만 쓴다.

resources:
  limits:
    amd.com/gpu: 1        # AMD ROCm device plugin
    # nvidia.com/gpu: 1   # NVIDIA device plugin

A pod asking for a GPU stays Pending until some node can satisfy it. Four reasons cover nearly every case:GPU 를 요구하는 파드는 이를 만족할 노드가 나올 때까지 Pending 에 머문다. 거의 모든 경우가 아래 넷 안에 있다.

Cause원인 How you confirm it확인 방법
No node advertises the resource — the device plugin isn't running, so the cluster believes there are zero GPUs.어떤 노드도 리소스를 광고하지 않음 — device plugin 이 안 떠서 클러스터는 GPU 가 0개라고 믿는다. kubectl get nodes -o custom-columns=NAME:.metadata.name,GPU:.status.allocatable.amd\.com/gpu shows blank or 0가 빈칸이거나 0
All GPUs are taken. Allocatable is nonzero but every one is bound to another pod — including pods you forgot about.GPU 가 전부 점유됨. allocatable 은 0 이 아닌데 전부 다른 파드에 묶여 있다 — 잊고 있던 파드 포함. kubectl describe node <n> → the Allocated resources blockAllocated resources 블록
A taint is repelling you. GPU nodes are commonly tainted so ordinary workloads stay off them; your pod needs a matching toleration.taint 가 밀어내고 있음. GPU 노드는 일반 워크로드가 올라오지 않도록 taint 를 두는 게 흔하다. 파드에 맞는 toleration 이 필요하다. kubectl describe node <n> | grep -i taint
Your selector matches nothing — a nodeSelector or affinity naming a label no node carries.셀렉터가 아무것도 못 맞춤 — 어떤 노드도 갖지 않은 라벨을 nodeSelector 나 affinity 가 지목. kubectl get nodes --show-labels
The one command that answers it답을 주는 한 줄 Do not guess between those four. The scheduler writes down exactly why it refused, in the pod's events: kubectl -n serving describe pod <pod> and read the bottom. You will see something like 0/3 nodes are available: 3 Insufficient amd.com/gpu or 1 node(s) had untolerated taint. That sentence names the cause.넷 중 뭔지 추측하지 마라. 스케줄러가 거절 이유를 파드 이벤트에 그대로 적어 둔다 — kubectl -n serving describe pod <pod> 를 치고 맨 아래를 읽으면 된다. 0/3 nodes are available: 3 Insufficient amd.com/gpu 나 1 node(s) had untolerated taint 같은 문장이 보인다. 그 문장이 원인을 지목한다.

Worth knowing: Pending and ContainerCreating are different failures. Pending means no node was chosen (scheduling). ContainerCreating means a node was chosen and something after that is slow or broken — usually pulling a multi-gigabyte image, or a volume that won't mount.알아 둘 것: Pending 과 ContainerCreating 은 다른 실패다. Pending 은 노드가 안 정해진 것(스케줄링). ContainerCreating 은 노드는 정해졌고 그 이후가 느리거나 깨진 것 — 보통 수 GB 이미지 pull 이거나 마운트 안 되는 볼륨이다.

4The debugging ladder디버깅 사다리

When a model server misbehaves, going in this order finds the answer faster than any other order. Each rung answers a different question, and rung 1 answers most of them.모델 서버가 이상할 때, 이 순서로 가는 게 다른 어떤 순서보다 빠르다. 각 단은 서로 다른 질문에 답하고, 대부분은 1단에서 끝난다.

Which rung to jump to, by symptom.증상별로 어느 단으로 뛸지.

# 1 — state and restart count, always start here
kubectl -n serving get pods -o wide

# 2 — why it won't schedule or start (read the Events at the bottom)
kubectl -n serving describe pod <pod>

# 3 — why the process died. --previous is the important half
kubectl -n serving logs <pod> --tail=200
kubectl -n serving logs <pod> --previous --tail=200

# 4 — what the cluster did, newest last
kubectl -n serving get events --sort-by=.lastTimestamp | tail -30

# 5 — is it actually serving, ignoring all networking in between?
kubectl -n serving port-forward pod/<pod> 8000:8000
curl localhost:8000/v1/models
Two symptoms worth recognising on sight보자마자 알아야 할 증상 둘 OOMKilled in describe means the container exceeded its memory limit — that is host RAM, not GPU memory. A CUDA/HIP OOM looks completely different: the pod stays Running and the traceback is in the logs.

CrashLoopBackOff is not an error, it is a backoff timer. Kubernetes is waiting longer and longer between restarts. The real error is in the previous container's logs, which is why rung 3 has two commands and not one.OOMKilled 이 describe 에 보이면 컨테이너가 메모리 제한을 넘은 것이다 — GPU 메모리가 아니라 호스트 RAM. CUDA/HIP OOM 은 양상이 완전히 다르다: 파드는 Running 을 유지하고 트레이스백이 로그에 남는다.

CrashLoopBackOff 는 에러가 아니라 백오프 타이머다. 재시작 간격을 점점 늘리며 기다리는 중이라는 뜻. 진짜 에러는 이전 컨테이너 로그에 있고, 그래서 3단에 명령이 하나가 아니라 둘이다.

5What llm-d adds on topllm-d 가 그 위에 더하는 것

llm-d does not replace any of the above. Your model servers are still Deployments making Pods. What it adds is a routing layer that knows those pods are inference servers — so it can pick a replica by KV-cache locality or queue depth instead of round-robin, which a plain Service cannot do.llm-d 는 위의 어떤 것도 대체하지 않는다. 모델 서버는 여전히 Pod 를 만드는 Deployment 다. 더해지는 건 그 파드들이 추론 서버임을 아는 라우팅 계층이다 — 덕분에 라운드로빈 대신 KV 캐시 지역성이나 큐 깊이로 레플리카를 고를 수 있다. 평범한 Service 는 못 하는 일이다.

It ships as the Gateway API Inference Extension (GIE): a set of CRDs plus an EPP (Endpoint Picker) that does the scoring. From our own Phase 4 run, the CR looks like this:배포 형태는 Gateway API Inference Extension(GIE) 다 — CRD 묶음 + 점수를 매기는 EPP(Endpoint Picker). 우리 Phase 4 실행에서 CR 은 이렇게 생겼다.

# manifests/phase4-llmd/pool/inferencepool.yaml
apiVersion: inference.networking.k8s.io/v1
kind: InferencePool
spec:
  selector: { matchLabels: { app: model-server } }   # ← the same pods
  targetPorts: [ { number: 8000 } ]
  endpointPickerRef: { name: qwen-epp, port: { number: 9002 } }

Read that as three sentences: which pods are in the pool (the same label your Service uses), what port they serve on, and who decides which one gets each request.문장 세 개로 읽으면 된다 — 풀에 어떤 파드가 들어가는지(Service 가 쓰는 것과 같은 라벨), 그들이 어느 포트로 서빙하는지, 그리고 요청마다 누가 고르는지.

Order matters: CRD before CR순서가 중요하다: CRD 먼저, CR 나중

A CR cannot exist before its CRD is registered. Applying both at once means the pool fails and retries until the CRD lands. Our Phase 4 log caught exactly this: t+33s CRD_registered=yes InferencePool_CR=no, converging one retry later.CR 은 CRD 가 등록되기 전엔 존재할 수 없다. 둘을 동시에 apply 하면 pool 이 실패하고 CRD 가 올라올 때까지 재시도한다. Phase 4 로그가 정확히 이걸 잡았다: t+33s CRD_registered=yes InferencePool_CR=no, 한 번 더 재시도 뒤 수렴.

CRD health is eventually consistentCRD health 는 최종 일관성이다

Freshly applied CRDs report Degraded for a moment while establishing. Phase 4 saw this and it resolved on its own once all four reported Established=True. A transient, not a failure.막 적용된 CRD 는 establishing 중에 잠깐 Degraded 로 보고된다. Phase 4 에서 이걸 겪었고, 넷 모두 Established=True 가 되자 저절로 풀렸다. 실패가 아니라 일시적 상태.

A real gotcha from our lab우리 실습에서 나온 실제 함정 InferencePool v1 requires endpointPickerRef.port. Omit it and the apply is rejected with port is required when kind is 'Service', and under ArgoCD the app just sits OutOfSync/Missing until you notice. Full write-up in Phase 4.InferencePool v1 은 endpointPickerRef.port 가 필수다. 빠뜨리면 port is required when kind is 'Service' 로 apply 가 거부되고, ArgoCD 아래선 알아챌 때까지 앱이 OutOfSync/Missing 로 앉아 있는다. 전체 기록은 Phase 4 에.

Where to look when llm-d misbehavesllm-d 가 이상할 때 보는 순서

# is the CRD even registered?
kubectl get crd | grep inference.networking

# does the pool exist, and does its selector match anything?
kubectl -n serving get inferencepool
kubectl -n serving describe inferencepool <name>
kubectl -n serving get pods -l app=model-server   # ← the selector, by hand

# the EPP is an ordinary Deployment — debug it like any other pod
kubectl -n serving logs deploy/qwen-epp --tail=100

The most common llm-d failure is unglamorous: the pool's selector matches zero pods, usually a label typo. Running the selector by hand as a -l query is the fastest way to prove it.가장 흔한 llm-d 실패는 시시하다 — pool 의 셀렉터가 파드를 하나도 못 맞추는 것, 대개 라벨 오타다. 셀렉터를 -l 쿼리로 직접 쳐 보는 게 가장 빠른 증명이다.

For what the EPP actually does with those endpoints — scorers, flow control, P/D routing — see the Heimdall deep-dives; this page is the operational half.EPP 가 그 엔드포인트로 실제로 무엇을 하는지 — 스코어러, flow control, P/D 라우팅 — 는 Heimdall 딥다이브를 보라. 이 페이지는 운영 쪽 반쪽이다.

6k9s — when it beats typing kubectlk9s — kubectl 을 치는 것보다 나을 때

It does nothing kubectl cannot, but it collapses the loop "type command → read → type next command" into arrow keys, which matters when you are watching a rollout or hunting through pods.k9s 는 같은 API 위의 터미널 UI 다. kubectl 이 못 하는 일을 하지는 않지만, "명령 치고 → 읽고 → 다음 명령 치고" 루프를 방향키로 접어 준다. 롤아웃을 지켜보거나 파드를 뒤질 때 차이가 크다.

1RBAC — and why the router needs itRBAC — 라우터가 왜 이걸 필요로 하나

Most inference engineers meet RBAC through a failure: a pod logs forbidden: User "system:serviceaccount:serving:default" cannot list resource "pods" and dies. Understanding the four objects makes that message trivially readable.대부분의 추론 엔지니어는 실패를 통해 RBAC 을 만난다 — 파드가 forbidden: User "system:serviceaccount:serving:default" cannot list resource "pods" 를 남기고 죽는다. 객체 넷을 이해하면 그 메시지가 대번에 읽힌다.

Identity, permission, and the binding between them — the whole model.신원, 권한, 그 사이의 바인딩 — 모델 전체.

Why this shows up in inference work specifically: the EPP is a controller. To pick an endpoint it must watch the pods behind an InferencePool — which means reading pods and endpointslices from the API, and reading the inferencepools CRs themselves. A plain model server needs no permissions at all; a router needs a real Role. That asymmetry surprises people.추론 작업에서 이게 유독 등장하는 이유: EPP 는 컨트롤러다. 엔드포인트를 고르려면 InferencePool 뒤의 파드를 watch 해야 하고, 그건 API 에서 pods 와 endpointslices 를 읽고 inferencepools CR 자체도 읽는다는 뜻이다. 평범한 모델 서버는 권한이 전혀 필요 없는데 라우터는 진짜 Role 이 필요하다. 이 비대칭이 사람들을 놀라게 한다.

rules:
  - apiGroups: [""]
    resources: ["pods", "endpoints"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["discovery.k8s.io"]
    resources: ["endpointslices"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["inference.networking.k8s.io"]
    resources: ["inferencepools"]
    verbs: ["get", "list", "watch"]

Illustrative shape, not a spec — the exact rules depend on your GIE version and gateway implementation. Take them from the chart you install, and if something is forbidden, the error names the missing verb and resource precisely enough to fix it.스펙이 아니라 형태 예시다 — 정확한 규칙은 GIE 버전과 게이트웨이 구현에 달렸다. 설치하는 차트에서 가져오고, forbidden 이 나면 에러가 빠진 verb 와 리소스를 고칠 수 있을 만큼 정확히 지목해 준다.

# the two commands that settle any RBAC argument
kubectl auth can-i list pods --as=system:serviceaccount:serving:qwen-epp -n serving
kubectl auth can-i --list --as=system:serviceaccount:serving:qwen-epp -n serving
Debug it as the identity, not as you당신이 아니라 그 신원으로 디버깅하라 You are almost certainly cluster-admin, so everything works when you try it. --as= impersonates the ServiceAccount and reproduces the pod's actual view. This turns "it works for me" into a decidable question.당신은 거의 확실히 cluster-admin 이라 직접 해 보면 다 된다. --as= 는 ServiceAccount 를 가장해 파드의 실제 시야를 재현한다. "나는 되는데" 를 판정 가능한 질문으로 바꿔 준다.

2Networking — why a Service isn't enough네트워킹 — Service 로 부족한 이유

A Service is a layer-4 load balancer with a stable name. It picks a backend without looking at the request. For inference that is exactly the wrong abstraction twice over: the model you want is named inside the JSON body, and the best replica depends on which one already has your prefix in its KV cache. A Service can see neither.Service 는 안정된 이름을 가진 L4 로드밸런서다. 요청을 들여다보지 않고 백엔드를 고른다. 추론에서 이건 두 겹으로 틀린 추상화다 — 원하는 모델은 JSON body 안에 이름이 있고, 최적 레플리카는 어느 쪽이 이미 그 prefix 를 KV 캐시에 갖고 있느냐에 달렸다. Service 는 둘 다 못 본다.

The readiness link people miss놓치기 쉬운 readiness 연결 A pod enters the EndpointSlice only when its readiness probe passes. So a model server that is Running but still loading 200 GB of weights is correctly excluded from traffic — and if your readiness probe is missing or too lenient, requests hit a server that isn't ready and time out. For LLM serving, the readiness probe is a load-bearing part of the deployment, not boilerplate.파드는 readiness probe 가 통과해야 EndpointSlice 에 들어간다. 따라서 Running 이지만 아직 200 GB 가중치를 로딩 중인 모델 서버는 트래픽에서 올바르게 제외된다 — 반대로 readiness probe 가 없거나 너무 느슨하면 준비 안 된 서버로 요청이 가서 타임아웃 난다. LLM 서빙에서 readiness probe 는 형식적인 게 아니라 배포의 하중을 받는 부품이다.

Above the Service sits the Gateway API (Gateway + HTTPRoute), the successor to Ingress, and GIE extends exactly that with inference-aware picking. How a request whose model name lives in the body actually gets routed is its own subject — covered in Routing an LLM request when the model name is in the body.Service 위에는 Ingress 의 후계자인 Gateway API(Gateway + HTTPRoute)가 있고, GIE 는 바로 그것을 추론 인지 선택으로 확장한다. 모델명이 body 에 있는 요청이 실제로 어떻게 라우팅되는지는 그 자체로 별도 주제다 — 모델명이 body 에 있을 때 LLM 요청 라우팅에서 다룬다.

3Storage — the model weights problem스토리지 — 모델 가중치 문제

Containers are ephemeral; a 200 GB checkpoint is not something you want to re-download on every restart. The options, and what each costs:컨테이너는 일회용인데 200 GB 체크포인트를 재시작마다 다시 받고 싶진 않다. 선택지와 각각의 대가는 이렇다.

Approach방식 How it behaves동작 The catch함정
Bake into the image이미지에 굽기 Weights ship with the container. Nothing to mount.가중치가 컨테이너에 딸려 온다. 마운트할 게 없다. A 200 GB image pull on a cold node, every time. ContainerCreating for many minutes.차가운 노드마다 200 GB 이미지 pull. ContainerCreating 이 수 분.

Two vocabulary items, since the error messages use them: a PersistentVolume (PV) is the actual piece of storage; a PersistentVolumeClaim (PVC) is a pod's request for one. A StorageClass creates PVs on demand so nobody has to pre-provision. When a pod hangs in ContainerCreating with a volume error, the question is almost always whether the PVC ever got Bound:에러 메시지가 쓰는 용어 둘 — PersistentVolume(PV) 는 실제 스토리지 조각이고, PersistentVolumeClaim(PVC) 는 파드가 그걸 달라는 요청이다. StorageClass 는 필요할 때 PV 를 만들어 주어 미리 준비할 필요를 없앤다. 파드가 볼륨 에러와 함께 ContainerCreating 에 멈췄다면, 질문은 거의 항상 PVC 가 Bound 됐는지다.

kubectl get pvc                      # STATUS should be Bound, not Pending
kubectl describe pvc <name>          # Pending → usually no matching StorageClass
