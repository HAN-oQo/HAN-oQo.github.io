0.1 Networks are built in "Layers" 네트워크는 "계층(Layer)"으로 만들어져 있다

Two machines talking is actually many small things happening at once, organized as the OSI (Open Systems Interconnection) 7-layer model. The slides use "L2" and "L3" as shorthand for Layer 2 and Layer 3 in this model — those are the only two we'll dig into.

두 컴퓨터가 통신하는 건 사실 여러 작은 일이 동시에 일어나는 거고, OSI(Open Systems Interconnection, 개방형 시스템 상호 연결) 7계층 모델로 정리됩니다. 슬라이드의 "L2", "L3"는 이 모델의 Layer 2, Layer 3를 줄여 부르는 말 — 우리가 파고들 건 이 둘뿐입니다.

L7 Application ← your app (browser, Slack, gRPC ...) L6 Presentation ← data format (often skipped) L5 Session ← session management L4 Transport ← TCP (Transmission Control Protocol) / UDP (User Datagram Protocol) L3 Network ← IP (Internet Protocol) — which network to deliver to ⭐ L2 Data Link ← MAC (Media Access Control) — who to give it to on this cable ⭐ L1 Physical ← wires, fiber — electrical signals
Analogy비유

Sending a paper letter:

  • L1 = the postal trucks & roads (physical infra)
  • L2 = the mailman delivering inside one neighborhood
  • L3 = Seoul → Busan delivery (postal offices route between cities)
  • L4 = registered mail vs. regular mail (reliability)
  • L7 = the actual content of the letter

편지 보내는 거랑 똑같습니다:

  • L1 = 우편 트럭이 달리는 도로 (물리 인프라)
  • L2 = 같은 동네 안에서 집배원이 직접 배달
  • L3 = 서울 → 부산 같은 다른 지역 (우체국이 경로 찾아줌)
  • L4 = 등기우편 vs 일반우편 (신뢰성)
  • L7 = 편지에 적힌 실제 내용

0.2 MAC address vs IP address — every computer has two MAC 주소 vs IP 주소 — 컴퓨터마다 두 개

This trips up everyone at first: your laptop has two addresses. They live at different layers and do different jobs. MAC here is "Media Access Control" (nothing to do with Apple Macs!). IP is "Internet Protocol."

처음엔 다들 헷갈리는 부분: 너 노트북에는 주소가 두 개입니다. 다른 Layer에 있고 역할이 다릅니다. 여기서 MAC은 "Media Access Control"(매체 접근 제어 — 애플 맥하고 무관), IP는 "Internet Protocol"(인터넷 프로토콜).

Why do we need both? If we only had IP, then on a cable with 10 computers, the switch wouldn't know which one to hand the packet to. If we only had MAC, we couldn't route across the planet (no one memorizes 280 trillion MACs). So we use IP to find the "neighborhood" and MAC to find the "person in that neighborhood."

둘 다 왜 필요해? IP만 있으면 같은 케이블에 컴퓨터 10대 있을 때 누구에게 줘야 할지 모릅니다. MAC만 있으면 전 세계 MAC을 다 외울 수 없고 경로도 못 찾습니다. 그래서 IP로 "동네"를 찾고, MAC으로 "그 동네 안의 누구"한테 줄지 정합니다.

0.3 Subnet — a group of "neighborly" IPs Subnet — 같은 "동네"인 IP들의 묶음

Subnet (short for "sub-network") means "a group of IPs that share the same local network." Written like 192.168.0.0/24 — the /24 means "the first 24 bits are the network part; the last 8 bits identify the host inside." So 192.168.0.1 through 192.168.0.254 are in the same neighborhood. (The /24 notation is called CIDR — Classless Inter-Domain Routing.)

Subnet("sub-network" 줄임말) = "같은 동네에 있는 IP들의 묶음". 192.168.0.0/24 처럼 적고, /24는 "앞 24비트는 네트워크 부분, 뒤 8비트는 동네 안 호스트"라는 뜻. 그래서 192.168.0.1 ~ 192.168.0.254가 같은 동네입니다. (/24 표기법을 CIDR — Classless Inter-Domain Routing, 클래스 없는 도메인 간 라우팅이라 부릅니다.)

  • Same subnet → talk via L2 directly (just a switch is enough)
  • Different subnet → need L3 (a router / gateway between)
  • 같은 subnet → L2로 직접 통신 (스위치만 있으면 됨)
  • 다른 subnet → L3 필요 (라우터/게이트웨이 거쳐야 함)
Analogy비유 Same apartment complex, building 1 ↔ building 2 — you can walk (L2). Different complex — you need a road and a car (L3). 같은 아파트 단지 1동 ↔ 2동은 걸어서 갈 수 있고(L2), 옆 단지로 가려면 도로/차 필요(L3).

0.5 Unicast / Broadcast / Multicast — three ways to send Unicast / Broadcast / Multicast — 패킷 보내는 3가지 방식

  • Unicast: A → B. one-to-one (the common case)
  • Broadcast: A → everyone. all hosts in the same subnet receive it ("hello, who's here?")
  • Multicast: A → subscribers only. like "subscribers of this channel receive this"
  • Unicast: A → B. 1대1 (제일 흔함)
  • Broadcast: A → 모두. 같은 subnet의 모든 호스트가 받음. "여기 누구 있어요?" 하고 외치는 것
  • Multicast: A → 가입자만. "이 채널 구독자만 받아라" 같은 것
Important중요 Broadcast does not cross subnets. If it did, the entire internet would scream at itself. Routers block broadcasts at the L3 boundary. Broadcast는 subnet을 못 넘습니다. 안 그러면 전 세계가 다 같이 소리지르고 망함. 라우터가 L3 경계에서 막아줍니다.

0.6 ARP — turning an IP into a MAC ARP — IP를 MAC으로 바꾸는 마법

Your laptop says "send to 192.168.0.10!" Fine. But the packet has to ship out on a cable, and the L2 header needs a MAC. We don't know the MAC yet.

너 노트북이 "192.168.0.10한테 보내!" 하면 좋은데, 케이블로 나갈 땐 L2 헤더에 MAC이 필요합니다. MAC을 모르네요.

ARP enters the room: "Hey, who has 192.168.0.10?! Tell me your MAC!" — shouted as a broadcast. The host with that IP answers (unicast): "It's me — my MAC is aa:bb:cc:dd:ee:ff." You cache it in the ARP table.

ARP 등장: "야 192.168.0.10 가진 놈 누구야! MAC 알려줘!" 하고 broadcast로 외칩니다. 그 IP 가진 호스트만 "나야! 내 MAC은 aa:bb:cc:dd:ee:ff" 라고 unicast로 답하고, 너는 ARP 테이블에 캐싱.

# the ARP table on a Linux machine
$ ip neigh show
192.168.0.1  dev eth0  lladdr aa:bb:cc:00:00:01  REACHABLE
192.168.0.10 dev eth0  lladdr aa:bb:cc:dd:ee:ff  REACHABLE

0.7 Encapsulation — packets are onions Encapsulation — 패킷은 양파

A packet is wrapped in layers. Each layer prepends its own header (this process is called encapsulation):

패킷은 여러 겹으로 만들어집니다. 각 Layer가 자기 헤더를 앞에 붙입니다(이 과정을 encapsulation, 캡슐화라 부릅니다):

[L2 hdr | L3 hdr | L4 hdr | Application data] MAC IP port your message

The receiver peels them off in reverse (decapsulation). VXLAN's trick is exactly here — take an already-finished L2 frame and stuff it inside another packet. (Like putting a sealed envelope inside a bigger box.) That's slide 10.

받는 쪽은 반대로 한 겹씩 깝니다(decapsulation). VXLAN의 트릭은 여기서 옵니다 — 이미 완성된 L2 프레임을 통째로 또 다른 패킷 안에 넣어버립니다. (편지를 봉투에 넣고, 그 봉투를 더 큰 박스에 넣는 식.) 이게 슬라이드 10의 핵심.

0.8 VLAN — slicing one cable into many "neighborhoods" VLAN — 한 케이블을 여러 "동네"로 쪼개기

An office has 100 PCs on one big switch. Sales' broadcasts shouldn't be heard by Engineering, and security wants separation. Solution: VLAN — physically one switch, but logically multiple LANs. Sales is VLAN 10, Engineering is VLAN 20. A broadcast stays inside its own VLAN.

사무실에 PC 100대가 한 대형 스위치에 다 꽂혀있다고 가정. 영업팀 broadcast를 개발팀이 듣는 건 이상하고, 보안도 별로입니다. 해법: VLAN — 물리적으론 한 스위치지만 논리적으로 여러 LAN으로 나눕니다. 영업팀 VLAN 10, 개발팀 VLAN 20. broadcast가 자기 VLAN 안에서만 돕니다.

VLAN ID is 12 bits → up to 4096. Plenty for an office, way too few for a cloud datacenter with tens of thousands of tenants × subnets each. That's slide 9's problem.

VLAN ID는 12비트 → 최대 4096개. 회사 안에선 충분한데, 수만 명 테넌트 × 각자 여러 subnet 쓰는 클라우드 데이터센터에선 턱없이 부족합니다. 이게 슬라이드 9의 문제.

0.9 So what is VXLAN? 그래서 VXLAN이란?

one-line definition한 줄 정의 VXLAN solves VLAN's limits (4096 IDs, broadcast confinement) by wrapping L2 frames inside UDP/IP — creating a virtual L2 tunnel that rides on top of any L3 network. VXLAN은 VLAN의 한계(4096개, broadcast 제약)를 넘기 위해, L2 프레임을 UDP/IP에 캡슐화해서 L3 인터넷 위로 보내는 가상 L2 터널을 만듭니다.

Imagine this: a company HQ and a branch office want their PCs to feel like they're on the same office LAN — even though the internet (L3) sits between them. VXLAN tunnels the L2 frames through.

상상해보세요: 회사 본사와 지사 컴퓨터들이 마치 같은 사무실 LAN에 꽂혀있는 것처럼 동작하길 원합니다. 둘 사이엔 인터넷(L3)이 있고요. VXLAN으로 그 L2 프레임을 인터넷 위로 터널링합니다.

Two terms to memorize now (they appear constantly):

지금 외워두면 좋은 용어 두 개 (계속 나옵니다):

  • VTEP (VXLAN Tunnel End Point) — the door at each end of the tunnel; does the L2 ↔ VXLAN wrapping
  • VNI (VXLAN Network Identifier) — the new "VLAN ID", but 24 bits → ~16 million IDs
  • VTEP (VXLAN Tunnel End Point) — 터널 양쪽 끝의 문; L2 ↔ VXLAN 변환 담당
  • VNI (VXLAN Network Identifier) — VLAN ID를 대체하는 ID, 24비트 → 약 1,600만 개
AI/ML side noteAI/ML 사이드 노트

Why does this matter for inference work? K8s clusters that run vLLM/SGLang typically have a "pod network" — a virtual L2 network that lets pods on different physical nodes talk as if they were on the same cable. That overlay is almost always VXLAN (Flannel, Calico-VXLAN, etc.). When you debug "pod can't reach pod" or "KV transfer is slow", you're often debugging VXLAN behavior under the hood.

추론 환경에서 왜 중요할까요? vLLM/SGLang을 띄우는 K8s 클러스터는 거의 항상 pod 네트워크를 가지고 있고, 이건 서로 다른 노드에 떠 있는 pod들이 마치 같은 케이블에 있는 것처럼 통신하게 해주는 가상 L2입니다. 이 오버레이가 십중팔구 VXLAN(Flannel, Calico-VXLAN 등). "pod 간 통신 안 됨" 또는 "KV 전송이 느림" 같은 이슈를 파면 결국 VXLAN 동작을 디버깅하는 경우가 많습니다.

  • Routing table — "for this destination IP, which interface / gateway do I send out?" (L3 decision)
  • ARP table — "for this IP on my local subnet, what's its MAC?" (L3 → L2 bridge)
  • MAC table — (lives on the switch) "for this destination MAC, which port?" (L2 decision)

  • ARP table — "내 subnet의 이 IP의 MAC은 뭔지" (L3↔L2 연결)
  • MAC table — (스위치가 가짐) "이 목적지 MAC은 어느 포트인지" (L2 결정)

Why "Direct" only needs the routing table왜 Direct는 라우팅 테이블만 필요한가

If two boxes are wired directly to each other (no switch), there's literally only one place a packet could go — the other end of the cable. No need to resolve MAC by ARP, no switch port lookup. The routing table just needs an entry saying "for that subnet, send out this interface."

두 컴퓨터가 케이블로 바로 직결되어 있으면(스위치 없음), 패킷이 갈 곳은 케이블 반대편 하나뿐입니다. ARP로 MAC 찾을 일도, 스위치 포트 찾을 일도 없습니다. routing table에 "이 subnet은 이 인터페이스로 내보내라"는 항목만 있으면 됩니다.

L2 and L3 both need all three? Why?L2와 L3가 둘 다 세 개 다 필요한 이유?

As soon as a switch is in the path, the switch must know which port a MAC lives on (= MAC table). For your machine to address by MAC at all, it had to discover the MAC for an IP (= ARP table). And the routing table is always queried first to decide whether the destination is local (use ARP) or remote (send to the gateway).

경로에 스위치만 들어오는 순간, 스위치는 어떤 MAC이 어떤 포트에 있는지 알아야 합니다(= MAC table). 너 컴퓨터가 MAC으로 주소를 적으려면 IP의 MAC을 먼저 알아내야 했습니다(= ARP table). 그리고 항상 routing table부터 먼저 본 뒤 "이 목적지가 같은 subnet이냐(ARP로) 다른 subnet이냐(게이트웨이로)"를 결정합니다.

We met ARP (Address Resolution Protocol) briefly in §0.6. The slide goes deeper with a specific scenario across multiple subnets.

ARP(Address Resolution Protocol, "주소 해석 프로토콜")는 0.6에서 잠깐 봤습니다. 슬라이드는 multi-subnet 시나리오로 더 들어갑니다.

Same-subnet ARP vs Proxy ARP across subnets.같은 subnet ARP vs subnet 간 Proxy ARP.

Same-subnet ARP (the basic case)같은 subnet ARP (기본 케이스)

  • Worker 1 (192.168.0.2) wants to talk to Worker 2 (192.168.0.3). Same subnet.
  • Worker 1 doesn't know Worker 2's MAC. Sends an ARP broadcast on the L2 segment: "Who has 192.168.0.3?"
  • Worker 2 replies unicast: "I do — MAC AAAA.AAAA.AAAA."
  • Worker 1 caches the mapping and now ships normal unicast L2 frames to that MAC.
  • Worker 1 (192.168.0.2)이 Worker 2 (192.168.0.3)와 통신하고 싶다. 같은 subnet.
  • Worker 1은 Worker 2의 MAC을 모릅니다. L2 segment에 ARP broadcast: "192.168.0.3 가진 놈?"
  • Worker 2가 unicast로 답: "나야 — MAC AAAA.AAAA.AAAA."
  • Worker 1이 캐싱하고, 이후엔 그 MAC으로 일반 unicast L2 프레임을 보냅니다.

Cross-subnet — Proxy ARP다른 subnet으로 — Proxy ARP

Same idea but now Worker 1 (192.168.0.2 in subnet A) wants to reach Worker 4 (192.168.1.3 in subnet B). Different subnets, so the packet must go through a gateway / router.

같은 아이디어지만, 이번엔 Worker 1(subnet A의 192.168.0.2)이 Worker 4(subnet B의 192.168.1.3)에게 보내고 싶습니다. 다른 subnet이라 게이트웨이/라우터를 거쳐야 합니다.

But Worker 1 still needs a destination MAC for its L2 header. Solution: the gateway answers ARP requests for IPs that aren't its own — it says "send to my MAC, I'll forward it on." This is Proxy ARP.

Worker 1은 여전히 L2 헤더에 적을 어떤 목적지 MAC이 필요합니다. 해법: 게이트웨이가 자기 IP가 아닌 IP에 대한 ARP에도 응답합니다 — "그건 내 MAC으로 보내. 내가 대신 전달할게." 이게 Proxy ARP입니다.

Worker 1 ─── ARP "who has 192.168.1.3?" ───► ALL hosts in subnet A (broadcast) ◄── ARP reply "send to my MAC" ─── Gateway (proxy ARP) Worker 1 then ships the frame with [Dst MAC = Gateway MAC | Dst IP = Worker 4 IP] Gateway sees its own MAC but a foreign IP → routes the packet onward.

Subnet mask /32Subnet mask /32 의미

A subnet mask of /32 means "all 32 bits are network" — the subnet contains exactly one host. No L2 broadcast (there's nobody else to receive it). So a /32 interface can only do L3 traffic. (You'll see this in K8s pods: each pod often has a /32, so the host wires unique routing per pod via the kernel rather than a shared L2 segment.)

/32는 "32비트 전체가 네트워크" = subnet에 호스트가 하나뿐이라는 뜻. L2 broadcast가 의미 없습니다(받을 다른 호스트가 없으니까). 그래서 /32 인터페이스는 L3 통신만 가능. (K8s pod에서도 자주 보입니다: 각 pod이 /32라서 호스트는 공유 L2 대신 커널 라우팅으로 pod별 경로를 깔아줍니다.)

key takeaway핵심 정리 ARP turns IPs into MACs. The IP world (L3) and MAC world (L2) are stitched together by this one protocol. Every cross-network packet uses ARP at least once on each end. Without ARP, the L2 frame can't even be built. ARP는 IP를 MAC으로 바꿉니다. IP 세계(L3)와 MAC 세계(L2)는 이 한 프로토콜로 꿰매져 있습니다. 모든 네트워크 간 패킷은 양 끝에서 적어도 한 번 ARP를 씁니다. ARP 없이는 L2 프레임 자체가 못 만들어집니다.

5 VLAN — Virtual LAN VLAN — Virtual LAN (가상 LAN)

LAN = Local Area Network (one office's network, basically). A VLAN (Virtual LAN) is an OSI Layer-2 protocol that logically subdivides one big LAN into multiple LANs that don't share broadcast traffic.

LAN = Local Area Network (지역 통신망 — 보통 한 사무실 네트워크). VLAN(Virtual LAN, 가상 LAN)은 OSI Layer 2 프로토콜로, 큰 LAN 하나를 broadcast(브로드캐스트)를 공유하지 않는 여러 LAN으로 논리적으로 쪼갭니다.

Frame format — what actually changes프레임 포맷 — 실제로 뭐가 바뀌는가

Traditional Ethernet frame: [Dst MAC (6)] [Src MAC (6)] [Length/Type (2)] [Payload 46-1500] [FCS (4)] 802.1Q VLAN-tagged frame: [Dst MAC (6)] [Src MAC (6)] [TPID (2) | PRI (3b) | CFI (1b) | VID (12b)] [Length/Type (2)] [Payload] [FCS] └─────────────── 4 bytes inserted (VLAN tag) ──────────────┘

The added 4-byte VLAN tag contains:

추가된 4바이트 VLAN tag의 구성:

  • TPID (Tag Protocol Identifier, 16b) — fixed value 0x8100 telling the switch "I'm tagged"
  • PRI (Priority, 3b) — priority for QoS (Quality of Service), 8 levels
  • CFI (Canonical Format Indicator, 1b) — legacy
  • VID (VLAN Identifier, 12b) — the VLAN ID itself (0–4095)
  • TPID (Tag Protocol Identifier, 태그 프로토콜 식별자, 16b) — 0x8100 고정값. "나 태그 됨"을 스위치에게 알림
  • PRI (Priority, 우선순위, 3b) — QoS(Quality of Service, 서비스 품질)용, 8단계
  • CFI (Canonical Format Indicator, 정규 형식 표시자, 1b) — 예전 호환용
  • VID (VLAN Identifier, VLAN 식별자, 12b) — VLAN ID 자체 (0–4095)

Without VLANs, every broadcast hits every PC. With VLANs, each VLAN is its own bubble.VLAN 없으면 broadcast가 모든 PC에 도달, VLAN 쓰면 각 VLAN이 독립 영역.

analogy비유 VLAN is like splitting one shared apartment kitchen into private kitchens with separate fume hoods. Each "room" still uses the same physical building, but the smells don't mix. VLAN은 공용 주방을 칸막이 + 별도 환기구로 나누는 것과 같습니다. 물리 건물은 그대로지만 냄새가 안 섞입니다.

6–7 Why VXLAN ① — the STP problem, and the fix VXLAN을 쓰는 이유 ① — STP 문제와 해결

First, what is STP?먼저, STP가 뭐예요?

STP = Spanning Tree Protocol — an L2 protocol that prevents loops between switches.

STP = Spanning Tree Protocol(스패닝 트리 프로토콜) — 스위치 사이 루프를 막는 L2 프로토콜.

Why would loops happen? For redundancy, switches are wired with multiple links. If a frame can travel in a circle, a broadcast that started on one switch will be re-broadcast by the next switch, and the next, and the next — infinite loop. This is called a broadcasting storm and it brings the network down instantly.

왜 루프가 생기나? 이중화를 위해 스위치들 사이를 여러 링크로 묶어둡니다. 프레임이 원형으로 돌 수 있으면, 한 스위치에서 시작된 broadcast가 다음 스위치, 다음 스위치 ... 무한 루프. 이걸 broadcasting storm이라 하고, 네트워크가 바로 마비됩니다.

STP's solution: use an algorithm to elect one "root" switch, then for any extra/redundant link, mark it as blocked. Loops disappear. But blocked links are wasted bandwidth. Worse, recovery from a real link failure is slow (STP convergence).

STP의 해결: 알고리즘으로 "root" 스위치를 선출하고, 나머지 잉여 링크는 block으로 막아버립니다. 루프 사라짐. 하지만 block된 링크는 대역폭 낭비입니다. 게다가 진짜 링크 장애 시 복구가 느립니다(STP 수렴).

The blocked-link pictureblock된 링크 그림

STP wastes bandwidth by blocking links. VXLAN on L3 + ECMP uses every link.STP는 링크를 차단해 대역폭을 낭비. L3 위 VXLAN + ECMP는 모든 링크 활용.

VXLAN's escape (slide 7) — make L2 ride on L3VXLAN의 탈출 (슬라이드 7) — L2를 L3 위에서 굴림

If the access layer becomes L2 + VXLAN, the Leaf switches act as VTEPs (VXLAN Tunnel End Points). The fabric between Leaves runs as L3 routing (IP). No loops at L2 across the fabric, so STP is no longer needed.

Access Layer를 L2 + VXLAN으로 만들면, Leaf 스위치들이 VTEP(VXLAN Tunnel End Point, VXLAN 터널 종단점) 역할을 합니다. Leaf 사이 fabric은 L3 라우팅(IP)으로 동작. fabric에 L2 루프가 없으므로 STP가 더 이상 필요 없습니다.

Benefits:

장점:

  • Full bandwidth — no link is blocked
  • ECMP = Equal-Cost Multi-Path — traffic spreads across all equal-cost L3 paths
  • The host's vSwitch (virtual switch — a software switch inside the hypervisor or kernel) tags frames into a VLAN; the Leaf (VTEP) maps that VLAN to a VNI (VXLAN Network Identifier) and tunnels through
  • MAC-in-UDP encapsulation + multicast (not broadcast) for the leftover BUM (Broadcast / Unknown unicast / Multicast) traffic
  • Full 대역폭 — block되는 링크가 없음
  • ECMP = Equal-Cost Multi-Path (등가 다중 경로) — 같은 비용의 L3 경로 여러 개에 트래픽 분산
  • 호스트의 vSwitch(virtual switch, 가상 스위치 — 하이퍼바이저/커널 안의 소프트웨어 스위치)가 VLAN을 태깅; Leaf(VTEP)가 그 VLAN을 VNI(VXLAN Network Identifier)로 매핑해 터널링
  • MAC-in-UDP 캡슐화 + 남은 BUM(Broadcast / Unknown unicast / Multicast) 트래픽은 broadcast가 아니라 multicast로 처리
why this matters in the AI datacenterAI 데이터센터에서 왜 중요 A GPU server cluster needs very high bisection bandwidth. Losing half the links to STP is unacceptable when you're trying to push tens of GB/s of KV transfers (think: PD-disaggregated vLLM). VXLAN-over-L3 with ECMP is the standard answer. GPU 서버 클러스터는 매우 높은 bisection bandwidth가 필요합니다. KV 전송 수십 GB/s가 오가는데(PD 분리 vLLM 떠올리세요) STP 때문에 링크 절반이 놀고 있으면 안 됩니다. L3 위에 VXLAN + ECMP가 표준 답입니다.

8 Why VXLAN ② — MAC / ARP table limits VXLAN을 쓰는 이유 ② — MAC / ARP 테이블 한계

MAC learning, in plain wordsMAC Learning, 쉽게

A switch isn't pre-configured with "this MAC is on port 3." It learns by inspecting incoming frames: "I just saw a frame with source MAC X arriving on port 3 → so MAC X must live on port 3."

스위치는 처음부터 "이 MAC은 3번 포트"라고 설정돼 있지 않습니다. 들어오는 프레임을 보면서 학습합니다: "방금 3번 포트로 소스 MAC X가 들어왔다 → MAC X는 3번 포트에 있구나."

For an unknown destination, the switch floods the frame to all ports (except the source port). The right host replies; the switch learns. Once learned, it forwards directly. This is the Transparent Bridging model with its 5 verbs: Learning, Flooding, Forwarding, Aging, Filtering.

목적지를 모르면 스위치가 모든 포트(소스 포트만 빼고)로 flooding합니다. 맞는 호스트가 응답하면 스위치가 학습. 다음부턴 직접 forward. 이게 Transparent Bridging 모델이고, 5개 동작이 있습니다: Learning(학습), Flooding(쏟아냄), Forwarding(전달), Aging(만료), Filtering(거르기).

The problem — finite tables문제 — 테이블 크기가 한정

  • A leaf switch's MAC table holds only thousands–tens of thousands of entries (hardware limit).
  • One AI training cluster can easily have tens of thousands of VMs / pods in one L2 segment.
  • If your switch fills up, new MACs cause continuous flooding → tail latency spikes, lost packets, weird drops.
  • Leaf 스위치의 MAC table은 수천~수만 엔트리만 보유(하드웨어 제약).
  • AI 학습 클러스터 하나에 VM / pod 수만 개가 같은 L2 segment에 있을 수 있음.
  • 스위치가 꽉 차면 새 MAC마다 지속적 flooding → tail latency 튀고, 패킷 drop, 알 수 없는 이상.

VXLAN's reliefVXLAN의 해결

In VXLAN, the Leaf (VTEP) only needs to remember the MACs of VMs directly below it. For VMs on other Leaves, it only needs the destination VTEP's IP. So the per-switch MAC table is sized by "VMs on me," not "VMs in the universe." Far smaller.

VXLAN에서는 Leaf(VTEP)가 자기 밑 VM의 MAC만 알면 됩니다. 다른 Leaf 밑의 VM은 그 VTEP의 IP만 알면 충분. 즉 스위치별 MAC 테이블 크기는 "내 밑 VM 수"가 결정하고 "온 세상 VM 수"가 아닙니다. 훨씬 작음.

Bonus: Unknown destination handling changes too. Instead of broadcasting to every host on the L2, the VTEP sends to a known multicast group of other VTEPs — much less noise.

덤: Unknown destination 처리도 달라집니다. L2의 모든 호스트에 broadcast 대신, 약속된 multicast 그룹의 다른 VTEP들에만 보내므로 소음이 훨씬 적습니다.

실사용 가능한 VLAN은 약 4000개. 회사 사무실엔 충분한데, 수천 tenant(테넌트 = 같은 물리 인프라를 공유하는 고객들)에게 클라우드 VM(Virtual Machine, 가상 머신)을 팔고 각자 격리된 네트워크 여러 개를 원하면 4000은 하루 만에 동납니다.

Plus — VM migration across regions또 하나 — Region 간 VM 마이그레이션

In an IaaS (Infrastructure-as-a-Service — cloud rental of raw VMs and storage) world, a VM may need to "move" across AZs (Availability Zones — physically separate datacenter rooms) — e.g. live migration for scaling, failure, or maintenance — while keeping the same IP / same logical network. VLANs are pinned to a physical L2 segment — that doesn't scale. You need an overlay that follows the VM anywhere.

IaaS(Infrastructure-as-a-Service, 서비스로서의 인프라 — VM/스토리지를 빌려주는 클라우드 형태) 환경에선 VM이 AZ(Availability Zone, 가용 영역 — 물리적으로 분리된 데이터센터 구역) 사이를 "이동"해야 할 수 있습니다(스케일링, 장애, 점검 등으로 live migration) — 같은 IP, 같은 논리 네트워크를 유지하면서. VLAN은 물리 L2 세그먼트에 고정 → 확장 안 됨. VM을 따라다니는 오버레이가 필요합니다.

VXLAN's answerVXLAN의 답

VNI is 24 bits → ~16 million IDs. Cloud tenants and overlay networks live on this. And because the overlay rides on L3, the VM can move to any reachable host and its VNI follows.

VNI는 24비트 → 약 1,600만 개. 클라우드 테넌트 / 오버레이 네트워크가 여기 들어갑니다. L3 위 오버레이라서 도달 가능한 어느 호스트로 VM이 이동해도 VNI가 따라다닙니다.

AI/ML angleAI/ML 관점 When you run multi-tenant inference (each customer gets their own pods, their own model, isolated routing), you implicitly need a high VNI count. VXLAN-based CNIs in K8s scale to this naturally; classic VLANs cannot. 멀티 테넌트 추론 운영(각 고객마다 별도 pod, 별도 모델, 격리된 라우팅)을 하면 암묵적으로 높은 VNI 수가 필요합니다. K8s의 VXLAN 기반 CNI는 이걸 자연스럽게 확장하지만, 전통 VLAN으론 불가능합니다.

10 VXLAN MAC-in-UDP encapsulation (the key picture) VXLAN MAC-in-UDP 캡슐화 (핵심 그림)

This is the slide to actually internalize. Once you see the packet structure, VXLAN clicks.

이 슬라이드는 꼭 머리에 새겨두는 쪽이 좋습니다. 패킷 구조가 보이면 VXLAN이 한번에 이해됩니다.

What each piece does각 부분의 역할

  • Outer MAC (14 B) — the L2 header for the next physical hop on the underlay. Rewritten at every L3 router along the way (normal IP routing).
  • Outer IP (20 B) — source = sending VTEP IP, destination = receiving VTEP IP. This is what lets VXLAN ride on L3.
  • UDP (8 B) — destination port is the fixed VXLAN well-known port 4789. Source port is randomized per-flow (so ECMP hashes spread load).
  • VXLAN header (8 B) — 8 bits flags + 24 bits reserved + 24-bit VNI + 8 bits reserved. The VNI is the whole point.
  • Original Ethernet frame — the VM's L2 frame, byte-for-byte unchanged. This is the "MAC-in-UDP" part.
  • FCS — frame check sequence (CRC) for the outer frame.
  • Outer MAC (14 B) — underlay에서 다음 물리 hop을 위한 L2 헤더. 중간 L3 라우터마다 재작성됨(보통의 IP 라우팅).
  • Outer IP (20 B) — 송신 VTEP IP → 수신 VTEP IP. VXLAN이 L3 위로 갈 수 있게 해주는 핵심.
  • UDP (8 B) — 목적지 포트는 VXLAN 공식 포트 4789. 소스 포트는 flow마다 다르게 랜덤화(ECMP 해시가 잘 펴지도록).
  • VXLAN 헤더 (8 B) — flags 8b + reserved 24b + VNI 24b + reserved 8b. 이 헤더의 존재 이유가 VNI.
  • Original Ethernet frame — VM의 L2 프레임 그대로. "MAC-in-UDP"가 이 부분.
  • FCS — outer frame의 CRC.

The "tunnel" mental model"터널" 멘탈 모델

If you imagine the source VTEP and destination VTEP as two doors connected by a pipe, what travels through the pipe is "an L2 frame stuffed in an IP envelope." The intermediate routers don't know or care about the inner frame — they just see "an IP packet, destination = receiving VTEP." They route it normally. At the far end, the VTEP unwraps and delivers the original L2 frame to the target VM.

송신 VTEP와 수신 VTEP를 파이프로 연결된 두 문이라고 상상하면, 파이프로 흐르는 건 "IP 봉투에 담긴 L2 프레임"입니다. 중간 라우터들은 안쪽 프레임에 관심 없음 — "수신 VTEP가 목적지인 IP 패킷이네" 하고 보통의 IP 라우팅으로 보냅니다. 반대편에서 VTEP가 봉투를 까서 원본 L2 프레임을 목표 VM에 전달.

acronym recap약어 정리
  • VTEP = VXLAN Tunnel End Point (the wrap/unwrap door, usually a Leaf switch or a hypervisor's vSwitch)
  • VNI = VXLAN Network Identifier (24-bit ID = the new "VLAN" inside the tunnel)
  • Underlay = the L3 IP fabric between VTEPs (you set it up; OSPF/BGP routes it)
  • Overlay = the virtual L2 networks that ride on top, identified by VNIs
  • VTEP = VXLAN Tunnel End Point (캡슐화 양쪽 문, 보통 Leaf 스위치나 하이퍼바이저 vSwitch)
  • VNI = VXLAN Network Identifier (24-bit ID = 터널 안의 새 "VLAN")
  • Underlay = VTEP들 사이의 L3 IP fabric (당신이 깔고, OSPF/BGP가 라우팅)
  • Overlay = 그 위에 얹는 가상 L2 네트워크들, VNI로 구분

11 VM-to-VM unicast flow (the happy path) VM-to-VM 유니캐스트 흐름 (정상 경로)

Now that we know the packet shape, walk the journey end-to-end.

The full journey — VM doesn't know VXLAN exists.전체 여정 — VM은 VXLAN의 존재조차 모름.

Step-by-step단계 설명

  1. The source VM sends its original L2 frame (with Dst MAC = destination VM's MAC) into its host's vSwitch — same as if both VMs were on the same physical LAN.
  2. The kernel vSwitch (which is the local VTEP) recognizes this VNI's traffic, looks up "VM with that destination MAC lives behind which VTEP?", finds VTEP 2's IP, and wraps the frame as we saw in §10.
  3. The wrapped packet is an ordinary IP/UDP packet from VTEP 1's IP to VTEP 2's IP. The intermediate IP network (the underlay) doesn't know it's VXLAN — it routes it like any other UDP packet.
  4. VTEP 2 receives. Sees the UDP port is 4789 → "it's VXLAN" → strips the outer headers and recovers the original L2 frame.
  5. VTEP 2 delivers the original L2 frame to the destination VM, locally on its host. The destination VM has no idea VXLAN happened.
  1. 송신 VM이 원본 L2 프레임(목적지 MAC = 수신 VM MAC)을 호스트의 vSwitch로 보냅니다 — 둘이 같은 물리 LAN에 있는 것처럼.
  2. 커널 vSwitch(=로컬 VTEP)가 이 VNI 트래픽임을 인식, "그 목적지 MAC을 가진 VM은 어느 VTEP 뒤에 있나" 룩업해서 VTEP 2의 IP를 찾고, §10에서 본 대로 감쌉니다.
  3. 감싼 패킷은 그냥 VTEP 1 IP에서 VTEP 2 IP로 가는 IP/UDP 패킷. 중간 IP 네트워크(underlay)는 이게 VXLAN인지 모르고 일반 UDP처럼 라우팅합니다.
  4. VTEP 2가 받습니다. UDP 포트가 4789인 걸 보고 "VXLAN이구나" → outer 헤더를 벗기고 원본 L2 프레임 복원.
  5. VTEP 2가 호스트 안에서 원본 L2 프레임을 목적지 VM에 전달. 목적지 VM은 VXLAN이 있었는지조차 모릅니다.

The big property: end VMs see a "flat L2"; the network engineers see a routed L3 fabric. Best of both.

큰 그림의 성질: 끝단 VM에게는 "평평한 L2"가 보이고, 네트워크 엔지니어에게는 라우팅되는 L3 fabric이 보입니다. 양쪽 다 좋은 점만.

The bootstrap problem초기 문제

In §11 we glossed over a step: "the VTEP looks up the destination VM's MAC → which VTEP IP." But how does the VTEP learn that mapping in the first place? The very first time VM1 wants to reach VM2, VM1 doesn't even know VM2's MAC, and VTEP 1 doesn't know which VTEP holds VM2.

§11에서 슬쩍 넘긴 단계: "VTEP가 목적지 VM의 MAC → 어느 VTEP의 IP인지 룩업". 그런데 VTEP는 처음에 그 매핑을 어떻게 알게 될까요? VM1이 VM2와 처음 통신할 때, VM1은 VM2의 MAC도 모르고, VTEP 1은 VM2가 어느 VTEP 뒤에 있는지도 모릅니다.

Without a control plane, VTEP1 floods the ARP via a multicast group; VTEP2 replies unicast.컨트롤 플레인이 없으면 VTEP1이 multicast group으로 ARP를 뿌리고, VTEP2가 unicast로 답.

  1. VM1 sends an ARP broadcast inside its own host: "who has 192.168.10.3?"
  2. VTEP 1 catches it. Wraps it in UDP, but instead of sending unicast (it doesn't know where to), sends to a multicast group that all VTEPs in this VNI have joined.
  3. Every VTEP in that VNI receives the multicast, unwraps, and broadcasts inside its own host. VTEPs whose VMs don't match → discard.
  4. VM2 sees the ARP and unicast-replies. The reply rides home through VTEP 2 → VTEP 1 → VM1.
  5. Now VTEP 1 has learned "MAC of VM2 lives behind VTEP 2." Future packets go unicast.
  1. VM1이 자기 호스트 안에서 ARP broadcast: "192.168.10.3 가진 놈?"
  2. VTEP 1이 받습니다. UDP에 감싸지만 unicast로 어디로 보낼지 모르므로, 이 VNI의 모든 VTEP가 가입한 multicast 그룹으로 보냅니다.
  3. 그 VNI에 가입한 모든 VTEP가 multicast를 받고, 풀어서 자기 호스트 안에 broadcast. 자기 밑에 해당 MAC이 없는 VTEP는 그냥 버림.
  4. VM2가 보고 unicast로 ARP reply. 답은 VTEP 2 → VTEP 1 → VM1으로 돌아옵니다.
  5. 이제 VTEP 1이 "VM2의 MAC은 VTEP 2 뒤"라고 학습했습니다. 다음 패킷부턴 unicast.

Why "manual" VXLAN isn't enough왜 "Manual" VXLAN으론 부족한가

Multicast-driven flood-and-learn works, but it has problems:

Multicast 기반 flood-and-learn은 동작하지만 문제가 있습니다:

  • BUM traffic (Broadcast / Unknown unicast / Multicast) — every ARP, every "haven't seen this MAC yet" packet, every actual multicast → all multicast to all VTEPs in the VNI. Doesn't scale.
  • No graceful "VTEP X just left — drop its MACs" — table garbage accumulates.
  • Underlay must support multicast (PIM, IGMP) reliably — many real networks don't, or don't want to.
  • BUM 트래픽 (Broadcast / Unknown unicast / Multicast) — ARP마다, 처음 보는 MAC마다, 진짜 multicast마다 → 전부 VNI의 모든 VTEP로 multicast. 확장성 떨어짐.
  • "VTEP X가 떠났다 → 걔 MAC들 지워" 같은 깔끔한 정리가 어렵 — 테이블 쓰레기가 쌓임.
  • Underlay가 multicast(PIM, IGMP)를 안정적으로 지원해야 함 — 실제 많은 네트워크가 안 지원하거나 안 쓰고 싶어 함.

Enter EVPN — Ethernet VPNEVPN — Ethernet VPN 등장

EVPN separates the data plane (= VXLAN forwarding, unchanged) from a control plane (= a protocol that explicitly distributes MAC ↔ VTEP IP mappings between VTEPs). The control plane is MP-BGP (next slides). So:

EVPN은 데이터 플레인(= VXLAN 포워딩, 그대로)과 컨트롤 플레인(= MAC ↔ VTEP IP 매핑을 VTEP 사이에 명시적으로 분배하는 프로토콜)을 분리합니다. 컨트롤 플레인은 MP-BGP(다음 슬라이드들). 그래서:

  • No flood-and-learn. VTEPs announce their local MACs via BGP. Other VTEPs learn directly.
  • No multicast needed in the underlay. BUM can be handled with ingress replication (unicast copies) or other techniques.
  • VM moves between hosts → BGP withdraw + re-advertise, cleanly.
  • flood-and-learn 없음. VTEP가 자기 밑 로컬 MAC을 BGP로 광고. 다른 VTEP는 직접 학습.
  • underlay에 multicast 필요 없음. BUM은 ingress replication(unicast 복사) 등 다른 방법으로 처리 가능.
  • VM이 호스트 사이 이동 → BGP withdraw + 재광고로 깔끔하게.

Where BGP sits in the family — under Dynamic, in the Path Vector camp.BGP의 위치 — Dynamic 아래 Path Vector 분류.

Quick taxonomy:

간단 분류:

  • Static — hand-configured. Doesn't react to topology changes.
  • Distance Vector (RIP) — "I'm N hops from you." Simple, slow, doesn't scale.
  • Link-State (OSPF, IS-IS) — every router publishes its own connections; everyone computes shortest paths. Great inside one administrative domain.
  • Path Vector (BGP) — carries the full path of ASes (Autonomous Systems). Designed for the internet, where policy matters more than shortest distance.
  • Static — 수동 설정. 토폴로지 변화에 반응 안 함.
  • Distance Vector (RIP) — "나 너로부터 N hop". 간단하고 느리고 확장성 ↓.
  • Link-State (OSPF, IS-IS) — 모든 라우터가 자기 연결을 광고, 다같이 최단경로 계산. 단일 관리 도메인에 적합.
  • Path Vector (BGP) — AS(Autonomous System) 경로 전체를 나름. 인터넷용 — 최단거리보다 정책이 더 중요.

What is BGP?BGP는 뭐예요?

BGP (Border Gateway Protocol) is the protocol that runs the internet. It exchanges reachability info between ASes (autonomous systems — each big ISP/cloud/company is one). Runs over TCP. Default flavor only carries IPv4 unicast routes.

BGP(Border Gateway Protocol)는 인터넷을 굴리는 프로토콜. AS(Autonomous System — 각 큰 ISP/클라우드/회사가 하나의 AS) 사이에 도달성 정보를 교환합니다. TCP 위에서 동작. 기본형은 IPv4 unicast 경로만 나릅니다.

MP-BGP — Multi-Protocol extensionsMP-BGP — Multi-Protocol 확장

Plain BGP advertises "this IPv4 prefix is reachable via this next hop." That's it. But what if you also want to advertise IPv6 prefixes, or VPN-tagged prefixes (so customer A's 192.168.2.0/24 is a different route from customer B's), or MAC addresses of VMs and their VTEPs?

일반 BGP는 "이 IPv4 prefix는 이 next hop으로 도달 가능"만 광고. 그게 전부. 하지만 IPv6 prefix도, VPN 식별자 붙은 prefix도(고객 A의 192.168.2.0/24과 고객 B의 그것을 다른 경로로), 더 나아가 VM의 MAC 주소 + 그 VTEP도 광고하고 싶다면?

MP-BGP (Multi-Protocol BGP) extends the BGP message format with Address Families (AF) and Sub-Address Families (SAFI). Each address family is a different kind of "thing you can advertise."

MP-BGP(Multi-Protocol BGP)는 BGP 메시지에 Address Family(AF)와 Sub-Address Family(SAFI) 개념을 추가합니다. 각 address family는 "광고할 수 있는 것의 종류".

The pain MPLS solvesMPLS가 해결한 고통

Normal IP routing: at every hop, the router parses the IP header, does a longest-prefix match against its routing table (which can have millions of entries on a backbone router), and forwards. That lookup is expensive.

일반 IP 라우팅: 매 hop마다 라우터가 IP 헤더를 파싱하고, 라우팅 테이블(백본 라우터는 수백만 엔트리)에 longest-prefix match를 한 뒤 forward. 이 룩업이 비쌉니다.

MPLS — Multiprotocol Label SwitchingMPLS — Multiprotocol Label Switching

MPLS replaces the per-hop expensive lookup with a fixed-length label lookup. The first hop (Ingress PE) classifies the packet into a Forwarding Equivalence Class (FEC) and attaches a short label. Each subsequent router (Provider router) does a simple label-swap (fast). The last hop (Egress PE) strips the label and delivers.

MPLS는 매 hop의 비싼 룩업을 고정 길이 라벨 룩업으로 바꿉니다. 첫 hop(Ingress PE)이 패킷을 FEC(Forwarding Equivalence Class — 같은 경로로 갈 패킷 묶음)로 분류하고 짧은 라벨을 붙임. 그 다음 라우터들(Provider 라우터)은 단순 label-swap(빠름). 마지막 hop(Egress PE)에서 라벨을 떼고 전달.

Push label at the door, swap label inside, pop label at the exit.입구에서 라벨 push, 내부에서 swap, 출구에서 pop.

Label header format라벨 헤더 포맷

[Link layer header] [Outer label] [Inner label] [Layer 3 packet] ▲ ▲ │ │ "transport label" "VPN/service label" (which path?) (which customer/service?)

MPLS supports a stack of labels. Typical use: outer label = how to reach the far PE, inner label = which VRF (customer) to deliver to. This is how carriers tunnel customer L3 VPN traffic.

MPLS는 라벨 스택을 지원합니다. 전형적 사용: outer label = 먼 PE까지의 경로, inner label = 어느 VRF(고객)에 전달할지. 통신사가 고객 L3 VPN 트래픽을 터널링하는 방식.

How does VXLAN relate?VXLAN과의 관계?

In a carrier or large enterprise:

통신사 또는 대형 엔터프라이즈에서:

  • Inside a single data center: VXLAN as the overlay (L2 over IP), BGP-EVPN as the control plane.
  • Between data centers / across the WAN: MPLS often carries the inter-DC VPN, sometimes wrapping VXLAN, sometimes via dedicated services (EVPN-MPLS).
  • EVPN as a control plane is encapsulation-agnostic — it can drive either VXLAN-encapped forwarding or MPLS-encapped forwarding. The same BGP messages.
  • 한 데이터센터 내부: VXLAN을 오버레이(L2 over IP)로, BGP-EVPN을 컨트롤 플레인으로.
  • 데이터센터 간 / WAN: MPLS가 inter-DC VPN을 자주 나름. VXLAN을 감싸기도, 별도 서비스(EVPN-MPLS)로 가기도.
  • EVPN은 컨트롤 플레인이 인캡슐레이션 불가지론적 — VXLAN-인캡슐 포워딩이든 MPLS-인캡슐 포워딩이든 같은 BGP 메시지로 굴립니다.

여기까지 온 이유:

  1. Traditional L2 has limits: 4096 VLANs, STP wasting links, MAC tables overflow, broadcast domains pinned to physical segments.
  2. Datacenter / cloud needs to push past all of these — many tenants, big bandwidth, mobility.
  3. VXLAN wraps L2 frames in UDP/IP — a virtual L2 over any L3 fabric. 16M VNIs, no STP needed, ECMP-friendly.
  4. But raw VXLAN still relies on multicast flood-and-learn → doesn't scale cleanly.
  5. EVPN separates control from data: VTEPs advertise their MACs via MP-BGP. No more flood-and-learn.
  6. MP-BGP is the same protocol used for carrier L3 VPNs (Address Families: VPNv4 / EVPN / etc).
  7. The carrier core often runs MPLS for label-switched forwarding; EVPN can sit on top of either VXLAN or MPLS.
  1. 전통 L2의 한계: VLAN 4096개, STP가 링크 낭비, MAC 테이블 폭발, broadcast 도메인이 물리 세그먼트에 고정.
  2. 데이터센터/클라우드는 이 모든 걸 넘어야 함 — 많은 테넌트, 큰 대역폭, 모빌리티.
  3. VXLAN이 L2 프레임을 UDP/IP에 감싸 — 어떤 L3 fabric 위에서도 가상 L2. VNI 1,600만, STP 불필요, ECMP 친화적.
  4. 하지만 raw VXLAN은 여전히 multicast flood-and-learn에 의존 → 깔끔한 확장 ✗.
  5. EVPN이 컨트롤과 데이터를 분리: VTEP가 자기 MAC을 MP-BGP로 광고. flood-and-learn 종말.
  6. MP-BGP는 통신사 L3 VPN에 쓰던 그 프로토콜과 동일 (Address Family: VPNv4 / EVPN 등).
  7. 통신사 코어는 MPLS로 라벨 스위칭. EVPN은 VXLAN 위든 MPLS 위든 같이 갈 수 있음.

In your inference setup:

  • K8s pods on the same node: usually a bridge (pure L2 inside the host).
  • K8s pods across nodes: an overlay — almost always VXLAN (Flannel-VXLAN, Calico-VXLAN, Cilium can do native routing or VXLAN, etc.).
  • Inference cluster across availability zones: probably EVPN-VXLAN, or VXLAN tunneled through MPLS WAN.
  • "Why is GPU node X unable to send KV blocks to GPU node Y?" — the answer is often "the VXLAN tunnel between their hypervisors is broken, or MTU is too small to fit VXLAN overhead, or BGP-EVPN didn't advertise the MAC yet."

너 추론 환경에 대입하면:

  • 같은 노드 안 K8s pod: 보통 브리지(호스트 내부 순수 L2).
  • 다른 노드 간 K8s pod: 오버레이 — 거의 항상 VXLAN (Flannel-VXLAN, Calico-VXLAN, Cilium은 네이티브 라우팅이나 VXLAN, 등).
  • AZ 사이 추론 클러스터: 십중팔구 EVPN-VXLAN, 또는 MPLS WAN을 통해 VXLAN 터널링.
  • "왜 GPU 노드 X가 GPU 노드 Y한테 KV block을 못 보내?" — 답은 종종 "두 하이퍼바이저 사이 VXLAN 터널이 깨졌거나, MTU가 작아서 VXLAN 오버헤드를 못 담거나, BGP-EVPN이 그 MAC을 아직 광고하지 않았거나."
