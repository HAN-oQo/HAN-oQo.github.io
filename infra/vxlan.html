0.1 Networks are built in "Layers" 네트워크는 "계층(Layer)"으로 만들어져 있다

Networking is organized as the OSI (Open Systems Interconnection) 7-layer model. "L2" and "L3" in the slides mean Layer 2 and Layer 3, the only two we dig into.

통신은 OSI(Open Systems Interconnection) 7계층 모델로 정리된다. 슬라이드의 "L2", "L3"는 Layer 2, Layer 3의 줄임말이고, 이 글은 이 둘만 다룬다.

L7 Application ← your app (browser, Slack, gRPC ...) L6 Presentation ← data format (often skipped) L5 Session ← session management L4 Transport ← TCP (Transmission Control Protocol) / UDP (User Datagram Protocol) L3 Network ← IP (Internet Protocol) — which network to deliver to ⭐ L2 Data Link ← MAC (Media Access Control) — who to give it to on this cable ⭐ L1 Physical ← wires, fiber — electrical signals
Analogy비유

Like sending a letter:

  • L1 = the postal trucks & roads (physical infra)
  • L2 = the mailman delivering inside one neighborhood
  • L3 = Seoul → Busan delivery (postal offices route between cities)
  • L4 = registered mail vs. regular mail (reliability)
  • L7 = the actual content of the letter

편지 보내기에 빗대면 이렇다.

  • L1 = 우편 트럭이 달리는 도로 (물리 인프라)
  • L2 = 동네 안 집배원 배달
  • L3 = 서울 → 부산 배송 (우체국이 경로를 찾음)
  • L4 = 등기우편 vs 일반우편 (신뢰성)
  • L7 = 편지에 적힌 실제 내용

0.2 MAC address vs IP address — every computer has two MAC 주소 vs IP 주소: 컴퓨터마다 두 개

Your laptop has two addresses, at different layers with different jobs. MAC is "Media Access Control" (not Apple Macs), IP is "Internet Protocol."

노트북에는 주소가 두 개 있고, 계층과 역할이 다르다. MAC은 "Media Access Control"(애플 맥과 무관), IP는 "Internet Protocol"이다.

Why both? With only IP, a switch with 10 computers on one cable wouldn't know whom to hand the packet to. With only MAC, nobody could route across the planet (no one memorizes 280 trillion MACs). IP finds the "neighborhood", MAC finds the "person in it."

왜 둘 다 필요할까? IP만 있으면 케이블 하나에 컴퓨터 10대가 있을 때 누구에게 줄지 모른다. MAC만 있으면 전 세계 MAC을 외울 수 없으니 경로를 못 찾는다. 그래서 IP로 "동네"를 찾고 MAC으로 "그 동네의 누구"를 찾는다.

0.3 Subnet — a group of "neighborly" IPs Subnet: 같은 "동네"인 IP 묶음

Subnet (short for "sub-network") means "a group of IPs that share the same local network." Written like 192.168.0.0/24 — the /24 means "the first 24 bits are the network part; the last 8 bits identify the host inside." So 192.168.0.1 through 192.168.0.254 are in the same neighborhood. (The /24 notation is called CIDR — Classless Inter-Domain Routing.)

Subnet(sub-network)은 같은 로컬 네트워크를 쓰는 IP 묶음이다. 192.168.0.0/24처럼 적고, /24는 앞 24비트가 네트워크 부분, 뒤 8비트가 호스트라는 뜻이다. 그래서 192.168.0.1 ~ 192.168.0.254가 같은 동네다. 이 표기법을 CIDR(Classless Inter-Domain Routing)라 부른다.

  • Same subnet → talk via L2 directly (just a switch is enough)
  • Different subnet → need L3 (a router / gateway between)
  • 같은 subnet → L2로 직접 통신 (스위치면 충분)
  • 다른 subnet → L3 필요 (라우터/게이트웨이 경유)
Analogy비유 Same apartment complex, building 1 ↔ building 2 — you can walk (L2). Different complex — you need a road and a car (L3). 같은 아파트 단지 1동 ↔ 2동은 걸어가고(L2), 옆 단지는 도로와 차가 필요하다(L3).

0.5 Unicast / Broadcast / Multicast — three ways to send Unicast / Broadcast / Multicast: 패킷 보내는 3가지 방식

  • Unicast: A → B. one-to-one (the common case)
  • Broadcast: A → everyone. all hosts in the same subnet receive it ("hello, who's here?")
  • Multicast: A → subscribers only. like "subscribers of this channel receive this"
  • Unicast: A → B. 1대1 (제일 흔함)
  • Broadcast: A → 모두. 같은 subnet의 모든 호스트가 받음 ("여기 누구 있어요?")
  • Multicast: A → 가입자만 ("이 채널 구독자만")
Important중요 Broadcast does not cross subnets. If it did, the entire internet would scream at itself. Routers block broadcasts at the L3 boundary. Broadcast는 subnet을 넘지 못한다. 넘으면 인터넷 전체가 서로에게 소리치게 되므로 라우터가 L3 경계에서 막는다.

0.6 ARP — turning an IP into a MAC ARP: IP를 MAC으로 바꾸기

To send to 192.168.0.10, the L2 header needs a MAC we don't know yet. ARP shouts a broadcast: "who has 192.168.0.10? Tell me your MAC!" Only that host answers (unicast): "my MAC is aa:bb:cc:dd:ee:ff." You cache it in the ARP table.

192.168.0.10에 보내려면 L2 헤더에 MAC이 필요한데 아직 모른다. 그래서 ARP가 "192.168.0.10 가진 사람, MAC 알려줘!"라고 broadcast로 묻는다. 그 IP를 가진 호스트만 "내 MAC은 aa:bb:cc:dd:ee:ff"라고 unicast로 답하고, 보낸 쪽은 이를 ARP 테이블에 캐싱한다.

# the ARP table on a Linux machine
$ ip neigh show
192.168.0.1  dev eth0  lladdr aa:bb:cc:00:00:01  REACHABLE
192.168.0.10 dev eth0  lladdr aa:bb:cc:dd:ee:ff  REACHABLE

0.7 Encapsulation — packets are onions Encapsulation: 패킷은 양파

A packet is wrapped in layers. Each layer prepends its own header (this process is called encapsulation):

패킷은 여러 겹이다. 각 계층이 자기 헤더를 앞에 붙이고, 이를 encapsulation(캡슐화)이라 한다.

[L2 hdr | L3 hdr | L4 hdr | Application data] MAC IP port your message

The receiver peels them off in reverse (decapsulation). VXLAN's trick: stuff an already-finished L2 frame inside another packet, like a sealed envelope in a bigger box (slide 10).

받는 쪽은 반대로 한 겹씩 벗긴다(decapsulation). VXLAN은 완성된 L2 프레임을 통째로 다른 패킷 안에 넣는다. 봉투를 더 큰 상자에 넣는 셈이고, 슬라이드 10에서 다룬다.

0.8 VLAN — slicing one cable into many "neighborhoods" VLAN: 한 케이블을 여러 "동네"로 쪼개기

100 office PCs share one big switch, but Sales' broadcasts shouldn't reach Engineering. VLAN keeps one physical switch but splits it into logical LANs: Sales is VLAN 10, Engineering VLAN 20, and a broadcast stays inside its VLAN.

사무실 PC 100대가 대형 스위치 하나에 꽂혀 있어도 영업팀 broadcast가 개발팀에 들리면 안 된다. VLAN은 물리 스위치 하나를 논리적으로 여러 LAN으로 나눈다. 영업팀은 VLAN 10, 개발팀은 VLAN 20이고, broadcast는 자기 VLAN 안에서만 돈다.

VLAN ID is 12 bits → up to 4096: plenty for an office, far too few for a cloud datacenter with tens of thousands of tenants × subnets (slide 9).

VLAN ID는 12비트라 최대 4096개다. 회사에는 충분하지만 수만 테넌트가 각자 여러 subnet을 쓰는 클라우드 데이터센터에는 턱없이 부족하다(슬라이드 9).

0.9 So what is VXLAN? 그래서 VXLAN이란?

one-line definition한 줄 정의 VXLAN solves VLAN's limits (4096 IDs, broadcast confinement) by wrapping L2 frames inside UDP/IP — creating a virtual L2 tunnel that rides on top of any L3 network. VXLAN은 VLAN의 한계(4096개, broadcast 제약)를 넘으려고 L2 프레임을 UDP/IP로 캡슐화해 L3 네트워크 위를 지나는 가상 L2 터널을 만든다.

Example: HQ and a branch office want their PCs on one LAN although the internet (L3) sits between them. VXLAN tunnels the L2 frames through. Two terms that recur:

예를 들어 본사와 지사 PC가 사이에 인터넷(L3)을 두고도 같은 LAN처럼 동작하게 하려면 VXLAN으로 L2 프레임을 터널링한다. 계속 나올 용어는 두 개다.

  • VTEP (VXLAN Tunnel End Point) — the door at each end of the tunnel; does the L2 ↔ VXLAN wrapping
  • VNI (VXLAN Network Identifier) — the new "VLAN ID", but 24 bits → ~16 million IDs
  • VTEP (VXLAN Tunnel End Point): 터널 양 끝의 문. L2 ↔ VXLAN 변환 담당
  • VNI (VXLAN Network Identifier): VLAN ID를 대체하는 24비트 ID, 약 1,600만 개
AI/ML side noteAI/ML 사이드 노트

K8s clusters running vLLM/SGLang usually have a pod network: a virtual L2 that lets pods on different nodes talk as if on one cable, almost always VXLAN (Flannel, Calico-VXLAN, etc.). Debugging "pod can't reach pod" or "KV transfer is slow" often means debugging VXLAN.

vLLM/SGLang을 띄우는 K8s 클러스터에는 대개 pod 네트워크가 있다. 다른 노드의 pod끼리 같은 케이블에 있는 것처럼 통신하게 하는 가상 L2이고, 거의 VXLAN(Flannel, Calico-VXLAN 등)이다. "pod 간 통신 안 됨", "KV 전송이 느림"을 파고들면 VXLAN을 디버깅하게 되는 경우가 많다.

The three tables in one breath세 표 한입에

  • Routing table — "for this destination IP, which interface / gateway do I send out?" (L3 decision)
  • ARP table — "for this IP on my local subnet, what's its MAC?" (L3 → L2 bridge)
  • MAC table — (lives on the switch) "for this destination MAC, which port?" (L2 decision)
  • Routing table: 이 목적지 IP를 어느 인터페이스/게이트웨이로 내보낼지 (L3 결정)
  • ARP table: 내 subnet에 있는 이 IP의 MAC (L3↔L2 연결)
  • MAC table: (스위치에 있음) 이 목적지 MAC이 어느 포트인지 (L2 결정)

Why "Direct" only needs the routing table왜 Direct는 라우팅 테이블만 필요한가

With two boxes wired back-to-back, a packet can only go to the other end of the cable. No ARP, no switch port lookup: the routing table just needs "for that subnet, send out this interface."

케이블로 직결된 두 컴퓨터 사이에서 패킷이 갈 곳은 반대편 하나뿐이다. ARP도 스위치 포트 조회도 필요 없고, routing table에 "이 subnet은 이 인터페이스로"라는 항목만 있으면 된다.

L2 and L3 both need all three? Why?L2와 L3는 왜 세 표가 다 필요한가

With a switch in the path, it must know which port a MAC lives on (MAC table). To address by MAC, the host first resolves IP → MAC (ARP table). The routing table is always checked first to decide local (ARP) vs remote (gateway).

경로에 스위치가 있으면 스위치는 MAC이 어느 포트에 있는지 알아야 한다(MAC table). 호스트는 MAC을 적기 전에 IP의 MAC을 알아내야 한다(ARP table). 그리고 언제나 routing table을 먼저 보고 목적지가 같은 subnet(ARP)인지 다른 subnet(게이트웨이)인지 정한다.

4 ARP — Address Resolution Protocol ARP: Address Resolution Protocol

We met ARP (Address Resolution Protocol) briefly in §0.6. The slide goes deeper with a specific scenario across multiple subnets.

ARP(Address Resolution Protocol)는 0.6에서 봤다. 슬라이드는 여러 subnet에 걸친 시나리오로 더 들어간다.

Same-subnet ARP vs Proxy ARP across subnets.같은 subnet ARP vs subnet 간 Proxy ARP.

Same-subnet ARP (the basic case)같은 subnet ARP (기본 케이스)

  • Worker 1 (192.168.0.2) wants to talk to Worker 2 (192.168.0.3). Same subnet.
  • Worker 1 doesn't know Worker 2's MAC. Sends an ARP broadcast on the L2 segment: "Who has 192.168.0.3?"
  • Worker 2 replies unicast: "I do — MAC AAAA.AAAA.AAAA."
  • Worker 1 caches the mapping and now ships normal unicast L2 frames to that MAC.
  • Worker 1 (192.168.0.2)이 같은 subnet의 Worker 2 (192.168.0.3)에게 보내려 한다.
  • Worker 2의 MAC을 모르므로 L2 segment에 ARP broadcast를 보낸다: "192.168.0.3 누구?"
  • Worker 2가 unicast로 답한다: "나, MAC AAAA.AAAA.AAAA."
  • Worker 1은 이를 캐싱하고 그 MAC으로 일반 unicast L2 프레임을 보낸다.

Cross-subnet — Proxy ARP다른 subnet으로: Proxy ARP

Now Worker 1 (192.168.0.2, subnet A) wants Worker 4 (192.168.1.3, subnet B), so the packet must pass a gateway. Worker 1 still needs a destination MAC, so the gateway answers ARP for IPs that aren't its own: "send to my MAC, I'll forward it." This is Proxy ARP.

이번엔 Worker 1(subnet A, 192.168.0.2)이 Worker 4(subnet B, 192.168.1.3)에게 보낸다. 다른 subnet이라 게이트웨이를 거쳐야 하지만 L2 헤더에 적을 목적지 MAC은 여전히 필요하다. 그래서 게이트웨이가 자기 IP가 아닌 ARP에도 "내 MAC으로 보내면 전달해 줄게"라고 답한다. 이것이 Proxy ARP다.

Worker 1 ─── ARP "who has 192.168.1.3?" ───► ALL hosts in subnet A (broadcast) ◄── ARP reply "send to my MAC" ─── Gateway (proxy ARP) Worker 1 then ships the frame with [Dst MAC = Gateway MAC | Dst IP = Worker 4 IP] Gateway sees its own MAC but a foreign IP → routes the packet onward.

Subnet mask /32Subnet mask /32 의미

/32 means all 32 bits are network: the subnet holds exactly one host, so there is no L2 broadcast and the interface does only L3. K8s pods often get a /32, and the host routes to each pod via the kernel instead of a shared L2 segment.

/32는 32비트 전체가 네트워크라 subnet에 호스트가 하나뿐이다. 받을 상대가 없으니 L2 broadcast가 없고 L3 통신만 한다. K8s pod도 흔히 /32를 받고, 호스트는 공유 L2 대신 커널 라우팅으로 pod별 경로를 깐다.

key takeaway핵심 정리 ARP stitches the IP world (L3) to the MAC world (L2). Without it the L2 frame can't even be built. ARP는 IP 세계(L3)와 MAC 세계(L2)를 잇는다. ARP가 없으면 L2 프레임을 만들 수조차 없다.

5 VLAN — Virtual LAN VLAN: Virtual LAN

LAN = Local Area Network (roughly, one office's network). VLAN is a Layer-2 protocol that splits one LAN into several that don't share broadcasts.

LAN은 Local Area Network(대개 사무실 하나의 네트워크)다. VLAN은 LAN 하나를 broadcast를 공유하지 않는 여러 LAN으로 나누는 L2 프로토콜이다.

Frame format — what actually changes프레임 포맷: 무엇이 바뀌나

6–7 Why VXLAN ① — the STP problem, and the fix VXLAN을 쓰는 이유 ①: STP 문제와 해결

First, what is STP?먼저, STP란

STP = Spanning Tree Protocol — an L2 protocol that prevents loops between switches.

STP(Spanning Tree Protocol)는 스위치 사이 루프를 막는 L2 프로토콜이다.

Switches are wired with multiple links for redundancy. If a frame can travel in a circle, a broadcast gets re-broadcast switch after switch forever: a broadcasting storm that takes the network down instantly.

이중화를 위해 스위치 사이를 여러 링크로 묶는다. 프레임이 원을 그릴 수 있으면 broadcast가 스위치마다 다시 퍼져 끝없이 돈다. 이것이 broadcasting storm이고, 네트워크가 즉시 마비된다.

STP's fix: elect a "root" switch and mark every redundant link blocked. Loops vanish, but blocked links waste bandwidth, and recovery from a real failure is slow (STP convergence).

STP는 "root" 스위치를 뽑고 잉여 링크를 block한다. 루프는 사라지지만 block된 링크만큼 대역폭이 낭비되고, 실제 장애 때 복구도 느리다(STP 수렴).

The blocked-link pictureblock된 링크 그림

STP wastes bandwidth by blocking links. VXLAN on L3 + ECMP uses every link.STP는 링크를 막아 대역폭을 낭비하고, L3 위 VXLAN + ECMP는 모든 링크를 쓴다.

VXLAN's escape (slide 7) — make L2 ride on L3VXLAN의 탈출 (슬라이드 7): L2를 L3 위에 태운다

With an L2 + VXLAN access layer, Leaf switches act as VTEPs (VXLAN Tunnel End Points) and the fabric between them runs L3 routing (IP). No L2 loops across the fabric, so no STP. Benefits:

Access Layer를 L2 + VXLAN으로 바꾸면 Leaf 스위치가 VTEP(VXLAN Tunnel End Point)가 되고, Leaf 사이 fabric은 L3 라우팅(IP)으로 돈다. fabric에 L2 루프가 없으니 STP도 필요 없다. 장점은 다음과 같다.

  • Full bandwidth — no link is blocked
  • ECMP = Equal-Cost Multi-Path — traffic spreads across all equal-cost L3 paths
  • The host's vSwitch (virtual switch — a software switch inside the hypervisor or kernel) tags frames into a VLAN; the Leaf (VTEP) maps that VLAN to a VNI (VXLAN Network Identifier) and tunnels through
  • MAC-in-UDP encapsulation + multicast (not broadcast) for the leftover BUM (Broadcast / Unknown unicast / Multicast) traffic
  • Full 대역폭: block되는 링크가 없음
  • ECMP(Equal-Cost Multi-Path): 비용이 같은 L3 경로 여러 개로 트래픽 분산
  • 호스트의 vSwitch(하이퍼바이저/커널 안의 소프트웨어 스위치)가 VLAN을 태깅하고, Leaf(VTEP)가 그 VLAN을 VNI로 매핑해 터널링
  • MAC-in-UDP 캡슐화. 남은 BUM(Broadcast / Unknown unicast / Multicast) 트래픽은 broadcast 대신 multicast로 처리
why this matters in the AI datacenterAI 데이터센터에서 왜 중요 A GPU server cluster needs very high bisection bandwidth. Losing half the links to STP is unacceptable when you're trying to push tens of GB/s of KV transfers (think: PD-disaggregated vLLM). VXLAN-over-L3 with ECMP is the standard answer. GPU 클러스터는 bisection bandwidth가 매우 높아야 한다. PD 분리 vLLM처럼 KV 전송이 수십 GB/s 오가는데 STP 때문에 링크 절반을 놀릴 수는 없다. L3 위 VXLAN + ECMP가 표준 해법이다.

8 Why VXLAN ② — MAC / ARP table limits VXLAN을 쓰는 이유 ②: MAC / ARP 테이블 한계

MAC learning, in plain wordsMAC Learning, 쉽게

A switch learns MAC locations from incoming frames: "source MAC X arrived on port 3 → X lives on port 3." For an unknown destination it floods all ports except the source; the right host replies and the switch learns. This is Transparent Bridging, with 5 verbs: Learning, Flooding, Forwarding, Aging, Filtering.

스위치는 들어오는 프레임으로 MAC 위치를 학습한다. "3번 포트로 소스 MAC X가 들어왔으니 X는 3번 포트에 있다"는 식이다. 목적지를 모르면 소스 포트를 뺀 모든 포트로 flooding하고, 맞는 호스트가 답하면 학습한다. 이것이 Transparent Bridging이고 동작은 5개다: Learning, Flooding, Forwarding, Aging, Filtering.

The problem — finite tables문제: 테이블 크기가 한정돼 있다

  • A leaf switch's MAC table holds only thousands–tens of thousands of entries (hardware limit).
  • One AI training cluster can easily have tens of thousands of VMs / pods in one L2 segment.
  • If your switch fills up, new MACs cause continuous flooding → tail latency spikes, lost packets, weird drops.
  • Leaf 스위치의 MAC table은 수천~수만 엔트리가 한계다(하드웨어 제약).
  • AI 학습 클러스터 하나의 L2 segment에 VM / pod가 수만 개 있을 수 있다.
  • 테이블이 차면 새 MAC마다 flooding이 계속되어 tail latency 급등과 패킷 drop이 생긴다.

VXLAN's reliefVXLAN의 해결

In VXLAN the Leaf (VTEP) only remembers MACs of VMs directly below it; for VMs elsewhere it needs just the remote VTEP's IP. The table scales with "VMs on me," not "VMs in the universe." Unknown destinations go to a multicast group of VTEPs instead of a broadcast to every host.

VXLAN에서는 Leaf(VTEP)가 자기 아래 VM의 MAC만 기억하고, 다른 Leaf의 VM은 그 VTEP의 IP만 알면 된다. 테이블 크기가 "온 세상 VM 수"가 아니라 "내 아래 VM 수"로 정해진다. Unknown destination도 모든 호스트에 broadcast하지 않고 약속된 multicast 그룹의 VTEP에만 보낸다.

In IaaS (Infrastructure-as-a-Service), a VM may live-migrate across AZs (Availability Zones) for scaling, failure or maintenance while keeping its IP and logical network. VLANs are pinned to a physical L2 segment, so you need an overlay that follows the VM.

IaaS(Infrastructure-as-a-Service)에서는 VM이 스케일링·장애·점검 때문에 IP와 논리 네트워크를 유지한 채 AZ(Availability Zone) 사이를 live migration할 수 있다. VLAN은 물리 L2 세그먼트에 묶여 있으니 VM을 따라다니는 오버레이가 필요하다.

VNI is 24 bits → ~16 million IDs, and because the overlay rides on L3, a VM can move to any reachable host and its VNI follows.

VNI는 24비트, 약 1,600만 개다. 오버레이가 L3 위에 있으니 VM이 도달 가능한 어느 호스트로 옮겨도 VNI가 따라간다.

10 VXLAN MAC-in-UDP encapsulation (the key picture) VXLAN MAC-in-UDP 캡슐화 (핵심 그림)

Once you see this packet structure, VXLAN clicks.

이 패킷 구조가 보이면 VXLAN이 이해된다.

What each piece does각 부분의 역할

  • Outer MAC (14 B) — the L2 header for the next physical hop on the underlay. Rewritten at every L3 router along the way (normal IP routing).
  • Outer IP (20 B) — source = sending VTEP IP, destination = receiving VTEP IP. This is what lets VXLAN ride on L3.
  • UDP (8 B) — destination port is the fixed VXLAN well-known port 4789. Source port is randomized per-flow (so ECMP hashes spread load).
  • VXLAN header (8 B) — 8 bits flags + 24 bits reserved + 24-bit VNI + 8 bits reserved. The VNI is the whole point.
  • Original Ethernet frame — the VM's L2 frame, byte-for-byte unchanged. This is the "MAC-in-UDP" part.
  • FCS — frame check sequence (CRC) for the outer frame.
  • Outer MAC (14 B): underlay의 다음 물리 hop용 L2 헤더. L3 라우터를 지날 때마다 다시 쓰임
  • Outer IP (20 B): 송신 VTEP IP → 수신 VTEP IP. VXLAN이 L3 위를 갈 수 있는 이유
  • UDP (8 B): 목적지 포트는 VXLAN 공식 포트 4789. 소스 포트는 flow마다 랜덤(ECMP 해시 분산용)
  • VXLAN 헤더 (8 B): flags 8b + reserved 24b + VNI 24b + reserved 8b. 핵심은 VNI
  • Original Ethernet frame: VM의 L2 프레임 원본. "MAC-in-UDP"의 MAC 부분
  • FCS: outer frame의 CRC

The "tunnel" mental model"터널" 멘탈 모델

Picture two VTEPs as doors joined by a pipe carrying "an L2 frame in an IP envelope." Routers in between only see an IP packet addressed to the receiving VTEP and route it normally. The far VTEP unwraps it and delivers the original frame to the VM.

두 VTEP를 파이프로 이어진 문으로 보면, 파이프 안에는 "IP 봉투에 담긴 L2 프레임"이 흐른다. 중간 라우터는 수신 VTEP 앞으로 가는 IP 패킷으로만 보고 평소대로 라우팅한다. 반대편 VTEP가 봉투를 벗겨 원본 L2 프레임을 VM에 전달한다.

acronym recap약어 정리
  • VTEP = VXLAN Tunnel End Point (the wrap/unwrap door, usually a Leaf switch or a hypervisor's vSwitch)
  • VNI = VXLAN Network Identifier (24-bit ID = the new "VLAN" inside the tunnel)
  • Underlay = the L3 IP fabric between VTEPs (you set it up; OSPF/BGP routes it)
  • Overlay = the virtual L2 networks that ride on top, identified by VNIs
  • VTEP = VXLAN Tunnel End Point (캡슐화 양쪽 문, 보통 Leaf 스위치나 하이퍼바이저 vSwitch)
  • VNI = VXLAN Network Identifier (24-bit ID = 터널 안의 새 "VLAN")
  • Underlay = VTEP 사이의 L3 IP fabric (직접 깔고, OSPF/BGP가 라우팅)
  • Overlay = 그 위에 얹는 가상 L2 네트워크들, VNI로 구분

11 VM-to-VM unicast flow (the happy path) VM-to-VM 유니캐스트 흐름 (정상 경로)

The journey end-to-end:

이제 패킷의 전체 여정을 따라간다.

The full journey — VM doesn't know VXLAN exists.전체 여정. VM은 VXLAN이 있는 줄도 모른다.

Step-by-step단계 설명

  1. The source VM sends its original L2 frame (with Dst MAC = destination VM's MAC) into its host's vSwitch — same as if both VMs were on the same physical LAN.
  2. The kernel vSwitch (which is the local VTEP) recognizes this VNI's traffic, looks up "VM with that destination MAC lives behind which VTEP?", finds VTEP 2's IP, and wraps the frame as we saw in §10.
  3. The wrapped packet is an ordinary IP/UDP packet from VTEP 1's IP to VTEP 2's IP. The intermediate IP network (the underlay) doesn't know it's VXLAN — it routes it like any other UDP packet.
  4. VTEP 2 receives. Sees the UDP port is 4789 → "it's VXLAN" → strips the outer headers and recovers the original L2 frame.
  5. VTEP 2 delivers the original L2 frame to the destination VM, locally on its host. The destination VM has no idea VXLAN happened.
  1. 송신 VM은 같은 물리 LAN에 있을 때처럼 원본 L2 프레임(목적지 MAC = 수신 VM MAC)을 호스트 vSwitch로 보낸다.
  2. 커널 vSwitch(로컬 VTEP)가 이 VNI 트래픽을 알아보고, 목적지 MAC이 어느 VTEP 뒤에 있는지 조회해 VTEP 2의 IP를 찾은 뒤 §10처럼 감싼다.
  3. 감싼 패킷은 VTEP 1 IP → VTEP 2 IP로 가는 평범한 IP/UDP 패킷이다. underlay는 VXLAN인지 모른 채 일반 UDP처럼 라우팅한다.
  4. VTEP 2는 UDP 포트 4789를 보고 VXLAN임을 알아채 outer 헤더를 벗기고 원본 L2 프레임을 복원한다.
  5. VTEP 2가 원본 프레임을 호스트 안의 목적지 VM에 전달한다. 목적지 VM은 VXLAN을 거쳤는지 모른다.

End VMs see a "flat L2"; network engineers see a routed L3 fabric.

VM에게는 "평평한 L2"가, 네트워크 엔지니어에게는 라우팅되는 L3 fabric이 보인다.

12–13 Manual VXLAN — no control plane, and why we need EVPN Manual VXLAN: 컨트롤 플레인이 없을 때와 EVPN이 필요한 이유

The bootstrap problem초기 문제

§11 skipped a step: the VTEP looks up "destination MAC → VTEP IP." How does it learn that mapping? The first time VM1 talks to VM2, VM1 doesn't know VM2's MAC and VTEP 1 doesn't know which VTEP holds VM2.

§11은 "VTEP가 목적지 MAC으로 VTEP IP를 조회한다"는 단계를 건너뛰었다. 그 매핑은 어디서 올까? VM1이 VM2와 처음 통신할 때 VM1은 VM2의 MAC을, VTEP 1은 VM2가 어느 VTEP 뒤에 있는지를 모른다.

Slide 12 — multicast-based ARP, in pictures슬라이드 12: 멀티캐스트 기반 ARP

Without a control plane, VTEP1 floods the ARP via a multicast group; VTEP2 replies unicast.컨트롤 플레인이 없으면 VTEP1이 multicast group으로 ARP를 뿌리고 VTEP2가 unicast로 답한다.

  1. VM1 sends an ARP broadcast inside its own host: "who has 192.168.10.3?"
  2. VTEP 1 catches it. Wraps it in UDP, but instead of sending unicast (it doesn't know where to), sends to a multicast group that all VTEPs in this VNI have joined.
  3. Every VTEP in that VNI receives the multicast, unwraps, and broadcasts inside its own host. VTEPs whose VMs don't match → discard.
  4. VM2 sees the ARP and unicast-replies. The reply rides home through VTEP 2 → VTEP 1 → VM1.
  5. Now VTEP 1 has learned "MAC of VM2 lives behind VTEP 2." Future packets go unicast.
  1. VM1이 호스트 안에서 ARP broadcast를 보낸다: "192.168.10.3 누구?"
  2. VTEP 1이 이를 UDP로 감싸되, 보낼 곳을 모르므로 이 VNI의 모든 VTEP가 가입한 multicast 그룹으로 보낸다.
  3. VNI의 모든 VTEP가 받아 풀고 자기 호스트 안에 broadcast한다. 해당 VM이 없는 VTEP는 버린다.
  4. VM2가 unicast로 ARP reply를 보내고, 답은 VTEP 2 → VTEP 1 → VM1으로 돌아온다.
  5. VTEP 1은 "VM2의 MAC은 VTEP 2 뒤"라고 학습하고, 이후 패킷은 unicast로 간다.

Why "manual" VXLAN isn't enough왜 "Manual" VXLAN으론 부족한가

Multicast flood-and-learn works, with problems:

Multicast 기반 flood-and-learn은 동작은 하지만 문제가 있다.

  • BUM traffic (Broadcast / Unknown unicast / Multicast) — every ARP, every "haven't seen this MAC yet" packet, every actual multicast → all multicast to all VTEPs in the VNI. Doesn't scale.
  • No graceful "VTEP X just left — drop its MACs" — table garbage accumulates.
  • Underlay must support multicast (PIM, IGMP) reliably — many real networks don't, or don't want to.
  • BUM 트래픽: ARP, 처음 보는 MAC, 실제 multicast가 모두 VNI의 전 VTEP로 multicast된다. 확장되지 않는다.
  • "VTEP X가 빠졌으니 그 MAC을 지운다" 같은 정리가 어려워 테이블에 쓰레기가 쌓인다.
  • Underlay가 multicast(PIM, IGMP)를 안정적으로 지원해야 하는데, 지원하지 않거나 쓰기 싫어하는 네트워크가 많다.

Enter EVPN — Ethernet VPNEVPN(Ethernet VPN) 등장

EVPN keeps the data plane (VXLAN forwarding) and adds a control plane that explicitly distributes MAC ↔ VTEP IP mappings: MP-BGP (next slides).

EVPN은 데이터 플레인(VXLAN 포워딩)은 그대로 두고, MAC ↔ VTEP IP 매핑을 VTEP끼리 명시적으로 나누는 컨트롤 플레인을 따로 둔다. 그 컨트롤 플레인이 MP-BGP다(다음 슬라이드).

  • No flood-and-learn. VTEPs announce their local MACs via BGP. Other VTEPs learn directly.
  • No multicast needed in the underlay. BUM can be handled with ingress replication (unicast copies) or other techniques.
  • VM moves between hosts → BGP withdraw + re-advertise, cleanly.
  • flood-and-learn이 없다. VTEP가 로컬 MAC을 BGP로 광고하고 다른 VTEP는 그대로 받아 배운다.
  • underlay에 multicast가 필요 없다. BUM은 ingress replication(unicast 복사) 등으로 처리한다.
  • VM이 호스트를 옮기면 BGP withdraw + 재광고로 깔끔하게 반영된다.

14 VXLAN requirements — provider networks & the VPN-A / VPN-B problem VXLAN 필요 조건: Provider 네트워크와 VPN-A/VPN-B 문제

The slide switches to telco / ISP (Internet Service Provider) terms, because VXLAN at scale rides on the same machinery as carrier VPNs (Virtual Private Networks).

대규모 VXLAN은 통신사 VPN(Virtual Private Network)과 같은 기반 위에서 돌기 때문에, 이 슬라이드는 telco(통신사) / ISP(Internet Service Provider) 용어로 넘어간다.

VRF) and a protocol that labels routes by customer (MP-BGP, MPLS)

Both customers use overlapping private IPs — the ISP must keep them separated.두 고객이 같은 사설 IP 대역을 쓰므로 ISP가 둘을 격리해야 한다.

Vocabulary first먼저 용어

  • CE — Customer Edge router (sits on the customer side)
  • PE — Provider Edge router (sits on the telco's side, talks to multiple CEs)
  • P — Provider core router (in the middle, doesn't see customers directly)
  • NLRI — Network Layer Reachability Information (the "I know how to reach 10.0.0.0/24" data carried inside routing protocols)
  • CE: Customer Edge 라우터 (고객사 측)
  • PE: Provider Edge 라우터 (통신사 측, 여러 CE와 연결)
  • P: Provider 코어 라우터 (중간, 고객을 직접 보지 않음)
  • NLRI: Network Layer Reachability Information (라우팅 프로토콜이 나르는 "이 prefix로 가는 법" 정보)

The core problem — overlapping addresses핵심 문제: 주소가 겹친다

Two customers (VPN-A and VPN-B) sign up with the same ISP. Both happen to use 192.168.2.0/24 internally (everyone uses private RFC 1918 ranges). When the ISP backbone needs to route these, "destination 192.168.2.5" is ambiguous — whose 192.168.2.5? Plain BGP / OSPF cannot distinguish.

같은 ISP에 가입한 두 고객(VPN-A, VPN-B)이 모두 RFC 1918 사설 대역 192.168.2.0/24을 쓴다. ISP 백본 입장에서 "목적지 192.168.2.5"는 누구의 주소인지 모호하고, 일반 BGP/OSPF로는 구분할 수 없다.

The required ingredient필요한 재료

PE routers must keep per-customer routing tables (called VRF — Virtual Routing & Forwarding instances), and a protocol that can carry routes labeled by customer. That protocol is MP-BGP (next slide). The transport that scales this across the carrier core is MPLS (the slide after).

PE 라우터에는 고객별 라우팅 테이블(VRF, Virtual Routing & Forwarding instance)과 고객 식별자가 붙은 경로를 나르는 프로토콜이 필요하다. 그 프로토콜이 MP-BGP(슬라이드 15)이고, 통신사 코어 전체로 확장하는 전송 방식이 MPLS(슬라이드 16)다.

why this slide sits between VXLAN basics and EVPN왜 이 슬라이드가 VXLAN 기본과 EVPN 사이에 있나 EVPN's control plane (MP-BGP) is literally the same machinery telcos already used for L3 VPN. Once you understand the carrier VPN problem, EVPN-over-VXLAN feels natural: same control plane, different data plane (VXLAN instead of MPLS-tagged frames). EVPN의 컨트롤 플레인(MP-BGP)은 통신사가 L3 VPN에 쓰던 것과 같다. 컨트롤 플레인은 같고 데이터 플레인만 MPLS-tag 프레임 대신 VXLAN으로 바뀐 것이 EVPN-over-VXLAN이다.

First — the routing protocol family tree먼저, 라우팅 프로토콜 계통도

Where BGP sits in the family — under Dynamic, in the Path Vector camp.BGP는 Dynamic 아래 Path Vector 계열이다.

  • Static — hand-configured. Doesn't react to topology changes.
  • Distance Vector (RIP) — "I'm N hops from you." Simple, slow, doesn't scale.
  • Link-State (OSPF, IS-IS) — every router publishes its own connections; everyone computes shortest paths. Great inside one administrative domain.
  • Path Vector (BGP) — carries the full path of ASes (Autonomous Systems). Designed for the internet, where policy matters more than shortest distance.
  • Static: 수동 설정. 토폴로지 변화에 반응하지 않음
  • Distance Vector (RIP): "너까지 N hop". 단순하지만 느리고 확장성이 낮음
  • Link-State (OSPF, IS-IS): 모든 라우터가 자기 연결을 광고하고 각자 최단 경로 계산. 단일 관리 도메인에 적합
  • Path Vector (BGP): AS(Autonomous System) 경로 전체를 나름. 최단 거리보다 정책이 중요한 인터넷용

What is BGP?BGP란

BGP (Border Gateway Protocol) is the protocol that runs the internet. It exchanges reachability info between ASes (autonomous systems — each big ISP/cloud/company is one). Runs over TCP. Default flavor only carries IPv4 unicast routes.

BGP(Border Gateway Protocol)는 인터넷을 움직이는 프로토콜이다. AS(큰 ISP·클라우드·회사가 각각 하나) 사이에 도달성 정보를 교환하고 TCP 위에서 돈다. 기본형은 IPv4 unicast 경로만 나른다.

MP-BGP — Multi-Protocol extensionsMP-BGP: Multi-Protocol 확장

Plain BGP only advertises "this IPv4 prefix via this next hop." To also carry IPv6, VPN-tagged prefixes (customer A's 192.168.2.0/24 distinct from B's), or VM MACs and their VTEPs, MP-BGP (Multi-Protocol BGP) adds Address Families (AF) and Sub-Address Families (SAFI): each is a kind of thing you can advertise.

일반 BGP는 "이 IPv4 prefix는 이 next hop으로"만 광고한다. IPv6, VPN 식별자가 붙은 prefix(고객 A와 B의 192.168.2.0/24을 다른 경로로), VM의 MAC과 그 VTEP까지 나르려고 MP-BGP(Multi-Protocol BGP)는 Address Family(AF)와 Sub-Address Family(SAFI)를 추가했다. address family마다 광고할 수 있는 대상의 종류가 다르다.

Typical config (FRR / Cisco-style)전형적인 설정 (FRR/시스코 스타일)

router bgp 65000
  bgp router-id 1.1.1.1
  neighbor 2.2.2.2 remote-as 65000

  address-family l2vpn evpn
    neighbor 2.2.2.2 activate
    neighbor 2.2.2.2 send-community both
    advertise-all-vni
  exit-address-family

In words: "I'm AS 65000; peer 2.2.2.2 is also AS 65000. Activate L2VPN-EVPN with it and advertise all our VNIs' MACs."

풀어 쓰면 "나는 AS 65000이고 피어 2.2.2.2도 AS 65000이다. 그와 L2VPN-EVPN address family를 켜고 모든 VNI의 MAC을 광고한다"는 뜻이다.

putting it together조립 In EVPN-over-VXLAN, VTEPs run MP-BGP with the L2VPN-EVPN address family. On learning a local VM's MAC, a VTEP advertises "VNI X, MAC m, VTEP IP v"; peers fill their forwarding tables and later packets go unicast over VXLAN. No multicast, no flood-and-learn. EVPN-over-VXLAN에서 VTEP는 L2VPN-EVPN address family로 MP-BGP를 돌린다. 로컬 VM의 MAC을 배우면 "VNI X, MAC m, VTEP IP v"를 피어에 광고하고, 피어는 포워딩 테이블을 채운다. 이후 그 MAC으로 가는 패킷은 VXLAN unicast로 간다. multicast도 flood-and-learn도 없다.

The pain MPLS solvesMPLS가 해결한 문제

In normal IP routing every hop parses the IP header and does a longest-prefix match against a routing table (millions of entries on a backbone router). That lookup is expensive.

일반 IP 라우팅은 hop마다 IP 헤더를 파싱하고 라우팅 테이블(백본 라우터는 수백만 엔트리)에서 longest-prefix match를 한다. 이 조회가 비싸다.

MPLS — Multiprotocol Label SwitchingMPLS: Multiprotocol Label Switching

MPLS replaces it with a fixed-length label lookup. The Ingress PE classifies the packet into a Forwarding Equivalence Class (FEC) and attaches a short label, Provider routers do a fast label-swap, and the Egress PE strips the label and delivers.

MPLS는 이를 고정 길이 라벨 조회로 바꾼다. Ingress PE가 패킷을 FEC(Forwarding Equivalence Class, 같은 경로로 갈 패킷 묶음)로 분류해 짧은 라벨을 붙이고, Provider 라우터는 빠른 label-swap만 하며, Egress PE가 라벨을 떼고 전달한다.

Push label at the door, swap label inside, pop label at the exit.입구에서 라벨 push, 내부에서 swap, 출구에서 pop

Label header format라벨 헤더 포맷

[Link layer header] [Outer label] [Inner label] [Layer 3 packet] ▲ ▲ │ │ "transport label" "VPN/service label" (which path?) (which customer/service?)

Labels form a stack: the outer label says how to reach the far PE, the inner label which VRF (customer) gets it. This is how carriers tunnel customer L3 VPN traffic.

라벨은 스택으로 쌓인다. outer label은 먼 PE까지의 경로, inner label은 전달할 VRF(고객)를 뜻한다. 통신사는 이렇게 고객 L3 VPN 트래픽을 터널링한다.

How does VXLAN relate?VXLAN과의 관계

In a carrier or large enterprise:

통신사나 대형 엔터프라이즈에서는 이렇게 나뉜다.

  • Inside a single data center: VXLAN as the overlay (L2 over IP), BGP-EVPN as the control plane.
  • Between data centers / across the WAN: MPLS often carries the inter-DC VPN, sometimes wrapping VXLAN, sometimes via dedicated services (EVPN-MPLS).
  • EVPN as a control plane is encapsulation-agnostic — it can drive either VXLAN-encapped forwarding or MPLS-encapped forwarding. The same BGP messages.
  • 데이터센터 내부: 오버레이(L2 over IP)는 VXLAN, 컨트롤 플레인은 BGP-EVPN
  • 데이터센터 간 / WAN: MPLS가 inter-DC VPN을 나르는 경우가 많다. VXLAN을 감싸기도 하고 EVPN-MPLS 같은 별도 서비스를 쓰기도 한다
  • EVPN은 캡슐화 방식과 무관하다. VXLAN 포워딩이든 MPLS 포워딩이든 같은 BGP 메시지로 제어한다
where you'll bump into this실무에서 부딪힐 지점 If a customer needs its inference cluster reachable from on-prem, you usually get an MPLS-based L3 VPN into the customer's VRF plus VXLAN overlays inside the cluster. Knowing both vocabularies, and that MP-BGP carries both, helps in design talks. 고객 온프레미스에서 추론 클러스터에 접근해야 하면 보통 고객 VRF로 MPLS 기반 L3 VPN이 들어오고 클러스터 안에는 VXLAN 오버레이가 깔린다. 두 용어와 둘 다 MP-BGP가 나른다는 사실을 알면 설계 논의가 수월하다.

∎ Wrap-up — the whole picture in one breath 마지막 정리: 전체 그림

How we got here:

여기까지 온 흐름

  1. Traditional L2 has limits: 4096 VLANs, STP wasting links, MAC tables overflow, broadcast domains pinned to physical segments.
  2. Datacenter / cloud needs to push past all of these — many tenants, big bandwidth, mobility.
  3. VXLAN wraps L2 frames in UDP/IP — a virtual L2 over any L3 fabric. 16M VNIs, no STP needed, ECMP-friendly.
  4. But raw VXLAN still relies on multicast flood-and-learn → doesn't scale cleanly.
  5. EVPN separates control from data: VTEPs advertise their MACs via MP-BGP. No more flood-and-learn.
  6. MP-BGP is the same protocol used for carrier L3 VPNs (Address Families: VPNv4 / EVPN / etc).
  7. The carrier core often runs MPLS for label-switched forwarding; EVPN can sit on top of either VXLAN or MPLS.
  1. 전통 L2의 한계: VLAN 4096개, STP의 링크 낭비, MAC 테이블 포화, 물리 세그먼트에 묶인 broadcast 도메인.
  2. 데이터센터/클라우드는 많은 테넌트, 큰 대역폭, 이동성 때문에 이를 넘어야 한다.
  3. VXLAN은 L2 프레임을 UDP/IP로 감싸 어떤 L3 fabric 위에서도 가상 L2를 만든다. VNI 1,600만, STP 불필요, ECMP와 잘 맞는다.
  4. 다만 raw VXLAN은 multicast flood-and-learn에 기대므로 깔끔하게 확장되지 않는다.
  5. EVPN은 컨트롤과 데이터를 분리해 VTEP가 MAC을 MP-BGP로 광고하게 한다. flood-and-learn이 사라진다.
  6. MP-BGP는 통신사 L3 VPN의 그 프로토콜이다 (Address Family: VPNv4 / EVPN 등).
  7. 통신사 코어는 MPLS 라벨 스위칭을 쓰고, EVPN은 VXLAN과 MPLS 어느 쪽 위에서도 돈다.

In your inference setup:

  • K8s pods on the same node: usually a bridge (pure L2 inside the host).
  • K8s pods across nodes: an overlay — almost always VXLAN (Flannel-VXLAN, Calico-VXLAN, Cilium can do native routing or VXLAN, etc.).
  • Inference cluster across availability zones: probably EVPN-VXLAN, or VXLAN tunneled through MPLS WAN.
  • "Why is GPU node X unable to send KV blocks to GPU node Y?" — the answer is often "the VXLAN tunnel between their hypervisors is broken, or MTU is too small to fit VXLAN overhead, or BGP-EVPN didn't advertise the MAC yet."

추론 환경에 대입하면 이렇다.

  • 같은 노드의 K8s pod: 보통 브리지(호스트 내부 순수 L2)
  • 노드 간 K8s pod: 오버레이, 거의 VXLAN (Flannel-VXLAN, Calico-VXLAN, Cilium은 네이티브 라우팅 또는 VXLAN)
  • AZ에 걸친 추론 클러스터: 대개 EVPN-VXLAN, 또는 MPLS WAN 위 VXLAN 터널
