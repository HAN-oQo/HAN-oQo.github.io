Not a Kubernetes course — the subset an inference engineer touches, in three tabs. Essentials: the six objects a model server is made of (and the one CRD llm-d adds), why a GPU pod sits in Pending and the four causes with the single describe that names which, a five-rung debugging ladder keyed by symptom, and enough k9s to stop retyping kubectl get pods -n …. Cheatsheet: dense kubectl and k9s reference, plus llm-d/GIE one-liners. Deeper: RBAC and why the EPP — unlike a model server — needs real cluster permissions, why a Service can't route on a model name that lives in the JSON body (and how readiness probes gate EndpointSlices), and the model-weights storage question where hostPath is often the right answer on a single-node lab. The llm-d examples are lifted from our own Phase 4 run, including the gotcha that InferencePool v1 rejects an endpointPickerRef without a port. Written as the prerequisite the ArgoCD series assumed you already had. 쿠버네티스 강의가 아니라, 추론 엔지니어가 실제로 만지는 부분만 탭 세 개로. 필수: 모델 서버를 이루는 객체 여섯 개(그리고 llm-d 가 더하는 CRD 하나), GPU 파드가 Pending 에 멈추는 원인 네 가지와 그중 무엇인지 짚어 주는 describe 한 줄, 증상별로 뛰어드는 5단 디버깅 사다리, 그리고 kubectl get pods -n … 을 다시 치지 않게 해 줄 만큼의 k9s. 치트시트: kubectl · k9s 압축 레퍼런스와 llm-d/GIE 한 줄 명령들. 더 깊게: RBAC, 그리고 모델 서버와 달리 EPP 는 왜 진짜 클러스터 권한이 필요한가, JSON body 안에 있는 모델명으로는 왜 Service 가 라우팅할 수 없는가(readiness probe 가 EndpointSlice 를 어떻게 여닫는지 포함), 단일 노드 실습에선 hostPath 가 종종 정답인 모델 가중치 스토리지 문제. llm-d 예시는 우리 Phase 4 실행 기록에서 그대로 가져왔고, InferencePool v1 이 port 없는 endpointPickerRef 를 거부하는 함정도 포함했다. Routing an LLM request when the model name is in the body 모델 이름이 body 안에 있을 때, 요청은 어떻게 라우팅되나

One request, end to end, through the Gateway API Inference Extension: BBR → HTTPRoute → InferencePool → endpoint picker → vLLM, plus the KV-event path that flows back the other way. Every object named, and two failure modes that produce no error at all. Now assumes no prior knowledge: plain-words boxes define proxy, L7, Envoy, ext_proc, gRPC, Istio, control vs data path and sidecar where each first appears, and a cast table separates the two processes from the pieces of configuration. 요청 하나가 Gateway API Inference Extension을 통과하는 전 과정 — BBR → HTTPRoute → InferencePool → endpoint picker → vLLM, 그리고 반대 방향으로 흐르는 KV 이벤트 경로까지. 거쳐가는 오브젝트를 전부 이름으로 짚고, 에러를 전혀 남기지 않는 장애 모드 두 가지도 함께. 사전 지식 없이 읽을 수 있게 보강했다 — 프록시·L7·Envoy·ext_proc·gRPC·Istio·control/data path·사이드카를 처음 나오는 자리마다 '쉽게 말하면' 블록으로 풀고, 등장인물 표로 프로세스 둘과 설정들을 갈라놓았다.
