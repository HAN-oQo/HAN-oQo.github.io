Routing an LLM request when the model name is in the body 모델 이름이 body 안에 있을 때, 요청은 어떻게 라우팅되나

Ordinary HTTP routing matches on paths and headers. An OpenAI-compatible API gives you neither — every request is POST /v1/chat/completions and the model name is buried in the JSON body. This note follows one request end to end through the Gateway API Inference Extension stack, names every Kubernetes object it passes, and explains what each one is actually for. 보통의 HTTP 라우팅은 path와 헤더로 판단한다. 그런데 OpenAI 호환 API는 둘 다 안 준다 — 모든 요청이 POST /v1/chat/completions이고 모델 이름은 JSON body 안에 묻혀 있다. 이 글은 요청 하나가 Gateway API Inference Extension 스택을 통과하는 전 과정을 따라가면서, 거쳐가는 쿠버네티스 오브젝트를 하나씩 이름으로 짚고 각각이 실제로 무슨 일을 하는지 설명한다.

1 The problem: the router cannot read the body 문제 — 라우터는 body를 못 읽는다

Say you are serving eight different models on one cluster and you want a single endpoint in front of all of them. A client sends this: 한 클러스터에 모델 여덟 개를 서빙하면서 그 앞에 엔드포인트 하나만 두고 싶다고 하자. 클라이언트는 이렇게 보낸다. 

POST /v1/chat/completions
Content-Type: application/json

{
  "model": "meta-llama/Llama-3.1-70B-Instruct",
  "messages": [ ... ]
}

Now look at what a proxy has to work with. The path is /v1/chat/completions — identical for all eight models. There is no Host difference, no query string, no custom header. The only thing that distinguishes one model from another is a field inside the request body. 이제 프록시가 가진 재료를 보자. path는 /v1/chat/completions — 여덟 모델 전부 똑같다. Host가 다른 것도 아니고, 쿼리스트링도, 커스텀 헤더도 없다. 모델을 구분해주는 유일한 정보가 요청 body 안에 있다.

And Envoy — like essentially every L7 router — makes its routing decision from the request line and headers. It does not buffer and parse the body to decide where to send something. That would mean holding the whole request in memory before you know its destination, which is exactly what you do not want in front of a streaming inference workload. 그런데 Envoy는 — 사실상 모든 L7 라우터가 그렇듯 — 요청 라인과 헤더만 보고 라우팅을 결정한다. 목적지를 정하려고 body를 통째로 버퍼링해서 파싱하지 않는다. 그러면 목적지를 알기도 전에 요청 전체를 메모리에 들고 있어야 하는데, 스트리밍 추론 워크로드 앞단에서 가장 피하고 싶은 게 바로 그거다.

The gap간극 The information you need to route is in a place the router structurally cannot look. Everything in the rest of this note is downstream of that one sentence. 라우팅에 필요한 정보가, 라우터가 구조적으로 볼 수 없는 곳에 있다. 이 글의 나머지는 전부 이 한 문장에서 파생된다.

The Gateway API Inference Extension solves it with a small component called BBR — Body-Based Routing. It is an ext_proc filter: Envoy streams the request to it over gRPC, BBR reads the model field, and sets a header: Gateway API Inference Extension은 BBR(Body-Based Routing)이라는 작은 컴포넌트로 이걸 푼다. ext_proc 필터다 — Envoy가 gRPC로 요청을 넘겨주면, BBR이 model 필드를 읽어서 헤더 하나를 심어준다. 

X-Gateway-Model-Name: meta-llama/Llama-3.1-70B-Instruct

That is the entire job. From that header onward, ordinary header-based routing works again, and the rest of the stack never has to think about JSON. 하는 일은 이게 전부다. 이 헤더가 생긴 순간부터는 평범한 헤더 라우팅이 다시 작동하고, 그 뒤로는 스택 어디서도 JSON을 신경 쓸 필요가 없다.

One consequence worth noticing early: BBR is wired in with INSERT_FIRST, at the very front of the HTTP filter chain. It has to be. No routing decision of any kind can be made before the model is known, so nothing may run ahead of it. 일찍 짚어둘 게 하나 있다. BBR은 INSERT_FIRST로, HTTP 필터 체인 맨 앞에 꽂힌다. 그럴 수밖에 없다. 모델을 알기 전에는 어떤 라우팅 판단도 불가능하므로, 그 앞에 뭔가가 먼저 돌 수 없다.

2 The full path, end to end 전체 경로

Here is the whole thing. Read it top to bottom; the one arrow that goes the other way is the interesting part, and we come back to it in section 4. 전체 그림이다. 위에서 아래로 읽으면 되고, 유일하게 거꾸로 올라가는 화살표가 재미있는 부분이다 — 4절에서 다시 다룬다.

Object names follow the convention <prefix>-<model>, one set per served model. 오브젝트 이름은 <prefix>-<model> 규칙을 따르며, 서빙하는 모델마다 한 세트씩 존재한다.

Two decisions get made on the way down, and they are made by two different components for two different reasons: 내려가는 길에 결정이 두 번 내려지는데, 서로 다른 이유로 서로 다른 컴포넌트가 내린다.

Which model?어느 모델인가?

Answered by BBR, once, globally, for every model. Cheap: parse JSON, set a header. BBR이 답한다. 전역에 하나뿐이고 모든 모델이 공유한다. 값싼 작업이다 — JSON 파싱하고 헤더 심기.

Which replica?어느 replica인가?

Answered by the EPP, per model, from live engine state. Expensive, and the whole point of the stack. EPP가 답한다. 모델마다 따로 있고, 살아있는 엔진 상태를 보고 판단한다. 비싼 작업이고, 이 스택이 존재하는 이유다.

Note the asymmetry in cardinality — one BBR for the whole cluster, one EPP per model. That is not an accident, and it has a consequence we will get to in section 5. 개수의 비대칭을 눈여겨보자 — BBR은 클러스터 전체에 하나, EPP는 모델마다 하나. 우연이 아니고, 5절에서 다룰 결과를 낳는다.

"epp-llama-70b"만으로는 어느 것인지 알 수 없고, 엉뚱한 오브젝트를 고치게 만든다. 반드시 종류를 같이 말하자 — HTTPRoute, InferencePool처럼. 변경 요청 리뷰에서 이 모호함 때문에 실제로 시간을 날리는 걸 봤다.

Why the picker is addressed as a Service, not a pod picker를 pod가 아니라 Service로 가리키는 이유

If the split between Deployment and Service has never quite clicked, this is a good place for it to. The Deployment is the thing; the Service is its stable address. Deployment와 Service의 구분이 아직 헷갈린다면 여기가 이해하기 좋은 지점이다. Deployment는 실물이고, Service는 그 앞에 붙은 고정 주소다.

Deployment/epp-llama-70b 2/2 ├─ pod epp-llama-70b-6bc8879976-2vr6s IP: changes on every restart └─ pod epp-llama-70b-6bc8879976-btw6z IP: changes on every restart Service/epp-llama-70b ClusterIP 10.43.x.x ← does not change └─ load-balances to the two pods above

The Deployment's job is "keep two of these alive". When one dies it makes a new one — with a different IP. On the cluster I read this from, those two picker pods had already restarted three and two times respectively. Had anything hardcoded a pod IP, routing would have broken silently each time. Deployment가 하는 일은 "이걸 두 개 살려둬라"다. 하나가 죽으면 새로 만드는데, 그 새 pod는 IP가 다르다. 내가 읽어온 클러스터에서 이 picker pod 두 개는 이미 각각 세 번, 두 번 재시작한 상태였다. 어딘가 pod IP를 박아뒀다면 그때마다 라우팅이 조용히 깨졌을 것이다.

That is precisely why InferencePool.endpointPickerRef points at a Service. Nothing in the configuration ever names a pod. InferencePool.endpointPickerRef가 Service를 가리키는 이유가 바로 이거다. 설정 어디에도 pod를 직접 지목하는 곳이 없다.

And that single Service carries three ports, all backed by the same two pods: 그리고 그 Service 하나가 포트 세 개를 갖는데, 전부 같은 pod 두 개로 연결된다.

4 The reverse path: how the picker knows anything 역방향 경로 — picker는 어떻게 아는가

Everything so far describes a request travelling down. But look at what the picker is being asked to do: given two identical replicas of the same model, choose the better one. On what basis? 여기까지는 요청이 아래로 내려가는 얘기였다. 그런데 picker가 요구받는 일을 보자 — 똑같은 모델의 replica 두 개 중 더 나은 쪽을 고르라는 것이다. 무엇을 근거로?

Queue depth and KV-cache utilization it can scrape from engine metrics. But the decision that actually matters for latency is prefix cache locality: if replica A already holds the KV blocks for this conversation's prefix and replica B does not, sending it to A can skip most of the prefill. That is not a metric you can average — it is a question about specific blocks on a specific pod. 큐 길이나 KV 캐시 사용률은 엔진 메트릭에서 긁어올 수 있다. 하지만 지연에 실제로 영향을 주는 판단은 prefix cache locality다 — 이 대화의 prefix에 해당하는 KV 블록을 replica A가 이미 들고 있고 B는 없다면, A로 보내면 prefill 대부분을 건너뛴다. 이건 평균 낼 수 있는 메트릭이 아니다. 특정 pod에 특정 블록이 있느냐는 질문이다.

So vLLM publishes it. Each engine is launched with a flag pointing back at the picker: 그래서 vLLM이 그걸 발행한다. 각 엔진은 picker를 가리키는 플래그를 달고 뜬다. 

--kv-events-config '{
  "enable_kv_cache_events": true,
  "publisher": "zmq",
  "endpoint": "tcp://epp-llama-70b:5557",
  "topic": "kv@<POD_IP>:8000@meta-llama/Llama-3.1-70B-Instruct"
}'

As blocks are cached and evicted, the engine streams those events over ZeroMQ to :5557 on the picker's Service. The picker keeps a running index of which pod holds which prefix, and scores against it. 블록이 캐시되고 축출될 때마다 엔진이 그 이벤트를 ZeroMQ로 picker Service의 :5557에 흘려보낸다. picker는 어느 pod가 어느 prefix를 들고 있는지 색인을 유지하면서 그걸로 점수를 매긴다.

The shape of it구조의 모양 Requests flow down; the information needed to route them flows up. The control loop is closed by the engines themselves reporting their own cache state — which means the routing quality of the whole stack depends on a flag on each vLLM process, not on anything in the gateway. 요청은 아래로 흐르고, 그 요청을 라우팅하는 데 필요한 정보는 위로 흐른다. 제어 루프를 닫는 건 엔진이 스스로 자기 캐시 상태를 보고하는 행위다 — 즉 이 스택 전체의 라우팅 품질이 게이트웨이가 아니라 각 vLLM 프로세스의 플래그 하나에 달려 있다.

That last point has a sharp edge, and it is the kind of thing you only notice by reading the actual launch arguments rather than the architecture diagram. On the cluster I looked at, one of the eight models was running without --kv-events-config at all. Nothing was broken; no alert fired. It was simply being routed with no cache-locality signal — the expensive picker in front of it degraded to something much closer to round-robin, silently, for as long as anyone cared to not look. 마지막 문장에 날카로운 구석이 있는데, 아키텍처 다이어그램이 아니라 실제 실행 인자를 읽어야만 보이는 종류의 것이다. 내가 본 클러스터에서는 여덟 모델 중 하나가 --kv-events-config 없이 돌고 있었다. 아무것도 고장 나지 않았고 알럿도 없었다. 그저 캐시 지역성 신호 없이 라우팅되고 있었을 뿐이다 — 앞에 붙은 비싼 picker가 조용히 라운드로빈에 가깝게 퇴화한 채로, 아무도 들여다보지 않는 동안 계속.

Failure mode with no symptom증상 없는 장애 A missing publisher flag does not produce an error anywhere. The engine serves correctly, the picker picks, the request succeeds. You lose only the thing you built the stack for. Worth an explicit check that every engine actually publishes, rather than trusting that it was configured once. publisher 플래그가 빠져도 어디서도 에러가 나지 않는다. 엔진은 정상 응답하고, picker는 고르고, 요청은 성공한다. 잃는 건 이 스택을 만든 이유 딱 하나뿐이다. 한 번 설정했으니 되어 있겠지 믿는 대신, 모든 엔진이 실제로 발행하고 있는지 명시적으로 확인할 가치가 있다.

5 Control path, data path, and where it breaks control path와 data path, 그리고 깨지는 지점

"The tokens don't pass through" is half true"토큰은 통과하지 않는다"는 절반만 맞다

This stack is normally described as control-plane routing: the components decide where a request goes, and the tokens flow straight from Envoy to the engine. That framing is useful but it papers over a detail visible in the filter's own configuration: 이 스택은 보통 control-plane 라우팅이라고 설명된다 — 컴포넌트들은 요청이 어디로 갈지만 정하고, 토큰은 Envoy에서 엔진으로 직행한다는 것이다. 유용한 설명이지만, 필터 설정에 드러나는 디테일 하나를 덮는다.

Request body (the prompt)요청 body (프롬프트) Response (generated tokens)응답 (생성 토큰)
BBR passes through — request_body_mode: FULL_DUPLEX_STREAMED 통과한다 — request_body_mode: FULL_DUPLEX_STREAMED no — response_body_mode: NONE, headers SKIP 아니다 — response_body_mode: NONE, 헤더도 SKIP
EPP endpoint decision only엔드포인트 결정만 no아니다

So the prompt genuinely does traverse BBR. What never touches either component is the response stream — and that is where the token volume and the TTFT/TPOT sensitivity live. That is the honest version of the claim: this is not a data-path gateway on the side that matters for latency. 즉 프롬프트는 실제로 BBR을 지나간다. 두 컴포넌트 어느 쪽도 건드리지 않는 건 응답 스트림이고, 토큰 부피와 TTFT/TPOT 민감도가 사는 곳이 바로 거기다. 정직하게 말하면 이렇다 — 지연에 중요한 쪽에서는 data-path 게이트웨이가 아니다.

The distinction matters the moment you consider replacing this with a true data-path gateway, where every token passes through. Such a gateway needs a sidecar on the serving pod, and attaching a sidecar means restarting the engine. A control-plane router can be swapped with a config change; a data-path one cannot. That single fact dictates the entire shape of a migration — you can only move a model without downtime if it has a spare replica to carry traffic while the other restarts. 이 구분은 이걸 진짜 data-path 게이트웨이로 바꾸려는 순간 의미를 갖는다. 모든 토큰이 통과하는 게이트웨이는 서빙 pod에 사이드카가 필요하고, 사이드카를 붙이려면 엔진을 재시작해야 한다. control-plane 라우터는 설정 변경으로 교체되지만 data-path는 그럴 수 없다. 이 사실 하나가 마이그레이션 전체의 모양을 결정한다 — 여유 replica가 있어서 한쪽이 재시작하는 동안 트래픽을 받아줄 수 있는 모델만 무중단 전환이 가능하다.

Both components fail closed — BBR with failure_mode_allow: false, the picker with failureMode: FailClose. Identical policy, very different consequences, because of the cardinality asymmetry from section 2. 두 컴포넌트 다 fail closed다 — BBR은 failure_mode_allow: false, picker는 failureMode: FailClose. 정책은 같은데 결과는 전혀 다르다. 2절에서 본 개수 비대칭 때문이다.

If it dies, no request for any model can be routed — none of them get their model header. Every model goes down at once. 죽으면 어떤 모델의 요청도 라우팅될 수 없다 — 모델 헤더가 안 붙으니까. 전 모델이 동시에 죽는다.

Losing one is survivable. Losing both takes out that one model and nothing else. 하나 잃는 건 버틴다. 둘 다 잃어도 그 모델 하나만 죽고 나머지는 멀쩡하다.

The component that is architecturally trivial — parse JSON, set a header — is the single point of failure for the entire fleet, while the component doing all the interesting work is comfortably redundant. It is worth noticing that this is an easy thing to get backwards when you reason from an architecture diagram, where BBR looks like a footnote and the picker looks like the system. 구조적으로 사소한 컴포넌트 — JSON 파싱하고 헤더 심기 — 가 전체 fleet의 단일 장애점이고, 정작 흥미로운 일을 다 하는 컴포넌트는 넉넉하게 이중화돼 있다. 아키텍처 다이어그램만 보고 판단하면 거꾸로 알기 쉬운 지점이다. 그림에서 BBR은 각주처럼 보이고 picker가 시스템처럼 보이기 때문이다.
