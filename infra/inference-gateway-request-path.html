Routing an LLM request when the model name is in the body 모델 이름이 body 안에 있을 때, 요청은 어떻게 라우팅되나

Ordinary HTTP routing matches on paths and headers. An OpenAI-compatible API gives you neither — every request is POST /v1/chat/completions and the model name is buried in the JSON body. This note follows one request end to end through the Gateway API Inference Extension stack, names every Kubernetes object it passes, and explains what each one is actually for. 보통의 HTTP 라우팅은 path와 헤더로 판단한다. 그런데 OpenAI 호환 API는 둘 다 안 준다 — 모든 요청이 POST /v1/chat/completions이고 모델 이름은 JSON body 안에 묻혀 있다. 이 글은 요청 하나가 Gateway API Inference Extension 스택을 통과하는 전 과정을 따라가면서, 거쳐가는 쿠버네티스 오브젝트를 하나씩 이름으로 짚고 각각이 실제로 무슨 일을 하는지 설명한다.

1 The problem: the router cannot read the body 문제 — 라우터는 body를 못 읽는다

Say you are serving eight different models on one cluster and you want a single endpoint in front of all of them. A client sends this: 한 클러스터에 모델 여덟 개를 서빙하면서 그 앞에 엔드포인트 하나만 두고 싶다고 하자. 클라이언트는 이렇게 보낸다. 

POST /v1/chat/completions
Content-Type: application/json

{
  "model": "meta-llama/Llama-3.1-70B-Instruct",
  "messages": [ ... ]
}

Now look at what a proxy has to work with. The path is /v1/chat/completions — identical for all eight models. There is no Host difference, no query string, no custom header. The only thing that distinguishes one model from another is a field inside the request body. 이제 프록시가 가진 재료를 보자. path는 /v1/chat/completions — 여덟 모델 전부 똑같다. Host가 다른 것도 아니고, 쿼리스트링도, 커스텀 헤더도 없다. 모델을 구분해주는 유일한 정보가 요청 body 안에 있다.

In plain words — proxy, L7, Envoy쉽게 말하면 — 프록시 · L7 · Envoy
proxy프록시
A server that stands between the client and the real servers: it receives the request on their behalf and forwards it to whichever one should handle it. Here it is the single front door in front of eight models. 클라이언트와 진짜 서버들 사이에 서 있는 서버. 요청을 대신 받아서 처리해야 할 곳으로 넘겨준다. 여기서는 모델 여덟 개 앞에 놓인 단 하나의 정문이다.
L7
Layer 7 of the seven-layer network model — the application layer. An L7 router understands HTTP, so it can decide based on the path, the method, the headers. An L4 router sees only IP and port and forwards blindly. Routing by model name is an L7 job by definition. 네트워크를 일곱 층으로 나눈 모델의 7층, 즉 애플리케이션 계층. L7 라우터는 HTTP를 이해하므로 path·메서드·헤더를 보고 판단할 수 있다. L4 라우터는 IP와 포트만 보고 그냥 넘긴다. 모델 이름으로 라우팅하는 건 정의상 L7의 일이다.
Envoy
The most widely used open-source L7 proxy. Nearly every Kubernetes gateway implementation is Envoy underneath — including the one in this note. When this page says "the gateway", the thing actually running is an Envoy process. 가장 널리 쓰이는 오픈소스 L7 프록시. 쿠버네티스 게이트웨이 구현체는 거의 다 내부가 Envoy이고, 이 글의 것도 그렇다. 이 페이지에서 "게이트웨이"라고 하면 실제로 돌고 있는 건 Envoy 프로세스다.

Why headers but not the body? Headers arrive at the front of a request, so a proxy can decide the moment they land. The body comes after and can be huge — waiting for all of it means holding the whole request in memory before you even know where it is going. 왜 헤더는 되고 body는 안 되나? 헤더는 요청 맨 앞에 도착하니 오는 즉시 판단할 수 있다. body는 그 뒤에 오고 얼마든지 커질 수 있다 — 그걸 다 기다린다는 건, 목적지도 모르는 요청을 통째로 메모리에 들고 있겠다는 뜻이다.

And Envoy — like essentially every L7 router — makes its routing decision from the request line and headers. It does not buffer and parse the body to decide where to send something. That would mean holding the whole request in memory before you know its destination, which is exactly what you do not want in front of a streaming inference workload. 그런데 Envoy는 — 사실상 모든 L7 라우터가 그렇듯 — 요청 라인과 헤더만 보고 라우팅을 결정한다. 목적지를 정하려고 body를 통째로 버퍼링해서 파싱하지 않는다. 그러면 목적지를 알기도 전에 요청 전체를 메모리에 들고 있어야 하는데, 스트리밍 추론 워크로드 앞단에서 가장 피하고 싶은 게 바로 그거다.

The gap간극 The information you need to route is in a place the router structurally cannot look. Everything in the rest of this note is downstream of that one sentence. 라우팅에 필요한 정보가, 라우터가 구조적으로 볼 수 없는 곳에 있다. 이 글의 나머지는 전부 이 한 문장에서 파생된다.

The Gateway API Inference Extension solves it with a small component called BBR — Body-Based Routing. It is an ext_proc filter: Envoy streams the request to it over gRPC, BBR reads the model field, and sets a header: Gateway API Inference Extension은 BBR(Body-Based Routing)이라는 작은 컴포넌트로 이걸 푼다. ext_proc 필터다 — Envoy가 gRPC로 요청을 넘겨주면, BBR이 model 필드를 읽어서 헤더 하나를 심어준다. 

X-Gateway-Model-Name: meta-llama/Llama-3.1-70B-Instruct
In plain words — ext_proc, gRPC, BBR쉽게 말하면 — ext_proc · gRPC · BBR
ext_proc
"External Processing" — Envoy's official way to phone a friend. Instead of building custom logic into the proxy, Envoy hands the request out to an external program and lets it inspect or modify it, then carries on. It is an extension point, not a product. "External Processing" — Envoy가 외부에 물어보는 공식 창구. 프록시 안에 커스텀 로직을 박아 넣는 대신, 요청을 외부 프로그램에 넘겨 살펴보거나 고치게 한 뒤 하던 일을 이어간다. 제품이 아니라 확장 지점이다.
gRPC
The protocol used for that conversation — a fast, typed RPC over HTTP/2. For reading this page you can treat it as "the private line between Envoy and the external program". 그 대화에 쓰는 프로토콜. HTTP/2 위에서 도는 빠르고 타입이 정해진 RPC다. 이 글을 읽는 데는 "Envoy와 외부 프로그램 사이의 전용선" 정도로 봐도 충분하다.
BBR
One such external program, and a tiny one. Its whole job: read model out of the JSON body and write it into a header. It makes no routing decision itself — it just moves one string from a place the router cannot see to a place it can. 그런 외부 프로그램 중 하나이고, 아주 작다. 하는 일 전부: JSON body에서 model을 읽어 헤더에 써 넣는 것. 라우팅을 직접 결정하지 않는다 — 문자열 하나를, 라우터가 못 보는 곳에서 볼 수 있는 곳으로 옮길 뿐이다.

That is the entire job. From that header onward, ordinary header-based routing works again, and the rest of the stack never has to think about JSON. 하는 일은 이게 전부다. 이 헤더가 생긴 순간부터는 평범한 헤더 라우팅이 다시 작동하고, 그 뒤로는 스택 어디서도 JSON을 신경 쓸 필요가 없다.

One consequence worth noticing early: BBR is wired in with INSERT_FIRST, at the very front of the HTTP filter chain. It has to be. No routing decision of any kind can be made before the model is known, so nothing may run ahead of it. 일찍 짚어둘 게 하나 있다. BBR은 INSERT_FIRST로, HTTP 필터 체인 맨 앞에 꽂힌다. 그럴 수밖에 없다. 모델을 알기 전에는 어떤 라우팅 판단도 불가능하므로, 그 앞에 뭔가가 먼저 돌 수 없다.

2 Three Kubernetes words first: Service, Operator, Gateway 먼저 쿠버네티스 단어 셋 — Service, Operator, Gateway

These three get thrown around loosely and it makes everything after this harder than it needs to be. All three have a concrete instance in the path we are about to follow. 이 셋은 대충 섞어 쓰이는 경우가 많은데, 그러면 뒤의 내용이 필요 이상으로 어려워진다. 셋 다 곧 따라갈 경로 안에 실물이 하나씩 있다.

Service — a stable address in front of a moving set of podsService — 계속 바뀌는 pod 앞에 붙은 고정 주소

Pods are disposable. They get replaced, and every replacement gets a new IP. A Service is a fixed virtual IP and DNS name that load-balances to whichever pods currently match a label selector. In a well-formed config, nothing ever names a pod IP. pod는 언제든 버려지는 것이다. 교체되고, 교체될 때마다 IP가 새로 붙는다. Service는 label selector에 현재 매칭되는 pod들에게 부하를 분산해주는, 고정된 가상 IP이자 DNS 이름이다. 제대로 된 설정이라면 어디에서도 pod IP를 직접 적지 않는다.

The types are worth knowing precisely, because one of them shows up later as a red herring: 타입은 정확히 알아두는 게 좋다. 그중 하나가 뒤에서 헷갈리는 요소로 등장하기 때문이다.

Type타입 What it adds추가되는 것 Reachable from접근 가능 범위
ClusterIP (default) a virtual IP + DNS name inside the cluster클러스터 내부 가상 IP와 DNS 이름 inside the cluster only클러스터 내부에서만
NodePort plus a static port (30000–32767 by default) opened on every node's IP추가로 모든 노드의 IP에 고정 포트(기본 30000–32767) 하나를 연다 outside, if you can reach a node IP노드 IP에 닿을 수 있다면 외부에서도

headlessheadless (clusterIP: None) no virtual IP — DNS returns the pod IPs directly가상 IP 없음 — DNS가 pod IP를 그대로 돌려준다 inside; the caller balances itself내부. 부하 분산은 호출자가 직접

NodePort exists as the low-tech way in from outside when there is no cloud load balancer: pick a port, and every node in the cluster starts answering on it and forwards to the Service. The costs are an ugly high port number, no TLS termination, and the caller needing to know a node IP. Keep this one in mind — a cluster can have a NodePort Service sitting next to the real entry point without it being the path anything actually uses. NodePort는 클라우드 로드밸런서가 없을 때 외부에서 들어오는 저기술 통로다. 포트 하나를 정하면 클러스터의 모든 노드가 그 포트로 응답하기 시작하고 Service로 넘긴다. 대가는 못생긴 고번호 포트, TLS 종료 없음, 그리고 호출자가 노드 IP를 알아야 한다는 것. 이건 기억해두자 — 실제 진입점 옆에 NodePort Service가 하나 놓여 있어도, 그게 실제로 쓰이는 경로가 아닐 수 있다.

Operator — a controller that keeps reality matching a custom resourceOperator — 선언한 것과 현실을 계속 맞춰주는 컨트롤러

Kubernetes natively understands only its built-in kinds. An operator extends it: you install a CRD (a new kind) plus a controller that watches those objects and continuously creates, updates and deletes real resources so the world matches what you declared. It is a loop, not a one-shot translation — delete something it manages and it puts the thing back. 쿠버네티스는 기본 제공 kind만 이해한다. operator는 그걸 확장한다 — CRD(새 kind)를 설치하고, 그 오브젝트를 감시하면서 선언한 대로 현실이 되도록 실제 리소스를 계속 만들고 고치고 지우는 컨트롤러를 함께 띄운다. 일회성 변환이 아니라 루프다. 그가 관리하는 걸 지우면 다시 만들어 놓는다.

Two operators appear in this request path. One turns a Gateway into an actual proxy; the other turns a custom "inference service" resource into a Deployment of engine pods. You can trace the second one entirely through ownership links: 이 경로에는 operator가 둘 등장한다. 하나는 Gateway를 실제 프록시로 만들고, 다른 하나는 커스텀 "inference service" 리소스를 엔진 pod들의 Deployment로 만든다. 두 번째는 ownership 링크만 따라가도 전부 추적된다.

InferenceService/llama-70b (spec.replicas: 2) ← what you declare └─ reconciled by the operator └─ Deployment/llama-70b 2/2 └─ ReplicaSet/llama-70b-75fb767c7d └─ pod llama-70b-75fb767c7d-dfg2x labels: pool=epp-llama-70b ← what InferencePool selects on
Where the two worlds join두 세계가 만나는 지점 That last label is the seam. The operator stamps it onto every pod it creates; the routing layer's InferencePool selects on it. Neither side knows about the other — they agree on a label, and that is the whole contract. 마지막 줄의 label이 이음매다. operator가 자기가 만드는 모든 pod에 그걸 찍고, 라우팅 쪽의 InferencePool이 그걸로 고른다. 양쪽은 서로를 모른다 — label 하나에 합의했을 뿐이고, 계약은 그게 전부다.

Gateway — a declaration of a proxy, not the proxyGateway — 프록시 그 자체가 아니라 프록시를 선언한 것

Gateway is a Gateway API resource. It says "I want a proxy listening on these ports" and names a gatewayClassName to say who should provide it. It is intent. Something has to materialize it — and that something is an operator, which is why the previous subsection comes first. Gateway는 Gateway API 리소스다. "이 포트들로 듣는 프록시가 필요하다"고 말하고, gatewayClassName으로 누가 제공할지를 지정한다. 이건 의도다. 누군가 실체로 만들어줘야 하고, 그 누군가가 operator다 — 앞 절을 먼저 둔 이유가 이거다.

In plain words — Istio and istiod쉽게 말하면 — Istio 와 istiod
Istio
A service mesh: a layer that takes over networking between services in a cluster — routing, retries, mTLS, telemetry — so applications do not implement it themselves. Its data plane is Envoy. You do not have to adopt the mesh to use its gateway; here it is being used only as a Gateway API implementation. 서비스 메시. 클러스터 안 서비스들 사이의 네트워킹(라우팅·재시도·mTLS·텔레메트리)을 대신 떠맡아, 애플리케이션이 그걸 직접 구현하지 않게 해주는 계층이다. data plane 이 Envoy 다. 게이트웨이를 쓰려고 메시 전체를 도입할 필요는 없고, 여기서는 Gateway API 구현체로만 쓰이고 있다.
istiod
Istio's control plane — the single process that watches Kubernetes objects and pushes configuration down to the Envoys. It is the thing that reads your Gateway and creates real pods for it. Istio 의 control plane. 쿠버네티스 오브젝트를 감시하다가 Envoy 들에게 설정을 내려보내는 프로세스 하나다. 당신이 쓴 Gateway 를 읽고 실제 pod 를 만들어 주는 게 이 녀석이다.
gatewayClassName
Which implementation should honour this Gateway. istio means "istiod, this one is yours". Swap the value and a different controller — NGINX, Envoy Gateway, a cloud LB — provides the proxy instead, from the same YAML. 이 Gateway 를 누가 맡을지 지정한다. istio 면 "istiod, 이건 네 거다" 라는 뜻이다. 값만 바꾸면 같은 YAML 로 다른 컨트롤러(NGINX, Envoy Gateway, 클라우드 LB)가 프록시를 대신 제공한다.

With gatewayClassName: istio, istiod's gateway controller materializes it as a Deployment of Envoy pods plus a ClusterIP Service in front of them — both owned by the Gateway object: gatewayClassName: istio라면 istiod의 gateway controller가 이걸 Envoy pod들의 Deployment와 그 앞의 ClusterIP Service로 실체화한다. 둘 다 Gateway 오브젝트가 소유한다.

Gateway/gw ← the declaration ├─ Deployment/gw-istio → 3 Envoy pods ← created by the controller └─ Service/gw-istio → ClusterIP :80 ← created by the controller metadata.ownerReferences: Gateway/gw labels: gateway.istio.io/managed=istio.io-gateway-controller

And the Gateway reports back where it ended up, in status.addresses. That field — not any Service you happen to find nearby — is the authoritative answer to "what address is this gateway on?". 그리고 Gateway는 자기가 어디에 자리 잡았는지를 status.addresses에 보고한다. "이 게이트웨이의 주소가 뭐냐"의 정답은 근처에서 우연히 발견한 Service가 아니라 이 필드다.

HTTPRoutes then attach to a Gateway through parentRefs. That is how a routing rule finds its proxy, and it is why routes and gateways can be owned by different teams in different namespaces. HTTPRoute는 parentRefs로 Gateway에 붙는다. 라우팅 규칙이 자기 프록시를 찾는 방법이 이거고, 덕분에 route와 gateway를 서로 다른 네임스페이스의 다른 팀이 소유할 수 있다.

The rest of the cast, one line each나머지 등장인물, 한 줄씩

Everything below shows up by name from here on. Two of them are processes — actual programs running in pods. The others are pieces of configuration: YAML that changes what the processes do. Mixing up which is which is the single most common source of confusion in this stack. 아래 이름들이 여기서부터 계속 등장한다. 이 중 둘은 프로세스 — pod 안에서 실제로 도는 프로그램이다. 나머지는 설정이다 — 그 프로세스들이 하는 일을 바꾸는 YAML. 어느 쪽인지 헷갈리는 게 이 스택에서 가장 흔한 혼란의 원인이다.

Name이름 Kind종류 What it is, in one line한 줄 설명
Envoy process프로세스 The proxy every request actually passes through. Created for you by istiod when you declare a Gateway. 모든 요청이 실제로 지나가는 프록시. Gateway를 선언하면 istiod가 대신 만들어 준다.
BBR process프로세스 Reads model from the body, writes it into a header. One deployment for the whole cluster. body에서 model을 읽어 헤더에 써 넣는다. 클러스터 전체에 배포 하나.
EPP (endpoint picker) process프로세스 Given the candidate pods for one model, picks which one this request goes to — by queue depth, KV-cache pressure and so on. One per model. Plain round-robin is wrong for LLMs because pod load is wildly uneven. 한 모델의 후보 pod 중 이 요청을 누구에게 보낼지 고른다 — 큐 길이, KV 캐시 압력 등을 보고. 모델당 하나. LLM은 pod마다 부하가 극단적으로 다르기 때문에 단순 라운드로빈으로는 안 된다.
EnvoyFilter config설정 Istio's escape hatch for editing Envoy's filter chain directly. Here it is what plugs BBR in as an ext_proc call. Nothing runs; it only tells Envoy who to call. Envoy의 필터 체인을 직접 손대는 Istio의 비상구. 여기서는 BBR을 ext_proc 호출로 꽂는 역할이다. 뭔가 실행되는 게 아니라, Envoy에게 누구를 호출할지 알려줄 뿐이다.
filter chain필터 체인 concept개념 The ordered list of steps Envoy runs on every request — auth, rewrites, ext_proc calls, and finally routing. Order matters, which is why BBR is forced to the front. Envoy가 요청마다 순서대로 실행하는 단계 목록 — 인증, 재작성, ext_proc 호출, 마지막에 라우팅. 순서가 중요하고, 그래서 BBR이 맨 앞으로 강제된다.
HTTPRoute config설정 One routing rule: if this header equals this value, send it to that pool. One per model. 라우팅 규칙 한 장: 이 헤더가 이 값이면 저 풀로 보내라. 모델당 하나.
InferencePool config설정 The candidate list: which pods serve this model (a label selector) and which EPP to ask. It does not pick — it says who is eligible and who decides. 후보 명단: 이 모델을 서빙하는 pod가 누구인지(label selector)와 어느 EPP에게 물을지. 직접 고르지는 않는다 — 자격자와 결정권자를 지정할 뿐이다.
The whole thing in one sentence한 문장으로 BBR moves the model name into a header so Envoy can route on it; the HTTPRoute says which InferencePool that model belongs to; the pool names an EPP, and the EPP picks the exact pod. Everything else in this note is detail hanging off those four steps. BBR이 모델 이름을 헤더로 옮겨 Envoy가 그걸로 라우팅할 수 있게 하고, HTTPRoute가 그 모델이 어느 InferencePool 소속인지 말해주고, 풀이 지정한 EPP가 정확히 어느 pod인지 고른다. 이 글의 나머지는 전부 이 네 단계에 딸린 디테일이다.

3 The full path, end to end 전체 경로

Here is the whole thing. The single most important thing this diagram has to get right is that everything happens inside Envoy — BBR and the picker are side-calls, not stops on the way. 전체 그림이다. 이 그림이 반드시 정확히 담아야 하는 한 가지는 모든 게 Envoy 안에서 일어난다는 것이다 — BBR과 picker는 지나가는 정거장이 아니라 곁가지 호출이다.

Object names follow the convention <prefix>-<model>, one set per served model. 오브젝트 이름은 <prefix>-<model> 규칙을 따르며, 서빙하는 모델마다 한 세트씩 존재한다.

Two things it is easy to draw wrong잘못 그리기 쉬운 두 가지 The picker does not forward the request. ext_proc is a gRPC side-call: Envoy asks, the picker answers with an endpoint, control returns to Envoy, and Envoy proxies to the pod. Drawing the flow as continuing downward out of the picker into the engine is wrong, and it matters — it means the picker can never be the cause of a slow or truncated response body. It only ever answers one question.

A NodePort Service next door is not the entry point. A cluster may well have one pointing at the same Envoy pods, left over or provisioned just in case. The authoritative address is whatever the Gateway itself reports in status.addresses — here a ClusterIP Service, meaning callers are in-cluster. picker는 요청을 넘겨주지 않는다. ext_proc은 gRPC 곁가지 호출이다 — Envoy가 묻고, picker가 엔드포인트로 답하고, 제어는 Envoy로 돌아오고, 그다음 Envoy가 pod로 프록시한다. picker에서 아래로 이어져 엔진으로 들어가게 그리면 틀린 그림이고, 이건 실제로 중요하다 — picker는 응답이 느리거나 잘리는 원인이 될 수 없다는 뜻이기 때문이다. 질문 하나에만 답할 뿐이다.

옆에 있는 NodePort Service는 진입점이 아니다. 같은 Envoy pod를 가리키는 NodePort가 남아 있거나 혹시 몰라 만들어져 있을 수 있다. 정답은 Gateway가 status.addresses에 스스로 보고하는 주소다 — 여기서는 ClusterIP Service이고, 즉 호출자가 클러스터 내부에 있다는 뜻이다.

Two decisions get made on the way down, and they are made by two different components for two different reasons: 내려가는 길에 결정이 두 번 내려지는데, 서로 다른 이유로 서로 다른 컴포넌트가 내린다.

Which model?어느 모델인가?

Answered by BBR, once, globally, for every model. Cheap: parse JSON, set a header. BBR이 답한다. 전역에 하나뿐이고 모든 모델이 공유한다. 값싼 작업이다 — JSON 파싱하고 헤더 심기.

Which replica?어느 replica인가?

Answered by the EPP, per model, from live engine state. Expensive, and the whole point of the stack. EPP가 답한다. 모델마다 따로 있고, 살아있는 엔진 상태를 보고 판단한다. 비싼 작업이고, 이 스택이 존재하는 이유다.

Note the asymmetry in cardinality — one BBR for the whole cluster, one EPP per model. That is not an accident, and it has a consequence we will get to in section 6. 개수의 비대칭을 눈여겨보자 — BBR은 클러스터 전체에 하나, EPP는 모델마다 하나. 우연이 아니고, 6절에서 다룰 결과를 낳는다.

Why the picker is addressed as a Service, not a pod picker를 pod가 아니라 Service로 가리키는 이유

If the split between Deployment and Service has never quite clicked, this is a good place for it to. The Deployment is the thing; the Service is its stable address. Deployment와 Service의 구분이 아직 헷갈린다면 여기가 이해하기 좋은 지점이다. Deployment는 실물이고, Service는 그 앞에 붙은 고정 주소다.

Deployment/epp-llama-70b 2/2 ├─ pod epp-llama-70b-6bc8879976-2vr6s IP: changes on every restart └─ pod epp-llama-70b-6bc8879976-btw6z IP: changes on every restart Service/epp-llama-70b ClusterIP 10.43.x.x ← does not change └─ load-balances to the two pods above

The Deployment's job is "keep two of these alive". When one dies it makes a new one — with a different IP. On the cluster I read this from, those two picker pods had already restarted three and two times respectively. Had anything hardcoded a pod IP, routing would have broken silently each time. Deployment가 하는 일은 "이걸 두 개 살려둬라"다. 하나가 죽으면 새로 만드는데, 그 새 pod는 IP가 다르다. 내가 읽어온 클러스터에서 이 picker pod 두 개는 이미 각각 세 번, 두 번 재시작한 상태였다. 어딘가 pod IP를 박아뒀다면 그때마다 라우팅이 조용히 깨졌을 것이다.

That is precisely why InferencePool.endpointPickerRef points at a Service. Nothing in the configuration ever names a pod. InferencePool.endpointPickerRef가 Service를 가리키는 이유가 바로 이거다. 설정 어디에도 pod를 직접 지목하는 곳이 없다.

5 The reverse path: how the picker knows anything 역방향 경로 — picker는 어떻게 아는가

Everything so far describes a request travelling down. But look at what the picker is being asked to do: given two identical replicas of the same model, choose the better one. On what basis? 여기까지는 요청이 아래로 내려가는 얘기였다. 그런데 picker가 요구받는 일을 보자 — 똑같은 모델의 replica 두 개 중 더 나은 쪽을 고르라는 것이다. 무엇을 근거로?

Queue depth and KV-cache utilization it can scrape from engine metrics. But the decision that actually matters for latency is prefix cache locality: if replica A already holds the KV blocks for this conversation's prefix and replica B does not, sending it to A can skip most of the prefill. That is not a metric you can average — it is a question about specific blocks on a specific pod. 큐 길이나 KV 캐시 사용률은 엔진 메트릭에서 긁어올 수 있다. 하지만 지연에 실제로 영향을 주는 판단은 prefix cache locality다 — 이 대화의 prefix에 해당하는 KV 블록을 replica A가 이미 들고 있고 B는 없다면, A로 보내면 prefill 대부분을 건너뛴다. 이건 평균 낼 수 있는 메트릭이 아니다. 특정 pod에 특정 블록이 있느냐는 질문이다.

So vLLM publishes it. Each engine is launched with a flag pointing back at the picker: 그래서 vLLM이 그걸 발행한다. 각 엔진은 picker를 가리키는 플래그를 달고 뜬다. 

--kv-events-config '{
  "enable_kv_cache_events": true,
  "publisher": "zmq",
  "endpoint": "tcp://epp-llama-70b:5557",
  "topic": "kv@<POD_IP>:8000@meta-llama/Llama-3.1-70B-Instruct"
}'

As blocks are cached and evicted, the engine streams those events over ZeroMQ to :5557 on the picker's Service. The picker keeps a running index of which pod holds which prefix, and scores against it. 블록이 캐시되고 축출될 때마다 엔진이 그 이벤트를 ZeroMQ로 picker Service의 :5557에 흘려보낸다. picker는 어느 pod가 어느 prefix를 들고 있는지 색인을 유지하면서 그걸로 점수를 매긴다.

The shape of it구조의 모양 Requests flow down; the information needed to route them flows up. The control loop is closed by the engines themselves reporting their own cache state — which means the routing quality of the whole stack depends on a flag on each vLLM process, not on anything in the gateway. 요청은 아래로 흐르고, 그 요청을 라우팅하는 데 필요한 정보는 위로 흐른다. 제어 루프를 닫는 건 엔진이 스스로 자기 캐시 상태를 보고하는 행위다 — 즉 이 스택 전체의 라우팅 품질이 게이트웨이가 아니라 각 vLLM 프로세스의 플래그 하나에 달려 있다.

That last point has a sharp edge, and it is the kind of thing you only notice by reading the actual launch arguments rather than the architecture diagram. On the cluster I looked at, one of the eight models was running without --kv-events-config at all. Nothing was broken; no alert fired. It was simply being routed with no cache-locality signal — the expensive picker in front of it degraded to something much closer to round-robin, silently, for as long as anyone cared to not look. 마지막 문장에 날카로운 구석이 있는데, 아키텍처 다이어그램이 아니라 실제 실행 인자를 읽어야만 보이는 종류의 것이다. 내가 본 클러스터에서는 여덟 모델 중 하나가 --kv-events-config 없이 돌고 있었다. 아무것도 고장 나지 않았고 알럿도 없었다. 그저 캐시 지역성 신호 없이 라우팅되고 있었을 뿐이다 — 앞에 붙은 비싼 picker가 조용히 라운드로빈에 가깝게 퇴화한 채로, 아무도 들여다보지 않는 동안 계속.

Failure mode with no symptom증상 없는 장애 A missing publisher flag does not produce an error anywhere. The engine serves correctly, the picker picks, the request succeeds. You lose only the thing you built the stack for. Worth an explicit check that every engine actually publishes, rather than trusting that it was configured once. publisher 플래그가 빠져도 어디서도 에러가 나지 않는다. 엔진은 정상 응답하고, picker는 고르고, 요청은 성공한다. 잃는 건 이 스택을 만든 이유 딱 하나뿐이다. 한 번 설정했으니 되어 있겠지 믿는 대신, 모든 엔진이 실제로 발행하고 있는지 명시적으로 확인할 가치가 있다.

6 Control path, data path, and where it breaks control path와 data path, 그리고 깨지는 지점

In plain words — control path, data path, sidecar쉽게 말하면 — control path · data path · 사이드카
control pathcontrol path
The part that decides. It looks at a request just long enough to say "this one goes to pod X", then steps aside. Small traffic, big influence. 결정하는 쪽. 요청을 "이건 pod X로" 라고 말할 만큼만 들여다보고 비켜선다. 트래픽은 적고 영향력은 크다.
data pathdata path
The part the bytes actually flow through. For an LLM that means every generated token. Anything on this path is directly in the latency budget. 실제로 바이트가 흐르는 쪽. LLM 이면 생성되는 토큰 전부가 여기를 지난다. 이 경로에 놓인 것은 곧바로 지연 예산에 들어간다.
sidecar사이드카
An extra container placed inside the same pod as the application, to intercept its traffic. Powerful, but a pod's container list is fixed at creation — adding one means recreating the pod, i.e. restarting the engine and reloading the weights. 애플리케이션과 같은 pod 안에 끼워 넣어 그 트래픽을 가로채는 추가 컨테이너. 강력하지만 pod 의 컨테이너 목록은 생성 시점에 고정된다 — 하나 붙이려면 pod 를 다시 만들어야 하고, 그건 엔진 재시작과 가중치 재적재를 뜻한다.

Why this section exists. Where a component sits decides both how much it can slow you down and how hard it is to replace. That is the whole argument below. 이 절이 있는 이유. 컴포넌트가 어느 쪽에 앉아 있느냐가 "얼마나 느려지게 할 수 있는가" 와 "교체가 얼마나 어려운가" 를 동시에 결정한다. 아래 내용은 전부 그 이야기다.

"The tokens don't pass through" is half true"토큰은 통과하지 않는다"는 절반만 맞다

This stack is normally described as control-plane routing: the components decide where a request goes, and the tokens flow straight from Envoy to the engine. That framing is useful but it papers over a detail visible in the filter's own configuration: 이 스택은 보통 control-plane 라우팅이라고 설명된다 — 컴포넌트들은 요청이 어디로 갈지만 정하고, 토큰은 Envoy에서 엔진으로 직행한다는 것이다. 유용한 설명이지만, 필터 설정에 드러나는 디테일 하나를 덮는다.

Request body (the prompt)요청 body (프롬프트) Response (generated tokens)응답 (생성 토큰)
BBR passes through — request_body_mode: FULL_DUPLEX_STREAMED 통과한다 — request_body_mode: FULL_DUPLEX_STREAMED no — response_body_mode: NONE, headers SKIP 아니다 — response_body_mode: NONE, 헤더도 SKIP
EPP endpoint decision only엔드포인트 결정만 no아니다

So the prompt genuinely does traverse BBR. What never touches either component is the response stream — and that is where the token volume and the TTFT/TPOT sensitivity live. That is the honest version of the claim: this is not a data-path gateway on the side that matters for latency. 즉 프롬프트는 실제로 BBR을 지나간다. 두 컴포넌트 어느 쪽도 건드리지 않는 건 응답 스트림이고, 토큰 부피와 TTFT/TPOT 민감도가 사는 곳이 바로 거기다. 정직하게 말하면 이렇다 — 지연에 중요한 쪽에서는 data-path 게이트웨이가 아니다.

The distinction matters the moment you consider replacing this with a true data-path gateway, where every token passes through. Such a gateway needs a sidecar on the serving pod, and attaching a sidecar means restarting the engine. A control-plane router can be swapped with a config change; a data-path one cannot. That single fact dictates the entire shape of a migration — you can only move a model without downtime if it has a spare replica to carry traffic while the other restarts. 이 구분은 이걸 진짜 data-path 게이트웨이로 바꾸려는 순간 의미를 갖는다. 모든 토큰이 통과하는 게이트웨이는 서빙 pod에 사이드카가 필요하고, 사이드카를 붙이려면 엔진을 재시작해야 한다. control-plane 라우터는 설정 변경으로 교체되지만 data-path는 그럴 수 없다. 이 사실 하나가 마이그레이션 전체의 모양을 결정한다 — 여유 replica가 있어서 한쪽이 재시작하는 동안 트래픽을 받아줄 수 있는 모델만 무중단 전환이 가능하다.

The blast radius is not symmetric장애 반경은 대칭이 아니다

Both components fail closed — BBR with failure_mode_allow: false, the picker with failureMode: FailClose. Identical policy, very different consequences, because of the cardinality asymmetry from section 3. 두 컴포넌트 다 fail closed다 — BBR은 failure_mode_allow: false, picker는 failureMode: FailClose. 정책은 같은데 결과는 전혀 다르다. 3절에서 본 개수 비대칭 때문이다.

BBR — 1 pod, globalpod 1개, 전역

If it dies, no request for any model can be routed — none of them get their model header. Every model goes down at once. 죽으면 어떤 모델의 요청도 라우팅될 수 없다 — 모델 헤더가 안 붙으니까. 전 모델이 동시에 죽는다.

EPP — 2 pods per modelEPP — 모델당 pod 2개

Losing one is survivable. Losing both takes out that one model and nothing else. 하나 잃는 건 버틴다. 둘 다 잃어도 그 모델 하나만 죽고 나머지는 멀쩡하다.

The component that is architecturally trivial — parse JSON, set a header — is the single point of failure for the entire fleet, while the component doing all the interesting work is comfortably redundant. It is worth noticing that this is an easy thing to get backwards when you reason from an architecture diagram, where BBR looks like a footnote and the picker looks like the system. 구조적으로 사소한 컴포넌트 — JSON 파싱하고 헤더 심기 — 가 전체 fleet의 단일 장애점이고, 정작 흥미로운 일을 다 하는 컴포넌트는 넉넉하게 이중화돼 있다. 아키텍처 다이어그램만 보고 판단하면 거꾸로 알기 쉬운 지점이다. 그림에서 BBR은 각주처럼 보이고 picker가 시스템처럼 보이기 때문이다.

What I'd take from this여기서 가져갈 것 Two things were only visible by reading the live objects rather than the design: an engine silently publishing no cache events, and a one-replica component gating every model in the cluster. Neither shows up as an error. Both are one kubectl get -o yaml away. 설계 문서가 아니라 실제 오브젝트를 읽어야만 보인 게 두 가지였다 — 캐시 이벤트를 조용히 발행하지 않던 엔진 하나, 그리고 클러스터의 모든 모델을 좌우하는 replica 1짜리 컴포넌트. 둘 다 에러로는 안 나타난다. 그리고 둘 다 kubectl get -o yaml 한 번이면 보인다.

7 The YAML, and how to read it off a cluster YAML, 그리고 클러스터에서 직접 읽는 법

Trimmed to the fields that matter — managed fields, timestamps and most of status removed. Read in order, these five objects are the whole path. 중요한 필드만 남기고 managed fields·타임스탬프·status 대부분을 걷어냈다. 순서대로 읽으면 이 다섯 오브젝트가 경로 전체다.

1. Gateway — the declaration선언

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: gw
spec:
  gatewayClassName: istio          # who materializes this
  listeners:
  - name: http
    port: 80
    protocol: HTTP
    allowedRoutes:
      namespaces:
        from: All             # routes may attach from any namespace
status:
  addresses:
  - type: Hostname
    value: gw-istio.<ns>.svc.cluster.local    # ← the authoritative address

2. Service — created by the operator, not by hand사람이 아니라 operator가 만든 것

apiVersion: v1
kind: Service
metadata:
  name: gw-istio
  labels:
    gateway.istio.io/managed: istio.io-gateway-controller
  ownerReferences:                  # ← delete the Gateway and this goes with it
  - kind: Gateway
    name: gw
spec:
  type: ClusterIP                  # ← in-cluster only
  selector:
    gateway.networking.k8s.io/gateway-name: gw
  ports:
  - name: http
    port: 80
    targetPort: http

The ownerReferences block is the fingerprint of an operator. Nobody wrote this Service; the gateway controller derived it from the Gateway and will recreate it if you delete it. ownerReferences 블록이 operator의 지문이다. 이 Service는 아무도 손으로 안 썼다. gateway controller가 Gateway에서 파생시킨 것이고, 지우면 다시 만들어 놓는다.

3. EnvoyFilter — how BBR gets into the chainBBR이 체인에 들어가는 방법

apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: body-based-router
spec:
  configPatches:
  - applyTo: HTTP_FILTER
    match:
      listener:
        filterChain:
          filter:
            name: envoy.filters.network.http_connection_manager
    patch:
      operation: INSERT_FIRST                # ← ahead of everything else
      value:
        name: envoy.filters.http.ext_proc
        typed_config:
          "@type": type.googleapis.com/envoy.extensions.filters.http.ext_proc.v3.ExternalProcessor
          failure_mode_allow: false          # ← BBR down = every request fails
          grpc_service:
            envoy_grpc:
              cluster_name: outbound|9004||body-based-router.<ns>.svc.cluster.local
          processing_mode:
            request_header_mode: SEND
            request_body_mode: FULL_DUPLEX_STREAMED   # ← the prompt does pass through
            response_header_mode: SKIP
            response_body_mode: NONE                  # ← the response does not

4. HTTPRoute — the rule규칙

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: epp-llama-70b
spec:
  parentRefs:                          # ← attaches to the Gateway
  - kind: Gateway
    name: gw
  rules:
  - matches:
    - headers:
      - name: X-Gateway-Model-Name       # ← the header BBR set
        type: Exact
        value: meta-llama/Llama-3.1-70B-Instruct
      path:
        type: PathPrefix
        value: /
    backendRefs:
    - kind: InferencePool               # ← not a Service
      name: epp-llama-70b
    timeouts:
      request: 0s                        # ← no timeout; generations run long
      backendRequest: 0s

5. InferencePool — the candidates and the picker후보와 picker

apiVersion: inference.networking.k8s.io/v1
kind: InferencePool
metadata:
  name: epp-llama-70b
spec:
  selector:
    matchLabels:
      pool: epp-llama-70b            # ← the label the operator stamped on the engine pods
  targetPorts:
  - number: 8000
  endpointPickerRef:
    kind: Service                   # ← a Service, never a pod
    name: epp-llama-70b
    port:
      number: 9002
    failureMode: FailClose         # ← picker down = this model's requests fail

Reading it yourself직접 읽어보기

# what kinds exist at all, and their API groups
kubectl api-resources | grep -iE 'gateway|route|inference'
kubectl get crd | grep -E 'inference'

# the schema of a kind, field by field — works for CRDs too
kubectl explain inferencepool.spec
kubectl explain inferencepool.spec.endpointPickerRef

# the full object
kubectl -n $NS get httproute epp-llama-70b -o yaml

# spec only, without the managedFields noise
kubectl -n $NS get gateway gw -o yaml | sed -n '/^spec:/,/^status:/p'

# one field
kubectl -n $NS get gateway gw -o jsonpath='{.status.addresses}'
kubectl -n $NS get inferencepool epp-llama-70b -o jsonpath='{.spec.endpointPickerRef}'

# who owns an object — this is how you trace an operator's work
kubectl -n $NS get svc gw-istio -o jsonpath='{.metadata.ownerReferences}'
kubectl -n $NS get pod <pod> -o jsonpath='{.metadata.ownerReferences}'

# which pods a Service actually resolves to right now
kubectl -n $NS get endpointslice -l kubernetes.io/service-name=gw-istio -o yaml

# what a running engine was actually launched with
# (beats trusting the manifest — this is how the missing flag turned up)
kubectl -n $NS exec <engine-pod> -- tr '\0' '\n' < /proc/1/cmdline
Two gotchas두 가지 함정 -o jsonpath has no conditionals — {if .nodePort} is not valid syntax and fails with unrecognized identifier if. Pipe into jq or python3 -c when you need logic.

-o yaml includes managedFields, which is routinely longer than the object itself. The sed line above is the fastest way to cut it down to something readable. -o jsonpath에는 조건문이 없다 — {if .nodePort}는 유효한 문법이 아니고 unrecognized identifier if로 실패한다. 판단이 필요하면 jq나 python3 -c로 넘기자.

-o yaml에는 managedFields가 딸려 오는데, 대개 오브젝트 본문보다 길다. 위의 sed 한 줄이 읽을 만한 크기로 줄이는 가장 빠른 방법이다.

That last command is worth singling out. Everything in this note came from reading live objects rather than the design docs — and the two findings in sections 5 and 6, the engine publishing nothing and the single-replica component gating the fleet, were both invisible in the architecture and one query away in the cluster. 마지막 명령은 따로 짚을 만하다. 이 글의 모든 내용은 설계 문서가 아니라 살아있는 오브젝트를 읽어서 나왔고, 5절과 6절의 발견 두 가지 — 아무것도 발행하지 않던 엔진, 그리고 fleet 전체를 좌우하는 replica 1짜리 컴포넌트 — 는 둘 다 아키텍처에서는 안 보이고 클러스터에서는 조회 한 번 거리였다.
