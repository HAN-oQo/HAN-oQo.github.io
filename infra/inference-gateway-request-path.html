Routing an LLM request when the model name is in the body 모델 이름이 body 안에 있을 때, 요청은 어떻게 라우팅되나

An OpenAI-compatible API sends every request to POST /v1/chat/completions with the model name in the JSON body, leaving path- and header-based routing nothing to match. This note follows one request through the Gateway API Inference Extension stack, read off a live cluster. OpenAI 호환 API는 모든 요청을 POST /v1/chat/completions로 보내고 모델 이름은 JSON body에 넣어, path·헤더 라우팅이 기댈 곳이 없다. 이 글은 요청 하나가 Gateway API Inference Extension 스택을 지나는 길을 실제 클러스터 오브젝트로 따라간다.

1 The problem: the router cannot read the body 문제: 라우터는 body를 못 읽는다

Say you are serving eight different models on one cluster and you want a single endpoint in front of all of them. A client sends this: 한 클러스터에 모델 여덟 개를 서빙하면서 그 앞에 엔드포인트 하나만 두고 싶다고 하자. 클라이언트는 이렇게 보낸다. 

POST /v1/chat/completions
Content-Type: application/json

{
  "model": "meta-llama/Llama-3.1-70B-Instruct",
  "messages": [ ... ]
}

The path is /v1/chat/completions for all eight models. There is no Host difference, no query string, no custom header. The only thing that tells the models apart is a field inside the request body. path는 여덟 모델 모두 /v1/chat/completions로 같다. Host도, 쿼리스트링도, 커스텀 헤더도 다르지 않다. 모델을 구분하는 정보는 요청 body 안에만 있다.

In plain words: proxy, L7, Envoy쉽게 말하면: 프록시 · L7 · Envoy
proxy프록시
A server between clients and the real servers that receives each request and forwards it to the right one. Here it is the single front door for eight models. 클라이언트와 실제 서버 사이에서 요청을 대신 받아 알맞은 서버로 넘기는 서버다. 여기서는 모델 여덟 개 앞의 단일 정문이다.
L7
The application layer. An L7 router decides on the HTTP path, method and headers. An L4 router sees only IP and port. Routing by model name is an L7 job. 애플리케이션 계층이다. L7 라우터는 HTTP의 path·메서드·헤더를 보고 판단하고, L4 라우터는 IP와 포트만 본다. 모델 이름으로 라우팅하는 일은 L7의 몫이다.
Envoy
The most widely used open-source L7 proxy. Nearly every Kubernetes gateway, including the one here, is Envoy underneath. "The gateway" in this note means an Envoy process. 가장 널리 쓰이는 오픈소스 L7 프록시다. 쿠버네티스 게이트웨이 구현체는 거의 다 내부가 Envoy이고, 이 글의 "게이트웨이"도 Envoy 프로세스를 뜻한다.

Envoy, like nearly every L7 router, routes on the request line and headers, which arrive first. The body comes later and can be huge. Routing on it means holding the whole request in memory before knowing where it goes, the last thing you want in front of streaming inference. Envoy를 비롯한 L7 라우터는 요청 맨 앞에 오는 요청 라인과 헤더만 보고 라우팅한다. body는 뒤에 오고 얼마든지 커질 수 있다. body로 판단하려면 목적지도 모르는 요청을 통째로 메모리에 들고 있어야 하는데, 스트리밍 추론 앞단에서 가장 피하고 싶은 일이다.

The gap간극 The information needed to route sits where the router structurally cannot look. The rest of this note follows from that. 라우팅에 필요한 정보가 라우터가 구조적으로 볼 수 없는 곳에 있다. 이 글의 나머지는 모두 여기서 나온다.

The Gateway API Inference Extension solves this with a small component called BBR (Body-Based Routing). It is an ext_proc filter: Envoy streams the request to it over gRPC, and BBR reads the model field and sets a header. Gateway API Inference Extension은 BBR(Body-Based Routing)이라는 작은 컴포넌트로 이 문제를 푼다. BBR은 ext_proc 필터다. Envoy가 gRPC로 요청을 넘기면 BBR이 model 필드를 읽어 헤더 하나를 붙인다. 

X-Gateway-Model-Name: meta-llama/Llama-3.1-70B-Instruct
In plain words: ext_proc, gRPC쉽게 말하면: ext_proc · gRPC
ext_proc
"External Processing": Envoy's official extension point for handing a request to an external program that inspects or modifies it before Envoy carries on. "External Processing". Envoy가 요청을 외부 프로그램에 넘겨 살펴보거나 고치게 한 뒤 이어서 처리하는 공식 확장 지점이다.
gRPC
A fast, typed RPC over HTTP/2. Here, think of it as the private line between Envoy and the external program. HTTP/2 위에서 도는 빠른 RPC다. 여기서는 Envoy와 외부 프로그램 사이의 전용선 정도로 보면 된다.

From that header onward, ordinary header-based routing works again and nothing else in the stack has to think about JSON. 이 헤더가 생기면 평범한 헤더 라우팅이 다시 통하고, 이후로는 스택 어디서도 JSON을 신경 쓰지 않는다.

BBR is wired in with INSERT_FIRST, at the very front of the HTTP filter chain. It has to be: no routing decision is possible before the model is known. BBR은 INSERT_FIRST로 HTTP 필터 체인 맨 앞에 꽂힌다. 모델을 알기 전에는 어떤 라우팅 판단도 할 수 없으니 그럴 수밖에 없다.

2 Three Kubernetes words first: Service, Operator, Gateway 먼저 쿠버네티스 단어 셋: Service, Operator, Gateway

These three are often used loosely. Each has a concrete instance in the path below. 이 셋은 자주 섞여 쓰인다. 셋 다 이어서 따라갈 경로 안에 실물이 있다.

Service: a stable address in front of a moving set of podsService: 계속 바뀌는 pod 앞의 고정 주소

Pods are disposable, and every replacement gets a new IP. A Service is a fixed virtual IP and DNS name that load-balances to whichever pods match a label selector. A well-formed config never names a pod IP. pod는 언제든 교체되고, 그때마다 IP가 바뀐다. Service는 label selector에 매칭되는 pod들로 부하를 나눠 주는 고정 가상 IP이자 DNS 이름이다. 제대로 된 설정은 pod IP를 직접 적지 않는다.

The types matter, because one of them shows up later as a red herring: 타입을 구분해 두자. 그중 하나가 뒤에서 혼동을 일으킨다.

Type타입 What it adds추가되는 것 Reachable from접근 가능 범위
ClusterIP (default) a virtual IP + DNS name inside the cluster클러스터 내부 가상 IP와 DNS 이름 inside the cluster only클러스터 내부에서만
NodePort plus a static port (30000–32767 by default) opened on every node's IP추가로 모든 노드의 IP에 고정 포트(기본 30000–32767) 하나를 연다 outside, if you can reach a node IP노드 IP에 닿을 수 있다면 외부에서도
LoadBalancer plus an external load balancer provisioned by the cloud추가로 클라우드가 프로비저닝하는 외부 로드밸런서 outside, via the LB's IPLB의 IP로 외부에서
headlessheadless (clusterIP: None) no virtual IP; DNS returns the pod IPs directly가상 IP 없음. DNS가 pod IP를 그대로 돌려준다 inside; the caller balances itself내부. 부하 분산은 호출자가 직접

NodePort is the low-tech way in from outside without a cloud load balancer: every node answers on the chosen port and forwards to the Service. The costs are a high port, no TLS termination, and callers needing a node IP. A NodePort Service can sit next to the real entry point without being the path anything uses. NodePort는 클라우드 로드밸런서가 없을 때 외부에서 들어오는 저기술 통로다. 모든 노드가 정한 포트로 받아 Service로 넘긴다. 대신 고번호 포트, TLS 종료 없음, 호출자가 노드 IP를 알아야 한다는 대가가 있다. 실제 진입점 옆에 NodePort Service가 있어도 실제로 쓰이는 경로가 아닐 수 있다.

Operator: a controller that keeps reality matching a custom resourceOperator: 선언과 현실을 계속 맞추는 컨트롤러

Kubernetes natively knows only its built-in kinds. An operator adds a CRD (a new kind) plus a controller that keeps real resources matching those objects. It is a loop, not a one-shot translation: delete something it manages and it comes back. 쿠버네티스는 기본 kind만 이해한다. operator는 CRD(새 kind)와, 그 오브젝트대로 실제 리소스를 계속 맞추는 컨트롤러를 함께 설치한다. 일회성 변환이 아니라 루프라서 관리 대상을 지우면 다시 만든다.

Two operators appear in this path. One turns a Gateway into a proxy, the other turns a custom "inference service" resource into a Deployment of engine pods. The second can be traced entirely through ownership links: 이 경로에는 operator가 둘 있다. 하나는 Gateway를 실제 프록시로, 다른 하나는 커스텀 "inference service" 리소스를 엔진 pod의 Deployment로 만든다. 두 번째는 ownership 링크만 따라가도 추적된다.

InferenceService/llama-70b (spec.replicas: 2) ← what you declare └─ reconciled by the operator └─ Deployment/llama-70b 2/2 └─ ReplicaSet/llama-70b-75fb767c7d └─ pod llama-70b-75fb767c7d-dfg2x labels: pool=epp-llama-70b ← what InferencePool selects on
Where the two worlds join두 세계가 만나는 지점 That last label is the seam. The operator stamps it on every pod it creates, and the InferencePool selects on it. Neither side knows the other. The label is the whole contract. 마지막 줄의 label이 이음매다. operator가 만드는 모든 pod에 이 label을 찍고, 라우팅 쪽 InferencePool이 이걸로 pod를 고른다. 양쪽은 서로를 모르고, label 하나가 계약의 전부다.

Gateway: a declaration of a proxy, not the proxyGateway: 프록시가 아니라 프록시의 선언

Gateway is a Gateway API resource. It says "I want a proxy listening on these ports" and names a gatewayClassName for who provides it. It is intent, and an operator materializes it. Gateway는 Gateway API 리소스다. "이 포트들로 듣는 프록시가 필요하다"고 선언하고, gatewayClassName으로 제공자를 지정한다. 이건 의도이고, 실체로 만드는 건 operator다.

In plain words: Istio and istiod쉽게 말하면: Istio와 istiod
Istio
A service mesh that takes over service-to-service networking (routing, retries, mTLS, telemetry). Its data plane is Envoy. Here it is used only as a Gateway API implementation, without adopting the mesh. 서비스 사이 네트워킹(라우팅·재시도·mTLS·텔레메트리)을 대신 맡는 서비스 메시다. data plane은 Envoy다. 여기서는 메시 없이 Gateway API 구현체로만 쓰인다.
istiod
Istio's control plane: the process that watches Kubernetes objects and pushes config to the Envoys. It reads your Gateway and creates real pods for it. Istio의 control plane. 쿠버네티스 오브젝트를 감시하다 Envoy에 설정을 내려보내고, Gateway를 읽어 실제 pod를 만든다.
gatewayClassName
Which implementation provides this Gateway. istio hands it to istiod. Change the value and another controller (NGINX, Envoy Gateway, a cloud LB) provides the proxy from the same YAML. 이 Gateway를 누가 맡을지 지정한다. istio면 istiod가 맡는다. 값만 바꾸면 같은 YAML로 다른 컨트롤러(NGINX, Envoy Gateway, 클라우드 LB)가 프록시를 제공한다.

With gatewayClassName: istio, istiod's gateway controller creates a Deployment of Envoy pods plus a ClusterIP Service in front, both owned by the Gateway: gatewayClassName: istio면 istiod의 gateway controller가 Envoy pod의 Deployment와 그 앞의 ClusterIP Service를 만든다. 둘 다 Gateway 오브젝트가 소유한다.

Gateway/gw ← the declaration ├─ Deployment/gw-istio → 3 Envoy pods ← created by the controller └─ Service/gw-istio → ClusterIP :80 ← created by the controller metadata.ownerReferences: Gateway/gw labels: gateway.istio.io/managed=istio.io-gateway-controller

The Gateway reports where it ended up in status.addresses. That field, not some Service nearby, is the authoritative address. Gateway는 자기 주소를 status.addresses에 보고한다. 근처에서 발견한 Service가 아니라 이 필드가 게이트웨이 주소의 정답이다.

HTTPRoutes attach to a Gateway through parentRefs, so routes and gateways can be owned by different teams in different namespaces. HTTPRoute는 parentRefs로 Gateway에 붙는다. 그래서 route와 gateway를 서로 다른 네임스페이스의 다른 팀이 소유할 수 있다.

The rest of the cast, one line each나머지 등장인물, 한 줄씩

Two of these are processes running in pods. The rest are configuration: YAML that changes what the processes do. Mixing the two up is the most common source of confusion in this stack. 이 중 둘은 pod 안에서 실제로 도는 프로세스이고, 나머지는 그 프로세스의 동작을 바꾸는 설정(YAML)이다. 둘을 헷갈리는 게 이 스택에서 가장 흔한 혼란이다.

Name이름 Kind종류 What it is, in one line한 줄 설명
Envoy process프로세스 The proxy every request passes through. istiod creates it when you declare a Gateway. 모든 요청이 지나가는 프록시. Gateway를 선언하면 istiod가 만든다.
BBR process프로세스 Reads model from the body, writes it into a header. One deployment for the whole cluster. body에서 model을 읽어 헤더에 써 넣는다. 클러스터 전체에 배포 하나.
EPP (endpoint picker) process프로세스 Picks which pod of one model gets the request, by queue depth, KV-cache pressure and so on. One per model, because LLM pod load is too uneven for round-robin. 큐 길이, KV 캐시 압력 등을 보고 한 모델의 pod 중 누구에게 보낼지 고른다. LLM은 pod별 부하 차이가 커서 라운드로빈이 맞지 않는다. 모델당 하나.
EnvoyFilter config설정 Istio's escape hatch for editing Envoy's filter chain. Here it plugs BBR in as an ext_proc call and runs nothing itself. Envoy 필터 체인을 직접 고치는 Istio의 비상구. 여기서는 BBR을 ext_proc 호출로 꽂을 뿐, 스스로 실행되지 않는다.
filter chain필터 체인 concept개념 The ordered steps Envoy runs on every request (auth, rewrites, ext_proc calls, then routing). Order matters, so BBR is forced to the front. Envoy가 요청마다 차례로 실행하는 단계(인증, 재작성, ext_proc 호출, 마지막에 라우팅). 순서가 중요해서 BBR이 맨 앞에 온다.
HTTPRoute config설정 One routing rule: if this header equals this value, send it to that pool. One per model. 라우팅 규칙 한 장: 이 헤더가 이 값이면 저 풀로 보내라. 모델당 하나.
InferencePool config설정 The candidate list: which pods serve this model (a label selector) and which EPP to ask. It does not pick. 후보 명단. 서빙 pod(label selector)와 물어볼 EPP를 지정할 뿐 직접 고르지 않는다.
The whole thing in one sentence한 문장으로 BBR moves the model name into a header so Envoy can route on it. The HTTPRoute maps that model to an InferencePool, the pool names an EPP, and the EPP picks the pod. The rest is detail on those four steps. BBR이 모델 이름을 헤더로 옮기면 Envoy가 그걸로 라우팅한다. HTTPRoute가 그 모델의 InferencePool을 정하고, 풀이 지정한 EPP가 pod를 고른다. 나머지는 이 네 단계의 디테일이다.

3 The full path, end to end 전체 경로

Everything happens inside Envoy. BBR and the picker are side-calls, not stops on the way. 모든 일은 Envoy 안에서 일어난다. BBR과 picker는 정거장이 아니라 곁가지 호출이다.

client │ POST /v1/chat/completions │ body: {"model":"meta-llama/Llama-3.1-70B-Instruct", ...} ▼ Service/gw-istio (ClusterIP :80) ← Gateway.status.addresses │ selector: gateway.networking.k8s.io/gateway-name=gw ▼ ┌──────────────────────────────────────────────────────────────────────────┐ │ Gateway/gw → Deployment/gw-istio, 3 Envoy pods │ │ │ │ ① ext_proc ──▶ Deployment/body-based-router :9004 (BBR, 1 pod) │ │ ◀── sets X-Gateway-Model-Name: meta-llama/Llama-3.1-70B-Instruct │ │ │ │ ② match HTTPRoute/epp-llama-70b on that header │ │ → backendRef: InferencePool/epp-llama-70b │ │ │ │ ③ ext_proc ──▶ Service/epp-llama-70b :9002 (EPP, 2 pods) │ │ ◀── replies with the chosen endpoint (a pod IP) │ │ │ │ ④ Envoy proxies the request to that pod │ └─────────────────────────────┬────────────────────────────────────────────┘ ▼ vLLM pod :8000 one of the Llama replicas │ KV events ──zmq──▶ Service/epp-llama-70b :5557 ──▶ EPP --kv-events-config how EPP learns what each pod has cached

Object names follow the convention <prefix>-<model>, one set per served model. 오브젝트 이름은 <prefix>-<model> 규칙을 따르고, 모델마다 한 세트씩 있다.

Two things it is easy to draw wrong잘못 그리기 쉬운 두 가지 The picker does not forward the request. ext_proc is a gRPC side-call: Envoy asks, the picker answers with an endpoint, and Envoy proxies to the pod. So the picker can never cause a slow or truncated response body.

A NodePort Service next door is not the entry point. The authoritative address is what the Gateway reports in status.addresses, here a ClusterIP Service, so callers are in-cluster. picker는 요청을 넘겨주지 않는다. ext_proc은 gRPC 곁가지 호출이다. Envoy가 묻고 picker가 엔드포인트로 답하면 Envoy가 pod로 프록시한다. 따라서 picker는 응답이 느리거나 잘리는 원인이 될 수 없다.

옆에 있는 NodePort Service는 진입점이 아니다. 정답은 Gateway가 status.addresses에 보고하는 주소다. 여기서는 ClusterIP Service이므로 호출자는 클러스터 내부에 있다.

Two decisions are made on the way down, by two different components: 내려가는 길에 두 번의 결정을 서로 다른 컴포넌트가 내린다.

Which model?어느 모델인가?

BBR, once, globally, for every model. Cheap: parse JSON, set a header. BBR이 답한다. 전역에 하나이고 모든 모델이 공유한다. JSON 파싱과 헤더 추가뿐이라 싸다.

Which replica?어느 replica인가?

The EPP, per model, from live engine state. Expensive, and the point of the stack. EPP가 모델마다 따로, 살아 있는 엔진 상태를 보고 답한다. 비싸고, 이 스택이 존재하는 이유다.

Note the asymmetry: one BBR for the cluster, one EPP per model. Section 6 shows why it matters. BBR은 클러스터에 하나, EPP는 모델마다 하나라는 비대칭에 주목하자. 6절에서 그 결과를 다룬다.

4 The resources, one by one 리소스 하나씩

Kind종류 Count개수 What it does하는 일
Service (NodePort)1 The address clients actually use. Selects the gateway pod. 클라이언트가 실제로 쓰는 주소. 게이트웨이 pod를 가리킨다.
Gateway1 The Envoy instance. One http:80 listener with no hostname, so everything arrives through one door. Envoy 인스턴스. hostname 없는 http:80 listener 하나로 모든 요청이 들어온다.
EnvoyFilter1 Config that wires BBR into the filter chain as an ext_proc call. BBR을 ext_proc 호출로 필터 체인에 꽂는 설정. 프로세스가 아니다.
Deployment (BBR)1 pod BBR itself, the process the filter calls. BBR 본체. 위 필터가 호출하는 프로세스다.
HTTPRouteN Routing rule: if the model header equals this, hand off to that pool. One per model. 라우팅 규칙: 모델 헤더가 이 값이면 저 풀로 넘겨라. 모델당 하나.
InferencePoolN Defines the candidate pod set (a label selector + a port) and names the endpoint picker to consult. 후보 pod 집합(label selector + 포트)을 정의하고, 물어볼 endpoint picker를 지정한다.
Deployment+Service (EPP)N × 2 pods The endpoint picker. Scores the candidates and returns one pod IP. endpoint picker. 후보들에 점수를 매겨 pod IP 하나를 돌려준다.

The name collision: read this before debugging 이름 충돌: 디버깅 전에 알아둘 것

Everything for one model shares one name. Query it and four kinds come back: 한 모델에 딸린 오브젝트가 모두 같은 이름을 쓴다. 그 이름으로 조회하면 네 종류가 나온다.

httproute/epp-llama-70b routing rule ← NOT the picker inferencepool/epp-llama-70b candidate pod set ← NOT the picker service/epp-llama-70b :9002 ┐ deployment/epp-llama-70b 2/2 ├ this is the picker pod/epp-llama-70b-<hash>-<id> ┘
Practical rule실전 규칙 "the epp-llama-70b" alone is ambiguous and leads to editing the wrong object. Always say the kind: the HTTPRoute, the InferencePool. I have seen this ambiguity cost real minutes in a change request review. "epp-llama-70b"만으로는 어느 오브젝트인지 알 수 없어 엉뚱한 것을 고치게 된다. HTTPRoute, InferencePool처럼 종류를 같이 말하자. 변경 요청 리뷰에서 이 모호함으로 실제로 시간을 날리는 걸 봤다.

Why the picker is addressed as a Service, not a pod picker를 pod가 아니라 Service로 가리키는 이유

The Deployment is the thing; the Service is its stable address. Deployment는 실물이고, Service는 그 앞의 고정 주소다.

Deployment/epp-llama-70b 2/2 ├─ pod epp-llama-70b-6bc8879976-2vr6s IP: changes on every restart └─ pod epp-llama-70b-6bc8879976-btw6z IP: changes on every restart Service/epp-llama-70b ClusterIP 10.43.x.x ← does not change └─ load-balances to the two pods above

The Deployment keeps two pods alive, and each replacement gets a different IP. On the cluster I read, the two picker pods had already restarted three and two times. Anything hardcoding a pod IP would have broken silently each time. Deployment는 pod 두 개를 살려 두고, 죽으면 새로 만든다. 새 pod는 IP가 다르다. 내가 읽은 클러스터에서 picker pod 두 개는 이미 각각 세 번, 두 번 재시작한 상태였다. pod IP를 박아 뒀다면 그때마다 라우팅이 조용히 깨졌을 것이다.

That is why InferencePool.endpointPickerRef points at a Service. No configuration names a pod. 그래서 InferencePool.endpointPickerRef는 Service를 가리킨다. 설정 어디에도 pod를 직접 지목하지 않는다.

That Service carries three ports, all backed by the same two pods: 이 Service는 포트 세 개를 갖고, 모두 같은 pod 두 개로 연결된다.

PortDirection방향Used by사용처

5557vLLM → EPP --kv-events-config — prefix cache stateprefix cache 상태
9090— metrics, most likely (not verified)메트릭으로 보이나 확인하지 않았다

The first two are the two arrows into the picker in the section 3 diagram: same Service, same pods, opposite directions. 앞의 둘이 3절 그림에서 picker로 들어가던 두 화살표다. 같은 Service, 같은 pod에 방향만 반대다.

5 The reverse path: how the picker knows anything 역방향 경로: picker는 어떻게 아는가

So far the request has only travelled down. But the picker must choose the better of two identical replicas. On what basis? 지금까지는 요청이 내려가는 이야기였다. 그런데 picker는 같은 모델의 replica 두 개 중 나은 쪽을 골라야 한다. 무엇을 근거로 고를까?

Queue depth and KV-cache utilization come from engine metrics. What matters most for latency is prefix cache locality: if only replica A holds the KV blocks for this prefix, sending it to A skips most of the prefill. That is a question about specific blocks on a specific pod, not an averageable metric. 큐 길이와 KV 캐시 사용률은 엔진 메트릭에서 얻는다. 지연에 가장 중요한 것은 prefix cache locality다. 이 prefix의 KV 블록을 replica A만 들고 있다면 A로 보내야 prefill 대부분을 건너뛴다. 평균 낼 수 있는 메트릭이 아니라 특정 pod에 특정 블록이 있는지의 문제다.

So vLLM publishes it. Each engine starts with a flag pointing back at the picker: 그래서 vLLM이 이 정보를 발행한다. 각 엔진은 picker를 가리키는 플래그를 달고 뜬다. 

--kv-events-config '{
  "enable_kv_cache_events": true,
  "publisher": "zmq",
  "endpoint": "tcp://epp-llama-70b:5557",
  "topic": "kv@<POD_IP>:8000@meta-llama/Llama-3.1-70B-Instruct"
}'

As blocks are cached and evicted, the engine streams events over ZeroMQ to :5557 on the picker's Service. The picker keeps an index of which pod holds which prefix and scores against it. 블록이 캐시되거나 축출될 때마다 엔진은 이벤트를 ZeroMQ로 picker Service의 :5557에 보낸다. picker는 어느 pod가 어느 prefix를 들고 있는지 색인을 유지하고 그걸로 점수를 매긴다.

The shape of it구조의 모양 Requests flow down; routing information flows up. Because the engines close the loop, routing quality depends on a flag on each vLLM process, not on the gateway. 요청은 아래로, 라우팅 정보는 위로 흐른다. 엔진의 보고로 루프가 닫히므로 라우팅 품질은 게이트웨이가 아니라 각 vLLM 프로세스의 플래그 하나에 달려 있다.

On the cluster I looked at, one of the eight models ran without --kv-events-config at all, visible only in the launch arguments, not the architecture diagram. Nothing broke and no alert fired; its picker had silently degraded to near round-robin. 내가 본 클러스터에서는 여덟 모델 중 하나가 --kv-events-config 없이 돌고 있었다. 아키텍처 그림이 아니라 실행 인자를 읽어야 보이는 문제다. 고장도 알럿도 없이, 그 앞의 picker가 라운드로빈에 가깝게 퇴화해 있었다.

Failure mode with no symptom증상 없는 장애 No error anywhere: the request succeeds, and you lose only the reason the stack exists. Check that every engine actually publishes rather than trusting a one-time config. 어디서도 에러가 나지 않고 요청도 성공한다. 잃는 것은 이 스택을 만든 이유 하나다. 한 번 설정했다고 믿지 말고 모든 엔진이 실제로 발행하는지 확인하자.

6 Control path, data path, and where it breaks control path와 data path, 그리고 깨지는 지점

In plain words: control path, data path, sidecar쉽게 말하면: control path · data path · 사이드카
control pathcontrol path
The part that decides where a request goes, then steps aside. Little traffic, big influence. 요청이 어디로 갈지 결정하고 비켜서는 쪽. 트래픽은 적고 영향력은 크다.
data pathdata path
The part the bytes actually flow through, every generated token for an LLM. Anything here is in the latency budget. 실제로 바이트가 흐르는 쪽. LLM에서는 생성 토큰 전부가 지나가므로 곧바로 지연 예산에 들어간다.
sidecar사이드카
An extra container inside the same pod that intercepts its traffic. A pod's container list is fixed at creation, so adding one means recreating the pod: restarting the engine and reloading weights. 애플리케이션과 같은 pod 안에 넣어 트래픽을 가로채는 추가 컨테이너. pod의 컨테이너 목록은 생성 시 고정되므로 붙이려면 pod를 다시 만들어야 한다. 엔진 재시작과 가중치 재적재가 따른다.

Where a component sits decides how much it can slow you down and how hard it is to replace. 컴포넌트의 위치가 지연에 끼치는 영향과 교체 난이도를 정한다.

"The tokens don't pass through" is half true"토큰은 통과하지 않는다"는 절반만 맞다

This stack is usually called control-plane routing: components pick the destination and tokens flow straight from Envoy to the engine. The filter config shows what that hides: 이 스택은 흔히 control-plane 라우팅으로 불린다. 컴포넌트는 목적지만 정하고 토큰은 Envoy에서 엔진으로 직행한다는 뜻이다. 필터 설정을 보면 이 설명이 가리는 부분이 있다.

Request body (the prompt)요청 body (프롬프트) Response (generated tokens)응답 (생성 토큰)
BBR passes through: request_body_mode: FULL_DUPLEX_STREAMED 통과한다: request_body_mode: FULL_DUPLEX_STREAMED no: response_body_mode: NONE, headers SKIP 아니다: response_body_mode: NONE, 헤더도 SKIP
EPP endpoint decision only엔드포인트 결정만 no아니다

The prompt does traverse BBR. What touches neither component is the response stream, where the token volume and TTFT/TPOT sensitivity live. The honest claim: this is not a data-path gateway on the side that matters for latency. 프롬프트는 실제로 BBR을 지나간다. 두 컴포넌트가 모두 건드리지 않는 것은 응답 스트림이고, 토큰 대부분과 TTFT/TPOT 민감도가 여기에 있다. 정확히 말하면 지연에 중요한 쪽에서는 data-path 게이트웨이가 아니다.

This matters once you consider a true data-path gateway, where every token passes through. It needs a sidecar on the serving pod, which means restarting the engine, whereas a control-plane router swaps with a config change. So only a model with a spare replica to carry traffic during the restart can migrate without downtime. 모든 토큰이 지나가는 진짜 data-path 게이트웨이로 바꾸려면 이 구분이 중요해진다. 그런 게이트웨이는 서빙 pod에 사이드카가 필요하고, 사이드카를 붙이려면 엔진을 재시작해야 한다. control-plane 라우터는 설정 변경만으로 바뀐다. 그래서 재시작 동안 트래픽을 받을 여유 replica가 있는 모델만 무중단으로 옮길 수 있다.

The blast radius is not symmetric장애 반경은 대칭이 아니다

Both components fail closed: BBR with failure_mode_allow: false, the picker with failureMode: FailClose. Same policy, very different consequences, because of the cardinality asymmetry from section 3. 두 컴포넌트 모두 fail closed다. BBR은 failure_mode_allow: false, picker는 failureMode: FailClose. 정책은 같지만 3절에서 본 개수 비대칭 때문에 결과는 전혀 다르다.

BBR: 1 pod, globalpod 1개, 전역

If it dies, no request for any model gets its model header. Every model goes down at once. 죽으면 어떤 모델의 요청에도 모델 헤더가 붙지 않는다. 전 모델이 동시에 멈춘다.

EPP: 2 pods per model모델당 pod 2개

Losing one is survivable. Losing both takes out that one model and nothing else. 하나 잃는 건 버틴다. 둘 다 잃어도 그 모델 하나만 죽고 나머지는 멀쩡하다.

The trivial component (parse JSON, set a header) is the fleet's single point of failure, while the one doing the interesting work is redundant. Architecture diagrams make this easy to get backwards: BBR looks like a footnote, the picker like the system. JSON 파싱과 헤더 추가만 하는 사소한 컴포넌트가 fleet 전체의 단일 장애점이고, 핵심 일을 하는 컴포넌트는 넉넉하게 이중화돼 있다. 아키텍처 그림에서는 BBR이 각주처럼, picker가 시스템처럼 보여서 거꾸로 알기 쉽다.

What I'd take from this여기서 가져갈 것 Two problems showed up only in the live objects: an engine publishing no cache events, and a one-replica component gating every model. Neither raises an error, and both are one kubectl get -o yaml away. 캐시 이벤트를 발행하지 않던 엔진, 모든 모델을 좌우하는 replica 1짜리 컴포넌트. 두 문제 모두 설계가 아니라 실제 오브젝트에서만 보였고, 에러 없이 kubectl get -o yaml 한 번이면 드러난다.

7 The YAML, and how to read it off a cluster YAML, 그리고 클러스터에서 직접 읽는 법

Trimmed to the fields that matter (managed fields, timestamps and most of status removed). In order, these five objects are the whole path. managed fields·타임스탬프·status 대부분을 걷어내고 중요한 필드만 남겼다. 순서대로 읽으면 이 다섯 오브젝트가 경로 전체다.

1. Gateway — the declaration선언

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: gw
spec:
  gatewayClassName: istio          # who materializes this
  listeners:
  - name: http
    port: 80
    protocol: HTTP
    allowedRoutes:
      namespaces:
        from: All             # routes may attach from any namespace
status:
  addresses:
  - type: Hostname
    value: gw-istio.<ns>.svc.cluster.local    # ← the authoritative address

2. Service — created by the operator, not by hand사람이 아니라 operator가 만든 것

apiVersion: v1
kind: Service
metadata:
  name: gw-istio
  labels:
    gateway.istio.io/managed: istio.io-gateway-controller
  ownerReferences:                  # ← delete the Gateway and this goes with it
  - kind: Gateway
    name: gw
spec:
  type: ClusterIP                  # ← in-cluster only
  selector:
    gateway.networking.k8s.io/gateway-name: gw
  ports:
  - name: http
    port: 80
    targetPort: http

The ownerReferences block is an operator's fingerprint. Nobody wrote this Service. The gateway controller derived it from the Gateway and recreates it if deleted. ownerReferences 블록이 operator의 지문이다. 이 Service는 사람이 쓰지 않았다. gateway controller가 Gateway에서 만들어 냈고, 지우면 다시 만든다.

3. EnvoyFilter — how BBR gets into the chainBBR이 체인에 들어가는 방법

apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: body-based-router
spec:
  configPatches:
  - applyTo: HTTP_FILTER
    match:
      listener:
        filterChain:
          filter:
            name: envoy.filters.network.http_connection_manager
    patch:
      operation: INSERT_FIRST                # ← ahead of everything else
      value:
        name: envoy.filters.http.ext_proc
        typed_config:
          "@type": type.googleapis.com/envoy.extensions.filters.http.ext_proc.v3.ExternalProcessor
          failure_mode_allow: false          # ← BBR down = every request fails
          grpc_service:
            envoy_grpc:
              cluster_name: outbound|9004||body-based-router.<ns>.svc.cluster.local
          processing_mode:
            request_header_mode: SEND
            request_body_mode: FULL_DUPLEX_STREAMED   # ← the prompt does pass through
            response_header_mode: SKIP
            response_body_mode: NONE                  # ← the response does not

4. HTTPRoute — the rule규칙

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: epp-llama-70b
spec:
  parentRefs:                          # ← attaches to the Gateway
  - kind: Gateway
    name: gw
  rules:
  - matches:
    - headers:
      - name: X-Gateway-Model-Name       # ← the header BBR set
        type: Exact
        value: meta-llama/Llama-3.1-70B-Instruct
      path:
        type: PathPrefix
        value: /
    backendRefs:
    - kind: InferencePool               # ← not a Service
      name: epp-llama-70b
    timeouts:
      request: 0s                        # ← no timeout; generations run long
      backendRequest: 0s

5. InferencePool — the candidates and the picker후보와 picker

apiVersion: inference.networking.k8s.io/v1
kind: InferencePool
metadata:
  name: epp-llama-70b
spec:
  selector:
    matchLabels:
      pool: epp-llama-70b            # ← the label the operator stamped on the engine pods
  targetPorts:
  - number: 8000
  endpointPickerRef:
    kind: Service                   # ← a Service, never a pod
    name: epp-llama-70b
    port:
      number: 9002
    failureMode: FailClose         # ← picker down = this model's requests fail

# what kinds exist at all, and their API groups
kubectl api-resources | grep -iE 'gateway|route|inference'
kubectl get crd | grep -E 'inference'

kubectl explain inferencepool.spec

kubectl -n $NS get httproute epp-llama-70b -o yaml

# one field
kubectl -n $NS get gateway gw -o jsonpath='{.status.addresses}'

kubectl -n $NS get svc gw-istio -o jsonpath='{.metadata.ownerReferences}'

Two gotchas두 가지 함정 -o jsonpath has no conditionals: {if .nodePort} fails with unrecognized identifier if. Use jq or python3 -c for logic.
