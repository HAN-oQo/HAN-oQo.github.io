5bFollow-up — Docker vLLM-ROCm + Argo CD external Service. Does it work?후속: Docker vLLM-ROCm + ArgoCD 외부 Service. 되나?

Date: 2026-06-12 · Node: mi250-052 (AMD MI250) · Status: ✓ YES — it works, end to end · the documented Phase-5 fallback A, executed live작성일: 2026-06-12 · 노드: mi250-052 (AMD MI250) · 상태: ✓ 된다. end to end 작동 · Phase 5에 적어 둔 폴백 A를 실제로 실행

The question질문
Phase 5 showed GPU passthrough into a kind node fails, but plain docker run --device exposes the MI250 fine. So: run vLLM-ROCm in Docker (GPU there), and have Argo CD manage an in-cluster Service that fronts it — is a "GPU model server under GitOps" actually reachable from the cluster? Answer: yes. Below is every step, including two real gotchas. Phase 5에서 GPU passthrough는 kind 노드로는 안 됐지만, 평범한 docker run --device로는 MI250가 잘 보였다. 그렇다면 vLLM-ROCm은 Docker에서 GPU로 띄우고, 그 앞단의 클러스터 내부 Service만 ArgoCD가 관리하면 "GitOps 아래 GPU 모델서버"에 클러스터에서 닿을까? 답은 된다. 아래에 함정 두 개를 포함한 전 과정을 적었다.

[ kind cluster: gitops-lab ] [ host: mi250-052 ] pod ──curl──► Service gpu-vllm ──► nginx proxy pod ──► 172.18.0.1:8001 ──► docker vLLM-ROCm ──► MI250 GCD0 (Argo CD-managed) (Argo CD-managed) (kind gateway=host) (--device /dev/kfd…) (Qwen2.5-1.5B) └──────── declared in Git, reconciled ────────┘ └── docker run, device passthrough ──┘
Fig — the full request path. Left of the gateway is GitOps-managed Kubernetes; right of it is a Docker GPU process.그림 · 전체 요청 경로. 게이트웨이 왼쪽은 GitOps가 관리하는 Kubernetes, 오른쪽은 Docker GPU 프로세스다. 직접 그림.

Step 1 — vLLM-ROCm on the host (the GPU half)1단계: 호스트에서 vLLM-ROCm 띄우기 (GPU 쪽)

docker run -d --name gpu-vllm \
  --device /dev/kfd --device /dev/dri --group-add video --group-add render \
  --ipc=host --security-opt seccomp=unconfined \
  -e HIP_VISIBLE_DEVICES=0 -e VLLM_ROCM_USE_AITER=0 \
  -v ~/.cache/huggingface:/root/.cache/huggingface -p 8001:8000 \
  rocm/vllm:latest \
  vllm serve Qwen/Qwen2.5-1.5B-Instruct --port 8000 --max-model-len 4096 \
       --gpu-memory-utilization 0.5 --enforce-eager

The rocm/vllm:latest image (30.7 GB) and the Qwen2.5-1.5B weights were already cached on the node, so no big pull. One GCD via HIP_VISIBLE_DEVICES=0. rocm/vllm:latest 이미지(30.7GB)와 Qwen2.5-1.5B 가중치가 노드에 이미 캐시돼 있어 큰 pull은 없었다. HIP_VISIBLE_DEVICES=0로 GCD 1개만 쓴다.

Gotcha 1 — the engine crashed on AMD's aiter kernels함정 1: AMD aiter 커널에서 엔진 크래시
First run: the model loaded onto the GPU fine (3.04 GiB, ROCm attention backend), then the EngineCore died right after importing aiter/module_rmsnorm.so → RuntimeError: Engine core initialization failed. AMD's aiter JIT kernels didn't play nice on this gfx90a. Fix: VLLM_ROCM_USE_AITER=0 → the KV-cache profiling then succeeded (GPU KV cache 1,017,488 tokens, 248× concurrency) and the API server came up. 첫 실행에서 모델은 GPU에 잘 올라갔다(3.04 GiB, ROCm attention backend). 그런데 aiter/module_rmsnorm.so를 import한 직후 EngineCore가 죽었다 → RuntimeError: Engine core initialization failed. AMD aiter JIT 커널이 이 gfx90a에서 말썽이었다. VLLM_ROCM_USE_AITER=0로 끄자 KV-cache profiling이 성공했고(GPU KV cache 1,017,488 tokens, 248× 동시성) API 서버도 떴다.
# host check — vLLM serving on the MI250:
$ curl localhost:8001/v1/models            → ["Qwen/Qwen2.5-1.5B-Instruct"]
$ curl localhost:8001/v1/chat/completions  → "MI250 online ..."   # real GPU completion

Step 2 — bridge the host into the cluster (the GitOps half)2단계: 호스트를 클러스터에 연결 (GitOps 쪽)

A pod reaches the host via the kind Docker network's gateway — docker network inspect kind → 172.18.0.1. The first instinct is a no-selector Service + a manual Endpoints pointing at 172.18.0.1:8001. It routes correctly... but: 파드는 kind Docker 네트워크의 게이트웨이(docker network inspect kind → 172.18.0.1)로 호스트에 닿는다. 처음에는 selector 없는 Service에 172.18.0.1:8001을 가리키는 수동 Endpoints를 붙였다. 라우팅은 맞았지만 문제가 있었다.

Gotcha 2 — Argo CD ignores Endpoints by default함정 2: ArgoCD는 기본으로 Endpoints를 무시한다
The Application went Synced/Healthy but managed only the Service — the Endpoints object was never applied. Cause: Argo CD v3's default resource.exclusions includes Endpoints / EndpointSlice (they're high-churn, k8s-managed). Applied by hand it works, but it isn't GitOps-managed and won't self-heal. Two ways out: (a) un-exclude Endpoints in argocd-cm, or (b) front the host with a tiny proxy Deployment — normal resources Argo CD does manage. Took (b). Application은 Synced/Healthy였지만 Service만 관리했고 Endpoints는 적용되지 않았다. ArgoCD v3의 기본 resource.exclusions에 Endpoints / EndpointSlice가 들어 있기 때문이다(자주 바뀌고 k8s가 관리하는 객체). 손으로 적용하면 동작하지만 GitOps 관리 대상이 아니라 self-heal도 안 된다. 방법은 두 가지다. (a) argocd-cm에서 Endpoints 제외를 푼다. (b) 작은 프록시 Deployment를 호스트 앞에 둔다. 이건 ArgoCD가 관리하는 일반 리소스다. 여기서는 (b)를 골랐다.

So the GitOps-managed unit is a 3-object slice — all normal, non-excluded resources: 그래서 GitOps 관리 단위는 객체 3개이고, 모두 제외 대상이 아닌 일반 리소스다.

# manifests/phase5-gpu-external/  (Argo CD app: phase5-gpu-external)
ConfigMap  gpu-vllm-proxy-conf   # nginx.conf:  proxy_pass http://172.18.0.1:8001;  (buffering off → stream)
Deployment gpu-vllm-proxy        # nginx:1.27-alpine shim → the host GPU server
Service    gpu-vllm              # selector app=gpu-vllm-proxy, port 8000

Step 3 — call the GPU from inside the cluster3단계: 클러스터 안에서 GPU 호출

$ kubectl -n argocd get application phase5-gpu-external -o ...
ConfigMap/gpu-vllm-proxy-conf  Synced
Service/gpu-vllm               Synced
Deployment/gpu-vllm-proxy      Synced       # app = Synced/Healthy, proxy 1/1 ready

# from a throwaway pod in the cluster:
$ curl http://gpu-vllm.serving.svc.cluster.local:8000/v1/models
{"data":[{"id":"Qwen/Qwen2.5-1.5B-Instruct","owned_by":"vllm","max_model_len":4096}]}

$ curl .../v1/chat/completions -d '{"model":"Qwen/Qwen2.5-1.5B-Instruct",
    "messages":[{"role":"user","content":"Reply with exactly: served by MI250 via ArgoCD"}]}'
{"choices":[{"message":{"content":"Served by MI250 through ArgoCD"}}],
 "model":"Qwen/Qwen2.5-1.5B-Instruct","usage":{"completion_tokens":12,"total_tokens":55}}

That reply was generated by the MI250, reached from a pod inside the kind cluster, through the Argo CD-managed Service → nginx proxy → host Docker vLLM-ROCm. The whole left side is reconstructable from Git.이 응답은 MI250가 만들었고, kind 클러스터 내부 파드에서 ArgoCD 관리 Service → nginx 프록시 → 호스트 Docker vLLM-ROCm을 거쳐 왔다. 왼쪽 전체는 Git에서 다시 만들 수 있다.

Verdict결론

Bench hygiene벤치 위생
After the demo the gpu-vllm Docker container was stopped to free GCD 0 on the shared node (docker start gpu-vllm to resume). The Argo CD-managed proxy/Service/ConfigMap stay in Git — cheap, CPU-only, and they reconnect the moment the GPU server is back. 데모 후 공유 노드의 GCD 0을 돌려주려고 gpu-vllm 컨테이너를 멈췄다(docker start gpu-vllm으로 재개). ArgoCD가 관리하는 프록시/Service/ConfigMap은 Git에 그대로 둔다. CPU만 쓰는 가벼운 객체라 GPU 서버가 돌아오면 바로 다시 연결된다.
