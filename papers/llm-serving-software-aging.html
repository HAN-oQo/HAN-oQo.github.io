one-line summary한 줄 요약 Six serving setups, 36 hours each. All six slowly leak memory inside the serving process, invisibly to latency/throughput and not because of the model or GPU. Packaging changes the leak rate by ~100× (best: vLLM V1 standalone, worst: Triton wrapping the old V0 engine). 서빙 구성 6개를 36시간씩 돌렸다. 여섯 개 모두 서빙 프로세스 안에서 메모리가 조금씩 샌다. 레이턴시와 스루풋에는 드러나지 않고, 모델이나 GPU 탓도 아니다. 엔진을 어떻게 포장하느냐에 따라 누수 속도가 약 100배 갈린다(최선은 vLLM V1 단독, 최악은 구형 V0를 Triton으로 감싼 조합).

📖 Software aging?📖 소프트웨어 에이징?

A long-running program slowly getting worse. A restart resets it, hence the classic cure "rejuvenation" (planned restarts).오래 켜 둔 프로그램이 서서히 나빠지는 현상이다. 재시작하면 풀리므로 고전적 처방을 "회춘(rejuvenation)", 즉 계획된 재시작이라 부른다.

📖 USS · RSS · VMS

USS: pages only this process uses (the most honest leak signal). RSS: all of it in RAM, shared libs included. VMS: address space merely reserved.USS는 이 프로세스만 쓰는 메모리로, 누수를 가장 정직하게 보여 준다. RSS는 공유 라이브러리까지 포함한 RAM 점유, VMS는 예약만 해 둔 주소 공간이다.

📖 Open-loop Poisson load📖 Open-loop Poisson 부하

Requests fire at random intervals whether or not the server keeps up, like real users.서버가 따라오든 말든 무작위 간격으로 요청을 보내는 방식이다. 실제 사용자 트래픽과 닮았다.

📖 vLLM V0 / V1

Two generations of vLLM's engine with the same algorithm and API. V0 is synchronous; V1 is the async redesign (today's default).알고리즘과 API가 같은 vLLM 엔진 두 세대다. V0는 동기식, V1은 비동기로 다시 짠 현재 기본값이다.

📖 "Triton-wrapped"📖 "Triton 래핑"

NVIDIA Triton runs vLLM as a child process and adds a request queue, dynamic batcher and OpenAI-compatible API.NVIDIA Triton이 vLLM을 자식 프로세스로 띄우고 요청 큐, dynamic batcher, OpenAI 호환 API를 얹은 구성이다.

📖 How big is "+157 KB/h"?📖 "+157 KB/h"는 얼마나 큰가?

About 110 MB per month, the worst case found. Not an outage tomorrow; what matters is that it is invisible and varies ~100×.발견된 최악의 경우로 한 달에 약 110 MB다. 당장 장애가 날 양은 아니고, 보이지 않는다는 점과 배포마다 100배 차이 난다는 점이 중요하다.

🗺️ Before we start: what leaks, and why would it hurt? 시작 전에: 무엇이 새고, 왜 문제인가

"Memory leak in LLM serving" sounds like a GPU problem, but it isn't. vllm serve starts a Python process on the Linux host. Weights and KV-cache live in GPU VRAM, while the process driving the GPU lives in ordinary host RAM.

"LLM 서빙의 메모리 누수"는 GPU 문제처럼 들리지만 그렇지 않다. vllm serve를 실행하면 리눅스 호스트에 Python 프로세스 하나가 뜬다. 가중치와 KV-cache는 GPU VRAM에 있고, GPU를 부리는 프로세스는 호스트의 일반 RAM에 있다.

Figure 1 · Where the leak lives (USS = blue box). Drawn by us from §IV-C·E.그림 1 · 누수가 사는 곳(USS = 파란 상자). §IV-C·E 근거, 직접 그림.

Which part of the blue box leaks? 파란 상자의 어느 부분이 새나?

All three deployments run the same model and the same inference math, yet their leak rates differ ~100×. So the leak lives in the wrapping:

세 배포는 같은 모델과 같은 추론 연산을 돌리는데 누수 속도는 ~100배 차이 난다. 그러니 누수는 포장 쪽에 있다.

  • Scheduler and request-lifecycle code (why old V0 leaks 7–27× more than V1).
  • The queue/batcher/frontend layers Triton adds (why wrapping amplifies both engines).
  • The CUDA runtime's host-side bookkeeping (why the PyTorch runs kept reserving address space).
  • 스케줄러와 요청 수명주기 코드. 구형 V0가 V1보다 7~27배 더 새는 이유다.
  • Triton이 얹는 큐·배처·프론트엔드 계층. 래핑이 두 엔진을 모두 증폭하는 이유다.
  • CUDA 런타임의 호스트 쪽 장부. PyTorch 런이 주소 공간을 계속 예약한 이유다.

The exact data structure is unknown; that needs heap profiling, left as future work.

정확히 어느 자료구조인지는 힙 프로파일링이 필요해 후속 과제로 남았다.

analogy비유 The kitchen (GPU) cooks at full speed, but the front counter (host process) keeps a receipt now and then and never throws it away. Service speed doesn't change until the counter is buried. 주방(GPU)은 풀스피드로 요리하는데, 카운터(호스트 프로세스)에는 영수증이 가끔 한 장씩 쌓이고 아무도 버리지 않는다. 카운터가 파묻히는 날까지 응대 속도는 그대로다.

How does host RAM ever hurt inference performance? 호스트 RAM이 어떻게 추론 성능을 해치나

Within the 36-hour runs it didn't: latency and throughput stayed flat (§IV-B). That is the danger. Such a leak ends in a cliff:

36시간 실험에서는 해치지 않았다. 레이턴시와 스루풋이 끝까지 평탄했다(§IV-B). 바로 그 점이 위험하다. 이런 누수는 서서히 나빠지지 않고 절벽으로 끝난다.

① RAM fills up → swapping① RAM이 차면 스왑

The OS pages the Python orchestrator to disk; batching slows and tail latency explodes.OS가 Python 오케스트레이터를 디스크로 내리면서 배칭이 늦어지고 tail latency가 치솟는다.

② Or: OOM kill → outage② 또는 OOM kill로 장애

Restart means minutes of model reloading, and every KV-cache on the GPU is lost.재시작하면 모델을 수 분간 다시 올려야 하고 GPU의 KV-cache가 모두 사라진다.

③ In k8s: OOMKilled loop③ k8s라면 OOMKilled 반복

The process hits its memory limit, restarts, leaks again: cold starts on a schedule you didn't choose.메모리 리밋에 닿아 재시작하고 다시 새기를 반복한다. 원치 않는 주기로 콜드 스타트가 생긴다.

the shape of the risk위험의 모양 Fine → fine → fine → bang, with nothing on the dashboard until just before the bang. Hence the paper's advice to monitor process memory itself. On magnitude: the worst rate (≈ 110 MB/month) leaves months of headroom; the genuinely scary pattern is E2's staircase (§3.5), whose jumps are unpredictable. 멀쩡 → 멀쩡 → 멀쩡 → 쾅이고, 대시보드에는 쾅 직전까지 아무것도 안 보인다. 그래서 프로세스 메모리를 직접 봐야 한다. 최악(≈ 월 110 MB)이라도 몇 달은 버티고, 진짜 위험은 언제 뛸지 모르는 E2의 계단 패턴(§3.5)이다.

1 Problem definition 문제 정의

1.1 We benchmark for minutes, then run for months 1.1 벤치마크는 몇 분, 운영은 몇 달

vLLM and Triton stay up for weeks or months, yet almost every number about them (peak throughput, p99 latency) comes from minute-long benchmarks. Nobody asked: what happens after hour 30?

vLLM과 Triton은 몇 주에서 몇 달씩 떠 있지만, 피크 스루풋이나 p99 레이턴시 같은 수치는 거의 다 몇 분짜리 벤치마크에서 나온다. 30시간째의 상태를 물어본 사람은 없었다.

"Yet the literature on these engines focuses almost entirely on peak metrics measured in minutes. What happens to them over longer windows is mostly unknown."

— §I, ¶1 · 원문 보기 (arXiv HTML §I)

A field for exactly this question exists. "Software aging and rejuvenation" (SAR) has studied rotting long-running software for ~30 years (databases, hypervisors, OSes, blockchains), but never LLM serving:

이 질문을 다루는 분야는 이미 있다. "소프트웨어 에이징·회춘(SAR)"은 약 30년간 DB, 하이퍼바이저, OS, 블록체인의 노화를 측정해 왔지만 LLM 서빙은 다루지 않았다.

"The SAR community has not yet engaged with LLM serving on the GPU."

— §I, ¶2 · 원문 보기 (§I)

LLM 서빙이 기존 연구의 가정을 모두 깨기 때문이다.

1.3 The three contestants (§II-A) 1.3 세 선수 (§II-A)

A serving engine loads the model once and generates token by token. Each in-flight request carries a KV-cache, hundreds of MB of GPU memory that grows while the request lives (§II-A ¶1). Modern engines manage it with continuous batching (requests share each forward pass) and paged attention (KV-cache in small fixed blocks); vLLM is the reference implementation.

서빙 엔진은 모델을 한 번 올리고 토큰을 하나씩 생성한다. 요청마다 KV-cache가 붙는데, 요청이 살아 있는 동안 자라는 수백 MB짜리 GPU 메모리다(§II-A ¶1). 현대 엔진은 이를 continuous batching(여러 요청이 forward pass를 공유)과 paged attention(KV-cache를 작은 고정 블록으로 관리)으로 다루고, 그 대표 구현이 vLLM이다.

The paper packages the same model three ways:

논문은 같은 모델을 세 가지로 포장한다.

🏎️ vLLM standalone

The bare engine with its own minimal HTTP server, on the new V1 engine.자체 미니멀 HTTP 서버만 붙인 엔진 그대로다. 신형 V1으로 돈다.

🏭 Triton + vLLM

"Enterprise packaging" with queue/batcher/OpenAI API; NVIDIA's patched build runs the old V0 engine.큐·배처·OpenAI API를 얹은 "엔터프라이즈 포장"이다. 내장된 NVIDIA 패치판은 구형 V0다.

🧪 Naive PyTorch + HF

transformers + FastAPI, one request at a time, with no batching or paged attention.transformers + FastAPI로 요청을 하나씩 처리한다. 배칭도 paged attention도 없다.

V0 and V1 share algorithm and API but differ in scheduling and in how per-request resources are acquired and released. Does that matter for reliability?

V0와 V1은 알고리즘과 API가 같지만 스케줄링 방식과 요청별 자원을 잡고 놓는 방식이 다르다. 이 차이가 신뢰성에 영향을 줄까?

"Whether this choice has reliability consequences over long-running operation is, to our knowledge, an open question."

— §II-A, ¶3 · 원문 보기 (§II-A)

2 Method 해결 방법

The design follows four stated goals: realistic configurations, enough monitoring to locate aging, statistics robust to this data, and reproducibility.

설계는 네 가지 목표를 따른다. 현실적인 구성, 에이징 위치를 짚어낼 만큼의 모니터링, 이 데이터에 맞는 통계, 재현 가능성이다.

"the campaign must compare practical deployment configurations under a controlled but realistic workload; monitor enough of the system to localize aging if present; use a statistical pipeline robust to the autocorrelation of monitoring traces; and remain reproducible end to end."

— §III, ¶1 · 원문 보기 (§III)

2.2 The traffic: hard but fair 2.2 트래픽: 혹독하되 공정하게

  • One open-loop Poisson client per engine.
  • Prompts from 3000 arXiv abstracts, 256–7500 tokens (median 1500); outputs up to 1500 tokens (median 200); 70% streamed.
  • Calibration: raise the rate until throughput stops growing (the engine's "ceiling"), then run 36 hours at 85% of each engine's ceiling, so every engine works equally hard relative to its own ability.
  • 엔진마다 open-loop Poisson 클라이언트가 하나씩 붙는다.
  • 프롬프트는 arXiv 초록 3000개로 만든 256~7500토큰(중앙값 1500), 출력은 최대 1500토큰(중앙값 200), 요청의 70%는 스트리밍이다.
  • 캘리브레이션: 처리량이 더 늘지 않을 때까지 요청률을 올려 엔진의 "천장"을 찾고, 36시간 본 실험은 각자 천장의 85%로 돌린다. 모든 엔진이 자기 능력 대비 똑같이 힘들게 일한다.

"We use the ceiling rather than the highest rate at which the client does not yet drop, because the ceiling is a property of the engine itself, while the no-drop rate is partly an artefact of the client-side concurrency cap."

— §III, "Workload and stress regime" · 원문 보기 (§III)

2.4 The statistics: why so much machinery for "is the line going up?" 2.4 통계: 우상향 하나 보는 데 왜 이렇게 거창한가

Memory at 12:00:05 is nearly identical to memory at 12:00:00, so samples are not independent (ρ ≈ 0.99). Naive statistics counts each as fresh evidence and becomes overconfident:

12:00:05의 메모리 값은 12:00:00과 거의 같아서 샘플이 독립이 아니다(ρ ≈ 0.99). 순진한 통계는 샘플마다 새 증거로 세므로 결과를 과신하게 된다.

"the resident memory of a process at time t is almost identical to its value at t−1, and naive tests that treat samples as independent produce drastically deflated p-values."

— §III, "Statistical Analysis" · 원문 보기 (§III)

So every candidate trend passes three filters:

그래서 모든 추세 후보는 세 겹의 필터를 거친다.

Figure 3 · The decision funnel. Drawn by us from §III, "Statistical Analysis".그림 3 · 판정 깔때기. §III "Statistical Analysis" 근거, 직접 그림.

Two more safeguards: the indicator list was frozen before seeing long-run data (no cherry-picking), and monotonic counters like "total I/O bytes" were converted to per-second rates so they don't count as "aging" by construction.

안전장치가 두 개 더 있다. 지표 목록은 장기 데이터를 보기 전에 고정해 골라 쓰기를 막았다. "누적 I/O 바이트"처럼 늘기만 하는 카운터는 초당 비율로 바꿔 구조적으로 에이징이 잡히는 일을 막았다.

3.3 Inside the process: everyone leaks, and the ranking is upside-down (§IV-C) 3.3 프로세스 안: 전부 새고, 순위는 뒤집혀 있다 (§IV-C)

On USS, every primary deployment shows a real, steady leak after all three filters. Intuition says the hand-rolled FastAPI server should leak most. It doesn't:

USS를 보면 세 필터를 모두 통과한 진짜 누수가 본 비교 세 배포 모두에서 나온다. 직관으로는 손으로 짠 FastAPI 서버가 가장 많이 샐 것 같지만 그렇지 않다.

"The naive PyTorch baseline, the textbook example of what production teams avoid, is not the cleanest: it sits in the middle at +31 KB/h. The cleanest is vLLM standalone (E1) at +1.8 KB/h, an engine built specifically to optimize serving. The heaviest is Triton-wrapped vLLM (E2) at +157 KB/h."

— §IV-C, ¶2 ("the order is the surprise of the campaign") · 원문 보기 (§IV-C)

This ranking is the clue behind "the leak lives in the wrapping" (see the start of this note):

이 순위가 앞에서 본 "누수는 포장에 있다"는 결론의 근거다.

"If the leak originated from the inference path, we would expect similar leak rates across all deployments. Instead, the observed rates differ by nearly two orders of magnitude. This strongly suggests that the source of the leak lies in the serving infrastructure rather than in the model execution itself."

— §IV-C, ¶3 · 원문 보기 (§IV-C)

CPU, threads, file descriptors, context switches and I/O are flat. So is GPU VRAM in every deployment, which surprised the authors (they expected allocator fragmentation). At this timescale, aging is a host-side memory story.

CPU, 스레드, 파일 디스크립터, 컨텍스트 스위치, I/O는 평평하다. GPU VRAM도 모든 배포에서 평평했는데, 할당기 단편화를 예상한 저자들에게는 의외였다. 이 시간 척도에서 에이징은 호스트 쪽 메모리 문제다.

3.4 Plot twist: lower the load, the leak gets worse (§IV-D) 3.4 반전: 부하를 낮췄더니 누수가 더 심해진다 (§IV-D)

Is the naive server leaking only because it runs at 100% capacity? Rerun at 0.05 RPS with no drops, the leak triples: +31 → +103 KB/h. It tracks wall-clock time, not request count:

순정 서버는 용량 100%로 허덕여서 새는 걸까? 0.05 RPS, 드롭 0%로 다시 돌리자 누수가 3배가 됐다(+31 → +103 KB/h). 누수는 요청 수가 아니라 흐른 시간을 따라간다.

"This result indicates that the leak is not caused by queueing effects or saturation-related behavior. Instead, it appears to be intrinsic to the runtime environment. The higher leak rate at lower load also suggests that memory growth is driven primarily by elapsed time rather than by the number of processed requests."

— §IV-D · 원문 보기 (§IV-D)

In the PyTorch runs, reserved address space (VMS) grows ~127 MB/h (≈7.5 GB per run) while used memory grows only ~20 MB in total, with thread/FD counts flat. That is not a classic object leak: something (consistent with the CUDA caching allocator's host-side bookkeeping) keeps reserving address space it never returns. Whether it becomes real memory pressure is open.

PyTorch 런에서는 예약 주소 공간(VMS)이 시간당 ~127 MB(런 전체 ≈7.5 GB)씩 커지는데, 실제 사용 메모리는 총 ~20 MB만 늘었다. 객체 누수라기보다 CUDA 캐싱 할당기의 호스트 쪽 관리처럼 주소 공간을 예약하고 반납하지 않는 현상이다. 실제 메모리 압박으로 이어질지는 미해결이다.

E1 and E2 differ twice (V1 vs V0, bare vs Triton). Two ablation runs fill the missing corners of an engine generation × packaging grid:

E1과 E2는 두 가지가 다르다(V1 vs V0, 단독 vs Triton). ablation 런 두 개가 빈칸을 채워 엔진 세대 × 포장 2×2 그리드를 완성한다.

V0 leaks more than V1 in both rows (≈7× bare, ≈27× under Triton), Triton amplifies both engines, and Triton×V0 explodes. Nuance: E1 climbs for a few hours then settles while A1 keeps creeping, so E1's cumulative growth isn't the smallest even though its steady-state rate is (§IV-E ¶3).

V0는 두 행 모두에서 V1보다 많이 새고(단독 ≈7배, Triton 아래 ≈27배), Triton은 두 엔진 모두를 키우며, Triton×V0 조합에서 폭발한다. 단, E1은 처음 몇 시간 오르다 안정되고 A1은 계속 오른다. 그래서 E1의 정상 상태 누수율은 최저지만 누적 증가량은 최소가 아니다(§IV-E ¶3).

The staircase is the scariest part. E2 sits still, then jumps several MB at once and never gives it back (top 1% of jumps ≈ 1.8 MB; RSS and VMS jump together at ρ ≈ 0.83, vs < 0.35 elsewhere):

가장 섬뜩한 것은 계단이다. E2는 가만히 있다가 한 번에 수 MB씩 뛰고 그 메모리를 반납하지 않는다(점프 상위 1%가 ≈1.8 MB, RSS와 VMS가 ρ≈0.83으로 같이 뛰며 다른 구성은 <0.35).

"Its memory footprint remains stable for extended periods and then increases through discrete jumps of several megabytes. […] One plausible explanation is that the engine periodically maps new memory regions from the operating system and retains them over time. […] this behavior is the strongest clue emerging from the experimental campaign and the most plausible candidate for unbounded growth over multi-day timescales."

— §IV-E, ¶4–5 (확정하려면 힙 프로파일링이 필요 — 이 논문 범위 밖) · 원문 보기 (§IV-E)

GPU side: "Once the model is loaded, VRAM occupancy remains essentially stable" (§IV-E ¶6). Caveat: the four cells use three vLLM versions (0.7.3 / 0.10.1.1 / 0.21.0) because newer releases dropped the V0 switch, so "V0 vs V1" is partly tangled with version. The gaps are too big to be only that, but clean attribution is open (§IV-E ¶7).

GPU 쪽은 "모델이 올라가면 VRAM 점유가 사실상 안정적"이다(§IV-E ¶6). 단서가 하나 있다. 최신 릴리스에서 V0 스위치가 사라져 그리드 4칸이 vLLM 버전 3개(0.7.3 / 0.10.1.1 / 0.21.0)로 돌았고, "V0 vs V1"에 버전 차이가 일부 섞여 있다. 차이가 커서 버전 탓만은 아니겠지만 깔끔한 귀속은 미해결이다(§IV-E ¶7).

4 Takeaways 시사점

4.1 The paper's three findings (§VI) 4.1 논문의 세 가지 결론 (§VI)

  • GPU LLM serving ages. "Every deployment exhibits a small but statistically significant process-private memory leak over a 36-hour window."
  • The model isn't the leaker — the packaging is. "Deployments running the same model and serving the same workload can differ by nearly two orders of magnitude in leak rate."
  • Leaks have different personalities. Most drift smoothly; "Triton+V0 shows a distinctive step-wise pattern in RSS and VMS, suggesting a different underlying mechanism."
  • GPU LLM 서빙도 늙는다. 모든 배포가 36시간 동안 작지만 통계적으로 유의한 프로세스 전용 메모리 누수를 보였다.
  • 새는 것은 모델이 아니라 포장이다. 같은 모델과 워크로드라도 배포에 따라 누수율이 거의 100배 갈린다.
  • 누수에도 성격이 있다. 대부분은 매끄럽게 늘지만 Triton+V0만 RSS·VMS가 계단식으로 뛰어, 다른 메커니즘을 시사한다.

4.2 For operators: your dashboard is blind to this 4.2 운영자에게: 대시보드는 이것을 못 본다

None of this showed up in latency, throughput, or error rate. Alerting built only on those misses this whole class of degradation:

이 중 어느 것도 레이턴시, 스루풋, 에러율에 나타나지 않았다. 알림이 이 셋에만 의존하면 이런 열화는 터지기 전까지 보이지 않는다.

"Notably, none of these effects is visible through client-side metrics over the timescale of our experiments. For practitioners, the results highlight that monitoring LLM serving systems cannot rely solely on latency, throughput, or error rates. Memory-related aging may remain invisible to users while steadily accumulating inside the serving stack. More generally, deployment choices have reliability implications that are not captured by short-term performance benchmarks."

— §VI · 원문 보기 (§VI)

4.3 What the authors want to do next (§VI) 4.3 저자들의 후속 과제 (§VI)

  • Repeat runs (quantify run-to-run noise); other GPUs and bigger models.
  • Longer windows, for effects that need more than 36 h to show.
  • Heap-profile the V0 engine to find where the staircase jumps come from.
  • Check whether specific request patterns can trigger or accelerate the leaks.
  • 반복 실험으로 런 간 노이즈를 정량화하고, 다른 GPU와 더 큰 모델로 넓힌다.
  • 36시간으로는 안 보이는 효과를 잡도록 관측 기간을 늘린다.
  • V0 엔진을 힙 프로파일링해 계단식 점프의 출처를 찾는다.
  • 특정 요청 패턴이 누수를 촉발하거나 가속하는지 확인한다.

4.4 Our read (not the paper's claims) 4.4 우리 관점 (논문의 주장 아님)

editor's note: implications for our serving work편집자 주: 우리 서빙 작업에 주는 함의
  1. Add per-process USS (one psutil call) to long-running vLLM benchmarks and PD-disaggregation experiments; client-side metrics miss this category entirely.
  2. Any layer wrapped around vLLM (Triton, gateways, sidecars) is part of the aging surface. Measure it.
  3. KB/h magnitudes are harmless monthly; alert on the E2-style staircase (RSS+VMS jumping together), the one candidate for unbounded growth.
  4. P/D disaggregation multiplies independently aging runtimes, so "the deployment is the aging surface" bites hardest there.
  1. 장기 vLLM 벤치마크와 PD 분리 실험에 프로세스별 USS(psutil 한 줄)를 추가한다. 클라이언트 지표는 이 범주를 통째로 놓친다.
  2. vLLM을 감싸는 계층(Triton, 게이트웨이, 사이드카)은 모두 에이징 표면이 된다. 믿지 말고 측정한다.
  3. KB/h 규모는 월 단위로 무해하다. 알림을 걸 대상은 무한 증가의 유일한 후보인 E2식 계단 패턴(RSS+VMS 동반 점프)이다.
  4. P/D 분리는 따로 늙는 런타임 수를 늘리므로, "배포 전체가 에이징 표면"이라는 결론이 가장 크게 적용된다.
