Heimdall vs NVIDIA Dynamo

요청이 들어온 순간부터 토큰이 돌아갈 때까지 — token-in → token-out 흐름 비교

1. 각각의 코드 흐름

Heimdall은 로컬 저장소의 실제 Rust 코드(crates/gateway/src)를 함수 단위로 추적했고, Dynamo는 NVIDIA 공식 아키텍처 문서의 단계(S1–S13)를 따랐습니다.

Heimdall (MoAI AI Gateway)

gateway-orchestrated · 전부 Rust 게이트웨이 내부

  1. HTTP 라우팅
    http/router.rs — /v1/chat/completions → chat_completions_handler (chat·messages·responses 모두 등록)
  2. Unified 변환
    http/chat.rs — OpenAI 요청을 CreateUnifiedChatRequest로. 3개 API가 한 타입으로 합류
  3. 엔드포인트 + 토크나이저 확보
    unified_chat.rs — endpoint_store.list()를 model+healthy로 필터, codec_registry.get(model)
  4. 토크나이즈 TOKEN IN
    codec/encode.rs : encode() — renderer.template()(chat template) + renderer.tokenize() → token_ids
  5. 스케줄링 컨텍스트
    SchedulingContext{ token_ids, kv_index } — prompt 블록 해시로 prefix-cache 점수 산정 준비
  6. 라우팅 결정 분기점
    e2e: pipeline.run() (Filter→Scorer→Picker, scheduler/pipeline.rs) → 워커 1개
    pd: PdCoordinator.decide() (pd/coordinator.rs) — decode·prefill 둘 다 발송 전에 선택
  7. 엔진으로 TITO 발송
    pd/generate.rs : generate_stream() → POST /inference/v1/generate (token_ids in/out, detokenize=false). PD면 sequential.rs가 prefill 먼저 → decode 순차 2회
  8. 디토크나이즈 + 파싱 TOKEN OUT
    codec/decode.rs : decode() — incremental detokenize + tool/reasoning 파싱(streaming jail)
  9. SSE 응답
    http/chat.rs — unified 프레임을 chat.completion.chunk SSE로 직렬화 → 클라이언트

NVIDIA Dynamo

worker-orchestrated · Rust 프런트 + Python 워커

  1. Frontend 수신
    Frontend (Rust, OpenAI 호환 :8000) 가 HTTP 요청 수신 (S2)
  2. Processor 검증·라우팅
    Processor = Request Handler & Router. 요청 validate 후 decode 워커로 route (S3)
  3. 토크나이즈 TOKEN IN
    Rust 프런트(Frontend+Processor)가 토크나이즈 → input_ids를 백엔드로 전달
  4. Router KV-aware 선택
    캐시 오버랩 + 부하 신호로 최적 decode 워커 결정 (KV-aware routing)
  5. Decode 워커 disagg 판단 분기점
    prefix-cache hit 조회(S4) → disagg 결정(S5) → 로컬 GPU에 KV 블록 미리 할당(S5a). 워커가 조율 주체
  6. 큐로 remote prefill 분배
    RemotePrefillRequest를 NATS PrefillQueue에 push(S6) → Prefill 워커가 consumer group으로 pull(S7)
  7. Prefill + NIXL 전송
    ETCD에서 NIXL 메타데이터 로드(S8) → prefill 계산(S9) → NIXL이 decode의 선할당 블록에 KV 직접 write(S10) → notify(S11)
  8. Decode 생성
    Decode 워커가 로컬 KV 캐시로 토큰 생성(S12)
  9. 디토크나이즈 + 응답 TOKEN OUT
    응답 → Processor 후처리 → Frontend가 디토크나이즈 → 클라이언트(S13)
토크나이저는 어디에 있나 — 두 시스템의 결정적 공통점입니다. 둘 다 토크나이저가 GPU 추론 엔진이 아니라 "앞단(front)" 프로세스에 상주합니다. Heimdall은 게이트웨이의 CodecRegistry에 모델별로 reactive 로드(model card 기반, 캐시 포함)되고, Dynamo는 Rust Frontend가 토크나이즈·디토크나이즈를 전담합니다. 그 결과 엔진은 token_ids / input_ids만 주고받는 순수 TITO 백엔드가 되고, 이 덕분에 게이트웨이/프런트가 prompt 토큰의 prefix 해시를 알아 KV/prefix-cache-aware 라우팅을 할 수 있습니다. 차이는 위치가 아니라 로딩 방식 — Heimdall은 InferenceWorker CRD의 model card에서 자동 발견·로드(수동 --model 불필요), Dynamo는 Frontend 구성에서 로드.

2. 그림으로 비교 8단계 정렬

같은 의미의 단계를 행으로 맞췄습니다. 1·2행(토크나이즈)과 7·8행(디토크나이즈)은 양쪽이 닮았고, 4–6행(prefill-decode 조율)에서 정반대로 갈라집니다.

프런트: 토크나이즈/디토크나이즈 라우팅 PD 조율 (핵심 차이) 워커 생성 prefill 큐 클라이언트
"첫 request는 어디로?" — Heimdall은 쏴보고 정하지 않습니다. PD 모드에서 PdCoordinator.decide()가 HTTP 발송 전에 decode·prefill 워커를 모두 점수화해 확정하고(토크나이즈한 prompt 블록 해시 ↔ sidecar가 채운 KvBlockIndex 대조 = prefix-cache routing의 실체), 그다음 sequential.rs가 prefill 워커로 첫 요청을 보냅니다. 콜드 캐시(첫 요청)면 prefix scorer는 전부 0점이라 KV-util·부하 scorer가 대신 타겟을 정하고, 그 워커가 prefill을 돌리면 sidecar의 KV 이벤트로 인덱스가 학습돼 이후 같은 prefix 요청이 그쪽으로 쏠립니다.

3. 단계 상세 설명 ④–⑦ 집중

그림의 핵심 분기인 ④–⑦을 용어까지 풀어서. ①–③은 앞에서 다뤘으니 ④부터 자세히 적었습니다.

Heimdall ④–⑦

게이트웨이가 직접 지휘

④PD 조율 — PdCoordinator.decide()

LLM 추론은 두 국면으로 나뉩니다. Prefill = 프롬프트 전체를 한 번에 forward해 KV 캐시(attention의 Key/Value를 저장해 재계산을 피하는 메모리)를 채우는 단계 — 연산 집약적이고 TTFT(첫 토큰까지 시간)를 좌우. Decode = 토큰을 하나씩 autoregressive로 생성하는 단계 — 메모리 대역폭 집약적이고 ITL(토큰 간 지연)을 좌우. 둘을 다른 워커로 분리하는 게 PD disaggregation. 게이트웨이가 decode_pipeline·prefill_pipeline을 각각 돌려(Filter→Scorer→Picker) 두 워커를 발송 전에 확정합니다.

⑤Prefill 발송 — TITO #1

sequential.rs 커넥터가 prefill 워커에 POST /inference/v1/generate를 보냅니다. TITO(Token-In/Token-Out) = 엔진이 텍스트가 아니라 token_ids를 주고받는 프로토콜. 요청에 KvTransferParams{do_remote_decode:true, do_remote_prefill:false}를 실어 "이 워커는 prefill만 하고 KV를 원격 decode로 넘길 것"을 지시. prefill 워커는 KV 캐시를 계산하고 응답에 kv_transfer_params(KV 블록 핸들/메타)를 돌려줍니다.

⑥Decode 발송 — TITO #2

prefill이 준 kv_transfer_params를 요청에 실어 decode 워커에 generate_stream(). decode 워커는 NIXL로 prefill의 KV를 받아 그 위에서 autoregressive 생성하고 토큰을 스트림으로 반환합니다. deferred decode re-selection: prefill이 임계(기본 5초)를 넘으면 decode 파이프라인을 최신 메트릭으로 다시 돌려 더 나은 decode 워커로 교체.

⑦디토크나이즈 — codec.decode()

엔진은 detokenize=false라 token_ids만 옵니다. 게이트웨이가 incremental detokenization(토큰이 도착할 때마다 누적해서 텍스트로 디코드)을 수행. streaming jail = tool call이나 특수 마커가 토큰 경계에 걸쳐 쪼개질 수 있어, 온전히 파싱될 때까지 토큰을 버퍼에 가둬두는 메커니즘. 이후 tool/reasoning 파서가 <think> 블록·tool_calls 등을 분리합니다.

Dynamo ④–⑦

decode 워커가 지휘 · 큐 기반

④Decode 워커의 disagg 판단 + KV 선할당

Router가 고른 decode 워커가 요청을 받아 ⒜ prefix cache hit(프롬프트 앞부분이 이미 캐시된 블록이 얼마나 되나) 조회, ⒝ disagg decision — prefill 길이와 큐 깊이를 보고 "원격 prefill이 필요한가"를 판단(짧으면 로컬에서 다 처리), ⒞ 필요하면 자기 로컬 GPU에 KV 블록을 미리 할당(pre-allocate)합니다. 이 빈 블록이 나중에 NIXL이 KV를 써넣을 목적지 메모리가 됩니다. 즉 조율의 주체가 게이트웨이가 아니라 워커 자신.

⑤NATS 큐로 prefill 분배

decode 워커가 RemotePrefillRequest(선할당한 블록 ID 포함)를 NATS PrefillQueue에 넣습니다. NATS = 분산 메시지 브로커, JetStream = 그 위의 영속 스트림/큐. consumer group = 같은 큐를 구독하는 prefill 워커 묶음으로, 각 메시지는 그룹 내 한 워커에만 전달(자연스러운 부하 분산 + 실패 시 재전송 보장). prefill 워커가 큐에서 pull하고, ETCD(분산 key-value 저장소, 서비스 디스커버리 + NIXL 메타 저장)에서 decode의 NIXL 메타데이터를 읽어 통신 채널을 엽니다.

⑥Prefill 실행 → NIXL 전송 → Decode 생성

prefill 워커가 input_ids로 KV 캐시를 계산한 뒤, NIXL(NVIDIA Inference Xfer Library)이 그 KV를 decode 워커의 사전할당 블록에 GPU-to-GPU로 직접 write합니다(NVLink/InfiniBand/PCIe, 중앙 스토리지 없이 worker-to-worker). 완료를 notify하면 decode 워커가 로컬 KV로 autoregressive 토큰 생성을 시작합니다.

⑦Frontend 디토크나이즈

decode 워커가 낸 token_ids가 Processor를 거쳐 Frontend로 돌아오고, Frontend가 디토크나이즈 + tool/reasoning 파싱을 수행해 텍스트 응답으로 만듭니다. Dynamo는 /tokenize·/detokenize 엔드포인트와 Fastokens 토크나이저를 프런트에 둡니다.

⑧의 SSE란? — SSE (Server-Sent Events)는 HTTP 위에서 서버→클라이언트 단방향 스트리밍을 하는 표준입니다. 응답 헤더가 Content-Type: text/event-stream이고, 연결을 닫지 않은 채 data: <payload>\n\n 형태의 이벤트를 순차적으로 흘려보냅니다. WebSocket과 달리 단방향 + 순수 HTTP라 프록시·방화벽 친화적이고 자동 재연결이 내장됩니다. OpenAI 스트리밍은 data: {chat.completion.chunk} 청크를 연달아 보내고 마지막에 data: [DONE]로 종결. Heimdall은 decode 토큰을 디토크나이즈한 청크를 SSE로 흘려보내며(build_chat_sse_response), 업스트림 에러 시 OpenAI Chat 스펙엔 error 이벤트가 없어 [DONE] 없이 조용히 종료합니다(클라이언트는 EOF로 추론). Responses·Anthropic Messages는 별도 error 이벤트가 있습니다.

지향 규모소~중 규모, 단순 운영, 검증·게이트웨이 일관성 중시초대규모 데이터센터, phase별 최적화·복원력 중시
한 줄 결론운영 단순 + 멀티-API + 게이트웨이 일관 검증이면 Heimdall초대규모 + 독립 스케일 + SLA 최적화 + 복원력이면 Dynamo
핵심 trade-off는 "중앙 동기 조율(Heimdall) vs 분산 큐 조율(Dynamo)"입니다. 전자는 단순·추적성·낮은 의존성을 얻는 대신 게이트웨이가 prefill·decode를 두 번 경유하고 백프레셔가 약합니다. 후자는 phase 독립 스케일·복원력·직접 KV 전송을 얻는 대신 ETCD/NATS 운영 부담과 분산 디버깅 비용을 감수합니다. 토큰을 앞단에서 다루는 큰 틀(TITO·프런트 토크나이저)은 같으니, 선택은 결국 운영 규모와 SLA 요구가 가릅니다.

6. prefill ↔ decode KV 전송: 거울상 비교 심화

두 시스템의 prefill·decode KV 전송을 같은 형식으로 그렸습니다. Heimdall은 decode가 당겨오고(pull), Dynamo는 prefill이 써넣습니다(push) — 전송을 주도하는 주체가 정확히 반대입니다.

Heimdall — 게이트웨이 조율 · decode-pull

Gateway: 조율 주체(순차) Prefill: KV 계산·원본 보관 Decode: KV pull·생성(능동)

Dynamo — 큐 조율 · prefill-push

Decode: 목적지 메모리 제공 Prefill: 계산 + RDMA read/write 큐: 블록 ID만 전달

전체 흐름 요약 — request → response

Heimdall (전체 경로)

①요청 도착 → unified 변환

클라이언트가 /v1/chat/completions(또는 messages/responses) 요청 → 게이트웨이가 CreateUnifiedChatRequest로 변환.

②토크나이즈 TOKEN IN

codec.encode() — chat template + HF 토크나이저 → token_ids. (토크나이저는 게이트웨이 CodecRegistry에 상주)

③워커 선택

PdCoordinator.decide()가 prefix·KV·load 점수로 prefill·decode 워커를 발송 전에 확정(Filter→Scorer→Picker).

④prefill 발송 (TITO #1)

do_remote_decode:true로 prefill 발송 → prefill이 KV 계산 후 "KV 위치"(kv_transfer_params) 반환.

⑤decode 발송 (TITO #2)

그 핸들을 실어 decode로 발송(do_remote_prefill:true).

⑥decode가 KV pull → 생성

decode가 prefill의 KV를 RDMA read로 당겨와 autoregressive 생성. (전송 주도 = decode)

⑦디토크나이즈 → 응답 TOKEN OUT

codec.decode()로 디토크나이즈 + tool/reasoning 파싱 → SSE로 클라이언트.

Dynamo (전체 경로)

①요청 도착 → Frontend 수신

클라이언트 요청을 Frontend(Rust, OpenAI 호환 :8000)가 수신 → Processor가 validate/route.

②토크나이즈 TOKEN IN

Frontend+Processor가 토크나이즈 → input_ids. (토크나이저는 Rust Frontend에 상주)

③Router가 decode 워커 선택

KV-aware 라우팅(cache overlap + load)으로 decode 워커 결정.

④decode가 disagg 판단 + KV 선할당

prefix-hit 조회 → 원격 prefill 필요 여부 판단(conditional disagg) → 로컬 GPU에 KV 블록 pre-allocate.

⑤NATS 큐로 prefill 분배

RemotePrefillRequest(블록 ID)를 큐에 push → prefill 워커가 consumer group으로 pull → ETCD에서 NIXL 메타 로드.

⑥prefill 실행 → push → 생성

prefill이 prefix-hit을 decode에서 read → 계산 → 결과 KV를 decode 블록에 RDMA write(push) → notify → decode 생성. (전송 주도 = prefill)

⑦디토크나이즈 → 응답 TOKEN OUT

decode token_ids → Frontend가 디토크나이즈 + 파싱 → 클라이언트.

심화 Q&A — prefill 메모리

세 질문에 대한 답

Q1prefill 쪽 KV 캐시는 신경 안 쓰나?

아니요 — 많이 씁니다. prefill 워커는 초기화 때 자기 GPU에 KV 캐시 풀 전체를 할당하고, 블록 메모리 디스크립터(NIXL metadata)를 ETCD에 등록합니다. prefill 결과 KV는 자기 VRAM에 올라가 전송 원본(source)이 되고, 자기 prefix 캐시·블록 매니저·연속 블록 병합 최적화까지 직접 관리합니다.

Q2큐에서 아무 노드나 받아 읽으면 되나?

노드 선택은 그렇습니다. 글로벌 큐(NATS JetStream)에서 가용 prefill 워커가 consumer group으로 pull — 그래서 워커 추가가 무설정이고 런타임 재구성(xPyD)이 자유롭습니다. (단순 로드밸런싱 외 KV-aware 라우팅 모드도 존재.) 단 큐에 실리는 건 KV 데이터가 아니라 블록 ID이고, 실제 KV는 VRAM에서 RDMA로 오갑니다.

Q3직접 쓰는 건 decode가 하나?

아니요 — 쓰는 주체는 prefill 워커입니다. decode는 목적지 블록을 선할당만 합니다. prefill 워커가 RDMA로 ① prefix-hit 블록을 decode에서 read → 나머지 계산 → ② 결과를 decode 블록에 write합니다. 전송은 non-blocking이라 그동안 양쪽 GPU가 다른 요청을 계속 처리합니다.

당신의 이해, 이렇게 정리됩니다

✓맞은 부분

"prefill 워커가 큐에서 (decode가 잡아둔) KV 캐시 위치를 받아 pull → 그걸로 prefill → 그 자리에 직접 적는다" — 핵심 흐름은 정확합니다.

＋다듬을 부분

① "어떤 req이든"이 아니라 decode가 'remote prefill 필요'라고 판단한 요청만 큐에 올라갑니다(conditional disaggregation — prefill이 짧거나 prefix-hit이 길면 decode 로컬에서 처리). ② prefill은 쓰기만 하는 게 아니라 prefix-hit 블록을 먼저 RDMA read한 뒤 나머지를 계산해 write합니다. ③ 큐가 나르는 건 위치(블록 ID)뿐, 실데이터는 VRAM↔VRAM RDMA.

⚑그래서 결론

prefill 노드는 "메모리 프리"가 아니라 KV 풀·전송 원본·prefix 캐시를 직접 관리하는 능동 주체이고, decode는 목적지 블록을 빌려주는 쪽입니다.

7. 마지막 정리 — 추론 관점 장단점 한 단락 요약

Heimdall

중앙 동기 조율 · decode-pull

＋장점

토크나이즈·스케줄링·PD 조율·디토크나이즈를 게이트웨이 한 곳에서 처리하므로 요청 경로가 단순하고 추적·디버깅이 쉽습니다. 외부 브로커(NATS/ETCD) 없이 쿠버네티스 네이티브 + ZMQ만으로 돌아 운영 의존성과 장애면이 작고, sidecar가 InferenceWorker CRD로 모델을 자동 발견해 수동 --model 없이 멀티모델·멀티토크나이저가 굴러갑니다. OpenAI(Chat·Responses)와 Anthropic Messages를 단일 unified path로 받아 게이트웨이 일관 검증(Huginn)이 쉽고, prefix-cache·KV·load를 가중 합성하는 스케줄러를 CRD로 무중단(hot-reload) 튜닝할 수 있습니다.

－단점

PD가 게이트웨이의 동기 2-hop(prefill→decode)이라 게이트웨이가 조율 병목·단일 장애점(SPOF)이 될 수 있고, KV 전송이 decode-pull이라 prefill 응답을 받아야 decode가 시작하는 순차 의존이 있습니다. prefill 폭주를 흡수할 큐·백프레셔 장치가 약하고, 세션/상태 어피니티가 없어 multi-replica stateful(Responses)에서 R5 drift가 발생합니다. 백엔드가 vLLM TITO에 사실상 고정이라 엔진 다양성도 제한적입니다.

NVIDIA Dynamo

분산 큐 조율 · prefill-push

＋장점

prefill과 decode를 독립적으로 스케일(서로 다른 TP, SLA별 워커 비율 튜닝)해 TTFT와 ITL을 따로 최적화할 수 있고, NATS JetStream 큐가 prefill 부하를 버퍼링·재분배·재시도해 트래픽 스파이크와 워커 증감(런타임 xPyD)에 강합니다. NIXL worker-to-worker 직접 전송으로 게이트웨이 병목을 우회하고, conditional disaggregation(프롬프트가 짧거나 prefix-hit이 길면 decode 로컬 처리)으로 불필요한 원격 prefill을 줄입니다. 백엔드가 vLLM/SGLang/TRT-LLM 플러그형이며 KV·세션 인지 라우팅과 Planner 오토스케일까지 갖춰 초대규모 데이터센터에 맞습니다.

－단점

ETCD·NATS 등 인프라 컴포넌트가 많아 셋업·운영 복잡도와 장애면이 커지고, 조율이 여러 주체(decode 워커·큐·prefill 워커)에 흩어져 흐름 추적과 디버깅이 어렵습니다. Python 워커 통합 레이어의 오버헤드가 있고, 큐를 거치며 경로가 길어져 소규모 배포에는 과합니다. API 표면도 주로 OpenAI 호환 중심이라 Anthropic 등 멀티 surface 일관 검증 측면에선 Heimdall보다 약합니다.

요컨대 — Heimdall은 단순성·추적성·낮은 의존성을 사는 대신 게이트웨이 동기 조율의 한계(병목·약한 백프레셔·고정 백엔드)를 안고, Dynamo는 phase 독립 스케일·복원력·직접 KV 전송을 얻는 대신 인프라·분산 디버깅 비용을 치릅니다. 소~중 규모에 멀티-API 일관 검증이 중요하면 Heimdall, 초대규모에 SLA 최적화와 복원력이 중요하면 Dynamo가 적합합니다.
