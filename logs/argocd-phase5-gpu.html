Fallback A below (Docker vLLM-ROCm + an Argo CD-managed Service) was then executed end-to-end and a cluster pod got a real completion from the MI250 → Phase 5 follow-up. 아래 폴백 A(Docker vLLM-ROCm + ArgoCD 관리 Service)를 실제로 end-to-end 실행했고, 클러스터 파드가 MI250로부터 진짜 응답을 받았다 → Phase 5 후속.
Goal of this phase이 단계 목표
Get a pod that actually uses an MI250 GCD, scheduled by Kubernetes and managed by Argo CD — by exposing the GPU into a kind node + the AMD device plugin (advertising amd.com/gpu). The plan flagged this as a stretch with a documented fallback if passthrough fights us. It fought us; here's exactly where and what to do instead. Kubernetes가 스케줄하고 ArgoCD가 관리하는, 실제 MI250 GCD를 쓰는 파드를 얻는 것 — kind 노드에 GPU를 노출 + AMD device plugin(amd.com/gpu 광고)으로. 계획은 이걸 "막히면 폴백 문서화"하는 stretch로 표시했다. 막혔고, 정확히 어디서 막혔고 대신 뭘 해야 하는지 적는다.

The attempt시도

To avoid disturbing the live gitops-lab cluster, a separate kind cluster gitops-gpu was configured to bind-mount the ROCm device files into its node, the way docker run --device does: 살아있는 gitops-lab을 안 건드리려고 별도 kind 클러스터 gitops-gpu를 만들어, docker run --device가 하듯 ROCm 장치 파일을 노드에 bind-mount하도록 구성했다:

# gpu-kind.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: gitops-gpu
nodes:
  - role: control-plane
    extraMounts:
      - { hostPath: /dev/kfd, containerPath: /dev/kfd }
      - { hostPath: /dev/dri, containerPath: /dev/dri }
Failure — the kind node won't boot with the device files mounted실패 — 장치 파일을 마운트하면 kind 노드가 부팅 안 됨
$ kind create cluster --config gpu-kind.yaml --wait 120s
 ✓ Ensuring node image (kindest/node:v1.36.1) 🖼
 ✗ Preparing nodes 📦
Deleted nodes: ["gitops-gpu-control-plane"]
ERROR: failed to create cluster: could not find a log line that matches
  "Reached target .*Multi-User System.*|detected cgroup v1"
A kind node is not a plain container — it runs systemd + containerd inside. Bind-mounting /dev/kfd and the /dev/dri device directory over the node's own /dev disrupts that init: the node never reaches the Multi-User System target, so kind times out and deletes it. The docker run --device trick that works for a normal container does not translate to kind's systemd node. kind 노드는 평범한 컨테이너가 아니다 — 안에서 systemd + containerd를 돌린다. /dev/kfd와 /dev/dri 장치 디렉터리를 노드 자기 /dev 위에 bind-mount하면 그 init이 깨진다: 노드가 Multi-User System 타깃에 도달하지 못해 kind이 타임아웃 후 삭제한다. 일반 컨테이너에 먹히는 docker run --device가 kind의 systemd 노드엔 안 통한다.
Honest side-effect (and cleanup)정직한 부작용 (그리고 정리)
Because the cluster create failed, the script's kubectl config use-context kind-gitops-gpu also failed — so kubectl stayed pointed at gitops-lab, and the next step accidentally applied the AMD device-plugin DaemonSet onto the main cluster, where it crash-looped (no GPU visible there). Caught it, deleted the stray DaemonSet, and confirmed gitops-lab was clean and all five Phase 1–4 Applications were still Synced/Healthy. Lesson: a failed context switch silently falls back to the current context — pin --context explicitly in scripts. 클러스터 생성이 실패하니 스크립트의 kubectl config use-context kind-gitops-gpu도 실패 → kubectl이 gitops-lab을 계속 가리켰고, 다음 단계가 AMD device-plugin DaemonSet을 실수로 메인 클러스터에 적용해 crashloop(거긴 GPU가 안 보임). 잡아서 stray DaemonSet 삭제, gitops-lab이 깨끗하고 Phase 1–4 앱 5개가 여전히 Synced/Healthy임을 확인. 교훈: context 전환이 실패하면 조용히 현재 context로 폴백한다 — 스크립트에선 --context를 명시적으로 고정할 것.

The contrast — Docker passthrough itself is fine대조 — Docker passthrough 자체는 멀쩡

To prove the GPU/device side is healthy and the problem is kind-specific, the same device flags on a plain container work: GPU/장치 쪽은 멀쩡하고 문제는 kind 특유임을 증명하려고, 같은 device 플래그를 평범한 컨테이너에 주면 잘 된다:

$ docker run --rm --device /dev/kfd --device /dev/dri busybox ls -l /dev/kfd
crw-rw----  1 root  44  510, 0  /dev/kfd       # ← the MI250 KFD char device, inside the container

$ rocm-smi --showproductname    # (host) GPUs present and healthy
GPU[0..]: AMD INSTINCT MI250 (MCM) ...

So the GPU is exposable to containers — it's the kind node's systemd init that the device mount breaks.즉 GPU는 컨테이너엔 노출 가능 — device mount가 깨뜨리는 건 kind 노드의 systemd init이다.

Takeaway핵심
The Argo CD / GitOps lessons (Phases 1–4) are entirely engine-agnostic — they don't need a GPU. Real GPU scheduling belongs on a real K8s node with the AMD device plugin (Option B), which is exactly the kind of cluster a production llm-d would run on. kind was the right call for learning the control plane; it is the wrong tool for GPU passthrough. Knowing that boundary precisely is the result of this phase. ArgoCD / GitOps 레슨(Phase 1–4)은 전적으로 엔진 무관 — GPU가 필요 없다. 실제 GPU 스케줄링은 AMD device plugin이 있는 진짜 K8s 노드(선택지 B)의 몫이고, 그게 바로 프로덕션 llm-d가 도는 클러스터다. kind은 컨트롤플레인 학습엔 옳은 선택, GPU passthrough엔 틀린 도구. 그 경계를 정확히 아는 것이 이 단계의 결과다.
