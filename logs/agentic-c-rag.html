검색(RAG) 에이전트 — 검색 도구 + EM 보상 (MI250)

환경: mi250-052 (MI250, ROCm 7.2.3) · Docker 전용 · verl 0.8.0 ToolAgentLoop + vLLM(hermes) · Qwen2.5-0.5B · HotpotQA · 로컬 BM25 검색 · EM 보상 · 2 GCD

2026-06-14

한 줄 요약. A의 도구 인프라를 재사용하되 도구를 검색(BM25 retriever)으로 바꿨다. 모델이 질문을 받아 search 도구로 로컬 문서를 검색하고, 읽고, <answer>로 답하면 EM(정답 일치) 보상. MI250에서 4스텝 완주, 검색 에이전트는 A(수학)보다 더 멀티턴(num_turns 2.6 vs 2.1)으로 돌며 도구를 실제로 호출한다. 그러나 두 가지 정직한 결과: (1) 로컬 BM25 검색은 매우 싸서(~7ms) rollout 병목을 못 바꾼다 — 실제 dense/웹 검색이라야 비용이 실린다. (2) 미학습 0.5B는 HotpotQA 멀티홉을 못 풀어 EM=0 — 인프라는 되지만 과제가 모델보다 크다.

1. 목표 — 도구가 외부 검색일 때

A의 도구는 코드 실행, B의 비용은 보상(테스트). C에서는 도구가 검색(retriever)이다 — 외부 지식을 가져오는 I/O. 멀티홉 QA(HotpotQA)를 주고, 모델이 검색→읽기→답을 반복하게 한다. 측정 목표: (a) 검색 에이전트가 도구를 정말 쓰는가(턴 수), (b) 검색 도구 지연이 rollout에 얼마나 실리는가 — B(보상 쪽 비용)와 대비되는 "도구 쪽 비용" 사례.

2. 구성 — BM25 검색도구 · HotpotQA · EM

Search-R1의 정통 스택은 <tool_call> 텍스트 태그 + 별도 retrieval 서버라 무겁다. 대신 A의 검증된 hermes 도구 경로를 그대로 재사용하고 도구만 검색으로 교체 — 인프라 위험을 줄였다.

조각무엇
코퍼스HotpotQA(train 512 + val 128)의 context 문단을 모아 dedup → 6,292 docs
검색도구SearchTool(BaseTool) — rank_bm25로 BM25 인덱스(인프로세스, 별도 서버 불필요), query→top-3 문단. A의 sandbox와 달리 외부 서버 없음
보상verl 내장 searchR1_hotpotqa 라우팅 → search_r1_like_qa_em: <answer> 추출 후 EM(정규화 일치)
롤아웃A와 동일: vLLM async + tool_agent loop + hermes 파서

데이터는 tool_agent 포맷(agent_name=tool_agent), 시스템 프롬프트가 "검색 도구로 찾고 <answer>로 답"하도록 지시, ground_truth={"target":[answer]}.

핵심 ① — 도구 비용은 도구 나름. B에서 보상(테스트 실행)이 1.5s였던 것과 달리, C의 검색 도구는 ~7ms다. 로컬 BM25(인메모리, 6.3k docs)라 사실상 공짜 → rollout은 그대로 생성 지배. 도구가 rollout 병목을 만들려면 dense 임베딩 검색(수백만 docs)·웹 API·원격 retrieval 서버처럼 진짜 I/O/연산이 있어야 한다. "agentic = 느리다"가 아니라 "어떤 도구냐"가 비용을 정한다.
핵심 ② — 인프라 성공 ≠ 과제 성공. 검색 루프는 완벽히 돌지만(턴 2.6, 도구 호출됨) EM=0. HotpotQA는 두 문서를 연결하는 멀티홉 추론이라 미학습 0.5B에겐 너무 크다. A(수학, 일부 정답)·B(코드, score 1.0)와 달리 C는 모델 용량이 과제에 못 미치는 사례 — agentic RL에서 "되게 만들기"와 "풀게 만들기"는 별개이고, 후자는 모델 크기·SFT·보상 설계가 좌우한다.

턴 수 대비: A 수학 2.1 → C 검색 2.6. 같은 0.5B인데 검색 에이전트가 도구를 더 자주 부른다(질문에 답하려면 검색이 거의 필수라 프롬프트 유도가 잘 먹힌 듯). 도구 호출 자체는 A보다 활발하지만(tool_calls 0.008 vs A 0.0005), 절대 비용은 여전히 미미.

4. 디버깅 — agent 경로의 보상 라우팅 함정 (5회)

C는 가장 많이 막혔다(5회). 핵심은 agent_loop(async) 경로의 보상이 단일턴 경로와 다르게 동작한다는 점:

  1. ConfigAttributeError: Missing key type — tool_config의 config에 "type":"native" 누락. → 추가.
  2. NotImplementedError: Reward function is not implemented for data_source='custom_hotpot' — agent_loop는 RewardLoopWorker가 data_source로 보상을 라우팅하며 custom_reward_function을 무시한다(B의 단일턴 경로는 존중했음). → 내장 EM이 걸린 data_source=searchR1_hotpotqa로 변경.
  3. TypeError: string indices must be integers — search_r1_like_qa_em이 ground_truth["target"]로 dict를 인덱싱. → ground_truth={"target":[answer]}로 변경. 성공
교훈. verl에서 단일턴 경로(B: custom_reward_function)와 agent_loop 경로(C: data_source 라우팅 + RewardLoopWorker)는 보상 메커니즘이 다르다. agentic 보상은 내장 reward_score 레지스트리에 등록하거나 그 형식(예: {"target":[...]})을 맞춰야 한다.

5. 결론 + 다음(D)

  1. 검색 에이전트 RL이 MI250에서 작동 — BM25 도구 + EM, 4스텝, 턴 2.6(시리즈 최다). A의 hermes 경로 재사용이 주효.
  2. 도구 비용은 도구가 정한다. 로컬 BM25는 ~7ms라 rollout을 못 바꾼다 — 진짜 비용은 dense/웹/원격 retrieval에서 온다.
  3. 인프라 ✓, 과제 ✗: 0.5B는 HotpotQA 멀티홉 불가(EM=0). 모델 용량·SFT·보상 설계가 다음 레버.
  4. agent 경로 보상 라우팅은 단일턴과 다르다 — 5회 디버깅의 핵심 교훈.

다음(D — GenRM): 보상을 규칙/EM이 아니라 LLM-as-judge(별도 모델 추론)로 바꾼다. C에서 검색 도구가 싸서 비용이 안 실렸다면, D는 보상이 모델 forward가 되어 reward 단계가 비싸지는 사례 — B(테스트 실행)보다 더 무거운 검증기.
