1. PD Disaggregation 이 무엇인가

LLM 추론은 두 단계로 나뉨 — 둘의 compute 특성이 완전히 다름:

단계하는 일특성GPU 적합
Prefillprompt 전체 token 을 한 번에 forward → KV cache 생성. 한 사용자의 첫 응답 토큰까지가 여기 포함compute-bound (matmul 무거움)H100 / B100 같이 compute 강한 GPU
Decode한 token 씩 autoregressive 생성. KV cache 를 재사용해서 새 token 1개씩 producememory-bound (KV cache 읽기 위주)A10 / L40 같이 memory bandwidth 위주의 저렴한 GPU

같은 GPU 에 P 와 D 를 같이 두면 비효율:

  • P 가 GPU compute 100% 점유하면 D 가 못 돌아감
  • D 가 KV cache 자주 읽으면 memory bandwidth 잡아먹음
  • 고가 GPU (H100) 가 memory-bound D 만 돌리면 compute 자원 낭비

PD Disaggregation 의 아이디어: P 와 D 를 다른 instance / 다른 GPU 에 분리. Prefill instance 가 KV cache 만들면 그 KV 만 Decode instance 로 transfer. P 끝나면 P GPU 는 다음 요청 받음.

사용자 요청 (긴 prompt) ↓ ┌────────────────────────┐ │ Prefill instance │ ← H100 (compute 강) │ - prompt forward │ │ - KV cache 생성 │ └────────┬────────────────┘ │ KV cache transfer (NIXL/NVLink/RDMA) ↓ ┌────────────────────────┐ │ Decode instance │ ← A10 / L40 (memory 강) │ - 한 token 씩 generate │ │ - 받은 KV cache 재사용 │ └────────────────────────┘ ↓ 응답 stream

NVIDIA Dynamo, llm-d, vLLM 자체 (experimental) 모두 PDD 지원. Meta / Hugging Face 가 production 에서 사용 중.

2. Apple Silicon 에서 시도하는 이유

Apple Silicon 의 vllm-metal 으로 두 vLLM instance 띄우고 PDD mechanism 동작 확인:

  • 학습 의도: PDD 가 어떻게 두 instance 를 연결하는지, KV cache 가 실제로 어떻게 transfer 되는지 손으로 보기
  • 구조 검증: vLLM 의 KV transfer config 가 어떻게 생겼는지 (yaml/JSON 형태 + producer/consumer role)
  • 성능 측정은 부수적: Apple Silicon 의 single host Metal 자원 공유로 의미 있는 throughput 비교는 어려움 — production NVIDIA H100 cluster 와는 다른 시나리오
전제: 같은 host 의 두 instance 가 Metal GPU 자원 공유라 throughput 향상 보장 X. PDD 의 진짜 가치는 서로 다른 GPU 형 (compute-bound vs memory-bound) 사이 분담. 본 시도는 mechanism 학습 한정.

3. KV transfer connector 9 종 검토

vLLM 의 PDD 는 두 instance 사이 KV cache 를 어떻게 옮기느냐의 backend 가 핵심. 공식 docs 에서 9개 connector 지원:

Connector방식Apple Silicon 가능?이유
NixlConnectorNVIDIA NIXL 라이브러리 (NVLink/InfiniBand RDMA)✗NVIDIA GPU + NIXL driver 필요
LMCacheConnectorV1LMCache 별도 서버를 통해 KV 저장/조회⚠LMCache 자체가 GPU 가정 강함. CPU mode 가 있긴 하지만 docs 가 NVIDIA 중심
MooncakeConnectorMooncake transfer engine (kimi-AI 의 KV cache pool)✗CUDA + InfiniBand 가정
MoRIIOConnectorAMD ROCm 전용✗ROCm only 라고 명시
ExampleConnectorshared filesystem 으로 KV blob 저장/조회✓유일하게 GPU 무관. 학습용 / offline batch 용. 시도 가능 후보
OffloadingConnectorCPU memory 로 KV 일부 offload⚠vllm-metal 의 GPU↔CPU offload path 미숙 가능성
MultiConnector여러 connector 조합위에 의존—
FlexKVConnectorV1유연한 KV 관리?NVIDIA 가정 추정
ExampleHiddenStatesConnectorhidden states 도 transfer?—

결정: ExampleConnector 만 GPU 무관. 가장 가벼움. 단 production 용 X — vLLM 공식 예제 (examples/disaggregated/example_connector/) 의 offline batch mode 이고 실제 serve 두 instance 는 아님.

4. ExampleConnector 로 실 시도

4-1. 환경 + 모델

# vllm-metal 0.3.0.dev 환경 (이전 글에서 install 완료)
source ~/.venv-vllm-metal/bin/activate
python -c "import vllm; print(vllm.__version__)"
# → 0.22.1

모델: Qwen/Qwen2.5-0.5B-Instruct (공식 예제의 Llama-3.2-1B 는 HF gated 라 token 필요. 0.5B 가 더 가볍).

4-2. prefill_example.py 가져옴

mkdir /tmp/pdd-test && cd /tmp/pdd-test
curl -s -o prefill_example.py \
  "https://raw.githubusercontent.com/vllm-project/vllm/main/examples/disaggregated/example_connector/prefill_example.py"

  "https://raw.githubusercontent.com/vllm-project/vllm/main/examples/disaggregated/example_connector/decode_example.py"

핵심 코드 (prefill_example.py):

from vllm import LLM, SamplingParams
from vllm.config import KVTransferConfig

llm = LLM(
    model="Qwen/Qwen2.5-0.5B-Instruct",
    enforce_eager=True,
    gpu_memory_utilization=0.8,
    kv_transfer_config=KVTransferConfig(
        kv_connector="ExampleConnector",
        kv_role="kv_both",
        kv_connector_extra_config={"shared_storage_path": "local_storage"},
    ),
)

sampling_params = SamplingParams(temperature=0, top_p=0.95, max_tokens=1)
outputs = llm.generate(prompts, sampling_params)
# → KV cache 가 local_storage/ 에 저장됨

# decode_example.py 가 같은 storage 에서 KV 읽고 generation 이어감

4-3. 실행

VLLM_ENABLE_V1_MULTIPROCESSING=0 python prefill_example.py

6. 분석 — 왜 안 됐나, 다른 경로 있나

6-1. 왜 vllm-metal worker 가 미구현인가

  • vllm-metal 0.3.0.dev — 아직 dev preview. README 가 명시: "experimental, FP32/FP16 만 지원"
  • Apple Silicon 의 Metal/MLX backend 는 NVIDIA GPU 와 메모리 모델 다름. KV cache 의 page 단위 transfer mechanism 이 NVIDIA NIXL 기반이라 그대로 적용 어려움
  • vLLM core team 의 PDD 자체가 experimental — production 에선 Meta/HF 가 NVIDIA stack 으로 운영. Apple Silicon 우선순위 낮음 추정

6-2. 다른 경로

(A) Docker 안 Linux vLLM + Rosetta amd64 emulation

Apple Silicon Docker Desktop 에서 amd64 emulation 으로 정통 Linux vLLM 두 컨테이너 띄움. 가능하지만:

  • vLLM CPU build image 필요 (또는 정통 GPU image 가 amd64 만)
  • Rosetta emulation 의 큰 성능 패널티 (3-5×)
  • CUDA backend 가 없으니 KV cache 가 CPU 에서 동작. PDD 의 의미 가 옅어짐 (KV 가 GPU 메모리 사이 빠른 transfer 가 핵심인데 둘 다 CPU 면 그냥 process 간 통신)

(B) LMCache 의 CPU mode

LMCache 는 별도 KV cache 서버. CPU mode 가 있긴 하지만:

  • LMCache 자체의 macOS arm64 wheel 확실치 않음
  • vllm-metal worker 의 handshake 미구현 문제는 동일

(C) vLLM source build + Metal worker fork 수정

이론적으론 가능. vllm-metal 의 worker 에 get_kv_connector_handshake_metadata 구현 추가. 단:

  • vLLM core 와 worker abstraction 깊은 이해 필요
  • upstream PR 보낼 수도 있는 작업 — 본 학습 범위 초과

(D) NVIDIA Linux 환경 (cloud)

가장 의미 있는 평가. AWS p4 / GCP A100 / Lambda Labs H100 등에서 vLLM 두 instance + NIXL connector. PDD 의 진짜 효과 (P/D 분리, KV transfer 시간, throughput 향상) 측정 가능.

7. 결론 + 다음 단계

7-1. 한 줄 결론

Apple Silicon 에서 PDD = mechanism 시연도 불가. vllm-metal dev 미숙 (KV connector handshake 미구현) + KV connector backend 들의 NVIDIA/Linux 가정. 시도해본 결과 자체가 finding.

7-2. 무엇을 배웠나

  • vLLM 의 PDD는 9 가지 KV connector 중 환경에 맞는 걸 선택해야 함. 대부분이 NVIDIA 또는 ROCm 가정.
  • KV transfer 자체가 PDD 의 핵심 — connector backend 가 동작 안 하면 mechanism 자체가 깨짐.
  • vllm-metal 의 dev 단계가 core feature 가 모두 working 한 게 아님. install 되고 단일 추론 되더라도 advanced feature 는 아직 미구현 가능.
  • 실 PDD 평가는 NVIDIA H100 + Linux + NIXL 인프라가 사실상 필수. Meta/HF 같은 big tech 가 production 에서 쓰는 이유.

7-3. NVIDIA Linux 환경에서 할 것 (시간/자원 있을 때)

  1. cloud GPU 인스턴스 빌림 (Lambda Labs / RunPod / AWS p4) — H100 1개 또는 2개
  2. vLLM 정통 install (pip install vllm — Linux 에선 즉시 wheel)
  3. 2 instance 띄움: 
    # Prefill (producer)
vllm serve Qwen/Qwen2.5-0.5B-Instruct --port 8100 \
  --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_producer",...}'

# Decode (consumer)
vllm serve Qwen/Qwen2.5-0.5B-Instruct --port 8200 \
  --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_consumer",...}'
  4. proxy script 로 client → prefill → decode 라우팅 (vLLM 공식 예제 의 disagg_proxy.py 같은)
  5. 벤치마크: 같은 워크로드를 (a) 단일 instance vs (b) PDD 두 instance 비교. throughput / TTFT / TPOT / KV transfer time 측정 → PDD 의 실 이점 정량화
