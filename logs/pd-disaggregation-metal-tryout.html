1. What is PD Disaggregation1. PD Disaggregation 이 무엇인가

LLM inference splits into two stages — their compute characteristics are completely different:LLM 추론은 두 단계로 나뉨 — 둘의 compute 특성이 완전히 다름:

Stage단계What it does하는 일Characteristic특성Suitable GPUGPU 적합
PrefillForward the entire prompt's tokens at once → generate KV cache. Covers up to the first response token for a userprompt 전체 token 을 한 번에 forward → KV cache 생성. 한 사용자의 첫 응답 토큰까지가 여기 포함compute-bound (heavy matmul)compute-bound (matmul 무거움)Compute-strong GPUs like H100 / B100H100 / B100 같이 compute 강한 GPU
DecodeAutoregressively generate one token at a time. Reuse KV cache to produce one new token at a time한 token 씩 autoregressive 생성. KV cache 를 재사용해서 새 token 1개씩 producememory-bound (mostly KV cache reads)memory-bound (KV cache 읽기 위주)Cheaper memory-bandwidth-oriented GPUs like A10 / L40A10 / L40 같이 memory bandwidth 위주의 저렴한 GPU

Placing P and D on the same GPU is inefficient:같은 GPU 에 P 와 D 를 같이 두면 비효율:

  • If P fully occupies 100% of GPU compute, D cannot runP 가 GPU compute 100% 점유하면 D 가 못 돌아감
  • If D frequently reads the KV cache, it eats into memory bandwidthD 가 KV cache 자주 읽으면 memory bandwidth 잡아먹음
  • Running only memory-bound D on an expensive GPU (H100) wastes compute resources고가 GPU (H100) 가 memory-bound D 만 돌리면 compute 자원 낭비

The idea of PD Disaggregation: separate P and D onto different instances / different GPUs. Once the prefill instance produces the KV cache, only that KV is transferred to the decode instance. When P finishes, the P GPU takes the next request.PD Disaggregation 의 아이디어: P 와 D 를 다른 instance / 다른 GPU 에 분리. Prefill instance 가 KV cache 만들면 그 KV 만 Decode instance 로 transfer. P 끝나면 P GPU 는 다음 요청 받음.

user request (long prompt) ↓ ┌────────────────────────┐ │ Prefill instance │ ← H100 (compute-strong) │ - prompt forward │ │ - build KV cache │ └────────┬────────────────┘ │ KV cache transfer (NIXL/NVLink/RDMA) ↓ ┌────────────────────────┐ │ Decode instance │ ← A10 / L40 (memory-strong) │ - generate 1 token/step│ │ - reuse received KV │ └────────────────────────┘ ↓ response stream

NVIDIA Dynamo, llm-d, and vLLM itself (experimental) all support PDD. Meta / Hugging Face use it in production.NVIDIA Dynamo, llm-d, vLLM 자체 (experimental) 모두 PDD 지원. Meta / Hugging Face 가 production 에서 사용 중.

2. Why try it on Apple Silicon2. Apple Silicon 에서 시도하는 이유

Bring up two vLLM instances on Apple Silicon's vllm-metal and verify that the PDD mechanism works:Apple Silicon 의 vllm-metal 으로 두 vLLM instance 띄우고 PDD mechanism 동작 확인:

  • Learning intent: see hands-on how PDD wires up two instances and how the KV cache is actually transferred학습 의도: PDD 가 어떻게 두 instance 를 연결하는지, KV cache 가 실제로 어떻게 transfer 되는지 손으로 보기
  • Structure check: see what vLLM's KV transfer config looks like (yaml/JSON form + producer/consumer role)구조 검증: vLLM 의 KV transfer config 가 어떻게 생겼는지 (yaml/JSON 형태 + producer/consumer role)
  • Performance measurement is secondary: meaningful throughput comparisons are hard given Apple Silicon's single-host Metal resource sharing — a different scenario from a production NVIDIA H100 cluster성능 측정은 부수적: Apple Silicon 의 single host Metal 자원 공유로 의미 있는 throughput 비교는 어려움 — production NVIDIA H100 cluster 와는 다른 시나리오
Premise: with two instances on the same host sharing Metal GPU resources, throughput gains are not guaranteed. The real value of PDD is splitting between different GPU types (compute-bound vs memory-bound). This attempt is limited to mechanism learning.전제: 같은 host 의 두 instance 가 Metal GPU 자원 공유라 throughput 향상 보장 X. PDD 의 진짜 가치는 서로 다른 GPU 형 (compute-bound vs memory-bound) 사이 분담. 본 시도는 mechanism 학습 한정.

6. Verified working with a 3-line monkey-patch6. 3줄 monkey-patch 로 동작 확인

Update — answer to the user's questions "can't we just transfer over CPU?" + "can we hack a simple implementation?": YES. Both possible. Monkey-patching the one method that the canonical GPU worker has into MetalWorker makes ExampleConnector (CPU buffer + filesystem) work as-is.업데이트 — 사용자 질문 "그냥 CPU 로 전송하면 안되는거야?" + "간단히 구현해서 해볼 수는?" 에 대한 답: YES. 둘 다 가능. 정통 GPU worker 의 method 한 개를 MetalWorker 에 monkey-patch 로 추가하니 ExampleConnector (CPU buffer + filesystem) 가 그대로 동작.

6-1. Reference implementation in the canonical GPU worker6-1. 정통 GPU worker 의 reference 구현

# vllm/v1/worker/gpu_worker.py
def get_kv_connector_handshake_metadata(self) -> dict | None:
    """Get KV connector metadata from this worker if available."""
    if not has_kv_transfer_group():
        return None
    connector = get_kv_transfer_group()
    if (metadata := connector.get_handshake_metadata()) is None:
        return None
    tp_rank = get_tp_group().rank_in_group
    return {tp_rank: metadata}

vllm-metal's MetalWorker (vllm_metal/v1/worker.py) is the only one that doesn't override this method. Mimic it and write a monkey-patch:vllm-metal 의 MetalWorker (vllm_metal/v1/worker.py) 가 이 method 만 override 안 함. 모방해서 monkey-patch 작성:

6-2. Patch script (3-line core)6-2. patch script (3줄 핵심)

# /tmp/pdd-test/patch_metal_worker.py
from vllm_metal.v1.worker import MetalWorker

def get_kv_connector_handshake_metadata(self):
    """Stub — same logic as GPU worker, tp_rank=0 (single process)."""
    from vllm.distributed.kv_transfer import has_kv_transfer_group, get_kv_transfer_group
    if not has_kv_transfer_group():
        return None
    metadata = get_kv_transfer_group().get_handshake_metadata()
    return {0: metadata} if metadata is not None else None

MetalWorker.get_kv_connector_handshake_metadata = get_kv_connector_handshake_metadata

Add one line import patch_metal_worker at the top of prefill_example.py / decode_example.py.prefill_example.py / decode_example.py 상단에 import patch_metal_worker 한 줄 추가.

6-4. Quality is a separate matter — separate working vs accuracy6-4. Quality 는 별개 — 동작 vs 정확도 구분

  • ExampleConnector is a learning example — not production-grade KV serialization. 7. Analysis — alternative paths + next steps7. 분석 — 다른 경로 + 다음 단계

6-1. Why is the vllm-metal worker unimplemented6-1. 왜 vllm-metal worker 가 미구현인가

  • vllm-metal 0.3.0.dev — still a dev preview. README states: "experimental, FP32/FP16 only"vllm-metal 0.3.0.dev — 아직 dev preview. README 가 명시: "experimental, FP32/FP16 만 지원"
  • Apple Silicon's Metal/MLX backend has a different memory model from NVIDIA GPUs. The page-level KV cache transfer mechanism is based on NVIDIA NIXL and isn't directly applicableApple Silicon 의 Metal/MLX backend 는 NVIDIA GPU 와 메모리 모델 다름. KV cache 의 page 단위 transfer mechanism 이 NVIDIA NIXL 기반이라 그대로 적용 어려움
  • PDD itself is experimental for the vLLM core team — in production, Meta/HF run it on the NVIDIA stack. Apple Silicon likely has low priorityvLLM core team 의 PDD 자체가 experimental — production 에선 Meta/HF 가 NVIDIA stack 으로 운영. Apple Silicon 우선순위 낮음 추정

6-2. Alternative paths6-2. 다른 경로

(A) Linux vLLM inside Docker + Rosetta amd64 emulation(A) Docker 안 Linux vLLM + Rosetta amd64 emulation

Bring up two canonical Linux vLLM containers with amd64 emulation on Apple Silicon Docker Desktop. Possible, but:Apple Silicon Docker Desktop 에서 amd64 emulation 으로 정통 Linux vLLM 두 컨테이너 띄움. 가능하지만:

  • Need a vLLM CPU build image (or the canonical GPU image is amd64-only)vLLM CPU build image 필요 (또는 정통 GPU image 가 amd64 만)
  • Heavy performance penalty from Rosetta emulation (3-5×)Rosetta emulation 의 큰 성능 패널티 (3-5×)
  • Without a CUDA backend, the KV cache runs on CPU. 8. Conclusion + next steps8. 결론 + 다음 단계

7-1. One-line conclusion7-1. 한 줄 결론

On Apple Silicon, PDD = even a mechanism demo is impossible. vllm-metal's dev immaturity (KV connector handshake not implemented) + KV connector backends assume NVIDIA/Linux. The result of trying is itself the finding.Apple Silicon 에서 PDD = mechanism 시연도 불가. vllm-metal dev 미숙 (KV connector handshake 미구현) + KV connector backend 들의 NVIDIA/Linux 가정. 시도해본 결과 자체가 finding.

7-2. What was learned7-2. 무엇을 배웠나

  • vLLM's PDD requires picking one of the 9 KV connectors that fits the environment. Most assume NVIDIA or ROCm.vLLM 의 PDD는 9 가지 KV connector 중 환경에 맞는 걸 선택해야 함. 대부분이 NVIDIA 또는 ROCm 가정.
  • KV transfer itself is the core of PDD — if the connector backend doesn't work, the whole mechanism breaks.KV transfer 자체가 PDD 의 핵심 — connector backend 가 동작 안 하면 mechanism 자체가 깨짐.
  • vllm-metal's dev stage means not all core features are working. Even if it installs and single inference works, advanced features may still be unimplemented.vllm-metal 의 dev 단계가 core feature 가 모두 working 한 게 아님. install 되고 단일 추론 되더라도 advanced feature 는 아직 미구현 가능.
  • Real PDD evaluation effectively requires NVIDIA H100 + Linux + NIXL infra. That's why big tech like Meta/HF runs it in production.실 PDD 평가는 NVIDIA H100 + Linux + NIXL 인프라가 사실상 필수. Meta/HF 같은 big tech 가 production 에서 쓰는 이유.

7-3. What to do on an NVIDIA Linux environment (when time/resources permit)7-3. NVIDIA Linux 환경에서 할 것 (시간/자원 있을 때)

  1. Rent a cloud GPU instance (Lambda Labs / RunPod / AWS p4) — 1 or 2 H100scloud GPU 인스턴스 빌림 (Lambda Labs / RunPod / AWS p4) — H100 1개 또는 2개
  2. Install vLLM canonically (pip install vllm — wheel installs immediately on Linux)vLLM 정통 install (pip install vllm — Linux 에선 즉시 wheel)
  3. Bring up 2 instances:2 instance 띄움: 
    # Prefill (producer)
vllm serve Qwen/Qwen2.5-0.5B-Instruct --port 8100 \
  --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_producer",...}'

# Decode (consumer)
vllm serve Qwen/Qwen2.5-0.5B-Instruct --port 8200 \
  --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_consumer",...}'
  4. Proxy script for client → prefill → decode routing (like vLLM's official disagg_proxy.py example)proxy script 로 client → prefill → decode 라우팅 (vLLM 공식 예제 의 disagg_proxy.py 같은)
  5. Benchmark: compare (a) single instance vs (b) PDD two instances on the same workload. Measure throughput / TTFT / TPOT / KV transfer time → quantify PDD's real benefit벤치마크: 같은 워크로드를 (a) 단일 instance vs (b) PDD 두 instance 비교. throughput / TTFT / TPOT / KV transfer time 측정 → PDD 의 실 이점 정량화
