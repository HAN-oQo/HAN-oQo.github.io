1. What is PD Disaggregation1. PD Disaggregation 이 무엇인가

LLM inference splits into two stages — their compute characteristics are completely different:LLM 추론은 compute 특성이 전혀 다른 두 단계로 나뉜다.

Stage단계What it does하는 일Characteristic특성Suitable GPUGPU 적합
PrefillForward the entire prompt's tokens at once → generate KV cache. Covers up to the first response token for a userprompt token 전체를 한 번에 forward 해 KV cache 생성 (첫 응답 토큰까지)compute-bound (heavy matmul)compute-bound (matmul 무거움)Compute-strong GPUs like H100 / B100H100 / B100 처럼 compute 강한 GPU
DecodeAutoregressively generate one token at a time. Reuse KV cache to produce one new token at a timeKV cache 를 재사용해 token 을 1개씩 autoregressive 생성memory-bound (mostly KV cache reads)memory-bound (KV cache 읽기 위주)Cheaper memory-bandwidth-oriented GPUs like A10 / L40A10 / L40 처럼 memory bandwidth 위주의 저렴한 GPU

Placing P and D on the same GPU is inefficient:P 와 D 를 같은 GPU 에 두면 비효율적이다.

  • If P fully occupies 100% of GPU compute, D cannot runP 가 GPU compute 를 100% 쓰면 D 가 돌지 못한다.
  • If D frequently reads the KV cache, it eats into memory bandwidthD 가 KV cache 를 자주 읽어 memory bandwidth 를 잡아먹는다.
  • Running only memory-bound D on an expensive GPU (H100) wastes compute resources고가 GPU (H100) 에서 memory-bound 인 D 만 돌리면 compute 가 남는다.

The idea of PD Disaggregation: separate P and D onto different instances / different GPUs. Once the prefill instance produces the KV cache, only that KV is transferred to the decode instance. When P finishes, the P GPU takes the next request.PD Disaggregation 은 P 와 D 를 서로 다른 instance(GPU)로 나눈다. Prefill instance 는 KV cache 를 만들어 그 KV 만 Decode instance 로 보내고, 곧바로 다음 요청을 받는다.

user request (long prompt) ↓ ┌────────────────────────┐ │ Prefill instance │ ← H100 (compute-strong) │ - prompt forward │ │ - build KV cache │ └────────┬────────────────┘ │ KV cache transfer (NIXL/NVLink/RDMA) ↓ ┌────────────────────────┐ │ Decode instance │ ← A10 / L40 (memory-strong) │ - generate 1 token/step│ │ - reuse received KV │ └────────────────────────┘ ↓ response stream

NVIDIA Dynamo, llm-d, and vLLM itself (experimental) all support PDD. Meta / Hugging Face use it in production.NVIDIA Dynamo, llm-d, vLLM (experimental) 이 PDD 를 지원하고, Meta / Hugging Face 가 production 에서 쓰고 있다.

2. Why try it on Apple Silicon2. Apple Silicon 에서 시도하는 이유

Bring up two vLLM instances on Apple Silicon's vllm-metal and verify that the PDD mechanism works:Apple Silicon 의 vllm-metal 로 vLLM instance 두 개를 띄워 PDD mechanism 이 도는지 확인한다.

  • Learning intent: see hands-on how PDD wires up two instances and how the KV cache is actually transferred학습: 두 instance 가 어떻게 연결되고 KV cache 가 어떻게 넘어가는지 직접 본다.
  • Structure check: see what vLLM's KV transfer config looks like (yaml/JSON form + producer/consumer role)구조 확인: KV transfer config 의 형태(yaml/JSON, producer/consumer role)를 본다.
Premise: with two instances on the same host sharing Metal GPU resources, throughput gains are not guaranteed. The real value of PDD is splitting between different GPU types (compute-bound vs memory-bound), a different scenario from a production NVIDIA H100 cluster. This attempt is limited to mechanism learning.전제: 두 instance 가 한 host 의 Metal GPU 를 나눠 쓰므로 throughput 비교는 의미가 없다. PDD 의 진짜 가치는 서로 다른 GPU(compute-bound vs memory-bound)에 일을 나누는 데 있고, production NVIDIA H100 cluster 와는 다른 상황이다. 이번 시도는 mechanism 학습에 한정한다.

6. Verified working with a 3-line monkey-patch6. 3줄 monkey-patch 로 동작 확인

Update — answer to the user's questions "can't we just transfer over CPU?" + "can we hack a simple implementation?": YES. Both possible. Monkey-patching the one method that the canonical GPU worker has into MetalWorker makes ExampleConnector (CPU buffer + filesystem) work as-is.업데이트: "그냥 CPU 로 전송하면 안 되나?", "간단히 구현해 볼 수는?" 두 질문의 답은 둘 다 YES다. 정통 GPU worker 의 method 하나를 MetalWorker 에 monkey-patch 로 붙이자 ExampleConnector (CPU buffer + filesystem) 가 그대로 동작했다.

6-1. Reference implementation in the canonical GPU worker6-1. 정통 GPU worker 의 reference 구현

# vllm/v1/worker/gpu_worker.py
def get_kv_connector_handshake_metadata(self) -> dict | None:
    """Get KV connector metadata from this worker if available."""
    if not has_kv_transfer_group():
        return None
    connector = get_kv_transfer_group()
    if (metadata := connector.get_handshake_metadata()) is None:
        return None
    tp_rank = get_tp_group().rank_in_group
    return {tp_rank: metadata}

vllm-metal's MetalWorker (vllm_metal/v1/worker.py) is the only one that doesn't override this method. Mimic it and write a monkey-patch:vllm-metal 의 MetalWorker (vllm_metal/v1/worker.py) 에는 이 method 만 없다. 같은 로직으로 monkey-patch 를 만든다.

6-2. Patch script (3-line core)6-2. patch script (3줄 핵심)

# /tmp/pdd-test/patch_metal_worker.py
from vllm_metal.v1.worker import MetalWorker

def get_kv_connector_handshake_metadata(self):
    """Stub — same logic as GPU worker, tp_rank=0 (single process)."""
    from vllm.distributed.kv_transfer import has_kv_transfer_group, get_kv_transfer_group
    if not has_kv_transfer_group():
        return None
    metadata = get_kv_transfer_group().get_handshake_metadata()
    return {0: metadata} if metadata is not None else None

MetalWorker.get_kv_connector_handshake_metadata = get_kv_connector_handshake_metadata

Add one line import patch_metal_worker at the top of prefill_example.py / decode_example.py.prefill_example.py / decode_example.py 맨 위에 import patch_metal_worker 한 줄을 넣는다.

6-4. Working and quality are separate6-4. 동작과 품질은 별개다

Generation quality is meaningless token repetition ("hi Hi Hi Hi..."). This is a separate issue from whether the mechanism works:생성 결과는 의미 없는 token 반복("hi Hi Hi Hi...")이다. mechanism 동작 여부와는 다른 문제이고, 원인 후보는 다음과 같다.

  • ExampleConnector is a learning example, not production-grade KV serialization. The KV blob's dtype / layout may not exactly match between normal vs disaggregatedExampleConnector 는 학습용 예제라 production 수준의 KV serialization 이 아니다. 일반 경로와 disaggregated 경로의 KV blob dtype / layout 이 어긋날 수 있다.
  • vllm-metal 0.3.0.dev's KV cache layout may differ from vLLM core's referencevllm-metal 0.3.0.dev 의 KV cache layout 이 vLLM core 의 reference 와 다를 수 있다.
  • Two processes each load the same model → need to verify whether the random-init results of the two processes (LoRA etc. beyond weights) are identical두 process 가 같은 모델을 각자 load 하므로 weights 외 random init 결과(LoRA 등)가 같은지 확인해야 한다.
  • prefill's max_tokens=1 + decode's max_tokens=10 is not a normal generation scenario (in actual PDD, prefill only forwards through the prompt, and decode does all the generation)prefill max_tokens=1 + decode max_tokens=10 은 정상 시나리오가 아니다. 실제 PDD 에서는 prefill 이 prompt forward 만 하고 생성은 decode 가 전부 맡는다.
Key finding: vllm-metal's missing KV connector was a small gap of one missing method. A 3-line patch makes the mechanism work, so a CPU-based KV transfer path works on Apple Silicon too. Quality, however, is unusable due to dev-preview limits + ExampleConnector's learning-oriented simplification. Real production still requires the NVIDIA + NIXL environment.핵심: vllm-metal 의 KV connector 미구현은 method 하나가 빠진 작은 누락이었다. 3줄 patch 로 CPU 를 거치는 KV transfer 가 Apple Silicon 에서도 돈다. 다만 dev preview 의 한계와 ExampleConnector 의 단순화 탓에 품질은 실사용 수준이 아니다. 실 production 은 여전히 NVIDIA + NIXL 환경이 필요하다.

6-5. Significance of the attempt6-5. 이번 시도에서 얻은 것

  • The hypothesis "theoretically possible, doesn't actually work" turned out to be wrong. Trying the monkey-patch made it actually work."이론상 가능하지만 실제로는 안 된다"는 가설은 틀렸다. monkey-patch 로 실제 동작했다.
  • A small fix that would likely be accepted as an upstream PR to vllm-metal (just borrows the canonical GPU worker's method as-is).정통 GPU worker 의 method 를 그대로 가져온 작은 fix 라 upstream vllm-metal 에 PR 로 받아질 가능성이 높다.
  • Distinguishing "working vs quality" matters: verifying the mechanism works ≠ guaranteeing production quality.동작과 품질은 구분해야 한다. mechanism 검증 ≠ production 품질 보장이다.
  • The "CPU transfer" the user intuitively guessed is exactly what vLLM's ExampleConnector does.직관으로 떠올린 "CPU 로 transfer" 가 바로 ExampleConnector 가 하는 일이다.

7. Analysis: alternative paths7. 분석: 다른 경로

7-1. Why is the vllm-metal worker unimplemented7-1. vllm-metal worker 에 왜 빠져 있나

  • vllm-metal 0.3.0.dev is still a dev preview. README states: "experimental, FP32/FP16 only"vllm-metal 0.3.0.dev 는 아직 dev preview다. README 에도 "experimental, FP32/FP16 만 지원"이라고 적혀 있다.
  • Apple Silicon's Metal/MLX backend has a different memory model from NVIDIA GPUs. The page-level KV cache transfer mechanism is based on NVIDIA NIXL and isn't directly applicableMetal/MLX backend 는 메모리 모델이 NVIDIA GPU 와 다르다. page 단위 KV cache transfer 는 NVIDIA NIXL 기반이라 그대로 옮기기 어렵다.
  • PDD itself is experimental for the vLLM core team; in production, Meta/HF run it on the NVIDIA stack. Apple Silicon likely has low priorityvLLM 에서도 PDD 는 experimental 이고, production 의 Meta/HF 는 NVIDIA stack 을 쓴다. Apple Silicon 은 우선순위가 낮을 것으로 보인다.

8. Conclusion + next steps8. 결론 + 다음 단계

8-1. One-line conclusion8-1. 한 줄 결론

On Apple Silicon, PDD = even a mechanism demo is impossible out of the box: vllm-metal's dev immaturity (KV connector handshake not implemented) + KV connector backends assume NVIDIA/Linux. With the §6 patch, the mechanism works but quality does not.기본 상태의 Apple Silicon 에서 PDD 는 mechanism 시연도 불가하다. vllm-metal 이 아직 미숙하고(KV connector handshake 미구현) KV connector backend 대부분이 NVIDIA/Linux 를 전제하기 때문이다. 6절의 patch 를 쓰면 mechanism 은 돌지만 품질은 나오지 않는다.

8-2. What was learned8-2. 배운 것

  • vLLM's PDD requires picking one of the 9 KV connectors that fits the environment. Most assume NVIDIA or ROCm.vLLM PDD 는 9 가지 KV connector 중 환경에 맞는 것을 골라야 하고, 대부분이 NVIDIA 나 ROCm 을 전제한다.
  • KV transfer is the core of PDD: if the connector backend doesn't work, the whole mechanism breaks.KV transfer 가 PDD 의 중심이라 connector backend 가 안 돌면 전체가 깨진다.
  • vllm-metal's dev stage means not all core features are working. Even if it installs and single inference works, advanced features may still be unimplemented.dev 단계의 vllm-metal 은 core feature 가 다 되는 상태가 아니다. 설치와 단일 추론이 돼도 advanced feature 는 빠져 있을 수 있다.
  • Real PDD evaluation effectively requires NVIDIA H100 + Linux + NIXL infra. That's why big tech like Meta/HF runs it in production.제대로 된 PDD 평가에는 NVIDIA H100 + Linux + NIXL 인프라가 사실상 필요하다. Meta/HF 가 production 에서 쓰는 환경도 이것이다.

8-3. What to do on an NVIDIA Linux environment (when time/resources permit)8-3. NVIDIA Linux 환경에서 할 일 (시간과 자원이 있을 때)

  2. Install vLLM canonically (pip install vllm; the wheel installs immediately on Linux)vLLM 설치 (pip install vllm. Linux 에서는 wheel 로 바로 설치된다)
  3. Bring up 2 instances:instance 2개 띄우기:

  4. Proxy script for client → prefill → decode routing (like vLLM's official disagg_proxy.py example)proxy script 로 client → prefill → decode 라우팅 (vLLM 공식 예제의 disagg_proxy.py 참고)
  5. Benchmark: compare (a) single instance vs (b) PDD two instances on the same workload.
