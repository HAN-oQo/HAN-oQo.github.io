Cactus prefill non-invariance — problem, reproduction, fixCactus 프리필 비등가 결함 — 문제 · 재현 · 해결

A standalone write-up of one defect in the Cactus on-device engine, built for someone who has never seen the framework. Part 1 explains it in diagrams from first principles — what prefill and decode are, why prefix caching must not change the answer, and how Cactus ships the same maths as two separately compiled op graphs (2,303 vs 2,276 nodes over the same 537 weights) then routes tokens between them by how many were submitted at once. Part 2 reproduces it two ways: by just chatting with cactus run, and precisely with curl against two servers that differ only in tail routing, hitting the boundary the source predicts (tail = prompt_tokens % 128: identical 9/9 at tail ≤ 8, diverged 43/46 at tail ≥ 9) — plus an op-level test that refutes the padding hypothesis outright. Part 3 proposes fixes, recommends chunk-aligned prefix reuse with a bounded per-turn recompute, and specifies the invariance test whose absence let this ship.Cactus 온디바이스 엔진의 결함 하나를, 이 프레임워크를 처음 보는 사람 기준으로 쓴 독립 문서. 1장은 그림으로 밑바닥부터 설명한다 — 프리필과 디코드가 뭔지, prefix caching 이 왜 답을 바꾸면 안 되는지, 그리고 Cactus 가 같은 수학을 별개로 컴파일된 op 그래프 두 벌(같은 가중치 537개 위에 노드 2,303 vs 2,276)로 만들어 놓고 한 번에 넣은 토큰 수에 따라 둘 사이로 라우팅한다는 것. 2장은 두 가지 재현 — cactus run 으로 그냥 대화하다 발견하는 법, 그리고 꼬리 라우팅만 다른 두 서버에 curl 로 소스가 예측한 경계를 맞히는 법(tail = prompt_tokens % 128: tail ≤ 8 은 9/9 일치, tail ≥ 9 는 43/46 불일치). 여기에 패딩 가설을 정면으로 반증하는 op 단위 테스트를 붙였다. 3장은 수정안 — 청크 정렬 프리픽스 재사용(턴당 재계산 상한 있음)을 권고하고, 이 결함이 통과해 온 이유인 불변식 테스트를 명세한다.

Cactus language-switch failure — model or framework?Cactus 언어 전환 실패 — 모델 문제인가 프레임워크 문제인가

Root-cause analysis of cactus run refusing to switch from Japanese to Korean mid-conversation. Systematic elimination (history, chat template vs the bundled official jinja, tokenizer, KV compression, sliding window) narrows it to one thing: the engine's three prefill paths are not numerically equivalent, and every turn after the first is pinned to the degraded incremental-KV-reuse path — same messages cold-prefilled switch 5/5, warm 0/5. The defect is language-independent and proven in pure English: under greedy (argmax) decoding, where the two arms see an identical token sequence, warm and cold emit different text in 5 of 6 conversations. Also documents a separate confirmed bug where cactus serve / the Python bindings destroy all non-ASCII input. Every experiment is reproducible: full scripts, N=5 tallies, and commit-pinned code permalinks.일본어로 시작한 대화에서 한국어 전환 요청이 먹히지 않는 cactus run 의 원인 분석. 히스토리·챗 템플릿(번들 동봉 공식 jinja 와 대조)·토크나이저·KV 압축·슬라이딩 윈도우를 차례로 소거하면 하나가 남는다 — 엔진의 프리필 경로 셋이 서로 수치적으로 등가가 아니고, 2턴 이후는 품질이 떨어지는 증분 KV 재사용 경로에 고정된다. 같은 메시지를 콜드로 넣으면 5/5 전환, warm 은 0/5. 이 결함은 언어와 무관하며 순수 영어로도 증명했다 — 두 갈래가 동일한 토큰 열을 보는 그리디(argmax) 디코딩에서 warm 과 cold 의 출력이 6개 중 5개에서 다르다. cactus serve/Python 바인딩이 모든 비-ASCII 입력을 파괴하는 별건 버그도 함께 확정. 전체 스크립트·N=5 집계·커밋 고정 퍼머링크로 전부 재현 가능.
