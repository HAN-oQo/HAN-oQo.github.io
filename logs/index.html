Tried to make the reward an LLM-as-judge (another model inference). It failed — instructively. Anatomy of the RL loop — vLLM rollout · Unsloth · veRL on MI250RL 루프 속도 해부 — vLLM rollout · Unsloth · veRL (MI250)

Actually ran GRPO on MI250 (Docker-only, ROCm 7.2.3) and dissected one step. The 2×2 (vLLM × Unsloth): turning on vLLM rollout is the one big lever — 4.4× generation, 3.7× the whole loop on a single GCD — while Unsloth full-param does almost nothing (it targets backward, but rollout is 80–92% of the step). Extended to bf16 LoRA + 4bit QLoRA: they shrink backward a little but slow the bottleneck (generation), so the loop only gets worse at this size — Unsloth's kernel path wouldn't even load on transformers 5.11. Then veRL flips the picture: with a fast rollout engine mandatory, generation is only ~27% and KL/ref forwards + reward share the cost. Input/output token lengths, every command, config, code-path, and ~9 debugging walls recorded.MI250에서 GRPO를 실제로 돌려(Docker 전용, ROCm 7.2.3) 한 스텝을 분해. 2×2(vLLM × Unsloth): vLLM rollout 켜기가 거의 유일한 큰 레버 — 단일 GCD에서 생성 4.4×, 루프 전체 3.7× — 반면 Unsloth full-param은 사실상 무효과(backward를 노리지만 rollout이 스텝의 80–92%). bf16 LoRA·4bit QLoRA로 확장: 학습부는 조금 줄지만 병목(생성)을 더 느리게 해 이 규모에선 오히려 손해 — Unsloth 커널 경로는 transformers 5.11에서 로드조차 실패. veRL로 옮기면 그림이 뒤집힌다: 빠른 롤아웃 엔진이 기본이라 생성은 ~27%뿐이고 KL/ref forward·reward가 비용을 나눠 가진다. 입출력 토큰 길이·모든 명령·config·코드 흐름·디버깅 ~9회 기록.
