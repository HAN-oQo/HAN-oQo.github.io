The question질문
Phase 0 found a single TP=2 instance is queuing/TTFT-bound — TPOT never broke. The paper's "co-located = interference/TPOT-bound" comes from 4 workers behind an InFaaS dispatcher. So Phase 0.5 builds exactly that — and asks: does 4× scale-out finally surface the interference regime? Building the dispatcher is also the point: it's the seed of the Tropical multiplexing toggle. Phase 0에서 단일 TP=2 인스턴스는 큐잉/TTFT-bound — TPOT가 안 깨졌다. 논문의 "co-located = 간섭/TPOT-bound"는 4 워커 + InFaaS 디스패처에서 온다. 그래서 Phase 0.5는 그걸 그대로 만든다 — 그리고 묻는다: 4× 스케일아웃이 드디어 간섭 체제를 드러내는가? 디스패처를 만드는 것 자체가 핵심이기도 하다 — Tropical 멀티플렉싱 토글의 씨앗이니까.

1The dispatcher (= the toggle's seed) + the pool디스패처(= 토글 씨앗) + 풀

dispatcher.py is a small async aiohttp service: it routes each request to the backend with the fewest unfinished tokens (in-flight max_tokens summed per worker) and streams the SSE response straight back. pool_up.sh brings up 4 vLLM-ROCm workers (TP=2 each, on GCD pairs (0,1)(2,3)(4,5)(6,7)) in parallel, then the dispatcher on :8000. This mirrors the paper's "4 workers, TP=2, InFaaS dispatch." dispatcher.py는 작은 비동기 aiohttp 서비스: 각 요청을 미완 토큰이 가장 적은 백엔드(워커별 in-flight max_tokens 합)로 라우팅하고 SSE 응답을 그대로 스트리밍한다. pool_up.sh는 vLLM-ROCm 워커 4개(각 TP=2, GCD 쌍 (0,1)(2,3)(4,5)(6,7))를 병렬 기동 후 :8000에 디스패처. 논문의 "4 워커, TP=2, InFaaS dispatch"를 그대로.

Why this is the toggle, not just a load balancer왜 이게 단순 LB가 아니라 토글인가
Right now the policy is "pick the least-loaded worker." Phase 2 swaps that one decision for Tropical's slack-guarded admission: route a prefill to a dedicated prefill worker only if predicted exec + queuing < TTFT slack (Path ①), or piggyback it onto a decode worker only if predicted prefill exec ≤ that worker's TPOT slack (Path ②). The plumbing — request queue, per-backend state, streaming passthrough — is already here. 지금 정책은 "가장 덜 바쁜 워커 선택"이다. Phase 2는 그 한 결정을 Tropical의 slack-가드 admission으로 교체한다: 예측 exec + 큐잉 < TTFT slack이면 전용 prefill 워커로(Path ①), 또는 예측 prefill exec ≤ 그 워커의 TPOT slack이면 decode 워커에 얹기(Path ②). 배관 — 요청 큐, 백엔드별 상태, 스트리밍 패스스루 — 은 이미 갖춰졌다.

Routing validated: 200 then 500-request replays spread evenly across the 4 workers (e.g. 598 / 651 / 620 / 631 at 40 rps), with the in-flight counters returning cleanly to zero. 라우팅 검증: 200·500 요청 리플레이가 4 워커에 고르게 분산(예: 40 rps에서 598 / 651 / 620 / 631), in-flight 카운터는 0으로 깔끔히 회수.

3Verdict — and why this is exactly Tropical's target결론 — 그리고 왜 이게 정확히 Tropical의 표적인가

The picture didn't change — it sharpened그림은 안 바뀌었다 — 더 또렷해졌다
At 4× scale, TPOT is still rock-flat at 100% (p90 ~17ms, 4.4× under SLO) while TTFT p90 explodes 144ms → 8.8s → 12.5s past 16 rps. chunked ≈ colocated (within noise). So across single-instance and 4-worker scale-out, this 7B / ShareGPT / MI250 regime is purely queuing/TTFT-bound; the paper's interference/TPOT regime needs its specific conditions (InternLM-20B, 200K context, the Mooncake long-context trace, larger sustained decode batches) that we don't reach here. 4× 규모에서도 TPOT는 여전히 100%로 완전 평탄(p90 ~17ms, SLO의 4.4× 아래), 반면 TTFT p90은 16 rps 넘어 144ms → 8.8초 → 12.5초로 폭발. chunked ≈ colocated(노이즈 수준). 즉 단일 인스턴스와 4-워커 스케일아웃 둘 다, 이 7B / ShareGPT / MI250 체제는 순수 큐잉/TTFT-bound; 논문의 간섭/TPOT 체제는 그 특유의 조건(InternLM-20B, 200K 컨텍스트, Mooncake 롱컨텍스트 트레이스, 더 큰 지속 decode 배치)이 있어야 하고 여기선 안 닿는다.

Far from a dead end, this is the strongest possible motivation for the Tropical toggle. Read the two failure signals together: 막다른 길이 아니라, 이건 Tropical 토글의 가장 강력한 동기다. 두 실패 신호를 같이 읽으면:

  • Decode is starving for work — 4.4× TPOT slack sitting idle.decode는 일이 없어 놀고 있다 — TPOT slack 4.4×가 유휴.
  • Prefill is drowning — the queue blows TTFT to 8–12s.prefill은 익사 중 — 큐가 TTFT를 8–12초로.

That is precisely the imbalance Tropical's Path ② exists to fix: spend the idle decode TPOT-slack on the prefill backlog — piggyback prefills onto the decode workers instead of letting them queue. A plain load balancer can't (it only moves whole requests between workers, all of which share the same queue problem); the slack-guarded toggle can. Our baselines didn't just measure the systems — they identified the operating point where the toggle should win. 그게 바로 Tropical Path ②가 고치려는 불균형이다: 놀고 있는 decode TPOT-slack을 prefill 적체에 쓴다 — prefill을 줄 세우는 대신 decode 워커에 얹어 태운다. 단순 LB는 못 한다(요청 통째로 워커 간 이동만 하고, 워커들은 같은 큐 문제를 공유); slack-가드 토글은 할 수 있다. 우리 베이스라인은 시스템을 측정만 한 게 아니라, 토글이 이겨야 할 동작점을 짚어냈다.
