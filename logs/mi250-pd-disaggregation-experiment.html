먼저 — 기본 hardware 용어 (form factor / die)

용어풀이
Form factor (폼팩터)부품의 물리적 모양 / 사이즈 / connector 표준. 비유: "신발 사이즈" — 같은 form factor 면 같은 슬롯에 들어감. GPU 의 form factor 예: PCIe (일반 desktop 그래픽카드), SXM (NVIDIA H100 module), OAM (open standard, AMD MI250 등). GPU server 만들 때 "어느 form factor" 가 case/power/cooling 다 결정
Die (다이)한 silicon wafer 에서 떼어낸 한 조각의 chip 본체. 트랜지스터가 실제로 박힌 silicon. 비유: "wafer = 큰 피자, die = 한 조각". 한 chip 패키지 안에: 1 die (monolithic, 보통 CPU/GPU) 또는 여러 die (chiplet / MCM — 작은 die 가 양품률 높아서 분할). MI250 = 1 OAM 안 2 die, AMD Ryzen 9 = 1 CPU 안 여러 chiplet, Apple M2 Ultra = 2 die UltraFusion 연결

다음 — MI250 의 OAM / GCD / MCM

용어풀이
OAM (OCP Accelerator Module)위에서 본 "GPU form factor 의 한 종류". Open Compute Project 가 정의한 open standard — NVIDIA SXM 의 대응. AMD MI200/MI250/MI300, Intel Gaudi 가 사용. PCIe 카드보다 큰 전력 (~ 560W) 가능. "카드 한 장의 케이스"
GCD (Graphics Compute Die)한 OAM 카드 안의 실 silicon die. "한 OAM 패키지 안의 한 die". MI250 의 한 OAM 안에 2 GCD 가 있음 (MCM 구조). ROCm 은 2 GCD 를 각각 별도 GPU 로 인식
MCM (Multi-Chip Module)위에서 본 "한 패키지 안에 여러 die" 가 들어간 chip 디자인. MI250 = MCM (2 GCD). 같은 OAM 카드 = 1 MCM 패키지 = 2 die

mi250-052 노드의 layout:

mi250-052 ├─ OAM 카드 0 → GCD 0 (64GB HBM) ↔ GCD 1 (64GB HBM) ← Infinity Fabric 으로 가깝게 ├─ OAM 카드 1 → GCD 2 ↔ GCD 3 ← 같은 OAM 안 GCD 쌍 = XGMI weight 15 ├─ OAM 카드 2 → GCD 4 ↔ GCD 5 └─ OAM 카드 3 → GCD 6 ↔ GCD 7 ※ ROCm 이 8 GCD 를 GPU0..GPU7 로 인식. "8 GPU" 라고 자주 부르지만 실은 4 OAM × 2 GCD. ※ Power sensor 는 OAM 단위 → secondary die 는 Power = N/A.

P/D GCD 선택 재검토

기존 plan: P=GCD 0-3, D=GCD 4-7. P↔D weight 평균 계산:

P (0,1,2,3) → D (4,5,6,7) 의 16 쌍 weight:
  0→4=15  0→5=30  0→6=15  0→7=30
  1→4=30  1→5=45  1→6=30  1→7=15
  2→4=15  2→5=30  2→6=15  2→7=30
  3→4=30  3→5=15  3→6=30  3→7=45
  평균 = 27.5  (중간 정도)

대안 (best): GCD 짝수 (0,2,4,6) = P, 홀수 (1,3,5,7) = D — 단 같은 카드의 두 GCD 가 P/D 로 분리되어 카드 안 Infinity Fabric 활용 못 함.

결정 유지: P=GCD 0-3 (카드 0+1), D=GCD 4-7 (카드 2+3). 이유:

  • 같은 instance 의 TP 통신 (P 안의 4 GCD 사이) 이 가장 자주 — Infinity Fabric (카드 안) 활용 best
  • P↔D transfer 는 매 request 마다 한 번 (각 layer 의 KV 전송) — TP 통신보다 빈도 낮음. weight 27.5 면 acceptable
  • 한 카드 안에 P 와 D 가 섞이면 TP 통신이 oversubscribe 됨

7-bis-0-b. Proxy 가 왜 필요한가

vLLM 자체는 단일 endpoint 가정. PDD 는 두 endpoint (prefill, decode) 가 한 logical "service" 처럼 동작해야 함. 사용자가 client 측에서 두 호출 분리하기 X. proxy 가 그 추상화 layer. 4 가지 일 함:

역할구체 행동왜 필요
① Single endpoint 제공client 는 POST :10001/v1/completions 한 번. proxy 가 내부적으로 prefill 호출 → decode 호출OpenAI 호환 API 유지 — client 가 PDD 인 줄 모름
② Prefill 단계 트리거받은 request 의 max_tokens 을 1 로 강제 변경 한 후 prefill 에 forward. prefill 는 prompt forward → KV 생성 → KV 를 RCCL 로 decode 에 sendprefill instance 가 "1 token 만 출력 + KV 보내라" 라는 신호. 실제 generation 은 decode 가 함
③ Decode 라우팅원본 request 를 decode 에 forward. request_id 에 prefill_addr + decode_addr 인코딩 (예: cmpl-___prefill_addr_192.168.3.52:20001___decode_addr_192.168.3.52:22001_<uuid>) — decode 가 그 ZMQ address 의 prefill 로부터 KV 받음을 알게 함decode 는 자기 ZMQ port 로 들어온 KV 가 어느 request 의 것인지 매칭해야 함. request_id 가 routing key
④ Service discoveryprefill/decode 가 시작 시 proxy 의 :30001 에 ping 보냄. proxy 가 그들의 http_address + zmq_address 등록. proxy 가 죽으면 새 instance 도 등록 가능proxy 가 어느 instance 가 살아있는지 + zmq 주소 동적 발견. config 에 hardcode 안 해도 됨 (XpYd scaling 위해)

즉 proxy = (a) client API gateway + (b) prefill/decode 매칭 + (c) request-ID 기반 KV routing key + (d) service discovery. 4 in 1.

8. KV cache 가 실제로 어디서 어떻게 전송되는가

8-1. 단일 engine 의 KV 생명주기 (baseline)

먼저 일반 vLLM 단일 instance 의 KV 흐름. 비교 baseline 으로 명확히 짚어둠.

한 vLLM instance (예: 8 GPU TP=8) 안에서 ┌─────────────────────────────────────────────────────────┐ │ │ │ ① Prefill (한 batch step): │ │ request prompt → tokenize → embed → forward (모든 │ │ layer) → KV (key, value) tensor 가 layer 마다 생성 │ │ → PagedAttention 의 block manager 가 GPU VRAM 안의 │ │ block table 에 page 단위로 저장 (16 token / page) │ │ │ │ ② Decode (매 token 마다): │ │ 이전 token + cached KV → forward (모든 layer) │ │ → 새 K, V 만 append 해서 cache 에 추가 → 1 token 생성│ │ │ │ ※ KV cache 는 같은 GPU process 의 VRAM 안에서만 살음. │ │ TP 시에도 GPU 사이 KV 는 stay — token dim 만 split. │ │ ※ Continuous batching: P 와 D 요청이 token-level 로 │ │ 같은 batch 에 섞임. 한 step 에서 P 토큰 일부 + D 토큰 │ │ 일부 동시 처리. │ └─────────────────────────────────────────────────────────┘

핵심: KV 가 같은 process / 같은 VRAM block table 에 머무름. transfer 자체가 없음. 같은 batch 안의 P 와 D 가 GPU compute 자원을 token-level 로 공유.

9. 만난 문제 + 진단

실 진행 순서로 만난 문제 4가지 + 진단:

9-1. 문제 1: aiter module_rmsnorm JIT compile silent kill

증상: TP=4 / TP=1 모두 worker 가 aiter module_rmsnorm import 직후 죽음 (silent — no error before kill). EngineCore initialization failed.

진단: image 가 ROCm 7.0 빌드 (rocm700), host 가 ROCm 6.2 → version mismatch. AMD aiter (AI Tensor library) 의 fused kernel 들이 host driver 와 호환 안 됨.

우회: VLLM_ROCM_USE_AITER=0 + VLLM_ROCM_USE_AITER_RMSNORM=0 + --enforce-eager. aiter 의 fused kernel 끄고 vanilla PyTorch 사용 + torch.compile graph capture 도 skip.

비용: aiter 의 fused kernel 이 없으니 약간 느림 (10-20% 추정, 직접 측정 안 함). production 에선 ROCm version 맞추는 것이 정답.

9-2. 문제 2: P2pNcclConnector 의 ZMQ port 충돌

증상:

zmq.error.ZMQError: Address already in use (addr='tcp://192.168.3.52:14579')

진단: P2pNcclConnector 가 ROUTER socket 을 default port 14579 에 bind. 두 instance 가 같은 host network 에서 동시 bind 시도 → 두번째가 fail.

원인 깊이: P2pNcclConnector source (p2p_nccl_engine.py:127) 가 kv_port + port_offset 식. port_offset 은 worker rank 기반. 같은 instance 의 worker 들은 다른 port 사용하지만 두 instance 끼리는 같은 base. 외부 proxy server (vLLM 의 disagg_proxy_server.py) 가 producer/consumer 매칭 + port discovery 해야 함.

우회: SharedStorageConnector 로 변경 (filesystem 기반, port 안 씀).

9-3. 문제 3: Generation quality 깨짐 (decode 가 garbage)

증상: prefill 의 답은 정상 ("Photosynthesis is the process..."), decode 가 같은 prompt + 저장된 KV 받아서 generation 하면 "10 to 10人 (如能本)便..." 같은 garbage 출력.

진단 가설 3가지:

  1. SharedStorageConnector 의 학습용 한계: source 의 docstring 이 "experimental" 명시. KV cache 의 dtype / layout / order 가 prefill 과 decode instance 사이 정확히 매칭하는 production guarantee 없음. 가장 가능성 높음.
  2. ROCm vLLM 0.11.2.dev 의 KV 직렬화 bug: vLLM core 의 SharedStorageConnector 가 ROCm backend 와 host filesystem 사이 safetensors 직렬화 시 dtype/byte order 차이. ROCm 의 bf16 layout 이 vLLM core 의 가정과 다를 수도.
  3. 두 instance 가 다른 random seed 로 init: weights 외 일부 (예: dropout, sample-state) 가 다름 → decode 가 받은 KV 로 다음 token attention 계산 시 distribution 어긋남. 단 temperature=0.2 / 답 deterministic 이라야 함.

검증 방법 (시도 안 함, 시간 비용 큼):

  • kv_role=kv_both 로 단일 instance 가 prefill + decode 둘 다 하면 quality 정상인지 — SharedStorage 의 round-trip 자체 검증
  • NixlConnector / Mooncake 같은 in-memory connector 시도 (NVIDIA 만 — 우리 환경 불가)
  • vLLM 최신 image 시도 (현재는 6 months old)

의미: 사용자 4번째 질문 ("현재 문제는 무엇") 의 핵심 답. production PDD 는 SharedStorage 가 아닌 NIXL/Mooncake/LMCache 같은 in-network connector 가 필요. SharedStorage 는 mechanism 시연 / prefix cache 공유 용.

9-4. 문제 4: rocm-smi 의 Secondary die Power = N/A

큰 문제 아니지만 모니터링 측면. 같은 OAM 카드의 두 GCD 중 한 GCD (secondary) 의 Power 가 N/A. 카드 단위로만 power 측정 가능. 8 GCD 의 power 비교가 4 카드 × 1 sensor 로 한정.

10. P/D 효과 분석 + 결론

10-1. 정량 측정 — 불가능했음, 솔직히

본 환경에서 P/D 의 throughput / latency 정량 비교는 불가능. 이유:

  1. SharedStorageConnector 의 quality 깨짐 (§9-3) — decode output 이 garbage 라 production 시나리오 시뮬레이션 의미 X
  2. P2pNcclConnector 같은 production connector 못 띄움 (§9-2)
  3. 의미 있는 PDD vs 단일 비교는 정확한 generation 가 전제 — quality 어긋난 KV 로 측정한 throughput 은 무의미
