1. 실험 목표

사용자가 명시한 4가지 질문에 답하기 위한 실험:

  1. 어떻게 돌릴 수 있는지 — 명령어 / config / 두 instance 띄우는 절차 전부 기록
  2. 잘 도는지 — 모니터링 로그 캡쳐 (rocm-smi, GPU util/memory/inter-GCD bandwidth, vLLM 메트릭)
  3. 내부 동작 — 실 call 한 번 보내면 KV cache 가 어디서 (어느 GPU) 어떻게 (어떤 transport — RCCL/HIP IPC/CPU bounce) 어디로 (decode 의 어느 GPU) 전송되는지 추적. 현재 stack 의 문제도
  4. P/D 효과 — 단일 vLLM 8 GPU vs P/D (P 4 GPU + D 4 GPU) 비교. TTFT / TPOT / throughput / GPU util 차이
기록 원칙 (사용자 요청): 모든 명령어 / 실패 / 우회 / 성공 / 결과 그대로 기록. Apple Silicon vLLM PDD 시도 글 (참조) 처럼 솔직히.

2. 환경 점검 — mi250-052 노드

2-1. SSH 접근 + 하드웨어

ssh mi250-052
# → user: herom, Ubuntu 5.15.0-25-generic x86_64
# → reachable, no jump host needed
항목값

GPU VRAM각 die 64 GB HBM2e → 총 512 GB GPU memory
ROCm6.2.0-66 (vLLM ROCm 빌드 호환)
Python3.10.12 (/usr/bin/python3)
HIP/usr/bin/hipcc 있음

Disk free287 GB on /
현재 GPU 점유각 die VRAM 10.5 MB 만 사용 (사실상 idle)
MI250 의 MCM 구조 이해: MI250 은 Multi-Chip Module — 한 OAM 카드 안에 2 개의 GCD (Graphics Compute Die) 가 들어감. ROCm 은 두 GCD 를 각각 별도 GPU 로 인식 → 4 카드 × 2 GCD = 8 logical GPU. 같은 카드 안의 두 GCD 는 Infinity Fabric 로 ~ 400 GB/s, 다른 카드의 GCD 와는 ~ 100 GB/s 의 inter-GCD link 가짐. 이게 KV transfer 시 매우 중요한 토폴로지.

3. 실험 설계 — 4 GPU P / 4 GPU D

3-1. 설계 결정

결정값이유
Prefill GPUGCD 0-3 (카드 0, 1)같은 OAM 카드 안 GCD 쌍 (0+1 / 2+3) 은 Infinity Fabric 400 GB/s — TP=4 시 fastest path
Decode GPUGCD 4-7 (카드 2, 3)Prefill 그룹과 다른 카드 → KV transfer 가 카드 간 (100 GB/s) 발생, real PDD 시뮬레이션
TP / PPTP=4 (각 instance)한 instance 가 4 GPU 사용 — 작은 모델이라 TP=4 면 거의 여유
모델 선택Qwen2.5-7B-Instruct (또는 1.5B 작은)4 × 64GB = 256GB 면 70B 도 가능. 7B 로 부하 시나리오 / 1.5B 로 작은 시작. 후보 둘 다 시도
KV connectorPyNcclConnector 또는 MoRIIOConnectorAMD ROCm 환경 — NCCL → RCCL 자동 매핑. MoRIIO 는 ROCm only 명시
비교 baselinevLLM 단일 (TP=8 또는 TP=4 + replica 2)같은 자원에서 PDD vs no-PDD throughput 측정

3-3. 실행 단계 plan

  1. Step 1 — 환경 검증: vLLM ROCm 빌드 install 또는 build, 모델 download
  2. Step 2 — baseline: 단일 vLLM TP=8 띄움. 실 call + 모니터링 캡쳐. 기준점.
  3. Step 3 — P/D deploy: prefill instance (TP=4, GCD 0-3) + decode instance (TP=4, GCD 4-7). proxy script (vLLM 공식 disagg_prefill_proxy_server) 으로 client → prefill → decode.
  4. Step 4 — 모니터링: 두 시나리오 모두 rocm-smi -d <gpu> --json 1초 단위 캡쳐 (util, mem, inter-GCD link bw). 기록.
  5. Step 5 — KV transfer trace: RCCL_DEBUG=INFO + vLLM --log-stats 로 KV transfer 시간 / 크기 / source GCD → target GCD 확인.
  6. Step 6 — 벤치마크: 동일 워크로드 (conc 1/4/16/32, prompt 길이 512/2048) baseline vs PDD. TTFT / TPOT / throughput / GPU util.
  7. Step 7 — 분석: 효과 정량화 + 만난 문제 + production 적용 시 고려사항.

docker pull rocm/vllm:latest

  --security-opt seccomp=unconfined --group-add video \
  --ipc=host --shm-size=16g \

  rocm/vllm:latest \
  vllm serve <model> --tensor-parallel-size 4 --port 8000 \
    --kv-transfer-config '...'

8. KV cache 가 실제로 어디서 어떻게 전송되는가

8-1. 단일 engine 의 KV 생명주기 (baseline)

먼저 일반 vLLM 단일 instance 의 KV 흐름. 비교 baseline 으로 명확히 짚어둠.

한 vLLM instance (예: 8 GPU TP=8) 안에서 ┌─────────────────────────────────────────────────────────┐ │ │ │ ① Prefill (한 batch step): │ │ request prompt → tokenize → embed → forward (모든 │ │ layer) → KV (key, value) tensor 가 layer 마다 생성 │ │ → PagedAttention 의 block manager 가 GPU VRAM 안의 │ │ block table 에 page 단위로 저장 (16 token / page) │ │ │ │ ② Decode (매 token 마다): │ │ 이전 token + cached KV → forward (모든 layer) │ │ → 새 K, V 만 append 해서 cache 에 추가 → 1 token 생성│ │ │ │ ※ KV cache 는 같은 GPU process 의 VRAM 안에서만 살음. │ │ TP 시에도 GPU 사이 KV 는 stay — token dim 만 split. │ │ ※ Continuous batching: P 와 D 요청이 token-level 로 │ │ 같은 batch 에 섞임. 한 step 에서 P 토큰 일부 + D 토큰 │ │ 일부 동시 처리. │ └─────────────────────────────────────────────────────────┘

핵심: KV 가 같은 process / 같은 VRAM block table 에 머무름. transfer 자체가 없음. 같은 batch 안의 P 와 D 가 GPU compute 자원을 token-level 로 공유.

8-2. P/D 분리 시 KV 의 생명주기

Prefill instance (4 GPU TP=4) → KV transfer → Decode instance (4 GPU TP=4) ┌─────────────────────────────────────────────────────────────────┐ │ │ │ ① Prefill instance 안: │ │ request 받음 → tokenize → embed → forward (모든 layer) │ │ → KV tensor 가 GCD 0-3 의 VRAM 의 block table 에 생성 │ │ → 첫 token 1 개 생성 (또는 prefill 종료 시점) │ │ → "이 request 의 KV 다 만들었음" 신호 │ │ │ │ ② KV connector 가 transfer: │ │ block table 안의 K, V tensor 들을 serialize → 다른 instance │ │ 로 보냄. 구체적 transport 는 connector 마다: │ │ - MoRIIO: ROCm 의 GPU-to-GPU direct memcpy (RDMA-like) │ │ - P2pNccl: RCCL collective (broadcast/send 같은) │ │ - LMCache: 중간 서버 (CPU memory pool) 거침 │ │ - ExampleConnector: filesystem write/read (CPU bounce) │ │ │ │ ③ Decode instance 안: │ │ KV 받아서 자기 block manager 에 install → 새 request 로 등록 │ │ → autoregressive 한 token 씩 generation. 모델 weights forward │ │ + cache 된 KV 사용 → 응답 stream. │ │ │ │ ※ Prefill instance 는 ② 끝나는 순간 그 request 의 KV 비움 → │ │ 다음 request 받음. P 는 throughput 위주, D 는 latency 위주. │ └─────────────────────────────────────────────────────────────────┘

8-4. P/D 단일 대비 성능에 영향 줄 수 있는 요인 (실험 전 가설)

측정 전 미리 어떤 차이가 결과에 나타날지 정리. 실험 결과로 검증/수정.

(가) Throughput 에 + 일 가능성

요인왜 + 효과본 실험 환경에서 영향도
P 와 D 의 GPU resource contention 제거단일 engine 에선 한 step 의 GPU 가 P 토큰 (compute-bound) 과 D 토큰 (memory-bound) 을 동시에 처리 → 둘 다 sub-optimal. 분리하면 각자 fully 활용★★★ (가장 큰 + 효과 예상)
P/D 별 batching policy 최적화P 는 큰 prompt 를 묶어 throughput, D 는 작은 batch 로 latency 우선 — 다른 batch size / scheduling 가능★★
P 의 자원 회수 빠름P 가 KV 만들고 transfer 끝나면 그 GPU 의 VRAM 즉시 비움 → 다음 request 즉시 받음. 같은 GPU 면 D 가 답할 때까지 KV 잡고 있어야★★
모델 weights 가 D 쪽에 동일하게 있음weights load 는 한 번이지만 P 와 D 가 같은 weights 의 다른 단계만 — KV transfer 외 redundant compute 없음중립

(나) Throughput / latency 에 − 일 가능성

요인왜 − 효과본 실험 환경에서 영향도
KV transfer 자체의 시간P 끝난 후 D 시작 전에 KV 를 옮겨야 함. transfer 시간 만큼 TTFT 추가. 작은 모델 / 짧은 prompt 면 transfer 가 forward 시간 대비 비싸 보임★★★ (가장 큰 − 효과 예상)
모델 weights 중복 loadP 와 D 가 각자 모델 weights 를 자기 VRAM 에 갖고 있어야 함. 단일 engine 면 한 번만. weights memory × 2 → 모델 크기 한계 / 또는 더 작은 KV cache 공간만 남음★★ (7B 면 weights 14GB × 2 = 28GB, 64GB GCD 중 작음. 70B 면 큰 문제)
P 와 D 의 batch size mismatchP 가 빠른데 D 가 느리면 D queue 쌓임 (또는 vice versa). load balancing 어려움. 단일 engine 은 자동으로 token-level mix★★
같은 모델 두 번 init두 instance 가 각자 model warmup + Metal/HIP kernel compile 등 cold start. 운영 시작 시 RAM/GPU 자원 두 배★ (한 번만 비용)
네트워크 overhead두 instance 사이 HTTP/gRPC handshake, RCCL init, NIXL handshake metadata 등. 매 request 마다는 아니지만 init 비용 + 매 transfer 의 control plane overhead★
한 instance 가 죽으면 같이 죽음P 와 D 가 강하게 coupled. P 가 죽으면 in-flight request 다 잃음. Decode 도 의미 없어짐. 단일 engine 도 같은 문제이지만 failure surface 2 배운영 측면

(다) 시나리오별 net effect 예상

시나리오P/D 가 유리?이유
긴 prompt + 짧은 답 (요약, 분류)★ 유리P 가 compute-bound 으로 길게, D 가 짧게 — 단일 engine 면 P 가 D batching 막음. 분리하면 P 가 다음 request 빨리
짧은 prompt + 짧은 답 (chat 일반)비슷 또는 - 일 수도P forward 시간이 짧아서 KV transfer 시간이 상대적으로 큼. transfer overhead 가 이득 잠식
긴 답 (창작, 코드 생성)★★ 유리D 가 길게 돌아감 — 분리하면 D 가 dedicated GPU 자원으로 더 efficient. P 는 짧게 끝나고 다음 request
High concurrency + 다양한 prompt 길이 mix★★★ 가장 유리다양한 P/D 토큰 비율의 request 들을 효율적 분배 가능. 단일 engine 은 batching 이 비효율적
낮은 concurrency (1-2 사용자)- 불리KV transfer overhead 만 추가. 단일 engine 면 그 자원 다 쓸 수 있음
같은 모델 다른 GPU 형 (P=H100, D=A10) mixed pool★★★ 가장 유리각 GPU 가 자기 강점만 활용. cost-efficiency 큼. 단 본 실험은 동일 MI250 8 GCD 라 이 효과 못 봄

(라) 본 실험 (MI250 8 GCD, 동일 GPU 형) 에서 예상되는 결과

본 실험은 P 와 D 둘 다 같은 MI250 GCD 4 개씩 — 비대칭 GPU 형 효과는 못 봄. 그래서:

  • 예상 1: 낮은 concurrency (1-4) 에선 P/D 가 단일 vLLM (TP=8) 보다 느림 — KV transfer 추가 비용 + 단일 engine 의 자원 활용이 이미 효율적
  • 예상 2: 높은 concurrency (16-32+) 에서 P/D 가 같거나 약간 유리 — batching resource contention 효과 보이기 시작
  • 예상 3: 긴 prompt + 짧은 답 워크로드에서 P/D 가 가장 유리 — P 의 빠른 회수가 효과
  • 예상 4: KV transfer 시간이 TTFT 의 5-30% 차지 (작은 모델 / 짧은 prompt) — 큰 모델 / 긴 prompt 면 5% 이하

이 예상들은 실험으로 검증. 결과는 §10 에서.
