1. 실험 목표

본 실험에서 답할 3 가지 질문:

  1. 어떻게 돌릴 수 있는지 — 명령어 / config / 두 instance 띄우는 절차 전부 기록
  2. 잘 도는지 — 모니터링 로그 캡쳐 (rocm-smi, GPU util/memory/inter-GCD bandwidth, vLLM 메트릭)
  3. 내부 동작 + 현재 stack 의 문제 파악 — 실 call 한 번 보내면 KV cache 가 어디서 (어느 GPU) 어떻게 (어떤 transport — RCCL/PCIe) 어디로 (decode 의 어느 GPU) 전송되는지 추적. 그리고 만나는 problem 들
P/D 효과 정량 비교는 본 실험 범위 밖: TP=1+1 (2 GCD) 의 mechanism 검증까지만. 단일 vLLM TP=8 vs P/D TP=4+4 의 throughput 비교는 다음 실험 (§11) — 본 실험은 mechanism + 문제까지.
기록 원칙: 모든 명령어 / 실패 / 우회 / 성공 / 결과 그대로 기록. Apple Silicon vLLM PDD 시도 글 (참조) 처럼 솔직히.

2-3. 실 GPU 토폴로지 (rocm-smi --showtopo 캡쳐)

먼저 — 기본 hardware 용어 (form factor / die)

용어풀이
Form factor (폼팩터)부품의 물리적 모양 / 사이즈 / connector 표준. 비유: "신발 사이즈" — 같은 form factor 면 같은 슬롯에 들어감. GPU 의 form factor 예: PCIe (일반 desktop 그래픽카드), SXM (NVIDIA H100 module), OAM (open standard, AMD MI250 등). GPU server 만들 때 "어느 form factor" 가 case/power/cooling 다 결정
Die (다이)한 silicon wafer 에서 떼어낸 한 조각의 chip 본체. 트랜지스터가 실제로 박힌 silicon. 비유: "wafer = 큰 피자, die = 한 조각". 한 chip 패키지 안에: 1 die (monolithic, 보통 CPU/GPU) 또는 여러 die (chiplet / MCM — 작은 die 가 양품률 높아서 분할). MI250 = 1 OAM 안 2 die, AMD Ryzen 9 = 1 CPU 안 여러 chiplet, Apple M2 Ultra = 2 die UltraFusion 연결

다음 — MI250 의 OAM / GCD / MCM

용어풀이
OAM (OCP Accelerator Module)위에서 본 "GPU form factor 의 한 종류". Open Compute Project 가 정의한 open standard — NVIDIA SXM 의 대응. AMD MI200/MI250/MI300, Intel Gaudi 가 사용. PCIe 카드보다 큰 전력 (~ 560W) 가능. "카드 한 장의 케이스"
GCD (Graphics Compute Die)한 OAM 카드 안의 실 silicon die. "한 OAM 패키지 안의 한 die". MI250 의 한 OAM 안에 2 GCD 가 있음 (MCM 구조). ROCm 은 2 GCD 를 각각 별도 GPU 로 인식
MCM (Multi-Chip Module)위에서 본 "한 패키지 안에 여러 die" 가 들어간 chip 디자인. MI250 = MCM (2 GCD). 같은 OAM 카드 = 1 MCM 패키지 = 2 die

mi250-052 노드의 layout:

mi250-052 ├─ OAM 카드 0 → GCD 0 (64GB HBM) ↔ GCD 1 (64GB HBM) ← Infinity Fabric 으로 가깝게 ├─ OAM 카드 1 → GCD 2 ↔ GCD 3 ← 같은 OAM 안 GCD 쌍 = XGMI weight 15 ├─ OAM 카드 2 → GCD 4 ↔ GCD 5 └─ OAM 카드 3 → GCD 6 ↔ GCD 7 ※ ROCm 이 8 GCD 를 GPU0..GPU7 로 인식. "8 GPU" 라고 자주 부르지만 실은 4 OAM × 2 GCD. ※ Power sensor 는 OAM 단위 → secondary die 는 Power = N/A.

P/D GCD 선택 재검토

기존 plan: P=GCD 0-3, D=GCD 4-7. P↔D weight 평균 계산:

P (0,1,2,3) → D (4,5,6,7) 의 16 쌍 weight:
  0→4=15  0→5=30  0→6=15  0→7=30
  1→4=30  1→5=45  1→6=30  1→7=15
  2→4=15  2→5=30  2→6=15  2→7=30
  3→4=30  3→5=15  3→6=30  3→7=45
  평균 = 27.5  (중간 정도)

대안 (best): GCD 짝수 (0,2,4,6) = P, 홀수 (1,3,5,7) = D — 단 같은 카드의 두 GCD 가 P/D 로 분리되어 카드 안 Infinity Fabric 활용 못 함.

결정 유지: P=GCD 0-3 (카드 0+1), D=GCD 4-7 (카드 2+3). 이유:

  • 같은 instance 의 TP 통신 (P 안의 4 GCD 사이) 이 가장 자주 — Infinity Fabric (카드 안) 활용 best
  • P↔D transfer 는 매 request 마다 한 번 (각 layer 의 KV 전송) — TP 통신보다 빈도 낮음. weight 27.5 면 acceptable
  • 한 카드 안에 P 와 D 가 섞이면 TP 통신이 oversubscribe 됨

7-bis-0-b. Proxy 가 왜 필요한가

vLLM 자체는 단일 endpoint 가정. PDD 는 두 endpoint (prefill, decode) 가 한 logical "service" 처럼 동작해야 함. 사용자가 client 측에서 두 호출 분리하기 X. proxy 가 그 추상화 layer. 4 가지 일 함:

역할구체 행동왜 필요
① Single endpoint 제공client 는 POST :10001/v1/completions 한 번. proxy 가 내부적으로 prefill 호출 → decode 호출OpenAI 호환 API 유지 — client 가 PDD 인 줄 모름
② Prefill 단계 트리거받은 request 의 max_tokens 을 1 로 강제 변경 한 후 prefill 에 forward. prefill 는 prompt forward → KV 생성 → KV 를 RCCL 로 decode 에 sendprefill instance 가 "1 token 만 출력 + KV 보내라" 라는 신호. 실제 generation 은 decode 가 함
③ Decode 라우팅원본 request 를 decode 에 forward. request_id 에 prefill_addr + decode_addr 인코딩 (예: cmpl-___prefill_addr_192.168.3.52:20001___decode_addr_192.168.3.52:22001_<uuid>) — decode 가 그 ZMQ address 의 prefill 로부터 KV 받음을 알게 함decode 는 자기 ZMQ port 로 들어온 KV 가 어느 request 의 것인지 매칭해야 함. request_id 가 routing key
④ Service discoveryprefill/decode 가 시작 시 proxy 의 :30001 에 ping 보냄. proxy 가 그들의 http_address + zmq_address 등록. proxy 가 죽으면 새 instance 도 등록 가능proxy 가 어느 instance 가 살아있는지 + zmq 주소 동적 발견. config 에 hardcode 안 해도 됨 (XpYd scaling 위해)

즉 proxy = (a) client API gateway + (b) prefill/decode 매칭 + (c) request-ID 기반 KV routing key + (d) service discovery. 4 in 1.

Proxy 가 만드는 2 request 의 정확한 형식 + 흐름

Client 가 한 번 호출 → proxy 가 sequential 로 2 request 만듬. 동작 순서:

Proxy 의 HTTP 호출 순서Sequential: prefill HTTP 완료 (response 소비) → decode HTTP 호출. async for _ in forward(prefill...): continue 로 prefill response 다 소비 후 진행
실 KV transferAsync background. send_type=PUT_ASYNC 라 prefill 가 KV 만들자마자 RCCL 로 즉시 send (HTTP response 와 무관). prefill HTTP 가 끝날 때쯤 KV 가 decode 에 거의 도착
왜 prefill HTTP 가 필요한가prefill 의 KV 생성을 트리거하기 위한 "신호". max_tokens=1 이라 첫 token 까지만 forward — 그게 prefill 단계의 일. 진짜 token generation 은 decode 가 함. prefill 의 1 token response 는 proxy 가 그대로 버림
"Prefill done" 의 정확한 의미 — 2 단계로 갈림
신호의미
① prefill HTTP response close
(= proxy 의 async for _ in prefill_response: continue 끝)		prefill 의 vLLM forward 완료. 모든 transformer layer 의 KV 가 prefill GPU 메모리에 존재 + 1 token output 반환. KV transfer 는 이 시점에 이미 PUT_ASYNC 로 send 진행 중 이지만 완료된 건 아님
② KV transfer 완료
(NCCL/RCCL 의 ncclSend/Recv 다 끝남)		decode 의 ZMQ channel 으로 metadata 도착 + RCCL data channel 으로 실 KV tensor 도착. HTTP 와 완전히 무관한 별도 channel
즉 proxy 는 ① 만 보고 decode 호출 시작. ② 의 보장은 decode 의 vLLM 이 자기 forward 시작 시 KV 확인 단계에서 함:
  • decode 가 자기 ZMQ inbound 에서 "이 request_id 의 KV 받았나?" 확인
  • 안 받았으면 short wait (P2pNccl 의 wait queue)
  • 받았으면 그 KV 로 generation 진행 → stream response
보통 짧은 prompt + 빠른 RCCL channel 이면 ① 시점에 ② 도 거의 완료 → wait 무시할 수 있을 정도
왜 같은 request_id?decode 가 받은 KV 가 어느 request 의 것인지 매칭하려면 same key. prefill 가 send 할 때도 같은 ID 로 tag. decode 가 자기 ZMQ 로 받은 KV 의 ID 와 자기 HTTP request 의 ID 매칭

ZMQ 가 뭐야?

ZMQ (ZeroMQ) = 고성능 비동기 messaging 라이브러리. TCP socket 위에 message queue + addressing layer 자동 처리. 단순 socket 보다 high-level abstraction.

특징설명
Message 단위byte stream 아닌 message 단위 (자동 framing). 보낸 message 1개 = 받는 message 1개
자동 reconnectpeer 가 잠시 죽었다가 다시 떠도 자동 재연결
Pattern 다양ROUTER/DEALER (req/rep multi-peer), PUB/SUB (broadcast), PUSH/PULL (load balance) 등
비유"socket 위의 우체국 layer" — 누가 어디로 보낼지만 신경 쓰면 됨, queueing/buffering/reconnect 자동
vLLM P2pNccl 의 ZMQ 사용
# 각 vLLM instance 가:
self.router_socket = self.context.socket(zmq.ROUTER)
self.router_socket.bind(f"tcp://{self.zmq_address}")  # 예: 0.0.0.0:20001

# peer (다른 instance) 가 :
sock = self.context.socket(zmq.DEALER)
sock.connect(f"tcp://192.168.3.52:22001")             # 상대 ROUTER 로 connect

# 이 ZMQ channel 위로 교환되는 것:
# - NCCL unique_id (handshake 시작 시)
# - KV tensor metadata (어느 layer 의 KV 보낼지)
# - 실 KV bytes (PUT mode 면 ZMQ 로, NCCL P2P 면 따로 RCCL 로)

즉 ZMQ 는 control plane (handshake 메타 정보), 큰 KV byte 는 NCCL/RCCL data plane 으로. 둘이 분리.

Channel전송하는 것왜 분리

send_type — PUT_ASYNC 가 선택된 이유 (Producer Push vs Consumer Pull)

사용자 지적이 좋음: 일반 PDD 설명에서 "decode 가 prefill 의 KV 를 받아옴" 이라고 자주 말함. 그러나 누가 trigger 하느냐 (producer push vs consumer pull) 는 connector / 옵션 별 다름. vLLM P2pNccl 의 send_type 옵션 3가지가 정확히 이 trigger 방향을 결정.

PR #18242 의 직접 인용:

"PUT and PUT_ASYNC: Both PUT and PUT_ASYNC involve the P instance actively sending KVcache to the D instance. The difference is that PUT is a synchronous transfer method that blocks the main process, while PUT_ASYNC is an asynchronous transfer method."

"GET: In contrast, the GET method involves the P instance saving the KVcache to the memory buffer after computing the prefill. The D instance then actively retrieves the computed KVcache from the P instance once it has allocated space for the KVcache."

"Experimental results have shown that the performance of these methods, from highest to lowest, is as follows: PUT_ASYNC → GET → PUT." + "PUT_ASYNC offers the best performance and should be prioritized."
send_type방향Trigger 누가동작장단점
PUT_ASYNC (우리 선택, default)Producer Push 비동기Prefill (P)P 가 KV 만들자마자 별도 thread 로 비동기 send. main process block 안 됨✅ 최고 성능 — P 의 forward 와 KV transfer 가 overlap. P 가 다음 request 즉시 받음

왜 PUT_ASYNC 가 default + 우리도 그것?
  1. vLLM 공식 예제의 default: disagg_example_p2p_nccl_xpyd.sh 가 그대로 PUT_ASYNC. PR #18242 도 "should be prioritized" 명시
  2. Latency overlap: P 가 forward 끝나면 KV 가 이미 send 시작됨 (async thread). proxy 의 prefill HTTP response 가 돌아올 즘 KV 가 D 에 거의 도착. D 가 호출되면 즉시 generation 시작 가능 — "prefill HTTP 시간 = KV transfer 시간" 이 overlap
  3. P resource 빠른 회수: P 의 main process 가 block 안 되니 다음 request 즉시 받을 수 있음. P throughput ↑
  4. GET 의 단점: D 가 trigger 라면 D 가 자기 forward 시작할 때 비로소 KV pull. 그 transfer 시간이 D 의 TTFT 에 직접 추가 (overlap X)
kv_buffer_size 가 send_type 별로 적용되는 곳이 다름

사용자 질문: "PUT 이면 kv_buffer_size 어떻게? PUT_ASYNC 와 다른지?" — PR #18242 직접 인용:

P (producer) instance 의 buffer:
"For P instances, the memory buffer is not required in PUT and PUT_ASYNC modes." → sender 가 buffer 필요 없음 (보내고 끝).
"For P instances in GET mode, the memory buffer should also not be too large." → GET 면 sender 가 consumer pull 까지 hold 해야 함 → buffer 필요. 단 너무 크면 GPU memory 낭비.

D (consumer) instance 의 buffer:
"For D instances, a memory buffer is needed in all three modes." → receiver 는 PUT / PUT_ASYNC / GET 모두 buffer 필요 (받은 KV 임시 hold)
send_typeProducer (P) bufferConsumer (D) buffer
PUT (sync)안 필요. main 이 block 이라 send queue 안 쌓임필요. 받은 KV → generation 까지 hold
PUT_ASYNC (우리 선택)안 필요 — async send thread 가 보내고 끝. 단 PR 의 말로는 "not required"필요 (동일)
GET필요. consumer 가 pull 할 때까지 P 가 KV 들고 있어야필요 (allocate 후 P 에서 pull)

결론:

  • 본 실험의 prefill kv_buffer_size=1e1 (10 bytes) 는 producer (P) 의 buffer — PUT_ASYNC 면 안 필요해서 거의 0. PUT 으로 바꿔도 동일 (10 bytes 그대로)
  • 본 실험의 decode kv_buffer_size=8e9 (8GB) 는 consumer (D) 의 buffer — 모든 mode 에서 필요. PUT 으로 바꿔도 동일 8GB 유지
  • 차이가 있는 경우: GET 으로 바꿀 때만 producer (P) buffer 도 늘려야 — D 가 pull 할 때까지 P 가 KV 들고 있어야 하므로

PR #18242 의 직접 설명:

역할: temporary GPU memory allocation for storing received KV cache data between instances.

Producer 작게 / Consumer 크게: "Prefill currently does not need to receive kvcache" → prefill (producer) 의 receive buffer 는 거의 0 (1e1=10 bytes) 으로 둠. Decode (consumer) 는 받은 KV 를 generation 시작까지 hold → 큰 buffer (8e9=8GB) 필요.

키우면? — Trade-off: "If it is too large, it will reduce the kvcache space available for normal inference by D instances, thereby decreasing the inference batch size." → buffer 가 클수록 KV cache 자체에 쓸 VRAM 줄어듦 → 동시 처리 가능한 sequence 수 ↓

키우는 한계 — Hardware bound

NCCL/RCCL channel 수는 결국 hardware link 수에 bound:

  • NVIDIA NVLink 4.0 (H100): 18 link/GPU → 32-64 channel 까지 의미 있음
  • AMD XGMI on MI250: 같은 OAM 안 4 link, 다른 OAM 1-2 link → 16 정도가 충분 (그 이상 marginal)
  • PCIe fallback: PCIe 5.0 x16 면 약 64GB/s — channel 많이 늘려도 bandwidth bound

한 줄: nccl_num_channels=16 이 대부분 환경의 sweet spot. MI250 에서는 16 보다 키워도 marginal. NVLink 의 H100 면 32 까지는 의미.

본 실험 (P2pNccl PUT_ASYNC = P push) vs 이전 글 (NIXL = D pull) — 같은 PDD 인데 방향성 왜 다른가
이전 본인 글 vllm_pd_disagg_flow.html 와 본 글의 방향성 차이: 이전 글은 "NixlConnector is 'READ'-based. Prefill (P) doesn't push KV; instead, Decode (D) pulls P's KV blocks directly (pull)" 라고 묘사. 본 실험은 "P가 push (PUT_ASYNC)" 라고 적음. 둘이 충돌이 아니라 connector 별로 다른 방향성:

왜 NIXL 은 D pull 인데 P2pNccl PUT_ASYNC 는 P push?
측면NIXL (D pull)P2pNccl PUT_ASYNC (P push)
Memory localityD 가 자기 ready 된 후 trigger → D 의 receive buffer overflow 위험 적음P 가 즉시 push → D 의 receive buffer 가 충분히 커야 (5-10% VRAM 권장)

결론: 둘 다 valid pattern. connector 가 다르면 KV 방향성도 다른 게 정상. 본 실험은 ROCm MI250 에서 NIXL 사용 불가 (NVIDIA 전용) → P2pNccl 선택 → 그 안의 best 성능인 PUT_ASYNC 사용 → 결과적으로 "P push" 방향. 이전 글의 "D pull" 은 NIXL 의 자체 design 시각.

일반 PDD 설명의 "decode 받아옴" vs PUT_ASYNC 의 "prefill 보냄"

이전에 본 일반 PDD 설명 (LLMServingSim / Heimdall / Frontier 문서들) 의 "decode 가 KV 받아옴" 표현은 받는 측 (consumer) 시각. KV 가 D 에 도착한다는 사실은 똑같음. 단 "누가 trigger" 는 connector / 옵션 별 다름:

설명 패턴해당 connector / 옵션본 실험
"Decode 가 받아옴" (general)모든 PDD — KV 가 P→D 로 흐른다는 사실만본 실험도 KV 가 D 에 도착
"Decode 가 pull (GET)"P2pNccl 의 send_type=GET, 또는 LMCache 의 일부 mode아님
"Prefill 가 push" (PUT/PUT_ASYNC)P2pNccl 의 default 옵션, NIXL 의 active send✓ 본 실험 (PUT_ASYNC)

즉 "PDD = decode 가 KV 받음" 은 결과 기준. "누가 trigger" 는 옵션 결정 사항. PR #18242 의 측정에서 PUT_ASYNC 이 가장 빠름 이라고 명시 (PUT_ASYNC > GET > PUT).

8. KV cache 가 실제로 어디서 어떻게 전송되는가

8-1. 단일 engine 의 KV lifecycle — 생성 → 사용 → 제거 (baseline)

용어 — "KV lifecycle (생명주기)": KV cache 한 덩이가 태어나고 → 사용되고 → 비워지는 전 과정. 영어 "lifecycle" 의 한국어 번역. 본 section 은 (1) 단일 engine 안에서 어떻게 도는지 → (2) P/D 분리 시 두 instance 사이로 어떻게 흐르는지 — 두 시나리오 비교.

먼저 일반 vLLM 단일 instance 의 KV 흐름. 비교 baseline 으로 명확히 짚어둠.

한 vLLM instance (예: 8 GPU TP=8) 안에서 ┌─────────────────────────────────────────────────────────┐ │ │ │ ① Prefill (한 batch step): │ │ request prompt → tokenize → embed → forward (모든 │ │ layer) → KV (key, value) tensor 가 layer 마다 생성 │ │ → PagedAttention 의 block manager 가 GPU VRAM 안의 │ │ block table 에 page 단위로 저장 (16 token / page) │ │ │ │ ② Decode (매 token 마다): │ │ 이전 token + cached KV → forward (모든 layer) │ │ → 새 K, V 만 append 해서 cache 에 추가 → 1 token 생성│ │ │ │ ※ KV cache 는 같은 GPU process 의 VRAM 안에서만 살음. │ │ TP 시에도 GPU 사이 KV 는 stay — token dim 만 split. │ │ ※ Continuous batching: P 와 D 요청이 token-level 로 │ │ 같은 batch 에 섞임. 한 step 에서 P 토큰 일부 + D 토큰 │ │ 일부 동시 처리. │ └─────────────────────────────────────────────────────────┘

핵심: KV 가 같은 process / 같은 VRAM block table 에 머무름. transfer 자체가 없음. 같은 batch 안의 P 와 D 가 GPU compute 자원을 token-level 로 공유.

9-1. 문제 1: aiter module_rmsnorm JIT compile silent kill

증상: TP=4 / TP=1 모두 worker 가 aiter module_rmsnorm import 직후 죽음 (silent — no error before kill). EngineCore initialization failed.

진단: image 가 ROCm 7.0 빌드 (rocm700), host 가 ROCm 6.2 → version mismatch. AMD aiter (AI Tensor library) 의 fused kernel 들이 host driver 와 호환 안 됨.

우회: VLLM_ROCM_USE_AITER=0 + VLLM_ROCM_USE_AITER_RMSNORM=0 + --enforce-eager. aiter 의 fused kernel 끄고 vanilla PyTorch 사용 + torch.compile graph capture 도 skip.

비용: aiter 의 fused kernel 이 없으니 약간 느림 (10-20% 추정, 직접 측정 안 함). production 에선 ROCm version 맞추는 것이 정답.

9-2. 문제 2: P2pNcclConnector 의 ZMQ port 충돌

증상:

zmq.error.ZMQError: Address already in use (addr='tcp://192.168.3.52:14579')

진단: P2pNcclConnector 가 ROUTER socket 을 default port 14579 에 bind. 두 instance 가 같은 host network 에서 동시 bind 시도 → 두번째가 fail.

원인 깊이: P2pNcclConnector source (p2p_nccl_engine.py:127) 가 kv_port + port_offset 식. port_offset 은 worker rank 기반. 같은 instance 의 worker 들은 다른 port 사용하지만 두 instance 끼리는 같은 base. 외부 proxy server (vLLM 의 disagg_proxy_server.py) 가 producer/consumer 매칭 + port discovery 해야 함.

우회: SharedStorageConnector 로 변경 (filesystem 기반, port 안 씀).

9-3. 문제 3: Generation quality 깨짐 (decode 가 garbage)

증상: prefill 의 답은 정상 ("Photosynthesis is the process..."), decode 가 같은 prompt + 저장된 KV 받아서 generation 하면 "10 to 10人 (如能本)便..." 같은 garbage 출력.

진단 가설 3가지:

  1. SharedStorageConnector 의 학습용 한계: source 의 docstring 이 "experimental" 명시. KV cache 의 dtype / layout / order 가 prefill 과 decode instance 사이 정확히 매칭하는 production guarantee 없음. 가장 가능성 높음.
  2. ROCm vLLM 0.11.2.dev 의 KV 직렬화 bug: vLLM core 의 SharedStorageConnector 가 ROCm backend 와 host filesystem 사이 safetensors 직렬화 시 dtype/byte order 차이. ROCm 의 bf16 layout 이 vLLM core 의 가정과 다를 수도.
  3. 두 instance 가 다른 random seed 로 init: weights 외 일부 (예: dropout, sample-state) 가 다름 → decode 가 받은 KV 로 다음 token attention 계산 시 distribution 어긋남. 단 temperature=0.2 / 답 deterministic 이라야 함.

검증 방법 (시도 안 함, 시간 비용 큼):

  • kv_role=kv_both 로 단일 instance 가 prefill + decode 둘 다 하면 quality 정상인지 — SharedStorage 의 round-trip 자체 검증
  • NixlConnector / Mooncake 같은 in-memory connector 시도 (NVIDIA 만 — 우리 환경 불가)
  • vLLM 최신 image 시도 (현재는 6 months old)

의미: 사용자 4번째 질문 ("현재 문제는 무엇") 의 핵심 답. production PDD 는 SharedStorage 가 아닌 NIXL/Mooncake/LMCache 같은 in-network connector 가 필요. SharedStorage 는 mechanism 시연 / prefix cache 공유 용.

11. 다음 실험 계획

본 실험 (TP=1+1, mechanism 검증) 의 다음 단계 — 2 가지 시나리오:

11-1. TP=4+TP=4 정통 8 GCD 활용 — Colocate 와 비교

본 실험은 TP=1+TP=1 (2 GCD) 로 mechanism 검증까지만. 다음 단계는 설계 plan 대로 TP=4+TP=4:

  • Prefill instance: TP=4, GCD 0-3 (카드 0, 1) — 카드 안 Infinity Fabric 4-link 활용
  • Decode instance: TP=4, GCD 4-7 (카드 2, 3) — 별도 카드
  • P↔D KV transfer 가 다른 OAM 카드 간 XGMI link 사용 — 진짜 multi-node 시뮬레이션
  • NCCL handshake 가 P 의 4 GCD ↔ D 의 4 GCD 사이 다 일어남 — 16 channel × 16 NCCL groups = memory 사용 ↑
  • kv_buffer_size 권장값 (5-10% VRAM) 다시 검증 — TP=4 면 각 GCD 가 KV partition 의 1/4 만 들고 있어 buffer 도 1/4 정도면 OK
  • 벤치마크: TP=1+TP=1 vs TP=4+TP=4 의 latency / throughput 비교

주의 사항:

  1. kv_port 가 instance 별 unique 인 것 + worker (TP rank) 별 port_offset 가 추가됨. 즉 prefill TP=4 면 kv_port 20001 / 20002 / 20003 / 20004 를 worker 4개가 사용. decode TP=4 면 22001-22004. 두 instance 의 port range 겹치지 않게
  2. TP=4 면 worker 사이 NCCL all_reduce 도 일어남 — KV transfer 의 P2P NCCL group 와 다른 group. NCCL channel memory 두 배로
  3. kv_buffer_size 가 작으면 spill 가능 — 8GB 가 적정한지 다시 측정

11-2. Multi-turn Bidirectional KV Transfer (PDD 의 확장)

본 실험은 single-turn 1P1D (1 prefill + 1 decode, 한 round 의 chat). 그러나 production 의 LLM chatbot 은 multi-turn 대화 (Q1 → A1 → Q2 → A2 → ...). 단순 PDD 는 multi-turn 에 비효율 — 이걸 해결하는 게 disagg_proxy_multiturn.py.

해결책 — Bidirectional KV Transfer

docstring 인용 (PR + source):

"Disaggregated Prefill/Decode Proxy with Bidirectional KV Transfer ... routing multi-turn chat requests so that each turn reuses KV cache blocks from the previous turn's Decode node via bidirectional KV transfer."

Mechanism:
"D finish ──► proxy caches │ next turn ──► proxy sends │ cached D blocks to P ──► P reads D blocks (bidir)"

Config flags: "do_remote_decode": True + "do_remote_prefill": False — explicitly enable prefill to read from decode's remote blocks in subsequent turns.
Turn 1 (initial): User: "What is photosynthesis?" ① Proxy → Prefill (Q1) → KV(Q1) → ② P→D transfer (단방향, 기존 PDD) ③ Decode (KV(Q1)) → A1 ④ Decode 가 자기 KV(Q1+A1) 들고 있음.
