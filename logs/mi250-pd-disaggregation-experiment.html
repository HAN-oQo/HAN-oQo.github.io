1. 실험 목표

사용자가 명시한 4가지 질문에 답하기 위한 실험:

  1. 어떻게 돌릴 수 있는지 — 명령어 / config / 두 instance 띄우는 절차 전부 기록
  2. 잘 도는지 — 모니터링 로그 캡쳐 (rocm-smi, GPU util/memory/inter-GCD bandwidth, vLLM 메트릭)
  3. 내부 동작 — 실 call 한 번 보내면 KV cache 가 어디서 (어느 GPU) 어떻게 (어떤 transport — RCCL/HIP IPC/CPU bounce) 어디로 (decode 의 어느 GPU) 전송되는지 추적. 현재 stack 의 문제도
  4. P/D 효과 — 단일 vLLM 8 GPU vs P/D (P 4 GPU + D 4 GPU) 비교. TTFT / TPOT / throughput / GPU util 차이
기록 원칙 (사용자 요청): 모든 명령어 / 실패 / 우회 / 성공 / 결과 그대로 기록. Apple Silicon vLLM PDD 시도 글 (참조) 처럼 솔직히.

MI250 의 MCM 구조 이해: MI250 은 Multi-Chip Module — 한 OAM 카드 안에 2 개의 GCD (Graphics Compute Die) 가 들어감. ROCm 은 두 GCD 를 각각 별도 GPU 로 인식 → 4 카드 × 2 GCD = 8 logical GPU. KV transfer 시 어떤 GCD 쌍이 빠른지가 매우 중요.

관찰의미
모든 GPU 간 link type = XGMI전 mesh 직접 연결. PCIe fallback 없음
weight 가 15 / 30 / 45 세 단계1 hop XGMI 라도 link 수 차이. weight 가 낮을수록 link 수 많음 → bandwidth 큼
GCD 쌍 (0,1), (2,3), (4,5), (6,7) 의 weight 15같은 OAM 카드 안의 GCD — Infinity Fabric 연결, 가장 빠름
가장 먼 쌍 (GPU3↔7, GPU1↔5) weight 45가장 link 수 적은 쌍 — 가장 느림. KV transfer 가 여기 거치면 손해

P/D GCD 선택 재검토

기존 plan: P=GCD 0-3, D=GCD 4-7. P↔D weight 평균 계산:

P (0,1,2,3) → D (4,5,6,7) 의 16 쌍 weight:
  0→4=15  0→5=30  0→6=15  0→7=30
  1→4=30  1→5=45  1→6=30  1→7=15
  2→4=15  2→5=30  2→6=15  2→7=30
  3→4=30  3→5=15  3→6=30  3→7=45
  평균 = 27.5  (중간 정도)

대안 (best): GCD 짝수 (0,2,4,6) = P, 홀수 (1,3,5,7) = D — 단 같은 카드의 두 GCD 가 P/D 로 분리되어 카드 안 Infinity Fabric 활용 못 함.

결정 유지: P=GCD 0-3 (카드 0+1), D=GCD 4-7 (카드 2+3). 이유:

  • 같은 instance 의 TP 통신 (P 안의 4 GCD 사이) 이 가장 자주 — Infinity Fabric (카드 안) 활용 best
  • P↔D transfer 는 매 request 마다 한 번 (각 layer 의 KV 전송) — TP 통신보다 빈도 낮음. weight 27.5 면 acceptable
  • 한 카드 안에 P 와 D 가 섞이면 TP 통신이 oversubscribe 됨

3. 실험 설계 — 4 GPU P / 4 GPU D

3-1. 설계 결정

결정값이유
Prefill GPUGCD 0-3 (카드 0, 1)같은 OAM 카드 안 GCD 쌍 (0+1 / 2+3) 은 Infinity Fabric 400 GB/s — TP=4 시 fastest path

KV connectorPyNcclConnector 또는 MoRIIOConnectorAMD ROCm 환경 — NCCL → RCCL 자동 매핑. MoRIIO 는 ROCm only 명시

5-2. 1초 polling 모니터링 script

#!/bin/bash
# ~/pd-experiment/monitor_rocm.sh
OUT=${1:-monitor.csv}
DURATION=${2:-60}
echo 'ts,device,temp_c,power_w,gpu_use_pct,vram_pct,mem_activity' > $OUT
END=$((SECONDS + DURATION))
while [ $SECONDS -lt $END ]; do
  ts=$(date +%s%3N)
  rocm-smi --showuse --showmemuse --showpower --showtemp --csv 2>/dev/null | \
    awk -v ts=$ts -F',' 'NR>1 && /^card/ {print ts","$1","$2","$9","$10","$12","$13}' >> $OUT
  sleep 1
done
echo "saved $(wc -l < $OUT) rows to $OUT"

6-4. 해결 — aiter 비활성화 + enforce-eager

$ docker run -d --name vllm-tp1 \
    --device=/dev/kfd --device=/dev/dri \
    --security-opt seccomp=unconfined --group-add video \
    --ipc=host --shm-size=8g \
    -v ~/.cache/huggingface:/root/.cache/huggingface \
    -p 8000:8000 \
    -e HIP_VISIBLE_DEVICES=0 \
    -e VLLM_ROCM_USE_AITER=0 \
    -e VLLM_ROCM_USE_AITER_RMSNORM=0 \
    rocm/vllm:latest \
    vllm serve Qwen/Qwen2.5-1.5B-Instruct \
      --tensor-parallel-size 1 \
      --enforce-eager \
      --host 0.0.0.0 --port 8000 \
      --max-model-len 4096

약 3분 후 server up. 환경변수 VLLM_ROCM_USE_AITER=0 가 aiter 의 fused kernel 사용을 끔. --enforce-eager 가 torch.compile graph capture 도 skip — 추가 안전망.

8. KV cache 가 실제로 어디서 어떻게 전송되는가

8-1. 단일 engine 의 KV 생명주기 (baseline)

먼저 일반 vLLM 단일 instance 의 KV 흐름. 비교 baseline 으로 명확히 짚어둠.

한 vLLM instance (예: 8 GPU TP=8) 안에서 ┌─────────────────────────────────────────────────────────┐ │ │ │ ① Prefill (한 batch step): │ │ request prompt → tokenize → embed → forward (모든 │ │ layer) → KV (key, value) tensor 가 layer 마다 생성 │ │ → PagedAttention 의 block manager 가 GPU VRAM 안의 │ │ block table 에 page 단위로 저장 (16 token / page) │ │ │ │ ② Decode (매 token 마다): │ │ 이전 token + cached KV → forward (모든 layer) │ │ → 새 K, V 만 append 해서 cache 에 추가 → 1 token 생성│ │ │ │ ※ KV cache 는 같은 GPU process 의 VRAM 안에서만 살음. │ │ TP 시에도 GPU 사이 KV 는 stay — token dim 만 split. │ │ ※ Continuous batching: P 와 D 요청이 token-level 로 │ │ 같은 batch 에 섞임. 한 step 에서 P 토큰 일부 + D 토큰 │ │ 일부 동시 처리. │ └─────────────────────────────────────────────────────────┘

핵심: KV 가 같은 process / 같은 VRAM block table 에 머무름. transfer 자체가 없음. 같은 batch 안의 P 와 D 가 GPU compute 자원을 token-level 로 공유.

8-2. P/D 분리 시 KV 의 생명주기

Prefill instance (4 GPU TP=4) → KV transfer → Decode instance (4 GPU TP=4) ┌─────────────────────────────────────────────────────────────────┐ │ │ │ ① Prefill instance 안: │ │ request 받음 → tokenize → embed → forward (모든 layer) │ │ → KV tensor 가 GCD 0-3 의 VRAM 의 block table 에 생성 │ │ → 첫 token 1 개 생성 (또는 prefill 종료 시점) │ │ → "이 request 의 KV 다 만들었음" 신호 │ │ │ │ ② KV connector 가 transfer: │ │ block table 안의 K, V tensor 들을 serialize → 다른 instance │ │ 로 보냄. 구체적 transport 는 connector 마다: │ │ - MoRIIO: ROCm 의 GPU-to-GPU direct memcpy (RDMA-like) │ │ - P2pNccl: RCCL collective (broadcast/send 같은) │ │ - LMCache: 중간 서버 (CPU memory pool) 거침 │ │ - ExampleConnector: filesystem write/read (CPU bounce) │ │ │ │ ③ Decode instance 안: │ │ KV 받아서 자기 block manager 에 install → 새 request 로 등록 │ │ → autoregressive 한 token 씩 generation. 모델 weights forward │ │ + cache 된 KV 사용 → 응답 stream. │ │ │ │ ※ Prefill instance 는 ② 끝나는 순간 그 request 의 KV 비움 → │ │ 다음 request 받음. P 는 throughput 위주, D 는 latency 위주. │ └─────────────────────────────────────────────────────────────────┘

측정 전 미리 어떤 차이가 결과에 나타날지 정리. 실험 결과로 검증/수정.

(가) Throughput 에 + 일 가능성

요인왜 + 효과본 실험 환경에서 영향도
P 와 D 의 GPU resource contention 제거단일 engine 에선 한 step 의 GPU 가 P 토큰 (compute-bound) 과 D 토큰 (memory-bound) 을 동시에 처리 → 둘 다 sub-optimal. 분리하면 각자 fully 활용★★★ (가장 큰 + 효과 예상)
P/D 별 batching policy 최적화P 는 큰 prompt 를 묶어 throughput, D 는 작은 batch 로 latency 우선 — 다른 batch size / scheduling 가능★★
P 의 자원 회수 빠름P 가 KV 만들고 transfer 끝나면 그 GPU 의 VRAM 즉시 비움 → 다음 request 즉시 받음. 같은 GPU 면 D 가 답할 때까지 KV 잡고 있어야★★
모델 weights 가 D 쪽에 동일하게 있음weights load 는 한 번이지만 P 와 D 가 같은 weights 의 다른 단계만 — KV transfer 외 redundant compute 없음중립

(라) 본 실험 (MI250 8 GCD, 동일 GPU 형) 에서 예상되는 결과

  • 예상 1: 낮은 concurrency (1-4) 에선 P/D 가 단일 vLLM (TP=8) 보다 느림 — KV transfer 추가 비용 + 단일 engine 의 자원 활용이 이미 효율적
  • 예상 2: 높은 concurrency (16-32+) 에서 P/D 가 같거나 약간 유리 — batching resource contention 효과 보이기 시작
  • 예상 3: 긴 prompt + 짧은 답 워크로드에서 P/D 가 가장 유리 — P 의 빠른 회수가 효과
  • 예상 4: KV transfer 시간이 TTFT 의 5-30% 차지 (작은 모델 / 짧은 prompt) — 큰 모델 / 긴 prompt 면 5% 이하

이 예상들은 실험으로 검증. 결과는 §10 에서.

9. 만난 문제 + 진단

실 진행 순서로 만난 문제 4가지 + 진단:

9-1. 문제 1: aiter module_rmsnorm JIT compile silent kill

증상: TP=4 / TP=1 모두 worker 가 aiter module_rmsnorm import 직후 죽음 (silent — no error before kill). EngineCore initialization failed.

진단: image 가 ROCm 7.0 빌드 (rocm700), host 가 ROCm 6.2 → version mismatch. AMD aiter (AI Tensor library) 의 fused kernel 들이 host driver 와 호환 안 됨.

우회: VLLM_ROCM_USE_AITER=0 + VLLM_ROCM_USE_AITER_RMSNORM=0 + --enforce-eager. aiter 의 fused kernel 끄고 vanilla PyTorch 사용 + torch.compile graph capture 도 skip.

비용: aiter 의 fused kernel 이 없으니 약간 느림 (10-20% 추정, 직접 측정 안 함). production 에선 ROCm version 맞추는 것이 정답.

9-2. 문제 2: P2pNcclConnector 의 ZMQ port 충돌

증상:

zmq.error.ZMQError: Address already in use (addr='tcp://192.168.3.52:14579')

진단: P2pNcclConnector 가 ROUTER socket 을 default port 14579 에 bind. 두 instance 가 같은 host network 에서 동시 bind 시도 → 두번째가 fail.

원인 깊이: P2pNcclConnector source (p2p_nccl_engine.py:127) 가 kv_port + port_offset 식. port_offset 은 worker rank 기반. 같은 instance 의 worker 들은 다른 port 사용하지만 두 instance 끼리는 같은 base. 외부 proxy server (vLLM 의 disagg_proxy_server.py) 가 producer/consumer 매칭 + port discovery 해야 함.

우회: SharedStorageConnector 로 변경 (filesystem 기반, port 안 씀).

9-3. 문제 3: Generation quality 깨짐 (decode 가 garbage)

증상: prefill 의 답은 정상 ("Photosynthesis is the process..."), decode 가 같은 prompt + 저장된 KV 받아서 generation 하면 "10 to 10人 (如能本)便..." 같은 garbage 출력.

진단 가설 3가지:

  1. SharedStorageConnector 의 학습용 한계: source 의 docstring 이 "experimental" 명시. KV cache 의 dtype / layout / order 가 prefill 과 decode instance 사이 정확히 매칭하는 production guarantee 없음. 가장 가능성 높음.
  2. ROCm vLLM 0.11.2.dev 의 KV 직렬화 bug: vLLM core 의 SharedStorageConnector 가 ROCm backend 와 host filesystem 사이 safetensors 직렬화 시 dtype/byte order 차이. ROCm 의 bf16 layout 이 vLLM core 의 가정과 다를 수도.
  3. 두 instance 가 다른 random seed 로 init: weights 외 일부 (예: dropout, sample-state) 가 다름 → decode 가 받은 KV 로 다음 token attention 계산 시 distribution 어긋남. 단 temperature=0.2 / 답 deterministic 이라야 함.

검증 방법 (시도 안 함, 시간 비용 큼):

  • kv_role=kv_both 로 단일 instance 가 prefill + decode 둘 다 하면 quality 정상인지 — SharedStorage 의 round-trip 자체 검증
  • NixlConnector / Mooncake 같은 in-memory connector 시도 (NVIDIA 만 — 우리 환경 불가)
  • vLLM 최신 image 시도 (현재는 6 months old)

의미: 사용자 4번째 질문 ("현재 문제는 무엇") 의 핵심 답. production PDD 는 SharedStorage 가 아닌 NIXL/Mooncake/LMCache 같은 in-network connector 가 필요. SharedStorage 는 mechanism 시연 / prefix cache 공유 용.

9-4. 문제 4: rocm-smi 의 Secondary die Power = N/A

큰 문제 아니지만 모니터링 측면. 같은 OAM 카드의 두 GCD 중 한 GCD (secondary) 의 Power 가 N/A. 카드 단위로만 power 측정 가능. 8 GCD 의 power 비교가 4 카드 × 1 sensor 로 한정.

10. P/D 효과 분석 + 결론

10-1. 정량 측정 — 불가능했음, 솔직히

본 환경에서 P/D 의 throughput / latency 정량 비교는 불가능. 이유:

  1. SharedStorageConnector 의 quality 깨짐 (§9-3) — decode output 이 garbage 라 production 시나리오 시뮬레이션 의미 X
  2. P2pNcclConnector 같은 production connector 못 띄움 (§9-2)
  3. 의미 있는 PDD vs 단일 비교는 정확한 generation 가 전제 — quality 어긋난 KV 로 측정한 throughput 은 무의미

10-2. 그래도 측정 된 것 — wall time, mechanism, monitoring

호출wall timeoutput
Prefill 만 (kv_producer 가 자체 generation)6,197 ms정상 ("Photosynthesis is...")
Decode 만 (같은 prompt, kv_consumer 가 KV load 후 generation)6,486 msgarbage

흥미로운 관찰: 두 호출 wall time 이 비슷 (6.2s vs 6.5s). 단일 TP=8 baseline 측정 안 했지만 (worker -3 fail 로 시도 미완), 1.5B 모델이 TP=4 면 약 같은 latency 일 듯. PDD 의 latency overhead 가 매우 작음을 시사 — 단 quality OK 일 때 의미.

10-3. 가설 (§8-4) vs 실 결과 비교

§8-4 가설실 결과검증?
예상 1: 낮은 conc 에서 PDD 가 단일보다 느림측정 못 함 (quality)—
예상 2: 높은 conc 에서 PDD 가 같거나 약간 유리측정 못 함—
예상 3: KV transfer 시간 = TTFT 의 5-30%부분 확인: 한 request 의 KV 564KB. filesystem 동기 write = 10-30ms 수준 (SSD 가정). 6초 prefill 의 0.5% 정도. 가설 예상보다 훨씬 작음 (단 작은 모델이라)가설 too high
예상 4: 모델 weights 중복 load 메모리 부담실 확인: VRAM 91% × 2 instance — Qwen2.5-1.5B 가 TP=4 에서도 GCD 당 58GB 사용. KV cache 가 max_model_len 만큼 미리 할당가설 맞음
예상 5: P/D resource contention 제거 +효과측정 못 함 (단일 baseline 미실험)—

10-4. 사용자 4가지 질문에 대한 답

질문답
1. 어떻게 돌릴 수 있는지✅ 답함. docker rocm/vllm:latest + 2 container (TP=4 each, GCD 0-3 / 4-7) + SharedStorageConnector + shared_kv dir mount. AITER 끄고 enforce-eager 필요 (ROCm version mismatch 우회).
2. 잘 도는지 (모니터링 캡쳐)⚠ 부분. mechanism 동작 (실 결과 §7-1, §7-2). GPU% 캡쳐 OK (prefill GCD 0-3 68-84%, decode 4-7 timing 못 잡음). quality 망가짐 으로 production 운영 X.
