Code agent — unit-test-pass reward (RLVR, MI250)코드 에이전트 — 유닛테스트 통과 보상 (RLVR, MI250)

Environment환경: mi250-052 (MI250, ROCm 7.2.3) · Docker onlyDocker 전용 · verl 0.8.0 GRPO · Qwen2.5-0.5B-Instruct · MBPP · custom test-execution reward커스텀 테스트실행 보상 · 2 GCD

2026-06-14 · updated갱신 2026-06-16

One-line summary. Code RL where the reward is no longer "rule matching" but the result of running unit tests. The model solves MBPP problems, its written code is run in a subprocess, and the reward is 1 if the tests pass. Ran 4 steps to completion on MI250, with 0.5B actually writing some passing code (score max 1.0). Key finding: the test-execution reward becomes a real cost taking up 14–24% of a step — the exact opposite of A's rule reward being ≈0. We confirmed by the clock that "the moment the reward becomes an external execution, the reward stage is a first-class cost".한 줄 요약. 보상을 "규칙 일치"가 아니라 유닛테스트 실행 결과로 바꾼 코드 RL. MBPP 문제를 풀게 하고, 모델이 쓴 코드를 서브프로세스로 실행해 테스트가 통과하면 보상 1. MI250에서 4스텝 완주, 0.5B가 일부 통과 코드를 실제로 작성(score max 1.0). 핵심 발견: 테스트실행 보상이 스텝의 14~24%를 차지하는 실재 비용이 된다 — A의 규칙 보상이 ≈0이던 것과 정반대. "보상이 외부 실행이 되는 순간 reward 단계가 1급 비용"이라는 걸 시간으로 확인했다.

1. Goal — when the test becomes the reward1. 목표 — 테스트가 보상이 될 때

In A (math), the reward was "integer answer match", so it was almost free. Code is different — to know whether an answer is correct you have to actually run the code and execute the tests. This is the archetype of RLVR (RL with verifiable rewards), and the first case where the reward has a compute cost.A(수학)에선 보상이 "정수 정답 일치"라 거의 공짜였다. 코드는 다르다 — 정답인지 알려면 코드를 실제로 실행해 테스트를 돌려봐야 한다. 이건 RLVR(검증가능 보상 RL)의 전형이자, 보상이 처음으로 계산 비용을 갖는 사례다.

Measurement goals: (a) does 0.5B write code that passes the tests, (b) what share of step time the test-execution reward takes — how different is it from A's rule reward (≈0).측정 목표: (a) 0.5B가 테스트를 통과하는 코드를 쓰는가, (b) 테스트실행 보상이 단계 시간에서 차지하는 비중 — A의 규칙 보상(≈0)과 얼마나 다른가.

Single-turn vs multi-turn. The ideal code agent is multi-turn: "write→test→report failure→fix". But as we saw in A, an untrained 0.5B barely uses tools (intermediate tests). So here we settled on single-turn generation + test-execution reward — because the measurement core is "the cost when the test becomes the reward" rather than multi-turn itself. A multi-turn self-debug version presupposes SFT warmup (same as A's conclusion).단일턴 vs 멀티턴. 이상적 코드 에이전트는 "작성→테스트→실패 보고→수정"의 멀티턴이다. 하지만 A에서 봤듯 미학습 0.5B는 도구(중간 테스트)를 거의 안 쓴다. 그래서 여기선 단일턴 생성 + 테스트실행 보상으로 잡았다 — 멀티턴 자체보다 "테스트가 보상이 될 때의 비용"이 측정 핵심이기 때문. 멀티턴 self-debug 버전은 SFT 워밍업이 전제(A의 결론과 동일).

2. Setup — MBPP · custom test-execution reward2. 구성 — MBPP · 커스텀 테스트실행 보상

verl's built-in code reward prime_code only accepts APPS-style stdin/stdout tests, which don't match MBPP's assert style. So we used a custom reward function (custom_reward_function) — verl calls compute_score(data_source, solution_str, ground_truth, extra_info) for each response.verl 내장 코드 보상 prime_code는 APPS식 stdin/stdout 테스트만 받아 MBPP의 assert 스타일과 안 맞는다. 그래서 커스텀 보상 함수(custom_reward_function)를 썼다 — verl이 매 응답에 compute_score(data_source, solution_str, ground_truth, extra_info)를 호출한다.

# reward_code.py — 모델 코드 + 테스트를 서브프로세스로 실행 (6s timeout)
def compute_score(data_source, solution_str, ground_truth, extra_info=None):
    gt = json.loads(ground_truth)                 # {"tests":[assert...], "setup":...}
    code = _extract(solution_str)                 # ```python ...``` 블록 추출
    prog = gt["setup"] + "\n" + code + "\n" + "\n".join(gt["tests"])
    p = subprocess.run([sys.executable, tmpfile], capture_output=True, timeout=6)
    return 1.0 if p.returncode == 0 else 0.0      # 테스트 전부 통과 = 1

Preprocessed MBPP (374 train / 500 test) into verl parquet — the prompt asks for "a self-contained function in a ```python``` block", ground_truth=test asserts (+setup). Model Qwen2.5-0.5B, GRPO, n=8, batch 16, 4 steps, 2 GCD, vLLM async.MBPP(374 train / 500 test)를 verl parquet으로 전처리 — 프롬프트는 "자기완결 함수를 ```python``` 블록으로", ground_truth=테스트 asserts(+setup). 모델 Qwen2.5-0.5B, GRPO, n=8, batch 16, 4스텝, 2 GCD, vLLM async.

Safety. Since model-generated code is executed, isolation is needed — this experiment was confined to inside a Docker container + a 6s timeout on the shared node. Production requires a dedicated sandbox (seccomp / network blocking).안전. 모델이 생성한 코드를 실행하므로 격리 필요 — 본 실험은 공유 노드의 Docker 컨테이너 안 + 6초 timeout으로 한정. 실제 운영은 전용 샌드박스(seccomp/네트워크 차단)가 필수.

Key — the verifier is the cost. A's gsm8k rule scoring is timing_s/reward≈0. B is the same loop, but changing only the reward to "test execution" gave 1.4–2.3s (14–24%). And it fluctuates per step (step2 2.35s vs step4 1.44s) — the longer failing code hangs until timeout, the slower the reward. With large/heavy tests, reward can become a bottleneck rivaling gen → verifier parallelization and an isolated sandbox pool are the real-world tasks.핵심 — 검증기(verifier)가 비용이다. A의 gsm8k 규칙 채점은 timing_s/reward≈0. B는 같은 루프인데 보상만 "테스트 실행"으로 바꿨더니 1.4~2.3s(14~24%). 게다가 스텝마다 출렁인다(step2 2.35s vs step4 1.44s) — 실패하는 코드가 timeout까지 매달릴수록 보상이 느려진다. 대규모/무거운 테스트면 reward 가 gen 과 맞먹는 병목이 될 수 있다 → verifier 병렬화·격리 샌드박스 풀이 실전 과제.

0.5B actually solves some. At step 4, critic/score/max=1.0, rewards mean 0.047 — even an untrained 0.5B solved some MBPP with passing tests (direct code generation seems easier for 0.5B than math tool use). Response length ~297 tokens.0.5B가 실제로 푼다. step 4에서 critic/score/max=1.0, rewards 평균 0.047 — 미학습 0.5B도 일부 MBPP를 테스트 통과로 풀었다(수학 도구 사용보다 코드 직생성이 0.5B엔 더 쉬운 듯). 응답 길이 ~297 토큰.

4. Conclusion + next (C)4. 결론 + 다음(C)

  1. Test-execution reward RLVR works on MI250 — MBPP, custom reward, 4 steps, some passing (score 1.0).테스트실행 보상 RLVR이 MI250에서 작동 — MBPP, 커스텀 reward, 4스텝, 일부 통과(score 1.0).
  2. When the reward becomes an external execution, the reward stage is a first-class cost (0 → 14–24%), and it fluctuates more as failure-timeouts increase. Contrast with A where it was ≈0.보상이 외부 실행이 되면 reward 단계가 1급 비용(0 → 14~24%)이고, 실패-timeout이 많을수록 더 출렁인다. A에서 ≈0이던 것과 대비.
  3. Stage landscape: gen 37% / update_actor 26% / reward 14% / weight-sync 14% / ref 11% — spread across four branches: gen·train·reward·sync.단계 지형: gen 37% / update_actor 26% / reward 14% / weight-sync 14% / ref 11% — gen·train·reward·sync 네 갈래로 분산.

Next (C — search agent): the reward goes back to a lightweight EM (answer match), but the tool becomes a retriever (search). A case where the tool call is external I/O (search latency), so the cost lands on the rollout side — contrasting with B (cost on the reward side).다음(C — 검색 에이전트): 보상은 다시 가벼운 EM(정답 일치)로 돌아가되, 도구가 검색(retriever)이 된다. 도구 호출이 외부 I/O(검색 지연)라 rollout 쪽에 비용이 실리는 사례 — B(보상 쪽 비용)와 대비된다.
