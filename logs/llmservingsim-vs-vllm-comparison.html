1. 왜 이 비교가 의미 있나

LLMServingSim은 "프로파일 1회 + sim 영원히 무료" 아키텍처 (자세한 건 Frontier 노트 §3-1). 핵심 가정:

  • vLLM이 측정한 op latency CSV를 룩업으로 재사용
  • 스케줄링/큐잉/comm은 시뮬레이터가 자체 모델로 처리

이 가정이 얼마나 잘 맞는지 검증하려면 실제 vLLM 측정값과 시뮬레이터 예측값을 같은 워크로드에 대해 직접 비교해야 함. LLMServingSim 논문은 sim 오차 <10% 클레임하지만 그건 그쪽 검증 셋. 우리 케이스에서도 그런지가 진짜 질문.

비교 결과로 얻고 싶은 것:

  • 절대 오차: TTFT / TPOT / latency p50/p95/p99 의 실측 vs 예측 (% 단위)
  • 발산 패턴: 어떤 요청에서 가장 많이 빗나가는가 (긴 input? 높은 concurrency? KV 압박 구간?)
  • 실용성 판단: 시뮬 결과를 어디까지 신뢰할 수 있나 — 절대값? 상대 비교? 트렌드만?

4. Option B — RTXPRO6000이 아닌 GPU로 가는 길

shipped 프로파일이 RTXPRO6000 1종밖에 없는데, 실제로 잡히는 GPU는 보통 H100 또는 A100. 이 경우 그 GPU용 프로파일을 한 번 새로 만들고, cluster config의 hardware 라벨을 그 새 라벨로 바꾸면 됨. 한 번만 하면 그 (HW, model) 조합으로는 영원히 무료 sim.

아래는 H100을 예시로 한 완전 워크플로. 다른 GPU도 동일한 흐름이며 HARDWARE 라벨과 cluster config의 mem_size/mem_bw만 그 GPU 사양으로 바꾸면 됨.

4-1. 시간 + 비용 추정

케이스대략 시간클라우드 spot 비용
Llama-3.1-8B × H100 × TP=1 (skew 포함)~25–45 분~$1.5 (H100 spot ~$2/h)
Llama-3.1-8B × H100 × TP=1 (SKIP_SKEW=1)~10–20 분~$0.7
Llama-3.1-8B × H100 × TP=1,2,4 (full)~1.5–2 h (TP=4면 4장 필요)~$3-12

본 비교는 TP=1만 필요 (single-GPU vLLM 서빙) → 25-45분 + 약 $1.5면 충분.

4-2. 준비된 아티팩트 (이 레포 안에)

유저가 GPU 확보하면 바로 쓸 수 있게 아래 두 파일을 미리 만들어둠:

파일역할
tools/run_profile_h100.shvLLM 컨테이너 안에서 실행할 wrapper. profile.sh의 MODEL/HARDWARE/TP_DEGREES 만 H100/Llama-3.1-8B/TP=1로 오버라이드한 후 실행, 결과 smoke-test까지 자동.
data/llmservingsim-vs-vllm/cluster_llama8b_h100.json프로파일 끝난 직후 LLMServingSim의 configs/cluster/에 복사할 cluster config. H100 SXM5 80GB 사양 (mem_size=80, mem_bw=3350) 반영.

4-4. 결과 비교 (RTXPRO6000 → H100 예측 변화)

같은 워크로드를 두 HW에 대해 sim 비교 가능 — H100이 빠를 거라 예상:

  • H100 SXM5는 3350 GB/s, RTX PRO 6000은 1597 GB/s — 메모리 대역폭 약 2.1× → decode TPOT이 약 절반 (~16-17ms 예상)
  • FLOPS도 더 큼 → prefill 처리율 향상 → TTFT 분포 좌측 이동
  • Throughput 4.57 req/s → 약 8-9 req/s 예상 (10 sps 도착률을 거의 따라잡음)

실제로 그렇게 나오는지가 부차 검증 포인트. 그 후에 실 vLLM 측 (§5) 비교가 본진.

5. 실 vLLM 측 (진행 중)

4-1. JSONL replay 클라이언트

일반 LMeterX는 random prompt를 던지는 방식이라 JSONL의 정확한 arrival timing 재생 못 함. 그래서 전용 replay 스크립트 작성: tools/replay_jsonl.py (이 레포에 같이 커밋).

역할:

  • JSONL을 한 줄씩 읽음
  • input_tok_ids → 토크나이저로 디토큰화 → prompt 문자열
  • arrival_time_ns 만큼 기다린 후 vLLM /v1/completions 에 stream 요청 발사
  • per-token 응답으로 TTFT / ITL / TPOT 측정
  • LLMServingSim CSV와 동일한 12 컬럼 스키마로 결과 저장 → 직접 diff 가능

4-2. vLLM 서빙 명령

# GPU 머신에서
docker run --gpus all --rm -p 8000:8000 \
  -e HF_TOKEN=$HF_TOKEN \
  vllm/vllm-openai:latest \
    --model meta-llama/Llama-3.1-8B \
    --dtype bfloat16 \
    --block-size 16 \
    --tensor-parallel-size 1 \
    --max-model-len 4096

4-3. Replay 실행

python tools/replay_jsonl.py \
  --workload ~/LLMServingSim/workloads/sharegpt-llama-3.1-8b-300-sps10.jsonl \
  --endpoint http://<gpu-host>:8000/v1/completions \
  --model meta-llama/Llama-3.1-8B \
  --output outputs/llama8b_real_300.csv \
  --tokenizer meta-llama/Llama-3.1-8B

6. 비교 메트릭 정의

두 CSV가 같은 스키마이므로 request_id로 1:1 매칭 후 메트릭별 비교:

메트릭정의판단 기준
per-request TTFT 오차|sim - real| / real중앙값 < 15% 이면 sim 신뢰 가능
per-request TPOT 오차동일중앙값 < 10% 이면 좋음
per-request latency 오차동일TTFT + TPOT × N 의 누적 — 분산 큼
throughput (전체)req/s 단위 비교±5% 이내면 시뮬이 정상
p95/p99 latency분포의 꼬리 비교여기서 큰 차이 나면 큐잉/eviction 모델이 부정확
발산 요청 분석오차 상위 10개 요청의 (input_len, output_len, arrival_time) 패턴긴 input? 혼잡 시점? 특정 KV size?

비교 스크립트 (tools/compare_csv.py) 가 위 표 자동 출력 + matplotlib으로 scatter plot 2개 (TTFT sim vs real, TPOT sim vs real) 생성. 다음 푸시에 포함 예정.
