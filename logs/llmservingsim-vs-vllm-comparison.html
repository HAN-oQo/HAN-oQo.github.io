1. Why this comparison matters1. 왜 이 비교가 의미 있나

LLMServingSim is a "profile once + sim forever for free" architecture (details in Frontier note §3-1). Core assumptions:LLMServingSim은 "프로파일 1회 + sim 영원히 무료" 아키텍처 (자세한 건 Frontier 노트 §3-1). 핵심 가정:

  • Reuse the op latency CSV measured by vLLM as a lookupvLLM이 측정한 op latency CSV를 룩업으로 재사용
  • Scheduling / queuing / comm are handled by the simulator's own model스케줄링/큐잉/comm은 시뮬레이터가 자체 모델로 처리

To verify how well this holds, you have to directly compare actual vLLM measurements with the simulator's predictions on the same workload. The LLMServingSim paper claims sim error <10%, but that is their own validation set. Whether it holds in our case is the real question.이 가정이 얼마나 잘 맞는지 검증하려면 실제 vLLM 측정값과 시뮬레이터 예측값을 같은 워크로드에 대해 직접 비교해야 함. LLMServingSim 논문은 sim 오차 <10% 클레임하지만 그건 그쪽 검증 셋. 우리 케이스에서도 그런지가 진짜 질문.

What we want from the comparison:비교 결과로 얻고 싶은 것:

  • Absolute error: measured vs predicted TTFT / TPOT / latency p50/p95/p99 (in %)절대 오차: TTFT / TPOT / latency p50/p95/p99 의 실측 vs 예측 (% 단위)
  • Divergence patterns: which requests miss the most (long input? high concurrency? KV-pressure regions?)발산 패턴: 어떤 요청에서 가장 많이 빗나가는가 (긴 input? 높은 concurrency? KV 압박 구간?)
  • Practical judgment: how far can we trust the sim results — absolute values? relative comparisons? trends only?실용성 판단: 시뮬 결과를 어디까지 신뢰할 수 있나 — 절대값? 상대 비교? 트렌드만?

4. Option B — Path for GPUs other than RTXPRO60004. Option B — RTXPRO6000이 아닌 GPU로 가는 길

The shipped profile only has one HW (RTXPRO6000), but the GPU you actually get is usually H100 or A100. In that case, build a new profile for that GPU once, swap the hardware label in the cluster config to that new label, and you're done. Do it once, and that (HW, model) pair gives you free sim forever after.shipped 프로파일이 RTXPRO6000 1종밖에 없는데, 실제로 잡히는 GPU는 보통 H100 또는 A100. 이 경우 그 GPU용 프로파일을 한 번 새로 만들고, cluster config의 hardware 라벨을 그 새 라벨로 바꾸면 됨. 한 번만 하면 그 (HW, model) 조합으로는 영원히 무료 sim.

Below is a full workflow using H100 as an example. The flow is the same for other GPUs — just change the HARDWARE label and the mem_size/mem_bw in the cluster config to match that GPU's spec.아래는 H100을 예시로 한 완전 워크플로. 다른 GPU도 동일한 흐름이며 HARDWARE 라벨과 cluster config의 mem_size/mem_bw만 그 GPU 사양으로 바꾸면 됨.

4-4. Result comparison (RTXPRO6000 → H100 prediction shift)4-4. 결과 비교 (RTXPRO6000 → H100 예측 변화)

You can sim-compare the same workload across two HWs — expect H100 to be faster:같은 워크로드를 두 HW에 대해 sim 비교 가능 — H100이 빠를 거라 예상:

  • H100 SXM5 is 3350 GB/s, RTX PRO 6000 is 1597 GB/s — about 2.1× the memory bandwidth → decode TPOT roughly halves (~16-17 ms expected)H100 SXM5는 3350 GB/s, RTX PRO 6000은 1597 GB/s — 메모리 대역폭 약 2.1× → decode TPOT이 약 절반 (~16-17ms 예상)
  • FLOPS are also higher → prefill throughput up → TTFT distribution shifts leftFLOPS도 더 큼 → prefill 처리율 향상 → TTFT 분포 좌측 이동
  • Throughput 4.57 req/s → about 8-9 req/s expected (nearly catches up with the 10 sps arrival rate)Throughput 4.57 req/s → 약 8-9 req/s 예상 (10 sps 도착률을 거의 따라잡음)

Whether it actually comes out that way is a secondary check. After that, the real vLLM comparison (§5) is the main event.실제로 그렇게 나오는지가 부차 검증 포인트. 그 후에 실 vLLM 측 (§5) 비교가 본진.

4-1. JSONL replay client4-1. JSONL replay 클라이언트

Regular LMeterX throws random prompts, so it can't reproduce the JSONL's exact arrival timing. So we wrote a dedicated replay script: tools/replay_jsonl.py (committed alongside in this repo).일반 LMeterX는 random prompt를 던지는 방식이라 JSONL의 정확한 arrival timing 재생 못 함. 그래서 전용 replay 스크립트 작성: tools/replay_jsonl.py (이 레포에 같이 커밋).

What it does:역할:

  • Reads the JSONL line by lineJSONL을 한 줄씩 읽음
  • input_tok_ids → detokenize → prompt stringinput_tok_ids → 토크나이저로 디토큰화 → prompt 문자열
  • Wait arrival_time_ns then fire a streaming request at vLLM /v1/completionsarrival_time_ns 만큼 기다린 후 vLLM /v1/completions 에 stream 요청 발사
  • Measure TTFT / ITL / TPOT from the per-token responseper-token 응답으로 TTFT / ITL / TPOT 측정
  • Save results with the same 12-column schema as LLMServingSim CSV → direct diff possibleLLMServingSim CSV와 동일한 12 컬럼 스키마로 결과 저장 → 직접 diff 가능
