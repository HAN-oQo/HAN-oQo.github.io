1Bootstrap — kind cluster + Argo CD부트스트랩 — kind 클러스터 + ArgoCD

Date: 2026-06-12 · Node: mi250-052 · Status: ✓ DONE · Result: Argo CD v3.4.3 on kind v0.32 (K8s v1.36.1), root-free, ~1m51s작성일: 2026-06-12 · 노드: mi250-052 · 상태: ✓ 완료 · 결과: kind v0.32(K8s v1.36.1) 위 ArgoCD v3.4.3, root 없이 약 1분 51초

Goal of this phase이 단계 목표
Stand up a throwaway Kubernetes cluster and an Argo CD control plane on a shared GPU node — without root, without touching the host — so the rest of the series has somewhere to run. Concept learned: the Argo CD control-plane components and the install gotcha. 공유 GPU 노드에 일회용 Kubernetes 클러스터와 ArgoCD 컨트롤플레인을 — root 없이, 호스트 안 건드리고 — 띄워서 시리즈 나머지가 돌 곳을 만든다. 배운 개념: ArgoCD 컨트롤플레인 구성요소 + 설치 함정.

Why kind (Kubernetes-in-Docker) and not kubeadm/k3s: this is a shared node with no passwordless sudo, and the house rule is "Docker-only, don't mutate the host." kind runs each K8s node as a Docker container, so the whole cluster is root-free and disappears with one command. Full rationale is in the series overview §3. kind(Kubernetes-in-Docker)를 쓰고 kubeadm/k3s를 안 쓴 이유: passwordless sudo 없는 공유 노드이고 "Docker 전용, 호스트 건드리지 말 것" 규칙이 있어서다. kind은 각 K8s 노드를 Docker 컨테이너로 띄워 클러스터 전체가 root 불필요하고 명령 한 줄로 사라진다. 자세한 근거는 시리즈 개요 §3.

Real gotcha — the ApplicationSet CRD didn't install실전 함정 — ApplicationSet CRD가 설치 안 됨
The CustomResourceDefinition "applicationsets.argoproj.io" is invalid:
  metadata.annotations: Too long: may not be more than 262144 bytes
$ kubectl get crd applicationsets.argoproj.io
Error from server (NotFound): ... not found     # ← silently missing
Client-side kubectl apply stamps a last-applied-configuration annotation on each object; the ApplicationSet CRD is large enough that this annotation exceeds Kubernetes' 256 KiB limit, so that one resource fails while everything else succeeds. Fix = server-side apply (no such annotation): 클라이언트 측 kubectl apply는 각 객체에 last-applied-configuration 어노테이션을 박는데, ApplicationSet CRD가 커서 그게 256 KiB 한도를 넘긴다. 그 리소스 하나만 실패하고 나머진 성공. 해결 = server-side apply(그 어노테이션 없음): 
$ kubectl apply --server-side=true --force-conflicts -n argocd -f .../install.yaml
$ kubectl get crd | grep argoproj
applications.argoproj.io       ...    applicationsets.argoproj.io  ✓    appprojects.argoproj.io  ...
Carried into the lab: the reproduce block below uses --server-side from the start, so you never hit this. 실습에 반영: 아래 재현 블록은 처음부터 --server-side라 이 함정을 안 밟는다.

Reproduce from scratch처음부터 재현

Any Linux host with Docker (your user in the docker group). No root, no system packages — only ~/bin + containers.Docker 있는 Linux 호스트면 됨(사용자가 docker 그룹). root·시스템 패키지 없음 — ~/bin + 컨테이너만.

set -euo pipefail
mkdir -p ~/bin && export PATH="$HOME/bin:$PATH"
curl -fLo ~/bin/kind    https://kind.sigs.k8s.io/dl/v0.32.0/kind-linux-amd64      && chmod +x ~/bin/kind
curl -fLo ~/bin/kubectl https://dl.k8s.io/release/v1.36.2/bin/linux/amd64/kubectl && chmod +x ~/bin/kubectl

kind get clusters | grep -qx gitops-lab || kind create cluster --name gitops-lab --wait 180s

kubectl create namespace argocd --dry-run=client -o yaml | kubectl apply -f -
kubectl apply --server-side=true --force-conflicts -n argocd \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl -n argocd rollout status deploy/argocd-server --timeout=420s

# verify + UI access
kubectl get crd | grep argoproj          # applications / applicationsets / appprojects
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d; echo
kubectl -n argocd port-forward svc/argocd-server 8080:443   # ssh -L 8080:localhost:8080 <node> → https://localhost:8080

# teardown (zero host footprint)
# kind delete cluster --name gitops-lab
