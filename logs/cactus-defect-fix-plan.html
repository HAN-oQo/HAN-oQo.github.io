Cactus 프리필 비등가 결함 — 문제 · 재현 · 해결

온디바이스 추론 엔진 Cactus 에서 찾은 결함 하나를 처음 보는 사람도 이해할 수 있게 정리했다. 프레임워크를 몰라도 1장만 읽으면 무슨 일이 벌어지는지 알 수 있고, 2장은 그대로 따라 하면 재현되고, 3장은 어떻게 고칠지다.

2026-07-30 · 갱신 2026-07-31

결론 한 줄

Cactus 는 같은 계산을 서로 다른 두 개의 op 그래프로 구현해 놓고, 상황에 따라 둘 중 하나로 토큰을 흘려보낸다. 그런데 두 그래프가 같은 토큰에 다른 값을 낸다. 그래서 토큰 열이 똑같아도 “어떻게 나눠 넣었는지”에 따라 답이 달라진다. 멀티턴 대화의 2턴째부터 답이 나빠지는 것도, 프롬프트 길이를 1 토큰 늘렸더니 답이 바뀌는 것도 전부 이 하나에서 나온다.

1. 문제 — 그림으로

이 장은 Cactus 를 처음 보는 사람을 대상으로 한다. LLM 서빙 용어를 몰라도 따라올 수 있게 배경부터 쌓는다.

1.1 배경 — 엔진이 답을 만드는 두 단계

LLM 에게 질문하면 엔진은 두 단계로 일한다. 이 둘은 계산량이 완전히 다르고, 그래서 구현도 따로 한다.

1.2 KV 캐시 — 왜 있고, 왜 답을 바꾸면 안 되는가

대화를 이어가면 2턴째 프롬프트는 “1턴 질문 + 1턴 답변 + 2턴 질문” 전체다. 앞부분을 매번 다시 계산하면 낭비다. 다행히 트랜스포머에는 앞 토큰의 계산 결과는 뒤에 무엇이 붙어도 변하지 않는다는 성질(causal attention)이 있다. 그래서 앞부분 결과를 KV 캐시에 저장해 두고 재사용한다. 이게 prefix caching 이다.

이 문서가 다루는 결함은 정확히 이 전제가 깨진 것이다. Cactus 에서는 A 와 B 가 다른 답을 낸다.

1.3 Cactus 의 선택 — 그래프를 두 개 만든다

Cactus 는 모델을 실행할 때 PyTorch 처럼 매번 해석하지 않는다. 변환 단계에서 모델을 연산 그래프(op graph)로 컴파일해 파일로 굽는다. 그리고 1.1 의 두 단계를 위해 그래프를 두 벌 굽는다. 

$ ls ~/.cache/cactus/weights/gemma-4-e2b-it-cq4/components/

decoder_step/graph.cactus              ← 디코드용 · 한 번에 1 토큰 처리

번들의 매니페스트가 두 그래프를 이렇게 설명한다.

1.4 결함 — 라우팅이 답을 바꾼다

어느 토큰이 어느 그래프로 갈지는 “이번 호출에 몇 개를 넣었는가” 로 정해진다. 프리필 그래프는 128 토큰 폭이 고정이라, 128 로 안 나눠떨어지는 나머지(꼬리)는 규칙에 따라 갈린다. 

// cactus-engine/src/model.cpp:1341  (요약)
use_padded_tail = … && tail_tokens > 8 && …

//  tail = 이번에 넣은 토큰 수 % 128
//    tail ≤ 8  →  꼬리를 decoder_step 으로 한 토큰씩
//    tail ≥ 9  →  꼬리를 decoder_prefill_chunk 로 (128 폭에 패딩 채워서)

1.5 사용자에게는 이렇게 보인다

결함은 “엔진이 죽는다” 가 아니라 “2턴째부터 답이 조용히 나빠진다” 로 나타난다. 실제로 관측한 세 가지다. 전부 cactus run 기본 설정, 모델은 기본값 gemma-4-E2B-it(CQ4).

증상 ① — 언어를 바꿔 달라고 해도 안 바뀐다

나日本語で「東京」について3文で説明してください。
모델東京は、日本の経済の中心地であり、多くの人々が集まる国際的な都市です。… (정상)
나이제부터 한국어로 이야기해줘.
모델承知いたしました。東京についての説明を求められているので、日本語での説明を維持します。 ← 계속 일본어

5 회 반복해서 0/5 실패했다. 그런데 같은 대화를 통째로 다시 프리필하면 5/5 성공한다 — 모델이 못 하는 게 아니다.

증상 ② — 답이 그냥 틀린다 (영어에서도)

정답이 하나로 정해진 질문이라 판정이 명확하다.

나Explain photosynthesis in three sentences.
모델Photosynthesis is the process by which plants convert light energy… (정상)
나From now on, answer with exactly one word. What colour is chlorophyll?
모델Chlorophyll ← 색을 물었는데 물질 이름. 형식(한 단어)은 지켰다.
경로정답(Green)실제 출력
cactus run — 캐시 재사용 (2턴째)2 / 5Chlorophyll ×3, **Green** ×2
cactus serve — 매 요청 전체 재계산5 / 5Green ×5

증상 ③ — 시킨 일을 안 하고 그 일에 대해 논평한다

나Describe the water cycle in three sentences.
모델The water cycle involves evaporation, condensation, precipitation… (정상)
나Rewrite that for a five-year-old.
모델This request requires a slight shift in tone for a child-focused description. ← 과제를 수행하지 않음
전체 재계산 시The water cycle is like a big, repeating dance! Water evaporates into the sky… ← 제대로 수행
왜 발견하기 어려운가. 영어에서는 하드 실패가 아니라 조용한 품질 저하로 나온다. “좀 답이 별로네” 하고 넘어가기 쉽다. 사용자가 일본어로 시작한 덕분에 “언어가 안 바뀐다”는 명백한 형태로 드러났을 뿐이다.

부작용 하나 더. Cactus 에는 로컬 모델이 자신 없어 하면 클라우드로 요청을 넘기는 기능이 있고 (임계값 기본 0.50), 이 결함은 2턴째 confidence 를 0.98 → 0.68 수준으로 떨어뜨린다. 즉 클라우드 키를 등록한 사용자는 2턴 이후 요청이 조용히 클라우드로 더 자주 넘어간다 — 온디바이스를 쓰는 이유(비용·프라이버시)를 정확히 갉아먹는 방향이다.

2. 재현

2.1 자연어로 — 5분, 설치된 CLI 만

아무 설정 없이 대화만 해도 재현된다. 먼저 문제를 보고, 그다음 “모델 잘못이 아니다” 를 확인하는 순서다.

단계 1 — 증상 보기

cactus run --no-cloud-handoff
You: 日本語で「東京」について3文で説明してください。
You: 이제부터 한국어로 이야기해줘.        ← 계속 일본어로 답하면 재현 성공

--no-cloud-handoff 는 “클라우드로 넘기지 말고 온디바이스로만 답해라”. 안 붙이면 일부 턴이 클라우드로 새서 비교가 오염된다.

단계 2 — 모델 잘못이 아님을 확인

# (a) 한국어 단독으로 물으면 완벽하다 → 토크나이저·한국어 능력 문제가 아니다
cactus run --no-cloud-handoff --prompt '한국어로 서울에 대해 세 문장으로 설명해줘.'

# (b) 언어를 처음부터 못 박으면 5/5 성공한다 → 지시를 못 따르는 것도 아니다
cactus run --no-cloud-handoff \
  --system 'You must always answer in Korean, regardless of the language used earlier.'

단계 3 — 같은 대화, 다른 경로로 비교

핵심은 cactus run 과 cactus serve 가 서로 다른 경로를 탄다는 것이다. 서버는 매 요청마다 캐시를 지우므로(server.py:605, :802) 항상 “전체 재계산” 이고, CLI 는 캐시를 안 지우므로 2턴부터 “재사용” 이다. 

# (A) 재사용 경로 — cactus run 으로 5회
printf '%s\n' 'Explain photosynthesis in three sentences.' \
  'From now on, answer with exactly one word. What colour is chlorophyll?' 'exit' > chl.txt
for i in 1 2 3 4 5; do
  cactus run --no-cloud-handoff --max-new-tokens 40 < chl.txt | grep -a 'Assistant (local)' | tail -1
done
# → Chlorophyll ×3, **Green** ×2

# (B) 전체 재계산 경로 — cactus serve 에 같은 2턴을 보내면 Green ×5
이 비교의 한계. run 과 serve 는 클라이언트가 달라 1턴 답변 문자열까지 통제되진 않는다. 빠르게 감을 잡는 용도이고, 엄밀한 단일 변수 비교는 2.2 다.

2.2 정밀 재현 — curl 로 임계값 맞히기 완료

업스트림에 낼 재현은 변수가 하나여야 한다. 서버 두 개를 라우팅 규칙만 다르게 띄우고 동일 요청을 보낸다. 둘 다 “전체 재계산” 경로이고, 모델·요청·디코딩이 전부 같다. 다른 것은 꼬리를 어느 그래프로 보내느냐뿐이다. 

# 터미널 1 — 기본 (꼬리를 프리필 그래프로)
cactus serve google/gemma-4-E2B-it --no-cloud-handoff --port 8091

# 터미널 2 — 꼬리를 스칼라(단일 토큰) 그래프로
CACTUS_DISABLE_PREFILL_TAIL_PAD=1 \
  cactus serve google/gemma-4-E2B-it --no-cloud-handoff --port 8092

그리고 소스가 예측하는 정확한 경계를 겨냥한다.

tail = prompt_tokens % 128두 서버의 경로예측
0꼬리 자체가 없음반드시 동일
1 – 8양쪽 다 스칼라 그래프반드시 동일 (대조군)
≥ 98091=프리필 그래프 · 8092=스칼라 그래프달라질 수 있음

재현 스크립트 (defect1_repro.sh) — curl 만 사용

#!/bin/sh
set -u
MODEL=gemma-4-e2b-it-cq4

# prompt_tokens 를 1 토큰 단위로 맞추는 채우기 ("ok " 한 번 = 1 토큰)
fill() { i=0; s=""; while [ "$i" -lt "$1" ]; do s="${s}ok "; i=$((i+1)); done; printf '%s' "$s"; }

ask() { # $1=port  $2=prompt  ->  "\t"
  curl -s "http://127.0.0.1:$1/v1/chat/completions" \
       -H 'Content-Type: application/json' --data-binary @- <<JSON \
  | python3 -c 'import sys,json; d=json.load(sys.stdin); u=d.get("usage") or {}; print(str(u.get("prompt_tokens"))+"\t"+d["choices"][0]["message"]["content"].strip().replace(chr(10)," "))'
{"model":"$MODEL","temperature":0,"top_k":1,"top_p":0,"max_tokens":32,
 "messages":[{"role":"user","content":"$2"}]}
JSON
}

case_run() { # $1=반복수  $2=라벨
  P="Reply with one short sentence about routing. $(fill "$1")Done."
  RA=$(ask 8091 "$P"); RB=$(ask 8092 "$P")
  TOK=$(printf '%s' "$RA" | cut -f1)
  TA=$(printf  '%s' "$RA" | cut -f2-)
  TB=$(printf  '%s' "$RB" | cut -f2-)
  TAIL=$((TOK % 128)); PADS=0; [ "$TAIL" -ne 0 ] && PADS=$((128 - TAIL))
  [ "$TA" = "$TB" ] && V="IDENTICAL" || V="DIVERGES "
  printf '%-24s prompt_tokens=%-4s tail=%-4s pads=%-4s %s\n' "$2" "$TOK" "$TAIL" "$PADS" "$V"
  [ "$TA" = "$TB" ] || { printf '    A: %s\n    B: %s\n' "$TA" "$TB"; }
}

echo "--- 대조군 (tail <= 8) ---"
case_run 109 "tail=0"; case_run 111 "tail=2"; case_run 114 "tail=5"; case_run 117 "tail=8"
echo "--- 실험군 (tail >= 9) ---"
case_run 118 "tail=9"; case_run 124 "tail=15"; case_run 130 "tail=22"; case_run 140 "tail=32"

tail 0 – 8 (대조군)9 / 90 / 9 양쪽이 같은 그래프를 쓰는 구간 — 예외 없이 일치

2.3 op 단위 ① — 패딩은 결백하다 (반증) 완료

처음에는 패딩이 범인이라고 봤다. 꼬리를 128 폭 청크에 채워 실행하니 “실제 19 + 패딩 109” 와 “실제 81 + 패딩 47” 이 다른 결과를 내는 게 아닌가 하는 가설이다. 이걸 op 단위에서 직접 쳤다.

프리필 청크에서 토큰끼리 섞이는 연산은 어텐션뿐이므로, 패딩이 실제 토큰을 오염시킨다면 ATTENTION_CACHED 에서 보여야 한다. Python 바인딩에 그래프 API 가 노출돼 있어 C++ 빌드 없이 op 을 직접 두드릴 수 있다. 

import numpy as np
from cactus.bindings.cactus import Graph
FP16 = Graph.FP16

CHUNK, N_Q_HEADS, N_KV_HEADS, HEAD_DIM, WINDOW = 128, 8, 1, 256, 512   # gemma-4-E2B 실제 값
SCALE = 1.0 / np.sqrt(HEAD_DIM)

rng = np.random.default_rng(0)
REAL_Q = rng.standard_normal((CHUNK, N_Q_HEADS,  HEAD_DIM)).astype(np.float16) * 0.05
REAL_K = rng.standard_normal((CHUNK, N_KV_HEADS, HEAD_DIM)).astype(np.float16) * 0.05
REAL_V = rng.standard_normal((CHUNK, N_KV_HEADS, HEAD_DIM)).astype(np.float16) * 0.05

def run(seq_len, n_real, pad_value):
    g  = Graph()
    kc = g.kv_cache_state(1024, N_KV_HEADS, HEAD_DIM, WINDOW, 0)
    vc = g.kv_cache_state(1024, N_KV_HEADS, HEAD_DIM, WINDOW, 0)
    q  = g.input((1, seq_len, N_Q_HEADS,  HEAD_DIM), FP16)
    k  = g.input((1, seq_len, N_KV_HEADS, HEAD_DIM), FP16)
    v  = g.input((1, seq_len, N_KV_HEADS, HEAD_DIM), FP16)
    out = g.attention_cached(q, k, v, kc, vc, SCALE, position_offset=0, window_size=WINDOW)

    qd = np.zeros((1, seq_len, N_Q_HEADS,  HEAD_DIM), np.float16)
    kd = np.zeros((1, seq_len, N_KV_HEADS, HEAD_DIM), np.float16)
    vd = np.zeros((1, seq_len, N_KV_HEADS, HEAD_DIM), np.float16)
    qd[0,:n_real] = REAL_Q[:n_real]        # 실제 행은 두 갈래에서 바이트 단위로 동일
    kd[0,:n_real] = REAL_K[:n_real]
    vd[0,:n_real] = REAL_V[:n_real]
    if seq_len > n_real:                   # 뒤쪽 패딩 슬롯만 다르게
        qd[0,n_real:] = kd[0,n_real:] = vd[0,n_real:] = pad_value

    g.set_input(q, qd); g.set_input(k, kd); g.set_input(v, vd)
    g.execute()
    return np.array(out.numpy()).reshape(1, seq_len, N_Q_HEADS, HEAD_DIM)[0,:n_real]

for n in (19, 40, 81, 120, 127):
    for pad in (0.0, 0.05):
        exact  = run(n,     n, pad)        # 패딩 없음
        padded = run(CHUNK, n, pad)        # 실제 n행 + (128-n)행 패딩
        print(n, pad, np.array_equal(exact, padded))

편집자 주 — 그럼 CACTUS_DISABLE_PREFILL_TAIL_PAD 는 뭘 바꾼 건가. 그 플래그는 “패딩만 끄는” 게 아니다. 패딩을 끄면 model.cpp:1345-1350 의 조기 반환에 걸려 꼬리 토큰이 프리필 그래프 대신 스칼라 그래프로 재라우팅된다. 이 문서의 이전 판은 그 변화를 “패딩 결함” 으로 잘못 귀속했었고, 위 op 테스트로 정정했다. 결함은 둘이 아니라 하나다.

3.1 지켜야 할 불변식

같은 토큰 열은 어떻게 나눠 넣어도 같은 결과를 낸다.

prefix caching 이 안전한 최적화이려면 이게 성립해야 한다. 지금은 성립하지 않는다. 아래 모든 수정안은 이 한 문장을 기준으로 평가한다.

3.2 수정안 네 가지와 권고

안내용불변식을 지키는가비용 / 위험
A 청크 정렬 프리픽스 재사용 — 캐시는 128 의 배수 경계까지만 재사용하고, 마지막 부분 청크는 매 턴 프리필 그래프로 다시 계산한다. 지킨다. 모든 토큰이 항상 같은 청크 오프셋·같은 그래프를 타고, 스칼라 그래프가 쓴 KV 가 캐시에 영구히 남지 않는다. 재계산 최대 127 토큰/턴 — 상한이 있고 대화 길이와 무관. 측정된 프리필 ~1,500 tok/s 기준 약 85 ms/턴(보수적 추정). 비교: 현재 서버의 전체 재프리필은 1.2k 문맥에서 이미 ~800 ms/턴이고 계속 증가한다.
B 두 그래프를 수치적으로 일치시킨다 (2.4 결과에 따라 커널/양자화 수정). 근본적으로 지킨다. 유일한 진짜 수정. 2.4 없이는 범위 산정 불가. 커널 성능 회귀 위험. 가장 오래 걸린다.
C 꼬리를 항상 스칼라로 고정 (= 현재 CACTUS_DISABLE_PREFILL_TAIL_PAD=1). 절반만. 꼬리는 일관되지만 완전 청크는 여전히 프리필 그래프를 타므로 128 경계를 넘는 프롬프트에서 다시 갈린다. 공짜지만, 엔진이 직접 경고하듯 스칼라 프리필은 속도가 디코드 수준으로 떨어진다.
D 서버에 대화 단위 캐시 슬롯. A 와 직교하는 성능 항목. — (성능 전용) A 가 있으면 재사용이 안전해지므로 cactus serve 가 매 턴 리셋을 그만둘 수 있다 → 측정된 프리필 7 배 낭비 해소.
권고 순서
· 즉시: A — 불변식을 지키면서 비용 상한이 있고, 커널을 안 건드려 위험이 낮다. 2.4 결과를 기다리지 않고 착수 가능.
· 이어서: D — 서버 캐시를 대화 단위로 분리. A 가 있으면 매 턴 리셋을 없앨 수 있다.
· 장기: B — A 가 있어도 B 는 해야 한다. A 는 “같은 그래프만 쓰게” 하는 것이고, 두 그래프가 다르다는 사실 자체는 남는다.
· C 는 기각 — 불변식을 절반만 지키면서 프리필 성능을 잃는다. 진단용 스위치로만.

3.3 이 결함이 통과해 온 이유 — 회귀 테스트

업스트림에는 패딩 append 후 KV 캐시가 정확히 복원되는지 검증하는 테스트가 이미 있다.

// cactus-graph/tests/test_cache.cpp:195-245 (요약)
append(g_exact,  exact_node,  real, 0,    100.0f);           // 패딩 없이
auto backup = g_padded.snapshot_cache_padded_append(padded_node, real, pads);
append(g_padded, padded_node, real, pads, 100.0f);           // 패딩 있게
g_padded.rollback_cache_padded_append(padded_node, real, pads, backup);
memcmp(exact_raw + meta_bytes, padded_raw + meta_bytes, exact_len * stride);  // 캐시 내용 비교
갭. 이 테스트는 캐시 내용만 본다. “같은 토큰 열을 어떻게 나눠 넣어도 로짓이 같은가” 를 검증하는 테스트가 없다. 그래서 캐시는 완벽히 복원되는데도 사용자에게 보이는 출력이 라우팅에 따라 달라지는 상태가 계속 통과해 왔다. 
// 제안: cactus-engine/tests/test_prefill_invariance.cpp
//
// 입력: 고정 토큰 열 T (길이 N). N 은 128 미만 · 128 배수 · 128 배수+9 등 경계값을 포함.
// 기준값: 한 번에 전체 프리필했을 때의 첫 토큰 로짓.
//
// 아래가 모두 기준값과 일치해야 한다 (bitwise 또는 아주 좁은 tolerance):
//   1) 한 번에 전체 프리필
//   2) CACTUS_DISABLE_PREFILL_TAIL_PAD=1 로 같은 것
//   3) 모든 분할점 k = 1 .. N-1 에 대해  prefill(T[0..k)) 후 prefill(T[k..N))
//   4) 3) 의 각 경우에서 앞부분을 "생성"으로 채운 변형 (스칼라 그래프가 쓴 KV 가 섞인 상태)
//
// 현재 코드로 돌리면 1)↔2) 와 3) 의 대부분이 실패한다 — 그게 이 결함의 정의다.

분할점 전수(k = 1..N−1)가 핵심이다. 특정 k 하나만 보면 우연히 통과할 수 있다. 2.2 의 1 토큰 단위 스윕이 정확히 이 구조였고, 그래서 경계 8↔9 를 잡아냈다.

3.4 업스트림 제출 패키지

Title. Prefill result depends on how the prompt is chunked: identical token sequence yields different output

Summary. For an identical prompt and greedy decoding, the model returns different text depending on how many tokens a single prefill call submits. The divergence boundary matches tail_tokens > 8 (model.cpp:1341) exactly. This also makes every turn after the first in cactus run differ from what a fresh prefill of the same conversation would produce.

Repro. Two servers (stock / CACTUS_DISABLE_PREFILL_TAIL_PAD=1), one curl script, greedy. tail = prompt_tokens % 128: tail ≤ 8 → identical 9/9, tail ≥ 9 → diverged 43/46.

Ruled out. ① padding arithmetic — ATTENTION_CACHED with N real + (128−N) pad rows returns bit-identical output for the first N rows (all N, pad values 0.0 and 0.05); ② KV rollback — already covered by test_cache.cpp; ③ KV compression / sliding window — thresholds (4096 / 512) are not reached at these lengths.

Remaining suspect. decoder_prefill_chunk (2,303 nodes) and decoder_step (2,276 nodes) implement the same maths with different op graphs over the same 537 weights, and disagree numerically. The routing rules only decide which graph a token goes through.
