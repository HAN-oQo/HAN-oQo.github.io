Cactus 프리필 비등가 결함 — 수정 계획과 실행

진단 문서(Cactus 언어 전환 실패 원인 분석)에서 찾은 결함을 고치기 위한 문서. 최소 재현을 curl 로 만들고, op 단위로 범위를 좁히고, 수정안을 비교한다.

2026-07-30

이 문서에서 바뀐 결론 (중요)

진단 문서 §7.3 은 결함을 두 개로 봤다 — ① 꼬리 패딩, ② 두 그래프의 수치 불일치. 이 문서의 Phase 1b(op 단위 테스트)가 ①을 반증했다.

  • ATTENTION_CACHED 에 실제 N행 + 패딩 (128−N)행을 넣어도 앞 N행 출력은 비트 단위로 동일하다 (N=19·40·81·120·127, 패딩값 0.0/0.05 전부). 즉 패딩 산술 자체는 결백하다.
  • CACTUS_DISABLE_PREFILL_TAIL_PAD=1 은 “패딩만 끄는” 플래그가 아니다. 패딩을 끄면 executable_tokens==0 && !use_padded_tail 조기 반환에 걸려 꼬리 토큰이 청크 그래프 대신 스칼라(단일 토큰) 그래프로 라우팅된다 (model.cpp:1345-1350). 그래서 그 플래그로 관측한 변화는 ①이 아니라 ②였다.
정정된 근본 원인 — 결함은 하나다.
배치 청크 그래프(decoder_prefill_chunk)와 단일 토큰 그래프(decoder_step)가 같은 토큰·같은 위치에 대해 다른 값을 낸다. 패딩·청크 경계·warm/cold 는 원인이 아니라 어떤 토큰이 어느 그래프로 가는지를 결정하는 라우팅 규칙일 뿐이다. 프리필 결과가 “한 번에 몇 개를 넣었는지”에 의존하는 이유도 이것이다 — 넣는 개수가 라우팅을 바꾸기 때문이다.

Phase 1 — curl 최소 재현 완료

설계

진단 문서의 실험은 Python 바인딩으로 cactus_reset() 을 토글했다. 업스트림에 제출하려면 설치된 CLI 와 curl 만으로 재현돼야 한다. 문제는 cactus serve 가 매 요청마다 캐시를 리셋해서 warm 경로를 아예 안 탄다는 것이다 — 그래서 warm/cold 를 비교할 수 없다.

대신 서버 두 개를 띄우고 라우팅 규칙만 다르게 한다. 둘 다 cold 경로이고, 모델·요청·디코딩이 전부 같다. 

# 터미널 1 — 기본
cactus serve google/gemma-4-E2B-it --no-cloud-handoff --port 8091

# 터미널 2 — 꼬리 토큰을 스칼라 그래프로 라우팅
CACTUS_DISABLE_PREFILL_TAIL_PAD=1 \
  cactus serve google/gemma-4-E2B-it --no-cloud-handoff --port 8092

그리고 코드가 예측하는 정확한 임계값을 겨냥한다. model.cpp:1341 의 조건은 tail_tokens > 8 이므로, tail = prompt_tokens % 128 에 대해:

tail두 서버의 경로예측
0양쪽 다 꼬리 청크 없음반드시 동일
1 – 8양쪽 다 use_padded_tail=false → 스칼라반드시 동일 (대조군)
≥ 98091=패딩 청크 · 8092=스칼라달라질 수 있음
이 설계가 좋은 이유. 임계값이 정확히 9에서 갈리면, 관측된 차이가 우연이나 샘플링이 아니라 소스의 그 한 줄에서 온다는 것이 증명된다. 8과 9 사이에서 모델이 달라질 이유는 그 조건문 말고 없다.

재현 코드 — 순수 curl (defect1_repro.sh)

#!/bin/sh
# Cactus 결함 최소 재현 — curl 만 사용. 위 두 서버를 먼저 띄울 것.
set -u
MODEL=gemma-4-e2b-it-cq4

# prompt_tokens 를 1 토큰 단위로 맞추기 위한 채우기 ("ok " 한 번 = 1 토큰)
fill() { i=0; s=""; while [ "$i" -lt "$1" ]; do s="${s}ok "; i=$((i+1)); done; printf '%s' "$s"; }

ask() { # $1=port  $2=prompt  ->  "\t"
  curl -s "http://127.0.0.1:$1/v1/chat/completions" \
       -H 'Content-Type: application/json' \
       --data-binary @- <<JSON | python3 -c 'import sys,json; d=json.load(sys.stdin); u=d.get("usage") or {}; print(str(u.get("prompt_tokens"))+"\t"+d["choices"][0]["message"]["content"].strip().replace(chr(10)," "))'
{"model":"$MODEL","temperature":0,"top_k":1,"top_p":0,"max_tokens":32,
 "messages":[{"role":"user","content":"$2"}]}
JSON
}

case_run() { # $1=반복수  $2=라벨
  P="Reply with one short sentence about routing. $(fill "$1")Done."
  RA=$(ask 8091 "$P"); RB=$(ask 8092 "$P")
  TOK=$(printf '%s' "$RA" | cut -f1)
  TA=$(printf '%s' "$RA" | cut -f2-)
  TB=$(printf '%s' "$RB" | cut -f2-)
  TAIL=$((TOK % 128)); PADS=0; [ "$TAIL" -ne 0 ] && PADS=$((128 - TAIL))
  if [ "$TA" = "$TB" ]; then V="IDENTICAL"; else V="DIVERGES "; fi
  printf '%-24s prompt_tokens=%-4s tail=%-4s pads=%-4s %s\n' "$2" "$TOK" "$TAIL" "$PADS" "$V"
  if [ "$TA" != "$TB" ]; then
    printf '    A stock  : %s\n' "$TA"
    printf '    B no-pad : %s\n' "$TB"
  fi
}

echo "--- 대조군 (tail <= 8, 같아야 정상) ---"
case_run 109 "tail=0 (128의 배수)"
case_run 111 "tail=2"
case_run 114 "tail=5"
case_run 117 "tail=8 (임계 직전)"
echo
echo "--- 실험군 (tail >= 9) ---"
case_run 118 "tail=9 (임계 직후)"
case_run 124 "tail=15"
case_run 130 "tail=22"
case_run 140 "tail=32"

Phase 1b — op 단위로 범위 좁히기 부분 완료

“패딩 때문”이라는 가설을 op 단위에서 직접 검증했다. 프리필 청크에서 크로스-토큰 연산은 어텐션뿐이므로, 패딩이 실제 토큰의 출력을 오염시킨다면 ATTENTION_CACHED 에서 보여야 한다.

테스트 코드 (defect1_op_level.py) — C++ 빌드 불필요

Python 바인딩에 그래프 API 가 노출돼 있어(Graph.kv_cache_state / attention_cached / Tensor.numpy()) 엔진을 통하지 않고 op 을 직접 두드릴 수 있다. 

import numpy as np
from cactus.bindings.cactus import Graph
FP16 = Graph.FP16

CHUNK, N_Q_HEADS, N_KV_HEADS, HEAD_DIM, WINDOW = 128, 8, 1, 256, 512   # gemma-4-E2B 실제 값
SCALE = 1.0 / np.sqrt(HEAD_DIM)

rng = np.random.default_rng(0)
REAL_Q = rng.standard_normal((CHUNK, N_Q_HEADS, HEAD_DIM)).astype(np.float16) * 0.05
REAL_K = rng.standard_normal((CHUNK, N_KV_HEADS, HEAD_DIM)).astype(np.float16) * 0.05
REAL_V = rng.standard_normal((CHUNK, N_KV_HEADS, HEAD_DIM)).astype(np.float16) * 0.05

def run(seq_len, n_real, pad_value):
    g  = Graph()
    kc = g.kv_cache_state(1024, N_KV_HEADS, HEAD_DIM, WINDOW, 0)
    vc = g.kv_cache_state(1024, N_KV_HEADS, HEAD_DIM, WINDOW, 0)
    q  = g.input((1, seq_len, N_Q_HEADS,  HEAD_DIM), FP16)
    k  = g.input((1, seq_len, N_KV_HEADS, HEAD_DIM), FP16)
    v  = g.input((1, seq_len, N_KV_HEADS, HEAD_DIM), FP16)
    out = g.attention_cached(q, k, v, kc, vc, SCALE, position_offset=0, window_size=WINDOW)

    qd = np.zeros((1, seq_len, N_Q_HEADS,  HEAD_DIM), np.float16)
    kd = np.zeros((1, seq_len, N_KV_HEADS, HEAD_DIM), np.float16)
    vd = np.zeros((1, seq_len, N_KV_HEADS, HEAD_DIM), np.float16)
    qd[0,:n_real] = REAL_Q[:n_real]      # 실제 행은 두 갈래에서 바이트 단위로 동일
    kd[0,:n_real] = REAL_K[:n_real]
    vd[0,:n_real] = REAL_V[:n_real]
    if seq_len > n_real:                 # 뒤쪽 패딩 슬롯만 다르게
        qd[0,n_real:] = kd[0,n_real:] = vd[0,n_real:] = pad_value

    g.set_input(q, qd); g.set_input(k, kd); g.set_input(v, vd)
    g.execute()
    return np.array(out.numpy()).reshape(1, seq_len, N_Q_HEADS, HEAD_DIM)[0,:n_real]

for n in (19, 40, 81, 120, 127):
    for pad in (0.0, 0.05):
        exact  = run(n,     n, pad)      # 패딩 없음
        padded = run(CHUNK, n, pad)      # 실제 n행 + (128-n)행 패딩
        print(n, pad, np.array_equal(exact, padded), np.abs(
              exact.astype(np.float32) - padded.astype(np.float32)).max())

Phase 1b 결론 (반증). 어텐션 op 의 causal 마스킹은 정확하다 — 패딩 행이 실제 행 출력에 전혀 영향을 주지 않는다. 따라서 “패딩 산술 오류”라는 가설은 폐기한다. 그리고 KV 캐시 롤백도 결백하다 — 업스트림 cactus-graph/tests/test_cache.cpp:195-245 가 패딩 append 후 캐시가 비패딩 append 와 비트 단위로 같음을 이미 검증하고 있고, 이 대화 길이(~100 토큰)는 슬라이딩 윈도우 512 안이라 롤백 자체가 no-op 에 가깝다.
남은 것. 이제 남은 단일 용의자는 두 그래프의 수치 불일치다. 두 그래프는 번들에 파일로 들어 있고 바인딩에 로더가 있으므로, Phase 2 에서 직접 대조할 수 있다.

Phase 2 — 두 그래프의 차이를 정밀 특정 계획

여기부터는 아직 실행하지 않았다. 순서와 각 단계의 판정 기준을 미리 정해 둔다.

단계할 일성공 판정 / 산출물
2.1 두 graph.cactus 를 Graph.load() 로 읽어 노드 op 시퀀스를 구조 diff. output_info() 로 각 노드의 shape/precision 도 같이 뽑는다. 한쪽에만 있는 op, 또는 같은 op 인데 precision·파라미터가 다른 지점 목록. 크기 차이(300,288 vs 314,957 bytes)의 정체가 여기서 드러난다.
2.2 동일 입력을 두 그래프에 통과시켜 최종 hidden state / 로짓을 비교. step 그래프는 seq=1, chunk 그래프는 실제 토큰으로 채운 완전한 128 청크를 쓰고 마지막 행을 비교한다 (패딩은 Phase 1b 에서 결백하므로 변수로 두지 않아도 된다). max|Δ| 가 0 이 아니면 결함 확정 — 그리고 그 크기가 뒤집기에 충분한지 평가.
2.3 레이어 이분 탐색: 중간 노드 출력을 Tensor.numpy() 로 받아 앞에서부터 비교, 처음 갈리는 노드를 찾는다. “노드 k 까지는 동일, k+1 에서 갈림” 형태의 단일 지점. 이게 있어야 수정 범위가 확정된다.
2.4 그 노드에서 후보 원인 확인 — ① 활성값 양자화 스케일 단위(per-tensor vs per-row/per-chunk), ② GEMM ↔ GEMV 누산 순서·정밀도, ③ INT8 반올림 모드, ④ RMSNorm/softmax 의 누산 dtype, ⑤ Metal ↔ CPU 백엔드 배치(tag_backend) 차이. 후보별로 “이 값을 맞추면 Δ 가 0 이 되는가” 를 하나씩 검증. 하나로 설명되지 않으면 복합 원인으로 기록.
2.5 Python API 로 부족하면 C++ 하네스. save_node() 로 텐서를 파일로 덤프할 수 있다. 선행 조건: brew install cmake (현재 이 머신에 cmake 없음 — 그래서 Phase 1b 를 Python 그래프 API 로 우회했다). cactus-graph 단독 빌드 성공 + tests/test_cache.cpp 옆에 새 테스트 추가 가능 상태.
백엔드 변수도 같이 통제할 것. CLI 와 서버 모두 --backend cpu|metal 을 받는다. Phase 2.2 를 cpu 와 metal 양쪽에서 돌려, 이 불일치가 Metal 커널 특정 문제인지 백엔드와 무관한 그래프 구조 문제인지 먼저 가른다. Phase 1 결과는 기본 백엔드에서만 얻은 것이다.

Phase 3 — 수정안 비교와 권고 계획

지켜야 할 불변식은 하나다 — “같은 토큰 열은 어떻게 나눠 넣어도 같은 결과를 낸다.” 이 기준으로 네 가지 안을 비교한다.

안내용불변식을 지키는가비용 / 위험
A 청크 정렬 프리픽스 재사용 — 캐시는 128 의 배수 경계까지만 재사용하고, 마지막 부분 청크는 매 턴 청크 그래프로 다시 계산한다. 지킨다. 모든 토큰이 항상 같은 청크 오프셋·같은 그래프를 타고, step 그래프가 쓴 KV 가 캐시에 영구히 남지 않는다. 재계산 최대 127 토큰/턴 = 상한 있음. 측정된 프리필 ~1,500 tok/s 기준 약 85 ms/턴, 대화 길이와 무관. 참고로 현재 서버의 전체 재프리필은 1.2k 문맥에서 이미 ~800 ms/턴이고 계속 증가한다.
B 두 그래프를 수치적으로 일치시킨다 (Phase 2 결과에 따라 커널/양자화 수정). 근본적으로 지킨다. Phase 2 없이는 범위 산정 불가. 커널 성능 회귀 위험. 유일한 진짜 수정이지만 가장 오래 걸린다.
C 라우팅을 한 그래프로 고정 — 꼬리를 항상 스칼라로 (= 현재 CACTUS_DISABLE_PREFILL_TAIL_PAD=1). 부분만. 꼬리는 일관되지만 완전 청크는 여전히 청크 그래프를 타므로 128 경계를 넘는 프롬프트에서 다시 갈린다 (§7.3 에서 P 가 4/6 에 그친 이유). 공짜. 다만 엔진이 직접 경고하듯 스칼라 프리필은 속도가 디코드 수준으로 떨어진다.
D 서버에 대화 단위 캐시 슬롯. A 와 직교하는 성능 항목. — A 와 합치면 cactus serve 가 매 턴 리셋을 그만둘 수 있다 → 앞서 측정한 프리필 7배 낭비 해소.
권고.
· 즉시(단기): A — 청크 정렬 재사용. 불변식을 지키면서 비용 상한이 있고, 커널을 건드리지 않아 위험이 낮다. Phase 2 결과를 기다리지 않고 착수할 수 있다.
· 이어서: D — 서버 캐시를 대화 단위로 분리. A 가 있으면 재사용이 안전해지므로 매 턴 리셋을 없앨 수 있다.
· 장기: B — Phase 2 로 지점을 특정한 뒤 두 그래프를 맞춘다. A 가 있어도 B 는 해야 한다 (A 는 “같은 그래프만 쓰게” 하는 것이고, 두 그래프가 다르다는 사실 자체는 남는다).
· C 는 채택하지 않는다 — 불변식을 절반만 지키면서 프리필 성능을 잃는다. 진단용 스위치로만 쓴다.
편집자 주. A 의 “85 ms/턴” 은 이 문서의 프리필 처리량 측정(1,244 토큰 ≈ 790 ms → ~1,500 tok/s)에서 환산한 값이고, 실제 구현에서는 부분 청크 재계산이 패딩 청크 한 번으로 처리되므로 토큰 수와 무관하게 청크 1회 비용에 가까울 가능성이 있다. 즉 상한 추정은 보수적이다. A 를 구현하면 실측해야 한다.

Phase 4 — 회귀 테스트: 업스트림의 테스트 갭

이 결함이 남아 있던 이유가 테스트에 드러난다. 업스트림에는 패딩 append 후 KV 캐시가 정확히 복원되는지 검증하는 테스트가 이미 있다. 

// cactus-graph/tests/test_cache.cpp:195-245 (요약)
append(g_exact,  exact_node,  real, 0,    100.0f);              // 패딩 없이
auto backup = g_padded.snapshot_cache_padded_append(padded_node, real, pads);
append(g_padded, padded_node, real, pads, 100.0f);              // 패딩 있게 (패딩값 9999.0f)
g_padded.rollback_cache_padded_append(padded_node, real, pads, backup);

// 그리고 두 캐시 버퍼가 바이트 단위로 같은지 검사
memcmp(exact_raw + meta_bytes, padded_raw + meta_bytes, exact_len * stride)
갭. 이 테스트는 캐시 내용만 본다. “같은 토큰 열을 어떻게 나눠 넣어도 로짓이 같은가” 를 검증하는 테스트가 없다. 그래서 캐시는 완벽히 복원되는데도 사용자에게 보이는 출력이 라우팅에 따라 달라지는 상태가 통과해 왔다.

추가할 테스트 — test_prefill_invariance

고정된 토큰 열 하나에 대해, 가능한 모든 라우팅이 같은 결과를 내는지 단정한다.

// 제안: cactus-engine/tests/test_prefill_invariance.cpp
//
// 입력: 고정 토큰 열 T (길이 N). N 은 128 미만·128 배수·128 배수+9 등 경계값을 모두 포함.
// 기준값: fused 경로(prefill_and_sample_first_token)로 얻은 첫 토큰 로짓 벡터.
//
// 아래 모든 라우팅이 기준값과 일치해야 한다 (bitwise, 또는 아주 좁은 tolerance):
//   1) 한 번에 전체 프리필                      chunk 그래프, 꼬리 패딩 O
//   2) 한 번에 전체 프리필, 꼬리 패딩 X          CACTUS_DISABLE_PREFILL_TAIL_PAD
//   3) 모든 분할점 k = 1 .. N-1 에 대해
//        prefill(T[0..k)) 후 prefill(T[k..N))    ← 증분 재사용 경로
//   4) 3) 의 각 경우에서 앞부분을 "생성"으로 채운 변형
//        (= step 그래프가 쓴 KV 가 섞인 상태)
//
// 현재 상태로 돌리면 1)↔2) 와 3) 의 대부분이 실패한다 — 그게 이 결함의 정의다.

분할점 전수(k = 1..N−1)가 핵심이다. 특정 k 하나만 보면 우연히 통과할 수 있다. Phase 1 의 1 토큰 단위 스윕이 정확히 이 구조였고, 그래서 임계값 8↔9 를 잡아낼 수 있었다.

업스트림 제출 패키지

이슈 본문 골자

Title. Prefill result depends on how the prompt is chunked: identical token sequence yields different output

Summary. For an identical prompt and greedy decoding, the model returns different text depending on how many tokens a single prefill call submits. The divergence boundary matches tail_tokens > 8 in model.cpp:1341 exactly. This also makes every turn after the first in cactus run differ from what a fresh prefill of the same conversation would produce.

Repro. two servers (stock / CACTUS_DISABLE_PREFILL_TAIL_PAD=1), one curl script, greedy. tail = prompt_tokens % 128: tail ≤ 8 → identical 9/9, tail ≥ 9 → diverged 43/46.

Ruled out. ① padding arithmetic — ATTENTION_CACHED with N real + (128−N) pad rows returns bit-identical outputs for the first N rows (all N, pad values 0.0 and 0.05); ② KV rollback — already covered by test_cache.cpp; ③ KV compression / sliding window — thresholds (4096 / 512) are not reached at these lengths.

Remaining suspect. decoder_prefill_chunk and decoder_step disagree numerically for the same token at the same position; the routing rules (chunk boundary, tail padding, prefix reuse) only decide which graph a token goes through.
