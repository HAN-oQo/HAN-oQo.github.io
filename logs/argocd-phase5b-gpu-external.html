5bFollow-up — Docker vLLM-ROCm + Argo CD external Service. Does it work?후속 — Docker vLLM-ROCm + ArgoCD 외부 Service. 되나?

Date: 2026-06-12 · Node: mi250-052 (AMD MI250) · Status: ✓ YES — it works, end to end · the documented Phase-5 fallback A, executed live작성일: 2026-06-12 · 노드: mi250-052 (AMD MI250) · 상태: ✓ 된다 — end to end 작동 · Phase 5의 문서화된 폴백 A, 실제 실행

The question질문
Phase 5 showed GPU passthrough into a kind node fails, but plain docker run --device exposes the MI250 fine. So: run vLLM-ROCm in Docker (GPU there), and have Argo CD manage an in-cluster Service that fronts it — is a "GPU model server under GitOps" actually reachable from the cluster? Answer: yes. Below is every step, including two real gotchas. Phase 5는 GPU passthrough가 kind 노드로는 안 되지만 평범한 docker run --device는 MI250를 잘 노출함을 보였다. 그래서: vLLM-ROCm을 Docker로(거기서 GPU) 띄우고 ArgoCD가 그걸 front하는 클러스터 내부 Service를 관리하면 — "GitOps 아래 GPU 모델서버"가 정말 클러스터에서 닿나? 답: 된다. 아래는 함정 둘 포함 전 과정.

[ kind cluster: gitops-lab ] [ host: mi250-052 ] pod ──curl──► Service gpu-vllm ──► nginx proxy pod ──► 172.18.0.1:8001 ──► docker vLLM-ROCm ──► MI250 GCD0 (Argo CD-managed) (Argo CD-managed) (kind gateway=host) (--device /dev/kfd…) (Qwen2.5-1.5B) └──────── declared in Git, reconciled ────────┘ └── docker run, device passthrough ──┘
Fig — the full request path. Left of the gateway is GitOps-managed Kubernetes; right of it is a Docker GPU process.그림 — 전체 요청 경로. 게이트웨이 왼쪽은 GitOps 관리 Kubernetes, 오른쪽은 Docker GPU 프로세스.

Step 1 — vLLM-ROCm on the host (the GPU half)1단계 — 호스트에서 vLLM-ROCm (GPU 쪽)

docker run -d --name gpu-vllm \
  --device /dev/kfd --device /dev/dri --group-add video --group-add render \
  --ipc=host --security-opt seccomp=unconfined \
  -e HIP_VISIBLE_DEVICES=0 -e VLLM_ROCM_USE_AITER=0 \
  -v ~/.cache/huggingface:/root/.cache/huggingface -p 8001:8000 \
  rocm/vllm:latest \
  vllm serve Qwen/Qwen2.5-1.5B-Instruct --port 8000 --max-model-len 4096 \
       --gpu-memory-utilization 0.5 --enforce-eager

The rocm/vllm:latest image (30.7 GB) and the Qwen2.5-1.5B weights were already cached on the node, so no big pull. One GCD via HIP_VISIBLE_DEVICES=0. rocm/vllm:latest 이미지(30.7GB)와 Qwen2.5-1.5B 가중치가 노드에 이미 캐시돼 있어 큰 pull 없음. HIP_VISIBLE_DEVICES=0로 GCD 1개.

Gotcha 1 — the engine crashed on AMD's aiter kernels함정 1 — AMD aiter 커널에서 엔진 크래시
First run: the model loaded onto the GPU fine (3.04 GiB, ROCm attention backend), then the EngineCore died right after importing aiter/module_rmsnorm.so → RuntimeError: Engine core initialization failed. AMD's aiter JIT kernels didn't play nice on this gfx90a. Fix: VLLM_ROCM_USE_AITER=0 → the KV-cache profiling then succeeded (GPU KV cache 1,017,488 tokens, 248× concurrency) and the API server came up. 첫 실행: 모델은 GPU에 잘 로드(3.04 GiB, ROCm attention backend), 그 직후 aiter/module_rmsnorm.so import 하자 EngineCore가 죽음 → RuntimeError: Engine core initialization failed. AMD aiter JIT 커널이 이 gfx90a에서 말썽. 해결: VLLM_ROCM_USE_AITER=0 → KV-cache profiling 성공(GPU KV cache 1,017,488 tokens, 248× 동시성)하고 API 서버 기동.
# host check — vLLM serving on the MI250:
$ curl localhost:8001/v1/models            → ["Qwen/Qwen2.5-1.5B-Instruct"]
$ curl localhost:8001/v1/chat/completions  → "MI250 online ..."   # real GPU completion

Step 2 — bridge the host into the cluster (the GitOps half)2단계 — 호스트를 클러스터에 연결 (GitOps 쪽)

A pod reaches the host via the kind Docker network's gateway — docker network inspect kind → 172.18.0.1. The first instinct is a no-selector Service + a manual Endpoints pointing at 172.18.0.1:8001. It routes correctly... but: 파드는 kind Docker 네트워크 게이트웨이로 호스트에 닿는다 — docker network inspect kind → 172.18.0.1. 첫 직감은 selector 없는 Service + 172.18.0.1:8001을 가리키는 수동 Endpoints. 라우팅은 맞는데... 그런데:

Gotcha 2 — Argo CD ignores Endpoints by default함정 2 — ArgoCD는 Endpoints를 기본 무시
The Application went Synced/Healthy but managed only the Service — the Endpoints object was never applied. Cause: Argo CD v3's default resource.exclusions includes Endpoints / EndpointSlice (they're high-churn, k8s-managed). Applied by hand it works, but it isn't GitOps-managed and won't self-heal. Two ways out: (a) un-exclude Endpoints in argocd-cm, or (b) front the host with a tiny proxy Deployment — normal resources Argo CD does manage. Took (b). Application은 Synced/Healthy인데 Service만 관리하고 Endpoints는 적용 안 됨. 원인: ArgoCD v3 기본 resource.exclusions에 Endpoints / EndpointSlice 포함(고-churn, k8s 관리). 손으로 적용하면 되지만 GitOps 관리가 아니고 self-heal도 안 됨. 탈출구 둘: (a) argocd-cm에서 Endpoints 제외 해제, 또는 (b) 작은 프록시 Deployment로 호스트를 front — ArgoCD가 관리하는 일반 리소스. (b) 선택.

So the GitOps-managed unit is a 3-object slice — all normal, non-excluded resources: 그래서 GitOps 관리 단위는 3-객체 — 전부 일반(비제외) 리소스:

# manifests/phase5-gpu-external/  (Argo CD app: phase5-gpu-external)
ConfigMap  gpu-vllm-proxy-conf   # nginx.conf:  proxy_pass http://172.18.0.1:8001;  (buffering off → stream)
Deployment gpu-vllm-proxy        # nginx:1.27-alpine shim → the host GPU server
Service    gpu-vllm              # selector app=gpu-vllm-proxy, port 8000

Step 3 — call the GPU from inside the cluster3단계 — 클러스터 안에서 GPU 호출

$ kubectl -n argocd get application phase5-gpu-external -o ...
ConfigMap/gpu-vllm-proxy-conf  Synced
Service/gpu-vllm               Synced
Deployment/gpu-vllm-proxy      Synced       # app = Synced/Healthy, proxy 1/1 ready

# from a throwaway pod in the cluster:
$ curl http://gpu-vllm.serving.svc.cluster.local:8000/v1/models
{"data":[{"id":"Qwen/Qwen2.5-1.5B-Instruct","owned_by":"vllm","max_model_len":4096}]}

$ curl .../v1/chat/completions -d '{"model":"Qwen/Qwen2.5-1.5B-Instruct",
    "messages":[{"role":"user","content":"Reply with exactly: served by MI250 via ArgoCD"}]}'
{"choices":[{"message":{"content":"Served by MI250 through ArgoCD"}}],
 "model":"Qwen/Qwen2.5-1.5B-Instruct","usage":{"completion_tokens":12,"total_tokens":55}}

That reply was generated by the MI250, reached from a pod inside the kind cluster, through the Argo CD-managed Service → nginx proxy → host Docker vLLM-ROCm. The whole left side is reconstructable from Git.이 응답은 MI250가 생성했고, kind 클러스터 내부 파드에서 ArgoCD 관리 Service → nginx 프록시 → 호스트 Docker vLLM-ROCm을 거쳐 도달. 왼쪽 전체는 Git에서 재구성 가능.

Verdict결론

Question질문Answer답
Does Docker vLLM-ROCm + Argo CD external Service work?Docker vLLM-ROCm + ArgoCD 외부 Service, 되나?Yes된다 — cluster pod → MI250, proven.클러스터 파드 → MI250, 증명.

Right pattern for production?프로덕션 정석?For a real fleet, prefer real K8s + AMD device plugin (Phase 5 Option B). This fallback shines when GPU lives outside the cluster.실 fleet엔 진짜 K8s + AMD device plugin(Phase 5 선택지 B)이 낫다. 이 폴백은 GPU가 클러스터 밖일 때 빛난다.
Bench hygiene벤치 위생
After the demo the gpu-vllm Docker container was stopped to free GCD 0 on the shared node (docker start gpu-vllm to resume). The Argo CD-managed proxy/Service/ConfigMap stay in Git — cheap, CPU-only, and they reconnect the moment the GPU server is back. 데모 후 공유 노드 GCD 0 반납을 위해 gpu-vllm 컨테이너 중지(docker start gpu-vllm으로 재개). ArgoCD 관리 프록시/Service/ConfigMap은 Git에 유지 — 싸고 CPU-only, GPU 서버 복귀 즉시 재연결.
