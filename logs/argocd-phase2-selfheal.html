2Our own GitOps repo — drift, self-heal, rollback우리 GitOps repo — drift · self-heal · 롤백

Date: 2026-06-12 · Node: mi250-052 · Status: ✓ DONE · Repo: github.com/hanq-moreh/argocd-gitops-lab작성일: 2026-06-12 · 노드: mi250-052 · 상태: ✓ 완료 · 저장소: github.com/hanq-moreh/argocd-gitops-lab

Goal of this phase이 단계 목표
Make a real Git repo the source of truth, register it as an Argo CD Application, and then prove the three behaviors that make GitOps worth it — by trying to break them: commit→auto-sync, self-heal (manual drift gets reverted), and rollback (git revert). Every status below is captured live. 진짜 Git 저장소를 진실 공급원으로 삼아 ArgoCD Application으로 등록하고, GitOps를 가치 있게 만드는 세 동작을 — 일부러 깨뜨려 보며 — 증명한다: commit→auto-sync, self-heal(수동 drift가 되돌려짐), 롤백(git revert). 아래 모든 상태는 라이브 캡쳐.

The source of truth진실 공급원

A trivial workload (traefik/whoami, which echoes which pod served you) plus an Argo CD Application that points at it. The Application lives in the repo too — that's the GitOps idea: even "what Argo CD manages" is declared in Git. 사소한 워크로드(traefik/whoami — 어느 파드가 응답했는지 알려줌)와 그걸 가리키는 ArgoCD Application. Application도 저장소에 들어있다 — 그게 GitOps: "ArgoCD가 무엇을 관리하는가"조차 Git에 선언.

# apps/phase2-hello.yaml  — the Argo CD Application
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: phase2-hello, namespace: argocd }
spec:
  source:
    repoURL: https://github.com/hanq-moreh/argocd-gitops-lab.git
    targetRevision: main
    path: manifests/phase2-hello          # ← sync this folder
  destination: { server: https://kubernetes.default.svc, namespace: demo }
  syncPolicy:
    automated: { prune: true, selfHeal: true }   # ← the two policies we test below
    syncOptions: [ CreateNamespace=true ]

Register it & first sync등록 & 첫 sync

$ kubectl apply -f https://raw.githubusercontent.com/hanq-moreh/argocd-gitops-lab/main/apps/phase2-hello.yaml

The three drills세 가지 드릴

A · commit → auto-synccommit → auto-sync

Bump replicas 2 → 3 in Git and push. Argo CD picks up the new commit and converges — no kubectl touched the cluster.Git에서 replicas 2 → 3 올리고 push. ArgoCD가 새 커밋을 잡아 수렴 — kubectl로 클러스터를 건드리지 않았다.

# local: git commit -am "scale whoami 2 -> 3" && git push   (commit 38cce16)
  t+2s  syncedRev=ba0e599  readyReplicas=2
  t+4s  syncedRev=38cce16  readyReplicas=2
  t+6s  syncedRev=38cce16  readyReplicas=3   -> auto-synced to new commit, 3 pods ready

In production the trigger is a Git webhook or the default 3-minute poll; here a manual refresh annotation made it instant for the demo.프로덕션에선 Git 웹훅 또는 기본 3분 폴링이 트리거; 여기선 데모용으로 refresh 어노테이션으로 즉시 반영.

B · self-heal — the 3 a.m. hotfix gets revertedself-heal — 새벽 핫픽스가 되돌려짐

Now drift the live cluster by hand: scale to 1. Git still says 3. Argo CD notices and reverts — in ~2 seconds.이제 클러스터를 손으로 drift: 1로 깎는다. Git은 여전히 3. ArgoCD가 알아채고 되돌린다 — 약 2초.

$ kubectl -n demo scale deploy/whoami --replicas=1     # the manual "fix"
  t+1s  spec.replicas=1  ready=1  appSync=OutOfSync
  t+2s  spec.replicas=3  ready=1  appSync=Synced        # ← Argo CD already rewrote it back to 3
  t+3s  spec.replicas=3  ready=3  appSync=Synced  -> self-heal reverted to 3

This is the line that makes "the cluster always matches Git" literally true. No silent config drift survives.이 한 줄이 "클러스터는 항상 Git과 일치"를 말 그대로 참으로 만든다. 조용한 설정 drift가 살아남지 못한다.

C · rollback = git revert롤백 = git revert

No "remember the old value." Roll back the scale by reverting the commit and pushing. Argo CD syncs the cluster back to 2."예전 값 기억하기" 없음. 커밋을 revert·push해서 스케일을 롤백. ArgoCD가 클러스터를 2로 되돌린다.

# local: git revert --no-edit HEAD && git push    (revert commit eb9a053)
  t+2s  syncedRev=38cce16  readyReplicas=3
  t+4s  syncedRev=eb9a053  readyReplicas=2   -> rolled back to 2 pods

# the deploy history is the audit trail:
  id=0  rev=ba0e599  at=12:51:49Z     (initial)
  id=1  rev=38cce16  at=12:53:22Z     (scale to 3)
  id=2  rev=eb9a053  at=12:54:18Z     (revert to 2)

Every state the cluster was ever in maps to a commit — that's the rollback target and the audit log, for free.클러스터가 거쳐간 모든 상태가 커밋에 대응 — 그게 롤백 대상이자 감사 로그, 공짜로.

Reproduce재현

Assumes Phase 1 (a kind cluster with Argo CD). The repo is public, so no credentials needed.Phase 1(ArgoCD 깔린 kind 클러스터) 전제. 저장소가 public이라 자격증명 불필요.

# 1) register the app (from the public repo)
kubectl apply -f https://raw.githubusercontent.com/hanq-moreh/argocd-gitops-lab/main/apps/phase2-hello.yaml

# 2) watch it converge
watch -n1 'kubectl -n argocd get application phase2-hello \
  -o jsonpath="{.status.sync.status}/{.status.health.status}{\"\n\"}"; kubectl -n demo get pods'

# 3) drills
#  A auto-sync : edit replicas in Git, push, then:  kubectl -n argocd annotate application phase2-hello argocd.argoproj.io/refresh=normal --overwrite
#  B self-heal : kubectl -n demo scale deploy/whoami --replicas=1   # watch it revert
#  C rollback  : git revert --no-edit HEAD && git push              # watch it go back

# cleanup:  kubectl -n argocd delete application phase2-hello   (prune=true removes the workload too)

Result결과

All three GitOps behaviors verified on a live cluster: changes flow Git→cluster automatically, manual drift is auto-corrected in seconds, and rollback is an ordinary git revert. The discipline this enforces — every change is a reviewable, revertible commit — is exactly what we want when the workload is a fleet of model servers. Next, Phase 3 puts a real model server under this same control. 세 GitOps 동작을 라이브 클러스터에서 검증: 변경이 Git→클러스터로 자동 전파, 수동 drift는 수초 내 자동 교정, 롤백은 평범한 git revert. 이게 강제하는 규율 — 모든 변경이 리뷰·되돌리기 가능한 커밋 — 이 워크로드가 모델 서버 fleet일 때 바로 우리가 원하는 것. 다음 Phase 3은 진짜 모델 서버를 이 통제 아래 둔다.
