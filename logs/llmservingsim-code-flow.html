1. 왜 한 시나리오로 따라가나

LLMServingSim 2.0은 4757 LoC 정도 되는 코드 (serving/ 하위). 모든 경로를 다 설명하기엔 분량이 너무 큼 — PD-split, DP/EP 동기화, prefix sharing, MoE expert routing, ns-3 network backend, agentic session 등은 각자 별도 줄기. 그래서 가장 단순하고 자주 쓰는 경로 하나만 깊이 따라가는 게 처음 본 사람한테 더 유용함.

선택한 시나리오:

  • 모델: Qwen/Qwen3-32B (dense, MoE 분기 안 탐)
  • 토폴로지: 1 노드 × 1 인스턴스 × TP=2 (router의 routing policy가 trivial)
  • 워크로드: ShareGPT JSONL 1줄 (prefill 단일 청크에 들어갈 만한 짧은 input)
  • 옵션: prefix cache off, chunked prefill off, PD split off, DP off — 모든 분기 false

이렇게 단순화하면 핵심 줄기 — "비용 표가 어떻게 쓰여서 한 batch의 시간이 나오는가" — 만 남음.

├── tp1/

메모리 표현

각 CSV는 pandas DataFrame으로 읽고 _build_1d_table() / _build_attention_table() 으로 가공해서 in-memory dict로 둠. 키 grid는 doubling grid (16, 32, 64, 128, 256, ...) 라서 lookup 시 log-space linear interpolation 사용 (_linear_interpolate(), _lookup_1d()).

왜 doubling grid? Op 시간이 토큰 수에 대해 대체로 log-affine. 16, 32, 64, ... 로 측정해두면 그 사이 값은 보간으로 1-3% 오차 안에 들어옴. linear grid (16, 17, 18, ...)로 똑같은 정확도 내려면 측정 점이 100배 더 필요.

한 번 로드한 perf_db는 TraceCtx 객체 (trace_generator.py:87)에 박혀서 그 인스턴스의 모든 batch trace 생성에 재사용됨.

8. ⑥ 메인 이벤트 루프 (한 iteration 분해)

파일: serving/__main__.py:482-863 · while True: 루프

요청 1개의 lifecycle은 여러 iteration에 걸쳐 진행됨:

  • iter 1: 요청이 arrival 시각에 도착 → 라우팅 → 첫 batch(=prefill)로 schedule → trace 생성 → ASTRA-Sim에 던짐
  • iter 2: ASTRA-Sim이 prefill 완료 통보 → add_done에서 ttft 기록 → schedule (이제 decode 단계) → 새 batch (decode 1 token)
  • iter 3 ~ N+1: decode iteration 반복 (1 token씩)
  • iter N+2: 마지막 add_done에서 요청 완료 마킹 → self.done 리스트에 추가

한 iteration 내부의 7단계를 따라가자.

8-1. Controller가 ASTRA-Sim 대기 메시지 읽기

파일: serving/__main__.py:484 → controller.py:13

def parse_output(self, output):
    pattern = r"sys\[(\d+)\] iteration (\d+) finished, (\d+) cycles, exposed communication (\d+) cycles."
    match = re.search(pattern, output)
    if match:
        sys = int(match.group(1))    # NPU ID
        id = int(match.group(2))     # batch ID
        cycle = int(match.group(3))  # 이 iteration까지 누적 cycle
        ...
        return {'sys': sys, 'id': id, 'cycle': cycle}
    return

cycle은 누적 시뮬레이션 시간 (ns 단위로 변환되어 current에 할당). 1 cycle ≈ 1 ns 가정.

8-3. 새로 도착한 요청 라우팅

파일: __main__.py:494 → router.py:189

def route_arrived_requests(self, current_time_ns):
    routed = 0
    while self._pending_idx < len(self._pending_requests):
        req_data = self._pending_requests[self._pending_idx]
        if req_data['arrival_time_ns'] > current_time_ns:
            break
        instance_id = self._select_instance(self.prefill_schedulers, "prefill")
        sched = self.prefill_schedulers[instance_id]
        sched.add_request([
            req_data['index'], sched.model,
            req_data['input_toks'], req_data['output_toks'],
            req_data['arrival_time_ns'], sched.instance_id,
        ], is_init=self._is_init)
        self._pending_idx += 1
        routed += 1
    return routed

arrival 시각이 current_time_ns 이하인 모든 요청을 한 번에 라우팅. 본 시나리오는 1개. sched.add_request() 안에서 Request 객체 (request.py:2) 생성 후 sched.request 큐에 push.

8-4. add_done — 직전 batch 완료 처리

파일: __main__.py:513 → scheduler.py:650-801

방금 ASTRA-Sim이 끝냈다고 알린 batch에 대해:

  • Prefill batch였으면 (scheduler.py:686-741): req.num_computed_tokens += chunk_len. 만약 num_computed_tokens >= req.input이면 prefill 완료, set_ttft(current) 호출 (request.py:62).
  • Decode batch였으면 (scheduler.py:742-783): req.num_computed_tokens += 1. add_itl(current)로 inter-token latency 누적. num_computed_tokens >= req.output이면 add_latency() + self.done.append(req) 후 KV-cache free.

리턴: (prompt_tokens_this_step, gen_tokens_this_step, finished_requests). 메인 루프가 throughput 계산에 사용.

8-5. schedule — 다음 batch 만들기

파일: __main__.py:532 → scheduler.py:54

  1. 도착 필터링 (line 73): batch_req = [req for req in self.request if req.arrival <= current]
  2. max_num_seqs 제한 (line 76-78): inflight + 새 batch 합쳐서 max_num_seqs 초과 못 하게 자름
  3. Chunked prefill 분기 (line 102-106): chunked prefill on이면 decode를 먼저, prefill을 뒤로 정렬. off면 prefill만/decode만 일관 batch
  4. 토큰 budget 할당 (line 108-173): 각 req에 이번 step에서 줄 토큰 수 (scheduled_tokens dict) 결정. max_num_batched_tokens 초과 안 하게 prefill 청크 잘라넣음
  5. KV-cache 메모리 체크 + eviction (line 174-215): get_block_kv()로 batch가 필요한 KV bytes 계산. 부족하면 decode req 일부를 CPU로 evict (req.evict=True)
  6. Batch 객체 생성 (line 245-282): q_list, prefill_q_list, decode_k_list 채워서 Batch(...) 인스턴스화 (request.py:74)
  7. 리턴: 생성한 Batch 객체 (없으면 None)

본 시나리오 첫 iteration: prefill batch — q_list=[287], num_prefill=1, num_decode=0.

8-6. generate_trace — cost table lookup으로 batch 시간 계산

파일: __main__.py:579 부근 (DP/PD 분기에 따라 호출 위치 여러 군데) → trace_generator.py:1447

이 함수가 비용 표 트릭의 사용 지점. Batch (token 카운트 + KV 길이) → per-layer per-op 지연 시간 → ASCII trace 파일.

generate_trace(batch, hardware, tp_size, pp_size,
               local_ep, ep_total, pd_type,
               node_id, instance_id, ...)
  ├─ get_config(model_name)              # HF config.json → num_layers, hidden_size, num_heads
  ├─ _load_perf_db(hardware, model, ...) # 캐시된 CSV (§5에서 로드)
  ├─ _synthesize_trace(batch_ctx, ...)   # trace_generator.py:1293-1445
  │    for layer in range(num_hidden_layers):
  │      for op in catalog (qkv_proj, attn, o_proj, gate_up_proj, ...):
  │        lookup perf_db[op][tp_size][input_size]
  │        → 보간으로 time_us 계산
  │        → ASCII trace에 한 줄 (op_name, duration_ns, comm_size_bytes)
  │      collectives (AllReduce for TP, AllToAll for EP)도 한 줄씩
  └─ write to inputs/trace/{hw}/{model}/instance{id}_batch{id}.txt

핵심: "이 batch에 이 op가 몇 us 걸리는지" 는 GPU 안 띄우고 CSV lookup으로 결정. 그게 cost table trick.

def write_flush(self, p, input):
    p.stdin.write(input+'\n')
    p.stdin.flush()
# Python이 ASTRA-Sim 프로세스에 "inputs/workload/.../llm" 경로 한 줄 던짐
# ASTRA-Sim이 그걸 받아서 시뮬레이션 1 iteration 더 돌림

ASTRA-Sim이 trace의 collective comm 명령(AllReduce 등) 시간을 자기 네트워크 모델로 시뮬해서 한 iteration cycle을 계산하고, 끝나면 다시 "Waiting" 보내고 다음 입력을 기다림. 그 시점에 메인 루프가 read_wait로 돌아옴 (위 8-1로 순환).

9. ⑦ CSV 출력

파일: 메인 루프 종료 후 → scheduler.py:911 save_output()

def save_output(self, output_file, is_append=False):
    output_file = f'../{output_file}'
    mode = 'a' if is_append else 'w'
    with open(output_file, mode=mode, newline='') as file:
        writer = csv.writer(file)
        if not is_append:
            writer.writerow(['instance id', 'request id', 'model', 'input', 'output',
                            'arrival', 'end_time', 'latency',
                            'queuing_delay', 'TTFT', 'TPOT', 'ITL'])
        for req in self.done:
            writer.writerow([
                req.instance_id, req.id, req.model,
                req.input, req.output - req.input,
                req.arrival, req.end_time, req.latency,
                req.queuing_delay, req.ttft, req.tpot, req.itl
            ])

각 컬럼 의미:

  • arrival — 요청 도착 (ns)
  • end_time — 마지막 토큰 생성 완료 (ns)
  • latency = end_time - arrival
  • queuing_delay — arrival → 첫 batch에 들어간 시각
  • TTFT — arrival → 첫 토큰 시각 (prefill 끝)
  • TPOT — (latency - ttft) / (output_tokens - 1), 평균 decode 토큰 간격
  • ITL — 각 decode 토큰의 inter-token-latency 리스트 (가변 길이)
경로 주의: 출력 경로 앞에 '../'가 붙음 (scheduler.py:912). 컨테이너에서 --output outputs/foo.csv 던지면 실제로는 /app/outputs/foo.csv가 아니라 /app/LLMServingSim/../outputs/foo.csv에 떨어질 수 있음. 본 시나리오에선 작업 디렉토리 구조상 잘 떨어지지만, sweep 스크립트 짤 때 주의.
