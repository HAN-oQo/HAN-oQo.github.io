1. Why follow a single scenario1. 왜 한 시나리오로 따라가나

LLMServingSim 2.0 is about 4757 LoC of code (under serving/). Explaining every path would be too much — PD-split, DP/EP sync, prefix sharing, MoE expert routing, the ns-3 network backend, agentic sessions, and so on are each separate threads. So it's more useful for a first-time reader to follow just the simplest, most commonly used path in depth.LLMServingSim 2.0은 4757 LoC 정도 되는 코드 (serving/ 하위). 모든 경로를 다 설명하기엔 분량이 너무 큼 — PD-split, DP/EP 동기화, prefix sharing, MoE expert routing, ns-3 network backend, agentic session 등은 각자 별도 줄기. 그래서 가장 단순하고 자주 쓰는 경로 하나만 깊이 따라가는 게 처음 본 사람한테 더 유용함.

The chosen scenario:선택한 시나리오:

  • Model: Qwen/Qwen3-32B (dense, no MoE branch taken)모델: Qwen/Qwen3-32B (dense, MoE 분기 안 탐)
  • Topology: 1 node × 1 instance × TP=2 (the router's routing policy is trivial)토폴로지: 1 노드 × 1 인스턴스 × TP=2 (router의 routing policy가 trivial)
  • Workload: one line of ShareGPT JSONL (short input that fits in a single prefill chunk)워크로드: ShareGPT JSONL 1줄 (prefill 단일 청크에 들어갈 만한 짧은 input)
  • Options: prefix cache off, chunked prefill off, PD split off, DP off — all branches false옵션: prefix cache off, chunked prefill off, PD split off, DP off — 모든 분기 false

Simplifying this way leaves only the core thread — "how is the cost table used to derive the time of one batch".이렇게 단순화하면 핵심 줄기 — "비용 표가 어떻게 쓰여서 한 batch의 시간이 나오는가" — 만 남음.

In-memory representation메모리 표현

Each CSV is read as a pandas DataFrame, processed via _build_1d_table() / _build_attention_table(), and kept as an in-memory dict. The key grid is a doubling grid (16, 32, 64, 128, 256, ...), so lookups use log-space linear interpolation (_linear_interpolate(), _lookup_1d()).각 CSV는 pandas DataFrame으로 읽고 _build_1d_table() / _build_attention_table() 으로 가공해서 in-memory dict로 둠. 키 grid는 doubling grid (16, 32, 64, 128, 256, ...) 라서 lookup 시 log-space linear interpolation 사용 (_linear_interpolate(), _lookup_1d()).

Why a doubling grid?왜 doubling grid? Op time is roughly log-affine in token count. If you measure at 16, 32, 64, ..., values in between are within 1-3% error via interpolation. To reach the same accuracy on a linear grid (16, 17, 18, ...) you'd need about 100× more measurement points.Op 시간이 토큰 수에 대해 대체로 log-affine. 16, 32, 64, ... 로 측정해두면 그 사이 값은 보간으로 1-3% 오차 안에 들어옴. linear grid (16, 17, 18, ...)로 똑같은 정확도 내려면 측정 점이 100배 더 필요.

The loaded perf_db is embedded into the TraceCtx object (trace_generator.py:87) and reused for all batch trace generation on that instance.한 번 로드한 perf_db는 TraceCtx 객체 (trace_generator.py:87)에 박혀서 그 인스턴스의 모든 batch trace 생성에 재사용됨.

A single request's lifecycle spans multiple iterations:요청 1개의 lifecycle은 여러 iteration에 걸쳐 진행됨:

  • iter 1: request arrives at its arrival time → routed → scheduled as the first batch (=prefill) → trace generated → handed to ASTRA-Simiter 1: 요청이 arrival 시각에 도착 → 라우팅 → 첫 batch(=prefill)로 schedule → trace 생성 → ASTRA-Sim에 던짐

def read_wait(self, p):
    out = [""]
    while "Waiting" not in out[-1] and out[-1] != "Checking Non-Exited Systems ...\n":
        line = p.stdout.readline()
        out.append(line)
        p.stdout.flush()
    return out

Blocking read on ASTRA-Sim's stdout until a "Waiting" line appears. The preceding line carries "sys[N] iteration M finished ..."."Waiting" 라인이 나올 때까지 ASTRA-Sim의 stdout 블로킹 read. 직전 라인에 "sys[N] iteration M finished ..." 가 와있음.

def parse_output(self, output):
    pattern = r"sys\[(\d+)\] iteration (\d+) finished, (\d+) cycles, exposed communication (\d+) cycles."
    match = re.search(pattern, output)
    if match:
        sys = int(match.group(1))    # NPU ID
        id = int(match.group(2))     # batch ID
        cycle = int(match.group(3))  # 이 iteration까지 누적 cycle
        ...
        return {'sys': sys, 'id': id, 'cycle': cycle}
    return

def route_arrived_requests(self, current_time_ns):
    routed = 0
    while self._pending_idx < len(self._pending_requests):
        req_data = self._pending_requests[self._pending_idx]
        if req_data['arrival_time_ns'] > current_time_ns:
            break
        instance_id = self._select_instance(self.prefill_schedulers, "prefill")
        sched = self.prefill_schedulers[instance_id]
        sched.add_request([
            req_data['index'], sched.model,
            req_data['input_toks'], req_data['output_toks'],
            req_data['arrival_time_ns'], sched.instance_id,
        ], is_init=self._is_init)
        self._pending_idx += 1
        routed += 1
    return routed

def save_output(self, output_file, is_append=False):
    output_file = f'../{output_file}'
    mode = 'a' if is_append else 'w'
    with open(output_file, mode=mode, newline='') as file:
        writer = csv.writer(file)
        if not is_append:
            writer.writerow(['instance id', 'request id', 'model', 'input', 'output',
                            'arrival', 'end_time', 'latency',
                            'queuing_delay', 'TTFT', 'TPOT', 'ITL'])
        for req in self.done:
            writer.writerow([
                req.instance_id, req.id, req.model,
                req.input, req.output - req.input,
                req.arrival, req.end_time, req.latency,
                req.queuing_delay, req.ttft, req.tpot, req.itl
            ])
