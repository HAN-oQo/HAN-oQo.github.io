1레포 클론 (서브모듈 포함)

cd ~/Desktop
git clone --recurse-submodules https://github.com/casys-kaist/LLMServingSim.git
cd LLMServingSim

--recurse-submodules가 중요. ASTRA-Sim, Chakra, ns-3, csg-htsim, fmt, spdlog, googletest, yaml-cpp 등 9개 서브모듈을 한 번에 가져옴 (~1GB).

이슈 1 (잠재): 클론 후에 git submodule status가 비어있으면 git submodule update --init --recursive로 보충. 본 세션에선 한 번에 잘 받아짐.

2Docker 이미지 pull + 컨테이너 띄우기

레포의 scripts/docker-sim.sh는 인터랙티브로 띄우게 돼 있는데, 자동화/재현성을 위해 detached 모드로 띄우고 docker exec로 명령 보내는 게 편함.

# 베이스 이미지 (linux/amd64)
docker pull astrasim/tutorial-micro2024

# detached 컨테이너 (sleep infinity로 살려둠)
docker run -d --name servingsim_docker \
  -v ~/Desktop/LLMServingSim:/app/LLMServingSim \
  -w /app/LLMServingSim \
  astrasim/tutorial-micro2024 \
  sleep infinity

# 살아있는지 확인
docker ps --filter "name=servingsim_docker"
이슈 2 (무해): Apple Silicon에서 WARNING: The requested image's platform (linux/amd64) does not match the detected host platform (linux/arm64/v8) 메시지가 뜸. Rosetta 에뮬로 정상 동작하므로 무시. 모든 명령이 그대로 작동함.

3Python 의존성 설치

docker-sim.sh가 인터랙티브 실행 시 자동으로 깔아주는 패키지들 — 우리는 detached이므로 수동:

docker exec servingsim_docker pip3 install \
  pyyaml pyinstrument transformers datasets \
  msgspec scikit-learn xgboost==3.1.2 matplotlib==3.5.3 \
  pandas==1.5.3 numpy==1.23.5

핀된 버전이 명확하니까 그대로 따르면 됨. ~1분 안에 끝남.

4ASTRA-Sim 컴파일

ASTRA-Sim은 C++로 짜인 백엔드. 레포의 scripts/compile.sh가 (1) Chakra(트레이스 포맷)를 pip 설치, (2) analytical backend 빌드 둘 다 처리.

docker exec servingsim_docker bash scripts/compile.sh

~3분 정도 걸림. 출력 마지막 줄이:

[100%] Built target AstraSim_Analytical_Congestion_Unaware
[100%] Built target AstraSim_Analytical_Congestion_Aware

이면 성공. 산출물은 astra-sim/build/astra_analytical/bin/AstraSim_Analytical_Congestion_{Aware,Unaware}.

5-2. 이슈 3: dtype 불일치

FileNotFoundError: Profile variant folder not found:
  ../profiler/perf/RTXPRO6000/meta-llama/Llama-3.1-8B/fp16.
Run the profiler with matching --dtype / --kv-cache-dtype,
or pick an existing variant under ../profiler/perf/RTXPRO6000/meta-llama/Llama-3.1-8B.

공식 docs는 --dtype float16이라 적혀있지만 레포에 커밋된 프로파일은 bf16(bfloat16)뿐. 확인:

docker exec servingsim_docker ls profiler/perf/RTXPRO6000/meta-llama/Llama-3.1-8B/
# → bf16

해결: --dtype bfloat16으로 변경.

5-3. 이슈 4: ZeroDivisionError on short traces

위 dtype을 고치고 다시 돌리면:

...
Total token throughput (tok/s):                                     427.01
Traceback (most recent call last):
  ...
  File "/app/LLMServingSim/serving/__main__.py", line 910, in main
    print_markup(f"Throughput per {1/RATIO} sec ...")
ZeroDivisionError: float division by zero

요약 줄까지는 다 찍히는데, 마지막 throughput-per-window 출력에서 RATIO=0이라 죽음. CSV가 안 적힘!

원인 추적 — serving/__main__.py:436:

FREQ = 1_000_000_000      # 1 GHz
INTERVAL = log_interval * FREQ
RATIO = FREQ // INTERVAL  # ← 정수 나눗셈!

--log-interval 5.0이면 INTERVAL=5e9, RATIO = 1e9 // 5e9 = 0. log_interval ≥ 2면 항상 0이 되는 버그.

해결: --log-interval 1.0 (또는 더 작게)로 변경. RATIO = 1e9 // 1e9 = 1 → 정상.

업스트림에 보고할 만함: RATIO = max(1, FREQ // INTERVAL) 또는 float 나눗셈으로 패치하면 깔끔.

새 (device, model) 추가하려면? 그 디바이스에 실 GPU 한 번만 있으면 됨:

  --device H100 \
  --dtype bfloat16 \
  --tp 4
# → profiler/perf/H100/meta-llama/Llama-3.1-70B/bf16/tp4/*.csv 생성
이후 그 H100 + Llama-70B 조합으로는 영원히 시뮬만 돌리면 됨.

7Qwen3-32B (dense) 시뮬레이션

7-1. Custom cluster config

레포에 Qwen3-32B용 cluster config가 따로 없어서 직접 작성. single_node_single_instance.json을 기반으로 모델명과 TP만 변경:

cat > configs/cluster/qwen3_32b_single.json <<'EOF'
{
    "num_nodes": 1,
    "link_bw": 16,
    "link_latency": 20000,
    "nodes": [{
        "num_instances": 1,
        "cpu_mem": {"mem_size": 512, "mem_bw": 256, "mem_latency": 0},
        "instances": [{
            "model_name": "Qwen/Qwen3-32B",
            "hardware": "RTXPRO6000",
            "npu_mem": {"mem_size": 96, "mem_bw": 1597, "mem_latency": 0},
            "num_npus": 2,
            "tp_size": 2,
            "pd_type": null
        }]
    }]
}
EOF

32B 모델은 96GB(RTX PRO 6000 한 장 VRAM) 한 대로 안 들어가서 TP=2 (GPU 2장으로 분할). 레포의 프로파일도 tp1·tp2 두 종류 다 있음.

7-2. 워크로드

레포에 sharegpt 기반 trace가 이미 있음:

workloads/sharegpt-qwen3-32b-300-sps10.jsonl
# 300 requests, starts-per-second=10 (즉 30초 분량의 도착 분포)
# 평균 input ~860 토큰, 평균 output ~665 토큰

7-3. 실행

docker exec servingsim_docker bash -c "
python -m serving \
  --cluster-config configs/cluster/qwen3_32b_single.json \
  --dtype bfloat16 --block-size 16 \
  --dataset workloads/sharegpt-qwen3-32b-300-sps10.jsonl \
  --output outputs/qwen3_32b_single.csv \
  --log-interval 1.0
"

해석: 워크로드가 sps=10(초당 10개 도착)인데 단일 인스턴스 처리율이 1.84 req/s 라서 심각한 백로그가 쌓임. 결과: 후순위 요청의 TTFT가 90초를 넘어감(앞의 요청 다 처리될 때까지 큐에서 대기). TPOT는 안정적 (~82ms) — 일단 처리 시작되면 정상 속도. 실제 운영이라면 인스턴스 늘리거나 도착율 제한 필요.

8Qwen3-30B-A3B (MoE) 시뮬레이션

MoE 모델은 expert parallelism(EP)이 필요해서 레포에 이미 들어있는 config 그대로 사용:

cat configs/cluster/single_node_moe_single_instance.json
# → Qwen/Qwen3-30B-A3B-Instruct-2507, num_npus=2, tp_size=2, ep_size=2

8-1. 실행 (100 요청만 — --num-reqs로 빠르게)

docker exec servingsim_docker bash -c "

  --dataset workloads/sharegpt-qwen3-30b-a3b-300-sps10.jsonl \
  --output outputs/qwen3_30b_a3b_moe.csv \
  --num-reqs 100 \

9비교 sweep — prefix cache on/off, 모델 비교

같은 워크로드(sharegpt-qwen3-32b-300-sps10.jsonl의 앞 100개), 같은 cluster config(TP=2 single instance), 단 --enable-prefix-caching 플래그만 변경:

9-1. Prefix cache OFF

docker exec servingsim_docker bash -c "
python -m serving \
  --cluster-config configs/cluster/qwen3_32b_single.json \
  --dtype bfloat16 --block-size 16 \
  --dataset workloads/sharegpt-qwen3-32b-300-sps10.jsonl \
  --output outputs/qwen3_32b_nopref.csv \
  --num-reqs 100 \
  --no-enable-prefix-caching \
  --log-interval 1.0
"

9-2. Prefix cache ON (default; 비교 베이스라인)

같은 명령에서 --no-enable-prefix-caching만 빼고 출력 파일명 변경:

... --output outputs/qwen3_32b_pref100.csv --num-reqs 100 ...

9-4. 비교 해석

A vs B — 요청 수 영향 (모델 동일): 300 요청을 같은 sps=10 도착율로 쏴넣으면 시스템 처리율(~1.84 req/s) 한계 때문에 큐가 폭발. p99 TTFT가 95초까지 치솟음. 100 요청으론 시스템이 따라잡을 수 있어 p99 7초 수준. 실 운영에선 sps=2 이하로 도착율을 막거나 인스턴스를 5× 늘려야 함.

B vs C — prefix cache on/off (같은 100 요청): ShareGPT trace는 요청 간 prefix 공유가 거의 없어서 cache 효과 미미 — TTFT mean 4,256 vs 4,416 (3.6% 개선), throughput 2,274 vs 2,253 (1% 개선). system prompt를 공유하는 챗봇 같은 워크로드라면 차이가 훨씬 크게 날 것.

B vs D — dense vs MoE (같은 100 요청, 같은 HW):

  • MoE는 token당 활성 파라미터 ~3B vs dense 32B → forward 비용 ~10× ↓
  • 실제 결과: TTFT mean 23×↓(4,256 → 180), TPOT 1.7×↓(62.3 → 36.0), throughput 1.8×↑(2,274 → 4,038)
  • TTFT 차이가 throughput 차이보다 큰 이유: 동시 처리가 가능해서 queuing 거의 없음

운영 결정에 대입하면: "Qwen3-32B(dense) vs Qwen3-30B-A3B(MoE) 중 뭐 쓸까?" → 같은 RTX PRO 6000 2장에 같은 워크로드라면 MoE가 처리량·지연 모두 명확히 우세. 단 모델 품질은 시뮬 영역 밖이라 별도 평가 필요.

10CSV 결과 해석

per-request CSV의 컬럼 (공식 docs reading-output.md 기준):

컬럼타입의미
instance idint이 요청을 처리한 인스턴스
request idintrouter가 부여한 monotonic ID
modelstring모델명
inputint프롬프트 토큰 수
outputint생성된 토큰 수
arrivalint (ns)요청 도착 시각 (시뮬 클럭)
end_timeint (ns)마지막 생성 토큰 완료 시각
latencyint (ns)end-to-end = end_time − arrival
queuing_delayint (ns)arrival → 첫 스케줄링까지
TTFTint (ns)Time-to-first-token
TPOTint (ns)평균 토큰 간격 (latency − TTFT) / (output − 1)
ITLstring토큰별 간격 list (직렬화된 Python list)

모든 시각은 나노초 단위. /1e9 = 초, /1e6 = 밀리초.

# pandas로 분석 예
import pandas as pd
df = pd.read_csv("outputs/qwen3_32b_single.csv")
df["TTFT_ms"] = df["TTFT"] / 1e6
df["TPOT_ms"] = df["TPOT"] / 1e6
df["latency_s"] = df["latency"] / 1e9
print(df[["TTFT_ms", "TPOT_ms", "latency_s"]].describe())

#증상원인해결
1git clone으로 받았지만 astra-sim 폴더가 비어있음--recurse-submodules 누락git submodule update --init --recursive
2Docker pull 시 linux/amd64 does not match linux/arm64 경고Apple Silicon에서 amd64 이미지무시 (Rosetta 에뮬로 정상 동작)
3FileNotFoundError: Profile variant folder not found: .../fp16공식 docs는 --dtype float16이지만 레포 프로파일은 bf16--dtype bfloat16 사용
4시뮬 끝나기 직전 ZeroDivisionError: float division by zero → CSV 안 적힘RATIO = FREQ // INTERVAL 정수 나눗셈이 log_interval ≥ 2에서 0--log-interval 1.0 이하 사용
5Qwen3-32B용 cluster config가 레포에 없음기본 예제만 들어있음single_node_single_instance.json 복사 + model_name·tp_size만 수정

12. 운영 명령어 모음

# 컨테이너 상태
docker ps --filter "name=servingsim_docker"

# 컨테이너 안에서 셸 잡기
docker exec -it servingsim_docker bash

# 모든 outputs CSV 호스트로 복사
docker cp servingsim_docker:/app/LLMServingSim/outputs ~/Desktop/LLMServingSim_outputs

# 컨테이너 중지 (재시작 가능)
docker stop servingsim_docker
docker start servingsim_docker

# 완전 제거 (이미지는 보존)
docker rm -f servingsim_docker

# 이미지까지 제거
docker rmi astrasim/tutorial-micro2024
