A tool-using math agent — verl multi-turn tool agent (MI250)도구 쓰는 수학 에이전트 — verl multi-turn tool agent (MI250)

Environment: mi250-052 (MI250, ROCm 7.2.3) · Docker only · verl 0.8.0 ToolAgentLoop + vLLM (hermes tool parser) · Qwen2.5-0.5B-Instruct · gsm8k · 2 GCD환경: mi250-052 (MI250, ROCm 7.2.3) · Docker 전용 · verl 0.8.0 ToolAgentLoop + vLLM(hermes 도구파서) · Qwen2.5-0.5B-Instruct · gsm8k · 2 GCD

2026-06-14·updated갱신2026-06-16

One-line summary. Extended single-turn GRPO (previous experiment) into a multi-turn tool agent — when the model reasons and then calls the code_interpreter tool, a code-execution sandbox returns the result and the model continues toward an answer. On MI250 ROCm, verl ToolAgentLoop + vLLM hermes tool parser work correctly (4 steps completed, num_turns avg 2.1 · max 8). The most important finding: in async rollout, update_weights (weight-sync) shows up as a distinct cost taking ~20% of the step — a stage that was hidden under colocate (previous experiment). However, the untrained 0.5B barely uses tools (tool_calls≈0); the infra works, but tool-use frequency is low without SFT.한 줄 요약. 단일턴 GRPO(앞 실험)를 멀티턴 도구 에이전트로 확장했다 — 모델이 추론하다 code_interpreter 도구를 호출하면, 코드실행 샌드박스가 결과를 돌려주고, 모델이 이어서 답을 낸다. MI250 ROCm에서 verl ToolAgentLoop + vLLM hermes 도구파서가 정상 작동(4스텝 완주, num_turns 평균 2.1·최대 8). 가장 중요한 발견: async 롤아웃에선 update_weights(weight-sync)가 스텝의 ~20%를 차지하는 뚜렷한 비용으로 드러난다 — colocate(앞 실험)에선 숨어 있던 단계다. 단, 미학습 0.5B는 도구를 거의 안 써(tool_calls≈0) 인프라는 되지만 도구 사용 빈도는 SFT 없이는 낮다.

1. Goal — from single-turn to multi-turn tools1. 목표 — 단일턴에서 도구 멀티턴으로

The previous speed experiment was single-turn GRPO: "generate once → score → update". Here we step up one level to an agent: instead of finishing in one turn, the model runs a multi-turn loop of call a tool (code executor) → receive the result → keep reasoning. It solves gsm8k math problems "without computing directly, but by using a calculator (Python)", and earns reward 1 if the final #### answer is correct.앞 속도 실험은 "생성 1번 → 채점 → 업데이트"의 단일턴 GRPO였다. 여기서는 에이전트로 한 칸 올린다: 모델이 한 턴에 끝내지 않고, 도구(코드 실행기)를 호출 → 결과를 받아 → 이어서 추론하는 멀티턴 루프. gsm8k 수학 문제를 "직접 계산하지 말고 계산기(파이썬)를 써서" 풀게 하고, 최종 #### 정답이 맞으면 보상 1.

What we want to measure: (a) how many turns an episode runs on average, (b) how much of the loop time tool calls take, (c) how the stage distribution changes versus single-turn — especially the weight-sync cost in async rollout.측정하고 싶은 것: (a) 에피소드가 평균 몇 턴 도는가, (b) 도구 호출이 루프 시간에서 차지하는 비중, (c) 단일턴 대비 단계 분포가 어떻게 바뀌는가 — 특히 async 롤아웃에서 weight-sync 비용.

Terminology. agent loop = the multi-turn rollout abstraction verl provides. ToolAgentLoop = the built-in loop that supports tool calls. tool parser = the vLLM component that extracts tool-call JSON from model output (the Qwen family uses hermes). weight-sync = reloading the updated policy weights into the vLLM server used for rollout.용어. agent loop = verl이 제공하는 멀티턴 롤아웃 추상화. ToolAgentLoop = 도구 호출을 지원하는 내장 루프. 도구파서(tool parser) = 모델 출력에서 도구 호출 JSON을 뽑아내는 vLLM 컴포넌트(Qwen 계열은 hermes). weight-sync = 업데이트된 정책 가중치를 롤아웃용 vLLM 서버로 다시 적재.

Based on verl 0.8.0's agent_loop tutorial (examples/tutorial/agent_loop_get_started), adapted to MI250 by swapping the model to Qwen2.5-0.5B and the data to gsm8k. 3. Code flow — how one episode calls a tool3. 코드 흐름 — 한 에피소드가 도구를 부르는 경로

The key point is that the tool call happens inside the rollout — generate → parse → external execution → token re-injection repeats within one episode, and the entire multi-turn sequence produced this way becomes a GRPO training sample. Reward applies only to the final answer (outcome-based).핵심은 도구 호출이 롤아웃 안에서 일어난다는 점이다 — 생성 → 파싱 → 외부 실행 → 토큰 재주입이 한 에피소드 안에서 반복되고, 그렇게 만들어진 멀티턴 시퀀스 전체가 GRPO의 학습 샘플이 된다. 보상은 마지막 답에만 걸린다(결과 기반).

Key finding ① — weight-sync surfaces. In the earlier single-turn colocate experiment, weight-sync was in-process and barely visible. Here, in async rollout (vLLM being a separate server process), the updated weights must be reloaded into that server every step, so update_weights registers as 2.85s (20%). This is exactly the item that grows into a network cost in distributed (multi-node) RL — the subject of experiment E.핵심 ① — weight-sync가 표면화된다. 앞 단일턴 colocate 실험에선 weight-sync가 in-process라 거의 안 보였다. 여기 async 롤아웃(vLLM이 별도 서버 프로세스)에선 매 스텝 업데이트된 가중치를 그 서버로 다시 실어야 해 update_weights가 2.85s(20%)로 잡힌다. 이게 분산(멀티노드) RL에서 네트워크 비용으로 커지는 바로 그 항목 — E 실험의 주제다.
Key finding ② — tool use is sparse without SFT. tool_calls≈0 is not because the infra is broken (parser · sandbox · multi-turn all work, max 8 turns observed) but because the untrained 0.5B does not know how to call tools. The tutorial itself states "the SFT stage is omitted". To actually make it use tools you need (a) tool-use SFT warmup, (b) a tool-call-format reward, (c) a larger model — tasks for the next stage.핵심 ② — 도구 사용은 SFT 없이는 희소하다. tool_calls≈0은 인프라가 안 된 게 아니라(파서·샌드박스·멀티턴 전부 작동, max 8턴 관찰됨) 미학습 0.5B가 도구를 부르는 법을 모르기 때문이다. 튜토리얼도 "SFT 단계는 생략"이라 명시한다. 도구를 실제로 쓰게 하려면 (a) 도구사용 SFT 워밍업, (b) 도구 호출 형식 보상, (c) 더 큰 모델이 필요 — 다음 단계 과제.

5. Conclusion + next (B)5. 결론 + 다음(B)

  1. verl multi-turn tool-agent RL works on MI250 ROCm — ToolAgentLoop + vLLM hermes parser + code-execution sandbox, 4 steps completed.MI250 ROCm에서 verl 멀티턴 도구 에이전트 RL이 작동한다 — ToolAgentLoop + vLLM hermes 파서 + 코드실행 샌드박스, 4스텝 완주.
  2. agentic (async) rollout changes the stage landscape: gen 36% / update_actor 26% / weight-sync 20% / ref 10% / old_log_prob 8%. The weight-sync that was hidden in single-turn colocate becomes a surface cost.agentic(async) 롤아웃은 단계 지형을 바꾼다: gen 36% / update_actor 26% / weight-sync 20% / ref 10% / old_log_prob 8%. 단일턴 colocate에서 숨어 있던 weight-sync가 표면 비용이 된다.
  3. Infra ≠ behavior. The tool loop works, but the untrained 0.5B barely uses tools (tool_calls≈0). The real difficulty of agentic RL is not "running it" but "making it use tools" (SFT warmup · format reward).인프라 ≠ 행동. 도구 루프는 되지만 미학습 0.5B는 도구를 거의 안 쓴다(tool_calls≈0). agentic RL의 진짜 난점은 "돌리기"가 아니라 "도구를 쓰게 만들기"(SFT 워밍업·형식 보상)다.

Next (B — code agent): reuse the same sandbox but change the task to "write code → run tests → pass". As reward becomes the unit-test execution result rather than a rule match, we look at whether the reward stage gets expensive (a continuation of the flow where reward was 24% in the previous experiment).다음(B — 코드 에이전트): 같은 샌드박스를 재사용하되 과제를 "코드 작성 → 테스트 실행 → 통과"로 바꾼다. 보상이 규칙 일치가 아니라 유닛테스트 실행 결과가 되면서 reward 단계가 비싸지는지 본다(앞 실험에서 reward가 24%였던 흐름의 연장).
