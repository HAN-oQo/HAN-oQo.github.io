1. 왜 이 문서가 필요한가

LLMServingSim 2.0은 "비용 표 + 행동 모델" 구조로 동작 (자세한 건 Frontier 노트 §3-1 참고). 핵심은:

  • cost table = (HW × 모델 × dtype × TP) 별 op 지연 CSV
  • 이 표가 있으면 sim은 GPU 없이 돌아감. 없으면 못 돔.

레포에는 KAIST 팀이 미리 만들어둔 일부 조합 CSV가 들어있음. 다른 (HW, 모델) 조합을 쓰려면 직접 만들어야 함. 이 문서는 그 작업의 전체 흐름.

2. 현재 사용 가능한 프로파일 인벤토리 (실측 확인)

2026-06-10 기준 레포 (profiler/perf/) 에 커밋되어 있는 (HW × model × variant × TP) 전체 목록. 이 표에 있는 조합은 GPU 없이 그대로 sim 가능:

3. 지원되는 모델 아키텍처 (YAML 카탈로그)

새 모델을 프로파일할 때 그 모델의 config.json의 model_type 필드가 아래 중 하나면 YAML 작업 없이 바로 가능:

profiler/models/
├── llama.yaml          # Llama 1/2/3.x/3.3 (Llama-3.1-8B/70B, Llama-3.3-70B 등)
├── qwen3.yaml          # Qwen3 dense (Qwen3-0.6B/1.7B/4B/8B/14B/32B/...)
├── qwen3_moe.yaml      # Qwen3 MoE (Qwen3-30B-A3B, Qwen3-235B-A22B 등)
├── mixtral.yaml        # Mixtral 8x7B / 8x22B
└── phimoe.yaml         # Phi-mini-MoE-instruct 등
지원 안 되는 모델 예시: Mistral-7B (별도 model_type), Gemma, Phi-3 dense, DeepSeek 등은 직접 YAML 작성 필요 (이 문서 §7 참고).

4. 시나리오 분류 — 뭐가 필요한가

상황필요한 작업대략 시간
레포 내장 (HW × 모델) 그대로 사용아무것도. 위 §2 표에 있으면 바로 sim0분
새 HW + 내장 모델 (예: H100 × Llama-3.1-8B)그 HW에 vLLM 띄워서 한 번 프로파일~1–2h (모델 크기 따라)
내장 HW + 새 모델, 모델 아키텍처는 지원됨 (Llama-3.3-70B 등)그 HW에서 프로파일 1회~1–3h
완전히 새 모델 (Mistral, Gemma, DeepSeek 등)YAML 작성 + 프로파일YAML ~1–4h + 프로파일
GPU 아닌 가속기 (TPU, NPU)별도 워크플로 (공식 docs)—

5. 필수 준비물

  • ✅ 실제 NVIDIA GPU — 모델이 적어도 1장에 들어가는 VRAM (TP > 1이면 그만큼 더)
  • ✅ 레포 클론 — git clone --recurse-submodules https://github.com/casys-kaist/LLMServingSim.git
  • ✅ vLLM Docker 컨테이너 (sim 컨테이너와 별개) — 레포의 scripts/docker-vllm.sh 사용
  • ✅ HF_TOKEN 환경변수 — gated 모델 (Llama 등) 다운용. huggingface.co에서 발급
  • ✅ 여유 시간 — 작은 모델 30분~1h, 큰 모델 2~3h
중요: sim 컨테이너 (astrasim/tutorial-micro2024, CPU 동작)와 profiler 컨테이너 (vLLM, GPU 동작)는 별도 환경. profiler는 GPU 머신에서 돌리고, 산출된 profiler/perf/<HW>/... 폴더만 sim 머신으로 복사하면 됨.

6. Step-by-step — 새 HW × 모델 프로파일 (가장 흔한 경우)

1vLLM 컨테이너 띄우기 (GPU 머신에서)

cd ~/LLMServingSim
export HF_TOKEN=hf_xxxxxxxxxx       # gated 모델 받으려면
bash scripts/docker-vllm.sh
# → vllm_docker 라는 별도 컨테이너 띄움, --gpus all 자동 적용

2profiler/profile.sh 변수 편집

스크립트 상단의 변수만 손대면 됨:

MODEL="Qwen/Qwen3-32B"        # HF 이름 (config.json 자동 다운)
HARDWARE="H100"                # 자유 라벨 (perf/<이거>/ 폴더가 됨)
TP_DEGREES="1,2,4"             # 측정할 TP 차수 (반드시 1 포함)
MAX_NUM_BATCHED_TOKENS=2048
MAX_NUM_SEQS=256
MEASUREMENT_ITERATIONS=3       # 5로 올리면 분산 ↓, ~1.67× 느려짐
# SKIP_SKEW=1                  # skew sweep 스킵 (분 단위 단축)

3실행

docker exec vllm_docker bash -c "cd /workspace && ./profiler/profile.sh"

내부 동작:

  1. configs/model/<MODEL>.json 읽음 (없으면 HF에서 자동 다운로드 + 캐싱)
  2. config.json의 model_type 필드로 profiler/models/<type>.yaml 매칭
  3. tmpdir에 model config 써놓고 vLLM 엔진 띄움
  4. 4가지 grid sweep: dense / per_sequence / attention / moe → CSV 작성
  5. (기본) heterogeneous decode skew sweep → α-law fitting → skew_fit.csv
  6. meta.yaml 작성 (vllm_version, cuda_version, gpu 등 환경 기록)

4실시간 진행 모니터링 (선택)

# 다른 터미널에서
docker logs -f vllm_docker

각 sweep 단계가 "Profiling dense:", "Profiling attention:" 같은 헤더로 시작. 중단됐다 다시 실행하면 이미 한 shot은 skip (resume 기능, FORCE=1 환경변수로 무효화 가능).

7. 새 모델 아키텍처 YAML 작성 (드문 케이스)

대상 모델이 §3 YAML 목록에 없으면 profiler/models/<model_type>.yaml을 새로 작성. qwen3.yaml을 템플릿으로:

# profiler/models/<model_type>.yaml
sequence:
  prologue:  [embedding]
  pre_attn:  [layernorm, qkv_proj, qk_norm, rotary_emb, attention]
  post_attn: [o_proj, layernorm]
  mlp_dense: [gate_up_proj, act_fn, down_proj]
  mlp_moe:   []                # MoE면 [router, experts, ...]
  head:      [final_layernorm, lm_head, sampler]

catalog:
  dense:
    embedding:     {vllm: VocabParallelEmbedding}
    layernorm:     {vllm: RMSNorm, within: <DecoderLayer클래스명>, tp_stable: true}
    qkv_proj:      {vllm: QKVParallelLinear}
    rotary_emb:    {vllm: RotaryEmbedding}
    o_proj:        {vllm: RowParallelLinear, within: <Attention클래스명>}
    gate_up_proj:  {vllm: MergedColumnParallelLinear}
    act_fn:        {vllm: SiluAndMul}
    down_proj:     {vllm: RowParallelLinear, within: <MLP클래스명>}
    final_layernorm: {vllm: RMSNorm, within: <CausalLM클래스명>, tp_stable: true}
    lm_head:       {vllm: ParallelLMHead}
    sampler:       {vllm: Sampler}

각 항목의 vllm: 필드는 vLLM 소스 (vllm/model_executor/models/<model>.py)의 클래스 이름. 카탈로그 채우려면 그 파이썬 파일을 읽으면서 매핑.

7-1. tp_stable 의미

tp_stable: true로 표시한 op는 TP=1로 한 번만 측정하고 다른 TP 폴더로 복제. layernorm 처럼 TP에 따라 시간이 변하지 않는 layer가 해당. 잘못 표시하면 (예: 실제론 TP-dependent한데 stable로 표시) 다른 TP에서 sim 결과가 틀어짐.

7-2. 검증

YAML 작성 후 TP=1 + TP=2 둘 다 측정해서 tp1/dense.csv와 tp2/dense.csv를 비교. tp_stable로 표시한 row가 두 파일에서 거의 동일하면 (~5% 이내) 맞음.

8. 산출물 구조

profiler/perf/H100/Qwen/Qwen3-32B/bf16/
├── meta.yaml                  # vllm_version, cuda_version, gpu, 측정 옵션
├── tp1/
│   ├── attention.csv          # (prefill_chunk, kv_prefill, n_decode, kv_decode) → time_us
│   ├── dense.csv              # (layer, tokens) → time_us
│   ├── per_sequence.csv       # (layer, sequences) → time_us
│   ├── moe.csv                # (tokens, experts) → time_us (MoE 모델만)
│   ├── skew.csv               # heterogeneous decode 측정 raw
│   └── skew_fit.csv           # α-law fitting 계수
├── tp2/
└── tp4/
TP=1만 측정해도 다른 TP는 자동 derive 가능 — TP-stable layer (layernorm 등)는 한 번만 측정하고 모든 TP 폴더로 복제됨. TP에 의존하는 layer (QKV/FFN GEMM)만 각 TP에서 따로 측정.

8-1. meta.yaml 예시

created_at: '2026-04-24T03:12:00Z'
vllm_version: '0.19.0'
cuda_version: '13.0'
torch_version: '2.6.0+cu130'
gpu_name: 'NVIDIA RTX PRO 6000 Blackwell Server Edition'
model: 'Qwen/Qwen3-32B'
model_type: 'qwen3'
dtype: 'bfloat16'
kv_cache_dtype: 'auto'
variant: 'bf16'
tp_degrees: [1, 2]
skew_fit: true
measurement_iterations: 3

9. 프로파일 시간 단축 트릭

플래그효과트레이드오프
TP_DEGREES="1"대략 ⅓~½ 시간다른 TP는 sim 시 정확도 ↓ (TP-dependent layer 외삽)
SKIP_SKEW=110–30분 단축heterogeneous decode 정확도 ↓ (constant α로 fallback)
MEASUREMENT_ITERATIONS=1~3× 빠름분산 15–25% (vs 5% with N=3)
ATTENTION_MAX_KV=4096 (기본 16384)attention grid 1/4긴 context (> 4K) 시 외삽
FORCE=1 안 쓰기 (기본)resume — 중단 후 재실행 시 이미 한 shot은 건너뜀없음 (기본값)

11. 새 프로파일을 시뮬에서 쓰는 법

1profiler 산출물을 sim 머신으로 복사

# profiler 머신 (GPU) 에서
tar czf perf-h100-qwen3-32b.tar.gz profiler/perf/H100

# sim 머신으로 전송
scp perf-h100-qwen3-32b.tar.gz simhost:~/

# sim 머신에서
cd ~/LLMServingSim
tar xzf ~/perf-h100-qwen3-32b.tar.gz
# → profiler/perf/H100/ 에 풀림

2새 HW 라벨 가리키는 cluster config 작성

cat > configs/cluster/qwen3_32b_h100.json <<'EOF'
{
    "num_nodes": 1,
    "link_bw": 16,
    "link_latency": 20000,
    "nodes": [{
        "num_instances": 1,
        "cpu_mem": {"mem_size": 512, "mem_bw": 256, "mem_latency": 0},
        "instances": [{
            "model_name": "Qwen/Qwen3-32B",
            "hardware": "H100",
            "npu_mem": {"mem_size": 80, "mem_bw": 3350, "mem_latency": 0},
            "num_npus": 2,
            "tp_size": 2,
            "pd_type": null
        }]
    }]
}
EOF

hardware 필드 값이 profile.sh에서 사용한 HARDWARE 라벨과 정확히 일치해야 함. 시뮬레이터는 profiler/perf/<hardware>/<model_name>/<variant>/tp<N>/ 경로로 CSV를 찾음.

3시뮬 실행 (GPU 없이)

docker exec servingsim_docker bash -c "
python -m serving \
  --cluster-config configs/cluster/qwen3_32b_h100.json \
  --dtype bfloat16 --block-size 16 \
  --dataset workloads/sharegpt-qwen3-32b-300-sps10.jsonl \
  --output outputs/qwen3_32b_h100.csv \
  --log-interval 1.0
"

4결과 확인

head outputs/qwen3_32b_h100.csv
# instance_id,request_id,model,input,output,arrival,end_time,latency,queuing_delay,TTFT,TPOT,ITL

12. 빠른 체크리스트

  1. 대상 (HW, 모델) 조합이 §2 표에 있나? → 있으면 끝
  2. 없다면, 모델의 model_type이 §3 YAML 5종 중 하나인가? → 맞으면 YAML 작업 ×
  3. GPU 머신 잡기 (로컬 또는 cloud spot)
  4. 레포 클론 + scripts/docker-vllm.sh로 vLLM 컨테이너 띄움
  5. HF_TOKEN 설정 (gated 모델인 경우)
  6. profiler/profile.sh 상단 변수 편집 (MODEL, HARDWARE, TP_DEGREES)
  7. ./profiler/profile.sh 실행 → 1~3h 기다림
  8. 산출물 profiler/perf/<HW>/<model>/ 확인
  9. sim 머신으로 복사 (또는 같은 머신이면 그대로)
  10. 그 HW 라벨을 가리키는 cluster config 작성 → python -m serving 실행
