Disaggregation & weight-sync 스케일링 — 멀티노드의 실제 비용 (MI250)

환경: mi250-052 / mi250-053 (MI250, ROCm 7.2.3) · Docker 전용 · verl 0.8.0 GRPO(async) · Qwen2.5-0.5B · gsm8k

2026-06-15

한 줄 요약. 목표는 롤아웃 GPU와 학습 GPU를 노드 단위로 분리해, weight-sync(A에서 본 update_weights)가 네트워크 비용으로 바뀌는지 보는 것이었다. 진짜 크로스노드(052+053)는 인프라 블로커로 막혔다(053에 vLLM-ROCm 이미지 없음 · 노드 간 ssh/registry 쓰기 불가 · 30GB 로컬 릴레이 비현실 · D에서 본 ROCm NCCL 취약성). 대신 052 단독에서 weight-sync 스케일링(2→4→8 GCD)을 실측했고, 분명한 패턴을 얻었다: weight-sync는 ~일정(≈1.5s)인데 학습(update_actor)은 GPU 수에 반비례로 줄어 → weight-sync의 상대 비중이 10%→20%로 커진다. 즉 학습을 병렬화할수록 동기 weight-sync가 병목이 되는 Amdahl 법칙이 RL 루프에 그대로 적용된다 — 이것이 disaggregation·async 가중치 전송이 푸는 문제다.

1. 목표 — 롤아웃을 떼어내면 weight-sync가 네트워크로

A에서 봤듯, async 롤아웃에선 매 스텝 업데이트된 정책 가중치를 vLLM 롤아웃 엔진으로 다시 실어야 한다(update_weights, A에서 ~20%). colocate(같은 노드·같은 GPU군)에선 이게 빠른 노드 내 인터커넥트(MI250의 xGMI/Infinity Fabric)를 탄다. 하지만 롤아웃을 별도 노드로 분리(진짜 disaggregation)하면 그 전송이 노드 간 네트워크(이더넷/IB)를 타게 된다 — 대역폭이 xGMI보다 훨씬 낮다. D가 "보상을 떼어내라"였다면 E는 "롤아웃을 떼어내라"이고, 그 대가가 weight-sync다.

2. 진짜 멀티노드 시도 — 인프라 블로커

052+053 양 노드로 verl nnodes=2를 띄우려 했으나 다음에서 막혔다:

단계상태

판정. 진짜 크로스노드는 이미지 배포 인프라(노드 간 ssh / registry 쓰기 / 빠른 전송 경로)가 없어 막혔다. 설령 이미지를 옮겨도, D에서 본 ROCm NCCL/RCCL 취약성 위에 크로스노드 RCCL(NCCL_SOCKET_IFNAME 튜닝 등)이 더해져 추가 디버깅이 필요하다. 정직하게 블로커로 기록하고, 핵심 측정(weight-sync)은 단일노드 프록시로 대체했다.

3. 단일노드 프록시 — weight-sync 스케일링 (2/4/8 GCD)

같은 verl async GRPO(gsm8k, batch 32, n=8)를 GCD 수만 2→4→8로 바꿔 돌렸다. 학습 풀(FSDP)과 롤아웃(vLLM)이 GCD 수에 따라 어떻게 갈리는지 본다. 정상 스텝:

GCDstep (s)genupdate_actor (학습)update_weights (weight-sync)weight-sync 비중
215.383.935.391.5610%
49.953.382.881.5215%
87.123.051.491.4320%
핵심 — weight-sync는 RL의 Amdahl 직렬 항. GCD를 2→8로 4배 늘리면 학습(update_actor)은 5.39→1.49s로 ~3.6배 빨라지지만, weight-sync는 1.56→1.43s로 거의 안 줄어든다. 0.5B 가중치를 colocate vLLM 엔진에 브로드캐스트하는 비용은 GPU 수에 비례해 줄지 않기 때문(작은 모델 + 빠른 xGMI라 절대값도 작음). 결과적으로 weight-sync의 상대 비중이 10%→20%로 커진다 — 학습을 병렬화할수록 직렬 weight-sync가 전체를 지배하기 시작한다. 이게 disaggregated RL이 가중치 전송을 학습/생성과 비동기로 겹치려는 이유다.

4. 크로스노드 투영 — xGMI → 네트워크

측정값은 모두 노드 내 xGMI(MI250 Infinity Fabric, 수백 GB/s)를 탄 weight-sync다. 진짜 멀티노드 disaggregation에선 같은 전송이 노드 간 네트워크(이더넷/IB)를 타며, 두 가지로 악화된다:

  • 대역폭: 노드 간 링크는 xGMI보다 보통 한 자릿수 이상 느리다 → 같은 0.5B라도 weight-sync가 수 배로.
  • 모델 크기: weight-sync는 가중치 바이트 수에 비례. 0.5B(≈1GB bf16)는 싸지만 7B(≈14GB)·70B면 매 스텝 수~수십 GB를 노드 간 전송 → weight-sync가 지배적 병목이 된다.

그래서 대규모 disaggregated RL 프레임워크(이번 시리즈의 verl 포함)는 weight-sync를 단순 동기 브로드캐스트로 두지 않고 — 전송을 학습/생성과 겹치고(async), RDMA/NCCL 기반 가중치 브로드캐스트나 파라미터 캐시로 최적화한다. 본 실험의 단일노드 곡선(직렬 weight-sync가 병렬화의 한계)은 그 동기를 작은 규모에서 그대로 보여준다.

측정의 한계. 크로스노드 절대 수치는 인프라 블로커로 못 쟀다(§2). 위 투영은 측정된 xGMI weight-sync(≈1.5s/0.5B)와 인터커넥트 특성에 근거한 방향성 추론이지 측정값이 아니다 — 정직하게 구분해 둔다.

5. 결론 + 시리즈 마무리

  1. weight-sync는 RL 루프의 직렬(Amdahl) 항. 학습은 GPU로 병렬화되지만 weight-sync는 안 줄어 — 비중이 10%→20%로 증가(2→8 GCD). 스케일이 커질수록 weight-sync가 한계를 정한다.
  2. 크로스노드면 더 나쁘다: xGMI → 네트워크 + 큰 모델 = weight-sync 폭증. disaggregation의 핵심 과제이며, async 가중치 전송이 답.
  3. 진짜 멀티노드는 인프라 블로커(이미지 배포 + ROCm NCCL)로 미완 — 정직하게 기록. 단일노드 스케일링이 동일한 통찰을 준다.
시리즈 5부작 종합. 단일턴 GRPO에서 출발해 agentic으로 확장하며 "비-정책 연산이 어디서 비용이 되는가"를 따라왔다:
· A 도구수학: 멀티턴 됨, async weight-sync ~20% 표면화, 도구사용은 SFT 없이 희소
· B 코드: 보상=테스트 실행 → reward 14~24% (검증기가 비용)
· C 검색: 도구=BM25, ~7ms로 저렴(도구 비용은 도구 나름), 0.5B는 멀티홉 못 풂
· D GenRM: 보상=모델 → colocate 인라인 불가(GPU NCCL 충돌 / CPU 마비), 전용 서빙 필요
· E disagg: weight-sync = Amdahl 직렬 항, 스케일·크로스노드에서 병목
관통 결론: agentic RL을 "돌리는" 것과 "스케일시키는" 것은 다르다. 작은 모델·단일노드에선 거의 다 돌지만, 검증기·보상모델·weight-sync 같은 비-정책 연산이 규모에서 차례로 병목이 되고, 각각 전용 인프라(샌드박스 풀·RM 서버·async 가중치 전송)를 요구한다.
