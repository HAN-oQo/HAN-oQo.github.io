6Prod-ops & disaster recovery실운영 & 재해 복구

Date: 2026-06-12 · Node: mi250-052 · Status: ✓ DONE · The payoff phase — whole cluster destroyed and rebuilt from Git in ~80s작성일: 2026-06-12 · 노드: mi250-052 · 상태: ✓ 완료 · 보상 단계 — 클러스터를 통째로 파괴하고 Git에서 약 80초에 재구축

Goal of this phase이 단계 목표
Prove the operational promise of GitOps: the cluster is cattle, not a pet. Delete the entire cluster, recreate it, apply one bootstrap object, and watch the whole stack from Phases 2–4 come back from Git — no snowflake state, no remembered commands. Plus the rest of the prod-ops toolbox. GitOps의 운영 약속을 증명한다: 클러스터는 애완동물이 아니라 가축이다. 클러스터를 통째로 삭제·재생성하고 하나의 부트스트랩 객체만 적용하면 Phase 2–4의 전체 스택이 Git에서 돌아온다 — 눈송이 상태도, 기억해 둔 명령도 없이. 그리고 실운영 툴박스의 나머지.

One object rebuilds everything객체 하나가 전부를 재구축

The bootstrap is an app-of-apps that registers the three top-level Applications; phase4-root in turn brings up its two children. So a single kubectl apply reconstructs the full tree. 부트스트랩은 상위 Application 3개를 등록하는 app-of-apps이고, phase4-root가 다시 자기 자식 2개를 올린다. 그래서 단 한 번의 kubectl apply가 전체 트리를 재구성한다.

apps/00-bootstrap.yaml (kubectl apply this ONE file) └─ creates 3 top-level Applications: ├─ phase2-hello → whoami Deployment (ns demo) ├─ phase3-model → llama.cpp model server (ns serving) └─ phase4-llmd-root → app-of-apps: ├─ phase4-gie-crds (GIE CRDs) └─ phase4-inferencepool (InferencePool CR)

The disaster-recovery drill — live재해 복구 드릴 — 실제

# 1) DESTROY — simulate losing the cluster entirely
$ kind delete cluster --name gitops-lab
$ kind get clusters        # → []   (gone)

# 2) REBUILD — recreate cluster + reinstall Argo CD (Phase 1, server-side) ... then ONE apply:
$ kubectl apply -f .../apps/00-bootstrap.yaml
application.argoproj.io/bootstrap created

# 3) WATCH everything repopulate FROM GIT (who=whoami pods, model=model-server, pool=InferencePool):
t+10s  who=0 model=0 pool=no    bootstrap=Synced phase2-hello=Synced phase3-model=Synced phase4-*=OutOfSync
t+15s  who=0 model=0 pool=yes   ... phase4-gie-crds=Synced phase4-inferencepool=Synced phase4-llmd-root=Synced
t+20s  who=2 model=0 pool=yes
t+80s  who=2 model=1 pool=yes   -> FULL STACK REBUILT FROM GIT

$ kubectl -n argocd get applications     # all six, Synced
bootstrap  phase2-hello  phase3-model  phase4-llmd-root  phase4-gie-crds  phase4-inferencepool

~80 s from an empty recreated cluster to the full stack healthy — and the only "input" was one Git URL. The model-server delay is just the GGUF re-download; everything else converged in ~15 s.빈 재생성 클러스터에서 전체 스택 정상까지 약 80초 — 유일한 "입력"은 Git URL 하나. model-server 지연은 GGUF 재다운로드 때문이고, 나머지는 약 15초에 수렴.

Why this is the whole point이게 핵심인 이유
There was no backup to restore, no runbook to follow, no "who remembers the replica count / image tag / pool selector." The cluster's entire desired state lived in Git, so recovery = recreate + point Argo CD at the repo. For a production llm-d fleet, that's the difference between a 20-minute rebuild and a frantic afternoon. 복원할 백업도, 따를 런북도, "replica 수/이미지 태그/풀 selector 기억하는 사람?"도 없었다. 클러스터의 전체 desired state가 Git에 있으니 복구 = 재생성 + ArgoCD를 저장소에 연결. 프로덕션 llm-d fleet이라면, 20분 재구축과 정신없는 오후의 차이다.

The rest of the prod-ops toolbox실운영 툴박스의 나머지

DR is the headline; these are the day-to-day guardrails Argo CD gives you, layered on the same repo (fully demoing some needs multiple clusters, so they're summarized here): DR가 헤드라인이고, 다음은 같은 저장소 위에 얹는 일상 가드레일이다(일부는 완전 시연에 여러 클러스터가 필요해 요약):

Tool도구What it buys you무엇을 주나
ApplicationSetOne template → an Application per env/cluster (dev→staging→prod) using Kustomize overlays. Promotion = merge a PR; no copy-paste drift between environments.템플릿 하나 → 환경/클러스터별 Application(dev→staging→prod), Kustomize overlay 사용. 승격 = PR 머지; 환경 간 복붙 drift 없음.
AppProjectRBAC/guardrails: restrict which repos, clusters, namespaces, and resource kinds a team's apps may touch — e.g. the inference team can deploy to serving only.RBAC/가드레일: 팀 앱이 건드릴 수 있는 repo·클러스터·네임스페이스·리소스 종류 제한 — 예: 추론 팀은 serving에만 배포.
Sync windowsSync windowBlock auto-sync during peak inference hours; allow it overnight. Change lands in Git now, deploys in the safe window.피크 추론 시간엔 auto-sync 차단, 야간엔 허용. 변경은 지금 Git에 들어오고 안전한 창에서 배포.
Notifications알림Slack/webhook on sync failed / health degraded / out-of-sync — operators learn about drift before users do.sync 실패 / health degraded / out-of-sync 시 Slack/webhook — 사용자보다 먼저 운영자가 drift를 안다.

Reproduce재현

# the DR drill (destroys + rebuilds the lab cluster):
kind delete cluster --name gitops-lab
kind create cluster --name gitops-lab --wait 180s
kubectl create namespace argocd --dry-run=client -o yaml | kubectl apply -f -
kubectl apply --server-side --force-conflicts -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl -n argocd rollout status deploy/argocd-server --timeout=420s
kubectl apply -f https://raw.githubusercontent.com/hanq-moreh/argocd-gitops-lab/main/apps/00-bootstrap.yaml
watch -n3 'kubectl -n argocd get applications; kubectl -n serving get deploy,inferencepool; kubectl -n demo get deploy'

Series wrap-up시리즈 정리

Six phases, all executed live on mi250-052: bootstrap (1), the GitOps loop and self-heal/rollback (2), a real model server (3), the llm-d control plane as app-of-apps + sync waves (4), an honest GPU-passthrough boundary (5), and disaster recovery (6). The throughline: operating a vLLM + llm-d fleet means operating Kubernetes objects, and Argo CD makes every one of them a reviewable, revertible, self-healing, rebuildable commit. Engine internals were covered in the Heimdall deep-dives; this series is the operational other half. 여섯 단계 전부 mi250-052에서 실제 실행: 부트스트랩(1), GitOps 루프와 self-heal/롤백(2), 진짜 모델 서버(3), app-of-apps + sync waves로 llm-d 컨트롤플레인(4), 정직한 GPU passthrough 경계(5), 재해 복구(6). 관통하는 주제: vLLM + llm-d fleet 운영은 곧 Kubernetes 객체 운영이고, ArgoCD는 그 하나하나를 리뷰·되돌리기·self-heal·재구축 가능한 커밋으로 만든다. 엔진 내부는 Heimdall 딥다이브에서 다뤘고, 이 시리즈는 그 운영 반쪽이다.
