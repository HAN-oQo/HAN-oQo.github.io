3A real model server under GitOpsGitOps 아래 진짜 모델 서버

Date: 2026-06-12 · Node: mi250-052 (CPU path) · Status: ✓ DONE · Served: Qwen2.5-0.5B-Instruct GGUF via an OpenAI-compatible endpoint작성일: 2026-06-12 · 노드: mi250-052 (CPU 경로) · 상태: ✓ 완료 · 서빙: Qwen2.5-0.5B-Instruct GGUF, OpenAI 호환 엔드포인트

Goal of this phase이 단계 목표
Put an actual inference server — an OpenAI /v1 endpoint serving a real model — under the same Argo CD control as Phase 2, and do a model version bump as a commit (watch the rolling update). The point is operating the inference workload itself declaratively. 실제 추론 서버 — 진짜 모델을 서빙하는 OpenAI /v1 엔드포인트 — 를 Phase 2와 같은 ArgoCD 통제 아래 두고, 모델 버전업을 커밋으로 수행한다(롤링 업데이트 관찰). 핵심은 추론 워크로드 자체를 선언형으로 운영하는 것.

Engine choice — why llama.cpp, not vLLM, on this CPU path엔진 선택 — 이 CPU 경로에서 vLLM 아닌 llama.cpp인 이유
The plan named "CPU vLLM," but vLLM's published images are CUDA-oriented and a CPU build is heavy to stand up in a kind pod (the earlier CPU-cluster log already established this). For a reliable, tiny, OpenAI-compatible server the stand-in is llama.cpp serving a Qwen2.5-0.5B GGUF. The GitOps lesson — and the API surface (/v1/models, /v1/chat/completions) — is identical; only the engine binary differs. Phase 5 is where a real GPU engine is attempted. 계획엔 "CPU vLLM"이라 적었지만, vLLM 공개 이미지는 CUDA 지향이고 CPU 빌드를 kind 파드에 띄우는 건 무겁다(앞선 CPU-cluster 로그에서 확인). 작고 안정적인 OpenAI 호환 서버 스탠드인은 Qwen2.5-0.5B GGUF를 서빙하는 llama.cpp. GitOps 레슨과 API 표면(/v1/models, /v1/chat/completions)은 동일하고 엔진 바이너리만 다르다. 진짜 GPU 엔진은 Phase 5에서 시도.

The manifest매니페스트

An initContainer downloads the GGUF to a shared volume, then the server loads it locally — this mirrors how a real model server loads weights via a PVC/initContainer (and it's robust, see the gotcha below). initContainer가 GGUF를 공유 볼륨에 받아두고, 서버는 그걸 로컬로 로드 — 실제 모델 서버가 PVC/initContainer로 가중치를 로딩하는 방식과 같다(그리고 견고하다, 아래 함정 참고).

# manifests/phase3-model/deployment.yaml  (excerpt)
initContainers:
  - name: fetch-model            # weights as a separate, cacheable step
    image: curlimages/curl:8.10.1
    args: ["-fL","-o","/models/model.gguf",
           "https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct-GGUF/resolve/main/qwen2.5-0.5b-instruct-q4_k_m.gguf"]
    volumeMounts: [{ name: models, mountPath: /models }]
containers:
  - name: llama
    image: ghcr.io/ggml-org/llama.cpp:server
    args: ["-m","/models/model.gguf","--host","0.0.0.0","--port","8000","-c","4096","--alias","qwen2.5-0.5b-q4_k_m"]
    readinessProbe: { httpGet: { path: /health, port: 8000 }, failureThreshold: 60 }
Real gotcha — llama.cpp's -hf auto-download hit HTTP 401실전 함정 — llama.cpp -hf 자동 다운로드가 HTTP 401
The first version used llama.cpp's built-in -hf ggml-org/... fetcher. It crash-looped: 첫 버전은 llama.cpp 내장 -hf ggml-org/... 페처를 썼다. 크래시루프: 
E get_repo_commit: error: GET failed (401): Invalid username or password.
W get_repo_files: failed to resolve commit for ggml-org/Qwen2.5-0.5B-Instruct-GGUF
failed to download model from Hugging Face   → exitCode=1, CrashLoopBackOff
The resolver authenticated badly against that repo path. Fix: stop using -hf and pull the GGUF directly with an initContainer (anonymous HTTPS works fine for the public Qwen/... repo). Robust and a better separation of concerns. This is the kind of thing that, once in Git, never bites the next operator. 그 resolver가 해당 repo 경로에 인증을 잘못 했다. 해결: -hf를 버리고 initContainer로 GGUF를 직접 받음(public Qwen/... repo는 anonymous HTTPS로 잘 됨). 견고하고 관심사 분리도 더 낫다. 이런 건 한 번 Git에 박히면 다음 운영자를 다신 안 문다.

Drill — model version bump as a commit드릴 — 모델 버전업을 커밋으로

Change the quant q4_k_m → q5_0 in Git (new weight URL + alias), commit, push. Argo CD does a rolling update: a new ReplicaSet downloads the new weights, becomes ready, and the old one scales to zero. Git에서 quant q4_k_m → q5_0 변경(새 가중치 URL + alias), 커밋, push. ArgoCD가 롤링 업데이트: 새 ReplicaSet이 새 가중치를 받아 ready가 되고 옛 것은 0으로 축소.

# local: git commit -am "model version bump q4_k_m -> q5_0" && git push   (commit ba709b5)

$ kubectl -n serving get rs
model-server-5d64bdbf99   desired=1  ready=1     # ← q5_0 (new)
model-server-69db74887f   desired=0  ready=0     # ← q4_k_m (rolled back to 0)
model-server-78bb96b484   desired=0  ready=0     # ← original -hf attempt

$ curl .../v1/models  →  "id":"qwen2.5-0.5b-q5_0"     # the new version is live

A model upgrade is now a reviewable commit with an automatic, ordered rollout — and rollback is git revert, exactly as in Phase 2.모델 업그레이드가 이제 리뷰 가능한 커밋 + 자동·순차 롤아웃이고, 롤백은 Phase 2처럼 git revert.

Result결과

A real OpenAI-compatible model server runs under Argo CD: deployed from Git, weight-loaded via initContainer, version-bumped by commit with an automatic rolling update. The workload that used to be a hand-run docker run is now a reviewable, revertible, self-healing GitOps object. Phase 4 puts the llm-d routing layer (gateway + Inference Extension + endpoint picker) in front of it — as an app-of-apps with sync waves. 진짜 OpenAI 호환 모델 서버가 ArgoCD 아래 돈다: Git에서 배포, initContainer로 가중치 로딩, 커밋으로 버전업 + 자동 롤링 업데이트. 손으로 docker run하던 워크로드가 이제 리뷰·되돌리기·self-heal 되는 GitOps 객체다. Phase 4는 그 앞에 llm-d 라우팅 계층(게이트웨이 + Inference Extension + endpoint picker)을 — sync wave 있는 app-of-apps로 — 둔다.
