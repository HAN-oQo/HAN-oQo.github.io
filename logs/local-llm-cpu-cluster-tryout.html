4-4. 이 단계의 학습 포인트

  • LB 가 stateless 가정: nginx round-robin 은 매 요청을 무지성 alternating. 그래서 같은 conversation 의 turn 1, turn 2 가 서로 다른 instance 에 갈 수 있음. KV cache hit 없음.
  • 실 production 에선 이게 문제: 같은 system prompt 시작하는 요청들이 prefix KV cache 를 공유해야 throughput 이 큼. round-robin 은 이걸 활용 못 함. → llm-d 의 prefix-cache-aware scorer 가 정확히 이걸 해결 (§8 에서 자세히).
  • Replica 확장은 trivial: 같은 모델 weights 를 N 개 process 에 로드하고 LB 뒤에 두면 됨. 단순. 어려운 부분은 prefix cache, KV transfer, prefill/decode 분리 같은 LLM 특수 사정.

6-4. 종합 결론

  1. Apple Silicon 에서는 llama.cpp 가 압도적 — vLLM-metal 은 아직 dev 단계, llama.cpp 가 Metal 활용 잘.
  2. Pod 갯수에 비례하는 성능 증가는 concurrent 부하가 단일 instance 능력 넘어설 때만. 낮은 부하면 단일이 더 효율.
  3. K8s container 화 가 GPU 활용 망가뜨림 — device plugin 명시 필수. 본 환경에선 Metal device passthrough 안 됨 → 19-27× 느림.
  4. llm-d chart 가 실 vLLM 으로 동작 시키려면 minikube 자원 부족 — 실 cluster 환경에서 측정 필요.
  5. Dynamo 는 Apple Silicon 에서 install 자체 불가 — NVIDIA + Linux 가정 강함.
  6. PDD 도 vllm-metal 의 KV connector handshake 미구현으로 불가 — 별도 로그 PD Disaggregation 시도 참조.

7. 정리 — 무엇을 얻었나 / 못 한 것

7-1. 얻은 것 ✓

  • OpenAI compatible API 의 실제 wire format 손맛 — request/response JSON, usage 필드, finish_reason, timings
  • 3 engine 시도 + 결과: vLLM pip 빌드 실패 → vllm-metal install 성공하지만 매우 느림 → llama.cpp 가 Apple Silicon 에서 압도적 실용
  • multi-replica + LB 의 Pod 갯수 비례 효과 측정: conc=1, 4 에선 거의 차이 X, conc=8 에서 1.6× — 단일 instance 한계를 넘어야 의미
  • K8s container 가 host GPU 활용 깨뜨림: 같은 llama.cpp 가 host 에선 5-13 req/s, k8s Pod 안에선 0.3-0.7 req/s (19-27× 느림). Apple Silicon Metal 안 보임. production NVIDIA 환경에서도 device plugin 명시 필수인 이유
  • llm-d 의 chart 구조 + inference-sim 의 의미: chart default 가 mock backend, 실 vLLM backend 로 교체하려면 별도 values 와 cluster 자원 필요
  • Dynamo 의 Apple Silicon install 불가: ai-dynamo-runtime wheel 없음 — NVIDIA Linux + CUDA 가정이 packaging 차원에서 강제됨
  • Step 2 의 round-robin LB 한계 직접 체험 → §8 의 llm-d / Dynamo 가 푸는 문제 정확히 보임

7-2. 못 한 것 ✗

  • vLLM 정통 PagedAttention / continuous batching 실 동작 측정 (Apple Silicon 빌드 실패, vllm-metal 은 dev 미숙)
  • llm-d + 실 vLLM backend 측정 — minikube 자원 부족 + vLLM container CPU 빌드 부담
  • NVIDIA Dynamo 실 동작 — install 자체 안 됨
  • high concurrency 부하 측정 (conc=32+) — 0.5B + Q4 모델이라 작아서 부하 의미 없음
  • prefix-cache hit rate 측정 (같은 prefix 반복 시 EPP scorer 가 같은 Pod 보내는지) — llm-d real backend 가 있어야 의미

7-3. 다음 단계 (NVIDIA Linux 환경에서)

  1. Docker 안 Linux vLLM (Apple Silicon Rosetta amd64) — 정통 PagedAttention 동작 확인. 단 emulation 으로 느림.
  2. 실 GPU node 1개 (cloud 또는 on-prem) — vLLM real + llm-d helm chart + vLLM backend swap. EPP scorer 의 prefix-cache hit rate 측정 가능.
  3. NVIDIA H100 cluster — Dynamo install + multi-node P/D disaggregation 실 측정. NIXL KV transfer 시간 측정.
  4. 비교 벤치마크: 같은 워크로드를 vLLM 단일 vs vLLM + llm-d 의 prefix-aware routing 으로 비교. throughput / KV hit rate / latency 모두 측정 → llm-d 의 실제 이점 정량화.

8. 다시 — vLLM / Dynamo / llm-d 가 각각 왜 필요한가

Step 2 의 simple round-robin LB 가 production 에서 왜 부족한지 알면 위 컴포넌트들의 존재 이유가 명확해짐. 주의: Dynamo 와 llm-d 는 같은 layer (orchestrator) 의 경쟁 솔루션이고 vLLM 은 그 아래 engine. 차례대로:

8-1. vLLM 만으론 뭐가 안 되는가

vLLM 은 한 GPU (또는 한 GPU 그룹) 안에서 inference 를 최적화하는 engine. 핵심 강점:

  • PagedAttention: KV cache 를 page 단위로 관리해서 fragmentation 제거. 같은 GPU 메모리로 훨씬 많은 concurrent request 처리.
  • Continuous batching: request 가 들어오는 대로 batch 에 합류. token-level scheduling.
  • Prefix cache (within engine): 같은 prompt 시작이면 KV reuse — 단 같은 engine instance 안에서만.

하지만 vLLM 만으로 안 되는 것:

못 하는 일왜 vLLM 만으론 안 되는가
여러 instance 로 scale-outvLLM 은 한 process. 두 instance 띄우면 두 process. 누가 어디로 갈지 분배할 사람 따로 필요
Prefill 과 Decode 의 다른 GPU 사정Prefill = compute-bound (H100 잘 활용), Decode = memory-bound (A10 도 충분). 같은 GPU 에 같이 두면 비효율. 분리하려면 누가 어떤 token 을 어디로 보낼지 조율 필요
Cross-instance prefix cachevLLM A 의 prefix cache 는 vLLM B 가 못 봄. 같은 system prompt 의 요청들이 같은 instance 로 가야 hit. 그 라우팅을 누군가 해야 함
여러 노드 / 여러 GPU 그룹한 모델이 여러 노드에 분산되어 있으면 KV cache 가 노드 사이 전송. 그 토폴로지 관리
장애 시 failovervLLM 한 process 가 죽으면 다른 instance 가 그 in-flight request 를 이어받아야 함. 이건 instance 차원 아니라 orchestrator 차원

이 모든 일을 누가 함? 그래서 orchestrator layer 가 필요. orchestrator 의 두 후보 (Dynamo, llm-d) 를 차례대로:

8-2. Dynamo 가 푸는 문제 — orchestrator option #1

NVIDIA Dynamo 는 여러 inference engine instance 를 한 cluster 처럼 묶는 orchestrator. vLLM / TRT-LLM / SGLang 등 다양한 engine 을 backend 로 받아들임. 핵심 기능:

  • KV cache aware routing: "이 요청의 prefix 가 어느 instance 의 cache 에 있는가" 를 알고 거기로 보냄. round-robin 이 아닌 cache-hit 최대화 라우팅. KV block 단위 granularity (16 token).
  • Prefill / Decode disaggregation (PDD): Prefill 전용 instance 와 Decode 전용 instance 분리. Prefill 끝나면 KV cache 만 Decode instance 로 NIXL (NVLink/RDMA) 전송. 각 GPU 의 강점 활용.
  • Multi-node 분산: 한 모델이 여러 노드에 split 되어 있을 때 token 흐름 조율.
  • SLO-driven autoscaling (Dynamo Planner 컴포넌트): TTFT/TPOT 목표에 맞춰 worker 수 자동 조절.
  • Worker management: 죽은 instance 감지, 새 instance 추가, drain.

즉 Dynamo 는 "여러 GPU 노드 위에서 inference 를 한 분산 시스템처럼 운영" 하는 orchestrator. NVIDIA 가 만들었으니 NVLink / NIXL / NCCL 등 NVIDIA 인프라 가정이 강함. 시장 포지션: NVIDIA proprietary, vertical performance 강조 ("7x throughput on NVIDIA GPUs").

8-3. llm-d 가 푸는 문제

llm-d 는 Kubernetes 위의 LLM-aware gateway + scheduler. K8s SIG-Network 의 Gateway Inference Extensions (GIE) 표준의 한 구현. 핵심:

  • K8s 의 ingress / API gateway 자리에 위치: 외부 사용자가 cluster 에 보내는 LLM 요청의 첫 진입점.
  • InferencePool CR: "어떤 Pod 들이 이 모델을 서빙하는가" 를 K8s 리소스로 선언적 관리.
  • Endpoint Picker Plugin (EPP): 각 요청에 대해 어느 Pod 으로 보낼지 plugin 기반 결정. 14 개 정도의 scorer (load, prefix-cache, latency, queue depth 등) 가 점수 매기고 picker 가 최종 선택. Prefix-cache 는 Pod 단위 (KV block 단위 X).
  • Flow control: queueing, fairness, eviction, ordering. 많은 사용자가 한꺼번에 요청해도 어느 사용자가 우선되고 누가 drop 될지 결정.
  • K8s 네이티브: helm 으로 배포, CRD 로 관리, ServiceMesh / Envoy 와 통합. CNCF sandbox 표준.

즉 llm-d 는 Dynamo 와 같은 카테고리 (K8s 위 LLM serving orchestrator). 시장 포지션: CNCF sandbox + vendor-neutral + GIE 표준 + Red Hat / Google / IBM / CoreWeave / NVIDIA 공동 founder. NVIDIA 가 Dynamo Planner / KV Cache Manager 를 llm-d 에 통합 발표 (2026).

8-4. Dynamo 와 llm-d 는 대체제다 (한 번에 정리)

결론: 대체제. 실무에선 둘 중 하나만 선택. "보완" 으로 보이려면 NVIDIA 가 Dynamo 의 component (Planner, KV Cache Manager) 를 llm-d 에 integration 하는 양다리 시각에서만 성립. 일반 organization 시각에서는 같은 카테고리 — 같은 문제 (K8s 위 LLM serving 의 routing + P/D 분리 + autoscaling) 를 다른 방식으로 푸는 경쟁 솔루션.

차원llm-d 와 Dynamo 의 관계

실무 선택 기준은 §8-5 에서 자세히.

8-5. 실무 / 시장 시각 — 둘은 경쟁 솔루션인가

위 §8-4 의 "다른 layer" 설명 정정: 깔끔하게 layer 로 나눠 보였지만 시장에서는 같은 카테고리. 실무에선 보통 하나 선택. §8-4 표가 "기능 직교성" 시각이라면, 여기는 "운영 시각".

8-6. llm-d 의 prefix-cache routing 과 Dynamo 의 KV-aware routing 의 차이

둘 다 "cache aware routing" 이라고 묶여서 같은 일 같은데 layer 가 완전히 다름. 헷갈리기 쉬워서 정리:

차원llm-d 의 prefix-cache routingDynamo 의 KV-cache aware routing
Layer 위치K8s gateway 차원 (HTTP request routing)inference engine backend 차원 (worker 선택 + KV block transfer)
Granularity (단위)Pod 단위. "이 prefix 는 Pod A 에 cache 있을 가능성 높음 → Pod A 로"KV block 단위 (보통 16 token). "block 1,2,3 은 worker A 에, block 4 는 worker B 에 있음"
Cache miss 시 대응그 Pod 이 그냥 새로 계산. Pod 끼리 격리되어 있어 다른 Pod 의 cache 활용 X다른 worker 의 cache block 을 NIXL (NVLink/RDMA) 로 가져옴 — 재계산 안 하고 transfer
메타데이터Pod 의 metrics endpoint 에서 pull (Prometheus 식). 약간 stale 가능KV block index 가 worker 간 실시간 sync (NCCL/NIXL 채널)
Backend 결합HTTP/gRPC 만으로 통신. vLLM/TRT-LLM/SGLang 모두 가능backend engine 에 KV connector hook 필요 (vLLM 의 KVConnector 등 source 차원 통합)
표준K8s SIG-Network 의 GIE 표준NVIDIA 의 독자 시스템 (NIXL 라이브러리 가정)

비유로

  • llm-d = 택시 호출 앱이 "가장 가까운 차" 매칭. 차들끼리 손님 안 바꿈. dispatcher (EPP) 가 누가 어디 있는지만 알고 최선 매칭.
  • Dynamo = 여러 가게가 같은 창고를 공유. 어느 가게든 창고에서 꺼내옴. 가게 사이 재고 (KV block) 이동 자유로움 (NIXL).

그래서 대체제가 아닌 이유 (다시)

  • llm-d 만 쓰면 Pod 끼리 cache 격리 → 같은 prefix 가 두 번째 Pod 에 가면 prefix cache miss. routing 만 똑똑할 뿐 KV 자체는 안 옮김.
  • Dynamo 만 쓰면 K8s 다중-사용자 / 다중-모델 entry 가 없음. NVIDIA cluster 안의 worker 들만 효율적으로 묶음.
  • 큰 cluster 면 둘 다: llm-d 가 "어느 InferencePool 로 보낼지" 결정 → 그 안의 Dynamo workers 가 KV block 차원 최적화. routing 이 2 단계로 일어나지만 각자 다른 문제 풀이라 redundant 아님.
요약: 같은 단어 "cache aware" 인데 llm-d 는 Pod 차원의 매칭, Dynamo 는 KV block 차원의 transfer + 매칭. cache miss 시 무엇이 일어나느냐 (재계산 vs RDMA transfer) 가 가장 큰 차이.

8-7. 한 줄 정리 + 실제 배포 시 선택

실제 배포 시나리오 두 가지 — orchestrator 를 어느 쪽으로 가느냐:

선택 가이드 (§8-5 의 표를 한 번 더):

  • 단일 모델 + 작은 cluster + GPU 1-N 대: vLLM 만으로 충분. orchestrator 없이 K8s Service LB 만으로 시작 가능.
  • K8s 위 multi-tenant + 여러 모델 + vendor-neutral / 표준 추구: llm-d 선택. CNCF sandbox + GIE 표준.
  • NVIDIA H100/H200 풀스택 + NVLink/InfiniBand 인프라 + 큰 모델: Dynamo 선택. NIXL 의 KV block transfer 활용 가능.
  • OpenShift / Red Hat / IBM 환경: llm-d (founder 라 first-party 통합).
  • 이미 Triton / NeMo 운영 중: Dynamo (NVIDIA stack 연속성).
  • 둘 다 같이 deploy: NVIDIA 가 component 차원에서 통합 작업 중. 현재로선 권장 X (routing 2번).

오늘 Step 1-2 에서 직접 본 한계 (round-robin LB 의 KV cache miss) 가 두 orchestrator 모두가 해결하려는 문제. vLLM = engine 최적화 (PagedAttention 등), Dynamo / llm-d = engine 들을 cluster 차원으로 묶는 orchestrator (둘 중 하나 선택). 작은 환경은 vLLM 만으로도 충분.
