1. 왜 이걸 하는가

vLLM / Dynamo / llm-d 같은 LLM serving stack 은 보통 H100 클러스터 + Kubernetes 환경 에서 운영. 코드를 읽거나 paper 를 본다고 손에 잡히지 않음. 직접 띄워보고 요청 흘려봐야 "아 이게 이런 거구나" 가 됨.

GPU 가 없어도 작은 모델 (0.5B-1B parameter) + CPU 면 충분히 mechanism 학습 가능. 절대 throughput 은 의미 없지만:

  • OpenAI-compatible API 가 어떻게 생겼는지
  • continuous batching 이 실제로 어떻게 동작하는지
  • KV cache 가 어디에 어떻게 잡히는지
  • multiple replica 를 LB 뒤에 두면 어떤 일이 일어나는지
  • K8s 위에서 LLM workload 가 어떤 식으로 배포되는지

이것들을 코드 / paper 가 아닌 손으로 직접 본다.

2. Stack 비교 — vLLM / Dynamo / llm-d 가 뭐가 다른가

원인: macOS Apple Silicon 용 공식 wheel 없음. pip 가 sdist 받아서 source build 시도 → vLLM 의 C extension (_C) 빌드 실패. vLLM 공식 가이드 도 macOS 는 git clone + uv source build 권장 (시간 부담 큼).

교훈: pip install vllm 가 Linux 에서는 즉시 되지만 Apple Silicon 에서는 안 됨. 가능한 정통 경로는 (a) Docker 안에서 Linux vLLM 컨테이너, (b) vllm-metal plugin (Apple Silicon 의 Metal backend, 정통 vLLM 의 공식 fork), (c) git clone + uv 로 source build. 셋 다 시간/디스크 부담 큼.

5. Step 2 — 두 instance + nginx LB (미니 cluster)

5-1. 두 번째 instance 띄우기

llama-server \
  --hf-repo Qwen/Qwen2.5-0.5B-Instruct-GGUF \
  --hf-file qwen2.5-0.5b-instruct-q4_k_m.gguf \
  --port 8081 --host 127.0.0.1 &
# → 1 초 만에 health OK (HF cache 재사용)

curl http://127.0.0.1:8080/health  # → ok
curl http://127.0.0.1:8081/health  # → ok

두 instance 가 같은 모델 weights 를 각자 메모리에 로드. RAM 사용은 약 1.5GB × 2 = 3GB (Q4_K_M 양자화).

5-2. nginx 설치 + round-robin LB 설정

brew install nginx

mkdir -p /tmp/nginx-llm
cat > /tmp/nginx-llm/nginx.conf <<'EOF'
worker_processes 1;
error_log /tmp/nginx-llm/error.log;
pid /tmp/nginx-llm/nginx.pid;
events { worker_connections 256; }
http {
  access_log /tmp/nginx-llm/access.log;
  upstream llm_pool {
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;
  }
  server {
    listen 9000;
    location / {
      proxy_pass http://llm_pool;
      proxy_set_header Host \$host;
      proxy_read_timeout 300s;
    }
  }
}
EOF

nginx -c /tmp/nginx-llm/nginx.conf -p /tmp/nginx-llm/

5-3. LB 동작 검증

for i in 1 2 3 4 5 6; do
  curl -s -o /dev/null -w "%{http_code} " \
    http://127.0.0.1:9000/v1/chat/completions \
    -H "Content-Type: application/json" \
    -d "{\"model\":\"qwen\",\"messages\":[{\"role\":\"user\",\"content\":\"say hi \$i\"}],\"max_tokens\":10}"
done
# → 200 200 200 200 200 200

6 요청 모두 성공. nginx 의 access log 에 6 POST 가 다 기록됨. nginx 기본 LB 정책은 round-robin 이라 instance 1, 2, 1, 2, 1, 2 순으로 분배.

curl client ↓ POST /v1/chat/completions ┌────────────────────────────────────┐ │ nginx :9000 (round-robin LB) │ └────────┬─────────────┬──────────────┘ ↓ ↓ ┌─────────────┐ ┌─────────────┐ │ llama-server│ │ llama-server│ │ :8080 │ │ :8081 │ │ Qwen2.5-0.5B│ │ Qwen2.5-0.5B│ │ GGUF Q4_K_M│ │ GGUF Q4_K_M│ └─────────────┘ └─────────────┘

5-4. 이 단계의 학습 포인트

  • LB 가 stateless 가정: nginx round-robin 은 매 요청을 무지성 alternating. 그래서 같은 conversation 의 turn 1, turn 2 가 서로 다른 instance 에 갈 수 있음. KV cache hit 없음.
  • 실 production 에선 이게 문제: 같은 system prompt 시작하는 요청들이 prefix KV cache 를 공유해야 throughput 이 큼. round-robin 은 이걸 활용 못 함. → llm-d 의 prefix-cache-aware scorer 가 정확히 이걸 해결 (§8 에서 자세히).
  • Replica 확장은 trivial: 같은 모델 weights 를 N 개 process 에 로드하고 LB 뒤에 두면 됨. 단순. 어려운 부분은 prefix cache, KV transfer, prefill/decode 분리 같은 LLM 특수 사정.

6. Step 3 — minikube + Service LB

6-1. 시도 안 한 이유 (솔직히)

minikube 위에 진짜 llm-d 차트를 깔려면:

  1. minikube ISO + container runtime (~ 2GB 디스크)
  2. helm install — 차트 + 의존성 컨테이너 image (~ 3-5GB)
  3. vLLM container image — Linux x86 이라 Rosetta emulation 필요. CPU mode build 가 official 한지 불명확
  4. llm-d 의 EPP, scheduler, gateway 컨테이너 — 모두 정상 동작 가정

현재 디스크 18GB 자유 공간. 가능은 하지만 시간 부담 큼 (1-2 시간), 그리고 핵심 학습 포인트 (LB + multi-replica + API) 는 이미 Step 2 에서 체득. 추가 가치 대비 비용 효율 낮음.

6-2. 했다면 어떻게 했을 것

# 1. minikube 시작 — 4 CPU, 8GB RAM 할당
minikube start --cpus=4 --memory=8g --driver=docker

# 2. 두 vLLM Pod (Deployment)
kubectl create deployment vllm-1 --image=<CPU vLLM image> \
  --replicas=2 \
  -- --model Qwen/Qwen2.5-0.5B-Instruct --port 8080

# 3. Service 만들면 자동 LB
kubectl expose deployment vllm-1 --port=8080 --type=NodePort

# 4. minikube service vllm-1 → LB URL 출력
# 5. curl 으로 요청 → kube-proxy 가 두 Pod 에 라운드로빈

# (옵션) llm-d 차트 추가
helm repo add llm-d https://llm-d.github.io/charts
helm install llm-d llm-d/llm-d \
  --set inference.backends.url="http://vllm-1:8080"
# → llm-d 의 gateway + scheduler 가 vLLM Pod 들을
#   prefix-cache aware 하게 라우팅

K8s 위에서 "Service = LB", "Deployment = replica controller" 라는 추상화는 nginx 했던 것의 K8s native 버전. llm-d 가 추가되면 그 위에서 "그냥 round-robin 이 아니라 prefix cache hit 가능성 높은 Pod 으로 라우팅" 으로 업그레이드.

다음 호스트 + 디스크 여유 있을 때 진행. (별도 로그로.)

7. 정리 — 무엇을 얻었나 / 못 한 것

7-1. 얻은 것 ✓

  • OpenAI compatible API 의 실제 wire format 손맛 (request / response JSON, usage 필드, finish_reason, timings)
  • GGUF 모델이 어떻게 자동 다운로드 + 메모리 로드되는지 (llama-server --hf-repo / --hf-file)
  • multi-replica + LB 가 단순 round-robin 일 때 한계 (KV cache hit 0, 같은 prefix 도 다른 Pod 으로 감)
  • 이게 왜 production 에서 부족한지 → §8 의 llm-d / Dynamo 가 풀려고 하는 문제 정확히 보임
  • "Apple Silicon 에서 pip install vllm 안 됨" 의 root cause (sdist + CMake 실패)

7-2. 못 한 것 ✗

  • vLLM 정통 PagedAttention / continuous batching 의 실제 동작 (llama.cpp 는 다른 구현)
  • K8s 위 cluster (minikube 안 띄움 — 시간/디스크 부담)
  • llm-d 의 prefix-cache scorer 실 동작 (Step 3 skip)
  • NVIDIA Dynamo — GPU 강한 의존, CPU 환경에선 의미 X
  • high concurrency 부하 측정 — 0.5B + Q4 모델이라 작아서 부하 의미 없음

7-3. 다음 단계 (시간/자원 있을 때)

  1. Docker 안 Linux vLLM — Apple Silicon Rosetta 로 amd64 emulation. docker run vllm/vllm-openai:latest --model facebook/opt-125m. 정통 vLLM 의 PagedAttention 실 동작 확인.
  2. minikube + simple Service LB — llm-d 없이도 K8s 위에서 LB 어떻게 동작하는지.
  3. llm-d minikube chart — prefix-cache scorer 가 실제로 같은 prompt 의 turn 2 를 같은 Pod 으로 보내는지 측정.

8. 다시 — vLLM / Dynamo / llm-d 가 각각 왜 필요한가

Step 2 의 simple round-robin LB 가 production 에서 왜 부족한지 알면 위 세 layer 의 존재 이유가 명확해짐. 차례대로:

8-1. vLLM 만으론 뭐가 안 되는가

vLLM 은 한 GPU (또는 한 GPU 그룹) 안에서 inference 를 최적화하는 engine. 핵심 강점:

  • PagedAttention: KV cache 를 page 단위로 관리해서 fragmentation 제거. 같은 GPU 메모리로 훨씬 많은 concurrent request 처리.
  • Continuous batching: request 가 들어오는 대로 batch 에 합류. token-level scheduling.
  • Prefix cache (within engine): 같은 prompt 시작이면 KV reuse — 단 같은 engine instance 안에서만.

하지만 vLLM 만으로 안 되는 것:

못 하는 일왜 vLLM 만으론 안 되는가
여러 instance 로 scale-outvLLM 은 한 process. 두 instance 띄우면 두 process. 누가 어디로 갈지 분배할 사람 따로 필요
Prefill 과 Decode 의 다른 GPU 사정Prefill = compute-bound (H100 잘 활용), Decode = memory-bound (A10 도 충분). 같은 GPU 에 같이 두면 비효율. 분리하려면 누가 어떤 token 을 어디로 보낼지 조율 필요
Cross-instance prefix cachevLLM A 의 prefix cache 는 vLLM B 가 못 봄. 같은 system prompt 의 요청들이 같은 instance 로 가야 hit. 그 라우팅을 누군가 해야 함
여러 노드 / 여러 GPU 그룹한 모델이 여러 노드에 분산되어 있으면 KV cache 가 노드 사이 전송. 그 토폴로지 관리
장애 시 failovervLLM 한 process 가 죽으면 다른 instance 가 그 in-flight request 를 이어받아야 함. 이건 instance 차원 아니라 orchestrator 차원

이 모든 일을 누가 함? 그래서 위 layer 가 필요.

8-2. Dynamo 가 푸는 문제

NVIDIA Dynamo 는 여러 inference engine instance 를 한 cluster 처럼 묶는 orchestrator. vLLM / TRT-LLM / SGLang 등 다양한 engine 을 backend 로 받아들임. 핵심 기능:

  • KV cache aware routing: "이 요청의 prefix 가 어느 instance 의 cache 에 있는가" 를 알고 거기로 보냄. round-robin 이 아닌 cache-hit 최대화 라우팅.
  • Prefill / Decode disaggregation (PDD): Prefill 전용 instance 와 Decode 전용 instance 분리. Prefill 끝나면 KV cache 만 Decode instance 로 NVLink/RDMA 전송. 각 GPU 의 강점 활용.
  • Multi-node 분산: 한 모델이 여러 노드에 split 되어 있을 때 token 흐름 조율.
  • Worker management: 죽은 instance 감지, 새 instance 추가, drain.

즉 Dynamo 는 "여러 GPU 노드 위에서 inference 를 한 분산 시스템처럼 운영" 하는 layer. NVIDIA 가 만들었으니 NVLink / NIXL / NCCL 등 NVIDIA 인프라 가정이 강함.

그럼 Dynamo 가 LB 도 함? — 일부 한다. 자체 router 가 있음. 하지만 K8s 의 일반적 ingress / API gateway 와는 다른 layer. Dynamo 의 router 는 "inference 도메인 안의 routing" 이고, K8s ingress 는 "cluster 전체의 트래픽 entry point".

8-3. llm-d 가 푸는 문제

llm-d 는 Kubernetes 위의 LLM-aware gateway + scheduler. K8s SIG-Network 의 Gateway Inference Extensions (GIE) 표준의 한 구현. 핵심:

  • K8s 의 ingress / API gateway 자리에 위치: 외부 사용자가 cluster 에 보내는 LLM 요청의 첫 진입점.
  • InferencePool CR: "어떤 Pod 들이 이 모델을 서빙하는가" 를 K8s 리소스로 선언적 관리.
  • Endpoint Picker Plugin (EPP): 각 요청에 대해 어느 Pod 으로 보낼지 plugin 기반 결정. 14 개 정도의 scorer (load, prefix-cache, latency, queue depth 등) 가 점수 매기고 picker 가 최종 선택.
  • Flow control: queueing, fairness, eviction, ordering. 많은 사용자가 한꺼번에 요청해도 어느 사용자가 우선되고 누가 drop 될지 결정.
  • K8s 네이티브: helm 으로 배포, CRD 로 관리, ServiceMesh / Envoy 와 통합.

즉 llm-d 는 "Kubernetes cluster 차원에서 LLM 트래픽의 entry + 정책 + 관측" 을 책임지는 layer.

8-4. Dynamo 와 llm-d 는 대체제인가 보완재인가

대체제도 보완재도 될 수 있음. 보는 각도에 따라:

관점대체? 보완?설명
"여러 inference instance 를 라우팅" 기능만 보면겹침 (대체 가능)둘 다 multi-instance routing 함. Dynamo 의 router 와 llm-d 의 EPP 모두 같은 일을 함. 둘 다 쓰면 routing 이 2번 일어남 (redundant)
운영 환경 측면다른 layer (보완)Dynamo = NVIDIA GPU 노드들 사이 disaggregation/KV transfer 최적화. llm-d = K8s cluster 의 일반 entry. K8s 안에서 Dynamo 가 backend 로 살고 llm-d 가 앞단에 있는 구성 가능
표준 측면다른 길llm-d 는 K8s SIG-Network 의 GIE 표준 구현. Dynamo 는 NVIDIA 의 독자 시스템. 표준 따르는 organization 은 llm-d, NVIDIA 통째 stack 으로 가는 organization 은 Dynamo
backend 측면다른 추상화llm-d 는 backend (vLLM, TGI 등) 와 디커플. EPP 는 일반 HTTP 로 backend 호출. Dynamo 는 backend 와 더 깊이 통합 (NIXL 으로 KV cache 직접 transfer 등)

8-5. 한 줄 정리 + 실제 배포 시 선택

┌────────────────────────────────────────────────────────────┐ │ K8s cluster │ │ │ │ 외부 사용자 트래픽 │ │ ↓ │ │ ┌──────────────────────────────────────────────────────┐ │ │ │ llm-d (또는 GIE 호환 게이트웨이) │ │ │ │ - cluster entry, auth, rate limit │ │ │ │ - InferencePool 별 routing │ │ │ │ - flow control / fairness │ │ │ └────────┬───────────────────┬─────────────────────────┘ │ │ ↓ ↓ │ │ ┌──────────────────┐ ┌──────────────────┐ │ │ │ InferencePool A │ │ InferencePool B │ │ │ │ (Llama-70B) │ │ (Mixtral-8x7B) │ │ │ │ │ │ │ │ │ │ Dynamo orch │ │ vLLM-only │ │ │ │ ├ vLLM #1 (P) │ │ ├ vLLM #1 │ │ │ │ ├ vLLM #2 (P) │ │ └ vLLM #2 │ │ │ │ ├ vLLM #3 (D) │ │ (no disagg) │ │ │ │ └ vLLM #4 (D) │ │ │ │ │ │ (PDD, KV xfer) │ │ │ │ │ └──────────────────┘ └──────────────────┘ │ └──────────────────────────────────────────────────────────────┘

선택 가이드:

  • 단일 모델 + 작은 cluster + GPU 1-N 대: vLLM 만으로 충분. Service LB 면 됨.
  • 여러 모델 + K8s 위 multi-tenant + 표준 GIE 따르고 싶음: llm-d 앞단 + 뒤에 vLLM. Dynamo 없이 가능.
  • 한 모델이 매우 큼 + multi-node + P/D 분리 필요: Dynamo. 이 경우 InferencePool 안의 backend 가 vLLM 단일이 아니라 Dynamo orchestrated 된 cluster.
  • 둘 다 풀로 도입: llm-d 가 K8s cluster 의 entry, 그 뒤에 Dynamo 가 큰 모델 cluster 들 orchestrate, 그 안에 vLLM 들이 engine. NVIDIA + K8s native 의 갓 구성. 단 운영 복잡도 큼.

오늘 Step 1-2 에서 직접 본 한계 (round-robin LB 의 KV cache miss) 가 위 세 layer 모두가 (각자 다른 각도에서) 해결하려는 문제. layer 가 많아 보이지만 각자 푸는 문제가 다름 — vLLM = single-engine 최적화, Dynamo = NVIDIA GPU cluster 위 disaggregation/KV-aware routing, llm-d = K8s 위 표준화된 LLM gateway. 셋이 같은 길에 같이 있을 수 있고 (각 layer 가 다른 layer 를 추상화), 하나만 있어도 작은 환경은 충분.
