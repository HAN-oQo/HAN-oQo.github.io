(b) is tried in §3-2; results in §6.: pip install vllm 가 Linux 에서는 즉시 되지만 Apple Silicon 에서는 안 됨. 가능한 정통 경로 3가지: (a) Docker 안 Linux vLLM 컨테이너, (b) vllm-metal plugin (Apple Silicon Metal backend, 정통 vLLM 의 공식 fork), (c) git clone + uv source build. 8-1. What can't be done with vLLM alone8-1. vLLM 만으론 뭐가 안 되는가

vLLM is an engine that optimizes inference within one GPU (or one GPU group). Core strengths:vLLM 은 한 GPU (또는 한 GPU 그룹) 안에서 inference 를 최적화하는 engine. 핵심 강점:

  • PagedAttention: manages KV cache in page units to remove fragmentation. Many more concurrent requests fit in the same GPU memory.: KV cache 를 page 단위로 관리해서 fragmentation 제거. 같은 GPU 메모리로 훨씬 많은 concurrent request 처리.
  • Continuous batching: requests join the batch as they arrive. Token-level scheduling.: request 가 들어오는 대로 batch 에 합류. token-level scheduling.
  • Prefix cache (within engine): KV reuse when prompt prefixes match — but only within the same engine instance.: 같은 prompt 시작이면 KV reuse — 단 같은 engine instance 안에서만.

But what vLLM alone cannot do:하지만 vLLM 만으로 안 되는 것:

8-2. The problem Dynamo solves — orchestrator option #18-2. Dynamo 가 푸는 문제 — orchestrator option #1

NVIDIA Dynamo is an orchestrator that bundles multiple inference engine instances into a cluster. It accepts various engines (vLLM / TRT-LLM / SGLang) as backends. Core features:NVIDIA Dynamo 는 여러 inference engine instance 를 한 cluster 처럼 묶는 orchestrator. vLLM / TRT-LLM / SGLang 등 다양한 engine 을 backend 로 받아들임. 핵심 기능:

  • KV cache aware routing: knows "which instance's cache holds this request's prefix" and sends there. Cache-hit-maximizing routing, not round-robin. KV block granularity (16 tokens).: "이 요청의 prefix 가 어느 instance 의 cache 에 있는가" 를 알고 거기로 보냄. round-robin 이 아닌 cache-hit 최대화 라우팅. KV block 단위 granularity (16 token).
  • Prefill / Decode disaggregation (PDD): dedicated Prefill instances and Decode instances are split. Once Prefill finishes, only the KV cache is transferred to the Decode instance via NIXL (NVLink/RDMA). Exploits each GPU's strengths.: Prefill 전용 instance 와 Decode 전용 instance 분리. Prefill 끝나면 KV cache 만 Decode instance 로 NIXL (NVLink/RDMA) 전송. 각 GPU 의 강점 활용.
  • Multi-node distributionMulti-node 분산: coordinates token flow when one model is split across nodes.: 한 모델이 여러 노드에 split 되어 있을 때 token 흐름 조율.
  • SLO-driven autoscaling (Dynamo Planner component): auto-adjust worker count to TTFT/TPOT targets.(Dynamo Planner 컴포넌트): TTFT/TPOT 목표에 맞춰 worker 수 자동 조절.
  • Worker managementWorker management: detect dead instances, add new ones, drain.: 죽은 instance 감지, 새 instance 추가, drain.

In short, Dynamo is an orchestrator that "runs inference as a distributed system on top of multiple GPU nodes". Built by NVIDIA, so assumptions of NVIDIA infrastructure like NVLink / NIXL / NCCL run strong. 8-3. The problem llm-d solves8-3. llm-d 가 푸는 문제

llm-d is an LLM-aware gateway + scheduler on top of Kubernetes. One implementation of the K8s SIG-Network Gateway Inference Extensions (GIE) standard. Core:llm-d 는 Kubernetes 위의 LLM-aware gateway + scheduler. K8s SIG-Network 의 Gateway Inference Extensions (GIE) 표준의 한 구현. 핵심:

  • Sits in the K8s ingress / API gateway slotK8s 의 ingress / API gateway 자리에 위치: the first entry point for LLM requests sent into the cluster from external users.: 외부 사용자가 cluster 에 보내는 LLM 요청의 첫 진입점.
  • InferencePool CR: declaratively manages "which Pods serve which model" as K8s resources.: "어떤 Pod 들이 이 모델을 서빙하는가" 를 K8s 리소스로 선언적 관리.
  • Endpoint Picker Plugin (EPP): per-request decision of which Pod to send to via plugins. About 14 scorers (load, prefix-cache, latency, queue depth, etc.) score and a picker makes the final selection. Prefix-cache is at Pod-level (not KV block-level).: 각 요청에 대해 어느 Pod 으로 보낼지 plugin 기반 결정. 14 개 정도의 scorer (load, prefix-cache, latency, queue depth 등) 가 점수 매기고 picker 가 최종 선택. Prefix-cache 는 Pod 단위 (KV block 단위 X).
  • Flow control: queueing, fairness, eviction, ordering. Even with many users requesting at once, decides which user is prioritized and which is dropped.: queueing, fairness, eviction, ordering. 많은 사용자가 한꺼번에 요청해도 어느 사용자가 우선되고 누가 drop 될지 결정.
  • K8s-nativeK8s 네이티브: deployed via helm, managed via CRDs, integrates with ServiceMesh / Envoy. CNCF sandbox standard.: helm 으로 배포, CRD 로 관리, ServiceMesh / Envoy 와 통합. CNCF sandbox 표준.
