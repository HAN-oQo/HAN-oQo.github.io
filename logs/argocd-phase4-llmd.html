4llm-d control plane — app-of-apps + sync wavesllm-d 컨트롤플레인 — app-of-apps + sync waves

Date: 2026-06-12 · Node: mi250-052 · Status: ✓ control-plane-as-code done · dataplane (Envoy+EPP routing) intentionally out of scope — see note작성일: 2026-06-12 · 노드: mi250-052 · 상태: ✓ 컨트롤플레인 as-code 완료 · 데이터플레인(Envoy+EPP 실라우팅)은 의도적으로 범위 밖 — 아래 주석

Goal of this phase이 단계 목표
Express the llm-d control plane as code: a single app-of-apps root that brings up the Gateway API Inference Extension (GIE) CRDs and an InferencePool in the correct order using sync waves (CRDs before the CR that needs them). This is the ArgoCD machinery you'd use to operate the real llm-d stack. llm-d 컨트롤플레인을 코드로 표현한다: 단일 app-of-apps 루트가 Gateway API Inference Extension(GIE) CRD와 InferencePool을 sync wave로 올바른 순서로 올린다(CRD를 그걸 필요로 하는 CR보다 먼저). 실제 llm-d 스택을 운영할 때 쓰는 바로 그 ArgoCD 장치다.

apps/phase4-root.yaml (app-of-apps) │ creates child Applications, applied in sync-wave order ├─ wave 0 ─► phase4-gie-crds → InferencePool / InferenceObjective / … CRDs └─ wave 1 ─► phase4-inferencepool → InferencePool CR (selector: app=model-server) │ │ ▼ ▼ CRD registered first → CR accepted (would point the EPP at the Phase-3 pods)
Fig — the llm-d slice as one app-of-apps. Apply the root, the rest unfolds in order.그림 — llm-d 조각을 app-of-apps 하나로. 루트를 적용하면 나머지가 순서대로 펼쳐진다.

What got applied무엇이 적용됐나

# apps/phase4-llmd/00-gie-crds.yaml   (child Application, wave 0)
metadata: { annotations: { argocd.argoproj.io/sync-wave: "0" } }
spec.syncPolicy.syncOptions: [ ServerSideApply=true ]   # ← avoids the Phase-1 256 KiB CRD trap

# apps/phase4-llmd/10-inferencepool.yaml  (child Application, wave 1)
metadata: { annotations: { argocd.argoproj.io/sync-wave: "1" } }

# manifests/phase4-llmd/pool/inferencepool.yaml  (the CR)
apiVersion: inference.networking.k8s.io/v1
kind: InferencePool
spec:
  selector: { matchLabels: { app: model-server } }   # ← the Phase 3 pods
  targetPorts: [ { number: 8000 } ]
  endpointPickerRef: { name: qwen-epp, port: { number: 9002 } }

Live — the waves unfold실제 — wave가 펼쳐진다

$ kubectl apply -f .../apps/phase4-root.yaml      # apply ONE object
application.argoproj.io/phase4-llmd-root created

# the root creates the two child apps; watched live:
t+33s  CRD_registered=yes   InferencePool_CR=no    # wave 0 done, wave 1 retrying
t+27s* InferencePool_CR=yes   inferencepool-app=Synced/Healthy   # wave 1 converged

$ kubectl -n argocd get applications | grep phase4
phase4-llmd-root       Synced   Healthy     # app-of-apps root
phase4-gie-crds        Synced   Healthy     # wave 0 (CRDs) — briefly Degraded while establishing
phase4-inferencepool   Synced   Healthy     # wave 1 (CR)

$ kubectl -n serving get inferencepool qwen-pool -o ...
name=qwen-pool  selector={"app":"model-server"}  port=8000  epp=qwen-epp:9002

The sync-wave ordering is the point: the CR (wave 1) cannot exist before its CRD (wave 0). Argo CD created the CRDs app first; the pool app's early attempts failed until the CRD was registered, then its retry succeeded — eventual convergence, no manual sequencing.sync-wave 순서가 핵심: CR(wave1)은 CRD(wave0) 없이 존재할 수 없다. ArgoCD가 CRD 앱을 먼저 만들고, pool 앱의 초기 시도는 CRD 등록 전까진 실패하다 재시도로 성공 — 수동 순서 지정 없이 최종 수렴.

Two real gotchas실전 함정 둘
① InferencePool v1 requires endpointPickerRef.port — without it the apply is rejected (port is required when kind is 'Service'); the pool app sat OutOfSync/Missing until fixed. ② phase4-gie-crds briefly showed Degraded while the four CRDs were still establishing (Argo CD returns empty health for a CRD until its Established condition is True), then resolved to Healthy on its own once all four reported Established=True. A transient, not a failure — a good reminder that CRD health is eventually-consistent. ① InferencePool v1은 endpointPickerRef.port 필수 — 없으면 apply 거부(port is required ...); 고치기 전까지 pool 앱이 OutOfSync/Missing. ② phase4-gie-crds가 잠깐 Degraded였다 — CRD 4개가 establishing 중일 때(ArgoCD는 CRD의 Established가 True가 되기 전까진 빈 health를 반환), 그 뒤 4개 모두 Established=True가 되자 스스로 Healthy로 풀렸다. 실패가 아니라 transient — CRD health가 eventually-consistent임을 보여주는 좋은 사례.

Honest scope — what this is and isn't정직한 범위 — 무엇이고 무엇이 아닌가

This phase delivers the control-plane-as-code: the GIE CRDs and an InferencePool that groups the model-server pods, brought up by an app-of-apps with sync-wave ordering — exactly the ArgoCD pattern you'd use for the real stack. It does not stand up the live dataplane (an Envoy-based gateway + a running EPP actually scoring endpoints and routing traffic): that needs a gateway implementation (kgateway/Istio) and the EPP image, which is heavy and flaky on a CPU kind box and adds little to the GitOps lesson. 이 단계는 컨트롤플레인 as-code를 제공한다: GIE CRD와 model-server 파드를 묶는 InferencePool을 sync-wave 순서의 app-of-apps로 기동 — 실제 스택에 쓸 바로 그 ArgoCD 패턴. 다만 라이브 데이터플레인(Envoy 기반 게이트웨이 + 엔드포인트를 실제로 스코어링·라우팅하는 EPP)은 세우지 않았다: 그건 게이트웨이 구현체(kgateway/Istio)와 EPP 이미지가 필요한데 CPU kind에선 무겁고 불안정하며 GitOps 레슨엔 보태는 게 적다.

Editor's note — connects to the Heimdall deep-dives편집자 주 — Heimdall 딥다이브와 연결
The EPP named here (qwen-epp) and the routing logic behind an InferencePool are exactly what the earlier code-level deep-dives covered: the heimdall-inference-scheduler (the EPP fork — scorers, flow control, P/D) and heimdall-aigateway. Phase 4 is the operational complement: how those components are deployed and ordered as code. Code internals there, GitOps wiring here. 여기 이름 붙인 EPP(qwen-epp)와 InferencePool 뒤의 라우팅 로직이 바로 앞선 코드 차원 딥다이브의 내용이다: heimdall-inference-scheduler(EPP fork — 스코어러·flow control·P/D)와 heimdall-aigateway. Phase 4는 그 운영 짝 — 그 컴포넌트들을 코드로 어떻게 배포·순서화하는가. 거긴 코드 내부, 여긴 GitOps 배선.

Reproduce재현

# needs Phase 1 cluster + Phase 3 model server. apply the app-of-apps root:
kubectl apply -f https://raw.githubusercontent.com/hanq-moreh/argocd-gitops-lab/main/apps/phase4-root.yaml
# watch the children + ordering:
watch -n2 'kubectl -n argocd get applications | grep phase4; kubectl get crd | grep inference; kubectl -n serving get inferencepool'
# cleanup (reverse order handled by Argo CD): kubectl -n argocd delete application phase4-llmd-root

Result결과

The llm-d control-plane slice is now a single committable unit: one kubectl apply of the root brings up CRDs then the InferencePool in dependency order, self-heals, and tears down cleanly. That's the operational backbone for running llm-d. Phase 5 attempts the part a CPU box can't fake — a real MI250 GPU under this same control. llm-d 컨트롤플레인 조각이 이제 커밋 가능한 단일 단위다: 루트를 한 번 kubectl apply하면 CRD→InferencePool이 의존 순서로 올라오고, self-heal하고, 깔끔히 내려간다. llm-d 운영의 골격이다. Phase 5는 CPU 박스가 흉내 못 내는 부분 — 같은 통제 아래의 진짜 MI250 GPU — 를 시도한다.
