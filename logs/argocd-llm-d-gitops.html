1. What Argo CD is and why it's needed1. ArgoCD가 뭐고 왜 필요한가

Argo CD is a declarative GitOps continuous-delivery tool for Kubernetes (a CNCF Graduated project). Plain version: you describe the desired state of your cluster as YAML files in a Git repository, and an agent running inside the cluster continuously makes the live cluster match that repo. ArgoCD는 Kubernetes를 위한 선언형 GitOps 지속배포(CD) 도구다 (CNCF Graduated 프로젝트). 쉽게 말하면: 클러스터가 어떤 상태여야 하는지를 Git 저장소에 YAML로 적어두면, 클러스터 안에서 도는 에이전트가 실제 클러스터를 그 저장소와 계속 일치시켜 준다.

"GitOps" — Git is the single source of truth"GitOps" — Git이 단일 진실 공급원

In GitOps the Git repo is the only place that defines what should be running. You don't kubectl apply from your laptop; you commit a change to Git, and the change reaches the cluster through the agent. So every change is a commit — meaning it is reviewable (PR), auditable (git log / who-changed-what), reproducible (rebuild a cluster from the repo), and revertible (git revert). GitOps에서 Git 저장소는 무엇이 돌아야 하는지를 정의하는 유일한 장소다. 노트북에서 kubectl apply로 직접 밀어넣지 않고, Git에 변경을 커밋하면 그 변경이 에이전트를 거쳐 클러스터에 도달한다. 그래서 모든 변경이 곧 커밋 — 즉 리뷰 가능(PR), 감사 가능(git log / 누가 무엇을 바꿨나), 재현 가능(저장소로 클러스터를 다시 구성), 되돌리기 가능(git revert).

Push CD vs Pull GitOps — the core differencePush CD vs Pull GitOps — 핵심 차이

Traditional CI/CD pushes: a CI job (Jenkins/GitHub Actions) holds cluster credentials and runs kubectl apply from outside, once, then forgets. Argo CD pulls: it lives in the cluster, watches Git, and reconciles continuously. Two practical wins: (1) cluster credentials never leave the cluster, and (2) it keeps watching, so it notices and corrects drift. 전통 CI/CD는 밀어넣는다(push): CI 작업(Jenkins/GitHub Actions)이 클러스터 자격증명을 들고 밖에서 kubectl apply를 한 번 쏘고 잊는다. ArgoCD는 당겨온다(pull): 클러스터 안에 살면서 Git을 지켜보고 계속 reconcile(조정)한다. 실무 이점 둘: (1) 클러스터 자격증명이 클러스터 밖으로 안 나가고, (2) 계속 감시하므로 drift를 알아채고 교정한다.

The reconcile loop — observe → diff → actReconcile 루프 — 관찰 → 비교 → 실행

Argo CD runs a loop: observe the desired state in Git, diff it against the live cluster, and if they differ, sync (apply the difference). Two policies make this powerful: auto-sync (apply automatically when Git changes) and self-heal (if someone hand-edits the live cluster away from Git, revert it back). "Rollback" is just syncing to an older Git revision — usually a git revert. ArgoCD는 루프를 돈다: Git의 원하는 상태를 관찰하고, 실제 클러스터와 비교(diff)하고, 다르면 동기화(sync)한다(차이를 적용). 두 정책이 이를 강력하게 만든다: auto-sync(Git이 바뀌면 자동 적용)와 self-heal(누가 실제 클러스터를 Git과 다르게 손으로 고치면 다시 Git대로 되돌림). "롤백"은 그냥 과거 Git 리비전으로 sync하는 것 — 보통 git revert.

┌──────────────────── Argo CD reconcile loop ─────────────────────┐ │ │ Git (desired) ──observe──► [ diff ] ──out-of-sync?──► [ sync/apply ] ──┼──► live cluster ▲ │ │ │ └── in-sync ──► do nothing │ │ │ └──── self-heal: live ≠ Git (누가 kubectl edit 함) → revert to Git ┘
Fig 2 — The reconciliation loop. self-heal is the arrow that makes "the cluster always matches Git" literally true.그림 2 — Reconcile 루프. self-heal 화살표가 "클러스터는 항상 Git과 일치한다"를 말 그대로 참으로 만든다.

Without GitOps, the failure mode is familiarGitOps 없이의 전형적 실패
The real config lives in someone's terminal history. Two engineers kubectl edit the same Deployment differently. A 3 a.m. hotfix is never written down, then a redeploy silently reverts it. Rollback means "does anyone remember the old replica count / image tag?" GitOps removes all four: Git is the history, the diff, the audit, and the rollback target. 진짜 설정이 누군가의 터미널 히스토리에만 있다. 두 엔지니어가 같은 Deployment를 서로 다르게 kubectl edit한다. 새벽 3시 핫픽스는 기록되지 않고, 재배포가 조용히 되돌려 버린다. 롤백은 "예전 replica 수/이미지 태그 기억하는 사람?"이 된다. GitOps는 이 넷을 전부 없앤다 — Git이 곧 히스토리이자 diff이자 감사 로그이자 롤백 대상.

2. Why Argo CD specifically for vLLM + llm-d ops2. 왜 하필 vLLM + llm-d 운영에 ArgoCD인가

A single vLLM container is easy — docker run and you're done (that's exactly the earlier mi250 P/D logs). The pain starts when you run it as a fleet under llm-d, because llm-d is a K8s-native, CRD-heavy, multi-component stack. That is precisely the shape of system GitOps was invented for. vLLM 컨테이너 하나는 쉽다 — docker run이면 끝(앞선 mi250 P/D 로그가 바로 그것). 고통은 그것을 llm-d 아래에서 여러 대(fleet)로 운영할 때 시작된다. llm-d는 K8s 네이티브에 CRD가 많고 컴포넌트가 여러 개인 스택이기 때문이다. 이게 바로 GitOps가 만들어진 이유에 해당하는 시스템 형태다.

3. Lab environment design — why kind on this node3. 실습 환경 설계 — 이 노드에서 왜 kind인가

Argo CD needs a Kubernetes cluster, and mi250-052 had none. It's a shared GPU node with no passwordless sudo and a "Docker-only, don't mutate the host" hygiene rule from earlier sessions. So the cluster has to be non-invasive and root-free. Options: ArgoCD는 Kubernetes 클러스터가 필요한데 mi250-052엔 없었다. 이 노드는 공유 GPU 노드이고 passwordless sudo가 없으며, 이전 세션들의 "Docker 전용, 호스트 건드리지 말 것" 위생 규칙이 있다. 그래서 클러스터는 비침습적이고 root 불필요해야 한다. 선택지:

The GPU caveat (handled honestly in Phase 5)GPU 단서 (Phase 5에서 정직하게 다룸)
kind nodes are containers, so exposing the MI250s to pods needs privileged nodes + /dev/kfd & /dev/dri mounts + the AMD device plugin — fiddly. But here's the key insight: Phases 1–4 (the entire GitOps + control-plane learning) need no GPU. The model servers can be tiny CPU vLLM pods. Real GPU passthrough is a stretch goal (Phase 5), with a documented fallback if it fights us. kind 노드는 컨테이너라 MI250를 파드에 노출하려면 privileged 노드 + /dev/kfd·/dev/dri 마운트 + AMD device plugin이 필요 — 까다롭다. 하지만 핵심 통찰: Phase 1–4(GitOps + 컨트롤플레인 학습 전부)는 GPU가 필요 없다. 모델 서버는 작은 CPU vLLM 파드면 된다. 실제 GPU passthrough는 stretch 목표(Phase 5)로 두고, 막히면 대안을 기록한다.

This is the classic Argo CD install trap. Client-side kubectl apply stuffs a last-applied-configuration annotation onto each object; the ApplicationSet CRD is so large the annotation blows past Kubernetes' 256 KiB limit, so that one resource silently fails while everything else applies. A. Kubernetes basics — the nouns that appear everywhereA. Kubernetes 기본 — 사방에 나오는 명사들

Kubernetes (K8s)
A container orchestrator: you declare what should run, it keeps that true across a fleet of machines (restart, reschedule, scale). "8" replaces the 8 letters in K-ubernete-s.컨테이너 오케스트레이터: 무엇이 돌아야 하는지 선언하면, 여러 머신에 걸쳐 그걸 계속 참으로 유지(재시작·재배치·스케일). K8s는 가운데 8글자 줄임.
Pod
The smallest deployable unit — one (or a few tightly-coupled) containers sharing a network/IP. Your vLLM process runs inside a Pod, not a bare container.배포의 최소 단위 — 네트워크/IP를 공유하는 컨테이너 1개(또는 밀접한 몇 개). vLLM 프로세스는 맨 컨테이너가 아니라 Pod 안에서 돈다.
Deployment
A controller that keeps N identical Pods running and does rolling updates. "Run 3 copies of this vLLM image" → a Deployment.동일한 Pod N개를 유지하고 롤링 업데이트를 하는 컨트롤러. "이 vLLM 이미지 3벌 띄워" → Deployment.
ReplicaSet / replica / rollout
replica = one copy of a Pod; a Deployment manages a ReplicaSet of them; a rollout = replacing old Pods with new ones gradually.replica = Pod 한 벌; Deployment가 그것들의 ReplicaSet을 관리; rollout = 옛 Pod를 새 Pod로 점진 교체.
Service
A stable virtual IP + DNS name in front of a changing set of Pods, with load-balancing. Pods come and go; the Service address doesn't.바뀌는 Pod 집합 앞에 두는 안정적 가상 IP + DNS 이름(부하분산 포함). Pod는 생기고 사라져도 Service 주소는 그대로.
Namespace
A logical partition of the cluster for grouping/isolating resources (e.g. everything Argo CD lives in namespace argocd).리소스를 묶고 격리하는 클러스터의 논리적 칸(예: ArgoCD 전부가 argocd 네임스페이스에).
ConfigMap / Secret
K8s objects holding config (ConfigMap) or sensitive data (Secret, base64-encoded), mounted into Pods. The EPP's scorer config is a ConfigMap.설정(ConfigMap) 또는 민감 데이터(Secret, base64)를 담아 Pod에 마운트하는 객체. EPP 스코어러 설정이 ConfigMap.
Node / control-plane
Node = a machine (or, in kind, a container) that runs Pods. control-plane = the brain (API server, scheduler, controllers) that decides what goes where.Node = Pod를 돌리는 머신(또는 kind에선 컨테이너). control-plane = 무엇을 어디 둘지 정하는 두뇌(API 서버·스케줄러·컨트롤러).
kubectl
The CLI that talks to the K8s API server (get, apply, edit, logs…). In GitOps you stop using it to change things and mostly use it to look.K8s API 서버와 대화하는 CLI(get·apply·edit·logs…). GitOps에선 바꾸는 용도로는 안 쓰고 주로 보는 용도로 쓴다.
controller / reconcile
A controller is a loop that watches desired vs actual and fixes the gap (reconcile). Argo CD is a controller; so is every Deployment under the hood.컨트롤러 = 원하는 상태 vs 실제를 보고 차이를 메우는 루프(reconcile). ArgoCD가 컨트롤러이고, 모든 Deployment도 속으로 그렇다.

B. Extension mechanism — CRDs and the llm-d resourcesB. 확장 메커니즘 — CRD와 llm-d 리소스

CRD / CR
CustomResourceDefinition teaches K8s a new kind of object; a CR is an instance of it. InferencePool is a CRD; your specific pool is a CR. This is how llm-d adds LLM-aware concepts to K8s.CustomResourceDefinition은 K8s에게 새로운 종류의 객체를 가르치고, CR은 그 인스턴스. InferencePool이 CRD, 당신의 실제 풀이 CR. llm-d가 LLM 개념을 K8s에 추가하는 방식.
Gateway API
The modern K8s standard for ingress/L7 routing: GatewayClass (which implementation), Gateway (a listener), HTTPRoute (match→backend rules). Replaces the older Ingress.인그레스/L7 라우팅의 현대 K8s 표준: GatewayClass(구현체), Gateway(리스너), HTTPRoute(매칭→백엔드 규칙). 구형 Ingress를 대체.
GIE (Inference Extension)
Gateway API Inference Extension — a SIG-Network standard that adds LLM-aware routing (load/KV-cache/SLO-aware) on top of Gateway API. llm-d implements it.Gateway API Inference Extension — Gateway API 위에 LLM 인지 라우팅(부하·KV cache·SLO 인지)을 더하는 SIG-Network 표준. llm-d가 이를 구현.
InferencePool / InferenceModel
GIE CRDs: an InferencePool groups the model-server Pods that can serve a model; InferenceModel/Objective expresses routing intent & SLOs for a model name.GIE CRD: InferencePool은 한 모델을 서빙할 수 있는 모델서버 Pod들을 묶고, InferenceModel/Objective는 모델명에 대한 라우팅 의도·SLO를 표현.
EPP (Endpoint Picker)
The inference scheduler process that, per request, picks which model Pod should serve it (prefix-cache / load / P-D aware). The Heimdall inference-scheduler is an EPP fork.요청마다 어느 모델 Pod이 처리할지 고르는 추론 스케줄러 프로세스(prefix-cache/부하/P-D 인지). Heimdall inference-scheduler가 EPP fork.
LeaderWorkerSet (LWS)
A workload type for multi-Pod groups that act as one unit — used when one model is sharded across several Pods/nodes (e.g. large TP / multi-node).여러 Pod가 한 단위로 동작하는 워크로드 타입 — 한 모델을 여러 Pod/노드로 샤딩할 때 사용(예: 큰 TP / 멀티노드).

C. Packaging & Argo CD objectsC. 패키징 & ArgoCD 객체

Helm / chart
A package manager for K8s. A "chart" is a templated bundle of manifests with values you fill in (image.tag, replicas…). llm-d ships as Helm charts.K8s의 패키지 매니저. "chart"는 값(image.tag·replicas…)을 채워 넣는 템플릿화된 매니페스트 묶음. llm-d는 Helm chart로 배포됨.
Kustomize / overlay
A template-free way to layer patches over a base set of manifests. A dev overlay and a prod overlay reuse one base — how you promote across environments.템플릿 없이 기본 매니페스트 위에 패치를 겹치는 방식. dev overlay와 prod overlay가 base 하나를 재사용 — 환경 간 승격 방법.
Application (Argo CR)
Argo CD's core object: "sync this Git repo+path to this cluster+namespace." Source can be raw YAML, Kustomize, or Helm.ArgoCD의 핵심 객체: "이 Git 저장소+경로를 이 클러스터+네임스페이스로 sync." 소스는 생 YAML·Kustomize·Helm.
ApplicationSet
A template that generates many Applications (one per cluster/env/directory) — multi-env, multi-cluster without copy-paste.여러 Application을 만들어내는 템플릿(클러스터/환경/디렉터리별 하나씩) — 복붙 없이 멀티 환경·멀티 클러스터.
AppProject
Guardrails/RBAC: which repos, clusters, namespaces, and resource kinds a group of Applications may touch.가드레일/RBAC: 한 Application 그룹이 어떤 repo·클러스터·네임스페이스·리소스 종류를 건드릴 수 있는지 제한.
app-of-apps
A pattern: one root Application whose job is to create other Applications — bootstrap a whole platform from one commit.패턴: 다른 Application들을 만드는 게 임무인 루트 Application 하나 — 커밋 하나로 플랫폼 전체 부트스트랩.
sync / sync wave / hook
sync = apply Git's desired state to the cluster. sync wave = ordering (low waves first). hook = run a Job at a phase (PreSync/PostSync), e.g. a migration.sync = Git의 원하는 상태를 클러스터에 적용. sync wave = 순서(낮은 wave 먼저). hook = 특정 단계(PreSync/PostSync)에 Job 실행, 예: 마이그레이션.
auto-sync / self-heal / prune
auto-sync = apply automatically on Git change. self-heal = revert manual drift back to Git. prune = delete resources removed from Git.auto-sync = Git 변경 시 자동 적용. self-heal = 수동 drift를 Git대로 되돌림. prune = Git에서 지워진 리소스를 클러스터에서도 삭제.
GitOps / reconcile / drift
GitOps = Git as single source of truth + an in-cluster agent reconciling to match it. drift = live cluster diverging from Git (self-heal fixes it).GitOps = Git을 단일 진실 공급원으로 + 클러스터 내부 에이전트가 거기에 맞춤. drift = 실제 클러스터가 Git과 어긋남(self-heal이 교정).

D. Cluster plumbing & GPU exposureD. 클러스터 배관 & GPU 노출

kind
"Kubernetes IN Docker" — runs each K8s node as a Docker container; root-free, seconds to create/destroy. Our lab cluster."Kubernetes IN Docker" — 각 K8s 노드를 Docker 컨테이너로 실행; root 불필요, 생성/삭제 초 단위. 우리 실습 클러스터.
containerd / CNI
containerd = the container runtime that actually runs Pods (below K8s). CNI = the plugin that gives Pods networking/IPs. You saw both in the Phase 1 output.containerd = Pod를 실제로 돌리는 컨테이너 런타임(K8s 아래). CNI = Pod에 네트워킹/IP를 주는 플러그인. Phase 1 출력에서 둘 다 봤다.
StorageClass / PVC / initContainer
PVC (PersistentVolumeClaim) = a Pod's request for disk; StorageClass = how that disk is provisioned. initContainer = a setup container that runs before the main one (e.g. download model weights).PVC = Pod의 디스크 요청; StorageClass = 그 디스크를 어떻게 만들지. initContainer = 본 컨테이너 전에 도는 준비 컨테이너(예: 모델 가중치 다운로드).
RBAC / ServiceAccount
RBAC = role-based access control (who/what may do which API action). ServiceAccount = an identity for in-cluster processes (Argo CD's controllers each have one).RBAC = 역할 기반 접근 제어(누가/무엇이 어떤 API 동작을 할 수 있나). ServiceAccount = 클러스터 내부 프로세스의 신원(ArgoCD 컨트롤러마다 하나씩).
port-forward
kubectl port-forward tunnels a local port to a Pod/Service inside the cluster — how we reach the Argo CD UI without exposing it publicly.kubectl port-forward는 로컬 포트를 클러스터 내부 Pod/Service로 터널링 — ArgoCD UI를 공개하지 않고 접근하는 방법.
device plugin (amd.com/gpu)
A DaemonSet that advertises hardware (GPUs) to K8s as a schedulable resource like amd.com/gpu: 1. Needs /dev/kfd & /dev/dri (ROCm device files) reachable by the Pod.하드웨어(GPU)를 K8s에 amd.com/gpu: 1 같은 스케줄 가능한 자원으로 광고하는 DaemonSet. Pod이 /dev/kfd·/dev/dri(ROCm 장치 파일)에 닿아야 함.
privileged containerprivileged 컨테이너
A container granted near-host-level access (devices, capabilities). Needed to push GPU device files into a kind node — and exactly why it's a Phase 5 stretch.호스트에 가까운 권한(장치·capability)을 받은 컨테이너. GPU 장치 파일을 kind 노드에 넣으려면 필요 — 그래서 Phase 5 stretch인 이유.
server-side vs client-side applyserver-side vs client-side apply
client-side apply stamps a last-applied annotation (256 KiB cap → broke our CRD); server-side apply lets the API server merge fields with no such annotation. Use --server-side for big CRDs.client-side apply는 last-applied 어노테이션을 박음(256 KiB 한도 → 우리 CRD 깨짐); server-side apply는 API 서버가 필드를 병합해 그 어노테이션이 없음. 큰 CRD엔 --server-side.
