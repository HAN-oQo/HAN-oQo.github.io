MI250 P/D Disaggregation 2차 — TP=4+4 실 실험

작성일: 2026-06-12 · 환경: mi250-052 (AMD MI250 OAM × 4 = 8 GCD, ROCm) · vLLM 0.11.2.dev673+g839868462 (rocm/vllm:latest, 최신 dev build) · 1차 실험 (v0.10.0 가정) 의 다음 단계로 TP=4+4 P/D + bidirectional 가능 여부 검증.

2. "Bidirectional" 의 실 의미 + 진행 방식

vLLM P2pNcclConnector 의 KV 전송은 본질적으로 단방향 — 한 instance 의 kv_role 이 평생 kv_producer 또는 kv_consumer 중 하나로 고정. config 옵션의 이름도 "producer / consumer" 라 양방향성이 없음.

그렇다면 본 실험의 "bidirectional" 의 실 의미는?

해석실 의미본 실험에서?
해석 A — 한 instance 가 동시 P + DX. vLLM 의 KVConnector framework 가 instance role 고정.불가
해석 B — XpYd (여러 P + 여러 D mesh)proxy 가 N P + M D 등록 후 routing. PR #18242 가 지원.가능, 단 8 GCD 라 TP=2+2+2+2 같이 작아져야
해석 C — Dual-instance (한 host 에 P + D 컨테이너 따로)모델 weights 중복 load. TP=4+4 가 이것.본 실험 노선
해석 D — 통신 방향 (P→D) 의 multi-channel parallelTP=4 라 rank 4 개가 동시 송신 — "양방향" 은 아니나 "병렬 4 채널"본 실험 확인

본 실험은 해석 C + 해석 D 의 조합: 같은 host (mi250-052) 에 P container (TP=4, GCD 0-3) + D container (TP=4, GCD 4-7), 4 NCCL Comm 으로 KV 4 채널 병렬 전송. 진정한 "양방향" (해석 A) 은 vLLM 코드 자체가 막아서 본 글에서 다루지 않음.

5-5. 각 config 옵션 의미 — TP=4+4 특이 사항

config값의미 — TP=4+4 에서
--tensor-parallel-size 44각 instance 내부 4 worker process. NCCL world size=4 (TP allreduce 용).
HIP_VISIBLE_DEVICESP=0,1,2,3 / D=4,5,6,7P 는 OAM1+2 의 4 GCD, D 는 OAM3+4 의 4 GCD. 같은 host 라도 OAM 분리.
--shm-size=32g32 GBNCCL shared memory. TP=1 때 16g 였음 — TP=4 라 worker 4 개 → 2 배
kv_port (top-level)P=20001 / D=22001ZMQ port 의 base. rank i 의 실 ZMQ = kv_port + i. P=20001-20004, D=22001-22004.
zmq_addr in extra_config(쓰지 말 것)v0.10.0 image 에선 무시됨. 실 ZMQ 는 kv_port 가 결정. 시도 #4 의 충돌 원인.
kv_buffer_sizeP=1e1 / D=8e9P 의 PUT_ASYNC queue depth 작게 (PR #18242 권장). D 는 미수신 KV pile-up 허용 크게.
send_typePUT_ASYNCP 가 fire-and-forget. P 가 send 후 즉시 다음 prefill 시작.
nccl_num_channels16RCCL ring channel. MI250 OAM 간 XGMI 4-link 위에서 16 channel 다중화 (oversubscribed but RCCL 이 scheduling).
--enforce-eagerflaghost ROCm 6.2 / image ROCm 7.0 mismatch 우회 (1차 실험에서 확정).

6-3. 분석

관찰의미
4 쌍 NCCL Comm 이 동시 (같은 timestamp) init 완료Deadlock 없음 — 4 쌍 핸드셰이크가 ZMQ 위에서 동시에 진행되어도 race 없음
P 의 모든 rank 가 MyRank:0각 NCCL Comm 안에서 P 가 rank=0 (sender), D 가 rank=1 (receiver). size=2 NCCL Comm.
P rank i ↔ D rank i 1:1 매칭port + self._rank 코드 (connector.py L245) 가 보장. 같은 rank 끼리.
총 NCCL Comm 수 = 4 (P-D 쌍) + 1 (P 내부 TP) + 1 (D 내부 TP) = 6 개vLLM 의 TP world 와 KV transfer Comm 이 다른 group. 충돌 없음 (다른 unique_id)

10. 일방 (PUT_ASYNC) 통신 의 실 동작 — Bidirectional 됐는가에 대한 답

본 실험 = Bidirectional 아닙니다. P → D 한 방향만 흘렀습니다. 글 제목에 "Bidirectional" 이 들어갔지만, vLLM v0.10.0 의 P2pNccl 자체가 한 instance 의 role 을 평생 고정하므로 진정한 양방향 (한 instance 가 동시에 P + D) 은 본질적으로 불가능. 본 글의 §2 표 도 그걸 admit. TP=4+4 가 한 것은 "4 channel 병렬 한 방향 송신 + phase 분리" 임.

10-1. "되지 않았다" 의 3 가지 증명

10-3. 본 실험의 KV 통신 방향 — P → D 한 방향만

P 측 로그의 화살표 👉 와 D 측의 👈 가 정확히 일치 — vLLM source 의 emoji 가 "from sender's perspective" 와 "from receiver's perspective" 로 다름. 한 방향만 흐름.

side활성 함수비활성 함수
P (kv_producer)save_kv_layer() → send_tensor() → NCCL ncclSendstart_load_kv() 첫 줄 if self.is_producer: return
D (kv_consumer)start_load_kv() → recv_tensor() → NCCL ncclRecv → inject_kv_into_layer()save_kv_layer() 첫 줄 if not self.is_producer: return

본 실험에서 P 가 send_tensor 4 channel 병렬, D 가 recv_tensor 4 channel 병렬 — "양방향" 아니고 "한 방향 + 4 channel".

10-2. PUT_ASYNC 의 fire-and-forget — 5.6s vs 0.8s 의 의미

2nd chat 이 0.8s 인 이유 — PUT_ASYNC 라 P 가 send 후 즉시 next prefill 시작 (queue 에 던지고 return). NCCL Comm reuse 까지 합쳐 latency 압축.

# engine.py L420 — PUT_ASYNC path
if self.send_type == "PUT_ASYNC":
    self.send_queue.put((tensor_id, tensor, dst_addr))
    return  # ← fire-and-forget, P 의 forward 가 계속 진행

# 백그라운드 thread (L460-490)
while True:
    (id, tensor, addr) = self.send_queue.get()
    self.nccl.ncclSend(tensor, peer_rank, comm)
    # 이게 wall clock 의 critical path 와 분리

10-3. 만약 PUT (sync) 였다면?

P 가 send 끝까지 block. concurrent 시나리오에서 한 prefill 이 끝날 때까지 다음 prefill 시작 못 함. 본 실험의 3 parallel (1.5s) 이 5-6s 수준으로 느려질 가능성.

PR #18242 가 PUT_ASYNC 를 default 로 설정한 이유 — concurrent throughput 위해. 단 PUT_ASYNC 는 queue overflow 가능성 (queue 가 P 의 producer 속도보다 느린 NCCL transfer 따라잡지 못하면).

10-4. "Bidirectional" 의 가능성 — 본 실험에서 시도하지 않은 이유

의미본 실험 시도 여부왜
한 instance 동시 P+D (해석 A)시도 XvLLM 의 KVConnector framework 가 instance role 고정. 시도해도 코드 자체가 block.
XpYd mesh (해석 B)미진행8 GCD 라 TP=4+4 이상 분할 불가능. 2P+2D (TP=2+2+2+2) 가 가능하지만 모델 1.5B 라 TP=2 의 NCCL overhead 가 compute 보다 큼. 큰 모델 (8B+) 로 의의.
Dual-instance per host (해석 C)본 실험본 글 §5-§9 가 정확히 이것.
P→D + D→P 양방향 KV exchangevLLM 미지원D 가 P 에 KV 보내는 path 없음. multi-turn KV reuse 는 D 내부 cache 로 — 또는 proxy 가 cache hit detection 후 P skip.

11. 결론 + 다음 실험

11-1. 결론

  • TP=4+4 P/D 가 실 mi250-052 위에서 동작. 8 회 시도 후 성공. 핵심 디버깅은 (1) JSON port int → string, (2) zmq_addr extra_config 무시 + kv_port top-level 사용.
  • 4 쌍 NCCL Comm 동시 init 이 deadlock 없이 됨. P rank i ↔ D rank i 1:1 매칭. KV transfer 가 4 channel 병렬.
  • P/D phase 분리가 monitoring 으로 확정. 8 parallel load 중 P GCD 0% / D GCD 70-99%.
  • Bidirectional = 안 됐음. KV 가 P → D 한 방향만 흐름. 3 가지 증명 (handshake 화살표, send/recv 함수 분리, instance role 고정 코드) — 자세히는 §10-1.
  • 최신 vLLM (0.11.2.dev673) 으로 재검증 해도 결과 동일. Mooncake 가 코드상 kv_both 지원하지만 CUDA 12 전용 (libcudart.so.12) 라 ROCm/MI250 사용 불가. NIXL / LMCache 도 의존성 미포함.
  • "Bidirectional" 의 본 실험에서의 실 의미 = "한 host 에 P+D 분리 + KV 4 채널 병렬 전송". 진정한 양방향은 NVIDIA + Mooncake 환경이라야 시도 가능.
  • PUT_ASYNC 가 concurrent throughput 의 핵심. 5.6s (cold) → 0.8s (warm reuse) → 1.5s (3 parallel) 의 패턴 확인.

11-3. 다음 실험 (남은 과제)

  1. 큰 모델 (8B+) 로 TP=4+4 다시 — 1.5B 는 TP=4 의 NCCL overhead 가 compute 보다 클 수 있어 TP=4 의 효과가 small. 8B / 13B 로 비교 의미 ↑
  2. Throughput 정량 — single TP=8 baseline vs PDD TP=4+4 — 같은 host 에 동시 띄울 VRAM 부족. host 2 개 (mi250-052 + mi250-053) 로 분리 + 같은 워크로드 (conc 1/4/16/32, prompt len 512/2048).
  3. send_type 비교 — PUT_ASYNC vs PUT (sync) vs GET — 같은 워크로드에서 latency / throughput 측정. PR #18242 의 default PUT_ASYNC 가 항상 우수한지.
  4. nccl_num_channels 4 vs 16 vs 32 — MI250 OAM 간 XGMI 4 link 위에서 채널 수 효과. small KV 일수록 4 가 충분, large 일수록 16 이 유리할 가설 검증.
  5. multi-turn KV reuse — 같은 conversation 의 2nd turn 에 P skip + D cache hit. proxy 가 cache hit detection 하는지 검증 (현재는 안 함).
  6. P 와 D 를 다른 host 로 분리 — mi250-052 (P, TP=8) + mi250-053 (D, TP=8). cross-host NCCL bandwidth 측정. 본 실험은 same-host XGMI.
  7. XpYd (2 P + 2 D) — 4 instance 가 같은 host 에. TP=2 씩. proxy 의 routing 분산 동작 확인.
  8. SharedStorage / NixlConnector / Mooncake 와의 성능 비교 — connector 별 KV transfer overhead.
