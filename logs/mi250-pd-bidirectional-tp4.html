1. 실험 목표

이전 실험 (§10 결론) 에서 다음 단계로 multi-turn bidirectional + TP=4+4 로 KV reuse 효과 정량화 를 잡았음. 본 실험은 그 첫 단계 — 다음 3 질문에 답.

질문본 글에서의 답

"Bidirectional" 의 다른 합당한 해석은 무엇이며 어떻게 구현 가능한가?4 해석 중 2 개 가능 — XpYd mesh / dual-instance per host. MultiConnector 로 동시 multi-role 일부 (§5)

3-2. is_producer 값은 어떻게 정해지나

KVTransferConfig.is_kv_producer 는 vLLM 띄울 때의 --kv-transfer-config 옵션 kv_role 에서 옴.

# vllm serve 의 --kv-transfer-config
'{"kv_connector":"P2pNcclConnector",
  "kv_role":"kv_producer",            # ← 또는 "kv_consumer"
  ...}'

가능한 값 3 개: kv_producer / kv_consumer / kv_both. 그러나 P2pNccl 에선 kv_both 가 작동 안 함 — is_producer 가 bool 이라 둘 중 하나만.

3-3. send_tensor / recv_tensor 분리

Engine 안에서도 send 와 recv 가 별 함수로 명확히 분리.

함수line호출자
send_tensor()L200오직 save_kv_layer → producer 만
recv_tensor()L255오직 start_load_kv → consumer 만
wait_for_sent()L419producer 의 PUT_ASYNC queue flush
get_finished()L468양쪽 다 (lifecycle 종료 알림용)

한 instance 에서 send_tensor 와 recv_tensor 가 동시에 사용 되는 코드 path 가 없음 — connector 의 entry point (start_load_kv / save_kv_layer) 가 role 로 갈라서 둘 중 하나만 활성.

결정적 결론: P2pNccl 은 한 instance 가 동시에 P + D 못 함. is_producer 값 하나로 일생 role 결정. 이건 ZMQ control 채널 부재 같은 인프라 문제가 아니라 connector class 자체의 의도된 설계.

5. "Bidirectional" 의 4 가지 해석 + 각각 가능 여부

사용자 요청의 "bidirectional" 의 가능한 의미 4 가지. 각각 코드 차원에서 가능한지 검증.

5-1. 해석 A — 한 instance 가 동시에 P + D (true symmetric)

불가능. §3, §4 의 코드 증거. is_producer 가 instance 평생 1회 set. 같은 process 가 동시에 send_tensor + recv_tensor path 가 활성될 수 없음.

구현하려면 vLLM core (KVConnectorBase_V1) 의 인터페이스 자체를 수정. start_load_kv 와 save_kv_layer 둘 다 항상 활성되도록. 그러나 그러면 schedule 측에서 P / D 구분이 사라져 새 routing layer 필요. 본질적 refactor.

5-2. 해석 B — XpYd mesh (여러 P, 여러 D, 다대다)

이미 가능. PR #18242 의 proxy (disagg_proxy_p2p_nccl_xpyd.py) 가 정확히 이걸 위한 것. proxy 가 prefill 노드 N 개 + decode 노드 M 개 등록 후 routing.

예: 2 P + 2 D 의 cmd 모형 (4 instance)

# Prefill A: port 20001 + ZMQ 21001
docker run --name vllm-P-A ... -e HIP_VISIBLE_DEVICES=0,1 \
  rocm/vllm:latest vllm serve Qwen/Qwen2.5-1.5B-Instruct \
    --tensor-parallel-size 2 --port 20001 \
    --kv-transfer-config '{"kv_connector":"P2pNcclConnector",
      "kv_role":"kv_producer",
      "kv_connector_extra_config":{"send_type":"PUT_ASYNC",
        "proxy_ip":"192.168.3.52","proxy_port":30001,
        "zmq_addr":"192.168.3.52:21001"}}'

# Prefill B: port 20002 + ZMQ 21002
docker run --name vllm-P-B ... -e HIP_VISIBLE_DEVICES=2,3 \
  ... --port 20002 \
    "zmq_addr":"192.168.3.52:21002"

# Decode A: port 22001 + ZMQ 23001
docker run --name vllm-D-A ... -e HIP_VISIBLE_DEVICES=4,5 \
  ... --kv-transfer-config '{...,"kv_role":"kv_consumer",...,
        "zmq_addr":"192.168.3.52:23001"}'

# Decode B: port 22002 + ZMQ 23002
docker run --name vllm-D-B ... -e HIP_VISIBLE_DEVICES=6,7 ... 23002

Proxy 는 4 instance 모두 등록 후, 요청 받으면 P-A or P-B 중 load 적은 곳에 prefill, 그 결과를 D-A or D-B 중 routing. 4 인스턴스 모두 8 GCD 에 분산. 단 "한 instance 가 양쪽" 은 여전히 아님.

5-3. 해석 C — Dual-instance per host (같은 host 에 P + D 둘 다)

가능 — 그러나 메모리 낭비. 같은 host (mi250-052) 에 vLLM container 2 개. instance1 = P (GCD 0-3), instance2 = D (GCD 4-7). 모델 weights 가 양쪽에 중복 load.

이게 우리의 TP=4+4 시나리오. §6, §7 에서 cmd 작성.

5-4. 해석 D — MultiConnector 로 한 instance 가 여러 channel 동시

일부 가능 — 단 multi-role 가 아니라 multi-transport. 한 P instance 가 SharedStorage 와 P2pNccl 두 connector 동시 등록 가능. 두 path 로 같은 KV 보냄 (redundancy / hierarchical caching). 그러나 그 instance 는 여전히 P role.

cmd 예시:

--kv-transfer-config '{
  "kv_connector":"MultiConnector",
  "kv_role":"kv_producer",
  "kv_connector_extra_config":{
    "connectors":[
      {"kv_connector":"P2pNcclConnector",
       "kv_role":"kv_producer",
       "kv_connector_extra_config":{"send_type":"PUT_ASYNC",...}},
      {"kv_connector":"SharedStorageConnector",
       "kv_role":"kv_producer",
       "kv_connector_extra_config":{"shared_storage_path":"/shared_kv"}}
    ]
  }
}'

두 connector 가 동시 등록되어 save_kv_layer 가 두 곳에 send. D 측은 그 중 빠른 쪽 (보통 P2pNccl) 으로 받음. SharedStorage 는 backup / debugging 용.

6. TP=4+4 코드 흐름 — NCCL world / KV layout / rank 매칭

6-1. vLLM 의 TP 가 NCCL world 어떻게 만드나

# vllm serve --tensor-parallel-size 4
# → mp.spawn 으로 4 worker process 생성
# → 각 worker 가 자기 rank (0,1,2,3) 에 GPU device 할당
# → NCCL Comm 초기화 (world_size=4, ranks=[0,1,2,3])
# → 모델 weights 가 head dim 으로 split (예: num_heads=12 → 12/4=3 head/rank)

P 와 D 가 각각 별도 vLLM container 라 NCCL world 도 분리. 2 개 NCCL world:

World구성용도
NCCL world P (size=4)P container 의 GCD 0,1,2,3P 내부 TP allreduce
NCCL world D (size=4)D container 의 GCD 4,5,6,7D 내부 TP allreduce

6-2. KV transfer 용 별도 NCCL group — rank 별 1:1 매칭

KV 전송은 위 2 world 와 별개의 NCCL Comm. P2pNccl source 의 결정적 라인:

# vllm/distributed/kv_transfer/kv_connector/v1/p2p/p2p_nccl_connector.py L244-249
for request in connector_metadata.requests:
    request_id = request.request_id
    ip, port = self.parse_request_id(request_id, True)
    remote_address = ip + ":" + str(port + self._rank)   # ← rank 별 다른 port
    self.p2p_nccl_engine.send_tensor(
        request_id + "#" + layer_name, kv_layer, remote_address, ...)

port + self._rank 가 핵심. P 의 rank 0 → D 의 base_port + 0 으로 보냄. P 의 rank 1 → D 의 base_port + 1.

6-3. TP=4+4 의 P↔D rank 매칭 다이어그램

┌─────────────────────────────┐ ┌─────────────────────────────┐ │ P container (TP=4) │ │ D container (TP=4) │ │ GCD 0,1,2,3 │ │ GCD 4,5,6,7 │ │ │ │ │ │ rank0 ──── NCCL Comm 0 ────┼─────────┼──── rank0 (ZMQ :20001) │ │ rank1 ──── NCCL Comm 1 ────┼─────────┼──── rank1 (ZMQ :20002) │ │ rank2 ──── NCCL Comm 2 ────┼─────────┼──── rank2 (ZMQ :20003) │ │ rank3 ──── NCCL Comm 3 ────┼─────────┼──── rank3 (ZMQ :20004) │ │ │ │ │ │ │ NCCL world P (TP allreduce)│ │ NCCL world D (TP allreduce)│ └─────────────────────────────┘ └─────────────────────────────┘ GCD 0-3 사이 XGMI 200 GB/s GCD 4-7 사이 XGMI 200 GB/s P↔D 사이는 GCD 같은 OAM 이면 200 GB/s, 다른 OAM 이면 4-link via XGMI hop

4 개의 NCCL Comm 이 P-D 사이에 동시 존재. 각 Comm 은 rank 1 pair 만 (size=2). port + rank 식으로 ZMQ handshake 가 매칭.

6-4. KV cache shape — TP=1 vs TP=4 비교

설정Layer 별 KV shape한 request 의 KV 총 크기 (Qwen2.5-1.5B, prompt 32 tok)
TP=1[2, num_blocks, page_size, 12, 128] (Qwen2.5 num_heads=12)약 564 KB (28 layer × 2 × 32 tok × 12 head × 128 head_dim × 2 byte)
TP=4[2, num_blocks, page_size, 3, 128] (head 분할 12/4=3)각 rank 약 141 KB (564/4), 4 rank 동시 transfer → 총 wall time 은 비슷

TP=4+4 의 이론적 장점: KV transfer 도 parallel 4 channel. 한 rank 의 데이터양은 1/4 이지만 4 채널 동시라 wall time 은 유사. NCCL channel 수 (nccl_num_channels=16) 가 충분히 크면 link 활용도 ↑.

6-5. TP=4+4 에서 새로 등장하는 문제 (TP=1+1 에 없던)

문제왜 새로 등장대응
ZMQ port 4 개 동시 bind (한 host)각 rank 가 다른 port 사용. 4 + 4 = 8 port 필요port 범위 미리 reserve. port_offset 충돌 회피
NCCL Comm init 시 deadlockP rank 0 가 D rank 0 와 handshake. 동시에 P rank 1↔D rank 1, ... 4 쌍 동시. 만약 ZMQ 우선순위 다르면 hangP 와 D 모두 같은 순서로 initialize. PR #18242 의 default 가 보장
GCD pair OAM 같은지 다른지에 따른 bw 차이GCD 0↔4 가 같은 OAM? MI250 의 4 OAM × 2 GCD 토폴로지. 0,1 = OAM1, 2,3 = OAM2, 4,5 = OAM3, 6,7 = OAM4. P(0,1,2,3)↔D(4,5,6,7) 는 모두 다른 OAMOAM 간 XGMI 4 link 활용도 확인 필요. rocm-smi --shownodesbw 로 측정
1.5B 모델 + TP=4 의 VRAM 분산 효율 X1.5B 가 너무 작아 TP=4 의 overhead (NCCL allreduce) 가 compute 보다 큼큰 모델 (8B+) 로 본 실험 의의. 또는 TP=2+2 로 절충

9. 일방 통신 (PUT_ASYNC) vs Bidirectional 의 코드 흐름 차이

본 글의 핵심 — 사용자 요청. "일방 통신 vs bidirectional" 의 코드 차원 정확한 차이.

9-1. PUT_ASYNC (일방, P→D push) 의 코드 흐름

┌─ P container (kv_producer) ────────────────────────────────────┐ │ 1. forward() │ │ 2. each layer: │ │ save_kv_layer(layer_name, kv_layer) │ │ └─ if not self.is_producer: return ← 분기 통과 │ │ └─ self.p2p_nccl_engine.send_tensor(req_id+"#"+layer, │ │ kv_layer, remote_address) │ │ └─ 만약 send_type == "PUT_ASYNC": │ │ self.send_queue.put((..., kv_layer)) │ │ return immediately ← fire-and-forget │ │ 3. async thread: │ │ while True: │ │ (id, addr, tensor) = self.send_queue.get() │ │ nccl.ncclSend(tensor, peer_rank, comm) ← 실 RCCL transfer│ └────────────────────────────────────────────────────────────────┘ │ │ NCCL ncclSend(...) → 16 channel RCCL ring → XGMI ▼ ┌─ D container (kv_consumer) ────────────────────────────────────┐ │ 1. start_load_kv(forward_context) │ │ └─ if self.is_producer: return ← 분기 통과 │ │ └─ for request in metadata.requests: │ │ for layer in no_compile_layers: │ │ kv_cache = self.p2p_nccl_engine.recv_tensor( │ │ req_id+"#"+layer) │ │ └─ self.recv_store[id].get_or_wait() │ │ ← 백그라운드 thread 가 nccl.ncclRecv() 로 받아 │ │ self.recv_store[id] = tensor │ │ inject_kv_into_layer(kv_cache_layer, kv_cache, ...) │ │ 2. forward() ← KV 이미 inject 됨, normal decode │ └────────────────────────────────────────────────────────────────┘

9-2. "Bidirectional" 의 가설적 코드 흐름 (해석 A — 한 instance 양쪽)

vLLM 에 없으니 가설적으로 어떻게 생겨야 하는가:

┌─ Hybrid container (kv_role=kv_both, 가설) ────────────────────┐ │ 1. forward() │ │ 2. each layer: │ │ save_kv_layer(layer_name, kv_layer): │ │ ├─ 만약 이 request 가 prefill 요청이면: │ │ │ self.engine.send_tensor(req_id+"#"+layer, ..., D_addr) │ │ └─ 만약 이 request 가 decode 요청이면: │ │ (skip — D 는 generate 만) │ │ │ │ start_load_kv(forward_context): │ │ ├─ 만약 이 request 가 decode 요청이면: │ │ │ kv = self.engine.recv_tensor(req_id+"#"+layer) │ │ │ inject_kv_into_layer(...) │ │ └─ 만약 prefill 요청이면: │ │ (skip — P 는 외부 KV 안 받음) │ │ │ │ ← 즉 request 단위로 role 분기 (instance 단위 X) │ │ ← scheduler 가 "이 request 는 prefill mode" 표시 줘야 │ └────────────────────────────────────────────────────────────────┘

이게 vLLM core 의 무엇이 바뀌어야 가능한가:

10. 결론

10-1. 코드 분석 결론

  • vLLM v0.10.0 의 모든 KV connector 는 단방향 (한 instance = 한 role). P2pNccl / NIXL / SharedStorage / MultiConnector / LMCache / Mooncake 전부 같은 분기 구조 (is_producer).
  • "진정한 bidirectional" (한 instance 가 동시에 P + D) 은 vLLM core 의 KVConnector framework refactor 필요. 단순 새 connector 추가로 안 됨.
  • 합당한 대안 2 가지: (B) XpYd mesh — PR #18242 의 proxy 가 이미 지원. (C) Dual-instance per host — 모델 weights 중복이지만 구현 단순. 본 글의 §7 cmd 가 해석 C.

10-2. TP=4+4 vs TP=1+1 의 차이 (코드 + 메모리)

  • NCCL world 수: 동일 (P world + D world + KV transfer Comm) — TP 값과 무관
  • KV transfer Comm 수: TP=N+N → N 개 (P rank i ↔ D rank i pair 별). TP=1+1 → 1 개. TP=4+4 → 4 개
  • 한 rank 의 KV 크기: TP=4 → 1/4. wall time 비슷 (4 parallel)
  • ZMQ port: rank 별로 별 port. TP=N → N port per role. TP=4+4 → 4+4=8 port
  • 모델 head 분할: Qwen2.5-1.5B num_heads=12 → 12/4=3 head/rank — 가능. 단 head 수가 TP 의 약수여야

10-3. 본 작업의 한계

  • SSH unreachable — 실 GPU 실행 못 함. 시도 #1~#25 중 분석 / 추정 / 가설은 다수, 실 측정은 0. NCCL deadlock / nccl_num_channels 효과 / OAM 토폴로지 bandwidth 등은 SSH 복구 후 verify 필요.
  • 코드 정적 분석 만으로 확정 가능한 결론: bidirectional 불가 (§3, §4), TP=4+4 의 NCCL Comm 매칭 패턴 (§6).
  • 코드 정적 분석 만으로 확정 불가: TP=4+4 의 실 throughput / latency, 같은 host 의 PCIe 경합, OAM 간 bandwidth.
