GenRM — 보상모델을 루프에 넣기 (negative result · 아키텍처 교훈, MI250)

환경: mi250-052 (MI250, ROCm 7.2.3) · Docker 전용 · verl 0.8.0 GRPO · Qwen2.5-0.5B · LLM-as-judge 보상 · 2 GCD

2026-06-15

한 줄 요약. 보상을 규칙/테스트가 아니라 LLM-as-judge(별도 모델 추론)로 만들려 했다. 결과는 실패(negative result)지만 교훈이 명확하다: 모델-as-보상은 colocate GRPO 트레이너의 reward 함수에 그냥 끼워넣을 수 없다. judge를 GPU에 올리면 FSDP 학습의 RCCL 집합통신과 충돌해 NCCL이 타임아웃되고, CPU에 올리면 너무 느려 동기화된 학습 루프를 NCCL watchdog(1800초)·잡 타임아웃까지 마비시킨다(4샘플에서도). 즉 보상이 "또 하나의 모델 추론"이 되는 순간, 그것은 전용 서빙 인프라(자체 GPU·자체 프로세스 그룹)를 요구한다 — 실제 GenRM/RM-in-the-loop 시스템이 보상모델을 별도 워커/서버로 띄우는 이유다.

1. 목표 — 보상이 모델이 될 때

시리즈의 보상 비용은 단조 증가해 왔다: A(규칙 일치)≈0 → B(유닛테스트 실행) 14~24% → 여기 D는 보상 자체가 또 다른 LLM 추론(judge가 "이 답이 맞나?"를 생성으로 판정). 규칙·테스트로 검증 불가능한 개방형 과제(요약·대화·선호)로 RL을 확장하는 길이다. 측정하려던 것: reward가 모델 forward가 되면 단계 시간을 얼마나 먹는가.

설계: 비-agent 단일턴 경로(B와 동일, custom_reward_function 존중) + reward_genrm.py — Qwen2.5-0.5B judge를 한 번 로드하고, 각 응답마다 "Yes/No" 한 토큰을 생성해 점수화.

2. 시도와 실패 — 4가지 벽

#구성결과
1judge를 GPU(cuda:0)에 로드, batch 16RCCL 집합통신 타임아웃 — rank1 NCCL fail. judge의 CUDA 컨텍스트가 FSDP 학습 프로세스 그룹과 충돌
2judge를 CPU로, batch 8 (64 샘플)NCCL watchdog 1800초 타임아웃 — _ALLGATHER_BASE ran for 1800005ms before timing out. 느린 CPU judge가 학습 collective를 30분 넘게 대기시켜 프로세스 강제종료
3CPU judge, batch 4 (16 샘플), max_new_tokens 115분 타임아웃 — 스텝 1도 완료 못 함
4CPU judge, batch 2 (4 샘플), 스레드 3215분 타임아웃 — 4샘플에도 스텝 미완
+judge 단독 벤치(verl 없이, CPU)transformers 5.11 generate 퀴크까지 (AttributeError) — 이 스택에선 judge 추론 자체도 매끄럽지 않음
관찰된 실제 에러.
GPU judge: [Rank 1] Some NCCL operations have failed or timed out.
CPU judge: Watchdog caught collective operation timeout: WorkNCCL(SeqNum=53, OpType=_ALLGATHER_BASE ...) ran for 1800005 milliseconds before timing out → we are taking the entire process down.

3. 왜 막히는가 — colocate의 구조적 한계

핵심은 동기화다. verl의 FSDP 학습은 rank들이 RCCL collective(all-gather 등)로 보조를 맞춘다. reward 단계는 그 사이에 끼어 있어, reward가 (a) 같은 GPU를 건드리면 collective용 CUDA 스트림/메모리를 교란하고, (b) 오래 걸리면 다음 collective가 watchdog 타임아웃(기본 1800s)에 걸린다. 규칙·테스트 보상은 빠르거나(≈0) GPU를 안 써서(B의 subprocess) 무사했지만, 모델 judge는 둘 다 위반한다.

4. 교훈 + 옳은 설계 + 다음(E)

  1. 모델-as-보상은 reward 함수에 인라인으로 못 넣는다. GPU면 학습 NCCL을 깨고, CPU면 동기 루프를 마비시킨다 — 이 스택(verl colocate + ROCm)에서 4가지 구성 모두 실패.
  2. 옳은 설계는 "분리된 RM 서빙": 보상모델을 자체 GPU·자체 프로세스 그룹의 별도 서버(예: vLLM RM 서버, 또는 verl의 reward_model 워커)로 띄우고, 학습 루프는 그 서버에 비동기로 점수를 요청한다. 그래야 학습 collective와 격리된다.
  3. 시리즈의 큰 그림: 보상/도구의 "비-정책 연산"이 A(≈0)→B(테스트 14~24%)→D(모델, 전용 인프라 요구)로 escalate한다. 검증기가 무거워질수록 RL은 "정책 학습"에서 "분산 서빙 오케스트레이션" 문제로 바뀐다.
다음에 D를 성공시키려면: (1) verl reward_model.enable=True + 호환 RM 체크포인트(verl이 RM 워커를 자체 프로세스 그룹으로 관리 → 인라인 충돌 회피), 또는 (2) 별도 GCD에 vLLM judge 서버를 띄우고 custom reward가 HTTP로 호출(비동기). 둘 다 "RM을 학습에서 떼어내는" 같은 원칙. 단 ROCm NCCL 취약성(본 실험 다수 관찰) 때문에 추가 디버깅 필요.

다음(E — 멀티노드 disaggregation): D가 "보상을 떼어내라"였다면, E는 "롤아웃을 떼어내라" — 롤아웃 GPU와 학습 GPU를 노드 단위로 분리하고, 그때 weight-sync(A에서 본 update_weights ~20%)가 네트워크 비용으로 바뀌는지 본다.
