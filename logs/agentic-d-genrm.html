One-line summary.한 줄 요약. I tried to build the reward not from rules/tests but from an LLM-as-judge (a separate model inference). The result is a failure (negative result), but the lesson is clear: model-as-reward cannot simply be dropped into the reward function of a colocate GRPO trainer. Put the judge on the GPU and it clashes with the RCCL collective communication of FSDP training, so NCCL times out; put it on the CPU and it is so slow that it paralyzes the synchronized training loop all the way to the NCCL watchdog (1800s) / job timeout (even with 4 samples). In other words, the moment the reward becomes "yet another model inference," it demands dedicated serving infrastructure (its own GPU, its own process group) — which is exactly why real GenRM / RM-in-the-loop systems stand the reward model up as a separate worker/server.보상을 규칙/테스트가 아니라 LLM-as-judge(별도 모델 추론)로 만들려 했다. 결과는 실패(negative result)지만 교훈이 명확하다: 모델-as-보상은 colocate GRPO 트레이너의 reward 함수에 그냥 끼워넣을 수 없다. judge를 GPU에 올리면 FSDP 학습의 RCCL 집합통신과 충돌해 NCCL이 타임아웃되고, CPU에 올리면 너무 느려 동기화된 학습 루프를 NCCL watchdog(1800초)·잡 타임아웃까지 마비시킨다(4샘플에서도). 즉 보상이 "또 하나의 모델 추론"이 되는 순간, 그것은 전용 서빙 인프라(자체 GPU·자체 프로세스 그룹)를 요구한다 — 실제 GenRM/RM-in-the-loop 시스템이 보상모델을 별도 워커/서버로 띄우는 이유다.

1. Goal — when the reward becomes a model1. 목표 — 보상이 모델이 될 때

The reward cost across the series has risen monotonically: A (rule match) ≈ 0 → B (running unit tests) 14–24% → here D, where the reward itself is yet another LLM inference (the judge decides "is this answer correct?" by generation). This is the path to extending RL to open-ended tasks (summarization, dialogue, preference) that rules/tests cannot verify. What I wanted to measure: once the reward becomes a model forward, how much step time does it eat?시리즈의 보상 비용은 단조 증가해 왔다: A(규칙 일치)≈0 → B(유닛테스트 실행) 14~24% → 여기 D는 보상 자체가 또 다른 LLM 추론(judge가 "이 답이 맞나?"를 생성으로 판정). 규칙·테스트로 검증 불가능한 개방형 과제(요약·대화·선호)로 RL을 확장하는 길이다. 측정하려던 것: reward가 모델 forward가 되면 단계 시간을 얼마나 먹는가.

Design: a non-agent single-turn path (same as B, respecting custom_reward_function) + reward_genrm.py — load a Qwen2.5-0.5B judge once and, for each response, generate a single "Yes/No" token to score it.설계: 비-agent 단일턴 경로(B와 동일, custom_reward_function 존중) + reward_genrm.py — Qwen2.5-0.5B judge를 한 번 로드하고, 각 응답마다 "Yes/No" 한 토큰을 생성해 점수화.

3. Why it gets stuck — the structural limit of colocate3. 왜 막히는가 — colocate의 구조적 한계

The crux is synchronization. verl's FSDP training keeps the ranks in lockstep via RCCL collectives (all-gather, etc.). The reward step sits in between them, so the reward, if it (a) touches the same GPU, disturbs the CUDA streams/memory used by the collective, and if it (b) takes long, the next collective hits the watchdog timeout (1800s by default). Rule/test rewards were safe because they were fast (≈0) or didn't use the GPU (B's subprocess), but a model judge violates both.핵심은 동기화다. verl의 FSDP 학습은 rank들이 RCCL collective(all-gather 등)로 보조를 맞춘다. reward 단계는 그 사이에 끼어 있어, reward가 (a) 같은 GPU를 건드리면 collective용 CUDA 스트림/메모리를 교란하고, (b) 오래 걸리면 다음 collective가 watchdog 타임아웃(기본 1800s)에 걸린다. 규칙·테스트 보상은 빠르거나(≈0) GPU를 안 써서(B의 subprocess) 무사했지만, 모델 judge는 둘 다 위반한다.

4. Lesson + the right design + next (E)4. 교훈 + 옳은 설계 + 다음(E)

  1. Model-as-reward cannot be put inline in the reward function.모델-as-보상은 reward 함수에 인라인으로 못 넣는다. On GPU it breaks training NCCL; on CPU it paralyzes the synchronous loop — on this stack (verl colocate + ROCm), all 4 configurations failed.GPU면 학습 NCCL을 깨고, CPU면 동기 루프를 마비시킨다 — 이 스택(verl colocate + ROCm)에서 4가지 구성 모두 실패.
  2. The right design is "separated RM serving"옳은 설계는 "분리된 RM 서빙": stand the reward model up as a separate server with its own GPU and its own process group (e.g. a vLLM RM server, or verl's reward_model worker), and have the training loop request scores from that server asynchronously. Only then is it isolated from the training collective.보상모델을 자체 GPU·자체 프로세스 그룹의 별도 서버(예: vLLM RM 서버, 또는 verl의 reward_model 워커)로 띄우고, 학습 루프는 그 서버에 비동기로 점수를 요청한다. 그래야 학습 collective와 격리된다.
  3. The series' big picture시리즈의 큰 그림: the "non-policy compute" of reward/tools escalates A (≈0) → B (tests 14–24%) → D (model, demands dedicated infra). The heavier the verifier, the more RL turns from a "policy-learning" problem into a "distributed-serving-orchestration" problem.보상/도구의 "비-정책 연산"이 A(≈0)→B(테스트 14~24%)→D(모델, 전용 인프라 요구)로 escalate한다. 검증기가 무거워질수록 RL은 "정책 학습"에서 "분산 서빙 오케스트레이션" 문제로 바뀐다.
To make D succeed next time다음에 D를 성공시키려면: (1) verl reward_model.enable=True + a compatible RM checkpoint (verl manages the RM worker in its own process group → avoids the inline clash), or (2) stand up a vLLM judge server on a separate GCD and have the custom reward call it over HTTP (asynchronous). Both follow the same principle of "detaching the RM from training." But because of ROCm NCCL fragility (observed many times in this experiment), extra debugging is needed.(1) verl reward_model.enable=True + 호환 RM 체크포인트(verl이 RM 워커를 자체 프로세스 그룹으로 관리 → 인라인 충돌 회피), 또는 (2) 별도 GCD에 vLLM judge 서버를 띄우고 custom reward가 HTTP로 호출(비동기). 둘 다 "RM을 학습에서 떼어내는" 같은 원칙. 단 ROCm NCCL 취약성(본 실험 다수 관찰) 때문에 추가 디버깅 필요.

Next (E — multi-node disaggregation):다음(E — 멀티노드 disaggregation): if D was "detach the reward," E is "detach the rollout" — separate the rollout GPUs and training GPUs at the node level, and see whether weight-sync (the update_weights ~20% seen in A) then turns into a network cost.D가 "보상을 떼어내라"였다면, E는 "롤아웃을 떼어내라" — 롤아웃 GPU와 학습 GPU를 노드 단위로 분리하고, 그때 weight-sync(A에서 본 update_weights ~20%)가 네트워크 비용으로 바뀌는지 본다.
