1. 30초 요약

Frontier 는 vLLM 기반 LLM 서빙의 discrete-event simulator. NetX-lab (홍콩과기대) 가 만든 open-source. 핵심 특징:

  • Modern runtime 모델링: CUDA Graph, speculative decoding/MTP, prefix caching, quantization, chunked prefill, hierarchical caching 모두 sim 안에서 모델
  • Operator-level fidelity: 단순 average-case 모델 아닌, profiling 된 op-level latency 를 룩업해서 batch 시간 계산
  • 3 가지 communication backend: analytical / ASTRA-Sim analytical / collective-sim (실제 시뮬) — runtime 에 swap 가능
  • Co-location 만 (현재 release): PDD (prefill-decode disagg), AFD (attn-FFN disagg) 는 roadmap. 코드는 들어있지만 release guard 가 차단
  • 4-level scheduler hierarchy: Global → Cluster → Replica → ReplicaStage. PDD/AFD 때문에 필요
  • 9+ replica scheduler variants: vLLM / SJ2Q-FastServe-lite / SGLang / Orca / LightLLM / Sarathi 등

파일: frontier/simulator.py:1255-1336

def _init_event_queue(self) -> None:
    requests = self._request_generator.generate()
    self._metric_store.register_total_requests(len(requests))

    if self._config.simulation_mode == "offline":
        # 모든 request 가 t=0 도착
        for request in requests:
            request.set_arrived_at(0)
            request.on_arrival(0, ClusterType.MONOLITHIC)
            self._global_scheduler.add_request(request=request, ...)
        self._add_event(GlobalScheduleEvent(0))
    else:
        # online: 각 request 의 arrival_time 에 따라 event 큐에 추가
        for request in requests:
            self._add_event(RequestArrivalEvent(request.arrived_at, request, ...))

Sequential event loop (코어)

파일: frontier/simulator.py:572-703

def _run_sequential(self) -> None:
    while not self._terminate:
        while self._event_queue and not self._terminate:
            _, event = heapq.heappop(self._event_queue)  # 최소 priority pop
            self._set_time(event._time)                  # 글로벌 clock 전진
            new_events = event.handle_event(self._global_scheduler, self._metric_store)
            self._add_events(new_events)
            if self._config.metrics_config.write_json_trace:
                self._event_trace.append(event.to_dict())
        if self._try_promote_terminal_pdaf_scheduler_work():
            continue
        break
    self._write_output()

핵심: min-heap of (event_time, event_type, event_id) → 결정성 보장. 같은 시간에 여러 event 있어도 type 우선순위 + id 로 정렬.

Event 11종 분류

Event역할
REQUEST_ARRIVALonline 시 각 request 의 arrival
GLOBAL_SCHEDULEglobal scheduler 호출 trigger
CLUSTER_SCHEDULEcluster scheduler 호출 → request 를 replica 에 assign
REPLICA_SCHEDULEreplica scheduler 호출 → batch 형성
BATCH_STAGE_ARRIVALbatch 가 pipeline stage 에 도달
REPLICA_STAGE_SCHEDULEstage 에 batch 할당, exec_time 예측, end_event 발행
BATCH_STAGE_ENDstage 끝 → 다음 stage 또는 cluster 완료
CLUSTER_BATCH_ENDcluster level batch 완료
GLOBAL_BATCH_END전체 batch 완료 → request 메트릭 기록
PERIODIC_SCHEDULE주기적 batching (high throughput 모드)
THINKING_ROUND_REQUEUEmulti-round thinking 모드 재큐잉

설계 약점 (Cluster Simulator)

  1. Non-deterministic FP arithmetic — batch aggregation 의 부동소수점 rounding 이 플랫폼 별로 다를 수 있음. PYTHONHASHSEED=0 안 쓰면 dict iteration 도 다름
  2. Unbounded event queue — request 가 완료보다 빠르게 도착하면 큐 무한 grow. 메모리 폭주 가능
  3. All-in-memory metrics — 100만 request 시뮬은 RAM 부족 가능. write_json_trace 끄는 게 안전
  4. Stale event detection silent — schedule_epoch 안 맞는 event 는 WARN 없이 skip. 디버깅 어려움
  5. Tie-breaking on event time — 같은 시각의 다른 type event 가 logically 다른 순서여야 할 때 우선순위 잘못 설정 시 결정 잘못됨
  6. Numerical precision — exec time 예측 결과가 1.0000000001 같이 나오면 ties 깨짐

3-2. Profiling System — 81 files, 5 op category

전체 파이프라인

Real GPU (single, TP 시뮬)
    ↓
Profiling Module (op 별 grid sweep)
    ↓
CSV (operation × shape × time_stats)
    ↓
Training Module (sklearn: RandomForest / Polynomial)
    ↓
Execution Time Predictor (cost-table lookup at sim time)
    ↓
Discrete-Event Simulator

핵심 설계 원칙

  • Single-GPU TP simulation — TP=N 측정도 GPU 1대로. weight 를 N 등분해서 각 shard 계산 → distributed setup 불필요
  • Operation-based organization — 토폴로지(TP/PP/EP) 아닌 model component (attention/linear/moe/collective) 별
  • Pluggable backends — attention: FlashInfer + NoOp / MoE: vLLM fused kernel
  • Measurement duality: record_function (KERNEL_ONLY) vs cuda_event (CUDA_EVENT) — 어떤 측정법 쓸지 사용자가 매번 명시

설계 약점 (Profiling)

  1. vLLM tight coupling — Attention/MoE/CPU overhead 모두 vLLM 의존. 비-vLLM 엔진 (TensorRT-LLM, lm-eval, 자체 inference) 측정 불가. vLLM API 변경 시 매번 깨짐 (0.3.x → 0.10.x 의 fused MoE API redesign)
  2. NVIDIA only — torch.cuda.Event, nvidia-smi 의존. AMD ROCm / Apple Silicon 미지원
  3. Sweep cost — 한 모델 × HW 완전 sweep 4-5 GPU-hour (~$4-15 H100 spot). 새 모델 → 처음부터, HW variant (A100→H100) → 처음부터
  4. Version drift — vLLM 0.5 로 측정한 데이터가 0.7 sim 에 부정확. CSV 에 vllm_version column 없음 → 사용자가 직접 관리
  5. Load imbalance: metadata 만 — load_imbalance_cv, load_gini_coefficient 가 feature 로 들어가지만 실제 imbalanced sweep 안 함 (모두 uniform load 로 측정, imbalance 영향은 synthetic feature)
  6. Single-GPU TP fidelity — TP>8 같은 큰 차수에서 실제 cross-GPU communication 못 측정. analytical 외삽

def _predict_from_models(self) -> Dict[str, Any]:
    predictions = {}
    for op_name in ["mlp_up_proj", ..., "attn_rope"]:
        model = self._models[op_name]
        for num_tokens in range(1, self._max_tokens + 1):
            features = pd.DataFrame([[num_tokens]], columns=["num_tokens"])
            predictions[op_name][(num_tokens,)] = model.predict(features)[0]
    return predictions

def _get_mlp_layer_up_proj_execution_time(self, batch: Batch) -> float:
    effective_tokens = batch.get_effective_total_tokens_rounded(self._cluster_type)
    key = (effective_tokens,)
    if key in self._predictions["mlp_up_proj"]:
        raw_time = self._predictions["mlp_up_proj"][key]   # ← exact lookup, O(1)
    else:
        features = pd.DataFrame([[effective_tokens]], columns=["num_tokens"])
        raw_time = self._models["mlp_up_proj"].predict(features)[0]   # ← regression fallback
    scale = self._get_calibration_scale("_mlp_up_proj_calibration_scale", ...)
    return raw_time * scale

3 backend (analytical / astra_sim_analytical / collective_sim) 중 runtime 선택.

설계 약점

  1. Profile staleness — vLLM 0.5 로 측정 시 0.7 sim 에서 10-30% 빗나감. Calibration scale 수동
  2. Coverage gaps — MoE expert 수가 profile 범위 밖이거나 context 가 grid 너머면 extrapolation
  3. No calibration validation — sim 결과를 실제 system 과 자동 비교 X. 사용자가 수동 calibration scale 조정
  4. No interpolation — exact lookup 아니면 regression. log-space affine 가정 X (이건 장점일 수도 단점일 수도)

3-4. Scheduler 4-level hierarchy

4 level 의 이유

[1] Global Scheduler (BaseGlobalScheduler)
        → ClusterType 별 routing (MONOLITHIC/PREFILL/DECODE/DECODE_ATTN/DECODE_FFN)
        → 현재 release 는 MONOLITHIC 만 (disagg release guard)
[2] Cluster Scheduler (RoundRobin/LOR/Random + Sticky variants)
        → cluster 안의 (replica_id, dp_id) 선택
        → 7+ 정책. sticky 는 prefix cache 활용 (같은 request → 같은 replica)
[3] Replica Scheduler (vLLM/SJ2Q/SGLang/Orca/LightLLM/Sarathi 등 9+ variant)
        → 큐에서 batch 형성 (continuous batching + chunked prefill + spec dec)
[4] ReplicaStage Scheduler (per-stage queue)
        → pipeline stage 별 batch 순서 (priority heap by global_id)

vLLM scheduler 의 token budget admission

파일: frontier/scheduler/replica_scheduler/vllm_replica_scheduler.py:68-131

while self._request_queue:
    request = self._request_queue[0]
    next_num_tokens = self._get_request_next_num_tokens(request)
    if not self._can_allocate_request(request):  # watermark check
        break
    new_num_batch_tokens = len(new_num_tokens) * max(new_num_tokens)
    if new_num_batch_tokens > self._config.max_tokens_in_batch:  # token budget
        break
    if len(self._allocation_map) == self._config.batch_size_cap:  # batch size cap
        break
    self._allocate_request(request)
    self._request_queue.pop(0)
    requests.append(request)
return self._create_batch(requests, num_tokens)

SJ2Q (Simple Two-Queue, FastServe-lite)

짧은 prompt 는 QH (high priority), 긴 prompt 는 QL. QH 가 충분히 token 처리되면 QL 을 promote. Tail latency 감소 효과.

queue_level: QH (0) | QL (1)
priority key: (queue_rank, qh_subrank, priority, arrived_at)

def _get_request_next_num_tokens(self, request: Request) -> int:
    if request.is_prefill_complete:
        if request.spec_decode_enabled:
            planned_draft_tokens = request.spec_next_planned_draft_tokens

설계 약점

  1. 4-level 과잉 — monolithic 만 쓰는 deployment 면 Level 1/2 거의 no-op pass-through. Disaggregation 위해 다 깔아둠
  2. Predictor 와 tight coupling — predictor 없으면 schedule 불가. vLLM 처럼 predictor 와 독립적이지 않음
  3. Online/offline 차이 미구현 — offline 모드인데 lookahead 안 함. 매번 reactive
  4. vs vLLM 충실도 격차 — CUDA graph warmup, request coalescing, preemption overhead, multi-LoRA overlap, dynamic token budget 등 미모델. 추정 fidelity ~75% dense, ~65% MoE disagg
  5. Schedule epoch silent drop — stale batch 가 silently dropped. WARN 없음 → 디버깅 어려움

Prefix cache — hash-based block matching

파일: frontier/kv_cache/base_kv_cache_manager.py

@dataclass
class PrefixCacheStats:
    requests: int       # 전체 query 수
    queries: int        # 전체 block hash query 수
    hits: int           # cache hit block 수

def get_computed_blocks(self, request: Request) -> tuple[list[KVCacheBlock], int]:
    block_hashes = self._get_request_block_hashes(request)
    computed_blocks = []
    for block_hash in block_hashes:
        cached_block = self.block_pool.get_cached_block(block_hash)
        if cached_block is None:
            break  # contiguous prefix only
        computed_blocks.append(cached_block)
    self.prefix_cache_stats.hits += len(computed_blocks)
    return computed_blocks, len(computed_blocks) * self.block_size

Quantization 모델링

Implicit: bytes_per_element 가 precision 별로 다름 (FP32=4, FP16=2, INT8=1, INT4=0.5) → communication data size 비례 감소. Profile CSV 도 precision 별 분리 (eager_fp16/ vs eager_int8/).

약점: Quantization 자체 overhead (dequant/requant, 보통 5-15%) 미모델. Quantization 처리율 이득 overestimate 가능.

Chunked prefill

VllmV1SchedulerConfig.enable_chunked_prefill flag. Token budget 부족 시 prefill 을 chunk 로 split → decode 와 interleave. TTFT 살짝 ↑, TPOT ↓, throughput ↑.

약점: Chunk boundary 의 context reuse overhead (KV cache reshape) 미모델.
