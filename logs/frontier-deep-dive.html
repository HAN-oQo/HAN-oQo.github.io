1. 30-second summary1. 30초 요약

Frontier is a discrete-event simulator for vLLM-based LLM serving. Open-source, built by NetX-lab (HKUST). It wasn't written from scratch — it's a fork of Vidur (Microsoft) with modern runtime + scheduler variants + disaggregation code added on top (lineage: vLLM → Sarathi-Serve → Vidur → Frontier — see §4-2 GPTModel provenance for details). Key features:Frontier 는 vLLM 기반 LLM 서빙의 discrete-event simulator. NetX-lab (홍콩과기대) 가 만든 open-source. 처음부터 새로 만든 게 아니라 Vidur (Microsoft) 의 fork 위에 modern runtime + scheduler variants + disaggregation 코드 추가한 것 (lineage: vLLM → Sarathi-Serve → Vidur → Frontier — 자세한 건 §4-2 GPTModel 출처 참조). 핵심 특징:

  • Modern runtime modeling모델링: CUDA Graph, speculative decoding/MTP, prefix caching, quantization, chunked prefill, hierarchical caching — all modeled inside the simCUDA Graph, speculative decoding/MTP, prefix caching, quantization, chunked prefill, hierarchical caching 모두 sim 안에서 모델
  • Operator-level fidelity: not a simple average-case model — it looks up profiled op-level latency to compute batch time단순 average-case 모델 아닌, profiling 된 op-level latency 를 룩업해서 batch 시간 계산
  • 3 communication backends3 가지 communication backend: analytical / ASTRA-Sim analytical / collective-sim (real sim) — swappable at runtimeanalytical / ASTRA-Sim analytical / collective-sim (실제 시뮬) — runtime 에 swap 가능
  • Co-location only (current release)Co-location 만 (현재 release): PDD (prefill-decode disagg), AFD (attn-FFN disagg) are on the roadmap. The code is present but a release guard blocks itPDD (prefill-decode disagg), AFD (attn-FFN disagg) 는 roadmap. 코드는 들어있지만 release guard 가 차단
  • 4-level scheduler hierarchy: Global → Cluster → Replica → ReplicaStage. Needed because of PDD/AFDGlobal → Cluster → Replica → ReplicaStage. PDD/AFD 때문에 필요
  • 9+ replica scheduler variants: vLLM / SJ2Q-FastServe-lite / SGLang / Orca / LightLLM / Sarathi, etc.vLLM / SJ2Q-FastServe-lite / SGLang / Orca / LightLLM / Sarathi 등

Why the 3-stage split matters왜 3 단계 인지가 중요한가:

  • [Stage 1] is the only one that needs a GPU[1단계] 만 GPU 필요. Do it once and a CSV is produced — done. Usually 1-2 GPU-hours for one model + one device sweep.한 번 하면 CSV 산출되어 끝. 보통 1-2 GPU-hour 으로 한 모델 + 한 device sweep.
  • [Stage 2] training is automatic[2단계] 학습 은 자동. The user doesn't run a separate command. On the first sim run, Simulator.__init__() calls sklearn GridSearchCV.fit → pickle cache (data/cache/<hash>.pkl). From the next sim on, it just loads the cache.사용자가 별도 명령 안 침. 첫 sim 실행 시 Simulator.__init__() 안에서 sklearn GridSearchCV.fit 호출 → pickle cache (data/cache/<hash>.pkl). 다음 sim 부터는 cache load 만.
  • [Stage 3] the sim is fast[3단계] sim 은 빠름. O(1) lookup in the trained model's _predictions dict. Everything up to 4096 tokens is precomputed, so it doesn't call sklearn on every event.학습된 모델의 _predictions dict 에서 O(1) lookup. 4096 token 까지 미리 다 계산되어 있어서 매 event 마다 sklearn 호출 안 함.
  • Benefit of the split분리의 이점: [1] is expensive but once, [2] is automatic, [3] is fast and repeatable — for a workload sweep (dozens of scenarios) you only repeat [3]. That's the value of the sim.[1] 은 비싸지만 한 번, [2] 는 자동, [3] 은 빠르고 반복 — workload sweep (수십 시나리오) 시 [3] 만 반복하면 됨. 이게 sim 의 가치.

Why not import vLLM's LlamaForCausalLM directly왜 vLLM 의 LlamaForCausalLM 직접 import 안 하나

vLLM's model class operates bundled with the scheduler / KV cache manager / sampler / the whole inference engine. So to import it directly and call forward you'd have to spin up the entire vLLM engine (30s+ init). And then the vLLM Python overhead leaks into the measurement, making it hard to isolate "pure op time."vLLM 의 model class 는 scheduler / KV cache manager / sampler / 전체 inference engine 과 묶여서 동작. 그래서 직접 import 해서 forward 하려면 vLLM 엔진 전체 띄워야 함 (init 시간 30초+). 그리고 그러면 측정값에 vLLM Python 오버헤드까지 다 들어가서 "순수 op 시간" 분리가 어려움.

This design isn't Frontier's invention — it's the choice Sarathi-Serve originally made. While building a simulator for the chunked prefill paper, Sarathi-Serve mirrored vLLM's nn.Linear subclasses (ColumnParallelLinear, RowParallelLinear, RMSNorm, etc.) into a stripped-down GPTModel. Vidur took it as-is, and Frontier took it again. The upside is fast measurement without spinning up vLLM + Python overhead not leaking into the measurement. The downside is that other overhead in vLLM's production forward path (cache management, scheduler, etc.) is missing — so calibration may be needed.이 design 자체는 Frontier 가 만든 게 아니라 Sarathi-Serve 가 원래 한 선택. Sarathi-Serve 가 chunked prefill paper 용 simulator 만들면서 vLLM 의 nn.Linear subclass 들 (ColumnParallelLinear, RowParallelLinear, RMSNorm 등) 을 mirror 해서 stripped-down GPTModel 작성. Vidur 가 그대로 받고, Frontier 가 또 받음. 장점은 vLLM 띄우는 시간 없이 빠른 측정 + Python 오버헤드 측정값에 안 들어감. 단점은 vLLM 의 production forward path 의 다른 overhead (cache 관리, scheduler 등) 가 빠짐 — 그래서 calibration 필요할 수도.

This is a question users often ask. Exactly how does Frontier's vllm_v1_engine_replica_scheduler.py (4421 LoC!) reproduce vLLM's decisions:이게 사용자가 자주 묻는 질문. Frontier 의 vllm_v1_engine_replica_scheduler.py (4421 LoC!) 가 정확히 어떻게 vLLM 의 결정을 재현하는가:

① What vLLM's scheduler decides① vLLM 의 scheduler 가 결정하는 것

A real vLLM v1 scheduler makes the following decisions every iteration:실 vLLM 의 v1 scheduler 는 매 iteration 마다 다음 결정을 내림:

  1. Token budget: if this batch's total token count exceeds max_num_batched_tokens (e.g. 8192), admit no more이번 batch 의 총 token 수가 max_num_batched_tokens (e.g. 8192) 넘으면 더 admit 안 함
  2. Batch size cap: if the number of concurrently active requests exceeds max_num_seqs (e.g. 256), admit no more동시 active request 수가 max_num_seqs (e.g. 256) 넘으면 더 admit 안 함
  3. KV cache watermark: if the KV blocks a new request needs fall below the available blocks, don't admit (the block_manager tracks this)새 request 가 필요한 KV block 수가 available block 아래로 떨어지면 admit 안 함 (block_manager 가 추적)
  4. Chunked prefill: split a long prompt into chunks and interleave with decode (chunk_size = max(prefill, decode) for balance)긴 prompt 를 chunk 로 나눠서 decode 와 interleave (chunk_size = max(prefill, decode) 균등화)
  5. Preemption: when KV is short, swap out the lowest-priority decode request (recompute or swap-to-CPU)KV 부족 시 lowest priority decode request swap-out (recompute or swap-to-CPU)
  6. Prefix cache: when enabled, already-cached blocks are subtracted from num_new_tokens for the admission calcenable 시 이미 캐시된 block 은 num_new_tokens 에서 빼서 admission 계산
② How Frontier mimics the same decisions② Frontier 가 어떻게 같은 결정 흉내내나

The key to making the same decisions without vLLM's real GPU forward or KV cache memory management: vLLM's decisions depend not on real GPU time but only on virtual resources like "block count / token count." Frontier tracks only those virtual resources:실 vLLM 의 GPU forward 와 KV cache 메모리 관리 없이도 같은 결정을 내릴 수 있는 핵심: vLLM 의 결정은 GPU 의 실 시간이 아니라 "block 수 / token 수" 같은 가상 자원만 의존. Frontier 는 그 가상 자원 만 tracking:

def _get_next_batch(self, is_micro_batch=False) -> Batch:
    requests = []
    num_tokens = []
    num_batch_tokens = 0

    while self._request_queue:
        request = self._request_queue[0]
        next_num_tokens = self._get_request_next_num_tokens(request)
        #   → prefill 중이면 남은 prefill token, decode 면 1 (spec dec 면 1+draft)

        if not self._can_allocate_request(request):       ← KV watermark 체크
            break
        new_num_tokens = num_tokens + [next_num_tokens]
        new_num_batch_tokens = len(new_num_tokens) * max(new_num_tokens)
        if new_num_batch_tokens > self._config.max_tokens_in_batch:  ← token budget
            break
        if len(self._allocation_map) == self._config.batch_size_cap: ← batch cap
            break

        request = self._request_queue.pop(0)
        self._allocate_request(request)
        requests.append(request)
        num_tokens.append(next_num_tokens)
        num_batch_tokens += next_num_tokens

    if requests:
        return self._create_batch(requests, num_tokens)

    # Preemption: KV 부족하면 preempted_requests pop 해서 retry
    while self._preempted_requests:
        ...
        while not self._can_allocate_request(request):
            if self._preempted_requests:
                victim = self._preempted_requests.pop(-1)
                victim.restart()
                self.free(victim.id)
                self._request_queue = [victim] + self._request_queue
            ...

def mean_absolute_percentage_error(y_true, y_pred):
    zero_true = y_true == 0
    non_zero = ~zero_true
    error[non_zero] = |y_true - y_pred| / y_true * 100

def _build_exact_feature_lookup(df, feature_cols, target_col):
    """Build exact profiling-row lookups before falling back to regression."""
    if df.empty: return {}
    grouped = df.groupby(feature_cols, dropna=False)[target_col].mean()
    lookup = {}
    for key, value in grouped.items():
        key_tuple = key if isinstance(key, tuple) else (key,)
        lookup[tuple(float(item) for item in key_tuple)] = float(value)
    return lookup

# Hash-based block matching
def get_computed_blocks(self, request: Request) -> tuple[list[KVCacheBlock], int]:
    block_hashes = self._get_request_block_hashes(request)
    computed_blocks = []
    for block_hash in block_hashes:
        cached_block = self.block_pool.get_cached_block(block_hash)
        if cached_block is None:
            break  # contiguous prefix 만
        computed_blocks.append(cached_block)
    self.prefix_cache_stats.hits += len(computed_blocks)
    return computed_blocks, len(computed_blocks) * self.block_size

Block pool: LRU-based eviction (only blocks with ref_cnt == 0 can be evicted). When a new request comes in: (1) reserve matching cached blocks (2) if short, allocate from free blocks (3) if memory-short, LRU-evict.LRU 기반 eviction (ref_cnt == 0 인 block 만 evict 가능). 새 request 가 들어오면 (1) 매칭되는 cached block 들 reserve (2) 부족하면 free block 으로 allocate (3) 메모리 부족하면 LRU evict.

Weakness약점: a meaningless hash collision could cause a false-positive cache hit (low probability). Realistic eviction (semantic block importance) is unmodeled.의미 없는 hash 충돌 시 false-positive cache hit 가능 (낮은 확률). Realistic eviction (semantic block importance) 미모델.

6-3. Interpolation difference — unpacked6-3. Interpolation 차이 — 풀어쓰면

Both simulators have profile measurements limited to the sweep grid. During a real sim, when a batch has a token count that wasn't measured (e.g. 333), how is that value obtained?두 simulator 모두 profile 측정 점이 sweep grid 한정. 실 sim 중에 batch 가 측정 안 한 token count (예: 333) 일 때, 그 값을 어떻게 구하나?

① LLMServingSim — log-space doubling grid + linear interpolation① LLMServingSim — log-space doubling grid + 선형 보간

The profile grid is doubling (16, 32, 64, 128, ...) → evenly spaced on a log scale.profile 의 grid 가 doubling (16, 32, 64, 128, ...) → log scale 에서 등간격.

Example: during sim a batch has 333 tokens. The two nearest points in the profile grid are 256 and 512.예: 시뮬 중 batch 가 333 token. profile grid 에서 가장 가까운 두 점은 256 과 512.

측정값:
  num_tokens=256 → 27 us
  num_tokens=512 → 43 us

추정 단계:
  1. log space 위치 비율:
     α = (log(333) - log(256)) / (log(512) - log(256))
       = log(333/256) / log(2)
       = 0.379 / 0.693
       = 0.547   (256 에서 약 55% 쯤)

  2. 선형 보간 (raw 또는 log space):
     선형(raw):    27 + 0.547 × (43 - 27) = 35.8 us
     선형(log):    exp(log(27) + 0.547 × (log(43) - log(27))) = 35.0 us
     ↑ 보통 log-space interp 이 op 의 실 곡선에 더 가까움

Why a doubling grid?왜 doubling grid 인가? Op time is roughly log-affine in token count (Roofline model — FLOPs is linear, memory bandwidth is linear, the max() of the two applies, so it's nearly a straight line in log space). Even measuring by doubling 16-32-64-128-256-... gives only 1-3% error in between.Op 시간이 token 수에 대해 대체로 log-affine (Roofline 모델 — FLOPs 도 linear, memory bandwidth 도 linear, 둘의 max() 가 적용되니 log space 에서 거의 직선). 16-32-64-128-256-... 식 doubling 으로 측정해도 그 사이 1-3% 오차.

Characteristics:특징:

  • few measurement points (~9 per op) → small lookup table (~few KB)측정 점 적음 (~9 per op) → lookup table 크기 작음 (~수 KB)
  • lookup is O(log N) bisect + 2 float arithmetic → ~50nsLookup 시 O(log N) bisect + 2 float arithmetic → ~50ns
  • tokens beyond the grid (e.g. 8192) extrapolate the 4096 trend as-is — underestimates under attention's quadratic scalingGrid 너머 token (예: 8192) 은 4096 의 trend 그대로 extrapolation — attention 의 quadratic scaling 시 underestimate

② Frontier — sklearn training + pre-compute every integer token into a dict lookup② Frontier — sklearn 학습 + 모든 정수 token 미리 계산해서 dict lookup

Measure many points (~620 per op) → smooth fitting with a sklearn model → pre-compute everything from 1 to max_tokens and store in a dict.점 많이 측정한 다음 (~620 per op) → sklearn 모델로 smooth fitting → 1부터 max_tokens 까지 모두 미리 계산해서 dict 로 저장.

       return model.predict([[333]])[0]   # ← regression fallback (드물게)

10-3. One-line verdict10-3. 한 줄 평

Compared to LLMServingSim, Frontier is a much larger codebase (3x), with richer modern runtime modeling (CUDA graph / 8 spec dec methods / MoE imbalance / quantization), more scheduler variants (9+ vs 1), at the cost of a steeper learning curve. Aside from the current release being co-location only, it's better suited for SLA-aware design space exploration. Once the disaggregation release lands, that side should get powerful too.Frontier 는 LLMServingSim 보다 훨씬 큰 코드베이스이고 (3x), modern runtime 모델링이 풍부하고 (CUDA graph / 8 spec dec method / MoE imbalance / quantization), scheduler variant 가 많고 (9+ vs 1), 그 대가로 학습 곡선이 가파름. 현재 release 가 co-location only 라는 한계만 빼면 SLA-aware design space exploration 에 더 적합. Disaggregation release 나오면 그쪽도 강력해질 듯.
