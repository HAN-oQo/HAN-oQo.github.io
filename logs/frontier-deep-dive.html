1. 30초 요약

Frontier 는 vLLM 기반 LLM 서빙의 discrete-event simulator. NetX-lab (홍콩과기대) 가 만든 open-source. 처음부터 새로 만든 게 아니라 Vidur (Microsoft) 의 fork 위에 modern runtime + scheduler variants + disaggregation 코드 추가한 것 (lineage: vLLM → Sarathi-Serve → Vidur → Frontier — 자세한 건 §4-2 GPTModel 출처 참조). 핵심 특징:

  • Modern runtime 모델링: CUDA Graph, speculative decoding/MTP, prefix caching, quantization, chunked prefill, hierarchical caching 모두 sim 안에서 모델
  • Operator-level fidelity: 단순 average-case 모델 아닌, profiling 된 op-level latency 를 룩업해서 batch 시간 계산
  • 3 가지 communication backend: analytical / ASTRA-Sim analytical / collective-sim (실제 시뮬) — runtime 에 swap 가능
  • Co-location 만 (현재 release): PDD (prefill-decode disagg), AFD (attn-FFN disagg) 는 roadmap. 코드는 들어있지만 release guard 가 차단
  • 4-level scheduler hierarchy: Global → Cluster → Replica → ReplicaStage. PDD/AFD 때문에 필요
  • 9+ replica scheduler variants: vLLM / SJ2Q-FastServe-lite / SGLang / Orca / LightLLM / Sarathi 등

10-0-b. "vLLM 의 GPTModel 가져와서 forward 하는 거 맞지?" 에 대한 정확한 답

부분적으로 맞고 부분적으로 다름. 정확히:

"vLLM 실제 돌려서 op 결과 가져오는 거랑 동일한가" — 정확한 답

일부는 동일하고 일부는 다름. 차원별로:

차원vLLM 실 forward 와 동일한가
GPU kernel 자체 (matmul, RMSNorm, RoPE 의 CUDA kernel call)✅ 동일. ColumnParallelLinear 같은 layer 가 호출하는 GPU kernel 은 vLLM 의 것과 똑같음 (Sarathi 가 mirror 한 nn.Linear subclass — 같은 kernel API)
Op 자체의 latency✅ 거의 동일. 같은 kernel + 같은 input shape → 같은 GPU 시간. 단 GPU thermal throttling / boost clock 변동 같은 noise 는 매번 다름 (그래서 WARMUP=3 + ACTIVE=20 회 측정 후 median)
전체 model forward 시간 (vLLM 의 LlamaForCausalLM.forward 1번 호출)❌ 다름. Frontier 는 op kernel 시간만 합산. vLLM 의 forward 는 그 외에 다음이 다 포함:
  • Scheduler 호출 (어떤 request 를 이번 batch 에)
  • KV cache block 관리 (allocate, evict, swap)
  • Sampler (logit → token)
  • Token detokenization
  • Python dispatcher overhead (PyTorch eager mode 의 op dispatch)
  • NCCL collective comm (TP 시 cross-GPU)
실 vLLM forward = op_kernel_time + 위 overhead 들. Frontier 측정은 op_kernel_time 만.
Surrounding overhead 모델링별도 sweep 으로 처리. cpu_overhead.csv (scheduler/sampler/prepare_inputs/ray_comm 시간) + cc_backend (NCCL allreduce 시간). 그래서 sim 의 total predict time = op_kernel + cpu_overhead + comm
Production batch 의 정확도op_kernel 만 정확. 보통 ±5-15% 오차 — surrounding overhead 가 cpu_overhead 측정 + cc_backend 예측으로 근사. Calibration scale 로 조정 (§3-4 참조)

정리: vLLM 실 forward 의 op kernel 시간만 정확히 같음. 그 외 모든 Python/scheduler/cache overhead 는 별도 측정한 다음 sim 안에서 합산. 그래서 sim 의 batch latency 가 production vLLM 의 batch latency 와 ~ 비슷하지만 정확히 같지는 않음 — 의도된 설계 (Sarathi 부터 이 방식).

측정 mechanism — 한 forward 안에서 모든 op 동시 측정

# frontier/profiling/linear_op/linear_op_impl.py 안의 op 들이 # 자기 자체에 CudaTimer 를 갖고 있음: class Attention(nn.Module): def __init__(self, ...): self._attn_pre_proj_timer = CudaTimer("attn_pre_proj") self._attn_rope_timer = CudaTimer("attn_rope") ... self.qkv_proj = ColumnParallelLinear(...) ← frontier 자체 self.rotary_emb = get_rope(...) ← frontier 자체 def forward(self, hidden_states, positions): with self._attn_pre_proj_timer: ← Timer ENTER (cuda Event) qkv = self.qkv_proj(hidden_states) ← Timer EXIT (cuda Event) q, k, v = qkv.chunk(3, dim=-1) with self._attn_rope_timer: ← Timer ENTER q, k = self.rotary_emb(q, k, positions) ← Timer EXIT ... class MLP(nn.Module): def __init__(self, ...): self._mlp_up_proj_timer = CudaTimer("mlp_up_proj") self._mlp_down_proj_timer = CudaTimer("mlp_down_proj") self._mlp_act_timer = CudaTimer("mlp_act") ... def forward(self, hidden_states): with self._mlp_up_proj_timer: h = self.up_proj(hidden_states) with self._mlp_act_timer: h = self.act_fn(h) with self._mlp_down_proj_timer: out = self.down_proj(h) ... # 그래서 한 GPTModel.forward(batch) 호출 시: # - attention.forward → attn_pre_proj_timer, attn_rope_timer 각각 발화 # - mlp.forward → mlp_up_proj_timer, mlp_act_timer, mlp_down_proj_timer 발화 # → TimerStatsStore 가 모든 timer 결과를 layer 별로 모음 # → 1 forward = 모든 op 의 latency 한 번에 측정 완료 # # ACTIVE_STEPS=20 회 forward 반복 → op 별 min/max/mean/median/std 계산

왜 vLLM 의 LlamaForCausalLM 직접 import 안 하나

vLLM 의 model class 는 scheduler / KV cache manager / sampler / 전체 inference engine 과 묶여서 동작. 그래서 직접 import 해서 forward 하려면 vLLM 엔진 전체 띄워야 함 (init 시간 30초+). 그리고 그러면 측정값에 vLLM Python 오버헤드까지 다 들어가서 "순수 op 시간" 분리가 어려움.

이 design 자체는 Frontier 가 만든 게 아니라 Sarathi-Serve 가 원래 한 선택. Sarathi-Serve 가 chunked prefill paper 용 simulator 만들면서 vLLM 의 nn.Linear subclass 들 (ColumnParallelLinear, RowParallelLinear, RMSNorm 등) 을 mirror 해서 stripped-down GPTModel 작성. Vidur 가 그대로 받고, Frontier 가 또 받음. 장점은 vLLM 띄우는 시간 없이 빠른 측정 + Python 오버헤드 측정값에 안 들어감. 단점은 vLLM 의 production forward path 의 다른 overhead (cache 관리, scheduler 등) 가 빠짐 — 그래서 calibration 필요할 수도.

이게 사용자가 자주 묻는 질문. Frontier 의 vllm_v1_engine_replica_scheduler.py (4421 LoC!) 가 정확히 어떻게 vLLM 의 결정을 재현하는가:

① vLLM 의 scheduler 가 결정하는 것

실 vLLM 의 v1 scheduler 는 매 iteration 마다 다음 결정을 내림:

  1. Token budget: 이번 batch 의 총 token 수가 max_num_batched_tokens (e.g. 8192) 넘으면 더 admit 안 함
  2. Batch size cap: 동시 active request 수가 max_num_seqs (e.g. 256) 넘으면 더 admit 안 함
  3. KV cache watermark: 새 request 가 필요한 KV block 수가 available block 아래로 떨어지면 admit 안 함 (block_manager 가 추적)
  4. Chunked prefill: 긴 prompt 를 chunk 로 나눠서 decode 와 interleave (chunk_size = max(prefill, decode) 균등화)
  5. Preemption: KV 부족 시 lowest priority decode request swap-out (recompute or swap-to-CPU)
  6. Prefix cache: enable 시 이미 캐시된 block 은 num_new_tokens 에서 빼서 admission 계산
② Frontier 가 어떻게 같은 결정 흉내내나

실 vLLM 의 GPU forward 와 KV cache 메모리 관리 없이도 같은 결정을 내릴 수 있는 핵심: vLLM 의 결정은 GPU 의 실 시간이 아니라 "block 수 / token 수" 같은 가상 자원만 의존. Frontier 는 그 가상 자원 만 tracking:

    zero_true = y_true == 0

Exact lookup vs regression — _build_exact_feature_lookup 의 역할

파일: sklearn_execution_time_predictor.py:83-90

def _build_exact_feature_lookup(df, feature_cols, target_col):
    """Build exact profiling-row lookups before falling back to regression."""
    if df.empty: return {}
    grouped = df.groupby(feature_cols, dropna=False)[target_col].mean()
    lookup = {}
    for key, value in grouped.items():
        key_tuple = key if isinstance(key, tuple) else (key,)
        lookup[tuple(float(item) for item in key_tuple)] = float(value)
    return lookup

3-tier lookup priority (sim 시):

  1. Exact profile row 매칭 — profile CSV 에 정확히 해당 feature 조합이 있으면 raw 측정값 사용 (regression 거치지 않음)
  2. Pre-computed integer cache — 미리 model.predict 한 dict 에 있으면 그 값
  3. Live regression — 둘 다 miss 면 model.predict([[features]]) 실시간 호출

1번이 가장 정확 (학습 거친 smooth curve 가 아닌 raw 측정값). 2번은 학습 결과의 smooth curve, 3번은 그 curve 의 즉석 계산.

# Hash-based block matching
def get_computed_blocks(self, request: Request) -> tuple[list[KVCacheBlock], int]:
    block_hashes = self._get_request_block_hashes(request)
    computed_blocks = []
    for block_hash in block_hashes:
        cached_block = self.block_pool.get_cached_block(block_hash)
        if cached_block is None:
            break  # contiguous prefix 만
        computed_blocks.append(cached_block)
    self.prefix_cache_stats.hits += len(computed_blocks)
    return computed_blocks, len(computed_blocks) * self.block_size

Block pool: LRU 기반 eviction (ref_cnt == 0 인 block 만 evict 가능). 새 request 가 들어오면 (1) 매칭되는 cached block 들 reserve (2) 부족하면 free block 으로 allocate (3) 메모리 부족하면 LRU evict.

약점: 의미 없는 hash 충돌 시 false-positive cache hit 가능 (낮은 확률). Realistic eviction (semantic block importance) 미모델.

def _run_sequential(self) -> None:
    while not self._terminate:
        while self._event_queue and not self._terminate:
            _, event = heapq.heappop(self._event_queue)  # 최소 priority pop
            self._set_time(event._time)                  # 글로벌 clock 전진
            new_events = event.handle_event(self._global_scheduler, self._metric_store)
            self._add_events(new_events)
            if self._config.metrics_config.write_json_trace:
                self._event_trace.append(event.to_dict())
        if self._try_promote_terminal_pdaf_scheduler_work():
            continue
        break
    self._write_output()

설계 약점 (Cluster Simulator)

  1. Non-deterministic FP arithmetic — batch aggregation 의 부동소수점 rounding 이 플랫폼 별로 다를 수 있음. PYTHONHASHSEED=0 안 쓰면 dict iteration 도 다름

  • Memory access pattern (cache miss, fragmentation)
  • Python overhead (PyTorch dispatcher, eager mode)
  • vLLM 의 batch 구성 overhead (padding, tensor 정렬)

Dense vs MoE — MoE 가 빠른 이유

Dense Llama-2-7B 는 모든 layer 의 MLP 매 forward 계산. MoE 는 같은 batch 에 활성 expert 만 계산 (top-k routing). dummy mode 라도 MoE 의 layer 구성 (gating → top-k expert → grouped GEMM) 이 dense 의 모든 MLP forward 보다 적은 op call → TTFT 약 절반 (3648 → 1944 ms), E2E 도 절반. 의도된 동작 — MoE 의 sparse activation 이 sim 의 op call 수로 정확히 반영됨.

Thinking mode — E2E 1.82s 인 이유

Thinking mode 는 multi-round 워크로드. 한 request 가 hidden round (planning) + final round (output) 들로 분해. NUM_REQUESTS=4 인데 default thinking workload 가 짧은 시퀀스 사용 → token 수 적음. E2E 짧은 게 정상.

Spec decode 효과 — TPOT 절반 (390ms → 198ms)

가장 흥미. MoE 의 spec decode (default 5 speculative tokens) 에서 acceptance ratio 0.5 — draft 의 50% accept. 한 verify iteration 당 평균 (1 + 0.5×5) = 3.5 token commit → 비-spec MoE 의 1 token/iter 보다 약 3.5× 효율. TPOT 가 198ms (vs 390ms) — 약 2× 빨라짐 (3.5× 의 효율이 verify 자체 overhead 로 일부 상쇄). 이게 진짜 sim 의 가치 — 실 GPU 없이 spec dec 의 acceptance 가설이 throughput 에 미치는 영향 검증.

5-2. Profiling 차이 — 풀어쓰면

위 비교표의 "Profiling" row 가 압축돼 있어서 풀어씀. 두 simulator 가 "GPU 한번 측정해서 CSV 만든다" 는 같지만, 어떻게 측정하느냐 가 다름.

① LLMServingSim 의 방식 — vLLM 안에서 hook 으로 측정

vLLM 에는 layerwise_profile 이라는 내장 도구가 있음. 각 nn.Module.forward() 호출 직전·직후에 callback (hook) 을 걸어서 레이어별 GPU 시간을 직접 측정:

1. vLLM 엔진 init (실 모델 로딩)
2. 모든 transformer layer 의 forward 에 hook 등록
3. 실 inference 요청 던지기 (예: 64 token 짜리 prompt 한 번)
4. vLLM 가 forward 실행 → 매 layer hook 발화 → 각 layer 의 attention/MLP/etc 시간 기록
5. 결과 모아서 CSV 한 줄로 — 한 batch shape 의 한 측정 끝
6. 다음 batch shape 로 다시 forward (token count, KV length 등 바꿔서)

핵심 특성:

  • vLLM 의 진짜 forward path 통과 — kernel launch, KV cache 접근, Python overhead 등 운영 환경 그대로 측정 → calibration 거의 필요 X
  • sparse grid sweep — token count 를 16, 32, 64, 128, ..., 4096 식 doubling 으로 9-10 점만 측정
  • 5 CSV 출력: attention.csv, dense.csv, per_sequence.csv, moe.csv, skew_fit.csv — 축이 명확히 분리
  • 한 모델/HW 당 profile 시간 ~30-90분

② Frontier 의 방식 — op 만 직접 instantiate

Frontier 는 vLLM 의 forward 를 거치지 않고 각 op 만 따로 instantiate 해서 측정:

1. nn.Linear (또는 attention kernel) 를 PyTorch 로 직접 생성 — vLLM 안 띄움
2. 입력 tensor 만 생성 (지정된 num_tokens, hidden_dim, TP_size)
3. CudaTimer (record_function 또는 cuda_event) 로 5 회 반복 측정
4. min/max/mean/median/std 5 통계 모두 CSV row 로
5. 다음 grid point — num_tokens 만 바꿔서 반복 (한 점당 ~50ms)

5-3. Interpolation 차이 — 풀어쓰면

두 simulator 모두 profile 측정 점이 sweep grid 한정. 실 sim 중에 batch 가 측정 안 한 token count (예: 333) 일 때, 그 값을 어떻게 구하나?

① LLMServingSim — log-space doubling grid + 선형 보간

profile 의 grid 가 doubling (16, 32, 64, 128, ...) → log scale 에서 등간격.

예: 시뮬 중 batch 가 333 token. profile grid 에서 가장 가까운 두 점은 256 과 512.

측정값:
  num_tokens=256 → 27 us
  num_tokens=512 → 43 us

추정 단계:
  1. log space 위치 비율:
     α = (log(333) - log(256)) / (log(512) - log(256))
       = log(333/256) / log(2)
       = 0.379 / 0.693
       = 0.547   (256 에서 약 55% 쯤)

  2. 선형 보간 (raw 또는 log space):
     선형(raw):    27 + 0.547 × (43 - 27) = 35.8 us
     선형(log):    exp(log(27) + 0.547 × (log(43) - log(27))) = 35.0 us
     ↑ 보통 log-space interp 이 op 의 실 곡선에 더 가까움

왜 doubling grid 인가? Op 시간이 token 수에 대해 대체로 log-affine (Roofline 모델 — FLOPs 도 linear, memory bandwidth 도 linear, 둘의 max() 가 적용되니 log space 에서 거의 직선). 16-32-64-128-256-... 식 doubling 으로 측정해도 그 사이 1-3% 오차.

특징:

  • 측정 점 적음 (~9 per op) → lookup table 크기 작음 (~수 KB)
  • Lookup 시 O(log N) bisect + 2 float arithmetic → ~50ns
  • Grid 너머 token (예: 8192) 은 4096 의 trend 그대로 extrapolation — attention 의 quadratic scaling 시 underestimate

② Frontier — sklearn 학습 + 모든 정수 token 미리 계산해서 dict lookup

점 많이 측정한 다음 (~620 per op) → sklearn 모델로 smooth fitting → 1부터 max_tokens 까지 모두 미리 계산해서 dict 로 저장.

1. profile CSV 읽기 (620 rows of (num_tokens, mean_us))
2. GridSearchCV 로 sklearn 학습:
   RandomForestRegressor or PolynomialRegression
   features = [num_tokens]  (attention/moe 는 multi-feature)
   target = time_stats.mlp_up_proj.median
3. 학습된 모델로 모든 정수 token count 미리 예측해서 dict 에 저장:
   predictions["mlp_up_proj"] = {}
   for n in 1..max_tokens:        # e.g. max_tokens=32768
       predictions["mlp_up_proj"][(n,)] = model.predict([[n]])[0]
   # → 32K × op 갯수 × 측정 환경 × precision = MB 단위 cache
4. sim 시점 lookup:
   key = (333,)
   if key in predictions["mlp_up_proj"]:
       return predictions[key]    # ← O(1) dict access, no math
   else:
       return model.predict([[333]])[0]   # ← regression fallback (드물게)

특징:

  • 측정 점 많음 (~620) + regression smoothing → 더 정확한 곡선 fitting
  • Sim 시점 lookup O(1) dict access → ~100ns (LLMServingSim 보다 살짝 느림 — math 없는 대신 Python dict 오버헤드)
  • 메모리 cache 큼 — 32K × 5 op × 2 TP × 2 measurement type = ~10MB. 절대 크기 작아서 문제 X
  • Grid 너머 extrap 은 sklearn 모델 종류에 따라 다름:
    • RandomForest: nearest leaf 의 값 그대로 (saturation 효과)
    • PolynomialRegression degree=2: quadratic 따라 외삽 — attention 의 quadratic 영역 잘 따라감

8-4. 실측 vs sim 비교 워크플로 (calibration)

  1. Profile sweep 으로 새 모델 + 새 HW profile 생성
  2. 같은 워크로드 (300-req ShareGPT JSONL 등) 를 실 GPU 클러스터에서 측정 — TTFT/TPOT/throughput CSV
  3. Frontier sim 으로 같은 워크로드 — CSV
  4. 두 CSV 의 request 별 metric 비교, mean error %
  5. 10% 초과면 calibration scale 조정: 
    --execution_time_predictor_config_attn_prefill_calibration_scale 1.05
--execution_time_predictor_config_mlp_up_proj_calibration_scale 0.95
...
  6. 재실행 → error 줄어들 때까지 반복. 일반적으로 3-4 iteration 이면 5% 이내

이 워크플로 자동화: LLMServingSim vs vLLM 비교 런북의 tools/replay_jsonl.py + tools/compare_csv.py 가 직접 활용 가능. JSONL replay + CSV diff 같은 framework 사용.

9-2. 기능적 약점 (코드 분석 기반)

  1. Acceptance rate 가 trace-based — speculative decoding 의 실제 quality (draft model accuracy) 변화 모델링 불가
  2. Prefix cache eviction 이 단순 LRU — 의미 분류 / cross-request affinity 미반영
  3. MoE expert load imbalance 가 metadata feature 만 — actual per-expert 측정 안 함
  4. Quantization 자체 overhead (dequant/requant) 미모델 → quantization 처리율 이득 overestimate
  5. CUDA Graph capture cost (100-500μs per shape) 미모델 → 다양한 batch shape 시 latency 변동 underestimate
  6. Calibration validation 자동화 X — operator 가 수동 scale 조정

9-3. LLMServingSim 과 cross-check 활용

두 simulator 가 모두 cost-table 방식이지만 다른 알고리즘:

  • Profile 의 같은 raw measurement 를 양쪽에 입력 → 결과 비교
  • 일치 → 결과 신뢰 ↑
  • 불일치 → 어느 쪽 모델이 어떤 가정에서 다른지 검증 기회

아쉽게도 두 시뮬레이터의 profile schema 가 달라서 자동 변환 안 됨. 손으로 raw GPU 측정값을 양쪽 format 으로 변환해야. 1회성 검증 cost ~1-2 일.

6-2. paper 와 코드 차이

arXiv 논문 (2605.21312) 은 4 가지 use case 시연 — Pareto frontier search, heterogeneous GPU allocation, stateful reasoning scheduler validation, dynamic reconfiguration for RL rollouts. 그 중 2 개 (Pareto, stateful reasoning) 는 현재 release 의 co-location 코드로 재현 가능. 나머지 2 개는 disaggregation release 기다려야.

6-3. 한 줄 평

Frontier 는 LLMServingSim 보다 훨씬 큰 코드베이스이고 (3x), modern runtime 모델링이 풍부하고 (CUDA graph / 8 spec dec method / MoE imbalance / quantization), scheduler variant 가 많고 (9+ vs 1), 그 대가로 학습 곡선이 가파름. 현재 release 가 co-location only 라는 한계만 빼면 SLA-aware design space exploration 에 더 적합. Disaggregation release 나오면 그쪽도 강력해질 듯.
