1. 30초 요약

Frontier 는 vLLM 기반 LLM 서빙의 discrete-event simulator. NetX-lab (홍콩과기대) 가 만든 open-source. 핵심 특징:

  • Modern runtime 모델링: CUDA Graph, speculative decoding/MTP, prefix caching, quantization, chunked prefill, hierarchical caching 모두 sim 안에서 모델
  • Operator-level fidelity: 단순 average-case 모델 아닌, profiling 된 op-level latency 를 룩업해서 batch 시간 계산
  • 3 가지 communication backend: analytical / ASTRA-Sim analytical / collective-sim (실제 시뮬) — runtime 에 swap 가능
  • Co-location 만 (현재 release): PDD (prefill-decode disagg), AFD (attn-FFN disagg) 는 roadmap. 코드는 들어있지만 release guard 가 차단
  • 4-level scheduler hierarchy: Global → Cluster → Replica → ReplicaStage. PDD/AFD 때문에 필요
  • 9+ replica scheduler variants: vLLM / SJ2Q-FastServe-lite / SGLang / Orca / LightLLM / Sarathi 등

def _init_event_queue(self) -> None:
    requests = self._request_generator.generate()
    self._metric_store.register_total_requests(len(requests))

    if self._config.simulation_mode == "offline":
        # 모든 request 가 t=0 도착
        for request in requests:
            request.set_arrived_at(0)
            request.on_arrival(0, ClusterType.MONOLITHIC)
            self._global_scheduler.add_request(request=request, ...)
        self._add_event(GlobalScheduleEvent(0))
    else:
        # online: 각 request 의 arrival_time 에 따라 event 큐에 추가
        for request in requests:
            self._add_event(RequestArrivalEvent(request.arrived_at, request, ...))

Sequential event loop (코어)

파일: frontier/simulator.py:572-703

def _run_sequential(self) -> None:
    while not self._terminate:
        while self._event_queue and not self._terminate:
            _, event = heapq.heappop(self._event_queue)  # 최소 priority pop
            self._set_time(event._time)                  # 글로벌 clock 전진
            new_events = event.handle_event(self._global_scheduler, self._metric_store)
            self._add_events(new_events)
            if self._config.metrics_config.write_json_trace:
                self._event_trace.append(event.to_dict())
        if self._try_promote_terminal_pdaf_scheduler_work():
            continue
        break
    self._write_output()

설계 약점 (Cluster Simulator)

  1. Non-deterministic FP arithmetic — batch aggregation 의 부동소수점 rounding 이 플랫폼 별로 다를 수 있음. PYTHONHASHSEED=0 안 쓰면 dict iteration 도 다름
  2. Unbounded event queue — request 가 완료보다 빠르게 도착하면 큐 무한 grow. 메모리 폭주 가능
  3. All-in-memory metrics — 100만 request 시뮬은 RAM 부족 가능. write_json_trace 끄는 게 안전
  4. Stale event detection silent — schedule_epoch 안 맞는 event 는 WARN 없이 skip. 디버깅 어려움
  5. Tie-breaking on event time — 같은 시각의 다른 type event 가 logically 다른 순서여야 할 때 우선순위 잘못 설정 시 결정 잘못됨
  6. Numerical precision — exec time 예측 결과가 1.0000000001 같이 나오면 ties 깨짐

핵심 설계 원칙

  • Measurement duality: record_function (KERNEL_ONLY) vs cuda_event (CUDA_EVENT) — 어떤 측정법 쓸지 사용자가 매번 명시

설계 약점 (Profiling) — 어떤 게 진짜 본질적이고, 어떤 건 패치 가능한지

각 약점이 "진짜 fundamental" 인지, "tooling 만 고치면 풀리는지" 구분해서.

1. vLLM 의존 — 본질적 (코드 수준 결합)

Attention/MoE/CPU overhead 측정이 진짜로 vLLM 의 내부 API 호출:

  • Attention 측정: vllm.v1.attention.backends.utils.get_kv_cache_layout 호출 — FlashInfer backend 의 KV cache 레이아웃 의존
  • MoE 측정: vllm.model_executor.layers.fused_moe.fused_moe_kernel 직접 사용 — load imbalance 측정용
  • CPU overhead: vLLM 의 scheduler/sampler 실제 호출해서 측정 (또는 vLLM trace replay)

대체 inference engine — TensorRT-LLM, SGLang, llama.cpp 등 — 측정하려면 그 엔진의 op 들을 따로 instantiate 하는 새 profiling script 작성 필요 (lm-eval 은 evaluation framework 라 여기 해당 X — vLLM 을 backend 로 쓰는 거지 대체 엔진 아님).

해결: Frontier 의 design choice 라 fork 해서 backend abstraction 만들거나 NetX-lab upstream PR. 양쪽 다 큰 작업.

3. Sweep cost — 부분 해결 가능 (theoretical fallback)

현재 한 모델 × HW 완전 sweep ~4-5 GPU-hour. 비용 줄이는 방법:

접근정확도비용현재 Frontier 지원?
완전 sweep (현재)실측 그대로 (점 수 많을 때 ±2%)4-5 GPU-hourO
SKIP_SKEW=1 + sparse grid factor 4.0중간 (~5-10% 오차)1-2 GPU-hourO (flag 있음)
Roofline 이론값으로 fill낮음 (~30-50% 오차 — 특히 작은 token 에서)0 GPU-hourX (구현 안 됨)
Dummy mode (고정 1ms)매우 낮음 — 절대값 의미 X, 구조 비교만 OK0O

Roofline 으로 때려넣는 게 안 되는 이유 — 작은 token (e.g. 32 token decode) 에서 실 시간이 Roofline 예측 보다 5-10× 큼:

  • Kernel launch overhead (GPU 당 5-20μs) — token 적으면 dominate
  • Memory access pattern (cache miss, fragmentation)
  • Python overhead (PyTorch dispatcher, eager mode)
  • vLLM 의 batch 구성 overhead (padding, tensor 정렬)

Roofline 은 큰 token (compute-bound 영역) 에서만 ~±15% 정도 맞음. 그래도 "초기 design space exploration" 용으론 충분. 권장 패치: Frontier 에 --analytical_roofline mode 추가 — sweep 안 하고 GPU TFLOPS + HBM BW 만으로 fill. Dummy 보다는 훨씬 의미있는 ballpark.

5. Load imbalance, single-GPU TP fidelity 등 — 본문 그대로
  • MoE load imbalance metadata-only — load_imbalance_cv, load_gini_coefficient 가 feature 로 들어가지만 sweep 은 모두 uniform load 로. 실제 imbalanced 시 정확도 ↓. 해결: imbalanced sweep 추가 (sweep 비용 ↑)
  • Single-GPU TP simulation — TP=N 측정도 single GPU 에서 weight 만 shard. TP>8 같은 큰 차수에서 cross-GPU comm 못 측정. 해결: 실 multi-GPU profile 추가 (별도 cluster 비용)

① LLMServingSim 의 방식 — vLLM 안에서 hook 으로 측정

vLLM 에는 layerwise_profile 이라는 내장 도구가 있음. 각 nn.Module.forward() 호출 직전·직후에 callback (hook) 을 걸어서 레이어별 GPU 시간을 직접 측정:

1. vLLM 엔진 init (실 모델 로딩)
2. 모든 transformer layer 의 forward 에 hook 등록
3. 실 inference 요청 던지기 (예: 64 token 짜리 prompt 한 번)
4. vLLM 가 forward 실행 → 매 layer hook 발화 → 각 layer 의 attention/MLP/etc 시간 기록
5. 결과 모아서 CSV 한 줄로 — 한 batch shape 의 한 측정 끝
6. 다음 batch shape 로 다시 forward (token count, KV length 등 바꿔서)

핵심 특성:

  • vLLM 의 진짜 forward path 통과 — kernel launch, KV cache 접근, Python overhead 등 운영 환경 그대로 측정 → calibration 거의 필요 X
  • sparse grid sweep — token count 를 16, 32, 64, 128, ..., 4096 식 doubling 으로 9-10 점만 측정
  • 5 CSV 출력: attention.csv, dense.csv, per_sequence.csv, moe.csv, skew_fit.csv — 축이 명확히 분리
  • 한 모델/HW 당 profile 시간 ~30-90분

2. 입력 tensor 만 생성 (지정된 num_tokens, hidden_dim, TP_size)

  • rich metadata CSV — 같은 op 라도 측정 method (CUDA_EVENT vs KERNEL_ONLY), precision (FP16/BF16/INT8), model_arch 다 column 으로 분리. 한 모델에 대해 linear_op.csv + linear_op_kernel_only.csv 등 별도 파일.
  • 한 모델/HW 당 profile 시간 ~4-5 GPU-hour (점이 많으니까)

5-3. Interpolation 차이 — 풀어쓰면

두 simulator 모두 profile 측정 점이 sweep grid 한정. 실 sim 중에 batch 가 측정 안 한 token count (예: 333) 일 때, 그 값을 어떻게 구하나?

① LLMServingSim — log-space doubling grid + 선형 보간

profile 의 grid 가 doubling (16, 32, 64, 128, ...) → log scale 에서 등간격.

예: 시뮬 중 batch 가 333 token. profile grid 에서 가장 가까운 두 점은 256 과 512.

측정값:
  num_tokens=256 → 27 us
  num_tokens=512 → 43 us

추정 단계:
  1. log space 위치 비율:
     α = (log(333) - log(256)) / (log(512) - log(256))
       = log(333/256) / log(2)
       = 0.379 / 0.693
       = 0.547   (256 에서 약 55% 쯤)

  2. 선형 보간 (raw 또는 log space):
     선형(raw):    27 + 0.547 × (43 - 27) = 35.8 us
     선형(log):    exp(log(27) + 0.547 × (log(43) - log(27))) = 35.0 us
     ↑ 보통 log-space interp 이 op 의 실 곡선에 더 가까움

왜 doubling grid 인가? Op 시간이 token 수에 대해 대체로 log-affine (Roofline 모델 — FLOPs 도 linear, memory bandwidth 도 linear, 둘의 max() 가 적용되니 log space 에서 거의 직선). 16-32-64-128-256-... 식 doubling 으로 측정해도 그 사이 1-3% 오차.

특징:

  • 측정 점 적음 (~9 per op) → lookup table 크기 작음 (~수 KB)
  • Lookup 시 O(log N) bisect + 2 float arithmetic → ~50ns
  • Grid 너머 token (예: 8192) 은 4096 의 trend 그대로 extrapolation — attention 의 quadratic scaling 시 underestimate

② Frontier — sklearn 학습 + 모든 정수 token 미리 계산해서 dict lookup

점 많이 측정한 다음 (~620 per op) → sklearn 모델로 smooth fitting → 1부터 max_tokens 까지 모두 미리 계산해서 dict 로 저장.

1. profile CSV 읽기 (620 rows of (num_tokens, mean_us))
2. GridSearchCV 로 sklearn 학습:
   RandomForestRegressor or PolynomialRegression
   features = [num_tokens]  (attention/moe 는 multi-feature)
   target = time_stats.mlp_up_proj.median
3. 학습된 모델로 모든 정수 token count 미리 예측해서 dict 에 저장:
   predictions["mlp_up_proj"] = {}
   for n in 1..max_tokens:        # e.g. max_tokens=32768
       predictions["mlp_up_proj"][(n,)] = model.predict([[n]])[0]
   # → 32K × op 갯수 × 측정 환경 × precision = MB 단위 cache
4. sim 시점 lookup:
   key = (333,)
   if key in predictions["mlp_up_proj"]:
       return predictions[key]    # ← O(1) dict access, no math
   else:
       return model.predict([[333]])[0]   # ← regression fallback (드물게)

특징:

  • 측정 점 많음 (~620) + regression smoothing → 더 정확한 곡선 fitting
  • Sim 시점 lookup O(1) dict access → ~100ns (LLMServingSim 보다 살짝 느림 — math 없는 대신 Python dict 오버헤드)
  • 메모리 cache 큼 — 32K × 5 op × 2 TP × 2 measurement type = ~10MB. 절대 크기 작아서 문제 X
  • Grid 너머 extrap 은 sklearn 모델 종류에 따라 다름:
    • RandomForest: nearest leaf 의 값 그대로 (saturation 효과)
    • PolynomialRegression degree=2: quadratic 따라 외삽 — attention 의 quadratic 영역 잘 따라감

7-1. Use case #1 — SLA-Aware Pareto Frontier Search

문제: TTFT < 500ms 와 generation speed > 50 tok/s 를 동시에 만족시키면서 비용 최저인 (architecture, parallelism) config 찾기.

전통적 방법: H100 4 vs 8장, TP=2 vs 4 vs 8, batch_size 32 vs 64 ... 모든 조합 실 GPU 클러스터 띄워서 측정. 한 조합당 셋업 30분 + 측정 30분 = 1h. 50 조합 × $20 (H100 spot 1h × 8장) = $1000.

Frontier 활용: 같은 50 조합을 sim 으로 돌리면 CPU 만 → 한 조합당 5-10분, 비용 $0. 후보 5개로 좁힌 다음 실 GPU 검증 → 90% 비용 절감.

      bash examples/architecture/co-location/offline/dense_model_basic.sh \
        ATTN_TP=$tp NUM_REPLICAS=$replicas MAX_BATCH=$batch_size \
        -- --metrics_config_run_id $run_id
    done
  done
done

9-2. 기능적 약점 (코드 분석 기반)

  1. Acceptance rate 가 trace-based — speculative decoding 의 실제 quality (draft model accuracy) 변화 모델링 불가
  2. Prefix cache eviction 이 단순 LRU — 의미 분류 / cross-request affinity 미반영
  3. MoE expert load imbalance 가 metadata feature 만 — actual per-expert 측정 안 함
  4. Quantization 자체 overhead (dequant/requant) 미모델 → quantization 처리율 이득 overestimate
  5. CUDA Graph capture cost (100-500μs per shape) 미모델 → 다양한 batch shape 시 latency 변동 underestimate
  6. Calibration validation 자동화 X — operator 가 수동 scale 조정

9-3. LLMServingSim 과 cross-check 활용

두 simulator 가 모두 cost-table 방식이지만 다른 알고리즘:

  • Profile 의 같은 raw measurement 를 양쪽에 입력 → 결과 비교
  • 일치 → 결과 신뢰 ↑
  • 불일치 → 어느 쪽 모델이 어떤 가정에서 다른지 검증 기회

아쉽게도 두 시뮬레이터의 profile schema 가 달라서 자동 변환 안 됨. 손으로 raw GPU 측정값을 양쪽 format 으로 변환해야. 1회성 검증 cost ~1-2 일.
