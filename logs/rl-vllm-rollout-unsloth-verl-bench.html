One-line summary. In the RL (GRPO) loop, turning on vLLM rollout is almost the only big lever — generation throughput jumped 4.4× on a single GCD (517 → 2,280 tok/s), and the whole loop got 3.7× faster. By contrast Unsloth has essentially no effect under the full-parameter toggle (it can't touch the generation bottleneck). Moving to veRL, a fast rollout engine is the default, so generation is no longer the dominant stage, and the KL/reference forward and reward computation take comparable shares of the cost. Every command, config, failure, and code flow is recorded as-is.한 줄 요약. RL(GRPO) 루프에서 vLLM rollout 을 켜는 것이 거의 유일한 큰 레버다 — 생성 처리량이 단일 GCD에서 4.4× (517 → 2,280 tok/s), 루프 전체는 3.7× 빨라졌다. 반면 Unsloth 는 full-parameter 토글에선 사실상 무효과(생성 병목을 건드리지 못함). veRL 로 옮기면 빠른 롤아웃 엔진이 기본값이라 생성은 더 이상 지배적 단계가 아니고, KL/reference forward·reward 계산이 비등하게 비용을 차지한다. 모든 명령·config·실패·코드 흐름을 그대로 기록한다.

1. What I was curious about — what we measure1. 궁금했던 것 — 무엇을 측정하나

The starting question was a single one: "In RL (GRPO) training, does vLLM rollout actually speed up the loop? By how much? Where is the bottleneck?" I added one more thing on top — Unsloth on/off. So we look at a 2×2 crossing two options:출발 질문은 하나였다: "RL(GRPO) 학습에서 vLLM rollout 이 실제로 루프를 빠르게 하는가? 얼마나? 병목은 어디인가?" 여기에 한 가지를 더 얹었다 — Unsloth on/off. 그래서 옵션 2개를 교차한 2×2를 본다:

  1. vLLM rollout on/off — whether to do generation (rollout) with vLLM (paged-attention, continuous batching) or with plain HuggingFace model.generate().vLLM rollout on/off — 생성(rollout) 을 vLLM(paged-attention, continuous batching)로 할지, 평범한 HuggingFace model.generate() 로 할지.
  2. Unsloth on/off — whether to apply Unsloth's kernel patching (in-place patches to attention, optimizer, etc.) or not.Unsloth on/off — Unsloth 의 커널 패칭(어텐션·옵티마이저 등 in-place 패치)을 입힐지 말지.

Then as follow-ups I looked at two more things: (a) putting Unsloth's real path (LoRA + 4bit) and vanilla LoRA · 4bit QLoRA on the same axis to directly check "so does shrinking the training portion shrink the bottleneck?", and (b) recording the input (prompt) and output (generation) token lengths in every condition (§6). Finally, moving to veRL (a large-scale RL framework), I look at how the time distribution changes between TRL's single-process colocate approach and veRL's Ray-based disaggregated approach (§7).그다음 후속으로 두 가지를 더 봤다: (a) Unsloth 의 진짜 경로(LoRA + 4bit) 와 vanilla LoRA·4bit QLoRA 를 같은 축에 올려 "그럼 학습부를 줄이면 병목이 줄어드나"를 직접 확인하고, (b) 모든 조건에서 입력(프롬프트)·출력(생성) 토큰 길이를 기록했다(§6). 마지막으로 veRL(대규모 RL 프레임워크)로 옮겨, TRL 의 단일 프로세스 colocate 방식과 veRL 의 Ray 기반 단계 분리(disaggregated) 방식에서 시간 분포가 어떻게 달라지는지 본다(§7).

Quick terms. GRPO = RL that draws G responses per prompt (rollout), scores them with a rule-based reward, and updates the policy with the within-group relative advantage. rollout = the stage where the model generates responses (inference). colocate = the training model and generation engine coexist on the same GPU and same process. weight-sync = pushing the one-step-updated policy weights back into the generation engine (vLLM).용어 빨리 풀기. GRPO = 한 프롬프트에 응답을 G개 뽑아(rollout), 규칙 기반 보상으로 채점하고, 그룹 내 상대 우위(advantage)로 정책을 업데이트하는 RL. rollout = 모델이 응답을 생성하는 단계(추론). colocate = 학습 모델과 생성 엔진이 같은 GPU·같은 프로세스에 공존. weight-sync = 한 스텝 업데이트한 정책 가중치를 생성 엔진(vLLM)에 다시 밀어넣는 것.
Recording principle. Every command, config, failure, workaround, and code flow as-is. Since it's a shared GPU node, no pip on the host → everything inside Docker. Tear down the container immediately after running, return the GPU.기록 원칙. 모든 명령·config·실패·우회·코드 흐름을 그대로. 공유 GPU 노드라 호스트에 pip 금지 → 전부 Docker 안에서. 실행 후 컨테이너 즉시 정리, GPU 반납.

3-2. How we split time per stage3-2. 어떻게 단계별로 시간을 쪼개나

TRL's GRPOTrainer abstracts the loop away, so I instrumented two spots directly:TRL GRPOTrainer 는 루프를 추상화해 버려서, 직접 두 군데를 계측했다:

  • rollout + scoring stage: wrap GRPOTrainer._generate_and_score_completions() with a monkeypatch to time it. This function handles the "generation → reward → logprob" bundle.rollout+채점 단계: GRPOTrainer._generate_and_score_completions() 를 monkeypatch 로 감싸 시간 측정. 이 함수가 "생성 → 보상 → logprob" 묶음을 담당한다.
  • whole step: step wall-clock via TrainerCallback.on_step_begin/on_step_end. whole − rollout = training (backward/optimizer).스텝 전체: TrainerCallback.on_step_begin/on_step_end 로 스텝 벽시계. 전체 − rollout = 학습(backward/optimizer).
# 핵심 계측 (grpo_bench.py 발췌)
orig = trainer._generate_and_score_completions
def timed(inputs):
    t = time.time(); r = orig(inputs); state["roll"] += time.time() - t
    state["gen_tok"] += sum(len(x) for x in r["completion_ids"])
    return r
trainer._generate_and_score_completions = timed   # rollout 시간·생성 토큰 집계

4. Code flow — anatomy of one RL step4. 코드 흐름 — RL 한 스텝의 해부

To know "where vLLM speeds things up," you have to see which code path one step actually takes. Based on TRL 1.6.0 grpo_trainer.py:"vLLM 이 어디를 빠르게 하나"를 알려면 한 스텝이 실제로 어떤 코드 경로를 타는지를 봐야 한다. TRL 1.6.0 grpo_trainer.py 기준:

The branch in ① where vLLM vs HF diverge①에서 vLLM vs HF 가 갈리는 분기

# grpo_trainer.py · _generate_single_turn()  (line ~1353)
if self.use_vllm:
    if self.state.global_step != self._last_loaded_step:
        with profiling_context(self, "sync_weights"):
            self.vllm_generation.sync_weights()      # ⑥ 갱신 가중치를 vLLM에 적재
        self._last_loaded_step = self.state.global_step
    # → vLLM 엔진으로 생성 (paged-attention, continuous batching)
else:
    with ..., torch.no_grad(), self._dist.summon_full_params(...):
        prompt_completion_ids = unwrapped_model.generate(   # ← 평범한 HF 자기회귀 생성
            **generate_inputs, generation_config=self.generation_config)

There are two key points. (1) The HF path gathers FSDP parameters via summon_full_params and then runs model.generate() — plain autoregressive decoding with no KV paging and no continuous batching. So it's slow (measured ~520 tok/s). (2) The vLLM colocate path hands tokens to a vLLM engine inside the same GPU and same process. Right before generation each step it pushes weights into vLLM via sync_weights() (⑥), but because it's colocate, it's an in-process state_dict load rather than a network transfer, so it's cheap — and that is the decisive difference from weight-sync in distributed RL.핵심은 두 가지다. (1) HF 경로는 FSDP 파라미터를 summon_full_params 로 모은 뒤 model.generate() 를 도는 단순 자기회귀 디코딩 — KV 페이징도, continuous batching 도 없다. 그래서 느리다(측정값 ~520 tok/s). (2) vLLM colocate 경로는 같은 GPU·같은 프로세스 안의 vLLM 엔진에 토큰을 넘긴다. 매 스텝 생성 직전 sync_weights() 로 가중치를 vLLM 으로 밀어넣는데(⑥), colocate 라 네트워크 전송이 아니라 in-process state_dict 적재라서 싸다 — 이게 분산 RL 의 weight-sync 와 결정적으로 다른 점이다.

5-1. Reading it — three things stand out5-1. 읽기 — 세 가지가 보인다

① vLLM rollout is almost everything. Just switching HF→vLLM gives 4.40× generation (517→2,280 tok/s), 4.66× per step, 3.71× for the whole loop. The reason is exactly Figure 1 — rollout was eating 91.8% of the loop, so speeding it up speeds up everything.① vLLM rollout 이 거의 전부다. HF→vLLM 으로 켜는 것만으로 생성 4.40× (517→2,280 tok/s), 스텝당 4.66×, 루프 전체 3.71×. 이유는 그림 1 그대로 — rollout 이 루프의 91.8%를 먹고 있었으니, 그걸 빠르게 하면 전체가 빨라진다.

② Unsloth has (under this toggle) almost no effect. Among vLLM-off pairs (A↔C), 517→557 tok/s, +7.6%. Among vLLM-on pairs (B↔D), essentially a tie (2,280 vs 2,269, within noise). Why? Unsloth's kernel patching aims at backward/optimizer (⑤), but in this loop where generation is 80–92%, no matter how much you shave there the total time doesn't move. In fact, looking at just the training portion — B's non-rollout time 0.530 s/step → D 0.435 s/step, so backward got ~18% faster. It's just buried because it's a small slice of the loop.② Unsloth 는 (이 토글에선) 거의 무효과. vLLM off 끼리(A↔C) 517→557 tok/s, +7.6%. vLLM on 끼리(B↔D)는 사실상 동률(2,280 vs 2,269, 노이즈 범위). 왜? Unsloth 의 커널 패칭은 backward/옵티마이저(⑤)를 노리는데, 생성이 80~92%인 이 루프에선 거기를 아무리 깎아도 총시간이 안 움직인다. 실제로 학습부만 보면 — B 의 비-rollout 시간 0.530 s/step → D 0.435 s/step 으로 backward 는 ~18% 빨라졌다. 다만 그게 루프의 작은 조각이라 묻힌 것.

Is this fair to Unsloth? No — it was designed that way on purpose. For apple-to-apple with A/B we toggled Unsloth in a "kernel-patching only" state: full-parameter, no LoRA, fast_inference=False. Unsloth's real strengths are (a) LoRA/4-bit training memory and speed, and (b) its own vLLM inference path — both areas this toggle turned off. In other words, this result doesn't mean "Unsloth is bad," it means "in a loop where generation is the bottleneck, kernel optimization of the training portion can't be a lever."Unsloth 에게 공정한가? 아니다 — 의도적으로 그렇게 설계했다. 우리는 A/B 와 apple-to-apple 을 위해 full-parameter, LoRA 없음, fast_inference=False 로 Unsloth 를 "커널 패칭만" 상태로 토글했다. Unsloth 의 진짜 강점은 (a) LoRA/4-bit 학습 메모리·속도, (b) 자체 vLLM 추론 경로다 — 둘 다 이 토글이 끈 영역. 즉 본 결과는 "Unsloth 가 나쁘다"가 아니라 "생성이 병목인 루프에서 학습부 커널 최적화는 지렛대가 못 된다"는 뜻이다.

③ Even with vLLM on, rollout is still the largest stage (77–81%). Even after the 4.4× speedup, generation is the biggest → "then what if we detach generation from training and run it asynchronously?" is the natural next question, and that's the design motivation of veRL.③ vLLM 을 켜도 rollout 은 여전히 최대 단계(77~81%)다. 4.4× 빨라졌어도 생성이 제일 크다 → "그럼 생성을 학습과 떼어 비동기로 돌리면?"이 자연스러운 다음 질문이고, 그게 veRL 의 설계 동기다.

6-1. Answer: the bottleneck doesn't shrink — it gets deeper6-1. 답: 병목은 줄지 않는다 — 오히려 더 깊어진다

Separating the two flows makes it clear:두 흐름을 분리해 보면 분명하다:

  • The training portion (train/step) does shrink — just barely. On the vLLM-on side: full 0.530 → bf16 LoRA 0.512 → 4bit QLoRA 0.464 → Unsloth full-param 0.435 s/step. Because it's 0.5B, the optimizer/memory savings are negligible (LoRA's gain grows the larger the model and the more memory-bound it is).학습부(train/step)는 줄긴 한다 — 아주 조금. vLLM on 기준 full 0.530 → bf16 LoRA 0.512 → 4bit QLoRA 0.464 → Unsloth full-param 0.435 s/step. 0.5B 라 옵티마이저/메모리 절감 효과가 미미하다(LoRA 의 이득은 모델이 클수록, 메모리 바운드일수록 커진다).
  • But the bottleneck (generation) gets worse. HF generation 517 → 325 → 192 tok/s, vLLM 2,280 → 998 tok/s (4bit). Because LoRA adds an adapter matmul and 4bit adds a dequant every token. On top of that, 4bit+vLLM merges LoRA into the 4bit base every step and reloads it into vLLM (peft even warns about "rounding differences when merging into 4-bit"), making it slower still.그런데 병목(생성)은 더 나빠진다. HF 생성 517 → 325 → 192 tok/s, vLLM 2,280 → 998 tok/s(4bit). LoRA 는 어댑터 행렬곱을, 4bit 는 디퀀트를 매 토큰 추가하기 때문. 게다가 4bit+vLLM 은 매 스텝 LoRA 를 4bit 베이스에 머지해 vLLM 에 다시 싣느라(peft 가 "4-bit 머지 시 rounding 차이" 경고까지 낸다) 더 느리다.
  • So the rollout share actually goes up (91.8% → 95.0% → 97.5%, vLLM off). The bottleneck doesn't move to the training portion — it concentrates more on generation. On small models, LoRA/4bit makes RL slower overall.그래서 rollout 비중이 오히려 올라간다(91.8% → 95.0% → 97.5%, vLLM off). 병목이 학습부로 옮겨가는 게 아니라 생성에 더 쏠린다. 작은 모델에선 LoRA/4bit 가 RL 을 전체적으로 더 느리게 만든다.
So the answer to "does using Unsloth/LoRA shrink the bottleneck?": at this scale, no. LoRA/4bit/Unsloth are tools that aim at the training portion, but here the training portion isn't the bottleneck. They become meaningful when (a) the model is so large that full-param doesn't fit in memory (then LoRA/4bit is the only way to "make it work"), or (b) generation is split out to a separate engine/GPU so the training portion becomes the real bottleneck.그러니 "Unsloth/LoRA 쓰면 병목 줄어?"의 답: 이 규모에선 아니오. LoRA/4bit/Unsloth 는 학습부를 노리는 도구인데, 여기선 학습부가 병목이 아니다. 의미가 생기는 건 (a) 모델이 커서 full-param 이 메모리에 안 들어갈 때(그땐 LoRA/4bit 가 "되게 만드는" 유일한 길), (b) 생성을 별도 엔진/GPU 로 떼어내 학습부가 진짜 병목이 됐을 때다.

6-1. A time distribution opposite to TRL — why?6-1. TRL 과 정반대인 시간 분포 — 왜?

In TRL-B rollout was 77%, but in veRL gen is 27%. Same model and data — why is it flipped? It's the combination of three things (and all three are lessons):TRL-B 에선 rollout 이 77%였는데 veRL 에선 gen 이 27%다. 같은 모델·데이터인데 왜 뒤집혔나? 세 가지가 합쳐진 결과다(그리고 셋 다 교훈이다):

  1. KL/reference was turned on. The TRL side skipped the reference forward entirely with beta=0, but veRL has use_kl_loss=True → two extra forwards attach: ref (1.15s) + old_log_prob (0.75s). It's seeing in time terms that one line of KL control adds two forwards to the training portion.KL/reference 를 켰다. TRL 측은 beta=0 으로 reference forward 를 통째로 생략했지만, veRL 은 use_kl_loss=True → ref(1.15s) + old_log_prob(0.75s) 두 번의 추가 forward 가 붙는다. KL 제어 한 줄이 학습부에 forward 두 개를 더한다는 걸 시간으로 본 셈.
  2. reward is costlier than expected (1.9s). The cost of running gsm8k rule scoring in CPU Python over 128 sequences. The smaller the model, the cheaper generation gets, so reward becomes a relatively large stage — a real-world signal that verifier parallelization is needed at scale.reward 가 생각보다 비싸다(1.9s). gsm8k 규칙 채점을 128개 시퀀스에 대해 CPU 파이썬으로 도는 비용. 작은 모델일수록 생성이 싸지니 reward 가 상대적으로 큰 단계가 된다 — 대규모에선 verifier 병렬화가 필요하다는 실전 신호.
  3. generate_sequences (pure generation) is 1.3s; the gap to gen (2.36s) ≈ vLLM engine wake/sleep + weight reshard overhead. Because it's colocate, training and generation alternate over the same GPU memory, and the cost of waking and putting it to sleep hides here.generate_sequences(순수 생성)는 1.3s, gen(2.36s)과의 차이 ≈ vLLM 엔진 wake/sleep + 가중치 reshard 오버헤드. colocate 라 학습과 생성이 같은 GPU 메모리를 번갈아 쓰며 깨우고 재우는 비용이 여기 숨어 있다.
This is the key insight. "Turn on vLLM rollout" is a necessary but not sufficient condition. Once you lay down a fast generation engine, the bottleneck moves generation → (KL forward + reward + backward). That's why large-scale RL frameworks don't stop at just making generation fast — they detach ref/logprob forward, reward, and backward each and try to overlap them asynchronously (disaggregated rollout).이게 핵심 통찰이다. "vLLM rollout 을 켜라"는 필요조건이지 충분조건이 아니다. 일단 빠른 생성 엔진을 깔면 병목이 생성 → (KL forward + reward + backward) 로 이동한다. 그래서 대규모 RL 프레임워크는 생성만 빠르게 하는 데서 멈추지 않고, ref/logprob forward·reward·backward 를 각각 떼어 비동기로 겹치려 한다(disaggregated rollout).

9. Conclusion — levers and bottlenecks9. 결론 — 레버와 병목

  1. vLLM rollout is almost the only big lever for RL loop acceleration. On a single GCD, 4.4× generation, 3.7× loop. Because rollout was eating 80–92% of the loop.vLLM rollout 은 RL 루프 가속의 거의 유일한 큰 레버. 단일 GCD 에서 생성 4.4×, 루프 3.7×. rollout 이 루프의 80~92%를 먹고 있었기 때문.
  2. Unsloth · LoRA · 4bit are not levers in this loop — they backfire. All three aim at the training portion (backward) (full 0.530 → bf16 LoRA 0.512 → 4bit 0.464 s/step, ~12% saved), but the training portion isn't the bottleneck. On top of that, the LoRA adapter and 4bit dequant make the generation that IS the bottleneck slower (generation 517 → 325 → 192 tok/s, vLLM-off). As a result the rollout share concentrates further, 91.8%→97.5%, and at 0.5B scale RL gets slower overall. LoRA/4bit shines when the model is large enough that full-param doesn't fit in memory.Unsloth·LoRA·4bit 는 이 루프에서 지렛대가 아니다 — 오히려 역효과. 셋 다 학습부(backward)를 노리는데(full 0.530 → bf16 LoRA 0.512 → 4bit 0.464 s/step, ~12% 절감), 학습부는 병목이 아니다. 게다가 LoRA 어댑터·4bit 디퀀트가 병목인 생성을 더 느리게 만든다(생성 517 → 325 → 192 tok/s, vLLM-off). 결과적으로 rollout 비중이 91.8%→97.5%로 더 쏠리고 0.5B 규모에선 RL 이 전체적으로 느려진다. LoRA/4bit 가 빛나는 건 모델이 커서 full-param 이 메모리에 안 들어갈 때다.
  3. input:output ≈ 1:4. gsm8k prompt ~99 tok, RL-untrained 0.5B natural generation ~395 tok. The length also reveals why generation is expensive (long output = long autoregressive decoding).입력:출력 ≈ 1:4. gsm8k 프롬프트 ~99 tok, RL-미학습 0.5B 의 자연 생성 ~395 tok. 생성이 비싼 이유가 길이에서도 드러난다(긴 출력 = 긴 자기회귀 디코딩).
  4. The bottleneck isn't fixed — it moves. Turn on vLLM and generation drops out; the next candidates are the KL/reference forward and reward computation (veRL: gen 27% / reward 24% / update 28% / ref+logprob 21%). Confirmed in time terms the cost of "one line of KL = two forwards."병목은 고정이 아니라 이동한다. vLLM 을 켜면 생성이 빠져나가고, 다음 후보는 KL/reference forward 와 reward 계산이다(veRL: gen 27% / reward 24% / update 28% / ref+logprob 21%). "KL 한 줄 = forward 두 개"라는 비용을 시간으로 확인.
  5. veRL 0.8.0 effectively forces a fast rollout engine (the HF-only rollout path was removed). At the framework level it has nailed down "slow generation is not an option."veRL 0.8.0 은 빠른 롤아웃 엔진을 사실상 강제한다(HF 단독 롤아웃 경로 제거). 프레임워크 차원에서 "느린 생성은 선택지가 아님"을 못박은 것.
  6. colocate weight-sync is cheap. It's an in-process load in the same process, so there's no network transfer — a separate problem from the weight-sync cost of distributed (multi-node) RL, which is the next experiment.colocate 의 weight-sync 는 싸다. 같은 프로세스 in-process 적재라 네트워크 전송이 없다 — 분산(멀티노드) RL 의 weight-sync 비용과는 별개 문제이며, 그건 다음 실험감.
Caution — limits of comparison. Do not directly pit the total times of TRL (1 GCD, KL off) and veRL (2 GCD, KL on) against each other. This experiment looks at two things separately: (a) the vLLM/Unsloth toggle effect within TRL, and (b) veRL's stage distribution. At 0.5B · 6-step scale, the message is the ratios and bottleneck structure, not absolute numbers.주의 — 비교의 한계. TRL(1 GCD, KL off)과 veRL(2 GCD, KL on) 의 총시간을 직접 맞대지 말 것. 본 실험은 (a) TRL 안에서의 vLLM/Unsloth 토글 효과, (b) veRL 의 단계 분포 두 가지를 따로 보는 것이다. 0.5B·6스텝 규모라 절대 수치보다 비율·병목 구조가 메시지다.
