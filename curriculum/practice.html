4. Dynamic Bucketing — 세 가지 의미

"버킷팅"은 문맥마다 다른 것을 가리킨다. 공통점은 하나: 가변 크기 입력을 미리 정한 몇 개의 크기로 맞춰서(패딩) 정적 shape의 이점을 얻고, 그 대가로 패딩 낭비를 낸다. "dynamic"은 버킷 경계나 배치 크기를 런타임 분포·예산에 맞춰 정한다는 뜻.

4-1. 정적 shape 실행을 위한 버킷 — CUDA graph, XLA/TPU, Gaudi

CUDA graph는 캡처한 shape로만 replay할 수 있다. 그래서 vLLM은 몇 개의 배치/토큰 크기로 graph를 캡처해 두고, 실제 배치를 그걸 담을 수 있는 가장 작은 graph로 패딩해 실행한다. dispatch()의 docstring이 그대로 이 동작을 설명한다:

"A uniform decode batch takes the smallest decode graph of its query length that covers `num_tokens`, which may be padded…"
— vllm/v1/worker/gpu/cudagraph_utils.py L569–571

SGLang도 같은 일을 bisect.bisect_left(buckets, raw_size)로 한다. XLA/TPU나 Gaudi처럼 컴파일이 shape에 묶인 하드웨어에서는 prefill 길이까지 버킷으로 나눠 미리 컴파일한다 (vLLM의 TPU·Gaudi 백엔드 문서 참고. 세부 env 이름은 백엔드 버전마다 달라 재확인 필요).

설계 판단: 버킷을 촘촘히 → 패딩 낭비↓, 캡처 메모리·시간↑. 듬성듬성 → 반대. 실제 배치 크기 분포(히스토그램)에 버킷을 맞추는 것이 실무 튜닝.

4-2. 요청 큐잉 측 dynamic batching — 언제 배치를 닫을 것인가

NVIDIA Triton Inference Server의 dynamic batcher는 preferred_batch_size와 max_queue_delay_microseconds로 "더 모을지 vs 지금 보낼지"를 정한다 (Triton 공식 문서: Batchers). LLM 엔진의 continuous batching은 이 질문을 step마다 다시 묻는 것이라 대기 타이머가 거의 필요 없지만, encoder형 음성 모델(ASR encoder, 코덱, FM TTS 한 step)은 요청 단위 실행이라 이 트레이드오프가 그대로 남는다. 실시간 음성에선 max-wait가 곧 지연 예산이다.

4-3. 가변장 음성의 길이 버킷 — 패딩 낭비를 줄이는 묶기

길이가 제각각인 오디오를 한 배치에 넣으면 가장 긴 것에 맞춰 패딩한다. 비슷한 길이끼리 묶으면(버킷) 낭비가 준다. 학습 쪽 표준 구현이 lhotse의 DynamicBucketingSampler(총 duration 예산으로 배치 크기를 정하고, 데이터 분포로 버킷 경계 추정) — 2차적으로 참고 (lhotse 문서). 추론 서버에서는 여기에 4-2의 max-wait가 붙는다: 같은 버킷의 짝을 기다리는 시간 vs 패딩 낭비.

패딩 낭비 공식 — 배치 길이 l₁…l_B, 패딩 후 길이 L = max lᵢ: 
waste = 1 − Σ lᵢ / (B · L)
예: 2s, 3s, 4s, 15s 를 한 배치 → 1 − 24/60 = 60% 낭비. [2,3,4] / [15] 두 버킷으로 나누면 1 − 9/12 = 25%, 0% → 전체 계산량 12+15 = 27 vs 60.
왜 LLM 엔진은 버킷 대신 packing을 쓰나LLM prefill은 varlen attention(FlashAttention의 cu_seqlens, FlashInfer ragged)으로 여러 시퀀스를 패딩 없이 한 줄로 이어붙여(packing) 처리한다. 이 경우 버킷이 필요 없다. 반면 conv/정적 shape 커널을 쓰는 음성 encoder·코덱·CUDA graph 경로는 아직 패딩이 필요해서 버킷이 의미를 갖는다. Whisper는 입력을 30초 고정 윈도로 패딩하므로(2212.04356 §2) 길이 버킷이 무의미하고, 대신 VAD로 잘라 30초 창을 채우는 쪽으로 최적화한다.

도장 위치: 4-1은 M4 실전 랩(CUDA graph 버킷 히스토그램), 4-2·4-3은 M8 토이 프로젝트(가변장 동적 배처 + max-wait)에서 직접 구현.
