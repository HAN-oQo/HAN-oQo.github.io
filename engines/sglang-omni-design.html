SGLang-Omni — the design behind multi-stage speech serving SGLang-Omni: 다단계 음성 서빙 런타임의 설계

Not a fork of SGLang, and not an orchestrator either. A serving engine whose unit of scheduling is the stage, because a speech model is not one transformer but three to seven pieces with opposite compute profiles. Based on the code and the two official design blogs, it goes down to the one component you would copy when building a voice agent yourself. SGLang 포크도, 오케스트레이터도 아니다. 스케줄링 단위가 스테이지인 서빙 엔진이다. 음성 모델이 트랜스포머 하나가 아니라 계산 성격이 정반대인 서너~일곱 개 조각이기 때문이다. 코드와 공식 설계 블로그 두 편을 근거로, voice agent 를 직접 만들 때 베낄 부분까지 다룬다.

1What it actually is — and the 1.4% that misleads정체: 오해를 부르는 1.4%

Open the repository looking for "how do I build a voice agent", and you land in models/streaming_cascade/: a declarative graph that wires an ASR server, an LLM server and a TTS server into a conversation. It reads like the whole product. It is not. It is 3,683 lines out of 271,850. "voice agent 를 어떻게 만드나"를 찾아 저장소를 열면 models/streaming_cascade/ 에 닿는다. ASR·LLM·TTS 서버를 선언적으로 엮어 대화를 만드는 그래프다. 제품 전체처럼 보이지만 271,850 줄 가운데 3,683 줄뿐이다.

The other 98.6% is an inference engine in the same seat as vLLM or SGLang: it loads models onto GPUs and runs them. The two halves answer different questions, and either can be used without the other. 나머지 98.6% 는 vLLM·SGLang 과 같은 자리의 추론 엔진으로, 모델을 GPU 에 올려 직접 돌린다. 두 부분은 서로 다른 질문에 답하고, 한쪽만 떼어 쓸 수도 있다.

Its relationship to SGLang is a patch layer, not a forkSGLang 과의 관계: 포크가 아닌 패치 계층

The dependency is pinned (sglang==0.5.22 in pyproject.toml) and every upstream symbol re-enters through one door, sglang_omni/vendor/sglang/, where the few patches carry comments saying they can be deleted once upstream merges the equivalent change. The clearest example is OmniScheduler: 4,224 lines, 126 methods, and it does not inherit from upstream Scheduler. It borrows unbound methods through __getattr__ and binds them to itself, keeping upstream's batch-selection logic without inheritance coupling. 의존성은 pyproject.toml 에 sglang==0.5.22 로 고정돼 있다. 상류 심벌은 모두 sglang_omni/vendor/sglang/ 한 곳을 거치고, 몇 안 되는 패치에는 "상류가 같은 변경을 머지하면 지워도 된다"는 주석이 붙어 있다. 가장 분명한 예가 OmniScheduler 다. 4,224 줄, 메서드 126 개인데도 상류 Scheduler 를 상속하지 않는다. __getattr__ 로 언바운드 메서드를 빌려 자기에게 바인딩해서, 상류의 배치 선택 로직은 쓰되 상속 결합은 피한다.

The division of labor역할 분담 SGLang owns the inside of one stage: autoregressive scheduling, KV cache, kernels. SGLang-Omni owns everything between stages: pipeline topology, stage lifecycle, inter-stage transport, model-family integration and the OpenAI-compatible surface. When a stage is autoregressive, its inside is handed to SGLang. SGLang 은 스테이지 하나의 안쪽(자기회귀 스케줄링, KV 캐시, 커널)을 맡는다. SGLang-Omni 는 스테이지 사이(파이프라인 토폴로지, 스테이지 수명주기, 단계 간 전송, 모델 패밀리 통합, OpenAI 호환 표면)를 맡는다. 자기회귀 스테이지라면 그 안쪽은 SGLang 에 넘긴다.

2The stage graph: why one model becomes five스테이지 그래프: 모델 하나가 다섯이 되는 이유

An LLM serving engine can assume one kind of step: take tokens, produce a token. Continuous batching, paged KV and prefix reuse all rest on that uniformity. A speech model breaks it. Qwen3-Omni is not a transformer you call but a graph you traverse, and its pieces disagree about almost everything. LLM 서빙 엔진은 토큰을 받아 토큰을 내놓는 한 종류의 단계만 가정한다. 연속 배칭, 페이지 KV, 접두사 재사용이 모두 그 균질함 위에 서 있다. 음성 모델은 이 가정을 깬다. Qwen3-Omni 는 호출하는 트랜스포머가 아니라 통과하는 그래프이고, 조각마다 성격이 거의 다 다르다.

Figure 2 · Qwen3-Omni stage graph. Redrawn from Figure 1 of the SPG topology blog; stage names from examples/configs/qwen3_omni_colocated_h200.yaml. 그림 2 · Qwen3-Omni 스테이지 그래프. SPG 토폴로지 블로그 Figure 1 재구성. 스테이지 이름은 examples/configs/qwen3_omni_colocated_h200.yaml 기준.

Three properties that decide where a boundary goes경계를 어디 그을지 정하는 세 가지 성질

The blog names three measurable properties that make this graph a design problem. The first is why talker and code predictor share one box above. 블로그는 이 그래프를 설계 문제로 만드는 측정 가능한 성질 셋을 꼽는다. 첫째가 위 그림에서 talker 와 code predictor 가 한 상자에 들어간 이유다.

Synchronization granularity동기화 입도

One-shot handoff, bufferable stream, or per-step feedback. Per-step feedback would cost a round trip every decode step, so those modules fuse into one stage.한 번 인계, 버퍼링 가능한 스트림, 매 스텝 피드백 중 하나다. 매 스텝 피드백이면 경계가 디코드 스텝마다 왕복 비용을 낳으므로 한 스테이지로 융합한다.

Bottleneck resource병목 자원

Device-bound or host-bound. Replicating host-side preprocessing costs almost nothing and relieves a real queue; replicating thinker costs 77% of a GPU.장치 병목인가 호스트 병목인가. CPU 작업인 preprocessing 은 복제가 거의 공짜이고, thinker 복제는 GPU 의 77% 를 또 쓴다.

Resident state size상주 상태 크기

Sets memory budgets and how many stages fit on one device; the per-stage gpu_memory_fraction in the YAML expresses it.메모리 예산과 한 장치에 들어갈 스테이지 수를 정한다. YAML 의 스테이지별 gpu_memory_fraction 이 이것이다.

"The execution strategy affects serving performance as strongly as the efficiency of any individual stage, and that the model architecture should not dictate it."

— SGLang-Omni, Stage–Process–GPU Topology

Read it as a statement about the problem, not about tuning: the language model is 77% of the budget and the vocoder 1.4%, yet the vocoder is what the listener hears first and where latency is felt. One scheduler and one memory pool for both would let the large one starve the small one. 튜닝 값이 아니라 문제를 보여 주는 숫자다. 언어 모델이 예산의 77%, 보코더가 1.4% 인데, 사용자가 가장 먼저 듣고 지연을 체감하는 곳은 보코더다. 스케줄러와 메모리 풀을 하나로 합치면 큰 쪽이 작은 쪽을 굶길 수 있다.

3SPG topology: separating what runs from where it runsSPG 토폴로지: 무엇이 도는지와 어디서 도는지의 분리

Once stages exist, a question appears that the model architecture cannot answer: which stages share an OS process, how many copies of each run, and which device each copy lands on. SGLang-Omni gives this its own notation. For a stage graph G = (S, E), a topology is 스테이지가 생기면 모델 구조가 답하지 못하는 질문이 따라온다. 어떤 스테이지가 OS 프로세스를 공유하는지, 각각 몇 벌 띄우는지, 각 벌을 어느 장치에 두는지다. SGLang-Omni 는 이를 따로 표기한다. 스테이지 그래프 G = (S, E) 의 토폴로지는 다음과 같다.

SPG

T = (G, π, r, q, μ)

π assigns stages to logical process groups · r replica count per group · q tensor-parallel ranks per replica · μ places physical processes on hosts and devices. π: 스테이지를 논리 프로세스 그룹에 배정 · r: 그룹별 복제 수 · q: 복제본당 텐서 병렬 랭크 수 · μ: 물리 프로세스를 호스트·장치에 배치.

Figure 3 · The same seven stages, with the two latency-critical ones replicated across GPUs 1 and 2. Redrawn from Figure 3 of the SPG topology blog. 그림 3 · 같은 일곱 스테이지에서 지연에 민감한 두 개만 GPU 1·2 에 복제한 배치. SPG 토폴로지 블로그 Figure 3 재구성.

The payoff: one notation covers strategies usually named separately이 표기가 주는 것: 따로 부르던 전략이 한 공간의 점이 된다

Strategies usually discussed as distinct architectures turn out to be points in the same space. Each one the blog lists is a different setting of π, r and μ over an unchanged G. 보통 서로 다른 아키텍처로 부르는 전략들이 사실 같은 공간의 점이다. 블로그가 꼽는 전략은 모두 변하지 않은 G 위에서 π, r, μ 를 달리 잡은 결과다.

Where this lands in the code코드에서의 위치 config/topology.py holds two plans. LogicalProcessPlan is compiled from config alone, "the single place where Process membership is decided". ProcessTopologyPlan is built after replica expansion and GPU placement, and answers only which expanded stages share an OS process. Placement itself belongs to config/placement.py. Three questions, three files, no overlap. config/topology.py 에는 계획이 둘 있다. LogicalProcessPlan 은 설정만으로 컴파일되며, 독스트링이 "Process 멤버십이 결정되는 유일한 장소"라고 적는다. ProcessTopologyPlan 은 복제 확장과 GPU 배치 뒤에 만들어지고, 확장된 스테이지가 어떤 OS 프로세스를 공유하는지만 답한다. 배치는 config/placement.py 가 정한다. 세 질문을 세 파일이 겹치지 않게 나눠 맡는다.

4Runtime layers, control plane, data plane런타임 계층, 제어 평면, 데이터 평면

Each stage becomes a worker process with the same three layers inside, and only the middle one differs per stage: a uniform shell around a scheduler matched to the stage's workload. 각 스테이지는 워커 프로세스가 되고, 안에 든 세 계층 중 스테이지마다 다른 것은 가운데 한 층뿐이다. 균일한 껍데기에 작업 성격에 맞는 스케줄러를 끼우는 것이 요령의 전부다.

Figure 4 · Runtime layers. Redrawn from Figure 4 of the SPG topology blog; relay backends from sglang_omni/relay/. 그림 4 · 런타임 계층. SPG 토폴로지 블로그 Figure 4 재구성. relay 백엔드 목록은 sglang_omni/relay/ 기준.

Why two planes instead of one평면을 둘로 나눈 이유

Control messages are small, ordered and must never block; tensors are large and must never be copied twice, so the two get separate channels. pipeline/control_plane.py opens with a one-line docstring, "Control plane for inter-stage communication via ZMQ", and carries typed messages (SubmitMessage, DataReadyMessage, DataAckMessage, AbortMessage, KVTransferPrepareMessage …) over msgpack. The payload moves on whichever relay backend the placement implies. 제어 메시지는 작고 순서가 있으며 막히면 안 된다. 텐서는 크고 두 번 복사되면 안 된다. 그래서 채널을 둘로 갈랐다. pipeline/control_plane.py 의 첫 줄 독스트링은 "ZMQ 를 통한 단계 간 통신의 제어 평면" 이고, SubmitMessage, DataReadyMessage, DataAckMessage, AbortMessage, KVTransferPrepareMessage 같은 타입 메시지를 msgpack 으로 나른다. 페이로드는 배치에 맞는 relay 백엔드로 따로 움직인다.

5Three roads to a voice agentvoice agent 로 가는 세 갈래 길

Beyond running models, conversation adds a problem that no model weight answers: who speaks when. The runtime's position: three answers exist, none has won, so the serving layer should support all three rather than bet on one. 모델을 돌리는 것과 별개로, 대화에는 모델 가중치가 답하지 못하는 문제가 하나 더 붙는다. 누가 언제 말하는가 다. 이 런타임은 답이 셋 있고 아직 승자가 없으니, 서빙 계층이 하나에 걸지 말고 셋을 모두 지원해야 한다고 본다.

6The cascaded session, dissected캐스케이드 세션 해부

Calling three HTTP endpoints in sequence takes an afternoon. What takes longer to discover is that a conversation needs a state machine between them, and that its hardest requirement is not interruption itself but what the model is told it said after an interruption. HTTP 엔드포인트 셋을 차례로 호출하는 건 반나절이면 된다. 늦게 깨닫는 사실은 둘이다. 대화에는 그 사이를 메우는 상태 기계가 필요하다. 그리고 가장 어려운 요구는 끼어들기 자체가 아니라, 끼어든 뒤 모델에게 "네가 말한 것"으로 무엇을 알려 주느냐 다.

Figure 6 · Cascaded session with playback-aware history. Redrawn from the cascaded-session figure of the interactive runtime blog; node names from examples/streaming_cascade/profiles/*/launch.yaml. 그림 6 · 재생을 아는 캐스케이드 세션. 인터랙티브 런타임 블로그 cascaded-session 그림 재구성. 노드 이름은 examples/streaming_cascade/profiles/*/launch.yaml 기준.

The same picture, as the config that produces it같은 그림을 설정으로 보면

Three of the nodes are nothing but HTTP clients. The declaration says where to call, not what to run, so the same graph works whether those endpoints are SGLang-Omni, vLLM, llama.cpp or a cloud API. 노드 중 셋은 HTTP 클라이언트일 뿐이다. 선언은 무엇을 돌릴지가 아니라 어디로 호출할지를 말한다. 그래서 엔드포인트가 SGLang-Omni 든 vLLM 이든 llama.cpp 든 클라우드 API 든 같은 그래프가 돈다. 

session_nodes:
  vad:    { stages: [vad], inputs: [input] }            # in-process, CPU
  asr:    { kind: openai_transcription, base_url: "http://127.0.0.1:8002/v1", … }
  dialog:
    kind: dialog
    inputs:
      - asr
      - { source: "llm:text_delta", feedback: true, overflow: drop_oldest, capacity: 1024 }
      - { source: "tts:session",    feedback: true, overflow: drop_oldest, capacity: 1024 }
      - "vad:session"
      - { kind: control, source: input,   event: interrupt }      # user barged in
      - { kind: control, source: aligner, event: reply.progress } # what was heard
    system_prompt: You are a helpful voice assistant. Answer in one spoken
                   sentence of at most 25 words, in the language the user speaks.
  llm:    { kind: openai_chat,   base_url: "…:8003/v1", inputs: [dialog, {kind: control, source: dialog, event: interrupt}] }
  tts:    { kind: openai_speech, base_url: "…:8005/v1", inputs: [llm,    {kind: control, source: dialog, event: interrupt}] }
  aligner:{ kind: alignment, method: forced, alignment_url: "http://127.0.0.1:8010", … }

Two details carry most of the design. First, the feedback: true edges make it a loop rather than a chain: dialog reads back from llm and tts, with a bounded queue and drop_oldest so a slow consumer degrades instead of blocking. Second, the control edges carry interrupt from dialog to both llm and tts. Cancelling generation without cancelling playback leaves the user listening to an answer the system has already abandoned. 설계의 대부분은 두 세부에 있다. 첫째, feedback: true 간선이 사슬을 고리로 만든다. dialog 가 llm 과 tts 의 출력을 되읽고, 유계 큐와 drop_oldest 덕분에 느린 소비자는 전체를 막지 않고 degrade 한다. 둘째, control 간선이 interrupt 를 dialog 에서 llm 과 tts 양쪽으로 보낸다. 생성만 취소하고 재생을 두면 사용자는 시스템이 이미 버린 답을 계속 듣는다.

The 800 ms that someone measured누군가 측정한 800 ms

Turn boundaries come from silence, and the threshold is not a round number chosen for neatness. models/vad/node.py carries the reason inline. 턴 경계는 침묵으로 정하고, 그 임계값은 보기 좋으라고 고른 어림수가 아니다. models/vad/node.py 가 이유를 주석으로 남겼다.

"A pause after a comma or a short 'Sorry.' often runs past 500 ms and split one utterance into two turns, which 800 ms avoided in our zh and en runs."

— sglang_omni/models/vad/node.py, note on주석 위치 silence_duration_ms

The part worth copying: playback-aware history베낄 가치가 있는 부분: 재생을 아는 이력

When the user interrupts, the system has generated more text than the listener heard. Writing the generated text into history is wrong: the model would believe it said things nobody heard. Truncating at the exact heard millisecond is also wrong, and the code says why. 사용자가 끼어들 때 시스템은 상대가 들은 것보다 많은 텍스트를 이미 생성했다. 생성된 텍스트를 그대로 이력에 적으면 모델은 아무도 듣지 않은 말을 했다고 믿는다. 들린 밀리초에서 정확히 자르는 것도 틀렸고, 그 이유는 코드에 적혀 있다.

"a cut reply shown as is reads to the model as how it answers, and after a few interruptions it replies with fragments (#3063)."

— sglang_omni/models/streaming_cascade/dialog.py, note above다음 함수 위의 주석 prompt_messages

So heard_prefix() cuts at the last sentence boundary whose audio ended at or before the heard position, and separately reports whether the listener heard past that boundary into text the cut discards. That needs a character-offset-to-milliseconds map for text generated token by token and spoken sentence by sentence, which is the entire reason the aligner node and its separate forced-alignment worker exist. 그래서 heard_prefix() 는 들린 위치 이전에 오디오가 끝난 마지막 문장 경계에서 자르고, 그 경계 너머 잘린 텍스트까지 들렸는지를 따로 보고한다. 이를 위해 토큰 단위로 생성되고 문장 단위로 발화된 텍스트의 문자 오프셋을 밀리초로 잇는 지도가 필요하다. aligner 노드와 별도 강제 정렬 워커가 있는 이유가 이것 하나다.

Streaming into TTSTTS 로의 스트리밍

OpenAISpeechSynthesizer speaks "sentence by sentence; turn.done follows the reply's audio", capped by max_sentence_words: 24. Waiting for the full reply would add its whole generation time to first-audio latency.OpenAISpeechSynthesizer 에는 "문장 단위로 발화하며 turn.done 은 답변 오디오를 뒤따른다"고 적혀 있고, 문장 길이는 max_sentence_words: 24 로 제한된다. 답 전체를 기다리면 생성 시간 전부가 첫 오디오 지연에 더해진다.

Deltas after the cancel취소 뒤에 오는 델타

A generator does not stop instantly. The synthesizer keeps a set of interrupted turns and drops their late deltas: "the generator may emit a few deltas after the interrupt before it stops."생성기는 즉시 멈추지 않는다. 합성기는 인터럽트된 턴을 기억해 두고 뒤늦게 온 델타를 버린다. 주석은 "생성기는 인터럽트 이후 멈추기 전까지 델타를 몇 개 더 내보낼 수 있다"고 적는다.

7If you build it yourself직접 만든다면

Two facts in the code decide how much of SGLang-Omni a cascaded voice agent needs, and both say the same thing: very little. 캐스케이드 voice agent 를 돌리는 데 SGLang-Omni 를 얼마나 가져와야 하는지는 코드의 두 사실이 정한다. 둘 다 아주 조금이면 된다고 말한다.

Fact 1 — the services block is optional사실 1: services 블록은 선택 사항

config/schema.py:785 declares services: list[ServiceConfig] = Field(default_factory=list). Leave it empty and the pipeline starts no model process at all; the three base_url values are just addresses of servers you started yourself, and the cascade becomes a pure orchestrator. config/schema.py:785 는 services: list[ServiceConfig] = Field(default_factory=list) 로 선언돼 있다. 비워 두면 파이프라인은 모델 프로세스를 하나도 띄우지 않고, 세 base_url 은 직접 띄운 서버 주소가 된다. 캐스케이드는 이미 돌고 있는 서버 위의 순수한 오케스트레이터가 된다.

Fact 2 — the process manager is 101 lines and has one contract사실 2: 프로세스 관리자는 101 줄, 계약은 하나

If you do fill it in, serve/services.py runs subprocess.Popen(service.command) with no validation of the command, and considers the service ready when http://127.0.0.1:<port>/v1/models returns 200. That is the entire interface. Three behaviors in it are worth lifting into your own code regardless. 채워 넣으면 serve/services.py 가 subprocess.Popen(service.command) 를 명령 검증 없이 실행하고, http://127.0.0.1:<port>/v1/models 가 200 을 돌려주면 준비된 것으로 본다. 인터페이스는 이게 전부다. 나머지를 쓰지 않더라도 가져갈 만한 동작이 셋 있다.

Adopt, don't restart이미 떠 있으면 그대로

If the port already answers, it logs and returns, and the process never joins the kill list. Model servers survive pipeline restarts, which is most of your iteration speed.포트가 이미 응답하면 로그만 남기고 반환하며, 그 프로세스는 종료 목록에 넣지 않는다. 모델 서버가 파이프라인 재시작을 견디니 반복 속도가 크게 오른다.

Kill the group그룹째 종료

start_new_session=True then os.killpg, SIGTERM with a 15 s grace before SIGKILL. Servers that spawn children die with them.start_new_session=True 로 띄우고 os.killpg 로 SIGTERM 을 보낸 뒤 15초 후 SIGKILL 한다. 자식 프로세스도 함께 죽는다.

Fail loudly on exit죽으면 바로 실패

A watcher calls poll() every second; a dead service fails the whole pipeline with its exit code instead of leaving a hung graph.감시자가 1초마다 poll() 을 확인한다. 서비스가 죽으면 멈춘 그래프를 두지 않고 종료 코드와 함께 전체를 실패시킨다.

On a Mac specificallyMac 이라면 SGLang-Omni's Apple support covers individual model serving, not the cascade: a Torch/MPS path (Qwen3-ASR, Fun-ASR, ARK-ASR, and Fun-CosyVoice3 for TTS) and a separate native C++ MLX runtime with no Python or CUDA at all (Whisper, Parakeet, SenseVoice, MOSS-TD, Silero VAD, Sortformer, and Voxtral-4B-TTS, measured at 0.55–0.85 s to first audio and RTF 0.72 on an M4 MacBook Air).
