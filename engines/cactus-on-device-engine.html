Cactus — an on-device AI inference engine, explained Cactus: 온디바이스 AI 추론 엔진 풀어 읽기

Cactus is a source-available engine that runs LLMs, vision, and speech models directly on a phone, watch, or Raspberry Pi, with a rotation-based quantization scheme that squeezes a 4.8 GB model to ~0.9 GB. This note walks its C/C++ stack and code path, pinned to a real commit. Cactus는 LLM·비전·음성 모델을 폰·워치·Raspberry Pi에서 직접 돌리는 소스 공개형 엔진이다. 4.8 GB 모델을 ~0.9 GB로 줄이는 회전 기반 양자화(rotation-based quantization)가 핵심이다. 이 글은 C/C++ 스택과 코드 경로를 실제 커밋 기준으로 따라간다.

one-line summary한 줄 요약
  • Cactus (YC S25) runs models on the device itself with three layers: hand-written Kernels (ARM SIMD + Apple Metal), a zero-copy Graph, and an OpenAI-compatible Engine.
  • On-device the limit is memory. CQ (rotation + codebook, 4→1 bit, every tensor) stays usable at 2-bit where GPTQ/AWQ/HQQ collapse, and shrinks Gemma-4-E2B from 4.79 GB to ~0.9 GB.
  • The research-preview TurboQuant-H takes the per-layer embedding tables down to ~2 bits with a Hadamard rotation.
  • Cloud handoff: when confidence drops below a threshold, the request is flagged for a cloud model. All numbers are vendor-reported.
  • Cactus(YC S25)는 모델을 기기 자체에서 돌린다. 계층은 셋이다. 손으로 짠 Kernels(ARM SIMD + Apple Metal), zero-copy Graph, OpenAI 호환 Engine.
  • 온디바이스의 병목은 메모리다. CQ(회전+코드북, 4→1비트, 모든 텐서)는 GPTQ/AWQ/HQQ가 무너지는 2비트에서도 쓸 만하고, Gemma-4-E2B를 4.79 GB에서 ~0.9 GB로 줄인다.
  • 연구 프리뷰인 TurboQuant-H는 Hadamard 회전으로 per-layer 임베딩 테이블을 ~2비트까지 내린다.
  • 클라우드 핸드오프: 확신도가 임계값보다 낮으면 요청에 플래그를 달아 클라우드 모델로 넘긴다. 수치는 모두 벤더 보고다.

Glossary — the systems words, in plain language (read this first)용어집: 시스템 용어를 쉬운 말로

on-device / edge inference온디바이스 / 엣지 추론

Running the model on the phone/watch itself, not on a server. Upsides: private, offline, no per-call cost, low latency. Downside: you're limited by a tiny device's RAM and battery.모델을 서버가 아닌 기기 자체에서 실행한다. 프라이버시·오프라인·무비용·저지연이 장점이고, RAM과 배터리가 제약이다.

inference engine추론 엔진

The software that actually runs a trained model to produce output. Cactus is one, built specially for small ARM devices instead of datacenter GPUs.학습된 모델을 실행해 출력을 내는 소프트웨어다. Cactus는 작은 ARM 기기용이다.

quantization (bits)양자화 (비트)

Storing each weight in fewer bits (FP16→INT4→2-bit) to shrink the model. A 2B model is ~4 GB at FP16, ~1 GB at 4-bit, ~0.5 GB at 2-bit — the difference between fitting on a phone or not.가중치를 더 적은 비트(FP16→INT4→2비트)로 저장한다. 2B 모델은 FP16 ~4 GB, 4비트 ~1 GB, 2비트 ~0.5 GB다.

kernel / SIMD / NEON / Metal커널 / SIMD / NEON / Metal

A kernel is a hand-optimized routine for one math op (e.g. matmul). SIMD = one instruction doing many numbers at once; NEON is ARM's SIMD, Metal is Apple's GPU API. This is where speed is won on a phone.커널은 연산 하나(예: matmul)의 최적화 루틴이다. SIMD는 명령 하나로 여러 숫자를 처리하며, NEON은 ARM의 SIMD, Metal은 Apple GPU API다.

computation graph계산 그래프

A model expressed as a graph of tensor operations (matmul → add → softmax…). "Zero-copy" means tensors are shared by reference, not duplicated in memory — precious on a device.모델을 텐서 연산(matmul → add → softmax…)의 그래프로 표현한 것이다. zero-copy는 텐서를 복제하지 않고 참조로 공유한다는 뜻이다.

per-layer embeddings (AltUp)per-layer 임베딩 (AltUp)

Newer models (Gemma 4/3n) give each layer its own embedding lookup table over a huge vocab. These tables can be 60%+ of the whole model — the biggest thing to compress.Gemma 4/3n은 레이어마다 자체 임베딩 테이블을 둔다. 모델의 60%+를 차지해 압축 1순위다.

rotation quantization (Hadamard)회전 양자화 (Hadamard)

Before quantizing, rotate the numbers with a special matrix (a Hadamard matrix) so they spread out evenly — which makes low-bit rounding far more accurate. The rotation is undone at inference.양자화 전에 Hadamard 행렬로 숫자를 회전시켜 고르게 퍼뜨린다. 저비트 반올림이 정확해지고, 회전은 추론 때 되돌린다.

codebook (Lloyd-Max)코드북 (Lloyd-Max)

Instead of even rounding steps, pick a small set of representative values ("centroids") that best fit the data, and store each number as an index into that set. Lloyd-Max finds the best centroids.데이터에 맞는 대표값(centroid) 몇 개를 골라 각 숫자를 그 인덱스로 저장한다. Lloyd-Max가 최적 centroid를 찾는다.

KV cacheKV 캐시

Cached per-token state so each new token doesn't re-read the whole prompt. On tiny models Cactus keeps it at INT8 (not lower) to avoid quality loss — a detail that shapes their quant choices.토큰별 상태를 저장해 프롬프트를 다시 읽지 않게 한다. Cactus는 작은 모델에서 품질을 위해 INT8로 유지한다.

FFI / bindingsFFI / 바인딩

FFI (Foreign Function Interface) = calling C code from another language. Cactus's core is C/C++; bindings (Swift, Kotlin, Flutter, Python…) are thin wrappers so app developers call it in their own language.FFI(Foreign Function Interface)는 다른 언어에서 C 코드를 부르는 방식이다. 바인딩(Swift, Kotlin, Flutter, Python…)은 C/C++ 코어를 감싼 얇은 래퍼다.

cloud handoff (hybrid)클라우드 핸드오프 (하이브리드)

"Edge-cloud hybrid": run on-device by default, but if the small model isn't confident enough, hand the query off to a big cloud model. Best of both — cheap/private when easy, accurate when hard.기본은 온디바이스로 돌리고, 작은 모델의 확신이 낮으면 큰 클라우드 모델로 넘긴다.

prefill / decode tps, TTFTprefill / decode tps, TTFT

Prefill = reading your prompt; decode = writing the answer token by token. tps = tokens/second (higher = faster). TTFT = time to first token (how long before it starts replying).Prefill은 프롬프트 읽기, decode는 토큰 단위 답 쓰기다. tps는 초당 토큰, TTFT는 첫 토큰까지 걸린 시간이다.

1What it is, and why "on-device" is a different gameCactus는 무엇이고, 온디바이스는 왜 다른가

Cactus (from Cactus Compute, a YC S25 company) is a source-available, energy-efficient inference engine for running LLMs, vision-language models, and speech models on small devices — phones, wearables, Macs, and ARM boards like the Raspberry Pi. The pitch is "a hybrid edge-cloud AI engine for mobile devices & wearables": run locally by default, reach for the cloud only when needed. Cactus(YC S25 회사 Cactus Compute)는 LLM·비전언어모델·음성모델을 폰·웨어러블·Mac·Raspberry Pi 같은 작은 기기에서 돌리는 소스 공개형 추론 엔진이다. 슬로건은 "모바일·웨어러블용 하이브리드 엣지-클라우드 AI 엔진"이다. 기본은 로컬에서 돌리고 필요할 때만 클라우드를 쓴다.

If you've read the datacenter-serving notes on this site (vLLM, SGLang, Netflix), this is the mirror image. There the enemy is GPU HBM and inter-node communication at huge batch sizes. On a phone there's no batch — it's one user, one request — and the enemies are total RAM, storage, and battery. A 2-billion-parameter model in full precision is about 4 GB; a phone might have 4–8 GB of RAM shared with the whole OS. So the entire design bends toward one goal: make the model small enough to fit, and cheap enough to run, without wrecking quality. 데이터센터 서빙(vLLM, SGLang, Netflix 노트)과는 정반대다. 거기선 큰 배치에서 GPU HBM과 노드 간 통신이 병목이지만, 폰은 한 사용자, 한 요청이고 병목은 RAM·저장공간·배터리다. 20억 파라미터 모델은 풀 정밀도로 약 4 GB인데, 폰 RAM은 OS와 나눠 쓰는 4–8 GB뿐이다. 그래서 설계 목표는 하나다. 품질을 지키면서 들어갈 만큼 작게, 돌릴 만큼 싸게.

Why bother running on-device at all?애초에 왜 온디바이스로?

The upside장점

Privacy (data never leaves the device), offline (works with no network), no per-request cost (no API bill), and low, predictable latency (no network round-trip). For always-on assistants, wearables, and robots, these matter more than raw quality.프라이버시, 오프라인 동작, 호출당 비용 없음, 낮고 예측 가능한 지연. 상시 비서·웨어러블·로봇에선 이게 원시 품질보다 중요하다.

The cost비용

Small devices force small models, which are less capable. Cactus's answer is two-fold: squeeze the model hard with quantization (§3), and when the small model isn't sure, hand off to the cloud (§4) — so you only pay the cloud for the hard queries.작은 기기에는 작은 모델만 들어가고 능력이 떨어진다. Cactus는 양자화로 모델을 줄이고(§3), 확신이 낮으면 클라우드로 넘긴다(§4). 클라우드 비용은 어려운 질의에만 든다.

the mental model to hold붙잡을 멘탈 모델 Cactus is a vertically integrated stack written mostly in C/C++: it does its own kernels, its own graph, its own quantization, and its own model conversion — because on a phone you can't lean on CUDA, cuDNN, or a big Python runtime. Think of it as "llama.cpp's ambition, but with a novel quantization scheme and an edge-cloud hybrid story built in." The single most differentiated piece is the quantization (§3); everything else is careful mobile engineering. Cactus는 대부분 C/C++로 된 수직 통합 스택이다. 폰에선 CUDA·cuDNN·큰 Python 런타임을 쓸 수 없어 커널·그래프·양자화·모델 변환을 모두 직접 만든다. "llama.cpp의 야망에 새 양자화 방식과 엣지-클라우드 하이브리드를 더한 것"으로 보면 된다. 가장 차별화된 부분은 양자화(§3)다.

Cactus is five named pieces. Three are the runtime layers a request flows through (Engine → Graph → Kernels); two are the offline pieces that prepare a model to run (Quants and the Transpiler). Here's each in plain terms. Cactus는 다섯 조각이다. 셋은 요청이 지나가는 런타임 계층(Engine → Graph → Kernels)이고, 둘은 모델을 미리 준비하는 오프라인 조각(Quants, Transpiler)이다.

Box by box상자별로

  • Engine (C API). The high-level surface an app calls: cactus_init(weights, rag_corpus, …) to load a model and cactus_complete(model, messages, …) to get a reply. Messages are JSON in the OpenAI chat shape; the response JSON carries the text plus confidence, cloud_handoff, tool function_calls, and timing (time_to_first_token_ms, decode_tps…). One API covers text, vision, audio, transcription, embeddings, RAG, and tools.Engine (C API). 앱이 호출하는 상위 API다. cactus_init(weights, rag_corpus, …)로 모델을 로드하고 cactus_complete(model, messages, …)로 응답을 받는다. 메시지는 OpenAI 챗 형태 JSON이고, 응답 JSON엔 텍스트와 confidence, cloud_handoff, 툴 function_calls, 타이밍(time_to_first_token_ms, decode_tps…)이 들어 있다. API 하나로 텍스트·비전·오디오·전사·임베딩·RAG·툴을 다룬다.
  • Graph (C++). A tiny tensor framework — "PyTorch for mobile." You declare inputs and ops (graph.matmul(a, b), transpose, …), then execute(). "Zero-copy" means intermediate tensors are referenced, not copied — critical when RAM is scarce. It supports mixed precision (FP16, INT8) tensor by tensor.Graph (C++). "모바일용 PyTorch"인 작은 텐서 프레임워크다. 입력과 연산(graph.matmul(a, b), transpose, …)을 선언하고 execute()를 부른다. 중간 텐서는 복사 없이 참조(zero-copy)하고, 텐서별 혼합 정밀도(FP16, INT8)를 지원한다.
  • Kernels (C/C++). The hand-written inner loops for matmul, attention, convolution, quantization, and DSP, tuned for ARM NEON SIMD (Apple, Snapdragon, Tensor, Exynos, MediaTek, Raspberry Pi) and Apple Metal for GPU. This is the layer that turns "correct" into "fast enough to feel instant."Kernels (C/C++). matmul·attention·convolution·양자화·DSP용 내부 루프를 손으로 짰다. ARM NEON SIMD(Apple·Snapdragon·Tensor·Exynos·MediaTek·Raspberry Pi)와 GPU용 Apple Metal에 맞췄다. 체감 속도는 여기서 갈린다.
  • Quants (CQ). The offline compression recipe — rotation-and-codebook quantization from 4-bit down to 1-bit, applied to every tensor. This is §3.Quants (CQ). 4비트에서 1비트까지의 회전+코드북 양자화를 모든 텐서에 적용하는 오프라인 압축이다(§3).
  • Transpiler (Python). Converts an arbitrary PyTorch / HuggingFace model into a Cactus runtime graph + CQ weights (a "bundle") via cactus convert. This is the offline bridge from the training world (PyTorch) to the on-device world.Transpiler (Python). PyTorch / HuggingFace 모델을 cactus convert로 Cactus 런타임 그래프와 CQ 가중치("번들")로 바꾼다.

3The headline — rotation-based quantization (CQ & TurboQuant-H)핵심: 회전 기반 양자화 (CQ & TurboQuant-H)

On a phone, storage and memory are the whole ballgame. A 2B model is ~4 GB at FP16, ~1 GB at 4-bit, ~0.5 GB at 2-bit — so the lower you can push the bits without wrecking quality, the more (and better) models fit. The catch: standard 4-bit methods (GPTQ, AWQ, HQQ) fall apart below 4 bits and don't handle the huge embedding tables at all. Cactus's answer is two related rotation-based schemes. 폰에선 저장공간과 메모리가 전부다. 품질을 지키며 비트를 낮출수록 더 좋은 모델이 들어간다. 그런데 표준 4비트 방법(GPTQ·AWQ·HQQ)은 4비트 미만에서 무너지고, 거대한 임베딩 테이블은 다루지 못한다. Cactus는 연관된 회전 기반 방식 두 개로 이 문제를 푼다.

The shared idea: rotate, then use a codebook공통 아이디어: 회전한 뒤 코드북 사용

Both schemes share one trick. Raw model weights are lumpy — a few big outliers force a coarse rounding grid that wastes precision on everyone else. If you first rotate the numbers with a Hadamard matrix (a fixed pattern of +1/−1 that mixes coordinates evenly), the lumps spread into a smooth, well-behaved spread. Now a small codebook of representative values covers them accurately at very few bits. At inference the rotation is undone — and because a normalized Hadamard matrix is its own inverse, "undo" is the exact same cheap operation as "do." 원시 가중치에는 큰 이상치가 몇 개 있어서 반올림 격자가 거칠어지고, 나머지 값의 정밀도가 낭비된다. Hadamard 행렬(좌표를 고르게 섞는 +1/−1 고정 패턴)로 먼저 회전하면 값이 매끄럽게 퍼지고, 작은 코드북으로도 아주 적은 비트에 정확히 담긴다. 정규화된 Hadamard 행렬은 자기 자신이 역행렬이라, 추론 때 되돌리는 연산도 똑같이 싸다.

Fig 2 · The rotate-then-codebook pipeline shared by CQ and TurboQuant-H. Schematic; math per the TurboQuant-H write-up.그림 2 · CQ와 TurboQuant-H가 공유하는 회전 후 코드북 파이프라인. 개략도, 수식은 TurboQuant-H 글 기준.

CQ (Cactus Quants) — the shipped, general schemeCQ (Cactus Quants): 실제 배포되는 범용 방식

CQ is the default (--bits 4). Unlike GPTQ/AWQ/HQQ, which only quantize transformer linear layers, CQ applies one recipe to every tensor — linears, vision/audio towers, cross-modal bridges, and both embedding tables. The payoff shows up as you push the bits down: CQ가 기본값(--bits 4)이다. GPTQ/AWQ/HQQ는 트랜스포머 linear 레이어만 양자화하지만, CQ는 linear·비전/오디오 타워·크로스모달 브리지·양쪽 임베딩 테이블까지 모든 텐서에 같은 레시피를 적용한다. 차이는 비트를 낮출수록 커진다.

Read the story in that table: at 4-bit everyone's close; at 3-bit CQ pulls ahead by tens of points; at 2-bit the baselines collapse to near-random while CQ still functions. 4비트에선 다들 비슷하다. 3비트에선 CQ가 수십 점 앞서고, 2비트에선 baseline이 near-random으로 무너지지만 CQ는 여전히 작동한다.

"At 2-bit, every baseline collapses. CQ is the only method retaining usable accuracy."

Because different tensors tolerate compression differently, CQ also does mixed precision: keep the sensitive layers at 4-bit, push the rest to 2–3. The production Gemma-4-E2B bundle uses 4-bit linears, 2-bit per-layer embeddings, 4-bit shared embeddings, and 2-bit vision/audio towers — 4.79 GB → ~0.9 GB, a 5.3× reduction, while holding MMLU 59.14 and GSM8K 74.00 (vs 62.33 / 73.67 at FP16). The runtime trick that makes this cheap: 텐서마다 압축 내성이 달라서 CQ는 혼합 정밀도를 쓴다. 프로덕션 Gemma-4-E2B 번들은 linear 4비트, per-layer 임베딩 2비트, 공유 임베딩 4비트, 비전/오디오 타워 2비트로 4.79 GB → ~0.9 GB(5.3× 감소)를 달성하면서 MMLU 59.14·GSM8K 74.00을 유지한다(FP16은 62.33 / 73.67). 런타임 비용을 낮추는 방법은 다음과 같다.

"the kernel applies a Walsh-Hadamard transform to the FP16 activation (not the weight), then performs a fused codebook-lookup + norm-scale + matmul in a single NEON pass."

— Cactus Quants docs · docs/cactus_quants.md

Honest weak spots the docs name: 2-bit audio transcription degrades (LibriSpeech WER ~5.9 → ~10.4), 2-bit tool calling is near-zero for everyone including CQ, and on the LFM family HQQ wins at 4-bit. 문서가 밝힌 약점도 있다. 2비트 오디오 전사는 나빠지고(LibriSpeech WER ~5.9 → ~10.4), 2비트 툴콜은 CQ를 포함해 모두 거의 0이며, LFM 계열 4비트에선 HQQ가 이긴다.

TurboQuant-H — squeezing the embedding tables (research preview)TurboQuant-H: 임베딩 테이블 짜내기 (연구 프리뷰)

A newer architecture pattern (AltUp, in Gemma 4/3n) gives every layer its own embedding table over a 262K-token vocabulary — and those tables balloon to 60%+ of the model. TurboQuant-H targets exactly them. It adapts TurboQuant (Zandieh et al., ICLR 2026) — which uses random rotation + optimal scalar quantizers for KV cache — into an offline weight scheme: swap the random rotation for a Hadamard one (deterministic, fast, self-inverse), train a per-position Lloyd-Max codebook, drop the extra correction stage. Gemma 4/3n의 AltUp은 262K 토큰 어휘에 대해 레이어마다 임베딩 테이블을 두고, 이 테이블이 모델의 60%+를 차지한다. TurboQuant-H는 바로 이 테이블을 겨냥한다. KV 캐시용 TurboQuant(Zandieh 외, ICLR 2026)를 오프라인 가중치 방식으로 바꿨다. 랜덤 회전 대신 Hadamard 회전(결정적·빠름·자기역)을 쓰고, 위치별 Lloyd-Max 코드북을 학습하며, 추가 보정 단계는 뺐다.

"On Gemma 4 E2B, TurboQuant-H compresses PLI weights from 2,496 MB to 624 MB (4x) at 2.125 effective bits per dimension, reducing total LLM storage by 40% (4,790 MB → 2,918 MB) with a perplexity increase of 0.06 (1.85 → 1.91) and no measured speed regression."

— TurboQuant-H, Abstract (Mosoyan & Ndubuaku, 2026) · blog/turboquant-h.md

The nice detail: the Hadamard butterfly costs ~56 vector ops per 128-element group (<2 µs per embedding lookup on an A15), but the compressed table is ~3.8× smaller to read from memory — so the rotation more than pays for itself in saved bandwidth. Status is important: TurboQuant-H is an explicit research preview — the blog says the weights "will ship in an upcoming release" and integration into cactus convert is listed as future work. So today the shipped compression is CQ; TurboQuant-H is the frontier. Hadamard 버터플라이는 128원소 그룹당 ~56 벡터 연산(A15에서 임베딩 룩업당 <2 µs)이 들지만, 읽어야 할 테이블이 ~3.8× 작아져 대역폭 절약이 더 크다. 단, TurboQuant-H는 명시적 연구 프리뷰다. 블로그는 가중치가 "곧 릴리스에서 배포될 것"이라 하고, cactus convert 통합은 향후 작업이다. 지금 배포되는 압축은 CQ다.

4Engine features — OpenAI-compatible API, cloud handoff, RAG, tools엔진 기능: OpenAI 호환 API·클라우드 핸드오프·RAG·툴

The Engine deliberately speaks the OpenAI-compatible shape (messages in, a chat completion out; cactus serve even starts a local OpenAI-compatible HTTP server). Same instinct as the Netflix and Cerebras notes: don't invent a new interface, so existing tools and app code just work. On top of that, three features are worth calling out. Engine은 일부러 OpenAI 호환 형태(메시지 입력, 챗 컴플리션 출력)를 쓴다. cactus serve는 로컬 OpenAI 호환 HTTP 서버도 띄운다. Netflix·Cerebras 노트와 같은 판단이다. 새 인터페이스를 만들지 않으면 기존 도구와 앱 코드가 그대로 돈다. 그 위에 눈여겨볼 기능이 셋 있다.

Cloud handoff — the "hybrid" in edge-cloud클라우드 핸드오프: 엣지-클라우드의 "하이브리드"

This is the most distinctive idea. A small on-device model handles most queries, but for each answer the engine also reports a confidence score. When confidence falls below a threshold, the response is flagged cloud_handoff: true so the app can re-route that one hard query to a big cloud model. You pay cloud cost (and give up privacy) only on the queries the local model can't handle well — the easy majority stay on-device, free and private. 가장 독특한 기능이다. 작은 온디바이스 모델이 대부분의 질의를 처리하고, 답마다 confidence 점수를 함께 낸다. confidence가 임계값보다 낮으면 응답에 cloud_handoff: true가 붙고, 앱은 그 질의만 큰 클라우드 모델로 보낸다. 클라우드 비용과 프라이버시 손실은 어려운 질의에서만 생긴다.

{
  "success": true,
  "response": "Hi there!",
  "confidence": 0.8193,
  "confidence_threshold": 0.7,   // model-dependent
  "cloud_handoff": false,        // true → app routes to a cloud model
  "time_to_first_token_ms": 45.23,
  "decode_tps": 168.42
}

The server/CLI exposes it directly: --confidence-threshold <0..1>, --cloud-timeout-ms, and --no-cloud-handoff to turn it off. It's the on-device mirror of the "route hard queries elsewhere" logic a datacenter gateway does — just with the local model itself as the cheap first tier. 서버/CLI 옵션은 --confidence-threshold <0..1>, --cloud-timeout-ms, 끄는 --no-cloud-handoff다. 데이터센터 게이트웨이의 "어려운 질의는 다른 곳으로" 라우팅을 기기 위에 옮긴 셈이고, 로컬 모델이 싼 1차 계층이 된다.

Auto-RAG and tool calling — small models with a memory and handsAuto-RAG와 툴콜: 기억과 손을 가진 작은 모델

Auto-RAG

Pass a folder of text at cactus_init and the engine automatically retrieves the relevant bits into context for each query — using an on-device vector index (cosine similarity). A small model punches above its weight when it can look things up.cactus_init에 텍스트 폴더를 넘기면, 엔진이 질의마다 온디바이스 벡터 인덱스(코사인 유사도)로 관련 조각을 찾아 컨텍스트에 넣는다. 찾아볼 수 있으면 작은 모델도 제 몫 이상을 한다.

Tool calling + Tool RAG

Define tools as JSON; the model returns structured function_calls. When there are many tools, Tool RAG first retrieves the top-k most relevant tools per query so the small model isn't overwhelmed. Cactus even ships Needle, a 26M-param model built just for on-device tool calling.툴을 JSON으로 정의하면 모델이 구조화된 function_calls를 돌려준다. 툴이 많으면 Tool RAG가 질의별 top-k 툴만 골라 준다. 온디바이스 툴콜 전용 26M 파라미터 모델 Needle도 배포한다.

Rounding it out: streaming (token callbacks), native vision and audio in messages (VLMs like Gemma 4 / LFM2-VL accept images and audio paths), on-device transcription (Whisper, Parakeet), embeddings, and a thinking mode for models that support chain-of-thought. One C API covers all of it. 그 밖에 스트리밍(토큰 콜백), 메시지 내 비전·오디오(Gemma 4 / LFM2-VL이 images·audio 경로를 받음), 온디바이스 전사(Whisper, Parakeet), 임베딩, chain-of-thought용 thinking 모드를 C API 하나로 지원한다.

6Using it, and status사용법, 그리고 상태

On a Mac it's two commands — brew install cactus-compute/cactus/cactus then cactus run google/gemma-4-E2B-it. The CLI also covers convert (HF → CQ bundle), serve (a local OpenAI-compatible HTTP server, with the cloud-handoff flags), transcribe, benchmark, and code (a coding agent). App developers use the language bindings (Swift, Kotlin, Flutter, React Native, Python, Rust) over the C API. Tested model families: Gemma 4/3/3n, Qwen 3/3.5, LiquidAI LFM2, Whisper, Moonshine, Parakeet, Nomic Embed; any HuggingFace model can be converted (cactus convert, marked experimental).
