one-line summary한 줄 요약
  • V1 has no separate prefill and decode phases. Each step walks running (decodes + in-flight prefill chunks), then waiting (new requests), draining one shared token budget (max_num_batched_tokens) until it hits zero or the running count hits max_num_seqs.
  • So one step can start many prefills at once. A long prompt is chunked across steps while decodes ride along. Effective defaults depend on hardware/usage (e.g. 8192/1024 on a big-GPU server, not the 2048/128 class fallback; §7).
  • When KV blocks run out, allocation refuses and the scheduler preempts a running request back to waiting.
  • Continuous batching always existed. Mixing prefill+decode in one forward pass is chunked prefill: opt-in on V0, the only always-on path on V1.
  • V1에는 prefill 단계와 decode 단계 구분이 없다. 매 스텝 running(decode + 진행 중인 prefill 청크)을 먼저, waiting(새 요청)을 나중에 훑으며 하나의 공유 token budget(max_num_batched_tokens)을 쓴다. budget이 0이 되거나 running 수가 max_num_seqs에 닿으면 멈춘다.
  • 그래서 한 스텝이 prefill을 여러 개 동시에 시작할 수 있다. 긴 프롬프트는 스텝마다 청크로 잘리고 decode가 같이 탄다. 실효 기본값은 하드웨어와 용도에 따라 다르다(예: 대형 GPU 서버는 8192/1024이고 클래스 fallback 2048/128이 아니다, §7).
  • KV block이 모자라면 할당이 거부되고, 스케줄러는 running 요청 하나를 waiting 큐로 preempt한다.
  • continuous batching은 처음부터 있었다. prefill+decode를 한 forward에 섞는 것은 chunked prefill이며, V0에선 opt-in이고 V1에선 유일한 상시 경로다.

1The one idea: there is no prefill phase핵심: prefill 단계는 없다

The one thing to remember, in the maintainers' own comment on the algorithm: 하나만 기억한다면 이것이다. 관리자들이 알고리즘 첫머리에 단 주석이다.

"There's no "decoding phase" nor "prefill phase" in the scheduler. Each request just has the num_computed_tokens and num_tokens_with_spec … At each step, the scheduler tries to assign tokens to the requests so that each request's num_computed_tokens can catch up its num_tokens_with_spec."

— vllm/v1/core/sched/scheduler.py, schedule() · L442–L450

Every request has num_computed_tokens (how far it's been processed) and num_tokens (how far it must go: prompt + generated + speculative tokens). Each step the scheduler just hands out new tokens to close that gap: 요청마다 num_computed_tokens(처리한 위치)와 num_tokens(가야 할 위치: 프롬프트 + 생성 토큰 + speculative 토큰)가 있다. 스케줄러는 매 스텝 이 격차를 좁히도록 새 토큰을 나눠 줄 뿐이다.

  • A fresh request has num_computed_tokens = 0 and a 4000-token gap → give it a chunk. That's "prefill."새 요청은 num_computed_tokens = 0, 격차 4000토큰이니 청크를 준다. 이것이 "prefill"이다.
  • A generating request has closed its prompt gap → give it exactly 1 new token. That's "decode."생성 중 요청은 프롬프트 격차를 다 닫았으니 새 토큰 1개를 준다. 이것이 "decode"다.

Prefill and decode aren't modes. They are two sizes of the same "give this request N new tokens" action (big N vs N=1), so they sit in the same batch trivially. prefill과 decode는 모드가 아니다. 같은 "새 토큰 N개 주기" 동작의 두 크기(큰 N과 N=1)라서 한 배치에 자연스럽게 함께 들어간다.

2Static vs continuous vs chunked — and why mixing ≠ continuous batchingstatic vs continuous vs chunked: 혼합 ≠ continuous batching

"Continuous batching" and "mixing prefill with decode" often get conflated, but they are two different levels: "continuous batching"과 "prefill과 decode 섞기"는 자주 혼동되지만 서로 다른 층위다.

Fig 1 · Three batching regimes: continuous batching is ①→②, mixing is ②→③. Original diagram.그림 1 · 세 가지 배칭 방식. continuous batching은 ①→②, 혼합은 ②→③이다. 직접 그림.

So "if they don't mix, isn't continuous batching broken?" No. Regime ② is fully continuous: C joins as soon as its prefill step finishes, and finished requests free slots immediately. It only lacks smoothness, since C's prefill monopolizes one step and A, B emit nothing that tick (a latency hiccup, not a batching failure). Chunked prefill (③) removes the hiccup. Mixing is a latency/utilization optimization layered on top of continuous batching, not a precondition. 그러니 "섞지 않으면 continuous batching이 깨지나?"의 답은 아니오다. ②도 완전히 continuous다. C는 prefill 스텝이 끝나는 즉시 합류하고, 끝난 요청은 바로 슬롯을 반납한다. 빠진 것은 매끄러움뿐이다. C의 prefill이 한 스텝을 독점해 A·B가 그 스텝에 토큰을 못 내는데, 이는 지연 딸꾹질이지 배칭 실패가 아니다. chunked prefill(③)이 이 딸꾹질을 없앤다. 혼합은 continuous batching의 전제가 아니라 그 위에 얹은 지연/활용 최적화다.

3Inside schedule() — two loops, one token budgetschedule() 내부: 두 루프, 하나의 token budget

Each step, schedule() gets a fresh token budget of max_num_batched_tokens and spends it across two loops in order. 매 스텝 schedule()은 max_num_batched_tokens짜리 새 token budget을 받아 두 루프에서 차례로 쓴다.

# vllm/v1/core/sched/scheduler.py:459
token_budget = self.max_num_scheduled_tokens   # = max_num_batched_tokens (default 2048)

Fig 2 · One step of schedule(): two loops drain one token_budget into one mixed forward pass. Original diagram, per scheduler.py:459/485/687.그림 2 · schedule() 한 스텝: 두 루프가 token_budget 하나를 써서 혼합 배치 한 번을 만든다. 직접 그림, scheduler.py:459/485/687 기준.

Loop 1 — the running set (decodes + in-flight prefills)루프 1: running 집합 (decode + 진행 중 prefill)

The first loop walks self.running. A decode takes 1 token (plus speculative ones); an in-flight prefill takes what the budget allows. Same subtraction either way: 첫 루프는 self.running을 훑는다. decode는 토큰 1개(speculative가 있으면 그만큼 더), 진행 중 prefill은 budget이 허락하는 만큼 가져간다. 어느 쪽이든 같은 뺄셈이다.

# vllm/v1/core/sched/scheduler.py:485
while req_index < len(self.running) and token_budget > 0:
    ...
    num_new_tokens = min(num_new_tokens, token_budget)   # decode → 1; prefill → a chunk
    ...
    token_budget -= num_new_tokens                       # scheduler.py:637

Loop 2 — the waiting set (this is where new prefills enter)루프 2: waiting 집합 (새 prefill이 들어오는 곳)

The second loop is a while, not an if, so it admits as many new requests as fit. Its two stop conditions are the whole answer to "how many prefills per step?": 둘째 루프는 if가 아닌 while이라서 들어가는 만큼 새 요청을 admit한다. 두 정지 조건이 "한 스텝에 prefill 몇 개?"의 답 전부다.

# vllm/v1/core/sched/scheduler.py:687
while (self.waiting or self.skipped_waiting) and token_budget > 0:   # ← STOP if budget spent
    num_running = len(self.running) + self.num_waiting_for_streaming_input
    if num_running >= self.max_num_running_reqs:                     # ← STOP at max_num_seqs
        break
    ...
    token_budget -= num_new_tokens                                   # scheduler.py:1073

There is no third condition. V1 has no cap on concurrent partial prefills; the old V0 knob max_num_partial_prefills doesn't exist here. Only the token budget and max_num_seqs gate it. 세 번째 조건은 없다. V1에는 동시 부분 prefill 개수 상한이 없고, 옛 V0 노브 max_num_partial_prefills도 이 스케줄러엔 없다. token budget과 max_num_seqs만이 막는다.

4How many prefills per step? (a worked example)한 스텝에 prefill 몇 개? (예시로)

Take max_num_batched_tokens = 2048 and max_num_seqs = 128 (the SchedulerConfig fallback; real defaults are higher, §7, but the arithmetic is the same), with 48 decodes already running (48 tokens). That leaves 2000 tokens for new prefills, and how many fit depends only on prompt lengths: max_num_batched_tokens = 2048, max_num_seqs = 128(SchedulerConfig fallback이다. 실제 기본값은 더 크지만 계산은 같다, §7)이고 decode 48개가 이미 돌고 있다고 하자(48토큰 소비). 새 prefill에 쓸 2000토큰이 남고, 몇 개가 들어가는지는 프롬프트 길이에만 달렸다.

Fig 3 · Same 2000 free tokens: four 500-token prefills, or one 5000-token prompt's chunk. Original diagram.그림 3 · 같은 2000토큰으로 500토큰 prefill 4개, 또는 5000토큰 프롬프트의 청크 하나. 직접 그림.

Each new prefill's chunk is this clamp: the whole remaining prompt, capped by long_prefill_token_threshold if set, never above the remaining budget: 새 prefill의 청크 크기는 아래 클램프로 정해진다. 남은 프롬프트 전부를 가져오되 long_prefill_token_threshold가 있으면 그 값으로 자르고, 남은 budget은 넘지 않는다.

# vllm/v1/core/sched/scheduler.py:899  (waiting-loop chunk sizing)
threshold = self.scheduler_config.long_prefill_token_threshold
if 0 < threshold < num_new_tokens:
    num_new_tokens = threshold              # cap one prefill's per-step size
...
num_new_tokens = min(num_new_tokens, token_budget)   # never exceed the jar
the two ways to change the answer답을 바꾸는 두 방법

1. --long-prefill-token-threshold. Set to 1024 in Scenario B, C's chunk becomes 1024, not 2000, leaving 976 tokens to admit a second prefill this step. It stops one giant prompt from hogging the batch. 2. --max-num-seqs. With 128 already running, the waiting loop breaks on its first check (num_running ≥ max_num_seqs) and admits zero prefills however much budget is free. 1. --long-prefill-token-threshold. Scenario B에서 1024로 두면 C의 청크가 2000이 아닌 1024가 되고, 남은 976토큰으로 같은 스텝에 두 번째 prefill이 들어온다. 거대한 프롬프트 하나가 배치를 독점하지 못하게 하는 노브다. 2. --max-num-seqs. 이미 128개가 돌고 있으면 waiting 루프는 첫 확인(num_running ≥ max_num_seqs)에서 break한다. budget이 아무리 남아도 새 prefill은 0개다.

5Chunked prefill across steps — following one long prompt스텝에 걸친 chunked prefill: 긴 프롬프트 하나 따라가기

Scenario B left C with 3000 tokens to prefill. C moves from the waiting loop to the running loop once its first chunk is scheduled, and flips to decode once its prompt is fully computed: Scenario B에서 C는 prefill할 토큰이 3000개 남았다. 첫 청크가 스케줄되면 C는 waiting 루프에서 running 루프로 옮겨 가고, 프롬프트 계산이 끝나면 decode로 바뀐다.

Fig 4 · A 5000-token prompt chunked as 2000+2000+1000 over three steps. Original diagram, per §1.그림 4 · 5000토큰 프롬프트를 세 스텝에 2000+2000+1000으로 나눈 모습. 직접 그림, §1 기준.

So the token budget is the TTFT ⇄ decode-smoothness dial. A big max_num_batched_tokens means fat chunks (fewer steps, lower TTFT) but more decode jitter; a small one does the reverse. There is no separate prefill/decode priority flag; the running-loop-first order already gives decodes first claim. 결국 token budget은 TTFT ⇄ decode 매끄러움 다이얼이다. max_num_batched_tokens가 크면 청크가 두꺼워져 TTFT는 줄지만 decode 지터가 늘고, 작으면 반대다. prefill/decode 우선순위 플래그는 따로 없다. running 루프를 먼저 도는 순서가 이미 decode에 우선권을 준다.

6Preemption — when a step runs out of blocksPreemption: 스텝에 block이 모자랄 때

The token budget caps compute; the harder limit is KV-cache blocks. A decode needs a new block every 16 tokens. If the block pool is empty, the allocator returns None and the scheduler preempts a running request: token budget이 연산을 제한한다면, 더 단단한 한계는 KV 캐시 block이다. decode는 block이 찰 때마다(16토큰마다) 새 block이 필요하다. block 풀이 비면 할당기가 None을 돌려주고, 스케줄러는 running 요청을 preempt해 자리를 만든다.

Fig 5 · Preemption (FCFS pops the newest; PRIORITY the lowest-priority). Original diagram, per scheduler.py preempt path.그림 5 · Preemption(FCFS는 가장 최근 요청, PRIORITY는 최저 우선순위를 pop). 직접 그림, scheduler.py preempt 경로 기준.

# vllm/v1/core/sched/scheduler.py:610  (FCFS branch, inside the running loop)
else:
    preempted_req = self.running.pop()          # newest running request
self._preempt_request(preempted_req, ...)       # free its blocks, → WAITING (PREEMPTED)
preempted_reqs.append(preempted_req)
if preempted_req == request:
    break                                        # nothing left to preempt → give up this req

It is the same allocator-returns-None hinge as in the block-management note §4, seen there from KVCacheManager.allocate_slots. The watermark (blocks the waiting loop can't touch) keeps a burst of admissions from pushing the running set into preemption. block 관리 노트 §4의 None 반환 지점과 같은 곳이다. 거기서는 KVCacheManager.allocate_slots 쪽에서, 여기서는 스케줄러 쪽에서 본다. 워터마크(waiting 루프가 못 쓰는 block 여유분)는 신규 요청이 몰려도 running 집합이 preemption으로 밀리지 않게 막는다.

Continuous batching is in every row; only step sharing changed. V1's novelty is that the unified/chunked path is the only, always-on scheduler, with no switch back to separate phases. continuous batching은 모든 행에 있다. 달라진 것은 스텝 공유 여부뿐이다. Editor's note — our take (not a vLLM claim), for MI250/MI300x serving편집자 주: 우리 관점 (vLLM의 주장 아님). MI250/MI300x 서빙 기준

  1. Report the effective defaults, not 2048/128. On a ≥70GB AMD GPU via vllm serve you're at 8192/1024; benchmarks assuming the class fallback misjudge concurrency.
  2. The token budget is the main latency knob, a TTFT ⇄ ITL trade, not a free lunch. The A100 regression in the code (PR #17885) shows "bigger budget = faster" is false on some hardware, so measure per GPU.
  3. Decode latency cliffs under load point to preemption (§6), not the kernel. Block exhaustion drives it, so tune gpu_memory_utilization + max_num_seqs. The scheduler itself is cheap host-side bookkeeping that keeps each step's one forward pass full.

  2. token budget이 가장 중요한 지연 노브다. 공짜 이득이 아니라 TTFT ⇄ ITL 교환이다. 코드에 남은 A100 회귀(PR #17885)가 보여 주듯 budget이 크다고 늘 빠르지 않으니 GPU별로 측정한다.
  3. 부하 중 decode 지연 절벽은 커널보다 preemption(§6)을 먼저 의심한다. 원인은 block 고갈이라 스케줄러가 아니라 gpu_memory_utilization + max_num_seqs로 조정한다. 스케줄러 자체는 스텝당 forward 한 번을 꽉 채우는 가벼운 호스트 쪽 장부다.
