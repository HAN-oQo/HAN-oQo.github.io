1 · Why KV events existKV 이벤트가 필요한 이유

Dynamo's router wants to send each request to the worker that already holds the most of that prompt's KV blocks — that's the whole point of KV-aware routing. But the prefix cache lives inside each GPU worker, and it changes every engine step as blocks are cached and evicted. The router runs in a separate Rust process. So how does it know what's in a cache it can't see? KV 인지 라우팅은 요청을 그 프롬프트의 KV 블록을 가장 많이 가진 워커로 보낸다. 그런데 prefix 캐시는 각 GPU 워커 안에 있고 엔진 스텝마다 바뀐다. 라우터는 별도의 Rust 프로세스다. 보이지 않는 캐시의 내용을 라우터는 어떻게 알까?

KV events are the answer. Every time a vLLM worker caches or evicts a KV block, it emits a tiny event (BlockStored / BlockRemoved) carrying only block hashes, not tensors. Dynamo subscribes and rebuilds a mirror of every worker's cache as a radix tree of block hashes, which the router scores candidates against. No GPU memory is shipped. 답은 KV 이벤트다. vLLM 워커는 KV 블록을 캐시하거나 쫓아낼 때마다 텐서 없이 블록 해시만 담은 작은 이벤트(BlockStored / BlockRemoved)를 낸다. Dynamo는 이 스트림을 구독해 모든 워커 캐시의 사본을 블록 해시 radix 트리로 만들고, 라우터는 이 사본으로 후보 점수를 매긴다. GPU 메모리는 전혀 옮기지 않는다.

2 · The data model — three event types데이터 모델: 이벤트 3가지

All KV events are defined in one vLLM file. There are exactly three, plus a batch wrapper. The base class is a msgspec.Struct with tag=True (so the wire carries a type tag) and array_like=True (encoded as a compact tuple, not a map). KV 이벤트는 vLLM 파일 하나에 모두 정의돼 있다. 이벤트 3가지와 배치 래퍼 하나다. 베이스 클래스는 msgspec.Struct이고, tag=True(타입 태그를 함께 전송)와 array_like=True(맵 대신 압축 튜플로 인코딩)를 쓴다.

That makes cross-worker overlap measurable from hashes alone. 실제로 중요한 페이로드는 block_hashes와 parent_block_hash뿐이다. 블록 해시는 그 블록의 토큰 id와 부모 해시로 계산하므로, 같은 prefix는 어느 워커에서든 같은 해시 체인이 된다. 그래서 해시만으로 워커 간 오버랩을 잴 수 있다.

3 · vLLM — when & where events firevLLM: 언제·어디서 발생하나 vLLM

All three event types are produced in the block pool (the prefix-cache allocator) on different triggers, and the scheduler flushes them once per engine step. 세 이벤트 모두 block pool(prefix 캐시 할당자)에서 서로 다른 트리거로 생기고, 스케줄러가 엔진 스텝마다 한 번 모아서 발행한다.

1Emit: a block gets cached → BlockStored발생: 블록이 캐시될 때 → BlockStored

When the scheduler finishes prefilling enough tokens to fill whole blocks, cache_full_blocks turns them into prefix-cache entries. If KV events are enabled, it appends a BlockStored to an in-memory queue (no I/O, just a list push). prefill로 블록이 꽉 차면 cache_full_blocks가 그 블록을 prefix 캐시에 등록한다. KV 이벤트가 켜져 있으면 메모리 큐에 BlockStored를 넣는다. I/O는 없고 리스트 push뿐이다.

Eviction is symmetric: when the LRU frees blocks, BlockRemoved is queued (block_pool.py L393); a full reset queues AllBlocksCleared (L492). 축출도 같은 방식이다. LRU가 블록을 해제하면 BlockRemoved가 큐에 들어가고(block_pool.py L393), 전체 리셋이면 AllBlocksCleared가 들어간다(L492).

Only full blocks fire events. The remainder is dropped. The block count is a floor division, so a partial block never gets hashed, cached, or announced. With block_size=32 and a 31-token prompt, 31 // 32 = 0 → cache_full_blocks early-returns and no BlockStored is emitted at all. The 32nd token completes the block and only then does one event fire. So a 100-token prompt at block_size 32 caches 100 // 32 = 3 blocks (96 tokens); the trailing 4 tokens are invisible to routing. 꽉 찬 블록만 이벤트를 내고, 자투리는 버린다. 블록 수를 floor 나눗셈으로 구하므로 partial 블록은 해시도, 캐시도, 발행도 되지 않는다. block_size=32에 prompt가 31토큰이면 31 // 32 = 0이라 cache_full_blocks가 바로 early-return하고 BlockStored는 아예 나오지 않는다. 32번째 토큰이 블록을 채워야 이벤트가 하나 난다. 100토큰 prompt라면 100 // 32 = 3블록(96토큰)만 캐시되고 남은 4토큰은 라우팅에 보이지 않는다.

This is why routing precision is quantized to the block: a larger block_size (e.g. the launch script's 64) discards more trailing tokens and coarsens the KV-overlap signal on short prompts; a smaller one sharpens it but produces more events and tree nodes. 그래서 라우팅 정밀도는 블록 단위로 양자화된다. block_size가 크면(예: 런치 스크립트의 64) 버리는 토큰이 많아 짧은 프롬프트의 오버랩 신호가 거칠어진다. 작으면 정밀해지는 대신 이벤트와 트리 노드가 늘어난다.

1bEmit: eviction → BlockRemoved · reset → AllBlocksCleared발생: 축출 → BlockRemoved · 리셋 → AllBlocksCleared

The other two events come from the same queue. When the pool is under pressure and the LRU reclaims a cached block, it queues a BlockRemoved carrying just that block's hash. When the whole prefix cache is reset, a single AllBlocksCleared is queued. 나머지 두 이벤트도 같은 큐로 들어간다. LRU가 캐시 블록을 회수하면 그 블록 해시만 담은 BlockRemoved를, prefix 캐시 전체를 리셋하면 AllBlocksCleared 하나를 넣는다.

Why eviction matters to routing. A worker that cached a long prefix but then evicted it under load must stop attracting requests for that prefix. Otherwise the router sends a request expecting a hit and the worker re-prefills anyway. BlockRemoved is what keeps the router's mirror honest as caches churn. 축출이 라우팅에 중요한 이유. 긴 prefix를 캐시했다가 축출한 워커는 그 prefix 요청을 더는 끌어오면 안 된다. 그렇지 않으면 라우터는 히트를 기대하고 보내지만 워커는 다시 prefill한다. 캐시가 계속 바뀌어도 라우터의 사본을 정확하게 지키는 것이 BlockRemoved다.

2Drain + publish: once per engine step모아서 발행: 엔진 스텝마다 한 번

At the end of every scheduler.step() the queued events are drained via take_events(), wrapped in a timestamped KVEventBatch, and handed to the publisher. This is the "when": one batch per engine iteration, so the cadence matches the decode loop, not individual tokens. scheduler.step()이 끝날 때마다 take_events()로 큐를 비우고, 타임스탬프를 단 KVEventBatch로 묶어 publisher에 넘긴다. "언제"의 답은 엔진 반복마다 배치 하나다. 토큰 단위가 아니라 decode 루프 주기를 따른다.

4 · The wire — ZMQ publish전송: ZMQ 발행 vLLM

publish() just drops the batch on a queue; a dedicated daemon thread does the network send so the engine step never blocks on I/O. The publisher is a reliable PUB socket with a sequence number and a replay buffer (a late subscriber can request missed events). publish()는 배치를 큐에 넣기만 하고, 네트워크 전송은 전용 데몬 스레드가 맡는다. 그래서 엔진 스텝이 I/O로 막히지 않는다. publisher는 시퀀스 번호와 리플레이 버퍼를 갖춘 신뢰성 PUB 소켓이라, 늦게 붙은 구독자도 놓친 이벤트를 다시 요청할 수 있다.

Each message is three frames: topic (for SUB filtering), 8-byte sequence (gap detection + replay), and the msgpack payload. The endpoint comes from --kv-events-config — recall the launch script bound each worker to its own port: 메시지 하나는 topic(SUB 필터링), 8바이트 시퀀스(누락 감지와 리플레이), msgpack 페이로드의 3프레임이다. 엔드포인트는 --kv-events-config로 정하며, 런치 스크립트는 워커마다 다른 포트를 bind한다.

tcp://*:20080 = the worker binds a PUB socket on 20080. Worker B uses 20081. Dynamo will connect a SUB socket to each. tcp://*:20080은 워커가 20080에 PUB 소켓을 bind한다는 뜻이다. 워커 B는 20081을 쓴다. Dynamo는 각 포트에 SUB 소켓을 connect한다.

5 · Dynamo — subscribe & indexDynamo: 구독과 인덱싱 Dynamo

1Wire it up: who subscribes to whom연결: 누가 누구를 구독하나

The same dynamo.vllm process that runs vLLM also starts a Dynamo-side subscriber. setup_kv_event_publisher reads vLLM's own --kv-events-config endpoint, rewrites the bind form tcp://*:PORT into a connect form tcp://127.0.0.1:PORT, and hands it to a Rust KvEventPublisher. vLLM을 돌리는 그 dynamo.vllm 프로세스가 Dynamo 쪽 구독자도 띄운다. setup_kv_event_publisher가 --kv-events-config의 bind 주소 tcp://*:PORT를 connect 주소 tcp://127.0.0.1:PORT로 바꿔 Rust KvEventPublisher에 넘긴다.

Decode workers skip this. setup_kv_event_publisher returns early for DisaggregationMode.DECODE and when enable_prefix_caching is off. Only caches worth routing on publish events. decode 워커는 이 단계를 건너뛴다. DisaggregationMode.DECODE이거나 enable_prefix_caching이 꺼져 있으면 setup_kv_event_publisher가 바로 반환한다. 라우팅에 쓸모 있는 캐시만 이벤트를 낸다.

2Receive + decode the msgpack batchmsgpack 배치 수신 + 디코드

The Rust zmq_listener connects a SUB socket and decodes each batch with decode_event_batch, a msgpack deserializer that understands vLLM's tag=True, array_like=True encoding and maps the variant tag to a RawKvEvent. Rust zmq_listener가 SUB 소켓을 연결하고 배치마다 decode_event_batch를 부른다. 이 msgpack 디코더는 vLLM의 tag=True, array_like=True 인코딩을 읽어 variant 태그를 RawKvEvent로 매핑한다.

3Process → batch → dedup → apply to the radix tree처리 → 배치 → 중복 제거 → radix 트리 반영

The decoded events run a short pipeline (event_processor → batching → dedup → sinks; see the module's own README diagram) and land in sinks::emit, which applies each RouterEvent to the local indexer. 디코드된 이벤트는 짧은 파이프라인(event_processor → batching → dedup → sinks, 모듈의 README 다이어그램 참고)을 지나 sinks::emit에 닿고, 여기서 각 RouterEvent를 로컬 인덱서에 반영한다.

apply_stored walks from parent_block_hash down and inserts the new hashes as child nodes, tagged with the worker id. The tree is now a live, per-worker mirror of every GPU's prefix cache, built entirely from hashes. apply_stored는 parent_block_hash에서 내려가며 새 해시를 워커 id와 함께 자식 노드로 넣는다. 이렇게 트리는 모든 GPU prefix 캐시를 해시만으로 실시간 반영한다.

4The shape of the data — one shared radix tree자료구조: 모든 워커가 공유하는 radix 트리

All workers feed one tree. A node represents a single cached block (keyed by its token-hash), and it holds the set of workers that currently have that block. A second per-worker map gives O(1) access to any node by hash for fast removes. 모든 워커가 하나의 트리를 채운다. 노드 하나는 캐시된 블록 하나(토큰 해시가 키)이며, 그 블록을 지금 가진 워커 집합을 저장한다. 워커별 보조 맵으로 해시에서 노드를 O(1)에 찾으므로 remove가 빠르다.

What arrives vs what is kept. A BlockStored event carries a fair amount, including the raw token_ids, but almost all of it is consumed at ingestion to compute a hash and then dropped. Only hashes and the worker set survive into the tree. 들어오는 것과 남는 것. BlockStored는 원본 token_ids까지 싣고 오지만, 대부분은 받자마자 해시 계산에 쓰고 버린다. 트리에는 해시와 워커 집합만 남는다.

Where token_ids actually live. Only the Frontend (the preprocessor / tokenizer) handles raw token_ids, and only per request, transiently: it tokenizes the prompt and hashes its blocks to query the tree. Neither the event tree nor the router keeps token_ids as state. Everything persistent is a hash. token_ids는 어디에 있나. 원본 token_ids는 Frontend(preprocessor/토크나이저)만 요청마다 잠깐 다룬다. 프롬프트를 토크나이즈하고 블록을 해시해 트리에 질의하는 용도다. 이벤트 트리도 라우터도 token_ids를 저장하지 않고, 남는 것은 모두 해시다.

Two hashes per block — token hash vs block hash, by example블록당 해시 두 개: token hash와 block hash

A block carries two hashes and they are not redundant. Take block_size = 4 and a prompt where the same 4 tokens repeat: 블록은 해시를 두 개 가지며, 둘은 서로 대체할 수 없다. block_size = 4에서 같은 4토큰이 반복되는 프롬프트를 예로 든다.

tokens = [10,11,12,13, 10,11,12,13] └─ block1 ─┘ └─ block2 ─┘ # 내용이 동일 token hash (이 블록의 토큰만): block1 = TH block2 = TH # 똑같음! block hash (이 블록 + 앞 prefix): block1 = seq1=TH block2 = hash(seq1,TH)=seq2 # 다름

That ambiguity is why both exist: token hash addresses content (tree branching & overlap), block hash addresses identity (pinpointing one block to remove). The remove event carries no tokens, so token hash can't be recomputed there. So apply_stored registers each node under both keys: 두 해시가 따로 있는 이유가 이 모호함이다. token hash는 내용을 가리키고(트리 분기와 overlap용), block hash는 개별 블록을 가리킨다(제거할 블록 특정용). remove 이벤트에는 토큰이 없어 token hash를 다시 계산할 수도 없다. 그래서 apply_stored는 노드를 두 키로 등록한다.

Mental model. Like a library shelving one book on a subject shelf (by content = token hash, how you browse) and also in the call-number catalog (by unique id = block hash, how you reclaim a specific copy). Browse by shelf, reclaim by call number. 비유. 도서관이 책을 주제별 서가(내용 = token hash)에 꽂고 청구기호 목록(고유 id = block hash)에도 올리는 것과 같다. 둘러볼 때는 서가를, 특정 책을 회수할 때는 청구기호를 쓴다.

The two destructive events are cheap and surgical. apply_removed uses the worker's lookup map to find the node in O(1) and drops the worker from its set. It deliberately does not cascade to descendants (the query reconciles stale descendants lazily). clear_all_blocks walks the worker's entries and removes it everywhere. 삭제 이벤트 두 개는 가볍고 정확하다. apply_removed는 워커 lookup 맵으로 노드를 O(1)에 찾아 그 노드의 집합에서 워커만 뺀다. 자손에는 일부러 전파하지 않으며, 남은 stale 자손은 query가 나중에 보정한다. clear_all_blocks는 워커의 항목을 돌며 모든 노드에서 워커를 지운다.

So what does the router actually do with this tree? On each incoming request it hashes the prompt's blocks and calls find_matches, which walks the tree top-down. The active worker set can only shrink as it descends (a worker missing the next block drops out), so the depth each worker survives to is its overlap: how many leading blocks of this prompt that worker already holds. The result is an OverlapScores map: worker → overlap_blocks. 라우터는 이 트리를 어떻게 쓰나. 요청이 오면 프롬프트 블록을 해시해 find_matches로 트리를 위에서부터 내려간다. 다음 블록이 없는 워커는 탈락하므로 활성 워커 집합은 줄어들기만 한다. 각 워커가 버틴 깊이가 곧 overlap, 즉 이 프롬프트의 앞 블록을 몇 개 갖고 있는지다. 결과는 worker → overlap_blocks 형태의 OverlapScores 맵이다.

Important: it does NOT just pick the longest-cache worker. The overlap is one input to a cost function. For each candidate the router computes a logit, and the lowest logit wins (argmin): 주의: "캐시가 가장 긴 워커"를 고르는 것이 아니다. overlap은 비용 함수의 입력 하나일 뿐이다. 후보마다 logit을 계산해 가장 낮은 값을 고른다(argmin).

In words: logit = (prefill blocks left after subtracting cache overlap) + current decode load. A big KV overlap shrinks the first term (the payoff of the event tree), but a worker that's already saturated with decode work carries a high second term and can still lose to a less-loaded peer with slightly smaller overlap. So the router selects the cheapest worker (best reuse and capacity), not merely the one holding the most cache. The full cost function and the argmin/softmax pick are in section 6. 식으로 쓰면 logit = (캐시 overlap을 뺀 남은 prefill 블록) + 현재 decode 부하다. overlap이 크면 첫 항이 줄고, 이것이 이벤트 트리가 주는 이득이다. 하지만 decode로 이미 바쁜 워커는 둘째 항이 커서 overlap이 조금 작은 한가한 워커에게 밀릴 수 있다. 라우터는 재사용 이득과 여력을 함께 따져 비용이 가장 낮은 워커를 고른다. 전체 비용 함수와 argmin/softmax 선택은 섹션 6에서 다룬다.

6 · Closing the loop — from events to a routing decision루프 닫기: 이벤트에서 라우팅 결정까지 Dynamo

When a request arrives, the router hashes the prompt's blocks the same way and queries the tree. find_matches returns OverlapScores (how many blocks each worker already has), and that number flows straight into the cost function from the overview. 요청이 오면 라우터는 프롬프트 블록을 같은 방식으로 해시해 트리를 조회한다. find_matches가 반환한 OverlapScores(워커별 보유 블록 수)는 개요 문서의 비용 함수로 바로 들어간다.

The full life of one event: vLLM caches a block → block_pool queues BlockStored → scheduler.step() publishes a KVEventBatch over ZMQ → Dynamo's zmq_listener decodes it → pipeline applies it to the radix tree → a later request's find_matches sees that block as overlap → worker_logit subtracts it from prefill cost → the request routes to that worker → which produces a cache hit instead of re-prefilling. The event is the feedback signal that makes the cache visible to a process that can't touch the GPU. 이벤트 한 개의 일생: vLLM이 블록 캐시 → block_pool이 BlockStored 큐잉 → scheduler.step()이 ZMQ로 KVEventBatch 발행 → Dynamo zmq_listener가 디코드 → 파이프라인이 radix 트리에 반영 → 이후 요청의 find_matches가 그 블록을 오버랩으로 인식 → worker_logit이 prefill 비용에서 차감 → 요청이 그 워커로 라우팅 → 다시 prefill하지 않고 캐시 히트. 이벤트는 GPU에 접근할 수 없는 프로세스에게 캐시를 보여 주는 피드백 신호다.
What if you turn events off? Setting enable_kv_cache_events:false means the tree is never populated. Dynamo then falls back to prediction-based routing (the router estimates overlap from the prompts it has itself dispatched) or to plain load-based modes. Events make the signal exact rather than predicted, but cost a small ZMQ stream per worker. 이벤트를 끄면? enable_kv_cache_events:false면 트리가 비어 있다. Dynamo는 예측 기반 라우팅(자기가 보낸 프롬프트로 오버랩 추정)이나 단순 부하 기반 모드로 돌아간다. 이벤트를 켜면 워커당 작은 ZMQ 스트림을 대가로 추정치 대신 정확한 신호를 얻는다.

7 · Worked scenarios시나리오별 그림

Three concrete cases, all at block_size = 32. The rule to keep in mind: an event fires only when a block becomes full, and prompt-prefill events are published in the engine step right after prefill, while decode events fire as later blocks top off. 1024 = 32×32 is block-aligned; 1055 = 1024 + 31 leaves a 31-token tail. 모두 block_size = 32 기준이다. 이벤트는 블록이 full이 될 때만 난다. prefill 이벤트는 prefill 직후 스텝에, decode 이벤트는 뒤 블록이 찰 때 발행된다. 1024 = 32×32는 블록 경계에 딱 맞고, 1055 = 1024 + 31은 31토큰 자투리가 남는다.

Legend. green = block cached at prefill · blue = block filled (cached) during decode · dashed gray = partial block, not full → no event · ● marks a BlockStored publish. 범례. 초록 = prefill에 캐시된 블록 · 파랑 = decode 중 채워져 캐시된 블록 · 회색 점선 = partial 블록(미완성) → 이벤트 없음 · ● 는 BlockStored 발행 시점.

A · Single turn — prompt 1024, output 32A · 싱글턴: prompt 1024, output 32

1024 is exactly 32 blocks, so prefill caches all of them and emits one batch of 32 hashes. The 32 output tokens form one more block (positions 1024–1055) that becomes full precisely on the last generated token → one final BlockStored. Total: 33 blocks, 2 publishes (32 + 1). 1024는 정확히 32블록이라 prefill이 모두 캐시하고 해시 32개를 한 배치로 발행한다. output 32토큰은 블록 하나(위치 1024–1055)를 이루고, 마지막 생성 토큰에서 full이 되어 BlockStored가 하나 더 난다. 합계는 33블록, 발행 2회(32 + 1)다.

B · Single turn — prompt 1055, output 32B · 싱글턴: prompt 1055, output 32

The extra 31 prompt tokens do not add a prefill event; they sit in a partial block (B33, 31/32). That block fills only when the first output token arrives, so B33's event is deferred into decode. Then 31 of the 32 outputs land in B34, which ends 31/32 and never fires. Total full blocks = 33, same as A, but the timing differs and a 31-token tail stays uncached. Lesson: a longer prompt does not mean more (or earlier) events — only crossed block boundaries do. 늘어난 prompt 31토큰은 partial 블록(B33, 31/32)에 들어갈 뿐 prefill 이벤트를 늘리지 않는다. B33은 첫 output 토큰이 와야 차므로 이벤트가 decode로 밀린다. 나머지 output 31개는 B34에 들어가 31/32로 끝나고 이벤트를 내지 않는다. full 블록은 A와 같은 33개지만 타이밍이 다르고, 31토큰 꼬리는 캐시되지 않는다. prompt가 길다고 이벤트가 더 많이, 더 일찍 나는 것이 아니다. 블록 경계를 넘어야 난다.

C · Multi-turn — turn 2 reuses turn 1's cacheC · 멀티턴: 턴2가 턴1 캐시를 재사용

Turn 2's prompt is the entire turn-1 conversation plus new text. The first 33 blocks are a prefix-cache hit: num_cached_blocks already covers them, so cache_full_blocks skips them: no recompute and no new events. Only the appended content emits, here one new full block (B34); the 8-token tail (B35) stays partial. Because the shared prefix produced no events but is already in the router's radix tree from turn 1, find_matches reports a large overlap and the request routes back to the same worker. 턴2의 prompt는 턴1 대화 전체에 새 텍스트를 붙인 것이다. 앞 33블록은 num_cached_blocks에 이미 들어 있는 prefix 캐시 히트라 cache_full_blocks가 건너뛴다. 재계산도 새 이벤트도 없다. 새로 붙은 부분만 발행되며, 여기서는 full 블록 B34 하나다. 8토큰 꼬리(B35)는 partial로 남는다. 공유 prefix는 턴1 때 이미 라우터 트리에 들어갔으므로 find_matches가 큰 오버랩을 보고 요청을 같은 워커로 보낸다.

D · Eviction & reset — BlockRemoved / AllBlocksClearedD · 축출과 리셋: BlockRemoved / AllBlocksCleared

The first three scenarios only produced BlockStored because the cache was growing. The destructive events appear once a worker is under memory pressure or is reset. 앞의 세 시나리오는 캐시가 커지기만 해서 BlockStored만 났다. 삭제 이벤트는 워커 메모리가 부족하거나 캐시를 리셋할 때 나온다.

So the full event vocabulary keeps the router's mirror in sync in both directions: BlockStored grows a worker's footprint and attracts matching requests; BlockRemoved / AllBlocksCleared shrink it so the router stops sending requests to a cache that no longer exists. Without the destructive events the router would keep routing to phantom hits and waste prefill. 세 이벤트는 라우터의 사본을 양방향으로 맞춘다. BlockStored는 워커의 캐시 영역을 넓혀 맞는 요청을 끌어오고, BlockRemoved / AllBlocksCleared는 영역을 줄여 사라진 캐시로 요청이 가지 않게 한다. 삭제 이벤트가 없으면 라우터는 있지도 않은 히트를 믿고 보내 prefill을 낭비한다.
