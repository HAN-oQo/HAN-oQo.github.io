What's a KV connector?KV 커넥터란?

A plug-in that moves a request's KV-cache out of an engine: to a peer engine (P/D), a shared store (prefix reuse), or CPU/disk (offload).요청의 KV-cache를 엔진 밖으로 옮기는 플러그인이다. 목적지는 다른 엔진(P/D), 공유 스토어(prefix 재사용), CPU/디스크(오프로드)다.

Push (prefill→decode)Push (prefill→decode)

The producer (prefill) initiates and writes KV into the consumer's memory.생산자(prefill)가 계산을 마친 KV를 소비자 메모리에 써넣는다.

Pull (decode→prefill)Pull (decode→prefill)

The consumer (decode) initiates and reads KV from the producer, which just exposes it and waits.소비자(decode)가 생산자에서 KV를 읽어온다. 생산자는 KV를 노출하고 기다린다.

Bidirectional (kv_both)양방향 (kv_both)

One instance is both producer and consumer (kv_both), e.g. multi-turn where roles flip.한 인스턴스가 생산자이자 소비자다(kv_both). 역할이 뒤바뀌는 멀티턴에 쓴다.

Store-mediated스토어 경유

No P↔D socket. The producer writes KV to a hash-keyed store/FS and the consumer reads it later.P↔D 소켓이 없다. 생산자가 해시 키로 스토어/FS에 쓰고 소비자가 나중에 읽는다.

Offload (intra-instance)오프로드 (인스턴스 내)

Not P/D: moves KV GPU↔CPU/disk within one engine for memory relief or prefix reuse.P/D가 아니다. 한 엔진 안에서 KV를 GPU↔CPU/디스크로 옮겨 메모리를 확보하거나 prefix를 재사용한다.

두 엔진 사이에서 KV를 네트워크로 옮기는 커넥터다. NIXL은 Pull/Push 변형으로 나뉘었고, 그냥 NixlConnector는 Pull의 별칭이다.

4Speed — what actually determines it속도: 실제로 무엇이 좌우하나

first, the question this raises: are all connectors the same speed?먼저, 여기서 나오는 질문: 커넥터마다 속도가 같은가? No. The interconnect sets a ceiling; the connector decides (a) which physical path it uses and (b) how close to the ceiling it gets.
  • Path: filesystem/store connectors copy GPU→host-CPU→disk→CPU→GPU. NIXL/Mooncake/MoRIIO go GPU→NIC→RDMA→NIC→GPU with GPUDirect, bypassing the host. The gap is orders of magnitude.
  • Software on the same link: LMCache loads KV from CPU at 400 Gbps vs vLLM-native 88 Gbps, 4.5× on the same hardware, from chunk-wise vs page-wise transfer (LMCache §8.6).
아니다. 인터커넥트는 천장(최대 대역폭)만 정한다. (a) 어떤 물리 경로를 쓰는지, (b) 천장에 얼마나 다가가는지는 커넥터가 정한다.
  • 경로: 파일시스템/스토어 커넥터는 GPU→호스트CPU→디스크→CPU→GPU로 복사한다. NIXL/Mooncake/MoRIIO는 GPUDirect로 호스트를 우회해 GPU→NIC→RDMA→NIC→GPU로 간다. 차이는 자릿수 단위다.
  • 같은 링크에서의 소프트웨어: LMCache는 CPU에서 KV를 400 Gbps로, vLLM 기본은 88 Gbps로 읽는다. 같은 하드웨어에서 4.5배 차이이고, chunk 단위와 page 단위 전송의 차이에서 나온다(LMCache §8.6).

Why "bandwidth-bound" still matters: transfer_time ≈ KV_bytes / link_bandwidth. Once a connector saturates the fast path (RDMA/GPUDirect), the interconnect becomes the dominant lever. vLLM's docs agree: overhead "depends on … the interconnect or network bandwidth, size of KV cache, the prefill/decode instance configurations" (disagg_prefill docs). DistServe's worked example: one 512-token request on OPT-66B ≈ 1.13 GB of KV, so 10 rps needs ~90 Gbps to stay invisible; intra-node over NVLink (600 GB/s on A100) it's "negligible" — measured at <0.1% of total latency on OPT-175B (DistServe, OSDI'24 §3.3/§6.3).

그래도 "대역폭 바운드"가 중요한 이유: 전송시간 ≈ KV바이트 / 링크대역폭. 커넥터가 빠른 경로(RDMA/GPUDirect)를 꽉 채우면 남는 변수는 링크뿐이라 인터커넥트가 가장 큰 지렛대가 된다. vLLM 문서도 오버헤드가 "인터커넥트/네트워크 대역폭, KV 캐시 크기, prefill/decode 인스턴스 구성에 달렸다"고 쓴다(disagg_prefill 문서). DistServe 예시로 보면 OPT-66B의 512토큰 요청 하나가 KV ≈ 1.13 GB이고, 10 rps에서 지연이 안 보이려면 ~90 Gbps가 필요하다. 노드 내 NVLink(A100 600 GB/s)에서는 "무시 가능"하며, OPT-175B에서 총 지연의 <0.1%로 실측됐다(DistServe, OSDI'24 §3.3/§6.3).

Same hardware path, different speed — why?같은 하드웨어 경로인데 왜 속도가 다른가?

Two connectors on the same link (e.g. the same 400G RoCE NIC with GPUDirect RDMA, or the same PCIe for GPU↔CPU) can still differ several-fold. The levers:

push vs pull — a latency difference, NOT a bandwidth onepush vs pull: 대역폭이 아니라 지연 차이 Same link and bytes means same bandwidth. What differs is who initiates and whether decode-side memory registration overlaps prefill. Push removes a proxy round-trip from the critical path. vLLM's own measurement (AWS P5en): "KV push mode showed 1.2× – 3.0× improvements over pull mode" on TTFT (e.g. TP4 512/128 conc8: 2948 ms → 1212 ms; P99 740 ms → 100 ms). vLLM RFC #36923 링크와 바이트가 같으면 대역폭도 같다. 다른 점은 누가 시작하는지, decode 측 메모리 등록이 prefill 연산과 겹치는지다. push는 임계경로에서 프록시 왕복을 없앤다. vLLM 실측(AWS P5en): TTFT에서 "push 모드가 pull 대비 1.2×–3.0× 개선"(예: TP4 512/128 conc8: 2948 ms → 1212 ms; P99 740 ms → 100 ms). vLLM RFC #36923
store-mediated: slower per transfer, but that's not the point스토어 경유: 전송당 느리지만 목적이 다르다 A store/filesystem (and the host CPU) in the data path has higher latency than zero-copy RDMA P2P (UCCL). The payoff is reuse: Mooncake Store in vLLM showed 46× lower P50 TTFT, but from cache hit rate 1.7% → 92.2%, not faster bytes (vLLM blog). It wins on shared prefixes and loses on a one-shot handoff. 스토어/파일시스템과 호스트 CPU가 데이터 경로에 끼면 zero-copy RDMA P2P보다 지연이 크다(UCCL). 대신 재사용을 얻는다. vLLM의 Mooncake Store는 P50 TTFT를 46× 줄였는데, 이는 캐시 적중률 1.7% → 92.2%에서 왔지 바이트가 빨라서가 아니다(vLLM 블로그). prefix를 공유하는 요청에서는 이기고, 일회성 핸드오프에서는 진다.
caveat: read these numbers carefully주의: 수치를 읽는 법 Almost everything above is vendor/first-party, and there is no independent three-way NixlConnector vs Mooncake vs LMCache benchmark. Models, workloads, and baselines differ, so Mooncake's 46× and the 252 GB/s storage figures are not like-for-like with NIXL P2P transport. The connectors are also partly layered, not competing: "Both LMCache and Mooncake can use NIXL under the hood" (vLLM docs). For a real comparison you must benchmark on your own hardware. 위 수치는 거의 전부 vendor/1차 출처이고, NixlConnector vs Mooncake vs LMCache 독립 3자 벤치마크는 없다. 모델·워크로드·기준이 제각각이라 Mooncake의 46×나 252 GB/s 스토리지 수치는 NIXL P2P 전송과 같은 조건이 아니다. 커넥터는 경쟁하기보다 층으로 겹치기도 한다. "LMCache와 Mooncake 모두 내부적으로 NIXL을 쓸 수 있다"(vLLM 문서). 제대로 비교하려면 자기 하드웨어에서 직접 측정해야 한다.

5Hardware & dependencies per connector커넥터별 하드웨어 · 의존성

The transport library decides the hardware: (1) GPU vendor (NVIDIA CUDA / AMD ROCm / NPU), (2) interconnect/NIC (RDMA NIC cross-node, NVLink/XGMI/PCIe intra-node), (3) extra deps (store cluster, GDS, etc.). Checked against each project's repo/docs.

어떤 하드웨어에서 도는지는 전송 라이브러리가 정한다. 볼 것은 (1) GPU 벤더(NVIDIA CUDA / AMD ROCm / NPU), (2) 인터커넥트/NIC(노드 간 RDMA NIC, 노드 내 NVLink/XGMI/PCIe), (3) 추가 의존성(스토어 클러스터, GDS 등)이다. 각 프로젝트 레포·문서로 확인했다.

the practical catch — wheel/build in your image, not just "support"실전 함정: "지원 여부"보다 이미지에 든 휠/빌드 "Supported" ≠ "works in your container." A connector runs only if the matching transport wheel/build is installed for your platform. In our MI250/ROCm PD test, the rocm/vllm image shipped a CUDA-linked Mooncake wheel (libcudart.so.12) and no NIXL, so both failed to import on AMD even though the projects list ROCm/non-CUDA support upstream. On AMD today, MoRIIO is the natively-built path; NIXL/Mooncake need the ROCm/non-CUDA wheel present. "지원함" ≠ "내 컨테이너에서 됨". 해당 전송 휠/빌드가 내 플랫폼용으로 설치돼 있어야 커넥터가 돈다. 우리 MI250/ROCm PD 실험에서 rocm/vllm 이미지에는 CUDA로 링크된 Mooncake 휠(libcudart.so.12)이 들어 있었고 NIXL은 없었다. 업스트림은 ROCm/non-CUDA를 지원하는데도 AMD에서 둘 다 import에 실패했다. 지금 AMD에서는 MoRIIO가 네이티브 빌드 경로이고, NIXL/Mooncake는 ROCm/non-CUDA 휠이 있어야 한다.

6Notes & what changed메모 · 달라진 점

removed since earlier versions이전 버전에서 제거됨 P2pNcclConnector (one-way P→D-push NCCL connector from PR #18242, in v0.10/v0.11) is gone from main, both factory and tree. NIXL Push/Pull and MoRIIO now fill its direct-P2P role. SharedStorageConnector is replaced by ExampleConnector (same filesystem-safetensors demo). P2pNcclConnector(PR #18242의 단방향 P→D-push NCCL 커넥터, v0.10/v0.11에 존재)는 main에서 사라졌다. 팩토리에도 트리에도 없다. 직접 P2P 역할은 NIXL Push/Pull 커넥터와 MoRIIO가 맡는다. SharedStorageConnector는 ExampleConnector(같은 파일시스템-safetensors 데모)로 대체됐다.
how to read "direction" honestly"방향"을 정직하게 읽는 법 Only NIXL/Mooncake/MoRIIO do direct engine↔engine transfer where push vs pull is a real distinction. Store/cache connectors "write-then-read" through a pool, so the right label is store-mediated, not push or pull. Offload connectors never leave the instance. The answer to "push / pull / bidirectional?" lives in §1. push와 pull의 구분이 실제로 의미 있는 건 NIXL/Mooncake/MoRIIO뿐이다. 스토어·캐시 커넥터는 풀에 쓰고 나중에 읽으므로 push/pull이 아니라 스토어 경유라고 불러야 맞다. 오프로드 커넥터는 인스턴스를 떠나지 않는다. "push / pull / 양방향?"의 답은 §1에 있다.
one-line takeaway한 줄 정리 Pull: NixlConnector (default), NixlPullConnector. Push: NixlPushConnector, MooncakeConnector, MoRIIO (default). Pull opt-in: MoRIIO (read_mode). Bidirectional (kv_both): only MooncakeConnector among the direct-transfer ones (LMCache/FlexKV/HF3FS support kv_both but as store-mediated, not direct P/D). Pull: NixlConnector(기본), NixlPullConnector. Push: NixlPushConnector, MooncakeConnector, MoRIIO(기본). Pull 옵션: MoRIIO(read_mode). 양방향(kv_both): 직접 전송 중에서는 MooncakeConnector만(LMCache/FlexKV/HF3FS도 kv_both를 지원하지만 직접 P/D가 아닌 스토어 경유다).
