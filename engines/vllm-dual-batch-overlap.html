vLLM Dual Batch Overlap (DBO) — theory, effects, code flow, status vLLM Dual Batch Overlap (DBO): 이론·효과·코드 흐름·구현 상태

DBO splits one batch into two micro-batches so that while one does the MoE all-to-all, the other does GPU compute. In vLLM it targets only data-parallel + expert-parallel (DP+EP) MoE. This note reads it from the design doc, PRs and commit-pinned code. DBO는 배치 하나를 마이크로배치 둘로 쪼개, 한쪽이 MoE all-to-all 통신을 하는 동안 다른 쪽이 GPU 연산을 하게 만든다. vLLM에서는 data-parallel + expert-parallel (DP+EP) MoE 배포에서만 동작한다. 설계 문서와 PR, 커밋에 고정한 코드를 근거로 정리했다.

one-line summary한 줄 요약
  • In MoE serving, every layer sends tokens to their experts' GPUs (all-to-all dispatch) and back (combine). Across nodes this can equal the compute (DeepSeek-V3: ≈1:1).
  • DBO splits the batch in two and overlaps µbatch-A's all-to-all with µbatch-B's compute.
  • Helps when comm is the bottleneck (multi-node, high EP); hurts on a single node (38 ms → 49 ms per step) because weights are loaded twice.
  • Off by default, opt-in via --enable-dbo, MoE all-to-all only (not tensor-parallel all-reduce).
  • MoE 서빙에서는 매 레이어가 토큰을 expert가 있는 GPU로 보냈다가(all-to-all dispatch) 다시 모은다(combine). 노드를 넘으면 이 통신이 연산과 맞먹는다(DeepSeek-V3 보고 ≈1:1).
  • DBO는 배치를 둘로 쪼개 µbatch-A의 all-to-all을 µbatch-B의 연산과 겹친다.
  • 통신이 병목인 멀티노드·높은 expert-parallel에서는 이득이고, 단일 노드에서는 손해다(스텝당 38ms→49ms). 가중치를 두 번 로드하기 때문이다.
  • 기본은 꺼져 있고 --enable-dbo로 켠다. MoE all-to-all 경로에만 구현돼 있고 tensor-parallel all-reduce는 대상이 아니다.

MoE

Mixture-of-Experts. Each token goes to a few of many expert FFNs, spread across GPUs in large models.Mixture-of-Experts. 토큰마다 여러 expert FFN 중 몇 개로 라우팅하고, 큰 모델은 expert를 여러 GPU에 나눠 둔다.

EP / DP

EP splits experts across GPUs; DP runs the full model per GPU on different requests. DBO needs DP>1 + EP.EP는 expert를 GPU에 나누고, DP는 GPU마다 전체 모델로 다른 요청을 처리한다. DBO는 DP>1 + EP가 필요하다.

all-to-all (dispatch / combine)all-to-all (dispatch / combine)

The collective that sends each token to its expert's GPU and gathers the result back. The thing DBO hides.토큰을 expert의 GPU로 보내고 결과를 다시 모으는 집합통신이다. DBO가 숨기는 대상이다.

all-reduce

The tensor-parallel collective that sums partial results across GPUs. Background only: vLLM DBO does not overlap it.GPU 간 부분합을 더하는 tensor-parallel 집합통신이다. 배경 설명용이며 vLLM DBO가 겹치는 대상은 아니다.

micro-batch (ubatch)마이크로배치 (ubatch)

Half of the batch. "ubatch" = µ-batch in ASCII. DBO hardcodes exactly 2.배치의 절반이다. "ubatch"는 µ-batch의 ASCII 표기이고, DBO는 2개로 고정한다.

DeepEP

DeepSeek's all-to-all GPU kernels for MoE. The only all-to-all backend DBO supports today.DeepSeek의 MoE용 all-to-all GPU 커널이다. 현재 DBO가 지원하는 유일한 all-to-all 백엔드다.

1Theory — why communication is the bottleneck, and what DBO hides이론: 통신이 왜 병목이고 DBO가 무엇을 숨기나

A GPU forward pass is normally compute-bound. Distributed inference adds collective communication to every layer, and by default it does not overlap with compute: the next op needs the result, so the GPU idles while bytes move. GPU forward는 보통 연산 바운드다. 그런데 분산 추론은 매 레이어에 집합통신을 넣고, 이 통신은 기본적으로 연산과 겹치지 않는다. 다음 연산이 통신 결과를 기다려야 해서 데이터가 오가는 동안 GPU는 논다.

Two regimes of communication통신의 두 가지 형태

Tensor parallel (TP) shards each weight matrix across GPUs and does two all-reduces per layer (after attention, after the MLP) — this is the original Megatron pattern [Megatron-LM]. It is blocking and not cheap: for a 70B model at TP=8 it can be ~38% of inference latency even over NVLink [Ladder-residual §2], and ~23% end-to-end on a single 8×H100 node [TokenWeave §1]. Tensor parallel(TP)는 가중치 행렬을 GPU에 쪼개고 레이어당 all-reduce를 2회(attention 후, MLP 후) 한다. Megatron에서 시작된 패턴이다 [Megatron-LM]. 이 통신은 블로킹이고 비용도 크다. 70B·TP=8이면 NVLink로도 추론 지연의 ~38%를 차지하고 [Ladder-residual §2], 단일 8×H100에서도 end-to-end ~23%다 [TokenWeave §1].

Expert parallel (EP) for MoE is worse, and it is what DBO targets. Each MoE layer sends every token to its experts' GPU (all-to-all dispatch), runs the experts, and sends outputs back (all-to-all combine). The more nodes the experts span, the more traffic crosses the slow inter-node fabric. MoE의 Expert parallel(EP)은 더 심하고, DBO가 노리는 곳이 여기다. MoE 레이어마다 토큰을 expert가 있는 GPU로 보내고(all-to-all dispatch), expert를 돌린 뒤 결과를 다시 모은다(all-to-all combine). expert를 여러 노드에 펼칠수록 느린 노드 간 링크를 건너는 트래픽이 늘어난다.

"the communication overhead introduced by cross-node expert parallelism results in an inefficient computation-to-communication ratio of approximately 1:1."

— DeepSeek-V3 Technical Report, §3.2.1 · arXiv:2412.19437

If comm takes as long as compute and they run back-to-back, a step takes nearly double what it should. DeepSeek adds that InfiniBand (~50 GB/s) is ~3.2× slower than NVLink (~160 GB/s) and "the upper limit of MoE inference speed is dictated by interconnection bandwidth" [Insights into DeepSeek-V3 §2.3.2]. So hiding comm behind compute is the highest-leverage optimization. 통신이 연산만큼 걸리고 둘이 차례로 돌면 스텝 시간이 거의 두 배가 된다. DeepSeek은 InfiniBand(~50 GB/s)가 NVLink(~160 GB/s)보다 ~3.2배 느리고, "MoE 추론 속도의 상한은 인터커넥트 대역폭이 결정한다"고 덧붙인다 [Insights into DeepSeek-V3 §2.3.2]. 그래서 통신을 연산 뒤에 숨기는 것이 가장 효과가 큰 최적화다.

TP all-reduce overlap is a separate, unmerged effort (open PR #44677). Many secondary write-ups blur this. 위의 TP all-reduce 수치는 배경일 뿐이다. vLLM DBO가 겹치는 것은 MoE expert-parallel all-to-all뿐이고, 설계 문서도 "현재 DP+EP 배포만 대상으로 한다"고 적는다 [vLLM DBO doc]. TP all-reduce 겹치기는 아직 병합되지 않은 별도 작업이다(open PR #44677). 2차 글들이 이 구분을 자주 흐린다.

2How it works — two micro-batches, two streams, a ping-pong동작 원리: 두 마이크로배치·두 스트림·핑퐁

The idea comes from DeepSeek's inference-side dual-microbatch overlap. vLLM's blog calls it "DeepSeek's microbatching strategy" [vLLM blog]: 아이디어는 DeepSeek의 추론용 dual-microbatch overlap에서 왔다. vLLM 블로그도 "DeepSeek의 microbatching 전략"이라고 부른다 [vLLM blog].

"while one micro-batch executes a portion of MLA or MoE computation, the other micro-batch simultaneously performs the corresponding dispatch communication … seamless overlap of all-to-all communication with ongoing computation."

— Insights into DeepSeek-V3, §2.3.1 · arXiv:2505.09343v1

In vLLM, the batch is split into 2 micro-batches, each on its own CPU worker thread, with two CUDA streams (compute and communication). One thread runs at a time. At dbo_yield points inside the MoE kernel, a thread launches its async all-to-all and hands over to the other thread, whose compute runs over the in-flight comm. The receive side finishes later via a stashed "recv hook" [PR #23693]. vLLM은 배치를 마이크로배치 2개로 쪼개 각각 별도 CPU 워커 스레드에서 돌리고, CUDA 스트림 2개(연산용·통신용)를 쓴다. 한 번에 한 스레드만 실행된다. MoE 커널 안의 dbo_yield 지점에서 한 스레드가 비동기 all-to-all을 띄우고 다른 스레드에 넘기면, 그 스레드의 연산이 진행 중인 통신 위에서 돈다. 수신은 저장해 둔 "recv hook"으로 나중에 마무리한다 [PR #23693].

Fig 2 · Timeline without vs with DBO. Schematic, block widths illustrative. Mechanism per vLLM DBO doc & PR #23693.그림 2 · DBO 유무에 따른 타임라인. 개략도이며 블록 폭은 예시다. 메커니즘 출처: vLLM DBO doc, PR #23693.

In short: Python threading (2 worker threads, one active) + 2 CUDA streams + CUDA events for ordering + a coroutine-like dbo_yield ping-pong inside the fused-MoE kernel. Not asyncio. The halves are concatenated along the batch dimension at the end. 정리하면 Python threading(워커 스레드 2개, 한 번에 하나) + CUDA 스트림 2개 + 순서를 맞추는 CUDA event + fused-MoE 커널 안의 코루틴 같은 dbo_yield 핑퐁이다. asyncio는 쓰지 않는다. 두 절반은 마지막에 배치 차원으로 이어 붙인다.

3Pros & cons — theory vs. what's actually been reported장단점: 이론과 실제 보고 수치

Bottom line: no public source isolates vLLM-DBO's standalone speedup, and the one direct vLLM measurement is a single-node regression. Strong wins are reported for the multi-node MoE regime DBO is built for. 결론부터 말하면 vLLM-DBO 단독 속도 향상을 따로 잰 공개 출처는 없다. 직접 측정한 vLLM 수치 하나는 단일 노드에서 느려진 결과다. 큰 이득은 DBO가 겨냥한 멀티노드 MoE 환경에서 보고된다.

editor's note: our angle (not a vLLM claim)편집자 주: 우리 관점 (vLLM 주장 아님)
  1. On a single MI250 node (our usual lab), DBO would almost certainly regress: comm is local and the weights-loaded-twice cost dominates, the 38→49 ms case.
  2. It pays off only for a large MoE spread across nodes with expert parallelism (llm-d / wide-EP). Plan for it at fleet scale, not for a single-box benchmark.
  3. It pairs with the EP all-to-all backends (DeepEP) wide-EP needs anyway.
  1. 단일 MI250 노드(우리 평소 랩)에서는 DBO가 거의 확실히 느려진다. 통신이 로컬이라 가중치 이중 로드 비용이 더 커지는 38→49ms 사례와 같다.
  2. 큰 MoE를 expert parallel로 여러 노드에 펼쳤을 때(llm-d / wide-EP)만 효과가 있다. 단일 박스 벤치가 아니라 fleet 규모에서 계획할 기능이다.
  3. wide-EP에 어차피 필요한 EP all-to-all 백엔드(DeepEP)와 함께 쓴다.

Hard constraints (all enforced in code):강한 제약(모두 코드에서 강제한다):

  • DP>1 + expert-parallel, else the DP-coordination step early-returns and DBO never triggers.
  • DeepEP all-to-all only (pplx/naive not supported).
  • Full CUDA graphs (or none): "essential for minimizing the CPU overhead".
  • A per-step token threshold must be cleared.
  • The decision is uniform across DP ranks: if any rank can't split (e.g. padding leaves an empty 2nd micro-batch), DBO is off for that step everywhere. On CPU platforms it is silently disabled.
  • DP>1 + expert-parallel. 아니면 DP 조정 단계가 바로 반환해 DBO가 켜지지 않는다.
  • DeepEP all-to-all만 지원한다(pplx/naive 미지원).
  • full CUDA graph(또는 graph 없음). full graph는 "essential for minimizing the CPU overhead"다.
  • 스텝마다 토큰 임계값을 넘어야 한다.
  • 결정은 모든 DP rank에서 같게 내린다. 한 rank라도 못 쪼개면(예: 패딩 후 2번째 마이크로배치가 비면) 그 스텝은 모든 rank에서 DBO를 끈다. CPU 플랫폼에서는 조용히 꺼진다.

Only the MoE all-to-all is overlapped, implemented solely in FusedMoEModularKernel. There are assert not dbo_enabled() guards on the non-async MoE paths, so DBO must use the async dispatch/finalize path. Dense/attention/TP layers are not overlapped.MoE all-to-all만 겹치며 FusedMoEModularKernel에만 구현돼 있다. 동기 MoE 경로에는 assert not dbo_enabled() 가드가 있어 DBO는 비동기 dispatch/finalize 경로를 반드시 쓴다. dense/attention/TP 레이어는 겹치지 않는다.

The collectives, in one breath집합통신 한눈에

all-reduce (TP)

Every rank contributes a partial result and everyone gets the sum. TP uses it for sharded matmul outputs. Blocking: the next op needs the sum.모든 rank가 부분 결과를 내고 모두가 합을 받는다. TP는 sharded matmul의 부분 출력을 더할 때 쓴다. 다음 연산이 합을 기다리므로 블로킹이다.

all-to-all (EP) = dispatch + combine

Every rank sends a different chunk to every other rank (a transpose). MoE does it twice: dispatch scatters each token to its expert's GPU; combine gathers the expert outputs back to the token's home GPU.각 rank가 모든 rank에 서로 다른 조각을 보낸다(transpose). MoE는 이를 두 번 한다. dispatch는 토큰을 expert의 GPU로 흩뿌리고, combine은 expert 출력을 토큰의 원래 GPU로 모은다.

point-to-point (PP)

One rank sends directly to one other (send/recv). PP passes a stage's activations to the next stage.한 rank가 다른 한 rank로 직접 보낸다(send/recv). PP는 stage의 activation을 다음 stage로 넘길 때 쓴다.

KV transfer (P/D · offload)

Not a collective: a one-shot move of an already-computed KV cache: prefill→decode (P/D), or GPU→CPU/remote (offload/tiering). Carried by NIXL/RDMA, LMCache, etc.집합통신이 아니다. 이미 계산된 KV cache를 한 번 옮긴다. prefill→decode(P/D)나 GPU→CPU/원격(offload/tiering)이 그 예이고, NIXL/RDMA, LMCache 등이 맡는다.

Fig 4 · all-reduce (TP), all-to-all (EP, dispatch+combine), KV transfer (P/D). DBO overlaps the middle one. Schematic.그림 4 · all-reduce(TP), all-to-all(EP, dispatch+combine), KV transfer(P/D). DBO가 겹치는 것은 가운데다. 개략도.

where DBO fitsDBO의 위치 DBO ⊂ Expert Parallel: it overlaps only the EP all-to-all, not TP all-reduce or KV transfer, and runs on whatever backend does the all-to-all (DeepEP, and now NIXL EP below). DBO ⊂ Expert Parallel이다. EP all-to-all만 겹치고 TP all-reduce나 KV transfer는 건드리지 않으며, all-to-all 백엔드(DeepEP, 그리고 이제 아래의 NIXL EP) 위에서 돈다.

editor's note: prediction (not a vLLM claim)편집자 주: 예측 (vLLM 주장 아님) Expected effects, in order of confidence:기대 효과를 확신이 큰 순서로 적는다.
  1. Wider reach. DBO no longer needs DeepEP; it also runs on NIXL EP. NIXL (NVIDIA Inference Xfer Library) is the transfer layer vLLM already uses for P/D KV transfer, so a fleet on NIXL EP (or wanting one stack for KV transfer and EP) gets DBO without switching to DeepEP.
  2. One fabric, composable. NIXL abstracts UCX/RDMA/GPUDirect and is shared by P/D + wide-EP, so DBO-over-NIXL-EP should compose cleanly with disaggregated / wide-EP MoE serving, the multi-node regime where DBO pays off.
  3. Full CUDA graphs on decode. With nixl_ep in the decode-optimized cudagraph guidance, DBO+NIXL EP keeps full CUDA graphs, which DBO needs to minimize CPU ping-pong overhead.
  4. Caveat: this is enablement, not a speedup kernel. If NIXL EP's all-to-all is slower than DeepEP's low-latency kernels, DBO hides a larger comm. It broadens where DBO can run more than it speeds up a DeepEP setup. For us the interesting part is convergence: NIXL as the single transfer layer under P/D KV transfer, wide-EP all-to-all, and DBO overlap.
  1. 적용 범위 확대. DBO가 DeepEP 없이 NIXL EP에서도 돈다. NIXL(NVIDIA Inference Xfer Library)은 vLLM이 P/D KV transfer에 이미 쓰는 전송 계층이다. NIXL EP를 쓰는 fleet(또는 KV transfer와 EP를 한 스택으로 묶고 싶은 fleet)은 DeepEP로 바꾸지 않고도 DBO를 쓸 수 있다.
  2. 한 fabric에서 조합. NIXL은 UCX/RDMA/GPUDirect를 추상화하고 P/D와 wide-EP가 함께 쓴다. 그래서 DBO-over-NIXL-EP는 분리형·wide-EP MoE 서빙과 잘 맞물릴 것이다. DBO가 효과를 내는 멀티노드 환경이 바로 여기다.
  3. decode에서 full CUDA graph. nixl_ep가 decode 최적화 cudagraph 가이던스에 들어가 DBO+NIXL EP도 full CUDA graph를 유지한다. DBO가 CPU 핑퐁 오버헤드를 줄이려면 필요한 조건이다.
  4. 단서: 속도를 올리는 커널이 아니라 사용 범위를 연 변경이다. NIXL EP의 all-to-all이 DeepEP low-latency 커널보다 느리면 DBO가 숨겨야 할 통신 자체가 커진다. DeepEP 환경을 빠르게 하기보다 DBO가 돌 수 있는 곳을 넓힌다. 우리에게 흥미로운 점은 NIXL이 P/D KV transfer, wide-EP all-to-all, DBO overlap 아래의 단일 전송 계층으로 모인다는 것이다.
