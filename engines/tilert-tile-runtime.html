TileRT — the tile-based ultra-low-latency LLM runtime (and what's open vs binary) TileRT: 타일 기반 초저지연 LLM 런타임 (오픈 vs 바이너리)

TileRT (from the TileLang team) serves LLMs for ultra-low latency — millisecond time-per-output-token, 1000+ tokens/s on a 1-trillion-param model — by treating the whole model as fine-grained tile-level tasks that a runtime overlaps and schedules across 8 GPUs. This note starts from scratch — what a "tile" even is — then walks what TileRT is, how it works, how to run it, and a code-walk of the repo (pinned to 242f7b3). Honesty up front: the shipped repo is a thin Python orchestration layer; the runtime and every kernel live in a closed binary, and every speed number is vendor-reported. TileRT(TileLang 팀)는 1조 파라미터 모델에서 밀리초 단위 TPOT, 1000+ 토큰/s를 내는 초저지연 LLM 런타임이다. 모델을 잘게 쪼갠 타일 단위 태스크로 보고 8-GPU에 겹쳐 스케줄한다. 이 노트는 "타일"이 뭔지부터 시작해 레포 코드(242f7b3 핀)까지 짚는다. 공개 레포는 얇은 Python 오케스트레이션 층일 뿐 런타임과 커널은 닫힌 바이너리이고, 속도 수치는 모두 벤더 발표다.

(b) thread → warp → block → grid(b) thread → warp → block → grid

A GPU is thousands of cores grouped into SMs (Streaming Multiprocessors). CUDA exposes a matching hierarchy: you launch a grid of blocks; each block runs on one SM; inside a block, threads run in lockstep groups of 32 — a warp (SIMT: all 32 execute the same instruction at once); each thread is one lane on a core. Blocks share fast SRAM; the warp is the unit the hardware actually schedules.GPU는 수천 코어를 SM(Streaming Multiprocessor) 단위로 묶은 칩이다. CUDA에서는 block들의 grid를 launch하고, 각 block은 SM 하나에서 돈다. block 안 스레드는 32개씩 같은 명령을 동시에 실행하는 warp(SIMT)으로 묶이고, thread 하나는 코어의 한 레인이다. block은 빠른 SRAM을 공유하며, 하드웨어가 실제로 스케줄하는 단위는 warp이다.

(c) A kernel's life & the "execution gap"(c) 커널의 생애와 "execution gap"

The host (CPU) launches the kernel — i.e. loads the op itself (its compiled code + grid/block config) onto the GPU and schedules it; this is separate from the data. Then each block loads its inputs HBM→SRAM/registers, computes (multiply-accumulate) in those fast levels, writes the result back to HBM, and the host usually syncs. A launch costs ~microseconds. When a model is a chain of ops, you pay launch + sync between every op — and at 1000 tokens/s each op is only microseconds, so those idle boundaries dominate. TileRT names this the "execution gap" and its whole design targets it (§3).호스트(CPU)는 커널을 launch해 연산(op) 자체(컴파일된 코드 + grid/block 설정)를 GPU에 올린다. 데이터와는 별개다. 이어서 각 블록이 입력을 로드(HBM→SRAM/레지스터)하고 연산(곱셈-누적)한 뒤 결과를 HBM에 쓰고, 호스트가 보통 동기화한다. launch에는 ~마이크로초가 든다. 모델이 op 체인이면 op마다 launch + sync 비용이 붙는데, 1000토큰/s에선 op 하나가 마이크로초 단위라 이 유휴 경계가 시간을 지배한다. TileRT는 이를 "execution gap"이라 부르고 설계 전체를 여기에 맞췄다(§3).

1What is a "tile"? (from scratch)"타일"이 뭔가? (기초부터)

Start with the one hardware fact everything follows from: a GPU has enormous compute but is starved for memory bandwidth. Reading a number from HBM (the GPU's main memory) is ~100× slower than doing arithmetic on it. So the whole game of fast GPU code is: read a chunk of data from HBM once, then reuse it many times out of the tiny fast on-chip memory (registers + shared memory / SRAM) before touching HBM again. GPU는 연산은 넘치는데 메모리 대역폭이 부족하다. HBM(GPU 주메모리)에서 숫자 하나를 읽는 데 산술보다 ~100배 오래 걸린다. 그래서 빠른 GPU 코드는 HBM에서 데이터 덩어리를 한 번 읽고, 작고 빠른 온칩 메모리(레지스터 + shared memory / SRAM)에서 여러 번 재사용한다.

A tile is that chunk. Take a matrix multiply C = A × B (the core of every LLM layer). Instead of computing all of C at once, you cut it into small rectangular tiles — say 128×128. To compute one output tile of C, you load the matching tiles of A and B into fast memory, multiply-accumulate, and only then write the tile out. Each GPU thread-block owns one output tile. Loading a tile costs one slow HBM read but feeds thousands of fast multiply-adds — that reuse is where the speed comes from. Attention (QKᵀ, softmax·V) tiles the same way. This "tiling" is the single most important trick in high-performance GPU kernels. 타일이 바로 그 덩어리다. 모든 LLM 레이어의 핵심인 행렬곱 C = A × B를 예로 들자. C를 128×128 같은 작은 타일로 쪼갠다. 출력 타일 하나를 계산하려면 A·B의 대응 타일을 빠른 메모리에 올려 곱셈-누적한 뒤 내보낸다. GPU 스레드블록 하나가 출력 타일 하나를 맡는다. 느린 HBM 읽기 한 번으로 빠른 곱셈-덧셈 수천 번을 돌리니, 이 재사용에서 속도가 나온다. 어텐션(QKᵀ, softmax·V)도 같은 식으로 타일링하며, 이것이 고성능 GPU 커널의 가장 중요한 기법이다.

Classic GPU tiling of a matmul. TileLang lets you write kernels at exactly this level of abstraction (tile shapes + the HBM↔SRAM↔register moves), and the compiler emits the CUDA. TileRT takes the idea up a level: it treats each tile of work as a schedulable task.행렬곱의 고전적 GPU 타일링. TileLang은 이 수준(타일 모양 + HBM↔SRAM↔레지스터 이동)으로 커널을 쓰게 하고, TileRT는 타일 작업 하나하나를 스케줄 가능한 태스크로 다룬다.

Two levels build on this: (1) TileLang — an open domain-specific language (built on Apache TVM) for writing GPU kernels at the tile level: you describe the tiles and the data movement, the compiler generates the kernel, instead of hand-writing threads. (2) TileRT — treats a whole LLM layer as many fine-grained tile-level tasks (a chunk of a matmul, an attention tile, a comm chunk) and its runtime dynamically schedules those tasks across 8 GPUs, overlapping compute with I/O and communication. So in TileRT "tile" is both the unit of computation and the unit of scheduling. 이 위에 두 층이 올라간다. (1) TileLang: GPU 커널을 타일 수준으로 쓰는 오픈 DSL(Apache TVM 기반)이다. 타일과 데이터 이동을 기술하면 컴파일러가 커널을 만든다. (2) TileRT: LLM 레이어를 잘게 쪼갠 타일 단위 태스크(행렬곱 조각·어텐션 타일·통신 조각)로 보고, 런타임이 이를 8-GPU에 동적으로 스케줄해 compute를 I/O·통신과 겹친다. TileRT에서 "타일"은 연산 단위이자 스케줄링 단위다.

TileLang — the open language (and why it's not the runtime)TileLang: 오픈 언어 (런타임이 아닌 이유)

Language vs runtime. TileLang is a kernel language + compiler: you write one kernel (a matmul, an attention) in Python tile primitives and it emits the GPU kernel. TileRT is a runtime: it takes a whole model's worth of kernels and schedules + overlaps them, persistently, across 8 GPUs. Language = how you author one kernel; runtime = how you run a model built from many. TileLang is fully open; the shipping TileRT kernels are the closed .so (§4–5).언어 vs 런타임. TileLang은 커널 언어 + 컴파일러다. 커널 하나(행렬곱·어텐션)를 Python 타일 프리미티브로 쓰면 GPU 커널을 만들어 준다. TileRT는 모델 전체의 커널을 8-GPU에 persistent하게 스케줄하고 겹치는 런타임이다. TileLang은 완전 공개이고, 배포되는 TileRT 커널은 닫힌 .so다(§4–5).

vs other kernel languages. Against raw CUDA/HIP the win is concrete: no hand-written thread indexing, shared-memory staging, double-buffering, or warp-level MMA intrinsics — alloc_shared / copy / gemm / Pipelined are tile-level primitives and the compiler does layout inference + software pipelining, so a FlashMLA-class kernel is ~80 lines of Python. What T.Pipelined(num_stages=3) does — software pipeliningT.Pipelined(num_stages=3)이 하는 일: 소프트웨어 파이프라이닝

Each K-loop iteration does two things: load the next A/B tiles (HBM→SRAM, slow) and compute (gemm, fast). Done naively they alternate, so compute waits on every load. T.Pipelined(num_stages=3) tells the compiler to run the loads ahead: it allocates 3 rotating SRAM buffers, prefetches a few iterations, then in steady state loads tile k+3 while computing tile k — so compute streams without stalling.K-루프의 각 반복은 다음 A/B 타일 로드(HBM→SRAM, 느림)와 연산(gemm, 빠름)으로 이뤄진다. 둘을 번갈아 하면 연산이 매번 로드를 기다린다. T.Pipelined(num_stages=3)은 SRAM 버퍼 3개를 돌려 쓰며 로드를 앞서 돌린다. 정상 상태에선 타일 k를 계산하는 동안 타일 k+3을 로드한다.

Software pipelining (schematic, ours). num_stages=3 keeps three loop iterations in flight, so the compute lane runs without waiting on HBM. It's the loop-level cousin of double-buffering / warp specialization.소프트웨어 파이프라이닝(개념도, 직접 그림). num_stages=3은 반복 3개를 동시에 진행시켜 compute가 HBM을 기다리지 않게 한다.

Pipelining vs warp specialization — the "cousins," and how they differ. Both hide load latency behind compute using multi-buffering, but along different axes of the same K-loop. Software pipelining (T.Pipelined) is a compiler loop transform: the same warps issue both the loads and the MMAs, just staggered in time — at steady state the async copy for iteration k+3 is already in flight while the tensor cores run iteration k (num_stages = how many iterations ahead = how many buffers). Warp specialization is a spatial split of the warps: dedicated producer warps do nothing but the loads, dedicated consumer warps do nothing but the MMAs, running concurrently and handing off through shared memory. So: pipelining staggers one set of warps across loop iterations; specialization gives different warps the load-vs-compute jobs. They're not either/or — modern kernels (Hopper GEMM, FlashAttention-3) use both together: specialized producer/consumer warps, each pipelined a few stages deep.Pipelining vs warp specialization. 둘 다 로드 지연을 숨기지만 축이 다르다. 소프트웨어 파이프라이닝(T.Pipelined)은 같은 warp이 로드와 MMA를 시간차를 두고 발행하는 루프 변환이다(반복 k의 MMA 중에 반복 k+3을 async copy, num_stages = 버퍼 개수). Warp specialization은 producer warp(로드)과 consumer warp(MMA)을 나눠 동시에 돌린다. Hopper GEMM·FlashAttention-3은 둘을 함께 쓴다.

Their fixes: TileRT의 진단에 따르면 병목은 커널 속도가 아니라 "다음 계산이 언제 시작될 수 있는가"다. 연산자/커널 경계의 유휴 틈, compute↔통신 정체, host↔device 동기화가 원인이다. 해법은 다음과 같다.

"Isn't the top row already tile-level?" The naive row above is op-level: each op (a matmul, an all-reduce) runs to completion — using tiles internally — before the next op can start, with a launch+sync gap between. The waste is that the next op waits for the whole previous op, so the compute engine sits idle during comm and vice-versa. TileRT's overlap is at tile granularity across ops: the moment op-A finishes tile 0, op-B can consume tile 0 while op-A still computes tiles 1, 2, 3."위 행도 이미 tile level 아니야?" naive 행은 op 단위다. 행렬곱·all-reduce가 내부적으로 타일을 쓰더라도 op이 통째로 끝나야 다음 op이 시작하고, 그 사이에 launch+sync 틈이 생긴다. 그래서 통신 중엔 연산 엔진이 놀고 반대도 마찬가지다. TileRT는 op을 가로질러 타일 단위로 겹친다. op-A가 타일 0을 끝내면 op-A가 타일 1, 2, 3을 계산하는 동안 op-B가 타일 0을 소비한다.

"isn't this what CUDA Graphs already fix?""이거 CUDA Graph가 이미 해결한 거 아냐?" Partly — CUDA Graphs fix the host-side half of the gap. You capture the whole kernel sequence once and replay it with a single launch, so you stop paying the CPU launch/API cost per op and the GPU can run queued kernels back-to-back without waiting on the CPU. That's why vLLM / TRT-LLM lean on graphs in decode. But a graph is still a DAG of separate kernels, so it does not remove: (1) the GPU-side per-kernel launch/teardown boundary, (2) the HBM round-trip between kernels (kernel A writes results to global memory, kernel B reads them back — no SRAM handoff), (3) the lack of cross-op tile overlap (op B still waits for op A's whole output unless you hand-split streams). TileRT's persistent single kernel targets exactly that remainder: one kernel = no kernel boundaries, no inter-op HBM traffic, tiles handed warp→warp in SRAM. So it's "beyond CUDA Graphs," not the same thing. (This megakernel argument — graphs aren't enough, fuse into one resident kernel — is a known direction; TileRT's is a closed, vendor-described instance.) 부분적으로만 맞다. CUDA Graph는 커널 시퀀스를 캡처해 launch 한 번으로 replay하므로 gap의 호스트 쪽(op마다 드는 CPU launch 비용)을 없앤다. vLLM/TRT-LLM이 decode에 graph를 쓰는 이유다. 그러나 graph도 분리된 커널들의 DAG라 (1) GPU 쪽 커널별 launch/teardown 경계, (2) 커널 사이 HBM 왕복, (3) op을 가로지르는 타일 겹침 부재는 그대로다. TileRT의 persistent 단일 커널은 이 나머지를 노린다. 커널이 하나라 커널 경계도, op 간 HBM 트래픽도 없고, 타일은 warp→warp로 SRAM에서 전달된다. (megakernel 방향은 알려진 흐름이고, TileRT는 그 닫힌 벤더 사례다.)

TileLang → TileScale → TileRT. TileLang은 오픈 타일 DSL, TileScale은 그 분산 확장("mega-device" 추상 + NVSHMEM 기반 타일 단위 통신), TileRT는 이 아이디어를 담은 닫힌 런타임이다. Why this can't chase throughput / concurrency왜 처리량/동시성은 못 노리나

The design is the latency↔throughput trade-off taken to the latency extreme, for structural reasons: (1) a persistent kernel occupies the whole GPU, so there's no free slot to batch other requests the way vLLM's continuous batching does; (2) num_devices=8 is hardwired, one backend per process — a single request owns all 8 GPUs, with no multi-tenant sharing or dynamic scaling; (3) the headline "1000+ TPS" is single-user (batch≈1), not 1000 users each at 1000 TPS. The same 8× B200 under a batching engine trades per-user latency for far higher aggregate throughput. It's a different corner of the design space, not a better engine. (Our reading, from the constraints above.)이 설계는 지연↔처리량 트레이드오프에서 지연 쪽 끝을 택했고, 이유는 구조적이다. (1) persistent 커널이 GPU 전체를 점유해 vLLM의 continuous batching처럼 다른 요청을 끼워 넣을 자리가 없다. (2) num_devices=8 하드코딩과 프로세스당 백엔드 하나 때문에 한 요청이 8 GPU를 통째로 쓰고, 멀티테넌트 공유나 동적 스케일링이 없다. (3) 헤드라인 "1000+ TPS"는 단일 사용자(batch≈1) 수치이지 1000명이 각각 1000 TPS를 받는다는 뜻이 아니다. 같은 8× B200을 batching 엔진에 쓰면 사용자별 지연은 늘지만 총 처리량은 훨씬 높다. 더 나은 엔진이 아니라 설계 공간의 다른 코너다. (위 제약에서 끌어낸 우리 해석.)

"occupies the GPU" = compute, not memory"GPU 점유"는 연산이지 메모리가 아니다Two separate resources. "The persistent kernel occupies the whole GPU" means it holds all the SMs (compute units) for its runtime — so there's no free compute to interleave another request (the throughput limit above). It does not mean it eats all of HBM: memory is occupied by weights + KV cache (data that stays resident regardless of which kernel runs — true of every engine, vLLM included). A running op uses HBM for its input/output tensors and on-chip registers + shared memory for its resident warps, but those free up when it finishes. So: compute (SM) monopoly ≠ memory monopoly.두 자원은 별개다. "persistent 커널이 GPU 전체를 점유"한다는 말은 도는 내내 모든 SM(연산 유닛)을 잡아 다른 요청에 줄 연산이 없다는 뜻이다. HBM을 다 쓴다는 뜻은 아니다. 메모리는 어느 엔진이든 상주하는 가중치 + KV 캐시가 차지하고, op이 쓰는 입출력 텐서와 온칩 레지스터+shared memory는 끝나면 반환된다. 연산(SM) 독점과 메모리 독점은 다르다.
