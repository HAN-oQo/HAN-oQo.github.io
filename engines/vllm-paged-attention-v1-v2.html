vLLM PagedAttention v1 vs v2 — what the two decode kernels do, and where they went vLLM PagedAttention v1 vs v2: 두 디코드 커널의 차이와 그 행방

vLLM's original decode attention had two kernels, paged_attention_v1 and paged_attention_v2. They compute the same thing, but v2 adds Flash-Decoding-style KV splitting for small-batch, long-context decode. This note explains the difference and why the CUDA versions are now removed while the shape survives on ROCm/AMD, with code pinned to real commits. vLLM 초기 디코드 어텐션에는 paged_attention_v1과 paged_attention_v2 두 커널이 있었다. 계산은 같지만 v2는 작은 배치·긴 컨텍스트를 위해 Flash-Decoding식 KV 쪼개기를 더한다. 이 글은 두 커널의 차이와, CUDA 버전은 제거됐는데 같은 구조가 ROCm/AMD에 남은 이유를 실제 커밋에 고정한 코드로 설명한다.

one-line summary한 줄 요약
  • v1 gives each (sequence, head) one thread block that sweeps the whole KV history in one pass. Fine when sequences × heads fill the GPU.
  • v2 splits each sequence's KV into 512-token partitions, computes partial softmax in parallel, then a reduction kernel merges them with log-sum-exp. This is Flash-Decoding, for small batch + long context.
  • vLLM picked v1 or v2 per step with a heuristic on sequence length and batch size.
  • At HEAD (2026-07-30) the CUDA v1/v2 kernels are removed (design doc marked "historical"). The split-and-reduce shape survives in the ROCm/AITER path (partition size 256); on CUDA, FlashAttention/FlashInfer/Triton do the job.
  • v1은 (시퀀스, 헤드)마다 thread block 하나를 배정하고, 그 블록이 KV 히스토리 전체를 한 번에 훑는다. 시퀀스 × 헤드가 GPU를 채울 만큼 많으면 충분하다.
  • v2는 KV 캐시를 512 토큰 파티션으로 쪼개 부분 softmax를 병렬로 계산하고, reduction 커널이 log-sum-exp로 합친다. 작은 배치 + 긴 컨텍스트용 Flash-Decoding이다.
  • vLLM은 시퀀스 길이와 배치 크기를 보는 휴리스틱으로 스텝마다 v1/v2를 골랐다.
  • HEAD(2026-07-30)에서는 CUDA v1/v2 커널이 제거됐고 설계 문서에도 "historical"이 붙었다. split-and-reduce 구조는 ROCm/AITER 경로(파티션 크기 256)에 남아 있고, CUDA에서는 FlashAttention/FlashInfer/Triton이 같은 일을 한다.

An A100 has ~108 SMs (Streaming Multiprocessors); occupancy is how many are busy. Too few thread blocks leave SMs idle, which is why v2 exists.A100에는 SM(Streaming Multiprocessor)이 ~108개 있고, occupancy는 그중 바쁜 비율이다. thread block이 적으면 SM이 놀고, v2는 이 문제 때문에 생겼다.

A thread block runs on one SM and shares on-chip memory; a warp is 32 threads in lockstep. In v1, one block handles one (sequence, head).thread block은 한 SM에서 온칩 메모리를 공유하며 도는 스레드 묶음이고, warp는 함께 움직이는 32스레드다. v1에서는 블록 하나가 (시퀀스, 헤드) 하나를 맡는다.

online softmax (log-sum-exp)online softmax (log-sum-exp)

Process scores in chunks with a running max and sum, so partial results combine exactly later. This makes splitting possible.running max와 running sum을 유지하며 점수를 조각으로 처리해, 부분 결과를 나중에 오차 없이 합친다. 쪼개기가 가능한 이유다.

partition / split-K파티션 / split-K

Cutting a sequence's KV into fixed chunks (vLLM: 512 tokens) so many blocks work on one sequence. "Split-K" = parallelizing over the reduction (KV-length) axis.KV를 고정 길이 조각(vLLM: 512 토큰)으로 잘라 여러 블록이 한 시퀀스를 나눠 맡는다. split-K는 reduction(KV 길이) 축 병렬화를 뜻한다.

A small second kernel that rescales and merges partition outputs via log-sum-exp. v2 has one; v1 doesn't.파티션 출력을 log-sum-exp로 재조정해 합치는 작은 두 번째 커널이다. v2에만 있다.

FlashAttention: tiled online-softmax attention. Flash-Decoding: its decode variant with KV-axis splitting, exactly what v2 does.FlashAttention은 타일 단위 online softmax 어텐션이고, Flash-Decoding은 여기에 KV 축 쪼개기를 더한 디코드 변형이다. v2가 하는 일과 같다.

A 60-second GPU primer60초 GPU 입문

A GPU is a room of ~108 identical workers (the SMs). You chop work into many small, independent task-cards (the thread blocks); each worker grabs a card, finishes it, and grabs another. Two rules follow, and they are the whole story of v1 vs v2: GPU는 똑같은 일꾼 ~108명이 있는 방이다(SM). 일을 작고 독립적인 task 카드(thread block)로 쪼개 놓으면, 일꾼이 카드를 하나씩 집어 처리하고 다음 카드를 집는다. 여기서 나오는 규칙 둘이 v1 vs v2의 전부다.

  • Too few cards → idle workers. 32 cards for 108 workers leaves 76 idle.카드가 적으면 일꾼이 논다. 108명에게 카드 32장이면 76명이 쉰다.
  • Each card should be small. One giant card stalls whoever grabs it while others wait; many small cards spread the load.카드는 작아야 한다. 거대한 카드 하나를 집은 일꾼이 붙잡혀 있는 동안 나머지는 기다린다. 작은 카드가 많아야 부하가 고르게 퍼진다.

1Background — PagedAttention and the decode-time kernel배경: PagedAttention과 디코드 시점 커널

PagedAttention (Kwon et al., 2023) stores each sequence's KV cache in fixed-size blocks scattered across GPU memory, like OS pages, which removes memory fragmentation. The cost: the attention kernel can't assume one contiguous array and must gather scattered blocks through a block table. PagedAttention(Kwon 외, 2023)은 시퀀스별 KV 캐시를 OS 페이지처럼 GPU 메모리 곳곳의 고정 크기 블록에 나눠 저장해 메모리 단편화를 없앤다. 대신 어텐션 커널은 KV가 연속 배열이라고 가정할 수 없고, block table로 흩어진 블록을 모아 읽어야 한다.

So vLLM wrote its own paged-KV CUDA kernel. In decode, each step has one query token per sequence attending to that sequence's whole KV cache. The kernel design doc describes the layout; its banner is the punchline of §5: 그래서 vLLM은 paged KV를 읽는 CUDA 커널을 직접 만들었다. decode에서는 스텝마다 시퀀스당 쿼리 토큰 1개가 그 시퀀스의 KV 캐시 전체에 어텐션한다. 커널 설계 문서가 이 구조를 설명하는데, 맨 위 배너가 §5의 결론이다.

"This is a historical document based on the original paper for vLLM. It no longer describes the code used in vLLM today."

— vLLM docs, docs/design/paged_attention.md (banner) · @ 8700f86

Both kernels share one structure: a grid (3-D array of thread blocks) shaped (num_heads, num_seqs, max_num_partitions), one block per head, sequence, and partition: 두 커널은 구조가 같다. grid(thread block의 3차원 배열) 모양은 (num_heads, num_seqs, max_num_partitions)이고, 블록 하나가 헤드·시퀀스·파티션 하나씩을 맡는다.

"In this kernel, the shape is (num_heads, num_seqs, max_num_partitions). Therefore, each thread block only handles the calculation for one head, one sequence, and one partition."

— vLLM kernel design doc, "Grid" · @ 8700f86

The third dimension, max_num_partitions, is the whole difference: always 1 in v1, possibly many in v2. The rest (reading query/key vecs, QK dot product, online softmax, value multiply) is shared code. 차이는 세 번째 차원 max_num_partitions 하나다. v1은 항상 1이고 v2는 여럿일 수 있다. query/key vec 읽기, QK 내적, online softmax, value 곱은 공유 코드다.

2v1 — one kernel, one pass over the whole contextv1: 커널 하나로 전체 컨텍스트를 한 번에

v1 launches the grid as (num_heads, num_seqs): one thread block per (sequence, head), max_num_partitions = 1. That block walks every KV block in the block table, computes query·key scores, runs online softmax over the whole context, multiplies by values, and writes the output. No second kernel. v1은 grid를 (num_heads, num_seqs)로 띄운다. (시퀀스, 헤드)당 thread block 하나, max_num_partitions = 1이다. 그 블록이 block table의 KV 블록을 모두 훑으며 query·key 점수, 전체 컨텍스트 online softmax, value 곱을 거쳐 출력을 쓴다. 두 번째 커널은 없다.

Fig 2 · v1: one thread block reads every KV block in order. Original diagram.그림 2 · v1: thread block 하나가 KV 블록을 차례로 읽는다. 직접 그림.

v1 works well when sequences × heads fill the GPU: 64 sequences × 32 heads = 2,048 thread blocks, far more than ~108 SMs. It is also cheaper: no partial-result memory traffic and no reduction launch. v1은 시퀀스 × 헤드가 GPU를 채울 때 잘 맞는다. 64 시퀀스 × 32 헤드 = 2,048 thread block이면 SM ~108개보다 훨씬 많다. 부분 결과용 메모리 트래픽도, reduction 실행도 없어 더 싸다.

where v1 falls downv1이 무너지는 곳 Small batch + long context. 1 sequence × 32 heads = 32 thread blocks on ~108 SMs leaves two-thirds of the GPU idle, while each block grinds sequentially through 32K tokens of KV. This is the case v2 was built for. 작은 배치 + 긴 컨텍스트다. 1 시퀀스 × 32 헤드 = 32 thread block을 SM ~108개에 띄우면 GPU의 3분의 2가 놀고, 블록마다 32K 토큰 KV를 순차로 처리한다. v2는 이 경우를 위해 만들어졌다.

3v2 — split the KV cache, then reduce (Flash-Decoding)v2: KV 캐시를 쪼갠 뒤 합친다 (Flash-Decoding)

v2 imports Flash-Decoding (Stanford, Oct 2023). Its diagnosis matches the v1 problem: decode has query length 1, so FlashAttention parallelizes only over batch × heads, and the GPU starves when that is below the SM count: v2는 Flash-Decoding(Stanford, 2023-10)을 가져왔다. 진단은 v1 문제와 같다. decode는 쿼리 길이가 1이라 FlashAttention이 배치 × 헤드로만 병렬화하고, 그 값이 SM 수보다 작으면 GPU가 논다.

"if the batch size is smaller than the number of streaming multiprocessors (SMs) on the GPU (108 for an A100), the operation will only use a small part of the GPU! … With batch size 1 and long sequences, FlashAttention will use less than 1% of the GPU."

— Flash-Decoding for long-context inference (Dao, Haziza, Massa, Sizov) · crfm.stanford.edu

The fix is a new parallel axis, KV length. Split each sequence's KV into partitions (PARTITION_SIZE = 512 tokens) and run two kernels: 해법은 KV 길이라는 새 병렬 축이다. KV를 파티션(PARTITION_SIZE = 512 토큰)으로 쪼개고 커널 두 개로 처리한다.

  1. Partition kernel. Grid (num_heads, num_seqs, num_partitions). Each block computes a partial softmax over its 512-token slice and writes the partial output (tmp_out), exp-sum (exp_sums), and max logit (max_logits). With 64 partitions, one sequence launches 32 heads × 64 = 2,048 blocks instead of 32.Partition 커널. grid는 (num_heads, num_seqs, num_partitions)이다. 블록마다 512 토큰 조각의 부분 softmax를 계산하고, 부분 출력(tmp_out), exp-sum(exp_sums), 최대 logit(max_logits)을 쓴다. 파티션이 64개면 시퀀스 하나가 32개가 아니라 32 헤드 × 64 = 2,048 블록을 띄운다.
  2. Reduction kernel. Merges all partitions of one (sequence, head). Each partial was normalized by its own max, so it rescales each by exp(local_max − global_max) weighted by exp_sum (log-sum-exp). The result equals attending over the whole context at once.Reduction 커널. 한 (시퀀스, 헤드)의 파티션을 모두 합친다. 부분 출력은 각자의 max로 정규화돼 있으므로, exp(local_max − global_max)와 exp_sum으로 가중해 재조정한다(log-sum-exp). 결과는 전체 컨텍스트에 한 번에 어텐션한 것과 같다.

Fig 3 · v1 vs v2 GPU occupancy for one long-context sequence. Schematic.그림 3 · 긴 컨텍스트 시퀀스 하나에서 v1과 v2의 GPU 점유. 개략도.

Why v2 needs a second "reduce" stepv2에 "reduce" 단계가 따로 필요한 이유

Softmax must sum to 1 over all tokens. Softmax each 512-token partition separately and each is normalized only against itself, so the outputs can't simply be added. Each partition therefore also reports its biggest score (max_logit) and sum of exp-scores (exp_sum), and the reduce step uses them to rescale every partition onto one common scale. The answer is exactly that of one big softmax (the log-sum-exp trick / online softmax). softmax는 모든 토큰에 걸쳐 합이 1이어야 한다. 512 토큰 파티션마다 따로 softmax하면 각자 자기 안에서만 정규화되므로 출력을 그냥 더할 수 없다. 그래서 파티션마다 최대 점수(max_logit)와 exp-점수 합(exp_sum)을 함께 보고하고, reduce 단계가 이를 써서 모든 파티션을 공통 척도로 재조정한다. 결과는 큰 softmax 하나와 정확히 같다(log-sum-exp 트릭, online softmax).

Fig 4 · v2 reduce kernel: rescale partitions by max and exp-sum, then merge. Original diagram.그림 4 · v2 reduce 커널: max와 exp-sum으로 파티션을 재조정해 합친다. 직접 그림.

v2 isn't freev2는 공짜가 아니다 v2 writes every partial output to global memory and reads it back in the reduction kernel: extra memory traffic and a second launch. When v1 already fills the GPU (big batch or short context), that is pure loss, so vLLM chooses per step (§4). v2는 파티션별 부분 출력을 global memory에 썼다가 reduction 커널에서 다시 읽는다. 메모리 트래픽과 커널 실행이 하나씩 늘어난다. v1이 이미 GPU를 채우는 경우(큰 배치, 짧은 컨텍스트)에는 순손해이므로 vLLM은 스텝마다 고른다(§4).

Worked example: one block table, 3 layers, read by v1 vs v2예제: block table 하나, 레이어 3개, v1과 v2의 읽는 방식

Sequence "A" has 12 tokens with a toy block_size = 4 (real vLLM: 16), so 3 storage blocks per layer. A block holds block_size tokens with all heads inside (heads are not separate blocks). The sequence has one block table mapping logical blocks to scattered physical slots, and every layer shares it while keeping its own KV values: 시퀀스 "A"는 12토큰이고 장난감 값 block_size = 4(실제 vLLM은 16)를 쓰면 레이어당 저장 block 3개가 된다. block 하나는 block_size 토큰을 모든 head와 함께 담는다(head별 block이 아니다). 논리 block을 흩어진 물리 슬롯에 매핑하는 block table은 시퀀스당 하나이고, 모든 레이어가 이를 공유하되 KV 값은 레이어마다 따로 둔다.

Fig 5 · Storage view: one shared block table maps 3 logical blocks to slots #7/#2/#5 in every layer. Original diagram.그림 5 · 저장 관점: 공유 block table 하나가 모든 레이어에서 논리 block 3개를 슬롯 #7/#2/#5에 매핑한다. 직접 그림.

The same 3 blocks (one layer), read two ways. v1: one worker gathers them in logical order (#7 → #2 → #5), sequentially. v2: blocks are grouped into partitions (here 8 tokens = 2 blocks; real: 512 tokens = 32 blocks), each run by its own worker in parallel, then reduced (Fig 4). Same storage, different grouping for compute: 같은 block 3개(한 레이어분)를 두 방식으로 읽는다. v1은 일꾼 하나가 논리 순서(#7 → #2 → #5)대로 차례로 읽는다. v2는 block을 partition(여기선 8토큰 = 2 block, 실제로는 512토큰 = 32 block)으로 묶어 파티션마다 일꾼을 붙여 병렬로 돌리고 reduce로 합친다(Fig 4). 저장은 같고 연산용 묶음만 다르다.

Fig 6 · Compute view of the same blocks: v1 sequential, v2 partitions + reduce. Original diagram.그림 6 · 같은 block의 연산 관점: v1은 순차, v2는 파티션 + reduce. 직접 그림.

4Choosing between them — the dispatch heuristic둘 중 고르기: dispatch 휴리스틱

v1 wins when the GPU is already full and v2 when it isn't, so vLLM decided per decode step: v1 unless the context is long and the batch is small (exact code in §6): GPU가 이미 차 있으면 v1이, 비어 있으면 v2가 유리하다. 그래서 vLLM은 디코드 스텝마다 판단했다. 컨텍스트가 길고 동시에 배치가 작을 때만 v2를 쓴다(정확한 코드는 §6).

_PARTITION_SIZE = 512
max_num_partitions = ceil(max_seq_len / _PARTITION_SIZE)

use_v1 = (max_seq_len <= 8192
          and (max_num_partitions == 1 or num_seqs * num_heads > 512))

The two ways v1 stays selected: v1이 선택되는 경우는 두 가지다.

Condition조건Meaning의미
max_num_partitions == 1The longest sequence fits in one 512-token partition. Nothing to split, so use v1.가장 긴 시퀀스가 512 토큰 파티션 하나에 들어간다. 쪼갤 것이 없으니 v1.
num_seqs * num_heads > 512Already >512 (sequence, head) blocks, enough to fill the SMs. v2's overhead isn't worth it, so use v1.(시퀀스, 헤드) 블록이 이미 512개를 넘어 SM을 채운다. v2 오버헤드가 손해이니 v1.
otherwise (long context, small batch)그 외 (긴 컨텍스트, 작은 배치)Use v2: few blocks, long KV each; splitting fills idle SMs.v2 사용. 블록은 적고 블록당 KV는 길어서, 쪼개면 노는 SM이 채워진다.

The max_seq_len <= 8192 guard is a hardware limit, per the code comment: "For context len > 8192, use V2 kernel to avoid shared memory shortage". v1 keeps the whole context's logits in one block's shared memory, which runs out past ~8K tokens. In short: v2 is the long-context, small-batch decode kernel; v1 is everything else. max_seq_len <= 8192 조건은 코드 주석대로 하드웨어 한계 때문이다("For context len > 8192, use V2 kernel to avoid shared memory shortage"). v1은 전체 컨텍스트의 logits를 블록 하나의 shared memory에 두는데, ~8K 토큰을 넘으면 공간이 모자란다. 정리하면 v2는 긴 컨텍스트·작은 배치용 디코드 커널이고, 나머지는 v1이다.

At HEAD (8700f86, 2026-07-30), the CUDA paged_attention_v1/v2 kernels are gone. csrc/attention/ holds only datatype headers: no paged_attention_v1.cu, no paged_attention_v2.cu. HEAD(8700f86, 2026-07-30)에서는 CUDA paged_attention_v1/v2 커널이 사라졌다. csrc/attention/에는 데이터타입 헤더만 있고 paged_attention_v1.cu도 paged_attention_v2.cu도 없다.

  1. May 2026: renamed out of csrc/attention/ ("migrate to torch stable ABI", PR #43717).
  2. 2026-07-02: deleted outright by PR #47361, titled "Delete PagedAttention", whose entire description is "It is time."
  3. The kernel design doc was stamped "historical … no longer describes the code used in vLLM today."
  1. 2026년 5월: csrc/attention/ 밖으로 rename됐다("torch stable ABI 이관", PR #43717).
  2. 2026-07-02: PR #47361이 완전히 삭제했다. 제목은 "Delete PagedAttention", 설명은 "It is time." 한 줄이다.
  3. 커널 설계 문서에는 "historical … no longer describes the code used in vLLM today." 표시가 붙었다.

Why: the whole attention layer got modular backends이유: 어텐션 계층이 모듈형 백엔드로

The "V1" engine rewrite replaced the built-in kernel with a backend registry: FlashAttention, FlashInfer, Triton, FlexAttention, or hardware-specific paths, chosen per platform and config (see vllm/v1/attention/backends/). These libraries already do Flash-Decoding-style KV splitting and are faster and better maintained, so the hand-written CUDA kernels were dropped. The v2 idea didn't die; it moved inside FlashAttention/FlashInfer. "V1" 엔진 재작성은 내장 커널을 백엔드 registry로 바꿨다. 어텐션은 플랫폼·설정에 따라 FlashAttention, FlashInfer, Triton, FlexAttention, 하드웨어별 경로 중 하나로 돈다(vllm/v1/attention/backends/). 이 라이브러리들은 이미 Flash-Decoding식 KV 쪼개기를 하고 더 빠르며 관리도 잘 되므로, 손으로 짠 CUDA 커널은 빠졌다. v2 아이디어는 죽지 않고 FlashAttention/FlashInfer 안으로 들어갔다.

Where it survives: the ROCm / AMD path살아남은 곳: ROCm / AMD 경로

Grepping HEAD for paged_attention_v1 finds essentially one place: the ROCm AITER backend. vllm/v1/attention/backends/rocm_aiter_fa.py still calls torch.ops.aiter.paged_attention_v1(...) with the same v2-shaped machinery: HEAD에서 paged_attention_v1을 grep하면 사실상 ROCm AITER 백엔드 한 곳만 나온다. vllm/v1/attention/backends/rocm_aiter_fa.py는 여전히 torch.ops.aiter.paged_attention_v1(...)을 호출하고, v2와 같은 구조를 쓴다.

  • Partition size _PARTITION_SIZE_ROCM = 256 on AMD (vs 512 on the old CUDA path), with tmp_output / exp_sums / max_logits scratch buffers sized by max_num_partitions.
  • csrc/rocm/attention.cu holds the paged_attention_ll4mi_QKV_* partition kernels and paged_attention_ll4mi_reduce_kernel, which is the v2 reduction.
  • The same 256-token partitioning appears in the Triton chunked_prefill_paged_decode path.
  • 파티션 크기는 AMD에서 _PARTITION_SIZE_ROCM = 256(옛 CUDA는 512)이고, max_num_partitions 크기의 tmp_output / exp_sums / max_logits 스크래치 버퍼를 둔다.
  • csrc/rocm/attention.cu에 paged_attention_ll4mi_QKV_* 파티션 커널과 paged_attention_ll4mi_reduce_kernel이 있다. 이 reduce 커널이 바로 v2 reduction이다.
  • 같은 256 토큰 파티셔닝이 Triton chunked_prefill_paged_decode 경로에도 있다.
so, the honest answer to "what's the difference?"그래서 "뭐가 다른가"의 정직한 답 The difference is parallelization strategy: v1 = one block sweeps the whole context; v2 = partitions across many blocks, then reduce. That is the timeless FlashAttention-vs-Flash-Decoding distinction. But a fresh vLLM clone has no CUDA kernels named v1 and v2: FlashAttention/FlashInfer/Triton replaced them, and the named kernels live on in ROCm/AITER (256-token partition instead of 512). 차이는 병렬화 전략이다. v1은 블록 하나가 전체 컨텍스트를 훑고, v2는 컨텍스트를 파티션으로 나눠 여러 블록에 맡긴 뒤 reduce한다. 이는 FlashAttention과 Flash-Decoding의 차이와 같아서 시대를 타지 않는다. 다만 지금 vLLM을 클론하면 v1/v2라는 CUDA 커널은 없다. CUDA에서는 FlashAttention/FlashInfer/Triton이 대체했고, 이름이 붙은 커널은 ROCm/AITER 경로(512 대신 256 토큰 파티션)에 남아 있다.

editor's note — our angle (not a vLLM claim)편집자 주: 우리 관점 (vLLM 주장 아님)
  1. Keep the v2 = Flash-Decoding insight. With long contexts and small batches (agents, long-doc RAG), decode attention must parallelize over KV length or it starves the GPU, whoever's kernel you run.
  2. On MI250/ROCm this is our code path, not history. AMD vLLM decode runs rocm_aiter_fa.py → csrc/rocm/attention.cu's ll4mi_QKV + ll4mi_reduce: v2 partition+reduce with a 256-token partition and an AITER dependency. Partition size and AITER are the knobs that govern our decode latency.
  3. Serving-stack churn. A paper-famous kernel ("PagedAttention") was deleted by a two-word PR ("It is time") once FlashAttention/FlashInfer absorbed its job. The paged-KV idea is permanent; the kernels were not.
  4. Boundary. The CUDA v1/v2 material is historical design pinned to pre-deletion commits, not a fresh benchmark.
  1. v2 = Flash-Decoding이라는 통찰은 남는다. 컨텍스트가 길고 배치가 작은 환경(에이전트, 긴 문서 RAG)에서는 어떤 커널이든 KV 길이 축으로 병렬화하지 않으면 GPU가 논다.
  2. MI250/ROCm에서는 역사가 아니라 우리 코드 경로다. AMD vLLM 디코드는 rocm_aiter_fa.py → csrc/rocm/attention.cu의 ll4mi_QKV + ll4mi_reduce, 즉 256 토큰 파티션과 AITER 의존성을 가진 v2 partition+reduce 구조로 돈다. 디코드 지연을 좌우하는 노브는 파티션 크기와 AITER다.
  3. 서빙 스택은 빠르게 바뀐다. 논문으로 유명한 커널("PagedAttention")이 FlashAttention/FlashInfer가 그 일을 흡수하자 두 단어짜리 PR("It is time")로 지워졌다. paged KV라는 아이디어는 남았지만 커널은 남지 않았다.
  4. 범위. CUDA v1/v2 내용은 삭제 전 커밋에 고정한 과거 설계이며, 새로 돌린 벤치마크가 아니다.
