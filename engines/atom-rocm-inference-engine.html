ATOM (AiTer Optimized Model) is AMD's LLM inference engine for Instinct GPUs, adapted from nano-vllm (a ~1.2k-line teaching reimplementation of vLLM), with every hot op routed to an AITER kernel. This note reads the code at a pinned commit and asks what ATOM gives you that vLLM-on-ROCm doesn't. ATOM(AiTer Optimized Model)은 AMD Instinct GPU용 LLM 추론 엔진이다. vLLM을 ~1.2천 줄로 다시 쓴 학습용 구현체 nano-vllm에서 출발했고, 무거운 연산은 전부 AITER 커널로 보낸다. 이 글은 커밋을 고정한 코드를 근거로, vLLM-on-ROCm 대신 ATOM을 쓰면 무엇이 다른지 살핀다.

one-line summary한 줄 요약
  • vLLM's architecture, re-implemented small: same continuous batching, paged KV cache, prefill-first scheduler, CUDA graphs and speculative decoding, in ~300 Python files, with compute-heavy calls on AITER kernels (ASM / Composable Kernel / Triton).
  • Dual identity: a standalone OpenAI-compatible server and a plugin backend that installs into vLLM and SGLang via their entry-point hooks.
  • The plugin shape was not AMD's first choice. vLLM's maintainers rejected the in-tree proposal.
  • The only apple-to-apple comparison AMD published is +2.8% to +6.9% over vLLM, not the "2–3×" its README once claimed and then deleted.
  • 작게 다시 구현한 vLLM 아키텍처다. continuous batching, paged KV cache, prefill-first scheduler, CUDA graph, speculative decoding을 Python 파일 ~300개로 구현했고, 무거운 연산은 AITER 커널(ASM / Composable Kernel / Triton)이 맡는다.
  • 정체성이 둘이다. 독립 OpenAI 호환 서버이면서, vLLM·SGLang의 entry-point 훅으로 들어가는 플러그인 백엔드이기도 하다.
  • 플러그인은 AMD의 1지망이 아니었다. vLLM 메인테이너들이 in-tree 제안을 거절했다.
  • AMD가 공개한 유일한 동일 조건 비교는 vLLM 대비 +2.8%~+6.9%다. README가 한때 주장했다가 지운 "2~3배"가 아니다.

Why AMD wanted its own engine at allAMD는 왜 자기 엔진을 원했나

An internal positioning draft in the repo (atom_overview_draft.md, "Draft – Internal Review Only") states the motive and names nano-vllm as the model: 레포에 들어 있는 내부 포지셔닝 초안(atom_overview_draft.md, "Draft – Internal Review Only")이 동기를 밝히고 nano-vllm을 본보기로 꼽는다.

"ATOM's embrace the same minimalist mindset of nano-vllm 'minimalist' architecture allows it to evolve at the speed of AMD silicon. By stripping away layers of abstraction found in generic frameworks, ATOM connects the model directly to the metal via the AITER kernel library."

— atom_overview_draft.md §Performance Momentum · atom_overview_draft.md#L25 @ cd161f1 (sic — the sentence is ungrammatical in the original)(원문 그대로 — 문장이 비문이다)

The same draft sets out ATOM's dual role, the key to the whole project: 같은 초안이 ATOM의 이중 역할을 정리한다. 이 프로젝트를 이해하는 열쇠다.

"Standalone Optimization Platform: It serves as a 'Proving Ground' for rapid iteration, allowing AMD to develop and validate internal system-level optimizations, compiler-driven graph enhancements, and kernel acceleration.
Integrated Plugin Backend: It integrates as a high-performance backend for popular frameworks like vLLM and SGLang, ensuring that the broader AI community can access AMD-specific optimizations without changing their existing workflows."

— atom_overview_draft.md §A Dual-Purpose Architecture · atom_overview_draft.md#L15-L17 @ cd161f1

This answers "vLLM already runs on ROCm, why a second engine?" ATOM is not mainly competing with vLLM for users. It is a lab where AMD lands new kernels, fused ops and Day-0 models on its own schedule, then exposes them through vLLM as a plugin. The standalone server proves an optimization; the plugin delivers it. "vLLM이 이미 ROCm에서 도는데 엔진을 왜 또 만드나"에 대한 답이 여기 있다. ATOM은 사용자를 두고 vLLM과 경쟁하려는 게 주 목적이 아니다. AMD가 새 커널·fused op·Day-0 모델을 자기 일정대로 얹는 실험실이고, 그 결과를 플러그인으로 vLLM 안에 내보낸다. 독립 서버는 최적화를 증명하는 자리, 플러그인은 그것을 쓰는 통로다.

read this as positioning, not measurement측정이 아니라 포지셔닝으로 읽을 것 atom_overview_draft.md is an unreleased marketing draft committed to a public repo: good evidence of intent, poor evidence of performance. Its throughput claims (e.g. "GPT-OSS (FP4): Throughput surged by 40.8% in 1K/1K tasks") have no named baseline and are treated as unverified here. atom_overview_draft.md는 공개 레포에 커밋된 미공개 마케팅 초안이다. 의도의 근거로는 좋지만 성능의 근거로는 약하다. 처리량 수치(예: "GPT-OSS (FP4): Throughput surged by 40.8% in 1K/1K tasks")는 기준선이 없어 이 글에서는 미검증으로 다룬다.

These are not one process. ATOM is a process tree: API server and tokenizer in the parent, one EngineCore process per data-parallel rank, one ModelRunner subprocess (one GPU) per tensor-parallel rank. They talk over ZeroMQ with pickled payloads. 이들은 한 프로세스가 아니다. ATOM은 프로세스 트리다. API 서버와 tokenizer는 부모에, data-parallel rank마다 EngineCore 프로세스가, tensor-parallel rank마다 GPU 하나를 쥔 ModelRunner 서브프로세스가 있다. 서로 ZeroMQ로 pickle 페이로드를 주고받는다.

Two details worth pausing on잠깐 멈춰 볼 만한 두 지점

Preemption is a full rollback, not a pause. When decode cannot get a block, the scheduler evicts the last running sequence: frees all its blocks, strips the speculative placeholder and rejected tokens postprocess() appended, zeroes the speculation state, and puts it at the front of the waiting queue to re-prefill from scratch. There is no swap-to-host path. preemption은 일시정지가 아니라 완전 롤백이다. decode가 블록을 못 얻으면 스케줄러는 마지막 running 시퀀스를 내보낸다. 블록을 모두 반납하고, postprocess()가 붙인 speculative placeholder와 rejected 토큰을 떼고, speculation 상태를 0으로 돌린 뒤, 대기 큐 맨 앞에 넣어 처음부터 다시 prefill한다. host swap 경로는 없다.
