Diffusion LLMs in vLLM — how they differ, forward count, KV cache, code flow vLLM의 Diffusion LLM: 트랜스포머와 뭐가 다른가, forward 횟수, KV cache, 코드 흐름

A diffusion LLM starts from a fully-masked answer and un-masks many tokens in parallel over a few denoising steps, on the same Transformer backbone with bidirectional attention + a masked-denoising objective. This note covers forward counts, why the KV cache breaks, and how vLLM's DiffusionGemma handles it, with code permalinks. Diffusion LLM은 완전히 마스킹된 답에서 시작해 몇 번의 denoising 스텝 동안 여러 토큰을 병렬로 un-mask한다. 백본은 같은 트랜스포머이고 양방향(bidirectional) 어텐션과 마스크 denoising 목적함수만 다르다. 이 노트는 forward 횟수, KV cache가 깨지는 이유, vLLM DiffusionGemma의 처리 방식을 코드 permalink와 함께 정리한다.

one-line summary한 줄 요약
  • Same Transformer, two changes: bidirectional attention + masked-denoising objective (Dream is even initialized from AR Qwen).
  • Generation = T denoising steps over the whole sequence (T ≪N for speed, up to N for AR-like quality), not N sequential steps.
  • Bidirectional attention breaks the standard KV cache, so systems move to block diffusion: finalize a block, cache its KV like a causal prefix.
  • vLLM's one native dLLM, DiffusionGemma, reuses the speculative-decoding path (canvas = draft tokens) and runs a causal encoder that writes KV and a bidirectional decoder that only reads KV.
  • 같은 트랜스포머에 양방향 어텐션과 마스크 denoising 목적함수만 바꿨다(Dream은 AR Qwen에서 초기화한다).
  • 생성은 N번 순차가 아니라 시퀀스 전체에 대한 T번의 denoising 스텝이다. 빠르게는 T≪N, AR급 품질은 T=N까지 간다.
  • 양방향 어텐션이 표준 KV cache를 깨뜨리므로 시스템들은 block diffusion으로 간다. 확정한 블록의 KV를 causal prefix처럼 캐시한다.
  • vLLM의 유일한 네이티브 dLLM인 DiffusionGemma는 speculative-decoding 경로를 재사용하고(canvas=draft 토큰), KV를 쓰는 causal encoder와 KV를 읽기만 하는 bidirectional decoder 두 모드로 돈다.

1What a diffusion LLM is — and is the architecture the same?Diffusion LLM이란? 아키텍처는 동일한가

An AR Transformer factorizes text left-to-right: each token conditions on all previous tokens, decoded one at a time. A masked diffusion LLM defines a forward process that progressively masks tokens, and learns the reverse: start from a fully-masked response and iteratively un-mask, predicting all masked positions simultaneously at each step [LLaDA] [Dream]. AR 트랜스포머는 이전 토큰들을 조건으로 한 번에 한 토큰씩 좌→우로 디코딩한다. 마스크 diffusion LLM은 토큰을 점점 마스킹하는 forward 과정의 역과정을 학습한다. 완전 마스킹된 답에서 시작해 스텝마다 마스킹된 모든 위치를 동시에 예측하며 반복적으로 un-mask한다 [LLaDA] [Dream].

The architecture is the same Transformer — with two changes아키텍처는 같은 트랜스포머이고 두 가지만 다르다

This is the crux. dLLMs are not a new architecture; they're a Transformer with (a) the causal mask removed and (b) a different training objective: dLLM은 새 아키텍처가 아니다. (a) causal mask를 없애고 (b) 학습 목적함수를 바꾼 트랜스포머다.

"LLaDA does not use a causal mask, as its formulation allows it to see the entire input for predictions."

— LLaDA §2.2 · arXiv:2502.09992

The strongest evidence the backbone is shared: Dream 7B is initialized from Qwen2.5 AR weights — the team found AR-initialization "more effective than training the diffusion language model from scratch" [Dream blog]. You can literally take an autoregressive model and adapt it into a diffusion one (also shown by DiffuLLaMA, ICLR 2025 [repo]). The upside of bidirectionality: dLLMs can "consider multiple conditioning directions," which breaks the AR "reversal curse" [LLaDA §3.1]. The downside: removing the causal mask is exactly what breaks KV caching (§3). 가장 강한 증거는 Dream 7B가 Qwen2.5 AR 가중치에서 초기화된다는 점이다. 팀은 AR 초기화가 처음부터 학습하는 것보다 효과적이었다고 밝혔다 [Dream blog]. DiffuLLaMA(ICLR 2025)도 AR 모델을 diffusion으로 바꿀 수 있음을 보였다 [repo]. 양방향성 덕에 dLLM은 AR의 "reversal curse"를 깬다 [LLaDA §3.1]. 대신 causal mask를 없앤 탓에 KV caching이 깨진다(§3).

Diffusion decouples token count from step count. Fewer steps → more tokens committed per step → faster but lower quality, because parallel un-masking assumes the tokens are conditionally independent (they aren't). diffusion은 토큰 수와 스텝 수를 분리한다. 스텝을 줄이면 스텝당 확정 토큰이 늘어 빨라지지만 품질이 떨어진다. 병렬 un-mask는 토큰끼리 조건부 독립이라고 가정하는데 실제로는 그렇지 않기 때문이다.

"LLaDA achieves optimal performance when the number of sampling steps equals the response length … reducing the number of sampling steps leads to a decrease in performance."

— LLaDA repo FAQ · github.com/ML-GSAI/LLaDA

Two fixes:해법은 두 가지다.

  • Confidence-aware parallel decoding: only commit tokens above a confidence threshold, so the step count adapts to difficulty. Fast-dLLM reports "up to 27.6× throughput improvement with minimal accuracy loss" [Fast-dLLM].
  • Block / semi-AR diffusion: generate a block of L tokens with K steps, finalize it, move on, interpolating between AR (block=1) and full diffusion (block=full length) [Block Diffusion / BD3-LM].
  • confidence-aware 병렬 디코딩: 확신 임계값을 넘는 토큰만 확정해 스텝 수가 난이도에 맞춰진다. Fast-dLLM은 정확도를 거의 잃지 않고 처리량을 최대 27.6× 높였다 [Fast-dLLM].
  • block / semi-AR diffusion: L개 토큰 블록을 K 스텝으로 확정하고 다음으로 넘어간다. AR(블록=1)과 full diffusion(블록=전체)의 중간이다 [Block Diffusion / BD3-LM].

So a practical forward count is (N / L blocks) × (K steps per block). 그래서 실제 forward 수는 (N / L 블록) × (블록당 K 스텝)이다.

3KV cache — why it's hard, and how it's doneKV cache: 왜 어렵고 어떻게 하나

AR KV caching is exact because the causal mask guarantees a token's K/V never change once computed. dLLMs break that on two counts: AR에서는 causal mask 덕에 한 번 계산한 K/V가 변하지 않으므로 KV caching이 정확하다. dLLM은 이 전제를 두 가지 면에서 깬다.

  1. Bidirectional attention → no causal prefix to cache. "Traditional ARM acceleration techniques, such as Key-Value caching, are incompatible with dLLMs due to their bidirectional attention mechanism" [dLLM-Cache].양방향 어텐션 → 캐시할 causal prefix가 없다. KV caching 같은 기존 AR 가속 기법은 양방향 어텐션 때문에 dLLM과 맞지 않는다 [dLLM-Cache].
  2. Tokens at every position change across steps → cached K/V go stale. Caching has to become approximate or delayed [dKV-Cache].스텝마다 모든 위치의 토큰이 바뀐다 → 캐시된 K/V가 낡는다. 캐싱은 근사나 지연 방식이 될 수밖에 없다 [dKV-Cache].

Two families of fix: 해법은 두 갈래로 나뉜다.

Approach방식Exact?정확?Idea아이디어
Block diffusion (BD3-LM)exact (between blocks)정확 (블록 간)finalized blocks form a causal prefix → cache their KV exactly, like AR. [BD3-LM]확정된 블록이 causal prefix가 되므로 그 KV를 AR처럼 정확히 캐시한다. [BD3-LM]
Fast-dLLM / dLLM-Cache / dKV-Cacheapproximate근사K/V drift slowly between adjacent steps → reuse them anyway ("adjacent steps … highly similar" [Fast-dLLM]).인접 스텝 사이 K/V는 천천히 변하므로 그대로 재사용한다("인접 스텝 … 매우 유사" [Fast-dLLM]).

Production systems converge on block diffusion because a normal prefix KV cache (and vLLM's automatic prefix caching) works again. vLLM's DiffusionGemma takes this route (§4). 프로덕션 시스템이 block diffusion으로 모이는 이유는 일반 prefix KV cache(와 vLLM의 automatic prefix caching)가 다시 작동하기 때문이다. vLLM의 DiffusionGemma도 이 길을 택했다(§4).

4What vLLM ships — DiffusionGemma, and how it's optimizedvLLM이 지원하는 것: DiffusionGemma와 최적화

Mainline vLLM natively supports exactly one diffusion model today: DiffusionGemma (Google's dLLM on the Gemma backbone), landed in PR #45163 (merged 2026-06-12) and announced as "the first dLLM natively supported in vLLM" [PR #45163]. LLaDA / Dream are not in mainline (there's a separate, still-mock dllm-plugin + RFC #36155). The design is deliberately minimal — it reuses existing machinery rather than adding diffusion-specific core types: 메인라인 vLLM이 네이티브로 지원하는 diffusion 모델은 DiffusionGemma(Gemma 백본의 Google dLLM) 하나뿐이다. PR #45163(2026-06-12 병합)으로 들어왔고 "vLLM 최초의 네이티브 dLLM"으로 발표됐다 [PR #45163]. LLaDA/Dream은 메인라인에 없고, 아직 mock 단계인 dllm-plugin + RFC #36155가 따로 있다. 설계는 diffusion 전용 코어 타입 없이 기존 장치를 재사용한다.

① Reuse the spec-decode path① spec-decode 경로 재사용

The denoising "canvas" is delivered through vLLM's speculative-decoding draft-token path — draft tokens = the canvas. No new request type; metrics are reinterpreted as denoising-step metrics.denoising "canvas"를 speculative-decoding draft-token 경로로 넘긴다(draft 토큰 = canvas). 새 요청 타입은 없고 지표는 denoising-step 지표로 읽는다.

② Block-based → prefix caching works② 블록 기반 → prefix caching 작동

It's block diffusion (canvas = a block), so "vLLM's automatic prefix caching works out of the box" [blog].block diffusion이므로(canvas=블록) automatic prefix caching이 그대로 작동한다 [블로그].

③ Dual-mode backbone (one set of weights)③ 이중 모드 백본(가중치 한 벌)

Same Gemma layers run as a causal encoder that writes KV (prefill/commit) or a bidirectional decoder that reads KV (denoise) — a per-request causal flag (dynamic_causal) lets one batch mix both.같은 Gemma 레이어가 KV를 쓰는 causal encoder(prefill/commit)나 KV를 읽는 bidirectional decoder(denoise)로 돈다. 요청별 causal 플래그(dynamic_causal)로 한 배치에 둘을 섞는다.

④ Entropy-bound sampler④ entropy-bound 샘플러

A custom sampler accepts confident positions and re-noises the rest each step; a block "commits" when it converges or hits max_denoising_steps (48).커스텀 샘플러가 스텝마다 확신 위치를 수락하고 나머지를 re-noise한다. 수렴하거나 max_denoising_steps(48)에 닿으면 블록을 "commit"한다.

The per-request causal flag brings constraints:요청별 causal 플래그 때문에 제약이 따른다.

  • FlashAttention is auto-upgraded to FA4 (or use TRITON_ATTN); FlashInfer is rejected.
  • Structured outputs are rejected (a parallel canvas isn't a left-to-right FSM).
  • max_num_seqs is capped to 8 (the fp32 [seqs, canvas, vocab] logits are memory-bound).
  • FlashAttention은 FA4로 자동 업그레이드된다(또는 TRITON_ATTN). FlashInfer는 거부한다.
  • structured output도 거부한다. 병렬 canvas는 좌→우 FSM이 아니기 때문이다.
  • max_num_seqs는 8로 제한한다. fp32 [seqs, canvas, vocab] logits가 메모리를 많이 먹는다.

Forwards for N tokens, precisely: block-wise. Per block of canvas_length (256): ~1 causal prefill share + up to max_denoising_steps (48) bidirectional denoise forwards (early-stop on convergence) + 1 commit forward. So N tokens ≈ ceil(N / 256) blocks; each denoise forward refines the entire 256-token canvas in parallel. N토큰당 forward: canvas_length(256) 블록마다 causal prefill ~1회, bidirectional denoise forward 최대 max_denoising_steps(48)회(수렴하면 조기 종료), commit 1회가 든다. N토큰은 ≈ ceil(N / 256) 블록이고, denoise forward 한 번이 256토큰 canvas 전체를 병렬로 다듬는다.

6Status & how to run it구현 상태 & 실행법

Mainline: DiffusionGemma only, merged & not behind a feature flag (PR #45163, 2026-06-12; follow-ups #45468, #45643). Diffusion mode is implicit — triggered by the model's canvas_length config, there is no --diffusion flag. Plugin/RFC: general dLLMs (LLaDA 2.0) live in the out-of-tree dllm-plugin (RFC #36155), which currently ships a mock model and needs a vLLM fork — not production-ready. LLaDA/Dream are not in mainline. 메인라인: DiffusionGemma만 병합됐고 feature flag 없이 쓸 수 있다(PR #45163, 2026-06-12, 후속 #45468, #45643). --diffusion 플래그는 없고, 모델 config의 canvas_length가 diffusion 모드를 켠다. 플러그인/RFC: 일반 dLLM(LLaDA 2.0)은 out-of-tree dllm-plugin(RFC #36155)에 있다. 지금은 mock 모델이고 vLLM fork가 필요해 프로덕션에 쓸 수 없다. LLaDA/Dream은 메인라인에 없다.

# DiffusionGemma (mainline) — no --diffusion flag; canvas_length in the model config triggers it
vllm serve google/diffusiongemma-26B-A4B-it \
    --max-num-seqs 4 --attention-backend TRITON_ATTN \
    --diffusion-config '{"canvas_length": 256}' \
    --hf-overrides '{"diffusion_sampler":"entropy_bound","diffusion_entropy_bound":0.1}'
# constraints: max_num_seqs ≤ 8 · FA4 or TRITON_ATTN (FlashInfer rejected) ·
#              structured outputs rejected · entropy-bound sampler config required

Other systems for context: SGLang added day-0 LLaDA 2.0 (block-diffusion) support, citing "the inefficient utilization of the KV Cache" of full bidirectional diffusion as the reason the field is moving to block diffusion [LMSYS/SGLang blog]. Commercial dLLMs: Mercury (Inception, claims >1000 tok/s) and Gemini Diffusion (DiffusionGemma's closed sibling). SGLang은 LLaDA 2.0(block-diffusion)을 day-0로 지원하면서, full bidirectional diffusion의 KV Cache 비효율을 업계가 block diffusion으로 옮겨 가는 이유로 꼽았다 [LMSYS/SGLang 블로그]. 상용 dLLM으로는 Mercury(Inception, >1000 tok/s 주장)와 Gemini Diffusion(DiffusionGemma의 비공개 형제)이 있다.
