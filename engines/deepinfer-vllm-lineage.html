DeepInfer — what DeepSeek kept from vLLM, and why every kernel is a DSLDeepInfer: DeepSeek 이 vLLM 에서 남긴 것과 커널이 전부 DSL 인 이유

DeepSeek open-sourced the engine behind its production service. It is not a vLLM fork, but 23 files still carry # Derived from vLLM, and where they sit tells the story. The control plane is vLLM's; the execution plane was rebuilt with zero lines of hand-written CUDA. Glossary용어 정리

Hard fork하드 포크

Code taken once and developed independently, with no intent to merge back or track upstream.코드를 한 번 떼어 온 뒤 upstream 을 따라가지 않고 독립적으로 발전시키는 포크다.

Control vs execution plane제어면 vs 실행면

Control decides what runs (batching, scheduling, request lifecycle). Execution does the arithmetic (kernels, model layers, memory movement).제어면은 배칭·스케줄링·요청 수명처럼 무엇을 돌릴지 정한다. 실행면은 커널·모델 레이어·메모리 이동 같은 실제 연산을 맡는다.

TileLang

A tile-level GPU kernel DSL: you write dataflow in Python, and the compiler handles thread binding, layout and pipelining, emitting CUDA, HIP or other backends.파이썬으로 데이터플로를 쓰면 컴파일러가 스레드 바인딩·레이아웃·파이프라이닝을 맡아 CUDA·HIP 등으로 내보내는 타일 단위 GPU 커널 DSL 이다.

vLLM v0 vs v1vLLM v0 vs v1

vLLM's original architecture (llm_engine + worker/model_runner + cache_engine) versus the later v1 rewrite. DeepInfer's skeleton is v0.vLLM 초기 아키텍처(llm_engine + worker/model_runner + cache_engine)와 이후 v1 재작성. DeepInfer 골격은 v0 다.

SM100 / Ascend 950

NVIDIA's Blackwell-class compute capability and Huawei's NPU generation: two different ISAs served from one source tree.NVIDIA Blackwell 급 compute capability 와 Huawei NPU 세대. DeepInfer 가 소스 트리 하나로 지원해야 하는 서로 다른 두 ISA 다.

Memory-bound kernel메모리 바운드 커널

A kernel whose runtime is set by data movement, not arithmetic (gathers, index math, normalisation). Vendor BLAS libraries do not cover these.실행 시간을 연산이 아니라 데이터 이동이 정하는 커널(gather, 인덱스 연산, 정규화). 벤더 BLAS 라이브러리가 다루지 않는다.

4Zero CUDA, and a C++ schedulerCUDA 0줄, 그리고 C++ 스케줄러

The most surprising fact in the repo: there is not one .cu or .cuh file outside the vendor submodules. A company famous for its kernel engineers ships zero hand-written CUDA in its inference engine.이 레포에서 가장 놀라운 사실은 vendor 서브모듈 밖에 .cu 나 .cuh 파일이 하나도 없다는 점이다. 커널 엔지니어로 이름난 회사가 추론 엔진에 손으로 쓴 CUDA 를 넣지 않았다.

There is C++ (33 files, 5,908 LOC in csrc/), but look at what it does:C++ 는 csrc/ 에 33개 파일 5,908 LOC 가 있다. 하는 일은 이렇다.

csrc/engine/
  scheduler.hpp          1,329 LOC   ← the batch scheduler
  block_manager.hpp                  ← KV block allocation
  flops_estimator.hpp                ← cost model for scheduling

Not a kernel in sight. This is the CPU-side hot path: the per-step work between forward passes that, at high batch rates, keeps the GPU waiting. The README's "asynchronous scheduling (zero-overhead batch scheduler)" is this code.커널은 없다. 전부 forward pass 사이에 도는 CPU 쪽 핫패스이고, 배치율이 높아지면 GPU 를 기다리게 만드는 병목이 된다. README 의 "asynchronous scheduling (zero-overhead batch scheduler)" 가 이 코드다.

The inversion뒤집힌 구도 Conventional engines write kernels in C++/CUDA and the scheduler in Python. DeepInfer does the opposite: kernels go up into a DSL, the scheduler comes down into C++. Each move targets the constraint that actually binds in that layer: portability for kernels, per-step latency for scheduling. It is a coherent position, not an accident.보통 엔진은 커널을 C++/CUDA 로, 스케줄러를 파이썬으로 쓴다. DeepInfer 는 반대로 커널을 DSL 로 올리고 스케줄러를 C++ 로 내렸다. 커널에는 이식성, 스케줄링에는 스텝당 지연이라는, 각 계층에서 실제로 걸리는 제약을 겨냥한 일관된 선택이다.

5Why TileLang — the Ascend answer왜 TileLang 인가: Ascend 라는 답

Why TileLang? The directory layout answers before you read a line of kernel code.왜 TileLang 일까. 커널 코드를 읽기 전에 디렉터리 구조가 답한다.

Figure 3 · tilelang_ops layout. Each of the 29 ops keeps its public entry point, two DSL backends, a torch reference and a differential test in one module.그림 3 · tilelang_ops 구조. 연산 29개마다 공개 진입점, DSL 백엔드 둘, torch 레퍼런스, 대조 테스트를 한 모듈에 둔다.

The top-level files are the interface, not just tests최상위 파일은 테스트가 아니라 인터페이스다 The 29 top-level *.py all import pytest, so they look like a test suite. They are more: each is the backend-neutral public entry point that production code calls. layers/sampler_utils.py does from ...tilelang_ops.fused_sample import fused_sample; layers/vocab_parallel_embedding.py imports gather the same way. Breaking down those 9,668 LOC by role:최상위 *.py 29개는 모두 pytest 를 import 해서 테스트처럼 보이지만, 실제로는 프로덕션 코드가 호출하는 백엔드 중립 공개 진입점이다. layers/sampler_utils.py 가 from ...tilelang_ops.fused_sample import fused_sample 를 하고, layers/vocab_parallel_embedding.py 도 같은 식으로 gather 를 가져온다. 9,668 LOC 를 최상위 함수 역할별로 나누면 다음과 같다. 
production interface (public entry points)   4,244 LOC   44%
torch reference implementations (*_ref)      1,609 LOC   17%
differential tests (test_*)                  2,913 LOC   30%
imports, constants, module level               902 LOC    9%
So verification is 4,522 LOC against 12,386 LOC of kernels, roughly 0.37:1, not the 1:1 a naive file-level count suggests. Still a serious investment, for the same reason: with two backends you cannot check correctness by inspection, you have to diff against a reference.검증 코드는 커널 12,386 LOC 대비 4,522 LOC, 약 0.37:1 이다. 파일 단위로 세면 1:1 처럼 보이지만 아니다. 그래도 큰 투자다. 백엔드가 둘이면 눈으로는 정합성을 확인할 수 없어 레퍼런스와 대조해야 한다.

And the platform object that drives it:이를 구동하는 플랫폼 객체는 다음과 같다.

So: DeepSeek must run the same model on NVIDIA SM100 and Huawei Ascend 950. Hand-writing the kernel set twice, in CUDA C++ and in AscendC, produces two unrelated codebases that drift apart immediately. TileLang gives one language, one set of tiling concepts, one test harness, two targets. Under export controls that is closer to a survival decision than a performance one.정리하면 DeepSeek 은 같은 모델을 NVIDIA SM100 과 Huawei Ascend 950 에서 돌려야 한다. 커널 세트를 CUDA C++ 와 AscendC 로 따로 쓰면 곧바로 어긋나는 코드베이스 두 벌이 생긴다. TileLang 은 언어, 타일링 개념, 테스트 하네스를 하나로 두고 타깃만 둘로 나눈다. 수출 규제 아래에서 이건 성능보다 생존에 가까운 결정이다.

Portability is not free이식성은 공짜가 아니다 asc/ is 49% longer than cuda/ (7,418 vs 4,968 LOC) and reaches for Ascend-specific primitives (simd, get_num_vec_cores). This is not write-once-run-anywhere. It is same language, same concepts, same tests, still hand-written per target. The win is shared tooling and reasoning, not shared source; the verification bill is quantified in the callout above.asc/ 는 cuda/ 보다 49% 길고(7,418 대 4,968 LOC), simd, get_num_vec_cores 같은 Ascend 전용 프리미티브를 쓴다. 한 번 쓰면 어디서나 도는 구조가 아니다. 같은 언어·개념·테스트로 타깃마다 여전히 손으로 쓴다. 공유되는 건 소스가 아니라 툴링과 사고방식이고, 검증 비용은 위 callout 에 수치로 정리했다.

How complete is the Ascend side, really?Ascend 쪽은 실제로 얼마나 완성됐나

1 · Pairing is partial1 · 짝이 다 맞지 않는다

The two backends are not mirror images. Several kernels exist only on CUDA, among them candidate_blocks, dflash, flash_mla_utils and outlier_detection.두 백엔드는 거울상이 아니다. candidate_blocks, dflash, flash_mla_utils, outlier_detection 등 CUDA 쪽에만 있는 커널이 여럿이다.

2 · Observability is CUDA-only2 · 관측은 CUDA 전용

Every entry point in csrc/graph_timer/graph_timer_asc.cpp throws "NPU graph timer primitives are not implemented yet". You cannot do in-graph timing on Ascend today.csrc/graph_timer/graph_timer_asc.cpp 의 모든 진입점이 "NPU graph timer primitives are not implemented yet" 를 던진다. 지금은 Ascend 에서 in-graph 타이밍을 할 수 없다.

3 · A rewrite, not a retarget3 · 리타깃이 아니라 재작성

CUDA kernels use fragments, T.Pipelined and PDL sync; Ascend ones use T.Persistent vector-core loops with explicit UB staging and inter-core flag barriers. Same DSL, different program.CUDA 커널은 fragment, T.Pipelined, PDL 동기화를 쓴다. Ascend 커널은 명시적 UB 스테이징과 코어 간 플래그 배리어를 둔 T.Persistent 벡터코어 루프를 쓴다. DSL 은 같아도 프로그램은 다르다.

Even the dependency files admit the asymmetry: requirements-nvidia.txt installs torch==2.13.0+cu132 and flash-attn-4, while requirements-ascend.txt installs torch==2.13.0+cpu and gets device support entirely from torch-npu==2.13.0rc1, an rc build.의존성 파일도 비대칭을 드러낸다. requirements-nvidia.txt 는 torch==2.13.0+cu132 와 flash-attn-4 를 깔지만, requirements-ascend.txt 는 torch==2.13.0+cpu 를 깔고 디바이스 지원을 rc 빌드인 torch-npu==2.13.0rc1 에 전부 맡긴다.

The delegated math is only half-ported, and you can trace the consequence위임한 연산도 절반만 이식됐고, 그 결과가 코드에 남아 있다

Which vendor submodules have an Ascend twin, and which do not:Ascend 쌍이 있는 vendor 서브모듈과 없는 서브모듈은 다음과 같다.

vendor/DeepGEMM        vendor/DeepGEMM-Ascend     ← paired
vendor/DeepEP          vendor/DeepEP-Ascend       ← paired
vendor/FlashMLA        (none)                     ← CUDA only
vendor/DeepSelect      (none)                     ← CUDA only

That explains the shim package. deepinfer/npu_ops/ exists to patch exactly these two gaps, and its comments say so:shim 패키지 deepinfer/npu_ops/ 는 정확히 이 두 구멍을 메우려고 있고, 주석에도 그렇게 적혀 있다.

npu_ops/deep_select.py:20  # TODO(NPU): To be removed when `topk` for sampler is ready
npu_ops/vit_attn.py:8      # TODO(NPU): To be removed when `_flash_attn_fwd` for ViT is ready

A clean causal chain: no Ascend build of DeepSelect and FlashMLA → sampler topk and ViT attention have no native NPU path → a shim package hooks builtins.__import__ to redirect those two imports to lazy replacements → both are marked for deletion once the real thing lands.인과 관계가 깔끔하다. DeepSelect 와 FlashMLA 의 Ascend 빌드가 없다 → 샘플러 topk 와 ViT attention 에 네이티브 NPU 경로가 없다 → shim 패키지가 builtins.__import__ 를 후킹해 두 import 를 지연 대체물로 돌린다 → 진짜가 들어오면 지울 예정이라고 표시돼 있다.

The best single illustration of portability friction이식성 마찰을 가장 잘 보여주는 한 장면 On an NPU-only host, torch_npu's transfer_to_npu maps torch.cuda.* onto torch.npu.*, so torch.cuda.is_available() returns True on a machine with no NVIDIA GPU. TileLang gates its CUDA probe on exactly that call, so left alone it would compile every kernel for CUDA on an Ascend box. The fix is one line:NPU 전용 호스트에서는 torch_npu 의 transfer_to_npu 가 torch.cuda.* 를 torch.npu.* 로 매핑한다. 그래서 torch.cuda.is_available() 이 NVIDIA GPU 가 없는 기계에서 True 를 반환한다. TileLang 의 CUDA 탐지가 바로 이 호출을 쓰므로, 그대로 두면 Ascend 장비에서 모든 커널을 CUDA 로 컴파일한다. 수정은 한 줄이다. 
os.environ.setdefault("TILELANG_DEFAULT_TARGET", "ascend")

None of this makes the portability argument wrong, only current: TileLang is what makes a second backend tractable at all, and DeepSeek is visibly mid-port rather than done.그렇다고 이식성 논거가 틀린 건 아니다. TileLang 은 두 번째 백엔드를 감당할 수 있게 해 주는 장치이고, DeepSeek 은 아직 이식이 진행 중일 뿐이다.

6"Only useful for low latency?" — correcting the premise"low latency 에서만 의미 있다?"는 전제 바로잡기

A common intuition says tile DSLs only pay off in latency-bound regimes, because vendor libraries dominate big dense GEMM. That intuition is half right, and DeepInfer shows which half.벤더 라이브러리가 큰 dense GEMM 을 지배하니 타일 DSL 은 지연 바운드 영역에서만 쓸모 있다는 직관이 흔하다. 이 직관은 절반만 맞고, DeepInfer 가 어느 절반인지 보여 준다.

DeepInfer does not use TileLang for heavy dense math at all. There are zero GEMM or matmul kernels in tilelang_ops/. The work is split:DeepInfer 는 무거운 dense 연산에 TileLang 을 전혀 쓰지 않는다. tilelang_ops/ 에 GEMM·matmul 커널은 0개다. 분업은 다음과 같다.

Work작업 Who does it담당 Import sitesimport 지점

Everything else나머지 전부TileLang (29 hand-written kernels)60

What "everything else" actually is:"나머지 전부"는 이런 커널들이다.

Gathers, index arithmetic, KV-cache movement, sampling, normalisation, quantisation: memory-bound, irregular, fused glue, the category where no vendor library exists and a Triton-class DSL genuinely wins.gather, 인덱스 연산, KV 캐시 이동, 샘플링, 정규화, 양자화. 모두 메모리 바운드이고 불규칙한 fused glue 커널이다. 벤더 라이브러리가 없고 Triton 계열 DSL 이 확실히 이기는 범주다.

The premise, restated correctly전제를 바르게 다시 쓰면 "TileLang is pointless for dense GEMM" is true here, and DeepSeek agrees: that work goes to DeepGEMM. But "therefore it only matters for latency" does not follow. These glue kernels are pure overhead between the GEMMs. They dominate decode, and they also tax throughput, because every microsecond spent gathering indices is a microsecond the tensor cores are idle. The right framing is not latency vs throughput but commodity dense math vs the long tail: buy the former, own the latter."dense GEMM 에서 TileLang 은 의미 없다"는 여기서 맞고 DeepSeek 도 동의한다. 그 일은 DeepGEMM 이 맡는다. 하지만 "그러니 지연에서만 중요하다"는 따라오지 않는다. glue 커널은 GEMM 사이의 순수 오버헤드라서 decode 를 지배할 뿐 아니라 throughput 도 깎는다. 인덱스를 모으는 1마이크로초 동안 텐서 코어는 논다. 그래서 옳은 구도는 지연 대 처리량이 아니라 상품화된 dense 연산 대 롱테일이다. 전자는 사 오고, 후자는 직접 만든다.
