ProblemOrganisations pay for AI through ledgers that do not talk to each other: Kubernetes allocations for self-hosted inference, gateway logs, and per-token bills from API providers. Where those systems meet, spend loses its owner — and inside a shared inference server, the rule used to meter tenants silently decides who pays for a KV cache everyone uses.조직의 AI 비용은 쿠버네티스 할당, 게이트웨이 로그, API 토큰 청구서처럼 서로 연결되지 않은 장부에 흩어져 있고, 그 이음매에서 비용이 주인을 잃는다. 공유 추론 서버 안에서는 계량 규칙이 공용 KV 캐시 비용을 누가 낼지 조용히 정한다.

MethodThe authors build unalloc, an open-source tool that joins OpenCost, LiteLLM, OpenAI and Anthropic cost data into one exact ledger and reports the share of spend with no owner. Five case studies run or simulate inference: a vLLM-style simulator with paged KV memory and prefix caching, a PyTorch transformer serving a multi-tenant trace with a real KV cache, tensor- and pipeline-parallel inference, the unmodified CLI against mock provider APIs, and four downstream use cases.OpenCost, LiteLLM, OpenAI, Anthropic 비용을 하나의 장부로 합치고 주인 없는 비율을 보고하는 오픈소스 도구 unalloc을 만든다. vLLM 방식 시뮬레이터, 실제 KV 캐시를 쓰는 PyTorch 멀티테넌트 서빙, 텐서·파이프라인 병렬 추론, 모의 API 대상 CLI, 하류 사용 사례 넷으로 다섯 사례 연구를 돌린다.

ResultsIn a constructed multi-pod scenario (one month of synthetic OpenCost allocations, not observed billing), owner labels set only on LeaderWorkerSet leader pods leave 66% of the GPU bill unowned; the natural fallback key assigns 61% of it to a Helm chart name while the headline unallocated share falls to 4%. On an H100 running vLLM, a token meter charges a retrieval-heavy tenant 12–14 percentage points more than an equal time-share meter at every load tested, while GPU utilisation reads 97–99% throughout.합성 OpenCost 할당 한 달치로 만든 다중 파드 시나리오에서 LeaderWorkerSet 리더 파드에만 라벨을 달면 GPU 비용의 66%가 주인을 잃고, 대체 키는 그중 61%를 Helm 차트 이름에 붙이는데 미할당 비율은 4%로 보인다. SummaryThe uncomfortable finding is that a healthy-looking dashboard — 4% unallocated, 99% utilisation — can coexist with most of the bill being attributed to the wrong thing. SPECTRA: Adaptive Execution of Speculative Decoding on a Runtime-Reconfigurable Tiled Architecturespeculative decodinghardwarearXiv:2609.24847
arxiv.org/abs/2609.24847 →

ProblemOn edge devices, speculative decoding helps because a small drafter proposes tokens and the target verifies several at once. But verification sits in an awkward middle regime: decode is a memory-bound GEMV, prefill is a compute-bound GEMM, and verification's arithmetic intensity moves between them depending on speculation length and acceptance rate. Hardware fixed for either extreme is under-used for the other.엣지의 추측 디코딩에서 검증 단계는 메모리 제약 GEMV(디코드)와 연산 제약 GEMM(프리필) 사이에 있고, 산술 강도가 추측 길이와 수락률에 따라 움직인다. 한쪽에 고정된 하드웨어는 다른 쪽에서 논다.

MethodSPECTRA is a runtime-reconfigurable tiled architecture. Inside each tile, the compute engine switches between systolic execution for GEMMs and vector-lane execution for GEMVs. Across tiles, the system adapts parallelism by choosing tile count, kernel partitioning and communication pattern. Both levels of reconfiguration happen per kernel, so draft, verify and decode each get the shape that suits them.SPECTRA는 실행 중 재구성되는 타일 구조다. 타일 안에서는 GEMM용 시스톨릭 실행과 GEMV용 벡터 레인 실행을 오가고, 타일 사이에서는 타일 수·커널 분할·통신 패턴을 커널마다 다시 고른다.

ResultsOn a 20-tile FPGA prototype across the Pythia, SmolLM2 and GPT-2 families, SPECTRA reports up to 2.09× speedup from tile-level reconfiguration and a further 1.25× from system-level adaptability, both measured against fixed designs.Pythia, SmolLM2, GPT-2 계열로 돌린 20타일 FPGA 시제품에서 고정 설계 대비 타일 수준 재구성으로 최대 2.09배, 시스템 수준 적응으로 추가 1.25배 빨라졌다.

SummaryThe models are small and the platform is an FPGA, so this is a hardware argument rather than a deployment result. The argument itself travels: speculative verification is its own workload class, and hardware or kernels tuned only for "prefill" and "decode" leave it in the gap.모델이 작고 플랫폼이 FPGA라 배포 결과보다는 하드웨어 논증이다. 다만 추측 검증이 프리필·디코드와 다른 별도 워크로드라는 논지는 커널 설계에도 그대로 통한다.

arxiv.org/abs/2609.24698 →

ProblemTree speculation keeps several branches from a shared prefix, so under the same budget it covers more futures than a single chain. On DeepSeek-V4 this is hard: its CSA/HCA online compressed attention folds context into compressed states as it goes, and branches that diverge from a shared prefix compress into different states — breaking the cross-branch consistency that tree verification assumes.트리 추측은 공유 프리픽스에서 여러 가지를 유지해 같은 예산으로 더 많은 후보를 덮는다. 그런데 DeepSeek-V4의 CSA/HCA 온라인 압축 어텐션에서는 갈라진 가지들이 서로 다른 압축 상태를 만들어, 트리 검증이 전제하는 가지 간 일관성이 깨진다.

MethodThe authors integrate tree speculation into the DeepSeek-V4-Flash pipeline with three pieces: branch-aware causal verification, temporary state isolation so each branch's compressed state does not contaminate the others, and an accepted-path state refresh that commits only the winning branch's compressed state afterwards.DeepSeek-V4-Flash 파이프라인에 가지 인지 인과 검증, 가지별 임시 상태 격리, 이긴 가지의 압축 상태만 확정하는 수락 경로 갱신을 넣는다.

ResultsAcross budgets D=5 to D=8, batch sizes 1 to 64 and three datasets (GSM8K, MBPP, ShareGPT), tree speculation gets a longer accepted length than matched linear configurations in every setting — at D=8 about 2.83–3.41 versus 2.39–2.84 — and higher throughput in nearly all, by up to about 18.5%. Gains grow with budget and are largest on less predictable workloads at small-to-medium batch; beyond a point, throughput plateaus even as accepted length keeps rising.예산 D=5~8, 배치 1~64, GSM8K·MBPP·ShareGPT의 모든 설정에서 선형 구성보다 수락 길이가 길고(D=8에서 2.83~3.41 대 2.39~2.84), 처리량은 거의 모든 설정에서 최대 약 18.5% 높다. 이득은 예측이 어려운 워크로드의 중소 배치에서 가장 크고, 어느 예산을 넘으면 처리량이 평평해진다.

SummaryThe throughput plateau is the useful engineering fact: past a certain budget, accepting more tokens stops buying wall-clock time. More broadly, it is a worked example of what speculative decoding needs once the model's context is no longer a plain KV cache.어느 예산을 넘으면 수락 토큰이 늘어도 실제 시간은 줄지 않는다는 점이 실무에 쓸모 있다. 문맥이 평범한 KV 캐시가 아닌 모델에서 추측 디코딩에 무엇이 필요한지 보여 주는 실례다.
