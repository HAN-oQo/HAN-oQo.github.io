vLLM — a KV connector and multi-token prediction stop deadlocking each other under cache pressure Sep 16

Sixty-two commits, no new tag. The key fix: with a KV connector and multi-token prediction both on, the engine could deadlock under KV-cache pressure, because the connector (mid-transfer) and MTP (holding speculative positions) both kept their blocks and neither gave way. A stall looks like a hang rather than a slowdown, the worst failure shape for a fleet. Other changes: 커밋 62개, 새 태그 없음. 핵심은 교착 수정이다. KV 커넥터와 다중 토큰 예측(MTP)을 함께 켜면 KV 캐시가 부족할 때 엔진이 멈출 수 있었다. 전송 중인 커넥터와 추측 위치를 붙든 MTP가 서로 블록을 내주지 않았기 때문이다. 이런 멈춤은 감속이 아니라 행으로 보여서 서빙 설비에서 가장 나쁜 고장이다. 그 밖의 변경은 다음과 같다.

  • Housekeeping: DeepGEMM pin moved, Cutlass FP8 linear no longer claims A100 support, a NumPy float leak in the KV-transfer metrics log fixed.

JustFit: 200K-Token LLM Serving on a 24 GiB Laptop with Just-in-Time State Managementlong contextlocal servingarXiv:2609.17475
arxiv.org/abs/2609.17475 →
Problem문제 정의 On a laptop, memory is squeezed by both the context and the execution state around it, and weight quantization only addresses the first. The real ceiling is how far one request can run before memory runs out. 노트북에서는 문맥과 그 주변 실행 상태가 함께 메모리를 누르는데, 가중치 양자화는 앞쪽만 줄인다. 실제 한계는 요청 하나가 메모리가 바닥나기 전까지 얼마나 길게 갈 수 있느냐다.
Method방법 An MLX runtime with three mechanisms: KVExec (compressed KV execution), PhaseSwap (component residency) and StateTrans (state-preserving serving transitions). Components are materialized just in time and released when no longer needed, independently of weight quantization. MLX 기반 런타임이며 KVExec(압축 KV 실행), PhaseSwap(구성 요소 상주 관리), StateTrans(상태 보존 서빙 전환)로 이뤄진다. 구성 요소를 필요한 순간에 만들고 다 쓰면 바로 해제하며, 가중치 양자화와는 별개로 작동한다.
Results결과 On a 24 GiB M4 Pro MacBook with Qwen3.8-27B MXFP4, three runs complete 196,608 input + 16,384 output tokens: 212,992 positions versus the mlx-vlm baseline's 30,720 (6.93×). Two requests hold 229,376 positions in aggregate. A 32K-input, 64-output probe hits 19.11 tokens/s, a repeated 32K+6K workload peaks at a median 16,374 MiB, and the runtime solves 29 of 30 AIME 2026 problems. 24 GiB M4 Pro 맥북에서 Qwen3.8-27B MXFP4로 입력 196,608·출력 16,384 토큰을 세 번 모두 완주했다. 단일 요청 문맥이 mlx-vlm 기준선 30,720에서 212,992 위치로 6.93배 늘었고, 두 요청은 합계 229,376 위치를 유지한다. 32K 입력·64 출력에서 19.11 tokens/s, 32K+6K 반복 워크로드의 최대 메모리 중앙값은 16,374 MiB이며, AIME 2026 30문제 중 29개를 맞힌다.
Summary요약 The idea to borrow is lifetime-aware execution: large objects are born and die inside one request instead of living for the whole process. It changes when memory is held, not how densely it is packed, which is why it stacks with quantization. 가져갈 관점은 수명 인식 실행이다. 큰 객체를 프로세스 내내 두지 않고 요청 안에서 만들고 없앤다. 메모리를 얼마나 촘촘히 싸느냐가 아니라 언제 붙잡느냐를 바꾸므로 양자화와 함께 쓸 수 있다.

Problem문제 정의 On heterogeneous edge servers with evolving inference state, the best server for a request changes per slot and couples across slots.
