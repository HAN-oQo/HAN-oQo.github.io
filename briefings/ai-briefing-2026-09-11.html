NVIDIA Dynamo — a WAN transport for the publisher, and a planner that stops grading its own failures as successes Sep 10

Forty-two commits and no new tag. The feature to read first is Relay WAN protobuf transport over universal publisher: Dynamo's publisher path now has a wide-area transport, which is the sort of plumbing you only add when KV and metrics have to cross a datacentre boundary rather than a rack. Problem문제 정의 Serving systems already reuse KV caches, but only when the reused text sits at the very start of the prompt. Two growing workloads break that condition: a RAG server assembles a different set of retrieved chunks for every query, and a multi-agent coordinator reads reports written by other agents. Reused inside a new prompt, a cache carries the wrong positions and never attended to the other sources — and it may have been written by a different checkpoint of the same model family, which changes the stored values. 서빙 시스템은 이미 KV 캐시를 재사용하지만, 재사용되는 텍스트가 프롬프트 맨 앞에 있을 때뿐이다. 늘어나는 두 워크로드가 그 조건을 깨뜨린다. RAG 서버는 질의마다 다른 검색 청크 조합을 모으고, 멀티 에이전트 조율자는 다른 에이전트가 쓴 보고서를 읽는다. 새 프롬프트 안에서 재사용되면 캐시는 잘못된 위치를 실어 나르고 다른 출처들을 한 번도 참조한 적이 없다. 게다가 그 캐시는 같은 모델 계열의 다른 체크포인트가 썼을 수도 있는데, 그러면 저장된 값 자체가 달라진다.
Method방법 Repair methods for such caches have appeared in three separate communities, each measured on its own terms, while existing benchmarks test only exact-prefix reuse where nothing is lost. KVShareArena benchmarks reuse across prompt contexts and across model checkpoints, on both retrieved chunks and agent reports. It scores every method by the fraction of the gap it recovers between no cache and full recomputation, and charges compute, memory and per-request latency with the cache in hand, reporting the one-time cost of building a cache separately. 그런 캐시를 보수하는 방법은 서로 다른 세 커뮤니티에서 각자의 기준으로 측정되며 따로 등장했고, 기존 벤치마크는 아무것도 잃지 않는 정확한 프리픽스 재사용만 시험한다. Results결과 Correcting positions, which needs no recomputation, is enough until a question needs several sources at once. Problem문제 정의 Autoregressive decoding re-reads a growing KV cache at every step, so long-context attention is bound by GPU memory bandwidth rather than by arithmetic. Block-sparse attention skips low-contribution KV blocks, but the two obvious ways to decide which blocks to skip each create a new dependency. A selector that decides after the current query-key product still has to read every K block, which is the cost you were trying to avoid. A processing-in-memory filter that decides from the current query puts a serial PIM stage directly on the critical path. 자기회귀 디코딩은 매 스텝 커지는 KV 캐시를 다시 읽으므로, 긴 문맥 어텐션은 연산이 아니라 GPU 메모리 대역폭에 묶인다. 블록 희소 어텐션은 기여가 낮은 KV 블록을 건너뛰지만, 어느 블록을 건너뛸지 정하는 뻔한 두 방법은 각각 새 의존성을 만든다. 현재 질의-키 곱 이후에 결정하는 선택기는 여전히 모든 K 블록을 읽어야 하는데, 그게 바로 피하려던 비용이다. 현재 질의에서 결정하는 메모리 내 연산(PIM) 필터는 직렬 PIM 단계를 임계 경로 위에 그대로 올려놓는다.
Method방법 AMEND removes both dependencies by predicting each block's sparsity verdict from margins audited at earlier steps, rather than computing it now. The GPU fetches only the predicted survivors, while near-bank PIM units inside HBM concurrently score the omitted complement — so every predicted drop is re-observed, just not on the critical path. A stack-level controller merges both observations, updates the predictor, and eagerly generates the next step's mask while the current token is still being produced. Operating points are chosen offline by constrained Bayesian optimization under an explicit false-drop budget. AMEND는 각 블록의 희소성 판정을 지금 계산하는 대신 앞선 스텝에서 감사한 마진으로 예측해 두 의존성을 모두 없앤다. GPU는 생존이 예측된 블록만 가져오고, HBM 안의 뱅크 근처 PIM 유닛이 생략된 나머지를 동시에 채점한다. 그래서 예측된 모든 탈락은 다시 관측되지만 임계 경로 위에서는 아니다. 스택 수준 컨트롤러가 두 관측을 합치고 예측기를 갱신하며, 현재 토큰이 아직 생성되는 동안 다음 스텝의 마스크를 미리 만든다. 동작점은 명시적인 오탈락 예산 아래 제약 베이지안 최적화로 오프라인에서 고른다.
Results결과 Across LongBench and RULER runs, AMEND preserves near-baseline task quality. Summary요약 Plainly: stop asking "is this block important?" at the moment you need the answer. Answer it from what the block did on previous steps, fetch accordingly, and let memory-side hardware quietly check your homework in parallel — so a wrong guess is caught by the next mask rather than by a stall. 쉽게 말하면, "이 블록이 중요한가?"를 답이 필요한 바로 그 순간에 묻지 않는다. 앞선 스텝에서 그 블록이 무엇을 했는지로 답하고, 그에 맞춰 가져오고, 메모리 쪽 하드웨어가 병렬로 조용히 답안을 검사하게 한다. 그러면 틀린 추측은 멈춤이 아니라 다음 마스크에서 잡힌다.

Problem문제 정의 Diffusion language models generate text by refining a fixed-size block of token positions through many forward passes. That loop does not match the per-forward execution unit that most LLM serving systems are built around. A dense MoE runtime binds all work to the refinement-iteration clock: it rebuilds similar routing structure on every forward, recomputes expert outputs for positions whose logits are already settled, and pushes those positions through dense expert-parallel collectives anyway. 디퓨전 언어 모델은 고정 크기의 토큰 위치 블록을 여러 번의 포워드 패스로 다듬어 텍스트를 만든다. 그 루프는 대부분의 LLM 서빙 시스템이 전제하는 포워드 단위 실행 단위와 맞지 않는다. 밀집 MoE 런타임은 모든 작업을 다듬기 반복 클럭에 묶는다. 매 포워드마다 비슷한 라우팅 구조를 다시 만들고, 이미 확정된 로짓을 가진 위치의 전문가 출력을 다시 계산하며, 그 위치들을 어차피 밀집 전문가 병렬 집합 연산에 통과시킨다.
Method방법 Epoch treats the diffusion block itself as the compilation unit. It compiles a small block plan for the block-clock structure of one diffusion block, and refreshes on the faster iteration clock only the values that can still affect a live decode decision. The plan is realized along three dense axes of an MoE forward: a coverage-driven active expert support per layer, with gate logits still recomputed every iteration; full sequence shards kept as model state while only live, newly decoded and refresh-required positions are routed through fresh expert computation; and a fresh token–expert worklist carried through expert-parallel dispatch, kernels and combine before the dense logical shard is restored at the layer boundary. Epoch은 디퓨전 블록 자체를 컴파일 단위로 다룬다. 디퓨전 블록 하나의 블록 클럭 구조에 대해 작은 블록 계획을 컴파일하고, 살아 있는 디코드 결정에 아직 영향을 줄 수 있는 값만 더 빠른 반복 클럭에서 갱신한다. 이 계획은 MoE 포워드의 밀집한 세 축에서 구현된다. 층마다 커버리지 기반의 활성 전문가 집합을 컴파일하되 게이트 로짓은 매 반복 다시 계산하고, 전체 시퀀스 샤드는 모델 상태로 유지하되 살아 있는·새로 디코딩된·갱신이 필요한 위치만 새 전문가 연산으로 보내며, 새 토큰-전문가 작업 목록을 전문가 병렬 디스패치·커널·결합까지 실어 나른 뒤 층 경계에서 밀집 논리 샤드를 복원한다.
Results결과 Implemented on 8 NVIDIA H100 GPUs and evaluated on three open-weight block-diffusion MoE models — LLaDA-MoE, LLaDA2.0-mini and LLaDA2.0-Flash, spanning 7B to 100B total parameters — across GSM8K, HumanEval, MGSM and MT-Bench, Epoch improves end-to-end execution time by up to 2.7x over the strongest surviving baseline under the same 8-GPU placement. It remains feasible at the largest batch sizes where multiple baselines run out of memory, while preserving task quality relative to the dense reference. NVIDIA H100 8장에 구현하고, 오픈 웨이트 블록 디퓨전 MoE 모델 셋(LLaDA-MoE, LLaDA2.0-mini, LLaDA2.0-Flash, 총 파라미터 7B~100B)을 GSM8K·HumanEval·MGSM·MT-Bench에서 평가했을 때, Epoch은 같은 8-GPU 배치에서 살아남은 가장 강한 기준선 대비 E2E 실행 시간을 최대 2.7배 개선한다. 여러 기준선이 메모리 부족으로 죽는 가장 큰 배치 크기에서도 동작하며, 밀집 기준 대비 과제 품질은 유지한다.

Problem문제 정의 Persistent agents need stored experience to stay available over time, but each answer needs evidence suited to one particular question. Problem문제 정의 LLM agents produce fluent action sequences across many tasks and then fail in characteristic ways once the environment is partially observable. Ambiguous feedback pushes them into premature commitments. A single informative observation can collapse their uncertainty onto the wrong hypothesis. Policies drift as the history grows. LLM 에이전트는 여러 과제에서 유창한 행동열을 내놓다가, 환경이 부분 관측이 되는 순간 특징적인 방식으로 실패한다. 모호한 피드백은 그들을 성급한 확신으로 밀어 넣는다. 정보량이 큰 관측 하나가 불확실성을 잘못된 가설 위로 붕괴시킬 수 있다. 히스토리가 길어지면 정책이 표류한다. 저자들은 이 세 증상을 하나의 구조적 원인으로 추적한다. 흔히 배포되는 형태의 LLM 에이전트는 은닉 상태에 대한 명시적 신념이 없는, 히스토리 조건부 정책이다.
