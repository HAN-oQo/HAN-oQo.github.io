Problem문제 정의Cartridges, a learned KV-cache compression method, answers questions about a document well but derails on off-context queries that need general knowledge, contaminating context and weakening instruction following. Heuristic compression variants keep the base model's off-context ability better, so the trade-off is real.학습형 KV 캐시 압축 기법인 Cartridges는 문서에 대한 질문에는 잘 답하지만, 일반 지식이 필요한 문서 밖 질의에서는 맥락이 오염되고 지시 따르기가 약해지며 탈선한다. 휴리스틱 압축 변형은 기본 모델의 문서 밖 능력을 더 잘 지키므로 이 트레이드오프는 실재한다.

Method방법Cartridges++ adds two remedies. A router variant decides at run time whether a query should use the compressed cache or the native one, and a data-mixing variant adds off-document training examples so the compressed cache keeps general capabilities.Cartridges++는 두 가지 처방을 더한다. 라우터 변형은 질의마다 압축 캐시를 쓸지 원본 캐시를 쓸지 실시간으로 정하고, 데이터 혼합 변형은 문서 밖 학습 예시를 섞어 압축 캐시가 일반 능력을 유지하게 한다.

Problem문제 정의Leech-lattice quantization gives good quality at two bits per weight, but its codebooks hold more than 10^14 points, too many for a lookup table. The authors' earlier kernel expanded codes at load time and read 4.804 bits per weight from GPU memory for 2 bits of code.Leech 격자 양자화는 가중치당 2비트에서 좋은 품질을 내지만 코드북이 10^14개가 넘어 조회 테이블로 둘 수 없다. 저자들의 이전 커널은 로드 시점에 코드를 펼쳐 2비트 코드에 GPU 메모리에서 가중치당 4.804비트를 읽었다.

Method방법Tetra is a new codebook on the same lattice. A 24-weight block still takes 48 bits, most of which index a 64-state trellis of the Golay code, with one shared 16 KiB table. The matrix-vector kernel decodes a block with six table loads and two small lookups and reads 2.148 bits per weight; for full models one scale per matrix row is retrained, and the matrices that lose the most are stored as 4-bit integers.Tetra는 같은 격자 위의 새 코드북이다. 24개 가중치 블록은 여전히 48비트이며, 대부분이 골레이 코드의 64상태 트렐리스를 색인하고 16KiB 공유 테이블 하나를 쓴다. 행렬-벡터 커널은 테이블 조회 6번과 작은 조회 2번으로 블록을 풀어 가중치당 2.148비트를 읽으며, 전체 모델에서는 행렬 행마다 스케일 하나를 재학습하고 손실이 가장 큰 행렬은 4비트 정수로 저장한다.

arxiv.org/abs/2609.35263 →

Problem문제 정의Pipeline parallelism can raise prefill throughput by running request chunks across stages concurrently, but keeping the pipeline full needs efficient scheduling. When stages keep and evict cache state independently, a local prefix hit does not guarantee the prefix is reusable across all stages, and coordination overhead slows request admission.파이프라인 병렬화는 요청 청크를 단계별로 동시에 돌려 프리필 처리량을 높일 수 있지만, 파이프라인을 채워 두려면 효율적인 스케줄링이 필요하다. 단계마다 캐시 상태를 따로 유지하고 축출하면 한 단계의 접두사 적중이 모든 단계에서 재사용 가능함을 보장하지 않으며, 조율 오버헤드가 요청 수용 속도를 늦춘다.

Method방법WavePP is a prefill runtime built on TensorRT-LLM that overlaps request admission with pipeline execution. It asynchronously finds a prefix reusable across all stages, protects the cached state, reserves space, and dynamically plans each request's chunk sizes to maximize pipeline fill; each stage finishes local preparation before executing.WavePP는 TensorRT-LLM 위에 만든 프리필 런타임으로 요청 수용과 파이프라인 실행을 겹친다. 모든 단계에서 재사용 가능한 접두사를 비동기로 찾고, 캐시 상태를 보호하고, 공간을 확보하며, 파이프라인 충전을 최대화하도록 요청별 청크 크기를 동적으로 계획한다. 각 단계는 로컬 준비를 마친 뒤 실행한다.

Results결과WavePP improves TensorRT-LLM prefill throughput in 37 of 40 tested settings on GLM 5.2 and MiniMax M2.7, by factors of 2.91 and 2.02 at concurrency 128 with high cache reuse. Across 28 Kimi K3 settings it has the highest measured throughput in all 18 settings at concurrency eight or higher.GLM 5.2와 MiniMax M2.7에서 시험한 40개 설정 중 37개에서 TensorRT-LLM의 프리필 처리량을 높이며, 동시성 128·높은 캐시 재사용에서 각각 2.91배와 2.02배다. Kimi K3의 28개 설정 중 동시성 8 이상인 18개 설정 모두에서 측정 처리량이 가장 높다.

Summary요약Overlapping admission with execution and agreeing on one cross-stage prefix keeps a prefill pipeline full.요청 수용과 실행을 겹치고 단계 전체가 합의한 접두사 하나를 쓰면 프리필 파이프라인이 계속 차 있다.
