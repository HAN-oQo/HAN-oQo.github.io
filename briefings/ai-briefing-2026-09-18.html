SGLang — a worker can now change its mind about whether it is a prefill node or a decode node Sep 17

At least a hundred commits in the window, no new tag. The structural change is runtime role switching in prefill–decode disaggregation: until now a worker was launched as a prefill node or a decode node and stayed that way, so a fleet sized for one traffic mix had to be redeployed when the mix moved. Making the role switchable at runtime turns a deployment-time decision into a scheduling decision, which is the same direction the rest of the disaggregation ecosystem has been moving. Around it, the DeepSeek-V4-family work continued to deepen rather than broaden: attention metadata, sparse prefill and the KV pool were generalized over compression ratios so one code path serves several compressed-cache configurations, and a V4.1 branch gained an Engram module with request history. The unified radix cache picked up an agentic-aware tail-optimized LRU eviction policy — an eviction rule tuned for the long, tool-interrupted sessions agents produce — and HiCache batched its device-to-host submits per step for hybrid pools. The router side got two smaller things: a --min-load-choices flag that samples k random candidates for the min-load fallback instead of scanning all of them, and chat-prompt rendering through dynamo-render. Security hygiene landed too, restricting which standard-library globals the SafeUnpickler will resolve. 구간 내 커밋 최소 100개, 새 태그 없음. 구조적 변화는 프리필–디코드 분리에서의 런타임 역할 전환이다. 지금까지 워커는 프리필 노드 또는 디코드 노드로 띄워져 그대로 남았고, 그래서 한 트래픽 구성에 맞춰 크기를 잡은 설비는 구성이 바뀌면 다시 배포해야 했다. 역할을 런타임에 바꿀 수 있게 하면 배포 시점의 결정이 스케줄링 결정이 된다. 분리 서빙 생태계 전반이 가고 있는 방향과 같다. 그 주변으로 DeepSeek-V4 계열 작업은 넓어지기보다 깊어졌다. 어텐션 메타데이터, 희소 프리필, KV 풀이 압축 비율 전반으로 일반화돼 하나의 코드 경로가 여러 압축 캐시 구성을 처리하고, V4.1 갈래에는 요청 이력을 담는 Engram 모듈이 붙었다. 통합 radix 캐시에는 에이전트 인식 tail-optimized LRU 축출이 들어갔다 — 에이전트가 만들어 내는 길고 도구로 끊기는 세션에 맞춘 축출 규칙이다. vLLM — a running engine can now hand its KV cache memory back Sep 17

At least a hundred commits in the window, no new tag. The headline addition is a release_kv_cache_memory() API: a live engine can release the KV arena it has reserved instead of holding it until the process exits. That matters for anyone co-locating inference with training or with a second model on the same device, because the KV arena is normally the largest single allocation an engine makes and it is normally permanent. Alongside it, the KV-cache metadata GET method used by external event consumers was restored, and a NIXL/HiSparse path was fixed so full blocks import without a tail prefill on the decode side. Two throughput bugs read like production reports: a max-load throughput cliff when max_num_seqs is not a multiple of eight, and stale FlashMLA workspace views that were not released after the workspace grew. The DeepSeek-V4.1 path integrated Mega-Gate from DeepGEMM and fixed FlashInfer DSpark non-causal attention; the ROCm side reverted the w4a4 ASM GEMM default back to off and added a missing hook that was crashing GLM-5.3-Flash at boot. A metrics nit worth noting: vLLM no longer logs a 0.0% prefix cache hit rate before any query has been served — the kind of zero that quietly poisons a dashboard's first minute. 구간 내 커밋 최소 100개, 새 태그 없음. 눈에 띄는 추가는 release_kv_cache_memory() API다. 살아 있는 엔진이 예약해 둔 KV 아레나를 프로세스 종료까지 붙잡는 대신 반납할 수 있다. 추론을 학습이나 같은 장치의 다른 모델과 함께 얹는 쪽에는 중요한 변화다. KV 아레나는 보통 엔진이 잡는 가장 큰 단일 할당이고, 보통 영구적이기 때문이다. 함께 외부 이벤트 소비자가 쓰던 KV 캐시 메타데이터 GET 메서드가 복구됐고, NIXL/HiSparse 경로에서 디코드 쪽 꼬리 프리필 없이 전체 블록을 들여오도록 고쳤다. 처리량 버그 둘은 운영 보고서처럼 읽힌다. max_num_seqs가 8의 배수가 아닐 때 나타나는 최대 부하 처리량 절벽, 그리고 워크스페이스가 커진 뒤 반납되지 않던 낡은 FlashMLA 워크스페이스 뷰다. DeepSeek-V4.1 경로에는 DeepGEMM의 Mega-Gate가 통합됐고 FlashInfer DSpark 비인과 어텐션이 수정됐다. ROCm 쪽은 w4a4 ASM GEMM 기본값을 다시 끄고, GLM-5.3-Flash가 부팅에서 죽던 누락 훅을 넣었다. 지표 쪽 사소하지만 반가운 것 하나. vLLM은 이제 질의가 하나도 처리되기 전에 접두사 캐시 적중률 0.0%를 기록하지 않는다. 대시보드의 첫 1분을 조용히 망치는 종류의 0이다.

Ask the Tool, Don't Guess: Agent Tool Calls Hold Their Progress, and the Serving System Should Read ItKV cacheagentic servingarXiv:2609.18849
arxiv.org/abs/2609.18849 →
Problem문제 정의 An agentic request spends much of its wall-clock time waiting for a tool to return, and its KV cache occupies GPU memory for that entire wait. Serving systems decide whether to keep, evict or restore that cache by guessing how long the tool will take — from the tool's name, its history, a duration declared before the call, or the engine's own occupancy. Problem문제 정의 When agentic sessions run to a million tokens and many of them are resident at once, the KV cache and the index that ranks it live in host memory rather than on the GPU. At that point the scan that ranks all n keys for a top-k step becomes the traffic that bounds decoding — the cost is bytes moved over the bus, not arithmetic. 에이전트 세션이 100만 토큰에 이르고 그런 세션이 여럿 동시에 상주하면, KV 캐시와 그것을 순위 매기는 인덱스는 GPU가 아니라 호스트 메모리에 놓인다. 그 지점에서 top-k 스텝을 위해 n개 키 전부를 순위 매기는 스캔이 디코딩을 묶는 트래픽이 된다. 비용은 산술이 아니라 버스로 옮긴 바이트다.
Method방법 Fathom is a key scan in which each query decides how many bits of each key channel to read. The 4-bit K cache is stored channel-major as bit planes, so reading a prefix of t planes is exactly the channel's t-bit quantizer — no separate low-precision copy is needed. The query then spends its bit budget by reverse water-filling over the variance-weighted importance of its channels, giving more bits to the channels that matter to that particular query.
