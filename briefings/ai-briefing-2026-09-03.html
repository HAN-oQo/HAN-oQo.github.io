vLLM — a GEMM learns to read strided tensors, and the Rust frontend stops shipping one chunk at a time Sep 2

Two changes on opposite ends of the stack define the day. At the bottom, the DSV3 GEMM used by the Kimi-K3 path was extended to inner-contiguous and row-strided tensors, which removes a copy that existed only to satisfy a layout assumption and is reported as a 12–81% kernel improvement. At the top, the Rust frontend now coalesces the decoded chunks produced within a single engine update instead of emitting them one by one, so per-chunk overhead stops scaling with tokens generated. Around them: a fused GemmaRMSNorm path for XPU eager execution, batch-invariant matmul and linear kernels registered for XPU, targeted online quantization driven by user-supplied patterns, two KV-offload correctness fixes (spec groups scaled by decode context parallelism, and stale async lookup results now ignored), int32 index arrays in the NIXL connector to skip an intermediate conversion, a cutlass bump to v4.7.1, and support for a new DeepSeek-V4-Flash-Vision-Exp model. 스택의 양 끝에서 일어난 변경 두 건이 이날을 규정한다. 아래쪽에서는 Kimi-K3 경로가 쓰는 DSV3 GEMM이 내부 연속·행 스트라이드 텐서까지 받게 확장됐다. 레이아웃 가정을 맞추기 위해서만 존재하던 복사를 없애는 변경이고, 커널 성능 12~81% 향상으로 보고됐다. 위쪽에서는 Rust 프런트엔드가 한 번의 엔진 업데이트 안에서 나온 디코드 청크들을 하나씩 내보내는 대신 합쳐서 내보내게 됐다. 청크당 오버헤드가 생성 토큰 수에 비례해 늘어나지 않게 된 것이다. 그 주변으로 XPU eager 실행용 fused GemmaRMSNorm 경로, XPU에 등록된 배치 불변 matmul·linear 커널, 사용자 패턴 기반의 표적 온라인 양자화, KV 오프로드 정확성 수정 두 건(디코드 컨텍스트 병렬에 맞춘 스펙 그룹 스케일링, 오래된 비동기 조회 결과 무시), 중간 변환을 없애는 NIXL 커넥터의 int32 인덱스 배열, cutlass v4.7.1 상향, 그리고 새 DeepSeek-V4-Flash-Vision-Exp 모델 지원이 있었다.

mzCache: On-Device LLM Memory Management under MultitaskingKV cacheon-devicearXiv:2609.01338
arxiv.org/abs/2609.01338 →
Problem문제 정의A phone is not a server: the user switches apps, the operating system reclaims memory, and the LLM's weights and KV cache are evicted without asking. When the next request arrives, the serving stack has to either read the evicted bytes back from slow storage or recompute the whole KV cache, and either way the first token arrives late. The paper's framing is that on-device inference is a memory-management problem before it is a compute problem.휴대폰은 서버가 아니다. 사용자는 앱을 바꾸고, 운영체제는 메모리를 회수하며, LLM의 가중치와 KV 캐시는 동의 없이 쫓겨난다. 다음 요청이 오면 서빙 스택은 쫓겨난 바이트를 느린 저장소에서 다시 읽거나 KV 캐시를 통째로 다시 계산해야 하고, 어느 쪽이든 첫 토큰이 늦게 나온다. 논문의 관점은 온디바이스 추론이 연산 문제이기 이전에 메모리 관리 문제라는 것이다.
Method방법mzCache is built around restoration rather than around eviction. LLM memory is partitioned into fine-grained shared buffers so that eviction and restoration can both be partial, and so that the CPU can restore a buffer while the GPU reads another one — the mobile SoC's unified memory is what makes that concurrent access possible. On top of the partitioning sit a hybrid swap policy and a backward-out eviction order, chosen so that restoration is cheap from whatever state the eviction left behind.mzCache는 쫓아내는 쪽이 아니라 복원하는 쪽을 중심으로 설계됐다. LLM 메모리를 잘게 나눈 공유 버퍼로 쪼개, 축출과 복원이 모두 부분적으로 일어날 수 있게 하고, CPU가 한 버퍼를 복원하는 동안 GPU가 다른 버퍼를 읽을 수 있게 한다 — 모바일 SoC의 통합 메모리가 그 동시 접근을 가능하게 한다. 그 위에 하이브리드 스왑 정책과 backward-out 축출 순서를 얹는데, 축출이 어떤 상태를 남겼든 복원이 싸지도록 고른 것이다.
Results결과Implemented on llama.cpp and shipped as an Android application, mzCache reports a 2.1–5.5x reduction in time-to-first-token compared with storage-backed partial offload, and the authors demonstrate the effect in real multitasking sessions rather than only in a synthetic memory-pressure harness.llama.cpp 위에 구현해 Android 애플리케이션으로 배포했고, 저장소 기반 부분 오프로드 대비 첫 토큰까지의 시간을 2.1~5.5배 줄였다고 보고한다. 저자들은 합성된 메모리 압박 장치가 아니라 실제 멀티태스킹 상황에서 효과를 보인다.
Summary요약The useful idea travels beyond phones: if eviction is going to happen anyway, design the layout so that restoration can start anywhere and overlap with compute, instead of treating an evicted cache as a binary loss. That is the same argument datacentre KV offloading keeps rediscovering, made under much harsher constraints.쓸모 있는 발상은 휴대폰 바깥으로도 옮겨간다. 축출이 어차피 일어날 것이라면, 축출된 캐시를 전부 아니면 전무의 손실로 다루지 말고 복원이 어디서든 시작되고 연산과 겹칠 수 있도록 배치를 설계하라는 것이다. 데이터센터 KV 오프로딩이 계속 재발견하는 논지를 훨씬 가혹한 제약 아래에서 다시 말하고 있다.

OUTLETS: Output-Length Prediction from Speculative Decoding Backbonesschedulingspeculative decodingarXiv:2609.01068
arxiv.org/abs/2609.01068 →
Problem문제 정의Output lengths in LLM serving are heavy-tailed, which is exactly the distribution that makes provisioning and cluster scheduling hard: a few very long generations dominate the tail while most requests are short. Knowing the length in advance would fix a lot of that, but the two existing routes both disappoint — an external proxy model adds its own latency and predicts poorly, while probing the target model's current internal state is cheap but shallow.LLM 서빙의 출력 길이는 롱테일 분포를 따르는데, 이는 자원 산정과 클러스터 스케줄링을 어렵게 만드는 바로 그 분포다. 대부분의 요청은 짧은데 아주 긴 생성 몇 개가 꼬리를 지배한다. 길이를 미리 알면 많은 문제가 풀리지만 기존 두 경로는 모두 아쉽다. 외부 프록시 모델은 자체 지연을 더하면서 예측이 부정확하고, 타깃 모델의 현재 내부 상태를 찔러 보는 방식은 싸지만 얕다.
Method방법The observation is structural: in a modern speculative-decoding framework such as EAGLE-3, the draft decoder already produces latent representations that look ahead along the trajectory, and those representations carry signal about how long the generation will run. Problem문제 정의Speculative decoding verifies a block of draft tokens in one target forward pass, and verification is sequential: everything from the first rejection onward is thrown away. Draft training does not reflect that. It is token-level imitation of the target with a fixed per-position weighting, which treats a position after the first rejection as if it mattered as much as one before it — even though, at serving time, that position will never be accepted.추측 디코딩은 드래프트 토큰 블록을 타깃의 한 번의 순전파로 검증하는데, 검증은 순차적이다. 첫 거부 지점 이후는 전부 버려진다. 그런데 드래프트 학습은 그 사실을 반영하지 않는다. 위치마다 고정된 가중치를 둔 토큰 단위 타깃 모방이라, 첫 거부 이후의 위치를 그 이전의 위치만큼 중요한 것처럼 다룬다 — 서빙 시점에는 결코 채택되지 않을 위치인데도.
Method방법Verification-Aware Training is a plug-in framework that simulates verification at every training step and turns the resulting accept/reject pattern into supervision. It has two parts. Problem문제 정의A dynamic agent harness lets a language model change the software that shapes its own execution — install a plugin, swap a component, tear one down. Method방법CordisBench is 1,200 questions built on that burden.
