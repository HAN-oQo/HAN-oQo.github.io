NVIDIA Dynamo v1.4.0 — cross-datacenter prefix routing, reservation replay, and a vLLM-compatible generate endpoint Aug 15

Dynamo's 17th feature release spans 640 merged PRs from 127 contributors. The router gets experimental cross-datacenter prefix routing: an in-process selection cache lets peers replay booking decisions instead of re-sending long prompts, a sequenced datacenter-scoped KV relay extends prefix routing across sites, event transport becomes endpoint-scoped so consumers aggregate explicit endpoints rather than inferring ownership from broadcasts, and cache-salt-aware KV routing isolates tenants so a request carrying a tenant namespace never reuses another tenant's KV cache. The frontend registers an experimental vLLM-compatible /inference/v1/generate token-in/token-out endpoint behind an opt-in flag, plus a default-on tokenizer prefix cache. vLLM-Omni pipelines gain NIXL RDMA disaggregation for multi-node autoregressive-to-diffusion serving, the Spica discrete-event simulation framework joins the repo, and the engine fleet moves to vLLM v0.26.0, SGLang v0.5.16, TensorRT-LLM 1.3.0rc22 and NIXL v1.3.x.

Dynamo의 17번째 기능 릴리스로, 127명이 병합한 640개 PR을 담았다. 라우터는 실험적 데이터센터 간 프리픽스 라우팅을 얻었다: 인프로세스 선택 캐시로 피어가 긴 프롬프트를 다시 보내는 대신 예약 결정을 재생하고, 순서화된 데이터센터 범위 KV 릴레이가 프리픽스 라우팅을 여러 사이트로 확장하며, 이벤트 전송이 엔드포인트 범위가 되어 소비자가 브로드캐스트로 소유권을 추론하지 않고 명시적 엔드포인트를 집계한다. 또 cache-salt 인지 KV 라우팅이 테넌트를 격리해, 테넌트 네임스페이스를 가진 요청이 다른 테넌트의 KV 캐시를 재사용하지 않는다. 프런트엔드는 옵트인 플래그 뒤에 vLLM 호환 실험 엔드포인트 /inference/v1/generate(토큰 입력·토큰 출력)와 기본 활성 토크나이저 프리픽스 캐시를 등록한다. vLLM-Omni 파이프라인은 다중 노드 자기회귀→확산 서빙을 위한 NIXL RDMA 분리를 얻었고, Spica 이산사건 시뮬레이션 프레임워크가 저장소에 합류했으며, 엔진 구성은 vLLM v0.26.0·SGLang v0.5.16·TensorRT-LLM 1.3.0rc22·NIXL v1.3.x로 올랐다.

DeaMoE: Efficient MoE Structure for Fast Small-Batch DecodingMoE servingdecoding2608.14385
Group experts into "departments" that share most parameters so small-batch decoding loads less weight (arXiv 2608.14385) ↗전문가를 대부분의 파라미터를 공유하는 "부서"로 묶어 소배치 디코딩의 가중치 로딩을 줄이기 (arXiv 2608.14385) ↗
Problem문제 정의MoE models are now standard in real-time interactive products — coding assistants, live audio-video systems — where response latency budgets force small-batch decoding. Under small batches MoE inference becomes memory-bound and is severely bottlenecked by expert weight loading, yet the paper argues this specific bottleneck has received limited attention. Existing answers either compress weights after training or design fine-grained experts during pre-training, which respectively hurt accuracy or add computation and communication overhead.MoE 모델은 코딩 어시스턴트, 실시간 오디오·비디오 시스템 같은 실시간 대화형 제품의 기본이 됐고, 이런 환경의 응답 지연 예산은 소배치 디코딩을 강제한다. 소배치에서 MoE 추론은 메모리 바운드가 되어 전문가 가중치 로딩이 심각한 병목이 되지만, 논문은 바로 이 병목이 상대적으로 주목받지 못했다고 지적한다. 기존 해법은 학습 후 가중치 압축이거나 사전학습 단계의 세분화된 전문가 설계인데, 각각 정확도를 떨어뜨리거나 추가 연산·통신 오버헤드를 만든다.
Method방법DeaMoE is a decoding-efficient MoE architecture in which experts are grouped into departments. Experts in the same department come from the same professional field and therefore share most of their parameters, with each expert additionally holding a few private parameters that carry its individuality. A customized two-stage routing strategy is designed on top of this layout specifically to avoid redundant loading — the router first settles the department, so the shared bulk is fetched once and only the small private parts vary per expert.DeaMoE는 전문가를 부서(department)로 묶는 디코딩 효율 중심 MoE 구조다. 같은 부서의 전문가는 같은 전문 분야에서 나왔다고 보고 파라미터 대부분을 공유하며, 각 전문가는 자기만의 개성을 담는 소량의 private 파라미터를 추가로 갖는다. 이 배치 위에 중복 로딩을 피하도록 맞춤 설계된 2단계 라우팅 전략을 얹는다 — 라우터가 먼저 부서를 정하므로 공유되는 큰 덩어리는 한 번만 읽고, 전문가별로는 작은 private 부분만 달라진다.
Results결과Against vanilla MoE, DeaMoE reduces per-step loaded weights by up to 50.9%. On a pre-trained 7B model on an A40 it delivers up to 1.33× end-to-end TPOT speedup, and in microbenchmarks on DeepSeek-V3 it reaches up to 2.00× peak speedup on A40 and 1.97× on H100.기본 MoE 대비 DeaMoE는 스텝당 로드되는 가중치를 최대 50.9% 줄인다. A40에서 사전학습된 7B 모델 기준 최대 1.33× 엔드투엔드 TPOT 가속을 내고, DeepSeek-V3 마이크로벤치마크에서는 A40 최대 2.00×, H100 최대 1.97× 피크 가속에 도달한다.

A deflation of the "loop engineering is dead, graph engineering is here" meme. Loops and graphs are not competing paradigms: a loop is one agent iterating toward a goal under an external verifier, and a graph is what you get when you connect several loops and handoffs. The graph structures themselves are old — chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer, plus DAG schedulers and state machines. What is genuinely new is that each node is now a probabilistic agent that may decide differently on identical input, which forces orchestration to become explicit: what runs in parallel, what state passes between nodes, who can veto whom, where to roll back, where to cap cost. The post also warns that stacking more agents is not verification, since reviewers sharing a model and bad context produce correlated errors.
