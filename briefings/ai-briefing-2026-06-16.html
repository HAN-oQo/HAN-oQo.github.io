vLLM main — DSv4 prefill chunk planning (+4.0% E2E) and NIXL expert-parallel work vLLMJun 15

vLLM's main branch merged roughly 40 commits in the window, weighted toward throughput and expert-parallel serving. The standout perf change reworks DeepSeek-V4 prefill chunk planning for a measured 4.0% end-to-end throughput gain, alongside a cluster of NIXL expert-parallel (EP) commits — enabling dual-batch overlap (DBO) with NIXL EP, querying the NIXL EP top-k index dtype, and skipping post-receive quantization for NVFP4. It also added first-class MiniMax M3 model support, a reset_cache path for the tiering KV-offload manager, an engine-based Gemma4 parser replacing the legacy one, and a Model Runner V2 LoRA-warmup fix. The thread is squeezing more out of disaggregated/EP serving while broadening model and KV-tiering coverage.

vLLM의 main 브랜치는 이 구간에 약 40 커밋을 머지했고 무게중심은 처리량과 전문가 병렬 서빙이었다. 두드러진 성능 변경은 DeepSeek-V4 prefill 청크 계획을 다시 짜 엔드투엔드 처리량을 측정상 4.0% 끌어올린 것으로, NIXL 전문가 병렬(EP) 커밋 묶음 — NIXL EP와 dual-batch overlap(DBO) 활성화, NIXL EP top-k 인덱스 dtype 질의, NVFP4의 수신 후 재양자화 생략 — 과 함께 들어갔다. 또한 MiniMax M3 모델 정식 지원, 계층 KV 오프로드 매니저의 reset_cache 경로, 레거시를 대체하는 엔진 기반 Gemma4 파서, Model Runner V2 LoRA 워밍업 수정이 추가됐다. 관통 주제는 분산/EP 서빙에서 더 짜내면서 모델·KV 계층 커버리지를 넓히는 것이다.

SGLang main — prefill/decode tuning: SWA allocation and DeepSeek-V4 kernel prewarm SGLangJun 15

After v0.5.13, SGLang's main branch shifted from last week's diffusion focus toward prefill/decode (PD) serving and DeepSeek-V4 correctness. New commits optimize sliding-window-attention (SWA) allocation in the PD path, remove an outdated backend whitelist for the decode radix cache, and prewarm the DeepSeek-V4 MHC prenorm kernel at server startup so the first request doesn't pay the compile cost. There's also an FA3 fix that prevents NaN embeddings when fa_skip_kv_cache runs under a piecewise CUDA graph, an OrcaRouter usage example, and a cookbook note on MTP with --max-running-requests. The throughline is steady hardening of disaggregated PD serving and day-one DeepSeek-V4 readiness.

v0.5.13 이후 SGLang의 main은 지난주의 디퓨전 집중에서 prefill/decode(PD) 서빙과 DeepSeek-V4 정합성으로 옮겨 갔다. 새 커밋은 PD 경로의 슬라이딩 윈도 어텐션(SWA) 할당을 최적화하고, decode radix 캐시의 낡은 백엔드 화이트리스트를 제거하며, 서버 기동 시 DeepSeek-V4 MHC prenorm 커널을 프리웜해 첫 요청이 컴파일 비용을 치르지 않게 한다. 또한 piecewise CUDA 그래프에서 fa_skip_kv_cache 실행 시 NaN 임베딩을 막는 FA3 수정, OrcaRouter 사용 예제, MTP의 --max-running-requests 쿡북 노트가 있다. 관통 주제는 분산 PD 서빙의 꾸준한 강화와 DeepSeek-V4 day-1 준비다.

NVIDIA Dynamo main — disagg-bootstrap across all routers, dynamic LoRA on the unified vLLM backend DynamoJun 15

Dynamo's main branch extended its disaggregated-serving reach across routing modes. A routing fix enables disagg-bootstrap for the LeastLoaded, Power-of-Two-Choices (P2C) and DeviceAwareWeighted policies, so prefill/decode split now works regardless of which load balancer is selected. Smaller fixes keep DeepSeek-V4 tool-call arguments as a JSON string for encode_messages and publish SGLang KV events with router block hashes — overall, broadening where disaggregation and adapters apply.

Dynamo의 main 브랜치는 분산 서빙 적용 범위를 라우팅 모드 전반으로 넓혔다. 라우팅 수정으로 LeastLoaded·Power-of-Two-Choices(P2C)·DeviceAwareWeighted 정책에서 disagg-bootstrap이 가능해져, 어떤 로드밸런서를 골라도 prefill/decode 분리가 동작한다. 또한 통합 vLLM 백엔드에 동적 LoRA 지원을 추가하고, 요청 mocker가 지연 예측에 aiconfigurator(AIC) Rust 크레이트를, num_gpu_blocks에 통합 KV 캐시 API를 쓰도록 업그레이드했다. 작은 수정으로 encode_messages용 DeepSeek-V4 tool-call 인자를 JSON 문자열로 유지하고, 라우터 블록 해시와 함께 SGLang KV 이벤트를 발행한다 — 종합하면 분산·어댑터의 적용 범위를 넓히는 흐름이다.

Direct Latent-Space Synthesis for Parallel Branches in LLM-Agent Workflowsagentic inference2606.14672
Towards Direct Latent-Space Synthesis for Parallel Branches in LLM-Agent Workflows (arXiv 2606.14672, submitted Jun 12) ↗Towards Direct Latent-Space Synthesis for Parallel Branches in LLM-Agent Workflows (arXiv 2606.14672, 6/12 제출) ↗
Problem문제 정의LLMs increasingly act as execution engines for agent systems, yet they still consume context through a sequential text interface. That mismatches modern structured agent workflows, where independent branches explore subtasks, retrieve evidence, or generate candidates in parallel and must be stitched back together as text.LLM은 점점 에이전트 시스템의 실행 엔진 역할을 하지만 여전히 순차적 텍스트 인터페이스로 컨텍스트를 소비한다. 이는 독립 분기들이 하위작업 탐색·증거 검색·후보 생성을 병렬로 하고 다시 텍스트로 꿰매야 하는 현대의 구조화된 에이전트 워크플로와 어긋난다.
Method방법The paper proposes synthesizing parallel branches directly in latent (cache) space instead of re-encoding each branch's text. Branch representations are combined as cached states, giving a more native interface for parallel agent execution.논문은 각 분기의 텍스트를 다시 인코딩하는 대신 병렬 분기를 잠재(캐시) 공간에서 직접 합성할 것을 제안한다. 분기 표현을 캐시된 상태로 결합해 병렬 에이전트 실행에 더 네이티브한 인터페이스를 제공한다.
Results결과Direct cache-based synthesis yields 2.5×–11× speedups over the sequential text interface, suggesting it is a promising path to more native and efficient synthesis across parallel agent branches.캐시 기반 직접 합성은 순차 텍스트 인터페이스 대비 2.5×–11× 속도 향상을 내며, 병렬 에이전트 분기에 더 네이티브하고 효율적인 합성으로 가는 유망한 길임을 시사한다.
Summary요약Stop re-reading each branch as text — merge parallel agent branches in cache space and get up to 11× faster synthesis.각 분기를 텍스트로 다시 읽지 말라 — 병렬 에이전트 분기를 캐시 공간에서 합치면 합성이 최대 11× 빨라진다.

Neither Parallel Nor Sequential: How DiffusionGemma Actually Commits Tokens (arXiv 2606.14620, submitted Jun 12) ↗Neither Parallel Nor Sequential: How DiffusionGemma Actually Commits Tokens (arXiv 2606.14620, 6/12 제출) ↗
Problem문제 정의Open diffusion language models are marketed as parallel, non-autoregressive decoders, yet the order in which a shipped checkpoint actually commits its tokens is almost never measured. Without that measurement, claims about "parallel" decoding — and the serving optimizations that assume it — rest on marketing rather than observed behavior.오픈 디퓨전 언어모델은 병렬·비자기회귀 디코더로 홍보되지만, 출시된 체크포인트가 실제로 토큰을 확정하는 순서는 거의 측정되지 않는다. 그 측정이 없으면 "병렬" 디코딩 주장과 그것을 전제한 서빙 최적화는 관찰이 아니라 홍보에 기댄다.
Method방법The authors instrument DiffusionGemma 26B — a masked discrete-diffusion mixture-of-experts model built on Gemma 4 — hooking its decode loop to record exactly when each position is committed, and controlling for confounds like monotonicity, block-size sensitivity, and large commit-batch ties that can manufacture a decoding-order result that isn't really there.저자들은 DiffusionGemma 26B(Gemma 4 기반 마스크드 이산 디퓨전 MoE)를 계측해 디코드 루프를 후킹, 각 위치가 언제 확정되는지를 정확히 기록하고, 실재하지 않는 디코딩 순서 결과를 만들어 낼 수 있는 단조성·블록 크기 민감도·대형 커밋 배치 동률 같은 교란 요인을 통제한다.
Results결과The measured commit order is neither cleanly parallel nor strictly sequential, and naive measurement can fabricate an apparent order; careful instrumentation is needed to characterize how diffusion LLMs actually decode.측정된 커밋 순서는 깔끔한 병렬도 엄격한 순차도 아니며, 안일한 측정은 겉보기 순서를 날조할 수 있다 — 디퓨전 LLM이 실제로 어떻게 디코딩하는지 특징짓는 데는 세심한 계측이 필요하다.
Summary요약"Parallel" diffusion decoding is a marketing label — instrument the checkpoint and the real token-commit order is messier, which matters for how you serve it."병렬" 디퓨전 디코딩은 홍보 라벨이다 — 체크포인트를 계측하면 실제 토큰 커밋 순서는 더 지저분하며, 이는 서빙 방식에 영향을 준다.

Native INT8 Compute for Diffusion Transformers on Consumer GPUs — a fused INT8 GEMM kernelquantization2606.14598
Realizing Native INT8 Compute for Diffusion Transformers on Consumer GPUs: A Fused INT8 GEMM Kernel for Ideogram 4.0 (arXiv 2606.14598, submitted Jun 12) ↗Realizing Native INT8 Compute for Diffusion Transformers on Consumer GPUs: A Fused INT8 GEMM Kernel for Ideogram 4.0 (arXiv 2606.14598, 6/12 제출) ↗
Problem문제 정의Post-training INT8 (W8A8) quantization of diffusion transformers is deployed widely as a speed optimization, yet on consumer Ampere GPUs it is frequently slower than the FP8 and NF4 alternatives it is supposed to beat.
