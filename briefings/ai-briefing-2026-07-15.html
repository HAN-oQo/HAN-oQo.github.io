vLLM v0.25.1 — guard mixed-dtype allreduce+RMSNorm quant fusion, defer TorchCodec import so missing FFmpeg no longer blocks startup vLLMJul 14

vLLM cut a patch tag v0.25.1 on Jul 14, two targeted fixes on top of v0.25.0. The headline fix guards the fused FlashInfer allreduce + RMSNorm + static-quant pattern, which could match graphs where the activation and RMSNorm-weight dtypes differ (e.g. a BF16 residual stream with an FP32 Gemma/Qwen-style RMSNorm weight in NVFP4 models), corrupting the hidden state into garbage "!!!" output (#48330). The second defers the TorchCodec import error to runtime so a missing system FFmpeg no longer blocks vllm serve startup (#47888). Underneath, main stayed busy (~70 commits across the window): a TPOT optimization for thinking-budget speculative decoding (#46662), split write/read KV-offload usage gauges (#47666), an MLA+SWA fix to check the layer backend rather than model config (#48520), and a DSv3.2 + MTP + sequence-parallel accuracy fix (#48036).

vLLM은 7/14 패치 태그 v0.25.1을 냈다 — v0.25.0 위 두 개의 표적 수정이다. 핵심 수정은 융합된 FlashInfer allreduce + RMSNorm + 정적 양자화 패턴을 방어한다. 이 패턴은 활성값과 RMSNorm 가중치의 dtype이 다를 때(예: NVFP4 모델에서 BF16 잔차 스트림 + FP32 Gemma/Qwen식 RMSNorm 가중치) 그래프에 잘못 매칭돼 은닉 상태를 "!!!" 쓰레기 출력으로 망가뜨렸다(#48330). 두 번째는 TorchCodec 임포트 오류를 런타임으로 미뤄, 시스템 FFmpeg가 없어도 vllm serve 시작을 막지 않게 했다(#47888). 그 아래 main은 계속 바빴다(구간 ~70커밋) — thinking-budget 추측 디코딩의 TPOT 최적화(#46662), KV 오프로드 사용량을 쓰기·읽기로 분리한 게이지(#47666), 모델 설정이 아닌 레이어 백엔드를 확인하도록 한 MLA+SWA 수정(#48520), DSv3.2 + MTP + 시퀀스 병렬 정확도 수정(#48036).

Problem문제 정의MoE LLMs activate only a few experts per token, but routing creates persistent "hotness skew": a small set of hot experts keeps receiving most tokens while the rest sit idle. On 3.5D multi-chiplet systems this skew doesn't just imbalance compute — it piles pressure onto communication, memory bandwidth, I/O, and execution queues.MoE LLM은 토큰당 소수 전문가만 활성화하지만, 라우팅은 지속적 "hotness 편중"을 만든다 — 소수 hot 전문가가 대부분 토큰을 계속 받고 나머지는 논다. 3.5D 멀티칩렛 시스템에서 이 편중은 연산 불균형에 그치지 않고 통신·메모리 대역폭·I/O·실행 큐에 압력을 쌓는다.
Method방법HCRMap is a residency-mapping framework that treats the goal not as "move fewer tokens" but as dynamically placing and reusing hot-expert replicas across memory tiers. Using expert hotness, weight-loading cost, migration overhead, and runtime resource pressure, it decides which experts to promote, replicate, or demote.HCRMap는 목표를 "토큰 이동 최소화"가 아니라 hot 전문가 복제본을 메모리 계층에 동적으로 배치·재사용하는 것으로 보는 레지던시 매핑 프레임워크다. 전문가 hotness, 가중치 로딩 비용, 마이그레이션 오버헤드, 런타임 자원 압력을 이용해 어떤 전문가를 승격·복제·강등할지 결정한다.
Results결과By promoting hot replicas into faster tiers and keeping cold experts cheaply resident, HCRMap relieves the coupled compute/bandwidth/I-O pressure that plain token-routing balancing ignores, targeting steadier throughput on chiplet MoE inference.hot 복제본을 빠른 계층으로 승격하고 cold 전문가를 값싸게 상주시켜, HCRMap는 단순 토큰 라우팅 균형이 무시하는 결합된 연산·대역폭·I/O 압력을 완화하고 칩렛 MoE 추론에서 더 안정적인 처리량을 노린다.

Problem문제 정의Speculative decoding accelerates text LLMs but yields limited gains on vision-language models: drafters diverge on vision-critical content, and existing multimodal accelerators neither filter irrelevant visual evidence nor optimize the verifier-accepted prefix length that governs speedup.추측 디코딩은 텍스트 LLM을 가속하지만 비전-언어 모델에선 이득이 제한된다 — 드래프터가 비전 핵심 내용에서 발산하고, 기존 멀티모달 가속기는 무관한 시각 증거를 거르지도, 속도를 좌우하는 검증자 수용 접두 길이를 최적화하지도 못한다.
