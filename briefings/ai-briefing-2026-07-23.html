SpecLA: Efficient Speculative Decoding for Linear-Attention Modelsspeculative decodinglinear attention2607.16673
SpecLA (arXiv 2607.16673) ↗SpecLA (arXiv 2607.16673) ↗
Problem문제 정의Speculative decoding is well studied for standard Transformers, but linear-attention (and gated linear-attention) models keep a compact recurrent state instead of a growing KV cache, so the usual trick of cheaply re-running verification over cached keys and values does not map onto them. Naively porting draft-and-verify to these stateful models forces expensive state rollbacks and breaks the acceptance bookkeeping.투기 디코딩은 표준 트랜스포머에는 잘 연구돼 있지만, 선형 어텐션(및 게이트 선형 어텐션) 모델은 커지는 KV 캐시 대신 압축된 순환 상태를 유지해, 캐시된 키·값 위에서 검증을 값싸게 재실행하는 통상적 기법이 적용되지 않는다. 이 상태 기반 모델에 초안-검증을 그대로 이식하면 비싼 상태 롤백이 강제되고 채택 계산이 어긋난다.
Method방법SpecLA is a speculative-decoding runtime built for stateful linear-attention targets. It verifies both chains and trees of draft tokens with topology-aware kernels that respect the recurrent state, prunes low-confidence branches, and pairs the target with a target-aligned, EAGLE-style drafter so proposed tokens match the target's distribution closely.SpecLA는 상태 기반 선형 어텐션 타깃을 위한 투기 디코딩 런타임이다. 순환 상태를 존중하는 위상 인지 커널로 초안 토큰의 체인과 트리를 함께 검증하고, 확신이 낮은 가지를 프루닝하며, 타깃 분포에 가깝게 제안하도록 타깃 정렬 EAGLE 스타일 드래프터를 짝짓는다.
Results결과On an NVIDIA H100 with a public GDN-1.3B linear-attention target, SpecLA reports up to a 1.70× end-to-end speedup over plain autoregressive decoding while remaining lossless, showing that topology-aware verification plus confidence pruning make speculation practical for the linear-attention family.NVIDIA H100에서 공개 GDN-1.3B 선형 어텐션 타깃을 대상으로 SpecLA는 무손실을 유지하면서 순수 자기회귀 디코딩 대비 최대 1.70배의 종단 간 가속을 보고하며, 위상 인지 검증과 확신 기반 프루닝이 선형 어텐션 계열에도 투기를 실용화함을 보인다.
Summary요약Make speculative decoding work on stateful linear-attention models by verifying chains/trees with state-aware kernels and an aligned drafter.상태 인지 커널과 정렬 드래프터로 체인·트리를 검증해, 상태 기반 선형 어텐션 모델에서도 투기 디코딩이 작동하게 하라.

Accelerating Masked Diffusion Large Language Models: A Survey of Efficient Inference Techniquesdiffusion LLMsurvey2607.12829
Masked diffusion LLM inference survey (arXiv 2607.12829) ↗마스크드 디퓨전 LLM 추론 서베이 (arXiv 2607.12829) ↗
Problem문제 정의Masked diffusion LLMs (dLLMs) promise a theoretical edge over autoregressive models because they can, in principle, reveal many tokens in parallel rather than one at a time. In practice, parallel generation alone does not translate into real wall-clock speedups, and the literature on how to actually make dLLM inference fast is scattered.마스크드 디퓨전 LLM(dLLM)은 원리적으로 토큰을 하나씩이 아니라 여러 개를 병렬로 드러낼 수 있어 자기회귀 모델 대비 이론적 이점을 약속한다. 그러나 실제로는 병렬 생성만으로 실측 속도 향상이 되지 않으며, dLLM 추론을 실제로 빠르게 만드는 방법에 대한 문헌은 흩어져 있다.
Method방법This survey (KAIST / Yonsei) organizes efficient-inference techniques for masked dLLMs into a taxonomy: diffusion-aware KV/feature caching and reuse across denoising steps, parallel-decoding and token-commit schedules that decide how many tokens to unmask per step, distillation of the number of steps, and hardware-oriented kernels. It maps how each family trades off quality against step count and throughput.이 서베이(KAIST/연세대)는 마스크드 dLLM의 효율적 추론 기법을 분류 체계로 정리한다: 디노이징 스텝 간 디퓨전 인지 KV/특징 캐싱·재사용, 스텝당 몇 개 토큰을 언마스크할지 정하는 병렬 디코딩·토큰 커밋 스케줄, 스텝 수 증류, 하드웨어 지향 커널. 각 계열이 품질과 스텝 수·처리량을 어떻게 절충하는지 도식화한다.
Results결과The survey's takeaway is that realized speedups come from specialized mechanisms — especially caching/reuse and adaptive token-commit schedules — rather than from parallelism per se, and it highlights open problems such as reliable confidence estimates for how many tokens to commit and cache invalidation as the denoising trajectory changes.서베이의 결론은 실현되는 속도 향상이 병렬성 자체가 아니라 특화된 메커니즘 — 특히 캐싱·재사용과 적응형 토큰 커밋 스케줄 — 에서 온다는 것이며, 몇 개 토큰을 커밋할지에 대한 신뢰할 만한 확신 추정과 디노이징 궤적 변화에 따른 캐시 무효화 같은 미해결 문제를 짚는다.
Summary요약A map of efficient-inference techniques for masked diffusion LLMs: caching, token-commit schedules, and step distillation matter more than raw parallelism.마스크드 디퓨전 LLM의 효율적 추론 기법 지도 — 캐싱·토큰 커밋 스케줄·스텝 증류가 순수 병렬성보다 중요하다.

PEEK: Predictive Queue-Informed KV Cache Management for LLM ServingKV cachescheduling2607.02525
PEEK (arXiv 2607.02525) ↗PEEK (arXiv 2607.02525) ↗
Problem문제 정의Prefix caching lets many requests that share a common prefix reuse the same KV blocks, but engines schedule and evict blocks looking only at requests already running — they are blind to the pending queue. As a result they can evict a prefix that a soon-to-be-admitted sibling request will need, and they admit requests in an order that fails to exploit sharing.프리픽스 캐싱은 공통 프리픽스를 공유하는 여러 요청이 같은 KV 블록을 재사용하게 하지만, 엔진은 이미 실행 중인 요청만 보고 블록을 스케줄·축출한다 — 대기 큐를 보지 못한다. 그 결과 곧 들어올 형제 요청이 필요로 할 프리픽스를 축출하고, 공유를 살리지 못하는 순서로 요청을 받아들인다.
Method방법PEEK maintains an incremental radix tree over the pending queue to expose prefix-sharing clusters, uses a low-overhead dual-walk to match that tree against the engine's prefix cache (longest-prefix-match on every waiting request), admits each cluster's "pioneer" first so siblings inherit the freshly cached prefix, adds an eviction hook that protects blocks ancestral to queued demand, and runs a multi-lane stride scheduler to bound starvation.PEEK은 대기 큐 위에 증분 래딕스 트리를 유지해 프리픽스 공유 클러스터를 드러내고, 저오버헤드 이중 워크로 그 트리를 엔진 프리픽스 캐시와 대조하며(대기 요청마다 최장 프리픽스 매칭), 각 클러스터의 "선발대"를 먼저 받아들여 형제가 갓 캐시된 프리픽스를 물려받게 하고, 큐 수요의 조상 블록을 보호하는 축출 훅을 더하며, 기아를 막는 다중 레인 스트라이드 스케줄러를 돌린다.
Results결과On SGLang and vLLM across five workloads up to 4×H100 (DP=2 over TP=2), PEEK reports up to 3.0×/2.6× cache hit, 7.9×/7.1× TTFT, 6.7×/5.5× end-to-end, and 3.6×/4.5× throughput gains over each engine's strongest stock baseline, while matching baselines within noise on workloads with no exploitable prefix structure. The gains hold as KV-cache pressure and inference parallelism scale.SGLang·vLLM에서 최대 4×H100(TP=2 위 DP=2)의 다섯 워크로드에 대해 PEEK은 각 엔진의 최강 기본 대비 캐시 적중 최대 3.0×/2.6×, TTFT 7.9×/7.1×, 종단 간 6.7×/5.5×, 처리량 3.6×/4.5× 향상을 보고하며, 살릴 프리픽스 구조가 없는 워크로드에선 기본과 오차 범위 내로 맞춘다. 이 이득은 KV 캐시 압력과 추론 병렬성이 커져도 유지된다.
Summary요약Schedule and evict the KV cache using a radix tree over the pending queue, so prefix sharing is planned before requests are even admitted.대기 큐 위 래딕스 트리로 KV 캐시를 스케줄·축출해, 요청을 받아들이기 전에 프리픽스 공유를 미리 계획하라.

CacheWeaver: Cache-Aware Evidence Ordering for Efficient Grounded RAG Inferenceprefix cacheRAG2606.19667
CacheWeaver (arXiv 2606.19667) ↗CacheWeaver (arXiv 2606.19667) ↗
Problem문제 정의In retrieval-augmented generation, each query stuffs several retrieved passages into the prompt. Prefix caching can reuse KV state for a shared leading context, but retrieval returns passages in relevance order, which scatters reusable evidence and defeats the cache — so time-to-first-token stays high even when the same passages have been served before.검색 증강 생성(RAG)에서는 각 쿼리가 검색된 여러 지문을 프롬프트에 채운다. 프리픽스 캐싱은 공유되는 앞부분 맥락의 KV 상태를 재사용할 수 있지만, 검색은 지문을 관련도 순으로 반환해 재사용 가능한 근거가 흩어지고 캐시가 무력화된다 — 같은 지문을 이전에 제공했어도 TTFT가 높게 남는다.
Method방법CacheWeaver is a lightweight prompt-layer method for cache-aware evidence ordering: it keeps a prefix tree over recently served evidence sequences and uses a greedy walk to place the most reusable passages first, so a new query's prompt maximizes the overlap with already-cached prefixes before appending the query-specific tail.CacheWeaver는 캐시 인지 근거 정렬을 위한 가벼운 프롬프트 계층 기법이다: 최근 제공된 근거 시퀀스 위에 프리픽스 트리를 유지하고 그리디 워크로 가장 재사용성 높은 지문을 앞에 배치해, 새 쿼리 프롬프트가 쿼리 고유 꼬리를 붙이기 전에 이미 캐시된 프리픽스와의 겹침을 최대화하게 한다.
Results결과Reordering evidence to align with the cache lowers median TTFT by roughly 20–33% relative to serving passages in retrieval order, without hurting answer quality on QA benchmarks — a purely prompt-side win that needs no engine changes.캐시에 맞춰 근거를 재정렬하면 지문을 검색 순으로 제공할 때 대비 중앙값 TTFT를 약 20~33% 낮추며, QA 벤치마크에서 답변 품질을 해치지 않는다 — 엔진 변경이 필요 없는 순수 프롬프트 측 이득이다.
Summary요약Reorder RAG evidence to front-load cache-reusable passages, cutting TTFT ~20–33% with no quality loss and no engine changes.RAG 근거를 캐시 재사용 가능한 지문이 앞에 오도록 재정렬해, 품질 손실·엔진 변경 없이 TTFT를 약 20~33% 줄여라.
