Broadcast, Don’t Replicate: Eliminating Weight HBM in Datacenter LLM Servingmemory architectureopticalarXiv:2611.17097
arxiv.org/abs/2611.17097 →

Problem문제 정의Model weights are read-only and identical across instances, yet datacenters replicate them in the local memory of tens of thousands of accelerators, paying in capital cost, static power and redundant fetch energy. A prior optical delay-line ring must hold the whole model, so its length grows with model size and it fits MoE layouts poorly.모델 가중치는 읽기 전용이고 인스턴스마다 동일한데도 데이터센터는 이를 수만 개 가속기의 로컬 메모리에 복제해 설비 비용, 정적 전력, 중복 읽기 에너지를 치른다. 이전의 광 지연선 링 방식은 모델 전체를 담아야 해서 모델이 커질수록 길이가 늘고 MoE 배치와 잘 맞지 않는다.

Method방법Optical Broadcast Memory (OBM) is a hierarchical tap-and-amplify fiber network: a central memory server continuously broadcasts weights, and inference nodes passively tap the stream with receive-only co-packaged optics, feeding compute units without intermediate buffering. Dynamically sized slack absorbs large and variable context lengths.Optical Broadcast Memory(OBM)는 계층형 tap-and-amplify 광섬유 네트워크다. 중앙 메모리 서버가 가중치를 계속 방송하고, 추론 노드는 수신 전용 co-packaged optics로 스트림을 수동적으로 받아 중간 버퍼 없이 연산 유닛에 공급한다. 동적으로 크기가 정해지는 슬랙이 크고 가변적인 컨텍스트 길이를 흡수한다.

Results결과Evaluated at a scale of 80,000 accelerators, OBM eliminates petabytes of HBM while matching or beating an HBM-based system in throughput and energy per token, and it serves MoE models efficiently once the ring restriction is removed.가속기 8만 개 규모에서 평가했을 때 OBM은 페타바이트급 HBM을 없애면서도 처리량과 토큰당 에너지에서 HBM 기반 시스템과 대등하거나 더 낫고, 링 제약을 없앤 덕분에 MoE 모델도 효율적으로 서빙한다.

Summary요약Treating weights as a shared broadcast stream rather than per-device copies removes weight HBM from the serving node.가중치를 장치별 복사본이 아니라 공유 방송 스트림으로 다뤄 서빙 노드에서 가중치용 HBM을 없앤다.

arxiv.org/abs/2611.16661 →

Problem문제 정의Benchmark evaluation, synthetic-data generation and RL rollouts run batches of agent tasks that alternate between LLM inference and environment interaction, and the slowest tasks set the batch makespan.벤치마크 평가, 합성 데이터 생성, RL 롤아웃은 LLM 추론과 환경 상호작용을 번갈아 하는 에이전트 작업을 배치로 실행하며, 가장 느린 작업이 배치 완료 시간(makespan)을 결정한다.

Method방법For hybrid LLMs, a workload-based resource model splits GPU memory between KV cache and recurrent state and sets a reference concurrency. Trajectory-aware routing and scheduling promote cache reuse while balancing load, and Chain-Advancing Action Scheduling (CAAS) decouples admission from environment execution and prioritizes long chains by observed progress.하이브리드 LLM에 대해 워크로드 기반 자원 모델이 GPU 메모리를 KV 캐시와 순환 상태에 나누고 기준 동시성을 정한다. 궤적 인지 라우팅·스케줄링은 부하를 맞추면서 캐시 재사용을 늘리고, Chain-Advancing Action Scheduling(CAAS)은 샘플 진입을 환경 실행과 분리해 관측된 진행도로 긴 체인을 우선 처리한다.

Results결과Live runs with Ling-3.0-Flash and Ling-3.1-Flash on BFCL, SWE-bench Multilingual, WideSearch and MCP-Atlas cut makespan by 10.4% to 65.0% with evaluation scores aligned; the methods are used in Ling-3.x training and evaluation.BFCL, SWE-bench Multilingual, WideSearch, MCP-Atlas에서 Ling-3.0-Flash와 Ling-3.1-Flash로 실측한 결과 평가 점수는 그대로 두고 makespan을 10.4~65.0% 줄였으며, 이 방법은 Ling-3.x 학습·평가에 쓰이고 있다.

Summary요약Coordinating the inference engine with the environment shortens the batch tail of agent workloads.추론 엔진과 환경을 함께 조율해 에이전트 워크로드 배치의 꼬리를 줄인다.

Read Once, Answer Many: Parallel Prompting for Shared-Context LLM InferencedecodingSGLangarXiv:2611.15130
arxiv.org/abs/2611.15130 →

Problem문제 정의Document QA, data labeling and LLM-based evaluation ask many independent questions about one long document. Prefix caching removes the shared prefill, but each decode step still reads the document’s KV cache once per question, so decoding stays bandwidth-bound and scales with the number of questions.문서 QA, 데이터 라벨링, LLM 기반 평가는 긴 문서 하나에 독립적인 질문을 여럿 던진다. 프리픽스 캐싱은 공유 프리필을 없애지만 디코드 단계마다 문서 KV 캐시를 질문마다 한 번씩 읽으므로 디코딩이 대역폭에 묶이고 질문 수에 비례해 늘어난다.

Method방법Parallel Prompting decodes P questions as P independent streams of a single request, so every step reads the shared document once for all streams. A stream-id attention mask evaluated inside the kernel keeps each answer conditioned only on the document and its own question; the change adds about 80 lines to three SGLang files plus a small engine package, and each step has a fixed shape captured as a CUDA graph.Parallel Prompting은 P개의 질문을 한 요청의 독립 스트림 P개로 동시에 디코딩해 매 단계 공유 문서를 모든 스트림에 대해 한 번만 읽는다. 커널 안에서 평가되는 스트림 ID 어텐션 마스크가 각 답이 문서와 자기 질문에만 조건화되도록 하며, SGLang 파일 세 개에 약 80줄과 작은 엔진 패키지를 더했고 매 단계 형상이 고정되어 CUDA 그래프로 캡처된다.

Results결과With CodeLlama-7B, 8k–16k-token documents and 64–256 questions per document, it is 3.7x faster than stock SGLang with FlashInfer on an A100 and 5.9–6.0x faster on an RTX A6000, and faster in all 144 timed runs.CodeLlama-7B, 8k~16k 토큰 문서, 문서당 64~256개 질문 조건에서 A100의 기본 SGLang(FlashInfer) 대비 3.7배, RTX A6000에서 5.9~6.0배 빨랐고 측정한 144회 모두에서 더 빨랐다.

Summary요약Batching questions inside one request turns per-question KV reads into one shared read.질문들을 한 요청 안에 묶어 질문별 KV 읽기를 한 번의 공유 읽기로 바꾼다.
