vLLM — Model Runner V2 learns to estimate acceptance, and quantization picks its own linear backend Sep 14

Sixty-nine commits, no new tag. The most forward-looking change is in Model Runner V2: acceptance estimation for adaptive verification. Speculative decoding usually verifies a fixed number of draft tokens per step; estimating the acceptance rate online is the prerequisite for deciding how many to verify, which is the difference between a speedup that holds on one workload and one that adapts to the traffic actually arriving. Alongside it, MRV2 learned to run pooling post-processing on non-final pipeline-parallel ranks, removing a needless serialization at the end of the pipeline. On the quantization side, linear backends are now selected per quantization scheme rather than globally — a small piece of plumbing that stops one scheme's best kernel from being imposed on another — and ReLU2 was fused with static FP8 activation quantization, collapsing an activation and its quantization into one pass. Metrics grew up too: MFU/MBU estimation now understands sliding-window attention and hybrid layers, so the utilization numbers stop silently assuming dense full attention. The ROCm DeepSeek-V4.1 lane stayed busy — the mHC post step was folded into the delayed pre-projection, the DSA decode candidate mask is strided over the live context rather than the full allocation, and CSA multi-stream overlap was enabled for DeepSeek-V4. Correctness and hygiene items: a padded-vocab d2t requirement was fixed for Qwen3 DSpark drafts, in-flight async lookup probes are reused in KV offload instead of being reissued, Qwen-VL video sampling knobs were capped, and credentials are now redacted from benchmark logs. 커밋 69개, 새 태그 없음. 가장 앞을 내다보는 변경은 Model Runner V2에 있다. 적응형 검증을 위한 수용률 추정이다. 스펙 디코딩은 보통 매 단계 정해진 개수의 초안 토큰을 검증하는데, 수용률을 온라인으로 추정하는 것은 몇 개를 검증할지 정하기 위한 전제 조건이다. 한 워크로드에서만 유지되는 속도 향상과 실제로 들어오는 트래픽에 맞춰 움직이는 속도 향상의 차이가 여기서 갈린다. 그 옆에서 MRV2는 파이프라인 병렬의 마지막이 아닌 랭크에서도 풀링 후처리를 돌리는 법을 배워, 파이프라인 끝단의 불필요한 직렬화를 걷어냈다. 양자화 쪽에서는 선형 백엔드가 전역이 아니라 양자화 방식별로 선택된다. 한 방식의 최적 커널이 다른 방식에 강요되지 않게 하는 작은 배관 작업이다. 그리고 ReLU2가 정적 FP8 활성값 양자화와 융합돼, 활성화와 그 양자화가 한 패스로 접혔다. 메트릭도 자랐다. SGLang — a DCP double-free is closed at the page boundary, and gfx950 attention gets length-aware split-KV Sep 14

Forty-three commits, no new tag. The sharpest fix is a memory-safety one: adjacent KV-row frees are now merged so that a mid-page split under decode context parallelism cannot double-free. A page that is split across CP ranks can have its halves returned independently, and without coalescing the allocator sees the same page freed twice — the class of bug that surfaces as corrupted output long after the real fault. A second ordering fix makes DeepSeek-V4 K-cache reads wait for PDL, and prefetch cache state is now scoped to the request attempt rather than the request, so a retry does not inherit the state of the attempt that failed. AMD got the bulk of the performance work: gfx950 assembly attention gained length-aware split-KV for dynamic workloads, the chunked-prefill compute budget is now filled exactly rather than approximately, and an FP8 two-pool unified KV landed on gfx950; the GLM-5.2 MI355X MXFP4 image was bumped and TOPK_V2 enabled. On Ascend, CANN 9.1.0 and a5 nightly suites were added to CI and a SWA-mask device mismatch in DSpark verify graph capture was fixed. Prefill-decode work continued — speculative workers may now stage prefill shared reads, and the prefill rank is preserved across rebootstrap — and one batch of four changes was reverted, with one of them relanded in clamped form the same day. 커밋 43개, 새 태그 없음. 가장 날카로운 수정은 메모리 안전 쪽이다. 인접한 KV 행 해제가 병합돼, 디코드 컨텍스트 병렬 아래에서 페이지 중간이 갈린 경우에도 이중 해제가 일어나지 않는다. Dynamo — a refused request stops looking like a server fault, and prompt tokens are shared across clones Sep 14

Twenty-eight commits, no new tag. The change with the longest operational tail is small: when a backend refuses a request it cannot serve, the runtime now returns 400 instead of 500. That single digit decides whether a client retries, whether a load balancer ejects the replica, and whether an on-call page fires — a refusal is the caller's problem, a 500 says the server broke. A second reliability fix stops the request-trace subsystem from losing already-accepted trace records when the frontend exits, which is exactly the moment the traces are most worth having. On the performance side, prompt tokens are now shared across request clones rather than copied per clone — n-best and parallel-sampling fan-out no longer pays for n copies of the same prefix in host memory. The build moved to consuming the upstream vllm-proto crate instead of a vendored copy, the GPU memory service's flock race test stopped failing when the racers never collide, and the AISimulate dependency was upgraded. The rest was documentation and CI plumbing, including codeowner review prompts for the frontend and runtime. 커밋 28개, 새 태그 없음. 운영상 여파가 가장 긴 변경은 작다. 백엔드가 서빙할 수 없는 요청을 거절할 때 런타임이 이제 500 대신 400을 반환한다. 이 숫자 하나가 클라이언트가 재시도할지, 로드밸런서가 레플리카를 빼낼지, 온콜 호출이 울릴지를 가른다. 거절은 호출자의 문제이고, 500은 서버가 망가졌다는 말이다. 두 번째 신뢰성 수정은 프런트엔드가 종료될 때 이미 수락된 트레이스 레코드를 잃던 문제를 막는다. 바로 그 순간이 트레이스가 가장 필요한 때다. 성능 쪽에서는 프롬프트 토큰이 요청 클론마다 복사되지 않고 공유된다. n-best와 병렬 샘플링 팬아웃이 같은 프리픽스를 호스트 메모리에 n번 두는 비용을 더는 치르지 않는다. 빌드는 벤더링된 사본 대신 업스트림 vllm-proto 크레이트를 쓰게 바뀌었고, GPU 메모리 서비스의 flock 경쟁 테스트가 경쟁자들이 충돌하지 않을 때 실패하던 문제가 정리됐으며, AISimulate 의존성이 올라갔다. 나머지는 문서와 CI 배관으로, 프런트엔드·런타임 코드오너 리뷰 프롬프트가 포함된다.

Dissecting GPU Utilization for LLM Inference on Nvidia HopperprofilingdecodearXiv:2609.12923
arxiv.org/abs/2609.12923 →
Problem문제 정의 A single SM-utilization percentage can make an inference workload look compute-saturated while hiding how much useful work is actually being done. The counter is not wrong; it collapses several distinct mechanisms into one number. The problem bites hardest during decode, where each request contributes only one new token and the dense projection GEMMs degenerate into small-row matrix multiplications. SM 사용률 백분율 하나는 추론 워크로드를 연산 포화 상태로 보이게 하면서, 실제로 쓸모 있는 일이 얼마나 되는지는 가려 버린다. 카운터가 틀린 것이 아니라, 서로 다른 여러 기전을 숫자 하나로 접어 버리는 것이다. 이 문제는 디코드 구간에서 가장 크게 물린다. 요청마다 새 토큰 하나만 보태므로 밀집 투영 GEMM이 행 수가 적은 행렬 곱으로 퇴화하기 때문이다.
Method방법 The authors profile vLLM with FlashAttention-3 and cuBLASLt on an H100 NVL across cold prefill, warm prefill and decode, sweeping sequence length and batch size. They replace the usual single utilization number with eight counter-validated views derived from raw Nsight Compute reports, each pinned to a specific NCU counter or an explicit formula. The framing rests on a hardware detail: on Hopper the bfloat16 GMMA path executes in fixed 64-row matrix fragments, so small-batch decode can fill only a small fraction of each fragment with real token rows. 저자들은 H100 NVL에서 FlashAttention-3와 cuBLASLt를 쓰는 vLLM을 콜드 프리필·웜 프리필·디코드에 걸쳐 프로파일링하며 시퀀스 길이와 배치 크기를 훑는다. 흔히 쓰는 사용률 숫자 하나 대신, 원시 Nsight Compute 리포트에서 끌어낸 여덟 가지 카운터 검증 시각을 두며 각각을 특정 NCU 카운터나 명시적 수식에 못 박는다. 이 틀은 하드웨어 사실 하나에 기댄다. Hopper의 bfloat16 GMMA 경로는 고정 64행 행렬 프래그먼트 단위로 실행되므로, 작은 배치 디코드는 각 프래그먼트의 일부만 실제 토큰 행으로 채울 수 있다.
Results결과 The eight views map utilization gaps onto concrete mechanisms — fragment fill, occupancy limits, stall signatures, wave quantization and kernel selection — across four production models and six per-layer kernel roles. The practical upshot is that a high SM-utilization reading during decode is frequently a fragment-fill artifact rather than evidence that the GPU is doing useful arithmetic. 여덟 시각은 사용률의 빈틈을 구체적 기전 — 프래그먼트 채움, 점유율 한계, 정체 신호, 웨이브 양자화, 커널 선택 — 으로 사상하며, 프로덕션 모델 넷과 층별 커널 역할 여섯에 걸쳐 이를 수행한다. 실무적 결론은 디코드 구간의 높은 SM 사용률 수치가 GPU가 쓸모 있는 산술을 하고 있다는 증거이기보다 프래그먼트 채움의 부산물인 경우가 잦다는 것이다.
Summary요약 A measurement paper that argues the standard utilization metric is the wrong instrument for decode, and replaces it with eight views each traceable to a counter. For anyone sizing a decode fleet, the fragment-fill view is the one that changes decisions. 표준 사용률 지표가 디코드를 재기에 잘못된 계측기임을 주장하고, 각각 카운터로 추적 가능한 여덟 시각으로 대체하는 측정 논문이다. 디코드 설비 규모를 잡는 사람에게 결정을 바꾸는 것은 프래그먼트 채움 시각이다.

RoofLang: Enabling AI-Driven Architecting of LLM Inference SystemsDSLoptimizer agentarXiv:2609.12551

Problem문제 정의 AI is already contributing to LLM inference optimization, but almost all of it is profiling-based. Profiling-bound feedback confines the search to the capabilities and measured performance of an existing software stack, so a fundamentally better architecture can never be identified — the search cannot evaluate a design the current stack cannot run. AI는 이미 LLM 추론 최적화에 기여하고 있지만, 그 대부분이 프로파일링에 기반한다. 프로파일링에 묶인 피드백은 탐색을 기존 소프트웨어 스택의 능력과 측정된 성능 안으로 가둔다. 그래서 근본적으로 더 나은 아키텍처는 결코 발견될 수 없다. 현재 스택이 돌릴 수 없는 설계를 탐색이 평가할 수 없기 때문이다.
Method방법 The authors argue that an AI-driven architecting loop needs three things: a general workload representation, a verifiable mutation space, and an implementation-independent evaluator. RoofLang is a domain-specific language providing all three, so a candidate architecture can be described, mutated under verification, and scored without being built first. 저자들은 AI 주도 아키텍처 설계 루프에 세 가지가 필요하다고 주장한다. 일반적인 워크로드 표현, 검증 가능한 변이 공간, 구현에 의존하지 않는 평가기다. RoofLang은 이 셋을 모두 제공하는 도메인 특화 언어로, 후보 아키텍처를 먼저 구현하지 않고도 기술하고, 검증 아래에서 변이시키고, 점수를 매길 수 있게 한다.
Results결과 RoofLang reports that DeepSeek V4-series models could reach 3.5–39.5× higher peak decode throughput than other representative models, a gap the paper calls disproportionate to their total parameter counts and attributes largely to compact KV-cache designs that support larger batches and reduce memory traffic. A persistent optimizer agent further discovered several new architectures improving both throughput and interactivity of DeepSeek V4 Pro on NVIDIA B300 by 6.23–50.1%. RoofLang은 DeepSeek V4 계열 모델이 다른 대표 모델보다 최대 디코드 처리량이 3.5~39.5배 높을 수 있다고 보고한다. 논문은 이 격차가 총 파라미터 수에 비해 불균형하다고 말하며, 배치를 키우고 메모리 트래픽을 줄이는 촘촘한 KV 캐시 설계에 크게 기인한다고 본다. 지속 동작하는 최적화 에이전트는 나아가 NVIDIA B300에서 DeepSeek V4 Pro의 처리량과 상호작용성을 함께 6.23~50.1% 개선하는 새 아키텍처 여럿을 발견했다.
Summary요약 The argument is that the bottleneck in AI-assisted serving optimization is the feedback signal, not the model doing the optimizing. Replace profiling with an implementation-independent evaluator and the search can propose architectures the current stack has never run. AI 보조 서빙 최적화의 병목이 최적화를 수행하는 모델이 아니라 피드백 신호라는 주장이다. 프로파일링을 구현 독립 평가기로 바꾸면, 탐색은 현재 스택이 한 번도 돌려본 적 없는 아키텍처를 제안할 수 있다.

HeatCache: Thermal-aware Energy-efficient LLM Inference Scheduling for Chassis-level Liquid CoolingschedulingenergyarXiv:2609.12449
arxiv.org/abs/2609.12449 →
Problem문제 정의 LLM inference is increasingly deployed at institution-scale edges, where multi-GPU serving consumes a large amount of electricity and produces substantial heat. To improve sustainability, operators and regulations often demand raising the ambient setpoint to cut cooling electricity — but a warmer room increases thermal throttling and hardware aging, which turns into SLO violations. LLM 추론은 점점 기관 규모의 엣지에 배치되고, 거기서 다중 GPU 서빙은 많은 전력을 쓰고 상당한 열을 낸다. 지속가능성을 위해 운영자와 규제는 냉방 전력을 줄이려고 주변 온도 설정을 올리라고 요구하곤 한다. 그런데 방이 더워지면 열 스로틀링과 하드웨어 노화가 늘고, 그것이 SLO 위반으로 나타난다.
Method방법 HeatCache is a thermal-aware, energy-efficient scheduler for commercial chassis-level all-in-one liquid-cooled GPUs. The key move is to treat the AIO loop as a temporary heat buffer — measured as a heat budget — rather than as a fixed cooling capacity. Requests are then scheduled to minimize energy subject to thermal-safety and SLO constraints, using an electrically informed heat-demand estimate from a component the authors call HeatiTS. The implementation sits on top of vLLM. HeatCache는 상용 섀시 수준 일체형 수랭 GPU를 위한 열 인식·에너지 효율 스케줄러다. 핵심 수는 AIO 루프를 고정된 냉각 용량이 아니라 임시 열 버퍼 — 열 예산으로 측정되는 — 로 다루는 것이다. 그 위에서 요청을 열 안전과 SLO 제약 아래 에너지를 최소화하도록 스케줄하며, 저자들이 HeatiTS라 부르는 구성요소의 전기 정보 기반 열 수요 추정을 쓴다. 구현은 vLLM 위에 얹혀 있다.
Results결과 HeatCache reduces computing energy by up to 18.0%, decreases thermal-throttle exposure by 81.7%, and keeps SLO violation rates below 0.9% even at an ambient temperature of 48 °C. The last number is the interesting one: it says the scheduler, not the chiller, is what buys back the headroom when the room is deliberately run hot. HeatCache는 연산 에너지를 최대 18.0% 줄이고, 열 스로틀 노출을 81.7% 낮추며, 주변 온도 48 °C에서도 SLO 위반율을 0.9% 아래로 유지한다. 마지막 숫자가 흥미롭다. 방을 일부러 덥게 돌릴 때 여유를 되사 오는 것이 냉각기가 아니라 스케줄러라는 뜻이기 때문이다.
Summary요약 A serving scheduler whose constraint is temperature rather than memory. It is the rare inference paper where the binding resource is the cooling loop, and it makes the case that the loop's thermal mass is schedulable capacity. 제약이 메모리가 아니라 온도인 서빙 스케줄러다. 묶이는 자원이 냉각 루프인 드문 추론 논문이고, 그 루프의 열 질량이 스케줄 가능한 용량이라는 주장을 편다.

OneLA: Scaling Linear-Attention Decoding to Large Beams in Generative Recommendationlinear attentionbeam decodearXiv:2609.12399
arxiv.org/abs/2609.12399 →
Problem문제 정의 Generative recommendation relies on large-beam decoding to produce hundreds of candidate items, which creates a scaling problem specific to recurrent linear attention. Existing linear-attention serving systems either materialize a full recurrent state for every beam or repeatedly replay the shared history, and both choices cost memory and memory traffic that grow with the beam count. 생성형 추천은 후보 항목 수백 개를 만들기 위해 큰 빔 디코딩에 기댄다. 그것이 순환 선형 어텐션에 고유한 규모 문제를 만든다. 기존 선형 어텐션 서빙 시스템은 빔마다 전체 순환 상태를 실체화하거나 공유된 이력을 반복해서 재생하는데, 두 선택 모두 빔 수에 따라 커지는 메모리와 메모리 트래픽 비용을 치른다.
Method방법 OneLA exploits the structure these workloads actually have — a shared prompt and short divergent suffixes. All beam states are represented by a single shared prompt-derived state plus compact, append-only records of each beam's divergent transitions, so only the state information needed at each decoding step is computed and no beam reconstructs a full recurrent state. A lightweight ancestry index tracks which transition records make up each beam's history, letting beams be updated without moving or copying existing records, and a fused GPU kernel reuses the shared state across beams. OneLA는 이 워크로드가 실제로 가진 구조 — 공유된 프롬프트와 짧게 갈라지는 접미사 — 를 이용한다. 모든 빔 상태를 프롬프트에서 유도한 공유 상태 하나와, 빔마다 갈라진 전이의 촘촘한 추가 전용 기록으로 표현한다. 그래서 디코딩 단계마다 필요한 상태 정보만 계산되고 어떤 빔도 전체 순환 상태를 재구성하지 않는다. 가벼운 계보 인덱스가 각 빔의 이력을 이루는 전이 기록을 추적해, 기존 기록을 옮기거나 복사하지 않고 빔을 갱신할 수 있게 한다. 융합된 GPU 커널이 공유 상태를 빔들 사이에서 재사용한다.
Results결과 The authors' analysis reports 1.54–2.46× end-to-end decode speedups while substantially reducing recurrent-state memory use and data movement. The shape of the gain follows directly from the representation: work scales with how much the beams differ rather than with how many beams there are. 저자들의 분석은 종단 디코드 속도 1.54~2.46배 향상을 보고하면서 순환 상태 메모리 사용과 데이터 이동을 크게 줄인다. 이득의 모양은 표현 방식에서 곧바로 따라 나온다. 작업량이 빔이 몇 개인지가 아니라 빔들이 얼마나 다른지에 비례하게 된다.
Summary요약 The idea generalizes past recommendation: any linear-attention workload where many candidates share a long prefix and diverge late has the same redundancy, and the append-only transition record plus ancestry index is a clean way to stop paying for it. 아이디어는 추천을 넘어 일반화된다. 여러 후보가 긴 프리픽스를 공유하고 늦게 갈라지는 선형 어텐션 워크로드는 모두 같은 중복을 갖고 있고, 추가 전용 전이 기록과 계보 인덱스는 그 비용을 그만 치르게 하는 깔끔한 방법이다.

Problem문제 정의 Auto-regressive decode is bandwidth-bound: every weight byte and every KV-cache byte crosses high-bandwidth memory once per token. A megakernel — fusing the whole decode step into one launch — is the natural answer, but existing automatic megakernel generators cannot deliver generalization across models and correctness guarantees at the same time. 자기회귀 디코드는 대역폭에 묶여 있다. 모든 가중치 바이트와 모든 KV 캐시 바이트가 토큰마다 한 번씩 고대역폭 메모리를 건넌다. 디코드 단계 전체를 하나의 실행으로 융합하는 메가커널이 자연스러운 답이지만, 기존 자동 메가커널 생성기는 모델 전반의 일반화와 정확성 보장을 동시에 내놓지 못한다.
Method방법 ForgeMegakernel generates a per-model decode megakernel using coding agents, pairing a universal knowledge base of ten progressive milestones with an independent mid-state test oracle. The milestones supply the structural properties a working megakernel needs: a fine-grained instruction stream for each SM, dependency counters replacing global synchronization, and a shared-memory buffer pool that balances workload across SMs for more parallelism. The oracle derives the megakernel's mid-states and checks performance, error and precision during generation, so correctness is enforced by the loop rather than hoped for after it. ForgeMegakernel은 코딩 에이전트로 모델별 디코드 메가커널을 생성하며, 열 단계 점진적 이정표로 이뤄진 범용 지식 기반과 독립적인 중간 상태 테스트 오라클을 짝짓는다. 이정표들은 동작하는 메가커널에 필요한 구조적 속성을 공급한다. SM마다의 세밀한 명령 스트림, 전역 동기화를 대체하는 의존성 카운터, SM 사이 작업 균형을 잡아 병렬성을 키우는 공유 메모리 버퍼 풀이다. 오라클은 메가커널의 중간 상태를 유도해 생성 과정 내내 성능·오차·정밀도를 검사한다. 정확성이 사후에 기대되는 것이 아니라 루프에 의해 강제된다.

Problem문제 정의 GPU kernels partition tensors into tiles, and individual tiles finish before the whole tensor does — which is what creates the chance to overlap computation with communication. GPU 커널은 텐서를 타일로 나누고, 개별 타일은 텐서 전체보다 먼저 끝난다. 연산과 통신을 겹칠 기회가 거기서 생긴다. 실제로는 둘의 진행 속도가 어긋난다. 통신은 준비된 데이터가 없으면 멈추고 데이터가 몰려 오면 뒤처지며, 통신 커널 자체가 SM 자원을 먹어 숨으려던 그 연산을 느리게 만든다.
Method방법 Entwine coordinates three things jointly: tile computation order, fine-grained communication, and SM resource allocation. Entwine은 세 가지를 함께 조율한다. 타일 연산 순서, 세밀한 통신, SM 자원 배분이다. 통신에 쓸 데이터가 더 고른 속도로 준비되도록 타일 연산 순서를 바꾸고, 그 스케줄을 SM 기반 세밀 통신과 결합해 타일 결과를 낮은 지연과 낮은 오버헤드로 옮기며, 그다음 둘 사이에 SM을 명시적으로 배분해 통신 진행과 그것이 유발하는 연산 지연을 저울질한다.
