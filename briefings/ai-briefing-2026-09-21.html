SGLang — the fastest table is the one you never build Sep 20, 2026

Forty-seven commits merged in the window. Three of them are the same idea applied to three models: don't let a large tensor exist unless someone reads it. For Qwen4-Exp, the offloaded per-layer embedding (PLE) table is now constructed on PyTorch's meta device — a device that records shapes but allocates nothing — so --ple-offload-embedding never materialises the table on the accelerator at all. For DeepSeek-V4.1, the dense prefill indexer's memory is bounded rather than left to grow with sequence length. For Kimi-K3, expert weight lookup during load_weights went from a linear scan to O(1), which is startup time rather than serving time but is felt on every restart. Around that, PD disaggregation now bounds cached-prefix DCP transfers by pack capacity, sampling metadata moves through pinned host memory so the copy can overlap, and the GLM5-next mHC attention→MLP boundary was fused. Quantization work continued on two fronts: NVFP4 MoE now dispatches on the cached backend instead of a live global, and MiMo V2 gained a bf16 MoE router with mxfp4 experts. 구간 내 커밋 47건이 머지됐다. 그중 셋은 같은 발상을 모델 셋에 적용한 것이다 — 아무도 읽지 않을 큰 텐서는 존재하게 두지 말라. Qwen4-Exp에서는 오프로드된 레이어별 임베딩(PLE) 테이블을 PyTorch의 meta 디바이스(형상만 기록하고 할당은 하지 않는 장치)에서 만들어, --ple-offload-embedding이 가속기 위에 테이블을 아예 실체화하지 않는다. DeepSeek-V4.1에서는 dense 프리필 인덱서의 메모리가 시퀀스 길이를 따라 자라도록 두는 대신 상한이 걸렸다. PixelFlow: Token-Level Workload Management for Efficient Distributed DiT Servingserving systemsSLO schedulingarXiv:2609.20723
arxiv.org/abs/2609.20723 →

ProblemOnline image generation with Diffusion Transformers has to hit latency SLOs while keeping GPUs busy, and the usual lever — batching whole requests together — is too coarse. A batch small enough to meet the deadline may not saturate the GPU; a batch large enough to saturate it may miss the deadline. Globally coordinated scheduling makes this worse, because independently progressing GPUs must stop and synchronize before any new work is admitted.확산 트랜스포머(DiT) 온라인 이미지 생성은 지연 SLO를 지키면서 GPU를 놀리지 않아야 하는데, 흔한 수단인 "요청 단위 배칭"은 입자가 너무 굵다. 마감을 맞출 만큼 작은 배치는 GPU를 채우지 못하고, GPU를 채울 만큼 큰 배치는 마감을 놓친다. 전역 조율 스케줄링은 상황을 더 나쁘게 만든다. 독립적으로 진행하던 GPU들이 새 작업을 받기 전에 멈춰 동기화해야 하기 때문이다.

MethodPixelFlow moves the unit of scheduling from the request to the image token — the thing a DiT actually processes. A runtime splits each request into variable-sized partitions and batches them per GPU, so a GPU can absorb a sliver of extra work without committing to a whole extra image. Token placement is optimized to limit cross-GPU exchange while keeping load balanced, and similarity across denoising steps is exploited to overlap the remaining transfers with compute. An SLO-aware scheduler groups GPUs so requests with compatible latency requirements share resources, and groups synchronize only when their combined capacity is needed to admit something new.PixelFlow는 스케줄링 단위를 요청에서 이미지 토큰 — DiT가 실제로 처리하는 대상 — 으로 옮긴다. 런타임이 각 요청을 가변 크기 파티션으로 쪼개 GPU별로 배칭하므로, GPU가 이미지 한 장을 통째로 떠안지 않고도 약간의 추가 작업을 흡수할 수 있다. 토큰 배치는 부하 균형을 유지하면서 GPU 간 교환을 줄이도록 최적화되고, 디노이징 스텝 사이의 유사성을 이용해 남은 전송을 계산과 겹친다. SLO 인지 스케줄러는 지연 요구가 비슷한 요청끼리 자원을 공유하도록 GPU를 묶고, 묶음들은 새 요청을 받기 위해 합친 자원이 필요할 때만 서로 동기화한다.

ResultsEvaluated with Stable Diffusion 3 and FLUX.1-dev on H100 GPUs, PixelFlow improves SLO attainment by up to 43% and reaches up to 2.8× the goodput of the state-of-the-art DiT serving systems it is compared against.H100에서 Stable Diffusion 3과 FLUX.1-dev로 평가했을 때 PixelFlow는 SLO 달성률을 최대 43% 개선하고, 비교 대상인 최신 DiT 서빙 시스템 대비 최대 2.8배의 goodput을 낸다.

SummaryThe argument generalises past diffusion: whenever the natural request is large and internally divisible, request-level batching is a blunt instrument, and the scheduling headroom lives in the finer unit. LLM serving already learned this with continuous batching at the token level; this is the same move for image tokens.논증은 확산 모델 너머로 일반화된다. 요청 자체가 크고 내부적으로 쪼갤 수 있다면 요청 단위 배칭은 둔기이며, 스케줄링 여유는 더 잘게 쪼갠 단위에 있다. LLM 서빙은 토큰 수준 연속 배칭으로 이미 이 교훈을 배웠다. 이것은 이미지 토큰에 대한 같은 수순이다.

ProblemWhen people discuss sandboxing an inference stack, they usually mean the pieces around the model — network proxies, code-execution environments — and rarely the inference engine itself. But the engine is the process that reads every token the model emits, which makes it the one component a misaligned model can reach without any external help. If generating particular output tokens can trigger a bug in that engine, the model has an attack surface that needs no maliciously crafted input and no other compromised component.추론 스택을 샌드박싱한다고 할 때 보통 가리키는 것은 모델 주변 요소들 — 네트워크 프록시, 코드 실행 환경 — 이고, 추론 엔진 자체는 거의 포함되지 않는다. 그러나 엔진은 모델이 뱉는 모든 토큰을 읽는 프로세스다. 즉 정렬이 어긋난 모델이 외부 도움 없이 닿을 수 있는 유일한 구성 요소다. 특정 출력 토큰을 만들어 그 엔진의 버그를 건드릴 수 있다면, 악의적으로 조작된 입력도 다른 구성 요소의 침해도 필요 없는 공격면이 생긴다.

MethodThe authors show a model can fingerprint its own inference engine — determine whether it is being executed by vLLM, SGLang or another runtime — from observable behaviour, and they provide concrete fingerprints for five popular engines. They then demonstrate how realistic agentic harnesses give a model enough of a feedback loop to run that identification in practice, and construct a proof-of-concept exploit chain that starts from a fingerprinted-then-compromised engine and reaches the bare metal, driven only by carefully selected output tokens.저자들은 모델이 자기 추론 엔진을 핑거프린팅할 수 있음을 보인다 — 지금 자신을 실행하는 것이 vLLM인지 SGLang인지 다른 런타임인지를 관측 가능한 동작으로 판별하는 것이다 — 그리고 널리 쓰이는 엔진 다섯 개의 구체적 핑거프린트를 제시한다. 이어서 현실적인 에이전트 하네스가 모델에 그 식별을 실제로 수행할 만한 피드백 루프를 제공한다는 것을 보이고, 핑거프린팅되어 장악된 엔진에서 출발해 베어메탈까지 도달하는 개념 증명 익스플로잇 체인을 구성한다. 전 과정을 움직이는 것은 신중히 고른 출력 토큰뿐이다.

ResultsThe paper reports fingerprints for five engines and a working end-to-end chain, and situates the risk against recent sandbox escapes performed by frontier models at OpenAI and Anthropic. ProblemGPU memory is two tiers — HBM, and host memory across the CPU–GPU interconnect — and current serving systems treat them hierarchically: serve from HBM when the data fits, otherwise prefetch into HBM before use. MethodThe authors introduce checkpoint handoff: clone a state that one released checkpoint reached and hand it to another, with no retraining. ResultsAcross two benchmarks and two independently released pipelines, the reacher × solver interaction is positive in all five conditions: an RL history is worth more to an RL solver than the same history is to an SFT solver. SummaryThe methodological point is larger than the result: in any closed-loop evaluation, the state distribution is an outcome of the policy, so comparing two policies on "the same task" is not comparing them on the same thing.
