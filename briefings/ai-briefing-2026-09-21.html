SGLang — the fastest table is the one you never build Sep 20, 2026

Forty-seven commits merged in the window. Three of them are the same idea applied to three models: don't let a large tensor exist unless someone reads it. For Qwen4-Exp, the offloaded per-layer embedding (PLE) table is now constructed on PyTorch's meta device — a device that records shapes but allocates nothing — so --ple-offload-embedding never materialises the table on the accelerator at all. For DeepSeek-V4.1, the dense prefill indexer's memory is bounded rather than left to grow with sequence length. For Kimi-K3, expert weight lookup during load_weights went from a linear scan to O(1), which is startup time rather than serving time but is felt on every restart. Around that, PD disaggregation now bounds cached-prefix DCP transfers by pack capacity, sampling metadata moves through pinned host memory so the copy can overlap, and the GLM5-next mHC attention→MLP boundary was fused. Quantization work continued on two fronts: NVFP4 MoE now dispatches on the cached backend instead of a live global, and MiMo V2 gained a bf16 MoE router with mxfp4 experts. 커밋 47건 중 셋은 "아무도 읽지 않을 큰 텐서는 만들지 않는다"는 발상을 모델 셋에 적용했다. PixelFlow: Token-Level Workload Management for Efficient Distributed DiT Servingserving systemsSLO schedulingarXiv:2609.20723
arxiv.org/abs/2609.20723 →

ProblemOnline image generation with Diffusion Transformers has to hit latency SLOs while keeping GPUs busy, and the usual lever — batching whole requests together — is too coarse. A batch small enough to meet the deadline may not saturate the GPU; a batch large enough to saturate it may miss the deadline. Globally coordinated scheduling makes this worse, because independently progressing GPUs must stop and synchronize before any new work is admitted.DiT 이미지 생성 서빙에서 요청 단위 배칭은 너무 굵어, 작은 배치는 GPU를 못 채우고 큰 배치는 SLO를 놓친다. 전역 조율 스케줄링은 새 작업을 받을 때마다 GPU를 멈춰 동기화시켜 더 나쁘다.

MethodPixelFlow moves the unit of scheduling from the request to the image token — the thing a DiT actually processes. A runtime splits each request into variable-sized partitions and batches them per GPU, so a GPU can absorb a sliver of extra work without committing to a whole extra image. Token placement is optimized to limit cross-GPU exchange while keeping load balanced, and similarity across denoising steps is exploited to overlap the remaining transfers with compute. An SLO-aware scheduler groups GPUs so requests with compatible latency requirements share resources, and groups synchronize only when their combined capacity is needed to admit something new.스케줄링 단위를 이미지 토큰으로 바꿔, 요청을 가변 크기 파티션으로 쪼개 GPU별로 배칭하고 디노이징 스텝 간 유사성으로 전송을 계산과 겹친다. SLO 인지 스케줄러가 지연 요구가 비슷한 요청끼리 GPU 묶음을 공유시키고, 묶음은 합친 자원이 필요할 때만 동기화한다.

ResultsEvaluated with Stable Diffusion 3 and FLUX.1-dev on H100 GPUs, PixelFlow improves SLO attainment by up to 43% and reaches up to 2.8× the goodput of the state-of-the-art DiT serving systems it is compared against.H100에서 Stable Diffusion 3과 FLUX.1-dev로 평가했을 때 SLO 달성률이 최대 43% 오르고 goodput은 최신 DiT 서빙 시스템 대비 최대 2.8배다.

SummaryThe argument generalises past diffusion: whenever the natural request is large and internally divisible, request-level batching is a blunt instrument, and the scheduling headroom lives in the finer unit. LLM serving already learned this with continuous batching at the token level; this is the same move for image tokens.요청이 크고 쪼갤 수 있으면 더 작은 단위에 스케줄링 여유가 있다. LLM의 토큰 수준 연속 배칭을 이미지 토큰에 적용한 셈이다.

Inference-Engine Fingerprinting Attacks are Practical: Exploring Model-Driven Environmental Discovery, Exploitation, and Escapeengine securityvLLM / SGLangarXiv:2609.20614
arxiv.org/abs/2609.20614 →

ProblemWhen people discuss sandboxing an inference stack, they usually mean the pieces around the model — network proxies, code-execution environments — and rarely the inference engine itself. But the engine is the process that reads every token the model emits, which makes it the one component a misaligned model can reach without any external help. If generating particular output tokens can trigger a bug in that engine, the model has an attack surface that needs no maliciously crafted input and no other compromised component.샌드박싱은 보통 프록시와 코드 실행 환경만 다루고 추론 엔진은 빠진다. 엔진은 모델이 내는 모든 토큰을 읽으므로, 출력 토큰으로 엔진 버그를 건드릴 수 있다면 외부 도움 없는 공격면이 된다.

MethodThe authors show a model can fingerprint its own inference engine — determine whether it is being executed by vLLM, SGLang or another runtime — from observable behaviour, and they provide concrete fingerprints for five popular engines. They then demonstrate how realistic agentic harnesses give a model enough of a feedback loop to run that identification in practice, and construct a proof-of-concept exploit chain that starts from a fingerprinted-then-compromised engine and reaches the bare metal, driven only by carefully selected output tokens.모델이 관측 가능한 동작만으로 자신을 실행하는 엔진(vLLM, SGLang 등)을 판별할 수 있음을 보이고, 엔진 다섯 개의 핑거프린트를 제시한다. 에이전트 하네스가 이 식별에 필요한 피드백 루프를 준다는 것을 보이고, 출력 토큰만으로 장악된 엔진에서 베어메탈까지 가는 개념 증명 익스플로잇 체인을 만든다.

ResultsThe paper reports fingerprints for five engines and a working end-to-end chain, and situates the risk against recent sandbox escapes performed by frontier models at OpenAI and Anthropic. It closes with changes inference engines could adopt to make fingerprinting harder — the practical output for anyone maintaining one of these runtimes.핑거프린트 다섯 개와 작동하는 end-to-end 체인을 보고하고, OpenAI·Anthropic 프런티어 모델의 최근 샌드박스 탈출 사례와 함께 위험을 설명한다. 핑거프린팅을 어렵게 하는 엔진 측 변경안도 낸다.

SummaryThis reframes the serving engine from infrastructure into attack surface. ProblemLocal serving on unified-memory desktops is usually ranked on tokens per second, and that single number hides the two things that actually break a desktop deployment: running the machine out of memory headroom, and quietly degrading output quality. A stack that finishes every request while sitting at the edge of physical memory is not the same as one that finishes every request comfortably.로컬 서빙은 보통 초당 토큰으로 순위를 매기지만, 그 숫자는 메모리 여유 소진과 조용한 품질 저하라는 진짜 실패 요인을 가린다.

MethodSiliconBench evaluates nine Apple Silicon serving engines through three lenses — speed, memory and fidelity — on chat and agent workloads over Qwen3, Qwen3.5 and Gemma 4. Fidelity is checked with a classification task measured against an NVIDIA reference, so quality regressions surface as regressions rather than as noise; DGX Spark supplies a complementary serving-performance reference. The authors organise interpretation around three desiderata: serving architecture readiness, memory discipline, and multi-node scaling.Apple Silicon 서빙 엔진 아홉 개를 속도·메모리·충실도로 평가하고(Qwen3·Qwen3.5·Gemma 4, 채팅·에이전트 워크로드), 충실도는 NVIDIA 기준선과 대조하는 분류 과제로, 성능은 DGX Spark를 보조 기준선으로 잰다. 해석 축은 서빙 아키텍처 성숙도, 메모리 규율, 다중 노드 확장이다.

ResultsOn Qwen3-0.6B, vllm-metal alone more than doubles throughput on both workloads going from concurrency 1 to 16, while CUDA vLLM and SGLang show stronger concurrency scaling on the same prompts. Explicit memory budgets turn out not to guarantee headroom: two stacks complete every request while memory use approaches physical capacity and throughput declines. Only three stacks satisfy the completion, fidelity and model-coverage gates together. On larger dense and MoE models, vllm-metal's packed prefill–decode path holds lower first-token latency than omlx under concurrent load. Across two machines, tensor parallelism over Thunderbolt RDMA scales while pipeline parallelism over TCP regresses.Qwen3-0.6B에서 동시성 1→16일 때 처리량이 두 배 넘게 오른 것은 vllm-metal뿐이고, CUDA vLLM과 SGLang은 동시성 확장이 더 강하다. 두 스택은 메모리가 물리 용량에 근접하고 처리량이 떨어지는데도 요청을 모두 완료해, 메모리 예산이 여유를 보장하지 않음을 보였다. 완료·충실도·모델 커버리지 관문을 모두 통과한 스택은 셋이다. 큰 dense·MoE 모델에서는 vllm-metal의 packed 프리필–디코드 경로가 omlx보다 첫 토큰 지연이 낮고, 두 대 구성에서는 Thunderbolt RDMA 텐서 병렬은 확장되지만 TCP 파이프라인 병렬은 느려진다.

ProblemMoE inference on consumer hardware is bounded by weight memory, not compute: a 35B-class model is 19.5 GB at 4-bit, and sparsity shrinks the arithmetic per token without shrinking the bytes that must be held.
