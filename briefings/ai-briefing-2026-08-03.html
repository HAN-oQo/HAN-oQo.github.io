Problem문제 정의Serving systems routinely "replay" a reasoning stage by re-prefilling identical tokens and assuming the fresh prefill continues from the same decoder state as the retained live cache. This paper asks whether that assumption actually holds at a whole reasoning-stage boundary, since any hidden divergence would make cached and re-computed continuations silently differ.서빙 시스템은 동일한 토큰을 다시 프리필해 추론 단계를 "재생"하며, 새 프리필이 보존된 라이브 캐시와 같은 디코더 상태에서 이어진다고 가정한다. 이 논문은 그 가정이 추론 단계 경계에서 실제로 성립하는지 묻는다 — 숨은 발산이 있으면 캐시된 연속과 재계산된 연속이 조용히 달라지기 때문이다.
Method방법On a Qwen2.5-derived system, a matched 200-item experiment compares a retained live cache against a one-shot prefill of identical integer tokens, placing an exact replica on both sides. A fixed-prefix 2×2 holds all token states constant while crossing construction (live vs re-prefill) against precision (BF16 vs FP32), isolating precision as the variable.Qwen2.5 기반 시스템에서 200개 항목의 대응 실험이 보존된 라이브 캐시와 동일 정수 토큰의 일회 프리필을 비교하고, 양쪽에 정확한 복제본을 놓는다. 고정 프리픽스 2×2가 모든 토큰 상태를 고정한 채 구성(라이브 대 재프리필)과 정밀도(BF16 대 FP32)를 교차시켜 정밀도를 변수로 분리한다.
Results결과In BF16 the two constructions diverge on 166 of 200 suffixes and 20 correctness labels, while FP32 produces no decoded disagreement (95% Wilson upper bound 1.88%). Divergence tracks the KV cache and precision, not the tokens — so a bidirectional cache transplant is safe at FP32 but risky at BF16.BF16에선 두 구성이 200개 중 166개 접미사와 20개 정답 라벨에서 발산하지만, FP32에선 디코딩 불일치가 전혀 없다(95% Wilson 상한 1.88%). 발산은 토큰이 아니라 KV 캐시와 정밀도를 따르므로, 양방향 캐시 이식은 FP32에선 안전하지만 BF16에선 위험하다.
Summary요약Stage-replay and cache transplantation are exact in FP32 but silently diverge in BF16 — precision, not tokens, controls whether a re-prefilled KV cache matches the live one.단계 재생과 캐시 이식은 FP32에선 정확하지만 BF16에선 조용히 발산한다 — 재프리필된 KV 캐시가 라이브와 일치하는지는 토큰이 아니라 정밀도가 결정한다.

Problem문제 정의Sequence labeling — tagging every token with a label — is a fine-grained task, but decoder-only LLMs handle it by autoregressively generating a formatted string, which is slow and can drift out of alignment with the input tokens. Making an LLM do per-token labeling both efficiently and in exact alignment with the source is the open problem.시퀀스 라벨링 — 모든 토큰에 라벨을 붙이는 것 — 은 세밀한 과제지만, 디코더 전용 LLM은 형식화된 문자열을 자기회귀로 생성해 처리하므로 느리고 입력 토큰과의 정렬이 어긋날 수 있다. The economic upside of refactoring agent-written code Aug 1

Martin Fowler's site reports that incrementally refactoring an agent-written 17,155-line Rust data-access layer cut the input tokens needed for the same feature change from about 159,564 to roughly 27,000, even though total code size barely changed. The savings came from splitting related code into cohesive files so the agent could read only the minimal set needed; input tokens didn't drop much until the largest file was made small enough, ending with the data layer split across many files and the biggest file shrunk substantially. Output tokens and feature volume stayed about flat, and the agent couldn't reliably pick or execute the right refactorings on its own — active human guidance in planning and execution was required.

Martin Fowler의 사이트는 에이전트가 작성한 17,155줄 규모 Rust 데이터 접근 계층을 점진적으로 리팩터링하자 같은 기능 변경에 필요한 입력 토큰이 약 159,564개에서 대략 27,000개로 줄었다고 보고한다 — 전체 코드량은 거의 그대로였는데도. 절감은 관련 코드를 응집도 높은 파일로 분리해 에이전트가 필요한 최소 파일만 읽게 한 데서 왔고, 입력 토큰은 가장 큰 파일이 충분히 작아지기 전까진 크게 줄지 않았으며 최종적으로 데이터 계층을 여러 파일로 나누고 최대 파일 크기를 크게 줄였다. 출력 토큰과 기능 구현량은 거의 그대로였고, 에이전트는 적절한 리팩터링을 스스로 안정적으로 고르거나 수행하지 못해 계획·실행에 사람의 적극적 지침이 필요했다.
