AsymSpec: Context-Asymmetric Speculative Decoding for Agentic LLMsspeculative decodingcontext compressionarXiv:2608.26004
arxiv.org/abs/2608.26004 — submitted Aug 26 2026
Problem / 문제 정의 Agentic pipelines accumulate context across retrieval, tool calls and multi-turn dialogue, and the standard way to hold latency down is to compress the input — which costs accuracy. Speculative decoding is the other lever, and it is lossless, but it assumes the drafter and the verifier see exactly the same context. That assumption is why speculative decoding cannot help with the accuracy-versus-overhead trade-off at all: it speeds up whatever context you already decided to feed the model. 에이전트 파이프라인은 검색·도구 호출·다중 턴 대화를 거치며 문맥을 쌓고, 지연을 억누르는 표준적인 방법은 입력을 압축하는 것인데 그 대가는 정확도다. 다른 레버는 추측 디코딩이고 이쪽은 무손실이지만, 드래프터와 검증자가 정확히 같은 문맥을 본다고 전제한다. 바로 그 전제 때문에 추측 디코딩은 정확도-오버헤드 절충에 전혀 도움이 되지 않는다: 이미 넣기로 정한 문맥을 빠르게 돌릴 뿐이다.
Method / 방법 AsymSpec breaks the symmetry deliberately: the lightweight drafter reads the full input, while the large verifier operates on the compressed view. The drafter steers the verifier through a contrastive δ-fusion of logits, so the information the verifier never saw enters as a correction term rather than as extra context. A divergence-aware acceptance gate modulates that fusion, which is what keeps verification stable and draft acceptance high when the two views disagree. AsymSpec은 그 대칭을 일부러 깬다: 가벼운 드래프터가 전체 입력을 읽고, 큰 검증자는 압축된 뷰에서 동작한다. 드래프터는 로짓의 대조적 δ-융합으로 검증자를 조향하므로, 검증자가 본 적 없는 정보가 추가 문맥이 아니라 보정항으로 들어온다. 발산 인식 수용 게이트가 그 융합을 조절하는데, 두 뷰가 어긋날 때 검증 안정성과 높은 초안 수용률을 지켜 주는 것이 이 부분이다.
Results / 결과 Evaluated across four agentic capabilities and two end-to-end agent benchmarks, AsymSpec reaches approximately 90% of full-context accuracy on average. On isolated text capabilities it reports 1.3–1.7x throughput speedups at 0.2–0.3x the compute cost. The paper's own reading of the pattern is that the gains concentrate exactly where compression was throwing away reasoning signal. 에이전트 역량 네 가지와 종단 에이전트 벤치마크 두 종에서 평가했을 때 AsymSpec은 평균적으로 전체 문맥 정확도의 약 90%에 도달한다. 격리된 텍스트 역량에서는 계산 비용 0.2~0.3배에 처리량 1.3~1.7배 향상을 보고한다. 논문 자신의 해석은, 이득이 압축이 추론 신호를 버리고 있던 바로 그 지점에 집중된다는 것이다.
Summary / 요약 The reframing is what to take away: context compression and speculative decoding have always been treated as two separate knobs on the same pipeline, and this makes them one mechanism by giving the cheap model the expensive view. Whether the δ-fusion holds up when the compressor is aggressive is the open question, and the acceptance gate is the part doing that work. 가져갈 것은 관점의 재구성이다: 문맥 압축과 추측 디코딩은 늘 같은 파이프라인의 서로 다른 손잡이로 다뤄져 왔는데, 여기서는 싼 모델에게 비싼 뷰를 줌으로써 둘을 하나의 메커니즘으로 만든다. 압축기가 공격적일 때도 δ-융합이 버티는지가 열린 질문이고, 그 일을 하는 부품이 수용 게이트다.

Problem / 문제 정의 In multi-agent serving, every agent carries a long system prompt, and keeping its KV cache resident makes that agent's next call cheap. Problem / 문제 정의 MoE keeps per-token compute bounded by activating only a few experts, but low-latency serving spans two phases with different bottlenecks. Prefill is dominated by the token-wise expert computation; decode is constrained by memory traffic from the set of experts the whole batch activates. Training-free acceleration methods optimize one proxy or the other — experts per token, or experts per batch — and then either discard the excluded experts' contribution outright or approximate it only implicitly. MoE는 소수의 전문가만 활성화해 토큰당 계산을 묶어 두지만, 저지연 서빙은 병목이 서로 다른 두 단계를 가로지른다. 프리필은 토큰별 전문가 계산이 지배하고, 디코드는 배치 전체가 활성화하는 전문가 집합에서 오는 메모리 트래픽에 묶인다. 학습 불필요 가속 기법들은 둘 중 한 대리 지표만 최적화하고 — 토큰당 전문가냐 배치당 전문가냐 — 제외된 전문가의 기여를 아예 버리거나 암묵적으로만 근사한다.
Method / 방법 ExFold casts both phases as one budgeted output-approximation problem: run only a phase-specific constrained expert set, and project the contribution of budget-excluded experts onto the retained ones using calibrated scalar projectors. Under this view prefill acceleration is token-level Top-K folding and decode acceleration is batch-level expert-pool folding; the phases differ only in how retained experts are chosen. ExFold는 두 단계를 하나의 예산 제약 출력 근사 문제로 놓는다: 단계별로 제한된 전문가 집합만 실행하고, 예산에서 제외된 전문가의 기여를 보정된 스칼라 투영자로 남은 전문가들에 투영한다. 출발점이 된 관찰은 많은 전문가 출력이 방향은 정렬돼 있고 크기만 다르다는 것이라, 레이블 없는 데이터로 보정한 쌍별 스칼라 투영자 행렬로 추론 시점에 제외 전문가를 남은 전문가에 접어 넣을 수 있다. 이 관점에서 프리필 가속은 토큰 수준 Top-K 접기이고 디코드 가속은 배치 수준 전문가 풀 접기이며, 두 단계는 남길 전문가를 고르는 방식만 다르다.

Summary / 요약 The elegance is in the single mechanism serving two phases: one calibrated projector matrix, two different ways of choosing what survives the budget. Problem / 문제 정의 Multi-agent workflows solve open-ended tasks by having specialized agents reason together, and they pay for it with repeated model invocations and context that keeps growing across a long horizon. Cascade routing is the standard cost control, but it makes a one-shot, query-level decision: pick a model for the whole query and live with it. That cannot adapt to a multi-step workflow, where the right model at each step depends on how far the task has already got, how hard the remainder is, and what budget is left. 다중 에이전트 워크플로는 특화된 에이전트들이 함께 추론하게 해 열린 과제를 풀고, 그 대가로 반복되는 모델 호출과 긴 지평에서 계속 불어나는 문맥을 치른다. 표준적인 비용 통제는 캐스케이드 라우팅이지만, 이는 질의 수준의 일회성 결정이다: 질의 전체에 대해 모델 하나를 고르고 그대로 간다. 각 단계에서 알맞은 모델이 과제가 이미 얼마나 진행됐는지, 남은 부분이 얼마나 어려운지, 예산이 얼마나 남았는지에 달린 다단계 워크플로에는 맞출 수 없다.

A dual-path progress predictor and an adaptive meta-gating mechanism then estimate the progress gain each candidate model would deliver from that state, and the router picks online by balancing that gain against time budget and long-term operating cost. Cursor's write-up starts from why Git is hard to host at scale: objects are stored as deltas inside packfiles that are not laid out in DAG order, so following a commit to a tree to a blob turns into random access, which collapses on network filesystems and remote object stores. GitHub's Spokes answered that by keeping real repositories on local NVMe and synchronizing replicas with three-phase commit, but that shape is wrong at both ends — too few replicas for a huge monorepo, three replicas too many for an enormous number of tiny repositories. Continuity makes a write-ahead log in S3 the source of truth and treats the local repository as a cache that can be rebuilt at any time: a push succeeds only once it is fully in the WAL, S3's compare-and-swap serializes writers, and a replica checks the WAL state just before reading, so it gets a consistent view without a consensus protocol. The stated goal is to scale in both directions at once — hundreds of replicas for a monorepo, one or zero warm replicas for the many small repositories that agents create. Cursor의 글은 Git을 대규모로 호스팅하기 어려운 이유에서 출발한다: 객체는 DAG 순서로 배치되지 않은 packfile 안에 delta로 저장되므로, 커밋에서 트리로 blob으로 따라가는 일이 랜덤 접근이 되고, 이는 네트워크 파일시스템과 원격 객체 저장소에서 무너진다.
