RoPE from scratch — rotary position embedding, derived RoPE 처음부터: 회전으로 위치를 심는 법

RoPE gives attention word order by rotating each query and key by an angle proportional to its position, instead of adding a position vector. This note derives it from the design goal (RoFormer), follows it into vLLM's kernels, and ends with why it matters for KV-cache reuse. RoPE는 위치 벡터를 더하는 대신 query와 key를 위치에 비례한 각도만큼 회전시켜 어텐션에 어순을 알려 준다. 설계 목표에서 출발해 유도하고(RoFormer), vLLM 커널까지 따라간 뒤, KV 캐시 재사용에서 이것이 왜 중요한지로 끝맺는다.

one-line summary한 줄 요약
  • Multiply each query and key by e^(i·position·θ), i.e. rotate it by an angle proportional to its position.
  • In the inner product the absolute positions cancel and leave only their difference, because R(a)ᵀR(b) = R(b−a).
  • The 128-dim head is split into 64 pairs with different speeds: fast pairs resolve neighbouring tokens, slow pairs carry document-scale position.
  • Rotations are orthogonal, so stripping RoPE off a cached key is exact and free.
  • query와 key에 e^(i·위치·θ)를 곱한다. 위치에 비례한 각도만큼 회전시키는 것이다.
  • 내적에서 두 절대 위치가 상쇄되고 차이만 남는다. R(a)ᵀR(b) = R(b−a)이기 때문이다.
  • 128차원 head를 속도가 다른 2차원 쌍 64개로 나눈다. 빠른 쌍은 옆 토큰 순서를, 느린 쌍은 문서 규모의 위치를 담는다.
  • 회전은 직교 변환이라 캐시된 key에서 RoPE를 벗겨내는 일이 정확하고 비용도 거의 없다.

📖 Query · Key · Value📖 Query · Key · Value

Each token makes a query (what it looks for), key (what it offers) and value (what it hands over). Query·key inner products weight the values.토큰마다 query(찾는 것), key(내놓는 것), value(넘겨줄 것)를 만든다. query·key 내적이 value의 가중치가 된다.

📖 Absolute vs relative position📖 절대 위치 vs 상대 위치

Absolute: "token #7". Relative: "4 places before that one". Attention mostly wants the second.절대는 "7번째 토큰", 상대는 "저 토큰보다 4칸 앞"이다. 어텐션이 주로 원하는 건 후자다.

📖 Orthogonal matrix📖 직교행렬

Transpose = inverse (RᵀR = I). It rotates or reflects but never stretches, so undoing it is free.전치가 곧 역행렬인 행렬이다(RᵀR = I). 돌리거나 뒤집을 뿐 늘이지 않으니 되돌리기도 공짜다.

📖 Wavelength📖 파장

A pair turning θ per token repeats every 2π/θ tokens: the distance scale it can resolve.토큰당 θ씩 도는 쌍은 2π/θ 토큰마다 한 바퀴를 돈다. 그 쌍이 구별할 수 있는 거리 단위다.

📖 KV cache📖 KV 캐시

Stored keys and values of the prompt. Keys are stored already rotated; queries are rotated fresh each decode step.프롬프트의 key와 value를 저장해 둔 것이다. key는 회전된 채로 저장되고, query는 디코드 스텝마다 새로 회전된다.

📖 Why you'd want to strip it📖 왜 벗겨내고 싶은가

A stored key mixes meaning with position. Cross-model mapping or re-indexing must separate them first (§7).저장된 key에는 의미와 자리가 섞여 있다. 모델 간 매핑이나 재색인은 둘을 먼저 떼어내야 한다(§7).

1 Attention cannot see word order 어텐션은 어순을 볼 수 없다

Strip attention down to its scoring step and this is all there is:

어텐션의 채점 단계만 남기면 이게 전부다.

score(m, n) = qm · kn

There is no m or n on the right. The score depends only on the two vectors' contents, so shuffling the tokens just relabels the same scores. Attention is permutation-equivariant: it has no idea which word came first.

우변에 m도 n도 없다. 점수는 두 벡터의 내용에만 달려 있어서, 토큰 순서를 섞어도 같은 점수가 이름표만 바뀌어 나온다. 어텐션은 순열 등변(permutation-equivariant)이다. 어느 단어가 먼저 왔는지 모른다는 뜻이다.

the concrete failure구체적인 실패 "The cat chased the mouse" and "The mouse chased the cat" have the same tokens, so bare attention scores them identically. Every transformer needs some way to inject position. "고양이가 쥐를 쫓았다"와 "쥐가 고양이를 쫓았다"는 토큰이 같아서, 위치 정보 없는 어텐션은 둘을 똑같이 채점한다. 그래서 모든 트랜스포머는 위치를 넣는 장치가 따로 필요하다.

1.1 — Why the obvious fix isn't the one that stuck 1.1 왜 가장 뻔한 해법이 살아남지 못했나

The original transformer's answer was absolute: build a vector p_m that encodes "position m" and add it to the token embedding before the projections.

원래 트랜스포머는 절대 위치를 썼다. "위치 m"을 나타내는 벡터 p_m을 projection 전에 토큰 임베딩에 더한다.

qm = Wq(xm + pm), kn = Wk(xn + pn)

This works, but when a head decides how much token 7 attends to token 3, it usually wants "how far apart are they", not "one is the 7th". Absolute tags force the model to infer distance, and say nothing about positions longer than training.

작동은 한다. 하지만 7번 토큰이 3번 토큰을 얼마나 볼지 정할 때 head가 알고 싶은 건 보통 "둘이 얼마나 떨어져 있나"다. 절대 태그로는 모델이 거리를 거꾸로 추론해야 하고, 학습 때보다 긴 위치에서는 어떻게 동작할지 보장이 없다.

RoPE asks a sharper question: can we inject absolute position into each vector separately so that only the relative position survives the inner product?

그래서 RoPE는 이렇게 묻는다. 벡터마다 절대 위치를 따로 심되, 내적을 거치면 상대 위치만 남게 할 수 있을까?

The original transformer's sinusoidal encoding sits in the same place as A: the table is fixed sin/cos instead of learned, but it is still added at the input. RoPE moves the position code from "one add at the bottom" to "one rotation in every layer", and the rest of this note explains why that move makes only m − n survive.

원래 트랜스포머의 sinusoidal 인코딩도 A와 같은 자리에 들어간다. 테이블이 학습값이 아닌 고정 sin/cos일 뿐 여전히 입력에서 더한다. RoPE는 위치 코드를 "맨 아래에서 한 번 더하기"에서 "모든 레이어에서 한 번씩 회전하기"로 옮긴 것이다. 이 노트의 나머지 부분은 그렇게 옮기면 왜 m − n만 남는지를 설명한다.

1.3 — Complex numbers in five minutes: what e^(imθ) means 1.3 5분 복소수 복습: e^(imθ)는 무엇인가

From §2 on, the derivation is written with complex numbers. You only need four facts, and all of them are pictures on a plane.

§2부터는 유도를 복소수로 쓴다. 필요한 사실은 네 가지뿐이고, 전부 평면 위의 그림으로 이해할 수 있다.

fact 1 · a complex number is a 2-D point사실 1 · 복소수는 평면 위의 점이다

a + bi is just the point (a, b): real part on the x-axis, imaginary part on the y-axis. The only new rule is i² = −1. Like any 2-D arrow it has a length r and an angle φ.

a + bi는 점 (a, b)와 같다. 실수부는 x축, 허수부는 y축에 놓는다. 새로 생기는 규칙은 i² = −1 하나뿐이다. 평면 위의 화살표이므로 길이 r과 각도 φ를 가진다.

a + bi = r(cos φ + i sin φ)
r = √(a² + b²) is the length, φ the angle
fact 2 · Euler's formula: e^(iφ) is a name for "unit arrow at angle φ"사실 2 · 오일러 공식: e^(iφ)는 "각도 φ인 길이 1 화살표"의 이름이다
eiφ = cos φ + i sin φ

Don't read it as "e raised to a power". Read it as the point on the unit circle at angle φ: x = cos φ, y = sin φ, length 1. So e^(i·0) = 1, e^(i·90°) = i, e^(i·180°) = −1.

"e의 거듭제곱"으로 읽지 않아도 된다. 단위원 위에서 각도가 φ인 점이라고 읽으면 된다. x = cos φ, y = sin φ이고 길이는 1이다. 그래서 e^(i·0) = 1, e^(i·90°) = i, e^(i·180°) = −1이다.

fact 3 · multiplying = multiply lengths, ADD angles사실 3 · 곱셈은 길이를 곱하고 각도를 더한다
eiα · eiβ = ei(α + β)
z · eiφ = z rotated by φ

Since e^(iφ) has length 1, multiplying by it changes nothing but the angle: it is a pure rotation. Example: i = e^(i·90°), and (3 + 4i)·i = 3i + 4i² = −4 + 3i, which is (3, 4) turned 90° counter-clockwise.

e^(iφ)는 길이가 1이므로 곱해도 각도만 바뀐다. 즉 순수한 회전이다. 예를 들어 i = e^(i·90°)이고, (3 + 4i)·i = 3i + 4i² = −4 + 3i다. 점 (3, 4)를 반시계 방향으로 90° 돌린 결과와 같다.

fact 4 · the conjugate mirrors, so it flips the angle's sign사실 4 · 켤레는 거울에 비추듯 각도 부호를 뒤집는다
conj(a + bi) = a − bi
conj(eiφ) = e−iφ

Reflect across the x-axis. This is where the minus sign in m − n will come from (§3, step 2).

x축을 기준으로 뒤집는 연산이다. 나중에 m − n의 빼기 부호가 바로 여기서 나온다(§3의 2단계).

so what is e^(imθ)?그래서 e^(imθ)는? θ is a fixed small angle per token, m is the token's position. e^(imθ) is the unit arrow at angle m·θ: "turn θ once per position step". With θ = 10°: token 0 → 0°, token 1 → 10°, token 3 → 30°. Multiplying a query by it rotates the query by mθ (fact 3). The inner product then pulls in a conjugate, which turns +nθ into −nθ (fact 4), and the angles add to (m−n)θ. That is the whole trick of §2–§3. θ는 토큰 하나당 도는 작은 고정 각도이고, m은 토큰의 위치다. e^(imθ)는 각도가 m·θ인 단위 화살표, 즉 "위치가 한 칸 늘 때마다 θ씩 돈다"는 뜻이다. θ = 10°라면 0번 토큰은 0°, 1번은 10°, 3번은 30°가 된다. query에 이것을 곱하면 query가 mθ만큼 회전한다(사실 3). 내적을 계산할 때 켤레가 끼어들어 +nθ를 −nθ로 바꾸고(사실 4), 두 각도가 더해져 (m−n)θ가 된다. §2와 §3의 핵심이 이것뿐이다.

2 The design goal, in one equation 설계 목표를 수식 한 줄로

We want one function that injects position into a query and one for a key, whose inner product keeps only the gap:

query에 위치를 심는 함수와 key에 위치를 심는 함수가 필요하다. 조건은 둘의 내적에 간격만 남는 것이다.

⟨ fq(x, m) , fk(y, n) ⟩ = g( x, y, m − n )
absolute position goes in on the left · only the difference comes out on the right

On the left, m and n enter separately: a key is computed and cached without knowing which query will read it. On the right they may appear only as m − n. The absolute information must cancel inside the inner product.

왼쪽에서 m과 n은 따로 들어간다. key는 나중에 어느 query가 읽을지 모른 채 계산돼 캐시에 들어가기 때문이다. 오른쪽에는 m − n 꼴로만 나와야 한다. 절대 위치가 내적 안에서 지워져야 한다.

why addition cannot do this덧셈으로는 안 되는 이유 Expand the inner product for f(x, m) = q + p_m:
⟨q + p_m, k + p_n⟩ = q·k + q·p_n + p_m·k + p_m·p_n
The middle terms depend on n alone and m alone, so nothing collapses into m − n. We need an operation where the position factors meet. f(x, m) = q + p_m로 내적을 전개하면 이렇다.
⟨q + p_m, k + p_n⟩ = q·k + q·p_n + p_m·k + p_m·p_n
가운데 두 항은 n만, m만 담고 있어서 m − n으로 합쳐질 수 없다. 두 위치 인자가 만나는 연산이 필요하다.

Fig 2 · Adding vs multiplying position. Drawn by the author.그림 2 · 위치를 더할 때와 곱할 때. 직접 그림.

An inner product multiplies its arguments, so if position enters multiplicatively, e^(im·) × e^(−in·) collapses to e^(i(m−n)·) for free.

내적은 두 인자를 곱한다. 그러니 위치를 곱셈으로 넣으면 e^(im·) × e^(−in·)가 저절로 e^(i(m−n)·)로 합쳐진다.

3 Solving it in 2D — multiply, don't add 2차원에서 풀기: 더하지 말고 곱한다

Start with d = 2 and treat a 2-vector as a single complex number, (a, b) ↔ a + bi. Complex multiplication is then rotation.

d = 2에서 시작한다. 2차원 벡터를 (a, b) ↔ a + bi처럼 복소수 하나로 보면, 복소수 곱셈이 곧 회전이 된다.

step 1 · the guess1단계 · 시도

Let q = W_q x and k = W_k y be complex. Multiply by a unit-modulus number whose angle is proportional to position:

q = W_q x, k = W_k y를 복소수로 두고, 위치에 비례한 각도를 가진 크기 1짜리 복소수를 곱한다.

fq(x, m) = q · eimθ fk(y, n) = k · einθ

The factor has modulus 1, so length is unchanged: position is encoded purely as direction.

곱하는 수의 크기가 1이라 길이는 그대로다. 위치는 오직 방향으로만 담긴다.

Check with u = a + bi, v = c + di:

The real part ac + bd is the dot product of (a,b) and (c,d). ✓ The conjugate flips the sign of the second vector's angle, which is the subtraction we want.

실수부 ac + bd가 (a,b)와 (c,d)의 내적이다. ✓ 켤레(conjugate)는 두 번째 벡터의 각도 부호를 뒤집는다. 바라던 뺄셈이 여기서 나온다.

why flip the sign at all?왜 굳이 부호를 뒤집나? Without the conjugate, the product is not the dot product. Three ways to see it: 켤레 없이 그냥 곱하면 내적이 나오지 않기 때문이다. 세 가지 방향에서 확인할 수 있다.
  • Algebra. Plain product: (a+bi)(c+di) = (ac − bd) + i(ad + bc). Its real part is ac − bd, the wrong sign. With the conjugate it becomes ac + bd.
  • Geometry. The dot product depends on the angle between the vectors, u·v = |u||v| cos(α − β), a difference. Multiplication adds angles (§1.3 fact 3), so u·v would land at α + β. Conjugating v turns β into −β, and the product lands at α − β.
  • Sanity check. A vector dotted with itself is its squared length. For u = i: i·i = −1 ✗, but i·conj(i) = i·(−i) = 1 ✓.
  • 대수로 보면 그냥 곱한 (a+bi)(c+di) = (ac − bd) + i(ad + bc)의 실수부는 ac − bd라서 부호가 틀린다. 켤레를 쓰면 ac + bd가 된다.
  • 기하로 보면 내적은 두 벡터 사이의 각도에 달려 있다. u·v = |u||v| cos(α − β)처럼 각도의 차이가 필요하다. 그런데 곱셈은 각도를 더하므로(§1.3 사실 3) 그냥 곱하면 α + β가 된다. v에 켤레를 취하면 β가 −β로 바뀌어 곱의 각도가 α − β가 된다.
  • 검산하면 자기 자신과의 내적은 길이의 제곱이어야 한다. u = i일 때 i·i = −1은 틀리고, i·conj(i) = i·(−i) = 1은 맞다.
So RoPE does not add the conjugate on purpose: it is already inside any dot product written in complex form. RoPE simply exploits it, because it is what turns the key's +nθ into −nθ. 즉 켤레는 RoPE가 일부러 넣은 장치가 아니다. 보통의 내적을 복소수로 쓰면 원래 들어 있는 것이다. RoPE는 이 켤레가 key의 +nθ를 −nθ로 바꿔 준다는 점을 이용할 뿐이다.

slowly: what j, θ_j and the wavelength mean천천히: j, θ_j, 파장이 각각 무엇인가
  • j is "which pair", not a position. The 128 dims are cut into 64 pairs numbered j = 0…63 (in Llama's half-split, pair j = dims j and j+64). Position is m; j never changes with the token.
  • θ_j is how far pair j turns per token, in radians (2π rad = 360°, 1 rad ≈ 57°). At position m, pair j sits at angle m·θ_j. The exponent −2j/d = −j/64 runs from 0 to almost −1, so θ goes from 10000⁰ = 1 rad down to about 1/10000 rad: pair 0 is fastest, pair 63 slowest.
  • Wavelength λ_j = 2π/θ_j is "tokens until this pair comes back to the same direction". One full turn is 2π rad, and each token adds θ_j, so it takes 2π/θ_j tokens. So for this pair, two tokens λ apart look exactly like two tokens 0 apart: it has wrapped.
  • j는 "몇 번째 쌍인가"이고 위치가 아니다. 128개 차원을 64개 쌍으로 잘라 j = 0…63으로 번호를 붙인 것이다(Llama의 half-split에서는 쌍 j = 차원 j와 j+64). 위치는 m이고, j는 토큰이 바뀌어도 변하지 않는다.
  • θ_j는 쌍 j가 토큰 하나마다 도는 각도이고 단위는 라디안이다(2π rad = 360°, 1 rad ≈ 57°). 위치 m에서 쌍 j의 각도는 m·θ_j다. 지수 −2j/d = −j/64는 0에서 거의 −1까지 내려가므로, θ는 10000⁰ = 1 rad에서 약 1/10000 rad까지 작아진다. 쌍 0이 가장 빠르고 쌍 63이 가장 느리다.
  • 파장 λ_j = 2π/θ_j는 "이 쌍이 같은 방향으로 돌아올 때까지 걸리는 토큰 수"다. 한 바퀴가 2π rad이고 토큰마다 θ_j씩 더해지므로 2π/θ_j 토큰이 걸린다. 그래서 이 쌍에서는 λ칸 떨어진 두 토큰이 0칸 떨어진 것과 똑같이 보인다. 한 바퀴를 돌아 제자리에 왔기 때문이다.

5.2 — Why long-context models raise the base 5.2 긴 컨텍스트 모델이 base를 올리는 이유

With base = 10,000 the slowest wavelength is ~54K tokens; beyond that even the slowest hand wraps and "near the start" looks like "near the end". The remedy is to raise the base, slowing every pair. Llama 3 uses base = 500,000 (Llama 3 paper, §3.1), stretching it to roughly 2.5M tokens.

base = 10,000이면 가장 느린 파장이 약 54K 토큰이다. 컨텍스트가 그보다 길면 가장 느린 바늘도 한 바퀴를 넘어 "앞쪽"과 "뒤쪽"을 구별하지 못한다. 처방은 base를 키워 모든 쌍을 느리게 하는 것이다. Llama 3는 base = 500,000을 쓰고 (Llama 3 논문 §3.1), 가장 느린 파장은 약 250만 토큰이 된다.

So two models in one family can disagree about the angle of position 5,000, which is why §7 maps in a position-free space.

그래서 같은 패밀리의 두 모델도 5,000번 위치의 각도가 서로 다를 수 있다. §7에서 위치 없는 공간에서 매핑하는 이유다.

6 What the kernels actually compute 커널이 실제로 계산하는 것

Nobody materializes R_Θ(m): of its 16,384 entries only 256 are nonzero (1.6%), so a full matmul wastes 98% of the FLOPs. The rotation becomes two elementwise multiplies and one add.

R_Θ(m)를 행렬로 만들어 쓰지는 않는다. 성분 16,384개 중 0이 아닌 것은 256개(1.6%)뿐이라 통째로 곱하면 FLOP의 98%가 0에 낭비된다. 대신 원소별 곱 두 번과 덧셈 한 번으로 계산한다.

Under half-split (pair i = dims i, i+64), define a helper that swaps the halves and negates one:

half-split(쌍 i = 차원 i, i+64)에서 두 절반을 맞바꾸고 한쪽 부호를 뒤집는 헬퍼를 쓴다.

rotate_half(x) = [ −x64…127 , x0…63 ]

RoPE(x, m) = x ⊙ cos(mΘ) + rotate_half(x) ⊙ sin(mΘ)

cos(mΘ) holds each of the 64 cosines twice. Dimensions i and i+64 get:

cos(mΘ)는 코사인 64개를 두 번씩 담은 128차원 벡터다. 차원 i와 i+64에는 이렇게 들어간다.

dim i : x_i · cos(mθ_i) + (−x_i+64) · sin(mθ_i) = x_i cos − x_i+64 sin dim i+64 : x_i+64 · cos(mθ_i) + ( x_i ) · sin(mθ_i) = x_i+64 cos + x_i sin

This matches §4's R(mθ)·[a; b] = [a cos − b sin ; a sin + b cos] with a = x_i, b = x_{i+64}. ✓ Not an approximation: the same operation, skipping the zeros.

§4의 R(mθ)·[a; b] = [a cos − b sin ; a sin + b cos]에 a = x_i, b = x_{i+64}를 넣은 것과 같다. ✓ 근사가 아니라 0을 건너뛴 같은 연산이다.

# the whole thing, once per layer per forward pass
# --- precomputed once at load, cached for all positions ---
inv_freq = base ** (-torch.arange(0, d, 2).float() / d)   # 64 values: theta_0 .. theta_63
angles   = torch.outer(positions, inv_freq)                # [T, 64]
emb      = torch.cat([angles, angles], dim=-1)             # [T, 128] each theta twice
cos, sin = emb.cos(), emb.sin()                            # lookup tables

# --- per forward pass ---
def rotate_half(x):
    x1, x2 = x[..., : d // 2], x[..., d // 2 :]
    return torch.cat([-x2, x1], dim=-1)

q = q * cos + rotate_half(q) * sin      # queries: recomputed every decode step
k = k * cos + rotate_half(k) * sin      # keys: rotated ONCE, then cached this way
# v is never touched — values carry no positional encoding

Cost비용

O(d), not O(d²): 256 multiply-adds per vector instead of 16,384. cos/sin tables are built once and indexed by position.O(d²)가 아니라 O(d)다. 벡터당 16,384번 대신 256번 곱셈-덧셈을 한다. cos/sin 테이블은 로드 때 한 번 만들고 위치로 찾아 쓴다.

How 6.2's steps map onto the kernel (nothing is allocated):

  • Step 1 (index_select): a pointer offset.
  • Steps 3–6 (view, split, chunk, unsqueeze): index arithmetic. i / embed_dim is the head, i % embed_dim the pair; every head reading the same cos_ptr[rot_offset] is the broadcast.
  • Steps 7–9 (rotate, cat, reshape): two stores back into the original slots.

  • 3–6단계(view, 분리, chunk, unsqueeze): 인덱스 계산. i / embed_dim이 head, i % embed_dim이 쌍이고, 모든 head가 같은 cos_ptr[rot_offset]을 읽는 것이 곧 broadcast다.

7 Why this matters for KV-cache reuse KV 캐시 재사용에서 왜 중요한가

This section connects to the cross-model KV cache transfer paper, whose §3.3 is about RoPE handling.

이 절은 cross-model KV cache transfer 논문과 이어진다. 그 논문의 §3.3이 RoPE 처리를 다룬다.

7.1 — The cache holds meaning entangled with position 7.1 캐시에는 의미와 위치가 엉켜 있다

kcached(t) = RΘ(t) · kcontent ← stored, position baked in
q(t) = RΘ(t) · qcontent ← recomputed each step, never stored
vcached(t) = vcontent ← no rotation at all

Any meaning-level operation on a cached key (mapping to another model, re-indexing, splicing caches) acts on something with position welded on. Step one is separating them.

캐시된 key로 의미 수준의 작업(다른 모델로 매핑, 재색인, 캐시 이어 붙이기)을 하려면 위치가 붙어 있는 값을 다뤄야 한다. 그래서 먼저 둘을 떼어내야 한다.

7.2 — Separating them is exact, and free 7.2 분리는 정확하고, 공짜다

By §4's fact 2, R_Θ's inverse is its transpose: no pseudo-inverse or least-squares. Undoing it is the same O(d) op with the sign of sin flipped.

§4의 사실 2에 따라 R_Θ의 역행렬은 전치다. 유사역행렬도 최소제곱 근사도 필요 없다. 되돌리기는 sin 부호만 뒤집은 같은 O(d) 연산이다.

"Since RΘ is orthogonal, the inversion is exact at negligible cost. Values carry no positional encoding and are mapped directly."

— Heo et al., §3.3 · 원문 보기 (§3.3)

The paper's pipeline: strip the source's rotation, map in content space, re-apply the target's rotation.

논문의 파이프라인은 소스 회전을 벗기고, content space에서 매핑한 뒤, 타깃 회전을 다시 입히는 순서다.

K̂t = ( Ks · RΘs−1(t) · WK + bK ) · RΘt(t)

R_Θs⁻¹ un-rotates, W_K maps meaning, R_Θt re-rotates with the receiver's base. W_K never sees an angle.

R_Θs⁻¹이 회전을 풀고, W_K가 의미를 옮기고, R_Θt가 받는 모델의 base로 다시 돌린다. W_K는 각도를 보지 않는다.

7.3 — Why a fit on rotated keys refuses to extrapolate 7.3 회전된 key로 피팅하면 왜 외삽이 안 되는가

Fitting on RoPE-coupled keys works fine on the paper's benchmarks, within noise of the decoupled pipeline. The objection is structural, not empirical:

RoPE가 붙은 key로 피팅해도 논문의 벤치마크에서는 잘 된다. 분리형과 노이즈 범위 안에서 같다. 반론은 실험이 아니라 구조에서 나온다.

"Fitting the mapper directly on RoPE-coupled keys also works within noise on short-context benchmarks (Table 2), but ties the weights to the 1024-token position distribution seen at fit. The decoupled formulation extends to longer contexts by construction, which matters for serving prompts up to 32k tokens."

— Heo et al., §3.3, ¶2 · 원문 보기 (§3.3)

§5 makes this quantitative. Calibration uses 1,024-token sequences; after t tokens pair j sits at angle t·θ_j. How much of its circle does each pair visit?

§5의 표로 이를 수치화할 수 있다. 캘리브레이션은 1,024 토큰 시퀀스를 쓰고, t토큰 뒤 쌍 j의 각도는 t·θ_j다. 각 쌍이 그동안 원을 얼마나 도는지 보자.

editor's note — my computation, not the paper's편집자 주: 논문이 아니라 내 계산
  1. The paper states the conclusion without deriving it; the arc arithmetic is mine.
  2. A pair completes a full turn in 1,024 tokens iff 1024·θ_j ≥ 2π, i.e. θ_j ≥ 0.00614, i.e. j ≤ 35. So 28 of the 64 pairs see only a partial arc during calibration, and those are the pairs whose angles move into unseen territory at long context.
  3. This also explains why the paper's ablation finds the coupled variant harmless: its accuracy benchmarks are short-context. The predicted failure would appear at 8K–32K, measured for latency but not accuracy.
  1. 논문은 결론만 적고 유도하지 않는다. 호(arc) 계산은 내 것이다.
  2. 1,024토큰 안에 한 바퀴를 다 도는 조건은 1024·θ_j ≥ 2π, 즉 θ_j ≥ 0.00614, 즉 j ≤ 35다. 따라서 64개 쌍 중 28개는 캘리브레이션 동안 원의 일부만 본다. 컨텍스트가 길어지면 이 쌍들의 각도가 본 적 없는 영역으로 넘어간다.
  3. 논문의 ablation이 결합형을 무해하다고 본 이유도 이것으로 설명된다. 정확도 벤치마크가 짧은 컨텍스트였다. 예상되는 실패는 8K~32K에서 드러날 텐데, 그 구간은 지연만 쟀고 정확도는 재지 않았다.

7.4 — The two things content-space mapping buys 7.4 content-space 매핑이 사주는 두 가지

① Length independence① 길이 독립성

Fit on 1K, serve 32K. The weights never saw position, so it holds "by construction", not by measurement.1K로 피팅하고 32K를 서빙한다. 가중치가 위치를 본 적이 없으니 "구조적으로(by construction)" 성립한다.

② Config independence② 설정 독립성

Base 10,000 vs 500,000 (§5.2) doesn't matter: strip with the source's base, re-apply with the target's. A content-space W is indifferent.base 10,000과 500,000의 차이(§5.2)는 상관없다. 소스 base로 벗기고 타깃 base로 입히면 content-space W는 그대로다.

where else this shows up이 성질이 또 등장하는 곳 Strip-and-re-apply is needed by anything that moves a cached key to a new position: re-indexing after prefix eviction, splicing separately prefilled caches, prompt-cache reuse at a different offset. Each is well-defined only on k_content, which orthogonality reaches losslessly. (Editor's note: a generalization, not a claim from the paper.) 캐시된 key를 다른 위치로 옮기는 작업은 모두 벗기고 다시 입히기가 필요하다. prefix evict 뒤 재색인, 따로 prefill한 캐시 이어 붙이기, 블록을 다른 offset에서 재사용하는 prompt-cache가 그렇다. 모두 k_content에서만 제대로 정의되고, 직교성 덕분에 손실 없이 거기 닿는다.
